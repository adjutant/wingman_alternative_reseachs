TinyAGI assessment against Wingman

  • Repository: https://github.com/TinyAGI/tinyagi
  • Local checkout: research/tinyagi/repo
  • Assessed commit: 2db3a03a891b302c460f624d6c5a0523b8aa3528
  • Assessment date: 2026-11-05
  • Product at this revision: TinyAGI, package version 0.0.20, a local daemon for persistent, independently configured assistants, multiple teams, messaging channels and a TinyOffice web interface.
  • Method: fresh static implementation assessment against WINGMAN_PURPOSE.md and the complete assessment guide. No dependency installation, CLI execution against providers, service startup or browser use. The checkout was kept read-only.

Fit verdict: a credible starting point for Wingman's standing-agent communication and local execution plane, with more implemented project management than a simple assistant router. It has actual CLI-backed workers, persistent team rooms, Telegram, a task/project database, web task dispatch, per-agent prompts and memory, heartbeat and cron. It does not implement Wingman's product organization: project-aware intake, product/technical leadership, proportionate discovery, acceptance-driven delivery, cross-host placement, or a reliable executive account of each agent's current/recent/next work. Adopting it would mean building that product layer and strengthening its run/cancellation semantics, not merely supplying a few personas.

Architecture and execution model

The shipped CLI points to packages/cli/bin/tinyagi.mjs; package.json, lines 1–34, defines the workspace build/start entry points. The operational center is packages/main/src/index.ts, lines 220–302: initialize SQLite, recover previous in-flight messages, start the Hono API, subscribe to queue events, poll every five seconds, prune old queue records, load plugins, and start scheduler/channels/heartbeat. Channels are separate managed processes; agent invocations are fresh local child processes. A durable agent is a configuration key plus workspace and resumable external CLI state, not a permanently running model process.

There are deliberately different persistence planes. Settings hold agents, teams, channels and provider configuration; tinyagi.db holds inbound jobs, outbound responses, room posts and agent message history (queues.ts, lines 12–76). tasks.db independently stores projects, tasks and comments (tasks-db.ts, lines 23–55 and 129–177). Schedules use schedules.json; per-agent files store instructions, memory and heartbeat prompts. Claude/Codex/OpenCode own the actual resumable coding conversation. The task records and message queue have no relational task-to-run association: a [task:id] token can carry that relationship as prompt text.

The API message route resolves the target before enqueueing, persists the user's message, and emits an incoming event (messages.ts, lines 22–67). The queue transaction claims all pending messages for an agent; agentChains serializes them per agent while separate agents run concurrently (queues.ts, lines 104–121; main/index.ts, lines 158–196). This is useful actor-like scheduling on one host, not a distributed actor system. There is no global worker pool limit or host-placement field in the inspected model.

processMessage reloads config, routes, consumes reset flags, transforms incoming text through plugins, invokes the adapter, emits progress and delegates final text to team-message extraction (main/index.ts, lines 43–137). invoke.ts, lines 181–276, constructs prompts, resolves working directories/provider environment and calls an adapter. The default Codex adapter invokes codex exec resume --last unless reset; Claude uses -c; OpenCode uses run -c. These are real coding harness processes with their own tools, not multiple names in one model prompt.

TinyOffice is a Next.js client over these APIs. Its project routes redirect into a task board. The board loads tasks, agents, teams and projects, supports board/list views and project filtering (tasks/page.tsx, lines 44–108). Its office scene combines polling and SSE, while per-agent pages expose chat, skills, schedule, prompt, memory and heartbeat tabs. These are genuine useful management surfaces, with important limits discussed below.

Agent definition, creation and full lifecycle

Definition and identity. AgentConfig is a persistent settings entry containing name, provider, model, working directory, optional inline/file prompt, and optional heartbeat configuration. TeamConfig is a name, member IDs and one leader. There is no template/profile object separate from an instance, project membership, host field, budget or explicit conversation identifier (types.ts, lines 9–27). A task is a tracker record. A queue job is an incoming message. The external CLI conversation is a separate continuation mechanism. Treating these as interchangeable would overstate the model.

Creation and provisioning. The interactive agent CLI validates an ID, asks for name/provider/model and optional instructions, writes settings, provisions <workspace>/<id>, and writes the supplied instructions to AGENTS.md (agent CLI, lines 14–102). The API also provisions new agents at a chosen/default working directory, but saves config before provisioning and logs provisioning errors without rolling back (agents API, lines 42–85). Provisioning copies Claude config, heartbeat and soul templates, creates an initially empty user AGENTS.md, creates memory, and synchronizes packaged skills with a Claude symlink (agent.ts, lines 49–119). No live model starts until a message reaches that identity.

Prompt construction and role behavior. Every invocation builds built-in communication instructions plus self/team information, memory index, workspace instructions and finally config customization. prompt_file takes precedence over inline config prompt. A missing prompt file is silently ignored. A hash cache tracks prompt composition (agent.ts, lines 126–241). Specialist competence and leadership policy are therefore actual configured instructions, not separate orchestration logic. Packaged skills are recopied on every ensureAgentDirectory, overwriting packaged skill directories while preserving unrelated custom ones. A notable custom-cwd limitation: invokeAgent provisions and reads prompts from <workspace>/<agentId> but executes in agent.working_directory; API prompt/memory editing instead targets that configured working directory. Nondefault cwd configurations can therefore split identity/configuration files from those actually injected into the run (invoke.ts, lines 191–209; agents API, lines 211–247).

Execution, tools and permissions. Providers are adapters over executable CLIs. Codex receives a developer-instruction config override and --dangerously-bypass-approvals-and-sandbox; Claude receives --dangerously-skip-permissions; tool execution is delegated to those harnesses, inheriting the daemon environment plus provider credentials and TINYAGI_AGENT_ID (Codex adapter, lines 18–46; Claude adapter, lines 27–43; invoke.ts, lines 216–252). Separate cwd/configs provide organization and continuation boundaries, not OS-level access isolation. There is no TinyAGI capability broker, per-tool approval policy or role-specific permission system in this path.

Routing and concurrency. Public routing matches a leading agent/team mention, team names resolve to leader, and unknown/unmentioned routes default to tinyagi, with fallback to the first configured agent during processing. Messages are claimed transactionally and processed serially per queue target, concurrently across targets. Consecutive room notifications are batched into one prompt. A non-room message flushes that batch (router.ts, lines 9–56; chatroom.ts, lines 8–42). This reduces repeated invocations without a dependency graph or a global concurrency limiter. A shared working directory can also undermine independent external-CLI continuation even when IDs differ.

Persistence and resume. SQLite persists pending/queued/processing/completed/dead state, outbound acknowledgement state, room history and an assistant/user message mirror. It is not the full coding transcript: Codex output filtering retains agent_message text, while Claude includes text and tool-name markers rather than structured tool arguments/results. Claude continues its cwd conversation; Codex resumes the last conversation rather than a stored TinyAGI-selected thread ID (queues.ts, lines 25–62; adapters cited above). Reset creates a workspace reset_flag, consumed on the next job to omit continuation. It does not itself erase transcripts or cancel a current subprocess (agent CLI, lines 355–383; main/index.ts, lines 90–96).

Scheduling and supervision. Heartbeat loops over configured agents, respects enabled/interval settings, reads heartbeat.md or a generic pending-task prompt and posts to the API. lastSentAt is memory-only, updated on enqueue success rather than useful completion. Busy agents accumulate those jobs. The heartbeat is not a liveness lease or stuck-job detector (heartbeat.ts, lines 13–90). Cron and one-shot schedules persist JSON and enqueue ordinary messages. Past one-shot dates are skipped at startup, and a one-shot is disabled after enqueueing rather than successful execution. There is no durable missed-run catch-up or completion-dependent recurrence (schedules.ts, lines 33–119).

Interruption and steering. The active-process map allows a per-agent SIGTERM. The kill endpoint calls failMessage, emits agent:killed and clears the current serialization chain. That is a retryable failure, not a terminal cancelled state. Existing promise closures are not invalidated, and a new chain can be created while an earlier child/queued closure is settling. runCommandStreaming treats code === null as success, including signal-exit cases. These interactions create source-visible risks of killed work being requeued, later marked complete, or work overlapping after stop; no runtime race reproduction was attempted (invoke.ts, lines 18–23 and 110–119; queue API, lines 163–178; main/index.ts, lines 158–196 and 247–251). New chat input is queued behind existing work, not injected into a live model turn. The UI has no full session fork/compact/archive control plane.

Failure, retry and recovery. SQLite retries failed jobs up to five attempts, then exposes dead jobs for manual retry/delete; startup returns all queued/processing messages to pending. This is useful crash recovery but replays whole messages and side effects, without a step checkpoint or exactly-once tool semantics (queues.ts, lines 13, 132–147 and 195–212). Adapter exceptions are caught inside processMessage, converted to a user-facing error response and then return normally: the outer queue usually marks that message complete rather than exercising the retry policy (main/index.ts, lines 100–137 and 175–185). Failures outside that catch can retry. Claude has a 30-second post-result grace timer, but no general maximum invocation duration; Codex does not call signalDone (invoke.ts, lines 122–134; Claude adapter, lines 46–55).

Completion, acceptance and retirement. Job completion means processMessage returned; task completion is an unrestricted tracker status update. There is no cross-check against tests, required reviewer, human product acceptance or done-triggered schedule shutdown. CLI removal cleans team membership, deletes empty teams/reassigns leaders and recursively removes the canonical agent workspace, whereas the API deletion only removes the settings key. Neither path provides a complete audit-preserving retirement transaction over queued jobs, schedules, active processes, task references and provider history (agent CLI, lines 107–163; agents API, lines 88–97). Queue maintenance prunes completed jobs and acknowledged responses after the default day, while agent/room history is separately retained (queues.ts, lines 207–249).

Concrete coordination trace

A source-traced request can begin as the human changing an assigned task to in_progress in TinyOffice. The detail panel first updates the task and then sends @<assignee> <title>\n\n<description>\n\n[task:<id>] to /api/message (task-detail-panel.tsx, lines 98–106). This is a real implementation bridge between tracker and agent. The bridge is UI-specific: the tasks API merely writes a record; changing status through the shell skill/API does not universally dispatch a run. A failed send is swallowed after the task has already changed status. Board drag-and-drop and the explicit assignment action also dispatch messages, with the opposite ordering: enqueue first, then persist status (tasks/page.tsx, lines 130–145 and 164–175). These paths are not atomic with the tracker update, so either side can disagree after an error.

The message route resolves the mention to an agent/team leader, persists user text and enqueues under that target. The queue transaction claims it and the per-agent promise chain invokes the local harness. Team-routed text has a subtle boundary: enqueue resolves the team to an explicit agent, and processMessage uses the pre-routed branch without re-parsing or stripping the original mention. It therefore loses explicit team-route context and can fall back to that agent's first configured team. An agent in multiple teams is not guaranteed to retain the originating project/team for its next DM (messages.ts, lines 22–42; main/index.ts, lines 69–84; conversation.ts, lines 37–49).

Suppose the worker replies Auth implementation ready. [@reviewer: Check login.ts and run regression tests] [#dev: Ready for review]. The balanced-bracket parser tolerates nested brackets in code expressions; text outside DM tags is attached as shared context, comma-separated recipients fan out, invalid/self/nonteammate recipients are filtered and recipients are deduplicated per response (routing.ts, lines 19–59 and 139–169). The room post is saved and separately enqueued to every other member. The DM becomes another flat job with a new message ID and fromAgent, not a child task or awaited future. Separate recipients can execute in parallel; multiple DMs to one agent serialize. Reviewer updates/comments can go through the tasks shell API (tasks.sh, lines 102–124 and 170–202).

Dispatch waits for invocation completion: the streaming callback persists and sends each assistant text event to the human, but DM/room extraction runs only after await invokeAgent returns (main/index.ts, lines 100–108 and 134–136). In the Codex adapter, each agent_message overwrites response rather than accumulating it (codex.ts, lines 32–47). A handoff or room tag in an earlier streamed message can therefore appear in the human-facing conversation without ever being dispatched if the final retained message omits it. Fan-out starts after the originating invocation ends, and reliable handoff requires the tags in the retained final response.

The reviewer must mention the requester again to route an answer back. There is no durable request/reply correlation, join over all recipients, maximum conversation hop count, supervisor loop detector or shared decision object. Room post fan-out can therefore also produce repeated invocations. The packaged agent instructions request restraint, and room batching reduces prompt count but does not enforce termination. Per-agent queue ordering is the hard coordination mechanism; plan quality and closure remain agent behavior.

Telegram follows the same API path after pairing and media download. Outbound assistant text is signed, hooks process it, files are extracted and a response row is queued; Telegram polls pending responses and uses the original message mapping or senderId to select a target chat (response.ts, lines 52–92; telegram.ts, lines 489–515). Internal DMs inherit the original channel/sender, but room notifications use channel chatroom. Their subsequent answers are not automatically Butler-mediated decisions to the human. Heartbeats use channel heartbeat, not a selected human Telegram recipient. A proactive escalation needs explicit paired-user send tooling or another deliberate routing step.

Substantial additional capabilities

Multiple harnesses and custom model endpoints. Claude, Codex and OpenCode can coexist agent by agent. Custom provider config selects a Claude/Codex harness and injects compatible API endpoints/credentials (invoke.ts, lines 211–259; opencode.ts, lines 15–43). This would let Wingman experiment with role-specific harnesses/models, beyond its described Codex organization. Integration must normalize resume, permissions and event fidelity. An alternate model endpoint is not another execution host.

Multi-channel media and controlled sender access. Telegram, Discord and WhatsApp adapters extend the human interface, with pairing and inbound/outbound file handling. Telegram accepts photos/documents/audio/voice/video/stickers and embeds local file references in prompts (telegram.ts, lines 281–357 and 447–465). That is useful for product references and demonstrations. It needs an explicit organization-level channel/identity policy to prevent unrelated chats sharing an agent's latest coding conversation. Pairing protects sender intake. It does not create a sandbox around file/tool access.

Hierarchical agent memory and deployable skills. The memory loader parses per-file name/summary metadata and formats a hierarchy for prompt injection; full text remains on disk for selective reading. Skills are synchronized into agents, and the API supports skill registry search/install (memory.ts, lines 19–131; agents API, lines 102–207). This provides selective reusable knowledge/capabilities beyond fixed role instructions. Wingman would need project-scoped ownership/versioning and protection against packaged skill refresh replacing edited packaged skills. Registry installation uses external npx execution. It was inspected, never run.

Arbitrary scheduled assistant work. Cron and one-shot jobs are first-class schedule records rather than only a ProjectMaster supervision timer. They could support scheduled research, reporting or maintenance across roles. Their enqueue-based completion, skipped overdue one-shots and absent missed-run ledger constrain unattended reliability (schedules.ts, lines 67–119 and 131–185).

Daemon plugins for transformation and event integration. Plugins dynamically load from the TinyAGI home, receive event subscription/logging context, and can transform incoming/outgoing messages and metadata (plugins.ts, lines 37–45, 82–144 and 150–170). This creates a practical extension seam for routing/notification/instrumentation. Plugins execute in the daemon process and hooks are best-effort, not a transactional durable workflow or isolation boundary.

Grounded mechanisms and innovation assessment

The strongest design is the combination of durable per-agent queues with a small textual collaboration protocol. A model can emit individual DMs, parallel fan-out and persistent room posts without a custom tool-call API. Balanced-bracket parsing allows programming expressions in messages; shared context plus directed content reduces duplicated handoff text; team validation reduces accidental dispatch to arbitrary identities. The queue makes recipients independent and room batching amortizes consecutive updates. This is a useful compact mechanism supported by routing.ts, lines 19–195, conversation.ts, lines 11–108, and chatroom.ts, lines 8–42. Its limits are prompt compliance, first-team ambiguity, unbounded conversation chains and lack of durable workflow correlation. It is not evidence of historical novelty.

A second useful combination is dynamic team/memory prompt construction with file-backed local identity. A new member becomes visible in teammate instructions on the next invocation, and memory summaries provide a small index instead of loading every remembered document. The implementation cleanly separates runtime self/team information from user-customized AGENTS.md (agent.ts, lines 126–241). This makes reconfiguration cheap but does not enforce organizational responsibilities or guarantee CLI conversation isolation when cwd is shared.

The office activity view is an interesting visibility experiment, but should not be treated as a stronger execution model. useOfficeSse attaches agent invokes/mentions/responses to the most recently open root and closes them on message:done; streamResponse emits that event for each streamed text response, not only after the whole team finishes (use-office-sse.ts, lines 46–75 and 120–166; response.ts, line 92). Parallel human requests and intermediate model text can therefore make its apparent work sessions misleading. Wingman should derive executive activity from authoritative run/task events with parent/root IDs and explicit completion, not copy this heuristic as business truth.

Practical use and remaining work

TinyAGI can contribute the local worker/harness adapter, named-agent settings, SQLite message/outbound queues, Telegram integration, dynamic team-room messaging, task/comment primitives, customizable agent memory and scheduling. The task-board dispatch and packaged task skill already connect human assignment to agent actions, so a prototype Wingman need not start from an empty orchestration framework.

Before making it the core,:

  • adapt agent identity to include stable profile, project and execution host.
  • explicitly persist provider thread IDs and task/run/root relationships.
  • fix custom-cwd prompt divergence and team-origin routing.
  • implement deterministic cancellation and late-event guards.
  • preserve adapter failures in queue state.
  • introduce replay-aware tool/workflow semantics.
  • normalize structured tool, usage, test and artifact events.

Current bypassed harness permissions and unauthenticated API route registration also need deliberate deployment treatment before exposing a control plane beyond a trusted environment (server/index.ts, lines 39–66 and 107–111). This is a concrete consequence of the execution/control architecture, not a claim that sender pairing is absent.

The main new product work remains substantial:

  • Butler/ProjectMaster intake tied to a registry.
  • per-project ProductMaster/TechMaster instances.
  • discovery/question/answer and scope/specification/acceptance records.
  • ticket dependencies and integration supervision.
  • test evidence and accepted delivery states.
  • Mac/Endeavour workers with shared coordination and coherent project placement.
  • structured executive briefings and linked activity timelines.
  • a real per-agent coding workspace.

Those capabilities could be layered on the substrate, but are not established merely by naming existing agents after Wingman roles.

Verification scope and uncertainty

Inspected source includes:

  • the CLI agent lifecycle.
  • main daemon/heartbeat.
  • core types/config/routing/invocation/queues/response/memory/schedules/plugins.
  • all three provider adapters.
  • team parser/DM/room/batching.
  • Telegram intake/outbound sections.
  • server message/agent/queue/project/task APIs and database.
  • TinyOffice task board/detail.
  • company relationships.
  • per-agent tabs/chat.
  • office data and SSE state.

Packaged task and paired-user-send scripts were read as implementation evidence, not invoked as skills. Checked the repository's root and docs AGENTS.md; no ancestor instruction files were present in the searched path. The documentation's older queue-processor layout and future-dashboard language were not used to override the actual packages/TinyOffice implementation.

Missing-capability searches covered packages/, tinyoffice/src/, CLI/provider paths and packaged skill inventory for project identity, dependencies, approvals/acceptance, discovery, host/remote runner, workflow and blocked-state terms. Project IDs appeared in tracker/UI code rather than the execution job model. Searches found no test/spec files in the tracked source inventory, and root package.json has build/start/development commands but no test script. No automated test suite was run, and that inventory result is not proof of runtime correctness or complete absence of external tests.

All described execution paths and edge cases are static findings. Provider CLI flag compatibility, actual resume behavior, Telegram delivery, race outcomes, database replay under crash, and browser rendering were not exercised. The report assesses the checkout at its stated commit, with no claims about newer upstream releases or hosted behavior.
