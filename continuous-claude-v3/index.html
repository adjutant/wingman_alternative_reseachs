Continuous Claude v3 assessment

Assessment date: 2026-11-05. Product: Continuous Claude v3, a Claude Code workflow, hook, agent-profile and memory kit. Upstream: https://github.com/parcadei/Continuous-Claude-v3 . Local checkout: research/continuous-claude-v3/repo. Assessed commit: d07ff4b06b62f43771bc0c927d0211b734d6149e.

Verdict: useful material for Wingman's execution and continuity layer, with unusually substantial discovery instructions and context-management hooks. It does not implement Wingman's standing development organization. Its center of gravity is a human's Claude Code session, delegating bounded work and carrying context between sessions. Telegram intake, project leadership identities, a portfolio registry, organizational chat, the connected dashboards and multi-host agent placement would still need to be built. Several advanced coordination paths reference implementation absent from this checkout, so the architecture documentation substantially overstates what can be established locally.

This is a source assessment, not a runtime certification. No dependencies were installed, no services or agents were launched, and checkout files were not changed. All source citations below are relative to this report; stated line numbers refer to the assessed revision. The comparison target is WINGMAN_PURPOSE.md, following ASSESSMENT_GUIDE.md.

Architecture and actual execution model

Claude Code and .claude/settings.json, lines 1–275, provide the entry point. Configuration registers a status command and hooks for session start, prompts, tools, compaction, stop, and session end. Most commands target the user's global ~/.claude installation. This checkout therefore provides configuration and supporting code for an external harness. It does not supply its own durable-agent server.

hook_launcher.py, lines 99–118 and 234–261, resolves project and global hook files. It prefers compiled JavaScript, then TypeScript, then Python. TypeScript inspection establishes source behavior. It does not prove that an installed compiled hook matches that source.

Agent execution has two paths. Markdown files define Claude Code roles. maestro.md, lines 1–10, declares a model and tools and directs orchestration through the host's Task tool. kraken.md, lines 1–12 and 57–89, defines implementation and TDD behavior. The external harness consumes those prompts.

claude_spawn.py, lines 653–753, separately starts a local claude -p process. It assigns a UUID session ID, redirects output to /tmp/claude-agents/<uuid>.json, and passes hierarchy environment variables. It returns the PID. This is independent temporary task execution. It does not create an enduring employee with a mailbox and project appointment.

The Python subprocess path reads JSON profiles, not the Markdown definitions. Profile loading, lines 276–328, searches the project, current directory and two user locations. kraken.json, lines 1–10, has a compact TDD prompt and a different tool declaration from the much longer Markdown profile. A caller must deliberately choose the path and profile. route_to_agent() provides an ordered keyword classifier at claude_spawn.py, lines 334–415, but spawn_agent() does not call it: it loads the explicit perspective argument. Searches found no active dispatcher calling that classifier. The checked-in DISABLED-task-router-hook.json is another reason not to infer transparent automatic delegation from the routing table.

Persistence is spread across several mechanisms, with different ownership and lifetimes:

  • Project Markdown/YAML under thoughts/shared/{specs,plans,research,handoffs} and legacy thoughts/ledgers stores specifications, phase records and continuation context. Build instructions, lines 281–321, describe writing an orchestration file; pre-compact-continuity.ts, lines 17–94, implements transcript-derived handoffs when the required legacy ledger exists.
  • A SQLite artifact index has handoffs, plans, continuity snapshots, queries and FTS5 indexes, including outcome annotations and trace IDs. See artifact_schema.sql, lines 13–125. It is a search and learning index, not a ticket registry or agent directory.
  • PostgreSQL code implements core and archival memory, text/vector/hybrid retrieval and optional session/agent scoping. See memory_service_pg.py, lines 74–142, 306–379 and 655–856. Hook helpers also implement session registration and advisory file claims directly with inline SQL in db-utils-pg.ts, lines 390–445 and 532–575.
  • Broader agent registration, blackboard and agent completion wrappers import scripts.agentica_patterns.coordination_pg. That package is absent locally. claude_spawn.py, lines 787–829, catches that failure and appends a temporary registry record instead. The registration and file-claim SQL above does not depend on the missing package. Those narrower implementations should still receive credit.

Pattern modules implement swarm, pipeline, jury, hierarchy, and related functions. Active integration requires more than source presence. The active settings, lines 6–275, register neither SubagentStart, SubagentStop, nor a pattern dispatcher. pipeline.ts, lines 110–164 and 220–351, can start a detached next stage. It requires the correct environment/configuration and an existing SQLite database. This does not establish automatic scheduling in an ordinary installed /build. Its SQLite coordination also differs from the PostgreSQL wrappers.

The optional OPC runtime provides separate Python tool execution. runtime.harness, lines 133–180, initializes an MCP manager and executes scripts. mcp_client.py, lines 421–556 and 598–703, supports local stdio and remote SSE/HTTP tools. Connections are lazy and retries are bounded. Remote tools do not establish remote coding-agent hosting.

Agent definition and complete lifecycle

Definition, creation and identity

An agent profile is a role template, not a durable agent instance. Markdown frontmatter names the role, model and host tools; its body supplies instructions. JSON profiles for subprocess spawning additionally parse permissions, blocked_patterns and inherit_blocks. The JSON loader, lines 276–328, only constructs configuration. The subprocess builder uses prompt, model, tools and the skip/queue choice. A search of the spawner found no enforcement of the parsed blocked-pattern or inheritance fields. This is a meaningful gap if treating those fields as a policy boundary.

Creation occurs through the external Task tool described by profiles/skills or by explicitly calling Python spawn_agent()/spawn_lead(). The latter assigns a fresh UUID unless a caller supplies one. AGENT_ID identifies this execution, PARENT_AGENT_ID its spawning relation, and SESSION_ID an inherited grouping that defaults to default. PATTERN_TYPE is optional. Environment construction, lines 549–577, does not establish an employee identity, a product appointment or a persisted mailbox. spawn_lead() embeds selected JSON worker definitions using Claude's --agents flag, while its returned premise is simply lead (lines 919–969).

There is also a distinct coordination session identifier. session-id.ts, lines 44–110, generates a short ID from a Braintrust span or timestamp and stores it in one user-global ~/.claude/.coordination-session-id file. Session registration, lines 33–44, sets an environment variable only in the hook process and writes that file. Later hook processes can therefore read the most recently written global ID unless a parent environment already supplied COORDINATION_SESSION_ID. Two terminals can overwrite that file. This is a source-visible isolation risk, not a reproduced runtime failure. The checked-in persistence tests actually assert overwriting behavior at session-id-persistence.test.ts, lines 107–112. Wingman should use canonical execution/session IDs throughout, with explicit project and host keys.

Execution, tools and permissions

Command construction, lines 488–546, runs claude -p, caps it at 100 turns and requests final JSON output. It injects persona text into the task. The optional system-context path deserves integration review: lines 543–544 pass a filesystem path string as the --append-system-prompt argument without reading that file. This code does not itself establish that the intended system-prompt contents are loaded. Model/tool declarations are forwarded to Claude. The project does not implement the model loop or tool authorization itself. By default it adds --dangerously-skip-permissions. A profile with permissions: queue merely suppresses that flag, delegating any approval behavior to Claude. No approval queue service is implemented here. Lead spawning always adds the skip-permissions flag (lines 626–648). These defaults would require deliberate integration with Wingman's human decisions and host execution policies.

Subprocesses inherit the calling environment and working directory. There is no per-task worktree creation, sandbox assignment or remote host placement in this path. Filesystem isolation is a coordination responsibility. file-claims.ts, lines 49–67, warns on an existing claim and allows the edit. It does not lock the file. Settings apply that hook to Edit, not Write or arbitrary Bash mutations. The check and claim are separate calls, and claims have no age filter in the inspected lookup. They should not be treated as serializable exclusive ownership.

The repository also has a separate Docker math-code sandbox runner (sandbox_runner.py, lines 1–42 and 77–150) with CPU/RAM limits, a timeout and reduced builtins. That does not sandbox the headless coding agent. Its existence should not be used to imply that skipped-permission coding runs execute inside containers.

Routing and concurrency

Routing is distributed between keyword-triggered skill suggestions, model interpretation of workflow instructions, the optional routing function and explicit profile selection. The prompt hook skill-activation-prompt.ts, lines 53–79 and 87–130, reads rules and optionally invokes Python pattern inference. The inference file it checks for is absent here, so this branch returns no inference rather than proving autonomous pattern selection. The plain skill-matching machinery still exists; advanced pattern claims need separate evidence.

The Python spawner enforces depth below three at lines 423–433, and a soft count of 50/hard count of 100 through lines 26–34 and 436–453. These are limits in a particular Python interpreter's global counter, not a distributed or even machine-wide quota. Checking the count and incrementing after Popen are separate operations, so concurrent callers could race. resources_available() samples CPU/RAM at lines 382–395, but the shown spawn_agent() and spawn_lead() do not call it. A comment about resource-aware spawning therefore cannot establish actual admission control. Environment depth is also a convention propagated to child processes, not a security isolation boundary across all native Task executions.

Persistence, resume and scheduling

The durable unit of continuity is mostly the work artifact. Kraken's resume instructions, lines 14–33, direct a new/resumed agent to the last validated checkpoint. implement_plan, lines 124–130 onward, describes using a host agent ID for clarification. Build, lines 584–592, instructs a resumed invocation to load orchestration.yaml and continue its incomplete phase. These are valuable protocols, but the Python spawner has no --resume/--continue operation and always normally creates a new session UUID. Reusing an ID is not an implemented conversation-resume controller.

Compaction continuity uses executable hooks. pre-compact-continuity.ts, lines 21–63, finds a legacy ledger and creates a transcript-derived YAML handoff during automatic compaction. It directly reads the ledger directory. A missing directory therefore differs from an empty ledger list. Its final catch reports the error.

session-start-continuity.ts, lines 323–428, first scans handoffs and loads embedded ledger/YAML content. Lines 433–540 provide legacy fallback. UUID-specific helpers exist at lines 16–85. The main handoff-first scan instead calls legacy session-name lookup. It selects the newest qualifying record across directories. UUID-helper tests alone cannot prove isolation in that main path.

Scheduling is session/event based. Hooks run when Claude triggers an event. A caller or model must begin the next work invocation. A conditional pipeline handler can advance a stage, and an in-process thread monitors PIDs. No long-lived organization scheduler starts idle project leaders, revisits unanswered product questions or periodically supervises multiple products.

The configured auto-handoff-stop.py, lines 18–68, reads a context-percentage file written by the status command and blocks a first stop at 85% or higher with a request to run /create_handoff. Despite its name, that stop hook does not write the handoff itself. It relies on the model following the instruction. Missing percentage data and recursive stop-hook invocations are allowed through.

Interruption, cancellation, failures and recovery

The native coding host owns interactive interruption. The spawner returns a PID, but exposes no corresponding managed cancel, task rollback, process-tree teardown or durable paused state. Its monitor is a daemon thread started on module import (claude_spawn.py, lines 217–222), so a short-lived python -c caller can exit while the spawned agent continues. That loses the interpreter-local concurrency counter and completion monitor. The agent system prompt, lines 21–30, itself suggests that short-lived invocation pattern. Wingman would need a persistent supervisor to own process handles and reconcile outcomes after restarts.

The monitor checks os.kill(pid, 0) once a second and, when the PID disappears, attempts to read JSON and write status/result summary (lines 142–214). It defaults to completed if the output file is absent and only classifies selected error subtypes as failed. It does not inspect an owned Popen.returncode or retry failed agent work. Its database update also uses a fixed development database target, unlike the environment-configurable hooks. This makes status consistency an integration concern. Registration falls back to append-only temporary JSONL, with no matching update of that fallback's running record in the monitor. A fallback registry is therefore an observation aid, not a reliable authoritative lifecycle ledger.

Workflow-level failure handling is more thoughtful but instructional: build, lines 520–547, says to mark a blocked phase and present retry/skip/abort/manual-intervention options. implement_plan, lines 78–88, asks the human about mismatches. The MCP client separately retries tool-call exceptions (mcp_client.py, lines 598–703), but tool retry is not agent/task recovery and could need idempotency controls for mutating calls. The harness has signal cleanup for its own execution (harness.py, lines 177 onward). It does not manage the independent coding-agent fleet.

Completion, acceptance and retirement

Process completion, model-declared task completion and human acceptance are distinct. A JSON result or vanished PID is only execution termination. Build, lines 549–580, asks the model to assemble specs, plans, validation, implementation handoffs and optional PR/commit details. implement_plan, lines 90–112, explicitly forbids marking manual checks complete before the human confirms them. This is a useful acceptance distinction, but there is no project-level transition that checks every ticket against an agreed product definition of done and retires the active team after accepted delivery.

Session-end cleanup, lines 68–120, updates the latest legacy ledger timestamp and removes an old latest-output.md from per-agent cache directories after seven days. Lines 123 onward optionally launch a Braintrust learning extractor with a user-global lock. The inspected hook does not deregister sessions, release file claims or kill spawned agents. The PID registry/output files under /tmp/claude-agents also have no corresponding retirement sweep in this spawner. An external harness may clean its own sessions, but that behavior is outside this checkout's demonstrated lifecycle.

Coordination mechanics and concrete task traces

The closest coordination model is orchestrator plus artifacts. The main Claude session supplies tasks; specialists return files. The main session reads and synthesizes them. Maestro, lines 88–117, explicitly follows that pattern. Skills can add a plan and human checkpoints, while file-claim hooks warn about concurrent editing. There is no durable organizational room where leadership and specialists retain membership, no common ticket lifecycle, and no implemented Butler to preserve question ownership across the human's conversations.

Blackboard code is mixed. The active pre-tool broadcast hook reads a project-local SQLite database when SWARM_ID is present (broadcast, lines 26–117). It repeatedly reads the latest ten messages from other senders; no unread cursor or acknowledgement is implemented in this hook. The PostgreSQL helper's blackboard API would read unread messages (db-utils-pg.ts, lines 104–151), but depends on the absent CoordinationDBPg implementation. These are different paths, not one proven end-to-end chat system.

Coding request: /build greenfield Add user authentication with OAuth

This concrete request is present in the repository's own build example, lines 596–649. The following traces its actual configured/prompt implementation, not an executed historical run:

  1. The user enters the request in Claude Code. UserPromptSubmit runs skill activation, memory awareness and other hooks (settings, lines 135–162). Skill activation can suggest relevant instructions. The host/model invokes the build skill. There is no Telegram update or project-registry lookup.
  2. Build's chain definition, lines 264–305, selects discovery → planning → plan validation → implementation → optional commit/PR and instructs creation of thoughts/shared/handoffs/<session>/orchestration.yaml with phase status. It is Markdown pseudocode/instructions, not a Python state-machine implementation.
  3. Discovery instructions, lines 23–53, 131–178 and 220–294, ask questions, research uncertain choices, confirm the understanding and write a spec with success/acceptance criteria. Answers remain in the host conversation and generated files. No cross-project pending-question router exists.
  4. Build, lines 387–419, passes the spec/research into a planning Task, records the plan path and asks for approval/change/abort. Task execution belongs to Claude Code. Separately, invoking spawn_lead() would use actual Popen, loaded workers and the environment/registry path described above. These are alternative entry paths, not a proven single automatic chain.
  5. During implementation, settings, lines 46–79 and 164–225, can inject code/architecture context, check an Edit claim and run diagnostics. A conflict produces a warning, so two workers can still edit the same file. implement_plan, lines 90–112, tells the implementer to run checks, fix failures and await manual verification.
  6. Build, lines 520–592, instructs error recording, human retry decisions, artifact reporting and later continuation from YAML. Completion returns to the direct human session. It does not update a portfolio dashboard or notify Butler.

Executable pipeline task: async error handling python

A narrower Python pipeline has explicit test configuration. test_research_pipeline.py, lines 38–44, supplies the topic. research_implement_pipeline.py, lines 95–115 and 501–530 onward, parses it and creates PipelineContext. It obtains the MCP manager and sequentially runs research, AST search, Morph search, quality checks, and Git status.

Nia research, lines 144–189, saves tool results. AST search uses a heuristic pattern (lines 192–226). Morph, lines 280–335, collects search matches. Steps return success, skipped, or failed and retain context/error lists. An unavailable configured tool can therefore produce an explicit skip.

The important boundary appears at lines 402–436: despite the introductory “stage changes” language, the Git step only checks status and explicitly leaves staged_files empty. Likewise, the Morph step searches. It does not apply an implementation patch. This trace demonstrates functioning orchestration code structure and graceful degradation, not an autonomous research-to-delivery engine. The source test harness was inspected but not executed, and no external tool result or quality outcome is claimed.

Major additional capabilities and integration consequences

Intent-sensitive code context and token management. The TLDR read hook, lines 120–148 and 151–356, chooses structure, entry-point context or flow analysis based on the search context. It asks an external daemon for AST/call graph/CFG/DFG/PDG information. At lines 388–428 it permits explicitly bounded reads and falls back to normal reading when analysis is unavailable. Task context injection, lines 50–121, recognizes data-flow, slicing, complexity and debugging intents. daemon-client.ts, lines 20–103, resolves project paths, creates project-hashed lock/PID files, detects existing processes and bounds query time. This could reduce worker context consumption and improve targeted code understanding. The parser/indexer implementation is external; claimed savings/latency percentages in comments were not benchmarked. Porting to Codex requires adapting host events and tool input/output formats, with careful escape hatches so compressed structure does not hide necessary implementation detail.

Searchable experience with explicit outcome labels. Artifact schema, lines 20–40 and 81–125, distinguishes what worked, what failed, decisions, outcome confidence and query feedback, and links handoffs to traces. PostgreSQL memory, lines 655–856, supports both weighted text/vector search and reciprocal-rank fusion. memory-awareness.ts, lines 108–128, actually uses a fast text-only recall subprocess for automatic hints, despite its header's broader semantic-search description. The richer semantic interface is a separate capability. Wingman could reuse outcome-aware retrieval across projects, but must define sharing boundaries: memories scoped to session/agent are not automatically organization-wide institutional knowledge, and automatically extracted model judgments need provenance and confidence.

Trace-derived learning and evaluation. braintrust_analyze.py, lines 983–1052, evaluates plans against succeeded/failed precedent, and lines 1120–1475 implement learning extraction from session traces into cached files. Session-end cleanup, lines 123 onward, starts extraction only when Braintrust is configured and guards against duplicate extractors with a PID/timestamp lock. This extends beyond simple task tracking into improvement of later decisions. Integration would require an optional external tracing backend and LLM judge, explicit cost control, and stable mapping from traces to Wingman agents/tasks. Generated learnings and judge scores are evidence to review, not acceptance verdicts.

Formal proof and numerical/symbolic tools. compiler-in-the-loop.ts, lines 71–109, invokes Lean/Lake and records errors/incomplete proofs; lines 129–150 check a local model endpoint for tactic assistance. The stop hook, lines 65–135, can ask Claude to repair unresolved errors while guarding recursive stop hooks and stale state. The repository also includes mathematical computation scripts and a restricted execution runner (sandbox, lines 33–42 and 77 onward). These could support verification-heavy products or specialist research. They bring separate toolchains and optional local-model infrastructure, and Lean proof correctness is not equivalent to whole-product acceptance. No proofs or compilers were run during this assessment.

A library of coordination patterns. pipeline.ts, lines 110–164 and 220–351, contains detached stage continuation and artifact passing; other source modules cover jury, generator/critic, adversarial and hierarchy. This is richer than Wingman's initially specified room/team structure and could provide reusable task execution strategies. Integration would first need to make dispatch explicit, reconcile SQLite/PostgreSQL state, enforce idempotent stage launch and define failure/acceptance criteria. The pipeline handler marks a stopped stage completed before considering any product-verification result, so its completion event is not a success gate. Advanced pattern inference/composition wrappers cannot be adopted as a working engine without supplying their missing Python implementations.

Distinctive mechanisms and grounded innovation assessment

The strongest implemented design idea is continuity as a generated, searchable work artifact rather than merely retaining a chat transcript. The transcript parser feeds automatic handoffs before compaction. A later start hook can inject the handoff or embedded ledger; SQLite indexing attaches outcomes and trace provenance. This permits a fresh coding context to recover the goal, decisions and next steps without replaying the entire prior conversation. Its limitations are concrete: some paths require legacy ledgers, newest-record selection can cross work streams, status is a checkpoint rather than live activity, and outcome marking is not compulsory product acceptance.

Another worthwhile mechanism is action-sensitive context selection: a recent search result names an actual target, which the read hook uses to request relevant structure/flow context instead of blindly loading whole files. Explicit offsets/limits and failure fallback preserve a route to source. This is a practical execution-layer pattern Wingman could port independently of the rest of the project. It does not establish measured token savings in this assessment, and it depends on the external TLDR analysis service being accurate and available.

composition-gate.ts, lines 39–78, throws on invalid pattern compositions. pattern-selector.ts, lines 99–169, validates adjacent pairs. It exposes isolation, shared, federated, and handoff scopes with sequential, parallel, and additive operators.

python-bridge.ts, lines 27–63 and 72–108, invokes two missing local scripts: scripts/validate_composition.py and scripts/agentica_patterns/pattern_inference.py. Failed validation returns an error. Failed inference falls back to a low-confidence hierarchy. Type contracts, wrappers, and tests do not establish a working algebraic scheduler. Pairwise checks also do not establish global properties of longer chains. This assessment makes no historical or industry-wide novelty claim.

Finally, the file-claim and peer-session hooks show a useful low-friction approach to concurrent sessions: make conflicts visible while letting coding continue. Its enabling tradeoff is advisory awareness with minimal central control. Wingman needs stronger identity isolation, freshness, cleanup and worktree/integration ownership before using it as protection for a standing organization. These mechanisms are useful seeds precisely when their boundaries remain explicit.

Practical fit for Wingman

Reusable material includes discovery/specification templates, TDD, manual acceptance, handoff schemas, outcome-aware indexing, targeted context, and optional learning extraction. Wingman can adopt these protocols or libraries separately. The independent-process launcher can inform a host adapter. A production adapter still needs owned process handles, canonical IDs, streaming output, cancellation, and durable reconciliation. A temporary registry and short-lived caller cannot provide that full contract.

Adaptation is substantial because the system is Claude-specific: event names, Task, frontmatter, CLI flags, JSON/stream formats and installed global paths all assume Claude Code. Wingman's Codex agents require equivalent adapters with clearly separated profile, identity, conversation, task and execution records. A single profile source should replace divergent JSON and Markdown role definitions. Permissions should be enforced at execution, not inferred from unused profile fields. Durable shared state should choose one coordination contract and explicit project/host namespaces; file claims need expiry/release and stronger integration rules; lifecycle events need idempotency and reliable exit/success classification.

Wingman still needs these organization capabilities:

  • Telegram Butler intake, answers, and escalation.
  • Cross-project registry and continuing ProductMaster/TechMaster appointments.
  • Shared tickets, dependencies, rooms, membership, and history.
  • Project/executive dashboards, agent briefings, timelines, and linked coding workspaces.
  • Multi-host placement, routing, and periodic blocker follow-up.

Product acceptance needs a durable transition tied to the definition of done. It must stop active development until new work arrives. Role names and hooks alone cannot implement these workflows.
