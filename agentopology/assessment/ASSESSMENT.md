# AgenTopology assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/agentopology/agentopology

Local checkout: `research/agentopology/repo`. Inspected commit: `6aab63339a1bad43e87ff156dabf77d18208ee26`. Package version: `0.8.0` ([package.json](../repo/package.json), lines 1–8). This report assesses that local revision, not a separately installed package or the current behavior of the external platforms it targets.

**Fit verdict:** AgenTopology can define teams, generate harness configuration, and prepare execution briefs for Wingman. Useful mechanisms include role/artifact contracts, topology validation, visualization, and scaffold reconciliation. It separates deterministic workflow phases from conversational orchestration.

Wingman still needs an organization runtime, portfolio and ticket records, and a persistent agent/session registry. Telegram routing, multi-host dispatch, supervision, and connected operational views also need implementation. Generating configuration does not start or supervise a standing team.

The distinction matters particularly for Codex: this revision generates actual named agent configurations and registers them in `.codex/config.toml`. It does not launch Codex conversations, retain their IDs, send them messages or expose their workspaces. Its Claude Code binding goes further in generated hooks, discussion transcripts and cron scripts, but execution remains the responsibility of Claude Code and the host agent. The separate `plan` command prints instructions for an existing host agent to interpret. It is not an embedded agent runner.

## Architecture and execution model

The executable is `dist/cli/index.js`, built from TypeScript. The CLI dispatches validation, scaffolding, sync, import, visualization, analysis, export and plan commands ([CLI](../repo/src/cli/index.ts), lines 73–129 and 1206–1324). The public AST represents a topology: nodes, edges, role descriptions, stores, retrieval declarations, skills, hooks, schedules, interfaces, providers, artifacts and optional checkpoint/observability declarations ([AST](../repo/src/parser/ast.ts), lines 985–1056). There is no organization database behind those declarations.

The source follows three materially different paths:

1. **Compile a persisted harness.** `cmdScaffold` reads and parses the `.at` source, resolves a binding, validates, calls `binding.scaffold(ast)`, computes an incremental file plan and writes the result plus a manifest. Validation errors stop compilation unless explicitly overridden. Existing files and authored-file references are considered before writing ([CLI](../repo/src/cli/index.ts), lines 392–524). The binding result is an array of paths/content. It is not a list of running agents. Codex output includes config, root `AGENTS.md`, one TOML per agent, memory directories, skills, scripts and optional protocol/metering files ([Codex binding](../repo/src/bindings/codex.ts), lines 1712–1753).
2. **Prepare an interpreted execution brief.** `cmdPlan` validates, records a best-effort Git revision, builds a brief and prints it. The host coding agent then supplies all actual spawning, commands, waiting and decisions ([CLI](../repo/src/cli/index.ts), lines 857–905; [brief renderer](../repo/src/plan/render.ts), lines 130–185). The brief resolves defaults, graph order, gates, branch/loop information, handoffs, missing inputs and output-file evidence. Its orchestration loop is generated prose, including how to parse subagent replies. A CLI mode named `execute` changes that prose's autonomy contract. It does not itself execute a topology.
3. **Compile a hybrid Claude host plus Workflow rung.** The Claude binding generates host agents, skills, hooks and Blackboard instructions. The Workflow binding generates JavaScript for explicitly selected deterministic phases and accompanying seam/loss reports. Workflow `agent(...)` and `parallel(...)` calls are emitted code for a separate runtime. Unrepresentable features are recorded rather than silently represented as implemented ([Workflow binding](../repo/src/bindings/claude-workflow.ts), lines 1–23, 111–175 and 191–235). Human input and nonselected phases remain host concerns. The generated Blackboard observer is still a marked TODO stub ([Claude binding](../repo/src/bindings/claude-code.ts), lines 3372–3398).

Persistence consists principally of versionable `.at` source, generated configuration/instructions, scaffold ownership manifests and whatever artifact or transcript files the host produces. Checkpoint declarations are not evidence of a checkpoint engine: the Codex path emits backend/strategy/replay values as Markdown ([Codex binding](../repo/src/bindings/codex.ts), lines 1023–1035). Likewise, declaring an observability exporter writes documentation rather than an operational telemetry service (lines 1010–1020), and its metering script merely prints a TODO (lines 1421–1444).

The graph visualizer is a self-contained HTML projection of AST and validation results, using inlined Dagre. It does not subscribe to a runtime ([visualizer](../repo/src/visualizer/index.ts), lines 1–6 and 97–100). The brain visualizer reads Markdown into a graph. These are valuable design/knowledge inspection surfaces, not executive summaries of current work.

## Agent definition and lifecycle

### Definition, creation and identity

An agent begins as an `AgentNode`: a stable topology-local `id`, optional label/role/description, prompt, model, permissions, tools, skills, read/write declarations and many optional policy fields. `runs` distinguishes subagent, inline skill and forked skill. `independent` states that an evaluator must see artifacts rather than the author's reasoning; validation rejects an independent inline mode ([AST](../repo/src/parser/ast.ts), lines 553–601; [validator registration](../repo/src/parser/validator.ts), lines 3582–3594). A node is therefore a role/invocation definition, not automatically a process, durable employee or conversation.

Scaffolding materializes that definition into platform files. Codex gets a role entry under `[agents.<id>]`, plus `.codex/agents/<id>.toml`. The TOML includes a name, description, developer instructions, optional model/sandbox/reasoning level, a derived nickname and referenced MCP configuration ([Codex binding](../repo/src/bindings/codex.ts), lines 1628–1704). Those names are reusable role identifiers. The compiler does not issue a separate agent-instance UUID, project membership or conversation ID. Multiple instances, if launched, are host-managed instances of a role.

Claude generally gets registered subagents. An inline/fork node becomes a skill instead, and explicitly Workflow-owned agents are omitted from host agent generation ([Claude binding](../repo/src/bindings/claude-code.ts), lines 584–598). Thus even within one `.at` file “agent” does not always mean an independent execution context. In interpreted mode, the declared orchestrator is explicitly the existing host session, not another spawned agent ([order resolver](../repo/src/resolve/order.ts), lines 12–16; [renderer](../repo/src/plan/render.ts), lines 181–185).

### Execution, tools, permissions and routing

The compiler never enters an LLM tool loop. Platform configuration is loaded later by Codex/Claude/OpenClaw/etc., or a human/host reads the execution brief. The brief instructs its interpreter to verify inputs, dispatch role cards verbatim, parse an `at-output` fenced block, resolve declared output enums and take the appropriate branches. If the formal return contract fails it prescribes token scanning then model inference, logging weaker interpretations and treating first-role inference as a reason to stop and ask ([renderer](../repo/src/plan/render.ts), lines 130–160). These are detailed prompts, not a programmatic reply parser or router running inside AgenTopology.

Enforcement depends on the target. Claude frontmatter carries tool allow/deny names, MCP access, max turns, permission mode, reasoning effort, background and isolation, while warning that a subagent cannot expand the launching session's authority ([Claude binding](../repo/src/bindings/claude-code.ts), lines 623–658). Codex has actual generated sandbox/model fields, but the helper's “available tools,” “disallowed tools,” reads and writes are instructions ([Codex binding](../repo/src/bindings/codex.ts), lines 1581–1618 and 1655–1665). In interpreted mode the tool policy explicitly says it is declared but not enforced ([renderer](../repo/src/plan/render.ts), lines 76–82). A `reads`/`writes` contract is not a filesystem ACL.

Routing is principally flow-edge routing. The order resolver removes true back-edges and error routes from happy-path ranking, groups same-layer nodes by kind, then splices gates around their `after`/`before` anchors. Conditional branches are distinguished from fan-out, avoiding the error of dispatching every exclusive branch ([order resolver](../repo/src/resolve/order.ts), lines 28–58, 123–205). The brief separately groups decisions by the actual node/output tested, with unconditional fallbacks ([brief](../repo/src/plan/brief.ts), lines 373–403). None of this selects an existing product based on a human's ambiguous conversational reference.

### Concurrency and coordination boundaries

For brief execution, the host is told to send all same-step role calls before reading any result. This limits inadvertent leakage of sibling reasoning into prompts but still depends on host obedience and available tools ([renderer](../repo/src/plan/render.ts), lines 140–150). For Codex scaffolding the generated global configuration chooses `max_threads = min(agent count, 10)` and `max_depth = 1`. It is not elastic capacity management. Workflow compilation turns scale into a fixed fan-out at `scale.max`, explicitly recording that the runtime cannot count filesystem items to implement dynamic scaling ([Workflow binding](../repo/src/bindings/claude-workflow.ts), lines 227–235).

Discussion groups deliberately use the opposite strategy: one member at a time, all reading/appending to one transcript. Sequential host dispatch is the “lock”. There is no concurrent append arbiter or message delivery system. That is a workable local round-based debate protocol, not direct asynchronous collaboration among independently long-lived workers ([Claude binding](../repo/src/bindings/claude-code.ts), lines 1062–1067 and 1235–1240).

### Persistence, resume and scheduling

Scaffolded role files outlive a session, but role-file durability does not preserve an invocation's private context. Group transcripts, workspace artifacts and brain notes can preserve shared context if the host writes them. Interpreted briefs derive `present/missing/undecidable` from output existence, requiring every declared write for a step to exist. They do not record that the task succeeded or when/by whom it ran ([brief](../repo/src/plan/brief.ts), lines 348–370). Old or invalid output files can therefore produce “present.” The renderer explicitly directs the host to inspect Git history and not skip on this evidence alone. There is no native `--resume` state machine, process recovery journal, durable conversation restoration or transactional completion stamp.

Scheduling is target-specific. Claude scripts change to the project root and call `claude -p` with the named agent, while the emitted crontab fragment still needs installation. Only expressible `every` durations convert to cron; unsupported recurrences produce commented entries and warnings ([Claude binding](../repo/src/bindings/claude-code.ts), lines 2800–2812 and 2844–2901). OpenClaw output enables cron and emits isolated-session `agentTurn` jobs; notably its first-class path uses `job.cron ?? job.every` as an expression with `kind: cron` rather than converting human-readable recurrence ([OpenClaw binding](../repo/src/bindings/openclaw.ts), lines 414–416 and 519–530). Such output needs platform compatibility checking. Codex has no generated schedule runner. No target comes with Wingman's ProjectMaster supervision algorithm.

### Interruption, cancellation and recovery

AgenTopology exposes no running-agent handle to interrupt or cancel. Human approval nodes, gate failures and declared max-turn/timeout fields provide stopping constraints in generated artifacts; user steering and cancellation during coding remain host functions. No queue of incoming human messages, attachment delivery or resume/fork/compact/archive API was found in CLI/plan/binding code.

Recovery support is uneven. Agent retries, fallback chains, circuit breakers and compensation relationships exist in the schema, and the validator checks their shapes/references. Many bindings render them as prose; for example Claude retry instructions are text in the agent body ([Claude binding](../repo/src/bindings/claude-code.ts), lines 882–893). They are not evidence of a circuit-breaker service or saga executor. In contrast, generated Claude gate wrappers contain an actual shell retry loop, optional `timeout`, and an exit-2 failure signal ([Claude binding](../repo/src/bindings/claude-code.ts), lines 2080–2113). That retries the check command. It does not respawn a failed worker or automatically repair an implementation. The generic retry loop permits the initial attempt plus the configured retries.

The safety of a gate depends on its authored check. Generic shell stubs print `TODO: implement this script` and have no explicit nonzero exit ([stub helper](../repo/src/bindings/lib/stub.ts), lines 49–59). Consequently, a scaffolded gate can appear successful before it verifies anything. The marker and `stubs` command expose unfinished work, but the wrapper does not itself reject a marker. Claude action placeholders for non-inline actions are better guarded: missing implementations print TODO and exit one ([Claude binding](../repo/src/bindings/claude-code.ts), lines 554–568). Wingman should distinguish “wired check” from “implemented and verified check.”

### Completion, acceptance and retirement

Interpreted completion is a host-produced closing report enumerating steps, spawned roles, output interpretation tiers, gate exit codes and loop use. It is not an authoritative ticket acceptance transition ([renderer](../repo/src/plan/render.ts), lines 157–160). Products have no built-in definition-of-done object, acceptance decision or delivery-stop state. These would need authored documents, verification programs and an organization workflow.

Retiring a role means removing its declaration and reconciling files. The incremental planner identifies previously generated files no longer emitted; pruning deletes only unedited owned files and avoids symlinks ([incremental scaffold](../repo/src/scaffold/incremental.ts), lines 221–251). That is cleanup of generated configuration. It does not archive past agent conversations, revoke a remote worker, stop an active host session or release a durable assignment.

## Coordination mechanics and a concrete source trace

Coordination uses three kinds of shared material: graph edges describe control dependencies; exact path intersections describe artifact handoffs; group transcript files describe discussions. The brief computes `passes = writer.writes ∩ reader.reads`, withholding other writer outputs from a reader's prompt and assigning blindness restrictions to readers ([brief](../repo/src/plan/brief.ts), lines 66–80, 125–143 and 267–285). This makes a useful distinction between “B follows A” and “B actually receives a declared artifact from A.” There is no broker delivering messages, locking shared tasks or guaranteeing atomic handoffs.

A real checked-in request shape is `/review <PR_URL>` in [examples/code-review.at](../repo/examples/code-review.at), lines 168–176. The following is a static implementation trace, not a claim that the example was run:

1. The topology declares an external GitHub-PR intake action handled by the orchestrator, plus four specialist role definitions (lines 21–44 and 49–129). Calling `scaffold ... --target claude-code` follows parse→validate→binding→incremental write in [CLI](../repo/src/cli/index.ts), lines 392–444. Trigger generation creates host command/playbook material. It does not open GitHub itself. Since intake supplies no commands, its generated external action is a TODO that exits one ([Claude action generation](../repo/src/bindings/claude-code.ts), lines 554–568). The integration must be implemented before the example can fetch a real PR.
2. Flow fans out from intake to analyzer and security-scanner, then joins at reviewer (example lines 136–139). The analyzer writes `workspace/analysis.md`; security-scanner writes `workspace/security.md`; reviewer declares both as reads (lines 63–64, 84–85 and 106–107). The planner can derive those exact-path handoffs and order independent specialists together, then the reviewer. It does not claim the external action produced the PR diff, since action outputs are not modeled as agent `writes`. The diff is consequently an input the brief requires to exist before enactment ([precondition computation](../repo/src/plan/brief.ts), lines 317–331).
3. The reviewer declares a verdict enum. Approve or request-changes routes to reporter; reject routes to create-report (example lines 108–109 and 140–143). Those are declared decisions resolved by the host from returned outputs, not a ticket state change. The example's `request-changes` branch still reports the outcome rather than automatically assigning repair work.
4. A gate named `human-approval` sits after reviewer/before reporter and names `scripts/human-approve.sh` (example lines 148–154). The name alone does not implement a human approval interface: it is a command gate. Claude generates the wrapper and a `SubagentStop` hook for the registered reviewer ([Claude settings generation](../repo/src/bindings/claude-code.ts), lines 2460–2540). The checker itself is a marked generic stub until authored. A distinct `human` node is the construct that generates an actual ask-before-agent hook (lines 261–295).
5. Reporter reads prior reports and writes `workspace/final-report.md`, then create-report is handled by the orchestrator (example lines 113–144). The final action is another unimplemented placeholder without authored commands. The example's `log-findings` hook names an event/script, but this does not create an agent timeline or status service (lines 181–186).

The sample contains a permission conflict. Analyzer, security-scanner, and reviewer instructions request written reports. Their tool lists allow only Read, Grep, and Glob. Global settings deny Write, Edit, and Bash. See example lines 62–64, 83–85, 105–107, and 191–194. A binding that preserves those restrictions can prevent the required artifact writes. Static topology validation does not prove that permissions permit the role instructions. The sample demonstrates modeling and compilation. It does not establish working end-to-end review automation.

For actual human decisions, the Claude before-agent script uses `jq` to inspect `tool_input.subagent_type`, runs applicable checks and emits the platform hook JSON asking permission. This is more concrete than a mere “please ask the human” prompt, but still needs the external host's hook semantics and local `bash`, `jq` and potentially `timeout`. Nothing in this path records an organization-wide escalation chain, Telegram answer correlation or durable decision ownership.

## Major additional capabilities and integration consequences

**Portable harness compilation and import/sync.** Wingman's purpose specifies real Codex agents; AgenTopology also targets Claude Code, Claude Workflow, OpenClaw, Gemini, Copilot, Cursor and Kiro. A shared declaration can generate a platform-native harness while preserving platform-specific extensions. This could keep Wingman team definitions inspectable and make alternative backends possible. It is not behaviorally uniform: gates, schedules, allowed tools and independent contexts have materially different mappings, and some targets carry concepts only as prose. Wingman should define a Codex capability contract instead of assuming every accepted `.at` field is executable.

Import and sync help adopt hand-maintained systems. Sync extracts edited prompt portions into `.at` for four named targets, with special handling to avoid reimporting unchanged generated prompts ([sync](../repo/src/sync/index.ts), lines 31–92). Flow import uses existing `.at` evidence or topology skill flow. It reports unwired nodes and suggested handoffs rather than inventing a sequence. Candidate topology matching requires shared agent IDs and reports skipped/no-file/dropped sources ([flow import](../repo/src/import/flow.ts), lines 1–44 and 62–144). This is valuable migration tooling, but heuristic source matching is not a durable identity merge, and sync support is narrower than the eight output targets.

**Regeneration with ownership and edits preserved.** The scaffold planner classifies creates, unchanged files, edits/conflicts, managed updates, blocked paths and deletions. It refuses symlink traversal and unsafe generated paths, preserves explicit authored files and keeps edited obsolete outputs ([incremental planner](../repo/src/scaffold/incremental.ts), lines 44–58, 101–145 and 178–237). The CLI has a dry-run path, separate force/allow-invalid/prune controls and per-topology manifests ([CLI](../repo/src/cli/index.ts), lines 410–524). This would be useful as Wingman grows its profiles without erasing custom prompts or local configuration. The integration cost is accepting reconciliation conflicts as work to resolve; generation is not automatically a successful deployment or agent reload.

**Architecture checks, diagrams and rule-specific teaching.** The validator registers checks for graph references, bounded loops, handoffs, gate placement, provider/model relationships, schema references, artifact cycles, hook types/events, secrets and execution mode combinations ([validator](../repo/src/parser/validator.ts), lines 3556–3648). The analyzer computes graph layers and structural patterns rather than operational progress. CLI error output can attach focused language examples ([CLI](../repo/src/cli/index.ts), lines 365–389). These mechanisms catch configuration errors before deployment and make the team comprehensible to humans or LLMs, but cannot prove a coding task succeeds or that an agent obeys its prompt.

**Memory stores and knowledge-graph modeling.** Stores can declare semantic, episodic, and procedural retrieval infrastructure. `custodian-of` and maintenance verbs assign knowledge upkeep to an agent. See [AST](../repo/src/parser/ast.ts), lines 604–621. A brain store seeds a Markdown index. Its visualizer derives real, index, and missing-link nodes from files, tags, and wikilinks. It embeds note content for offline inspection. See [brain viewer](../repo/src/visualizer/brain.ts), lines 20–50 and 153–220.

The generator does not implement ingestion, embeddings, or retrieval. Generated memory commands ask the host agent to use external MCP tools or a suitable library. See [Claude memory commands](../repo/src/bindings/claude-code.ts), lines 1938–1944 and 1983–1986. The brain parser derives note slugs from basenames (lines 158–170). Avoid duplicate filenames that make those slugs ambiguous.

**Hybrid compilation with explicit loss accounting.** Selected phases compile into deterministic Workflow calls, while human input, hook-driven behavior and conversation stay in the host. The compiler emits a loss ledger for unsupported or degraded semantics; static scaling is a concrete example. This can make high-throughput bounded phases easier to audit than a wholly improvised orchestration session. It adds a second external runtime and seam contract, and the generated observer/launch glue includes implementation work. It is not a Codex multi-host scheduler or durable distributed execution engine.

## Distinctive mechanisms and grounded innovation

AgenTopology's most useful design is its separation of **control flow, information flow and enforcement strength**. A graph edge does not automatically grant every upstream artifact to a reader. The planner derives passed and withheld files, puts the restriction on the reader and marks independent same-step agents as mutually blind. The renderer then ties concurrent dispatch to information isolation. This enables independent review designs in which a critic receives the work product without the author's self-justification. Its limits are explicit: pathname matching is exact, model instructions are not ACLs, and a host with filesystem access can still read a withheld path. There is no claim here of historical novelty. This is a concrete, useful implementation choice in this project.

The **gate-placement resolver** also embodies an important correction to naive graph rendering. A gate's placement is carried in `after`/`before`, so simply topologically ranking all nodes puts gates at the start. The resolver ranks work nodes and inserts gates at anchors, including gates anchored to other gates, while preserving declaration order ([order resolver](../repo/src/resolve/order.ts), lines 1–16 and 180–205). This improves executable briefs without requiring authors to encode checks as ordinary dataflow edges. It still emits an execution prescription. The host must follow it, and target hooks enforce only the cases the binding can wire.

The **derived evidence model** is unusually candid about continuity. It checks artifacts rather than maintaining a misleading sidecar “done” flag, and returns undecidable for steps with no declared writes. Tests explicitly guard that no resume shortcut is offered ([evidence tests](../repo/src/plan/__tests__/evidence.test.ts), lines 69–122). This helps a human or agent inspect partial work after interruption, but cannot detect stale content, correctness or provenance. Wingman should reuse this as one observation within durable work state, not replace its tracker with file existence.

Finally, the **host/workflow seam plus loss ledger** treats portability as a translation with observable compromises. It avoids making a deterministic Workflow runtime pretend to support live human input, dynamic scaling, shell gates or per-invocation permissions. The practical advance is reviewable degradation: generated comments/reports tell an operator where host responsibilities remain. Its boundary is equally important: the generated observer is a stub, and tests checking emitted hook names are not evidence that live work summaries or notifications exist.

## Practical fit and remaining work

Wingman could use the parser/validator, `.at` source format, static diagrams and scaffold reconciliation directly as development tooling. Its initial Butler/ProjectMaster/ProductMaster/TechMaster/specialist definitions could become topology role definitions with explicit artifact handoffs, an acceptance gate and named knowledge stores. Codex TOML generation is a plausible starting point for role deployment, subject to checking generated fields against the actual Codex runtime Wingman chooses. Keeping the generated role definition separate from a durable instance registry would preserve the distinction between “BackendCoder profile” and “BackendCoder instance serving product A.”

Adaptation would need a Wingman-specific mapping from topology IDs to profile IDs, project IDs, instance IDs, host IDs and conversation IDs. The planner's graph could help instantiate bounded work, but Wingman would need authoritative task transitions, idempotent dispatch, message correlation and recovery instead of treating a brief as the runtime. Tool and artifact access requirements should be validated against actual permissions, and unimplemented stubs should block deployment/acceptance rather than merely appear in a warning. Codex schedule, gate and tool-policy declarations need executable implementation or an explicit unsupported-feature error.

Most of the user-facing product remains to build: Telegram intake and Butler routing; cross-project registry and continuity; separately accountable project leadership. A persistent shared tracker; asynchronous agent rooms; supervision and blocker follow-up; real Mac/Endeavour placement and shared coordination; executive agent summaries/timelines; and linked, controllable coding workspaces. Those are runtime/data/UI responsibilities this compiler neither contains nor hides behind its visualizer. The highest-value adoption would therefore be a subordinate configuration and inspection layer inside Wingman, not replacement of Wingman's organization architecture.
