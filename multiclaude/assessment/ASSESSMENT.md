# multiclaude assessment

Assessed **2026-11-05** against [Wingman's purpose](../../WINGMAN_PURPOSE.md). Upstream: https://github.com/dlorenc/multiclaude . Local checkout: `research/multiclaude/repo`. Actual checked-out commit: `dfad1a58343bceaf20017fe93cfad55af54550d1`.

**Fit verdict:** multiclaude is a useful reference for Wingman's local coding execution and supervision layer, with genuinely independent Claude Code processes, isolated worker branches, configurable roles, durable mailboxes, periodic nudges and GitHub delivery. It begins with repositories and coding assignments. It lacks discovery and product definition workflows. It also lacks Butler/Telegram, portfolio leadership, shared product tickets, collaboration rooms, executive timelines, web/mobile workspaces and distributed hosts. Adopting it as the whole product would leave most of Wingman's organizational and human-facing behavior to build. Its execution patterns are more reusable than its complete application because Wingman specifically requires Codex agents.

This is a **source assessment**, not an observed autonomous production run. Implementation evidence below distinguishes executable machinery from instructions supplied to a model. Line references refer to this revision; links are relative to this report.

## Architecture and actual execution model

The application is a Go CLI and a local background daemon. The daemon loads `state.json`, claims a PID file, opens a Unix socket, restores tracked repositories and starts five goroutines: health checks, message routing, wakes, socket serving and worktree refresh. These are separate from the Claude processes and tmux server. Stopping the daemon cancels its loops, closes its socket and saves state. It does not itself kill all agent terminals. See [daemon.go](../repo/internal/daemon/daemon.go), lines 44–116 and 170–197. The transport is JSON request/response over a Unix-domain socket with mode `0600`, accepting connections concurrently. It is neither a network worker protocol nor an event subscription service ([socket.go](../repo/internal/socket/socket.go), lines 11–21, 51–70, 101–132 and 151–172).

Repository initialization does substantial work in the CLI itself: clone a GitHub repository, detect forks, create tmux windows, write prompts, launch Claude and then register repository/agents through the daemon. A normal repository starts supervisor and merge-queue, while fork configuration selects a PR shepherd. A separate default human workspace receives its own worktree and conversation. This differs from restoration: when the whole tmux session is missing, the daemon recreates a supervisor and workspace, sends the definitions to the supervisor, and asks that model to decide which additional roles to spawn. Therefore initial provisioning and recovery do not share one declarative reconciler. See [cli.go](../repo/internal/cli/cli.go), lines 1162–1275, 1350–1509 and 1510–1602; [daemon.go](../repo/internal/daemon/daemon.go), lines 1817–1908 and 1913–2018.

Each coding worker is a Claude Code CLI process launched inside a tmux window whose current directory is its Git worktree. The CLI fetches origin best-effort, normally starts from `origin/main` or `HEAD`, creates `work/<name>`, writes the worker system prompt, sends an initial `Task: ...` message, captures output and registers identity. The daemon is not implementing an LLM tool loop: Claude Code supplies coding tools, conversation storage, model execution and terminal interaction. The repository supplies coordination and process plumbing around it ([cli.go](../repo/internal/cli/cli.go), lines 2081–2321 and 5871–5911). The reusable runner also models `--session-id`, `--resume`, system prompt files and text submission, but initial CLI and daemon launch code still contain their own command construction ([runner.go](../repo/pkg/claude/runner.go), lines 164–205 and 220–339).

State is a repository map containing named agents, task history, GitHub/fork settings and a current-repository selector. Agent state includes type, worktree, tmux window, session UUID, PID, task, optional completion summary/failure, creation time, last nudge and cleanup flag. There are no organization/team entities, product requirements, dependency edges or human-decision records in this schema. State uses an in-process mutex and unique temporary file plus rename; messages are separate JSON files rather than rows in that atomic state transaction. See [state.go](../repo/internal/state/state.go), lines 129–175 and 186–257; [messages.go](../repo/internal/messages/messages.go), lines 23–32 and 175–191.

A compact execution path is:

```text
Human terminal / interactive workspace
  -> CLI repo resolution and worker creation
  -> Git worktree + tmux window + Claude Code conversation
  -> local socket registration -> daemon state.json
Worker/supervisor CLI messages -> per-recipient JSON mailbox
  -> daemon periodic delivery -> literal terminal input
Worker PR + complete command -> notifications + cleanup + task history
  -> merge-queue model uses gh/CI/review -> merge or follow-up worker
```

## Agent definition and lifecycle

### What an agent actually is

An **agent definition** is Markdown content identified by filename, with a source path and local/repository origin. It is not a running agent, tool policy or organizational identity. The reader discovers `.md` files and merges local templates with checked-in custom content; contrary to nearby “repo wins” comments/documentation, the actual collision behavior appends repository content to the local base under `Custom Instructions`. This is explicitly covered by [agents_test.go](../repo/internal/agents/agents_test.go), lines 145–249, and implemented in [agents.go](../repo/internal/agents/agents.go), lines 97–145. Supervisor/workspace have embedded defaults; older `.multiclaude/SUPERVISOR.md`-style customization still passes through `LoadCustomPrompt`, despite being deprecated ([prompts.go](../repo/internal/prompts/prompts.go), lines 36–135).

A **running agent** is a state-map entry paired with a local tmux window and Claude Code conversation/process. A **task** is primarily a string attached to a worker and supplied as its first user message. It is not a durable ticket entity assigned to a standing specialist. A **session** is the Claude UUID plus externally maintained conversation files. Persistence means selected types are eligible for process restart. It does not mean every agent has an immutable identity independent of processes, or that completed workers remain members of an organization. State types explicitly separate persistent supervisor/merge-queue/PR-shepherd/workspace/generic agents from transient worker/review agents ([state.go](../repo/internal/state/state.go), lines 12–35 and 143–175).

### Creation, execution and permissions

The usual worker path creates a generated adjective/animal name (or accepts `--name`), selects a repository, fetches origin, chooses `origin/main` when available, and creates a worktree/branch. `--branch` can override the starting point, while `--push-to` can continue an existing PR branch. It then creates a detached tmux window, UUID and prompt; copies optional repository hook configuration; starts Claude, sends the task, enables output capture and calls `add_agent` on the socket. This is not a transaction: errors after Git/window creation do not have a unified rollback across all stages ([cli.go](../repo/internal/cli/cli.go), lines 2081–2321).

The generic spawn path validates a persistent/ephemeral class, rejects an already registered name and accepts full prompt content. Persistent generic roles run in the shared repository checkout; ephemeral roles receive `work/<name>` from `HEAD`. Persistent names `merge-queue` and `pr-shepherd` get corresponding special types; other persistent names become generic-persistent. Ephemeral names containing “review” become reviewers; others become workers. This is flexible but mixes identity and lifecycle semantics. Also, the generic handler records optional `task` after startup without sending the usual `Task: ...` initial message: a caller needs that assignment in the actual prompt or subsequent input ([daemon.go](../repo/internal/daemon/daemon.go), lines 1535–1662 and 2039–2095).

Tools and permissions come from the installed Claude Code environment, not a multiclaude capability router. Production launch paths pass `--dangerously-skip-permissions`; optional `.multiclaude/hooks.json` is copied verbatim to `.claude/settings.json`. Workers have Git isolation, not an OS sandbox: they run under the same user with access to the common environment and authenticated `gh`. These are material integration differences from a Codex organization with host/tool policy and visible approvals ([cli.go](../repo/internal/cli/cli.go), lines 5871–5907; [daemon.go](../repo/internal/daemon/daemon.go), lines 2062–2069; [hooks.go](../repo/internal/hooks/hooks.go), lines 10–40).

### Identity, routing, concurrency and scheduling

The effective address is repository plus agent name. CLI repository resolution tries explicit `--repo`, Git remote, working directory and the daemon's current-repository fallback. Self-context inference uses the worktree path or tmux window in the shared repository, with a supervisor fallback. That makes normal CLI messaging convenient, but address identity is environmental rather than a signed agent credential ([cli.go](../repo/internal/cli/cli.go), lines 4042–4128). Worker branches allow parallel edits; persistent roles share a checkout and depend on instructions to avoid interfering with it. No host/resource scheduler, concurrency quota, atomic ticket claim or dependency-aware work release was found in the command dispatcher, spawn paths or state model.

The daemon sends role-specific nudges every two minutes, skipping agents nudged within the last two minutes. Workspace is deliberately excluded from both wakes and automated message delivery. Health checks also run every two minutes; worker worktrees refresh every five minutes after a 30-second startup delay. These are fixed timers, not cron jobs, goals/budgets or workload-driven team scaling ([daemon.go](../repo/internal/daemon/daemon.go), lines 274–281, 366–488 and 490–607).

### Persistence, interruption and recovery boundaries

State writes use a temporary file and rename. Claude conversation history is not copied into the state store: restart checks `~/.claude/projects/<encoded-worktree>/<session-id>.jsonl`, using `--resume` only if a nonempty file exists. Otherwise it launches with the prior session ID but without resume. Existing prompts are reused when available ([state.go](../repo/internal/state/state.go), lines 186–257; [daemon.go](../repo/internal/daemon/daemon.go), lines 2148–2191).

Recovery has important limits. With a surviving tmux session and window, dead persistent-agent PIDs trigger restart, but dead transient PIDs are not restarted or automatically enqueued for cleanup in that branch. Missing windows are marked for cleanup even for persistent types. With the entire tmux session gone, `restoreRepoAgents` removes **every old registration**, starts a new supervisor and default workspace with fresh UUIDs, and relies on supervisor interpretation of definitions to restore other roles. It does not iterate/resume the old workers or restore all named human workspaces. This is recovery of a usable repository environment, not recovery of every agent conversation and assignment ([daemon.go](../repo/internal/daemon/daemon.go), lines 284–364, 1742–1813, 1817–1908 and 2039–2095).

Moreover, `GetPanePID` reads tmux's `#{pane_pid}`. The launch code sends a Claude command into an existing shell rather than replacing that shell with `exec`. Thus the stored PID is the pane process and may stay alive after its Claude child exits. A signal-0 check on that PID does not establish model-process health or useful progress. This is a source-level reliability concern, not a runtime failure reproduced here ([tmux/client.go](../repo/pkg/tmux/client.go), lines 341–359; [cli.go](../repo/internal/cli/cli.go), lines 5871–5896; [daemon.go](../repo/internal/daemon/daemon.go), lines 2200–2208).

Human interruption is chiefly native terminal steering plus CLI restart/removal/hibernate/stop controls. Removing a worker kills its window and can remove its worktree; hibernation creates a patch and metadata before stopping selected agents. It is not resumable suspended agent state. Its archive saves `git diff HEAD` and a list of untracked filenames, not untracked file contents; forced worktree removal can therefore discard material absent from the patch. There is no implemented structured pause/resume job state or automated retry/backoff budget ([cli.go](../repo/internal/cli/cli.go), lines 2866–2991, 2993–3228 and 4248–4301). Recovery after failed PRs is mostly the supervisor/merge-queue model spawning another worker with prior context, as instructed in [supervisor.md](../repo/internal/prompts/supervisor.md), lines 42–49, and [merge-queue.md](../repo/internal/templates/agent-templates/merge-queue.md), lines 25–58.

### Completion, acceptance and retirement

A worker is instructed to create a PR and run `agent complete`. The CLI infers the caller and optionally supplies summary/failure. The daemon sets `ReadyForCleanup`, writes notifications and immediately schedules routing and a health check. It does not verify a PR exists, tests passed, changes were pushed, product criteria were met, or a human accepted the work. Workers notify fixed supervisor and merge-queue addresses; reviewers notify merge-queue. The completion handler does not substitute PR shepherd in fork mode ([cli.go](../repo/internal/cli/cli.go), lines 4201–4245; [daemon.go](../repo/internal/daemon/daemon.go), lines 1024–1098).

Cleanup records worker task history, kills the terminal, removes state, forcibly removes worker/review worktrees and deletes orphaned recipient message directories. The surviving summary is task/branch/times/optional summary or failure; initial PR status is unknown unless failure was supplied. CLI history later asks GitHub for PR state by branch. Consequently completion is retirement of the worker, PR integration is a separate process, and accepted product delivery is not a lifecycle state ([daemon.go](../repo/internal/daemon/daemon.go), lines 1397–1487; [messages.go](../repo/internal/messages/messages.go), lines 210–242; [cli.go](../repo/internal/cli/cli.go), lines 2596–2863). There is no policy to stop active development/testing after an accepted product definition of done because no such product acceptance object exists.

## Coordination mechanics and a traced request

The durable message record has sender, recipient, timestamp, body, status and optional acknowledgement time. `Send` writes a pending JSON file in the recipient's repository mailbox. The daemon enumerates active non-workspace agents, reads pending messages and submits `Message from <sender>: <body>` as literal tmux text followed by Enter. A failed terminal send leaves the message pending. A successful send changes its state to delivered. Only pending messages are submitted: once marked delivered, a message is not automatically reinjected even if it remains unread or unacknowledged. Delivery means text submission, not proof the model understood or acted. Reads/acks are separate CLI operations. Message updates use direct writes. The renderer bridges messages to terminal input. These mechanisms do not establish transactional events, exactly-once delivery, ordered conversation threads or a model-response receipt ([messages.go](../repo/internal/messages/messages.go), lines 44–116, 147–191; [daemon.go](../repo/internal/daemon/daemon.go), lines 372–424).

The method called `SendKeysLiteralWithEnter` chains `set-buffer`, `paste-buffer` and Enter in one shell command and passes message text as a positional argument. That reduces split-call submission problems and preserves multiline input. It still uses the shared tmux buffer without a visible per-agent mutex or named buffer, so “atomic” in comments should not be interpreted as isolation across concurrent router/wake/refresh callers ([tmux/client.go](../repo/pkg/tmux/client.go), lines 315–334). The current model/input readiness is also not checked before delivery.

A concrete supported request, `multiclaude worker create "Add authentication tests" --repo product-a`, follows this implementation path (a traced example, not a run performed during assessment):

1. `createWorker` joins the task description, resolves `product-a`, fetches origin, chooses a branch base and creates `work/<name>` in its isolated worktree ([cli.go](../repo/internal/cli/cli.go), 2081–2183).
2. The CLI creates the tmux window and UUID, loads fork settings and worker instructions, copies hooks and launches Claude. It sends `Task: Add authentication tests`, starts capture and registers the task/session/PID using socket `add_agent` (same file, 2217–2308). Subsequent work and test/tool execution belong to Claude Code.
3. If blocked, the worker's prompt directs `message send supervisor`. `sendMessage` infers the originating agent, writes the mailbox and requests immediate routing best-effort; two-minute polling is the fallback for injection into the supervisor's terminal ([worker.md](../repo/internal/templates/agent-templates/worker.md), 24–28; [cli.go](../repo/internal/cli/cli.go), 3779–3810; [daemon.go](../repo/internal/daemon/daemon.go), 372–424).
4. After coding, the instructed worker creates a GitHub PR and calls `complete`. The executable handler marks cleanup and sends fixed completion messages to supervisor and merge-queue, then triggers routing and cleanup immediately ([daemon.go](../repo/internal/daemon/daemon.go), 1024–1098). No scheduler waits for downstream task dependencies.
5. The merge-queue **model** is instructed to inspect main CI, open PRs, reviews, unresolved comments and roadmap alignment, then squash merge. It can spawn a fixer or mark `needs-human-input`. This is prompt-specified behavior carried out using `gh`, not Go logic enforcing a merge state machine ([merge-queue.md](../repo/internal/templates/agent-templates/merge-queue.md), 7–73). Actual repository branch protections would be an external enforcement boundary.
6. Cleanup records worker history and removes the ephemeral environment. The history command obtains live PR status by branch when displayed ([daemon.go](../repo/internal/daemon/daemon.go), 1397–1487; [cli.go](../repo/internal/cli/cli.go), 2816–2863).

There are no shared collaboration rooms or ticket dependency tables behind this flow. Optional Claude task tools are recommended in prompts, but the repository's own [task guide](../repo/docs/TASK_MANAGEMENT.md), lines 65–76, describes them as conversation-local progress tracking. Searches found no `CLAUDE_CODE_TASK_LIST_ID` plumbing or common native task database that would establish cross-agent shared TaskList behavior. GitHub PRs/comments/issues and mailboxes are the practical inter-agent shared records; supervisor escalation and human decisions are conventions over those records.

## Major additional capabilities beyond Wingman's stated scope

**GitHub integration as a continuing delivery ratchet.** The merge-queue role combines green-CI checks, review-response handling, emergency broken-main mode, follow-up worker creation and stale branch hygiene. That adds an opinionated delivery policy beyond Wingman's product acceptance description. It could usefully become Wingman's integration/release role after TestMaster, but it must distinguish passing code checks from business acceptance and implement important gates in code/branch protection rather than relying entirely on a prompt. Evidence: [merge-queue.md](../repo/internal/templates/agent-templates/merge-queue.md), lines 7–106; real reviewer provisioning in [cli.go](../repo/internal/cli/cli.go), lines 4303–4463.

**Fork contribution mode and PR shepherd.** Fork detection first recognizes an upstream remote, then consults GitHub via `gh`; initialization records upstream metadata and chooses shepherd instead of merge-queue. Generated fork prompts adapt contribution/review behavior to upstream ownership. This is useful if Wingman contributes to third-party software rather than only delivering its own products. Adoption would require reconciling upstream human review with Wingman's human acceptance and fixing hardcoded completion notifications. Evidence: [fork.go](../repo/internal/fork/fork.go), lines 37–86; [cli.go](../repo/internal/cli/cli.go), lines 1267–1309 and 5753–5790; [daemon.go](../repo/internal/daemon/daemon.go), lines 1942–1998.

**Automatic worktree synchronization during execution.** Every five minutes, workers can be brought forward onto the upstream/default branch, with checks for detached HEAD, merge/rebase state and whether refresh is useful. Refresh stashes local/untracked changes, rebases, aborts conflicting rebases and restores the stash; successful refresh sends a notification. This reduces long-lived branch drift but mutates files beneath an active coding agent and is not guarded by a model/tool-activity lock. For Wingman this needs coordination with active tools and a visible event tied to the affected task. Evidence: [daemon.go](../repo/internal/daemon/daemon.go), lines 490–607; [worktree.go](../repo/internal/worktree/worktree.go), lines 621–715 and 740–885.

**Operational preservation and inspection.** Human workspaces have separate branches, read-only attachment can observe an agent without typing into its terminal, and hibernation offers patch/metadata salvage for stopped work. These can help Wingman operators inspect and reclaim local execution capacity. Hibernation is only partial preservation, however: untracked file names are saved without content, and retirement discards the active agent identity. It should not be exposed as reliable project archival. Evidence: [cli.go](../repo/internal/cli/cli.go), lines 2993–3228, 3250–3420 and 4739–4819.

## Distinctive mechanisms and grounded innovation

The most distinctive design decision is the **Brownian-ratchet orchestration policy**: tolerate overlapping speculative workers, keep the supervisor focused on throughput, and let CI/review plus merge-queue choose what becomes durable progress. The supervisor explicitly says not to prevent overlap and to accept whichever attempt passes first ([supervisor.md](../repo/internal/prompts/supervisor.md), lines 59–66). Combined with real branch isolation and independent review processes, this is a coherent alternative to a strict dependency DAG. It enables exploration and replacement of failed attempts without elaborate preplanning. Its limits are duplicate cost, conflicting PRs and the incompleteness of CI as a product-value oracle. “Progress is permanent” is a policy metaphor, not a guarantee that passing merges are correct or irreversible.

A second useful mechanism is **model-interpreted role bootstrap**. The daemon supplies raw definitions plus fork/merge configuration to the supervisor, and the supervisor decides persistent versus ephemeral and whether to spawn. Code then provides a generic lifecycle class rather than needing a Go type for every new specialist ([daemon.go](../repo/internal/daemon/daemon.go), lines 1913–2018 and 1535–1664). This makes organization changes cheap to express as Markdown. It also makes reconciliation nondeterministic, lacks a durable desired-team specification, and uses naming heuristics for some lifecycle behavior. Wingman could reuse the separation of profile from instance while adding explicit role/team/host entities and deterministic instance reconciliation.

A third mechanism is the **terminal-as-agent transport**: persistent tmux keeps independent coding sessions alive, file mailboxes survive daemon intervals, and text insertion reuses the coding CLI's ordinary conversation interface. This avoids embedding an SDK or rebuilding a coding IDE while giving humans direct visibility. The implementation is inspectable and approachable ([socket.go](../repo/internal/socket/socket.go), 51–70; [messages.go](../repo/internal/messages/messages.go), 44–59; [tmux/client.go](../repo/pkg/tmux/client.go), 315–334). The limits are input-readiness uncertainty, shared-buffer concurrency, weak structured telemetry and process/conversation recovery boundaries. This is a distinctive combination in this checkout, not a claim of historical invention or industry uniqueness.

## Practical fit for Wingman

Wingman can reuse the local execution model. It assigns one instance to each coding conversation and isolates workers with worktrees. Named message addresses support coordination. Background supervision runs independently of the human view. Ephemeral workers have explicit completion. Integration agents remain separate from coding workers. These are compact, understandable mechanisms with concrete source and tests. Its PR-first delivery loop is particularly relevant once product scope and technical tickets already exist.

Direct adoption would need a Codex execution adapter, stable identities independent of tmux/PID lifetime, correct model-process monitoring, repository-namespaced prompt files and transactional provisioning/cleanup. Prompts currently use global `prompts/<agent-name>.md`, so common names such as supervisor can be overwritten across repositories and later reused on restart. This is a source-level cross-project isolation concern ([daemon.go](../repo/internal/daemon/daemon.go), 1624–1633, 2131–2139 and 2164–2171; [cli.go](../repo/internal/cli/cli.go), 5671–5685). Recovery should preserve every persistent role and named workspace, retry or surface failed transient work, retain conversation/mail history and distinguish health from mere pane existence. A host registry, authenticated network coordination and host-specific execution paths are needed for Mac/Endeavour operation.

Most of the organizational product remains to build:

- Butler's Telegram intake and answer routing.
- ProjectMaster's portfolio registry and supervision.
- real ProductMaster discovery and human clarification.
- TechMaster's shared tickets/dependencies.
- maintained product directives and acceptance evidence.
- Room1/Room2 chat.
- agent directory/relationships.
- executive current/recent/next/blocker summaries.
- per-agent timelines.
- connected project/dashboard/session navigation.

Adding new Markdown role prompts does not supply these shared data models or interfaces. Wingman also needs a completion policy that stops accepted product work and preserves continuity for later requests, rather than treating every self-completed worker as a finished delivery.

The strongest fit is therefore **an execution and GitHub-delivery reference beneath Wingman's own organization layer**. Using the CLI unchanged would give the human a capable terminal-centric multi-agent coding tool, while still requiring the human or another system to provide product understanding, organization-wide routing and the integrated management experience.
