Basis: independent static source review against Wingman's purpose. No application, agent, service or test was run.

Verdict

Strong candidate for Wingman's agent execution, coordination and detailed workspace layer; incomplete as its standing development organization. Orca is an Electron/TypeScript development workbench with a substantial host runtime, CLI, structured coding sessions, terminal workers, durable orchestration records, automation scheduling and real remote execution. It can launch independent coding workers, assign dependency-aware tasks, exchange durable messages, recover uncertain execution outcomes and show the actual session behind a fleet card.

The primitives do not supply the complete product organization. Missing capabilities include Telegram/Butler intake, continuing employee identities, extensible business roles and portfolio routing. They also include per-product ProductMaster/TechMaster leadership, adaptive discovery, shared organizational rooms and independent product acceptance. Its dashboard supplies useful session state, recent messages, questions and drill-down. It does not supply Wingman's complete narrative of each continuing agent's accomplished/current/planned work and its chronological summary feed.

Two boundaries materially affect adoption. First, the built-in Coordinator is a polling DAG dispatcher: its decomposition method requires tasks to exist already, and processEscalations() is empty. Model agents can create tasks using the CLI, but the class does not itself discover or plan a product (coordinator.ts, lines 142–161 and 210–228). Second, real federation is implemented, but local group broadcasts explicitly skip remote dispatches; direct addressing is required (send-group.ts, lines 35–53). Neither limitation negates the useful underlying capability.

Architecture and actual execution model

Entry points and ownership

The desktop entry registers IPC and starts initialization from Electron's app.whenReady() (index.ts, lines 157–172). Desktop startup constructs OrcaRuntimeService with the profile store, agent-hook identity observers, lazy PTY provider, persistent session-claim signer and remote orchestration transport. The same host is used for desktop and headless serve behavior (main-process-runtime-service.ts, lines 70–148). The separate Node orcad entry waits for daemon startup, constructs the runtime, registers headless PTY execution and restores host account selection before work can launch (orcad-entry.ts, lines 170–224 and 231–273). This is execution on a host, not a renderer pretending that a remote process is local.

The CLI parses and validates a command, resolves host/environment selection, and dispatches a handler through a lazily constructed RuntimeClient (CLI index, lines 94–159). For example, orchestration task-create reads literal/file specification text and sends orchestration.taskCreate. It does not implement its own task store (task-handlers.ts, lines 21–42). RPC methods perform run/caller admission and call the host's database and execution services. The renderer consumes these services and projects them into task/session/dashboard views.

Durable coordination versus execution resources

Orchestration uses a SQLite database, with WAL, busy timeout, schema migration, startup settlement reconciliation and file-permission hardening (orchestration-db.ts, lines 21–65). Profile/workspace/automation state also uses the application's Store; native conversation records and journals are distinct from orchestration task rows. Treating every persisted thing as an “agent memory” would obscure important boundaries.

The schema's entities establish the actual model (types.ts, lines 21–71, 113–167 and 182–227):

  • A Run is an objective with coordinator binding and consumer generation, not a product organization or employee.
  • A Task is specified work with readiness/status, parent and dependencies. A Dispatch is an assignment attempt. Retrying work can preserve its task while changing its dispatch.
  • A worker dispatch records execution stage, runtime epoch, setup, effects and residual resources. Its start_unknown/stop_unknown states preserve uncertainty.
  • A session is the provider conversation, represented by an Orca session address or terminal/pane/process identity. The process may stop while its conversation or output remains.
  • A mailbox delivery belongs to a run/dispatch and consumer generation. A question retains asker, dispatch, answer and state. These are coordination records, not a shared chat room by themselves.
  • A federated dispatch links the home task/attempt to a saved execution environment, peer fingerprint, remote runtime epoch and relay cursors. The execution host retains a corresponding attachment.

Workers have two execution surfaces: terminal/TUI launch or structured native chat. Both use a common launch executor; setup/worktree factories and recorded effects preserve orchestration-specific ownership (worker-start-agent-placement.ts, lines 1–24 and 78–145). This accommodates independent harnesses rather than making all specialists personas inside one model call. Specialist responsibilities, however, come from task/instructions rather than first-class organizational job definitions.

Agent definition and lifecycle

Definition, creation and execution

A worker launch combines specification or existing task, run/caller identity, launcher, optional model/effort, target host/workspace, setup and timeout. The schema requires exactly one of task/spec; retryOf cannot accompany a new specification because a new task is not a retry of the old task (start parameters, lines 11–59). Configured aliases must resolve to an accepted single executable on the target host, and launch validation rejects inconsistent reuse/creation options (preflight, lines 8–35; validation, lines 51–86 and 137–165). These are launcher definitions, not persistent job profiles.

Local start performs effect-free validation and resolves the caller's workspace before binding the run. It can reuse the current/exact workspace or create a new child/top-level worktree. An explicitly reused worker must be admitted before assignment. It then records the starting dispatch, runtime epoch and start options, including parent/helper ancestry and nesting limit (local start, lines 59–153; dispatch creation, lines 43–85).

Placement can reuse a live terminal, reopen an eligible previous worker for follow-up, or launch a fresh agent. If reopening safely refuses, fresh execution can receive the earlier work as task context instead of pretending it resumed the conversation (placement, lines 78–119). Setup, terminal creation and prompt readiness are separately recorded. Structured workers wait for setup and assignment delivery; TUI workers wait for actual composer readiness. An existing chat can accept queued work without waiting for a TUI idle state (local start, lines 170–239). The distinctions matter when an apparent launch success has not yet made the agent capable of receiving its assignment.

Identity, authority, tools and routing

Task, dispatch, conversation/session ID, terminal handle, stable pane key, process incarnation, runtime epoch and mailbox generation are separate identities. Dispatch claim checks task readiness, creator nesting depth and assignee occupancy, and records execution identity transactionally (dispatch store, lines 31–105). A worker's display name is therefore neither a durable employee identity nor authority to settle another worker's task.

Tool execution comes from the chosen coding harness, not from the role's name. Orca does implement provider-specific permissions: Codex Ask uses read-only/on-request; Auto uses workspace-write with automatic review; full access uses never/danger-full-access. Per-turn handling preserves or safely reacquires the appropriate sandbox rather than inventing a grant (permission policy, lines 21–46; turn admission, lines 19–38 and 53–79). Orca RPC workspace permission is a separate transport/API boundary. It should not be confused with the provider child's filesystem sandbox or organizational approval authority.

The assignment preamble gives exact task/dispatch/coordinator addresses and CLI recipes for questions, blockers and completion. It explicitly says that text left only in the worker terminal/chat does not reach the coordinator; after reporting, agents should idle rather than poll forever. It also instructs workers not to delegate unless the task asks (preamble, lines 64–95 and 138–165). These are behavioral instructions supported by runtime identity/depth checks. The prose itself is not an enforceable product process.

Mailbox consumption is generation-fenced inside the delivery transaction, using either a current run consumer or active local/remote dispatch consumer. Replacement consumers cannot acknowledge old ownership (mailbox-consumer.ts, lines 14–44). Run use rebinds a coordinator and cancels obsolete waiters while preserving explicit run context (runs.ts, lines 104–124). This protects continuation against stale processes; Wingman would still need the higher-level stable agent/profile ID.

Concurrency, scheduling, interruption and recovery

Workers may execute concurrently in different workspaces/runs, while atomic task claims prevent duplicate assignment. The built-in Coordinator polls every two seconds by default and allows four concurrent dispatched tasks. It creates at most one missing terminal per tick and checks base drift before assignment (coordinator.ts, lines 31–32 and 220–285). Its task queries are unscoped to run, so this class should not be treated as the portfolio/team isolation model. The legacy RPC gate surface also holds one globally active Coordinator rather than one per team or run (gates.ts, lines 14–28). The run-aware worker/RPC paths offer the more appropriate foundation.

AutomationService is a separate recurring-work mechanism: default one-minute evaluation, renderer/headless dispatchers, per-automation serialized lanes, completion observation and reconciliation of retained runs at startup (service.ts, lines 45–99 and 118–145). It can wake a configured supervisor. It does not define which projects to inspect or which blockers need human judgment.

User steering, queued sends, cancellation, rewind and provider conversation commands live in the structured session API. Resume is explicit: restart offers are scoped to client-readable agents, restartContinue asks eligible sessions to continue, and continueInterrupted targets an exact interrupted turn. Merely reattaching is deliberately not synonymous with starting work (session RPCs, lines 75–141; restart methods, lines 17–89).

Process stop is a distinct operation from completing a task or releasing its terminal resources. Remote stop requires a durable request and negotiates whether the host can prove its outcome. A disconnected/old host returns an unknown outcome, not a false “stopped” result (worker-stop.ts, lines 17–104). Runtime restart during a starting/stopping stage similarly produces start_unknown/stop_unknown on inspection (worker-control.ts, lines 55–67).

Failures escalate through a high-priority run mailbox without allowing notification failure to break primary failure handling. The polling coordinator's triage checks exact task/dispatch/sender ownership. A still-live supervised worker is not silently requeued, and repeated settled failures can trip a circuit breaker (failure escalation, lines 18–69; triage, lines 20–63). This is mechanical recovery and notification. It does not replace management investigation. The coordinator's higher-level escalation-processing function is empty.

Completion, acceptance and retirement

Worker completion is a typed, dispatch-bound success/failure report. Settlement validates existence, task/dispatch match, active/stale attempts, duplicates and conflicting live workers within lifecycle transactions. A firsthand report can also correct a prior unobserved-prompt failure rather than discarding real completion evidence (worker-report-settlement.ts, lines 61–160). Reporting while stopping or from the wrong process is refused; uncertainty itself need not prevent an exact worker from reporting (report admission, lines 4–46).

That is assignment accounting, not product acceptance. It establishes which attempt reported what, not whether an independent tester verified agreed business scenarios. Wingman should introduce explicit evidence and acceptance ownership above it. The fleet's distinct finished_unverified outcome is a useful reminder that provider-turn completion need not prove task success (outcome model, lines 3–8 and 31–57).

Release tracks execution-resource ownership, archival state and user retention. A transferred/external/user-kept resource must not be treated as disposable just because its process exited. Requested cleanup can be retried without inventing release intent; failed archival/endpoint work leaves the intent durable for a later pass (worker-release.ts, lines 20–91; release reconciliation, lines 24–41 and 65–104). Output reads distinguish retained archives from live identity-proven output (worker-control.ts, lines 118–167). Retirement here concerns attempts/processes/panes; retiring a continuing organizational role and reassigning its duties remains Wingman work.

Coordination trace: a task and its remote result

The following is an implemented request path traced through source, not an executed demonstration:

  1. A coordinator already running in a coding session creates/binds a run objective through orchestration.runCreate. The RPC captures the current terminal/pane/session identity (runs.ts, lines 30–61). This is explicit scope selection, not automatic product-intake classification.
  2. orca orchestration task-create reads the specification and sends its dependency/parent/run flags (CLI handler, lines 21–42). RPC resolves the current consumer, records creator authority and writes the task (message-methods.ts, lines 190–233). SQLite rejects cross-run parent/dependency references and starts it as ready only when dependencies are completed (task store, lines 25–83).
  3. A worker-start targeting a saved remote environment must carry a durable mutation request, use an exact remote workspace or new-top-level, and negotiate orchestration/federation/model capabilities. The home records the attempt and peer fingerprint before invoking orchestration.federationAttachStart on the execution server (federated-worker-start.ts, lines 43–112 and 114–165). Remote launchers and repository paths are resolved there, not inferred from the home machine.
  4. The worker receives its assignment and reports/asks using task and dispatch IDs. A question answer is stored under the owning run consumer, then either wakes the local worker or is enqueued as to_worker relay mail (reply RPC, lines 101–141). Logical management rooms would have to be built over these addressed exchanges.
  5. For completion, the home verifies that the saved environment still identifies the same peer, pulls bounded relay pages, rejects noncontiguous sequences, binds each imported message to its known dispatch/run, and applies lifecycle settlement. It then acknowledges only the safe sequence range, with runtime-epoch identity and settlement information (federation-sync.ts, lines 64–105, 125–179 and 182–225). This separates “message imported” from “remote settlement safely acknowledged.”
  6. Accepted task completion promotes newly unblocked dependencies (task store, lines 207–231). Resource release can follow independently. Dashboard cards route the human to the actual host/session, while higher-level delivery and acceptance still require Wingman policy.

A decision gate checks task/requester ownership and refuses an active supervised worker. Opening the gate stores the question/options and blocks the task within a savepoint. Resolution stores the answer and makes the task ready (gate store, lines 17–94 and 98–126). This is a stronger work-state boundary than a transient approval popup, but it needs a Butler/human transport and a product decision policy to become Wingman's escalation experience.

Major additional capabilities

A multi-harness workstation and external issue-management bridge. Wingman requires a rich per-agent workspace but does not prescribe GitHub/GitLab/Linear/Jira product integrations. Orca's TaskPage explicitly composes provider issue creation, mutations, lists/boards, repository selection and workspace actions (TaskPage.tsx, lines 1–41 and 44–85). This could connect Wingman tickets to existing engineering systems rather than creating another isolated tracker. The integration consequence is explicit ownership/synchronization of ticket IDs, statuses and acceptance records. These provider views are not evidence that the internal orchestration DAG already appears as Wingman's ProjectTracker.

A programmable plugin platform. Plugins have background workers, commands/events, panels, approval/capability resolution, content verification and audit hooks. The service supplies granted capabilities to workers, requires enabled/registered command handlers, and gates event delivery on approval (plugin-service.ts, lines 71–99 and 275–300). Host-call requests authenticate a qualified plugin identity, validate input and resolve policy before dispatch (plugin-host-call-adapter.ts, lines 25–52). This offers a possible extension seam for organization-specific UI and services. It also makes capabilities, worker lifecycle and client compatibility part of the integration; no claim is made that an existing plugin supplies Butler or room semantics.

Integrated browser observation/control. The runtime exposes navigation, DOM actions, pointer input, screenshots/PDF/capture, console/evaluation, network controls, storage and profiles (browser-commands.ts, lines 17–95). Capture resolves an explicit browser/workspace target and delegates through the installed browser bridge (browser-capture.ts, lines 21–78). That can equip TestMaster's browser verification with a shared inspectable surface. Wingman still needs test planning, assertions, evidence retention and acceptance decisions, and bridge availability is a runtime dependency.

Searchable historical coding sessions. Session search returns scoped hits with evidence snippet, role/timestamp, source presence and, when available, a resume command. It rejects unknown host scope and stale/malformed cursors (session-search-service.ts, lines 24–107). This is valuable for rediscovering previous reasoning across workspaces. Integration must distinguish retrieved conversation evidence from authoritative specifications and decisions; search results do not themselves maintain a curated project knowledge base.

Distributed lifecycle engineering beyond simply opening SSH terminals. Saved peer fingerprints, versioned capabilities, runtime epochs, import/ack cursors and remote settlement let the home coordinate execution on another server (federated launch, lines 73–112 and 146–165; synchronization, lines 73–105 and 182–225). Wingman already asks for multi-host execution. The extra value is this explicit compatibility/recovery protocol. Adopting it also adopts pairing, protocol rollout, connectivity and reconciliation obligations. It should not be extended into claims of transparent distributed rooms or automatic cross-host filesystem consistency.

Distinctive mechanisms and innovation assessment

These are grounded engineering mechanisms worth reusing, not claims of historical novelty:

  1. Work is separated from attempt and process. The task survives retries while each dispatch carries creator/assignee authority and execution observations. Atomic ready-task claims and failure-count carryover prevent two schedulers from casually treating the same work as two fresh assignments (dispatch store, lines 31–105). This is directly useful for an agent organization that replaces workers. It does not supply product requirements or decide whether two assignments are semantically duplicates.
  2. Mailbox consumers are fenced by generation. Validation occurs inside the delivery transaction, so a stale coordinator cannot continue acting as the current consumer after replacement (mailbox consumer, lines 14–44). That is stronger than routing solely by a friendly name. The higher-level employee identity and authorization policy remain separate.
  3. Unknown is a durable outcome. Launch/stop uncertainty, runtime epochs and exact process observations avoid converting a network timeout into proof of process death (types, lines 142–167; stop, lines 48–104). This reduces duplicate work and unsafe cleanup. The price is visible unresolved state and a need for eventual reconciliation rather than a simple green/red status model.
  4. Mutation receipts preserve retry meaning. A request is keyed by caller fingerprint/request ID and checked against method/payload hash in BEGIN IMMEDIATE; reusing the ID with different input fails. Completed/pending receipts are returned distinctly (mutation-receipt-store.ts, lines 35–108). This is useful after dropped RPC responses. It is not a blanket exactly-once guarantee for arbitrary external tool effects.
  5. Federated import and acknowledgement are different facts. The home can retain imported data while postponing acknowledgement until compatible lifecycle settlement is safe; peer and epoch checks prevent changed servers from inheriting old authority (federation sync, lines 73–105 and 150–225). This addresses a concrete distributed recovery problem. It cannot by itself resolve product-level disagreement or file merge conflicts.
  6. Cleanup requires recorded intent and resource ownership. Release reconciliation retries only requested/releasing resources, preserving evidence and user retention instead of inferring disposal authority from discovery (release reconciliation, lines 24–41 and 65–104). Wingman should carry this separation into retiring workers, conversations and workspaces.

Practical fit and adoption consequences

Use directly, subject to runtime validation: independent Codex/harness session launch, worker task/attempt accounting, structured send/queue/cancel/resume, workspace placement, durable messages/questions, scheduled launches, remote worker execution and dashboard-to-session inspection. These are the parts most expensive to reconstruct correctly, especially under restart and connection loss.

Adapt around a stable Wingman domain model: employee/profile IDs separate from Orca sessions, project IDs separate from runs/repos/worktrees, leadership/team membership separate from execution ancestry, and product tickets/acceptance evidence separate from dispatch success. Map these identities deliberately so an archived session does not retire an employee and a retried task does not become a new product. Use addressed run/dispatch mail underneath organizational rooms; bridge remote participants explicitly because local group fan-out does not cover them.

Build the missing organization:

  • Telegram Butler and contextual question routing.
  • Cross-project intake/registry.
  • Product discovery and clarification records.
  • Scoped ProductMaster/TechMaster duties.
  • Shared room history/membership.
  • ProductTracker portfolio views.
  • Durable directives and decision provenance.
  • Executive current/recent/planned summaries and linked per-agent timeline.
  • Independent integrated verification and human acceptance/delivery rules. Schedules can wake ProjectMaster, but its actual review and follow-up responsibilities must be implemented in instructions and shared records.

Extraction is not a small library import. Worker placement depends on runtime services, the profile store, provider launch adapters, SQLite, workspace/setup policy, signed process identity and renderer/client capability negotiation. Federation and structured sessions carry mixed-version behavior that Wingman would have to maintain. A full-workbench foundation offers the richest detailed workspace quickly; selective borrowing keeps Wingman's organizational model independent but requires rebuilding these integration contracts. This report supports a focused prototype of execution/inspection integration, not a claim that dropping in Orca completes Wingman.

Verification scope and limits

Read applicable Orca root and daemon AGENTS.md; reviewed source without modifying the checkout. Confirmed Git remote and actual HEAD locally. The earlier draft was not treated as evidence. Architecture findings come from desktop/Node startup, CLI entry/handler, runtime RPCs, orchestration schema/store, launch/placement/readiness, permissions, messaging/gates, coordination/retry/settlement, automation, federation and dashboard/native-session code linked above.

Relevant test bodies inspected, not executed:

  • Coordinator tests, lines 149–187, assert no-task failure and dispatch/completion using a mocked runtime and fake timers. They support the decomposition boundary and intended orchestration flow, not real provider execution.
  • Automation durability tests, lines 56–145, assert deduplicated occurrences, persistence-before-dispatch, refusal on disk failure and no redispatch after an interrupted schedule advancement. These inspect intended durability behavior, not a passing result here.
  • Release ownership tests, lines 12–67, assert retention of user-kept/transferred/external resources and explicit unavailable archives.
  • Federation settlement tests, lines 130–181 and 227–259, drive a remote report through worker/home dispatchers with simulated transport and assert home-authoritative success or task-mismatch rejection. These are intended protocol tests, not a real Mac/Windows network exercise.

Negative/partial findings used case-insensitive searches for Telegram, Butler, ProductMaster/ProjectMaster/TechMaster, room names, acceptance criteria/definition of done, discovery and timeline concepts across likely implementation paths. The review then inspected run/task stores, preambles/questions/gates, coordinator, profile/launcher/provider contracts, TaskPage and dashboard schema/cards. A Telegram token appeared only as an agent-hook test platform value, not an implemented transport. Existing issue text mentioning acceptance criteria was not credited as a product acceptance system. Timeline/transcript UI and journals were not credited as Wingman's synthesized agent feed.

No dependencies were installed, services started, credentials inspected, providers invoked or tests run. Runtime readiness, protocol behavior under real disconnection, native UI rendering, performance and compatibility with the user's installed harnesses remain unverified. Plugin interfaces are credited as extension mechanisms; uninspected or third-party plugins are not credited with missing organization features.

Retained Orca experiment evidence

Scope

Useful findings

A Run is a durable coordination namespace. A Dispatch identifies one execution attempt. Mail uses those identities for ownership and routing. Completion must come from the worker that owns the attempt. A successful task can unlock dependent work. A failed task cannot satisfy a success dependency.

The main snapshot consumes a normal mailbox check with a mutation receipt. The older inspected release required explicit acknowledgment. Do not apply one release's acknowledgment behavior to every release. Consumption still does not prove that the model understood a message.

Remote workers route control mail to the Run's home coordinator. This differs from unrestricted remote peer messaging. Generation checks and receipts limit stale reports and repeated mutations. They do not guarantee exactly-once effects in external tools.
