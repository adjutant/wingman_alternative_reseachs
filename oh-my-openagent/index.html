oh-my-openagent assessment against Wingman

Assessed 2026-11-05, from the local checkout at researchs/oh-my-openagent/repo, commit 8c9e1a991b3603dca14dd1a8dd6ebcaeff2cd26f. The checkout's origin is https://github.com/code-yeongyu/oh-my-openagent.git and its complete GitHub URL is https://github.com/code-yeongyu/oh-my-openagent. Root package metadata reports version 5.1.60, still named oh-my-opencode; oh-my-openagent, lazycodex, and lazycodex-ai are aliases in the same distribution. This assessment concerns that revision, not the current hosted product or a release inferred from documentation.

Verdict: a substantial source of execution, planning, coordination, memory, and verification mechanisms, but not a replacement for Wingman's persistent development organization. It has real independently executing coding sessions, named teams, durable mailboxes and tasks, dependency scheduling, cross-session addressing, and increasingly sophisticated lifecycle recovery. Its strongest organizational equivalents are a task leader and resident team members within a workspace. It does not establish Butler, a portfolio-owning ProjectMaster, persistent product/technical leadership per project, a product registry, Room1/Room2 chat application, or Wingman's executive and project dashboards. Codex support is real but is a lighter, host-dependent edition. The extensive native lifecycle implementation is Senpi-dependent, not a Codex orchestration backend ready to adopt unchanged.

Scope and evidence conventions

The implementation is now a multi-harness monorepo. Treating the whole checkout as the old OpenCode plugin would miss major capabilities; treating every capability as available identically in Codex would overstate it. Findings distinguish OpenCode, Codex Light, and Senpi/native. The native omo launcher stages the Senpi adapter and runs an exact-pinned external Senpi engine. The actual Senpi host/supervisor and the external remote-device service are not fully implemented in this checkout. A local RPC “host” is a process endpoint, not evidence of execution on another machine.

Architecture and actual execution model

There are three materially different integrations. OpenCode loads a plugin module into an existing OpenCode server/session lifecycle. Startup migrates legacy workspace/configuration state, validates merged configuration and creates background, skills/MCP, tmux and optional monitor managers. Tool factories and hooks adapt the server's session API. The LLM loop, credentials, conversation store and base coding environment belong to OpenCode. A specialist is initially an AgentConfig/prompt/model policy. It becomes an independently running agent session only when the delegation or team runtime calls client.session.create and sends its task prompt. The parent can continue while that child executes. The queue and live task bookkeeping are largely manager memory, while host sessions and selected project records persist separately (E01–E04, E17).

Codex Light registers the omo plugin namespace, with rules, LSP, comment checking, workflow/continuation hooks and shared skills. Its team implementation stores a team manifest and invokes capabilities supplied by the Codex host: native flat agents addressed through /root/<task_name>, or actual Codex App threads addressed by thread ID. Transport identity is persisted and checked rather than silently mixing address types. The team script prepares state, guides and optional git worktrees. The skill instructs the model to call the host's spawn/message tools. It does not embed the OpenCode background manager or the Senpi task engine into Codex. That distinction matters for Wingman's requirement that all organizational roles be real Codex agents (E21).

Senpi/native is the most extensive execution substrate in this revision. The native omo distribution launches the pinned external Senpi engine with a staged TypeScript extension. Its task component wires the senpi-task manager to real child sessions, record persistence, concurrency, steering, lifecycle reconciliation, teams, DAGs and workpools. A child can be a separate session in the same JS process, an RPC subprocess, or a session in a local engine host. “In-process” still creates a real conversation with its own transcript. It is not merely asking the parent's model to pretend to be another role. It does share execution resources and permitted tool closures, so it is not an OS isolation boundary. Process-mode auto routing checks host capabilities and otherwise selects in-process; explicit per-spawn/agent choices take precedence (E07–E12).

Shared packages hold harness-neutral pieces: team-core, memory-core, model-core, boulder-state, hashline-core, rules/AGENTS discovery, MCP/LSP and skills. senpi-task is deliberately adapter-coupled. It is not another neutral core. The checked-in packages/web app is a marketing/docs/download site: its routes are localized landing/docs/support/download/design pages and download/stat APIs. It is not an organizational project dashboard. References to a Desktop surface and session shards expose integration contracts. This checkout does not contain a complete Wingman-style desktop workbench UI.

Agent definition and lifecycle walkthrough

Definition, creation and identity

A profile is a reusable model/prompt/tool policy. An instance is a created conversation/session with an assignment. A task is a managed execution record; its ID differs from the child session ID. A team member adds a member name and team-run association. A process may host one or many sessions. A memory identity selects persistent knowledge and is not itself proof of a running employee. These distinctions are explicit in the native task states and thread address book (E07–E09, E13).

OpenCode builtins are factory-built host agent configurations. Delegation chooses an agent or task category and skills. The background manager reserves descendant/depth capacity, creates a bg_* record in pending state, records parent/root lineage, queues by resolved concurrency key and returns promptly. Once a slot is available it creates a real child session in input.cwd or the parent directory, attaching parentID, title, permissions and selected model. It binds the returned session to the current attempt before starting polling/prompt delivery. A profile existing in the agent list does not mean a standing instance is already running (E02).

OpenCode team creation loads/normalizes a TeamSpec and runtime UUID. It can reuse the caller as lead, creates inbox directories, resolves each category/agent and launches members through the same background manager. Each sessionID is registered immediately through the launch callback, before later hooks might look it up; that closes the race between spawning and persisting a member. On partial failure it cancels acquired children and removes resources with an explicit cleanup report (E03–E04).

Native agent definitions are more general: named configuration overlays can change description, prompt, model list/distribution, tools, background status, execution mode, allowed subagents and turn/depth policy. Research/plan-review builtin agents are pinned in-process, so process mode does not accidentally omit their persona/tool restrictions. Native tasks maintain task_id, parent/root/child session identity, run epoch, resolved/effective model, residency, host/session attachment and spawn specification. The manager seeds its ID floor from stored records and separates live handles from durable records (E07–E09). Named-team creation persists a member-task mapping before declaring the team active; otherwise failed sidecar writes could leave uncancellable live members. The current session is the lead sentinel. Actual member spawn code forces process mode and supplies its scoped mailbox extension (E10). An older comment in team/runtime.ts still describes in-process members. The executable spawn-members.ts:149 is the decisive evidence.

Codex teammode has another identity model: durable team manifest plus immutable transport. On V2 it binds task name and canonical agent path; on Codex App it binds a real thread ID. The scripts validate identity and guide bootstrap/routing but do not manufacture missing host APIs. A fallback from one transport to the other is a new orchestration choice, not a transparently shared runtime (E21).

Execution, tools, routing and concurrency

OpenCode children run through the host session API. Agent restrictions include read-only research/consultation roles, delegation restrictions for some executors and team-tool restrictions; team creation also denies direct child questions so decisions route through the lead. These are tool/host permission and hook policies, not independent OS sandboxes. See agent-tool-restrictions.ts, lines 9–75, and E04 lines 194–208. Some policies live in prompts, some in tool lists, and some in actual guards; their enforcement strength differs.

Native in-process execution calls Senpi createAgentSession, builds a child SessionManager with lineage and a dedicated transcript directory, filters shared parent tools and applies trust/model policy. RPC execution launches a child with an isolated session directory and tracked async prompt, with steering/abort over the protocol. Host-session mode is selected only after supported capability checks. Model/category selection, model availability and fallback belong to an execution planner. A role name is not synonymous with one hardcoded model. Routing and spawn restrictions also apply to DAG agent nodes so graph execution cannot bypass the direct task policy (E07, E09, E19).

OpenCode's default concurrency is five per resolved key, with model overrides taking precedence over provider overrides and a zero meaning unlimited. FIFO queues hand released slots to waiting tasks. Team max_parallel_members bounds the creation worker loop, not a proof of a global lifetime cap across all teams; model/provider queues and spawn guards enforce separate limits. Native concurrency also supports configured global/provider/model limits and distinguishes active execution from resident sessions. A completed but resident member may still be messageable and consume residency until eviction/cleanup. No admission system here is an organization-wide fair scheduler across products (E02, E04, E08–E10).

Workspace isolation requires following the specific path. The core has real detached git worktree creation and Codex teammode has real provisioning/integration. OpenCode createMemberWorktree, and native team spawnOneMember, simply mkdir a supplied path then use it as cwd. Declaring worktreePath there does not prove an isolated checkout was created. Native task isolation separately provides baseline/clone/settle/salvage integration through isolation-core: prepare.ts, lines 27–73, refuses a spawn when it cannot establish the sandbox; settle.ts, lines 19–57 and 78–90, controls merge and retain/cleanup. Wingman should deliberately select and test that path rather than infer isolation from team metadata (E04, E10, E23).

Persistence, resumption and scheduling

Core team specs are project- or user-scoped configuration. Default runtime data is under ~/.omo/runtime/<teamRunId>/state.json, inboxes/<member>/ and tasks/<decimal-id>.json; worktrees use a separate root. This is confirmed by path functions, and supersedes an older team AGENTS example showing JSONL mailboxes beneath the team spec. Native tasks default to a project-derived directory under the canonical agent home, preserve an existing project .omo/senpi-task store when appropriate, and allow task.state_dir overrides. Its team base is inside that task store. Thus shared state is durable local filesystem state with locks, not a network coordination service (E03, E08, E10).

OpenCode can continue existing child sessions and uses compaction-aware result retrieval and bounded task history, but its active maps, queue and history are process memory. Host conversation persistence and a persisted team state are not equivalent to automatic reconstruction of the full background manager after arbitrary process death. Native lifecycle is stronger: session-start wiring reconciles children, re-observes member liveness, recovers mailbox reservations, redelivers unnotified completions, performs awaited TTL cleanup and polls the lead. Reconciliation checks live foreign ownership before terminality/residency and refuses to seize sibling-owned tasks. Scoped revival targets the resumed parent, preserving other sessions' children (E11, E17).

Scheduling is principally event-driven: asynchronous completion wakes a parent, resident member mail wakes/steers the recipient, idle hooks continue unfinished goals, and DAG frontier admission starts dependents when ready. These are useful persistent-work mechanisms. They are not a cron-driven ProjectMaster that wakes tomorrow, reads all products and initiates management follow-up. Optional monitors start long-running commands and batch observations into the owning session. They are closer to CI/log watching than organization supervision (E10–E12, E18–E19).

Steering, cancellation, failure and recovery

OpenCode cancellation distinguishes pending queue removal from running session abort. It finalizes the attempt, releases concurrency, updates history/continuation markers and notifies or schedules removal. Failure handling includes fallback attempts, stale-task/session checks and loop guards. Attempt/session binding prevents stale callbacks from overwriting a later attempt. Native steering resolves task/name, sends into a running child or revives an eligible resident conversation; non-continuable state produces a typed refusal rather than silently spawning a replacement. Thread tools additionally expose interrupt and model/reasoning changes through supported host APIs (E02, E08, E12–E13).

Native lifecycle separates task status (pending, running, paused, completed, error, cancelled, interrupted, lost) from residency (resident, evicted, disposed, persisted_only, rpc_detached). An interrupted task is not inherently dead forever, and a completed task is not inherently destroyed. Shutdown is reason-aware; owned host-session tasks can keep running when the parent quits/new-sessions, while other children suspend for later revival according to configuration and context. The bridge warns the user about continuing children and resume instructions. resume_children=false selects disposal semantics. Reconciliation, run epochs and ownership fences are necessary because multiple local processes/sessions may read the same store (E08, E11–E12).

Completion delivery distinguishes idle parent wake, streaming delivery at a safe boundary and buffering during compaction/session switch/shutdown. Normal completion/error/lost notify; parent-requested cancellation/interruption already returns synchronously and does not generate the same notification. Durable receipts, run epochs and transcript confirmation support deduplication/recovery, but they should not be described as universal exactly-once execution of arbitrary tool side effects (E10–E13).

Completion, acceptance, retirement and cleanup

A child becoming idle/completed establishes an execution outcome, not product acceptance. The core team-task completion transition checks the supplied owner and lifecycle. Native member sessions receive only the scoped task_send coordination tool. The lead therefore calls the completion service for a member, using messages or other evidence. This is not automatic completion by the working member or independent validation of the result. DAG completion means graph nodes reached their terminal contract. The scheduler can mark failed dependent branches skipped. ULW adds a stronger optional evidence contract: criteria must pass, required batches close, reviewer/QA fields validate and artifacts/report paths exist before a final aggregate checkpoint. The validator still cannot decide whether a screenshot proves the desired behavior or a test oracle is correct. Independent reviewer work and honest evidence generation remain essential (E06, E12, E16, E19).

Resident team members end turns while remaining available for injected work; shutdown uses request/approve/reject messaging, and team deletion cancels mapped members and removes runtime directories. Native TTL cleanup uses a two-phase process and retains live ownership or undelivered terminal notification state so pruning does not orphan a handle or lose a result. OpenCode has bounded terminal/archive retention and process cleanup rather than a standing employee retirement record. Wingman must separately preserve employment/role history, product acceptance, deactivation and future reactivation policy (E10–E11, E17).

Coordination mechanics and a concrete code trace

Consider a lead organizing backend and frontend implementation. The following is a source trace through the real Senpi team path, not an executed demonstration or a claim that natural-language intake automatically creates such a team.

  1. The team tool resolves/normalizes a named or inline TeamSpec. createTeam checks member bounds before spawning, writes creating state, creates inbox/runtime directories and invokes spawnTeamMembers. The caller remains lead; backend/frontend are distinct named member instances, not two labels inside the lead prompt (E10).
  2. spawnOneMember builds a process-mode background start request with parent/root IDs, member-specific task name, team identifiers, prompt and optional cwd. It waits for slow admission when needed, then records the real task/session identity. The bootstrap tells the member to report with task_send, end its turn and await injected work (E10, spawn-members.ts:99–178).
  3. The lead creates shared tasks such as “API contract” and “UI integration,” making the latter blocked by the former, and assigns/updates them with the intended member owner. In this native trace the member reports progress/completion through task_send. It cannot call the lead's task_create/task_update surface. team-service.ts:202–205 passes the supplied owner to the core claim/status primitive on the lead's behalf. The claim primitive checks status/dependencies, takes the task lock, rereads both and atomically writes owner/claimed time, preventing two successful claims. These library guarantees do not establish native member self-service task claiming or owner-authenticated completion (E03, E06).
  4. The backend member reports the API contract through a durable message to frontend/lead. sendMessage validates recipients and limits, serializes one JSON message, locks the recipient inbox and accounts for reserved deliveries when checking backpressure. Broadcast requires lead role. Structured references can point to artifacts, but they are references rather than a foreign-key ticket/chat system (E03, E05).
  5. Member self-polling acquires an inbox consumer lease and reserves a message by renaming it to .delivering-<id>.json. Injection does not immediately count as acknowledgment. The poller checks the session JSONL for the message ID before moving the reservation into processed/. On restart it can distinguish a transcript-confirmed prior delivery from a reservation needing recovery. This is a material improvement over tailing a shared text file and assuming the model saw it (E05, E10).
  6. Native task completion routes a wake/steer/buffer notification to the lead depending on its actual state. The lead can inspect output, steer another turn, create follow-up tasks or initiate QA. If the lead's session restarts, the adapter's ordered recovery chain reconstructs task ownership/liveness and redelivery. These mechanisms recover coordination, not a forgotten product requirement that was never written down (E11–E12).
  7. The lead records evidence and closes work via ULW if that workflow was selected, or simply updates team tasks otherwise. The difference is consequential: only the former calls the evidence validators. On acceptance/stop it uses the shutdown handshake or deletion; no automatic ProductMaster acceptance or organization-wide archival follows (E06, E10, E16).

Cross-session collaboration outside a team uses another mechanism. Native thread_send/thread_handoff resolve a durable session address from live endpoints plus disk sessions, write durable gateway deliveries/receipts, and wake a registered receiver or leave work queued offline. The SQLite schema records state (queued through applied/refused/uncertain), per-target sequence and causal edges, rather than equating a successful socket write with execution. The relay layer binds an external conversation to a session and supplies outbox cursors, idempotent acknowledgments and binding-scoped reply tokens. This is promising for Butler's transport and human-decision continuity, but the business routing and Telegram connector still need to be supplied (E13–E14).

Major capabilities beyond Wingman's described scope

Dependency-frontier DAG execution and reusable worker pools. The native DAG engine journals run/node transitions and admits every ready node through the task manager instead of waiting for an entire presentation “wave” to finish. It can suspend a controller without cancelling children, reattach owned work, send to a node and retry failed/cancelled/skipped nodes with a new scheduler. Failure cascade waits until frontier quiescence, permitting an eligible failed task to be revived while siblings still run. senpi-task/src/workpool/engine.ts additionally creates durable named pools, queues items, exposes push/close/cancel and worker yield/results, with dispatcher/policy integration. Wingman describes tasks and independent workers but not these reusable execution engines. Adapting them could improve throughput and recovery. It would also import Senpi coupling and require translation into project/ticket identities (E19; workpool engine, lines 18–19, 61, 95–103 and 156–168).

Versioned agent memory and background maintenance. The memory engine is much more than a product documentation directory. It has git-backed MemFS, committed-revision prompt compilation, explicit persona/identity, expiry, transcript search, people records, facts/reflection pipelines and agreement governance. Compiling only a committed revision prevents uncommitted edits from silently changing authoritative memory. Background reflection uses separate execution/merge machinery. It is not the same as a ProductMaster maintaining requirements. Reuse could help organizational continuity, but Wingman needs separate namespaces for human preferences, agent-private memory, shared product truth and approved specifications (E20 and memory-core source map, lines 7–42).

Durable session gateway and external conversation relay. Addressing terminal, child, desktop and daemon sessions through durable IDs plus endpoint-specific routing is a stronger primitive than terminal injection. Queued-offline work, receipt recovery, causal loop controls, outbox cursors and question reply scoping are valuable for reliable coordination. These contracts could underpin Butler and human decisions, but platform vocabulary such as telegram in a schema is not a delivered Telegram user experience. External connectors and authenticated human/project routing remain integration work (E13).

Model routing, host interoperability and coding intelligence. The project bundles provider/model fallback, category-based routing, shared LSP services/MCP tools, structural search/edit support, Claude-compatible configuration/skill loaders and rules injection. These can make each execution agent more capable and efficient without being part of Wingman's organization specification. Their cost is configuration/model-version churn and edition-specific behavior. A Codex-first Wingman should adopt selected pieces through explicit adapters, not install the whole OpenCode/Senpi stack and assume parity (E01, E07, E09, E21).

Computer-use execution and process observation. Additional desktop packages implement protocol/engine/service/tool layers for computer actions and observations, while OpenCode's monitor engine manages continuous command output. The desktop service is an execution capability, not a dashboard showing the agent organization. These could expand TestMaster's real-surface QA, but require independent host permission, lifecycle and platform validation. This assessment inspected the package boundaries and desktop service, lines 33–100, desktop tool exports, lines 1–57, and monitor code. It did not deeply audit the desktop engine or exercise computer control (E18).

Native distribution and device observation. Canonical agent state, setup/import, daemon lifecycle and remote-session observation are significant operational capabilities. They help make local agents usable beyond an individual terminal. However remote release bootstrap is deliberately fail-closed at this revision, and remote input is explicitly unavailable. Wingman cannot treat the remote client scaffold or external service promise as implemented distributed organizational execution (E22).

Grounded innovation assessment

Several mechanisms are especially worth learning from. These are claims about this implementation's design, not historical novelty or uniqueness across the industry.

  • Delivery acknowledgment follows durable conversation evidence. Team mail remains reserved until its message ID appears in the recipient transcript; consumer leases and processed history support recovery. This ties delivery state to the actual conversation rather than a best-effort enqueue. Limits include local filesystem semantics, retained transcript availability and no guarantee that the model correctly understood or acted on the message (E05, E10).
  • Task execution, residency and ownership are separate axes. Native tasks can be completed yet resident, detached from an RPC host, suspended or awaiting input. Reconciliation checks live owners and run epochs before revival; DAG controllers can retire without terminating their children. That separation enables restart and host lifecycle recovery without pretending every ended turn is agent retirement. It also creates a complex state space and substantial adapter obligations (E08–E12, E19).
  • Cross-session messaging represents uncertainty explicitly. Gateway receipts and delivery states distinguish admitted/applied from queued or uncertain; durable session IDs are separate from per-endpoint routing IDs. An offline target can remain addressable. This is a useful basis for reliable agent collaboration, but arbitrary tool side effects still require their own idempotency/acceptance contract (E13).
  • Evidence-gated completion is partly executable policy. ULW validators inspect criteria coverage, expected reviewer identities, required QA/report artifacts and blocker state, and repeated authorization failures become a human-decision state. This is stronger than a completion instruction in a prompt. Evidence content remains agent-authored, and surface-specific gates differ: native Senpi currently rejects the Codex codeReview lane instead of sharing every field identically (E16).
  • Memory governance preserves human-authored rules. Committed-revision compilation plus immutable human agreement entries and nondecreasing violation counts gives the human's durable directions stronger protection than generic append-only notes. This is directly relevant to Wingman's standing relationship with one person. It does not replace human ownership of product scope or ensure every agent consults the correct project namespace (E20).
  • Hashline edits detect stale read assumptions. The edit protocol compares line/content fingerprints and returns updated context/remappings on mismatch. That provides a low-level optimistic concurrency check useful when multiple agents touch code. Two-character fingerprints are a heuristic, and this does not serialize whole-file transactions or solve semantic merge conflicts; work ownership and isolated integration are still needed (E23).

Practical fit and integration consequences

Wingman could use the Codex Light team scripts and workflow components most directly: they already reason about real Codex agents versus App threads, durable team manifests, communication addresses, worktrees and integration. The planning templates and QA/evidence contract are also useful design inputs. They should be evaluated as components in Wingman's own authorized agent runtime, with explicit host capability detection and persistence tests. The implementation's own distinction between a member profile and a running bound instance should carry through to Wingman's directory.

The most reusable neutral mechanisms are team/task/mailbox schema and locking, boulder plan progress, memory compilation/governance, rules/AGENTS discovery, hashline validation and selected LSP/MCP components. Their data should map to Wingman-owned agent_instance_id, project_id, ticket and conversation identities. Team-run UUIDs and session IDs should remain execution attachments, so retiring a run does not erase an employee's or project's history. A unified event projection could turn these low-level records into directory, tracker, chat and timeline views.

The Senpi task lifecycle, DAG/workpool and peer gateway offer the deepest machinery, but require adaptation or reimplementation for a Codex-only organization. Their external engine APIs, capabilities, session files, control endpoints and shutdown semantics are part of the contract. A wrapper that merely renames tool calls would not preserve revival, ownership or delivery guarantees. The native remote device client should remain an experimental integration until acquisition, the external service and actual cross-host execution/coordination are verified.

Wingman still needs its core application layer:

  • Telegram Butler intake.
  • a persistent project registry.
  • new/existing project resolution.
  • standing organization identities.
  • per-project product and technical leads.
  • durable discovery questions/answers.
  • maintained product directives.
  • shared ProjectTracker and room history.
  • periodic portfolio supervision.
  • navigable executive/project/agent views.

It also needs product-level acceptance/delivery and quiescence after acceptance. Existing task completion and ULW aggregate completion can feed that policy but do not define it.

Reuse must account for licensing. The root LICENSE.md, lines 3–8 and 24–29, uses the Sustainable Use License for content outside separately licensed components, with internal-business/personal/noncommercial use and distribution restrictions. The Codex plugin manifest says MIT (E21 line 12), which is insufficient evidence that every source file proposed for reuse is MIT. This is a repository inconsistency requiring component-level provenance review before redistribution, not a claim of legal clearance. No external legal interpretation was performed.
