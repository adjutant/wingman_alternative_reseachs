CompanyHelm assessment against Wingman

  • Product: CompanyHelm, a distributed coding-agent control plane and company workspace.
  • Repository: https://github.com/CompanyHelm/companyhelm
  • Local checkout: research/companyhelm/repo.
  • Assessed commit: 8651f20e14b3fa0daa4d11e56abca0981554532b.
  • Assessment date: 2026-11-05.
  • Method: Read-only source and test inspection; no dependency installation, service startup, model calls, browser session, or execution of tests. Findings concern this checkout, not the hosted service.

Fit verdict: CompanyHelm is a substantial candidate for Wingman's execution, persistence, task, conversation and detailed-workspace infrastructure. Its agents are durable identities with independently executable sessions, not merely named prompts, and those sessions can exchange messages, create more agents, execute tasks and run scheduled workflows. However, the product implements a general company workspace around coding sessions, rather than Wingman's continuing product-development organization. Telegram/Butler, a project registry, project-specific product and technical leadership, management rooms, portfolio supervision, acceptance governance and executive agent briefings still need implementation. The biggest infrastructure mismatch is execution placement: the concrete remote compute provider is E2B Linux, and the separately published runner CLI does not execute work on the user's Mac and Endeavour machines.

The distinction matters for adoption. The code already supplies many difficult platform mechanisms; adding role prompts alone would not supply Wingman's missing organizational behavior. Conversely, dismissing CompanyHelm as a chat UI would understate its durable task runs, transaction-scoped agent messaging, runtime reconstruction, scheduling, remote environments and artifact records.

Architecture and actual execution model

The TypeScript monorepo has a Fastify/Mercurius GraphQL API, a React/Relay web application and a standalone runner package. API startup lines 19–29 loads configuration, builds the dependency container, runs database bootstrap and starts the server. ApiServer lines 190–234 registers GraphQL, authentication, GitHub webhook and environment terminal routes, then starts in-process BullMQ consumers for sessions, schedules, usage, GitHub events, skill updates, deletion and environment metrics. The durable control plane is PostgreSQL through Drizzle; Redis supplies queueing, live publication and session ownership. These are real deployment dependencies, not an optional Markdown-only mode.

Web UI / GraphQL mutation / agent tool / GitHub event / cron
    → company-scoped PostgreSQL state and queued message
    → Redis/BullMQ wake job
    → worker acquires Redis session lease
    → reconstruct PI Mono agent runtime from stored context
    → model + CompanyHelm custom tools
        → remote E2B environment for shell/files/desktop
        → tasks, artifacts, skills, inbox and agent messages
    → persist transcript, tools, context and usage; publish updates
    → dispose runtime, release lease, wake again if work remains

SessionPromptService lines 67–227 persists a prompt and attribution before notifying execution; SessionProcessExecutionService lines 122–408 coordinates one leased processing pass. The worker lines 58–101 uses configured concurrency. The lease implementation lines 19–79 uses token-checked heartbeat/release operations. Consequently, multiple worker processes may consume the shared queue, while a session has one live owner. This is distributed control-plane infrastructure. It is not proof of a supplied heterogeneous local-runner fleet.

The LLM loop itself runs in the API worker through @mariozechner/pi-coding-agent, rather than launching a local Codex CLI per agent. PiMonoSessionManagerService lines 180–288 creates an in-memory SDK session, restores PostgreSQL context, resolves model credentials and registers custom tools. It explicitly disables PI's built-in tools. Codex OAuth is a model credential/provider path here, not evidence of Codex desktop session parity. Shell, file patching and computer use are CompanyHelm adapters into the execution environment.

Remote execution is concrete: E2B provider lines 79–143 creates Linux sandboxes, tags them with company/agent/session identity and enables pause-on-timeout with auto-resume. But the README's claim that every agent session gets a fresh VM is broader than the implementation. Environment selection lines 40–103 first searches session lease history, then agent lease history, skipping leased or unhealthy environments. Prompt scope lines 29–57 lazily acquires one environment and reuses it during a prompt. A durable agent, a session, a transient model runtime and an environment therefore have different lifetimes. Warm reuse improves continuity and cost, but means filesystem cleanliness cannot be inferred from the word “session.”

Company isolation is a first-class persistence boundary: AppRuntimeTransactionProvider lines 13–29 wraps operations with company context; schemas consistently carry companyId. Wingman products are not an equivalent existing boundary: no projects entity or project ID appears in the inspected schema/API/task/routing paths. Using one company for all products would require adding a project partition within it; using one company per product would split the shared organization.

Agent definition and lifecycle

What is an agent, and what is a session?

An agent is a persistent company-scoped configuration and identity: UUID, name, optional title, model/default reasoning/options, compute template, auto-compaction percentage and system prompt (agents schema, lines 30–52). Skills, skill groups, MCP servers, secrets and secret groups attach through related records. It is not a permanently running operating-system process or a separately implemented BackendCoder class. Its specialization comes from instructions and tools.

A session is an independently addressable ongoing conversation owned by an agent. It stores selected model configuration, optional human owner, status, title, context snapshot, context usage and fork lineage (sessions schema, lines 25–97). One durable agent can have multiple concurrent sessions, including a fresh self-handoff. A turn records an individual prompt execution and usage. A task is shared business work, while a task run links an execution attempt to a task, agent and session. An environment is a remote filesystem/process resource with a separate lease history. A runtime is the short-lived in-memory PI Mono object reconstructed for a wake pass. These distinctions are valuable for Wingman: agent continuity can survive runtime disposal, but a single agent's multiple sessions do not automatically share conversational memory.

Definition, creation and identity

Humans create/configure agents through GraphQL and the Agents page; agents can also create/update them through the activated Manage agents system skill. AgentManagementToolService, lines 259–329, checks required fields, resolves a company-accessible model credential, verifies compute/template selection, writes the agent and attaches selected secrets in a transaction. Creating an agent does not itself start an inference loop. Starting a session or delivering a message supplies work.

Session creation, lines 121–215, resolves the agent within the company, selects an explicit or default model, derives reasoning/options, inserts a queued session, copies default secrets and inserts its first queued prompt. User-initiated sessions record an owner; task, workflow and agent-initiated work also carry principal attribution. The company seed CEO is an ordinary durable agent with broad system skills, not a supplied executive orchestration engine; its custom prompt is null and the OSS bootstrap test expects no onboarding workflow. The remaining onboarding service can start a named workflow if it exists, but this is insufficient to credit a turnkey organization in this checkout.

Execution and tool/permission assembly

The worker wakes a session by ID, acquires a Redis ownership lease, loads current runtime/model/company settings and builds the SDK runtime. Runtime creation, lines 180–288, restores the stored context into PI's in-memory session manager, adds company/resource prompts and registers CompanyHelm's tools. The ordered module registry, lines 62–87, covers core/runtime, terminal, optional computer use, secrets, skills, system commands, GitHub, Exa web search, MCP, human inbox, conversations and assigned tasks. MCP module, lines 27–56, discovers enabled attached servers and exposes their catalogs as tools.

This has useful explicit boundaries: company-scoped transactions; agent-attached MCP capabilities; selected session secrets; and activated system skills. SystemCommandService, lines 105–155, rejects a command unless its owning system skill is active, then dispatches to company-scoped handlers. Activation is an instruction/capability discovery gate, not proof of a separate human approval for each command or a complete least-privilege role hierarchy.

Shell execution, lines 16–95, runs commands through the leased remote environment; one-shot commands have a 60-second maximum and long-lived work uses PTYs. File patches, image reads and remote computer actions are custom tools as well. The LLM is not granted ordinary PI built-in host filesystem tools. Nevertheless, there is no inspected per-command approval system equivalent to Codex sandbox approval modes. The optional ask-human tool is a conversational handoff. Infrastructure isolation and product acceptance policy must not be conflated.

Routing and concurrency

Every wake identifies company and session. The worker pool can execute different sessions concurrently; Redis lease, lines 43–79, serializes ownership of one session. If another worker owns it, execution, lines 131–138 and 513–530, can enqueue a delayed wake when pending work exists. Environment leases separately prevent two live sessions from using the same warm environment. There is no corresponding project-leader scheduler assigning capacity across Mac and Endeavour.

Direct messages can target a particular session or an agent. Delivery planner, lines 79–175, rejects archived recipients, steers a selected/reusable session, or creates a fresh target session. createNewSession: true also permits parallel work by the same agent identity. This makes agent IDs durable contacts while session IDs disambiguate concurrent work. The model must still choose the right collaborator and supply relevant context; addressing an agent is not a semantic project router.

Persistence, resumption and scheduling

Runtime prompt processing, lines 291–390, starts a durable turn, runs the SDK prompt, drains late steering messages, finishes the turn and persists the resulting model context. Event handling, lines 260–335, 366–424, 883–959 and 1444–1479, serializes streamed events, writes transcript/tool content, publishes updates and saves context snapshots. The agent-end path saves context and marks a session stopped; stopped means idle/resumable, not accepted or retired. Auto-compaction is represented in state and transcript, with configurable thresholds, rather than silently replacing the durable agent.

A subsequent prompt reconstructs the runtime from the latest context snapshot. Forking, lines 418–524, requires available context and a completed turn, creates a stopped session with copied context/model settings and fork lineage, then copies session secrets. This is a latest-context conversational fork, not a point-in-time clone of the remote VM, source checkout or every task assignment.

Queued-message schedules, lines 65–95 and 98–216, store a cron pattern, timezone, and target session. They create a schedule-run record, queue attributed text, and notify execution. Disabled or archived targets produce skips. Errors produce failed schedule runs. A message schedule becomes done after queueing and execution notification (lines 180–190). The agent need not have finished the work. Schedule delivery success therefore does not establish product success.

Workflow service, lines 552–715 and 717–812, launches named durable workflows. It copies ordered steps into each run. A scheduled workflow skips an occurrence when its previous scheduled run remains active. A step stores instructions and progress for execution through an agent session. It is not a separately provisioned agent at each node of a general dependency graph.

Workflow execution session service, lines 134–180 and 208–260, supports execution in the existing chat or delegation to another agent. The owning session updates step status. Wingman could build supervision on these mechanisms. The checkout does not supply that scheduled ProjectMaster workflow.

Steering, interruption, cancellation and failure

Queued input is durable and can be promoted to steering or deleted while pending. The execution service subscribes to steer and interrupt channels; steering reaches the active SDK runtime rather than merely updating a UI placeholder (execution, lines 186–242 and 466–505). Interrupt lifecycle, lines 540–680, checks owner/state, marks stopped, closes active turn/message records with interruption information, clears queued work and publishes an abort signal. The worker persists interrupted context/usage and aborts PI. The tmux PTY adapter’s dispose() is a no-op (adapter, lines 179–181), so interruption or ordinary runtime disposal does not establish that long-running remote PTYs were killed. A separate PTY kill tool, lines 22–42, terminates environment processes. Session interruption should not be assumed to roll back repository edits or every external side effect.

Wake queue configuration, lines 45–65, gives three attempts with exponential backoff starting at two seconds. Execution failure handling, lines 291–408, returns primary queued input to pending on a prompt exception, disposes runtime/tool resources, releases the lease and requeues undispatched steering. Lease-heartbeat loss aborts the runtime. Event handler, lines 822–959, persists model error information alongside transcript state.

These are meaningful recovery mechanisms, but not an exactly-once external-action guarantee. A command, network action or source edit may complete before an exception/retry; PostgreSQL, Redis wake notification and remote tool effects are separate operations. A hard worker death also differs from the caught-exception path: a lease eventually expiring does not itself establish that every previously dispatched queue row will be safely replayed. The inspected tests cover lease contention, prompt failures, undispatched steer recovery and interrupts. They do not demonstrate end-to-end recovery from every process/Redis/Postgres/E2B failure combination. Wingman would need operational reconciliation and idempotence rules around business-critical delivery actions.

Completion, acceptance and retirement

Task status synchronization, lines 821–890, closes an open run when the task is marked completed, or cancels it when reset/reassigned. Task start checks, lines 532–557 and 936–1052, prevent taking another agent/user's task and reject a task already active in a different session. A normal model turn ending is not equivalent to task completion. An agent must update the tracker, and a workflow must update its own steps. There is no automatic integrated test verdict or human product-acceptance transition attached to task completion.

Sessions can be archived/unarchived and renamed. Lifecycle archive/delete, lines 218–417, marks the session archived, removes queued input and requests interruption of running work; deletion requires an archived session. The Redis interrupt is a request handled asynchronously by the worker, not an awaited acknowledgment that remote activity has stopped. Archiving resolves open human questions and makes history read-only in the relevant UI. DeleteAgentMutation, lines 44–85, deletes the company-scoped identity; database relationships cascade or restrict different histories (for example task runs restrict agent deletion). There is no separate “retired agent” state retaining an organizational directory entry. Environment stop/delete is separate from session archive. Environment disposal, lines 140–150, releases an idle lease. It does not kill the warm sandbox. This is another reason not to interpret an archived conversation as guaranteed filesystem cleanup.

Coordination mechanics and a traced task

The shared task model is richer than a flat to-do list: parent/root IDs support decomposition, stages support configurable lanes, tasks can belong to a human or an agent, and runs preserve session-backed attempts. It is narrower than a project-management system with dependency scheduling: the task schema, lines 44–131, has no dependency edge, blocked reason, project foreign key or definition-of-done relation. Searches in task services, tools, GraphQL and web pages found no separate implementation of those concepts. A stage named “Blocked” would be a user convention, not an automatic blocker engine.

Agent messages are actual executable handoffs. Conversation command service, lines 43–94 and 122–155, validates source identity, resolves recipient delivery, persists canonical conversation/message state and queues the target prompt in the same transaction before notifying after commit. Conversations bind agent/session participants and are browsable by humans. There is no named room with many participating agents, room subscriptions or organization-wide management room semantics in the inspected service/schema. Loop guard, lines 14–79, suppresses short acknowledgment ping-pong when both parties have already sent low-information closures. It deliberately permits substantive questions/links, and its English phrase heuristic is not a general loop/cost controller.

Human decisions use a durable inbox. Agents can ask a question with proposals, pros/cons, ratings and optional freeform answers. The result is tied to the originating agent/session and optional tool call. Resolution, lines 281–390, validates the selected/custom answer, persists it, sends a steer prompt back and reopens the question if prompt delivery throws. This routes context better than an unassociated notification. Asking does not suspend the runtime behind a mandatory approval latch: it is a nonblocking record-and-resume pattern, so organizational instructions must tell agents when to wait.

A concrete existing execution path is the human clicking Execute for an agent-assigned task. This is a static trace through implemented code, not a scenario exercised during assessment:

  1. ExecuteTaskMutation, lines 42–63, authenticates company/user and calls TaskRunService.executeTask with the task ID.
  2. TaskRunService, lines 106–161, loads the task under company scope, requires an agent assignee, reuses an existing open session-backed run, or closes a stale run missing its session. This avoids silently launching duplicate attempts through repeated clicks.
  3. The same service, lines 164–237, renders the task description and stage into a prompt. It creates a session and queued message with principalType: task and the run ID. It stores the linked run, marks the task in progress, commits, and notifies execution. The execute-task template, lines 1–14, directs work in that session. It requires a review/approval request before the agent considers the task complete.
  4. Session execution, lines 122–291, acquires ownership, restores runtime state, marks queued input processing and calls PI. A shell/file tool lazily leases an E2B environment. A non-coding question need not allocate one.
  5. The agent can activate Manage tasks to create child tasks, send another agent an implementation question or start a fresh specialist session. Delivery planner, lines 65–175, makes that handoff queued/steered execution rather than passive chat text.
  6. If product intent is unclear, the agent can create an inbox question. The answer returns to the exact requesting session through the resolution path above. No Butler or management hierarchy is involved.
  7. Event handler, lines 883–959 and 1008–1099, persists messages/tools and publishes UI updates. Artifacts can attach documents, links or PRs to the task/session. These are durable outputs, not proof the deliverable passed acceptance.
  8. The agent marks the task completed through assigned-task/system-command tools. TaskService, lines 821–890, timestamps and closes the open run. The human can inspect the run/session and artifact in the task detail UI, but there is no enforced TestMaster verification or accepted-delivery ceremony.

This trace covers the useful infrastructure boundary precisely: CompanyHelm executes and records assigned work, coordinates addressed sessions and carries human answers, while Wingman's portfolio interpretation, product definition and acceptance obligations remain to be supplied.

Major additional capabilities and consequences

Managed remote development environments with interactive inspection. E2B templates, lazy acquisition, warm reuse, pause/resume, terminal connections, environment metrics and optional desktop/VNC access provide a concrete way to run applications and let a human inspect them before merging. This goes beyond Wingman's described Mac/Endeavour execution layer and is useful for sandboxed tests and demos. It also introduces E2B credentials, templates, network/storage behavior, cost and lifecycle management. It cannot substitute unchanged for durable local product placement. Evidence: E2B provider, lines 79–143 and later start/stop/VNC methods; environment terminal page; metrics collection.

A provider-independent model and credential control plane. The schema/configuration separates model credentials, synchronized models, default selections, reasoning/options and actual session model choices. OAuth refresh and provider errors/rate-limit handling are implemented services rather than a single hardcoded API key. This supports a mixed-model organization and cost experiments, but adopting it means Wingman's explicit Codex-agent experience becomes a PI-based model/tool experience unless a separate Codex execution backend is built. Evidence: model credential schema, lines 54–119; runtime model resolver; OAuth refresh service.

GitHub integration and PR-feedback continuation. GitHub App installation/repository access and tracked pull requests provide delivery integration. Webhook processor, lines 52–88 and 149–307, handles PR/review/comment activity and routes tracked PR activity back into linked sessions. This can support post-review fixes without manual transcript copying, but depends on GitHub App setup, correct artifact/PR/session linkage and filtering/idempotence. It is not an integrated acceptance gate or a general issue-to-product intake engine.

Typed artifacts and human decision records. Documents, links and pull requests have names, state, authorship and company/task/session scope, while questions preserve structured alternatives and final answers. These provide an inspectable product-output and decision substrate that Wingman's lightweight records would otherwise need to implement. The consequence is a database/API-based record system that must be exported or bridged if Wingman keeps canonical filesystem directives. Evidence: artifacts schema, lines 19–93, and inbox service, lines 162–254 and 281–390.

Reusable workflows with execution history and cron. Durable definitions/inputs/step snapshots, local or delegated execution, parent workflow links and scheduled overlap control support repeatable review, maintenance and onboarding procedures. This is more explicit process infrastructure than Wingman's described initial supervision cycle. However, steps remain model-executed instructions with reported status, not verified deterministic transitions, and schedules do not themselves implement stalled-agent diagnosis. Evidence: workflow service, lines 552–812, and workflow session service, lines 134–260.

Company tenancy, membership and operational accounting. Multiple authenticated users/companies, invitations, company-scoped database operations, LLM cost/token aggregation and environment usage/metrics support a collaborative hosted control plane. Wingman's single-director organization could use these for access and observability, but would inherit authorization, migration, queue and operations complexity. Company tenancy does not automatically solve per-product isolation within one organization. Evidence: company bootstrap membership, lines 98–161; usage aggregate schema, lines 137–180; dashboard usage queries, lines 66–140.

Distinctive mechanisms and grounded innovation assessment

The strongest design contribution is the separation of durable identity, durable conversation, transient runtime and leased environment. Rather than equating a browser tab, subprocess and agent, the code reconstructs model context on demand and manages execution resources separately. That enables resumed sessions, independently concurrent sessions for one identity, optional environment allocation and warm resource reuse. Its limit is that conversational forks are not filesystem snapshots and remote workspace state is not guaranteed clean for every new chat. This is a useful architectural pattern to borrow, without a claim of historical novelty.

The durable message plus disposable wake design keeps the actual work input in PostgreSQL and uses BullMQ jobs to request processing. Redis leases serialize session ownership, while explicit principal metadata distinguishes human/task/workflow/schedule/agent/GitHub input in the transcript. This enables several sources to feed the same session pipeline and supports live steering during a model run. The code takes care to requeue undispatched steering and avoid replaying already in-flight input. Its limits are cross-system failure windows and side effects outside transactions; three queue attempts are not an organizational recovery policy.

The canonical conversation plus executable delivery mechanism bridges chat records and work. A send transaction resolves/creates participants, persists an understandable conversation and inserts the recipient's prompt, followed by an execution notification. It can reuse a known collaborating session or deliberately make a new one. That offers a stronger foundation than a transcript-only chat room, but currently binds a pair of sessions and requires model-authored coordination. The acknowledgment loop guard adds a focused safeguard, with phrase/length-based limits rather than a proof that collaboration cannot cycle.

The activated skill to typed platform command boundary separates reusable instructions from the data-mutating command catalog. Command dispatcher, lines 105–155, verifies active skill ownership for a command; session skill activation, lines 56–103, records activation separately from default attachments. This enables an extensible agent to learn product operations on demand without embedding every management command in the initial tool list. It is a context/capability assembly mechanism, not an authority hierarchy or blanket safety guarantee.

Finally, workflow-run snapshots and session-bound execution keep a launched process associated with the exact ordered instructions and agent session it started with, while allowing delegation to another agent. This supports repeatable organizational routines and inspectable progress. It does not supply dependency-aware multi-agent scheduling or objective acceptance tests: “done” is an agent-reported workflow/task state. The practical innovation is in combining these mechanisms into one inspectable control plane, not in establishing an unprecedented autonomous company.

Practical use for Wingman

Useful mechanisms after configuration include:

  • Company/agent catalog and independent tool-using sessions.
  • Task, subtask, and run records.
  • Human inbox with answer routing and direct agent messages.
  • Durable artifacts and skills.
  • Live transcripts, tools, usage, queues, leases, and persistence.
  • Named workflow schedules.
  • E2B remote shell/desktop execution where that deployment model fits Wingman.

Adapt these areas:

  • Represent product boundaries in explicit project records.
  • Add team, profile-instance membership, and leadership relationships.
  • Make scope, specification, and harness documents discoverable as project knowledge.
  • Connect task decomposition to acceptance documents.
  • Extend two-party conversations into project-aware management and collaboration rooms.
  • Generate evidence-linked summaries of recent results, current work, next work, and blockers.
  • Supervise actual progress signals.

Generic agent IDs and APIs can support these extensions. The UI and query schema still need the new records and relationships.

Wingman still needs Telegram intake, Butler replies, and persistent project selection with disambiguation. ProjectMaster needs portfolio state. ProductMaster needs discovery and clarification ownership. TechMaster needs planning and dependency policy. TestMaster needs integration and acceptance gates. Organization-wide escalation and accepted-delivery stop/continuation rules also need implementation.

Reliable Mac/Endeavour placement requires a new compute provider and runner protocol. The provider registry, lines 14–19, knows only E2B. The runner CLI, lines 48–69, lacks a connection loop, registration, polling, process execution, and result upload. Its package name does not establish a working remote runner.

There are two credible adoption paths. Wingman could use CompanyHelm as the primary agent/session/task control plane and build organizational workflows plus local providers into it. This maximizes reuse but adopts PI Mono and the web/database operational stack. Or Wingman could retain its Codex-native execution/Telegram organization and borrow CompanyHelm's task-run, durable message, lease, decision and artifact designs. This preserves the intended agent experience but requires implementing and connecting the platform. Neither path is a configuration-only transformation. For the specific Wingman purpose, CompanyHelm is a strong infrastructure base or mechanism source, with substantial organizational and host-execution gaps.

Verification scope and limits

The implementation review covered these areas:

  • API/server/worker startup and company/agent/session/task/conversation/artifact/environment schemas.
  • Company initialization, onboarding, agent creation, prompts, lifecycle, and runtime reconstruction.
  • Redis leases, queue retries, event persistence, and context snapshots.
  • Environment selection, E2B provisioning, task execution, and status synchronization.
  • Conversation planning, loop guards, inbox answers, workflows, and message schedules.
  • Skill/system-command dispatch, GitHub webhook feedback, and web agent/task/dashboard/chat/environment views.

The review inspected the standalone runner separately from the main API runtime.

Relevant tests inspected include:

  • Session process execution tests, especially lines 14–128, 199–238, 461–499, 963–1005, 1196–1230 and 1645–1695: lease contention/delayed wake, in-flight replay avoidance, follow-up wakes, undispatched steering recovery, cleanup after failure and interrupts.
  • Session event-handler tests, lines 436–618, 1102–1163, 1368–1523 and 1973–2053: running/stopped/archive state, serialized turn closure, streamed tool content and principal/queue attribution.
  • Conversation service tests, lines 100–283, 325–413 and 453–595: explicit-session steering, fresh recipient sessions, same-agent fresh sessions and canonical readable history; loop guard tests cover the narrow acknowledgment heuristic.
  • Task-run idempotency tests, lines 136–237: repeated status/start transitions, linking a session-backed run and claiming an unassigned task.
  • Environment reuse test, lines 5–86: fallback past an unhealthy history candidate into a reusable environment.
  • Workflow tools tests, lines 71–278: local/delegated execution and rejecting conflicting workflow ownership; schedule worker tests, lines 72–200: dispatch into workflow versus queued-message services.
  • Bootstrap test, lines 688–745: OSS CEO identity/defaults/system skills and no seeded onboarding process. Inbox tool tests, lines 6–64, cover exposure and compact acknowledgment of a durable human question.

These tests largely use test harnesses or mocked dependencies. Their presence supports intended contracts; none was run for this assessment, and no claim is made that the checked-out system currently boots or that its external integrations succeed. In particular, E2B provisioning/desktop access, model/OAuth calls, Redis/Postgres crash recovery, GitHub authentication/webhooks, real simultaneous model sessions and mobile interaction were not exercised.

Negative-feature checks covered these implementation areas:

  • Database schema, indexes, and GraphQL for projects, teams, and timelines.
  • Agent initialization, onboarding, and templates for leadership and discovery.
  • Task services/tools/pages for dependencies, blockers, and acceptance gates.
  • Server/integration routes for Telegram.
  • Dashboard/agent/chat pages for executive summaries.
  • Provider registry and runner source for local multi-host execution.
