Bernstein assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/sipyourdrink-ltd/bernstein

Local checkout: researchs/bernstein/repo. Actual inspected revision: 1ad038ab7f2475e45afc008a614c17da83090966. This is a source assessment of that revision, not a claim about a currently hosted service or a live deployment. Repository sources remained unchanged; no dependencies were installed and no agents or services were launched.

Fit verdict: Bernstein is a substantial candidate for Wingman's execution, task coordination, governance and evidence substrate. It already runs real coding-agent instances, schedules a shared task graph, exposes operational web/TUI views, coordinates remote workers, and gates changes before merge. It is not a ready implementation of Wingman's standing personal development organization. The human-facing Butler, conversational portfolio intake, persistent project leadership, product discovery cycle, organizational rooms and executive agent narratives remain significant application work. Its source is unusually explicit about the difference between a recorded claim and verified evidence, but several apparently complete surfaces have incomplete wiring. The default Telegram /run path contains enum mismatches, the ordinary SPA fleet routes can be stubs, and some declared quality settings are not seed-configurable.

Architecture and actual execution model

The application is primarily Python, with a Click CLI, FastAPI task server, Textual TUI and React web application. Package entry points include bernstein, bernstein-worker, an evaluation CLI and an audit-receipt verifier (pyproject.toml, lines 343 onward). Some old-looking imports are deliberately redirected to new modules by a meta-path finder. The assessment follows the physical implementations rather than treating compatibility imports as separate systems (core/init.py).

bernstein run accepts seed, goal, or plan input and calls bootstrap functions. See run_bootstrap.py, lines 2460–3080. Bootstrap starts the server, synchronizes work, and starts the spawner/watchdog. It injects a seed manager task where appropriate. Existing sessions and backlog work can take precedence over a new goal. See bootstrap.py, lines 442–564 and 627–811. A manager task is an assignment for a spawned agent.

A separate ManagerAgent class performs model-assisted planning, review, and replanning. It reads project context and roles, then fetches existing tasks. It can request web research. It parses structured output and posts tasks. See manager.py, lines 173–365 and 607–723. The dispatch loop uses deterministic Python. Some planning and judgment paths invoke models.

The task server is the coordination authority. TaskStore maintains task/agent maps, status/role indices, priority queues and an asynchronous mutation lock, appending state to JSONL. Startup replays the records. The default store is explicitly single-process: its append path has no OS-level file lock, and server startup rejects multiple Uvicorn workers (task_store_core.py, lines 451–523, 740–794; server_app.py, lines 1000–1063, 1190). Optional PostgreSQL storage and PostgreSQL-plus-Redis coordination are selected by the store factory. Those entail separate infrastructure and do not retroactively make a JSONL deployment safe for multiple writers (store_factory.py, lines 1–100, 129–157).

The orchestrator fetches all tasks, constructs a graph, filters dependencies and retry deadlines, groups ready work, claims tasks, spawns workers, monitors running sessions, verifies completed work and repeats. Fast/normal/slow tick phases keep heavyweight checks off every tick (orchestrator.py, lines 1541–1552, 1681–1860). Claim/spawn explicitly handles capacity, per-role fairness, file overlap, claim conflicts, response-cache and deterministic fast paths before a real spawn (task_lifecycle.py, lines 2024–2332, 2429–2505, 2815–2955). Dependencies can resolve through successful retry lineage. This is stronger than a simple list of pending futures.

Execution is usually a short-lived CLI process in an isolated Git worktree, with other supported paths for containers, sandbox sessions, in-process wrapping and runtime bridges. A session is assigned a role-prefixed random ID, its task context and skills are rendered, and the adapter invokes the actual coding agent (spawner_core.py, lines 4320–4395, 4640–4765, 5070–5455). Role templates and catalog personas are definitions. They become independently executing agents only after this dispatch. AgentSession is a runtime/session record, not inherently a permanent employee with one continuous conversation (models.py, lines 1202–1355).

The UI has real Tasks, Agents, Approvals, Costs, Audit, Governance, Missions and Fleet routes. Task detail has logs, diff, trace, artifacts, dependencies and gate components. This is more than a terminal grid (Tasks.tsx, lines 327 onward; web components). Fleet is a fan-out aggregator over configured project servers and SSE feeds, with offline/backoff behavior (fleet/config.py, lines 1–101, 126–230; aggregator.py, lines 1–170). The standalone fleet web app is real. The ordinary task-server Fleet router deliberately returns empty stub responses if no aggregator is attached (fleet/web.py, lines 112–243; routes/fleet.py, lines 1–70).

Agent definition and lifecycle

Definition and creation. A seed declares the goal, explicit/automatic team, CLI, max agents, model policies, context files, MCP definitions/allowlist, budget, workspace and isolation/governance options (seed_config.py, lines 365–488). Role templates, catalog matches and team manifests define instructions and routing, not permanent running agents. Manifest digest/signature checks pin what configuration was used. The agent_kind field's own documentation warns that accepting a modality is not dispatching it (manifest.py, lines 121–151). A Task carries role, dependencies, owned files, acceptance signals, artifact contract, parent/context, model/CLI hints, approvals, retry counters, tags and evidence producers (models.py, lines 516–680).

Identity. A dispatch receives a new role-<random> session ID, task IDs, trace ID, model/provider, heartbeat/spawn time, PID/log, isolation and optional parent ID. Resume creates role-resume-<random> rather than silently continuing the same runtime identity (spawner_core.py, lines 4653, 5976). Separate principal/grant/delegation infrastructure can establish who authorized what and reconstruct which principals exist, but a cryptographic principal is not a remembered ProductMaster conversation. Runtime agent rows may be synthesized from task assignments when no heartbeat agent exists. The API labels those synthetic: true (agents.py, lines 140–247).

Routing and execution. Tasks are filtered by dependency readiness and deadlines, grouped by role, constrained by total/per-role capacity and file conflicts, then claimed before spawn. Partial batch claims spawn only the claimed subset, avoiding stranded claims (task_lifecycle.py, lines 2429–2505, 2815–2843). Role policy, explicit task model and provider health/fallback affect adapter selection. Catalog prompts may replace the standard prompt, with bulletin/mailbox, predecessors, project context and skills injected. Worktree context is recorded with attachment/skill digests. Dispatch can choose a direct subprocess, wrapped in-process execution, container, sandbox session or configured runtime bridge. These do not all have identical observability or isolation (spawner_core.py, lines 4200–4314, 4640–4765, 5070–5455).

Tools and authority. Role-specific file and command rules feed guardrails. Model/adapter admission, security floors, and capability checks run before process creation. Each task receives MCP configuration with an allowlist and requested servers. Supported adapters also receive a hook gate for task-owned paths and evidence producers. Hook installation is best-effort. The authoritative scheduler gate still runs. See permissions.py, lines 40–65 and 156–225; and spawner_core.py, lines 5070–5172 and 5290–5355.

A worktree separates normal relative writes. It is not an OS sandbox. The Codex adapter distinguishes vendor sandboxing from declared external container or VM isolation. Review the effective boundary for the selected adapter. A role prompt cannot establish that boundary. See codex.py, lines 23–64 and 112–146. Unknown role permissions default broadly. Adding a profile therefore changes execution authority.

Concurrency and hosts. The scheduler can run several genuine specialist sessions, share a task server across remote nodes, and use cells. WorkerLoop registers capacity and supported roles/models, claims tasks on the central server, spawns agents in its local workspace, and reports finished work. On successful remote completion it pushes the agent branch and includes the branch/SHA in the completion request; delivery failure becomes task failure (worker_cmd.py, lines 79–151, 325–449, 534–668). This deserves credit independently of the lower-level SSH/rsync backend, which also exists (ssh_backend.py, lines 179–245, 426 onward). Remote server availability, credentials, Git access and workspace provisioning are operational requirements, not supplied by the organizational UI.

Remote terminal-state reporting is best-effort at this revision: _report_finished clears its pending list before sending; _complete_task/_fail_task do not check response status and catch transport errors without restoring an outbox item. A lost/rejected report can therefore leave central state unchanged until a separate reconciliation/recovery path intervenes. The reap path also defaults to success when a process is gone but exit status is unavailable, subject to successfully pushing its branch (worker_cmd.py, lines 345–374, 552–625). Real multi-host execution is established by code, while durable terminal-report delivery and strong success attribution are not established by this path.

Persistence and resume. JSONL task/progress history, session/checkpoint state, worktrees, journals, traces and artifacts persist outside the child model context. Full checkpoints include graph, agent session records, cost state and WAL position; partial checkpoints capture operator-visible progress (checkpoint.py, lines 1–16, 64–135). Retry continuity can restore files, summary/context hints, branch and commit. Crash resume reuses a preserved worktree and tells a newly spawned agent what changed (session_continuity.py, lines 35–143; spawner_core.py, lines 5902–5990). This is strong work continuity with bounded conversation reconstruction. Adapter-owned persistent conversation state is not universally recoverable/replayable: persistent_agent_step causes exported journal identity to become unverifiable rather than falsely certifying it (run_artifacts.py, lines 796–807, 866–872).

Scheduling and supervision. The running orchestrator continually checks task state, process/heartbeat liveness, budget and completion. Separate cron/event rules create work with filters, cooldown, deduplication and rate caps. A schedule supervisor computes fire instants, accounts for missed windows, supports bounded catch-up and records fire/collision receipts (trigger_manager.py, lines 1–8, 61–156; schedule_supervisor.py, lines 1–29, 70–124). This provides periodic wake machinery, but a schedule must be authored and run. It does not make a ProjectMaster automatically inspect every product, infer a useful follow-up, and converse with its leaders. Stalled-manager detection is explicitly a diagnostic and clean-shutdown path, not a managerial repair conversation (stalled_manager.py, lines 1–35).

Interruption and steering. Task cancellation can cascade through descendants. Cooperative cancellation uses STOP_REQ as a nonterminal state until the reaper observes cessation. The stop reaper escalates notify→SIGINT→SIGTERM→SIGKILL and can return unverified rather than pretend a process is gone (task_crud.py, lines 1974–2048; stop_reaper.py, lines 25–151). Operator steering records an audit receipt before a pause/resume/guidance/redirect/abort effect and delivers typed mailbox messages/process signals (task_steer.py, lines 1–18, 135–170). These are execution controls. They are not universal conversational steering for all backend tools. Telegram's separate marker-based /stop implementation should not be assumed equivalent without demonstrating a consumer.

Failure, retry and recovery. The task model distinguishes failed, orphaned, blocked, suspended, abandoned, refused, waiting for subtasks and blocked-by-dependency states. Retries preserve lineage, limit attempts, delay execution, carry failure context or deliberately start fresh, and can escalate effort/model or propose decomposition (models.py, lines 187–209, 600–648; task_lifecycle.py, lines 451–638, 682–963, 1204 onward, 1722–1953). Provider failures/cooldowns and shutdown are checked before spawning. A bounded repair task can continue a failed gate on the same branch instead of causing duplicate generic retries (task_lifecycle.py, lines 3410–3482, 5300–5394). Exhaustion is an explicit failure/operator problem. This is not evidence of guaranteed autonomous recovery.

Completion, acceptance and retirement. Worker completion is an intermediate claim. The scheduler resolves janitor evidence, runs configured verification gates, evaluates approval, reaps/merges or preserves the worktree, records metrics and bulletin output, then closes/reopens/fails the task. Bounded repair and merge failures have separate outcomes (task_lifecycle.py, lines 5235–5394). Tests and type checking are off by default; gate results prove only configured checks. A successful task/merge is not automatically product-level DoD satisfaction, release deployment or human acceptance. Sessions are short-lived; cleanup includes process reaping, token revocation and worktree/sandbox cleanup rather than keeping the specialist active indefinitely (spawner_core.py, lines 2054–2073, 2182–2220, 2363–2405, 6764–6798, 7370–7432; spawner_merge.py). Wingman needs a stable role/employee layer above that session retirement.

Coordination mechanics and a concrete code-path trace

Bernstein has several distinct communication mechanisms, which should not be conflated. The bulletin is broadcast cross-agent/cell status; its message types include blocker/finding/dependency. MessageBoard handles role-addressed delegation with claim/completion/expiry. Direct session inboxes are file-backed and polled; their source explicitly defers TUI inbox rendering and read receipts. Task mailbox messages are typed, signed and chained and can be rendered into subsequent worker context in chain order. None of those, by itself, is Wingman's human-browsable organizational chat room system (bulletin.py, lines 1–10, 136–215; direct.py, lines 1–23; task_mailbox.py, lines 1–26, 75–110).

A representative request is bernstein run with a goal to add a feature. The following is a static trace of the real implementation path, not a run performed during this assessment:

  1. CLI resolves the goal/seed and bootstrap starts or connects the local coordination environment. Existing backlog/session work has precedence checks. When it needs decomposition, bootstrap injects a manager task containing the goal and context (run_bootstrap.py, lines 2972–3078; bootstrap.py, lines 529–564, 627–811).
  2. A manager CLI agent can create child tasks over the task API. The independent optional ManagerAgent.plan path also demonstrates the structured planning contract: context/roles/existing tasks→research decision→model output→dependency resolution→POST tasks (manager.py, lines 207–365). These are different entry paths, not two mandatory managers in every run.
  3. POST /tasks validates and creates a task through TaskStore.create. The task has a role, owned files and machine-checkable completion signals. Store mutation persists the record and listeners/SSE make changes visible (task_crud.py, lines 1022–1226; task_store_core.py, lines 1501–1634).
  4. Tick fetches tasks once, resolves graph readiness including successful retry lineage, then claims eligible role batches. Capacity and overlap guards prevent unbounded fan-out. A competing claim is re-fetched/retried rather than treated as ownership (orchestrator.py, lines 1759–1860; task_lifecycle.py, lines 2168–2332, 2429 onward).
  5. The spawner assembles role/catalog prompt, bulletin and mailbox context, worktree files/skills and per-task tool configuration, assigns a real session and calls the selected adapter. Logs and progress can reach the UI while it executes (spawner_core.py, lines 4640–4765, 5070–5455; agents.py, lines 282–384).
  6. If a worker posts a blocker, the signal action layer can materialize a deterministic clearance task and inject dependency edges, making the blocker constrain scheduling rather than merely appearing in a log. The chain records the projection/resolution. This is a useful operational analogue to leadership follow-up, but the resolution policy and affected scope still need configuration (signal_actions.py, lines 1–36, 75–94).
  7. Worker /complete reports a result; completion processing verifies the claims, runs quality gates, consults approval policy and merges/cleans up only along the appropriate path. Required-gate inconclusive blocks just as failure does. A repair task or bounded retry can be created instead of closing (task_crud.py, lines 1678–1798; task_lifecycle.py, lines 5235–5394; gate_pipeline.py, lines 25–56).
  8. Human approval is authenticated against task, outcome and a fresh request nonce. CLI/web/chat decision paths share that record format. This gives a reviewable execution decision, not a conversation about whether product requirements were sufficiently discovered (approval_decision.py, lines 1–40, 93–111).

Source limitations that affect this trace's human entry and visibility

The Telegram transport is real, but the default chat dispatcher discards the requested adapter and opens its own TaskStore against the JSONL file rather than calling the running server. _create_task_via_store supplies scope="chat" and task_type="feature" (chat_cmd.py, lines 172–191, 514–546). TaskStore.create constructs Scope(req.scope) and TaskType(req.task_type), while the enums permit small/medium/large and standard/upgrade_proposal/fix/research (task_store_core.py, lines 1501–1573; models.py, lines 175–185, 224–231). Static analysis therefore predicts /run raises a ValueError, which the handler catches and reports as failure. Even after correcting those values, direct file append is not demonstrated to refresh a running server's in-memory task map, and the store's single-process contract makes this an integration boundary to repair. The inspected chat tests deliberately replace dispatch with a stub and “never touch the real TaskStore,” so their successful /run assertions do not establish the default integration (test_chat_session.py, lines 55–108).

The default /switch consequently does not prove adapter switching, and /stop writes a local chat_stop marker and deletes the binding rather than visibly calling the task cancellation API (chat_cmd.py, lines 292–343). A search for chat_stop in runtime sources found the writer; no consumer establishing actual cancellation was identified. /status reads the saved binding rather than querying live execution state; stream_progress exists but a runtime-source search found no caller. run_forever starts the bridge and waits, without a task-progress polling loop. Telegram dispatch accepts slash commands/buttons rather than free-text intake (chat_cmd.py, lines 231–239, 273–287, 485–499; telegram.py, lines 213–264). This limits F04/F21 even though robust cancellation and live status exist elsewhere.

The Agents drawer displays static HISTORY_FALLBACK data before live logs arrive. Its “Open log full” button has no handler in the inspected component. See Agents.tsx, lines 239–251 and 684–724. These elements do not establish actual history or full-log navigation.

Fleet cards set project in the URL. The inspected Tasks list/detail requests do not consume it. Until end-to-end routing is verified, credit the standalone Fleet app as the portfolio surface. See Fleet.tsx, lines 299–306, and Tasks.tsx, lines 440–466. /fleet/search parses filters but always returns matches: []. An aggregator can make stub false without implementing search. See routes/fleet.py, lines 89–125.

Major capabilities beyond Wingman's described product

Governance and verifiable authority. Bernstein adds task-scoped grants/delegation, operator/model/adapter admission, signed approval records and a reconstructable principal registry. An offline reviewer can distinguish recorded authority, currently effective capability and invalid delegation rather than trust a UI's role label (agent_registry.py, lines 1–46; approval_decision.py, lines 1–40; spawner_core.py, lines 2594–2785). This would strengthen Wingman's controls, but introduces key custody, grants, identities and policy configuration. The approval source itself states that a process running as the same OS user can read the audit key; HMAC records do not turn an unsandboxed agent into an isolated security principal.

Artifact provenance and independently checkable evidence. The always-on lineage spine records chained artifact identities and authenticated heads. In-process adapter writes cross one boundary; ordinary CLI writes require merge-time provenance because they occur outside Bernstein's interpreter. An empty provenance store has a distinct result rather than a trivial pass (spine.py, lines 1–36; base.py, lines 1458–1547; merge_provenance.py). Wingman could tie deliverables to sessions, commits, checks and approvals. Integration must preserve the merge/write boundary and distinguish authenticated recording from proof that product behavior is correct.

Ledger-projected multi-day missions. Missions define ordered phases, task gates and budget envelopes across runs/machines. Their state is computed from chain transitions and referenced evidence, not an independently editable “done” field. Missing/altered evidence makes phase status unverified; projection versions preserve older interpretations (missions.py, lines 1–43, 97–124). Mission UI and deterministic chat digests give human outcome-level visibility (Missions.tsx, lines 193–245; mission_digest.py, lines 1–40). This is useful for product milestones, but phase definitions and evidence bindings must be mapped from Wingman's product DoD; missions do not create product leadership or discovery.

Multi-adapter execution, routing and cost controls. Bernstein can use different CLI agent families, per-role models, provider health/fallback, explicit model admission, task budgets and provider batch routes. This is broader than Wingman's Codex-only organization (seed_config.py, lines 365–488; spawner_core.py, lines 4200–4314, 5275–5400; task_lifecycle.py, lines 2860–2955). It enables cost/quality tradeoffs and outage recovery, but model/adapter differences affect sandboxing, session identity, tokens and tool visibility. Wingman could deliberately constrain this surface to Codex initially instead of inheriting all adapter complexity.

Specification compilation and phase handoffs. Offline plan compile maps acceptance requirements into a gated graph with requirement hashes. Optional phase execution gives fresh agents validated summaries, decisions, and constraints. Mechanical checks cover unresolved questions, cross-references, cycles, retained constraints, and size. See plan_compile_cmd.py, lines 64–128; phase_pipeline.py, lines 1–18 and 142–170; and phase_gates.py, lines 1–52. This can improve handoff review and limit context drift. It validates form and references. It does not establish complete or correct research. Phase execution is opt-in.

Reproducibility and honest replay limits. Model call recordings key on provider/model/prompt/temperature/token cap and strict replay refuses cache misses. A run that recorded no model calls on the CLI-agent path is explicitly refused for hermetic replay rather than silently launching live agents (deterministic.py, lines 1–32, 82–135). This would help Wingman diagnose planning regressions and reproduce coordination decisions. It does not promise identical stochastic coding-agent execution, external websites or hidden provider conversation state.

Event/cron work and deterministic blocker gates. Triggers turn external events and schedules into bounded tasks; blockers can become clearance nodes in the same dependency graph. Scheduling has misfire/catch-up/collision records rather than a generic periodic script (trigger_manager.py, lines 1–8, 61–156; schedule_supervisor.py, lines 1–29; signal_actions.py, lines 1–36). These could drive ProjectMaster wake cycles and backlog follow-up. Wingman still must decide which observations warrant organizational action and prevent excessive agent/event churn.

Distinctive mechanisms and grounded innovation

These are distinctive engineering mechanisms in this checkout; no historical novelty or industry-wide uniqueness is claimed.

  1. State as a verified projection rather than a parallel status database. Missions and agent principals derive human-readable state from authenticated transition/grant evidence. This makes an executive claim reproducible by another reviewer holding the same evidence, and avoids a dashboard saying “passed” after its evidence disappears. Its practical limit is the completeness and trustworthiness of the recorded inputs. A valid chain can faithfully record an inadequate test. See missions.py, lines 1–43, and agent_registry.py, lines 1–46.
  2. Blockers become scheduling constraints with provenance. A typed bulletin blocker can deterministically produce a clearance task plus dependency edges, with a graph-delta receipt. This closes the common gap between “the agent reported a blocker” and “the scheduler withheld affected work.” The affected scope and authenticated gate resolution matter; logging a blocker alone does not deliver that behavior. See signal_actions.py, lines 1–36, 75–94.
  3. Receipt-before-effect operator steering. Steering records who authorized the displayed command before delivering task-mailbox/control effects, and supports payload-hash consistency checks. This connects a human decision to the action a worker receives. It remains bounded by the actual adapter/process control and credential environment. It is not proof that every model immediately understands a new instruction. See task_steer.py, lines 1–18, 135–170.
  4. Explicit unverifiable/inconclusive outcomes. Required gates block missing evidence, provenance distinguishes empty stores, stop reaping can remain unverified, and hidden persistent-agent state downgrades replay identity. This is valuable for Wingman because successful-looking logs are a weak delivery criterion. The limits are real: disabled or unwired gates still cannot verify product behavior. See gate_pipeline.py, lines 25–56, stop_reaper.py, lines 25–39, 121–151, and run_artifacts.py, lines 866–872.
  5. Task-session separation with reconstruction rather than pretending immortality. Crashed work can resume under a new identity in a retained worktree, with explicit partial-work and retry context. Fresh-context retry is separately configurable. This fits reliable execution better than treating a role prompt as a permanent autonomous entity, but it means Wingman must build stable employee identity and conversation indexing above the runtime. See spawner_core.py, lines 4375–4395, 5902–5990, and session_continuity.py, lines 35–143.

Practical use for Wingman

Usable directly after focused runtime validation: the shared task graph/API, actual Codex worker adapter, isolated worktree dispatch, concurrency/claim machinery, remote worker registration and Git delivery, task logs/diffs/traces, authenticated approvals, evidence recording and configured quality gates. These cover a large fraction of specialist execution and ProjectTracker plumbing. Prefer a single supported backend and one clearly defined persistence topology for an initial integration. The checkout contains many optional mechanisms that should not all be enabled merely because they exist.

Adapt these areas:

  • Map Wingman profiles to explicit role permissions, prompts, and model policies.
  • Map product directories and DIRECTIVES to context, specification, and evidence paths.
  • Link stable organizational identities to temporary sessions.
  • Connect Telegram intake to the authoritative server API.
  • Route human questions and answers with project identity.
  • Connect fleet/server selection to the dashboards.

Use executable acceptance gates where possible. Retain human acceptance for judgments that require it. Select the required audit and lineage guarantees explicitly. Keys, receipts, and projection versions add operational work.

Still to build:

  • Butler and ProjectMaster as persistent organizational agents.
  • Semantic cross-project intake.
  • Per-product ProductMaster and TechMaster stewardship.
  • Proportionate domain/product discovery and iterative clarification. A chat application with Room1/Room2, participants and task/decision links. A stable agent/team directory.
  • Executive agent current/recent/next/blocker summaries.
  • Individual narrative timelines linked to detailed sessions.
  • Portfolio supervision policies that communicate through the organization.
  • Accepted-delivery/idle-until-follow-up product lifecycle. These are core Wingman experiences, not small role-template edits.

Bernstein is therefore better evaluated as a governed execution backend to place under Wingman than as a replacement whose existing UI is merely rebranded. Its strong evidence machinery could make Wingman more trustworthy, but the observed broken/incomplete seams require integration tests before treating the checked-out product as turnkey.

Verification scope and limits

The original review read repository instructions for orchestration, adapters, CLI, quality, security, lineage, and tests. It also read the Wingman purpose and assessment guide. Implementation inspection covered these areas:

  • Commit, package, CLI/bootstrap entry, task/session models, and task-store persistence.
  • Dependency ticks, claims, process creation, retries, completion, context, routing, resume, and control.
  • Telegram transport, chat integration, task/agent/steering/cluster routes, and remote worker reports.
  • Fleet configuration, aggregation, web/stub routes, and React Tasks/Agents/Fleet/Missions views.
  • Project context, team manifests, approval authentication, quality defaults, and lineage.
  • Specification compilation, phase pipelines/gates, missions, digests, schedules, triggers, and selected recovery/replay paths.

Relevant tests were read, not executed:

  • test_chat_session.py, lines 55–245: stubbed dispatch, binding, allowlist, approval and stop-marker assertions; demonstrates why these tests do not prove actual Telegram task creation.
  • test_worker_cmd_reporting.py, lines 1–170: remote process reap→branch delivery→completion/failure reporting, including failed push; mocked HTTP/process checks are not a live multi-host test.
  • test_stop_req_lifecycle.py, lines 1–100: exactly allowed stop-request transitions and nonterminal classification.
  • test_spawner_persistent_agent_wiring.py, lines 1–165: real spawn-path wiring with mock adapter, and explicit downgrade of persistent-agent replay identity.
  • test_missions_projection.py, lines 228–311, 377–430, 570–602: deterministic ledger fold, evidence binding/deletion and copy-to-fresh-directory restart invariants. The “two hosts” test uses two local directories, not live remote machines.
  • test_quality_gates.py, lines 1–100: command behavior and an explicit _KNOWN_UNWIRED set. Several settings, including intent verification/mutation/integration-test-generation fields, are not consumed by the seed parser at this revision. Existence in a dataclass is not ordinary YAML configurability.

No runtime behavior, adapter conformance, service startup, browser interaction, real model call, multi-host race, database backend, cryptographic interoperability or end-to-end Telegram flow was exercised. The Telegram enum mismatch, no-op-looking UI controls, missing project selection in inspected Tasks queries, and configuration gaps are source-derived observations, not reproduced incidents. Likely missing organizational behavior was searched across chat/CLI handlers, bootstrap/manager/planning, roles/team manifests, fleet/workspace routes, communication primitives and web/TUI surfaces rather than inferred from README silence. Lower-level security and optional workflow breadth is large. This report credits traced mechanisms and does not assert exhaustive security correctness or that every module is reachable in the default run.
