Sortie assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/sortie-ai/sortie . Local checkout: research/sortie/repo. Actual checked-out commit: d297d5a2a9dc7a3eae785262b18e6bd0e746be54. Scope: this local revision, inspected without changing the checkout, installing dependencies, or starting services. Applicable repository instructions: AGENTS.md.

Fit verdict: a strong candidate for Wingman's issue-execution and delivery substrate, but a poor substitute for its standing organization. Sortie already solves difficult operational problems: real coding-runtime sessions, bounded concurrent issue processing, persistent retries, remote execution over SSH, handoff evidence, review/CI repair loops, spend limits, and a browser dashboard with session activity. Its organizing unit is a tracker issue and its attempts, rather than an independently named employee with a continuing role, relationships, rooms, and product responsibility. Wingman would still need its human-facing Butler, portfolio intake, ProductMaster/TechMaster organization, discovery conversations, shared project knowledge conventions, collaboration application, and agent-centric executive views.

Sortie is an actual Go orchestration service, not just workflow prose. It integrates Codex, Claude Code, Copilot, OpenCode and Agent Client Protocol runtimes, with mock support for tests; Jira, Linear and file trackers; GitHub, GitLab and Gitea SCM; and several outbound notification backends. These are explicitly registered by the executable in main.go, lines 45–61. These integration names describe implemented adapters, not proof of live compatibility in this assessment.

Architecture and actual execution model

The executable boots one workflow-bound service. run loads configuration, opens persistence, reconstructs state, resolves adapters, creates the orchestrator and optionally serves the dashboard. main.go, lines 333–490, 820–954 and 956–1005, shows those wiring steps. A --once path runs the work from one poll and returns a structured result and appropriate process exit status. It is an alternative to the continuing scheduler, not an interactive agent chat. The exit mapping is at lines 64–80.

Repository-owned WORKFLOW.md combines YAML configuration with a Go template prompt. Configuration selects the tracker/project/filter, issue states, runtime and model settings, concurrency, hooks, reactions and budgets. Named dispatch rules can override the runtime, settings and prompt, match issue attributes, and chain stages with next. config/dispatch.go, lines 18–133, defines this actual shape. These are routing and prompt selections; assigning a rule the name backend would not create a durable BackendCoder employee. A default runtime and template still cover unmatched issues.

The orchestrator has one authoritative event loop. It receives poll timers, worker exits, retry timers, normalized agent events, snapshots and queued control actions. Worker attempts execute concurrently in goroutines; adapters start real external runtimes. orchestrator.go, lines 741–878, and dispatch.go, lines 801–842, make the ownership split explicit. The event loop records claims and a fresh dispatch ID before launching a worker, avoiding a second concurrent run for the same issue within that process. It is not a cluster-wide distributed lock or a multi-tenant organization service.

On each scheduling pass, Sortie reconciles existing work, checks configuration and spend eligibility, fetches tracker candidates, sorts them, applies dependency and capacity gates, resolves a dispatch rule, obtains a host and resolves the attempt's settings. The concrete candidate-to-host path is orchestrator.go, lines 1102–1293. Blocker resolution is implemented in dispatch.go, especially lines 200–225 and 448–501. This is dependency-aware execution of existing tasks, not automatic product decomposition.

A worker prepares or reuses an issue-specific directory and executes configured hooks. It verifies credentials where applicable, starts a session and renders prompts. Bounded turns observe tracker state and .sortie/status. Optional self-review precedes the final result. worker.go, lines 861–1011, 1161–1305 and 1496–1693. Git cloning, branch preparation, pushing and product-specific setup are generally operator hooks or agent work rather than a repository-management service embedded in the scheduler. The Codex example, lines 23–35, concretely supplies clone, reset-to-base, commit and push hooks. Hook policy therefore materially affects continuity and delivery safety.

Persistence uses embedded SQLite through a pure-Go driver, one writer connection, WAL mode and synchronous=NORMAL: sqlite/store.go, lines 20–79. The initial schema, lines 1–39, starts with retries, run history, session metadata and aggregate metrics; later migrations add stage hops, parks, reaction fingerprints/escalations, costs, comment delivery and turn history. Startup actually restores retries, usage holds, parks, stage hops and acknowledgements in main.go, lines 412–457, and reconstructs PR reactions/escalations around lines 820–845. Durable state survives service restart. It does not keep a subprocess alive through that restart or move a runtime's transcript automatically between hosts.

The HTTP server embeds its UI and exposes runtime state, issue detail, history, events, stats, prices, refresh, retry-now, attention acknowledgement and PR-check-now routes. server.go, lines 557–583. The React router has Overview, Pipeline, History, Analytics, Health, Workflow, Prices, issue pages and per-dispatch session pages: router.tsx, lines 19–105. This is a substantial operational interface, but its domain remains one service's issues and runs.

Agent definition and lifecycle in detail

What the entities mean

An agent kind is a compiled runtime integration, such as codex, not a named worker. A dispatch rule is a named selection of runtime, prompt and settings, optionally part of a stage chain. An issue is durable external work with an ID, identifier, state, labels and blockers. A dispatch is one scheduled attempt, carrying a random dispatch ID. A session is an adapter-owned conversation handle. It may span turns and may be resumed on a later attempt. A process is the runtime or transport implementing that session. They are deliberately separate: Claude/Copilot can use fork-per-turn execution while Codex keeps app-server alive across turns. No separate durable employee object owns multiple unrelated issues.

The distinctions are visible in domain/agent.go, lines 295–411 and 483–499; dispatch.go, lines 817–842; codex.go, lines 1–6; and the shared fork-per-turn engine, lines 23–66. A prompt saying “you are a senior engineer” is specialization text, not another independently executing agent. Conversely, separate dispatches really do get separate runtime sessions and workspaces; Sortie is not merely pretending concurrency in one model conversation.

Configuration, creation and identity

An operator defines a workflow and any partial/template files, tracker credentials and filters, runtime settings and hooks. Ordered rules match labels, issue type, priority, identifier, assignee and title; stage labels can select a particular rule directly. config/dispatch.go, lines 18–133. The loaded workflow is validated; runtime constructors are cached and selected by kind. main.go, lines 102–161. This is extensible operational configuration, with neither an interactive hire-agent operation nor an organizational team builder.

Creation occurs when a candidate passes scheduling gates. DispatchIssue claims the issue, stores its tracker identity, dispatch labels, retry counter, timestamp, host and cancellation handles, registers event retention and starts the worker. dispatch.go, lines 801–842. The adapter supplies the accepted session ID and process identity. On session start the worker writes dispatch identity and uses that accepted ID for comment delivery and metadata (worker.go, lines 1268–1305). Run history records rule, template, configured/reported model, chain lineage and issue identity, so the audit trail preserves what actually executed even when configuration later changes (exit.go, lines 432–489).

Workspace, execution, tools and permissions

Workspace keys are sanitized and paths checked for containment; workspace.go, lines 50–166, implements path resolution before directory creation. Normal coding dispatches call Prepare, including after_create and before_run hooks; read-only label reviews use Ensure, skip clone/build hooks and skip issue-state transitions (worker.go, lines 960–1011). “Read-only” here describes orchestration posture and instructions, not a proof that a full external runtime can never write or invoke an authorized remote tool.

The adapter contract is StartSession, RunTurn, StopSession. The worker attaches a rendered prompt and normalized issue to every turn and receives normalized events. Each turn has a deadline. The run also has inactivity detection and budget policy. The worker checks .sortie/status after successful turns and refreshes tracker state before continuing, stopping on recognized status, a non-active issue or the configured turn count. worker.go, lines 575–610 and 1545–1678. A successful turn alone does not mean accepted product delivery.

Runtime-native coding tools are supplied by the external harness. Sortie's own session tools add project-scoped tracker reads/search/state transitions, status, history, budget inspection and conditional notify_operator. sessiontools.go, lines 90–155, supplies the session tool assembly; main.go, lines 881–913, wires that metadata to the worker. The advertisement is withheld if the runtime has no tool channel, so a prompt does not falsely promise unavailable tools (worker.go, lines 1496–1516). Tools are not a general chat bus, nor does tracker_api create/decompose tickets: its operation enum is trackerapi.go, lines 49–66.

Permission behavior is explicit and unattended. A genuine human-input request ends an attempt. A permission request is refused where possible so the runtime can try another route, unless an operator-declared approval and an exactly offered one-call approval apply. humanrequest.go, lines 123–159. Runtime sandbox/approval settings remain adapter configuration; for example the Codex workflow, lines 49–53, declares approval_policy: never and thread_sandbox: workspaceWrite. Sortie does not turn runtime questions into a waiting Telegram approval transaction. A Wingman integration would need that mediation separately.

Routing, concurrency and real remote execution

Global, per-state and per-host ceilings control admission. Claimed/running/retry/parked/held state prevents unsuitable redispatch, while dependency reads can hold a candidate when blockers are unresolved or not safely known. orchestrator.go, lines 1192–1259. This concurrency is across issues, not a team of several runtime sessions simultaneously collaborating on the same issue. Stage chaining can sequence specialists on that issue after an attempt completes.

SSH execution is implemented rather than just documented future work. AcquireHost prefers a previous available host, otherwise picks the least-loaded eligible host; saturation holds dispatch instead of silently executing locally (hostpool.go, lines 41–79). Launch resolution uses the local SSH client and carries a remote command and workspace (launchtarget.go, lines 102–165). A remote shell supervises process groups, and the SSH client explicitly disables connection sharing; reverse forwarding can expose Sortie's tool server on a remote loopback port (sshutil.go, lines 215–299). The HTTP MCP transport requires a bearer and compares it in constant time (http.go, lines 46–65 and 115–125).

The same absolute workspace path must be meaningful on both hosts; hooks prepare remote contents while the central service owns its local metadata. Retry affinity assists conversation/workspace locality, but it is a preference subject to capacity, not durable project placement. A different host may lack the prior conversation files and code. The SSH architecture appendix explicitly documents these operational assumptions. This is useful for a Mac controller and Linux execution machine, but does not itself synchronize Communication, ProjectTracker and product directives across those machines.

Persistence, resumption and scheduling

Retries, parks, stage hops and run/session history survive process restart. The service reconstructs timers and pending reactions. The active runtime itself is not serialized. Session resume is a checked proposition: the shared continuity layer probes the runtime, carries history only on an affirmative verdict, fails when transport is lost, and otherwise warns and starts a new conversation (continuity.go, lines 70–111). A new ID therefore does not silently imply preserved dialogue. Native runtime storage and host availability remain prerequisites for true conversational continuity.

The scheduler has periodic polling and retry due times, not personal agent calendars or management wake goals. The timer restarts from the effective poll interval. A refresh endpoint can initiate an earlier pass (orchestrator.go, lines 757–774 and 870–872). Product-specific periodic reasoning would have to be modeled as externally created work or added supervision logic. The workflow manager retains the prior successful config and prompt on a bad reload, as exposed by manager.go, lines 172–217 and 232–245. Invalid edits are an operational attention condition, not a reason to destroy existing run state.

Interruption, failure, recovery and bounded continuation

Cancellation reasons include inactivity, leaving active tracker states, reaching terminal states, service shutdown and budget ceilings. run_cancel.go, lines 9–65, preserves causes rather than reporting every stop identically. There is no general conversation-management API for human stop/fork/archive/compact. A human can change external task state or stop the service, and operational APIs can accelerate checks/retries.

Worker panic recovery attempts session stop and workspace teardown before reporting an error (worker.go, lines 916–958). Failed turns stop the runtime and report a structured result. Exit processing releases host slots, defers workspace deletion until the worker has ended, records history/usage and chooses retry, park, handoff or stage advancement (exit.go, lines 259–297 and 323–489). Classified errors determine retryability; unknown errors default to exponential retry. Backoff is min(10000 * 2^(attempt-1), configured cap), with a five-minute default cap (exit.go, lines 1640–1700). That is useful recovery policy, but unknown failures can continue consuming attempts until other configured limits or parking rules intervene.

An absence-of-work evidence check can withhold handoff and eventually park repetitive unproductive attempts. Budget controls separately limit sessions, tokens, per-issue money and windowed spend; usage-limit holds can wait for a runtime allowance to reset. The dashboard's attention model includes these conditions rather than treating them as ordinary success (attention.go, lines 11–65). Recovery restores operational state and revisits tracker/SCM truth. It does not resume a live process at the instruction where it crashed.

Completion, acceptance and retirement

The worker can declare blocked, needs-human-review or no-change-needed through .sortie/status; exit processing records the statement and disposition. A configured handoff may move an active issue to human review, while a named rule can advance it to another stage. Advancement adds the next stage label, records chain lineage, releases runtime state and removes old stage labels, with explicit partial-failure handling (stage_hop.go, lines 151–284). This is a deterministic handoff mechanism; adding a label and recording SQLite state are not one external transaction.

Optional self-review executes configured verification commands, asks the same session to emit a verdict, and alternates review/fix turns up to a cap (self_review.go, lines 499–684). PR reactions can continue with CI failures, review feedback or merge conflicts, and auto-merge may act when configured checks allow it. None of these mechanisms independently proves product-level acceptance or creates a TestMaster instance. Human Review is an external workflow boundary. The human's product acceptance and its communication still need Wingman.

There is a material cross-host verification limit: runSingleVerification launches local sh -c with cmd.Dir = workspacePath, rather than using the worker's SSH executor (self_review.go, lines 178–215). The worker passes the session, local workspace path and adapter into self-review, with no SSH executor/host parameter (worker.go, lines 1717–1745). Thus a remotely executing coding session does not by itself establish that configured verification commands checked the remote changed files. They need synchronized/shared filesystem contents or explicitly remote commands; otherwise a successful local check may concern a different tree. This limitation is established from launch code, not a reproduced runtime failure.

At runtime exit the session is stopped exactly once by the adapter contract, host capacity is released, run history remains and terminal workspaces can be removed. Startup cleans known terminal workspaces (main.go, lines 492–520); periodic sweeps run later (orchestrator.go, lines 1102–1118). Hooked workspace deletion and optional retention are filesystem lifecycle, not retirement/archive of a named employee. Shutdown stops intake, drains workers/triage/tracker operations and cancels retry timers (orchestrator.go, lines 881–893).

Coordination mechanics and one request trace

The coordination plane consists of tracker state and labels, comments, local scheduler state, SQLite history, agent-authored workspace files and SCM/CI observations. Agents do not exchange direct mailbox messages. A tracker comment can influence a future turn. A .sortie/status file changes worker disposition; normalized events update progress and usage; PR/CI reactions create continuation attempts. These mechanisms are asynchronous and evidence-oriented rather than a management-room conversation.

The comment feed is more careful than concatenating all comments on every turn. It records comment identity and body hash against the accepted conversation, distinguishes edits and comments seen by earlier conversations, and reports exactly which comments were delivered (feed.go, lines 30–60 and 95–111). The worker uses the actual CarriedHistory value when selecting them (worker.go, lines 1299–1315). This supports tracker-based steering across replaced sessions, but delivery happens at prompt boundaries. It is not live bidirectional chat or a message guarantee that the model understood and acted on an instruction.

The following is a source-traced example, not a request executed during this assessment. Take an existing Jira issue selected by the supplied Codex workflow's agent-ready filter:

  1. The workflow identifies Jira, its project, active states, In Progress, Human Review and terminal states; hooks clone and prepare a branch (WORKFLOW.codex.md, lines 2–35). There is no initial Telegram idea routing or project creation in this path.
  2. The poll fetches candidates, sorts them and evaluates capacity/dependencies. It resolves the rule/default adapter/template and a host (orchestrator.go, lines 1147–1293). A non-terminal blocker holds the issue rather than invoking a planning agent to remove it.
  3. Dispatch records a claim and a fresh dispatch ID, then runs a worker (dispatch.go, lines 817–842). The worker may transition Jira to In Progress, emits session-start notification and prepares the workspace (worker.go, lines 861–1011).
  4. The Codex adapter starts codex app-server locally or through SSH, returns a session and communicates via JSON-RPC (codex.go, lines 1–6; launchtarget.go, lines 102–165). The first prompt includes issue context and available Sortie tools. The runtime does actual coding through its native harness.
  5. Events flow back through the orchestrator's event channel and are available to snapshot/history/live event views. A human-written Jira comment is selected for a subsequent prompt with delivery tracking, while an agent notify_operator call can send a contextual decision-needed message to configured channels (worker.go, lines 1299–1315 and 1496–1549; notify.go, lines 120–153). A Telegram reply does not re-enter this flow automatically.
  6. The worker observes a status signal, tracker state change or turn ceiling. It can enter configured self-review, stop the session and execute teardown hooks. Exit processing records its observed outcome, usage, rule and chain lineage. It can withhold handoff when work evidence is absent (worker.go, lines 1619–1717; exit.go, lines 323–489).
  7. Depending on workflow, Sortie hands the issue to human review, schedules another attempt, parks it or advances a stage label. If PR reactions are enabled, current-head CI or review feedback can generate follow-up work; auto-merge and merge-completion can finish the tracker lifecycle. stage_hop.go, lines 151–284; ci_reconcile.go, lines 45–57; merge_completion_reconcile.go, lines 240–305. This completes an issue delivery loop, not a whole product's discovery-to-acceptance journey.

Major additional capabilities beyond Wingman's described product

Forge-aware post-implementation automation. Sortie has specific reactions for CI failure, human and bot review feedback, merge conflicts, explicit label-triggered review/fix, auto-merge and observing merges to close tracker work. These are more concrete delivery mechanisms than Wingman's high-level implementation/testing/delivery description. CI resolves the PR's current head before asking for status (ci_reconcile.go, lines 45–57 and 117–145). Auto-merge requires a suitable mergeability state, an approved or not-required review decision, optionally acceptable CI, and a known head SHA passed to MergePR (auto_merge_reconcile.go, lines 175–290). The implementation accepts an empty CI conclusion alongside success, so require_ci should not be read as a universal proof that every product check ran. Wingman could reuse this issue/PR delivery controller, but must align tracker states, credentials, repository permissions and acceptance policy; mergeability is not product acceptance.

Explicit PR commands with different execution postures. Label commands inspect the forge's label-event journal, collapse bursts and respect retraction, rather than repeatedly executing while a label remains present. Read-only review uses scratch space without normal setup hooks; fix dispatches work on the branch. label_review_reconcile.go, lines 80–184, and worker.go, lines 960–1011. This is useful for human-triggered review operations and avoids unnecessary cloning, but a bridge must expose the distinction honestly and avoid claiming an OS-enforced read-only sandbox. A persisted mark is advanced before scheduling. A crash in that window can lose the command, and a failed mark write weakens durable deduplication to best effort. The code explicitly documents those limits at lines 167–173.

Usage accounting, prices and spend control. Session/run/turn accounting separates measured spend, unmeasured figures, lower bounds and sources. TurnResult carries cumulative token counts, per-turn incompleteness and provenance (agent.go, lines 434–480). Exit history records completeness and reported amounts (exit.go, lines 454–481); pricing is recorded with each run rather than revaluing all past work solely at today's rates (exit.go, lines 1745–1798). Layered rate tables include embedded/downloaded/operator configuration (rates.go, lines 131–200 and 292–317), and a downloader preserves accepted tables across transient failure (download.go, lines 195–245 and 469–551). Analytics and Prometheus provide operational reporting beyond Wingman's stated usage inspection. Integration needs a shared definition of budget scope, model identity and unmeasured usage; absent usage must not be presented as zero cost, and Sortie's estimate is not a provider billing ledger.

Deterministic triage before spending another model turn. A configured reaction triage command can return handled, dispatch-agent or escalate; invalid/failed triage defaults to dispatching rather than silently declaring resolution. reaction_triage.go, lines 20–61 and 82–100. This can cheaply resolve recognized CI/review conditions or route a known exception. It adds trusted command configuration and a result-file protocol; scripts must be maintained and are not reasoning managers. In-flight triage is runtime-only, not durable execution state.

Multiple interchangeable harness and service adapters. Wingman's purpose is Codex-centric; Sortie normalizes several runtime protocols as well as several trackers, forges and notifications. main.go, lines 45–61. The capability is valuable for heterogeneous execution or gradual adoption, and the single Go binary with pure-Go SQLite reduces control-service deployment friction. External runtimes, auth, Git, shell/hook tools and SSH prerequisites still exist; “single binary” does not mean coding agents and product builds need no dependencies. Active SCM reactions share one provider instance; startup rejects conflicting forge providers (main.go, lines 564–598), which limits a single service spanning unrelated forge configurations.

Distinctive mechanisms and grounded innovation assessment

These are noteworthy design mechanisms in this checkout. They are not claims of historical invention or industry-wide uniqueness.

Evidence-gated handoff rather than trusting a clean process exit. Sortie captures a workspace baseline, then distinguishes observed work, observed absence and undeterminable evidence. Changed commits/worktree or SCM metadata can establish work; no-change-needed is an explicit accepted declaration. An observed absence withholds handoff, and strict mode also withholds when evidence cannot be established (handoff_evidence.go, lines 45–103). Repeated absence can park the issue instead of looping indefinitely. This is directly useful for Wingman's autonomous workers because “turn completed” is weak delivery evidence. Its limits are equally important: a changed file, pushed SHA or explicit no-change claim is not proof of correct implementation, and metadata can be stale or agent-authored. The evidence check must sit below functional acceptance.

Truthful conversation continuation coupled to comment delivery. The ResumeCarried/ResumeReplaced/ResumeUnknown model prevents continuity from being inferred merely from asking to reuse an ID. The comment feed can then replay earlier comments appropriately to a fresh conversation while preserving delivered edits (continuity.go, lines 13–25 and 70–111; feed.go, lines 30–60). The combination is stronger than blind retries with an assumed transcript. It remains harness/host dependent and does not supply a durable agent's independent memory or shared organizational knowledge.

Durable staged specialization through tracker labels. Named prompt/runtime rules and next form bounded chains with recorded source dispatch, prior outcome, target label, chain ID and hop count (stage_hop.go, lines 151–254). A different specialist can pick up an issue on a subsequent pass while humans can still inspect the tracker. The hop ceiling prevents uncontrolled progression. Its externally visible state is inspectable, but tracker-label writes and SQLite writes cannot be atomic together; recovery/confirmation logic and partial-failure states are necessary. This is a useful technical pipeline mechanism, not a replacement for simultaneously available project leaders and peer discussion.

Head-scoped, independently deduplicated delivery reactions. CI follows the current PR head, merge attempts bind the head SHA and review decision, and merge completion uses the real merge SHA as its durable latch (ci_reconcile.go, lines 45–57; auto_merge_reconcile.go, lines 256–290 and 357–364; merge_completion_reconcile.go, lines 240–305). This prevents stale evidence from being treated as completion of newer code and limits repeated side effects. Guarantees depend on successful persistence and external API semantics. The label-command implementation explicitly chooses possible loss over duplication in one crash window, not exactly-once execution.

Remote process lifetime tied to orchestration lifetime. SSH dispatch is backed by process-group supervision, explicit non-shared connections, a grace period and an exit barrier rather than merely spawning ssh and forgetting it (sshutil.go, lines 215–299; exitbarrier.go, lines 37–64). Reverse forwarding makes central tools available to remote agents. This is relevant to Mac/Linux execution control. Processes that deliberately leave the managed process group, missing flock, an unreachable host and remote filesystem drift remain limitations. The local controller cannot guarantee host-wide cleanup under every failure.

Accounting that preserves unknowns. Explicit lower-bound and unaccounted-turn state avoids presenting absence of telemetry as free work. This supports honest ceilings, analytics and operator decisions (agent.go, lines 447–480; worker.go, lines 681–794). That operational precision would be valuable in an organization with many agents. It does not remove uncertainty from vendor-specific units, missing measurements or model-rate mappings, so budgets require deliberate handling of incomplete accounting.

Practical fit and implementation consequences

Wingman could use Sortie directly for already-defined technical tickets: configure a Codex workflow, prepare isolated issue workspaces, enforce concurrency and budgets, execute on local/SSH resources, collect events/history, and react to PR/CI feedback. The tracker/SCM integrations, safe workspace path handling, restart recovery, handoff-evidence check and run dashboard are substantial reusable behavior. The repository's Apache 2.0 license is the checked-in licensing basis; no broader licensing analysis was performed.

The cleanest integration boundary would be an execution adapter below TechMaster/ProjectTracker. Wingman creates sufficiently specified assignments; Sortie executes them and returns issue/dispatch/session IDs, host, state, evidence and outcomes. Wingman's directory should map those attempts to a persistent specialist identity and project instead of treating agent_kind as the employee. A dedicated execution record can preserve attempt lineage even when the runtime replaces its conversation. Product-level stop/acceptance should control tracker states and admission, while Wingman remains responsible for whether the product definition of done is met.

A different lightweight tracker requires the tracker interface or an explicit bridge. The adapter must support comments, labels, dependencies and state transitions. Translating task titles alone is insufficient for a tracker outside Jira, Linear or file JSON. Self-review's configured checks run on the controller. Remote deployments must synchronize the changed tree or supply explicit remote verification commands. Only then can those results establish evidence about SSH-worker changes. Repository hooks need to be designed for Wingman's stable product directories and remote placement. The sample's branch-reset hook is a coding-task example, not automatically the desired continuity policy for ongoing product teams. Configuring several service instances for separate products also needs an organization-wide launcher/registry and aggregate reporting, because one workflow/project-bound daemon does not supply that control plane.

The major missing systems remain:

  • conversational Telegram intake and answer correlation.
  • Butler/ProjectMaster routing.
  • durable named agent profiles and leadership.
  • discovery research and question cycles.
  • product scope/specification/acceptance records.
  • task decomposition and team assignment.
  • rooms and peer collaboration.
  • shared multi-host project knowledge.
  • portfolio and agent directory.
  • per-agent executive summaries and cross-task timelines.
  • rich coding-workspace controls, attachments and artifacts.

Sortie's bounded prompt stages can assist a pipeline, but modeling all of these as issue labels would conceal rather than implement the missing relationships and conversations.

For Wingman, this makes Sortie best evaluated as a focused delivery engine to reuse or study. Its strengths are below the organizational layer. Turning it into the whole product would require building much of Wingman around it and extending its domain from issues/runs to projects, employees, conversations and decisions.

Verification scope and limits

This was a static implementation assessment. No build, unit tests, integration tests, live coding runtime, tracker mutation, Telegram message, browser UI, SSH connection or service was executed. Source inspection establishes the mechanisms and intended branches, not their operational reliability in the user's environment. No dependency/toolchain installation or network verification was needed. Generated UI bundles and vendored/generated protocol bodies were excluded from detailed reading.

Important implementation inspected:

  • CLI startup/adapter wiring/recovery in cmd/sortie/main.go.
  • Domain session/turn/tool contracts.
  • Workflow manager and dispatch configuration.
  • Orchestrator event loop, candidate gating, dispatch, worker turns, exit, retry classification, reconciliation and host pool.
  • Stage advancement, handoff evidence and self-review.
  • Comment feed.
  • Telegram and notification tool.
  • SQLite setup/initial schema and migration inventory.
  • SSH launch/continuity/process lifetime helpers.
  • Server routes.
  • React router and session timeline/page. Major-reaction review included CI current-head handling, auto-merge prerequisites, label-command journal and merge-completion fingerprint path. The architecture index and SSH appendix were used for navigation and assumptions, while verdicts were checked against code.

Relevant tests inspected, not run:

  • hostpool_test.go, lines 27–140: local/SSH modes, least-loaded allocation, preferred-host affinity and saturation/fallback. These are host allocation tests, not proof of a real remote agent run.
  • continuity_test.go, lines 20–115: fresh starts, unknown resume verdict, connection loss and cancellation; assertions distinguish a new session from carried history.
  • handoff_absence_test.go, lines 54–125: setup and cases for consecutive absence ceilings and human-review labels.
  • run_events_test.go, lines 52–120: newest 1,000 event retention, redaction, ordering and exclusion of empty liveness/token-only events. The UI timeline therefore should not be advertised as an unlimited exact transcript.
  • telegram_test.go, lines 85–145: outbound request shape, UTF-16 limit and token-safe error handling through a test server. These test sends, not inbound Telegram conversations.

Missing-capability conclusions were checked across likely implementation paths: internal/domain, config, storage/SQLite migrations, tracker and agent tools, notification adapters, orchestrator, CLI, HTTP routes and web/src navigation/screens. Searches included organizational roles/rooms/directives, project-scoped operations, Telegram receive/update/webhook APIs, and conversation steering/archive/compact/attachment controls. The matches establish narrower implemented mechanisms (outbound Telegram, project-scoped tracker access, runtime-specific compaction settings/generated protocol types), not the absent organization features. External harnesses may provide additional tools or native controls, but those should not be counted as integrated Sortie product capabilities without an implemented path.
