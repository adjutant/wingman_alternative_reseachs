# Paperclip assessment for Wingman

Repository: https://github.com/paperclipai/paperclip

Checkout: `research/paperclip/repo`  
Commit: `46fb933b0155d183ce64a8bdc4950d1b58c926f6`  
Assessed: November 5, 2026. Static implementation review; services and providers were not launched.

## Fit verdict

Paperclip is a strong candidate for Wingman's organizational control plane: durable agents, reporting relationships, governed hiring, projects, task ownership, runs, human decisions, channel integrations and an extensive operator UI are implemented together. This checkout is substantially broader than a minimal task board. In particular, Telegram transport, agent chat, summary generation, execution environments, watchdogs and runner recovery have concrete implementations.

Its organizing primitive is the **company-scoped issue and its authorized execution**, rather than Wingman's two shared agent rooms. A company can represent the organization and projects can represent products. The desired Butler/ProductMaster/TechMaster workflow still needs deliberately configured teams and operating instructions. Existing chat screens are not proof of arbitrary agent group chat, and generated status cards are not yet Wingman's prescribed per-agent current/recent/next timeline.

## Architecture and execution model

The Express server owns company-scoped state and orchestration. The React application presents it. Drizzle/PostgreSQL schemas hold agents, issues, sessions, wake requests, environments, approvals, documents and work products. An agent is a durable organization member, separate from the provider process handling a particular run.

The [agent schema](../repo/packages/db/src/schema/agents.ts), lines 20–59, includes company membership, arbitrary role/title/capabilities, `reportsTo`, adapter and runtime configuration, environment selection, permissions, monthly budget, lifecycle holds and an operation version. That is directly useful for an extensible organization: a new role is data plus instructions and an execution configuration, not a new hardcoded application class.

[Heartbeat orchestration](../repo/server/src/services/heartbeat.ts) delegates queueing, session preparation, workspaces, execution, completion and recovery into cohesive modules. [Runtime execution](../repo/server/src/services/heartbeat/runtime-execution.ts), lines 1–130 and its execution body, distinguishes provider execution, environment ownership, workspace preservation and finalization. The adapter/runner layer is responsible for actual coding harnesses. The server remains the source of work authority.

### Entry points and execution authority

The source confirms the control-plane split rather than only describing it. [Server bootstrap](../repo/server/src/index.ts), lines 493–528 and 699–719, selects external PostgreSQL or an embedded PostgreSQL cluster; lines 935–950 and 1060 onward construct the app and bind its listener. The repository AGENTS.md still mentions PGlite, but that is not the default bootstrap path inspected here. [Express app wiring](../repo/server/src/app.ts), lines 764–783, 880 onward and 1038, mounts agent, project and issue services under `/api`. This is a database-backed service with web and agent clients, not a terminal multiplexer or a set of role prompts.

A wake request is distinct from dispatch permission. [Queue admission/dispatch](../repo/server/src/services/heartbeat/queue.ts), lines 1911–1937, reloads agent invokability, counts running attempts and computes remaining slots before selecting queued work. [Runtime execution](../repo/server/src/services/heartbeat/runtime-execution.ts), lines 523–547 and 794–870, branches into native Runner execution or the adapter contract, realizes assigned MCP access and invokes the provider under a guarded dispatch callback. The [legacy Codex adapter](../repo/packages/adapters/codex-local/src/server/execute.ts), lines 1388–1425, actually launches the selected execution target, streams accounting/logs and parses Codex JSONL. The durable agent owns configuration and work authority. The run owns an execution attempt. The provider session is continuation state. This separation lets the organization persist while coding processes start, end or move across environments.

## Agent lifecycle in depth

**Definition and creation.** Agent configuration combines role/capabilities, instruction files, adapter/model settings, tools and an environment. Hiring can require board approval. Creation is not equivalent to starting a long-lived subprocess: the durable organization member is created first, then preparation and verification establish that its execution environment is usable.

The [hire route](../repo/server/src/routes/agents.ts), lines 4558–4573 and 4585–4689, normalizes skill/runtime configuration, validates environment selection, fingerprints the request and reuses an existing same-run hire when appropriate. It calls the lifecycle service with a new UUID, chooses `pending_approval` when company policy requires it, materializes the instruction bundle and creates the hiring approval. This is an executable creation path; naming a role does not itself start coding. The same-run lock and activity lookup shown here should not be mistaken for proof of exactly-once distributed hiring under arbitrary process failures.

**Lifecycle authority.** [Lifecycle effects](../repo/server/src/services/agent-lifecycle.ts), lines 32–85, connect policy holds, configuration, hiring, budget changes, creation events and dependency cleanup. The [driver](../repo/server/src/services/agent-lifecycle-driver.ts), lines 15–65, invokes lifecycle plugins and rejects results whose operation ID or version no longer matches. It resumes queued work only after readiness. Pause/termination request actual invocation stops, and some operations remain pending until execution has settled.

**Work admission and execution.** A wake request enters the queue. Scheduling, agent eligibility, budgets, issue ownership and environment readiness determine whether it may become a run. Session preparation selects or resumes the appropriate context. A configured adapter or native runner executes the coding task with an injected identity and controlled tool/API access. Thus agent identity, task identity, run identity and provider session identity are separate concepts.

**Concurrency and stale work.** Atomic issue checkout checks the assignee, expected status, execution run and dependency readiness. Subtree pause holds can prohibit checkout. The update writes both checkout and execution run ownership; competing invocations cannot legitimately become the same ticket's owner simply because they both saw it available. This is much closer to a reliable task control plane than a prompt telling workers not to collide.

**Persistence and restart.** Run/session state, events and workspace operations survive process lifetimes. [Recovery](../repo/server/src/services/heartbeat/recovery.ts) treats restart reconciliation separately from normal dispatch. Workspace saving and provider completion have separate owners; accepted provider work can still require preservation/finalization. Source presence establishes these paths, not fault-free behavior in an actual deployment.

**Interruption and retirement.** Pausing and termination pass through lifecycle state and the heartbeat stop paths. Plugin-owned resources can require cleanup; policy holds and operation versions protect transitions. Provider-specific termination limitations remain visible rather than being erased by a UI status change. Deleting an agent also removes/reconciles dependent state through the lifecycle effects and dependency cleanup service.

### The identities and states that actually exist

The lifecycle has more precision than the word “agent” suggests:

| Concept | Durable identity and responsibility | What it does not mean |
|---|---|---|
| Agent | Company member with UUID, arbitrary role/title/capabilities, manager, configuration, policy holds and lifecycle version; [schema](../repo/packages/db/src/schema/agents.ts), lines 20–55. | A continuously resident model process or one global conversation. |
| Issue/task | Assignable unit, parent/child context, dependencies, documents, comments and execution ownership; [checkout](../repo/server/src/services/issues.ts), lines 12168–12300. | A dedicated agent identity. |
| Heartbeat run | One authorized execution attempt with run-specific context, result and resource settlement. | Proof that an issue or product was accepted. |
| Task session | Saved provider continuation keyed uniquely by company, agent, adapter and task key; [schema](../repo/packages/db/src/schema/agent_task_sessions.ts), lines 17–56. | Guaranteed preservation of provider context after a configuration or model change. |
| External conversation | Channel endpoint plus external conversation/thread and session generation, bound to an internal issue; [binding](../repo/server/src/services/chat-channels/inbound/conversation-binding.ts), lines 16–70. | A project classifier or shared peer collaboration room. |

The actual [transition function](../repo/server/src/modules/agent-lifecycle/domain/policy.ts), lines 21–67, allows approval to move `pending_approval → preparing`, preparation to move `preparing → verifying → ready`, pause to move eligible agents through `pausing → paused`, and resume through `resuming`. Termination moves through `terminating → cleaning_up → terminated`; rejection is separate. Purge is permitted only for terminated or rejected agents. Compatibility `status` and `lifecycleState` are distinct: an agent can have a stable organizational identity while its execution status is idle, running or error. This is useful for Wingman's standing workforce because neither an idle worker nor the end of one run destroys the role.

[Lifecycle commands](../repo/server/src/modules/agent-lifecycle/index.ts), lines 46–100, route hiring, configuration, pause, resume, retry and termination through the same service. The [driver](../repo/server/src/services/agent-lifecycle-driver.ts), lines 12–65, selects required lifecycle plugins, passes operation ID/version/phase, checks returned operation identity, and verifies the harness before readiness. A required missing plugin is an error, not a silent downgrade. Stop phases wait for invocations to settle. These are concrete preparation and retirement hooks, distinct from simply creating a prompt file.

### Tools, permissions and execution placement

The agent row's `permissions` is only one part of authority. [Runtime MCP preparation](../repo/server/src/services/heartbeat/run-preparation.ts), lines 893–940, resolves effective assigned tools/connections and run-bound human identity; [runtime tool access](../repo/server/src/services/heartbeat/run-preparation.ts), lines 1227–1260, mints a token scoped to agent, company, run and responsible user. With no responsible user or reachable API, that tool access is unavailable. Paperclip's governance must therefore be carried into any Wingman bridge instead of sending an unscoped master credential to every worker. Coding-harness filesystem/shell permissions remain adapter/environment concerns. A governed API token is not by itself a shell sandbox.

[Runner selection](../repo/server/src/services/agent-runner-selection.ts), lines 24–94 and 97–190, evaluates environment driver and platform compatibility, native versus legacy runner availability, and whether supplied settings can be honored. It can reject incompatible settings rather than silently reinterpret them. SSH is an actual execution target here, not just a URL field. [Remote workspace reservation, preparation and saving](../repo/server/src/services/remote-workspaces.ts), lines 166–288, 373–535 and 618–734, connect remote execution to shared durable workspace authority. This supports the mechanics needed for Mac/Endeavour cooperation, while host provisioning, credentials, path policy and exact persistent project placement remain deployment decisions to validate.

### Resume, scheduling and failure semantics

[Session preparation](../repo/server/src/services/heartbeat/session-preparation.ts), lines 73–230, computes a configuration fingerprint from instructions, agent revision, model/runtime config, environment, workspace policy, secret manifest, skills and relevant overrides. It compares saved metadata, chooses a compatible provider session or resets it, and prepares a fresh-session handoff from task history. This is a strong continuity mechanism, but “same agent” does not guarantee “same model conversation forever.” Wingman should keep its authoritative product knowledge in project documents even when provider continuation works.

[Timer scheduling](../repo/server/src/services/heartbeat/scheduling.ts), lines 1296–1378, filters active companies and invokable agents, reads interval policy, claims due timer work and submits it through normal queue admission. A consequential boundary is [supportsUnscopedTimerHeartbeat](../repo/server/src/services/heartbeat-policy.ts), lines 4–11: `paperclip_runner` cannot receive a generic taskless interval heartbeat. Task-bound schedules and monitors use other paths. A Wingman ProjectMaster on that runner needs a supervisory task or routine, rather than assuming that enabling a heartbeat interval alone creates portfolio supervision.

Retries are a durable execution mechanism, not a promise of unlimited self-healing. [Retry configuration](../repo/server/src/services/heartbeat/retries.ts), lines 126–140, sets two bounded transient retry delays, 30 and 60 seconds, and classifies selected workspace preparation failures. Other reasons have their own policies. [Retry tests](../repo/server/src/services/heartbeat/retries.test.ts), lines 99–147, inspect exhaustion recording before escalation, avoiding duplicate successor work after a case handoff, and publishing promotion effects after the durable change. Those tests were read, not run in this assessment.

Cancellation has an equally important boundary. [Run-control tests](../repo/server/src/services/heartbeat/run-control.test.ts), lines 109–141, check that unknown native ownership retains leases, persisted failure changes resource disposition, and a busy warm session defers destruction. [Recovery tests](../repo/server/src/services/heartbeat/recovery.test.ts), lines 515–550, require exact authenticated remote termination evidence before retiring a remote identity. A mismatched receipt does not qualify. The [recovery implementation](../repo/server/src/services/heartbeat/recovery.ts), lines 975–1017, also distinguishes reattaching an existing local/remote runner, resuming a dead runner and incomplete bootstrap, with lease renewal for remote reattachment; lines 2019–2027 register workspace finalization as separately tracked work. The source therefore aims to avoid both losing unfinished work and falsely reporting a remote process stopped. This is an implementation contract, not evidence that every failure mode has passed against live providers.

### Completion, review and retiring the workforce

A run finishing, an issue entering review, a reviewer accepting an output, workspace copy-back completing and an agent being retired are separate events. [Required quality review](../repo/server/src/services/required-quality-review.ts), lines 11–124, is opt-in. Once accepted in policy, an agent cannot remove or change that requirement. An authenticated human can. Review targets must be exact current output-document revisions or attachments bound by asset/hash, not a plan or a generic assertion. Changed outputs make earlier approval stale. The service checks human-only resolution and the current target before reporting the gate satisfied.

This is a valuable DoD enforcement primitive, but it is not Wingman's TestMaster. Someone still must define the integrated scenarios, execute tests and attach meaningful evidence. Similarly, done tickets do not automatically retire the organization or halt every recurring routine. Wingman's accepted-product stop rule must explicitly resolve ongoing work and supervision obligations while keeping identities and records available for later continuation. Final deletion follows termination/cleanup. It should not substitute for an idle standing team.

## A concrete coordination path

A Telegram message is normalized by the channel platform implementation and passes common admission/authorization. [Conversation binding](../repo/server/src/services/chat-channels/inbound/conversation-binding.ts) connects the external endpoint/thread to an internal conversation. The channel service creates a task for the endpoint's configured agent or reuses its conversation binding, then stages normal authorized execution. This is configured-agent routing, not autonomous portfolio classification. That agent can create or update company-scoped work; assignment and dependencies govern later execution.

The worker checks out its issue, receives task/context/instructions, executes through its configured runtime and writes comments or work products. Review policy and task state control the delivery transition. Channel publication sends the response back through the originating transport. This supports a Butler-like entry agent, but the application must still teach Butler how to classify product requests and delegate to ProjectMaster.

The specific state transitions are visible in [channel processing](../repo/server/src/services/chat-channels.ts), lines 1436–1500 and 2140–2290. Incoming self/bot/system messages are filtered, provider data is normalized, and durable admission deduplicates receipt. Under task creation authority checks for both the human and assigned agent, a new thread creates a `todo` issue with `originKind: chat_channel`, an idempotency key and optional project/workspace defaults. The binding records endpoint, external channel/thread, generation, communication guidance and issue ID. A later message can reopen a done/cancelled bound task and is persisted as a comment. Project selection at this point comes from endpoint/resource defaults. It does not infer whether “the CRM we discussed yesterday” belongs to an existing portfolio project.

Downstream, the [checkout write](../repo/server/src/services/issues.ts), lines 12168–12300, tests dependency readiness, active subtree holds and expected statuses, and conditionally updates assignee, checkout run, execution run and `in_progress`. [Session preparation](../repo/server/src/services/heartbeat/session-preparation.ts), lines 73–230, loads compatible continuation/context before execution. Review gates then concern the actual saved outputs. That trace demonstrates a channel-to-task execution product; adding Butler and ProjectMaster must add the separate project-intake, discovery and delegation policy rather than assuming the transport implements it.

The key caution is chat semantics. `sendAgentChatMessage` requires a current task-bound run, verifies that it still owns its source task, and creates/uses a conversation with the responsible human. It deliberately rejects restricted source content flowing into company-visible chat. Peer work largely revolves around issue comments, mentions, assignments and handoffs. External provider group chats are supported: [endpoint schema](../repo/packages/db/src/schema/chat_channels.ts), line 74, stores allowGroupChats, and provider setup/UI exposes group participation. Those are external destination settings for a configured bot/agent, not evidence of an internal multi-agent room membership model. A chat page alone should not be counted as Wingman's two shared agent rooms.

The wake and outbound ends are also concrete. After persisting the inbound comment, [channel processing](../repo/server/src/services/chat-channels.ts), lines 2377–2384, stages an inbound wake in the task transaction. [Publication transport](../repo/server/src/services/chat-channels/publications/transport.ts), lines 302–345, supports Telegram Markdown fallback attachments and sends through the provider thread. Thus the trace is external message → durable task/comment → admitted run → task result/publication, not an assumed call directly from Telegram to a permanent model process. This is a static path trace; no actual Telegram request was delivered during review.

### Discovery and planning are shipped behavior, with a delegation boundary

Paperclip supplies more than empty text fields for product planning. [AGENT_CHAT_DIRECTIVE](../repo/server/src/services/agent-conversations.ts), lines 90–119, is injected into conversation task context by [task Markdown rendering](../repo/server/src/services/heartbeat/task-markdown.ts), lines 222–224. It asks the agent to research, clarify, develop and revise a plan, inspect available projects and repositories, reuse a suitable project or create one, and carry accepted scope into assigned execution tasks. Explicitly requested plan approval is revision-bound. An ambiguous answer with several pending proposals requires clarification. [Task-planning instructions](../repo/packages/skills-catalog/catalog/bundled/paperclip-operations/task-planning/SKILL.md), lines 18–36, say to plan only as much as the work needs and split work when ownership, parallel output, dependencies or review justify it. These are concrete prompts wired into execution, though they do not mechanically guarantee good domain research.

A critical fit limit is in that same chat directive: ordinary tasks default to the agent in the conversation, and another agent/person is assigned only when the user explicitly specifies that owner. Conversation tasks are kept separate from execution tasks. The conversational agent must not do substantial implementation in the chat. This supports a persistent planning relationship, but it is not automatically Wingman's Butler deciding to delegate through ProjectMaster and per-project leaders. Changing only an agent's display name would leave the injected handoff policy in place. Wingman needs a reviewed organizational workflow or role-aware directive extension that gives the intended delegation authority while preserving approval boundaries. This finding concerns the shipped human Agent Chat path. It does not imply ordinary managerial execution tasks are globally forbidden from delegating.

The implementation also has an actual accepted-plan decomposition API. [decomposeAcceptedPlan](../repo/server/src/services/issues.ts), lines 9819–10095, verifies that the supplied revision belongs to the source task's `plan` document and has an accepted confirmation. It stores a request fingerprint and child cursor under a durable claim. Repeating the same revision with a different child set is a conflict. Child creation advances the cursor in individually locked transactions, so partial creation can resume without duplicating the already recorded prefix. [The route](../repo/server/src/routes/issues.ts), lines 13335–13485, validates assignments, environment selection, monitor policy and attribution before invoking the service. This is a substantial technical-planning feature rather than a README promise, while the quality of the proposed decomposition still belongs to the agents.

## Major capabilities beyond Wingman's description

- **Company governance and economic controls.** Company isolation, hiring approval, scoped tools, budgets and accounting turn an organization into a governed execution system. [Budget admission](../repo/server/src/services/budgets.ts), lines 195–219, applies company, project and agent scopes, so this is more than a spending chart. Wingman could adopt these to control spending and authority, but would inherit more administrative concepts than its personal-team workflow currently requires.
- **Pluggable execution environments and lifecycle ownership.** Plugins can provision agent environments and participate in preparation/cleanup through [versioned lifecycle calls](../repo/server/src/services/agent-lifecycle-driver.ts), lines 20–65. This is a substantial extension point for remote compute, not merely another model selector.
- **Reusable team, skill and connection catalogs.** Teams can package agent instructions and skills into installable organizations. That offers a practical mechanism for Wingman's future growth beyond its initial profiles.
- **Model-generated, watched status cards.** [Status-card generation](../repo/server/src/services/status-cards.ts), lines 88–146 and 580–613, compiles a human interest prompt into bounded searches. A summarizer updates Markdown from changed issues and keeps revisions. This is a useful executive information product in its own right.
- **Governed work products and decisions.** Deliverables, task documents, approval records and [revision-bound quality review](../repo/server/src/services/required-quality-review.ts), lines 44–124, provide inspectable organizational outputs rather than only conversation transcripts. Adopting them makes artifact registration and revision identity part of Wingman's delivery contract, with the benefit that approval cannot silently apply to a later changed file.
- **Reusable recurring work as a product.** [Routines](../repo/server/src/services/routines.ts), lines 112–115, 245–265, 334–465 and 550–587, support webhook URLs, time-zone-aware cron, typed input validation and revision snapshots of routine/trigger settings. This extends Wingman's periodic supervisory wake into configurable operational workflows. It also creates obligations to manage trigger authorization, secrets, duplicate delivery and what should continue after a product is accepted.

### Portable company packages and controlled import

Paperclip can move organizational configuration and selected work as an inspectable company package, rather than requiring every installation to rebuild its teams manually. [Export construction](../repo/server/src/services/company-portability.ts), lines 3879–3934, selects agents, projects, issues and skills, excludes built-in managed skills and rejects project-restricted skills whose access cannot be preserved. Lines 4240–4274 normalize portable agent/runtime configuration, collect environment inputs and remap reporting relationships to slugs. [Export preview](../repo/server/src/services/company-portability.ts), lines 4815–4860, returns manifest/files, an inventory and resource counts. This is a useful mechanism for versioned Wingman organization templates, sharing a development team and moving a curated project setup to another instance. It is broader than the team catalog's installation entry point.

The transfer has explicit authority and validation boundaries. [Company-scoped routes](../repo/server/src/routes/companies.ts), lines 1125–1175, authorize the board or same-company CEO, provide preview/apply operations and prohibit replacement or targeting a different existing company through the safe import path. [Import implementation](../repo/server/src/services/company-portability.ts), lines 5257–5331, rejects incomplete inline bundles, preview errors, update actions in agent-safe mode and blobs whose contents do not match their declared SHA-256. Optional `pauseAutomations` parks imported agents and routines ([agent import](../repo/server/src/services/company-portability.ts), lines 5690–5703; [routine import](../repo/server/src/services/company-portability.ts), lines 6066–6088), making activation a separate operational step.

For Wingman, this means a reusable organization can be a concrete package with reviewable changes and environment requirements. Integration must still bind destination accounts, execution environments, secrets and filesystem/workspace placement. The inspected package path is not proof that a running provider process, every external credential or an arbitrary live conversation can migrate intact. Hash validation proves the packaged blob matches its declared bytes. It does not establish that imported instructions are trustworthy or that a multi-resource import is globally atomic under every failure. Source-level route checks and import validation were inspected; no actual export/import was performed.

### Governed connection and tool gateway

Paperclip also implements a connected-tool execution boundary beyond Wingman's stated chat/tracker/dashboard requirements. The [app](../repo/server/src/app.ts), lines 977–990, mounts the tool gateway alongside browser-use and plugin routes. [Tool execution admission](../repo/server/src/services/tool-gateway.ts), lines 10319–10326, validates an active gateway session and its `tools/call` authority. Lines 10975–10991 evaluate policy with session, tool, effective arguments and idempotency key, consume rate-limit policy and record the invocation/audit decision. Lines 11060–11105 persist approval requests or surface a denial with its policy/rate-limit evidence. This is implemented execution governance, not just a list of configured MCP server URLs.

The approved action is bound to what was reviewed. [Approval revalidation](../repo/server/src/services/tool-gateway.ts), lines 10872–10920, compares the current connected target to the signed approval snapshot and verifies the stored arguments' hash/signature. Lines 10330–10386 recover the originating identity context even if the run subsequently accepted steering from another person; lines 10950–10974 reject already-consumed action requests and record the execution claim. [Provider dispatch](../repo/server/src/services/tool-gateway.ts), lines 11140–11222, rechecks the current issuer, then invokes remote HTTP MCP/REST, local stdio MCP, plugin or builtin tools and validates/redacts the result before saving outcome metadata.

Wingman could use this as the shared authority layer for repository, browser and business-service capabilities across its workers. The integration consequence is that Butler, managers and remote coding agents must carry run/company/user identity through the gateway; handing workers unrestricted connector credentials would bypass the principal mechanism being adopted. Approval snapshots also require stable target/argument identity and refreshed decisions when that identity changes. These checks do not themselves sandbox arbitrary shell commands, prove perfect prompt-injection detection or establish exactly-once external side effects after an ambiguous provider failure. Live provider compatibility, human approval delivery and failure recovery across external services remain untested here.

### Experimental Cases and reusable workflow handoffs

A further substantial capability is a persistent business/work record whose primary task can move through agents and named workflow phases. [Case handoff application](../repo/server/src/services/case-handoffs.ts), lines 242–281, checks the case handoff version, task status version, old assignee, current execution ownership, original actor authority and recipient visibility before assigning that same task to the next agent and saving `pending_dispatch`. Lines 459–499 create the case/initial primary task and save initial workflow documents. [Workflow capture/application](../repo/server/src/services/case-workflows.ts), lines 8–44, snapshots workflow names/phases and the exact document revision, then adopts a selected workflow through the ordinary document revision API.

This extends Wingman's ticket-and-room structure with a durable case that can carry an evolving process across successive owners. It could implement a controlled discovery → planning → engineering → acceptance handoff. The source inspected implements explicit authorized transfers and document-based guidance. It does not establish an executable, validated state-machine language for every transition described in the Markdown. It is experimental, and a single moving primary task is a different coordination model from concurrently assigned specialist subtasks. Adopting it needs a deliberate choice about which work belongs to a case and which belongs to a parallel task tree.

## Distinctive mechanisms and innovation

The strongest design is the separation of **durable organizational authority from disposable model execution**. The [lifecycle transition policy](../repo/server/src/modules/agent-lifecycle/domain/policy.ts), lines 21–67, [conditional issue checkout](../repo/server/src/services/issues.ts), lines 12240–12285, and [task-bound chat authorization](../repo/server/src/services/agent-chat-messages.ts), lines 50–149, are concrete expressions of that design. Agent lifecycle versions, task checkout, run-specific permissions and finalization ownership prevent an old invocation from being treated as the current organization merely because it still runs.

Accepted-plan decomposition is another distinctive mechanism: an approved revision, immutable request fingerprint and persisted child cursor connect human intent to recoverable delegation. It prevents a retried planning operation from silently inventing a different task tree, while explicitly representing partial progress rather than assuming the whole handoff was atomic.

The signed connected-tool approval mechanism is also substantive: it binds the reviewed arguments and target snapshot to the originating identity, then checks them again at execution. It enables approval of a concrete external action while rejecting target drift and identity confusion. It does not convert every provider into a transactional service. The portability path similarly treats import as a previewed, mode-restricted transfer with blob-integrity checks and optional paused activation, rather than copying raw database rows without policy.

Versioned case handoffs are another grounded mechanism: task ownership transfers revalidate both the original principal and the recipient when the transfer is applied, rather than treating earlier acceptance as permanent permission. Capturing workflow document revisions also preserves what a transition meant at that time. This enables inspectable process continuity while leaving semantic workflow correctness to instructions and agent decisions.

Status cards are especially relevant to Wingman's executive dashboard. The implementation compiles the human's interest into structured queries, provides bounded snapshots or changed issues, and requests a short update from a designated summarizer. Watched issue references can expand the card's tracking scope. This is more sophisticated than counting completed tickets, but its scope and privacy controls also make it more complex to reuse as a simple agent feed.

The code also makes **result acceptance, provider termination, workspace preservation and resource cleanup separate facts**. That is valuable for distributed coding agents where a finished model turn may coexist with unfinished copy-back or uncertain remote termination. These are distinctive engineering choices in this checkout. This assessment does not establish industry-first novelty.

## Practical use for Wingman

Use Paperclip as a potential backend and operator surface for agents, projects, tickets, runs, environments, decisions and summaries. Configure a Wingman-specific team with Butler, ProjectMaster and per-project product/technical leads, and reconcile the injected chat handoff policy with autonomous managerial delegation. Prototype the discovery-to-ticket workflow before replacing Wingman's coordination layer wholesale.

The [AgentOverview component test](../repo/ui/src/pages/AgentOverview.test.tsx), lines 26–94, expects Activity, Runs, Costs, Budget used, Profile, Skills and Recent tasks. Those are useful operator controls, but they do not establish the executive current/recent/next narrative. The detailed run panel exposes provider sessions and clearing task sessions ([AgentDetail](../repo/ui/src/pages/AgentDetail.tsx), lines 3359–3407). Searches in AgentDetail and agent routes did not establish a complete uniform fork/compact/archive conversation workflow. Wingman should validate those individual controls per chosen harness rather than infer them from a generic agent-management page.

The largest adaptations are shared group-room semantics, per-agent executive current/recent/next feeds, project creation/routing policy, DIRECTIVES integration and the exact product acceptance process. Preserve the existing authority model when adding those features; bypassing it with an external chat relay would discard much of Paperclip's strongest value.
