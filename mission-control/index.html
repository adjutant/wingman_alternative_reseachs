Mission Control assessment against Wingman

Identity and verdict

  • Product: Builderz Labs Mission Control, package version 2.3.0; self-hosted agent operations control plane.
  • Repository: https://github.com/builderz-labs/mission-control
  • Local checkout: research/mission-control/repo.
  • Assessed commit: c1a846fe020567bb3ceb3b65db9f00db875618cd (actual checkout HEAD).
  • Assessment date: 2026-11-05.
  • Basis: Wingman purpose and assessment guide; static source and test inspection. No dependencies installed, services started, agent runs dispatched or external accounts contacted. Checkout sources remained unchanged.

Verdict: a useful operations and coordination foundation, but not a ready-made Wingman organization. Mission Control actually stores projects, agents, tickets, conversations, notifications, activity, usage and reviews. It can dispatch real Claude Code/Codex CLI processes or invoke an OpenClaw gateway. Its scheduler implements assignment, execution, completion reconciliation, quality review and retry. This goes substantially beyond a dashboard mockup. However, its principal abstraction is an operator-controlled fleet with tasks, rather than a persistent organization that performs product discovery, creates project leadership and specialists, negotiates scope through Telegram, integrates code and delivers an accepted product. Those behaviors would need an organizational layer and a deeper Codex execution adapter.

The distinction between execution paths is consequential. An agent database row may represent a real externally running agent, a persistent Claude base session, a one-shot CLI worker, or merely a persona sent to a plain completion API. These do not have equal tools, autonomy or continuity. The README accurately calls the product a control plane above runtime reasoning loops (README, lines 71–89), but broad runtime names must be checked against their specific code paths.

Architecture and actual execution model

Control plane and persistent state

The web application is Next.js/React/TypeScript, using better-sqlite3, Zustand, WebSockets and node-pty (package manifest, lines 1–100). The routed page imports the actual phase-three agent panel, comms panel, standup view and project manager (page entry, lines 15–17, 53, 507–509 and 567–585). The deployed system is a Node server with authenticated route handlers and local filesystem access. It is not a browser-only orchestration framework.

getDatabase() creates one process-local SQLite connection, enables WAL, foreign keys and a five-second busy timeout, runs migrations and lazily imports the scheduler and webhook listener. Scheduler startup is skipped during builds/test mode (database initialization, lines 22–98). The original schema, lines 4–102, defines tasks, agents, threaded comments, activities, notifications, subscriptions, standups and quality reviews. It is not the whole current schema: migrations, lines 689–758, 810–839, 1329–1400 and 1490–1552, add projects, project assignments, richer run records, workspace-scoped agent name uniqueness and Claude base sessions. A workspace is a control-plane tenancy/isolation boundary. A project is a separate record inside it. Neither automatically means a Git checkout or an execution host.

The server event bus broadcasts workspace-attributed task/chat/agent/run events to SSE clients (event bus, lines 18–79; SSE route, lines 12–84). It is a singleton EventEmitter per server process, with no replay cursor or external durable message broker. SQLite preserves records. The event stream itself is transient. Multi-process/high-availability deployment therefore requires more than sharing a database file.

Execution paths, with unequal depth

The primary automated path is the built-in scheduler: inbox routing → assigned-task dispatch → deferred completion reconciliation → Aegis review → done/requeue/failure. The scheduler registers one-minute dispatch, review, recurring-task and stale-task jobs and five-minute presence checks (scheduler, lines 301–429, 444–499). Jobs have per-job in-process running guards, not distributed leases. Each tick awaits jobs in sequence, but setInterval does not await the preceding tick: a later tick can skip a still-running dispatch job and execute other due jobs. Workers within one direct-dispatch batch remain sequential. The scheduler as a whole is not globally serialized.

There are four materially different execution models in task dispatch:

  1. OpenClaw gateway execution: invoke agent, or chat.send for an explicit target session; save accepted run/session IDs and reconcile with agent.wait later (lines 1813–1960, 493–619). The gateway owns the agent/tool loop. The backend WebSocket client uses the configured gateway host and port, performs the protocol connection and sends RPCs (gateway client, lines 82–174).
  2. Explicit Claude runtime: runtime_type='claude' outranks gateway/direct routing and creates or resumes/forks a per-agent base session. It starts a real host claude --print --output-format json subprocess, supplies soul content and optional tools/budget/cwd, and refuses fallback into a different authority context if this fails (dispatch, lines 997–1155 and 1820–1828).
  3. Other direct CLI dispatch: Anthropic work prefers installed Claude Code; OpenAI dispatch can use installed Codex. Codex is codex exec --sandbox workspace-write --skip-git-repo-check --output-last-message … -, with prompt on stdin, optional configured cwd and a five-minute timeout. It returns no session ID from automated dispatch (dispatch, lines 1280–1379). This is real coding execution but not a standing resumable Codex agent per role.
  4. Plain provider fallback: Anthropic/OpenAI-compatible/local/MiniMax calls send a soul/system prompt and task as a text completion request. In the inspected Anthropic and OpenAI-compatible paths there are no registered tools or iterative tool-result loop. They return text and null session ID (dispatch, lines 744–806 and 1158–1205). A successful response does not establish file edits or test execution.

External agents can also register/connect and pull work through REST. The queue route atomically claims an assigned or unowned inbox task and reports an existing in-progress task on subsequent polls (queue, lines 84–145). /api/connect stores tool/connection identity and gives heartbeat/SSE/token endpoints (connect, lines 14–75). This is a usable integration contract, not an installed remote worker daemon.

The runtime capability manifest, lines 263–355, explicitly distinguishes dispatch and resume depth: Hermes profile provisioning and OpenCode observation do not imply a task dispatcher. The manifest does not always match execution. It lists Codex cwd as false, although task dispatch resolves cwd. It lists OpenClaw PTY as true, but the actual PTY attachment route, lines 36–69, permits Claude/Codex tmux attachment and rejects gateway kinds. The code paths are the basis for this assessment.

Agent definition and lifecycle

What an “agent” actually means

The durable agent entity is an SQLite row: integer ID, name, role, soul content, runtime/session references, status, last seen/activity and JSON config. Agent names are unique within a workspace after migration 054; session keys remain globally unique (migration, lines 1490–1540; identity tests, lines 16–50). A project assignment is another row containing an agent name and a role. It does not create an agent process or make the dispatcher enforce project membership: auto-routing selects candidate agents from the workspace, not from project_agent_assignments.

A task is an assignable durable work item and result. A gateway run ID identifies an accepted invocation, while a session key/ID identifies a runtime conversation. A Claude base session is persistent per-agent conversation ancestry, and a per-task fork can differ from it. A Codex dispatch is a temporary process with no returned session identity in the automated path. A PTY is a terminal attachment process with viewers, not an agent identity. A workflow template is a saved prompt/configuration, not an independently reasoning worker. The separately exposed Agent Run Protocol record is telemetry/provenance storage and should not be mistaken for a process supervisor.

Definition, creation and provisioning

Operators create an agent using role/config/soul/session/runtime fields, optionally selecting a template. Template config includes primary/fallback models, sandbox mode/workspace access, tool allow/deny lists and allowed subagents. It is copied into the row, with optional OpenClaw config writeback. Explicit provisioning invokes openclaw agents add … --workspace … --non-interactive before insertion (create route, lines 153–274). Hermes creation can write a profile config and SOUL.md, but that does not create a Hermes task execution branch (lines 278–300).

Self-registration is idempotent by name/workspace, validates the name and a fixed role list, saves capabilities/framework and marks the agent idle (register, lines 23–125). Re-registering an existing identity updates status/last_seen. It does not automatically revise its role/capabilities. Direct connection registration can auto-create an identity, replaces previous connected records for the same agent and returns integration endpoints (connect, lines 26–75). Thus a directory entry can exist before any runtime is available; “registered” and “running” are separate claims.

Assignment, routing and execution

Task creation has explicit assignee and project fields; optional MC_COORDINATOR_AGENT routes unassigned tasks to a configured coordinator (tasks, lines 213–221). Unowned inbox tasks are otherwise scored using role keyword affinity (+10 each), config capabilities (+15), idle preference (+5), and a minimum fallback score. This is deterministic matching, not a planning model or competence assessment. Candidate selection excludes hidden/offline/error agents, and capacity selection considers fewer than three in-progress tasks (routing, lines 2111–2246). The direct-mode exception in the score function does not override the outer SQL exclusion of offline agents; do not infer all offline identities can be auto-routed merely from that comment.

The scheduler selects three assigned tasks by priority/age and claims each using an UPDATE … WHERE status='assigned'. Only the claimant invokes execution (dispatch, lines 1731–1792). This protects against a duplicate dispatch race at that transition. It is not a distributed run lease or a task-wide lock on the repository. External queue clients also atomically claim tasks, but need to implement their own execution and reporting loop.

The dispatched prompt includes ticket, priority, tags, description and optional rejection feedback. It does not automatically fetch product specifications, related conversations, sibling tasks, acceptance cases or dependency results (prompt builder, lines 268–294). Coder tools therefore need contextual instructions or a retrieval integration to operate as a Wingman specialist.

Tools, permissions and execution boundaries

OpenClaw template tool policy is runtime config; host CLI policy is a separate implementation. Claude dispatch accepts a conservative exact allowlist of tool names and a positive budget capped at USD 100; task metadata overrides agent config per field. Cwd resolution requires a configured workspace root, canonicalizes real paths and rejects traversal/symlink escape (sandbox helpers, lines 130–265). Invalid options are ignored/omitted. The CLI runs with the server's environment and login context. It is not a per-agent OS/container identity by default.

Claude dispatch passes --allowedTools, --max-budget-usd and an appended system prompt where configured. Codex passes its own workspace-write sandbox and cwd, but does not translate Claude's tool list or budget cap. The term “sandbox options” must not be read as equal enforcement across runtimes. Generic API generation has no filesystem tool loop; OpenClaw policy enforcement remains gateway-owned.

Strict workspaces deliberately deny unowned global runtime resources, including host sessions, terminal sessions, runtime configuration/tasks and transcripts (workspace isolation, lines 8–18 and 91–112). Background dispatch/review joins only shared workspaces. This is a meaningful boundary, but it means selecting strict isolation can remove the execution surfaces Wingman needs until ownership-aware adapters are built.

Concurrency and host routing

Several external workers can poll the shared server and several accepted gateway runs can proceed independently. However, direct task dispatch awaits each selected process inside a for loop. There is no Promise.all worker pool or per-product semaphore. Routing's capacity check does not prevent manually assigned batches from targeting the same runtime concurrently through other routes. There is no automatic branch/worktree creation tied to worker identity. Two coding specialists pointed at the same directory must coordinate file ownership themselves.

Gateway inventory stores multiple hosts, but the central RPC helper constructs its address from config.gatewayHost/gatewayPort. The automated dispatch branch does not select a gateway from the agent's host assignment. Remote HTTP clients can share the tracker, but implementing durable project placement and full worker process control on the Mac and Endeavour remains Wingman work. Merely configuring a remote gateway or observing its devices does not establish that complete distributed lifecycle.

Persistence and resume

Work records survive server restarts in SQLite; conversations/transcripts also depend on native runtime stores and filesystem availability. Claude opt-in lazily claims a server UUID with a guarded update. First dispatch uses --session-id; later ones use --resume <base> --fork-session. The fork ID is saved on the task (base-session lifecycle, lines 45–101; dispatch, lines 997–1010 and 1093–1155). A failed first dispatch marks materialization to avoid retrying --session-id into a collision loop. That permits a resume attempt. It does not prove the on-disk session is healthy. Rotation clears the base pointer for a later fresh claim.

This is useful conversation ancestry, but later task forks do not feed their accumulated histories back into the base automatically. Wingman still needs a shared knowledge update protocol and clear distinctions between standing agent identity and task-specific conversation branches.

The manual continue endpoint supports claude --resume, codex exec resume and opencode run --session. For Claude it reads authoritative cwd from a transcript, offers coexist/block-active/nudge host-session modes, and may fall back to a fresh session when the requested one is missing (continue, lines 40–123, 191–259 and 262–287). Coexist is default, allowing interleaved native-session writers. Replies are buffered until the subprocess finishes (explicit TODO, lines 156–165). This is neither a universal streaming session transport nor a guarantee that an apparent resume preserves history.

Scheduling, supervision and waking

Scheduler state (nextRun, running, last result) is held in process memory; work to be performed is queried from SQLite. The scheduler starts on server/database initialization, not from a separate durable workflow engine. Recurrence is task metadata: a template row stores cron/last_spawned_at/spawn_count; due schedules clone a dated child task, allocate a ticket and update the template in a transaction (recurring tasks, lines 54–180). This can schedule a supervisor task, but it does not provide ProjectMaster's reasoning or active conversations by itself.

Heartbeat reads discover assignments, notifications and urgent activity. The POST can report status/activity, connection heartbeat and usage (heartbeat, lines 64–159 and 168–235). GET also updates status to idle, so a presence check is not an independent proof of current execution. Manual waking sends a gateway session message. It is not OS-level resurrection of a stopped Codex process. The scheduled heartbeat job marks stale agents offline and writes notifications (scheduler, lines 176–228).

Interruption, cancellation and failure recovery

Gateway session control supports monitor/pause/terminate: terminate calls sessions_kill, while pause/monitor send control messages (session control, lines 35–65). Actual pause semantics depend on the runtime. Host CLI dispatch has timeouts—180 seconds for Claude, 300 seconds for Codex—and sends SIGTERM; Claude also kills on excessive output. The automated dispatcher does not retain a per-task process handle exposed through a common cancellation API. Deleting a task or marking a pipeline cancelled should not be interpreted as stopping its already running subprocess.

Ordinary dispatch exceptions increase dispatch_attempts. The code reassigns for retry and moves to failed at five attempts (failure tail, lines 2029–2081). The same counter participates in quality rejections, whose threshold is three. Stale in-progress tasks older than ten minutes are requeued only if their agent is offline/unknown, eventually failing at five attempts. The check is skipped in direct-API mode (stale recovery, lines 1640–1724). This detects absent workers, not a busy-but-looping agent, and has no process-tree reconciliation or guaranteed idempotency of repository side effects on retry.

Accepted gateway runs remain in-progress with metadata. Reconciliation waits by run ID, handles completion text, optionally searches local transcript messages after task markers, and transitions to review with a comment. Accepted sends without run IDs are explicitly labelled manual reconciliation rather than pretending a session ID is a run (dispatch, lines 431–619, 1846–1889 and 1915–1956). This is a well-defined recovery boundary. A run reported completed without usable text can still become a reviewable task using fallback text; that is not artifact verification.

Two static limitations deserve attention before adoption. The rejection insertion text is Quality Review Rejected (attempt …): (line 1592), whereas redispatch searches LIKE 'Quality Review Rejected:%' (line 1798). The intended feedback path appears not to match its own inserted comments. Also, Aegis's review → quality_review update lacks the dispatch path's WHERE status='review' claim guard (lines 1480–1482), so the in-process scheduler guard should not be generalized into cross-process review deduplication. These are source observations, not reproduced runtime failures.

Completion, acceptance and retirement

A nonempty direct response sets task outcome success and status review, truncates the stored resolution at 10,000 characters and adds a worker comment (dispatch, lines 1963–2025). Aegis's prompt includes the description and up to 6,000 characters of resolution. It parses VERDICT: APPROVED by substring, records a review and sets done, or requeues/rejects; errors revert to review (Aegis, lines 1407–1623). It may call a persona named Aegis through the configured provider/gateway rather than enforce a distinct independent TestMaster process. The core check is response adequacy, not mandatory filesystem inspection or functional acceptance.

Task-update routes require Aegis approval to move to done. That is a useful state gate. It does not ensure a human accepted the overall product, stop all associated agents after delivery, merge/integrate work or publish a deliverable. Product-level acceptance and quiescence are absent from the traced path.

Agents can be hidden; administrator deletion optionally calls OpenClaw workspace deletion, tries config cleanup, then deletes the row and records an event (delete, lines 214–300). Config-cleanup failure is reported as a warning while database deletion proceeds. No general local Codex session retirement, in-flight worker cancellation, task reassignment or transcript archival accompanies this route. PTY cleanup kills its attachment after five minutes without clients, not necessarily the underlying tmux workload (PTY manager, lines 152–195). Daily data cleanup is retention-based, not a product-delivery lifecycle.

Coordination mechanics and a concrete task trace

This is a source-traced request path, not a runtime scenario exercised during assessment. Consider an authenticated operator creating a project ticket, “Implement the applications API,” with a coder assignee.

  1. POST /api/tasks authenticates the operator and workspace, validates the body, resolves the project/assignee, validates mentions, increments the project's counter and inserts the task in one transaction (tasks route, lines 174–283). It creates subscriptions and assignment/mention notifications (lines 294–323), joins project information for the response and can trigger outbound GitHub synchronization (lines 326 onward).
  2. With no explicit assignee, an opt-in coordinator can own intake; otherwise the scheduled router scores workspace agents and moves an inbox ticket to assigned. This is assignment, not technical decomposition or a check that the agent belongs to that product (router, lines 2152–2246).
  3. The next dispatch tick atomically claims assigned→in_progress and records an activity. It constructs a prompt and selects the explicit-Claude, direct-provider or gateway path (lines 1728–1828). A gateway accept records run/session metadata and leaves work in progress. A CLI response is stored directly for review.
  4. During execution, agents can read/update tickets through REST, add comments with mentions, post chat messages or poll heartbeats. Persisted chat is separate from forwarding: forward is optional. Without it, the route stores/broadcasts a message without ensuring a runtime consumed it. With forwarding, it resolves the agent/coordinator session, attempts gateway delivery and emits visible offline/error/processing status where appropriate (chat route, lines 377–418, 442–512 and 513–706). The direct agent-message endpoint requires a configured gateway session key (agent message, lines 43–88).
  5. Completion reconciliation or direct execution writes the worker result/comment and review status. Aegis evaluates the result, records approval/rejection and sets done or assigned/failed. Failure escalations are task events, not a management conversation (dispatch, lines 509–619, 1532–1623 and 1983–2025).
  6. Dashboard listeners receive workspace SSE events, while later page loads query durable SQLite state. Comms views derive timeline and inter-agent graph from message rows. The graph does not itself deliver, synchronize or resolve anything (comms, lines 24–111).

Coordination is consequently strongest for shared records and observable task state. There is no transactional sequence unifying “ticket assigned, room message delivered, agent started, files locked.” Dependencies are a particular gap: the main task schema/creation/router/queue path has no prerequisite task graph or readiness check. Ordered pipelines are a different primitive. Pipeline runs, lines 8–33, 95–156 and 229–310, snapshot prompt-template steps with stop/continue failure policies, but advancement is an explicit API action with a caller-supplied success flag. Spawning uses an OpenClaw command and does not wire a task-dependency DAG or automatic accepted-result handoff. Cancellation updates run/step state. It does not issue a runtime kill in this path.

Human decisions can enter through ordinary chat, execution approvals or quality review. They are not first-class product questions with responsible agent, project/spec reference, answer correlation, expiry or escalated-room ownership. Conversation IDs can encode such context, but that convention would need to be implemented and enforced for Wingman.

Major capabilities beyond the Wingman description

Runtime operations and capability-aware adapters

Mission Control detects and manages several runtime installations, exposes health/configuration and declares adapter capability depth. It can therefore serve as a fleet console across existing tooling instead of requiring every worker to be Codex. The benefit is practical visibility. The cost is heterogeneous semantics. The runtime manifest's Hermes/OpenCode dispatch=false declarations and the external framework adapter contract make the distinction explicit (runtime capabilities, lines 263–355; adapter contract, lines 29–67). For example, the CrewAI adapter, lines 8–50, broadcasts registration/status/task events and reads pending assignments. It does not run a CrewAI agent or persist every task report. Wingman could absorb heterogeneous telemetry, but should not assume these adapters are full worker controllers.

Financial and performance governance

The schema/API provide token/cost tracking, task outcomes/feedback and agent evaluations. The evaluation engine derives completion/correctness from task records and tool reliability from MCP logs. It computes convergence as total calls divided by distinct tools. It derives drift from rolling metrics (agent evals, lines 34–95, 112–181 and 189 onward). This is useful for operational baselines and prioritizing investigation. It does not establish code correctness or reasoning quality: repeated use of one appropriate tool can resemble “looping,” and absent data may default to perfect scores. Wingman would need calibrated product/test evidence before using these numbers for autonomous staffing or acceptance.

Audit receipts and run provenance

The platform stores structured run steps, tool/cost/model/runtime fields, parent lineage and evals through the Agent Run Protocol model (runs, lines 15–98 and 127–175). Run provenance is workspace-scoped in its API (provenance route, lines 9–25). MCP call audit records can be signed using a canonicalized payload, SHA-256 and Ed25519, with verification endpoints (receipt signing, lines 27–113 and 121–147; MCP audit, lines 42–91 and 155–224).

These are valuable building blocks for evidence-linked timelines and accountable tool use. Limits matter: run hashes cover selected configuration inputs, not the whole output/artifact content, and signing keys persist in the same local settings database. A signature shows a record matches a signing key's payload. It does not prove tests passed, prevent a fully privileged database/key owner rewriting history, or automatically capture every runtime action. The automatic task-dispatch path does not by itself create complete diff/test/browser receipts, as the runtime manifest also acknowledges.

Bidirectional GitHub issue synchronization and external automation

The GitHub sync engine pushes task descriptions/status/priority, preserves non-Mission-Control labels, records issue mappings/sync timestamps and pulls updates by project (GitHub engine, lines 38–145). It can make a Wingman tracker participate in an existing repository workflow. Integration requires resolving the source of truth and acceptance policy: closing an issue because a task is done is not equivalent to a verified merged change.

CLI, MCP, REST, webhooks and transient SSE offer automation surfaces beyond Wingman's described Telegram/dashboard interface. Webhooks have persisted deliveries/retry support, and the scheduler processes retries (migrations, lines 170–196; scheduler, lines 346–353 and 468–470). They can bridge a Butler service or external CI; durable orchestration must still handle duplicated deliveries, downtime and independent execution completion.

Knowledge operations and deployment governance

Filesystem memory browsing, full-text ranking, context summaries and knowledge-health signals are more operationally developed than Wingman's basic directives layout. The context endpoint returns file trees/recent files/health signals; scoped FTS ranks indexed document text (context, lines 11–65; search, lines 24–43, 61–108 and 174–244). These can improve retrieval and maintenance, but they do not automatically decide which scope/spec is authoritative or inject those documents into every task.

Workspace/tenant checks, per-agent keys, strict/shared runtime boundaries, device pairing, audit/security signals and administrator operations make the system useful for governing a deployment. Strict mode explicitly disables unowned host resources rather than pretending they are scoped. Wingman can reuse the policy shape, but would need ownership metadata for the two execution hosts and product workspaces; splitting each product into a strict workspace currently sacrifices parts of integrated execution.

Grounded mechanisms and innovation assessment

These are distinctive combinations in the inspected implementation, not claims of historical invention or uniqueness.

1. Durable tickets bridged to asynchronous native runtime runs. Saving dispatch_run_id, dispatch_session_id and explicit async state allows the UI/server to stop waiting for a gateway agent while preserving a later completion path. Run-ID-only reconciliation and accepted_without_run_id avoid treating acceptance as completion or polling the wrong identifier. Transcript recovery adds a fallback when the gateway completes without returning text (dispatch, lines 409–619 and 1846–1956). The limit is output attribution by task markers/native filesystem availability, and review promotion can occur with fallback text rather than a verified artifact.

2. Explicit authority and persistent-session ancestry for Claude agents. The opt-in runtime branch takes precedence over automatic provider selection, lazily allocates a per-agent base UUID, forks task sessions and refuses fallback on failure. This lets persistent identity coexist with bounded task conversations without silently changing the login/policy context (Claude sessions, lines 45–101; dispatch, lines 1093–1155 and 1820–1828). It is a useful pattern for Wingman's Codex adapter. It does not guarantee task-fork knowledge is consolidated or that concurrent first-session creation/process execution is fully serialized.

3. Honest capability differentiation paired with operational surfaces. A manifest distinguishes installed/authenticated from dispatch/resume/PTY/tool-policy/budget/receipt depth. That prevents treating every logo as a fully controlled agent (manifest, lines 263–355). Its current discrepancies with actual PTY/cwd code show why capability contracts need executable conformance checks and runtime-version qualification.

4. Workspace isolation through denial of unowned runtime resources. Instead of filtering global sessions by display names, strict workspaces deny access until authoritative ownership exists; memory separately uses workspace-specific root/index scopes (isolation, lines 45–68 and 91–135). This provides a concrete migration path from single-user host integrations toward stronger tenancy. Its price is reduced functionality until runtime ownership is implemented.

5. An observable autonomous task loop with explicit review/failure states. Keyword routing, atomic dispatch claims, deferred reconciliation, review records, bounded retry and failure escalation are assembled into a practical closed task loop (scheduler, lines 479–487; dispatch, lines 1532–1623, 1762–1792 and 2029–2081). Wingman can reuse the state-machine shape. Its semantic boundary remains the task's reported resolution: independent verification, product intent and management judgment are outside that loop.

Practical fit and what remains to build

Useful directly:

  • the SQLite project/ticket/comment/notification records.
  • agent directory and configurable profiles.
  • project-filtered Kanban.
  • per-agent tasks/activity/standup reporting.
  • web chat persistence.
  • runtime session observation.
  • usage/evaluation/audit surfaces.

The REST/CLI/MCP integration contract; periodic dispatch and mechanical recovery. These components would reduce the amount of ordinary control-plane CRUD/UI Wingman must build.

Needs substantial adaptation: implement a Codex adapter with stable agent↔conversation identity, resumable/forkable sessions, streamed typed events, tool/approval visibility, queued steering, stop/interrupt semantics and explicit goal/budget handling. Map projects to persistent repositories/hosts/worktrees; map workers to roles and project membership in assignment logic. Introduce task dependencies and readiness/integration gates. Extend chat from arbitrary thread IDs to project rooms with membership, task links, correlated decisions and reliable agent inbox consumption. Build evidence ingestion so agent summaries lead to actual diffs/tests/artifacts rather than just claimed success. Formalize product directives and include the relevant context during dispatch.

Still to build as Wingman behavior:

  • Butler's Telegram intake and reply correlation.
  • ProjectMaster's portfolio routing and supervision.
  • Adaptive ProductMaster discovery/specification.
  • TechMaster decomposition/staffing.
  • Workload-based specialist instances.
  • Direct room collaboration and management escalation.
  • Genuine two-host scheduling/recovery.
  • Integrated TestMaster acceptance and delivery followed by quiescence. Giving these names to existing agent rows would configure personas, not implement the intended organization.

A practical adoption boundary is to keep Mission Control as an operations/tracker UI while Wingman owns the domain workflow and worker runtime adapters. Start by integrating one real resumable Codex specialist with one project and a completion evidence contract, then connect organizational decisions and a second host. If Wingman must supply native Codex workspace fidelity, robust distributed execution and all organizational intelligence anyway, reuse should be weighed against the coupling to OpenClaw/global filesystem assumptions and the breadth of alpha control-plane surface. This report establishes mechanisms worth reusing, not a cost estimate or runtime deployment recommendation.
