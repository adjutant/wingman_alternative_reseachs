cmux assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/manaflow-ai/cmux . Checkout: research/cmux/repo. Assessed commit: 7af8f3ce26c8e6e181cabe60ebef679ff25f55ca (actual local HEAD). This is a fresh source assessment of that revision, not a claim about the current hosted product. The comparison target is WINGMAN_PURPOSE.md.

Verdict: cmux provides a strong coding workbench and several useful control-plane mechanisms for Wingman. Chief is a Claude/Codex-backed human coordinator with durable conversations and memory. The checkout also implements worker dispatch, durable messages, attention/approval feeds, recovery, remote execution, mobile chat, Cloud VMs, and CodeRouter.

Wingman still needs project intake, a product registry, separate product/technical leaders, and shared assigned tickets. Organization rooms, Telegram routing, accepted delivery, and portfolio supervision also need implementation. Naming a coding session BackendCoder does not establish an enduring organizational responsibility.

Architecture and actual execution model

Native host and separate execution lanes

The main application is a native Swift/AppKit/SwiftUI host built around workspaces, pane/surface identities and Ghostty terminals. The CLI submits control requests rather than owning the GUI's workspace graph. A particularly concrete entry path is CMUXCLI+ChiefDispatch.swift, lines 48–170: validate app capabilities, read the task, optionally create a Git worktree, prepare a launcher and call workspace.create with initial terminal input. The returned workspace/surface UUIDs are the control addresses. The terminal then owns a separately running Codex or Claude process, with its own provider session and repository access.

Chief is a separate, implemented conversational agent, not merely a proposed persona. ChiefService.swift, lines 130–174 and 265–274, loads a ChiefConversationOwner, builds a native Home store and chooses a real harness brain. ChiefCatalogSection.swift, lines 14–54, makes Chief enabled by default, Claude the default harness and permission bypass off by default. ChiefTurnContextBuilder.swift, lines 18–41 and 47–81, supplies memory, instructions, workspace snapshots, model settings and the control socket. Chief can inspect workspaces, launch workers and message them. The behavior is partly prompt-directed: ChiefSystemPrompt.swift, lines 169–230, explicitly teaches the CLI, one independent task per workspace, worktree selection, dispatch and status inspection. This is useful coordination, but no typed ProductMaster/TechMaster organization appears underneath it.

The browser-based agent-chat sidecar registers providers and creates session/conversation IDs. Its session registry is a process-local Map. It serves loopback HTTP/WebSocket traffic with host, origin, and token-path checks. See server.ts, lines 152–207, 384–447, and 2111–2125. types.ts, lines 1–37 and 95–140, defines provider-neutral events and adapter contracts.

Claude uses a separate process. Codex sessions are independent threads sharing one codex app-server. They do not each have an OS process. codex.ts, lines 96–151 and 263–307, implements thread creation/resume and turn start through that shared server. Native terminal agents, Chief processes, and sidecar sessions have different owners. Their persistence and permission guarantees need separate review.

Persistence and projections

Chief uses a different backend topology. ClaudeCodeBrain.swift, lines 4–12 and 60–70, keeps one stream-JSON process per conversation. It resumes after process loss. CodexAppServerBrain.swift, lines 4–13 and 42–44, uses one app-server process and one thread per Chief conversation. The sidecar instead shares its Codex app-server across threads.

Chief's conversations are durable JSONL logs with real participants, read cursors, streamed drafts, tool/work rows, questions and approvals. ChiefConversationOwner+Loading.swift, lines 22–49 and 64–127, loads conversation files off the main thread, preserves damaged originals and settles interrupted state. ChiefConversationOwner+Turns.swift, lines 139–147, persists provider session IDs. Chief memory is injected at conversation startup and refreshed through a preamble when it changes. It is separate from worker repository directives.

Local agent lifecycle is reduced from semantic hooks into a durable journal and UI state. AgentJournalLifecycleCenter.swift, lines 4–16, 93–147 and 153–186, commits events before ordered reduction, awaits main-actor application and separates live events from replay. AgentJournalEventKind.swift, lines 8–39, distinguishes turns, children, approval/question/plan requests, errors, messages and session end. This is meaningful execution telemetry, not an executive progress narrative or shared project tracker.

Native session snapshots preserve pane layout, agent bindings and restore metadata; see SessionPersistence.swift, lines 455–475, 1555–1614 and 1821–1839. In contrast, sidecar replay history is in memory and capped: server.ts, lines 461–496. Terminal-backed sidecar views can reconstruct from provider transcripts, whereas freshly created sidecar sessions do not thereby acquire a durable server-side registry. The reconstruction and stale-view cleanup paths are server.ts, lines 687–727 and 775–807: re-resolve by provider session identity, attach a transcript tail, and stop tailing/remove an unviewed projection after a grace period.

Remote and Cloud execution

This is real remote execution infrastructure, not just a subprocess on the Mac. CMUXCLI+SSHTui.swift, lines 4–47, carries SSH destination/options and the remote initial command into workspace.ssh.open; SSH is the carrier for daemon-owned terminals. SSHTuiAgentStatusProjector.swift, lines 6–14 and 40–66, projects remote daemon agent badges into native lifecycle state, clearing stale status on disconnect. The Rust remote daemon handles authenticated links in daemon.rs, lines 64–79, 769–806 and 1407–1422. Cloud has a provider-independent persistent runtime abstraction with tenant/owner identity, idempotency keys, versioning, lifecycle and suspend/resume/attach interfaces in persistentWorkspace.ts, lines 5–102. This is machine/workspace orchestration, not a shared organizational work graph.

Agent definition, creation and full lifecycle

What is an agent here?

There are four distinguishable concepts. First, an installed coding harness such as Codex, Claude, pi or an ACP CLI is an executable/protocol family. The native Vault registration describes how to detect it and resume/fork its sessions, not its job description. Second, a worker instance is a concrete CLI/provider conversation attached to a workspace/surface and directory. Its assignment is task text and its persistent identity is chiefly the provider session ID. Third, Chief is a durable human-facing conversational participant with its own logs, memory, tool policy and backend harness. Multiple Chief conversations can run separately, but they do not instantiate a team hierarchy. Fourth, sidecar SessionCtx is an in-memory transport/controller record around a process/thread/transcript; its short UI ID, conversation ID and provider session ID serve different purposes.

This distinction matters operationally. Wingman needs BackendCoder-2 to retain responsibility and project identity while its conversation is resumed, replaced or compacted. cmux can preserve and address a particular coding session extremely well. It does not provide the domain object that remains the same organizational worker across arbitrary conversation replacement.

Definition and configuration

Native custom agent support is concrete. VaultAgentRegistry.swift, lines 13–24 and 52–106, declares identity/name/icon, detection, session-ID source, resume/fork templates, cwd policy and session directory. The decoder validates IDs and requires session placeholders in resume/fork commands. Registrations merge by ID, and project config extends global entries at lines 459–494. Built-in process classification is separately defined in CmuxTaskManagerCodingAgentDefinition+BuiltIns.swift, lines 4–47, including wrapper aliases and executable/argument signatures. A process-classification catalog is not a configurable organization role catalog.

Chief engine settings choose Claude/Codex, model, effort and permission bypass; ChiefEngineSettings.swift, lines 5–42, normalizes settings and prevents carrying unsupported effort choices between models. Its identity/behavior prompt incorporates current workspaces, facts, profile and instructions. Sidecar providers instead come from a static registry and adapter map in server.ts, lines 152–182; adding an ACP provider requires code registration, not merely declaring a new specialist profile in the UI.

Creation, identity and execution

A Chief conversation is created through the Home owner, not by opening a bare shell; ChiefService.swift, lines 249–256, calls .createChief. Conversation loading creates the default human/Chief participants and initial conversation if absent (ChiefConversationOwner+Loading.swift, lines 52–92). Provider session identifiers are persisted when the brain emits .session, enabling subsequent turns to resume the same backend conversation.

For workers, chief dispatch accepts task words, a prompt file or stdin, optional explicit agent args, a cwd or new worktree and branch. CMUXCLI+ChiefDispatch.swift, lines 58–115, rejects when Chief is unavailable, creates the worktree if requested, creates private launcher files and opens a new workspace. ChiefDispatchPlan.swift, lines 3–13, explains the task boundary: the launcher reads the private task file, deletes its temporary directory and execs the chosen agent with the whole prompt as one argv element. Workspace creation sends a fixed launcher command to a terminal. The task itself is not parsed as shell code. That protects task text quoting, but the prompt can still be visible in process argv, as the CLI help states.

The dispatch result contains workspace UUID/ref, surface UUID/ref, agent, title, cwd and optional worktree/branch. --wait-working is a launch-readiness check, not task completion: lines 172–215 wait on surface.wait_text_change revisions and classify the screen until working or a deadline. Failures distinguish trust/sign-in/missing binary/timeout. There is no durable assigned-ticket acceptance or automatic duplicate-work reconciliation after a general coordinator restart.

Sidecar session creation (server.ts, lines 384–447) starts idle and broadcasts session summaries. Its first send invokes the provider adapter. Codex single-flights first-thread creation and post-crash resume, then calls turn/start with model/effort/approval/sandbox choices (codex.ts, lines 96–151). The shared app-server's response requests have 30-second timeouts (lines 263–307). Independence here is conversation and execution state, not a guaranteed OS-process boundary per worker.

Tools, permissions and human input

Normal terminal workers retain their harness's tools, authentication and permission prompts. Chief dispatch does not silently add bypass flags (ChiefDispatchPlan.swift, lines 17–28). Chief itself has an explicit tool gate: ChiefToolPolicy.swift, lines 5–38 and 67–89, auto-allows bounded inspection/search, asks for writes and many control actions and scrutinizes shell constructs and credential paths. Its “Always Allow” rules are loaded per owner/home before a turn. Its default is human review of mutating delegation/control, with an opt-in dangerous bypass setting. This is a different autonomy balance from Wingman's routine autonomous coordination.

Permission behavior is not uniform across surfaces. Chief converts actual backend approval requests into cards and retains turn-scoped request mapping (ChiefConversationOwner+Turns.swift, lines 194–212). Native mobile chat has an explicit answer RPC (TerminalController+MobileChat.swift, lines 50–61). However, the sidecar Codex adapter does not provide an interactive approval UI: codex.ts, lines 377–404, accepts supported requests only when its approvals setting is never, otherwise declines, and rejects unsupported reverse requests. That limitation must survive any evaluation that combines all these interfaces. A terminal-backed chat view can direct the human to the existing terminal. It is not a second independent agent with a duplicate permission channel.

Routing and concurrency

Chief sees a snapshot of all native workspaces, but the prompt tells it to re-read before acting. It chooses worker destination/provider by language-model reasoning and explicit command arguments. No deterministic project/intake router or staffing optimizer was found. Chief's owner holds a queue per conversation and a running map: ChiefConversationOwner+Turns.swift, lines 29–65, starts one turn at a time in each conversation and leaves other conversations independent. A read cursor must advance durably before queued work starts, with a cancellable retry if persistence fails.

Workers run simultaneously in different terminals/worktrees. Nothing in that fact ensures filesystem isolation if two workspaces use the same cwd. Dispatch's optional worktree is a useful concrete isolation mechanism, but branch integration, ownership conflicts, task dependencies and shared test resource contention are not automatically coordinated. Sidecar starts are idempotent within bounded request-ID caches: server.ts, lines 2364–2415, reuses a start promise, tracks cancellation during startup and replays history when a client retries. This avoids duplicate transport requests, not semantic duplicate assignments across an organization.

Persistence, resume, fork and background continuity

Chief saves provider session IDs, conversations and work rows. Its memory context separates durable facts from provider context and inserts memory-change preambles when resuming. Its backend process remains app-owned: ChiefService.swift, lines 176–179 and 259–274, stops turns/processes when disabled or shut down. Durable history does not mean Chief runs autonomously after the application exits.

Native session snapshots record agent and resume bindings, working directory, running state and restore recovery. The trust distinction is explicit: SessionPersistence.swift, lines 455–475, treats untrusted imported bindings as manual-restore-only rather than automatically executing them. Vault registrations encode provider-specific resume/fork recipes. Sidecar forkSession rejects a running source, copies event history, delegates native provider fork, records parent/conversation lineage and removes the child if fork fails (server.ts, lines 825–855). Generic UI support does not guarantee every provider supports native fork, compaction or restore.

Hibernation is a separate resource lifecycle. AgentHibernationController.swift, lines 10–55 and 59–119, tracks process identity, protected/busy state, transcript validation and settings-driven timers. AgentHibernationController+Manual.swift, lines 3–28 and 60–88, documents concrete refusal conditions: visible, busy, unknown lifecycle, recent activity, unconfirmed input, unsafe process scope, missing restore evidence or teardown in progress. It frees supported idle agents while retaining a route to resume. It is not task retirement or success acceptance.

Remote terminals have daemon-owned state and a Rust journal with explicit replay classes/policies and authority metadata (session_journal.rs, lines 19–55 and 78–104). This is a stronger basis for remote background continuity than a GUI-only shell view. Runtime daemon adoption/upgrades and hosted availability were not exercised in this assessment.

Scheduling, interruption, failure and recovery

No autonomous project supervision loop was found. There are three narrower mechanisms: event-triggered AutomationEngine actions, retryable-error auto-resume and resource hibernation timers. The Chief wake scheduler explicitly owns a single replacement one-shot engine deadline (ChiefWakeScheduler.swift, lines 4–26). It must not be mistaken for a persistent cron-like ProjectMaster.

Chief stop commits partial text, marks outstanding work failed, interrupts its brain and cancels the consuming task before starting queued input (ChiefConversationOwner+Turns.swift, lines 6–25). Chief exposes retry of the previous user turn (ChiefService.swift, lines 221–233). Loading isolates damaged logs, keeps readable records and expires unresolved previous-run approvals rather than letting stale cards authorize new requests (ChiefConversationOwner+Loading.swift, lines 16–29 and 97–127).

Sidecar Stop covers the creation race as well as existing sessions (server.ts, lines 2470–2489). Codex stop requests use turn identity rather than killing the shared app-server, and codex-stop-timeout.test.ts, lines 15–82, specifies that repeated Stop during startup shares one bounded waiter and reports one failure. Sidecar fork/delete disposes adapter resources, not necessarily provider transcript files. Auto-resume is deliberately conservative: AgentAutoResumeCoordinator.swift, lines 8–15, 110–144 and 182–192, checks a managed-session match and terminal screen state before sending continue, a Codex goal resume or Return. New input/permission/new turn cancels pending retry. This recovers a narrow class of transport/capacity stalls. It does not diagnose a blocked ticket or reassign failed work.

Completion, acceptance and retirement

Provider done, a Chief .finished event and inferred workspace “done” are execution signals, not proof the requested product passed acceptance. Chief dispatch only verifies startup. Workspace status can infer review/done from PR and Git state (Workspace+Todos.swift, lines 15–53), but does not evaluate acceptance scenarios or gather independent TestMaster sign-off.

Sidecar delete disposes its adapter and removes the Map entry (server.ts, lines 2583–2592); SIGINT disposes all sessions at lines 2609–2612. Native workspace close, provider exit and hibernation remain separate operations. Chief Home hiding is explicitly only a durable local projection because its owner has no delete/archive operation yet (ChiefHomeView.swift, lines 20–37). Dispatch cleans its temporary launcher, but no reviewed lifecycle here automatically closes PRs, merges branches, removes task worktrees and retires an organizational specialist after acceptance.

Coordination mechanics and a traced request

A concrete, implemented flow is the documented cmux chief dispatch --agent codex --name ... --cwd ... --wait-working --json -- '<task>' recipe. It is not necessary to assume that the LLM follows the recipe perfectly to establish what the mechanism does.

  1. Human intent reaches Chief. Home submits a user message to ChiefConversationOwner. The per-conversation queue advances its read cursor before running the backend (ChiefConversationOwner+Turns.swift, lines 29–65). The backend receives the current memory/instructions, socket and workspace snapshot via ChiefTurnContextBuilder.swift, lines 18–41.
  2. Chief decides a task and asks for the necessary control permission. The prompt teaches one task per independent workspace and a standalone assignment including what to report (ChiefSystemPrompt.swift, lines 208–229). Dispatch is mutating and normally asks under ChiefToolPolicy.swift, lines 19–38. Its approval is an executable human decision in a Chief card, not a management-room escalation record.
  3. The CLI creates execution context. CMUXCLI+ChiefDispatch.swift, lines 86–115, creates a worktree if requested, stages a private launcher and calls workspace.create. Lines 117–152 return concrete addresses and readiness/failure evidence. The worker CLI then runs independently in the selected directory.
  4. Worker activity becomes shared visibility. Provider hooks record semantic journal events; AgentJournalLifecycleCenter.swift, lines 93–147, reduces committed events into sidebar state and attention. The worker's detailed terminal can be opened, and the existing transcript can also be viewed through chat/mobile APIs. TerminalController+MobileChat.swift, lines 42–74, distinguishes history, send, interrupt, answer and artifact operations.
  5. Another agent can send a direct coordination message. TerminalController+AgentMessages.swift, lines 49–147, resolves target or reply-to into a recipient surface/workspace, enforces relay scope and constructs a threaded draft. AgentMessageStore.swift, lines 160–199, validates and appends the journal record before publishing the queued state. This is a real durable inbox rather than arbitrary keystroke injection.
  6. Delivery follows provider hook semantics. AgentMessageStore.swift, lines 21–40, 114–119 and 202–217, implements poller ownership, deferred leases and claiming. Claude's wrapper installs a background asyncRewake inbox hook on session start/stop in cmux-claude-wrapper, lines 2062–2063. Provider limitations are explicit in agent-messages.md, lines 21–29: Claude can wake idle interactive sessions; Codex/Kiro messages wait for compatible prompt/stop hooks; headless paths do not receive them. Messages are held during a human prompt. The recipient can reply by ID; read/delivered are transport/turn milestones, not confirmation that the requested code change was made.
  7. Outcome returns through conversation/status. Chief can inspect the worker by CLI and report to the human. The prompt asks for PR URLs/test reports, but the code does not create an assigned task record, run a dependency transition, notify a ProductMaster or validate a definition of done automatically. Those are the precise coordination steps Wingman still needs.

There are no formal Room1/Room2 memberships, product-linked ticket dependencies or cross-host organization message federation in this flow. RemoteRelayCommandPolicy.swift, lines 116–139, prevents a remote caller from addressing unowned local objects. agent-messages.md, lines 59–66 and 82–84, records that remote messaging is within its session and Cloud VM messaging is not available. This is a meaningful present boundary for the MacBook/Endeavour organization design.

Major capabilities beyond Wingman's described product

Programmable native terminal/browser environment. cmux provides a surface-addressed workbench, GPU terminal rendering, browser panes and browser control, rather than only an abstract per-agent web conversation. BrowserCommands.swift, lines 187–265, exposes navigation snapshots, element actions, screenshots and evaluation command structures. This could give TestMaster a scriptable local product view and let a human inspect terminals/browser state beside an agent. Integration would need an explicit host/surface binding, authenticated control and an evidence contract. A browser screenshot alone is not a test result. No browser automation was executed here.

Session conservation and recovery machinery. Vault registrations, imported-restore trust, provider-specific resume/fork, hibernation and ordered lifecycle replay go substantially beyond Wingman's high-level continuity requirement. Their value is operational: reduce idle process cost without losing session provenance, and avoid replaying stale state over live state. Adoption needs provider-version checks, lifecycle event correctness and a stable agent-to-conversation binding. Hibernation refusal rules show why treating every idle terminal as disposable would be unsafe.

Remote daemon and managed Cloud workspaces. SSH/TUI projection and the persistent Cloud runtime abstraction can supply remote compute, reconnectable terminal state and centralized machine lifecycle. persistentWorkspace.ts, lines 24–102, provides tenant/owner separation, idempotent creation seam, versioning and resume/suspend/attach primitives. Wingman would still need project placement rules, shared directive/tracker access, cross-machine agent identity and its own coordination transport. The checked-in server has a materially different deployment/licensing boundary from local app code.

Mobile session interaction and artifact access. The mobile RPC dispatcher covers session enumeration, transcript, steering, interruption, answer and artifact gallery/fetch/thumbnail (TerminalController+MobileChat.swift, lines 42–74). This can turn a session viewer into an actionable phone surface. Wingman already wants mobile visibility, but this checkout supplies specific existing transport operations worth adapting. It does not create the Telegram Butler channel or the executive data model.

CodeRouter account routing and capacity. claudeUpstream.ts, lines 3–13 and 405–434, selects healthy team accounts. Sticky clients use rendezvous hashing. Other requests use least-recently-used selection. The router excludes cooled or already tried accounts and decrypts the selected credential. codexProxy.ts, lines 273–289, adds bounded capacity holding between routing rounds.

Account routing can improve availability. It does not route product tasks or select their models. It adds credential custody, account/quota policy, and hosted-service dependencies. The assessment did not inspect real credentials or account state.

Event-driven automations. AutomationEngine.swift, lines 4–24, 127–168 and 171–185, bridges typed app events to configured notification/RPC/process/webhook actions, replays a retained sequence window, detects gaps and rearms a closed subscription with bounded backoff. This is useful for external notification and supervision integration. It is not itself an agent scheduler or durable workflow engine; Wingman must own semantic task idempotency and reconciliation after gaps/restarts.

Licensing split. LICENSE, lines 5–22, states GPL-3.0-or-later as the default while enumerating BUSL-1.1 server directories, including web/ and relay infrastructure, with production/self-hosting terms stated there. This directly affects whether Wingman uses the installed application/control interface, modifies/distributes native components or adopts server code. The source notice is recorded here; no external legal interpretation or hosted licensing verification was performed.

Distinctive mechanisms and grounded innovation

The most useful design combination is a conversational coordinator acting through a concrete, independently addressable terminal workspace. Chief does not impersonate the worker in one transcript: dispatch yields a new workspace, surface and real process, supports an isolated worktree and optionally waits for observable working evidence. The quoting boundary in ChiefDispatchPlan.swift, lines 3–13, and readiness loop in CMUXCLI+ChiefDispatch.swift, lines 172–215, make delegation concrete. Limits are equally concrete: startup evidence is screen-pattern/provider-dependent, and subsequent acceptance remains model/human work.

The durable, semantic event reducer is stronger than deriving an entire agent state from last terminal text. The journal vocabulary separates parent/child work, attention and session boundaries. A single FIFO consumer applies projections in commit order and startup replay does not trigger live auto-resume (AgentJournalLifecycleCenter.swift, lines 4–16 and 93–117). Wingman could reuse this architectural principle to make dashboards reproducible. It still needs project/task semantics and a summary layer. An event stream cannot answer “what will this BackendCoder do next?” without additional records.

The hook-delivered mailbox with reservation and acknowledgement addresses a real coordination hazard: messages should not collide with someone's partially typed prompt. The durable store serializes appends/claims, distinguishes queued/delivered/read, and holds short-lived leases for waking hooks (AgentMessageStore.swift, lines 21–62, 114–119 and 160–217). It enables asynchronous direct collaboration while preserving the terminal as the human's interface. Its limit is dependence on supported interactive hooks and surface-bound addressing; no generic guarantee wakes every provider, headless worker or remote host. The TypeScript mail broker is a different, provider-neutral primitive (core.ts, lines 148–165). It should not be mistaken for the native deployed messaging path.

The split between human-facing conversational history, provider execution history and projected workbench state is instructive. Chief's JSONL logs can survive corrupt lines while old permission cards expire; provider session IDs resume backend context; workstreams preserve actionable records and paged telemetry. The native journal reconstructs lifecycle. This avoids making terminal output the sole durable record. It also creates integration complexity: Wingman must correlate its durable agent ID with conversation, provider session, workspace, surface, host and task IDs, and define which store owns each kind of truth.

Finally, conservative automatic recovery and resource retirement preserve user control. Auto-resume checks a live managed-session identity and rendered prompt state before sending input; hibernation refuses busy/unsafe/unconfirmed cases. These mechanisms are grounded operational innovations in this codebase, not claims of historical or industry-wide novelty. They improve reliability but cannot replace higher-level blocker diagnosis or re-planning.

Practical fit for Wingman

Use directly as an external workbench/control surface:

  • Run Codex/Claude worker sessions in named workspaces, optionally dedicated worktrees.
  • Inspect live terminal/browser output.
  • Use structured CLI/RPC addresses.
  • View local/SSH activity.
  • Deliver compatible local agent messages.
  • Receive attention and act on mobile session artifacts. This is the clearest low-coupling use of cmux. It does not require declaring the application's workspace list to be Wingman's project database.

Adapt deliberately: Chief offers a useful prototype for the Butler/coordinator experience, durable conversation ownership and permission cards. Wingman would need to feed it authoritative project/agent/task records and enforce its organization semantics outside a prompt. Translate journal/workstream events into an executive view with explicit source links, freshness, current assignment and planned next work. Put stable organizational IDs above cmux workspace/surface/provider IDs, and handle moved/closed/restored surfaces. Extend collaboration to cross-host organization mail and project rooms rather than weakening the existing remote ownership gate. Preserve normal provider permissions and disclose differences between native terminal, Chief and sidecar adapters.

Still build:

  • Telegram intake and correlation. The cross-project registry.
  • Standing role/profile and worker identity models.
  • Project-specific ProductMaster/TechMaster leadership.
  • Proportionate discovery with recorded questions/answers.
  • Scopes/specs/acceptance artifacts.
  • Assigned dependency-aware tickets and shared tracker.
  • Room1/Room2 with membership/history.
  • Periodic supervision and blocker follow-up.
  • Integrated testing/acceptance/delivery.
  • Portfolio and executive dashboards including recent/next/blockers.
  • Coherent MacBook/Endeavour coordination and placement. These are not small presentation changes to cmux's terminal grid.

A practical architecture is Wingman as the organizational authority and cmux as one execution/view adapter, with Chief patterns informing the human-facing layer. A full fork is a much larger commitment: Swift/macOS native ownership, Rust remote infrastructure, web/Cloud deployment and multiple protocol/provider integrations, plus the license boundaries noted above. The source supports component reuse and operational integration much more strongly than a claim that cmux already is Wingman.
