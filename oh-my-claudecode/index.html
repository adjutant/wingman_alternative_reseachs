oh-my-claudecode assessment against Wingman

Repository: https://github.com/Yeachan-Heo/oh-my-claudecode
Local checkout: research/oh-my-claudecode/repo
Assessed commit: 0564555b63dfedd158669c6799d53743abd7d6bf
Package identity: oh-my-claude-sisyphus, version 5.7.31, MIT license (package.json, lines 1–17, 129–138).
Assessment date: 2026-11-05.
Method: static implementation and test inspection; no dependency installation, agent launch, network integration exercise, or service startup.

Fit verdict

OMC supplies local development orchestration and workflows. Independent coding CLI workers use durable tasks, dependency-aware claims and worker mailboxes. Provider routing and lifecycle controls support execution and recovery. Discovery and delivery instructions define additional workflows. It is a strong source of execution infrastructure and workflow mechanisms for Wingman. It is not the continuing personal development organization described in WINGMAN_PURPOSE.md.

The important gap is organizational scope. A team is an execution run attached to a leader session and workspace, not a durable staff of named agents with project leadership and organizational relationships. Telegram is a notification/reply bridge to existing sessions and approval gates, not a Butler that accepts arbitrary requests and resolves their projects. The optional terminal mission board summarizes real worker tasks and blockers, but no connected web/mobile portfolio dashboard, browsable collaboration rooms, organizational agent directory, or executive-to-agent workspace navigation was found. Multi-repository shared state is implemented; multi-host worker execution and shared distributed coordination are not.

For Wingman, the best use is to study or adapt the local execution substrate, task/claim protocol, recovery ordering, and evidence-oriented delivery practices. Replacing Wingman with OMC would leave the human-facing organization, persistent identities, project registry, distributed execution control plane, and connected interfaces to build. OMC already supports Codex as a worker CLI, which makes an execution adapter plausible; its main plugin, workflow hooks, and headless factory sessions remain Claude Code-centered.

Architecture and actual execution model

OMC has several execution surfaces which should not be conflated.

  1. Claude Code plugin and workflow prompts. hooks/hooks.json, lines 4–49, 73–200, registers command hooks for user prompts, session start, tool use, subagent start/stop, and compaction. The hooks invoke scripts rather than a standing organization server. Markdown skills describe discovery, planning, execution, review, and delivery behavior. The host model follows those instructions and invokes tools. Thus a planner or analyst definition alone is a prompt/model/tool configuration, not an independently running agent.
  2. Library/SDK integration. src/index.ts, lines 299–410, createOmcSession() loads configuration and project context, constructs an orchestrator prompt, registers agent definitions and MCP tools, and returns query options and in-memory state. It does not start an SDK query itself or create a durable agent service. The SDK caller supplies execution. This surface permits Bash/Edit/Write according to configuration and sets permissionMode: 'acceptEdits'.
  3. Real CLI teams, default runtime v2. src/cli/commands/team.ts, lines 768–843, parses/decomposes a launch task and calls startTeamV2(). src/team/runtime-flags.ts, lines 3–10, makes v2 default-on. Legacy startTeam() explicitly throws before side effects, so disabling v2 does not provide a supported alternate startup (legacy runtime, lines 113–123). src/team/runtime-v2.ts, lines 3987–4185, validates dependencies/owners, resolves provider/model routing, pins executable paths, reserves a team incarnation under a lifecycle lock, and creates state. Lines 4188–4424 write tasks, optional worktrees, worker instructions, a tmux session, versioned config, and a manifest. The parent Claude Code session is normally the leader; worker CLI processes run in separately addressable multiplexer panes. These are real concurrent sessions with filesystem and shell execution, not simulated turns in one chat.
  4. Headless delivery chains and intake. src/factory/listener.ts, lines 57–105, 187–278, routes whitelisted GitHub intake/check-failure events into new headless Claude sessions with chain ledgers. src/hooks/session-end/spawn-next.ts, lines 153–208, persists handoff/next-stage state and spawns another session. This is workflow continuation by successor sessions, not the same employee agent remembering a conversation forever.
  5. Deterministic graph runtime. src/graph/runtime/runner.ts, lines 528–708, binds a sealed descriptor to a contained run directory and ownership epoch, folds committed journal records, and persists journal-before-snapshot transitions. Lines 863–1029 dispatch approval/join/executable nodes with a concurrency limit. This is a separate, more mechanical workflow engine, not proof that all Markdown skills execute as deterministic graphs. The default graph agent executor is deliberately read-only and sets persistSession: false (agent executor, lines 105–167).

The main durable coordination substrate is inspectable .omc/ files: team config/manifest, canonical task JSON, per-worker status/heartbeat/inbox, per-recipient mailbox JSON, append-only event logs, mode state, plans, memory, goal ledgers, and graph journals. It is not a centralized organization database or network task broker. File locks, atomic writes, revisions, claim tokens, instance IDs, worker generations and process identities prevent specific local races. They do not, by themselves, supply cross-machine consistency.

A source-versus-guidance distinction matters at this revision. src/hooks/AGENTS.md still describes old swarm/ultrapilot surfaces and a soft stop-hook contract. The inspected current implementation creates continue: !result.shouldBlock, with explicit escape hatches (persistent-mode, lines 2348–2425, 2619–2631). Similarly, root guidance describes shared worker launch configuration, whereas current startup accepts provider arrays, per-worker roles and resolved routing. This assessment follows the implementation, not stale capability counts or older examples.

Agent definition and lifecycle

What is an agent here?

There are at least four distinct concepts. A role definition is prompt/configuration data. A Claude Code native subagent is a host-managed independent model execution whose lifecycle hooks OMC observes. A team worker is an independently running supported coding CLI, associated with a team incarnation, worker name, pane, working directory and tasks. A graph agent node is a bounded SDK attempt with read-only tools and no persisted SDK session. A factory stage is a fresh headless Claude session with a chain ledger and handoff to a successor. Persistent files preserve work. They do not automatically transform these units into permanent organizational employees.

Definition, configuration and creation

The agent registry explicitly enumerates exploration, analysis, planning, architecture, implementation, testing, security/review, design and other specialist definitions. getAgentDefinitions() overlays configured/explicit models, prompts and tools, and reads disallowed tools from prompt frontmatter (definitions, lines 202–280). loadAgentPrompt() validates names, uses embedded prompts in bundles, or reads agents/<name>.md and strips frontmatter; missing prompts return a visible unavailable-prompt fallback (utils, lines 81–127). The registry is code-enumerated. An override changes an existing role rather than automatically registering arbitrary new SDK agents.

CLI team creation loads requested role prompts and generates launch tasks before runtime side effects. The raw decomposition utility recognizes numbered/bulleted lists and simple conjunctions. It is not an autonomous project planner. Explicit worker scopes receive fixed worker-N ownership. For ambiguous atomic input, multiple workers can receive the same full launch request. The user or orchestrator must provide meaningful independent scopes (team CLI, lines 218–260, 563–615, 749–802).

startTeamV2() validates task dependencies and owner names, assigns a team instance ID, captures immutable resolved routing, preflights the selected local executables and reserves the team name under a lifecycle lock before creating state. It writes task records, creates optional worktrees, renders worker overlays/inboxes, creates the multiplexer session and commits config/manifest. Startup rollback is explicit because side effects can fail after only some resources exist (runtime-v2, lines 3987–4185, 4188–4424). These mechanisms make the run concrete and recoverable; creation is not merely a role name mentioned in a prompt.

Identity and execution

Workers have run-local names such as worker-1. Team manifests contain instance identity, leader session, leader role, roster, provider/role, assigned tasks, pane/worktree information and a permission snapshot. The same readable team name can later denote a new incarnation; instance fencing exists to prevent stale controls from affecting the replacement. The leader is generally the parent session, rather than a separately instantiated ProjectMaster. Native subagents and team workers can coexist, but they are different lifecycles and telemetry paths.

Bootstrap instructions require the worker to read its inbox, claim before work, send a startup acknowledgement, execute, report, and transition the task using its claim token. Worker status and heartbeat files convey current task, state, reason, turn progress and timestamps. Codex/Claude use interactive TUIs; some other adapters support prompt modes. Cursor has a special keep-alive contract and trusted reviewer-output handling (worker-bootstrap, lines 106–178, 188–259; model-contract, lines 205–276). An idle Cursor worker remaining alive and another provider exiting after its task are not interchangeable persistence guarantees.

Tools and permissions

Native definitions can restrict tools. The library helper exposes configured tool access through the Agent SDK. Team worker adapters instead launch full external coding clients. At this revision Claude launch arguments include --dangerously-skip-permissions, Codex includes --dangerously-bypass-approvals-and-sandbox, and Gemini includes --approval-mode yolo (model-contract, lines 205–276). The separate worker permission module explicitly calls its path/command restrictions advisory, rendered as prompt instructions (permissions, lines 3–9, 153–195). A manifest permission snapshot is not proof of an enforced per-worker sandbox.

Different surfaces have different authority. Factory links construct a narrower Claude tool allowlist and explicit setting-source isolation; declared verify commands extend that allowlist (spawn-next, lines 48–116). Graph agent nodes pass a read-only tool list and a canUseTool denial callback, disable session persistence, and timeout/interrupt SDK queries (agent executor, lines 105–167, 197 onward). Wingman should preserve these distinctions if adapting OMC rather than treating every role as equally restricted.

Routing and concurrency

Startup captures routing once and reuses that snapshot for subsequent worker lifecycle operations. Per-task roles and team role overrides select providers/models; explicit owners take precedence, and dependency-free unowned tasks use a role-aware allocator. The CLI accepts provider arrays and per-worker roles. This is materially broader than a single shared model team (runtime-v2, lines 4015–4023, 4051–4123).

Concurrency is local, with a hard maximum of 20 team workers. Optional worktrees isolate files/branches; shared workspace mode is also possible. Claims, not conversational promises, decide task ownership. Under lock, the runtime checks expected version, dependency readiness, nonterminal state, owner conflict and recovery reservation. It generates a claim token and 15-minute lease, advances status to in_progress, and increments version (tasks, lines 170–227). This prevents duplicate successful claims within the supported local filesystem protocol, but does not automatically prevent two agents editing overlapping files when assignments/workspace policy permit it.

Dynamic scale-up/down is explicit and disabled by default. It uses monotonic worker indices, locking, and draining rather than silently recycling worker identities (scaling, lines 1–10, 88–104). It is not an autonomous organization staffing policy.

Persistence, resume and scheduling

Team config, task files, inboxes, mailbox messages, events and worker reports outlive a single model turn. Project memory and plans preserve repo knowledge; ultragoal stores durable multi-goal plans and ledger events with explicit plan IDs for parallel workspaces (artifacts, lines 11–33, 35–101). These are useful continuity layers, but no single organization store unifies stable people, product histories and all conversations.

resumeTeamV2() reads persisted config and verifies a matching multiplexer server/owned leader pane before returning a live team handle. It does not promise to resurrect every dead worker or restore that worker's full language-model context (runtime-v2, lines 6680–6723). Task checkpoint recovery is a separate operation. Factory continuation likewise starts a new session with a pointer/handoff rather than resuming the identical employee conversation.

A monitor snapshot itself is one pass: its caller drives repeated checks. It gathers task records, status, heartbeats, pane capture and provider liveness. It detects missing work-start evidence, stale reporting, missing dependencies and repeated turns without meaningful progress. It emits recommendations/events and persists a monitor snapshot (runtime-v2, lines 5720–5954). runtime-cli.ts provides repeated owner maintenance/recovery loops and an ordinary five-second-default monitoring loop (runtime CLI, lines 497–636, 1029, 1188–1214). Periodic intake is separately registered with host cron or Windows Task Scheduler. It performs a headless Harbor sweep, rather than waking a standing manager for all projects (intake, lines 167–267).

Interruption and cancellation

Persistent mode enforcement checks context exhaustion, explicit cancel, session cancellation, user abort, rate limits, authentication failures, scheduled wakeups and intentional async waiting before normal continuation logic. Current createHookOutput() hard-blocks an attempted stop when shouldBlock is true. Those bypasses prevent continuation from wedging compaction, cancellation or auth/rate-limit recovery (persistent-mode, lines 2348–2459, 2619–2631). This is session workflow enforcement, not a system-wide employee wake mechanism. Merely clearing mode state should not be confused with safely terminating every CLI process.

Team shutdown is a separate ownership-bound protocol. It evaluates task state and governance, reserves a shutdown attempt, writes worker requests, considers accept/reject acknowledgements, terminates only owned resources, verifies process/pane liveness and preserves state when cleanup cannot be proven. Force can bypass some task/worker gates but does not justify killing an unrelated incarnation or discarding uncertain worktree state (runtime-v2, lines 6095–6196, 6355–6602).

Failure, retry and recovery

Task failures are durable terminal records with errors. Monitor recommendations identify reassignment needs, but monitorTeamV2() does not itself prove an autonomous root-cause conversation occurred. Recovery follows an ordered sequence: inspect liveness and reject unknown liveness. Validate checkpoints for owned in-progress tasks. Reserve/requeue continuations and spawn a gated replacement. Persist replacement identity and require a synchronized manifest. Activate the replacement, adopt continuations with proof and repair services. Only then authorize provider execution (recovery-saga, lines 53–132). If a precommit config write fails, the uncommitted pane attempt is killed. Once committed, an incomplete adoption/manifest repair becomes a pending/uncertain outcome rather than blindly killing or replaying the replacement.

The practical boundary is important: task continuation requires an authenticated safe checkpoint. It cannot infer an exact restart point from arbitrary shell effects. Replacement generation and adoption tokens protect lifecycle ownership, not semantic idempotency of every command the coding agent previously ran. Factory next-stage spawning has explicit failure comments/labels and describes no automatic retry for that failure path (spawn-next, lines 149–151, 175–208). Recovery behavior depends on the surface involved.

Completion, acceptance and retirement

A successful team task transition checks legal state changes, current owner, claim token and unexpired lease, optionally requires delegation evidence, atomically publishes result/status/version, and appends completion/failure events. Event/snapshot failures are treated separately from the committed task record (tasks, lines 287–369). This establishes ownership and lifecycle completion. It does not universally validate that the feature works. A result string saying “Verification” is evidence reporting, not automatic product acceptance.

Launch adds stronger workflow requirements: independent standards/spec review axes, repair loops, integrated smoke checks, whole-change verification, explicit human acceptance and a report/paper trail. A C4 human decision in a parallel Team is a terminal failed task outcome, requiring later explicit re-entry after supported lifecycle cleanup. The skill expressly avoids promising automatic redispatch (launch, lines 118–185). These are valuable instructions, but not a universal property of every arbitrary omc team request.

Terminal CLI output deliberately preserves the team for inspection and instructs the user to request explicit shutdown (runtime CLI, lines 732–745). Retirement is run cleanup: workers acknowledge/exit, owned processes and panes are proven gone, optional worktrees are removed or preserved, and team state is disposed when safe. Dirty/preserved worktrees keep state for follow-up (runtime-v2, lines 6633–6672). There is no organizational archive entry for a permanent agent retiring while its long-term human-browseable timeline remains attached to its identity.

Coordination mechanics and a request trace

The strongest implemented coordination unit is the team, with durable tasks, direct per-recipient mailboxes, event records, worker heartbeat/status, inbox instructions, and a leader. teamSendMessage() locks the recipient mailbox, generates a message ID, atomically writes the message and appends a message_received event; broadcast sends to the configured roster except the sender (team-ops, lines 955–1061). Separate delivered/notified timestamps avoid conflating persistence with notification. This is not a shared room transcript or discussion thread with a room identity. Human approvals also have explicit records/events (lines 1068–1090), while graph approvals belong to the graph journal protocol.

Consider a concrete two-scope launch: implement a bounded API change and verify its integration. The following is an implementation trace, not a task actually run during this assessment.

  1. The user/leader supplies explicit worker scopes to omc team. splitTaskString() recognizes the list; buildTeamLaunchTasks() creates owned tasks and checks scope-count alignment. The CLI loads role prompts and calls startTeamV2() (team CLI, lines 218–260, 563–615, 749–802). A real dependency between implementation and integration verification should be represented in the task dependency fields, not inferred from the word “and.” The lower-level runtime/task APIs support those fields. The simple CLI launch helper does not automatically invent a meaningful technical DAG.
  2. Runtime validates dependency IDs/owners, resolves providers/models, allocates ready work, validates local binaries, reserves the team instance, writes canonical tasks, creates worktrees/instructions and starts worker panes (runtime-v2, lines 3987–4424).
  3. Each worker reads its assigned inbox and calls claim-task. A verification task with incomplete dependencies receives blocked_dependency. A competing/version-stale claim fails. A successful claim returns a token and advances the task version (tasks, lines 136–227).
  4. Worker startup acknowledgement/progress goes through send-message to leader-fixed; direct messages can also coordinate worker integration. The task remains authoritative for ownership/status. A chat acknowledgement alone does not complete it (worker-bootstrap, lines 205–259; team-ops, lines 955–1039).
  5. Implementation/testing happen in the worker's coding CLI. The worker reports concrete results and calls transition-task-status with the claim token. Transition validation and atomic publication preserve task authority; completion events and monitor/mission summaries follow (tasks, lines 287–369; mission-board, lines 495–549).
  6. Leader/runtime monitoring observes liveness, stale reporting and dependencies, supplies recommendations, and sees all-terminal status. If a worker died, checkpoint recovery is separately requested rather than treating a surviving shell pane as proof that its provider is alive (runtime-v2, lines 5778–5895; runtime CLI, lines 107–125).
  7. Under Launch, independent review and whole-change verification precede C5 human acceptance. Under a raw team launch, the leader must deliberately add that policy. Supported shutdown then handles worker consent, owned process termination and worktree cleanup. The terminal task count alone is not accepted product delivery.

Telegram adds a useful return path to this trace. Successful notifications register platform message ID, session, pane, project path and optional approval reference (notifications/index.ts, lines 251–282). The listener accepts only replies in the configured chat to those known messages; graph approval replies write a decision, ordinary text is sanitized and injected into the mapped live pane. Update offsets are persisted before injection, giving at-most-once processing rather than guaranteed delivery across a crash (reply-listener, lines 781–873). This correlates a human answer with existing work well, but does not accept a new freeform Telegram request and choose a project/team.

Major capabilities beyond Wingman's stated product

Heterogeneous coding providers and immutable routing

OMC can run Claude, Codex, Gemini, Cursor, Grok and Antigravity CLI adapters, and maps roles/tasks to configured provider/model/effort choices (model-contract, lines 10–21, 205 onward). Routing is captured once per team, avoiding accidental mid-run changes from config edits. Wingman describes Codex agents. This broader adapter layer offers model specialization and fallback design ideas. Adoption adds provider-specific permission, startup, output and shutdown semantics, so a common role name cannot be assumed to imply common authority or conversation persistence.

Deterministic graph runs with durable approvals and replay

The graph runtime offers sealed descriptors, executable/approval/join scheduling, bounded concurrency, committed-transition replay and ownership epochs. Descriptor equality and journal provenance are checked before replay; snapshot state is a cache, not the authority (runner, lines 528–708, 863–1029). This could underpin auditable Wingman workflows and human approval checkpoints more mechanically than freeform conversations. The default graph agent executor is read-only and ephemeral, so it is not an immediately usable replacement for an autonomous coding worker. Custom side-effect execution needs an explicit effect/idempotency policy rather than assuming journaling makes external effects exactly-once.

Worktree integration and automatic merge/rebase orchestration

Optional auto-merge forces named worker branches and rejects a main/master leader branch. A dedicated merger worktree serializes integration, watches worker commit heads, rebases peers, persists observed SHAs and records conflicts in actionable leader/worker inboxes (runtime-v2, lines 4025–4040; merge-orchestrator, lines 5–55, 83–114). This is substantial engineering support beyond Wingman's broad coordination description. Wingman would need to decide how automatic integration interacts with ticket review, acceptance and multi-host repository synchronization. A clean Git merge is not a verified product increment.

Tracker-driven factory chains and scheduled intake

GitHub intake/check-failure routing can start headless work from an external event, write chain ledgers and hand off to later sessions. HMAC validation, repository allowlists, serialized intake and narrower headless tool profiles make this more concrete than an always-on prompt (listener, lines 43–96, 187–278, 289 onward; spawn-next, lines 48–116, 153–208). Scheduled Harbor sweeps use the host scheduler. This offers Wingman a possible issue/CI intake lane, but it would need project/host mapping and organizational decision routing. The current listener uses its configured cwd for local execution; whitelisting several repositories is not equivalent to placing each product on its proper host/workspace.

Evaluator-driven improvement and durable multi-goal work

Autoresearch defines a single-mission bounded improvement loop with structured evaluator JSON, per-iteration artifacts, decision logs and an explicit runtime ceiling (autoresearch skill, lines 24–82). It expressly excludes multi-mission v1 orchestration and the deprecated autoresearch CLI. Ultragoal separately persists multi-goal plans, attempts, evidence, review-blocked states and quality-gate contracts (artifacts, lines 35–169). These could help Wingman run bounded optimization or longer backlogs, but are work-program artifacts, not product/agent registries. Evaluator correctness and human-approved objective boundaries remain necessary.

Compaction-resilient knowledge and delivery discipline

Beyond basic persistent directives, OMC has project-memory lifecycle hooks, notepads, glossary/ADR/standards practices, source-linked review, separate review axes and cross-session handoff contracts. Launch keeps canonical tracker artifacts primary, creates fresh contexts per ticket and asks for evidence-backed final acceptance (launch, lines 87–185). This can materially improve Wingman's quality and handoffs. Much of it is instruction-level policy rather than independently enforced control logic; adapting it requires deciding which requirements must be encoded in schemas/state transitions and which can remain agent guidance.

Distinctive mechanisms and grounded innovation

No historical or industry-wide novelty claim is made here. The following mechanisms are distinctive and useful in this checkout.

Team-incarnation fencing through the full lifecycle. Readable team names are separated from instance identity; startup reserves before side effects, writes pending/committed records, and rollback retains evidence when cleanup is incomplete. Monitoring revalidates the same instance immediately before mutation, and shutdown verifies owned providers/panes before disposal (runtime-v2, lines 4008–4018, 4145–4176, 5905–5935, 6095–6196). This enables safe repeat operations and guards against a stale caller monitoring/stopping a replacement team with the same name. It is local lifecycle authority, not a distributed consensus protocol or stable organizational identity.

Checkpoint adoption before replacement execution. Recovery separates spawning a pane from letting its provider run. Task reservations, proof of adoption, manifest synchronization and service repair precede execution, while committed but incomplete outcomes remain recoverable (recovery-saga, lines 53–132). This addresses a difficult practical failure mode: a replacement agent must not start while it still lacks authoritative continuation ownership. It depends on safe checkpoints and correct effect boundaries. It cannot reconstruct unknown side effects or guarantee a semantically identical model continuation.

Journal authority with contained filesystem writes. Graph runs bind immutable descriptors, epoch-fenced ownership, journal fingerprints/provenance and projection snapshots. Transitions append before snapshots, and replay folds committed history rather than trusting a cached final state (runner, lines 528–708; journal, lines 44–94 onward). This makes orchestration state auditable and crash-conscious. Containment guards are for run-state files, not a general sandbox for every command executed by arbitrary team workers.

Explicit approval correlation distinct from terminal steering. Notifications carry either a pane target or a graph approval reference. The same messaging integration routes an answer into the right kind of authority: decision file for an approval, terminal input for ordinary steering (notifications/index.ts, lines 251–282; reply-listener, lines 803–873). This is a good reusable pattern for Butler: answers should refer to a durable pending decision, not depend solely on whichever agent happens to be active. The present bridge is reply-only and at-most-once, so it still needs intake, delivery reconciliation and project routing.

Meaningful progress synthesis from task state. Mission board combines owned/current tasks, worker reports, recent completions, mailbox handoffs and events to produce concise mission/worker summaries (mission-board, lines 480–549, 678–721). This is more useful than presenting every tool event as executive progress. Its short retention/display limits, missing next-work field and lack of links prevent it from satisfying Wingman's connected personal agent briefing, but the underlying projection is a good starting design.

Discovery and delivery policies that preserve decision provenance. Deep interview targets unresolved dimensions and records readiness state; Launch keeps spec acceptance criteria, ticket blocking edges, independent review, C4 questions and human acceptance explicit. These practices can reduce ungrounded implementation and forgotten decisions (deep-interview, lines 38–54; launch, lines 87–185). Ambiguity scores are model-produced judgments, not empirically validated measurements, and a Markdown policy is not evidence that every run obeys it.

Practical adoption and remaining work

Usable directly in a local execution experiment:

  • independently running Codex/other CLI workers.
  • canonical team task APIs.
  • dependency and lease/token claim semantics.
  • durable mailboxes.
  • inspectable state/trace/mission summaries.
  • optional worktrees.
  • existing notification reply plumbing.

This would provide a capable execution lane for a Wingman project under a separately managed organizational layer. Runtime compatibility and permissions must be tested before relying on it. This assessment did not run it.

Adapt with a clear boundary:

  • Map stable Wingman agent IDs to run-local worker identities.
  • Attach organization/project/task references to every team and message.
  • Adapt specialist prompts for ProductMaster/TechMaster/BackendCoder/FrontendCoder/MobileCoder/TestMaster.
  • Map scope/spec/harness records into the existing memory and planning machinery.
  • Route human decisions through a durable decision record and Butler rather than raw terminal input. Retain checkpoint/instance fencing when replacing the process/multiplexer transport. If OMC is embedded wholesale, account for Claude plugin/session dependencies even when workers themselves use Codex.

Still build for Wingman:

  • An organizational service and durable staff identities.
  • Cross-project registry and new/existing project intake.
  • Butler's Telegram conversation and request/answer routing.
  • Standing project leadership and management escalation.
  • Shared room/thread chat application.
  • Human portfolio/tracker dashboard.
  • Executive agent summaries with explicit current/recent/next/blockers.
  • Permanent per-agent linked timelines.
  • Detailed web/mobile agent workspaces and conversation controls.
  • Cross-host scheduling, workspace placement, authenticated messaging and consistency across Mac/Endeavour.
  • Accepted-delivery state and a supervision policy spanning all active products.

A useful integration direction is to make OMC team runs subordinate to Wingman tickets. Wingman owns product intent, identity, portfolio state and human decisions. A run consumes an explicit assignment and returns artifacts, evidence and lifecycle outcomes. That keeps OMC's well-developed run machinery useful without misrepresenting its sessions as the standing organization. More selective code reuse may be simpler than inheriting every plugin skill, hook and provider adapter, especially for a Codex-only organization.

Verification scope and limits

The checkout commit and package identity were read directly from Git/package metadata. Source was kept read-only; only this report was written. No installs, builds, tests, model queries, multiplexer workers, Telegram traffic, scheduler modifications, webhook listeners or external services were run. Runtime behavior is source-established, not runtime-verified in this assessment.

Inspected implementation paths:

  • src/team/state/tasks.ts.

  • src/graph/runtime/{runner,journal,executors/agent}.ts.
  • src/ultragoal/artifacts.ts.
  • the discovery/launch/verify/autoresearch skills.

Large runtime files were inspected by relevant lifecycle sections, not every line.

Relevant tests were read as evidence of intended invariants, not reported as passing:

  • Task storage integrity, especially cases at lines 200–251 and 494–659: parallel claims, dependencies, committed completion despite secondary I/O failures, corrupt records and symlink handling.
  • Recovery saga, lines 77–174: identity commit→activation→adoption→service repair→execution ordering; precommit rollback; uncertain manifest/adoption; refusal to infer death from unknown liveness. These inject fake dependencies and do not prove every live provider behaves correctly.
  • Runtime shutdown, cases at lines 251–284, 414–468, 775–829, 955 onward: worktree preservation, unknown/alive pane cleanup, manifest failures and stale-instance protection.
  • Role routing/verdicts, cases at lines 319–389, 659 onward, 853 onward: configured provider authority, approve/revise transitions, lock contention, stale artifacts and Cursor reviewer behavior. These are not proof of independent product acceptance.
  • Approval replies, lines 28–97: keyword parsing, persisted channel-attributed decisions, nondecision/stale-reference handling. Live Telegram bot polling/injection remains unverified.
  • Mission-board rendering, lines 73–89: actual mission/role/timeline text rendering, not a web dashboard.
  • Factory listener, lines 72–145, 171–234, 245–342: signature/whitelist routing, prewritten ledgers, stall scheduling, and server boundary behavior.
  • Graph crash recovery, lines 1–12, 84–107, 121–159: the suite is designed to kill/resume real CLI child processes and compare replayed state. Its setup can build missing/stale output. It was deliberately not executed under the read-only/no-install assessment constraint.

Missing-capability conclusions used searches across likely code and skill surfaces for project registry/portfolio/agent directory/rooms/Butler/dashboard and SSH/remote-host/distributed execution, together with inspection of the actual team launch, filesystem state, notifications and HUD paths. Results established substantial related primitives but no organizational directory/room UI, product registry/router or remote worker control plane. A hostname HUD label explicitly helps users distinguish manual SSH sessions. It is not a multi-host coordinator. Features supplied by the external Claude Code/Codex applications are not counted as OMC-built web/mobile workspaces. Runtime correctness, provider compatibility, permission enforcement in installed clients, recovery under real crashes, and end-to-end delivery quality remain verification limits.
