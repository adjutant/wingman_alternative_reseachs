# OpenClaw: runtime, agents, coordination and operator surfaces

Supporting chapter for [the complete assessment](ASSESSMENT.md), at commit `6d3ff6f8bd62154540fee1ad3a123bdd539d904b`, assessed 2026-11-05. Source links here are relative to this chapter. All behavior below is established by reading implementation/contracts or explicitly identified documentation; no live runtime was exercised.

## 1. What “agent” means in this implementation

The durable roster is `agents.entries: Record<string, AgentEntryConfig>` with defaults and agent-specific tool, sandbox, memory and voice settings ([types.agents.ts](../repo/src/config/types.agents.ts), lines 19–40). The entry schema covers logical ID, display name/description, workspace, cwd, agent-state directory, model/utility/decision-model preferences, thinking/verbosity defaults, permission defaults, bootstrap limits, skills and delegation settings ([agent-entry schema](../repo/src/config/zod-schema.agent-entry-base.ts), lines 86–133). Its runtime union selects embedded or ACP execution; ACP has backend/harness agent, cwd and persistent/oneshot options (lines 66–84).

These fields create a reusable identity and execution policy with durable files/state. They do not allocate one permanently resident operating-system process for every listed agent. A session is a continuing conversation/work identity. A run is an admitted turn. Child sessions can use the same configured identity concurrently subject to spawn/session/runtime limits. This allows multiple independent specialist instances, but Wingman must decide whether “BackendCoder instance 2” is a distinct configured identity, a persistent assignment session using one profile, or a bounded child. The choice affects directory display, permissions, memory scope and Workboard owner capacity.

There are three different role concepts that should remain separate:

- Agent operating role: instructions/persona plus tools/delegation, such as coordinator or researcher.
- Human/operator role: Gateway access, scope ceilings and session visibility.
- Runtime relationship: parent/requester/controller/child and whether a session is independent or supervised.

None by itself encodes a project's ProductMaster, its TechMaster and their organizational reporting relationship. A model description is not the same thing as a policy, and a parent-child run tree is not the same thing as a persistent team chart.

## 2. Definition and creation paths

Four bundled role IDs exist: coordinator, researcher, writer and reviewer. The role loader reads each `CLAW.md`, resolves the role's workspace `AGENTS.md`, uses the body as `SOUL.md` and generates `IDENTITY.md` ([agent-roles.ts](../repo/src/agents/agent-roles.ts), lines 9–14, 52–87). This is more substantial than setting one system-prompt sentence: it materializes an operating program, identity and reusable instruction files. The four-role enum constrains bundled template selection, not all possible configured agents.

The coordinator template owns the requested outcome, discovers permitted specialists, creates bounded assignments through `sessions_spawn` or follows up through `sessions_send`, demands exact artifacts/verification/stop conditions and inspects important claims. Its explicit policy is to send all results and follow-up assignments through the coordinator and prevent specialists from looping on each other ([coordinator program](../repo/docs/reference/templates/roles/coordinator/workspace/AGENTS.md), lines 5–35). Escalation and approval instructions cover missing authority/access, conflicts and budget limits (lines 37–51). Researcher and reviewer similarly have concrete evidence/handoff programs. They are prompt-level operating policies backed by real tool/runtime mechanisms, not an automatic product-management state machine.

Team construction validates the preset and roles before creation, rejects colliding IDs and unfinished deletion cleanup, then calls the normal creation owner for each member. Each gets a separate child workspace. The coordinator receives a specialist `allowAgents` list and `delegationMode: "prefer"`; specialists receive `allowAgents: []` ([agent-team.ts](../repo/src/agents/agent-team.ts), lines 32–60, 88–110, 128–149). If no ambient owner exists, it makes the coordinator that owner (lines 155–178). If member three fails after two creations, it preserves and names the created agents (lines 120–124, 180–184). This is deliberate partial-success recovery, not a team transaction that can be assumed to roll back completely.

Custom agents are also a first-class conversational setup path. The system agent's instructions distinguish agent ID, display name and operating purpose, preserve custom purpose in `AGENTS.md`, and describe appearance in Agents home after creation ([assistant-prompts.ts](../repo/src/system-agent/assistant-prompts.ts), lines 150–167). The system agent is a configuration assistant using a protected tool/proposal protocol. It should not be confused with ProjectMaster. Its “create team” capability configures agents but does not create product registry/specification/acceptance records.

At the lifecycle owner, directory resolution precedes configuration apply; role delegation/bindings are persisted, approved workspace instructions are populated and transcript/state infrastructure is prepared before committed metadata is returned ([agent-create.ts](../repo/src/agents/agent-create.ts), lines 487–642). Workspace handling recognizes `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, tools/bootstrap and memory files ([workspace.ts](../repo/src/agents/workspace.ts), lines 66–74, 638–679, 737–764). Their contents may be reusable programs, persona or knowledge. They are not typed product documents simply because they live under the same agent.

Gateway `agents.create` validates creation/onboarding and retained owner/upload authority, invokes the creation owner, revives databases and confirms runtime application. It returns the created identity and onboarding result and can initiate a first conversation as detached retained work ([agents.ts](../repo/src/gateway/server-methods/agents.ts), lines 230–394). A created agent with failed onboarding is still a created agent. For provisioning Wingman, the organization layer should reconcile such partial states and record readiness independently from membership.

## 3. Sessions, child creation and actual concurrency

The spawn schema separates task instructions, task alias, visible label, target agent ID/model, timeout and cwd. It supports hidden one-shot `run`, persistent/thread-bound `session` where supported, visible sessions, cleanup keep/delete, context/bootstrap variants, collector fan-out, structured output and ACP resume/stream-to-parent ([sessions-spawn-tool.schema.ts](../repo/src/agents/tools/sessions-spawn-tool.schema.ts), lines 30–65, 77–134, 163–173). A persistent child conversation can therefore outlive the first answer without becoming a new durable roster profile.

Spawn planning checks caller depth, maximum depth, active-child or collector live/total-group limits, and allowed target identity. It derives child role/control scope and depth ([spawn-plan.ts](../repo/src/agents/spawn-plan.ts), lines 296–349). The implementation calls Gateway `agent`, captures the accepted run ID and carries parent/controller/session identity, inherited tool restrictions and sandbox facts ([subagent-spawn.ts](../repo/src/agents/subagents/spawn/subagent-spawn.ts), lines 394–430). It records child session, requester/controller, task/task alias, model, timeout, workspace, delivery/cleanup and collector metadata (lines 535–590). These are real independent executions with explicit admission and retained outcomes.

The independent-session tool intentionally differs. `sessions.create` uses visible-session containment/attribution but does not register a supervised-child run, emit child-completion events or establish yield expectations. It returns a visible session identity even when its initial run failed ([sessions-create-tool.ts](../repo/src/agents/tools/sessions-create-tool.ts), lines 7–19, 46–60). This is a useful fit for separate continuing specialist work, but it leaves supervision and completion aggregation to the caller/organization design.

Execution prepares session state and required placement, selects lane and abort ownership, waits for session maintenance/projection and enters global admission ([run-orchestrator.ts](../repo/src/agents/embedded-agent-runner/run-orchestrator.ts), lines 104–230). The lane controller's `withSessionTurn` retains queued-run/abort state and waits for raw producer and cleanup settlement before completing the operation ([lane-controller.ts](../repo/src/agents/embedded-agent-runner/run/lane-controller.ts), lines 621–678). It explicitly notes the removal of the old per-session command-queue mechanism. Describing this revision simply as “one command queue per agent” would obscure both session-level independence and current authority ownership.

Workboard adds another concurrency policy: one active card slot per assigned owner across boards ([dispatcher.ts](../repo/extensions/workboard/src/dispatcher.ts), lines 130–205). Raw subagent concurrency and task-dispatch concurrency should not be conflated. If Wingman wants two BackendCoders executing Workboard cards at once, it should establish two appropriate owner identities/instances, rather than assume one configured owner will receive an unlimited number of simultaneous cards.

## 4. Tools, permissions and live authority

Tool policy supports allow/alsoAllow/deny and minimal/coding/messaging/full profiles, plus sandbox mode/workspace access and per-agent settings ([agent-runtime schema](../repo/src/config/zod-schema.agent-runtime.ts), lines 58–71, 211–229, 465–472, 583–598). Effective execution is narrower than simply exposing a tool in a model request. Permission-mode translation maps read-only to deny, guarded to ask, workspace to automatic execution under containment and full to full execution. Retained/current ceilings are intersected, filesystem/apply-patch stay contained unless full, and an override can tighten but not loosen the session mode ([session-permission-exec-mode.ts](../repo/src/agents/session-permission-exec-mode.ts), lines 13–87).

The lane controller ties attempt liveness to the exact owner, abort state, lifecycle generation and delegated admission. Retained callbacks cannot keep mutating a replacement attempt after closure ([lane-controller.ts](../repo/src/agents/embedded-agent-runner/run/lane-controller.ts), lines 180–194, 239–270). Similar ownership checks appear at remote launch, card claim and human-question resolution. This is a meaningful implementation strength for a long-running autonomous organization: permission is not merely a Boolean copied once into a prompt.

For Wingman, technical authority and product authority still need separate records. “Allowed to run a command,” “allowed to ask this human,” “the human approved this business direction,” and “the product meets acceptance” are different decisions. OpenClaw supplies useful command approval and question mechanisms. The organization must preserve product decision provenance and connect the correct response back to the correct project's leadership.

## 5. Persistence, project knowledge and resumption

The session manager is bound to explicit SQLite transcript identity. It supports asynchronous full-fidelity context reading and durable asynchronous append distinct from an in-memory manager ([session-manager.ts](../repo/src/agents/sessions/session-manager.ts), lines 1–5, 708–715, 741–750). The write contract includes branches, suffix replacement/rewrite, compaction and message append ([session-manager-write-contract.ts](../repo/src/config/sessions/session-manager-write-contract.ts), lines 73–159). Continuity thus has actual stored conversation/event structure, not only reloaded persona files.

Subagent records live in SQLite and can be selected by run, controller, requester or child, retaining tasks/results/delivery/error/structured output ([subagent-registry.store.sqlite.ts](../repo/src/agents/subagents/registry/subagent-registry.store.sqlite.ts), lines 23–43, 71–120). The decisive limit is explicit in the restorer: **“Hydration preserves task history. A restarted process never reconstructs child execution.”** It restores persisted metadata/history and reports errors ([subagent-registry-restore.ts](../repo/src/agents/subagents/registry/subagent-registry-restore.ts), lines 9–50). Metadata restore validates child authority/retention while large payloads remain database owned ([restore-metadata.ts](../repo/src/agents/subagents/registry/subagent-registry-restore-metadata.ts), lines 18–41). A retained unfinished record is not proof that the worker is still running or has automatically resumed.

The project catalog is concrete but narrower than a product registry. Workspace projects are synthesized from agent IDs/workspaces; registered or cloned repositories are loaded from shared state ([project-registry.ts](../repo/src/projects/project-registry.ts), lines 24–32, 58–102). Persistent registration deduplicates root and, for clones, origin; slug-based IDs disambiguate names ([project-registry.kernel.ts](../repo/src/projects/project-registry.kernel.ts), lines 40–83). Record fields are ID, repository root/origin/source/display name and optional agent ID ([project-registry.types.ts](../repo/src/projects/project-registry.types.ts), lines 1–18). There is no product stage, ProductMaster, scope approval or delivery definition in that record.

Project context has additional useful machinery. Repository origin normalization converges SSH/HTTPS identity while removing userinfo; no-origin repositories use local path identity. The code explicitly accepts a rare same-host/path collision between SSH accounts for relevance within one operator's store, and preserves remote path case to avoid cross-repository injection ([project-memory-scope.ts](../repo/src/agents/project-memory-scope.ts), lines 22–55). Curated `MEMORY.md`/`USER.md` context is filtered by project annotations. Automatic bootstrap admits eligible project facts only, orders them deterministically and caps entry/total size (600/2,000 characters) ([project-memory-bootstrap.ts](../repo/src/agents/project-memory-bootstrap.ts), lines 25–60, 76–135). This helps relevance and bounded context. It is not a replacement for authoritative shared specs or a cross-user access-control boundary.

Bootstrap continuation can skip reinjection only when a valid full-bootstrap marker survives on the active transcript branch; reset/compaction invalidates its reuse ([bootstrap-files.ts](../repo/src/agents/bootstrap-files.ts), lines 46–84). It is therefore useful to distinguish persisted knowledge, selected prompt context and the exact conversation branch. Wingman should keep authoritative product documents outside lossy summaries/recall snippets and link them to the project registry rather than rely on automatic memory to retain every business requirement.

## 6. Scheduling, autonomous continuation and supervision

An active Goal is session work state with objective, status, usage and optional token budget. Usage accounting can change active to budget-limited; state transitions support pause/block/complete and budget-window resumption ([goals-transitions.ts](../repo/src/config/sessions/goals-transitions.ts), lines 26–149). Goal continuation checks exact session/lifecycle/goal identity, abort state, supported harness placement and terminal outcome eligibility. It does not enqueue over pending tool calls, accepted children, deterministic approval prompts, errors or queued/unsettled work ([goal-continuation.ts](../repo/src/auto-reply/reply/goal-continuation.ts), lines 74–90, 120–206). This supplies sustained pursuit within a session, not an organization-wide task scheduler or proof that an objective is correctly complete.

The current proactive model is ordinary automation. The default prompt reviews its scratch and relevant context and explicitly says not to infer or repeat old tasks. Setup normally creates one 30-minute, idle-only, scratch-skipping proactive check in the ambient owner's main session, announcing to the owner ([default-proactive-job.ts](../repo/src/cron/default-proactive-job.ts), lines 23–55). It provisions once using a durable receipt, so deletion remains deletion. It does not recreate the job on every startup or assign one to every agent (lines 71–138). The old heartbeat scheduling/`HEARTBEAT.md` model is migrated rather than the current runtime scheduling contract ([heartbeat documentation](../repo/docs/gateway/heartbeat.md)). Infrastructure keepalives and task claim heartbeats are different mechanisms.

Timer execution checks time-zone active hours, idle-only policy and empty scratch, and routes script/shared-session/detached work into the appropriate execution path. Agent automation hands occurrence, current authority, abort and delivery context to `runSessionEvent` ([timer-execution.ts](../repo/src/cron/service/timer-execution.ts), lines 130–225, 341–433). Persisted jobs have schedule, agent, session target, payload, delivery and failure alert fields ([types-shared.ts](../repo/src/cron/types-shared.ts), lines 33–54).

These mechanisms can wake a ProjectMaster and sustain work, but supervision still needs authoritative active-project selection, blocker semantics, follow-up history, escalation and a rule for stopping accepted/completed products. Merely enabling the default proactive job would not meet Wingman's portfolio supervision contract; its intentionally cautious default prompt would not infer those obligations from old chats.

## 7. Workboard: shared tracker joined to execution

The bundled Workboard is a major product, not a cosmetic card view. Its card tools accept assigned agent, notes/acceptance criteria, priority, board/tenant, parent links, workspace, schedules and budgets ([tools.ts](../repo/extensions/workboard/src/tools.ts), lines 73–108). `specify` updates rough work into specified todo work; `decompose` creates up to twenty children with inherited namespace and derived idempotency keys, links dependencies and can complete the orchestration parent ([store-workflow.ts](../repo/extensions/workboard/src/store-workflow.ts), lines 433–550). That last completion means decomposition was done. It is not product acceptance.

Dependencies have actual execution consequences. Claiming checks readiness; status promotion holds future schedules and requires every parent to be done. Cycle detection traverses parent links ([store-workflow.ts](../repo/extensions/workboard/src/store-workflow.ts), lines 81–168; [store-core.ts](../repo/extensions/workboard/src/store-core.ts), lines 790–833). Triage candidates can be marked as awaiting specification/decomposition without pretending the scheduler itself has reasoned through requirements (lines 836–860).

The dispatcher reconciles expiration/timeouts/retry exhaustion, ranks runnable cards and preserves one active slot per owner. It checks archived sessions and workspace authority, acquires the exact card claim, and may create a managed worktree ([dispatcher.ts](../repo/extensions/workboard/src/dispatcher.ts), lines 130–205, 311–428). It prepares durable launch identity before calling `subagent.run`, with claim protocol, permitted tools, lane/idempotency identity and recorded acceptance ([dispatcher.ts](../repo/extensions/workboard/src/dispatcher.ts), lines 459–539). A task therefore links to actual runtime identity and has a recovery story for accepted dispatch rather than relying on an untracked model promise.

Worker context includes card notes/history, parent outcomes and recent same-owner work, not just a title ([store.ts](../repo/extensions/workboard/src/store.ts), lines 609–629; [store-card-helpers.ts](../repo/extensions/workboard/src/store-card-helpers.ts), lines 471–518). Heartbeat/block/complete mutations are claim-scoped. Completion stores structured summary/proof/artifact/notification/attempt facts; runtime hooks reconcile end/error/subagent terminal state ([store-workflow.ts](../repo/extensions/workboard/src/store-workflow.ts), lines 230–299; [workboard index](../repo/extensions/workboard/index.ts), lines 159–210).

The essential acceptance limit is visible in the completion code. Proof is optional; completion can finish the run as done without independent verification. Missing proof/artifacts/attachments on a done card produces a warning ([store-card-helpers.ts](../repo/extensions/workboard/src/store-card-helpers.ts), lines 418–431). This deserves credit as useful evidence transport, not credit as an enforced TestMaster acceptance system. Wingman should add a verifier assignment, evidence schema/requirements and accepted-product transition separate from worker completion.

## 8. Communication, human questions and decisions

`sessions_send` is a real execution operation with requester source and authority wrappers. Placement contracts cover Gateway, paired-device and cloud-worker recipients; normal peer sends produce turns, eligible no-wait sends may enter active input, and idle recipients start work. Cross-tree/stale-incarnation targets are denied ([sessions-send-tool.ts](../repo/src/agents/tools/sessions-send-tool.ts), lines 18–40; [sessions-placement-tool-contract.ts](../repo/src/agents/tools/sessions-placement-tool-contract.ts), line 11 and surrounding contract). A2A waiting can capture a terminal answer and reinject it with attribution ([sessions-send-tool.a2a.ts](../repo/src/agents/tools/sessions-send-tool.a2a.ts), lines 73–110, 202–208).

Steering differs from a fresh turn and from delivery notification. Follow-up code distinguishes a steered run from a separately started run and warns if accepted input lacks a proactive state watch ([sessions-send-followup.ts](../repo/src/agents/tools/sessions-send-followup.ts), lines 190–194, 248–266, 341). Recipient-owned custody retains accepted steering through commit/cancel after the sender's lifetime ends ([sessions-send-tool.steering.ts](../repo/src/agents/tools/sessions-send-tool.steering.ts), lines 14–77). That is valuable asynchronous collaboration machinery, but organization membership and management escalation routing are separate.

Human questions have request/wait/resolve methods with current session/run authority, waiting-state recording and channel/UI dispatch ([question.ts](../repo/src/gateway/server-methods/question.ts), lines 135–180, 269–364, 438–495). Exec approvals have their own list/get/request path ([exec-approval.ts](../repo/src/gateway/server-methods/exec-approval.ts), lines 77–128). These are better substrates than parsing an unstructured “yes” from arbitrary transcript text. A Wingman layer still needs project/question IDs, ownership, options/research context and a durable decision record linked to scope/spec changes.

Optional ClickClack provides a real room/discussion integration. Gateway `session.discussion` delegates to a provider and can return no provider. The plugin registers a discussion provider, persists bindings and opens session-bound channels ([session-discussion.ts](../repo/src/gateway/server-methods/session-discussion.ts), lines 86–153; [service.ts](../repo/extensions/clickclack/src/discussions/service.ts), lines 60–90, 194–245). It adds a discussion reader tool and constrains discussion-session access to its attached main session ([register.ts](../repo/extensions/clickclack/src/discussions/register.ts), lines 36–42, 154–174). The Control UI frames the external application and rejects same-origin URLs ([session-discussion-panel.tsx](../repo/ui/src/pages/chat/components/session-discussion-panel.tsx), lines 57–94). Service availability and security policy matter. This is not an entirely in-process Room1/Room2 implementation.

## 9. Real multi-host execution and its boundary

This checkout implements actual off-host agent execution. A worker-turn tunnel validates current environment ownership, owner epoch, worker claim, session ID and run ID, then launches on the selected device. It explicitly refuses to launch an embedded worker turn for a remote-exec environment ([node-worker-tunnel.ts](../repo/src/gateway/worker-environments/node-worker-tunnel.ts), lines 386–423). The node adapter invokes supervisor launch/status, reconciles potentially dispatched launches using durable receipts and bounds admission rearming ([node-launch-adapter.ts](../repo/src/gateway/worker-environments/node-launch-adapter.ts), lines 467–605). It treats restart after possible dispatch differently from confirmed cancellation (lines 638 onward).

On the remote node, the supervisor admits capacity, checks prior receipts and physical ownership, journals the claim and starts a child ([node-worker-supervisor.ts](../repo/src/node-host/node-worker-supervisor.ts), lines 158–352). Child lifecycle prepares real process/container transport, requires a PID, establishes process identity and records the running owner behind a journal gate ([node-worker-child-lifecycle.ts](../repo/src/node-host/node-worker-child-lifecycle.ts), lines 121–240). The launch caller waits for the exact journal terminal receipt and finalizes its result ([worker-turn-execution.ts](../repo/src/gateway/worker-environments/worker-turn-execution.ts), lines 663–705). This is materially different from giving a model an `ssh` command or running another local subprocess.

Canonical transcript commits stay Gateway-owned, ordered per session and epoch-checked, with an idempotent ledger tied to captured storage identity ([transcript-commit.ts](../repo/src/gateway/worker-environments/transcript-commit.ts), lines 33–74). Shared conversational authority can therefore survive a change in physical execution placement. Organizational collaboration can use the same Gateway/session messaging contracts while computation occurs elsewhere.

Runtime modes have different locality. Documentation describes OpenClaw worker-turn mode as a restricted remote OpenClaw process, normally proxying inference through the Gateway. Native Codex remote-exec keeps app-server/auth/transcript at the Gateway and places the authorized exec-server remotely. This distinction is documented in [dispatching a session](../repo/docs/gateway/cloud-workers/dispatching-a-session.md). It is not a claim to have inspected the unavailable underlying Codex source. Runtime/provider capability gates apply and there is no documented silent Gateway-local fallback. Child sessions use separate managed worktrees and inherit the selected parent worker profile.

Recovery is bounded by workspace synchronization. The [session lifecycle documentation](../repo/docs/gateway/cloud-workers/session-lifecycle.md) explains reconciliation of completed turns. A machine loss can discard edits made between checkpoints. Checkpoint manifests/delta packs cover the repository; they do not contain a complete upstream repository. A replacement worker needs fetchable or cached base commits. It also distinguishes stopping a turn from stopping the cloud device. The full machine-loss/recovery implementation matrix was not traced here. Those caveats are documentation-backed. No claim is made that arbitrary unfinished non-idempotent tool calls are blindly replayed.

## 10. Visibility: directory, semantic overview and detailed workspace

The Agents home consumes actual policy-filtered configured identities, with settings panels for identity/model/files/memory/cron/channels/tools/skills ([agents.ts](../repo/src/gateway/server-methods/agents.ts), lines 118–175; [agents view](../repo/ui/src/pages/agents/view.tsx), lines 54–60, 99–127; [overview panels](../repo/ui/src/pages/agents/panels-overview.tsx), lines 94–118, 155–166). This is a real directory/settings surface. The gap is durable project/team/reporting relationships, not the absence of an agent list.

The observer goes beyond raw logs. A utility-model prompt asks whether the session is progressing, grinding, stuck, waiting on the user, wrapping up, done or failed. A strict response schema retains headline, optional assessment, health and optional completed/total plan progress ([session-observer-model.ts](../repo/src/gateway/session-observer-model.ts), lines 249–268). Preamble publication can provide fast coalesced deterministic updates ([session-observer-preamble.ts](../repo/src/gateway/session-observer-preamble.ts), lines 8–9, 47–127). These mechanisms can misjudge underlying task truth, but they are actual summary-producing behavior and should not be dismissed as an event log.

Activity rows link the session, agent chip, observer headline, run inspection and retained recap; Current Work links active and queued sessions ([session-activity-row.tsx](../repo/ui/src/pages/activity/session-activity-row.tsx), lines 94–105, 128–150, 193–251; [current-work-view.tsx](../repo/ui/src/pages/activity/current-work-view.tsx), lines 34–79). Summary-source reads are bounded committed transcript batches ([session-activity-summary-source.ts](../repo/src/gateway/session-activity-summary-source.ts), lines 25–103). This supports useful recent/current status and drill-down. It is session-centric and does not establish all of the agent's product obligations, next assignments or portfolio-level blockers.

The detailed session workspace includes terminal, browser, desktop, file/preview, context, subprocess, subagent and discussion views ([chat-pane-embedded-view.tsx](../repo/ui/src/pages/chat/chat-pane-embedded-view.tsx), lines 40–110, 184–240, 370–385). Send/abort and permission-aware subagent stopping are wired through actual runtime controls ([chat-view.tsx](../repo/ui/src/pages/chat/chat-view.tsx), lines 700–701; [chat-subagents-panel.tsx](../repo/ui/src/pages/chat/components/chat-subagents-panel.tsx), lines 281–303, 425–478). These are strong foundations for Wingman's individual workspaces, though capabilities depend on selected harness/session/node and the interface does not automatically become a career-long standing-agent workspace.

Three “boards” should not be collapsed into one feature claim. Core `board.*` is session dashboard/widget composition. Workboard card boards are durable task namespaces with dependencies/claims and their own UI. Workboard Sessions boards organize Gateway-owned observer/run/PR facts into columns and can scope to agent IDs ([workboard index](../repo/extensions/workboard/index.ts), lines 36–103, 247–252). The plugin's card tools explicitly distinguish card boards from Sessions boards ([tools.ts](../repo/extensions/workboard/src/tools.ts), line 247; [tools-orchestration.ts](../repo/extensions/workboard/src/tools-orchestration.ts), line 198). Each is useful; none alone implies the whole product-management dashboard.

## 11. Failure, retry, cancellation, completion and retirement

Provider retry is not task redispatch. The embedded run loop creates retry budgets, persistent idle/compaction guards and per-attempt authority checks; budget exhaustion chooses failover/error rather than unbounded retry. Provider rate-limit deadlines/auth recovery and permission-change continuation have distinct handling ([run-loop.ts](../repo/src/agents/embedded-agent-runner/run-loop.ts), lines 148–161, 235–284, 385–397, 444–461). Workboard separately owns task attempts/retry exhaustion/claim expiration; remote launch separately owns dispatch receipts/admission rearm. Wingman should preserve these owners rather than add one global “retry everything” loop.

Spawn has meaningful compensation. If launch/registration fails, it cleans provisional sessions, prepared context and attachments; if a child was already accepted before registration failure, it can terminate that child ([subagent-spawn.ts](../repo/src/agents/subagents/spawn/subagent-spawn.ts), lines 448–530). This avoids assuming failure to record a child means no child ran. Other external effects remain governed by their own idempotency and outcome contracts.

Cancellation mutates/stops and joins execution settlement, then cascades across a captured child tree. It refreshes descendants while avoiding unrelated newly created work; explicit root cancellation reconciles terminal state as well ([subagent-control-kill.ts](../repo/src/agents/subagents/registry/subagent-control-kill.ts), lines 44–99, 244–424). “Stop” is therefore more than closing a UI panel or signaling a guessed process. It does not imply all arbitrary external effects have been undone.

Terminal result, reply delivery, retained child history, card completion, independent verification and product acceptance are separate facts. The code supports the first four with substantial machinery. Reviewer instructions ask for evidence-based independent findings, but neither those instructions nor a Workboard `review` status ensures that a separate TestMaster executed required product scenarios. A Wingman acceptance owner must compare the agreed definition of done, integrated test evidence and unresolved defects, obtain the human's decision where required and stop active development after accepted delivery.

Agent deletion defaults to file deletion, delegates to its deletion owner and confirms configuration reload. It explicitly reports when configuration removal succeeded but physical cleanup is pending ([agents.ts](../repo/src/gateway/server-methods/agents.ts), lines 555–592). Team creation checks pending deletion cleanup before reusing identities. For a standing organization, “retired employee,” “archived assignment,” “deleted session” and “deleted agent files” should therefore remain distinct operations. The core lifecycle is a substrate, not a supplied HR/project-retirement model.

## 12. Verification evidence and confidence
