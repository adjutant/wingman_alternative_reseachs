# OpenClaw assessment against Wingman

Assessment date: **2026-11-05**. Repository: https://github.com/openclaw/openclaw

Local checkout: `research/openclaw/repo`. Inspected commit: **`6d3ff6f8bd62154540fee1ad3a123bdd539d904b`**, on `main`; package version `2026.10.10`. The checkout was clean when inspected. This report concerns that revision, including its bundled plugins, rather than historical versions of OpenClaw or the current hosted service. Evidence links are relative to this report; line numbers refer to this commit.

**Verdict: a strong candidate runtime and operating substrate for Wingman, with substantial existing coordination and operator interfaces, but not a ready-made implementation of Wingman's standing software-development organization.** This revision is much more than a Telegram-to-model wrapper. It has durable configurable agents, directed team creation, independent sessions and supervised subagent runs, real distributed workers, a shared card-based Workboard, model-generated activity summaries, structured human questions, detailed session workspaces and extensible native plugin UI. Those capabilities deserve direct credit. The missing center is the product organization: semantic intake across products, persistent ProductMaster/TechMaster responsibilities, proportionate product discovery, authoritative product specifications and acceptance, management room topology and organization-wide delivery supervision.

OpenClaw's native center of gravity is a self-hosted **multi-channel personal/team assistant Gateway**. Wingman's center is a continuing development organization whose named people, projects, decisions and delivery obligations remain explicit. Much of that organization could be built above OpenClaw without replacing its executor. It would still be real product work, not simply renaming the four bundled roles. See [the detailed lifecycle and coordination chapter](Runtime_and_Coordination.md) for the implementation trace and failure boundaries.

## Architecture and actual execution model

The installed `openclaw` executable enters the TypeScript CLI, whose entrypoint dynamically loads `runCli` and preserves structured failure reporting ([entry.ts](../repo/src/entry.ts), lines 352–398). The Gateway CLI loads and starts the server ([gateway-cli/run.ts](../repo/src/cli/gateway-cli/run.ts), lines 439 and 871 onward). The server owns database admission and a Gateway lock before initializing the runtime. It retains ownership if shutdown cannot finish safely ([server.ts](../repo/src/gateway/server.ts), lines 72–125). Its core creates a Gateway kernel, HTTP transport and attached runtime, then finishes plugin, scheduler and worker startup ([server-start.ts](../repo/src/gateway/server-start.ts), lines 19–49, 62–85, 113–129). Web, CLI, native apps and channels meet this shared control plane through typed methods and events.

There are several distinct state and execution objects:

| Object | What actually persists or executes | Wingman implication |
|---|---|---|
| Configured agent | Entry in `agents.entries`, identity, instructions, workspace, model/runtime and tool policy. | Suitable base for Butler, leadership and specialist profiles; does not imply a permanently running process. |
| Session | Conversation identity, transcript, owner/sharing, current execution and workspace/project facts. | Useful continuing work context. A session is not itself a product or a standing employee. |
| Run/turn | Admitted execution under a session lifecycle and authority, possibly local or placed on a worker. | The actual independently executing unit. |
| Supervised subagent | Child session/run plus requester/controller, task, result, delivery and cleanup records. | Real delegation and concurrency. A bounded child is not automatically a long-lived team member. |
| Independent visible session | Durable visible work context with optional initial run, without supervised-child completion registration. | Appropriate for separate continuing work, with organization membership supplied separately. |
| Project registry entry | Repository root/origin/display name and stable ID, plus synthesized agent workspaces. | Real repository catalog, but no product scope/leadership lifecycle. |
| Workboard card | Durable assigned work, dependency/status/claim/run/proof/notification metadata. | Substantial shared tracker and task execution basis. |
| Core session board/widget | Agent-created or operator-created dashboard surface within a session. | Presentation/composition capability; distinct from Workboard's task database. |

Agent configuration is keyed and extensible ([types.agents.ts](../repo/src/config/types.agents.ts), lines 19–40; [agent-entry schema](../repo/src/config/zod-schema.agent-entry-base.ts), lines 66–133). This revision uses **SQLite-backed canonical transcripts and state**, with database-engine support also declared for PostgreSQL families. It should not be described using older `sessions.json`/JSONL architecture. The transcript manager explicitly binds a SQLite transcript identity and distinguishes durable asynchronous append from in-memory operation ([session-manager.ts](../repo/src/agents/sessions/session-manager.ts), lines 1–5, 708–715, 741–750). Database families and schema versions are declared in [package.json](../repo/package.json), lines 4–21; no database backend was started to verify operational conformance.

The embedded runner prepares the session, required placement and lane/abort ownership, waits for same-session maintenance, and enters admission ([run-orchestrator.ts](../repo/src/agents/embedded-agent-runner/run-orchestrator.ts), lines 104–143, 155–230). The current lane controller uses `withSessionTurn` and joins producer/cleanup settlement; its comment explicitly says it no longer uses a per-session command queue ([lane-controller.ts](../repo/src/agents/embedded-agent-runner/run/lane-controller.ts), lines 621–678). Follow-up input queues still exist for steering and continuation. Configured agents can select embedded or ACP execution. Native inference/harness behavior beyond OpenClaw's checked-in adapter contracts remains an external dependency. The `../codex` source required by OpenClaw's own guidance was unavailable here.

## Agent definition, creation and lifecycle

The durable agent/session/run separation is central to evaluating fit. OpenClaw has real configured agent identities and independently executing child work. It is incorrect either to dismiss them as personas or to say every agent is an always-running process. An agent is a reusable stateful configuration owner. Multiple sessions and turns supply ongoing work and concurrency. A spawn request's `taskName` is a stable target alias and `label` a work title. Neither creates a new durable roster member ([spawn schema](../repo/src/agents/tools/sessions-spawn-tool.schema.ts), lines 30–65).

Creation runs through a common lifecycle owner, resolving workspace and agent-state directories, committing configuration/delegation/bindings, populating approved instructions, creating transcript/state infrastructure and returning committed metadata ([agent-create.ts](../repo/src/agents/agent-create.ts), lines 487–642). Gateway creation then revives databases, confirms runtime configuration application and may initiate detached onboarding under retained operator authority ([agents.ts](../repo/src/gateway/server-methods/agents.ts), lines 230–394). Persistent creation can succeed while onboarding reports a separate error. Team creation is sequential and deliberately retains successful members when a later member fails. It is not an all-or-nothing organizational transaction.

Permissions combine configured tool profiles, allow/deny lists, sandbox/workspace policy, session permission mode and live run authority. Read-only maps to denied execution, guarded to asking, workspace to automatic contained execution and full to full execution; per-call overrides can tighten, not loosen, session policy ([session-permission-exec-mode.ts](../repo/src/agents/session-permission-exec-mode.ts), lines 13–87). Those are technical authority boundaries. They do not decide whether a mortgage workflow is sufficiently understood or a delivered product meets human business acceptance.

Delegation creates actual independently executing child sessions, propagates controller identity and authority ceilings, calls Gateway `agent`, and records accepted run identity and completion/cleanup policy. Admission checks depth, child/group limits and target-agent permissions. Persistent visible sessions and collector fan-out are separate supported forms. `sessions.create` deliberately creates independent visible work without supervised-child run registration or completion events ([sessions-create-tool.ts](../repo/src/agents/tools/sessions-create-tool.ts), lines 7–19, 46–60). Wingman should use durable configured identities for roles, sessions for continuing assignments and bounded children for explicit subtasks, with membership records connecting them.

Continuation has several different meanings. SQLite restores conversation and task history; prompt bootstrap and project memory reconstruct useful context. An explicitly active Goal may enqueue another turn after eligible successful completion; automation may wake an idle session; remote worker recovery has its own launch/claim/receipt machinery. They are not interchangeable promises of automatic restart. The child registry explicitly says hydration preserves task history and **never reconstructs child execution** after process restart. Goal continuation also checks current session/lifecycle/goal identity, status, abort state, supported harness placement, queued work and unsettled children ([goal-continuation.ts](../repo/src/auto-reply/reply/goal-continuation.ts), lines 74–90, 120–206). Goals track active/paused/blocked/complete and budget-limited states; token accounting can stop pursuit at its limit ([goals-transitions.ts](../repo/src/config/sessions/goals-transitions.ts), lines 26–64, 67–149).

Cancellation is owned, tree-aware work. Subagent controls capture the relevant child tree, interrupt siblings/descendants and join execution settlement. They avoid treating a successor or newly unrelated child as the canceled task ([subagent-control-kill.ts](../repo/src/agents/subagents/registry/subagent-control-kill.ts), lines 44–99, 244–424). Spawn failure cleans provisional state and can terminate an accepted child if subsequent registration fails. The run loop separately budgets provider retries/failover, validates admission/abort state and distinguishes permission-change continuation from model failure ([run-loop.ts](../repo/src/agents/embedded-agent-runner/run-loop.ts), lines 148–161, 235–284, 385–397, 444–461).

Completion records a terminal run/result and, where applicable, a delivered child answer or Workboard card outcome. It does not mean an independently accepted product. Retirement removes a configured agent and normally its files; partial cleanup is explicitly reported as pending with retry guidance ([agents.ts](../repo/src/gateway/server-methods/agents.ts), lines 555–592). The [supporting chapter](Runtime_and_Coordination.md) expands these paths, workspace/tool behavior and remote execution limits.

## Coordination and one end-to-end task trace

The strongest concrete coordination path is a **Workboard task dispatched to a real subagent**, with Telegram as a possible intake/delivery channel. This is a source trace, not a live demonstration.

1. Telegram ingress determines account/chat/topic and authorized agent; route resolution derives a stable agent/session identity. Webhook success follows durable spool enqueue, so accepting a message does not depend on completing model work ([bot-message-context.ts](../repo/extensions/telegram/src/bot-message-context.ts), lines 175–219; [resolve-route.ts](../repo/src/routing/resolve-route.ts), lines 474–527, 578–607; [webhook.ts](../repo/extensions/telegram/src/webhook.ts), lines 381–389).
2. The selected coordinator reasons about the request and can call `workboard_create`. The tool forwards a structured card to the shared store. This reasoning step is model/prompt behavior, not a deterministic product-intake classifier ([tools.ts](../repo/extensions/workboard/src/tools.ts), lines 243–256).
3. `workboard_specify` can clarify a rough triage/backlog card, and `workboard_decompose` creates up to twenty linked children with inherited board/tenant and idempotency keys. Dependency state affects readiness and is checked when work is claimed ([store-workflow.ts](../repo/extensions/workboard/src/store-workflow.ts), lines 81–168, 433–550).
4. Dispatcher promotion/expiry/retry logic prepares eligible work. Ranking and one active slot per owner prevent the same assigned agent from being dispatched simultaneously across boards; launch failures are bounded during outages ([store.ts](../repo/extensions/workboard/src/store.ts), lines 424–518; [dispatcher.ts](../repo/extensions/workboard/src/dispatcher.ts), lines 130–205).
5. The dispatcher verifies workspace authority and worker-session status, then claims the exact card. It can create a managed worktree. Context includes the task, parent outcomes and recent same-agent work. The dispatcher persists a prepared launch. It calls `subagent.run` with card/claim identity, required tools, lane and idempotency key ([dispatcher.ts](../repo/extensions/workboard/src/dispatcher.ts), lines 311–428, 459–539; [store-card-helpers.ts](../repo/extensions/workboard/src/store-card-helpers.ts), lines 471–518).
6. The worker performs actual tool work and reports heartbeat, proof, completion or blocking under claim authority. Terminal completion records summary/proof/artifacts, notifications and attempt state; lifecycle end/error and `subagent_ended` hooks reconcile the runtime back into Workboard ([store-workflow.ts](../repo/extensions/workboard/src/store-workflow.ts), lines 230–299; [index.ts](../repo/extensions/workboard/index.ts), lines 159–165, 190–210).
7. Operator interfaces expose card/run/workspace and generated session status. A coordinator can synthesize results or ask a structured human question. **No mandatory final TestMaster/product acceptance gate is inserted by this path.** A completed card can lack passing proof, and a decomposed orchestration parent can be completed as decomposition rather than as delivered software.

Direct collaboration is richer than a shared filesystem. Session messages can wait for a terminal reply and reinject it with attribution, steer active work or start a new turn. Recipient-owned custody prevents accepted steering from losing authority merely because the sender has finished. Optional ClickClack adds externally hosted session-bound discussion channels and a read tool. The Control UI embeds that service and deliberately rejects same-origin framing ([session-discussion-panel.tsx](../repo/ui/src/pages/chat/components/session-discussion-panel.tsx), lines 57–94). Wingman's Room1/Room2 membership, project context, escalation routing and durable decision linking remain a distinct organizational layer.

## Grounded distinctive mechanisms and innovation assessment

1. **Durable task-to-run coordination.** Workboard combines cards/dependencies, exact claims, workspace authority, a prepared launch, actual subagent execution, lifecycle reconciliation and structured completion. The meaningful mechanism is the join between durable planning state and real runtime identity, including accepted-but-not-yet-linked failures. It enables recoverable shared execution rather than merely displaying a task list. It still cannot establish the truth of a worker's tests or whether completing an orchestration parent means product delivery.
2. **Placement authority independent of machine lifetime.** Remote launch binds environment, epoch, session, run and current turn claim before a node starts a physical child. Gateway transcript commits remain ordered and idempotent under their captured storage owner. This permits remote computation with continuing conversation authority, while rejecting stale launches and receipts. Workspace checkpoints and machine disappearance still bound recovery. There is no basis for claiming transparent replay of arbitrary side effects.
3. **Recipient-owned asynchronous steering.** Accepted steering moves into the target's custody through commit/cancellation, rather than retaining the sender as an accidental lifetime owner ([steering.ts](../repo/src/agents/tools/sessions-send-tool.steering.ts), lines 14–77). This is valuable for independent specialists whose controller may finish while a message is pending. It does not create persistent organizational rooms or decide who should receive a business escalation.
4. **Semantic execution health.** A utility-model observer emits bounded headline, assessment, categorical health and plan progress, while a faster preamble publisher coalesces deterministic updates ([session-observer-model.ts](../repo/src/gateway/session-observer-model.ts), lines 249–268, 426–439; [session-observer-preamble.ts](../repo/src/gateway/session-observer-preamble.ts), lines 8–9, 47–127). This directly addresses the difference between exposing a transcript and helping a human understand progress. Its judgment remains a model interpretation, not verified product health or autonomous blocker resolution.
5. **Explicit durable proactive intent.** One-time provisioning receipts, per-job scratch, idle admission and active hours make periodic work inspectable and preserve deliberate deletion ([default-proactive-job.ts](../repo/src/cron/default-proactive-job.ts), lines 23–55, 71–138). This is a useful model for ProjectMaster wakeups. The default prompt explicitly avoids inferring old tasks, so persistent portfolio obligations must be authored and maintained rather than assumed.
6. **Repository-scoped context with bounded recall.** Project keys normalize origin identities or fall back to local roots; bootstrap admits only eligible facts whose project annotations match active scope, orders them deterministically and caps total/entry characters ([project-memory-scope.ts](../repo/src/agents/project-memory-scope.ts), lines 22–55; [project-memory-bootstrap.ts](../repo/src/agents/project-memory-bootstrap.ts), lines 25–60, 76–135). This can reduce cross-product context contamination. It is relevance filtering within an operator's store, not a security boundary or complete source of product truth.

These are distinctive, grounded design choices in this implementation. No historical priority or industry-wide uniqueness claim is made.

## Practical fit and remaining engineering

Use directly:

- Telegram transport/routing.
- Configured agent identities and custom instruction workspaces.
- Native coding tool/harness boundaries.
- Child session lifecycle and direct messaging.
- Workboard cards/dependencies/claims/dispatch.
- Project repository registry.
- Proactive automations.
- Human questions and technical approvals.
- Actual remote execution.
- Activity summaries/run inspectors and detailed coding session interfaces. These are expensive primitives Wingman would otherwise need to build.

**Adapt:** Define Butler, ProjectMaster, per-product ProductMaster/TechMaster and specialist profiles; give persistent agent instances explicit product/team membership; connect project records, Workboard boards/cards, session/worktree identities and `DIRECTIVES` files through stable IDs. Replace the generic four-role preset with the intended organization while preserving the useful one-artifact-owner and bounded-handoff rules. Decide where direct peer collaboration is allowed: the shipped coordinator program deliberately routes specialist results/follow-ups through the coordinator and disallows specialist loops, which differs from Wingman's direct Room2 collaboration. Build project and portfolio projections above Workboard and existing session summaries instead of treating a Kanban board as the whole executive view.

Build:

- A durable natural-language intake owner that distinguishes new products from follow-ups.
- Project knowledge/discovery/question/decision records.
- Proportionate discovery and approved product scope/spec/scenario/definition-of-done workflow.
- Enduring leadership assignments.
- Room membership and escalation topology.
- ProjectMaster's portfolio review and blocker resolution policy. An executive next-assignment/blocker view.
- Independent integrated verification and human acceptance. Product acceptance must have its own authoritative state transition, evidence requirements and stop/resume behavior. Neither a terminal model reply, a `done` card, a `review` column nor an observer's “done” health is sufficient.

The lowest-risk adoption experiment would configure one bounded product with these roles, a Workboard namespace, explicit directive files, a clarification round, two independently executing specialists, a separate verifier and one human acceptance decision. Include a second product only after demonstrating that cross-product intake and context routing remain correct. Distributed workers should be evaluated with an interruption/recovery exercise and explicit checkpoint expectations. This is an implementation proposal, not a test executed for this assessment.

OpenClaw is a large integrated product, so adoption also means accepting its Gateway/state/plugin lifecycle and tracking a fast-moving upstream. For Wingman, the strongest strategy is an organization plugin/service on documented contracts, rather than invasive edits to runner internals or pretending arbitrary agent prompts amount to a managed organization.
