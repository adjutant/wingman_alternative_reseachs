OpenClaw assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/openclaw/openclaw

Local checkout: research/openclaw/repo. Inspected commit: 6d3ff6f8bd62154540fee1ad3a123bdd539d904b, on main; package version 2026.10.10. The checkout was clean when inspected. This report concerns that revision, including its bundled plugins, rather than historical versions of OpenClaw or the current hosted service. Evidence links are relative to this report; line numbers refer to this commit.

Verdict: a strong candidate runtime and operating substrate for Wingman, with substantial existing coordination and operator interfaces, but not a ready-made implementation of Wingman's standing software-development organization. This revision is much more than a Telegram-to-model wrapper. It has durable configurable agents, directed team creation, independent sessions and supervised subagent runs, real distributed workers, a shared card-based Workboard, model-generated activity summaries, structured human questions, detailed session workspaces and extensible native plugin UI. Those capabilities deserve direct credit. The missing center is the product organization: semantic intake across products, persistent ProductMaster/TechMaster responsibilities, proportionate product discovery, authoritative product specifications and acceptance, management room topology and organization-wide delivery supervision.

OpenClaw's native center of gravity is a self-hosted multi-channel personal/team assistant Gateway. Wingman's center is a continuing development organization whose named people, projects, decisions and delivery obligations remain explicit. Much of that organization could be built above OpenClaw without replacing its executor. It would still be real product work, not simply renaming the four bundled roles. See the detailed lifecycle and coordination chapter for the implementation trace and failure boundaries.

Architecture and actual execution model

The installed openclaw executable enters the TypeScript CLI, whose entrypoint dynamically loads runCli and preserves structured failure reporting (entry.ts, lines 352–398). The Gateway CLI loads and starts the server (gateway-cli/run.ts, lines 439 and 871 onward). The server owns database admission and a Gateway lock before initializing the runtime. It retains ownership if shutdown cannot finish safely (server.ts, lines 72–125). Its core creates a Gateway kernel, HTTP transport and attached runtime, then finishes plugin, scheduler and worker startup (server-start.ts, lines 19–49, 62–85, 113–129). Web, CLI, native apps and channels meet this shared control plane through typed methods and events.

There are several distinct state and execution objects:

Object What actually persists or executes Wingman implication
Configured agent Entry in agents.entries, identity, instructions, workspace, model/runtime and tool policy. Suitable base for Butler, leadership and specialist profiles; does not imply a permanently running process.
Session Conversation identity, transcript, owner/sharing, current execution and workspace/project facts. Useful continuing work context. A session is not itself a product or a standing employee.
Run/turn Admitted execution under a session lifecycle and authority, possibly local or placed on a worker. The actual independently executing unit.
Supervised subagent Child session/run plus requester/controller, task, result, delivery and cleanup records. Real delegation and concurrency. A bounded child is not automatically a long-lived team member.
Independent visible session Durable visible work context with optional initial run, without supervised-child completion registration. Appropriate for separate continuing work, with organization membership supplied separately.
Project registry entry Repository root/origin/display name and stable ID, plus synthesized agent workspaces. Real repository catalog, but no product scope/leadership lifecycle.
Workboard card Durable assigned work, dependency/status/claim/run/proof/notification metadata. Substantial shared tracker and task execution basis.
Core session board/widget Agent-created or operator-created dashboard surface within a session. Presentation/composition capability; distinct from Workboard's task database.

Agent configuration is keyed and extensible (types.agents.ts, lines 19–40; agent-entry schema, lines 66–133). This revision uses SQLite-backed canonical transcripts and state, with database-engine support also declared for PostgreSQL families. It should not be described using older sessions.json/JSONL architecture. The transcript manager explicitly binds a SQLite transcript identity and distinguishes durable asynchronous append from in-memory operation (session-manager.ts, lines 1–5, 708–715, 741–750). Database families and schema versions are declared in package.json, lines 4–21; no database backend was started to verify operational conformance.

The embedded runner prepares the session, required placement and lane/abort ownership, waits for same-session maintenance, and enters admission (run-orchestrator.ts, lines 104–143, 155–230). The current lane controller uses withSessionTurn and joins producer/cleanup settlement; its comment explicitly says it no longer uses a per-session command queue (lane-controller.ts, lines 621–678). Follow-up input queues still exist for steering and continuation. Configured agents can select embedded or ACP execution. Native inference/harness behavior beyond OpenClaw's checked-in adapter contracts remains an external dependency. The ../codex source required by OpenClaw's own guidance was unavailable here.

Agent definition, creation and lifecycle

The durable agent/session/run separation is central to evaluating fit. OpenClaw has real configured agent identities and independently executing child work. It is incorrect either to dismiss them as personas or to say every agent is an always-running process. An agent is a reusable stateful configuration owner. Multiple sessions and turns supply ongoing work and concurrency. A spawn request's taskName is a stable target alias and label a work title. Neither creates a new durable roster member (spawn schema, lines 30–65).

Creation runs through a common lifecycle owner, resolving workspace and agent-state directories, committing configuration/delegation/bindings, populating approved instructions, creating transcript/state infrastructure and returning committed metadata (agent-create.ts, lines 487–642). Gateway creation then revives databases, confirms runtime configuration application and may initiate detached onboarding under retained operator authority (agents.ts, lines 230–394). Persistent creation can succeed while onboarding reports a separate error. Team creation is sequential and deliberately retains successful members when a later member fails. It is not an all-or-nothing organizational transaction.

Permissions combine configured tool profiles, allow/deny lists, sandbox/workspace policy, session permission mode and live run authority. Read-only maps to denied execution, guarded to asking, workspace to automatic contained execution and full to full execution; per-call overrides can tighten, not loosen, session policy (session-permission-exec-mode.ts, lines 13–87). Those are technical authority boundaries. They do not decide whether a mortgage workflow is sufficiently understood or a delivered product meets human business acceptance.

Delegation creates actual independently executing child sessions, propagates controller identity and authority ceilings, calls Gateway agent, and records accepted run identity and completion/cleanup policy. Admission checks depth, child/group limits and target-agent permissions. Persistent visible sessions and collector fan-out are separate supported forms. sessions.create deliberately creates independent visible work without supervised-child run registration or completion events (sessions-create-tool.ts, lines 7–19, 46–60). Wingman should use durable configured identities for roles, sessions for continuing assignments and bounded children for explicit subtasks, with membership records connecting them.

Continuation has several different meanings. SQLite restores conversation and task history; prompt bootstrap and project memory reconstruct useful context. An explicitly active Goal may enqueue another turn after eligible successful completion; automation may wake an idle session; remote worker recovery has its own launch/claim/receipt machinery. They are not interchangeable promises of automatic restart. The child registry explicitly says hydration preserves task history and never reconstructs child execution after process restart. Goal continuation also checks current session/lifecycle/goal identity, status, abort state, supported harness placement, queued work and unsettled children (goal-continuation.ts, lines 74–90, 120–206). Goals track active/paused/blocked/complete and budget-limited states; token accounting can stop pursuit at its limit (goals-transitions.ts, lines 26–64, 67–149).

Cancellation is owned, tree-aware work. Subagent controls capture the relevant child tree, interrupt siblings/descendants and join execution settlement. They avoid treating a successor or newly unrelated child as the canceled task (subagent-control-kill.ts, lines 44–99, 244–424). Spawn failure cleans provisional state and can terminate an accepted child if subsequent registration fails. The run loop separately budgets provider retries/failover, validates admission/abort state and distinguishes permission-change continuation from model failure (run-loop.ts, lines 148–161, 235–284, 385–397, 444–461).

Completion records a terminal run/result and, where applicable, a delivered child answer or Workboard card outcome. It does not mean an independently accepted product. Retirement removes a configured agent and normally its files; partial cleanup is explicitly reported as pending with retry guidance (agents.ts, lines 555–592). The supporting chapter expands these paths, workspace/tool behavior and remote execution limits.

Coordination and one end-to-end task trace

The strongest concrete coordination path is a Workboard task dispatched to a real subagent, with Telegram as a possible intake/delivery channel. This is a source trace, not a live demonstration.

  1. Telegram ingress determines account/chat/topic and authorized agent; route resolution derives a stable agent/session identity. Webhook success follows durable spool enqueue, so accepting a message does not depend on completing model work (bot-message-context.ts, lines 175–219; resolve-route.ts, lines 474–527, 578–607; webhook.ts, lines 381–389).
  2. The selected coordinator reasons about the request and can call workboard_create. The tool forwards a structured card to the shared store. This reasoning step is model/prompt behavior, not a deterministic product-intake classifier (tools.ts, lines 243–256).
  3. workboard_specify can clarify a rough triage/backlog card, and workboard_decompose creates up to twenty linked children with inherited board/tenant and idempotency keys. Dependency state affects readiness and is checked when work is claimed (store-workflow.ts, lines 81–168, 433–550).
  4. Dispatcher promotion/expiry/retry logic prepares eligible work. Ranking and one active slot per owner prevent the same assigned agent from being dispatched simultaneously across boards; launch failures are bounded during outages (store.ts, lines 424–518; dispatcher.ts, lines 130–205).
  5. The dispatcher verifies workspace authority and worker-session status, then claims the exact card. It can create a managed worktree. Context includes the task, parent outcomes and recent same-agent work. The dispatcher persists a prepared launch. It calls subagent.run with card/claim identity, required tools, lane and idempotency key (dispatcher.ts, lines 311–428, 459–539; store-card-helpers.ts, lines 471–518).
  6. The worker performs actual tool work and reports heartbeat, proof, completion or blocking under claim authority. Terminal completion records summary/proof/artifacts, notifications and attempt state; lifecycle end/error and subagent_ended hooks reconcile the runtime back into Workboard (store-workflow.ts, lines 230–299; index.ts, lines 159–165, 190–210).
  7. Operator interfaces expose card/run/workspace and generated session status. A coordinator can synthesize results or ask a structured human question. No mandatory final TestMaster/product acceptance gate is inserted by this path. A completed card can lack passing proof, and a decomposed orchestration parent can be completed as decomposition rather than as delivered software.

Direct collaboration is richer than a shared filesystem. Session messages can wait for a terminal reply and reinject it with attribution, steer active work or start a new turn. Recipient-owned custody prevents accepted steering from losing authority merely because the sender has finished. Optional ClickClack adds externally hosted session-bound discussion channels and a read tool. The Control UI embeds that service and deliberately rejects same-origin framing (session-discussion-panel.tsx, lines 57–94). Wingman's Room1/Room2 membership, project context, escalation routing and durable decision linking remain a distinct organizational layer.

Grounded distinctive mechanisms and innovation assessment

  1. Durable task-to-run coordination. Workboard combines cards/dependencies, exact claims, workspace authority, a prepared launch, actual subagent execution, lifecycle reconciliation and structured completion. The meaningful mechanism is the join between durable planning state and real runtime identity, including accepted-but-not-yet-linked failures. It enables recoverable shared execution rather than merely displaying a task list. It still cannot establish the truth of a worker's tests or whether completing an orchestration parent means product delivery.
  2. Placement authority independent of machine lifetime. Remote launch binds environment, epoch, session, run and current turn claim before a node starts a physical child. Gateway transcript commits remain ordered and idempotent under their captured storage owner. This permits remote computation with continuing conversation authority, while rejecting stale launches and receipts. Workspace checkpoints and machine disappearance still bound recovery. There is no basis for claiming transparent replay of arbitrary side effects.
  3. Recipient-owned asynchronous steering. Accepted steering moves into the target's custody through commit/cancellation, rather than retaining the sender as an accidental lifetime owner (steering.ts, lines 14–77). This is valuable for independent specialists whose controller may finish while a message is pending. It does not create persistent organizational rooms or decide who should receive a business escalation.
  4. Semantic execution health. A utility-model observer emits bounded headline, assessment, categorical health and plan progress, while a faster preamble publisher coalesces deterministic updates (session-observer-model.ts, lines 249–268, 426–439; session-observer-preamble.ts, lines 8–9, 47–127). This directly addresses the difference between exposing a transcript and helping a human understand progress. Its judgment remains a model interpretation, not verified product health or autonomous blocker resolution.
  5. Explicit durable proactive intent. One-time provisioning receipts, per-job scratch, idle admission and active hours make periodic work inspectable and preserve deliberate deletion (default-proactive-job.ts, lines 23–55, 71–138). This is a useful model for ProjectMaster wakeups. The default prompt explicitly avoids inferring old tasks, so persistent portfolio obligations must be authored and maintained rather than assumed.
  6. Repository-scoped context with bounded recall. Project keys normalize origin identities or fall back to local roots; bootstrap admits only eligible facts whose project annotations match active scope, orders them deterministically and caps total/entry characters (project-memory-scope.ts, lines 22–55; project-memory-bootstrap.ts, lines 25–60, 76–135). This can reduce cross-product context contamination. It is relevance filtering within an operator's store, not a security boundary or complete source of product truth.

These are distinctive, grounded design choices in this implementation. No historical priority or industry-wide uniqueness claim is made.

Practical fit and remaining engineering

Use directly:

  • Telegram transport/routing.
  • Configured agent identities and custom instruction workspaces.
  • Native coding tool/harness boundaries.
  • Child session lifecycle and direct messaging.
  • Workboard cards/dependencies/claims/dispatch.
  • Project repository registry.
  • Proactive automations.
  • Human questions and technical approvals.
  • Actual remote execution.
  • Activity summaries/run inspectors and detailed coding session interfaces. These are expensive primitives Wingman would otherwise need to build.

Adapt: Define Butler, ProjectMaster, per-product ProductMaster/TechMaster and specialist profiles; give persistent agent instances explicit product/team membership; connect project records, Workboard boards/cards, session/worktree identities and DIRECTIVES files through stable IDs. Replace the generic four-role preset with the intended organization while preserving the useful one-artifact-owner and bounded-handoff rules. Decide where direct peer collaboration is allowed: the shipped coordinator program deliberately routes specialist results/follow-ups through the coordinator and disallows specialist loops, which differs from Wingman's direct Room2 collaboration. Build project and portfolio projections above Workboard and existing session summaries instead of treating a Kanban board as the whole executive view.

Build:

  • A durable natural-language intake owner that distinguishes new products from follow-ups.
  • Project knowledge/discovery/question/decision records.
  • Proportionate discovery and approved product scope/spec/scenario/definition-of-done workflow.
  • Enduring leadership assignments.
  • Room membership and escalation topology.
  • ProjectMaster's portfolio review and blocker resolution policy. An executive next-assignment/blocker view.
  • Independent integrated verification and human acceptance. Product acceptance must have its own authoritative state transition, evidence requirements and stop/resume behavior. Neither a terminal model reply, a done card, a review column nor an observer's “done” health is sufficient.

The lowest-risk adoption experiment would configure one bounded product with these roles, a Workboard namespace, explicit directive files, a clarification round, two independently executing specialists, a separate verifier and one human acceptance decision. Include a second product only after demonstrating that cross-product intake and context routing remain correct. Distributed workers should be evaluated with an interruption/recovery exercise and explicit checkpoint expectations. This is an implementation proposal, not a test executed for this assessment.

OpenClaw is a large integrated product, so adoption also means accepting its Gateway/state/plugin lifecycle and tracking a fast-moving upstream. For Wingman, the strongest strategy is an organization plugin/service on documented contracts, rather than invasive edits to runner internals or pretending arbitrary agent prompts amount to a managed organization.

OpenClaw: runtime, agents, coordination and operator surfaces

Supporting chapter for the complete assessment, at commit 6d3ff6f8bd62154540fee1ad3a123bdd539d904b, assessed 2026-11-05. Source links here are relative to this chapter. All behavior below is established by reading implementation/contracts or explicitly identified documentation; no live runtime was exercised.

1. What “agent” means in this implementation

The durable roster is agents.entries: Record<string, AgentEntryConfig> with defaults and agent-specific tool, sandbox, memory and voice settings (types.agents.ts, lines 19–40). The entry schema covers logical ID, display name/description, workspace, cwd, agent-state directory, model/utility/decision-model preferences, thinking/verbosity defaults, permission defaults, bootstrap limits, skills and delegation settings (agent-entry schema, lines 86–133). Its runtime union selects embedded or ACP execution; ACP has backend/harness agent, cwd and persistent/oneshot options (lines 66–84).

These fields create a reusable identity and execution policy with durable files/state. They do not allocate one permanently resident operating-system process for every listed agent. A session is a continuing conversation/work identity. A run is an admitted turn. Child sessions can use the same configured identity concurrently subject to spawn/session/runtime limits. This allows multiple independent specialist instances, but Wingman must decide whether “BackendCoder instance 2” is a distinct configured identity, a persistent assignment session using one profile, or a bounded child. The choice affects directory display, permissions, memory scope and Workboard owner capacity.

There are three different role concepts that should remain separate:

  • Agent operating role: instructions/persona plus tools/delegation, such as coordinator or researcher.
  • Human/operator role: Gateway access, scope ceilings and session visibility.
  • Runtime relationship: parent/requester/controller/child and whether a session is independent or supervised.

None by itself encodes a project's ProductMaster, its TechMaster and their organizational reporting relationship. A model description is not the same thing as a policy, and a parent-child run tree is not the same thing as a persistent team chart.

2. Definition and creation paths

Four bundled role IDs exist: coordinator, researcher, writer and reviewer. The role loader reads each CLAW.md, resolves the role's workspace AGENTS.md, uses the body as SOUL.md and generates IDENTITY.md (agent-roles.ts, lines 9–14, 52–87). This is more substantial than setting one system-prompt sentence: it materializes an operating program, identity and reusable instruction files. The four-role enum constrains bundled template selection, not all possible configured agents.

The coordinator template owns the requested outcome, discovers permitted specialists, creates bounded assignments through sessions_spawn or follows up through sessions_send, demands exact artifacts/verification/stop conditions and inspects important claims. Its explicit policy is to send all results and follow-up assignments through the coordinator and prevent specialists from looping on each other (coordinator program, lines 5–35). Escalation and approval instructions cover missing authority/access, conflicts and budget limits (lines 37–51). Researcher and reviewer similarly have concrete evidence/handoff programs. They are prompt-level operating policies backed by real tool/runtime mechanisms, not an automatic product-management state machine.

Team construction validates the preset and roles before creation, rejects colliding IDs and unfinished deletion cleanup, then calls the normal creation owner for each member. Each gets a separate child workspace. The coordinator receives a specialist allowAgents list and delegationMode: "prefer"; specialists receive allowAgents: [] (agent-team.ts, lines 32–60, 88–110, 128–149). If no ambient owner exists, it makes the coordinator that owner (lines 155–178). If member three fails after two creations, it preserves and names the created agents (lines 120–124, 180–184). This is deliberate partial-success recovery, not a team transaction that can be assumed to roll back completely.

Custom agents are also a first-class conversational setup path. The system agent's instructions distinguish agent ID, display name and operating purpose, preserve custom purpose in AGENTS.md, and describe appearance in Agents home after creation (assistant-prompts.ts, lines 150–167). The system agent is a configuration assistant using a protected tool/proposal protocol. It should not be confused with ProjectMaster. Its “create team” capability configures agents but does not create product registry/specification/acceptance records.

At the lifecycle owner, directory resolution precedes configuration apply; role delegation/bindings are persisted, approved workspace instructions are populated and transcript/state infrastructure is prepared before committed metadata is returned (agent-create.ts, lines 487–642). Workspace handling recognizes AGENTS.md, SOUL.md, IDENTITY.md, USER.md, tools/bootstrap and memory files (workspace.ts, lines 66–74, 638–679, 737–764). Their contents may be reusable programs, persona or knowledge. They are not typed product documents simply because they live under the same agent.

Gateway agents.create validates creation/onboarding and retained owner/upload authority, invokes the creation owner, revives databases and confirms runtime application. It returns the created identity and onboarding result and can initiate a first conversation as detached retained work (agents.ts, lines 230–394). A created agent with failed onboarding is still a created agent. For provisioning Wingman, the organization layer should reconcile such partial states and record readiness independently from membership.

3. Sessions, child creation and actual concurrency

The spawn schema separates task instructions, task alias, visible label, target agent ID/model, timeout and cwd. It supports hidden one-shot run, persistent/thread-bound session where supported, visible sessions, cleanup keep/delete, context/bootstrap variants, collector fan-out, structured output and ACP resume/stream-to-parent (sessions-spawn-tool.schema.ts, lines 30–65, 77–134, 163–173). A persistent child conversation can therefore outlive the first answer without becoming a new durable roster profile.

Spawn planning checks caller depth, maximum depth, active-child or collector live/total-group limits, and allowed target identity. It derives child role/control scope and depth (spawn-plan.ts, lines 296–349). The implementation calls Gateway agent, captures the accepted run ID and carries parent/controller/session identity, inherited tool restrictions and sandbox facts (subagent-spawn.ts, lines 394–430). It records child session, requester/controller, task/task alias, model, timeout, workspace, delivery/cleanup and collector metadata (lines 535–590). These are real independent executions with explicit admission and retained outcomes.

The independent-session tool intentionally differs. sessions.create uses visible-session containment/attribution but does not register a supervised-child run, emit child-completion events or establish yield expectations. It returns a visible session identity even when its initial run failed (sessions-create-tool.ts, lines 7–19, 46–60). This is a useful fit for separate continuing specialist work, but it leaves supervision and completion aggregation to the caller/organization design.

Execution prepares session state and required placement, selects lane and abort ownership, waits for session maintenance/projection and enters global admission (run-orchestrator.ts, lines 104–230). The lane controller's withSessionTurn retains queued-run/abort state and waits for raw producer and cleanup settlement before completing the operation (lane-controller.ts, lines 621–678). It explicitly notes the removal of the old per-session command-queue mechanism. Describing this revision simply as “one command queue per agent” would obscure both session-level independence and current authority ownership.

Workboard adds another concurrency policy: one active card slot per assigned owner across boards (dispatcher.ts, lines 130–205). Raw subagent concurrency and task-dispatch concurrency should not be conflated. If Wingman wants two BackendCoders executing Workboard cards at once, it should establish two appropriate owner identities/instances, rather than assume one configured owner will receive an unlimited number of simultaneous cards.

4. Tools, permissions and live authority

Tool policy supports allow/alsoAllow/deny and minimal/coding/messaging/full profiles, plus sandbox mode/workspace access and per-agent settings (agent-runtime schema, lines 58–71, 211–229, 465–472, 583–598). Effective execution is narrower than simply exposing a tool in a model request. Permission-mode translation maps read-only to deny, guarded to ask, workspace to automatic execution under containment and full to full execution. Retained/current ceilings are intersected, filesystem/apply-patch stay contained unless full, and an override can tighten but not loosen the session mode (session-permission-exec-mode.ts, lines 13–87).

The lane controller ties attempt liveness to the exact owner, abort state, lifecycle generation and delegated admission. Retained callbacks cannot keep mutating a replacement attempt after closure (lane-controller.ts, lines 180–194, 239–270). Similar ownership checks appear at remote launch, card claim and human-question resolution. This is a meaningful implementation strength for a long-running autonomous organization: permission is not merely a Boolean copied once into a prompt.

For Wingman, technical authority and product authority still need separate records. “Allowed to run a command,” “allowed to ask this human,” “the human approved this business direction,” and “the product meets acceptance” are different decisions. OpenClaw supplies useful command approval and question mechanisms. The organization must preserve product decision provenance and connect the correct response back to the correct project's leadership.

5. Persistence, project knowledge and resumption

The session manager is bound to explicit SQLite transcript identity. It supports asynchronous full-fidelity context reading and durable asynchronous append distinct from an in-memory manager (session-manager.ts, lines 1–5, 708–715, 741–750). The write contract includes branches, suffix replacement/rewrite, compaction and message append (session-manager-write-contract.ts, lines 73–159). Continuity thus has actual stored conversation/event structure, not only reloaded persona files.

Subagent records live in SQLite and can be selected by run, controller, requester or child, retaining tasks/results/delivery/error/structured output (subagent-registry.store.sqlite.ts, lines 23–43, 71–120). The decisive limit is explicit in the restorer: “Hydration preserves task history. A restarted process never reconstructs child execution.” It restores persisted metadata/history and reports errors (subagent-registry-restore.ts, lines 9–50). Metadata restore validates child authority/retention while large payloads remain database owned (restore-metadata.ts, lines 18–41). A retained unfinished record is not proof that the worker is still running or has automatically resumed.

The project catalog is concrete but narrower than a product registry. Workspace projects are synthesized from agent IDs/workspaces; registered or cloned repositories are loaded from shared state (project-registry.ts, lines 24–32, 58–102). Persistent registration deduplicates root and, for clones, origin; slug-based IDs disambiguate names (project-registry.kernel.ts, lines 40–83). Record fields are ID, repository root/origin/source/display name and optional agent ID (project-registry.types.ts, lines 1–18). There is no product stage, ProductMaster, scope approval or delivery definition in that record.

Project context has additional useful machinery. Repository origin normalization converges SSH/HTTPS identity while removing userinfo; no-origin repositories use local path identity. The code explicitly accepts a rare same-host/path collision between SSH accounts for relevance within one operator's store, and preserves remote path case to avoid cross-repository injection (project-memory-scope.ts, lines 22–55). Curated MEMORY.md/USER.md context is filtered by project annotations. Automatic bootstrap admits eligible project facts only, orders them deterministically and caps entry/total size (600/2,000 characters) (project-memory-bootstrap.ts, lines 25–60, 76–135). This helps relevance and bounded context. It is not a replacement for authoritative shared specs or a cross-user access-control boundary.

Bootstrap continuation can skip reinjection only when a valid full-bootstrap marker survives on the active transcript branch; reset/compaction invalidates its reuse (bootstrap-files.ts, lines 46–84). It is therefore useful to distinguish persisted knowledge, selected prompt context and the exact conversation branch. Wingman should keep authoritative product documents outside lossy summaries/recall snippets and link them to the project registry rather than rely on automatic memory to retain every business requirement.

6. Scheduling, autonomous continuation and supervision

An active Goal is session work state with objective, status, usage and optional token budget. Usage accounting can change active to budget-limited; state transitions support pause/block/complete and budget-window resumption (goals-transitions.ts, lines 26–149). Goal continuation checks exact session/lifecycle/goal identity, abort state, supported harness placement and terminal outcome eligibility. It does not enqueue over pending tool calls, accepted children, deterministic approval prompts, errors or queued/unsettled work (goal-continuation.ts, lines 74–90, 120–206). This supplies sustained pursuit within a session, not an organization-wide task scheduler or proof that an objective is correctly complete.

The current proactive model is ordinary automation. The default prompt reviews its scratch and relevant context and explicitly says not to infer or repeat old tasks. Setup normally creates one 30-minute, idle-only, scratch-skipping proactive check in the ambient owner's main session, announcing to the owner (default-proactive-job.ts, lines 23–55). It provisions once using a durable receipt, so deletion remains deletion. It does not recreate the job on every startup or assign one to every agent (lines 71–138). The old heartbeat scheduling/HEARTBEAT.md model is migrated rather than the current runtime scheduling contract (heartbeat documentation). Infrastructure keepalives and task claim heartbeats are different mechanisms.

Timer execution checks time-zone active hours, idle-only policy and empty scratch, and routes script/shared-session/detached work into the appropriate execution path. Agent automation hands occurrence, current authority, abort and delivery context to runSessionEvent (timer-execution.ts, lines 130–225, 341–433). Persisted jobs have schedule, agent, session target, payload, delivery and failure alert fields (types-shared.ts, lines 33–54).

These mechanisms can wake a ProjectMaster and sustain work, but supervision still needs authoritative active-project selection, blocker semantics, follow-up history, escalation and a rule for stopping accepted/completed products. Merely enabling the default proactive job would not meet Wingman's portfolio supervision contract; its intentionally cautious default prompt would not infer those obligations from old chats.

7. Workboard: shared tracker joined to execution

The bundled Workboard is a major product, not a cosmetic card view. Its card tools accept assigned agent, notes/acceptance criteria, priority, board/tenant, parent links, workspace, schedules and budgets (tools.ts, lines 73–108). specify updates rough work into specified todo work; decompose creates up to twenty children with inherited namespace and derived idempotency keys, links dependencies and can complete the orchestration parent (store-workflow.ts, lines 433–550). That last completion means decomposition was done. It is not product acceptance.

Dependencies have actual execution consequences. Claiming checks readiness; status promotion holds future schedules and requires every parent to be done. Cycle detection traverses parent links (store-workflow.ts, lines 81–168; store-core.ts, lines 790–833). Triage candidates can be marked as awaiting specification/decomposition without pretending the scheduler itself has reasoned through requirements (lines 836–860).

The dispatcher reconciles expiration/timeouts/retry exhaustion, ranks runnable cards and preserves one active slot per owner. It checks archived sessions and workspace authority, acquires the exact card claim, and may create a managed worktree (dispatcher.ts, lines 130–205, 311–428). It prepares durable launch identity before calling subagent.run, with claim protocol, permitted tools, lane/idempotency identity and recorded acceptance (dispatcher.ts, lines 459–539). A task therefore links to actual runtime identity and has a recovery story for accepted dispatch rather than relying on an untracked model promise.

Worker context includes card notes/history, parent outcomes and recent same-owner work, not just a title (store.ts, lines 609–629; store-card-helpers.ts, lines 471–518). Heartbeat/block/complete mutations are claim-scoped. Completion stores structured summary/proof/artifact/notification/attempt facts; runtime hooks reconcile end/error/subagent terminal state (store-workflow.ts, lines 230–299; workboard index, lines 159–210).

The essential acceptance limit is visible in the completion code. Proof is optional; completion can finish the run as done without independent verification. Missing proof/artifacts/attachments on a done card produces a warning (store-card-helpers.ts, lines 418–431). This deserves credit as useful evidence transport, not credit as an enforced TestMaster acceptance system. Wingman should add a verifier assignment, evidence schema/requirements and accepted-product transition separate from worker completion.

8. Communication, human questions and decisions

sessions_send is a real execution operation with requester source and authority wrappers. Placement contracts cover Gateway, paired-device and cloud-worker recipients; normal peer sends produce turns, eligible no-wait sends may enter active input, and idle recipients start work. Cross-tree/stale-incarnation targets are denied (sessions-send-tool.ts, lines 18–40; sessions-placement-tool-contract.ts, line 11 and surrounding contract). A2A waiting can capture a terminal answer and reinject it with attribution (sessions-send-tool.a2a.ts, lines 73–110, 202–208).

Steering differs from a fresh turn and from delivery notification. Follow-up code distinguishes a steered run from a separately started run and warns if accepted input lacks a proactive state watch (sessions-send-followup.ts, lines 190–194, 248–266, 341). Recipient-owned custody retains accepted steering through commit/cancel after the sender's lifetime ends (sessions-send-tool.steering.ts, lines 14–77). That is valuable asynchronous collaboration machinery, but organization membership and management escalation routing are separate.

Human questions have request/wait/resolve methods with current session/run authority, waiting-state recording and channel/UI dispatch (question.ts, lines 135–180, 269–364, 438–495). Exec approvals have their own list/get/request path (exec-approval.ts, lines 77–128). These are better substrates than parsing an unstructured “yes” from arbitrary transcript text. A Wingman layer still needs project/question IDs, ownership, options/research context and a durable decision record linked to scope/spec changes.

Optional ClickClack provides a real room/discussion integration. Gateway session.discussion delegates to a provider and can return no provider. The plugin registers a discussion provider, persists bindings and opens session-bound channels (session-discussion.ts, lines 86–153; service.ts, lines 60–90, 194–245). It adds a discussion reader tool and constrains discussion-session access to its attached main session (register.ts, lines 36–42, 154–174). The Control UI frames the external application and rejects same-origin URLs (session-discussion-panel.tsx, lines 57–94). Service availability and security policy matter. This is not an entirely in-process Room1/Room2 implementation.

9. Real multi-host execution and its boundary

This checkout implements actual off-host agent execution. A worker-turn tunnel validates current environment ownership, owner epoch, worker claim, session ID and run ID, then launches on the selected device. It explicitly refuses to launch an embedded worker turn for a remote-exec environment (node-worker-tunnel.ts, lines 386–423). The node adapter invokes supervisor launch/status, reconciles potentially dispatched launches using durable receipts and bounds admission rearming (node-launch-adapter.ts, lines 467–605). It treats restart after possible dispatch differently from confirmed cancellation (lines 638 onward).

On the remote node, the supervisor admits capacity, checks prior receipts and physical ownership, journals the claim and starts a child (node-worker-supervisor.ts, lines 158–352). Child lifecycle prepares real process/container transport, requires a PID, establishes process identity and records the running owner behind a journal gate (node-worker-child-lifecycle.ts, lines 121–240). The launch caller waits for the exact journal terminal receipt and finalizes its result (worker-turn-execution.ts, lines 663–705). This is materially different from giving a model an ssh command or running another local subprocess.

Canonical transcript commits stay Gateway-owned, ordered per session and epoch-checked, with an idempotent ledger tied to captured storage identity (transcript-commit.ts, lines 33–74). Shared conversational authority can therefore survive a change in physical execution placement. Organizational collaboration can use the same Gateway/session messaging contracts while computation occurs elsewhere.

Runtime modes have different locality. Documentation describes OpenClaw worker-turn mode as a restricted remote OpenClaw process, normally proxying inference through the Gateway. Native Codex remote-exec keeps app-server/auth/transcript at the Gateway and places the authorized exec-server remotely. This distinction is documented in dispatching a session. It is not a claim to have inspected the unavailable underlying Codex source. Runtime/provider capability gates apply and there is no documented silent Gateway-local fallback. Child sessions use separate managed worktrees and inherit the selected parent worker profile.

Recovery is bounded by workspace synchronization. The session lifecycle documentation explains reconciliation of completed turns. A machine loss can discard edits made between checkpoints. Checkpoint manifests/delta packs cover the repository; they do not contain a complete upstream repository. A replacement worker needs fetchable or cached base commits. It also distinguishes stopping a turn from stopping the cloud device. The full machine-loss/recovery implementation matrix was not traced here. Those caveats are documentation-backed. No claim is made that arbitrary unfinished non-idempotent tool calls are blindly replayed.

10. Visibility: directory, semantic overview and detailed workspace

The Agents home consumes actual policy-filtered configured identities, with settings panels for identity/model/files/memory/cron/channels/tools/skills (agents.ts, lines 118–175; agents view, lines 54–60, 99–127; overview panels, lines 94–118, 155–166). This is a real directory/settings surface. The gap is durable project/team/reporting relationships, not the absence of an agent list.

The observer goes beyond raw logs. A utility-model prompt asks whether the session is progressing, grinding, stuck, waiting on the user, wrapping up, done or failed. A strict response schema retains headline, optional assessment, health and optional completed/total plan progress (session-observer-model.ts, lines 249–268). Preamble publication can provide fast coalesced deterministic updates (session-observer-preamble.ts, lines 8–9, 47–127). These mechanisms can misjudge underlying task truth, but they are actual summary-producing behavior and should not be dismissed as an event log.

Activity rows link the session, agent chip, observer headline, run inspection and retained recap; Current Work links active and queued sessions (session-activity-row.tsx, lines 94–105, 128–150, 193–251; current-work-view.tsx, lines 34–79). Summary-source reads are bounded committed transcript batches (session-activity-summary-source.ts, lines 25–103). This supports useful recent/current status and drill-down. It is session-centric and does not establish all of the agent's product obligations, next assignments or portfolio-level blockers.

The detailed session workspace includes terminal, browser, desktop, file/preview, context, subprocess, subagent and discussion views (chat-pane-embedded-view.tsx, lines 40–110, 184–240, 370–385). Send/abort and permission-aware subagent stopping are wired through actual runtime controls (chat-view.tsx, lines 700–701; chat-subagents-panel.tsx, lines 281–303, 425–478). These are strong foundations for Wingman's individual workspaces, though capabilities depend on selected harness/session/node and the interface does not automatically become a career-long standing-agent workspace.

Three “boards” should not be collapsed into one feature claim. Core board.* is session dashboard/widget composition. Workboard card boards are durable task namespaces with dependencies/claims and their own UI. Workboard Sessions boards organize Gateway-owned observer/run/PR facts into columns and can scope to agent IDs (workboard index, lines 36–103, 247–252). The plugin's card tools explicitly distinguish card boards from Sessions boards (tools.ts, line 247; tools-orchestration.ts, line 198). Each is useful; none alone implies the whole product-management dashboard.

11. Failure, retry, cancellation, completion and retirement

Provider retry is not task redispatch. The embedded run loop creates retry budgets, persistent idle/compaction guards and per-attempt authority checks; budget exhaustion chooses failover/error rather than unbounded retry. Provider rate-limit deadlines/auth recovery and permission-change continuation have distinct handling (run-loop.ts, lines 148–161, 235–284, 385–397, 444–461). Workboard separately owns task attempts/retry exhaustion/claim expiration; remote launch separately owns dispatch receipts/admission rearm. Wingman should preserve these owners rather than add one global “retry everything” loop.

Spawn has meaningful compensation. If launch/registration fails, it cleans provisional sessions, prepared context and attachments; if a child was already accepted before registration failure, it can terminate that child (subagent-spawn.ts, lines 448–530). This avoids assuming failure to record a child means no child ran. Other external effects remain governed by their own idempotency and outcome contracts.

Cancellation mutates/stops and joins execution settlement, then cascades across a captured child tree. It refreshes descendants while avoiding unrelated newly created work; explicit root cancellation reconciles terminal state as well (subagent-control-kill.ts, lines 44–99, 244–424). “Stop” is therefore more than closing a UI panel or signaling a guessed process. It does not imply all arbitrary external effects have been undone.

Terminal result, reply delivery, retained child history, card completion, independent verification and product acceptance are separate facts. The code supports the first four with substantial machinery. Reviewer instructions ask for evidence-based independent findings, but neither those instructions nor a Workboard review status ensures that a separate TestMaster executed required product scenarios. A Wingman acceptance owner must compare the agreed definition of done, integrated test evidence and unresolved defects, obtain the human's decision where required and stop active development after accepted delivery.

Agent deletion defaults to file deletion, delegates to its deletion owner and confirms configuration reload. It explicitly reports when configuration removal succeeded but physical cleanup is pending (agents.ts, lines 555–592). Team creation checks pending deletion cleanup before reusing identities. For a standing organization, “retired employee,” “archived assignment,” “deleted session” and “deleted agent files” should therefore remain distinct operations. The core lifecycle is a substrate, not a supplied HR/project-retirement model.

12. Verification evidence and confidence

The source paths above were inspected by focused read-only review. No source modifications, installations, live credentials, channel messages or service launches were performed. Tests were read as contracts, not executed. Particularly useful source tests were:

  • subagent persistence/resume, lines 103–167: retaining large task/result payloads while reloading metadata and preserving exact suspended/in-progress delivery owner after restart without reannouncement.
  • subagent retirement, lines 180–260: injected persistence failure retains pending cleanup/ownership and prevents incorrect successor/unrelated-child cancellation.
  • Workboard dispatcher: cross-board one-owner slot (around lines 357 and 667), bounded failed launches (539), serialized concurrent dispatch (791), workspace ceilings (248, 302), managed-worktree cleanup (460) and exact-card launch (921).
  • Workboard store: exclusive owner claim (329), SQLite reopen (345), correlated proof (843), dependencies (1166), cycles (1399) and structured completion/blocking (1552).
  • node launch adapter, lines 186–200, 328–405: transferring possibly dispatched work to restart recovery, deterministic bounded rearm and payload/credential constraints.
  • agent role operations, lines 124–155, 158 onward: preserving custom instructions/identity and actual directed team creation.
  • project registry, lines 46–74 and following persistence/clone cases; project scope preparation, lines 24–70: same-turn discovery sharing and separation of differing session/workspace inputs.
  • activity recap state, lines 34–99: current/stale/pending recap, retries and cached recap retention on refresh failure.
  • Telegram inbound pipeline, lines 6–55: debounce lane isolation by account/sender/topic.

Additional supervisor/container/reboot, tunnel authority, transcript, automation and discussion test files exist; their presence does not constitute passing evidence. Distributed checkpoint caveats and runtime-mode locality are partly documentation-backed, with actual launch/authority/transcript mechanisms independently traced. Native Codex internals could not be inspected because no sibling source checkout was available. Provider authentication, real node operating-system permissions, optional discussion-service behavior and all live delivery/UI behavior remain unverified.
