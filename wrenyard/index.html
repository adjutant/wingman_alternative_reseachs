Wrenyard assessment

Identity, revision and fit

  • Product: Wrenyard, a local-first desktop workbench for orchestrating AI engineering work; package version 1.0.172.
  • Repository: https://github.com/wrenyard/wrenyard
  • Local checkout: research/wrenyard/repo.
  • Assessed commit: cdaed14b3cfa0901d2feddc86d9b82060d6c3d5b.
  • Assessment date: 2026-11-05.
  • Basis: Wingman purpose, assessment guide, and static inspection of the checked-out implementation. No checkout changes, dependency installation, service startup, model calls or browser operations were performed. No applicable checkout or ancestor AGENTS.md file was found. The supplied global instructions were followed.

Verdict: A substantial execution, continuity and desktop-observability foundation, with a genuine standing-bot layer above disposable coding tasks. Wrenyard is meaningfully closer to Wingman than a terminal grid: bots have durable identities, private context and memory, peer messaging, a shared group conversation, routines and event-driven follow-up on delegated sessions. Its engineering sessions coordinate typed exploration/edit/test/commit tasks across registered repositories. However, it does not supply Wingman's product-management organization: Butler/Telegram, portfolio intake policy, per-project ProductMaster/TechMaster teams, proportional discovery, enforceable product completion and an executive current/recent/next briefing remain to build. Remote execution is real SSH access to another daemon, but the application deliberately selects one daemon at a time. It is not a distributed organization with shared live coordination.

The central distinction is bot → work session → task run → native client process. A bot is a durable orchestrator with enabled tools, not itself a permanently running coding process. A work session is a persistent engineering conversation, not necessarily a named organizational employee. The built-in edit/test/etc. definitions are task roles that instantiate real executions, not standing BackendCoder/TestMaster identities. Sources: bot kernel, lines 95–132, 323–372 and 685–703; task workflow runner, lines 82–138; Codex native protocol, lines 97–118.

Architecture and actual execution model

Surfaces, control plane and state

Electron/React Desktop and the CLI are clients of a TypeScript daemon. Packaged launch uses the bundled Node executable to run daemon/daemon.mjs run --config …: launch, lines 9–19. The daemon composes session, scheduler and bot services and registers their RPC handlers: daemon, lines 1556–1595 and 1631–1634. The owner-facing control transport is framed NDJSON JSON-RPC over a Unix socket/named pipe with a required protocol-version handshake, rather than a public organization API: IPC server, lines 11–30 and 128–175. Bot methods explicitly reject non-IPC transport: agent handlers, lines 22–47. The separate loopback model gateway serves inference. It is not a chat/team server.

State is deliberately split by purpose:

State Implementation and implication
Registered projects Workspace projects/**/<name>.fmproj metadata; host-specific checkout paths resolve against the current hostname. Project manager, lines 185–239, 1763–1838. A project registry exists, but registration does not provision a product team.
Project knowledge Workspace project docs/specs, docs/reports, docs/handoff and associated AGENTS.md; document APIs resolve canonical locations. Document service, lines 1–31 and 64–104.
Todos Authoritative Markdown files under todos/, with request, acceptance, project, dependencies, tags and comments; SQLite is a disposable index. Todo service, lines 1–13 and 77–100.

Engineering session and task execution

The ordinary session's main reasoning model cannot directly read source or run shell commands. It declares native typed actions: search, dispatch, document, todo, vcs, project, or an isolated ask. Auxiliary models compile intents into service calls. The action router is explicit, not prose parsing. Project source is viewed/changed through tasks. Independent actions can run concurrently, and task results return later into the ledger. Sources: reasoning prompt, lines 42–84; action router, lines 123–145; dispatch compiler, lines 1–17 and 60–87.

This separation is operationally significant. A session reasons over a curated workspace snapshot, documents and task findings, while a cheaper/native executor does bounded work. Tasks receive explicit compiled context. They do not automatically inherit every specification. The edit task's prompt specifically restricts it to declared target files and excludes tests/commits; testing is a separate role. Edit task, lines 12–36 and 76–94. That improves control of concurrent file changes but places substantial responsibility on the orchestrator to supply complete, correct instructions.

TaskService discovers definitions, validates input and resolves project/worktree context. TaskWorkflowRunner persists the acceptance placeholder, registers write targets and invokes the execution kernel asynchronously. The kernel runs pre-gates, builds a prompt, resolves exactly one automatic runtime target, launches one task attempt, records report/facts and applies post-gates. Task completion produces a natural-language report; filling the declared output schema is a separate on-demand compilation step, especially for TaskGraph consumers. Sources: TaskService, lines 173–240; workflow runner, lines 82–138; execution kernel, lines 436–510 and 634–709.

The lower execution service chooses a client and starts it, consumes its events once, offers replay and cancellation, and normalizes terminal status: ExecService, lines 123–200, 300–339 and 388–499. For Codex, this is a real native app-server conversation: initialize, optional account login, thread start/resume, then turn start. It is not one model persona pretending to be several workers. Codex protocol, lines 97–118.

Agent definition, creation and full lifecycle

The four entities must remain distinct

A bot is the closest equivalent to a durable Wingman agent. Its immutable directory slug is identity; name, description, icon and role body are presentation/persona. bot.json holds user-controlled primary, enabled and tool switches. It has a private session ledger and a memory store rooted in its definition directory, and is driven by wakes rather than a permanent LLM loop. A work session is a durable UUID conversation over a workspace snapshot. It can orchestrate many projects/tasks. A task definition is a reusable typed execution contract with a prompt, schema, dispatch requirements, optional write-target function/features/gates. A task run has a separate durable ID/status and launches a native client process for one attempt. Model roles such as reply/title/search/dispatch are stateless auxiliary calls, not organizational agents. Sources: config, lines 53–81; kernel, lines 120–132 and 690–717; session engine, lines 174–194; execution kernel, lines 351–429 and 501–510.

Definition and creation

Definitions live in <workspace>/bots/<id>/ or the device config bot root; routines remain device-local. The ID must be a lowercase path-safe slug of at most 32 characters. Known tool switches in code are session, todo, message, memory, routine, and workspace. The user guide's tools table omits the last one. Strict validation rejects unknown config fields/tool names and invalid identity front matter; errors disable only the affected bot. Files are checked for real containment and ordinary-file status. Workspace bots shadow duplicate device IDs visibly. Sources: config, lines 1–19, 29–81, 174–241, 252–260 and 470–510.

agent.create validates the name and ID availability across both roots, exclusively creates a directory and identity files, reloads definitions, then enqueues an onboarding greeting. The generated role asks the user for name, how to address them and the bot's main responsibility, then stores identity/preferences. This is real persisted onboarding, but it is generic personal-assistant creation, not project-team recruitment. Initial switches are primary: true and session/todo/memory/workspace enabled; message and routine are not automatically enabled. Multiple primary claims resolve to the first valid ID with warnings, so “primary” is not automatically the last-created bot. Sources: kernel creation, lines 80–90 and 1897–1938; exclusive creation/defaults, lines 496–507 and 529–562.

New task roles follow a separate definition registry. Built-in and project definitions share plain IDs with project overrides and inheritance metadata. These are executable TypeScript definitions, not just Markdown employee profiles. Source: definition registry, lines 25–46 and 78–119. Wingman could define backend/mobile-specific tasks here, but would still need a durable specialist identity/task-ownership model above them.

Execution, tools and permissions

The bot prompt combines its fixed runtime contract, role body, device routines and enabled peer roster. It explicitly delegates code/search/document/task work to sessions. A proxy gives bot context sessions their own state root, own tool port and private memory, while reusing the engineering session engine. Tool specs are restricted to enabled switches; execution errors become failed results the model can correct. Sources: kernel, lines 323–372 and 685–703; tools, lines 1–9 and 289–345.

The session tool lists/creates/sends/interrupts workspace sessions. A bot-created or messaged session records a watch for the exact next turn, optionally associated with todo IDs. If the initial send fails, its newly created empty session is deleted. The todo tool updates the shared tracker, and memory tools modify the bot's own identity and memories using exact previous-body checks for destructive updates. The workspace tool allows narrowly instructed workspace version-control work. Sources: tools, lines 79–171, 191–281, 434–469 and 665–708.

This is a tool allowlist, not an OS sandbox or per-action approval boundary. The native Codex adapter starts/resumes threads with approvalPolicy: 'never' and sandbox: 'danger-full-access': Codex protocol, lines 105–118. Session prompts require explicit authorization for commits/pushes/deployments/messages/deletions, and test prompts block sensitive surface actions, but those instructions differ from enforceable organization-level approvals. Session prompt, lines 71–74; test task, lines 66–74 and 99–108. A Wingman integration must preserve that distinction.

Routing and concurrency

Bots use an automatic ranked provider/model ladder with capability/context/effort and quota/price/speed weights. The source requirement asks for mid minimum/premium expected intelligence, 131072 minimum context and high reasoning, preferring premium/high abundant then sufficient candidates. The kernel holds the last offered model for one hour to favor prompt-cache reuse, rotates oversized bot context, then filters routes by the actual context requirement. Sources: bot routing, lines 3–18; kernel route admission, lines 1514–1577. Bots do not independently pin a model in bot.json; task runtime selection is separately resolved by TaskSettingsService at launch.

Several bots/sessions/task runs may progress concurrently. Wakes are persisted until session admission. The kernel's current code first attempts to steer an active bot turn and otherwise starts a new turn. Thus “one wake = one completely isolated sequential bot turn” is an inaccurate reading of the guide. Multiple incoming wake texts may be handled inside the same active turn. Kernel, lines 1487–1511 and 1587–1603; session steer, lines 212–237. Peer bots retain separate contexts; individual task processes retain separate execution IDs.

Repository write coordination supports exact file sets: different declared paths in one repository may be edited together, overlapping paths or repo-wide locks conflict. Worktrees have owner/creator locks and support separate branches. These are daemon-local coordination primitives, not distributed file locks. Sources: write locks, lines 70–101 and 123–138; worktree metadata, lines 60–84. The declarations coordinate compliant executors. They do not confine a full-access native process to those paths.

Persistence, resume and context management

Bot state persists queued wakes, private session ID, watches, held model and deduplication records in kernel.json; admission removes a wake only after it has entered the conversation. Watched-session completion matches an exact turn, avoiding a later result incorrectly settling earlier work. Startup restores watches and publication cursors, repairs pending peer wakes and dispatches remaining queued wakes. Kernel, lines 895–920, 944–1011, 1255–1297 and 1789–1817. The JSONL ledger is the durable history; compaction appends a summary rather than rewriting history, with deterministic fallback if summarization fails. Ledger, lines 1–23; compaction, lines 1–10 and 28–55.

Bot context rotation additionally creates a fresh session and seeds it with watched work/todo briefs; old ledgers, watches and routines remain. Kernel facts restate watches, routine timestamps, peer roster and memory index after compaction. Kernel, lines 739–782, 1348–1384 and 1548–1574. This supports long-running identities without requiring unbounded active prompts. The public agent.events API resolves the bot's current context session; seamless UI access to all old rotated bot contexts was not established. Agent handler, lines 76–87.

Continuity does not mean live process resurrection. On restart the execution supervisor kills/verifies stale recorded processes and marks queued/starting/running executions interrupted. It explicitly relaunches nothing. Session recovery appends synthetic interruption for unfinished turns. Supervisor, lines 550–610; engine recovery, lines 1069–1099. A later bot message/routine can reason from recorded state and continue; native clients also support explicit resume IDs. These are different recovery paths.

Scheduling and supervision

A five-second scheduler tick fires due active interval routines. Definitions support 1 minute–7 day intervals, and source additionally supports on: todo event matching with author filtering to avoid immediately reacting to the bot's own changes. Interval run counters/next fire/error state persist; todo-trigger wakes are transient. Scheduler, lines 13–16, 305–378 and 589–602; routine tools, lines 734–774; kernel routine wake, lines 2040–2055. This is more capable than the interval-only prose guide.

The busy gate concerns a wake of the same routine still queued; work sessions launched by an earlier fire do not hold off later fires. A supervisory bot may therefore revisit work already in flight, and must use its watches/todo associations responsibly. The scheduler protects workspace switches and shutdown admission, and records wake rejection rather than silently failing. No built-in ProjectMaster periodically checks every product; that behavior must be expressed as bot policy.

Interruption, retries and failure recovery

A user can interrupt a session turn or cancel a task. The bot session tool can interrupt delegated work. Bot-tool interruption removes the session watches before interruption, deliberately preventing that interrupted outcome from waking supervisors. Bot tools, lines 498–521. Engine interruption aborts work and appends durable interruption/finished records, with late results identified appropriately: engine, lines 674–706. Task cancellation waits for the linked execution to reach terminal state and returns persisted truth on repeated cancellation: workflow runner, lines 141–180.

Current retry behavior must be read from code: model-call source describes jittered 2/4/8/16-second ambiguous-failure retries, up to four, no replay after output begins, and automatic bot route movement after two consecutive failures. Retry switches are read live for sessions and bots; known route recovery can create a cancellable nonterminal wait. Model request, lines 11–18 and 736–849; engine wait state, lines 98–109. This supersedes the bot guide's simpler “single fallback attempt” description. A structured task run resolves one route and launches at most one attempt; redispatch belongs to its caller, not an unlimited hidden retry loop. Execution kernel, lines 501–510 and 700–709.

If no bot route is available or admission fails, the kernel removes that wake and records a visible error. It does not promise durable retry until a model appears. Kernel, lines 1539–1541 and 1578–1583. Invalid bot files disable only that bot. Shutdown stops polling/subscriptions, closes the private engine, waits for admission promises and flushes state. Kernel stop, lines 1821–1864.

Completion, acceptance and retirement

Engineering turns end with a reply/no further actions or an ask awaiting the user. A watched turn's exact final status and answer become a supervising wake. A task run reaching done means report collection and applicable gates finished. Its report may contain failed/blocked test assessments, so done is not product acceptance. Test criteria are explicitly independent and verdicts are passed, failed, blocked, not_supported: test task, lines 29–55 and 145–157. A todo can be set done by its authorized tool; no code-level cross-check requires all product tests or human acceptance first. There is no built-in “accepted product delivery stops development/testing” lifecycle.

Bots are retired by disabling or removing their definition; disabled config is a service switch rather than conversation deletion. File polling makes changes visible. No bot-delete/archive/retirement RPC was found in the complete agent handler, lines 27–89. Work sessions independently support rename, archived/pinned metadata and guarded deletion (including ledger/media cleanup); archival is list metadata, not a stop command. Engine, lines 556–610 and 653–671. No public fork operation was found in session contracts/handlers/engine/UI searches. Automatic compaction exists. A manual compact control was not established. Removing a bot definition should not be treated as proven cancellation of work sessions it previously launched or garbage collection of its historical state.

Coordination mechanics and a concrete source trace

Shared work, messages and decisions

The group transcript is real shared coordination state, not just independently rendered agent logs. User text is appended once, @mentions resolve against enabled IDs/unique names, and text with no resolved mention goes to the effective runnable primary bot. Bot replies are published from real ledger reply events or visible final answers; raw tool intents are not republished as chat. Mentions from bot replies only deliver if the sender has the message tool. Publication keys, cursors and pending peer wakes are persisted together before delivering derived wakes. Kernel, lines 1050–1160, 1210–1297 and 2006–2033. Mention parsing, lines 86–147, resolves longest aliases, drops self-mentions and collapses duplicates. This is practical peer collaboration with restart bookkeeping, but it has no project-room taxonomy or management membership model.

Todos provide shared durable request/acceptance/dependency/comment records. Updates validate dependency existence and cycles; exact old title/request/acceptance checks help prevent overwriting another contributor's changes. The record has no dedicated assignee or bot ownership field. A watch can associate work-session IDs with todo IDs, retaining the connection through bot context rotation. Sessions are expressly read-only toward todos; bot tools are the mutation path. Todo service, lines 1–13 and 86–100; bot todo tool, lines 118–171; session prompt, lines 48–51. Wingman's tracker integration would need to decide whether specialists update as bots or through a new authorized session tool.

TaskGraph is an additional explicit coordination engine, distinct from todo dependencies. Graph nodes have input/output schemas, dependencies and actions including condition/convert/join/checkpoint/task/shell. The runner schedules satisfied dependencies, cancels impossible branches, persists failures, and can pause or cancel on a node failure. Pause stops new scheduling while existing tasks run; cancellation fans out to running task IDs. Graph model, lines 25–68 and 116–152; runner, lines 414–460, 533–618, 795–852 and 1054–1097. These are workflow primitives, not evidence that everyday bots automatically generate/maintain a complete product DAG.

Human decisions currently live in chat replies or session questions, and optionally graph checkpoints. The system does not maintain a durable escalation case linking worker → technical/product leader → management → Butler → human answer. Nor does a normal authorization instruction become an enforced native-client permission prompt.

Trace: a user asks the primary bot to fix a registered project's defect

This is a code-path walkthrough of implemented behavior, not a live run or a claim that the model will choose these exact tools reliably.

  1. Desktop group input reaches agent.group.send, which is allowed only via IPC. groupSend appends the user message and resolves mentions; absent mentions it selects the runnable primary. It enqueues wakes, persists the group transition, then dispatches. Agent handler, lines 29–35 and 74–75; kernel, lines 2006–2033.
  2. runWake ensures the bot's private context, chooses an eligible model (with one-hour affinity/context-fit checks), and sendWake steers an existing turn or admits a new one. Its prompt contains identity, enabled tools and peers. Kernel, lines 323–372 and 1487–1577.
  3. The bot may add a todo containing request/acceptance/project. It then calls session.create with the task message and todo ID. The session is a full engineering conversation. It does not execute code inside the bot context. runSessionTool sends the opening message and registers a watch for the returned turn. Bot tools, lines 434–465 and 562–574.
  4. The work session receives the registered project snapshot and task catalogue, reasons about required exploration, and emits a dispatch action. ActionRunner invokes the auxiliary compiler, which validates task input/context before the host starts the task run. Session host, lines 246–253 and 303–333; actions, lines 123–145; dispatch, lines 1–17 and 60–87.
  5. TaskWorkflowRunner stores the queued run and declared write targets; execution kernel builds the prompt, gates admission and resolves a runtime. The native Codex client, if selected, starts a real thread/turn and streams events. An edit task touches specified files. An independent test task can run the acceptance commands and return assessments. Workflow runner, lines 82–138; execution kernel, lines 390–463 and 501–510; Codex protocol, lines 97–118.
  6. On completed work-session turn, onWatchedTurn matches exactly the watched turn, removes its watch, extracts the actual final answer/status, deduplicates and persists a [wake:session …] message. The bot can inspect that outcome, continue/reassign work, update the todo/comment or ask the human. Kernel, lines 979–1011.
  7. The bot's final user-visible answer is published into the group, optionally waking a peer mention. Todo writes may additionally fire matching todo-event routines; self-author changes are filtered. Kernel publication, lines 1099–1152; scheduler event routines, lines 589–602.

The trace supplies genuine asynchronous delegation and return routing. What is missing is a required discovery/specification/technical-ticket/test/acceptance sequence and explicit ownership at each transition. Those are model decisions and configurable instructions here.

Major capabilities beyond Wingman's described product

Provider/model economics and gateway interoperability

Wrenyard makes automatic runtime selection a first-class system, rather than assuming every role is Codex. It separates main reasoning, auxiliary work and native task execution, with capability/context/effort requirements, price/speed/quota weighting, route health and usage instrumentation. The bot ladder and model affinity are explicit: routing, lines 3–18; kernel, lines 1514–1577. Global session/bot retry controls are read live: session host, lines 218–235 and 263–271. Workshop Ledger aggregates token/task/model investment and activity: StatsPage, lines 40–64 and 124–135.

The loopback inference gateway can expose connected providers to external editors through a persistent local token. This is a material interoperability capability, although not an externally accessible management server. Architecture documentation, runtime-surface section; gateway handlers, lines 283–335; gateway token/binding, lines 2449–2456 and 2974–2987. Wingman could use routing/cost controls even with a default Codex organization, but would need to bind usage to enduring agents/projects and avoid treating provider credentials as organization permissions. No current provider count or real account compatibility was verified.

Explicit executable task graphs

TaskGraph offers schema-checked dataflow, branch/condition/join nodes, checkpoints, revisions/patches and persisted failure policy. A product organization could encode a repeatable verification or release procedure independently of a model's freeform conversational plan. Graph model, lines 25–68 and 116–152; runner scheduling and signals, lines 533–618 and 795–852. Integrating it requires mapping graph nodes to tickets/agent accountability. A graph is not itself an organization, and the current ordinary bot/session flow should not be assumed to use it automatically.

Managed browser/desktop verification components

Tasks can request browser-use or computer-use features, with daemon-managed readiness/attachment and isolated execution resources. The generic test role has distinct prompts for agent-browser and Cua Driver and can return screenshots as artifacts. Test features, lines 59–124 and 173–178; operation adapter, lines 1–20 and 118–176. Browser testing overlaps Wingman's TestMaster, while desktop-native interaction and component management broaden that scope. It would be useful for testing Wingman-created desktop products, but availability/OS permissions need to become honest blocked outcomes rather than simulated verification. This assessment did not install or use either component.

Managed worktree and write-conflict execution

Creator-locked worktrees, exact target write coordination, per-run baselines and recorded terminal facts support concurrent engineering and recovery review. Worktree ownership, lines 60–84; write locks, lines 70–138; execution facts, lines 637–649 and 738–769. This goes beyond Wingman's stated workspace layout and would reduce same-repository collisions. It does not make full-access task code unable to write elsewhere, and daemon-local locks need a different authority if agents execute on multiple hosts.

SSH remote workbench with endpoint fencing

The remote relay preserves the same JSON-RPC handshake, cancellation and timeouts, uses strict SSH host-key handling, bounded buffers and version compatibility checks. Active endpoint generations fence stale replies and reset endpoint-bound caches together. SSH relay, lines 5–39; connection context, lines 1–16 and 58–78. That is useful infrastructure for opening Endeavour's development environment from the Mac. Turning it into Wingman's simultaneous shared organization would require federation/shared coordination, rather than just enabling a second UI connection.

Distinctive mechanisms and grounded innovation assessment

These are notable mechanisms in this implementation, not claims of historical novelty.

  1. Expensive reasoning declares intent; auxiliary models compile narrow typed actions. The main model is prevented by interface design from directly running shell/source tools, while the dispatch compiler binds context and validates selected task inputs. This can keep main-model context concentrated on decisions and send cheap, bounded work to other models. Reasoning prompt, lines 42–69; dispatch, lines 1–17 and 60–87. Its limit is compilation and context quality: a mechanical executor cannot recover requirements omitted by the orchestrator, and cheaper compilation adds another failure surface. No measured cost or correctness advantage was established here.
  2. Append-stable request reconstruction with durable compaction events. The renderer keeps historical event bytes stable and represents late-running action results as later records instead of rewriting old tool responses. A compaction event records the floor and handover without destroying original history. Prompt renderer, lines 121–145; compaction, lines 1–10 and 115–123. This serves auditability and provider prefix-cache reuse simultaneously. Cache benefits depend on provider behavior, and summaries can omit nuance; deterministic fallback preserves factual continuity but does not replace a full product knowledge model.
  3. Durable supervisors connected to exact session-turn outcomes. A bot's watch tracks session ID, exact next turn and optional todo IDs; completion produces a deduplicated wake. Rotation seeds in-flight work and kernel facts restore watches/roster/routines/memory index after compaction. Kernel, lines 739–782, 944–1011 and 1348–1384. This enables supervision without repetitive polling. It does not automatically diagnose blockers, and interrupted native work still needs a new decision/dispatch.
  4. Group publication and mention delivery share persisted bookkeeping. Visible replies derive from actual ledger events, with source keys/cursors and peer wakes recorded before dispatch. Kernel, lines 1050–1152 and 1210–1297. It reduces replay duplication and prevents publishing raw tool actions as if they were chat decisions. The claim is limited to the code's deduplication/recovery design; no crash-injection test was run, and it is a single-daemon shared group, not a distributed transactional message bus.
  5. Portable bot identity separated from device execution triggers. Workspace bots carry identity/memory while device routine files and runtime kernel state stay local; duplicate IDs have explicit precedence. Config, lines 1–19 and 470–510. This lets a human share bot definitions without blindly duplicating scheduled jobs. It does not synchronize conversation state or provide agent migration/federated identity across active hosts.

Practical Wingman fit

Directly useful foundations: the bot kernel for standing identity and event-driven follow-up. The session/action/task/native-client execution stack; Markdown knowledge/todos with attributed comments and dependency validation; exact-path write coordination and managed worktrees. The detailed session/task transcript; and SSH transport for remote inspection. These are implemented primitives with substantial source depth, not just roadmap bullets.

Adaptation required: define actual role profiles and separate instances, add project/team/reporting relationships and task assignees, establish ProductMaster/TechMaster discovery/planning policies, and connect task runs/acceptance evidence to durable tickets. Bot creation currently makes a personal assistant. The organization needs controlled team instantiation, lifecycle/retirement and ownership. Sessions cannot mutate todos by design, so worker tracker updates need an explicit authorized path. Native executions run unattended with broad permissions, while Wingman's human decisions need durable case routing and execution-aware enforcement. Context rotation, failure waits and interruption need a clear executive explanation so the human sees whether work is progressing, waiting on quota, blocked or stopped.

Still to build:

  • Telegram ingestion/replies/attachments and Butler routing.
  • Cross-project conversational intake.
  • Standing management and per-project leadership.
  • Proportionate research and clarification records.
  • Product scope/DoD and acceptance delivery workflow.
  • Project-specific management/collaboration rooms.
  • Executive current/recent/next/blocker summaries and semantic agent timelines. A connected directory/portfolio/tracker/chat/agent workspace navigation model.
  • Web/mobile human surfaces.
  • Simultaneous Mac/Endeavour execution sharing one authoritative organization. The existing SSH endpoint switch is useful but does not remove that distributed-coordination gap.

The most promising integration is to treat Wrenyard as a local execution and work-session substrate beneath Wingman's organization, or borrow its durable-bot/watch/ledger mechanisms. Adopting its whole desktop product would still require major organizational UI and backend work. Its broader provider ecosystem is valuable if desired, but Wingman's Codex-only standing-agent requirement should not be diluted into “many model calls” without explicit identity and accountability.
