Fit verdict

Kander is a strong candidate for Wingman's local delivery and recovery substrate, rather than a replacement for its persistent software-development organization. It launches real external coding agents, gives each launched card a recoverable execution identity, coordinates concurrent work through a shared Markdown board, and supplies unusually detailed dispatch, review, integration, and completion evidence protocols. Its optional dsh integration adds an actual project board and interactive agent terminals in a web/desktop host. These are implemented capabilities, not just workflow aspirations.

Its unit of continuity is primarily a task card and execution session, not a standing specialist employee. Agent definitions mostly describe executable adapters, argv, session discovery and review isolation. Orchestration is an LLM session obeying shipped rules and invoking mechanical commands. There is no continuously running portfolio manager or organization service. Telegram/Butler intake, project registry and discovery leadership, agent rooms, an organizational directory, executive summaries and timelines, and true cross-machine shared coordination remain to build. The released protocol explicitly makes the board local to one machine/filesystem (kanban protocol, lines 9–19).

Architecture and actual execution model

The Go executable's entry point calls cli.Run(os.Args) (main.go, lines 1–11). The CLI owns a command registry, including board operations, start, orchestrate, resume, notify, dispatch, coordinator, subscribe, and review. The no-subcommand runner is provided by the terminal UI (cli.go, lines 20–72). Launch registers its implementations and the issue-triage starter at initialization (launch/cmd.go, lines 16–26). This is an executable toolset used by humans and coding agents, not a model inference server.

The main durable store is a main-worktree kanban/ directory shared by that repository's local worktrees. Cards occupy backlog, todo, working, review, done, archived, or trash; allowed transitions are explicit (board.go, lines 16–54). New tasks are directory cards with spec.md; SIZE determines small/large semantics, independent of physical directory form. Card fields include owner, external CLI session reference, terminal address, timestamps, task group, branch and result. Contract sections include goal, user decisions, expected outcome, acceptance criteria, threat model, out of scope and discussion (template.go, lines 19–68). The task creation implementation allocates the dated ID, checks uniqueness and stages the directory under an exclusive board transaction (move.go, lines 11–64).

This is more than editable Markdown. Snapshot carries an optimistic revision; Version also pins execution fencing information. Transactions fix a lock set, stage multiple document/control changes, publish a prepared redo record, then apply it. A publication failure leaves explicit recovery work; readers do not silently repair it. Once a redo intent exists, publication follows a non-cancellable completion protocol (transaction.go, lines 15–91 and 100–163). The rules distinguish controlled update from direct file editing and require explicit init recovery for interrupted publication (kanban protocol, lines 113–130). These guarantees apply to cooperating tools, not arbitrary programs rewriting the files.

Start resolves the card, its task-size execution settings and any pins, prepares a terminal backend, locates the executable, allocates or discovers its session, writes a UTF-8 task file and builds argv. It records a start attempt before launching, then persists the terminal location and discovered session or settles failure (start.go, lines 24–187). The external coding CLI performs planning, tools, edits and testing. Git worktree creation, dependency scheduling, integration and many policy decisions are instructions for the executing/orchestrator agent. The start command itself is not a complete deterministic delivery scheduler.

Terminal control goes through a capability-based Backend: create container, run command, session marking/reporting, pane facts/output, text delivery, reverse identity lookup, focus and close. Direct foreground/console execution and terminal containers have deliberately different capabilities (terminal.go, lines 29–60 and 161–203). Embedded declarative backends cover herdr, herdr-core, luvus, tmux/tmux-session and dsh; definitions can be extended without making launch logic build terminal-specific commands. The implementation boundary matters: a live terminal may expose a rich coding CLI, but Kander does not thereby acquire a structured tool-call/edit/test model of its own.

The optional Node dsh plugin maps dsh workspaces to their Git main-worktree boards, executes kander list --json --agent-status asynchronously, and starts tasks through kander start --launcher dsh (boards.js, lines 61–92 and 119–155). Its host owns pane multiplexing, input/output subscription and carrier status (host.js, lines 13–107). The host application supplies authenticated web routing; Kander's plugin opens no independent network port. This optional integration is a useful interface layer, but requires the external dsh environment.

Agent definition, creation and lifecycle

What is an agent here?

There are four distinct concepts. An execution-agent definition is an adapter for a coding program. A card is an assignment/contract and its work state. An execution record is one claim/start/takeover/recovery cycle on that card. An external CLI session is the conversation/runtime that actually uses tools. Reviewers are separate bounded CLI invocations with role prompts. An orchestrator is another interactive coding-agent session, instructed to coordinate a plan, but it owns no card. None of these automatically creates a durable person with a role, project and organizational relationships.

AgentDefinition is explicit about this boundary: it records Path, ProcessName, Dialect, Args, Session, PromptDelivery, Review, ExitCommand and program-status reporting. A custom map key becomes the stable name stored on cards; missing fields inherit appropriate dialect defaults (agents.go, lines 15–56 and 110–182). A user could name a wrapper backend-coder, but Kander would still see an executable adapter, not infer a backend responsibility or team relationship. Its session policies include generated/none IDs, preallocated IDs and discovered/hooked sessions; session file declarations can resolve a path identity into a true session ID (agents.go, lines 44–88; session.go, lines 89–107).

Creation begins with new, which stages a contract in backlog, or with issue import. Creation does not start an agent. A card must become ready, pass the todo contract gate and then be picked/started. RequiresCardReview requires a record for large or grouped cards, but explicitly says the tool checks the line, while reviewer independence remains a human/agent duty (gate.go, lines 3–15). The shipped intake module offers current-session self-execution, separate executor/orchestrator handoff, backlog-only creation, direct execution without a board, or plan revision. These are workflow rules, not an autonomous product-discovery engine (intake rules, lines 23–40).

Identity, launch, permissions and tools

A launched card gets OWNER (the adapter name), SESSION (adapter plus external session reference) and WINDOW (backend-specific address). Multiple codex owners are distinguished by task/execution/session IDs, not by a directory of named employees. The execution ledger separates pending, running, unresolved, rolled-back and handed-off records; immutable transitions account for owner, session, window and cycle changes (execution.go, lines 22–125).

Start performs validation and resource resolution before claiming wherever possible. It writes a task-file instruction, persists a pending start, launches, discovers/records identity and confirms success. A failure after launch is not casually treated as “nothing started.” When an executor may exist or cleanup cannot be proved, Kander preserves the card/container and returns started-unresolved (exit 3). Adoption or takeover must then explicitly settle the situation. An ordinary failed start can roll back only when there is no executor evidence and cleanup succeeds (start.go, lines 130–187; settle.go, lines 14–45, 48–83 and 120–154). This is a valuable protection against duplicate executors following an uncertain launch.

Tools and sandboxing mostly belong to the selected CLI. In this checkout, embedded Codex start/resume argv includes --dangerously-bypass-approvals-and-sandbox, whereas review uses exec, --sandbox read-only, --ephemeral, a private CODEX_HOME, and a last-message output file (codex.json, lines 5–67). Therefore ordinary worker launch is not a Kander-enforced per-role capability sandbox. Wingman adopting these adapters should make the execution permission policy an explicit integration decision. Rules and epoch tokens govern cooperating agent behavior. They are not protection against a malicious local user or fully privileged worker.

Routing, concurrency and scheduling

Execution selection uses task size, configuration and optional card-level executor/reviewer/model/effort pins. Terminal placement is delegated through the backend's capabilities. notify routes by task identity, repairs missing session information when possible, probes the target, and delivers an instruction to read a message file; busy or uncertain identity must not simply trigger another session. Legacy fallback can native-resume when safe and not dispatch-bound (notify/command.go, lines 16–74 and 85–159).

There is no central queue of autonomous standing workers. An orchestrator session is launched from the large execution tier with plan notes and card/group references. The command checks backlog/todo readiness and complete group expansion but intentionally writes no board state. It also records no card session/window identity for the orchestrator (orchestrate.go, lines 44–151 and 154–211). The LLM follows rules to start ready members, inspect overlapping files, release dependencies only after delivery is actually received, and arrange reviews and integration. This enables concurrent specialists but depends on an alive, rule-following orchestrator. TaskDependenciesOf resolves in-group, external-card and external-group prerequisites. It is a validator/resolver, not an always-running scheduler (deps.go, lines 23–91).

The separate subscribe process polls committed state and emits JSONL events with subscription ID, sequence, task revisions, membership version/completeness, dispatch summaries and liveness observation identity/age/validity. Its default heartbeat is 900 seconds; orchestrator rules require 600 seconds (subscribe.go, lines 20–80; orchestrator sessions, lines 12–26). The heartbeat wakes a consumer; follow-up reasoning is performed by that orchestrator, not by the event producer. A new snapshot supports restart without relying on an in-memory event sequence. TUI runtime observation is a separate five-second display mechanism and must not be confused with supervisory reasoning (agent_status.go, lines 17–109).

Continuation, interruption, failure and recovery

Native resume is limited to working/review cards and a resumable external session. Supplying an explicit replacement agent selects takeover and allocates a new session, instead of pretending another executable can resume the old conversation (commands.go, lines 107–217). A self-claimed card has no executor session; its recovery path is claim/reclaim/recover evidence rather than ordinary notify/dismiss. Direct foreground/console identities receive special native-resume refusals. The presence of a generic resume command does not mean every backend/session supports it.

Interruption has several levels. External coding terminals expose that CLI's own stop/input behavior. Subscription APIs carry cancellation. Review installs SIGINT/SIGTERM handling and collects its process tree. Board publication, once its redo intent is durable, completes under its explicit recovery semantics rather than aborting halfway. These are different guarantees. There is no unified Wingman-style goals/budgets and conversation interruption controller.

Review runtime execution creates a private temporary directory, snapshots applicable task context, writes a read-only review contract, collects stdout/error/output and process evidence, and checks that the target worktree was not changed. It treats failed process collection or changed target state as failure (review.go, lines 147–164; execute.go, lines 16–42 and 54–175). Its safety posture is per adapter and platform. The assessment does not infer universal OS isolation from an inspection prompt.

Completion, acceptance and retirement

Task completion is evidence-aware. validateTaskReview requires the execution's review plan, preserves obligations across cycle changes, requires sealing and coverage, detects unplanned/stale runs, and checks closed-batch target/conclusion/evidence bindings. Pending obligations reject completion (review_gate.go, lines 48–170 and 244–288). Review plans can explicitly mark roles N/A, so this does not mean every card must run every reviewer. The Kander repository's own AGENTS.md disables Security for work on itself; that repository exception should not be mistaken for the released product's only possible review configuration.

The engine still relies on agents to write truthful implementation/test records and judge the user-level result. The ordinary done target validator checks RESULT: completed and a non-placeholder summary for a small card or readable nonempty report.md for a large card. It does not itself require every acceptance checkbox to be checked (document.go, lines 246–269). The acceptance-freezing test reaches done after an explicit N/A review fixture while its original checklist remains unticked (acceptance_ticks_test.go, lines 99–128). A closed review chain is therefore not independently observed product acceptance. Group rules add actual Git containment/delivery checks and integration ordering. They cannot replace Wingman's integrated functional acceptance role.

done retains a recent card. dismiss is restricted to done/archived, resolves the executor identity and terminal topology, sends its exit command and closes the verified container (dismiss.go, lines 28–93 and 96–147). Card archiving is terminal, stores the outcome/decision, and can prune settled review/execution/dispatch control evidence. Pruning uses an archive-time durable intent and per-card receipts so an interrupted cleanup can resume without calling deliberately removed originals corruption (prune.go, lines 17–68 and 84–105). Wingman would need an explicit retention policy before treating these records as permanent organizational memory. Board-free chat/orchestrator sessions are outside card liveness/dismiss coverage and require separate container cleanup.

Coordination mechanics and a source-grounded task trace

Kander has two communication layers: human/agent prose in cards and terminal messages, and machine-verifiable protocol records. Cards provide task contracts, discussion, implementation updates and references. Task groups/prerequisites describe dependencies. Subscriptions announce observations. Durable dispatches bind fix/sync/wrap-up work to a stable ID, execution epoch, message hash, base commit and optional evidence. A dispatch moves through prepared, delivery-unknown, accepted, completed, failed or cancelled; transport success never implies acceptance (dispatch.go, lines 15–82 and 109–129).

Acceptance is the receiving agent's ID/epoch-bound move into working. Completion is a bound move into review or done with a full delivery commit and, where applicable, disposition/integration evidence. The receipt and relocation are published in one transaction. An identical receipt is replayable, while a conflicting one is rejected (dispatch_receipt.go, lines 31–118). A timeout does not license inventing a new logical request or resetting its original confirmation deadline.

The coordinator checkpoint adds a separate fence over the consumer's progress cursor. It records members, revisions, execution cycle/transition positions, expected dispatch identity, pending confirmation/delivery/wrap-up and review references. Its authority token controls checkpoint writers only, not task execution, integration or cleanup (coordinator.go, lines 13–121). A bad member can remain blocked at its last good mirror while other members advance. This is recoverable coordination state, not a transcript or a replacement for source-owned receipts and review originals.

The following trace follows the implemented multi-card handoff path. It is a representative code trace, not a task run performed during this assessment:

  1. A user confirms a multi-card plan and chooses separate execution. The intake rule instructs the creating agent to create complete card contracts, preserve plan decisions and pass ordered references plus notes to kander orchestrate (intake rules, lines 33–38). New card creation is a locked transaction. A prose plan alone creates no executor.
  2. StartOrchestrator loads the named cards, expands groups, rejects duplicate/already-started references, validates backlog readiness, picks an execution adapter, writes the handover task file and launches one board-free coordination session (orchestrate.go, lines 48–151 and 154–211). The Go command does not automatically execute the plan after returning.
  3. That LLM session reads the group rules, verifies outside prerequisites, claims a full-member coordinator checkpoint and starts ready cards. Each Start records pending ownership/session identity before starting its CLI, then confirms the actual result (start.go, lines 80–187; orchestrate-start, lines 90–97). Separate ready cards become separate CLI sessions, while overlapping/dependent cards wait.
  4. A worker completes its branch/tests, records delivery and enters review. The orchestrator's subscriber wakes it. The orchestrator verifies the recorded SHA against the real task branch and receives it into the group branch before releasing a dependent task (orchestrate-start, lines 48–55 and 75–80). The review column alone is explicitly insufficient evidence of group reception.
  5. If group drift requires a rebase or a reviewer identifies a fix, the orchestrator prepares one logical sync/fix dispatch and notifies the original worker. Durable acceptance/completion receipts distinguish a delivered instruction from work actually begun and a branch actually re-delivered (dispatch.go, lines 34–82; dispatch_receipt.go, lines 62–118). A restarted consumer reconciles the current snapshot with those receipts rather than replaying presumed historical transitions.
  6. Review runs produce retained originals/report evidence. The plan/batch closure and Git checks establish what was reviewed/integrated. Wrap-up binds the final delivery and integration evidence to done. The completion gate rejects outstanding plans/batches/dispositions (review_gate.go, lines 244–288). The orchestrator reports final states, integration results and unresolved blockers in its own session. There is no automatic Butler/Telegram handoff.
  7. A blocked worker is inspected on heartbeats using both runtime facts and pane/card evidence. The rules permit bounded in-contract answers and same-ID reconciliation, but route scope changes, takeovers and unresolved issues to the user while other cards continue (orchestrator sessions, lines 15–41). This is useful technical supervision, without persistent rooms or a management hierarchy.

Major additional capabilities beyond Wingman's stated product

Recoverable local transaction and execution protocol. Wingman describes lightweight shared tickets and continuity but does not prescribe multi-file redo transactions, execution-cycle chains, receipt-based dispatch or checkpoint fencing. Kander supplies these concretely. The value is preventing conflicting writers, duplicate launches after uncertainty, stale-owner writes and false completion after coordinator restart. Integration would require all relevant Wingman writers to use the protocol; simply placing ordinary Markdown tickets beside managed files would bypass its guarantees. Same-host file locks and local paths make a distributed translation a separate design task.

Independent review runtime with retained evidence and completion gates. Kander supports configurable reviewer adapters/models, task-context snapshots, immutable run originals, role conclusions, author dispositions, plan/batch chains and Git-bound closure checks. The runner supplies process cleanup and worktree-unchanged checks as well as prompts (review.go, lines 59–164; execute.go, lines 89–175). This is useful for auditability and incremental repair review, beyond a generic TestMaster assignment. It adds storage/operational complexity and needs explicit applicability and retention policies. It complements functional product tests rather than establishing them by itself.

GitHub issue intake and result reconciliation. Imports preserve a schema-versioned issue/comment snapshot under source/, canonical repository/source identity and a binding to one card; remote title/body data is separated from managed contract structure (import.go, lines 19–103 and 129–195). Result proposals assess every card acceptance item as met/unmet/unknown, cite recorded verification commands and require completion-document evidence for full resolution. Publication records uncertainty before calling the provider and reconciles matching observed comments; issue closure requires a fresh target-bound user decision/reference and refuses blind retry or old consent reuse (result_sync.go, lines 16–100, 130–218 and 221–285). This is a valuable alternate engineering intake/output channel, but does not replace conversational multi-product discovery or actually execute the cited verification itself. Wingman would need to connect issue identity to its product registry and preserve the issue text's untrusted-data boundary.

Interchangeable execution programs and terminal backends. Instead of assuming Codex-only sessions, the embedded agent inventory supports multiple coding CLIs plus custom adapters, while terminal capabilities describe what liveness, identity, focus and recovery operations are possible. The dsh plugin supplies an optional board-plus-terminal web surface with output streaming, input ordering and resize handling. This gives Wingman a practical adapter pattern and local operator interface, at the cost of maintaining each CLI's session/permission/output contract and accepting weaker visibility on limited backends. dsh's carrier mechanism handles local host-process contention, not remote-machine routing.

Distinctive mechanisms and grounded innovation

  1. Uncertainty is preserved as state. Launch has a third outcome, started-unresolved, and delivery has delivery-unknown. An API error is not treated as proof that the external action never occurred. This enables safe operator recovery without blindly duplicating work. The limit is deliberately conservative availability: unknown evidence may require human adoption/takeover or diagnosis rather than an automatic retry (settle.go, lines 14–83 and 120–154; dispatch.go, lines 15–25).
  2. Transport, business acceptance and delivery are separate facts. Stable dispatch intent, payload hash and epoch bind receipt-producing state changes. The same ID can be retried without creating a new deadline/authorization; completion records the exact delivery SHA. This directly addresses terminal message delivery's ambiguity. It relies on cooperating receivers using controlled commands; terminal output alone still proves no business completion (dispatch.go, lines 34–82 and 120–129; dispatch_receipt.go, lines 31–118).
  3. Recovery consumes producer-owned evidence rather than promoting events into truth. Coordinator checkpoints retain explicit expected rounds and source references; subscription events carry revision/membership/observation validity. A changed column or a heartbeat cannot silently become a completed dispatch. Per-member blocking helps the rest of a group progress. This is a useful design for an LLM coordinator because it constrains recovery reasoning with machine checks, but it does not remove the LLM's scheduling/integration judgments (coordinator.go, lines 21–121; orchestrate-start, lines 90–97).
  4. Review closure is a durable obligation graph. Plans bind members/cycles and batches; closure verifies reviewed target, role conclusions, disposition state and unchanged evidence. A new execution cycle or stale report cannot simply borrow an old pass. This makes “done” more meaningful than a label, while retaining explicit N/A and user-decision paths. It remains a code/review evidence protocol rather than automatic proof of product quality (review_gate.go, lines 48–170 and 244–288).
  5. Bounded composite protocol exploration. The repository includes a state-model test that drives real board operations from seeded lifecycle/dispatch/review situations and searches for dead ends within explicit bounds/allow lists. Seeds include unresolved starts, stale runs, dropped review obligations, old takeovers and group recovery (model_test.go, lines 3–6, 19–24 and 40–118). This is valuable engineering evidence for protocol composition. It is bounded testing, not an exhaustive correctness proof or an assessment-time test run.

These are distinctive mechanisms visible in this checkout. This assessment makes no historical priority or industry-wide uniqueness claim.

Practical adoption path and remaining gaps

Use directly, within a local delivery boundary:

  • The card contract and controlled update API.
  • Real CLI execution adapters.
  • Task/session/window association.
  • Dependency/group vocabulary.
  • Subscribe snapshots and observed liveness.
  • Guarded message delivery.
  • Uncertain-launch recovery.
  • Review/evidence completion gates.
  • Optional dsh board/terminal inspection. They could support Wingman's TechMaster-to-worker delivery loop on either individual machine.

Adapt before making them organizational foundations:

  • Give profiles and agent instances first-class identities separate from executable names and card ownership.
  • Map project/team IDs into task/session records.
  • Route human decisions through Butler while retaining exact decision/authorization references.
  • Keep product specifications and acceptance scenarios above card-level contracts.
  • Translate subscriptions/receipts into executive summaries with links.
  • Make permissions, reviewer applicability and retention explicit. Persistent chat and orchestrator sessions need lifecycle tracking because Kander deliberately leaves them outside the card ledger.

Build rather than configure:

  • Telegram intake/routing.
  • portfolio registry.
  • ProductMaster/TechMaster standing leadership and discovery cycles.
  • direct retained agent rooms.
  • directory/relationship views.
  • per-agent summary timelines.
  • structured usage/artifact/workspace controls.
  • autonomous portfolio supervision independent of an open orchestration session.

A shared Mac/Endeavour system needs a networked coordination and execution-host layer. The current local board must not simply be mirrored with Git or symlinks: both its protocol and safety assumptions prohibit that approach. dsh's two-host carrier does not solve this gap.

The main tradeoff is favorable if Wingman wants a rigorous local engine under a new organization layer. It is unfavorable if the aim is to obtain most of the organization by installing Kander: the majority of Wingman's human relationship, persistent team and knowledge-discovery behavior would still be new product work.

Relevant tests were inspected, not executed:

  • launch_test.go, lines 200–250: fake CLI/terminal boundary, task-size agent selection and persisted owner/session/window.
  • orchestrate_test.go, lines 57–115: ordered task handoff, prompt/container launch and no board state writes by the launcher.
  • dispatch_crash_test.go, lines 59–140: sender killed before/after send, preserved delivery uncertainty and same-ID reconciliation without changing the deadline/authorization.
  • coordinator_test.go, lines 33–100: checkpoint observation construction, blocked-mirror assertions and concurrent claim/fencing setup.
  • review_gate_test.go, lines 64–145: explicit N/A fixture closure versus a missing plan rejected at done. These structural fixtures explicitly do not prove real Git execution.
  • acceptance_ticks_test.go, lines 99–128: done freezes checklist changes, but reaching done does not itself require checklist completion.
  • subscribe_dispatch_test.go, lines 86–115: fast accepted/completed wrap-up observable from a restarted initial snapshot without a historical working edge.
  • model_test.go, lines 19–118: explicit bounded state exploration and seeded lifecycle/review/dispatch combinations.
  • dsh routes tests, lines 27–135: fake host/board setup, board/start routing, non-carrier refusal, ordered terminal input, resize and streamed replay setup.

Absence findings are based on searches across cmd, internal, shipped rules and non-vendored dsh integration sources for Telegram/Butler/management roles/rooms, portfolio, timelines, cron and remote-host/SSH coordination. The review then inspected command registry, agent definitions, board location/snapshot, TUI chat, subscriptions, terminal backends and dsh carrier/view. The only relevant SSH matches were GitHub remote identity parsing. The only substantial periodic supervisor is the rule-driven orchestrator consuming subscriptions. The board's explicit local-only contract is stronger evidence for F17 than the absence of a README claim.

No runtime claim is made about actual external CLI compatibility, model availability, terminal behavior, Windows isolation, dsh authentication, live GitHub operations or completion quality. Those boundaries depend on external programs/platforms and were not exercised. Confidence is high for the architectural fit/gaps and the existence of the local protocols; operational robustness remains a candidate for a separate authorized runtime evaluation.
