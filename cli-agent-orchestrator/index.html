CLI Agent Orchestrator (CAO) assessment

Repository: https://github.com/awslabs/cli-agent-orchestrator
Local checkout: research/cli-agent-orchestrator/repo
Revision inspected: 8b962ee515caf9351838c1805f4cfef969e04dda
Package version: 2.5.4 (package metadata, lines 1–5).
Assessment date: 2026-11-05.
Basis: Wingman purpose and the complete assessment guide. Source inspection only; no dependencies installed, services launched, provider conversations run, or checkout files changed.

CAO is a strong candidate for Wingman's coding-agent execution and coordination substrate, but a substantial organizational application must sit above it. It launches real independent coding CLI processes, supports heterogeneous specialists, asynchronous assignments, synchronous handoffs, durable inboxes, scoped discovery, local worktree isolation, actual remote-node placement, scheduled flows, workflow recovery, and useful operational interfaces. Those are considerably more than personas inside one model conversation.

Its native unit is a terminal-bound CLI instance, grouped into a terminal session. A named profile is reusable configuration. It is not a standing employee with its own durable organizational history. Projects are working directories, grouping metadata and memory identities rather than a portfolio of products with intake, ProductMaster/TechMaster ownership, shared tickets, rooms and acceptance criteria. The bundled coding supervisor's organization is principally a prompt directing a developer/reviewer loop. Telegram/Butler, the product discovery process, persistent role-instance identities, ProjectTracker, organizational chat, and meaningful executive briefings remain Wingman work.

Architecture and execution model

The installed commands select four distinct control surfaces: cao (Click), cao-server (FastAPI), cao-mcp-server (tools used inside running agents), and cao-ops-mcp-server (operator integration); see entry points, lines 130–134. The browser application is React source in web/, with xterm for the live terminal. These are clients of the same server rather than alternative agent runtimes.

The concrete execution chain is: a CLI/UI/MCP operation calls an HTTP route; session_service.create_session delegates to terminal_service.create_terminal; terminal creation allocates backend resources, records a terminal, creates a provider adapter, and initializes the provider CLI. Session creation, lines 71–176, forwards provider, profile, working directory, tools, initial message, optional provider conversation ID and worktree choice. Terminal creation, lines 2852–3061 and 3117–3299, creates a backend session/window, writes registry facts, then creates and initializes the provider. The default tmux backend, lines 34–81 and 105–143, actually delegates session/window/pane creation to TmuxClient. It does not simulate agents in an in-process LLM loop. Its input methods send keys to the terminal (lines 160–181). There is also an alternate herdr backend, so terminal mechanics and provider adapters are separate interfaces.

Provider adapters own native CLI flags, system-prompt delivery, initialization, output interpretation and status detection. For Codex, the implementation, lines 1647–1900, constructs the codex command, chooses --profile versus --yolo, injects developer instructions, and maps MCP settings. Completion and permission detection involve terminal-frame parsing, not a uniform typed provider SDK: Codex tracks a dispatch and its pre-send screen baseline (lines 1495–1597), and detects native footer/prompt evidence. This retains native coding-tool behavior but creates version-sensitive integration work and an important distinction between “the CLI finished a turn” and “the product is accepted.”

Persistence is divided among SQLite, files, terminal processes and provider storage. Database models, lines 177–317, store terminal identity, parent/caller, configuration and inbox state; lines 1034–1155 add project aliases, outcomes, flows, handoff results and idempotency keys. Workflow run/step/event journals are separate tables (lines 2141–2405). The memory service, lines 379–398, uses Markdown wiki content plus SQLite metadata. tmux preserves a live CLI independently of a browser connection. It does not by itself recreate a dead provider conversation after machine loss.

At server startup, the lifespan code, lines 1592–1815, initializes/reconciles state and starts terminal-output consumers, status monitoring, inbox delivery and scheduled flows. Output reaches an event bus and log/status consumers; inbox readiness is derived from provider status. The inbox consumer, lines 90–158, runs delivery independently per terminal, coalesces readiness events and serializes each receiver's delivery to avoid interleaved or duplicate pastes. This is operational coordination infrastructure, not a product-level task state machine.

Agent definition, creation and lifecycle

What an agent actually is

An AgentProfile defines reusable frontmatter plus Markdown instructions. The model, lines 35–85, distinguishes name, description, provider, body/system prompt, role, tool policy, delegation policy, advertised skills, capabilities/tags, MCP servers, resources, model and permission mode. Provider-specific fields follow: Codex named configuration and inline TOML overrides (lines 88–108), Claude/Kiro effort knobs and other provider options. role changes defaults and guidance. It does not instantiate a person or create a management position.

A live Terminal has a generated eight-hex ID and a backend session/window. It records the provider, optional profile/model, caller, effective/delegable tools, group, description, metadata, lifecycle facts and status. See the terminal model, lines 10–22 and 126–229. Multiple terminals can share one profile. A session groups backend terminals and their environment. Provider conversations and products have different identities. The terminal is the independent execution instance. Its prompt defines behavior. Workflow runs and steps add separate durable units of work.

The grouping field is intentionally general-to-specific prefix metadata. CAO explicitly leaves its meaning to consumers (terminal model, lines 172–185). Wingman could encode organization/project/team here, but that would be its schema. Identity must also be separated from a profile: agent-scoped memory uses profile-scoped storage (memory path rules, lines 752–786), so two workers with the same profile do not automatically receive independent personal memories.

Defining and launching instances

Profiles can be installed/created/updated through the profile API, lines 2886–3345, with validation/template support. The search service, lines 1–14 and 23–25, indexes name/description/capabilities/tags rather than the full prompt and rebuilds its corpus each query. This supports a supervisor discovering suitable specialist definitions, not automatic team staffing against a product plan.

cao launch resolves tools from explicit flags and profile/role defaults. It resolves a delegation ceiling, selects a provider and sends the launch request (launch command, lines 256–315). Session creation, lines 139–162, forwards the effective parameters into the terminal service. Terminal creation optionally prepares an isolated Git worktree (lines 2689–2705). It creates a backend session/window under lifecycle ownership and inserts terminal registry facts (2852–3061). It then builds the provider (3139–3150). Initialization runs synchronously or through a deferred task (3158–3196). Creation returns a terminal backed by a process.

Optional ephemeral profile creation is a distinct, gated surface (MCP implementation, lines 1759–1930). The orchestration claim code, lines 856–925, requires a creator-owned claim for reserved ephemeral targets and can return an already-recorded terminal on keyed retry. It is useful for bounded task-specific agents, but it is not an unrestricted durable organization designer; remote ephemeral placement is refused by the assignment path (lines 2699–2701).

Tools, authority and execution isolation

The native provider remains responsible for filesystem edits, commands and its own tools. CAO adds orchestration/memory/workflow MCP tools, scoped catalogs and role/tool mappings. The effective child capability must be capped by the recorded parent delegation ceiling; remote placement checks that the other node supports this policy before it sends the ceiling (remote placement, lines 2534–2547). Explicit messaging targets are also checked, rather than allowing arbitrary terminal IDs (lines 2898–2907). This is a meaningful capability boundary around coordination.

Those controls do not imply identical enforcement of native tools across providers. Codex launch, lines 1647–1732, explicitly uses --yolo unless an applicable codexProfile preserves the native sandbox/approval policy; unrestricted * forces yolo, and narrower tools also add prompt constraints. Therefore a Wingman deployment must select provider-native permission configuration deliberately. “CAO allowed tools” is not a uniform OS sandbox.

The default workspace is shared. Opting into worktrees, lines 1–20 and 100–123, creates .cao/worktrees/<terminal_id> and branch cao/<terminal_id> from the repository's HEAD. This isolates concurrent edits, not credentials, machine access or external side effects. There is no automatic merge-back pipeline. On cleanup, force-removal discards uncommitted/untracked worktree content but safe branch deletion leaves unmerged commits recoverable (lines 148–185). Wingman must arrange committing, integration and verification before worker retirement.

Routing and concurrency

assign creates a worker and returns quickly while server-owned initialization/task delivery continues. The implementation, lines 2679–2687 and 2767–2801, explicitly decouples initialization so several assigns can initialize concurrently. caller_id stores the creator relationship for automatic replies. handoff uses the shared run-step substrate to wait for a result; orchestration helpers, lines 1605–1844 and 1996–2454, handle blocking execution, transport ambiguity and cleanup/result reporting. These are execution semantics rather than a hierarchy of organizational accountability.

The inbox, lines 65–158, serializes one receiver while permitting other receivers to proceed. Readiness events trigger delivery. The service also reconciles orphaned messages (lines 547–560 onward). Delivery is not synonymous with agent acceptance: after_dispatch means only that the immediate attempt has been decided, explicitly not acknowledgment (lines 180–186). There are submit-confirmation/redelivery paths for swallowed Enter or stale terminal state. Wingman would still need explicit task acknowledgment/completion records above message transport.

Remote assignment creates a session on the selected CAO server. It resolves that server's profile and sets CAO_CALLBACK_URL/CAO_CALLBACK_TERMINAL_ID to route replies back. See the remote implementation, lines 2473–2505 and 2555–2588. The remote filesystem interprets cwd (2558–2562). Assignment does not copy code or create project records. target_host and local worktree provisioning cannot be combined (2520–2528). Callback context lives in the process-local session environment. A server restart can lose it (terminal model, lines 146–155). Wingman's Mac/Endeavour continuity must account for this limit.

Persistence, scheduling and resumption

A running terminal can outlive the viewing UI. The browser closes only its socket and xterm instance (terminal view, lines 113–119); backend/provider lifecycle is separately managed. SQLite and output logs permit rediscovery. They do not guarantee that every provider's internal conversation can be reconstituted. The public resume launch option specifically promises Claude Code --resume (launch, lines 220–224). No equivalent general Codex conversation restoration was established in the inspected launch path.

Workflow continuity is stronger than ordinary terminal continuity. The YAML engine, lines 1342–1465 and 1573–1706, reconstructs state from the journal and resumes from unfinished steps while preventing overlapping live drive loops. The Python script tier starts a subprocess (script runner, lines 1356–1570), whose shim, lines 64–158, sends run ID, generation and explicit step identity over HTTP. On resume the script executes top-to-bottom and stored agent-step results may be replayed after fingerprint/provenance checks. Arbitrary Python side effects between step calls are not automatically rolled back or deduplicated.

Scheduled flows, lines 220–231 and 284–388, advance their next schedule before execution, optionally run a script, render a prompt, skip busy conductors, and otherwise recycle/create a named flow session. The daemon, lines 236–254, checks due work every minute. This can run a configured “inspect projects” supervisor, but CAO does not supply ProjectMaster's domain-specific inspection/follow-up behavior, and recycling flow sessions is different from waking the same durable employee conversation.

Interruption, failures, recovery and completion

Human steering is available through ordinary input, key events and graceful exit/delete actions (agent UI, lines 93–139). Native dialogs have a separate explicit answer_user_prompt path (MCP tool, lines 1062–1077). Terminal error types, lines 25–106, distinguish a live CLI waiting for a human from an exited provider or failed initialization; orchestrated task delivery must not become an accidental menu answer or shell command.

Deferred initialization failures are persisted rather than silently turning into an idle worker. Recovery implementation, lines 4022–4218, revisits interrupted ownership and initial deliveries; failure sidecars preserve outcomes across database-write trouble. These mechanisms protect transport/lifecycle truth, not the semantic success of an implementation. The recovery tests, lines 29–79 and 83–105, explicitly model unreadable rows, preserved prior failure, restart interruption and capped retry backoff.

For workflow steps, agent execution, lines 436–594 and 813–919, waits for provider completion, extracts output and handles cancellation/teardown. YAML retries, lines 738–969, retry run failures, separately handle output-schema reprompts, and apply halt/continue policy. Cancellation sets a flag and event to interrupt the in-flight wait (1259–1284), rather than only waiting for the next step boundary. This should not be confused with undoing already-completed edits or external actions.

Script-tier recovery uses a deliberately conservative replay decision, lines 19–73 and 129–141: replay/execute/diverged/decision-required depend on identity, stored envelope, outcome and declared recovery policy. Human-authorized skip/rerun does not bypass all provenance checks. The reconcile policy currently behaves like idempotent re-execution because generic external reconciliation is deferred (52–60). Approval gating is separate: the gate, lines 188–234, checks the frozen plan identity, distinguishes unavailable identity/store from absent approval, and refuses execution when needed.

Completion in the ordinary agent layer means the adapter observed the end of a CLI turn or the worker sent a result. A workflow can additionally validate structured output, but completed transport/workflow state is not proof that tests passed or requirements were satisfied. The shipped supervisor's developer/reviewer cycle (profile, lines 37–50) is an instruction to the LLM. There is no mandatory product acceptance state machine. Wingman must supply integrated verification, acceptance evidence, delivery assessment and “stop until further request” policy.

Retirement is explicit for long-lived assignments: the returned assignment message asks the caller to delete its worker (orchestration, lines 2788–2797). Handoff/run-step paths can tear down workers after successful extraction, while errors expose terminal IDs for inspection. Teardown, lines 6616–6662 and 6805–6876, removes runtime resources before registry rows and retains retry handles when cleanup is uncertain. Exact identity checks for failure tombstones avoid killing a later session that reused the same name. Deletion is lifecycle cleanup, not an archive of a persistent organizational employee.

Coordination trace: a supervisor assigns coding work

The following is a source-traced request path, not a live run conducted for this assessment.

  1. The human launches code_supervisor in a product directory. CLI permission/provider resolution, lines 256–315, and session service, lines 139–176, produce the initial supervisor terminal. The profile, lines 28–33, instructs the supervisor to put task descriptions in files and delegate coding to developer.
  2. The supervisor calls MCP assign(agent_profile="developer", message=...). MCP registration, lines 647–691, checks its tool authorization and forwards to _assign_impl; assignment implementation, lines 2716–2786, resolves caller identity, adds callback instructions where appropriate, and requests deferred creation. Parent tools/cwd/provider are read in _create_terminal (1034–1060 onward), with profile overrides and delegation constraints applied.
  3. The server allocates a new window/process and database row, returns the terminal ID, then initializes and sends the accepted initial message. Creation, lines 2852–3196, and deferred initialization, lines 5019–5086, separate admission from provider readiness. The supervisor can assign another specialist without waiting for the first CLI to finish its startup.
  4. The developer uses native CLI coding tools. Its progress is visible as terminal output/status. No ticket record appears automatically: the supervisor's task file is the shared assignment artifact, while the terminal row stores execution metadata.
  5. The developer calls send_message(message=...) without receiver ID. Reply routing, lines 2832–2879, chooses its recorded caller or cross-node callback supervisor. An explicitly named colleague is allowed only through the target binding/discovery rules (2898–2907). Inbox route, lines 9017–9094, records the message and attempts delivery; consumer, lines 90–158 and 160–218, delivers when the supervisor can receive it. This wakes interaction through ordinary provider input rather than a room subscription model.
  6. The supervisor sends the code to reviewer, discusses changes via messages/files, and repeats as the profile requests, lines 37–50. The operator may inspect the receiver inbox or open its real live terminal, lines 47–103. Questions can surface through native CLI prompts, but no Butler carries them to Telegram.
  7. When the result is satisfactory, the supervisor reports to the user and deletes assigned worker terminals. Cleanup, lines 6856–6876, confirms runtime teardown before deleting registry state. Worktree commits must first be integrated or preserved. The framework does not decide product DoD or create a delivery acceptance record.

For remote execution, step 2 instead reaches _assign_remote, posts to the other node's /sessions, forwards the delegation ceiling, and installs callback environment (remote code, lines 2531–2588). This provides a concrete Mac-to-Linux primitive. A shared filesystem or repository synchronization and shared product/tracker identity remain deployment/application responsibilities.

Major capabilities beyond Wingman's stated product

Heterogeneous provider orchestration. Wingman specifies Codex agents. CAO's provider-aware profile model, lines 40–49 and 88–141, and Codex adapter, lines 1647–1900, support cross-provider staffing with native authentication, model/config choices and provider-specific tool mapping. That could allocate reviewing or execution to other coding CLIs. Integration costs include different status parsers, permission semantics, prompt delivery, availability and resume guarantees. It is not a drop-in uniform provider protocol.

A durable, inspectable workflow runtime with replay and plan approval. Script execution, lines 1356–1570 and 1572–1897, shim identity, lines 104–157, replay gate, lines 19–73, and approval gate, lines 188–234, go beyond Wingman's described coordination records. They can make repeatable delivery operations recoverable and reviewable. Wingman could use this for bounded validation/build/release procedures, but must model external side effects deliberately and keep run identity separate from product/ticket identity. YAML accepts several reserved constructs it cannot execute: the engine, lines 1972–1990, explicitly raises for parallel/loop/guards. Python-authored branching/concurrency is a different, implemented route.

Elastic worker placement. The elastic assign tool, lines 784–931, acquires a broker lease, waits for the worker, passes a broker callback gateway and assigns remote work. complete_assignment first returns the final message then releases capacity (972–1010). This is useful if Wingman expands beyond two fixed hosts. The completion protocol is cooperative: a worker that never acknowledges completion can look like a slow worker; infrastructure/lease cleanup and deployment setup remain necessary. The ordinary target_host API is already useful without adopting the EKS topology.

Cross-session memory, wiki projection and opt-in instruction learning. Memory storage, lines 379–398 and 731–797, supplies inspectable scoped knowledge beyond individual CLI transcripts. Promotion service, lines 1–24, 116–176 and 178–190, can turn recalled agent-scope lessons into a bounded Learned Patterns block with planning/apply separation and opt-in gating. Wingman could carry conventions and lessons across new conversations. Recall count is reinforcement evidence, not measured quality improvement, which the source explicitly acknowledges (lines 3–9); evaluation must precede automated promotion of consequential guidance.

Protocol-level embedding and operational observability. The AG-UI supervisor construct, lines 53–127, folds snapshots/deltas and lifecycle counters; session timeline, lines 33–82, exposes delegation/message metadata. API routes, lines 2161–2679, provide event and AG-UI surfaces; workflow UI supports playback/diagnostics. These are useful building blocks for Wingman's custom dashboards and external operator clients. They carry runtime state and events, so Wingman must add product/task semantics and narrative summaries instead of presenting protocol counters as executive progress.

Pluggable launch decisions. The decision engine, lines 1–47, 54–73 and 133 onward, separates policy checks, decision answers, fallbacks and shadow work; profiles include model/effort/provider knobs. This can experiment with routing a delegation to an appropriate model/effort within policy. It does not solve product prioritization or human business decisions, and should be evaluated as a bounded launch policy rather than autonomous organizational judgment.

Distinctive mechanisms and grounded innovation

CAO's most useful distinctive mechanism is retaining full native coding CLI processes while exposing a common orchestration interface. A worker can preserve its native tool repertoire and authentication, yet another independent model can assign it work and receive an inbox callback. The concrete backend/provider split (tmux, lines 68–181; provider launch, lines 1647–1900) makes this adaptable. Its cost is substantial engineering around TUI status, disappearing processes, modal dialogs, stale output and dropped submission. Codex's dispatch baseline attribution (adapter, lines 1495–1597) shows that the project addresses those failure modes instead of assuming every captured “done” footer belongs to the latest request. This is a mechanism assessment, not a claim of industry uniqueness.

A second strong mechanism is layered execution truth: admission, initialization, initial-message delivery, provider status, workflow step outcome and product success are distinguishable. Terminal lifecycle fields, lines 186–225, persist failure/initial-delivery/incarnation facts, and cleanup, lines 6635–6656, refuses to destroy resources on uncertain identity. That separation is directly valuable for Wingman because a dashboard must not turn an accepted assignment into an apparent accomplishment. It still requires Wingman to create the product-level truth above it.

The script workflow's fingerprinted replay with human recovery decisions is another substantial mechanism. The gate, lines 19–73, checks provenance before equality and refuses changed/unsafe replay rather than quietly repeating an effect. The shim makes replay visible to authors (shim, lines 144–157), including the fact that a replayed terminal ID may no longer identify a live process. Limits are explicit: reconciliation is not a distinct implemented operation, arbitrary script effects remain outside step replay, and recovery declarations do not prove external idempotence.

Finally, delegation authority is transported with work, including remote placement (orchestration, lines 2534–2547), while message targets stay bound to creation/discovery relationships (2898–2907). This provides a useful foundation for a growing organization in which specialists should not automatically inherit their supervisor's unrestricted privileges. Native provider enforcement must still be configured correctly. The Codex yolo path demonstrates why a coordination capability boundary alone is insufficient.

Practical Wingman fit and gaps

CAO could be used directly for launching Codex supervisors/specialists, parallel assignments and callbacks, operator terminal drill-down, scheduled entry points, structured workflow steps, scoped memory, and explicit Mac/Endeavour node targeting. Its profile CRUD and discovery reduce the cost of adding BackendCoder/FrontendCoder/MobileCoder/TestMaster definitions. Existing browser controls provide a workable operations console while Wingman builds its richer views.

The most important adaptation is to introduce stable organizational identity above CAO terminal identity. A Wingman agent instance should retain role, project, team, responsibilities, personal timeline and conversation history while it acquires/replaces terminal sessions. Profile names, backend session names, workflow runs, tickets and organizational agents need explicit separate identifiers. Persist remote callback/host bindings in Wingman records rather than relying only on process-local session environment.

Wingman must build these product capabilities:

  • Intake, a portfolio registry, and routing for new or existing products.
  • Telegram Butler and question/answer correlation.
  • ProductMaster discovery and specification records.
  • TechMaster ticket decomposition and dependencies.
  • A shared tracker with comments and blockers.
  • Management and project room histories.
  • TestMaster integrated acceptance and deliverable assessment.
  • Executive current/recent/next summaries linked to original evidence.

Metadata groups and inboxes can carry references to these records. Wingman still needs durable schemas and views for them.

For concurrent coding, choose explicit integration ownership. Shared cwd is vulnerable to concurrent edits; optional local worktrees isolate source but do not merge results. Remote nodes need usable repo paths, credentials, profiles and common coordination records; CAO does not automatically transfer the Mac workspace to Endeavour. Provider-native sandbox/approval settings and terminal-status compatibility should be verified on the exact deployed Codex version. A standing organizational service must also decide when to relaunch a dead employee session, what context to restore and how to avoid duplicate work.

Overall, adopt CAO most plausibly as an execution adapter beneath Wingman's own organization model. Treating it as the full Wingman product would leave the central product-discovery, project-management, human-channel and executive-continuity requirements implicit in prompts.
