Intent assessment against Wingman

Assessment date: 2026-11-05. Product: Intent, a desktop workbench for coordinating coding agents, with the intentd daemon and an early iOS companion. Repository: https://github.com/intent-hq/intent. Local checkout: researchs/intent/repo/. Actual checked-out monorepo commit: 33fcf9273d2f819897cdbc81f5f1f472813e809d.

Fit verdict: Intent is a promising execution, coordination, persistence and individual-agent workbench reference for Wingman. Its documented design goes substantially beyond a terminal launcher: separate provider sessions, task-linked delegation, durable message queues, completion watches, background hooks, cross-workspace Assistant tools and remotely executed agents are all specified. It does not establish Wingman's standing organization, Telegram Butler, product/technical leadership split, proportionate discovery process, or executive briefing/timeline product.

Critical evidence boundary: this checkout contains the integration monorepo, documentation, scripts and reference fixtures, but none of the component runtime source. All three submodules are uninitialized and their directories are empty. git submodule status reports pins e7075a9da49f66f9a55e916f2d5b63fc539154cc for packages/intentd, 959ae25a7e49e461f9948c1f3a1544065fa1fe22 for packages/cloudlands-fe, and dd80a3a209950314b4fe040929272dd775ef172f for packages/ios. These are recorded gitlinks, not inspected component revisions. .gitmodules, lines 1–13, identifies their repositories; AGENTS.md, lines 15–30, confirms that application code belongs in those submodules. No initialization, download or installation was performed.

Accordingly, runtime capability verdicts below use Unclear where component source is required. The accompanying text explains the documented fit. Resembles identifies a narrower primitive whose documented semantics already differ from Wingman, and Absent is scoped to the inspected local material. No feature is certified Exact from prose or a static fixture. Protocol version 15.4 is explicitly a documented version, not a shipped-version claim: protocol introduction, lines 1–34. This distinction is especially important here because the monorepo deliberately allows documentation to precede implementation.

Architecture and actual execution model

The available architecture document describes a daemon-primary system. Electron/SvelteKit desktop and SwiftUI mobile clients call a long-lived Rust daemon using JSON-RPC. Local transport is a Unix socket or Windows named pipe; network clients use authenticated TLS/WebSocket connections. Business services, rather than renderer state, own workspaces, notes, task metadata, agents, scripts, source control and persistence. The daemon owns SQLite plus a file tree and an append-only event log. An ACP client launches external coding-provider programs over piped stdio, multiplexing many independent sessions. A per-agent MCP bridge exposes the same workspace service API back to each provider. Thus an Intent agent is documented as a durable application session with an independently running provider process when active, not merely a persona in one coordinator's prompt. See architecture, lines 10–59 and 63–120.

The documented entry point is the intentd binary, responsible for CLI parsing, daemon wiring and transport composition. The meaningful execution path is transport router → shared intent-services operation → store/git/runtime dependencies → intent-acp provider process → streaming and persisted agent messages. ACP callbacks handle files, terminals and permissions. Agent-authored JavaScript runs through QuickJS and invokes typed ws.* host bindings, which return to the same services. Provider-specific MCP delivery differs: temp configuration, environment configuration, ACP session/new server definitions, or a Pi extension wrapper. These are substantial integration details, but the Rust entry point, service implementations, provider adapters and MCP dispatch code named in architecture, lines 23–42 and 104–120, are not available to trace directly.

A workspace combines a repository checkout, a spec note, task notes, agent sessions and related artifacts. workspace.create is documented as one idempotent orchestration operation: clone/cache resolution → checkout → spec seed → initial agent. Checkout modes include linked worktree and standalone CoW/direct clone. Current per-agent CoW sandboxes differ from workspace checkouts: delegation can provision a child sandbox asynchronously and gate its first provider spawn on settlement. On unsupported CoW or provisioning failure, legacy child isolation may fall back to the shared checkout. This is a preference with fallback, not a universal isolation or security guarantee. See workspace contract, lines 56–65; checkout architecture, lines 223–262; delegation contract, lines 344–355.

There are two different remote-execution stories. The complete phase-one static-node/hub/checkpoint architecture is explicitly prepared and unimplemented at the current pins. Its structural tests do not establish live scheduling, recovery or native transport. Separately, the protocol documents a narrower daemon-to-daemon remoteMachines executor feature behind frontend Labs and capability remoteMachines: 1. It uses an owner-minted executor credential, certificate pin and on-demand connection, and can place an agent on another daemon with an isolated checkout. It does not require or imply the full agentNodes feature. It starts from committed state and does not carry uncommitted changes; remote batch placement and various full-node/hub operations are excluded. This is a genuine distributed-execution contract, rather than just a remote viewing client, but its implementation cannot be confirmed in this checkout. See prepared architecture, lines 122–167; remote machine contract, lines 278–321 and 406–446; static fixture implementation, lines 1–2 and 85–108.

Agent definition, creation and lifecycle

Definition is separate from identity

A specialist definition is reusable configuration/prompt material, not a running agent. The documented catalog resolves project .intent/specialists/ over user ~/.intent/specialists/ over bundled resources. It supports create/edit/delete, read-only imported definitions, alias resolution and rescan notifications. Frontmatter can configure provider, model, reasoning effort, agent type, picker role/icon, model recommendations and team roster. Configuration scalars inherit independently when omitted; explicit empty values clear an inherited setting. The prompt body and roleReminder are winner-takes-all. This lets a project change a worker's domain instructions while retaining selected defaults, but can also make a superficially small override inherit more than expected. Specialist contract, lines 96–120, 150–218, 250–302, 348–406.

role: orchestrator has documented spawn-time file-edit restrictions captured in session metadata. The teamAgents array, by contrast, is an advisory picker roster, never an enforced delegation boundary. A role label does not install a reporting structure or automatically create teammates. Historical v1.1 resources describe a spec-writer orchestrator, implementor and verifier; current documentation explicitly says harness 3.8 no longer bundles them and callers should omit specialist for a general agent. The source does not support advertising that old trio as the current default organization. Specialist roles, lines 303–345.

An agent is a server-assigned agent-{uuid} session, with one session per agent in agent.listActive, persisted workspace association, model/provider, parent/task links and metadata. Its provider process is an expendable execution resource, while its turn is one prompt/stream operation. Its task is separate note metadata and can survive agent changes. A background hook is executable JS owned by an agent. It is not another coding agent. Provider-native worker observations are yet another concept: their observed state is not automatically an Intent session or authoritative ongoing execution. Agent identity, lines 5–13; worker evidence boundary, lines 3–25, 216–246.

Creation and execution

Creation can originate from the client (agent.create), initial workspace creation, delegation, or wakeOrCreate when a task has no suitable resumable assignee. Delegation persists parent identity, incremented depth, the resolved first message and background status. Provider/model/effort resolution validates explicit choices before side effects, can inherit a usable local parent's provider, and otherwise consults specialist/settings defaults. An unavailable provider does not silently become another provider. wakeOrCreate has a depth cap of two and an explicit poisoned-session recovery path that moves durable queued messages before deleting an unusable session. Creation/delegation, lines 274–344 and 618–631.

The documented provider startup is ACP initialize/session open or load, per-session MCP delivery and then prompt execution. Agent tool calls carry a caller-specific bridge address, making updates attributable to an agent rather than a shared anonymous tool user. The runtime is daemon-owned, so UI disconnection need not stop an agent. Local ACP process handles, cancellation and respawn implementation are missing from the checkout. These remain specified behavior. Architecture, lines 23–42, 104–120; resume protocol, lines 463–479.

Each session receives a creation-time harness version and feature snapshot. Doctrine/system-prompt assembly is pinned; live API reference and runtime semantics are not. A child receives the current harness even when its parent is older. Background-hook scheduling and external MCP forwarding have documented live-setting exceptions, and turn-envelope/wake call sites still resolving the latest harness are an acknowledged limitation. This is useful reproducibility rather than absolute behavioral freezing. Some older protocol paragraphs retain older literal “current” version examples; without intent-core::CURRENT_HARNESS_VERSION, this assessment does not infer the actual current component constant from them. Harness design, lines 10–32, 34–69, 72–110; agent harness fields, lines 993–1027.

Tools, permissions, routing and concurrency

Agents can be given workspace notes/tasks, messages, scripts, host commands, terminal reads, browser automation, source-control operations, external MCP tools and attention requests. Feature gates shape the tool surface. Structured human questions are top-level-only. A delegated worker is expected to escalate through its parent. Provider tool approval is a separate ACP-mediated policy: documented default AllowAll, with Interactive, AutoByRisk and DenyAll alternatives. Interactive prompts can be re-fetched after client reconnect and time out after five minutes. These controls are not business acceptance gates. Settings gates, lines 445–446; permissions, lines 12–41, 61–100.

Routing normally follows workspace/task/session identity. A chief/Assistant workspace has special cross-workspace access for agent lookup, ask/send/wait and workspace search/proposal actions; ordinary agents' completion watches are workspace-scoped. Peer creation makes another top-level session; parentless peers do not automatically form a team. A2A sends default to interrupt at the MCP binding, whereas ordinary wire sends default to queue-if-busy. A peer send does not automatically subscribe the sender to the peer's completion. These choices matter for Wingman: ordinary collaboration chatter must explicitly choose queued delivery where interruption would destabilize independent work. Assistant tools, lines 49–130; watch scope, lines 567–590; send semantics, lines 382–400.

The task graph supports dependencies, tree-child readiness and symmetric conflict interpretation during batch classification. Admission favors the longest effort-weighted downstream critical path. This is a deterministic heuristic, not an exact solver. Estimates parse free text and default when missing, and incomplete relation graphs are flagged. Single-task delegation can bypass the batch conflict hold. The batch writes no scheduler state and never automatically starts held tasks: the coordinator must re-submit after settlement. This yields a useful planning aid but not an autonomous organization scheduler. Relations, lines 723–733; batch algorithm, lines 356–380.

Persistence, waking, interruption and recovery

SQLite persists sessions/transcripts, queue mutations and sealed delegation groups. On restart, interrupted sessions are captured before status healing. A human can resume/abandon, or serve --resume-all can continue headlessly. Resume claims a recovery record, restores parent watches, sends a continuation and lazily respawns/loads the provider session, with recreate fallback. Failure after the claim restores retryability. The continuation precedes the preserved FIFO queue; abandoned queues remain durable but inert. Group completion is recorded before the idle event. Recovery, lines 401–491.

Not every persistence promise is equally strong. Completion-watch registration is documented as a best-effort asynchronous store write for many paths; even the awaited explicit registrations are fail-open on persist errors. Group durability therefore does not establish that every watch survives every crash. Completion-watch persistence, lines 518–578. This is a concrete reliability caveat for a persistent ProjectMaster.

Hooks execute short JS checks on delay/cron/runAt schedules, immediately validate on registration, retain agent/workspace caller scope and wake their owner on dispatch, expiry or failure. Perpetual hooks can dispatch repeatedly, but still expire. Schedules rehydrate at daemon boot. A run interrupted by daemon death heals to scheduled. Hook wake delivery is explicitly best-effort. The scheduler is an excellent low-cost waiting primitive, but a permanently staffed supervisor requires its own renewal and recovery policy. Hook contract, lines 3–47; hook architecture, lines 523–588.

Interrupt-priority steering sends ACP cancellation while keeping the provider process alive, emits terminal stream state and starts a new turn; pending input is retained. Startup races queue instead of killing the not-yet-cancellable session. agent.retry is valid on an error session, tears down a stale handle and redrives parked input using retry/backoff; poisoned sessions force a fresh ACP session with prior history replayed rather than loading deterministically broken state. Interrupt semantics, lines 392–400; retry, lines 2772–2782.

Completion, acceptance and cleanup

An agent reporting to its parent is not necessarily finished. reportToParent persists a report and may deliver a progress wake; terminal completion remains armed. Grouped after_all children contribute reports to one aggregate parent wake. Idle is considered settled only after queue/busy, hook, PR-monitor and outgoing-agent-watch deferrals clear. A special distinction prevents the coordinator's own group watch from deadlocking group sealing, and a mutual two-agent watch cycle is handled; deeper cycles remain a documented limitation. Parent report, lines 633–648; settlement, lines 744–797.

Sandbox completion may trigger an automatic merge. Conflicts bounce work to the agent, while blocked/retry-exhausted merges surface as merge-pending. Successful code merge or a task status change is not product acceptance. Acceptance criteria can be stored, tests/scripts can run and a reviewer can be assigned, but there is no inspectable automatic DoD adjudicator or end-to-end acceptance/delivery workflow. Sandbox completion, lines 2784–2801; task API, lines 699–711.

Soft retirement retains the conversation, guards against active descendants and retiring the last top-level agent, cascades eligible children, cancels hooks/PR monitors/subscriptions, preserves queued input and settles incoming watchers. Restore clears the retired mark but does not resurrect cancelled wake sources. Workspace deletion performs database/tombstone work before background filesystem removal, with safeguards for user-owned checkout locations. Legacy settled sandbox directories are not universally auto-cleaned merely because a child becomes idle. These are lifecycle semantics worth preserving explicitly if Wingman adds permanent staff identities above temporary sessions. Retirement, lines 1334–1389; workspace deletion, lines 60–65; sandbox lifetime, lines 348–355.

Coordination and a request trace

The durable coordination objects are workspace notes/task metadata, session transcripts/queues, parent/task assignments, completion watches/groups and events. Task dependencies are structured data; ordinary discussion is text, and workspace discussion rooms have their own access and explicit addressing rules. Neither group completion nor a dependency-ready event guarantees the next task starts. Human decisions enter through top-level questions/proposals or provider permission answers. Child blockers/discussion requests update linked task state and wake parents/watchers immediately, even inside an incomplete after_all group. Attention flow, lines 1065–1153.

The following is a contract-level trace of a supported real API request, not a runtime execution claim:

  1. The human asks an Assistant to continue a repository change. The Assistant can search existing workspaces by text, PR or repository and inspect matching agents/conversations; creation is exposed as a proposal. This resembles Butler intake, but routes to workspaces rather than discovering a product/organization model. Assistant bindings, lines 49–57 and 117–129.
  2. A top-level worker writes a spec note containing @@@task blocks with keys, estimates and dependencies. Note writes auto-convert these into child task notes; references resolve against sibling keys/titles or existing task IDs, with invalid attributes reported as warnings. The spec retains links whose checkboxes project authoritative task-note status. Note/task contract, lines 11–19, 699–709 and 743–765.
  3. The coordinator calls agent.delegate with a task list and waitMode: after_all. Classification validates task IDs, checks active assignment occupancy and dependency/conflict state, admits startable work by critical-path priority and returns every task's disposition. Child sessions are created and assigned; held tasks remain held. Delegation, lines 312–380; assignment, line 711.
  4. Each child waits for any sandbox provisioning, opens its ACP provider session, receives task/context through the workspace API and streams work. If blocked, it invokes reportBlocker. The durable attention fields change, a linked task becomes blocked, and the parent receives a wake. It can respond through A2A send or bring the issue to the human. Provisioning gate, lines 348–355; blocker flow, lines 1074–1142.
  5. A child can run verification as a saved script and monitor the accepted run. Completion/trigger state must survive the transition into a queued wake and actual turn admission. It then updates its task and reports to its parent. Genuine settlement produces the group's aggregate wake, including completion reports and hints about newly unblocked tasks. The coordinator must delegate the next batch and independently decide whether verification satisfies the requested change. Group recovery/unblock hints, lines 485–511; settlement, lines 744–797.

There is an executable reference-model trace for step 5 in the actual checkout. ActiveMonitors.register validates ownership, run identity, live state and capacity, then stores the active row. retire atomically removes that row and creates a stable script-monitor:<id> delivery job. enqueue, persistMessage, transfer and admit model the handoff to queue, transcript and durable turn receipt; restart clones the persisted model state, and lifecycle suppression removes obligations for an archived/retired scope. See actual reference model, lines 5–21, 30–112. Its first three lines explicitly state that it is not production SQL or the process runner. The inspected and executed reference tests cover fault/restart/admission cases, proving model invariants rather than daemon behavior.

Major additional capabilities

Multi-provider execution and account failover. Intent's documented ACP registry supports multiple coding harnesses, dynamically discovered models and separately configured provider profiles. Quota failover rotates through eligible backup profiles within the same base provider and model. It does not silently migrate Codex work to another model/vendor. This could improve Wingman availability and account administration, but adds authentication, provider-specific session restoration and budget attribution requirements. It is unnecessary for an initially Codex-only organization. Provider architecture, lines 23–39, 110–111; backup failover, lines 510–535.

Workspace portability and source-control lifecycle. Export/import carries workspace records, assets, queued/conversation state and Git bundles, including qualifying unpublished submodule commits. It supports staged/chunked/idempotent transfer and explicit source finalization. Exact daemon-version compatibility is required at import; event history is deliberately excluded and authority does not simply transfer. This is valuable for moving work between personal machines and retaining useful artifacts, but is distinct from real-time distributed execution and requires an explicit authority/rebinding policy. Transfer contract, lines 47–54 and 67–75; authorship transfer section, line 2609 onward.

Human multiplayer and scoped sharing. Principals, forge-backed identities, workspace memberships, invites, Participants/Managers and live presence serve multiple humans, beyond Wingman's one-person organization. Experimental discussions can explicitly address agents under grants. The benefit is outside collaborators or reviewers. The consequence is a much larger authorization surface. Guest Manager is deliberately not general host management, and Labs status must be honored. Multiplayer baseline/roles, lines 3–89; discussion readiness, lines 5–18.

Integrated development operations. PTY-backed commands/services, retained script output, automatic service restart, source-control review/check integrations, centralized PR monitoring, browser routing and local-model server management make the workbench a broader development operating environment. PR polling uses one shared loop and quota-aware cadence rather than one agent repeatedly polling each PR. Wingman could reuse these as infrastructure beneath TestMaster and specialist work, but still needs product acceptance policy. Service inventory, lines 104–120; central PR loop, lines 590–622; managed local models, lines 10–73.

Distinctive mechanisms and grounded innovation

These are mechanisms worth borrowing, not claims of historical uniqueness. Their runtime implementations remain uninspected. The locally available executable code supplies contract/reference-model support only.

Settlement-aware coordination. Separating progress reports, interim idle and genuine completion allows a parent to stop consuming turns while children, hooks or PRs remain active. Stable completion-wake identities and durable group accounting address duplicate/lost wake hazards. The explicit two-cycle guard and acknowledged deeper-cycle limitation show that this is a state-machine problem, not simply “send a message when idle.” Wingman needs the same distinction to avoid delivering a product while tests or workers are still pending. Settlement architecture, lines 744–797; progress/final wake contract, lines 633–648. Watch registration's best-effort persistence remains a limit.

Runnable specifications with explicit evidence scope. The checked-in monitor oracle represents active observation, delivery jobs, queue/transcript persistence and turn admission as separate phases, with injected store failure and restart paths. That decomposition makes failure windows inspectable without launching a provider. It cannot prove SQLite transactions or native process lifecycle, but offers a useful testing pattern for Wingman's future supervisor. Model, lines 1–20 and 53–112; tests.

Versioned doctrine with live reference. Session-pinned prompt/rule doctrine and creation-time feature snapshots preserve interpretability across upgrades, while current tool schemas remain live. Wingman could distinguish an agent's durable role contract from current APIs in the same way. Limits include live-setting exceptions, mixed-version parent/child trees, and wake/envelope call sites not all using the pinned version. Harness, lines 10–69 and 72–110.

Task-graph-aware delegation. Effort-weighted critical-path ordering, conflict holds, explicit dispositions and relation-coverage warnings give a coordinating model useful scheduling information. It does not manufacture missing estimates/edges or run held tasks automatically. Wingman's TechMaster could adopt the advisory algorithm while keeping responsibility for graph quality and renewed delegation. Batch admission, lines 356–380.

Attributable routing between execution and viewing clients. Browser target selection is modeled separately from the coding daemon: workspace pin → desktop-session client → claimed-tab host → default eligible client, then newest live connection for that logical client. An offline pin fails instead of silently selecting another browser. This is useful when a Mac hosts UI/browser surfaces and Linux runs coding work. The local resolver is actual inspectable JS, but is explicitly a reference implementation. It proves rule consistency, not remote browser execution. Resolver source, lines 40–65; workspace browser pin contract, lines 42–43.

Mechanized cross-component drift checks. The local check-agent-feature-toggles.mjs parses daemon setting registrations, frontend feature lists and canonical documentation, with fail-closed parsing and staged rollout rules. This is genuinely inspected repository tooling, not missing product code. It prevents a backend capability shipping with no user-visible toggle and is directly relevant if Wingman separates agent runtime, dashboards and chat clients. It does not prove the underlying feature functions. Checker, lines 3–43, 53–58 and 129–159.

Practical fit and adoption consequences

Intent's best role is a candidate technical foundation or design reference for the coding-workbench layer, subject to inspecting its component sources. Directly reusable ideas include durable session identity, task-note assignments, streamed detail views, queue/interrupt semantics, completion/group watches, scripts/PR monitors and explicit machine placement. The available monorepo also provides usable reference fixtures and drift-check tooling today. Reusing production code is not assessable until the actual component revisions are available; no buildability or API compatibility claim is made.

The organization model needs adaptation. Map durable Wingman agent identities to possibly many Intent sessions; keep role/profile, staff instance, task assignment, execution process and conversation as separate entities. Map products to a registry above workspaces so a product can retain leadership and directives across several branches/workspaces. Give Butler/ProjectMaster a clearly defined cross-workspace authority rather than distributing chief-level access to every specialist.
