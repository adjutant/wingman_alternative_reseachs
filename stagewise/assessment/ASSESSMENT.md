A registered `AgentProfile` controls prompt fragments and environment domains. It is not a business role, team membership or reporting relationship. ## Architecture and actual execution model

Stagewise is an Electron application with a React interface, a backend service layer and an extracted TypeScript agent runtime. The backend [entry point](../repo/apps/browser/src/backend/index.ts), lines 39–42 and 127–158, configures local profile storage, imports `main` after Electron is ready, and quits when all windows close. Execution therefore lives behind the viewing panel while the app is running, but this is not a separately deployed durable organization daemon.

The composition root creates an `AgentStore`/command seam, an `AgentHost` with paths and model services, and `AgentCorePersistence`; later it registers the browser chat constructor and constructs `AgentManagerService`. The host wires environment adapters for workspaces, `AGENTS.md`, skills, memory, plans, logs and file diffs. See [main.ts](../repo/apps/browser/src/backend/main.ts), lines 273–320, 590–635, 655–737 and 750–819. The layering is concrete: `packages/agent-core` owns the agent loop, state, persistence and universal file tools. The browser subclass adds shell, sandbox, console, diagnostics, library-documentation and question tools. The Node runtime and shell packages provide filesystem/search and PTY execution; Electron supplies browser control and UI.

UI actions reach typed Karton procedures. `AgentManagerService` forwards lifecycle and message procedures into `CommandRegistry`, and core `AgentManager` creates or addresses the runnable instance. `AgentStore` is canonical for migrated agent state; `AgentCoreBridge` projects granular Immer patches into Karton, so streaming updates can reach the interface without copying a whole chat envelope. This is application state synchronization, not an agent-to-agent messaging bus. Evidence: [browser manager](../repo/apps/browser/src/backend/services/agent-manager/agent-manager.ts), lines 32–66, 107–134 and 212–227; [bridge](../repo/apps/browser/src/backend/services/agent-core-bridge/index.ts), lines 40–67 and 96–125.

There are two materially different execution paths:

1. **Native Stagewise harness:** `BaseAgent.runStep` checks eligibility, captures context, obtains the selected model and tools, and calls AI SDK `streamText` with an abort signal, retry configuration and output limits. Tool results drive subsequent steps; ordinary model completion returns the conversation to idle. See [base-agent.ts](../repo/packages/agent-core/src/agents/base-agent.ts), lines 1676–1715, 1884–1903 and 2673–2774.
2. **External harness through ACP:** a per-instance `AcpAgentRuntime` selects a Codex, Claude Code or OpenCode adapter. It launches a **local** subprocess over NDJSON stdio, initializes ACP, creates/resumes the provider session, forwards prompts and translates notifications into Stagewise messages, plans, tools, images and usage. See [adapter registry](../repo/apps/browser/src/backend/agents/acp/adapter-registry.ts), lines 1–18; [runtime](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 153–221, 280–335 and 397–440; [process client](../repo/apps/browser/src/backend/agents/acp/process-client.ts), lines 60–128. Calling a cloud model or launching a local external agent is not multi-host execution.

The primary durable record is a local SQLite database: instance UUID, type, title, model/provider instance, drafts, queued input, mounts, approval preference, unread and archive state, plus normalized message rows. See [schema](../repo/packages/agent-core/src/services/agent-persistence/schema.ts), lines 98–150. Separate persistence services hold diffs, attachment blobs and read/image caches. The runtime also writes inspectable Markdown/JSONL memory transcripts and an index. These complement the database rather than creating a project management system.

The separate `apps/stagewise-cli` is a minimal extracted-runtime host. It accepts a prompt and working directory. It creates a fresh UUID under the temporary directory, registers `CliChatAgent` and mounts the workspace. Permission mode is `alwaysAllow`. It waits up to ten minutes for idle, then removes its PTYs. It does not expose the browser's durable multi-conversation interaction or a cross-machine control plane. See [CLI entry](../repo/apps/stagewise-cli/src/index.ts), lines 57–109, 168–175, 193–260 and 307–351.

## Agent definition, creation and lifecycle in depth

### What an agent is

The native agent is a `BaseAgent` subclass instantiated in the Electron main process, with its own instance ID, message state, model selection, tool access and loop. The external ACP process is a separate harness execution resource attached to that instance, with its own provider session ID. A shell session is a PTY, not a specialist agent. A plan task is a Markdown checkbox, not a scheduled worker. A side chat is a conversation branch. None of those constructs by itself creates Wingman's standing role-bearing employee.

Definition has three levels. `ChatAgent.config` declares persistence, model requirements, user input, title generation, context compression and finish-tool behavior. Host subclasses choose extra tools. `AgentHost.defineAgentProfile` sets environment-domain allowlists, output protocols/aliases and system-prompt slot overrides. These let a developer build another host or agent class. They do not currently let the human grow an organization by defining a profile in the UI. The sole enum member and sole browser constructor are chat. See [ChatAgent configuration](../repo/packages/agent-core/src/agents/chat/chat.ts), lines 11–47; [host profile](../repo/packages/agent-core/src/host/host.ts), lines 108–143 and 294–324; [prompt builder](../repo/packages/agent-core/src/agents/chat/system-prompt-builder/system-prompt-builder.ts), lines 35–100.

### Creation, identity and routing

The UI's `agents.create` handler accepts a model ID, provider-instance ID, approval mode, draft input and workspace paths. It always creates `AgentTypes.CHAT`. Explicit mount paths normally resolve to the repository's main worktree unless the caller requests exact preservation; without explicit paths it reuses the last chat's workspace paths. `createAgent` generates a UUID, seeds a canonical store envelope, obtains the registered constructor, binds state mutations and persistence callbacks, creates any external-runtime adapter and inserts the agent in `activeAgents`. There is no discovery of a product from the meaning of a request. The caller chooses the conversation and mounts. See [manager](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 465–537 and 1046–1246.

Routing preserves `(providerInstanceId, modelId)`, allowing the same model label to address different provider instances. New conversations can inherit the last valid selection; resume validates that the persisted provider/model still exists. ACP routing maps provider type to adapter and derives a process key incorporating approval behavior. A native turn after an ACP turn can invalidate the old ACP thread so subsequent use re-seeds appropriate history. This is harness routing for one conversation, not project/personnel routing. See [manager selection](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1061–1084 and 1292–1315; [ACP runtime](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 139–150 and 280–335.

### Execution, tools and permissions

`sendUserMessage` assigns a fresh message UUID. Working conversations queue input; idle conversations append it and start a step. Older queued input retains order, while special queue flushes can prioritize steering. Before accepting a new direct message, the agent terminates obsolete pending tool states so the loop cannot remain blocked by stale approvals. `canRunStep` prevents overlapping native generation using the abort controller and checks tool parts for unresolved execution/approval states. Different agent objects can run concurrently. This is a collection of independent loops, with no team scheduler, dependency graph or per-product concurrency policy. See [base-agent.ts](../repo/packages/agent-core/src/agents/base-agent.ts), lines 800–863 and 3181–3217.

The universal toolset supplies read/write/copy/edit/delete/glob/grep. Browser additions supply persistent JavaScript, documentation lookup, lint diagnostics, console reading, structured questions, PTYs and watchers. Filesystem mounts have read/list/create/edit/delete permissions, including explicit read-only and full-access sets. Tool approval defaults to `alwaysAsk`; users can choose `alwaysAllow` or `smart`. In smart mode, a classifier tries a bounded sequence of models and falls back to human approval if all classifiers fail. This is an operational approval system, not a product management escalation policy. See [permissions](../repo/packages/agent-core/src/env/permissions.ts), lines 12–25; [approval modes](../repo/packages/agent-core/src/types/tool-approval.ts), lines 3–20; [classifier](../repo/apps/browser/src/backend/services/toolbox/tools/shell/smart-approval/index.ts), lines 58–151.

Mount restrictions should not be interpreted as a demonstrated whole-machine security sandbox: the shell tool resolves a working directory and runs a real local PTY. ACP permission behavior is provider-specific; inspected tests explicitly cover automatically approving Claude workspace edits and mapping Codex “Always ask” to a read-only agent mode. A Wingman integration would need to retain and understand those differences rather than assume all harnesses enforce identical capabilities. See [shell cwd resolution](../repo/packages/agent-shell/src/tools/execute-shell-command.ts), lines 270–299; [ACP tests](../repo/apps/browser/src/backend/agents/acp/runtime.test.ts), lines 667–705 and 1269–1327.

The protected child-spawn helper can return a synchronous child's finish output or start an asynchronous child with an error callback. The manager supplies parent IDs and completion/error callbacks. However, no current `getSpawnChildAgentTool` call site was found beyond its definition/documentation, and neither chat tool list includes delegation. The asynchronous helper's success response merely says a child spawned. It is not a collaboration room or automatic aggregation workflow. Sub-agent rows cannot be resumed directly. This is latent extension infrastructure, not a shipped specialist hierarchy. See [spawn helper](../repo/packages/agent-core/src/agents/base-agent.ts), lines 1528–1604; [manager spawn/resume](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1249–1289.

### Persistence, resume and branching

The database separates instance metadata from messages. The persisted queue, drafts, model/provider and mounts survive normal persistence; working state, errors and pending approval maps are ephemeral. Resume refuses archived records until unarchived and refuses sub-agent records, recreates the top-level runtime with `isWorking: false`, then remounts saved workspaces while logging individual mount failures. It restores a conversation's ability to continue. It does not resume an instruction pointer in an interrupted tool/process. Startup attempts the last open conversation and otherwise creates a default one. See [state annotations](../repo/packages/agent-core/src/types/agent.ts), lines 59–127; [resume](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1265–1348; [startup wiring](../repo/apps/browser/src/backend/main.ts), lines 657–674.

Forking uses the side-chat path: copy message history and selection, clone attachment blobs, mount the same workspaces, persist the branch, then promote it by clearing `sideChatParentId`. Forking does **not** create a worktree automatically. The copies initially point at the same source paths. A side chat cannot be forked again before promotion, and a working side chat cannot be promoted. The mechanism is useful for exploring an alternative conversation without equating it with delegated work. See [fork/side-chat implementation](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1397–1497.

The native loop compresses history when its token threshold is crossed, retaining a recent tail and summary context. In addition, the memory writer records full history in Markdown and JSONL with metadata and a global index, using content hashes, append/tail replacement and periodic rewrites. Those records help recover detailed context after compaction. They are transcripts rather than curated product specifications or executive timeline entries. See [post-step compression](../repo/packages/agent-core/src/agents/base-agent.ts), lines 2832–2857; [memory writer](../repo/packages/agent-core/src/agents/shared/memory/index.ts), lines 31–39, 64–107 and 431–535.

ACP adds `acp-session.json` with adapter/process/session identity. It resumes only when adapter/key match and the provider advertises resume; otherwise the runtime creates a session and can seed chat history. This adds real continuity but relies on external harness behavior, which was not executed here. See [ACP persistence shape](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 62–67 and 111–126, and [session setup](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 280–335.

### Scheduling, interruption, failure and recovery

There is no durable periodic organizational scheduler in the inspected execution paths. A native chat can create a one-shot watcher with a command and deadline. The engine starts a dedicated PTY, stores the full command in a temporary script, and arms a timeout. Zero exit becomes a triggered event; nonzero exit becomes failure; expiry kills the session and records timeout. The browser manager packages event data as a user message to the owning agent, with verification/follow-up guidance and `queueIfBlocked: true`. Watchers explicitly run only in the current application process and are not restored after restart. See [watcher tool guidance](../repo/packages/agent-shell/src/tools/execute-shell-command.ts), lines 147–162; [engine](../repo/packages/agent-shell/src/engine/session-manager.ts), lines 637–705, 1268–1276 and 1361–1398; [event routing](../repo/apps/browser/src/backend/services/agent-manager/agent-manager.ts), lines 166–209.

Stopping invalidates the step generation before aborting, clears deferred continuations, cancels host dialogs, stops any external runtime and marks unfinished tools as interrupted/denied. Manager stop recurses through active children. ACP sends cancellation and waits three seconds. It closes/restarts a process that does not settle, and some adapters request restart after cancellation even when settled. Cancellation therefore has defined recovery semantics, but it does not undo files or external side effects. See [native internal stop](../repo/packages/agent-core/src/agents/base-agent.ts), lines 3307–3363; [manager stop](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1759–1802; [ACP stop/teardown](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 245–277.

Recovery includes SDK retries, model fallback and explicit retry-last-user-message. The manager scans for network failures every five seconds with bounded backoff intervals, but only registers automatic retry when connectivity is actually offline. A retryable-looking error while online is not automatically treated as an offline event. Recovery after suspend/event-loop stall only selects working agents without pending user questions or approvals. These mechanisms restore a coding run after infrastructure failure, not semantic detection of stalled tasks, missing deliverables or unresolved project blockers. See [retry constants](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 144–147; [network/recovery logic](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 897–1042; [fallback transition](../repo/packages/agent-core/src/agents/base-agent.ts), lines 2045–2070.

### Completion, acceptance and retirement

The loop continues after tool calls, pauses on approvals, can continue after truncated output, and ends on ordinary completion or configured limits. `ChatAgent` additionally returns idle after creating/updating a plan so the user can review it. A child type could supply a finish schema and callback, but shipped chat has no structured product-completion output. No system-level acceptance tests, definition-of-done reconciliation, delivery approval or automatic stop-after-accepted-delivery policy was found. Testing can be performed through shell/browser tools, with the model and human deciding what the results mean. See [continuation conditions](../repo/packages/agent-core/src/agents/base-agent.ts), lines 2673–2774; [plan stop hook](../repo/packages/agent-core/src/agents/chat/chat.ts), lines 50–69.

Archive stops execution, reports premature termination to a parent, finalizes pending diffs, archives active children, optionally persists/marks the row and tears down/removes active state. Hard deletion recursively deletes children, removes the database record and attachment blobs. That path does not demonstrate deletion of all memory transcript artifacts, and worktree deletion is a separate operation. Worktree deletion refuses the main worktree and requires force for uncommitted changes, then detaches that path from all agents while preserving conversations. See [agent cleanup](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1517–1614; [worktree cleanup](../repo/apps/browser/src/backend/services/toolbox/services/mount-manager/index.ts), lines 1072–1122.

## Coordination mechanics and a traced request

The central coordination mechanism is shared application state around a **single selected conversation**. Messages, queued steering, tool approvals, plan files and mount state are keyed by agent ID; Karton provides live UI updates. Global plan/log/memory directories and mounted source files allow information reuse, but they do not supply room participants, peer delivery, task ownership arbitration or dependency scheduling. A user must intentionally supply shared-file protocols if several chats are to cooperate. Worktrees reduce edit collision without deciding integration responsibility.

A representative supported request is: **“Inspect this repository, propose an implementation plan, then implement it after review.”** This is a static path trace, not a claim that a live request was executed:

1. The UI calls `agents.create` with model/provider/mount options. The core handler creates a chat and mounts the chosen repository, normally resolving a linked checkout back to the main worktree. The instance UUID becomes the routing key. [Creation handler](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 465–537.
2. `agents.sendUserMessage` reaches the per-instance agent; working sessions queue it, otherwise it enters history and triggers `runStep`. [Browser forwarding](../repo/apps/browser/src/backend/services/agent-manager/agent-manager.ts), lines 212–227; [base-agent message intake](../repo/packages/agent-core/src/agents/base-agent.ts), lines 800–863.
3. Registered adapters capture the allowed environment domains and render full state/change state. The agent can inspect source, its root `AGENTS.md`, skills, plans and browser/shell context. Changed-domain entries become durable message context rather than a live lookup required whenever old messages are rendered. [Domain capture](../repo/packages/agent-core/src/env/contract.ts), lines 117–191; [adapter registration](../repo/apps/browser/src/backend/main.ts), lines 750–819.
4. If product intent is unclear, `askUserQuestions` allocates a question UUID and deferred response keyed to the agent. Each step advances state; submit resolves answers; cancellation or a new user message resolves partial/cancelled output. No Butler or room intervenes. [Question lifecycle](../repo/apps/browser/src/backend/services/toolbox/tools/user-interaction/ask-user-questions.ts), lines 27–125 and 155–180.
5. The agent writes `plans/example.md`. `ChatAgent.onStepFinished` detects the plan-path write and stops. Plan ownership is inferred from that conversation's write/edit tool history. The UI computes progress and offers implementation actions. This is a user-review checkpoint, not a technical manager assigning tickets. [Plan stop](../repo/packages/agent-core/src/agents/chat/chat.ts), lines 50–69; [ownership](../repo/packages/agent-core/src/plans/ownership.ts), lines 35–60; [plan status](../repo/apps/browser/src/ui/screens/main/agent-chat/chat/_components/footer-status-card/index.tsx), lines 145–188.
6. The user triggers implementation. The same agent loop edits files and invokes shell/browser/diagnostic tools, subject to operational permissions. State changes and tool output stream through the store/bridge; messages, queue and mounts persist through `persistAgentState`. [Plan protocol](../repo/packages/agent-core/src/env/adapters/plans.prompt.md), lines 7–13; [persistence](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1351–1394.
7. The loop returns idle when the model finishes. The user can examine edits/results, continue, branch, archive or retry. There is no automatic handoff to an independent TestMaster or portfolio-level delivery report. [Loop decisions](../repo/packages/agent-core/src/agents/base-agent.ts), lines 2673–2774; [lifecycle catalog](../repo/apps/browser/src/backend/services/agent-manager/agent-manager.ts), lines 32–66.

The ACP alternative follows the same user-selected conversation at the surface but sends the task to a local external harness; tool/plan notifications are normalized back into the same interface. This is valuable execution interoperability. It does not create inter-agent coordination merely because different chats can select different harnesses.

## Major additional capabilities beyond Wingman's described baseline

**Integrated browsing, debugging and programmable browser operations.** Stagewise combines browser tabs and source editing with a persistent per-agent JavaScript VM in a separate utility process. Worker APIs send CDP commands, subscribe to CDP events, emit streamed output and create attachments that can be returned to agent context. This could make Wingman's frontend/TestMaster workspace far more capable for reproducing and inspecting UI problems. Integration would require an explicit binding between the owning organizational agent, tabs, mounts and artifact permissions. This VM's persistence is process-local and its timeouts are execution bounds, not a durable workflow engine. See [sandbox service](../repo/apps/browser/src/backend/services/sandbox/index.ts), lines 19–40 and 72–109; [worker APIs](../repo/apps/browser/src/backend/services/sandbox/sandbox-worker.ts), lines 309–409 and 594–628; [execution limits](../repo/apps/browser/src/backend/services/sandbox/sandbox-worker.ts), lines 664–716.

**Multiple provider/harness routes within one workbench.** Native direct models and ACP Codex/Claude Code/OpenCode can share UI primitives for messages, file edits, plans, images, approvals and usage. This offers a migration path or toolbench for non-Codex specialists, although Wingman's stated organization uses Codex. The adaptation cost includes handling divergent provider permissions, resume capabilities, plan formats and subprocess lifecycle. The normalization layer is substantial code, not proof all providers behave identically. See [ACP registry](../repo/apps/browser/src/backend/agents/acp/adapter-registry.ts), lines 1–18; [notification translation](../repo/apps/browser/src/backend/agents/acp/runtime.ts), lines 397–440; [Codex native-harness provider](../repo/apps/browser/src/backend/agents/providers/codex/stagewise-harness.ts), lines 150–172.

**Repository/worktree lifecycle and setup integration.** The workbench can create a worktree from the trusted main repository, remember pending setup, start setup after mounting, group chats by repository/worktree and detach removed paths from all conversations. Wingman describes parallel specialists but does not prescribe that isolation mechanism. These controls could support worker placement and cleanup, provided Wingman adds assignment ownership, merge/integration responsibility and a policy for preserving deliverables. Conversation forking alone shares paths, so it must not be confused with worktree isolation. See [worktree creation](../repo/apps/browser/src/backend/services/toolbox/services/mount-manager/index.ts), lines 811–843 and 920–927; [deletion](../repo/apps/browser/src/backend/services/toolbox/services/mount-manager/index.ts), lines 1072–1122; [grouping](../repo/apps/browser/src/ui/screens/main/_lib/agent-list-model.ts), lines 366–423.

**Credential substitution and mini-app interaction.** The sandbox exposes credential lookup through placeholders, and a host-scope fetch wrapper substitutes real values only for allowed origins while disabling automatic redirects for requests carrying placeholders. It also exposes open/close/send-message APIs for mini-apps. Those are richer application-integration primitives than Wingman's stated chat/tracker baseline. Reusing them would require binding plugin/credential authority to organizational roles and project context. Their specific protection is credential handling on this fetch path. It is not a demonstrated universal data-loss prevention system. See [worker credential/app APIs](../repo/apps/browser/src/backend/services/sandbox/sandbox-worker.ts), lines 358–368 and 411–455; [fetch origin validation and substitution](../repo/apps/browser/src/backend/services/sandbox/utils/credential-fetch.ts), lines 121–147 and 245–330.

**Conversation branching with attachment continuity.** Side chats and promoted forks copy conversation state and attachment blobs while retaining mounts. This can support exploratory product questions, alternative plans and investigation without overwriting the original discussion. Wingman would need to decide whether a branch represents a new worker identity, a temporary advisory session or merely a conversation branch; Stagewise does not make that organizational decision. See [branching](../repo/packages/agent-core/src/services/agent-manager/agent-manager.ts), lines 1397–1497.

## Distinctive mechanisms and grounded innovation assessment

The strongest mechanism is **versioned environment snapshots with rendered differences**. Each domain owns state capture, equality, prompt rendering and optional prompt guidance. On change the registry stores raw state, a full rendered keyframe and a rendered change; unchanged domains are omitted. Profiles explicitly select allowed domains, and adapter failures are isolated. This reduces repetitive prompt context and makes previous turns interpretable even when a current workspace/tab no longer exists. It is useful for Wingman's agent-session observability and future host separation. Its limits are equally important: captured state can be stale, failed domains retain earlier effective state, and the mechanism does not coordinate agents or execute remotely. See [contract](../repo/packages/agent-core/src/env/contract.ts), lines 24–78 and 117–191; [profile contract](../repo/packages/agent-core/src/host/host.ts), lines 108–143.

A second mechanism is **one canonical agent store with granular UI projection**. The bridge validates command coverage at attachment and forwards only relevant mutation patches into Karton. It gives a way to separate reusable agent logic from an Electron host while preserving efficient token/tool streaming. Wingman could use the same principle to make executive and detailed views derive from one source of truth. The current bridge is a local host/UI adapter; comments about future clients and remote use do not establish a distributed replicated organizational store. See [bridge](../repo/apps/browser/src/backend/services/agent-core-bridge/index.ts), lines 40–67, 96–125 and 179–202.

A third mechanism is **event-to-conversation continuation**. Watcher completion is converted into structured metadata and a normal queued user turn, using existing agent serialization and blocked-input semantics. This reuses one control path for both human steering and background follow-up. It is a good building block for operational monitoring. It needs durable event ownership, restart recovery, deduplication and a real supervision policy before it could serve ProjectMaster. See [watcher finalization](../repo/packages/agent-shell/src/engine/session-manager.ts), lines 1361–1398; [chat injection](../repo/apps/browser/src/backend/services/agent-manager/agent-manager.ts), lines 166–209.

A fourth mechanism is **inspectable full-history memory alongside compressed model context**. The writer tracks ID/content hashes and tail offsets to append new messages or repair the changing final message, forcing periodic full rewrites. This preserves detailed tool input/output for retrieval without repeatedly serializing the entire conversation. It is useful evidence continuity, but automatic transcript capture does not produce curated knowledge, executive summaries or a project decision model. See [writer state](../repo/packages/agent-core/src/agents/shared/memory/index.ts), lines 31–39 and 64–107; [rewrite/append paths](../repo/packages/agent-core/src/agents/shared/memory/index.ts), lines 431–535; [restart-tail test](../repo/packages/agent-core/src/agents/shared/memory/memory.test.ts), lines 749–779.

These are distinctive engineering choices within this checkout. This assessment makes no claim of historical invention or industry-wide uniqueness.

## Practical fit and remaining work

**Use directly as a workbench reference:** per-conversation history, queued steering, structured questions, approval state, live tool rendering, file/browser inspection, plan review and worktree navigation. Stagewise is especially useful when designing the detailed workspace reached from Wingman's agent directory. The extracted core/shell boundaries provide a more focused starting point than adopting the entire browser product.

Adapt before reuse:

- Introduce durable organizational agent IDs separately from conversation IDs.
- Represent roles, team and product membership.
- Bind multiple sessions to one standing agent.
- Preserve tool/provider permissions.
- Expose task/room/evidence links in the detailed UI.
- Replace local-only assumptions with host routing and durable shared coordination. Ensure forks and worktrees have distinct semantics. Operational recovery and watchers should feed a supervisor policy rather than being presented as that policy themselves.

**Build beyond Stagewise:**

- Telegram/Butler.
- project intake and registry.
- ProductMaster/TechMaster roles.
- specialist allocation.
- discovery/clarification records.
- product scopes/specifications/acceptance scenarios.
- shared ticket dependencies and ownership.
- agent rooms/direct messaging.
- management escalation.
- executive semantic summaries/timelines.
- product acceptance/delivery.
- periodic supervision and true Mac/Endeavour execution.

Generic extension hooks lower some implementation cost but do not supply these features.

There are also concrete adoption boundaries in this revision. `agent-core` and `agent-shell` package manifests identify version `0.0.0`, `private: true` and `license: MIT`. The root README identifies the complete application as AGPLv3. This is mixed repository metadata to resolve for the precise components chosen, not an assumption that the whole browser can be consumed under a package's declaration. See [core manifest](../repo/packages/agent-core/package.json), lines 1–9; [shell manifest](../repo/packages/agent-shell/package.json), lines 1–9; [README](../repo/README.md), lines 83–89.
