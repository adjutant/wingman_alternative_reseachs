Beads task management assessment

Repository: https://github.com/gastownhall/beads

Commit: 2edea9ced8c6f6124b6c157896ae53a0e09ff7be. Baseline: Shared task management for an agent organization. Review: November 9, 2026. Full local checkout; targeted static implementation and selected test-source review. Candidate applications, databases, dependencies, builds and tests were not installed or run.

Fit decision and assessment boundary

Beads is a substantial native task authority for agents, rather than a board-shaped interface over uncoordinated files. It implements durable issues, dependency-aware ready work, atomic claims, claim-next selection, hierarchical work, comments, change journals, revisions and claim leases with heartbeat/reclamation. CLI, Go role interfaces, HTTP and an included MCP adapter make those records accessible to agents. It is a strong candidate for the task-record component of the baseline.

It does not implement a complete agent organization. Actors are caller-asserted provenance, not authenticated worker identities. Revision guards are optional and do not establish a mandatory execution-attempt token. The service does not launch or supervise child workers, enforce worker capacity or bind qualified reviewer approval to a delivered revision. Its charter deliberately leaves orchestration policy above the issue primitives. See claim contract, lines 35–67, and project charter, lines 1–60.

Several distinctions materially affect adoption. A named claim and claim-next do different work: the latter selects from a ready set, while the former checks status/assignment eligibility without querying readiness. Durable claims have local leases; ephemeral work can be claimed without a lease or durable claim history. Close verbs have holder and pin guards that a generic status patch into a done state does not apply. These are source-level boundaries, not failures reproduced by running the product.

The repository is MIT licensed. The preserved checkout contains 5,315 tracked files. This review traces the shared task mutation bodies, Dolt wrappers/retries, ready/dependency predicates, leases and replicas, close/update alternates, HTTP authorization/events, molecule advancement and representative MCP forwarding. It is not an every-line audit of every command, tracker integration, migration, backup/repair path or storage driver. Source/test inspection does not establish successful installation, runtime concurrency, database durability, performance or live usability. See license and review ledger.

Architecture and data model

The task model includes title, description, design, acceptance text, notes, status, priority, type, assignee, human owner, dates, external references, metadata, labels, dependencies and comments. It also carries template/pin, async gate, formula/molecule and persistence-plane fields. A detail projection can expose an opaque lifecycle revision while generic issue JSON deliberately omits the internal row token. Lease fields are hydrated from a separate node-local table. This is richer than a minimal ticket/status schema, but it is not a separate task-versus-execution-attempt model. See issue model, lines 20–208.

Public roles separate lifecycle, reads, claims, ready claims, heartbeat, reclaim, graph operations and other capabilities. Common transaction bodies sit below storage adapters. A static public role inventory is retained separately from implementation-body coverage. The reviewed Dolt claim/ready-claim wrappers and embedded lifecycle wrapper delegate to those bodies rather than each implementing a different business rule. HTTP reaches role accessors, while the Python MCP client invokes the CLI for its claim operation. See claim role, ready-claim role, Dolt wrapper, embedded wrapper, lines 1–82, and MCP forwarding, lines 609–628.

Dolt provides the versioned store, in server and embedded configurations, with further unit-of-work/proxy layers. The workspace declares Go 1.27.3 and specific Dolt/driver dependencies. Contributor builds and test lanes use Bazel. The public issueops package also marks its compatibility contract experimental and asks embedders to pin an exact version. These are the pinned repository's requirements; no local build or database-mode compatibility result is claimed. See API stability, lines 1–6. See module metadata, lines 1–55, and contributor instructions, lines 121–180.

The source distinguishes an SQL transaction's durable branch working set from a later Dolt history commit. The operation funnel commits SQL first and then attempts the history commit. Failure of that trailing history step is logged rather than returned as though the task mutation failed. Concurrent sessions may also have one writer's history commit absorb another writer's rows under its message. Task events and version records therefore matter separately from grepping Dolt commit messages. See operation funnel, lines 11–103.

Lifecycle and alternate mutation paths

Creation validates an attempt-local request, loads prefix/status/type configuration, assigns an ID and wires parent/dependency records in one transaction. A guarded create refuses if its requested dependency edges were skipped; it does not report success with the relationship silently missing. Results are hydrated before the transaction returns. Configured infrastructure types and typed wisps can deliberately route to the ephemeral plane. A supervisor must choose that persistence class knowingly because it changes history and recovery. See create body, lines 37–137.

The ordinary ready reader derives filters through shared SQL builders and maintains a projection of blocked state. It excludes pinned and, by default, ephemeral work; it supports priority, type, assignment and deferred/hierarchy-related filtering. Dependency writes validate endpoints, type/hierarchy constraints and scheduling cycles, with a final batch cycle check. Those are implemented graph rules, not just instructions for agents. This review does not certify every concurrent graph interleaving or a merge of separately edited replicas. See readiness, lines 45–155; SQL predicate, lines 207–285; and edge checks, lines 246–483, plus final batch check, lines 226–254.

A direct named claim checks whether the issue's status and assignee are claimable and applies a row-token CAS. It does not ask whether dependencies are satisfied. A caller that wants select-and-claim uses claim-next, which reads candidate ready work, attempts claims and hydrates the winner in the same transaction. The scan can continue past a row a competing actor took, and an empty front is a normal result. It deliberately clears pagination/cap fields for its scan, so returning one issue does not imply the selection query did bounded work. See named claim, lines 48–145, and claim-next, lines 266–328; hydration, lines 47–118.

A successful durable claim grants one local lease and records claim/event/version state. Repeated same-actor in-progress claims return without refreshing that lease. Heartbeat is the explicit keepalive operation. A heartbeat refresh changes the lease row without reminting the task revision or writing noisy history; a rare missing-lease re-arm does remint and record a mutation so it conflicts with an ending claim. See claim post-state, lines 155–245, and heartbeat, lines 400–675.

Progress is a typed patch, notes merge/append, label/metadata change or comment. Expected revision/status/assignee checks are available and run inside the writing transaction. They are optional, and actor identity is not authenticated by them. An expected assignee can authorize a transfer based on known current state; force fields provide further explicit policy bypasses. These controls are suitable for a trusted coordinator but do not constitute hostile-worker authorization. See request contract, lines 254–365; guard execution, lines 138–253; and transfer predicate, lines 200–240.

The close role checks an optional revision, then template, pin and holder guards, followed by children and live direct blockers. Child-count policy writes coordination cells so a concurrent parent-child insertion cannot silently merge beside the stale close count without a conflict. The close deletes its lease, records a close event/version and recomputes affected blocked state. An optional flag can also close a completed molecule. This is meaningful controlled task state, even though it does not verify acceptance evidence or run a worker's tests. See checked close, lines 42–213 and 333–417; coordination cells, lines 1–60; and molecule caller, lines 328–368.

Generic update into a done category also checks child/blocker policy. It deliberately does not apply the close verb's pin or foreign-holder guard when only status changes. A client can therefore reach a done state for another actor's or pinned issue by using a status patch that the close verb would refuse. This is a traced public alternate path: HTTP accepts status in a patch and delegates to Lifecycle.Update, whose common body reaches the generic update. It is not inferred from an unused internal helper. See HTTP patch, lines 35–100; update execution, lines 138–253; and done crossing, lines 400–442.

CLI close adds a selected gate-satisfaction check before the role call. It checks GitHub run/PR, timer and bead conditions; a non-bead evaluation error emits a warning and permits close, while an unreadable bead condition refuses. The reviewed HTTP close calls the role directly and has no equivalent external-condition check. Gate issue state, parent completion and acceptance of a delivered artifact therefore remain distinct policies with different interface coverage. See CLI gate check, lines 683–755, and HTTP close, lines 20–95.

Recovery, replicas and stale writers

A lease's clock expiring does not itself change issue ownership or revoke the process. Reclaim selects sufficiently expired durable claims, repeats expiry/provenance predicates in its delete and resets the issue to open/unassigned with a fresh lifecycle token. A racing heartbeat can rescue the lease, while row-token rewrites make competing close/update/reclaim mutations conflict rather than silently cell-merge. The caller still needs to invoke recovery and reject stale writes through the available guards. See reclaim, lines 937–1066.

A generic update can set in-progress/assignee without arming a lease. The first legitimate heartbeat can re-arm that claim; until then, expiry-based recovery has no lease row to discover. Wisps remain a sharper boundary: claim-next can admit them explicitly, but they receive no lease and heartbeat refuses them. A vanished worker's ephemeral issue needs another release/finish or an external supervisor's recovery policy. See re-arm branch, lines 550–675; heartbeat refusal, lines 42–80; and ready-claim contract, lines 65–98.

Leases are node-local and excluded from Dolt history/replication. Imported snapshots can nevertheless materialize a lease with granting-node provenance. On a named node, reclamation protects positively foreign grants unless explicitly overridden. An unnamed node or unknown provenance uses the permissive default. Heartbeat refresh preserves an existing foreign node label, so renaming a node or importing a lease can require deliberate operator recovery rather than silently moving its enforcement authority. See replica rule, lines 864–920, and refresh provenance, lines 400–477.

One shared database/server can serialize competing claims. Two independent replicas do not share that live decision point, and node-local lease clocks are not a distributed fencing service. A supervisor that needs one task owner across hosts should define which authority grants work and how replicas exchange changes, rather than assume versioned data automatically gives globally exclusive execution. The storage driver's full merge/replication implementation was not audited here.

The lifecycle revision is equality-only and only partly covers record change. The source explicitly excludes some direct text, label, relationship and other changes from its complete coverage. It also exposes a generic issue JSON shape that omits the token, with detail/write responses carrying a separate revision where needed. Clients must use the right projection and send their expected value; an unguarded write has no stale-attempt rejection promise. See revision model, lines 75–102, and HTTP close response, lines 69–91.

Storage completion, retry and audit

The Dolt retry loop recreates the entire transaction on recognized serialization losses and selected pre-commit connection failures. It explicitly refuses to replay an indeterminate commit that may already have landed. That avoids converting an uncertain create/comment/claim into an automatic duplicate mutation. The caller may still need to reread state after the error; a new external claim-next request has no operation key in its request type that pins it to the prior winner. See retry boundary, lines 1283–1400, and claim-next request, lines 1–48.

The SQL task mutation and trailing Dolt history publication are separate stages. The funnel treats a failed trailing history commit as an audit-publication problem and returns the already-durable mutation as successful. It logs a metric/warning, and the changed rows can ride a later commit. A concurrent writer's history commit can also absorb this write under another message. This preserves the distinction between applied task data and one expected log line; it does not establish one immutable history commit per request. See funnel, lines 11–103.

The events API offers checkpointed change recovery with a configured journal, bounded pages, a published head and explicit retention-loss errors. It refuses a disabled journal instead of returning a misleading empty feed. Clients can checkpoint processed sequence records and reconcile after a truncation response. Heartbeat refresh intentionally does not produce a task-change journal record, while re-arm/reclaim do. This is a change feed rather than a recipient inbox or proof of work completion. See event handler, lines 12–184, and heartbeat recording boundary, lines 646–675.

Human and agent usability, permissions and design

The CLI's ready command explicitly distinguishes ready listing from atomic selection with --claim and supplies structured JSON for agents. Go roles and HTTP let clients avoid scraping terminal output. The included MCP claim client delegates to bd update --claim; it does not add a separate lock or ownership interpretation. The operating workflow is well suited to agents that can read issues and use precise mutation contracts. Live installation, terminal interaction and a human visual board were not evaluated. See ready command, lines 24–70, and MCP forwarding, lines 609–628.

HTTP defaults and validation favor a local automation service. Binding beyond loopback requires explicit opt-in and a token file, with a separately named insecure override. Accepted tokens are compared against cached SHA-256 digests and can be reloaded without restarting. This is service-access authentication: the request still supplies the actor and policy override fields. It does not enforce project-scoped leader/worker/reviewer roles or bind a worker identity to one bearer credential. See bind validation, lines 598–626; auth posture, lines 251–262; token check, lines 115–145; and actor contract, lines 63–100.

Shared mutation bodies, typed request/result contracts, copy-before-mutation and explicit refusal types are strengths. The close/update distinction and separate CLI gate checks also show the integration cost: callers cannot assume that every path to one final status applies every policy. A large command/storage surface, multiple persistence planes, proxy configurations, revisions, journal retention and driver publication semantics make operational expertise necessary. The HTTP update/close contracts also omit per-command hooks and auto-commit machinery; an automation that relies on CLI hooks must account for that interface difference. See HTTP update contract, lines 63–75, and HTTP close contract, lines 20–42. The project deliberately provides primitives that an orchestrator must compose into one organizational contract.

Test-source evidence and implementation limits

The selected ready-claim conformance body seeds durable and ephemeral work and asserts exactly one lease for the durable winner and none for the ephemeral winner. The heartbeat conformance body asserts that two refreshes do not invalidate a guarded write using the claim's revision. That heartbeat test explicitly skips when its fixture supplies no Lifecycle role; reading the test does not prove that a particular test lane ran it. See ready lease contract, lines 405–448, and heartbeat guard contract, lines 213–235.

The replica predicate test checks a named local node, an explicit any-replica override and the unnamed-node permissive case. It establishes intended SQL-fragment selection, not a multi-host recovery experiment. The HTTP close tests use fake role refusals and verify typed conflict mapping; they do not independently execute the database guards. The event test likewise verifies a typed truncation error maps to HTTP 410 with checkpoint-window fields. See replica predicate test, lines 16–82; HTTP close mapping, lines 1–125; and event error mapping, lines 201–239.

No candidate test, build or database service was run. The shared conformance framework is useful source evidence, while actual backend/runtime equivalence, graph races, crash durability, performance and platform support remain unverified here. The complete checkout and source ledger preserve the evidence needed for later experiments without presenting those experiments as already performed.

Adoption gaps and useful components

Beads can supply the central issue graph and coordinated local/shared-server task transitions for the baseline. Useful components include its atomic claim/ready-claim roles, explicit lease recovery, typed preconditions, parent-close coordination, change journal and common mutation bodies. Those are substantial implementation assets.

The layer above it must establish authenticated agent and execution-attempt identities, mandatory stale-result fencing, capacity and dispatch policy, child-worker supervision, immutable context/artifact references and revision-bound reviewer approval. It must also choose consistent close rules across status patches, close verbs, CLI gate checks and remote callers, and define explicit recovery for unleased/ephemeral work and replica authority. The issue tracker is a capable foundation; the full organization lifecycle remains composition and policy work above it.
