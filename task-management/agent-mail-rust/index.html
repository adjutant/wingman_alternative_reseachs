Rust Agent Mail task management assessment

Repository: https://github.com/Dicklesworthstone/mcp_agent_mail_rust

Commit: 49866939b1f52af5741bd3c87145d01846b93a38. Baseline: Shared task management for an agent organization. Review: November 9, 2026. Full local checkout; targeted static source and test-assertion review. Candidate applications, dependencies, builds and tests were not installed or run.

Fit decision and assessment boundary

Rust Agent Mail is a substantial communication and resource-coordination service for a trusted operator's agents. It supplies persistent project/agent identities, mail and shared project mailboxes, recipient receipts, ordered delivery events, keyed mutation retries, file reservations, build slots and operational inspection. It also has an automated controller for liveness and coordination advisories. These mechanisms can complement an agent task system.

It does not supply the baseline's complete task authority. The mailbox schema has no task/attempt/acceptance model. The embedded Beads command surface queries external issues through ready, list, show and status operations; the reviewed dispatcher does not add task creation, claims or completion there. Threads and reservation reasons can reference those external issue IDs. Those links do not make a message acknowledgement, file lease or controller decision an accepted task result. See mailbox schema, lines 15–165; Beads commands, lines 1207–1273; and dispatcher, lines 22863–22926.

This implementation must be assessed separately from Python Agent Mail. The Rust reserve path excludes conflicting paths and rechecks grants inside a transaction. It also implements inbox event cursors and idempotency keys that are absent from the inspected Python send interface. These are concrete implementation differences, not a general reliability ranking. The Python assessment retains its own revision and evidence limits.

The pinned license has an OpenAI/Anthropic rider, and workspace metadata identifies LicenseRef-MIT-Rider. It is not classified here as unrestricted MIT or unqualified open source. That adoption constraint is separate from the technical assessment. See license and workspace metadata, lines 1–70.

The review covers core schema/type inventory, tool registration, registration and session/lifecycle authorization, message persistence and archive dispatch, event cursors, file and slot leases, selected HTTP/browser checks, representative TUI structure, Beads query dispatch and selected tests. The complete 3,928-file checkout was preserved, but this is not an every-line audit of its search engines, repair framework, export/crypto stack, installers or controller mathematics. No live interface, performance, crash-recovery or accessibility acceptance was established.

Architecture and authority

The workspace separates core configuration/types, database access, Git storage, tool implementations, server/TUI, CLI, guards, search, sharing and test support. Tools run through FastMCP and the Asupersync runtime. Database work uses SQLModel/FrankenSQLite dependencies; storage and operational recovery include additional layers. The source pins a nightly toolchain and declares Rust 1.100. The specialized dependency graph increases the need to validate the actual production feature build before adoption; no build result is claimed here. See workspace, lines 1–100, and toolchain.

The static catalogue records 45 tool names in TOOL_CLUSTER_MAP and 33 resource-handler registrations in the server builder. Resource handlers include exact/query variants, so 33 is not a count of independent logical products or workflows. The tool builder applies configuration filtering before registration. The inventory reads literal declarations without compiling or executing the candidate; older descriptive counts do not override these declarations. See tool map, lines 3893–3973, and builder/filter, lines 635–704 and 965–1036.

Persistent mailbox entities include projects/products, agents, messages, direct recipient state, project-addressed deliveries and receipts, file reservations and release state. Migrations also declare event cursors, delivery-signal receipts, idempotency records and controller state. Agent records retain focus and lifecycle information, but do not identify an execution attempt with its own immutable inputs, lease token and accepted output. See schema declarations, agent row, lines 122–164, and reservation row, lines 377–435.

The database is authoritative for message and reservation state. Git/archive publication can lag message persistence through a write-behind queue and retry backlog. Reservation grants have a stronger foreground requirement: their guard-visible JSON must be published before successful admission, although the database lease may already have committed when publication fails. These are distinct durability contracts. See message dispatch, lines 48–158; reservation publication, lines 329–399 and 2630–2778.

Work lifecycle and enforcement

A leader creates a project namespace and agents register identities with program/model and focus metadata. Registration generates a token and can rotate an existing named identity's token. By default this is a self-asserted trusted-local identity model, not proof that a specific process or human owns the name. Optional session binding restricts a session that already holds an identity from acting as another identity in that project. A fresh unconstrained session still has the trusted-local fallback described by the implementation. See registration/token policy, lines 2924–2968 and 3035–3288; session authorization, lines 317–386.

An optional registration proof gate is wired before explicit identity writes, with separate rejection of implicit registration when enabled. It is disabled by default. This review traces the caller and interface; it does not certify its cryptography, issuers or deployment key management. A signed identity grant would still not establish a task's acceptance criteria or the revision delivered by one attempt. See gate caller, lines 3075–3124, and proof interface, lines 1–100.

Task selection remains in the external issue system. The included Beads dispatcher sends read-oriented requests and renders issue summaries. There is no mailbox transaction that claims a ready issue and reserves files together. The coordinator must resolve that split across systems and decide which failure leaves work assigned, reserved or merely announced. See Beads dispatcher, lines 22863–22926.

File reservation validates count, TTL, scope and patterns, resolves the actor and checks session context. It builds a current conflict view and proposes only clear paths. The database then begins an immediate transaction, checks idempotency and agent lifecycle, repeats conflict detection and inserts or renews leases. A late conflict is rolled back and converted to a structured conflict response by the tool. This is stronger than a read-only preflight followed by unconditional inserts. See validation/entry, lines 1989–2178; grant path, lines 2330–2485; and database checks, lines 15506–15655.

This lease protects a named edit surface among cooperating callers. It does not stop direct filesystem edits, enforce a task owner, or reject a late result from a worker whose reservation expired. Build-slot leases are weaker admission signals: under their local slot lock they report conflicts and still write a granted lease. Their atomic temporary-file replacement and propagated I/O errors improve persistence but do not make the slot single-winner. See slot locking/write, lines 240–337, and grant, lines 435–488.

Agents communicate progress and questions through messages. The send path distinguishes token/session-verified senders from unverified local names and can require proof under a fail-closed profile. Message creation deduplicates recipients and groups row insertion and optional idempotency result in a database transaction. Archive publication and notification signals happen afterward. A task supervisor must treat the durable mail record, signal receipt, worker outcome and accepted deliverable as separate facts. See sender verification, lines 2523–2625; transaction, lines 8926–9045 and 9630–9758; post-commit effects, lines 3798–4008.

Recipient acknowledgement and reservation release update communication/resource state. They do not evaluate tests, pin artifacts, enforce child completion or close an external issue. Retiring or deregistering an identity also does not cancel a worker process. HTTP lifecycle calls require the registration token; a same-user stdio pane can supply a different local proof path. See lifecycle authorization, lines 2231–2318; transport stamping, lines 17460–17535; and ACK/release, lines 6270–6378, and release entry, lines 2790–2880.

Recovery and concurrency boundaries

Database retries are stronger than external-effect replay

The reservation idempotency record is committed with its lease rows. A replay returns the historical grant and checks current conflicts/coverage instead of silently acquiring newly available paths from an old partial request. The message path similarly records its key with the message and skips one-time indexing, signal and archive dispatch on replay. These are meaningful protection against duplicate database work after an uncertain response. See reservation replay, lines 2404–2485 and 2630–2725; key commit, lines 15770–15806; and message replay, lines 3798–3886.

They do not make post-commit side effects exactly once. A crash after the message transaction but before a signal/archive enqueue can leave those effects absent; replay deliberately skips them. Background archive recovery is a separate mechanism and must converge the missing materialization. The reviewed dispatch fallback explicitly distinguishes durable backlog entries from ephemeral entries and dropped operations. The database message can remain valid in all three cases. No crash experiment or complete proof of background convergence was performed. See archive dispatch outcomes, lines 48–92, and effect ordering, lines 3880–3993.

A failed reservation reply can follow a committed grant

A fresh lease can commit before guard-visible JSON publication fails. The foreground path reports a typed publication error, with committed IDs and recovery guidance, rather than reporting successful edit admission. It does not roll back that database lease as though nothing happened. Renewal can repair publication, and exact keyed replay checks coverage before certifying the historical grant. See publication contract, lines 329–399 and 2630–2778.

This is a deliberately recoverable partial state, not an atomic database-plus-filesystem transaction. Another agent can see the committed reservation while a local guard artifact is missing. Callers must inspect the error's committed IDs and follow its recovery path rather than switch to a new request key or assume the lease never existed. The selected regression test creates that disk-pressure state and checks replay refusal and renewal guidance. See regression, lines 4271–4385.

Cursor delivery is distinct from inbox snapshots

The event reader uses one read snapshot for retained range, cursor state and visible events. It orders by independent delivery sequence, returns one extra row to determine continuation, and distinguishes a future cursor from a cursor whose relevant history was pruned. It also includes shared project-mailbox visibility rather than treating a missing shared schema as an honest empty page. See event query, lines 1014–1210, and tool response, lines 5462–5606.

This directly addresses monitoring gaps that a bounded newest-first snapshot cannot solve by itself. The caller must still store next_cursor only after handling the returned page and explicitly recover from retention loss. An event says mail was delivered; it is not an execution checkpoint or task acceptance event. The selected test checks two-page ordering, independence from read receipts and explicit ahead/expired errors. See cursor test, lines 3002–3087.

Expiry and release protections are scoped to reservations

Force release evaluates activity and then supplies the observed expiry to the database mutation. A changed lease can cause a conflict instead of allowing an old heuristic decision to release a renewed lease. Degraded release replay also has creation and optional holder-activity cutoffs to avoid releasing a newer acquisition or revived holder merely because an old queued release-all exists. These safeguards should not be conflated with fencing an old worker's task updates. See force release, lines 3372–3442, and replay-cutoff API, lines 16215–16275.

ACK/release calls can durably queue future intent during selected database failures. The entry paths capture session authorization first and refuse unresolved actors when that context is constrained. A queued intent is a pending future mutation, not a completed database acknowledgement or released lease. The complete intent file verification and replay machinery received only targeted boundary review, not an exhaustive audit. See release entry, lines 2790–2880, and ACK entry, lines 6270–6378.

Generation markers are not execution-attempt tokens

Reservation artifacts can carry a database-generation marker so reused numeric IDs from reconstructed databases are distinguishable from older files. Session bindings compare project, ID and canonical name, but explicitly do not identify a new database generation whose values all remain the same. Neither marker issues a new per-task attempt token that every progress/result write must present. See artifact replay checks, lines 2630–2725, and session binding, lines 78–102.

Permissions, controller and human operation

Defaults bind HTTP to loopback, leave fail-closed sender proof and session identity disabled, and document a trusted-local operator. Naming an existing agent can rotate its registration token under the default registration model. Optional session restrictions and proof-gated registration strengthen particular paths, but do not make a shared OS account or bearer token a hostile-client isolation boundary. Project keys are also client-selected. See defaults, lines 1716–1720 and 1797–1798; token rotation, lines 2924–2968 and 3250–3288; security model, lines 31–43.

The HTTP server applies reader/writer checks to tool calls and separately gates browser POST mutations with CSRF and configured writer roles. This is an explicit alternate-interface boundary, rather than an assumption that all ordinary browser requests look like MCP calls. Lifecycle transport stamping also overwrites a caller's claimed transport so an HTTP request cannot select the stdio pane-only authorization rule. These controls were traced in source and selected tests, not exercised on a deployed server. See browser guard, lines 12524–12565; MCP guard, lines 13333–13408; and transport injection, lines 17460–17535.

The automated controller has typed advisory, reservation-release and probe actions. Its current module adds epoch/report admission so a reset or stale report cannot simply spend a newer in-process notification budget. The reviewed action type does not launch a worker, create a child issue, submit a result or close a task. Load-routing concepts in the engine are therefore not credited as a complete task scheduler. The statistical model, policy calibration and every runtime delivery effect remain outside this targeted review. See controller admission, lines 1–70; action type, lines 12376–12381; and load actions, lines 388–443.

The 16-screen registry provides stable screen IDs, keyboard jump keys and ordered navigation for mail operations. It includes messages, threads, agents, search, reservations, health, history, projects, attachments and controller inspection. This is useful situational awareness, but it does not supply a native agile board or acceptance dashboard. Representative registry and handler source cannot establish visual quality, screen-reader behavior or day-to-day operating ease. No candidate terminal or browser was launched. See screen registry, lines 1–170.

Design quality, tests and adoption work

The separation of tool, database, storage and server layers makes several contracts inspectable. Strong examples include conflict checks inside the reservation transaction, keyed mutation/result commits, explicit cursor-loss responses, guard-visible publication errors and transport-owned lifecycle policy. The design also has substantial complexity: database snapshots, caches, archive queues, retry journals, JSON guard artifacts, session context and controller epochs have different lifetimes and authorities. Their relationship needs operational verification, not only unit-level reasoning.

Several comments and reference tables retain earlier counts or durability descriptions. The report uses live registration and mutation code where these differ. The foreground reservation path and best-effort message path are a concrete example: a general statement that every successful call means a completed Git archive would be wrong. The pinned source's large modules also make change review costly even with workspace-level separation.

Selected test bodies establish intended contracts, not executed results. The reservation conflict test checks exact/glob/ancestor conflicts, excludes the caller's own and expired/released/shared reservations, and compares before/after state for a read-only check. The publication regression checks a committed but unpublished lease and keyed replay recovery guidance. See conflict test, lines 5309–5455, and publication test, lines 4271–4385.

The cursor test checks ordered pagination and explicit retained-history failures. The lifecycle test expects HTTP pane assertions without tokens to be refused with a structured explanation. The browser role test expects reader/unknown and unconfigured writer labels to be refused before creating a cold mailbox or archive state. These selected assertions do not certify every JWT configuration, replay interleaving, deployment or repair operation. See cursor test, lines 3002–3087; lifecycle test, lines 151–208; and browser test, lines 25880–25945.

For adoption, this is a communication/resource service to pair with one authoritative task/attempt system. Retain its ordered inbox events, explicit delivery facts, scoped idempotency and reservation diagnostics as useful components. Add or integrate authenticated task claims, worker capacity, supervised children, durable execution checkpoints, stale-attempt result rejection and revision-bound review. Define how those task transitions and mail/resource side effects recover when only one system commits.

Before operational selection, validate the production feature build, supported platforms, sustained multi-client behavior, archive convergence under crash/disk pressure, recovery authority and usable human controls. Those are unresolved validation needs, not failures established by this static review. The pinned license restriction also remains an adoption constraint. The service has deep coordination mechanisms, while the full organizational task lifecycle remains outside its authority.
