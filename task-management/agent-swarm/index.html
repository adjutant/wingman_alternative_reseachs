Agent Swarm: a coordination runtime with uneven task transition rules

Source: https://github.com/desplega-ai/agent-swarm

Reviewed commit: 6aff700f53755cb71bd6a1aa2e2fa1da9586b892. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

Agent Swarm implements much of the desired agent organization. A lead can create durable assignments, route work to specialized workers, receive follow-ups and request human decisions. Workers use one server authority. Task lineage, dependencies, capacity, progress, session records, recovery and a human dashboard have substantive implementations. This is a candidate coordination runtime, rather than only a human board with an agent adapter.

Its most important limitation is inconsistent enforcement across paths. Manual task claims check dependencies. Automatic pool claims select by routing and model compatibility without that readiness check. The normal MCP completion path validates structured output, while fresh HTTP completion does not perform the same server validation. Ordinary task completion does not join accepted child results. The workflow engine supplies stronger execution fences and explicit validation or human approval nodes, but those guarantees do not automatically govern every task.

The source is useful for a shared execution organization if adoption includes a transition-policy consolidation. Retain the server authority, explicit worker identity, lifecycle inspection, continuation records and workflow machinery. Add consistent readiness and ownership admission, current-attempt credentials and result-bound acceptance before treating an ordinary task's completed status as a verified organizational outcome. The repository declares MIT in the package, lines 1–34, and the license, lines 1–17.

Scope and evidence level

The preserved worktree has 6,392 tracked files. This review follows task creation, routing, claim, progress, delegation, completion, cancellation and recovery. It inspects the task/agent/repository/session model, database transaction implementation, selected MCP and HTTP mutations, output validation, workflow checkpoints and approvals, channels and read cursors, heartbeat recovery, provider launch configuration, representative dashboard query/view/mutation code and deployment manifests. Selected test assertion bodies were read.

No candidate application, installation, build, migration or test was executed. The ledger identifies the actual inspected ranges, including partial large files. This is not an every-line audit, security certification or verification of all providers, integrations, migrations, extension handlers, script sandboxes, storage services, browser behavior or production races. Earlier Wingman experiments remain historical evidence under their original scope; they are not new executions for this assessment.

Architecture and domain boundaries

The server combines TypeScript/Bun interfaces with SQLite persistence. Database initialization, lines 73–139, enables WAL, foreign keys, a busy timeout and NORMAL synchronization. The transaction implementation, lines 404–481, serializes a transaction, starts BEGIN IMMEDIATE, commits or rolls back and schedules after-commit hooks. This gives a meaningful place to combine selection and acquisition. After-commit callbacks are not themselves a durable delivery queue.

Task fields, lines 667–855, include stable IDs, assignee, creator, status, priority, dependencies, parent, result/progress/failure text, repository and source context, routing affinity, output schema and workflow links. The lifecycle distinguishes unassigned, offered, pending, in-progress, paused and terminal work, with draft/backlog and superseded states as well. An offered task can reserve a worker through a separate offered-to field.

Agents, lines 1307–1346, have durable IDs, lead status, roles, capabilities, instructions and capacity. Active sessions, lines 2133–2150, separately identify runner/provider sessions, runtime identity and heartbeat time. These are stronger domain boundaries than equating a task assignee with a terminal session. They do not introduce a required task-attempt generation on every mutation.

Repository records, lines 2036–2085, hold URL, clone path, branch and repository guidelines. Tasks also have context keys and source references. These help organize several repositories and work streams, but the inspected model does not provide the baseline's complete project registry, project-level leadership and isolated project authority. A swarm-wide lead role and repository association need additional governance to represent several concurrent managed projects.

Creation, selection and ownership

Task creation, lines 2505–2599, chooses initial state and begins inheritance from a parent. The insertion transaction, lines 2890–3044, combines workflow actionability checks, task insertion and routing decision capture. Dependencies are stored as task IDs. The transaction addresses particular duplicate tracker work; it is not proof that all arbitrary create requests have one universal idempotency key.

The send-task tool, lines 396–430 and 482–554, resolves parent context, checks attachment/routing constraints and constructs creation options. Later handling, lines 581–628 and 656–705, checks recent or tracker-related duplicates and creates work transactionally. Agent instructions can request research, planning and implementation children. The parent pointer itself is not a dependency edge or a completion join.

Manual claim, lines 340–451, performs a transaction containing task state, capacity, dependency, affinity and runtime checks. The low-level claim, lines 3107–3161, updates only an unassigned task and assigns the winning worker. Capacity counting, lines 538–560, includes in-progress work and reviewing offers. This provides a real atomic ownership transition when callers use this path; selecting a task in a list is not that transition.

There is a specific readiness inconsistency. Assigned pending selection, lines 161–204, checks dependencies. Automatic pool selection, lines 548–662, obtains eligible IDs, applies admission and claims a candidate. Its candidate helper, lines 3610–3642, filters unassigned tasks through routing eligibility and a supplied callback. Routing eligibility, lines 642–679, checks affinity/role/capability constraints. The pool callback, lines 107–122, checks harness compatibility. None of those checks dependency completion. The separate dependency function, lines 3648–3667, is therefore not applied to this pool claim chain. A blocked pool task can be acquired through this path. This is a static path finding, not a reproduced runtime test.

Admission also varies by path. Budget admission, lines 64–133, considers global, agent and requester spend thresholds. Poll applies budget admission, and offer acceptance, lines 455–533, starts a budget check. The inspected manual claim branch has capacity/readiness checks without that same budget call. Cost policy should not be inferred from the presence of one admission helper.

Progress introduces another boundary. Legacy progress rights, lines 238–251, allow an assignee, lead, user or operator, and allow an ordinary agent when the task has no assignee. Explicit task selection, lines 231–267, avoids the omitted-task lookup restrictions. The transaction, lines 377–415, reloads the agent/task and applies those rights. Progress persistence, lines 1188–1211, can move a nonterminal record to in-progress by ID without assigning it. Completion persistence, lines 416–479, can finish a nonterminal record without requiring prior claim. Thus the reviewed registered-worker/legacy tool path does not make claim acquisition a universal prerequisite for writing an unassigned task. Token posture or a configured extension can impose additional restrictions; this finding is not a claim that every credential can access every task.

Delegation, context and acceptance

Deferral, lines 287–452, validates watched tasks, creates a scheduled continuation and completes the current task in a transaction. This releases an execution slot while waiting. It is a useful alternative to leaving an idle worker in progress. It also shows why completed can mean that a segment deferred its work, rather than that the original goal has been accepted.

Terminal effects, lines 27–174, arrange memory/rating work and lead follow-ups, with a separate workflow boundary and caught failures. Resume follow-ups, lines 474–662, retain parent linkage, model/routing intent and resume-generation tags. These are durable continuation records once created. A successful primary task write does not certify that every later memory, rating or lead-notification effect succeeded.

The context preamble, lines 31–49 and 112–198, walks a bounded ancestor chain and selects prior description, output, artifacts and recent logs within a token budget. Provider resumption, lines 1–75, deliberately produces a fresh session rather than a native provider resume. This preserves inspectable continuity while bounding prompt cost. It cannot restore all former conversation or external process state.

MCP completion, lines 503–620, short-circuits repeated terminal writes, validates a configured output schema and performs citation checks. Citation problems refuse completion at most once per task. Later completion can proceed with unresolved references dropped or reclassified. The schema validator, lines 1–100, implements a subset of JSON Schema; supplying arbitrary schema keywords does not make them enforced acceptance criteria.

Fresh HTTP completion follows a weaker path. The finish route, lines 1673–1815, checks identity/state and calls the terminal guard, then completes an in-progress task. It does not apply the MCP path's fresh output-schema validation. The terminal guard, lines 25–130, handles an already terminal result, including explicit text corrections; it leaves fresh completion to its caller. Runner completion, lines 1853–1985, attempts client-side output validation/extraction before posting. That client behavior does not protect a direct HTTP caller. Neither ordinary completion path requires accepted children or a reviewer decision tied to an immutable result revision.

Authored workflows provide a different contract. Agent-task execution, lines 56–89 and 109–159, correlates a task with a workflow step and waits asynchronously. The engine, lines 843–902 and 1120–1228, creates step identities, carries retry fences and applies output/validation rules before checkpointing. Checkpoint writes, lines 1–102, verify the current running step, retry count, live run and uncancelled lineage inside the transaction. An outdated step execution cannot commit through that fenced call. This is a substantive stale-attempt mechanism within workflows, rather than a universal fence on arbitrary task progress.

Human approval nodes, lines 35–143 and 237–335, support approver policies, waiting and separate resolution ports. Approval responses, lines 493–552, check the responder, pending state, deadline, workflow actionability and listed approvers. Resolution persistence, lines 9951–10009, changes only pending requests, with an optional actionable-workflow condition. These mechanisms can enforce a designed approval flow. They should be used explicitly where acceptance matters; lead prompt instructions about review and merge are not equivalent enforced rules for ordinary task completion.

Communication, escalation and recovery

Message posting, lines 4068–4136, persists channel messages, replies and mentions, records an event and schedules a worker nudge. The tool, lines 17–75, exposes posting and then marks the channel read. Message reading, lines 74–178, can load unread messages, select the most recent limited batch and advance the channel read state. The stored cursor, lines 4222–4293, uses the current timestamp, while unread retrieval filters by creation time. Consequently, older unread entries omitted by a limit—and potentially messages arriving between fetch and cursor update—can be marked read without being returned. Posting also advances this cursor without first reading the other messages. Records remain in history, but unread state is not a reliable per-message acknowledgement protocol.

Worker nudges, lines 1–22, are best-effort realtime signals. Durable task/message queries provide later inspection, but do not turn each nudge into replayable event delivery. Human input, lines 85–134, creates typed questions with source-task linkage or a detached mode. The response path, lines 722–741, emits a resolution and requests a standalone follow-up. Asking a question returns promptly; use a deferral or workflow wait when the execution must actually yield.

Lead checklists, lines 1796–1862, create management work when the lead has nonempty heartbeat instructions and no active checklist task. A configured gate can suppress quiet ticks. This is a useful supervisor loop, but the decisions in its prompt still need a working lead execution and usable organizational instructions.

Heartbeat thresholds, lines 125–164, distinguish fresh claims, quiet tasks, missing sessions and stale session heartbeats, with a default maximum of three resume generations. Classification, lines 513–595, examines task/session state rather than only whether an HTTP endpoint responds. Recovery, lines 764–830, compares the task's last-update value before superseding or failing it. New progress can defeat the stale decision. Boot recovery, lines 894–1006, includes fresh-claim and heartbeat guards. Gap repair, lines 658–700, revisits superseded work whose resume record or dependency settlement was interrupted.

Dependent settlement, lines 908–956, repoints never-started dependencies to a resume task or propagates terminal failure. Failure cascading, lines 3704–3733, uses a visited set. This bounds traversal of an existing cycle; it does not demonstrate that creation rejects dependency cycles. Recovery can requeue useful work, but ordinary writes still lack a required generation token to reject every surviving old session.

Cancellation, lines 689–813, records a guarded terminal state, schedules notification effects, promotes pending steering and can fail dependents. The runner, lines 5350–5415, observes terminal/cancelled tasks, aborts the local session and eventually releases its slot after a grace period. Releasing a slot is not proof that an operating-system process stopped. Database cancellation cannot reverse a pushed commit or an external request already issued. Pause/resume persistence, lines 1003–1076, changes task state; it should not be interpreted as a universal process-freeze primitive.

Access, human inspection and operation

Authentication, lines 1–72, distinguishes the shared operator key, active user tokens and ephemeral session credentials. Session token resolution, lines 887–973, checks hashed credentials, revocation and expiry and returns bound agent/task/runtime identity. HTTP admission, lines 458–641, binds credential identity and applies session posture/access checks. Tool hooks, lines 976–1055 and 1069–1159, can block or modify an MCP call before its handler. That extension point does not by itself impose ownership or readiness. These are meaningful protections. A common shared key plus caller-supplied agent identity is a broader deployment trust boundary than individually constrained credentials. The example worker configuration should not be mistaken for project-isolated authentication.

The runner launch, lines 7620–7665, registers an active session before spawning the provider with task/runtime context. Codex configuration, lines 593–613, requests no approval prompts and danger-full-access execution. Adapter selection, lines 2510–2529, defaults to subprocess sessions and disables native resume. Container/workspace/credential isolation therefore matters; the task database alone is not a sandbox for the worker's side effects.

Dashboard task queries, lines 1–123, support filtering and lineage. Global query defaults, lines 1–71, use ten-second polling and a persisted cache configuration. The task page, lines 107–154 and 370–489, offers search, filters, page sizes, board/table modes and a small-screen list. The board, lines 1–118, disables drag sensors and displays the supplied task page. Its columns and counts are not an all-project snapshot when only one page was fetched.

Detail loading, lines 379–402, stops repeated log/context reads for terminal tasks. Detail rendering, lines 775–843, offers a transcript, raw session log and citations. Pause mutation, lines 463–496, snapshots affected queries, rolls back on error, applies the authoritative response and invalidates afterward. That is a useful failed-save pattern, though it does not prove that every mutation and view reconciles identically. No browser, keyboard, mobile or accessibility acceptance was performed on the candidate.

The API container, lines 1–100 and 150–191, builds with pinned Bun, bundles script runtimes and persists database data separately from code. Example API configuration, lines 250–283, mounts only the data directory and an encryption secret. Worker configuration, lines 290–338, connects a lead to the API and file service and supplies provider credentials. Identity initialization, lines 54–72, persists an agent ID on its personal workspace. Multiple hosts can share the API authority, but file paths, repository clones and credentials must be made appropriate for each host.

Version guidance in the example, lines 28–48, warns that an unpinned image follows latest and migrations are forward-only. Database backups, encryption keys, workspace state, file-service storage and compatible API/worker versions are operating concerns. The inspected SQLite and container paths do not establish replicated control-plane availability or validated upgrade/restore procedures. The combined system has more operational surface than a file-backed task list, in exchange for substantially deeper execution and recovery support.

Test-source evidence and adoption work

Capacity assertions, lines 36–82, count active tasks and check remaining room. Budget assertions, lines 244–316, expect refused work to remain unassigned and one winner for two sequential polls. The test named a race uses back-to-back awaited polls; it is not a concurrent stress experiment. Trigger claiming assertions, lines 303–350, likewise check repeated sequential acquisition.

Stall-CAS assertions, lines 25–80, inject fresh progress before remediation and expect the task to remain active without a resume child. Completion assertions, lines 1–105, check first-result preservation and duplicate history behavior. Cascade assertions, lines 156–189 and 234–263, exercise a manually injected cycle and dependency repointing. These are useful, specific intended contracts. They were read, not run, and do not establish that the alternate interface gaps above are covered.

Before adoption, route manual claims, poll claims, progress and completion through shared transition functions. Apply the same dependency/cycle policy and admission checks, and require ownership acquisition before worker writes. Bind worker mutations to a current attempt and revoke that authority when recovery replaces an execution. Preserve the workflow fence design and expose its guarantees clearly in ordinary task operation.

Add an explicit accepted-child join and result-version-bound review where required. Make fresh output validation server-side across all completion interfaces. Replace time-of-read cursor advancement with acknowledgement of the actual returned message boundary. Make pending post-commit handoffs visible and recoverable. Add project records and authority boundaries if one swarm must manage several projects. Verify installation, credentials, process cancellation, multi-host files, backup/restore and representative human workflows before relying on this as the organization's sole work authority.
