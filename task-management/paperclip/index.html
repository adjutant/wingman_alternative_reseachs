Paperclip: an agent work authority with distinct runtime guarantees

Source: https://github.com/paperclipai/paperclip

Reviewed commit: 46fb933b0155d183ce64a8bdc4950d1b58c926f6. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

Paperclip implements much of the desired agent organization directly. Companies contain projects, goals, agents and issues. Tasks connect responsibility to execution runs, sessions, workspace context, discussion, dependencies and results. The native runner adds bound mutation authority, durable operation receipts, completion contracts, evidence assessment, status decisions and recovery records. These are substantive coordination mechanisms rather than a board that merely launches a coding session.

The guarantees depend on the execution profile and entry point. Native runner tools have stronger current-run and replay checks than an ordinary legacy write. A durable parent relationship does not require every child result to be accepted before its parent finishes. Per-agent dispatch controls do not establish cluster-wide project capacity. Completion can use an agent-claim policy unless a stronger review policy is configured.

Treat this as a serious integrated candidate for the shared authority. Adoption still requires selecting one execution policy, governing alternate writers, defining child acceptance and validating recovery across the intended hosts. Do not transfer native-runner guarantees to every adapter or API caller. The inspected license, lines 1–21, grants MIT rights subject to its notice and disclaimer.

Scope and evidence level

The preserved checkout has 14,032 tracked files. This targeted static review follows issue creation, child creation, dependency checks, checkout, update, native tool mutations, completion policy, cancellation and selected recovery paths. It inspects agent/run/task schemas, authentication branches, per-agent dispatch, the project-admission boundary, documents, activity persistence, durable interaction/delivery records, representative CLI/browser source and server database startup. Selected test assertions were read.

No candidate application, dependency installation, build, migration or test was executed. The ledger records the actual inspected ranges. This is not an every-line audit of providers, remote runners, plugins, chat transports, all bulk/import/admin routes, workspace finalization, all approval and budget paths, deployment, accessibility, performance or production races. The historical Wingman report remains separate from this task-management assessment.

Architecture and authority

Projects, lines 1–43, retain company, name, description, status and leadership context. Agents, lines 1–60, have durable identity, reporting relationships, adapter/runtime configuration and budget-related fields. Issues, lines 35–110, retain hierarchy, assignment, execution linkage, source context and policy. Project leadership, agent identity and task ownership are related records, rather than interchangeable names for a process.

Heartbeat runs, lines 1–107, record the execution attempt, runtime/session/controller data, context and terminal information. Completion contracts, lines 1–59, retain revisioned policy and content hashes. This gives the native path a durable foundation for reasoning about which attempt and which contract produced an outcome.

Runtime selection is a material boundary. Profile resolution, lines 1–175, selects native execution through the paperclip_runner adapter and checks rollout, provider, work mode and agent status. A direct adapter can remain on the legacy profile even when configuration contains older native settings. The report therefore separates native tools and finalization from shared issue services and legacy mutation guards.

The design uses PostgreSQL transactions and explicit modules for authority, completion, evidence and recovery. Some central issue, route and runner-authority files are very large. This does not prove a defect, but it raises the cost of auditing alternate paths and keeping policy consistent. The code's own execution-admission boundary is a useful example of resisting a premature public guarantee: storage exists before enforcement is enabled.

Create, select and claim

Child creation, lines 9656–9729, can reuse a durable idempotency key, checks that it belongs to the same parent and validates reuse policy. The optional parent blocker, lines 9770–9820, is a distinct operation. Native task creation, lines 1724–1825, constructs trust/review policy, assignment, origin identity and dependency context. It explicitly sets blockParentUntilDone: false.

This distinction matters for delegation. An agent can create a child and continue coordinating other work. It cannot infer from that relationship that the server will hold the parent until all children have passed review. Use explicit blocking relationships where execution ordering is required, and define a separate result-acceptance rule when that is the desired parent contract.

Dependency readiness, lines 2719–2803, treats unresolved blockers as an admission obstacle. A cancelled blocker is not equivalent to a done blocker. A nominally done prerequisite with pending workspace finalization can also remain unready. Cycle traversal, lines 7598–7676, checks whether the proposed relation reaches its source. These are implemented graph rules; this static review does not certify every concurrent graph mutation or finalization race.

The checkout route, lines 16396–16519, checks issue access, project pause, agent self-checkout, assignment authority and run context, and handles workspace generation rules before calling the issue service. Checkout persistence, lines 12168–12432, conditions the update on eligible state, assignment and execution ownership. It can adopt compatible existing checkout state and returns a conflict when another owner wins. This is materially stronger than an unassigned read followed by an unconditional assignee write.

The CLI commands, lines 1294–1341, parse agent/expected-status input and call the same HTTP checkout endpoint; release calls the corresponding endpoint. The CLI does not create an independent local ownership store. This is useful for agents on different execution hosts that can reach the service.

Ownership, capacity and alternate writers

Route ownership checks, lines 5645–5845, distinguish the actor's active checkout, unassigned work, allowed idle foreign work, watchdog scopes and override cases. The active own-checkout branch calls the ownership assertion. These branches must not be summarized as a requirement that every issue edit belongs to the current execution attempt. Human management and some service operations intentionally have different authority.

Signed run authentication, lines 373–468, rejects a conflicting supplied run identifier and derives actor identity from the authenticated run context. The reusable agent-key branch, lines 469–531, checks the agent/company/status and takes run attribution from a header. This is a different binding model. A header that records a run ID is not by itself proof that the credential belongs only to that run.

The shared cancellation guard, lines 1–38, locks the matching run for a share check and rejects revoked writes or yielded handoffs. It returns early when agent/run identity is absent, and a missing matching run is not itself a rejection. It also does not reject every non-cancelled terminal state. Treat it as a cancellation/handoff gate, rather than a universal validator of current execution authority.

Native tools impose a stricter contract. Locked mutation context and receipts, lines 2650–2896, check company, agent, issue, execution run, running native state and actor eligibility. Operation replay checks input/operation consistency, and the mutation and result receipt share a transaction. These controls reduce duplicate business effects and stale native writes. They do not make an uncontrolled external tool action exactly once.

Queue dispatch, lines 1898–1973, calculates available per-agent slots and selects queued work under a start lock. That lock, lines 1–48, is a process-local promise map, with a timeout while waiting. It is not a PostgreSQL lock that proves exclusive admission across server processes. Dispatch rechecks, lines 868–909 and 2640–2672, include invokability and budget admission; blocked work can remain durably queued. The budget wrapper, lines 1359–1393, evaluates through a transaction. This review does not certify every cost settlement or budget hard-stop path.

Execution-admission persistence, lines 1–112, locks project records in order and records admission charges. However, its application policy, lines 1–49, explicitly keeps commands internal and forbids route/tool/import updates until admission enforces the configured maximum. A table or policy field is therefore insufficient evidence of an available project-wide WIP limit.

Progress, review and completion

Document writes, lines 350–405, require the base revision to match the current revision before creating the next one. Work-product records, lines 1–55, connect task evidence to the shared authority. This supports precise handoffs without assuming the next worker still has the previous conversation in memory.

Completion-contract creation, lines 148–236, uses a task-scoped transaction lock and revision/hash identity. Policy selection, lines 80–114, is significant: policies other than human_only and not_creator can select the low-risk agent-claim path. The term low risk here is a policy classification, not proof that the server performed a semantic analysis of the task's consequences.

Evidence classification, lines 1–100 and 105–183, distinguishes proposed provider output from durable control-plane evidence. Criterion/verification aggregation, lines 261–407, supplies completion assessment inputs. This is stronger than trusting a successful provider exit. It still depends on which references and policies the workflow requires.

Status arbitration, lines 343–422, checks unresolved dependencies, required quality review, assessment outcomes and pending child-completion delivery. Under agent-claim policy, claimed criteria can permit completion without every evidence/verification item independently passing, provided the other failure/attention/blocking conditions are clear. This is a deliberate lightweight policy and must not be presented as mandatory independent verification.

Required quality review, lines 1–119, supplies a stronger opt-in gate. It protects the requirement from agent removal and binds approval to the current non-plan output document revision or attachment asset and hash. Missing, changed, removed or unapproved output does not inherit a prior approval. The common issue writer, lines 11393–11604, applies this gate before the done transition and includes run-write checks. It is more robust than putting a review instruction only in a prompt.

Native decision commit, lines 1610–1818, validates replay and uses current issue/contract/decision state and version predicates before applying a decision. Decision effects, lines 2330–2410 and 2420–2475, retain parent/dependent wakes and keyed delivery effects. A stopped provider, a committed status decision and a delivered wake remain separate states with different recovery work.

Child-completion delivery checks, lines 1–29, concern undelivered fresh parent wake information. Holding completion until that information is delivered is useful. It is not the same rule as waiting for all active children or human acceptance of each child's result. The integration must specify which children are required and what constitutes their accepted output.

Stop, recovery and communication

Stop intent, lines 1206–1278, locks the issue/run transaction and records write revocation before waiting for the executor. Executor settlement, lines 1468–1516, distinguishes a native stop still awaiting recovery from completed termination, and uses process termination handling for local adapters. It cannot undo a network request or code change already issued outside the service.

Controller recovery, lines 158–220, checks checkpoint binding across company, agent, issue, run, session and runner. Exhausted or unknown history can cause a hold rather than an unsafe restart. Runner ownership, lines 1–81, also retains ambiguous executions for reconciliation. Heartbeat recovery, lines 2374–2428, considers owner boot/process/start/lease data and declines takeover of a live owner. These are substantive safeguards, with an availability tradeoff: ambiguity can require operator action.

Work assessments, lines 1–78, persist assessment identity and digest. Finalization, lines 1300–1332 and 1484–1524, loads retained result/contract state, validates the terminal envelope and builds policy inputs. The reconciler, lines 432–490, has a separate pending-work entry point. This review does not certify all provider-resume or finalization retries; durable phase identity alone does not prove external side effects are replay-safe.

Thread interactions, lines 1–82, retain task conversation state. Question-response delivery records, lines 1–65, retain response-processing identity and errors. The delivery coordinator, lines 1–80, combines database signals, non-overlapping drain work and retry deadlines. This supports recovery beyond a single transient notification. Transport-specific acknowledgement, channel credentials and every external chat replay path were outside the inspected scope.

Activity persistence, lines 152–216, records actor/run/responsible-user details and schedules relevant delivery work. Publication, lines 223–245, distinguishes immediate publication from collected post-commit handling. Native tool transactions can retain business mutation and evidence together; the ordinary checkout route calls activity logging after the primary checkout. Do not assume every activity event has the same atomic boundary as its business mutation.

Usability, implementation depth and operation

Issue listing, lines 263–328, connects company-scoped filters, workspace/participant/origin context, ordering and paginated queries. Issue detail, lines 8425–8462 and 8776–8818, connects chat, activity and related-work inspection. These views make the shared authority inspectable by a person. Their presence does not certify responsive layout, keyboard navigation or screen-reader behavior.

Optimistic update helpers, lines 1–127, retain previous values and roll back a field only when the cached value still matches that mutation's optimistic value. This avoids blindly replacing a newer field update with an entire stale snapshot. The mutation entry, lines 153–194, connects the common API and write-turn coordination; the rest of its connectivity/replay lifecycle was not fully audited.

Server startup, lines 408–431 and 498–532, chooses external PostgreSQL or embedded PostgreSQL and runs database preparation. Root development instructions mention PGlite, but the inspected executable path imports embedded PostgreSQL. Use current code and deployment-specific configuration when planning operations. Package requirements, lines 110–116, specify Node 24.11.0 or newer and pnpm 9.15.4. The repository's version requirements take precedence over a user's general toolchain defaults.

Operate and restore the database, stored assets, secrets, workspaces, runner/controller identities and pending work coherently. A database restore without the corresponding external artifact and ownership state can leave references or recovery decisions invalid. The source offers a lighter embedded-database option and an external database option; neither was installed or load-tested here. Shared PostgreSQL is not proof that several application processes enforce all the same local admission locks.

Receipt recovery test assertions, lines 83–110, model wake failure after a business mutation and recovery of the wake without repeating that mutation. Quality-review test assertions, lines 57–76 and 98–105, check removal protection and stale output targets. These are meaningful intended contracts. They were read, not run, and do not establish successful production concurrency or all alternate-route enforcement.

Retain the task/run separation, conditional checkout, native authority binding, durable receipts, revisioned evidence, stop-before-settlement revocation and conservative recovery. Define one supported profile and credential policy for workers. Add explicit required-child acceptance where needed. Verify project-wide capacity across every application process before relying on it. Select stronger review policies for results that require independent or human acceptance, and validate claim races, stale credentials, partial finalization, remote ownership loss, restore and representative human workflows before making the system the sole authority.
