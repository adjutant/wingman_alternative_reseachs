Python Agent Mail task management assessment

Repository: https://github.com/Dicklesworthstone/mcp_agent_mail

Commit: 9138f34b1ed220235dbfeaa3f1fc9fe4444f4e72. Baseline: Shared task management for an agent organization. Review: November 9, 2026. Full local checkout; targeted static implementation and test-source review. Candidate applications, dependencies and test suites were not installed or run.

Fit decision and assessment boundary

Python Agent Mail is a communication and shared-resource coordination companion. It gives agents persistent project identities, authenticated mailbox operations, threaded messages, attachments, recipient read/acknowledgement receipts, search and an auditable Git archive. It also records expiring file reservations and optional build-slot leases. These are useful building blocks for agents that already share a task system.

It is not an independent task-management authority. There is no task entity with status, dependencies, acceptance criteria, child assignments or execution attempts in the complete model declaration. A thread ID or reservation reason can contain an external ticket key, but that convention does not enforce ticket ownership or completion. The candidate's instructions explicitly use Beads as the task authority; that architectural separation is consistent with the inspected implementation. See models, lines 1–219, and integration instructions, lines 224–260.

Reservations are advisory even when marked exclusive. The reserve function serializes its database read/check/write, reports conflicting holders and still grants the requested reservation. Build-slot acquisition uses the same report-and-grant approach. Neither mechanism should be presented as a single-winner task claim. Optional Git hooks can block conflicting commits, but do not stop competing file edits or authenticate a worker's execution attempt.

The license file adds an explicit OpenAI/Anthropic restriction to an MIT-form text, while package metadata says MIT. This report therefore does not classify the pinned repository as unqualified MIT or unrestricted open source. The restriction is an adoption constraint separate from the technical findings. See license and package metadata, lines 1–70.

The review traces identity/session binding, message persistence and delivery, receipts, reservations and renewal/release, stale cleanup, HTTP role checks, an alternate browser write, archive sequencing and selected tests. It includes a static MCP declaration inventory, not an every-line audit of the 306 tracked files. No live MCP client, HTTP service or browser was used for this assessment.

Architecture and data authority

FastMCP tools call application helpers backed by SQLModel and asynchronous SQLAlchemy sessions. A FastAPI wrapper supplies HTTP transport, authentication, rate limiting, background workers and server-rendered mailbox pages. The package also includes a Typer CLI, Git hooks and export/viewer assets; those complete surfaces were not audited here. The central application module is roughly 14,670 lines, with additional large HTTP, CLI and storage modules. This concentration makes it especially important to trace alternate callers rather than infer one universal lifecycle from a tool description.

The model contains projects, products and project links, agents, messages, per-recipient state, file reservations, contact links, window identities and summaries. An agent name is unique within a project, with program/model, focus, last activity, registration token and retired state. A message has its own ID, project, sender, thread, direct reply edge, importance, acknowledgement flag and attachments. A reservation has an owner, path pattern, expiry and optional release timestamp. There is no durable task execution attempt or independently verified work result. See complete model declaration, lines 1–219.

The catalogue inventory records 49 mcp.tool and 29 mcp.resource decorators in app.py. It was generated by parsing syntax without importing candidate modules. Some declarations are conditional, including build slots and product features. The counts establish the declared surface at this commit, not the set advertised by every runtime configuration or the correctness of every operation.

Database rows serve mailbox reads and recipient state, while Git contains message copies, agent profiles, reservation JSON and thread digests. A message database commit and its archive writes are separate operations. The commit queue waits for completion and can fall back to a direct commit, but is an in-memory batching mechanism rather than a durable transaction outbox. See message creation, lines 3935–3977; archive bundle, lines 1551–1687; and queue, lines 109–216.

Lifecycle and authority boundaries

A coordinator ensures a project and registers an agent. Agent uniqueness is scoped to a project. Registering an existing named identity first authenticates that identity; successful registration obtains its token and binds the current MCP session. Authentication later accepts a session binding or verifies the token with a constant-time comparison. A configured window identity can also rebind after reconnect. The bindings are TTL-pruned process memory, so durable identity survives a server restart while a session's authorization state does not. See registration, lines 6210–6253, and authentication, lines 5240–5466.

Project setup is idempotent by its unique slug and retries selected lock failures. Default identity uses path-derived information; gated alternatives can use normalized Git remotes or common directories. Consistent identity configuration remains necessary across different client paths and hosts. A shared remote name does not itself synchronize two independently deployed mail databases. See slug selection, lines 2000–2056, identity defaults, lines 2152–2210, and project creation, lines 2420–2457.

Work selection happens outside this product. An agent may put the external task key in a message thread and reservation reason, reserve its anticipated edit paths, then announce its start. The database reservation update is serialized, but a conflict does not reject the request. The response includes both grants and conflicts and warns that code-repository enforcement is advisory. A consumer must inspect those fields and apply its own decision to wait, narrow scope or ask the holder. See reservation mutation, lines 11365–11612.

Progress and questions are messages. The send path authenticates the sender, resolves recipients and applies contact policy before delivery. Delivery creates one message and its recipient rows in a database transaction, then writes canonical, outbox, inbox and thread archive files under an archive lock. Cross-project deliveries are separate operations and may partially succeed; the result reports per-project delivery errors. An agent that retries the whole request can duplicate deliveries already committed to successful projects. See sender authentication, lines 7598–7622, message transaction, lines 3935–3977, delivery, lines 5575–5856, and multi-project result, lines 8355–8423.

Inbox fetch does not consume messages. Mark-read and acknowledge are explicit authenticated operations and preserve their original timestamps through conditional updates. Acknowledgement sets read and ack in separate calls, so an interruption can leave a read receipt without an ack; retry can complete the missing step. This is useful delivery state, not a proof that an agent performed the requested work. See inbox, lines 9454–9558, receipt helper, lines 5129–5179, and acknowledgement, lines 9784–9863.

There is no task review or completion transition to enforce. An agent releases its own reservations and posts a result; the external task system must decide whether the deliverable is accepted and the assignment is complete. Release filters by authenticated agent and project and uses a database transaction, then rewrites archive artifacts. It neither cancels a process nor makes a prior message an immutable final result. See release, lines 11665–11759, and domain model.

Concurrency, failure and recovery findings

Advisory exclusivity remains advisory after serialization

BEGIN IMMEDIATE gives reservation checks and updates one serialized SQLite transaction. The conflicting-holder branch nevertheless appends to conflicts and continues to create or renew the reservation. This behavior is deliberate and is asserted by a selected test that expects a second overlapping exclusive request to receive both granted and conflicts. Database serialization improves the accuracy of the report, not the strength of work ownership. See reserve branch, lines 11445–11576; transaction helper, lines 643–698; and test, lines 1–21.

Build slots also return a grant despite active incompatible holders. Their file writes are wrapped in exception suppression, so a returned grant or successful renewal need not establish that its lease was persisted. Slot keys use agent and branch, without a new generation token per execution. This is a convenience signal for cooperating build wrappers, not a durable capacity reservation service. See acquire, lines 12189–12248, and renew/release, lines 12252–12332.

Git hooks enforce a narrower boundary

The generated pre-commit hook inspects staged paths and active reservation artifacts. It defaults to blocking conflicts when its feature gate is enabled, but supports advisory mode and an explicit bypass. It takes the acting agent name from an environment variable. The hook reads locally available archive JSON, rather than asking a central service for a fenced task claim at each write. A path-listing failure or absent detected paths can also end the hook successfully. See hook gates and path collection, lines 268–354, and conflict result, lines 437–473.

A commit hook cannot prevent two processes editing the same file before commit. It also does not make reservations in another host's independent archive immediately visible. Its value depends on installation, configuration, current artifacts and cooperation by the caller. It should not be treated as the baseline's authenticated task-owner invariant.

Expiry uses activity heuristics, without stale-attempt fencing

Stale analysis combines agent activity, sent/read/acknowledged mail, filesystem touches and Git activity. It reports the reasons behind its result and can release orphaned reservations whose agent has disappeared. TTL expiration and heuristic stale release are real recovery mechanisms, but do not establish that a worker has stopped or that its output must be rejected. Quiet computation and a disconnected worker require a separate execution heartbeat policy. See stale analysis, lines 4093–4261, and expiry, lines 4347–4438.

The stale heuristic is evaluated before the subsequent release transaction. That update checks reservation ID and unreleased state, without rechecking the activity/expiry state used for the heuristic decision. A renewal or activity update between evaluation and mutation can therefore be overtaken by the older release decision. The force-release path has a similar check-then-update boundary for non-expired stale records. These are source-derived interleavings; they were not reproduced here. See automatic stale update, lines 4385–4410, and forced release, lines 11850–11905.

Database and Git recovery is compensation, not one transaction

Normal delivery commits the database message before writing the archive bundle. On an archive exception it attempts to delete message and recipient rows in a separate transaction, suppressing cleanup errors so the original archive failure is returned. Files already written by a partial bundle are not removed by that compensation. A process crash between commit and cleanup can also leave a database/archive mismatch. The archive lock serializes cooperating writers but cannot make these storage systems one transaction. See delivery compensation, lines 5736–5856, and bundle write order, lines 1551–1687.

Reservation creation likewise removes only rows newly created by the failed call on archive error. Previously existing reservations whose expiry or exclusivity changed are left changed. Renewal and release commit database changes before updating Git artifacts. Consumers of database state and local guard JSON can therefore temporarily disagree after a failure. See reservation compensation, lines 11570–11612; renewal, lines 12070–12118; and release, lines 11700–11759.

The browser human-message route follows a different recovery path. It commits message and recipient rows, then writes Git artifacts; an archive error returns HTTP 500 without deleting those rows. The message may therefore be visible even though the sender saw a failed request. A blind retry can create another message. See browser database/archive sequence, lines 3914–4038.

Polling needs a deliberate catch-up strategy

Inbox queries order newest first, apply a fixed limit and optionally require created_ts strictly greater than since_ts. There is no returned continuation cursor or message-ID tie-break condition in that helper. If a client receives only the newest page after a burst, advancing its timestamp can skip older unread messages. Unread-only polling with explicit receipts helps drain pending mail, but callers must actually use it and handle limits rather than assume timestamp polling is a complete event replay protocol. See inbox query, lines 4592–4666, and tool interface, lines 9454–9558.

Notification signals are emitted after the archive lock and exceptions are suppressed. Fetching can clear the signal independently of whether every pending message fit in the response. The durable mailbox, rather than a signal file, must remain the recovery source. See signals, lines 5810–5856 and 9525–9558.

Permissions and alternate interfaces

Per-agent token checks and visibility filters are meaningful safeguards. Registration cannot freely take over an existing named identity through the normal path, and mailbox receipt operations require the addressed agent's authentication and visible message. Search fallback queries restrict results to messages sent by or addressed to the authenticated viewer. See registration, lines 6210–6253; receipt callers, lines 9706–9863; and search fallback, lines 10600–10698.

Project administration is broader than a manager role. The helper accepts an existing authenticated project agent or any matching token belonging to a project agent. It does not consult a distinct owner/admin assignment. The baseline's project leader, worker, reviewer and human override roles therefore need a separate policy layer. See admin authentication, lines 5468–5519.

HTTP can enforce a shared bearer token, JWT roles and rate limits. Default configuration binds to loopback and permits unauthenticated localhost access; the bypass rejects requests bearing forwarded headers. A valid static bearer can be used alongside JWT when both are enabled, with the configured default role. These deployment choices need to match the intended trust boundary. See bearer/local check, lines 722–790, role selection, lines 1009–1073, and defaults, lines 394–430.

The role classifier recognizes MCP tools/call and resource requests by their JSON body. An ordinary POST to the browser human-message route is classified as other, while writer-role enforcement applies only to classified tools/resources. That handler does not call the per-agent authentication or contact-policy path. It creates a generic HumanOverseer identity and sends high-importance messages directly. Source inspection therefore indicates that a principal admitted by transport authentication can use that browser write even when the same principal's role cannot call a write tool. This was not tested with a live server. See classification, lines 888–908; role boundary, lines 1056–1073; middleware installation, lines 1608–1628; and browser writer, lines 3773–4038.

The UI's generic human identity and priority preamble are conventions, not evidence of a separately authenticated human owner. The same route also bypasses normal message reservation checks and their compensation behavior. A protected network deployment should unify authorization and storage semantics across those entry points before treating this as an organizational control plane.

Completeness, design and usability

The strongest implemented area is communication. Persistent identities, direct reply edges, per-recipient state, sender authentication, search, cross-project delivery results and archive inspection are concrete capabilities. The task-management gap is architectural: the product expects a different system to own task state. Adding a board alone would not supply dependencies, claims, attempt fencing, review and worker supervision.

Several design choices show attention to concurrent operation: immediate reservation transactions, conditional timestamp updates, archive locks with cancellation cleanup and an awaited commit queue. Other state spans remain split across database, Git, session memory, JSON leases and generated hooks. The different human-message write path illustrates the maintenance risk of implementing one lifecycle more than once. See transaction helper, lines 643–698; receipt helper, lines 5129–5179; archive lock, lines 1239–1270; and browser sequence, lines 3914–4038.

The browser project page provides clear links to threads, reservations, attachments and human messaging. It displays project state and has labeled navigation controls. Its purpose is inspection and communication, with no task progress or review dashboard. Only representative template source was inspected; no desktop/mobile render, keyboard walkthrough or assistive-technology acceptance test was performed. See project template, lines 1–125.

Operation requires managing a database, Git archive, credentials, expiry settings and any installed hooks. The package declares Python >=3.12, while contributor instructions target 3.14. That metadata difference is recorded without asserting a runtime compatibility defect. Dependencies include FastMCP, FastAPI, SQLModel/SQLAlchemy, GitPython, Redis and LLM/image libraries; the optional Postgres driver does not establish compatibility of every operation, especially the literal SQLite BEGIN IMMEDIATE helper used by reservations. No alternate database backend was validated. See package, lines 1–70; contributor instructions, lines 41–51; and transaction helper, lines 643–698.

Test-source evidence and limits

The overlapping-reservation test explicitly expects both a grant and a conflict for a second exclusive holder. The same test file checks a contact macro returning a nonfatal welcome-message conflict rather than claiming successful delivery. The renewal test checks a later expiry and a corresponding JSON artifact. These assertion bodies support the intended advisory and archive behavior, but were not executed here. See conflict/macro tests, lines 1–49, and renewal test, lines 32–76.

The mailbox regression tests check that repeated fetches leave read state unchanged and that explicit mark-read makes the receipt visible. Another test verifies that repeated read/ack calls preserve their first timestamps. The HTTP test checks missing-bearer rejection, read-tool success, write-tool refusal for a reader and rate limiting. Despite its name, that selected test body configures static bearer/RBAC rather than enabling JWT validation. It does not cover the ordinary browser writer's role classification. See fetch test, lines 191–244; receipt test, lines 825–879; and HTTP test, lines 1–65.

Archive setup tests inspect directory creation, Git initialization, idempotent setup and lock paths. They do not prove cross-store crash recovery or successful installation of this revision. The larger disaster-recovery, guard, identity and UI suites were inventoried, but not all assertion bodies were reviewed. No suite result or production reliability claim is inferred from test filenames. See archive setup tests, lines 1–135, and the evidence ledger.

Adoption decision and useful components

Use this architecture as a communication companion to a task authority that owns project outcomes, task dependencies, atomic claims, execution attempts and acceptance. The useful components are the per-recipient mailbox state, token/session identity separation, threaded context, explicit partial-delivery results and inspectable archive. Reservation signals and hooks can reduce accidental overlap among cooperating agents, with their advisory and deployment limits made explicit.

For the baseline, the remaining work includes a task/attempt schema, conditional worker claims, capacity policy, parent-child execution supervision, result-bound review, replayable operation identifiers and a consistent failure journal across storage phases. Authorization must also cover browser and maintenance paths with the same role and project rules as agent calls. The pinned license restriction must be resolved for the intended adoption context before selecting it as an unrestricted reusable dependency.

This source review establishes a substantial communication layer and several precise coordination limits. It does not establish a complete task system, executed acceptance evidence or a reliability ranking against the Rust implementation. That implementation requires its own source assessment.
