# Plane: shared planning and discussion with external agent execution

Source: https://github.com/makeplane/plane

Reviewed commit: `618d0eb74658329a6f6e92434ac54231422c5b96`.
Assessment date: November 9, 2026.
Baseline: [Shared task management for an agent organization](../../../AGENT_TASK_MANAGEMENT.md).
Evidence ledger: [review.json](review.json).
Companion: [Plane MCP adapter assessment](../../plane-mcp/assessment/ASSESSMENT.md).

## Fit decision

Plane provides a substantial shared planning authority. Workspaces contain projects, members, work items, cycles, modules, pages and notifications. Projects have leads and default assignees. Work items have stable identifiers, hierarchy, relations, descriptions, discussion and retained history. Agents can operate on these records through an authenticated external API. The browser supplies a connected human planning and inspection surface.

The reviewed source does not make a work item an exclusive agent execution reservation. Multiple assignees are ordinary project users. A member can replace an assignee list or change state without acquiring an unowned task, proving capacity or identifying the current execution attempt. Dependency relations describe work, but the normal state/assignment writer does not use them as dispatch readiness rules. A parent can reach a completed state without accepted child results or a reviewer decision.

Plane fits as a project, backlog and discussion layer behind an agent coordinator. It would require substantial additions to serve as the entire runtime for the baseline. Keep its project structure and human inspection experience. Put ownership, attempts, leases, dispatch and result acceptance in one authority that also controls alternate and background mutations. The reviewed files declare AGPL-3.0-only in their headers; [the license](../repo/LICENSE.txt), lines 1–45, contains AGPL version 3. This assessment covers the checked-out source, not uninspected commercial editions or hosted features.

## Scope and evidence level

The full preserved worktree has 5,166 tracked files. This is a targeted static review of work item, project, workspace, user/token, state, relation, cycle, module, page and notification models; browser and external API create/update/delete paths; serializers and association replacement; selected bulk and maintenance writers; permissions and authentication; asynchronous history, notifications and webhooks; representative browser detail/board/store code; deployment configuration; and selected test assertion bodies.

No candidate application, dependency installation, build, migration or test was executed. Source and test assertions are implementation evidence, not passing runtime results. This is not an every-line audit or verification of every importer, export format, extension, file route, integration, migration, live collaboration service, authorization rule, token-management route, deployment, performance characteristic or browser interaction. The source ledger records actual inspected ranges and hashes. The separate MCP adapter does not supply upstream ownership or recovery guarantees merely by exposing API operations.

## Architecture and shared records

[Backend dependencies](../repo/apps/api/pyproject.toml), lines 1–70, specify Python 3.12, Django, Django REST Framework, PostgreSQL, Redis, Celery and storage/integration clients. [Database configuration](../repo/apps/api/plane/settings/common.py), lines 214–248, configures PostgreSQL and an optional read replica. [Worker configuration](../repo/apps/api/plane/settings/common.py), lines 350–395, uses RabbitMQ/AMQP and JSON task serialization. These background workers process application effects; they are not the baseline's autonomous task workers.

[Base records](../repo/apps/api/plane/db/models/base.py), lines 17–47, use UUIDs and assign audit users from request context. [Project-bound saving](../repo/apps/api/plane/db/models/project.py), lines 230–241, derives the workspace from the project. [Workspaces and memberships](../repo/apps/api/plane/db/models/workspace.py), lines 119–150 and 198–232, retain owners, slugs, roles and active membership. [Projects](../repo/apps/api/plane/db/models/project.py), lines 68–112, retain description, network visibility, identifier, lead, default assignee and feature settings. This is a native project registry, although agent-specific leadership continuity remains external.

[The work item](../repo/apps/api/plane/db/models/issue.py), lines 109–178, includes parent, state, description formats, dates, priority, estimates, multiple assignees, labels, sequence number, completion/archive markers and external references. [State groups](../repo/apps/api/plane/db/models/state.py), lines 15–62, distinguish backlog, unstarted, started, completed, cancelled and triage. These are planning states. Neither a started state nor an assignee row identifies a process or grants it a fenced execution attempt.

[Creation saving](../repo/apps/api/plane/db/models/issue.py), lines 180–255, takes a PostgreSQL transaction-level advisory lock per project before allocating its sequence and inserting an IssueSequence. This is meaningful concurrency control for identifiers. It must not be attributed to normal task assignment or editing: the existing-record branch saves without that allocation lock. The item model has no ordinary edit revision counter or expected-version predicate.

## Creation, assignment and concurrent editing

[Browser creation](../repo/apps/api/plane/app/views/issue/base.py), lines 406–503, validates a serializer, saves the item and queues activity, webhook-related model activity and description-version work. [Its serializer](../repo/apps/api/plane/app/serializers/issue.py), lines 82–285, checks project-related fields, creates the item and then creates assignee/label associations. When no usable explicit assignee list is supplied, it can use the project's valid default assignee. The row and all later effects are not expressed as one transaction in this path.

[External API creation](../repo/apps/api/plane/api/views/issue.py), lines 534–605, checks an existing external-source/ID pair before saving. This can detect a prior item, but the check precedes the create transaction. The inspected item model has no matching uniqueness constraint. The per-project sequence lock does not repeat this duplicate lookup. Concurrent create requests can therefore both pass that pre-check; it is not a durable request-idempotency contract. This is a static concurrency inference, not an executed race.

[External serializer validation](../repo/apps/api/plane/api/serializers/issue.py), lines 46–184, rejects nonmember assignees and foreign labels, and binds state, parent and estimates to the project. The browser serializer instead filters invalid assignee/label IDs to those accepted in the project. This difference matters to an agent: one interface returns an error for a partially invalid list, while the other can silently reduce it. Both treat responsibility as a set of users, not an exclusive execution owner.

[Browser updating](../repo/apps/api/plane/app/serializers/issue.py), lines 286–342, soft-deletes existing assignee/label associations and bulk-inserts replacements, then saves the item. [The external serializer](../repo/apps/api/plane/api/serializers/issue.py), lines 267–355, follows the same pattern. [Assignee constraints](../repo/apps/api/plane/db/models/issue.py), lines 349–375, prevent duplicate live pairs for one issue/user, rather than multiple distinct assignees. There is no inspected unowned-state condition, capacity check or execution token on replacement. Concurrent replacements can interleave, and failure between association replacement and item saving can leave a partially applied edit.

[The browser PATCH](../repo/apps/api/plane/app/views/issue/base.py), lines 628–719, reads a current instance, validates and saves, then queues effects. [The external PATCH](../repo/apps/api/plane/api/views/issue.py), lines 840–900, similarly loads a record and saves without an expected-version condition or row-lock acquisition. [Change tracking](../repo/apps/api/plane/db/mixins.py), lines 92–211, compares in-memory fields with their load-time values; it does not compare them against the latest database row or reject a stale writer. A later save of a loaded item can overwrite another edit. Request serialization, deployment timing or a successful single-user edit would not establish safe concurrent assignment.

Read-only fields are a useful narrower protection. The serializers prevent direct PATCH changes to system-controlled completion/archive/deletion/sequence fields and draft status after creation. A normal editable state change can still set completion through the model. That is different from allowing the caller to forge every timestamp, but it is also different from controlled worker acquisition and acceptance.

## Hierarchy, dependencies and completion

[Sub-item assignment](../repo/apps/api/plane/app/views/issue/sub_issue.py), lines 210–275, binds the parent and candidate children to the URL project, bulk-updates their parent pointers and returns state distribution. It does not reject selecting the parent itself or an ancestor in that method. [Normal serializer parent validation](../repo/apps/api/plane/app/serializers/issue.py), lines 178–197, checks project membership of the referenced item, rather than traversing ancestry. A project-valid pointer is not proof of a valid decomposition tree.

[Relation records](../repo/apps/api/plane/db/models/issue.py), lines 258–317, support blocked-by, ordering, duplicate and related-work semantics, with reverse mappings. [Browser relation creation](../repo/apps/api/plane/app/views/issue/relation.py), lines 247–315, binds the URL item to its project and related items to its workspace, then inserts relations. [The external route](../repo/apps/api/plane/api/views/issue.py), lines 2715–2795, validates relation choices and follows the same cross-project workspace boundary. Neither path traverses the graph for cycles. The uniqueness constraint is on the live issue pair, not a scheduler invariant. Cross-project relation creation is broader than separate authorization of both endpoint projects in these methods.

An agent can read these links and choose ready work externally. The ordinary update serializers do not load blockers, children or reviewer decisions before accepting a state change. [Completion synchronization](../repo/apps/api/plane/db/models/issue.py), lines 240–255, sets `completed_at` when a newly created or changed state belongs to the completed group, and clears it for other groups. Completion therefore reflects state classification. It does not prove that a parent incorporated child results, tests passed, a result matches acceptance criteria or a human approved that result revision.

Maintenance is a distinct mutation path. [Automatic closing](../repo/apps/api/plane/bgtasks/issue_automation_task.py), lines 92–155, selects old open items, chooses a configured default state or the first cancelled state, and bulk-updates only the state field. The fallback state query has no project filter. Thus a project without a configured default can receive a state from another project. The bulk writer also bypasses the normal save-based completion timestamp synchronization; a completed default state need not receive the timestamp that a normal state edit would create. These are source-level findings, not reproduced runtime failures. This maintenance policy is inactivity-based record cleanup, not stalled-agent recovery or verification of finished work.

[Bulk date updating](../repo/apps/api/plane/app/views/issue/base.py), lines 1129–1186, provides another important ordering boundary: it queues per-item activity while collecting changes, before the final bulk write. A later invalid date can return early after earlier activity was queued. A write failure can likewise leave effects describing an unapplied update. Alternate writers need the same transition/effect contract if agent decisions will depend on history.

## Context, communication and audit limits

[Pages](../repo/apps/api/plane/db/models/page.py), lines 23–62, retain rich content, ownership, access mode, hierarchy and project associations. [Work item links and attachments](../repo/apps/api/plane/db/models/issue.py), lines 377–405, retain URLs, metadata and file references. [Comment creation](../repo/apps/api/plane/app/views/issue/comment.py), lines 95–145, scopes the issue, filters writable fields, attributes the actor and queues discussion effects. These are useful handoff materials. They do not require a successor to acknowledge a typed result, nor bind acceptance to a content hash and attempt.

[The activity task](../repo/apps/api/plane/bgtasks/issue_activities_task.py), lines 1548–1650, maps event types into activity records, bulk-inserts them and then queues notifications. It catches general exceptions and returns. It can also update the issue's modification time while processing activity, so a recent item timestamp can reflect background processing rather than fresh worker progress. The primary work item save and this record creation have no shared outbox transaction in the inspected paths. A queued event is not proof of a recorded event.

The browser PATCH accepts `skip_activity` from the request and treats it together with a present description update as a migration update. [That branch](../repo/apps/api/plane/app/views/issue/base.py), lines 629–716, suppresses the route's activity, model-activity and description-version effects. It does not restrict the request to changing only the description. A mixed state/description edit with that flag can therefore bypass these ordinary history effects while still saving the state. This is a specific writer boundary, not a claim that no other deployment logging exists.

[Version snapshots](../repo/apps/api/plane/db/models/issue.py), lines 677–782, retain prior work item data and an owner. [Description-version processing](../repo/apps/api/plane/bgtasks/issue_description_version_task.py), lines 15–78, can update the latest same-author snapshot within a ten-minute interval instead of appending a new immutable revision. [Issue-version processing](../repo/apps/api/plane/bgtasks/issue_version_sync.py), lines 34–65, also coalesces nearby same-owner changes and catches failures. These histories help inspection. They are not optimistic concurrency versions, append-only acceptance evidence or current-attempt fences.

[Notification generation](../repo/apps/api/plane/bgtasks/notification_task.py), lines 190–260 and 610–674, handles active project members, mentions and database notifications/email logs. General exceptions are caught. [Notification records](../repo/apps/api/plane/db/models/notification.py), lines 13–76, retain receiver, read, snooze and archive state. [Listing](../repo/apps/api/plane/app/views/notification/base.py), lines 33–72, scopes records to the receiver and workspace; [individual actions](../repo/apps/api/plane/app/views/notification/base.py), lines 157–204, also bind the receiver. This supplies later inspection after a missed browser interaction. It does not guarantee that every primary update generated a notification, or that marking one read means an agent accepted a handoff.

[Webhook delivery](../repo/apps/api/plane/bgtasks/webhook_task.py), lines 235–389, adds a delivery UUID, optional HMAC signature, logs and up to five retries for transport exceptions. [Pinned fetching](../repo/apps/api/plane/utils/url_security.py), lines 106–224, validates/resolves the target, pins the request to the selected IP and disables redirects, with a timeout. The returned HTTP response is logged as successfully sent without a success-status check in this chain. An HTTP 500 response therefore does not itself enter the transport retry path. The delivery UUID is regenerated on each task invocation, so consumers must not assume it identifies a stable retry series. Initial queue publication and receiver-side idempotency remain separate concerns.

## Access, cancellation and human usability

[API authentication](../repo/apps/api/plane/api/middleware/api_authentication.py), lines 17–52, requires an active unexpired token and active user, and updates last use. [Token storage](../repo/apps/api/plane/db/models/api.py), lines 15–48, retains token strings, a user/bot type and optional workspace association. This authentication method resolves user authority; it does not bind each mutation to an execution attempt or check the token's workspace field against the URL. [External endpoint defaults](../repo/apps/api/plane/api/views/base.py), lines 51–70, use API-key authentication and throttling. [Project entity permissions](../repo/apps/api/plane/app/permissions/project.py), lines 135–167, require active project membership and member/admin rights for writes. That user membership remains an important boundary even without attempt-scoped credentials.

[Browser session authentication](../repo/apps/api/plane/authentication/session.py), lines 25–63, checks allowed origins for unsafe requests, while allowing absent Origin for nonbrowser clients. [Role decorators](../repo/apps/api/plane/app/permissions/base.py), lines 19–105, include membership and creator rules. [The base viewset guard](../repo/apps/api/plane/app/views/base.py), lines 90–199, rejects a generic mixin action left under only nonauthorizing default permissions. These mechanisms show active authorization work in this revision; they are not evidence that every subresource, integration or edition has been audited.

[User identity](../repo/apps/api/plane/db/models/user.py), lines 56–120, supports bot identity and activity/login metadata. That activity is not a worker heartbeat. [Deleting an item](../repo/apps/api/plane/api/views/issue.py), lines 914–946, checks administrator/creator rights and invokes deletion. [Soft deletion](../repo/apps/api/plane/db/mixins.py), lines 48–91, normally marks the record and queues related-object deletion. Cancelling, archiving or deleting a work item changes shared records; it cannot stop an external coding session or revoke its filesystem/network effects. There is no native execution resume or late-attempt rejection to attribute to these record operations.

[Browser detail fetching](../repo/apps/web/store/issue/issue-details/issue.store.ts), lines 87–121, expands parent, reactions, links and attachments. [Detail composition](../repo/apps/web/components/issues/issue-detail/root.tsx), lines 228–271, connects main content and a responsive sidebar and provides a route back when the item is missing. [Board rendering](../repo/apps/web/components/issues/issue-layouts/kanban/default.tsx), lines 180–279, provides group counts, expandable collapsed columns, lazy rendering and more-item loading. This is a useful human overview, though a partially loaded board must not be interpreted as a complete ready queue.

[The shared update store](../repo/apps/web/store/issue/helpers/base-issues.store.ts), lines 548–590, saves an optimistic snapshot, updates lists, sends PATCH and rolls back on failure. [The service](../repo/apps/web/services/issue/issue.service.ts), lines 226–241, sends ordinary field data without an expected revision. Rollback can restore an older local snapshot if another edit occurred meanwhile. [Detail updating](../repo/apps/web/store/issue/issue-details/issue.store.ts), lines 181–192, fetches activity in parallel with mutation; it need not wait for the newly queued activity to exist. These are reconciliation limits, not proof of a failed browser session. [The workflow drag helper](../repo/apps/web/components/workflow/use-workflow-drag-n-drop.ts), lines 10–23, returns no workflow restriction in this source tree. Its name is not evidence of enforced transition approval.

## Planning, operation and implementation completeness

[Cycles](../repo/apps/api/plane/db/models/cycle.py), lines 62–112, have an owner, dates, progress snapshot, timezone and issue linkage. [Modules](../repo/apps/api/plane/db/models/module.py), lines 61–114, have status, dates, lead, members and external references. Together with work item priority, estimates and state-based views, these provide native planning depth beyond a task/session launcher. They do not automatically supervise an autonomous organization or allocate its execution capacity.

[The package manifest](../repo/package.json), lines 1–43, supplies a pnpm/Turbo workspace and a Node minimum. [The API container](../repo/apps/api/Dockerfile.api), lines 1–83, pins Python 3.12 and uv, installs locked production dependencies and starts its entrypoint. [Startup](../repo/apps/api/bin/docker-entrypoint-api.sh), lines 1–38, waits for database/migrations, configures the instance, creates storage, clears cache and starts Gunicorn/Uvicorn. These are source procedures, not a successful build or deployment observation.

[The example stack](../repo/docker-compose.yml), lines 1–107 and 108–155, separates web, administration, public space, API, application worker, scheduler, migrator, live service, PostgreSQL, Redis-compatible cache, RabbitMQ and object storage. Persistent volumes help preserve server state, but restoring only PostgreSQL would not restore all files, credentials and operational configuration. Version-compatible workers, completed migrations, broker health, email/file configuration and backup/restore verification add maintenance cost. Optional read replicas improve deployment choices without establishing strongly fresh inspection or a verified highly available authority.

[API membership tests](../repo/apps/api/plane/tests/contract/api/test_issue_assignee_label_validation.py), lines 77–138, assert rejection of invalid assignees/labels and acceptance of a valid member. [Sub-item tests](../repo/apps/api/plane/tests/contract/app/test_sub_issue_cross_project_scope_app.py), lines 141–196, assert project scoping and no foreign-item activity dispatch. [Read-only-field tests](../repo/apps/api/plane/tests/contract/api/test_issue_read_only_fields.py), lines 21–68, assert that ignored fields are neither saved nor reported as changes. These are selected contract assertions, with effects mocked in some paths. They were not run and do not establish concurrent claim safety, reliable queue delivery or accepted task completion.

Adoption should retain the planning models, human detail and discussion surface, while defining a separate execution contract. Add atomic eligible claims, capacity reservations, current attempts, heartbeats, recovery and accepted-child joins. Make state transitions consistent across browser, API, bulk edits and maintenance. Use transactionally recorded effects and a recoverable delivery process where handoff reliability matters. Scope fallback states and relationship authorization deliberately. Make history suppression explicit and restricted, and bind review to an immutable result revision. Verify real multi-host agent work, concurrent edits, failed delivery, cancellation, restore and representative desktop/mobile operation before relying on the combined system.
