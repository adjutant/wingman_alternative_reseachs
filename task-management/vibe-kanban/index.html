Vibe Kanban: local agent execution with a retired project UI

Source: https://github.com/BloopAI/vibe-kanban

Reviewed commit: 08064e043c2d78ad123b473257ed867e7ce74768. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

Vibe Kanban has substantive mechanisms for running and inspecting coding agents. It distinguishes workspaces, sessions, execution processes and agent turns. An orchestrator-scoped MCP server can create other sessions, send prompts and inspect execution IDs. Workspaces can contain Git worktrees for several repositories. Approval questions, process cancellation, follow-up sessions, logs and commit references support interactive supervision.

The current project experience is a material adoption limit. The project page, lines 1–115, returns a sunset component after project/authentication loading. The local wrapper delegates to that page. The sunset component, lines 1–63, offers export and says project functionality is retired. The local project route mounts that wrapper. Existing board components and screenshots are not proof of a usable routed Kanban board at this pin.

The maintainer announcement dated April 10, 2026 says the company is shutting down, the project will continue under community maintenance, and hosted remote project/issue services will be removed after a 30-day transition. It says local workspaces will continue. This is maintenance and service evidence, not a live availability test: https://www.vibekanban.com/blog/shutdown

The repository still contains a remote issue API, PostgreSQL models, synchronization code and self-hosting configuration. These can inform a fork or component reuse. They do not restore the retired project UI automatically. The assessed implementation also lacks a transactional ready-work claim, renewable ownership, stale-attempt rejection and an accepted-child completion barrier. It is a useful local execution and supervision reference, but adoption as the baseline's complete shared task authority requires substantial work.

Scope and evidence level

The full checkout contains 2,208 tracked files. This targeted static review follows remote issue create/update/bulk paths, selected relationship/assignee/schema constraints and workflow status synchronization; local workspace creation/link/deletion, session follow-up, execution creation/monitoring/cancellation/startup recovery, reset, logs and summary paths; MCP modes, delegation and context restrictions; approvals, queued follow-ups, selected notification and permission paths; and the current project routing and synchronization mutation hooks. Selected test assertion bodies were read. No candidate application, install, build, migration or test was executed.

This is not an every-line, full security or runtime audit. All executor providers, complete relay/SSH/cryptography, OAuth flows, file upload/security, preview and terminal isolation, every migration, Git host integrations, complete worktree cleanup, browser rendering and deployed multi-host behavior are outside certification. The ledger identifies inspected ranges; source tests are not passing experiments. Absence claims apply to the inspected models, writes, schema constraints and operation inventory.

The root license, lines 1–16, identifies Apache License 2.0. The remote manifest, lines 1–18, declares optional private billing code. The self-hosted Docker build, lines 88–103, removes that dependency when no features are selected. Private billing internals receive no credit from this checkout. No license obligations or successful dependency resolution were certified.

Architecture and identity boundaries

The workspace manifest, lines 1–60, separates Rust crates for the local API, persistence, executors, services, worktrees, MCP and relay components; remote is excluded from that main workspace. Package metadata, lines 1–20, identifies version 0.1.45 and separate frontend/backend checks. The remote crate, lines 1–65, uses Rust 2024, Axum, SQLx/PostgreSQL and JWT support. This describes the pin, not a build result.

The project type, lines 8–38, gives projects organization, name, color and ordering. The remote issue type, lines 21–149, stores project, issue number/simple ID, status, text, priority, dates, parent, ordering, creator and extension metadata. Local task, lines 14–56, is a different SQLite-backed legacy-shaped record. Do not combine these two models into an imagined single task scheduler.

The workspace, lines 41–81, holds branch, container path/reference, setup/archive/pin state and an optional task ID. A session, lines 23–38, belongs to that workspace and identifies its configured executor. An execution process, lines 40–85, records a concrete action, run reason, status, exit code, timestamps and whether it is dropped from current history. Agent turns, lines 8–59, retain prompts, provider session/message IDs, summaries and seen state.

This is a useful attempt/session distinction. An executor selection is still not a persistent organizational worker with independent capacity, role, task lease and owner generation. Multiple sessions in one workspace use the same workspace context. Worktree creation, lines 292–373, separates repositories into worktrees and attempts rollback on partial creation. It is Git state separation, not evidence of an OS/container security boundary around every agent.

Issue creation, selection and allocation

Issue creation, lines 264–342, checks project access, inserts through the repository and then attempts creator auto-follow separately. Repository creation, lines 325–407, uses a transaction and returns a PostgreSQL transaction ID. A client-generated UUID supports stable optimistic identity. The insert is not a recover-original-result idempotency protocol; repeating the same ID can encounter a key conflict, while choosing another ID can create another issue.

List handling, lines 180–218, builds a structured query. Search construction, lines 40–90, supports filters, safe sort selection and escaped text patterns. It selects records, not worker reservations. Issue schema, lines 55–90 and 123–152, provides foreign keys, parent pointers, multiple assignees with a unique issue/user pair, and relationship constraints against self-links and duplicate edges. The inspected issue/relation mutations and migration inventory establish no general dependency cycle or ready-work acquisition rule.

Relationship creation, lines 98–120, checks access to the source issue and calls a plain relationship insert, lines 86–131. This path does not walk a dependency graph or check the target's completion. The remote issue update can directly change parent/status fields. It must not be described as an enforced dependency scheduler.

Assignee insertion, lines 85–126, inserts one issue/user relation. Workspace-created synchronization, lines 602–693, counts linked workspaces, moves pending issues/parents to a status named In progress for the first workspace, and adds its creator if the assignee list was empty. These are separate reads and writes, not exclusive acquisition. Concurrent creators can both observe an empty assignee list; different users can both be inserted. Names such as Backlog, To do and In progress also carry workflow meaning beyond their UUIDs.

Launch, delegation and partial operations

Local workspace start, lines 23–66 and 212–320, creates a workspace record, adds repositories, imports/associates attachments and starts execution in separate steps. Attachment import failures can be logged and tolerated. Earlier records/worktrees do not share one transaction with process spawn or remote linking.

MCP start, lines 95–225, resolves an optional issue into a prompt, starts the local workspace, then links it remotely. If the final link fails, it returns a tool error after local execution has started. Retrying that error as if nothing happened can launch another workspace. Linking, lines 24–89, creates the remote workspace and starts separate PR synchronization. Remote workspace creation, lines 65–104, logs a failure to synchronize the issue after creating the workspace. These are explicit partial-success boundaries.

MCP routers, lines 52–85, expose broad discovery/issue/workspace tools in global mode and a smaller context/session/workspace set in orchestrator mode. Startup context loading, lines 87–121, fails orchestrator startup when context cannot be loaded. The scope check, lines 177–204, rejects another workspace when context exists. This initialization check matters: the helper alone permits a workspace when context is absent, as a unit test explicitly records. Do not infer a normal startup bypass from that isolated helper behavior.

Session tools, lines 146–193 and 258–320, create a session in the selected workspace, check its scope, prevent launching in the orchestrator session itself and return an execution ID for the child prompt. This is real delegation, beyond board assignment. It does not persist parent/child result dependencies or join accepted outputs. Sessions created in the same workspace also share that workspace's files; a coordinator must manage concurrent edits or allocate separate workspaces.

Execution consistency, completion and review

Workspace execution setup, lines 1047–1132, creates a session, supports parallel repository setup or a sequential setup chain, and starts the coding action. Parallel setup errors can be logged while the coding agent still starts. Execution start, lines 1133–1255, captures repository HEADs, creates the execution record, prepares local message state and an agent turn, then spawns. Model creation, lines 383–415, inserts Running before OS spawn and inserts repository-state rows separately. Some failures before the spawn error handler can leave a Running record for startup reconciliation.

Host spawn, lines 1316–1405, builds approval support and workspace environment, spawns with a timeout and tracks the child, cancellation token and exit monitor in local maps. The inspected start path has no atomic issue claim, per-worker capacity reservation or expected owner token. Distinct execution IDs help inspect attempts but do not prevent overlapping calls or stale issue writes.

Exit monitoring, lines 480–585, listens for OS exit or an executor completion signal. It maps a closed completion channel to a successful exit, then writes process completion unless the record already looks stopped. Completion SQL, lines 417–456, updates by process ID without an expected prior status or generation. Its read-before-write stopped check is not an atomic terminal-state guard. A successful process status consequently does not prove accepted product work, and an uncertain signal is not automatically a verified successful result.

Finalization, lines 204–272, sends success/failure notifications and skips intentional kills. Chained actions, queued follow-ups and unseen markers are handled separately in monitor continuation, lines 585–755. The turn summary, lines 897–942, takes the last assistant message, truncates it to about 4,096 bytes and fills an unset summary. This is convenient reporting, not an independent acceptance decision or structured result contract.

Issue update SQL, lines 408–506, preserves omitted fields and distinguishes explicit nulls, but updates by issue ID without an expected revision, owner or attempt predicate. Bulk updates, lines 491–584, use one transaction and reject items from another project; notifications follow commit. This is useful batch consistency without stale-attempt rejection.

PR/merge status synchronization, lines 523–601, selects In review or Done by name and checks whether all linked PRs are merged before the latter transition. With no linked PRs, the all-merged test is true; local merge sync uses that same path. Ordinary updates and bulk updates remain alternate writers. Neither path requires accepted child issues, an artifact digest or a qualified reviewer. Executor tool approval answers a different question from final task acceptance.

Cancellation, reset and restart

Stop, lines 1406–1479, writes terminal status before graceful cancellation and process-group kill. A kill failure returns an error after that database change. Best-effort workspace stop, lines 707–748, logs individual stop failures, and its HTTP endpoint, lines 139–157, returns success after that helper. A coordinator must not infer proven process termination from the endpoint response or database status alone.

Startup, lines 155–169, invokes orphan cleanup, lines 273–326. It marks all remaining Running records failed and captures available HEAD state. It does not attach to surviving OS processes or acquire an expiring distributed ownership lease. Host-level process cleanup and safe retry remain separate concerns.

Follow-up, lines 124–235, checks executor continuity and uses a provider session/message ID when available. Reset, lines 633–705, validates that the target process belongs to the session, reconciles worktrees, then calls best-effort stop and marks later history dropped. Git reconciliation, lines 892–929, can skip dirty state or log reset failure and return an outcome; the reset caller does not check that outcome. The record history can therefore advance after an unapplied reset. Worktree reconciliation also precedes stop in this inspected ordering, rather than establishing that all writers have stopped first.

Deletion, lines 99–185, refuses a workspace with running non-dev-server records, tries to stop dev servers, deletes the local record, optionally requests remote deletion and schedules cleanup. It returns Accepted. The running check is separate from deletion, dev-server stop/remote deletion can fail, and asynchronous file cleanup is not an atomic rollback boundary. Complete worktree cleanup was not certified.

Decisions, communication and persistence

Approvals, lines 20–258, contain an execution ID, question/tool distinction, pending/completed maps, oneshot response, timeout and typed answer validation. The executor bridge, lines 16–149, notifies the user and waits for an answer or cancellation. The approval patch stream supplies a snapshot and replaces it on broadcast lag. These are meaningful interactive decision mechanisms. Their authoritative pending state is in process memory, so they are not durable escalations that another host can resolve after restart. No organizational reviewer identity is bound to the ordinary local approval response handler.

The follow-up queue, lines 1–90, stores one message per session in a DashMap and replaces a previous one. Monitor consumption, lines 615–674, removes the queued message before launch, discards it on failed/killed execution and falls back to finalization after a launch error. It is a convenience queue, not reliable fan-out or a durable manager mailbox. A draft scratch record is distinct from that queue's execution authority.

Log persistence, lines 241–306, writes raw stdout/stderr as local JSONL through an asynchronous writer; failures are logged. These files and local execution/turn records do not commit atomically with provider effects, remote issues or before/after Git state. Commit capture and local-to-remote synchronization include best-effort paths. Remote sync, lines 14–87, checks remote existence and logs update failures rather than recording a durable outbox item.

Remote notifications, lines 45–83, create recipient rows after the originating operation and log failures. Persistence makes successfully inserted notifications recoverable records. It does not make their creation atomic with the issue write. The sync mutation hook, lines 627–724, posts inserts, PATCHes or bulk changes and returns transaction IDs for synchronization. The database helper, lines 44–83, obtains that PostgreSQL transaction ID. It is a read-sync acknowledgement marker, not an expected issue revision or a worker attempt fence. Full Electric/fallback/reconnect behavior was not certified.

Access, operation and implementation quality

The remote router, lines 113–150, puts resource routes behind session middleware, lines 28–95. The middleware decodes the access token and verifies its user against its session. Project access, lines 604–648, resolves the organization's ID and checks membership. Ordinary issue updates use that membership boundary; they do not reserve completion for reviewers or bind writes to a current worker attempt. Relationship creation checks only source-issue access in the inspected handler. Full relational/project isolation was not established.

The local server defaults to loopback, lines 59–84. Its origin check, lines 40–80, permits requests without Origin. Relay authentication, lines 30–71, validates relay-marked requests and leaves ordinary direct requests to proceed. Local routing, lines 35–86, shows these controls around workspace/session/remote-proxy operations. This is a local host trust design, not per-agent authorization on every direct local API call. Scoped MCP tools restrict one interface; they do not sandbox an agent already able to call that host API through another tool.

Authentication/member audit emission, lines 5–34 and 117–132, produces structured tracing events. Transaction context, lines 44–72, tags PostgreSQL's application name with a request ID; it does not persist an issue change journal. Combine process logs, turn records, comments and Git references for inspection, but do not describe them as a complete immutable audit of all task changes.

The Compose source, lines 1–20 and 50–80, describes PostgreSQL logical replication, Electric and the remote service. Self-hosting requires that stack, authentication/secrets, frontend builds and separate local workspaces, plus storage/relay choices outside this review. The Docker path for omitting private billing is implemented, but no successful build is established. The retired project routes must also be addressed before promising team Kanban functionality from this pin.

The modular code has useful concrete features: shared Rust/TypeScript request types, transactional remote bulk updates, distinct execution/turn records, worktree rollback attempts, native orchestrator MCP and typed questions. Its main architectural cost is coordinating SQL, local files, Git, OS processes, provider sessions and remote services through partially committed or best-effort operations. None of those individual boundaries substitutes for an authoritative distributed task protocol.

Test evidence and adoption work

Selected MCP assertions, lines 414–438 and 468–483, verify the orchestrator tool set, global discovery and the context/helper distinction. Attachment tests, lines 351–388, check prompt link rewriting. Issue search test, lines 698–705, checks wildcard escaping. No candidate test ran. These assertions do not establish two-agent exclusion, crash-safe launch/link recovery, successful cancellation, reset correctness, durable decisions or current browser usability.

For this baseline, reuse the execution/session model, worktree management, provider resume references, scoped delegation and interactive approval bridge as components. Add a durable task authority with atomic readiness/claim/capacity checks, attempt generations and stale-write rejection; explicit result/evidence and reviewer/child-acceptance gates; durable handoffs/questions and delivery reconciliation; and process-stop/reset outcomes that the coordinator can verify. Restoring an active project interface and maintaining the remote service are separate substantial adoption tasks at this pin. The source supports an execution-supervision foundation, not a complete ready-to-adopt replacement for the requested shared work system.
