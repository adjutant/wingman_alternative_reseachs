# Vibe Kanban: local agent execution with a retired project UI

Source: https://github.com/BloopAI/vibe-kanban

Reviewed commit: `08064e043c2d78ad123b473257ed867e7ce74768`.
Assessment date: November 9, 2026.
Baseline: [Shared task management for an agent organization](../../../AGENT_TASK_MANAGEMENT.md).
Evidence ledger: [review.json](review.json).

## Fit decision

Vibe Kanban has substantive mechanisms for running and inspecting coding agents. It distinguishes workspaces, sessions, execution processes and agent turns. An orchestrator-scoped MCP server can create other sessions, send prompts and inspect execution IDs. Workspaces can contain Git worktrees for several repositories. Approval questions, process cancellation, follow-up sessions, logs and commit references support interactive supervision.

The current project experience is a material adoption limit. The [project page](../repo/packages/web-core/src/pages/kanban/ProjectKanban.tsx), lines 1–115, returns a sunset component after project/authentication loading. The [local wrapper](../repo/packages/web-core/src/pages/kanban/LocalProjectKanban.tsx) delegates to that page. The [sunset component](../repo/packages/web-core/src/pages/kanban/ProjectSunsetPage.tsx), lines 1–63, offers export and says project functionality is retired. The [local project route](../repo/packages/local-web/src/routes/_app.projects.$projectId.tsx) mounts that wrapper. Existing board components and screenshots are not proof of a usable routed Kanban board at this pin.

The maintainer announcement dated April 10, 2026 says the company is shutting down, the project will continue under community maintenance, and hosted remote project/issue services will be removed after a 30-day transition. It says local workspaces will continue. This is maintenance and service evidence, not a live availability test: https://www.vibekanban.com/blog/shutdown

The repository still contains a remote issue API, PostgreSQL models, synchronization code and self-hosting configuration. These can inform a fork or component reuse. They do not restore the retired project UI automatically. The assessed implementation also lacks a transactional ready-work claim, renewable ownership, stale-attempt rejection and an accepted-child completion barrier. It is a useful local execution and supervision reference, but adoption as the baseline's complete shared task authority requires substantial work.

## Architecture and identity boundaries

The [workspace manifest](../repo/Cargo.toml), lines 1–60, separates Rust crates for the local API, persistence, executors, services, worktrees, MCP and relay components; remote is excluded from that main workspace. [Package metadata](../repo/package.json), lines 1–20, identifies version 0.1.45 and separate frontend/backend checks. The [remote crate](../repo/crates/remote/Cargo.toml), lines 1–65, uses Rust 2024, Axum, SQLx/PostgreSQL and JWT support. This describes the pin, not a build result.

The [project type](../repo/crates/api-types/src/project.rs), lines 8–38, gives projects organization, name, color and ordering. The [remote issue type](../repo/crates/api-types/src/issue.rs), lines 21–149, stores project, issue number/simple ID, status, text, priority, dates, parent, ordering, creator and extension metadata. Local [task](../repo/crates/db/src/models/task.rs), lines 14–56, is a different SQLite-backed legacy-shaped record. Do not combine these two models into an imagined single task scheduler.

The [workspace](../repo/crates/db/src/models/workspace.rs), lines 41–81, holds branch, container path/reference, setup/archive/pin state and an optional task ID. A [session](../repo/crates/db/src/models/session.rs), lines 23–38, belongs to that workspace and identifies its configured executor. An [execution process](../repo/crates/db/src/models/execution_process.rs), lines 40–85, records a concrete action, run reason, status, exit code, timestamps and whether it is dropped from current history. [Agent turns](../repo/crates/db/src/models/coding_agent_turn.rs), lines 8–59, retain prompts, provider session/message IDs, summaries and seen state.

This is a useful attempt/session distinction. An executor selection is still not a persistent organizational worker with independent capacity, role, task lease and owner generation. Multiple sessions in one workspace use the same workspace context. [Worktree creation](../repo/crates/workspace-manager/src/workspace_manager.rs), lines 292–373, separates repositories into worktrees and attempts rollback on partial creation. It is Git state separation, not evidence of an OS/container security boundary around every agent.

## Issue creation, selection and allocation

[Issue creation](../repo/crates/remote/src/routes/issues.rs), lines 264–342, checks project access, inserts through the repository and then attempts creator auto-follow separately. [Repository creation](../repo/crates/remote/src/db/issues.rs), lines 325–407, uses a transaction and returns a PostgreSQL transaction ID. A client-generated UUID supports stable optimistic identity. The insert is not a recover-original-result idempotency protocol; repeating the same ID can encounter a key conflict, while choosing another ID can create another issue.

[List handling](../repo/crates/remote/src/routes/issues.rs), lines 180–218, builds a structured query. [Search construction](../repo/crates/remote/src/db/issues.rs), lines 40–90, supports filters, safe sort selection and escaped text patterns. It selects records, not worker reservations. [Issue schema](../repo/crates/remote/migrations/20260112000000_remote-projects.sql), lines 55–90 and 123–152, provides foreign keys, parent pointers, multiple assignees with a unique issue/user pair, and relationship constraints against self-links and duplicate edges. The inspected issue/relation mutations and migration inventory establish no general dependency cycle or ready-work acquisition rule.

[Relationship creation](../repo/crates/remote/src/routes/issue_relationships.rs), lines 98–120, checks access to the source issue and calls a plain [relationship insert](../repo/crates/remote/src/db/issue_relationships.rs), lines 86–131. This path does not walk a dependency graph or check the target's completion. The remote issue update can directly change parent/status fields. It must not be described as an enforced dependency scheduler.

[Assignee insertion](../repo/crates/remote/src/db/issue_assignees.rs), lines 85–126, inserts one issue/user relation. [Workspace-created synchronization](../repo/crates/remote/src/db/issues.rs), lines 602–693, counts linked workspaces, moves pending issues/parents to a status named In progress for the first workspace, and adds its creator if the assignee list was empty. These are separate reads and writes, not exclusive acquisition. Concurrent creators can both observe an empty assignee list; different users can both be inserted. Names such as Backlog, To do and In progress also carry workflow meaning beyond their UUIDs.

## Launch, delegation and partial operations

[Local workspace start](../repo/crates/server/src/routes/workspaces/create.rs), lines 23–66 and 212–320, creates a workspace record, adds repositories, imports/associates attachments and starts execution in separate steps. Attachment import failures can be logged and tolerated. Earlier records/worktrees do not share one transaction with process spawn or remote linking.

[MCP start](../repo/crates/mcp/src/task_server/tools/task_attempts.rs), lines 95–225, resolves an optional issue into a prompt, starts the local workspace, then links it remotely. If the final link fails, it returns a tool error after local execution has started. Retrying that error as if nothing happened can launch another workspace. [Linking](../repo/crates/server/src/routes/workspaces/links.rs), lines 24–89, creates the remote workspace and starts separate PR synchronization. [Remote workspace creation](../repo/crates/remote/src/routes/workspaces.rs), lines 65–104, logs a failure to synchronize the issue after creating the workspace. These are explicit partial-success boundaries.

[MCP routers](../repo/crates/mcp/src/task_server/tools/mod.rs), lines 52–85, expose broad discovery/issue/workspace tools in global mode and a smaller context/session/workspace set in orchestrator mode. [Startup context loading](../repo/crates/mcp/src/task_server/mod.rs), lines 87–121, fails orchestrator startup when context cannot be loaded. The [scope check](../repo/crates/mcp/src/task_server/tools/mod.rs), lines 177–204, rejects another workspace when context exists. This initialization check matters: the helper alone permits a workspace when context is absent, as a unit test explicitly records. Do not infer a normal startup bypass from that isolated helper behavior.

[Session tools](../repo/crates/mcp/src/task_server/tools/sessions.rs), lines 146–193 and 258–320, create a session in the selected workspace, check its scope, prevent launching in the orchestrator session itself and return an execution ID for the child prompt. This is real delegation, beyond board assignment. It does not persist parent/child result dependencies or join accepted outputs. Sessions created in the same workspace also share that workspace's files; a coordinator must manage concurrent edits or allocate separate workspaces.

## Execution consistency, completion and review

[Workspace execution setup](../repo/crates/services/src/services/container.rs), lines 1047–1132, creates a session, supports parallel repository setup or a sequential setup chain, and starts the coding action. Parallel setup errors can be logged while the coding agent still starts. [Execution start](../repo/crates/services/src/services/container.rs), lines 1133–1255, captures repository HEADs, creates the execution record, prepares local message state and an agent turn, then spawns. [Model creation](../repo/crates/db/src/models/execution_process.rs), lines 383–415, inserts Running before OS spawn and inserts repository-state rows separately. Some failures before the spawn error handler can leave a Running record for startup reconciliation.

[Host spawn](../repo/crates/local-deployment/src/container.rs), lines 1316–1405, builds approval support and workspace environment, spawns with a timeout and tracks the child, cancellation token and exit monitor in local maps. The inspected start path has no atomic issue claim, per-worker capacity reservation or expected owner token. Distinct execution IDs help inspect attempts but do not prevent overlapping calls or stale issue writes.

[Exit monitoring](../repo/crates/local-deployment/src/container.rs), lines 480–585, listens for OS exit or an executor completion signal. It maps a closed completion channel to a successful exit, then writes process completion unless the record already looks stopped. [Completion SQL](../repo/crates/db/src/models/execution_process.rs), lines 417–456, updates by process ID without an expected prior status or generation. Its read-before-write stopped check is not an atomic terminal-state guard. A successful process status consequently does not prove accepted product work, and an uncertain signal is not automatically a verified successful result.

[Finalization](../repo/crates/services/src/services/container.rs), lines 204–272, sends success/failure notifications and skips intentional kills. Chained actions, queued follow-ups and unseen markers are handled separately in [monitor continuation](../repo/crates/local-deployment/src/container.rs), lines 585–755. The [turn summary](../repo/crates/local-deployment/src/container.rs), lines 897–942, takes the last assistant message, truncates it to about 4,096 bytes and fills an unset summary. This is convenient reporting, not an independent acceptance decision or structured result contract.

[Issue update SQL](../repo/crates/remote/src/db/issues.rs), lines 408–506, preserves omitted fields and distinguishes explicit nulls, but updates by issue ID without an expected revision, owner or attempt predicate. [Bulk updates](../repo/crates/remote/src/routes/issues.rs), lines 491–584, use one transaction and reject items from another project; notifications follow commit. This is useful batch consistency without stale-attempt rejection.

[PR/merge status synchronization](../repo/crates/remote/src/db/issues.rs), lines 523–601, selects In review or Done by name and checks whether all linked PRs are merged before the latter transition. With no linked PRs, the all-merged test is true; local merge sync uses that same path. Ordinary updates and bulk updates remain alternate writers. Neither path requires accepted child issues, an artifact digest or a qualified reviewer. Executor tool approval answers a different question from final task acceptance.

## Cancellation, reset and restart

[Stop](../repo/crates/local-deployment/src/container.rs), lines 1406–1479, writes terminal status before graceful cancellation and process-group kill. A kill failure returns an error after that database change. [Best-effort workspace stop](../repo/crates/services/src/services/container.rs), lines 707–748, logs individual stop failures, and its [HTTP endpoint](../repo/crates/server/src/routes/workspaces/execution.rs), lines 139–157, returns success after that helper. A coordinator must not infer proven process termination from the endpoint response or database status alone.

[Startup](../repo/crates/server/src/startup.rs), lines 155–169, invokes [orphan cleanup](../repo/crates/services/src/services/container.rs), lines 273–326. It marks all remaining Running records failed and captures available HEAD state. It does not attach to surviving OS processes or acquire an expiring distributed ownership lease. Host-level process cleanup and safe retry remain separate concerns.

[Follow-up](../repo/crates/server/src/routes/sessions/mod.rs), lines 124–235, checks executor continuity and uses a provider session/message ID when available. [Reset](../repo/crates/services/src/services/container.rs), lines 633–705, validates that the target process belongs to the session, reconciles worktrees, then calls best-effort stop and marks later history dropped. [Git reconciliation](../repo/crates/git/src/lib.rs), lines 892–929, can skip dirty state or log reset failure and return an outcome; the reset caller does not check that outcome. The record history can therefore advance after an unapplied reset. Worktree reconciliation also precedes stop in this inspected ordering, rather than establishing that all writers have stopped first.

[Deletion](../repo/crates/server/src/routes/workspaces/core.rs), lines 99–185, refuses a workspace with running non-dev-server records, tries to stop dev servers, deletes the local record, optionally requests remote deletion and schedules cleanup. It returns Accepted. The running check is separate from deletion, dev-server stop/remote deletion can fail, and asynchronous file cleanup is not an atomic rollback boundary. Complete worktree cleanup was not certified.

## Decisions, communication and persistence

[Approvals](../repo/crates/services/src/services/approvals.rs), lines 20–258, contain an execution ID, question/tool distinction, pending/completed maps, oneshot response, timeout and typed answer validation. The [executor bridge](../repo/crates/services/src/services/approvals/executor_approvals.rs), lines 16–149, notifies the user and waits for an answer or cancellation. The approval patch stream supplies a snapshot and replaces it on broadcast lag. These are meaningful interactive decision mechanisms. Their authoritative pending state is in process memory, so they are not durable escalations that another host can resolve after restart. No organizational reviewer identity is bound to the ordinary local approval response handler.

The [follow-up queue](../repo/crates/services/src/services/queued_message.rs), lines 1–90, stores one message per session in a DashMap and replaces a previous one. [Monitor consumption](../repo/crates/local-deployment/src/container.rs), lines 615–674, removes the queued message before launch, discards it on failed/killed execution and falls back to finalization after a launch error. It is a convenience queue, not reliable fan-out or a durable manager mailbox. A draft scratch record is distinct from that queue's execution authority.

[Log persistence](../repo/crates/services/src/services/execution_process.rs), lines 241–306, writes raw stdout/stderr as local JSONL through an asynchronous writer; failures are logged. These files and local execution/turn records do not commit atomically with provider effects, remote issues or before/after Git state. Commit capture and local-to-remote synchronization include best-effort paths. [Remote sync](../repo/crates/services/src/services/remote_sync.rs), lines 14–87, checks remote existence and logs update failures rather than recording a durable outbox item.

[Remote notifications](../repo/crates/remote/src/notifications.rs), lines 45–83, create recipient rows after the originating operation and log failures. Persistence makes successfully inserted notifications recoverable records. It does not make their creation atomic with the issue write. The [sync mutation hook](../repo/packages/web-core/src/shared/lib/electric/collections.ts), lines 627–724, posts inserts, PATCHes or bulk changes and returns transaction IDs for synchronization. [The database helper](../repo/crates/remote/src/db/mod.rs), lines 44–83, obtains that PostgreSQL transaction ID. It is a read-sync acknowledgement marker, not an expected issue revision or a worker attempt fence. Full Electric/fallback/reconnect behavior was not certified.

## Access, operation and implementation quality

The [remote router](../repo/crates/remote/src/routes/mod.rs), lines 113–150, puts resource routes behind [session middleware](../repo/crates/remote/src/auth/middleware.rs), lines 28–95. The middleware decodes the access token and verifies its user against its session. [Project access](../repo/crates/remote/src/routes/organization_members.rs), lines 604–648, resolves the organization's ID and checks membership. Ordinary issue updates use that membership boundary; they do not reserve completion for reviewers or bind writes to a current worker attempt. Relationship creation checks only source-issue access in the inspected handler. Full relational/project isolation was not established.

The local server [defaults to loopback](../repo/crates/server/src/main.rs), lines 59–84. Its [origin check](../repo/crates/server/src/middleware/origin.rs), lines 40–80, permits requests without Origin. [Relay authentication](../repo/crates/server/src/middleware/relay_request_signature.rs), lines 30–71, validates relay-marked requests and leaves ordinary direct requests to proceed. [Local routing](../repo/crates/server/src/routes/mod.rs), lines 35–86, shows these controls around workspace/session/remote-proxy operations. This is a local host trust design, not per-agent authorization on every direct local API call. Scoped MCP tools restrict one interface; they do not sandbox an agent already able to call that host API through another tool.

[Authentication/member audit emission](../repo/crates/remote/src/audit/mod.rs), lines 5–34 and 117–132, produces structured tracing events. [Transaction context](../repo/crates/remote/src/db/mod.rs), lines 44–72, tags PostgreSQL's application name with a request ID; it does not persist an issue change journal. Combine process logs, turn records, comments and Git references for inspection, but do not describe them as a complete immutable audit of all task changes.

The [Compose source](../repo/crates/remote/docker-compose.yml), lines 1–20 and 50–80, describes PostgreSQL logical replication, Electric and the remote service. Self-hosting requires that stack, authentication/secrets, frontend builds and separate local workspaces, plus storage/relay choices outside this review. The Docker path for omitting private billing is implemented, but no successful build is established. The retired project routes must also be addressed before promising team Kanban functionality from this pin.

The modular code has useful concrete features: shared Rust/TypeScript request types, transactional remote bulk updates, distinct execution/turn records, worktree rollback attempts, native orchestrator MCP and typed questions. Its main architectural cost is coordinating SQL, local files, Git, OS processes, provider sessions and remote services through partially committed or best-effort operations. None of those individual boundaries substitutes for an authoritative distributed task protocol.

## Test evidence and adoption work

Selected [MCP assertions](../repo/crates/mcp/src/task_server/tools/mod.rs), lines 414–438 and 468–483, verify the orchestrator tool set, global discovery and the context/helper distinction. [Attachment tests](../repo/crates/server/src/routes/workspaces/create.rs), lines 351–388, check prompt link rewriting. [Issue search test](../repo/crates/remote/src/db/issues.rs), lines 698–705, checks wildcard escaping. No candidate test ran. These assertions do not establish two-agent exclusion, crash-safe launch/link recovery, successful cancellation, reset correctness, durable decisions or current browser usability.

For this baseline, reuse the execution/session model, worktree management, provider resume references, scoped delegation and interactive approval bridge as components. Add a durable task authority with atomic readiness/claim/capacity checks, attempt generations and stale-write rejection; explicit result/evidence and reviewer/child-acceptance gates; durable handoffs/questions and delivery reconciliation; and process-stop/reset outcomes that the coordinator can verify. Restoring an active project interface and maintaining the remote service are separate substantial adoption tasks at this pin. The source supports an execution-supervision foundation, not a complete ready-to-adopt replacement for the requested shared work system.
