Taiga backend: shared planning records without an agent execution contract

Source: https://github.com/taigaio/taiga-back

Reviewed commit: 8ab6a4e3b5f6fbbfcbf108a6449011f07b7308aa. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json. Companion: Taiga frontend assessment.

Fit decision

Taiga supplies a substantial shared planning and discussion service. Projects contain stories, tasks, milestones, roles, statuses and retained context. Agents can use the same HTTP records as a human-facing client. Database-backed history, comments, watchers, notifications, attachments and exports make it more than a board that only launches coding sessions.

The reviewed backend does not supply an autonomous-worker ownership protocol. A task assignee is a project member, not an execution reservation. The normal edit path has version checks, transactions and database advisory locks. These are useful collaboration safeguards. They do not require an eligible worker, an unowned task, a live lease or a current execution-attempt token. An authorized editor can reassign work or finish its record while the previous worker continues elsewhere.

Story completion has a meaningful child-status calculation. With tasks present, all task statuses must be closed for the calculated story completion flag to become true. Without tasks, the story's status decides. This is progress aggregation, not acceptance of versioned child results. Bulk board movement also follows a different persistence and recalculation path from normal record editing.

Taiga fits as a planning and communication authority behind an added agent coordinator. Adopting it as the complete coordination runtime would require ownership, readiness, recovery and acceptance mechanisms. The backend declares MPL 2.0 in its license and contribution statement, lines 42–46, and license, lines 1–18. The frontend's implementation and AGPL declaration are covered in its separate companion assessment; they are not attributed to this server repository.

Scope and evidence level

The full worktree contains 2,015 tracked files. This is a targeted static review of task and story records; project membership, role and status models; CRUD hooks and serializers; advisory locking and optimistic conflict checks; selected bulk writers; completion signals; history; notifications; event backends; webhooks; authentication and project permissions; context models, search, export and deployment entry points. Selected integration-test assertion bodies were read. No candidate application, dependency installation, build, migration or test was executed.

The ledger records source ranges and hashes. It also identifies the separately inspected source archive of the pinned locking dependency. This is not an every-line audit or a certification of all imports, plugins, migrations, file serving, token lifecycle, HTTP security, scaling, browser behavior or production races. The browser client is a separate codebase. Test names and source assertions do not establish passing runtime tests.

Architecture and domain model

API routing, lines 8–23, mounts the custom REST router under api/v1/. Task and story registrations, lines 179–206, expose records, watchers and related planning resources. The server uses its own serializer/viewset machinery with model-specific permissions, validation and chained pre/post hooks. This is not simply current upstream Django REST Framework behavior.

Dependency inputs, lines 1–32, constrain Django below version 4. The resolved dependencies, lines 25–82, include Django 3.2.25, Celery 5.5.3 and django-pglocks 1.0.4. PostgreSQL is explicit in database configuration, lines 25–33, and in model ArrayFields. The container definition, lines 7–41, starts from Python 3.11 and installs the resolved requirements. These describe the pinned deployment, not a successful compatibility or security test.

The project and membership model, lines 53–105 and 164–231, has a stable project row, unique slug, description, owner, members, optional backlog/Kanban/wiki/issue panels and public/anonymous permission arrays. Membership links users to project roles and distinguishes administrators. Roles, lines 300–332, carry project-specific permission arrays. Custom role labels can represent coordinators, specialists and reviewers, but the schema does not turn those labels into separate worker execution identities.

The task model, lines 23–120, stores a subject, description, project, optional story and milestone, status, owner, assignee, ordering, dates, attachments and external references. Owner is the creator set by the API; assignee is mutable responsibility. Stories, lines 65–167, add estimates, several planning orders, generated-from links, a swimlane and multiple assigned users. The inspected models have no execution attempt, lease expiry, heartbeat or fencing generation.

Reference allocation, lines 22–62 and 93–132, uses a project sequence and a project/ref uniqueness constraint. Sequence operations, lines 13–56, use PostgreSQL nextval. Database IDs identify rows; display references are project-local and are regenerated when records move between projects. They should not be treated as immutable global artifact identifiers.

Creation, discovery and assignment

Task creation and list handling, lines 81–115, validate input, check permissions, run hooks, save the record and run post-save hooks before serialization. Task-specific checks, lines 98–134, enforce common project membership for story, milestone and status, align a task's milestone with its story and set the creator. Assignee validation, lines 16–31, requires the target user to be a project member. That is meaningful relationship validation, not a rule that only the assignee may edit or finish the task.

Task discovery, lines 40–96, supports project, story, milestone, status, assignee, owner, watchers, tags, text and dates. Story discovery, lines 49–92, adds dashboard, epic, swimlane and planning orders. These are query snapshots. Neither surface reserves a returned item or verifies an executable prerequisite graph. Bulk task creation, lines 246–268, creates several ordinary task records with callbacks; it does not launch workers.

Blocked data, lines 17–29, is a boolean and free-text note. Clearing the flag clears the note. The similarly named BlockedByProjectMixin, lines 264–315, rejects writes to a project with a blocking code; it is not dependency readiness for an individual task. This distinction matters when an agent interprets a displayed blocked state.

Concurrent editing and ownership limits

The base update path, lines 156–193, wraps the normal edit in an explicit transaction and model/id advisory-lock decorator. The decorator, lines 37–51, obtains a PostgreSQL advisory lock for the model and primary key. OCC validation, lines 21–87, requires a valid supplied version, compares it with the current database version, checks fields changed in intervening history and increments the stored version. A stale edit to an overlapping field is rejected; stale edits to disjoint fields can be accepted.

The history lookup, lines 347–364, derives intervening field names from the latest history diffs. This is not a compare-and-swap predicate on an unassigned task or a current attempt. A worker with ordinary modify permission can read a fresh version and replace an existing assignee. An old worker can likewise fetch a fresh version and continue writing. The authorization contract is project editing, not ownership of execution.

There are also narrower concurrency concerns. Task update, lines 177–207, loads self.object before delegating into the decorated base method. Story update, lines 310–340, does the same. The base method retains a previously loaded object. Serializer restoration, lines 1063–1087, applies supplied fields to that object, and saving, lines 1097–1127, calls its ordinary model save without a dirty-field restriction. Source-level inference: two requests can preload the same row, then a permitted disjoint edit can save stale values for fields absent from its request. The lock does not itself refresh that snapshot. This scenario was not reproduced at runtime.

The pinned dependency archive confirms that advisory_lock acquires a session lock and releases it when its context exits. The server nests that context inside the outer transaction decorator. Unlock therefore precedes the outer transaction's exit; do not infer commit-spanning serialization from the decorator name alone. Primary dependency source: https://files.pythonhosted.org/packages/59/76/2c7d104151316077dcaa103e1d5652ded6c32798c8d706570fb7b48385cb/django-pglocks-1.0.4.tar.gz. The ledger records its verified archive hash and inspected member. These observations qualify the lock's boundary; they are not a production race test.

Alternate writers, WIP and planning consistency

Bulk task validators, lines 81–177, validate project and selected related scopes. They accept task IDs and order values, not expected record versions. Task order and milestone services, lines 75–148, calculate several writes and emit change events. The low-level bulk helper, lines 115–155, schedules its ID-based SQL update in transaction.on_commit, retries database errors up to its limit and does not re-raise after exhausting that path. Its transaction decorator does not make the eventual callback part of the already committed transaction.

The task services request events before scheduling these bulk SQL writes. With autocommit, an event can be sent before the write. Under an outer transaction, its callback can also precede the SQL callback. A client that refetches immediately on that event can observe old ordering. A post-commit failure cannot roll back the original operation. This is a source-level ordering and failure boundary, not a measured delivery failure.

Bulk Kanban movement, lines 468–512, checks project permissions, blocked/archive state and destination scope. Its validator, lines 169–199 and 244–253, verifies relevant project relationships. The service, lines 284–398, separately updates ordering, then status/swimlane, then invokes or queues closure recalculation and history. It does not call normal OCC validation or increment each story's version. An ordinary editor operation therefore cannot be assumed to have the same concurrency semantics as a board move.

Status WIP limits, lines 603–631 and 946–969, are stored integers. Neither the reviewed normal story preconditions nor this bulk movement service counts occupancy and rejects overflow. They are planning configuration, not an authoritative worker-capacity reservation. The separate frontend determines their presentation.

Decomposition, progress and completion

Epic relationships, lines 60–85 and 105–116, associate stories with epics and prevent duplicate story/epic pairs. Stories have tasks and generated-from issue/task links. These support decomposition and follow-up provenance, but not arbitrary nested agent executions or dependency ordering.

Task signal registration, lines 14–53 and 83–89, connects finished-date handling and story/milestone recalculation. Signal bodies, lines 27–100, update parent progress when tasks are saved, deleted or moved and set/reset the task's finished date from its status. Story signals, lines 49–98, propagate milestones and recalculate closure.

The story calculation, lines 455–488, requires a non-null story status. Without tasks, its status must be closed. With tasks, all task statuses must be closed, regardless of whether the story's own status is open. is_closed and finish_date are then updated. A visually closed story status with open tasks does not establish calculated completion; conversely, all closed tasks can complete a story still assigned an open status. Deleting the last task changes which rule applies.

Milestone closure, lines 17–43, aggregates closed stories, unparented tasks and issues, and requires at least one constituent. These are useful consistency calculations. They do not check test reports, reviewer qualification, unresolved decisions or accepted result versions. A review column can be configured as a status, but normal editing still lacks the baseline's acceptance contract. The server also does not cancel a real worker when a record is closed or deleted.

Context, audit and communication

Wiki pages, lines 21–71, retain project content and owner/modifier metadata. Custom attributes, lines 24–102 and 139–150, supply project-scoped schema and JSON values. Attachments, lines 25–101, retain metadata, a SHA-1 content digest and a deprecation flag. Attachment API checks, lines 54–76, verify that the target exists and shares the attachment's project. These are useful context primitives. They do not bind a review decision to an immutable accepted task result, and database rollback does not prove rollback of external file storage.

History hooks, lines 44–73, take snapshots and comments on normal save/delete. Snapshot creation, lines 367–436, uses its own transaction/advisory lock, stores actor identity, diffs, values and optional snapshots, and skips empty changes. This records human and API changes. Derived closure writes and bulk recalculation have different history/version paths; it is not a uniform attempt journal.

Notification hooks, lines 64–137 and 373–387, process comments, mentions, watchers and assignment. Notification storage, lines 47–83 and 114–123, persists pending history notifications and web notifications. Recipient selection and email queuing, lines 136–206 and 243–269, apply view permissions/preferences and retain associated histories and recipients. Web notification listing, lines 48–77, filters to the current user's records and can return unread items. These durable records permit later inspection; receiving one does not prove a worker acted.

Pending email is not guaranteed delivery. Email processing, lines 272–389, locks the pending record, attempts recipient sends, catches/logs send exceptions and then deletes the notification. Periodic scheduling, lines 34–39, and bulk processing, lines 577–585, provide a processing route, not an acknowledgement-based retry contract for each failed recipient.

Live events, lines 23–94, normally defer publication until database commit. That prevents a normal rolled-back write from intentionally publishing its event, but there is no SQL outbox linking commit to reliable publication. RabbitMQ publication, lines 40–67, uses a topic exchange and logs connection/publish failures; the PostgreSQL backend, lines 14–23, uses NOTIFY. Neither inspected publisher supplies a persisted consumer replay cursor. Durable history and refetching remain distinct recovery mechanisms.

Webhook dispatch, lines 29–73, follows visible history and schedules work after commit. Sending, lines 53–129, signs payloads, checks private addresses when configured, controls redirects and logs responses/errors. Its session.send call has no explicit timeout. The task wrappers, lines 132–182, do not add an automatic retry policy. Only ten logs are retained per webhook. Manual resend, lines 47–67, exists, but consumers must handle duplicate effects; this is not an exactly-once delivery or agent handoff protocol.

Permissions and cross-host operation

Task permissions, lines 14–46, distinguish view, add, modify, comment, delete and bulk operations, with administrator/superuser alternatives. Comment-versus-edit checks, lines 49–71, permit comment-only requests under a separate permission. Permission calculation, lines 63–129, combines roles and public/anonymous permissions. List filtering, lines 136–172 and 207–208, limits task results by relevant project access. The task list's AllowAny declaration does not mean every task is public.

JWT authentication, lines 61–73 and 93–152, validates tokens and loads an active non-system user. Token decoding, lines 113–130, uses the configured algorithm and signature verification. Default authentication configuration, lines 473–483, also includes a debug session backend and application-token authentication. Application authentication, lines 14–31, and token lookup, lines 15–22, resolve a stored token to its user. They do not create per-task execution capability tokens. Complete issuance, revocation and inactive-user behavior across every mechanism were not audited.

One inspected permission boundary needs correction before relying on notification isolation. Read-marker handling, lines 52–95, defines a boolean ownership check, calls it without a target and ignores its false return, then loads a notification by ID without a user filter and sets its read timestamp. The lookup helper, lines 51–63, supplies lookup/error conversion, not ownership enforcement. API initialization, lines 361–369, authenticates and throttles but does not supply the missing ownership check. Routes, lines 35–42, register the marker paths. Router construction, lines 227–254, and viewset binding, lines 77–95, retain the class's raw patch handler on the registered list views. Source-level implication: a caller who can reach the marker route and knows another notification ID can alter its read state. This was not exercised against a running service and is not a claim that notification contents can be read through that route.

Several execution hosts can share one server/database. This avoids independent local board replicas, but a disconnected worker can continue external work after reassignment. Project edit permissions, JWT expiry and database advisory locks cannot fence that worker's filesystem, Git or external side effects.

Usability, operation and implementation quality

Search, lines 22–92, combines permitted project resource categories, with bounded parallel query workers and separate result groups. Task serializers expose versions, blocker information, dates, descriptions and extra display data, lines 25–83. These help agents and a human client inspect the same state. They do not reveal running agent attempts because those records do not exist in the reviewed domain.

Milestone records, lines 24–77, include dates, ordering and availability; date validation rejects an inverted interval. This and optional project panels support a small team's choice of workflow. An agent adapter still needs to resolve several related IDs, provide versions, understand calculated versus configured closed state and distinguish ordinary edits from bulk planning.

The API entry point, lines 9–32, runs migrations and loads initial templates before starting three Gunicorn workers. The async entry point, lines 9–20, starts Celery with its scheduler. Production configuration, lines 16–99, includes PostgreSQL, protected media storage, email, RabbitMQ events and Celery. Container configuration, lines 18–48, takes database/site/secret values from the environment and controls webhook policy. These are explicit operating components, not evidence of a tested production topology. Coordinated database/media backups, broker/worker supervision and compatibility of the separately deployed frontend/event service remain deployment work.

Project export, lines 48–81, checks permissions and supports immediate JSON/gzip files or an asynchronous export with expiry. This is an interoperability path; it does not establish full-instance backup, restore fidelity or recovery of missing execution-attempt state.

The architecture has substantive implementation behind its planning abstractions: scoped validation, database references, conflict checking, durable history and aggregate progress. Its complexity is concentrated in inherited hooks, model signals, direct SQL and post-commit/background side effects. Those mechanisms do not enforce identical rules across every mutation. Adding a claim endpoint alone would leave ordinary edits, bulk changes and completion paths outside the new contract.

Test-source evidence and adoption work

Selected OCC assertions, lines 251–349, expect sequential same-field stale edits to fail, current versions to succeed, disjoint stale edits to succeed and missing versions to fail. They patch task preconditions and use sequential client requests. They do not test the overlapping preload/commit windows described above or exclusive agent acquisition.

Story autoclosing assertions, lines 17–124, cover open tasks blocking calculated completion, status-based closure without tasks and the effect of deleting/moving tasks. Bulk Kanban assertions, lines 36–92, check resulting ordering, status and swimlane without supplied versions. Task permission/assignee assertions, lines 971–1044, cover private/public filter access and project-member assignment; assignment cases mock OCC validation. Notification assertions, lines 1198–1246 and 1452–1514, inspect assignment/watcher/mention records and mocked SMTP error logging. None was run in this assessment.

For the target organization, retain Taiga's shared records, project roles, discussion, history, filters, exports and planning views. Add an authoritative assignment/attempt model, an atomic readiness-and-claim transition, renewal/reclaim and stale-attempt checks, and explicit stop/recovery semantics. Enforce those rules in ordinary, bulk and background writers. Bind acceptance to an artifact version and required child results. Add durable delivery/reconciliation where downstream actions need reliability, and repair the notification marker permission path. Evaluate the separate frontend before choosing the combined product for daily human use.
