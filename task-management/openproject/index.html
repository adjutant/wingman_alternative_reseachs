OpenProject: governed project work without an agent execution lease

Source: https://github.com/opf/openproject

Reviewed commit: 05d9afe72a3c9198e26c0284c213f733c4863ca2. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

OpenProject provides a substantial shared project authority. Projects, work packages, hierarchy, relations, role permissions, workflow transitions, journals, notifications, versions, boards and sprints have native implementations. Work-package editing combines contracts, optimistic lock versions and database transaction/advisory-lock context. This is useful infrastructure for a human manager and several agents sharing planning records.

It does not make an assignee a leased agent execution owner. The inspected model and mutation interfaces have no current execution-attempt identity, worker capacity reservation or heartbeat-based task recovery. A worker can use the same governed records as a person, but a separate coordinator must decide who may execute, how interrupted execution resumes, and which child results the parent has accepted.

The native MCP server is an important interface and an adoption constraint. Its endpoint, lines 31–72, returns unavailable unless the Enterprise mcp_server entitlement and server configuration are enabled. The HTTP API remains a separately reviewed agent interface. Accessible MCP implementation should not be described as an unconditionally available Community feature. The top-level license, lines 1–25, is GPL version 3; inherited components carry their own notices. This report covers the pinned source and the inspected feature gates, not every hosted or commercial offering.

Adopt it as a governed planning and discussion layer if its operating footprint and edition boundaries fit. To adopt it as the complete agent coordination runtime, add an execution contract that uses the existing service/permission boundaries and governs alternate writers as well as the normal API.

Scope and evidence level

The preserved checkout has 25,930 tracked files. This targeted static review follows work-package create, read/selection, update, hierarchy/relation mutation, progress calculation, closure, duplicate closure and deletion. It inspects shared service context, lock/version handling, contracts, MCP/API entry points, selected backlog batch and sprint lifecycle code, journal creation/aggregation, notification jobs and visibility, outgoing webhooks, token authentication, representative browser changesets/detail markup and deployment configuration. Selected contract, request and concurrency-test assertion bodies were read.

No candidate application, dependency installation, build, migration or test was executed. This is not an every-line audit, production race test or certification of all plugins, automation actions, custom fields, integrations, importers, exporters, edition gates, hierarchy operations, attachment/file routes, mail/push delivery, OAuth/OIDC lifecycle, deployment, performance or browser/accessibility behavior. The ledger identifies the actual inspected ranges. Framework/gem configuration and source tests are evidence of implementation and intended contracts, not passing runtime results.

Architecture and domain model

The work-package table, lines 31–68, stores project, type, subject, description, dates, status, assignee, author, responsible principal, effort/progress fields, parent and a nonnull lock version. The model, lines 31–95, connects projects, principals, journals, storage links, repository changesets, pull requests and meeting context. Stable numeric records coexist with semantic identifier support. These are work records, rather than process/session records.

Project modeling, lines 31–110, supports project/program/portfolio workspace types, members, groups, hierarchy, work packages, versions, phases, queries, forums, repository and wiki associations. Project/work-package permissions can differ; a human or technical account gains authority through roles and memberships. There is no need to invent a project out of a repository path, but agent-specific leadership continuity and supervision remain external responsibilities.

Service context, lines 31–72, runs updates within a user and notification context, using a model advisory-lock transaction when a model exists. The mutex helper, lines 31–94, names locks by model class and ID and passes transaction-scoped locking inside an ActiveRecord transaction. The base contracted writer, lines 31–126, sequences validation, attribute setup, persistence and dependent effects. Failure results cause rollback through the context helper. This is a coherent place to enforce business transitions across entry points.

The update service, lines 31–203, also updates ancestors, reschedules related work, handles project/type changes and consolidates duplicate dependent updates. That depth has costs: completion and movement involve several domain objects and callbacks. A transaction boundary does not imply that every generated side effect, workflow override or plugin has the same policy as a direct user edit.

Create, select, edit and assign

API routing, lines 31–105, exposes collection reads/create, visible work-package detail, updates, deletion and related resources. Creation, lines 31–127, sets attributes through a contract, saves, updates ancestors, reschedules related packages and attempts to add the creating user as watcher. The create contract, lines 30–74, requires project add rights and applies field permissions. A new default model is created for a normal call. The MCP create tool explicitly declares itself non-idempotent; retrying a request is not equivalent to retrieving its prior result.

MCP search, lines 31–143, filters visible work packages by project, assignee, status, type, subject, labels and versions. The search machinery, lines 95–138, applies filters and pagination; the base tool defines a page size of 40. Null assignee search is useful for finding unassigned work. It is a snapshot query, not acquisition of those records.

MCP updating, lines 31–90, requires lockVersion, loads a visible record and calls the common UpdateService. API parsing, lines 31–58, converts missing lock version into nil. The update contract, lines 30–125, rejects nil or changed lock versions and checks visibility and edit/move permissions. Persistence, lines 31–84, saves the versioned model. These mechanisms protect against ordinary stale edits; the database lock version remains relevant if another edit committed after the model was loaded.

This is a useful building block for an agent claim, but not that claim itself. Assignee fields, lines 91–115, validate visible assignable principals. They do not require a previously unassigned task, a live worker runtime, remaining capacity or a current attempt token. The model permits one assigned principal and another responsible principal, each potentially representing a user/group. Default assignment, lines 667–672, can come from the category. An authorized editor can reassign a task while an earlier external worker continues. Rejecting the worker's old lock version helps, but a worker that reloads the record can regain ordinary edit capability without proving it still owns execution.

Contracted updates, lines 54–80, and the shared context combine the primary edit with dependent results. Project movement, lines 92–125, checks source rights as well as target-side field rights. Dependent updates, lines 69–144 and 171–203, use dedicated contracts and consolidate related changes before saving. These are deliberate collaboration controls. They should be reused for a coordinator integration, rather than bypassed through raw database status/assignee writes.

Hierarchy, relation rules and completion boundaries

Parent validation, lines 300–359, checks existence, milestone suitability, self/descendant relationships, project policy and permission to manage the parent. Relatability, lines 179–226 and 256–285, excludes the work package itself, existing/incompatible links and transitive paths through a recursive query. Relation contracts, lines 31–118, require visible/manageable endpoints and reject nonrelatable endpoint changes. Relations therefore have more semantics than decorative blocker labels.

There is a precise coverage boundary. The relation contract's relation_changed? checks changes to the two endpoints, not relation_type. The update contract, lines 31–57, keeps endpoints immutable except swaps. The MCP update tool, lines 31–101, nevertheless permits changing type while retaining endpoints. A type-only change between canonical types does not run the same circular-dependency validation. Model normalization, lines 104–140 and 211–219, swaps endpoints only for reverse types. This is a source-level validation gap; concurrent graph edits and an actual cycle insertion were not exercised. Do not generalize the existence of a cycle check into proof that every relation mutation preserves an acyclic graph.

Blocking, lines 231–247, finds still-open blocker packages. Normal allowed-status calculation, lines 708–768, combines workflow transitions with the current state and removes closed statuses while blocked. This can prevent an ordinary closure while a blocker remains open. It does not prevent all open-state progress or assignment, so it is not a ready-queue admission rule for execution.

Workflow validation, lines 188–204 and 361–373, uses the original persisted status to avoid skipping ordinary intermediate transitions. Roles, author/assignee conditions and type-variant workflow rows determine available states. There is a type-change exception: the transition validator bypasses its predecessor check when type changes. Type reassignment, lines 459–473, uses the destination type's available statuses and retains an already available target status. The report therefore attributes blocker/role transition enforcement to the normal path, not to every compound type/status update.

Readonly-state rules, lines 654–674, limit writes in an already readonly status to status transitions. This is a real controlled-edit mechanism. It does not bind a review decision to an immutable execution result. Native workflow configuration can represent review, but a closed status alone proves neither test success nor acceptance of the exact artifacts produced by a particular worker attempt.

Ancestor updating, lines 31–151, derives effort, remaining work and progress across the hierarchy, with weighted or simple-average modes. Status-based progress, lines 31–82, can derive percent complete from status and remaining work from that percentage. These are progress calculations. The inspected normal close contract does not require a parent to join accepted child results.

Duplicate closure is another explicit exception. The model callback, lines 139–145, runs duplicate closure before save. Its implementation, lines 673–695, updates duplicates as User.system with EmptyContract and records a duplicate-closure cause, logging a failure rather than making it the initiating package's accepted result. Regular user workflow/readiness rules cannot be assumed to gate that secondary closure. This is a business automation path, not a reviewer decision for each duplicate's current execution.

Planning and alternate mutation paths

Versions, lines 31–110, have project sharing, open/locked/closed state, dates and targeted work packages. Sprints, lines 31–122, have goals, planning/active/completed state, date requirements and configurable active-sprint limits. Boards, lines 31–79, retain project, linked planning object, query-backed content and free/action board types. These are substantial planning capabilities; their limits concern planning structure, not the count of concurrent agent executions.

Backlog single-item movement, lines 31–91, wraps common work-package updating and list reordering in a transaction, re-raising rollback when the nested result fails. Batch movement, lines 31–245, uses a separate savepoint, declares a 50-item limit, orders lifecycle/member locks, serializes placement and revalidates the cohort and destination. Members are reloaded before sequential movement, and final records are reloaded before callbacks observe them. This is stronger implementation evidence than assuming a board drag is merely a sequence of unrelated PATCHes. It still does not reserve agent capacity or join completed results.

Finishing a sprint, lines 31–101, can move open work to another sprint or backlog and mark the sprint completed. The completion timestamp is prepared before moving work to preserve burndown meaning. This is an appropriate distinction between ending an iteration and completing its remaining tasks. An integration should retain that distinction when reporting project delivery.

Deletion, lines 31–128, plans descendant deletion or detachment, validates deletability, updates related/ancestor scheduling and removes associated notifications. It also reloads and retries a stale descendant destruction. This manages shared records and hierarchy, not a worker process. Deleting or closing work cannot undo an external commit, network call or tool action already issued by an agent.

Journals, communication and asynchronous effects

Journal save hooks, lines 50–107, run after model save, create journal data and send a journal-created event. Journal creation, lines 44–111 and 209–231, uses a journal transaction and a composed SQL statement for snapshot changes. Associated snapshot data include context beyond plain notes. This gives durable inspection integrated with the work record's save path, rather than only a transient activity stream.

History is deliberately aggregatable. Aggregation rules, lines 592–641, require an enabled time window, same user and compatible note, restriction and cause. Predecessor cleanup, lines 41–62, can delete prior snapshot data for the aggregated record before replacement. The journal ID can remain useful for navigation while its content changes. It is therefore unsuitable as an immutable acceptance reference without an added revision/content binding.

MCP comments, lines 31–75, add public/internal notes through the note service, lines 31–91. That service validates permissions within model context, saves journals and handles attachment claims. Comments and actor/cause records make practical handoffs possible. They are not a typed question-answer protocol, successor acknowledgement or proof that a parent incorporated an agent result.

Event subscription, lines 31–72, schedules work-package follow-up logic, notification creation and journal-completion jobs. The event facade, lines 30–88, uses in-process ActiveSupport notifications; it is not itself a durable consumer queue. Application job configuration, lines 201–219, uses external GoodJob workers, preserves job records and disables automatic retry of unhandled errors. Specific jobs can define narrower retry policies. This review does not certify every event-to-job crash boundary or adapter transaction behavior.

Notification workflow, lines 53–96, creates notifications before sending mail, sends eligible mentions promptly and schedules later alerts after aggregation. Journal completion jobs, lines 31–87, compare journal ID and update timestamp so an outdated aggregation job does not finalize a superseded snapshot. Recipient notification creation, lines 65–140, creates or updates existing per-journal/recipient records and removes recipients no longer selected. These are substantive asynchronous lifecycle mechanisms, not worker heartbeat or task-attempt fences.

Stored notifications, lines 31–74, retain reason, actor, recipient, journal/resource and delivery state, with push scheduled after commit. Visibility, lines 31–46, requires both the recipient and current access to the work package. The notification API, lines 31–112, scopes individual reads and read/unread changes, and offers filtered bulk actions. Later inspection can recover missed interface events. A read marker does not acknowledge accepted work or guarantee prior email/push delivery.

Outgoing represented webhooks, lines 31–101, check configured project acceptance, serialize a system-user view and optionally sign the body. Sending, lines 31–98, uses the SSRF-protection wrapper, records response/error details and re-raises selected network timeouts. The job policy, lines 31–46, retries selected timeout classes up to three attempts. Other logged outcomes are not proof that a receiver processed an event. A coordinator needs its own acknowledgement and reconciliation contract.

Identity, human inspection and operation

Authentication registration, lines 31–62, distinguishes API and MCP scopes and their allowed strategies. The API-token strategy, lines 31–82, requires token authentication to be enabled, resolves a token and rejects inactive users. Token inheritance, lines 31–40, uses hashed tokens; hash lookup, lines 49–110, supports peppered HMAC and legacy upgrade. Expiry, lines 31–82, rejects expired tokens. These credentials identify user authority. They do not identify the task attempt currently allowed to execute or revoke every old worker when assignment changes.

MCP tool handling, lines 112–157, obtains current user from server context and formats plain/structured responses. Read-only/idempotent annotations are hints about an operation, rather than transaction identifiers or replay protection. The update tool's lock-version requirement is a useful agent-facing instruction: re-read conflicts and reason about the changed state. It is not authorization to overwrite a new owner's work after re-reading.

The browser changeset, lines 175–215 and 395–465, serializes form refreshes, carries lock version and applies schema-writable changes. Work-package specialization, lines 34–123, refreshes forms after project/type changes and avoids sending unedited descriptions/generated subjects. It also emits a work-package-updated event when a local value is set, with a source comment acknowledging that this can precede persistence. Interface refresh signals must not be treated as committed progress events.

Detail markup, lines 1–115, connects state, author, last-update time, description, project navigation and schema-driven attribute groups. Layout selection, lines 309–331, changes column layout by available width. These are useful inspection provisions. Their presence does not establish successful keyboard, screen-reader, mobile or large-project browser operation; none was executed in this review.

Pinned dependency data, lines 1248–1266 and 1558–1568, identifies Rails 8.1.4 and with_advisory_lock 7.6.0. Ruby selection specifies 4.0.9; the Node/npm manifest, lines 1–25, declares project-specific engines. Production container variants, lines 1–62 and 102–172, provide slim and all-in-one images, persisted assets and, for all-in-one, PostgreSQL data. Slim startup and external worker services remain deployment responsibilities; these files were inspected, not built.

The root Compose file, lines 1–100, is a development stack and explicitly redirects production Compose users elsewhere. It must not be presented as a verified production installation. PostgreSQL, migrations, persistent assets/attachments, configuration/secrets, cache, GoodJob workers, mail and optional collaboration services form the operating boundary. Back up and restore that boundary together, and verify matching application/worker versions. The database edit mutex supports several application hosts sharing PostgreSQL; it does not provide disconnected/offline ownership or prove high availability.

Test-source evidence and adoption work

Lock-version contract tests, lines 77–100, reject nil/changed versions and accept an unchanged version. API request examples, lines 1128–1156, construct missing and stale version requests; their shared response, lines 191–196, specifies HTTP 409 UpdateConflict. Blocker tests, lines 1697–1711, assert removal of closed statuses using a mocked blocker predicate. Parent authorization tests, lines 31–88, check rights in the parent's project as well as the child's.

Batch concurrency test source, lines 93–158, uses threads, database connections, barriers and a final order assertion for two disjoint batches entering one empty target. This is a meaningful intended concurrency scenario, rather than two merely sequential calls. It was not run. These selected tests do not certify all alternate type/relation mutations, graph races, plugin effects, job delivery or external agent execution.

Retain the common contracts, transactional service context, optimistic conflict handling, hierarchy checks, journals and native planning views. Add atomic claim admission on eligible/unowned work, attempt-scoped mutation rights, capacity, heartbeats and recovery. Keep execution completion, parent result acceptance, iteration end and human delivery acceptance separate. Close relation/type-change policy gaps where acyclicity or blocker gating is required. Make system/empty-contract overrides visible and bind review to immutable result revisions. Verify edition availability, deployment/restore, concurrent agents, failed delivery, external cancellation and representative human workflows before making the combined system the sole agent work authority.
