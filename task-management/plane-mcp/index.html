Plane MCP adapter task management assessment

Repository: https://github.com/makeplane/plane-mcp-server

Commit: 5c3467adb36fe15a2ef8f9df6fb9f5dc24b6d881. Baseline: Shared task management for an agent organization. Review: November 9, 2026. Full local checkout; static implementation and selected test-source review. Candidate code, dependencies, tests and services were not installed or run.

Fit decision and assessment boundary

This repository is an agent interface to Plane, not an independent task-management authority. It makes substantial project-management operations available through MCP: projects, work items, relations, cycles, milestones, comments, pages, attachments and other resources. It is useful when Plane is already the shared record and agents need structured access to it.

It does not add exclusive task claims, execution attempts, worker leases, delegation supervision, task acceptance or recovery scheduling. Its normal assignment helper is a retrieve-then-update operation, without a conditional version or transaction spanning both API calls. Installing this adapter therefore does not establish safe concurrent allocation among independent workers.

The adapter is MIT licensed. That license does not establish the availability or licensing of every resource in a particular Plane deployment. The code explicitly handles plan restrictions and workspace/project governance differences. The separate Plane codebase assessment remains necessary for persistence, permissions, lifecycle enforcement and human usability supplied by the product.

Verdicts below distinguish an exposed API operation from behavior implemented here. An adapter verdict does not assert that the upstream product lacks a feature. No live Plane service, MCP client or browser was used to validate these findings.

Architecture and source scope

The package declares Python >=3.10 and pins FastMCP 3.2.0, MCP 1.28.1 and plane-sdk 0.3.1. Server factories configure authentication, common middleware and tool registration. The middleware logs calls, repairs string-encoded arguments and checks arguments against the selected action. Resource functions build SDK request models and call a credential-bound Plane client. See package metadata, server factories and middleware.

There are 30 declared resource tools and 207 action declarations at this commit. The static catalogue inventory records their names, source hashes and declaration ranges. It was produced by parsing Python syntax, without importing candidate modules. It establishes the declared surface, not successful runtime registration or correct implementation of every action.

The explicit registry fixes catalogue order and builds action and legacy-name maps. Resource modules describe their actions through a shared declaration type; descriptions and conservative annotations are generated from it. Registration also strips output schemas and installs optional retired-name transforms. This reduces advertised tool count while retaining a broad API surface. See registry, registration and specification helpers.

Task data is not stored by this process. Its persistence is an OAuth token store: configured Redis variants or an in-memory fallback. Projects, work items, comments, relations and history remain in Plane. The MCP process does not execute a worker, own the backlog database or keep a durable task-operation journal. See client construction, lines 47–99, and token storage, lines 146–263.

The review traces the core work-item lifecycle, assignments, dependencies, comments/mentions, activity, project operations, planning helpers, selected attachment paths, authentication/context and server configuration. Other resources received declaration inventory and targeted interface review. The SDK and upstream Plane implementation were not audited as part of this adapter report.

Lifecycle and alternate mutation paths

A connection resolves a Plane client and workspace slug from its authenticated token, or from environment variables in stdio mode. Projects and work items can then be listed, retrieved and created through SDK calls. There is no independent local task copy to reconcile with the service. The successful result and durable record are supplied by Plane, rather than by a local database transaction. See client binding, lines 20–99, and work-item dispatch, lines 284–383.

A worker can search by PQL, resolve members/types/states and update an item's assignees or parent. That operation is not a claim. manage_assignee reads the current IDs, removes requested IDs, adds requested IDs and writes a whole list. Two callers reading the same old list can lose one another's additions. No lock, expected revision or conditional API parameter is passed by this helper. The same issue applies to its label-set merge. The adapter does not establish whether upstream facilities could provide a stronger alternative. See set merge, lines 385–410.

Progress can be posted as comments or linked pages/files. The mention helper checks project membership before writing a mention, then the comment function sends generated HTML through the SDK. This improves addressing, but a rendered chip is not proof of notification delivery or recipient action. Comments and links can be edited or deleted; none is an immutable execution checkpoint. See comment dispatch, lines 83–158, and mention validation, lines 158–180.

Completion is an ordinary state update. The adapter does not fetch criteria, require verification, check child results or bind approval to a commit before making that request. Deleting or archiving records is also an ordinary API operation, without an adapter-level worker stop/acknowledgement protocol. The baseline needs this lifecycle implemented by another authority or a coordination service above the adapter. See state/delete/archive, lines 367–383.

Concurrency, retry and recovery conditions

One tool call can contain several writes

Cycle membership management can add several items and then remove others one by one. A later failure does not undo successful earlier requests. Archive retrieves the cycle, may first set its end date, then calls archive. An archive failure can leave the changed end date behind. There is no adapter transaction, compensation log or restartable operation ID for either sequence. See cycle helpers, lines 235–293.

The same caution applies to composing a task workflow across several tools. Creating a child, assigning it, posting a comment and changing the parent state are separate service requests. An interrupted agent must inspect upstream state before continuing. The adapter has no durable record of which steps its prior conversation intended or completed.

Payload omission is deliberate but not universal patch expressiveness

Work-item writes omit sentinel empty strings and zero values. Explicit empty assignee/label lists are retained, and explicit null dates clear dates. Other fields such as description and parent are normalized through opt, so the same interface does not expose every conceivable clearing operation. A request that omitted a field is different from one that successfully cleared it. See payload construction, lines 254–283, and sentinel helper, lines 64–66.

external_id and external_source are sent to the API but do not become idempotency keys in adapter code. The annotations conservatively mark consolidated tools non-idempotent. When a response is lost, the caller cannot infer that a create/comment/upload failed merely because the MCP call did not return. It needs a read-back/reconciliation strategy and upstream guarantees appropriate to that operation. See work-item writes, lines 254–283 and 351–360, and annotations, lines 49–70.

Credential durability is separate from work durability

HTTP token storage supports Redis, including URL, password and optional AWS credential-provider paths. Configured Redis is checked at startup. If no backing store is configured, the fallback is process memory and its tokens are lost on restart. Task records remain in Plane, but clients may need to authenticate again. There is no task lease or abandoned-work reaper associated with this token cache. See storage construction, lines 146–263.

HTTP mode creates OAuth and API-key applications and also mounts legacy SSE. It creates the OAuth factory even if an operator only intends to use the API-key endpoint. The OAuth provider validates its required client settings at construction. Remote deployment therefore needs the actual factory/configuration graph, not just a PAT endpoint copied into a client. See HTTP construction, lines 145–173, and OAuth required settings, lines 326–332.

The entry-point enum includes sse, but main has startup branches only for stdio and HTTP. Selecting standalone SSE reaches the end without starting a server. Legacy SSE remains available through the HTTP assembly. This is a static control-flow finding; no candidate command was executed. See entry point, lines 116–204.

Identity, access and artifact boundaries

Header/PAT validation calls Plane's current-user endpoint and requires a workspace header. That verifies the key, not membership of the supplied workspace inside the adapter; resource authorization remains with Plane's API. The returned access token carries read/write scopes set by the provider. The adapter does not derive an independent least-privilege agent policy from those scope labels. See PAT verifier, lines 19–73.

OAuth verification reads the user and application installations, selects the first installation and records its workspace in token claims. This creates a connection binding rather than a per-tool arbitrary workspace argument. The client context uses those claims even when the slug is empty, avoiding silent fallback to a different environment workspace. Several projects can be addressed within that bound workspace. A multi-workspace operator needs to verify which installation was selected. See OAuth binding, lines 167–209, and context, lines 20–99.

All server factories register the common catalogue. Read/destructive/idempotency annotations are hints derived across every action of a resource, not permission enforcement for individual operations. The shared governance helpers explain upstream plan/scope refusals; they are not an agent authorization system. See configuration, lines 58–104; annotations, lines 49–70; and governance, lines 48–132.

Attachment handling adds actual outbound I/O beyond basic API wrapping. URL upload uses bounded fetching, redirect checks and direct-connection DNS pinning. In proxy mode, hostname network safety is delegated to the proxy; private literal IPs are still rejected locally. This is an explicit deployment boundary, not proof that every supplied URL is safe in every proxy configuration. See upload, lines 128–162, and fetch path, lines 211–274 and 308–320.

The attachment read helper fetches a returned download URL with requests.get, then checks the buffered payload against image/text limits. Those limits bound what is returned to the model, but do not bound the network read before buffering. It also uses a different path from the DNS-pinned URL-upload helper. This review did not certify all attachment, OAuth, proxy or SDK internals. See read helper, lines 91–125.

Agent and human usability

The adapter makes several deliberate agent-facing improvements. Its generated action descriptions name required/optional fields. Middleware can repair JSON values encoded as strings and reject valued arguments that the selected action does not accept. PQL errors include the failed query and reference material. Paged work-item reads preserve counts and cursor fields, avoiding a first page that looks like a complete result. See middleware, lines 19–109, and paging, lines 44–135.

These improvements do not eliminate interface cost. An agent must discover UUIDs for states, types and members, choose an action from a large shared schema, and perform multi-step work through separate calls. Several validation refusals are strings or error dictionaries rather than an explicitly marked MCP execution error in adapter code. A consuming agent should inspect returned content as well as protocol failure status. See validation return, lines 36–45; required-field helper, lines 19–35; and PQL failure, lines 107–124.

One documentation inconsistency is visible at the pinned revision. The README uses state__group in list-filter examples, while the work-item footer explicitly says that it is a grouping key and filtering on it is rejected. Agents copying the example can spend a round trip repairing a query the tool description already warns against. See README examples, lines 106–130, and work-item guidance, lines 143–157.

For the human owner, this repository supplies no board, task-detail browser, review interface or portfolio view. Those experiences belong to Plane or the MCP client. The ability to query a count is useful for reporting but does not establish that the complete project is understandable or manageable in a particular UI. No candidate user interface was rendered or tested.

Completeness, design quality and test-source evidence

As an API adapter, the design is cohesive. The registry, declarations, common factories, typed SDK models and response helpers reduce repeated plumbing. Conservative annotations avoid advertising destructive resources as read-only. Credential-bound workspace selection is separated from resource arguments. The scope is broad, but breadth must not be mistaken for an implemented autonomous-work lifecycle.

The source includes useful contract tests:

  • Catalogue tests pin resource order, require matching declarations/signatures and check action/parameter consistency. Conformance source, lines 34–143.
  • Dispatch tests parameterize declared actions against a spy that binds the genuine SDK signature and validates argument types. They also require missing-argument calls to return before hitting the SDK. The spy's default response is deliberately permissive and does not model real backend constraints. Dispatch assertions, lines 119–153; spy, lines 24–55 and 106–207.
  • Pagination tests check cursor preservation and refuse a response that lacks the promised pagination fields. Paging source, lines 50–78.
  • Argument tests check wrong-action parameters, accepted count scope, absent actions and literal-action behavior. Validation source, lines 50–125.
  • Client tests check that OAuth/header/stdio report the same workspace they use and that a missing token slug does not borrow the environment's slug. Context source, lines 45–92.

These are inspected source assertions, not test results from this assessment. The live integration test explicitly requires credentials and writes/deletes real project data; it was not run. Its existence does not establish success against the user's Plane edition or configured server. No backend concurrency, stale-worker, task-acceptance or recovery guarantees were demonstrated by this review. See integration scope, lines 1–95.

Adoption work and useful components

Use this adapter when Plane is the chosen management system and agents need a coherent MCP bridge. Keep the explicit catalogue, typed payloads, pagination envelopes, parameter correction and mention handling. Verify the target Plane version/edition and required API resources before relying on the full advertised surface.

For autonomous task coordination, put authoritative claim/attempt state, ownership transfer, stale-worker fencing, recovery and acceptance in Plane extensions or a separate service. Do not implement exclusive allocation by reading assignees and writing a replacement list. Add explicit retry/reconciliation contracts for multi-step operations and distinguish the Plane user's identity from each worker and execution attempt. Provide a typed handoff/result operation if completion must include evidence and reviewer approval.

The review ledger records the inspected ranges, source hashes and all 24 verdicts. The catalogue inventory covers declarations across all resources; the detailed lifecycle findings cover the named paths, not an every-line or every-endpoint audit.
