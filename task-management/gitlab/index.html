GitLab: shared planning and agent sessions with separate ownership rules

Source: https://gitlab.com/gitlab-org/gitlab

Reviewed commit: a8f1a2df276bdcf7f0e612492ab5412f16de62fe. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

GitLab provides a deep shared planning and development authority. Projects, namespaces, issues, typed work items, hierarchy, boards, milestones, iterations, notes, to-dos, resource events and merge requests connect planned work to implementation. REST, GraphQL and native MCP tools let agents operate those records. The reviewed revision also contains substantial agent infrastructure: durable workflow sessions, parent and child flows, checkpoints, approval/input states, workplan generation, external-agent identity and session governance.

These layers do not form one universal exclusive task-execution protocol. An issue assignee is a planning responsibility. A workflow turn claim protects a particular session turn. A parent work item and a parent workflow are different relationships. Closing an issue, finishing a session and merging code have different checks. A coordinator must define which of these events establishes an accepted task outcome and must protect that rule across normal edits, board moves, bulk changes and automation.

Use GitLab as the planning and development authority when its deployment and edition boundaries fit. Use a separate, explicit task-attempt contract for independent workers, or validate a narrowly selected native flow that supplies it. Do not describe every Enterprise agent implementation as an unrestricted open-source component. The root license, lines 1–28, distinguishes MIT-covered content from exceptions. The Enterprise license, lines 1–32, states subscription and production-use conditions for covered code. This report identifies source boundaries; it does not determine a particular customer's entitlement.

Scope and evidence level

The preserved checkout contains 116,819 tracked files. This targeted static review follows issue/work-item creation, metadata filtering, assignment, update, hierarchy, dependency relations, board movement, bulk updating, close/reopen and deletion. It inspects native MCP write construction, GraphQL/REST entry points, representative authentication, resource history, notes and to-dos. The agent review follows selected workflow creation/chain admission, turn claiming, status changes, checkpoint persistence, stop, restart, stale cleanup, input/tool approval, workplan and external-identity records. Representative browser detail code, dependency/configuration files and selected test assertions were read.

No candidate application, dependency installation, build, migration or test was executed. The ledger identifies actual inspected ranges. This is not an every-line audit of GitLab, all EE extensions, custom roles, import/export paths, quick actions, merge strategies, CI scheduling, provider execution, Workhorse, external AI Gateway/Workflow Service, chat transports, Geo/Cells, backup/restore, accessibility, performance or production concurrency. The checked-out Rails application references separate executors and services; their complete behavior is not established by this checkout.

Architecture and records

Projects, lines 226–244 and 350–358, connect namespace, boards, merge requests and work records. Issues, lines 74–145, retain namespace/project membership, namespace-scoped internal identifiers, assignment associations, discussions/context and implementation links. WorkItem, lines 1–105, reuses the issues table and adds typed widgets and parent/child associations. This unifies existing issue infrastructure with newer project and group planning surfaces.

Work-item creation, lines 1–69, extends the issue creator with widget handling and structured service results. The issue creator, lines 1–75, checks creation authority, builds the record and passes it through common persistence. The shared create path, lines 217–268, filters input, assigns attributes and runs save callbacks inside a transaction, then performs additional notes, hooks and triggers. This is a coherent reuse strategy, with a large inherited policy surface.

Workflow sessions, lines 138–205, retain user/service account, project/namespace, work item, merge request, catalog version, checkpoints, artifacts, workload links and immutable parent identity. External-agent identities, lines 1–90, identify user/project/agent type and machine fingerprint. Governance sessions, lines 1–108, distinguish native workflow identity from external session identity and retain session state. These are real agent-specific records, but they do not turn the ordinary issue assignment association into an execution lease.

Assignment, concurrency and alternate mutations

Metadata filtering, lines 65–145, removes assignment and other fields when the actor lacks metadata authority and filters assignees by visibility. The widget assignee callback, lines 1–51, performs corresponding checks and composite-identity linking. IssueAssignee, lines 1–16, prevents a duplicate issue/user pair. This is not a predicate that the task is unowned, ready and reserved for one new attempt.

The common updater, lines 314–407, accepts a lock version when supplied, prepares changes and saves with widget callbacks in a transaction. However, optimistic locking, lines 169–190, is enabled for title or description changes. An assignee-only update does not gain the same ownership-conflict semantics. Assignment preparation, lines 526–540, calculates assignee differences and touches the record; it does not acquire a worker lease. Independent agents should not use read-unassigned then set-assignee as an exclusive claim.

The REST update, lines 399–448, authorizes the issue, scopes parameters and calls the common issue service. GraphQL updating, lines 1–125, applies granular project/group boundaries, checks base-attribute authority and delegates widget permissions separately. Bulk updating, lines 1–81, scopes candidate records and checks each item's update permission, then returns a count of successful item updates. This is per-item processing, not one atomic all-or-nothing batch or one shared attempt reservation.

Board movement, lines 1–124, derives label/state/order changes and checks administration authority. The issue mover, lines 1–65, calls the common updater; its multi-item loop can report partial success. The EE extension, lines 1–111, adds readable-assignee, milestone, iteration and status changes. List WIP configuration, lines 28–86, validates maximum/count/weight values and edition availability. The inspected movement paths do not reserve execution capacity against those fields. A displayed board limit should not be assumed to reject every excess move or API assignment.

These common services and typed callbacks give an integration useful enforcement points. They also expose a design obligation: a new claim or acceptance rule must cover both old issue routes and newer work-item/widget paths. EE update extensions, lines 1–143, add iteration, status/type, requirement-test-report and notification behavior; an audit limited to the CE method would miss that policy surface.

Hierarchy, dependency and completion

Parent-link validation, lines 1–130, checks organization, parent uniqueness, allowed type/depth, confidentiality, self-parent and ancestor cycles. The parent service, lines 36–55, requires parent-link authority on the relevant records. Hierarchy callbacks, lines 1–181, validate mutually exclusive operations, delegate linking and gate request/rate limits. Model graph validation is useful; this review does not certify concurrent multi-edge graph changes as serializable.

Related-link validation, lines 35–85, checks self/opposite relationships and link counts. EE blocking relations, lines 14–65, add directed blocking semantics and open-blocker queries. This is a different graph from parent hierarchy. The inspected concern does not supply a graph-wide dependency cycle traversal or ready-work acquisition operation.

The issue close service, lines 7–91, checks update authority unless explicitly bypassed, closes the issue and performs history/notification/hooks. The issue state machine, lines 355–385, transitions opened to closed and records closure attribution. The EE close extension, lines 17–66, synchronizes a legacy epic and status. These paths do not test that all blockers, children or result reviews have passed. Dependency and hierarchy information must not be mistaken for an enforced completion join.

Custom-status callbacks, lines 59–138, require a permitted status in the type's lifecycle and use the close/reopen services when its state changes. State-event dispatch, lines 476–497, can call close/reopen while preparing additional attributes, before the later general attribute-save transaction. Do not assume every compound status/metadata edit has one universal atomic acceptance boundary.

Code integration has stronger, separate controls. Merge execution, lines 18–49, uses a merge lease and locked state. Head checks, lines 78–82 and 195–199, reject a requested source SHA that no longer matches. The EE merge extension, lines 14–39, rechecks configured approval inside commit processing. These controls protect a code integration path. They do not automatically bind an ordinary issue's closed state to the approved artifact.

Agent workflows, delegation and capacity

Session creation, lines 35–109, checks usage/access, persists workflow identity and links source artifacts. Access resolution, lines 510–576, distinguishes authorized client execution, background workflow access, enabled foundational agents and licensing. Execution capability is therefore not uniform across every installation or caller.

Flow-chain creation, lines 165–219, records a parent workflow, checks authorized chain context, human root and depth, and conditionally checks top-level namespace. It locks the chain root while applying breadth and total-chain limits before saving. This is substantive delegation admission. Assignment-trigger handling, lines 63–104, checks trigger authority and authorized parent context before launching configured flows. These mechanisms support bounded flow families, not automatic accepted-child completion for every issue.

Usage admission and session-count observation, lines 245–279, call the quota service but only log the inspected maximum-concurrent-session threshold. Transition observation, lines 2339–2367, explicitly treats the corresponding breach as observability. Those checks do not establish a hard global session cap. CI runner scheduling and other quota enforcement are separate mechanisms outside the complete audit scope.

Workplan generation, lines 27–89, places both the existing-workflow check and creation under a two-minute Redis lease. The general lease, lines 117–130, uses atomic Redis SET with NX and expiry. This protects the named admission window across service processes. It does not give a worker an issue-level reservation for the duration of implementation.

MCP session-turn claiming, lines 273–295, acquires a turn claim and rechecks primary status before execution. TurnClaim, lines 1–32, uses a one-hour lease and a fixed workflow-derived UUID so another process can release it. Lease cancellation, lines 20–33 and 63–69, compares that UUID. It is not a distinct fencing token for each task attempt; expiry/release must not be presented as stale-worker write rejection.

Progress, interruption and recovery

The workflow state machine, lines 2500–2648, distinguishes running, pause, input, plan/tool approval, resume, retry, finish, drop and stop. A stopped CI session cannot use the normal retry transition to revive itself. Its inspected finish transition accepts a running session without a Rails-side accepted-child join. External flow graphs may impose narrower rules; this review does not certify them.

Status updates, lines 34–96, check workflow authority, validate events and retain status before publishing best-effort updates. Stop queues associated-pipeline cancellation. The worker, lines 1–46, checks cancellable pipelines and invokes their cancellation service. A recorded stop is not synchronous proof that every runner/tool has stopped, and it cannot undo an external effect.

Restart, lines 1–117, starts a new session and preserves the old one. A short lease suppresses overlapping restart requests; links retain provenance. The new session ID prevents an old workload from simply writing into a reused workflow identity. It does not revoke ordinary project credentials or fence every issue mutation by an old worker. Resume configuration, lines 15–66, rebuilds token/flow and environment data rather than blindly retaining old credentials, and carries a fresh goal or approval decision where applicable.

Checkpoint persistence, lines 13–109, writes state in a transaction and updates workflow activity for stale discovery. Blobs use a deduplication index. Headers, lines 226–252, intentionally append on resend, with readers selecting the latest. This is scoped replay behavior, not an exactly-once transition ledger. Internal checkpoint access, lines 24–42, 308–312 and 350–385, combines authenticated owner/ability lookup, blocked-flow checks and Workhorse access. The full executor/gateway credential boundary was not audited.

Stale cleanup, lines 10–50, finds created/running sessions with old activity timestamps and drops them. Checkpoint touch handling, lines 98–109, avoids treating an already committed checkpoint as failed merely because touching activity conflicts. Cleanup marks session failure; it does not release or transfer an ordinary issue assignee. Waiting-for-input sessions are a separate state, rather than automatically failed because a person has not answered.

Deletion, lines 1–31, checks work-item deletion authority. Issue deletion follow-up, lines 7–26, publishes retained parent context and update signals after destruction. Reopening uses its own service, lines 5–44. These are planning-record operations; an independent worker needs an explicit cancellation/recovery integration.

Communication, review and human inspection

Note creation, lines 8–50 and 123–140, validates and persists discussion, runs quick actions and creates to-dos. A comment can mutate work through commands; it is another path to include in an execution policy. To-do reads, lines 62–64 and 102–125, scope to the current user, paginate and filter allowed targets. Durable later reads can recover information beyond a missed live notification.

Workflow events, lines 10–27, retain queued/delivered state and optional correlation identity. The internal event API, lines 611–657, lists queued records and updates delivery state. A delivered marker is not semantic acceptance of work. Status notifications/audit, lines 112–181, distinguish input to-dos, email and best-effort audit. The whole business transition, notification publication and external delivery are not one proven transaction.

Assignment changes, lines 51–88, create notes, resource events, notifications and flow triggers. State events, lines 1–55, and assignment events, lines 1–19, retain inspectable attribution. The shared updater performs several history/hook effects after a successful save. An integration should reconcile authoritative task state rather than assuming every external event was delivered once.

Workplan questions, lines 15–54, can be resolved by an authorized actor without resuming a flow. The plan callback, lines 38–67, edits retained content with update permission. Generation status, lines 10–27, explicitly describes the run, because the separate plan write may fail. This prevents a session-completed label from being treated as proof that the task's plan exists.

Session tool approvals, lines 15–62, check authority, namespace configuration and administrator constraints, then lock before updating approval data. Resume decisions, lines 253–270, distinguish an approval from a message. These are useful control points. They do not bind every issue completion to an immutable reviewed output revision.

Native MCP mutation construction, lines 15–28 and 164–199, chooses create/update and explicitly labels the combined operation non-idempotent. The update tool, lines 16–108, constructs typed GraphQL widgets and masks access failures. MCP access, lines 51–105, checks authentication, scopes and instance settings; the EE override, lines 16–35, uses namespace enablement on the relevant SaaS path. There is no universal assumption that every deployment exposes MCP.

The browser detail query, lines 255–326, selects stable ID/IID context, subscribes to updates and warns when retained data may be stale. Mutation error handling, lines 685–719, reports returned errors. Board markup, lines 479–504, displays count and limit context. These are implementation provisions for inspection, not executed usability/accessibility evidence.

Planning, operating cost and adoption work

Milestones, lines 21–65, connect project/group releases, dates and implementation. Iterations, lines 35–98, connect group/cadence and issues, validate dates and enqueue optional rollover after closure. Iteration assignment, lines 133–182, validates arguments, visibility and edition availability. Timebox closure is distinct from completing every remaining task.

The database configuration, lines 1–35, uses PostgreSQL. Background dependencies, lines 305–316, include Sidekiq and its fetcher. Repository configuration, lines 1445–1477, connects Gitaly storage. Redis also holds the inspected leases. Application processes, workers, database, repositories, uploads/artifacts, secrets and any selected agent gateway/executor/runtime must be operated and restored coherently. The inspected files establish dependencies, not a tested production installation or recovery procedure.

Ruby selection specifies 3.4.10; Node selection specifies 22.23.1. The frontend manifest, lines 346–354, declares Yarn tooling; the tool-version file, lines 1–11, has additional development pins. Resolve such project-specific selections rather than replacing them with general latest-toolchain defaults. The footprint can be reasonable when GitLab is already the development authority, but a deployment solely for agent tickets has a much broader maintenance boundary than a small task store.

Parent-race test assertions, lines 642–660, simulate a competing parent insert and require a structured conflict result. Workplan admission tests, lines 62–86, reject an existing run or held lease. Restart assertions, lines 129–154, check new-session provenance and preservation of the original status. Cleanup assertions, lines 14–83 and 106–124, distinguish waiting states and retain failure after broadcast errors. These tests were read, not run; the mocked parent conflict is not a production threaded graph-race experiment.

Retain the project/work-item authority, hierarchy checks, common services, versioned interfaces, implementation links, durable events and distinct session identities. Add atomic eligible/unowned task acquisition, attempt-scoped writes, project capacity admission and explicit child/result acceptance where independent agents require them. Govern quick actions, bulk operations, board moves and automation with the same contract. Validate edition access, concurrent claims, stale credentials, partial event/checkpoint failures, stop settlement, artifact binding, restore and representative human workflows before relying on the combined system as the sole task-execution authority.
