agent-kanban-rs task management assessment

Repository: https://github.com/fxeqxmulfx/agent-kanban-rs

Commit: 3ab1218eac51edca8556e6dfbeea322477e7a444. Baseline: Shared task management for an agent organization. Review: November 8, 2026. Full local checkout, static implementation review. Candidate code and tests were not executed.

Fit decision

This is a coherent local coordination tool for cooperating developer and reviewer agents. It has substantially more lifecycle enforcement than a board whose cards simply change columns. Claims, dependency checks, guarded edits, review submission and acceptance decisions have real database invariants.

Evaluate it as a small single-host work queue and as a reference for transactional lifecycle design. It does not supply a project-management service for the complete baseline. There is no project registry, durable delegation hierarchy, authenticated remote access, execution-attempt identity or general progress/checkpoint record. Two sessions using the same agent name remain indistinguishable when one reclaims a task.

The source is MIT licensed. Its compact CLI and explicit SQLite rules are useful components, but turning it into a shared multi-host project system would require a service and a richer identity/context model.

Architecture and domain model

The application is a Rust command-line program. Command dispatch, lines 400–503, routes creation, list/detail, claim, review, editing, export/import, mail and waiting into separate modules. Each invocation discovers one local .kanban/board.db or uses an explicit --db path. There is no daemon or HTTP/MCP server in that command surface.

The schema, lines 22–128, has agents, tasks, dependencies, acceptance results, review history and messages. Roles are the fixed enum Developer and Reviewer. Task states are Backlog, Todo, In Progress, Review and Done. Each task requires at least one acceptance specification, stores a revision number and can have an executor with a claim time and lease expiry. SQL checks require the ownership fields to be present or absent together.

Task IDs use AUTOINCREMENT to avoid reusing a deleted task's identifier. Review and acceptance records copy the executor name, so attribution remains meaningful after an agent is removed. There is no task description, project entity, parent task, session identity or separate attempt row. Acceptance specifications and messages carry most contextual information.

The database opener, lines 146–184, sets a busy timeout, WAL and foreign keys. Lifecycle writes, lines 31–37, acquire an Immediate transaction before checking mutable state. This protects the check/write span across processes, rather than relying on one process's event loop.

Lifecycle and mutation authority

Creation validates the title, priority and non-empty acceptance list. It inserts the task and dependencies in one Immediate transaction. Unknown or cyclic prerequisites reject the transaction.

A developer claims Todo or reclaimable In Progress work. The claim statement checks unfinished dependencies and updates ownership and state together. Claim-next uses one update with a selection subquery, rather than a separate availability read followed by an unguarded write. Repeated claims by the current identity renew its lease.

Submission checks the live holder and requires one result per criterion, without duplicates or empty evidence. It increments the revision, stores the results, clears ownership and moves to Review atomically. A reviewer claims Review work and receives the developer's results. Approval checks that every result in that revision exists and passed. Requesting changes requires notes and returns the task to unclaimed In Progress work.

Ordinary moves only operate between Backlog and Todo. They cannot bypass review by moving directly to Done. Edits and removal reject live claims, Review and Done. Dependency edits share a transaction with the guarded task update. This is a consistent normal lifecycle, with important administrative exceptions below.

Concurrency and recovery boundaries

Shared predicates and upfront write locking

The ready predicate, lines 8–15, is reused by direct and next-task developer claims. Cycle checks run while their caller holds the write lock. This avoids the split selection/claim and check/write gaps found in several simpler trackers. The schema also prevents partially populated ownership fields and Done tasks retaining an executor.

The reviewed code does not establish a performance result. SQLite still serializes writers, and a busy timeout can fail after contention rather than guaranteeing progress. The design is appropriate to a local cooperative queue, not distributed consensus.

Agent identity does not fence an old attempt

Submission and review checks, lines 418–440, compare current executor and live expiry. They do not compare an attempt token. An old invocation of agent Alice is rejected while Alice's lease is expired or another agent owns the task. If a new Alice invocation claims it, the old invocation using the same name can satisfy the renewed identity check.

The task revision protects submitted result history, not process identity or external code changes. This distinction matters when a project leader expects a restarted agent to invalidate all of its prior sessions.

Administration shares the worker's trust boundary

Any local caller can remove a registered agent; the removal transaction, lines 107–172, clears all of that agent's leases. Any caller with filesystem access can also invoke load --replace. Replacement import, lines 185–256, deletes and restores board state in one transaction. It is a deliberate maintenance facility, but there is no separate privileged principal or active-worker drain protocol.

Restoring data is not a promise that old workers are fenced. Operators would need to quiesce workers and define ownership recovery around a restore. The normal CLI's guarded mutations should not be generalized into an authenticated security boundary.

Message retrieval is not acknowledged delivery

Inbox, lines 74–107, marks all unread messages read in its transaction and returns their text. The database change commits before the process prints its result. A broken output pipe or lost caller response can therefore consume messages without the recipient seeing them. Full export retains the underlying messages, but normal inbox has no separate acknowledgement or replay selector. The unread hint is useful; it is not an exactly-once delivery guarantee.

Human and agent usability

The CLI deliberately keeps responses compact. Work orders include criteria and reviewer evidence; rework includes the latest requested changes. Filtered lists report omitted tasks instead of silently truncating them. Status shows columns, blockers and live task holders. These source-level interface decisions suit agents working on a small local board.

The data model is narrow for project leadership. There is no long description, durable project specification, shared decision record, dedicated progress note or parent outcome. Free-text mail and acceptance fields can carry references, but they do not make those relationships inspectable entities. Human inspection is terminal-based; a browser board would be an additional interface.

No process is launched or monitored by the tracker. The external agent must execute work, renew ownership, record truthfully what it verified and respond to mail. One criterion may be satisfied by any non-empty evidence text; the tracker cannot verify the truth of that report.

Completeness and operating design

The small module boundaries are clear: command parsing, persistence, lifecycle, dependency graph, mail and output projection. Database constraints reinforce application checks. Unlike a flexible status editor, alternate ordinary commands do not silently bypass the acceptance path.

Migration uses schema-version checks and a transaction, while task IDs remain non-reused across deletion and supported restore. Full dump reads a snapshot, checks that its result can be loaded, and preserves criteria, history, mail and the next-ID high-water mark. Import checks cross-record references and dependency cycles before its transaction commits. See dump/load, lines 169–256 and 1045–1148.

These are meaningful completeness features for a local tool. They do not supply backups scheduled off-host, high availability, a fleet identity model or an operator access policy. The overview uses several reads rather than one consistent read snapshot, so concurrent changes can also make its counts represent slightly different moments.

Test-source review

The claim race tests, lines 13–125, launch separate processes for repeated contention on developer and reviewer claims. They check one winner, useful refusal errors and agreement between the returned work order and stored state. They also explicitly test same-agent overlapping claims as renewals. These tests target actual process concurrency rather than only sequential calls.

Inspected implementation tests and test declarations cover dependency rules, guarded edits/removal, role restrictions, complete review results, mail retrieval, formatting, migration and export/import. The repository also has mutation, claim-next and initialization race test files. No tests or candidate binary were executed in this study. Their presence is evidence of intended checks, not a current pass result.

Installation, terminal behavior, restore under real failure, sustained contention and coordination through a remote invocation layer remain unobserved.

Adoption work

For the full baseline, add durable projects and leadership, decomposition and parent completion, richer context and progress records, and an authenticated service for workers on different hosts. Introduce per-attempt fencing rather than identifying an execution only by agent name. Separate worker and maintenance privileges, add acknowledged message consumption, and bind acceptance to the actual delivered artifact revision.

Retain the transactional lifecycle, shared readiness predicate, explicit review results, guarded edits and non-reused task identifiers as useful design patterns. The review ledger records the source evidence and its limits.
