Kanboard: a shared backlog with human workflow conventions

Source: https://github.com/kanboard/kanboard

Reviewed commit: 2ddb31bf72d355727d0639fc3423630f3bae1a9c. Assessment date: November 9, 2026. Baseline: Shared task management for an agent organization. Evidence ledger: review.json.

Fit decision

Kanboard can provide the durable shared backlog and human board for an agent team. It has project permissions, task assignment, subtasks, task relationships, comments, attachments, notifications, automation and a substantial JSON-RPC API. Agents can use ordinary user accounts and API calls to participate in the same work records that people inspect.

It does not implement the baseline's execution coordination protocol. Assignment is an unconditional task-field update. There is no native execution-attempt registry, renewable task lease, atomic claim-next operation or stale-attempt fencing in the reviewed core models and API surface. A separate coordinator must establish those guarantees. Adding a client that reads an unassigned task and then sets its owner does not make the two operations atomic.

Completion also has different semantics from the baseline. Closing a task marks all its subtasks done; it does not wait for their results to be submitted and accepted. Dependency labels and review columns communicate workflow, but the inspected mutation paths do not turn them into universal execution or acceptance gates.

The license is ordinary MIT. The pinned README declares maintenance mode, with small fixes and community contributions rather than active development of major features. That is the repository's statement at this revision, not a forecast of its future. Kanboard is a plausible conventional task authority to extend, with substantial additional work needed for reliable autonomous allocation.

Scope and evidence level

The checkout contains 2,792 tracked files. The review inspects selected source bodies for projects, tasks, assignment, status, position, relationships, subtasks, recurrence, metadata, files, API authentication and authorization, event jobs, activity and notification delivery, plugin loading and board interaction. It also reads selected test assertion bodies. No candidate application, dependency install, build, migration or test suite was executed.

This is not an every-line audit or runtime usability certification. SQLite schema excerpts support the model findings. Full migration histories, other database backends, every import/duplication path, all authentication providers, third-party plugins and the complete attachment/HTTP security implementation are outside certification. The ledger separates inspected ranges, manifests and test-source evidence. Method inventories and searches are used to locate operations, not as substitutes for reading their bodies.

Architecture and data model

composer.json requires PHP 8.1 or later and several PHP extensions. It combines Pimple services, Symfony components and vendored libraries for the database, validation, JSON-RPC and browser application. DatabaseProvider, lines 1–115, chooses the configured driver and can run schema migrations at initialization. SQLite, MySQL and PostgreSQL are among the switch branches. Backend-specific isolation and deployment behavior were not tested.

The current SQLite task table rebuild, lines 1–150, retains project, column, swimlane, owner, creator, description, priority, estimates, dates, recurrence and external-provider fields. owner_id is the task assignee. It is not an exclusive runtime reservation. The separate browser sessions table in this schema is not an agent execution-attempt table.

TaskModel, lines 1–125, defines only open and closed as task activity states. Board columns supply the visible workflow. Thus a task in a column named Review or Done can still be open; moving to that column and closing the task are separate operations unless configured automation connects them.

Project creation, lines 365–425, groups project insertion, initial board and swimlane creation in a database transaction. It records an owner, normalizes an identifier and can add the creator as project manager. Project membership, lines 1–97, combines direct and group-associated projects. These are real shared organizational records, but agent-specific leadership, capability and attempt identity remain conventions outside the model.

The API provider registers procedure objects for projects, boards, tasks, subtasks, comments, files, metadata, permissions and related entities. jsonrpc.php delegates requests to that server. The inspected core provides JSON-RPC rather than a native MCP task server or an agent process launcher.

Creation, assignment and concurrent updates

TaskProcedure, lines 1–222, authorizes the project or task, verifies assignability for nonzero task owners, validates fields and calls the corresponding model. Updates omit null fields so a caller can make a partial edit. These are useful API semantics. They do not accept a current-owner condition, expected revision or attempt token.

TaskCreationModel prepares default column, swimlane, color and timestamps, computes a position and persists the row. Tags and queued events follow the row write. It does not use a single enclosing transaction for all these effects. It returns an integer, including zero when the persistence result is false. A client must validate the returned ID rather than treating any completed HTTP response as task creation.

TaskModificationModel reads the current row, updates tags, prepares values and executes an update constrained only by ID. The prior read is used for event differences, not a compare-and-swap predicate. Two workers can both read an unassigned task, each set its own owner and both receive successful writes. The last stored owner wins; earlier external work is not stopped or fenced.

The browser assign-to-me controller, lines 1–106, applies CSRF and role-helper checks before calling the same model. Those checks do not close the race between observation and save. The automatic action assign current user if unassigned tests the owner in event data and then also calls the unconditional model update. Its name describes an intention, not an atomic storage precondition.

Task position changes, lines 1–175 and 177–315, do use database transactions to renumber tasks and change column/swimlane. This protects a useful multi-row operation. They do not reserve agent work or compare the original task revision. The database wrapper's transaction methods, lines 282–341, delegate to PDO begin/commit/rollback. No cross-backend concurrency guarantee is inferred from the mere presence of a transaction.

The task validator, lines 1–140 and 150–230, checks field types, dates and required inputs. It does not turn an acceptance description, board label or arbitrary metadata field into a completion gate.

Relationships and decomposition

The link schema, lines 943–968, includes labels such as blocks, is blocked by, child/parent and milestone targeting. A unique index prevents duplicate link triples. TaskLinkModel, lines 97–235 and 278–305, transactionally creates or updates the forward and opposite relationship records. This is useful consistency for the pair.

There is no graph traversal or cycle check in that create/update body. The link validator rejects a self-link and missing opposite task in the form validation path, but the API link procedure calls the model directly after permissions. Form validation therefore must not be credited to every writer. Database constraints still apply; exact invalid-link outcomes were not exercised.

Link search selects tasks with a matching link label. It does not determine whether all upstream work is accepted or reserve a ready task. Moving, assigning and closing tasks do not call a dependency scheduler in the inspected bodies. A coordinator needs its own readiness policy and must enforce it at the ownership boundary.

SubtaskModel, lines 1–108 and 213–337, gives each subtask a parent task, assignee, estimate, elapsed time and todo/in-progress/done status. Subtask update saves by ID, without attempt fencing. The API procedure checks that an updated subtask belongs to the supplied parent, which prevents a simple parent-ID mismatch. It still permits direct status changes rather than requiring a delegated result envelope.

Subtask conversion creates a full task, adds a child relationship if the label exists, copies tags and removes the old subtask. These steps are not one transaction. Its strict comparison against false also differs from TaskCreationModel's integer-zero failure return, so a failed creation can enter later conversion steps with an invalid ID. Subsequent database and helper failures determine the final outcome; no runtime data-loss result is claimed.

Capacity, automation and completion

Task limits are visible in the board task template and container template. They add a limit-warning class when counts exceed configured values. The reviewed creation and position bodies do not reject a write because the limit is reached. This is advisory WIP visibility rather than a shared capacity reservation.

SubtaskStatusModel can detect another in-progress subtask for a user when restriction is enabled. The subtask helper, lines 1–84, routes the UI to a restriction dialog. That dialog's save performs two separate status updates. Direct API status updates do not pass through that dialog, and toggle itself does not atomically test capacity. A one-at-a-time UI convention is not a general agent admission invariant.

TaskStatusModel closes all subtasks first, then changes the task's activity flag and completion timestamp. There is no prerequisite for submitted evidence, dependency completion or reviewer identity. The subtask update and task update are separate operations, and the close path does not condition the latter on the former succeeding. The confirmation template explicitly tells the person that subtasks will also close.

The status controller checks a confirmation and CSRF token and invokes this model. TaskCloseColumn invokes the same operation automatically after a configured column event. A Review or Done column can therefore drive closure without implementing qualified acceptance.

Recurring-task creation, lines 81–132, reads pending recurrence state, saves a new task, copies ancillary records and only afterward marks the parent processed. The parent check/update is not an atomic reservation in this body. Replayed or concurrent trigger processing can create a duplication risk. Recurrence is a planning convenience, not a retry-safe execution-attempt protocol.

Progress, context and artifact evidence

Task descriptions and comments provide durable context. CommentModel, lines 148–222, persists text, timestamps and visibility, emits events and allows edits/deletion. CommentProcedure restricts per-user author impersonation and comment changes. These are useful communication records, but no required progress/result schema distinguishes implementation submitted, rejected and accepted.

Metadata procedures expose task key/value data. MetadataModel, lines 1–127, records change time and user and groups a save in a transaction. It checks existence then writes, without an expected old value. Storing attempt_id or lease_until as metadata would not make other task mutation paths honor them.

Task file procedures check that the task belongs to the supplied project and provide upload/download. The file model, lines 164–193, 278–288 and 350–390, writes an object before creating its SQL metadata row. A database failure can leave an orphan object. Generated keys hash filename plus wall-clock seconds, not content. Equal filenames uploaded for the same task within one second can target the same key in this path. The storage writer, lines 16–73, uses a normal file write.

This is attachment storage rather than an immutable reviewed artifact registry. The core does not bind a content digest, source revision, result, reviewer decision and current task attempt into one accepted record. Complete file-security and concurrent-upload behavior were not runtime tested.

Communication, audit and failure recovery

TaskEventJob builds current task details and dispatches event names. TaskEventBuilder, lines 1–154, rereads the task when building the event. A delayed job can therefore observe task data newer than the originating write. Some paths carry explicit changes or an original task snapshot, but this is not a transactionally captured event stream for every mutation.

QueueManager executes synchronously when no queue driver is configured. With a driver, it publishes a serialized job separately from the task write. JobHandler preserves the initiating user ID, prepares a worker session and catches execution exceptions for logging. The queue loop marks the job completed after this handler returns. A caught job failure is therefore not itself proof of a retry or dead-letter record. Driver-specific recovery is outside this review.

The notification subscriber feeds NotificationJob. Web notifications persist to the unread-notification table. Reads are user-scoped, and marking read removes the row. This supplies durable pending human notifications. It is not a complete addressed agent-message protocol with a delivery cursor, acknowledgement history and replay from the task transaction.

WebhookNotification makes one HTTP POST, with a token in the URL and private-network checks unless configured otherwise. It does not inspect an acknowledgement or maintain a delivery ledger in this body. The request uses the HTTP client, lines 65–82 and 150–182, with error raising disabled by the caller. A receiver should not assume every task mutation produces exactly one retrievable webhook.

ActivityStreamNotification records activity only when the session has a logged-in user. Application-wide jsonrpc credentials do not initialize such a user. Those writes can therefore lack this normal activity record. ProjectActivityModel stores event JSON and supports cleanup; the archive command removes entries older than one year. This is useful operational history, not an immutable compliance or attempt audit.

There is no native worker process for Kanboard to resume or stop. Reopen and reassignment change records; they do not cancel an old agent's external effects. Task removal, lines 90–107, attempts attachment removal before deleting the row. Those file and database operations do not form one reversible cancellation transaction.

The API's alternate move-to-project writer, lines 20–65, directly updates the task and prepares it as open. It can therefore reopen a closed task as part of relocation. Its method returns true even when the row update returns false. This path must be included in any added transition policy and in client reconciliation; a success boolean alone is not proof that relocation persisted.

The JSON-RPC parser, lines 92–181, executes the procedure and then echoes the request ID into the response. It does not cache a durable outcome keyed by that ID. After an uncertain response, repeating create, comment or other side-effecting calls can repeat effects. The reviewed core task/API/schema operation inventory has no task lease or attempt-fencing alternative to those ordinary mutations.

Access, deployment and human interaction

API authentication supports user authentication and a separate application credential named jsonrpc. The application credential is compared with the configured API token and does not initialize a user session. Procedure authorization denies selected personal procedures to that mode. User authorization, project authorization and task authorization apply user/role checks when a user is logged in.

Consequently, the application token is a broad integration credential. Separate per-agent user credentials preserve more useful scope and attribution. ApiAccessTokenAuth, lines 1–105, checks active users and API-scoped access tokens. The middleware switches two-factor-enabled users to this token provider. The API access maps, lines 180–239, distinguish application roles and project member/manager/viewer operations.

Browser operations also use project authorization middleware, which resolves the task's actual project. Role helpers, lines 1–162 and 183–292, add configured column and assignment restrictions to applicable UI paths. These helpers are not a universal storage policy: the status controller and JSON-RPC procedures must be assessed through their own checks. This review does not claim a complete authorization security audit or identical custom-role behavior across every interface.

Board dragging, lines 1–116, sends a position mutation and refreshes returned markup on success. Its generic error path clears loading state without explicitly restoring the prior card position; a 403 reloads. BoardAjaxController, lines 1–116, checks project association and movement permission but does not use the supplied source column as an expected current-state predicate in storage.

Polling refreshes while the page is visible and not saving. It uses the project's last-modified check rather than a durable event cursor. Project timestamps, lines 434–458, use integer seconds and a strict greater-than comparison. Event-driven timestamp updates are separate from the task write. This can delay or miss a refresh around failed event processing or same-second changes. It is a presentation-freshness boundary, not ownership protection.

The included Dockerfile uses Alpine and PHP 8.5 packages; the SQLite compose example persists data, plugins and certificate volumes. ObjectStorageProvider binds uploaded files to local storage. Multiple web hosts need consistent database, files, session and plugin configuration. No clustered setup was trialed.

Plugin loading, lines 1–137, checks declared version compatibility and initializes plugin PHP code, services and schema. Reference hooks, lines 94–116, can modify values in place. This gives useful extension power with application-level trust. Cron-driven task triggers and overdue notifications, lines 1–90, require operational scheduling; they do not supply agent heartbeats.

Test-source evidence and adoption work

Selected assertions were read, not executed:

  • Task status tests, lines 58–143, check close/reopen timestamps and explicitly expect all subtasks to become done after parent close.
  • Modification tests, lines 46–109, check ordinary title/owner changes and event counts. They do not exercise competing claimers or expected-revision rejection.
  • Link tests, lines 103–145, verify reciprocal labels and linked task data. They do not establish graph readiness or cycle prevention.
  • Unread notification tests, lines 50–93, check user-scoped removal and stored notifications. They do not prove task-write/outbox atomicity.
  • Role-helper tests, lines 165–219, exercise custom assignee restrictions in the helper. That is not certification of every API and controller mutation.
  • JSON-RPC batch tests verify per-request access-denial responses and whole-batch authentication failure using registered closures. They do not prove application authorization for every procedure or transactional batches.

For adoption, retain Kanboard's project/task API and human board, but add a single authoritative claim and attempt service that every worker mutation must pass. It needs conditional ownership acquisition, renewal, expiry, fenced progress writes, retry-safe outcomes and restart reconciliation. Enforce capacity and readiness during acquisition rather than through a prior search or UI warning.

Add explicit submitted results and qualified acceptance, with pinned artifacts and child integration. Prevent ordinary close, automation and alternate writers from bypassing that policy. A transactional outbox and durable delivery/acknowledgement records would strengthen communication. Keep pending questions separate from notification read state, and expose unresolved ownership or delivery failures to the human owner.

Kanboard's strengths are conventional task records, familiar inspection and extension points. Its adoption cost for this baseline lies in the distributed coordination and acceptance invariants that the conventional board intentionally leaves to people and integrations.
