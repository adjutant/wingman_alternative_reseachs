# Task Master: agent planning without shared execution ownership

Source: https://github.com/eyaltoledano/claude-task-master

Reviewed commit: `c0c98d367c55296bfe69e65680625b6db437af02`.
Assessment date: November 9, 2026.
Baseline: [Shared task management for an agent organization](../../../AGENT_TASK_MANAGEMENT.md).
Evidence ledger: [review.json](review.json).

## Fit decision

Task Master provides useful task planning and agent-facing workflow tools. It supports structured tasks, subtasks, dependency-aware suggestions, priorities, tag contexts, AI expansion, implementation notes, CLI/JSON output, native MCP and a VS Code board. Its optional autopilot workflow persists TDD phases and integrates Git branches, commits and clean-tree finalization. The separate loop command launches a coding agent repeatedly.

These mechanisms do not establish a shared execution authority for several agents. Next-task selection returns a candidate without reserving it. Start checks a snapshot of in-progress tasks, permits the already-running target, supports force and can continue after status persistence fails. Mutable status/assignee fields have no owner generation, lease or execution-attempt fence. Two agents can receive and start the same work.

Local persistence has real file-locking and replacement safeguards, but two distinct writer implementations coexist. Higher-level operations also load a task collection before entering their save lock. Saving that older collection can overwrite another same-tag update. The mixed legacy and newer lock protocols need reconciliation before trusting concurrent writes. Atomic replacement of a file is a different property from an atomic task transition based on current ownership.

The authenticated API mode is a client for separate hosted services/Supabase. Its client-side scoping and subscriptions are present, but this checkout does not establish the external database's RLS, task authority, acceptance or recovery guarantees. Do not attribute those server guarantees to this repository from client comments.

The [license](../repo/LICENSE), lines 1–25, is MIT with the Commons Clause condition, including a restriction on the defined right to Sell. The [package declaration](../repo/package.json), lines 62–63, names `MIT WITH Commons-Clause`. Treat this as a source-available option with an adoption constraint rather than unqualified permissive MIT. This review records the declaration and condition; it does not certify legal compliance.

## Scope and evidence level

The full checkout contains 1,254 tracked files. This targeted source review follows published entry points and mixed CLI/MCP registration; core task models, next/status/start paths; newer and legacy local storage/locks, selected creation/expansion/dependency/note writers; remote storage/repository update and subscription paths; workflow start, phase changes, commit/finalize/abort/state/activity; coding-agent loop execution and result parsing; and selected extension activation, board, cache and optimistic status behavior. Selected test assertion bodies were read. No candidate application, dependency install, build, migration or test was executed.

This is not an every-line, full security or runtime audit. All AI providers, prompt transformations, full authentication/OAuth/MFA and credential storage, remote server/database enforcement, every import/export/move/remove writer, all extension messages and browser/VS Code rendering are outside certification. Source and test inspection do not establish passing tests, reliable concurrent operation, large-project usability or deployed service availability.

## Architecture and shared records

The [root manifest](../repo/package.json), lines 1–16 and 125–137, declares version 0.43.1, Node 20 or later, npm 10.9.2 and CLI/MCP binaries. [Build configuration](../repo/tsdown.config.ts), lines 33–46, bundles `scripts/dev.js` and `mcp-server/server.js`. The [CLI entry](../repo/scripts/dev.js), lines 19–56, loads project environment and the command module. [Command registration](../repo/scripts/modules/commands.js), lines 1815–1820, imports the newer CLI command registry. [Its task entries](../repo/apps/cli/src/command-registry.ts), lines 40–78, select the newer list/show/next/start/status implementations.

The [MCP entry](../repo/mcp-server/src/index.js), lines 60–127, registers a selectable tool set and starts stdio transport. The [tool registry](../repo/mcp-server/src/tools/tool-registry.js), lines 6–145, combines TypeScript status/read/autopilot tools from `@tm/mcp` with JavaScript planning, dependency, tag and next-task tools. Core/standard/all selection controls exposed operations and context size; it does not implement worker/reviewer authorization. Retained older status helpers must not be mistaken for the currently registered MCP status implementation.

[Task types](../repo/packages/tm-core/src/common/types/index.ts), lines 131–179, store stable task IDs, title/description, status, priority, dependencies, details, test strategy, subtasks, dates, effort, optional assignee and metadata. Subtasks cannot themselves contain subtasks in this type. The file status updater explicitly accepts one parent/subtask separator. The integration guide's examples of deeper dotted IDs therefore do not establish uniform recursive hierarchy support.

[Local path resolution](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/path-resolver.ts), lines 11–42, places all tag contexts in `.taskmaster/tasks/tasks.json`. [Storage selection](../repo/packages/tm-core/src/modules/storage/services/storage-factory.ts), lines 50–163, can use explicit file/API configuration or auto-select API storage from authenticated context, otherwise file storage. A tag is a task collection context, not a separate worker, tenant or work lease. API mode uses organization/brief context; it is not just the same local JSON file transported to another host.

## Selection, dependencies, creation and launch

[Core next-task selection](../repo/packages/tm-core/src/modules/tasks/services/task-service.ts), lines 299–417, builds a completed-ID set, first considers eligible subtasks of in-progress parents, then considers main tasks. It accepts pending or in-progress candidates and sorts by priority, dependency count and ID. It returns a record without changing ownership. [The MCP next wrapper](../repo/mcp-server/src/core/direct-functions/next-task.js), lines 45–82, uses a separate [JavaScript selector](../repo/scripts/modules/task-manager/find-next-task.js), lines 24–138, with similar snapshot logic. Neither operation reserves its answer for the caller.

[Dependency creation](../repo/scripts/modules/dependency-manager.js), lines 54–204, checks the target exists, rejects self-dependency, walks dependencies for a cycle, updates the snapshot and saves it. [The recursive walker](../repo/scripts/modules/dependency-manager.js), lines 377–435, normalizes relative sibling dependencies. These are implemented validation rules. The graph read/check occurs outside the eventual write lock, and arbitrary task-field/AI expansion writers are separate paths. The checks do not establish a graph invariant under all concurrent writers or prevent direct completion while a dependency remains unfinished.

[Task creation](../repo/scripts/modules/task-manager/add-task.js), lines 203–240, 285–295 and 490–548, reads the tag structure, allocates the next ID as the highest tag ID plus one, creates a pending task and writes the collection. This identity allocation is not reserved during the AI work or protected by a transaction spanning read and save. Two creators can calculate the same next ID. [Expansion](../repo/scripts/modules/task-manager/expand-task.js), lines 95–126 and 320–365, loads a task before AI generation, optionally clears its subtasks for force, validates an array-shaped response and appends subtasks before saving. Older task snapshots can survive a long provider request and then replace newer local edits.

[Start service](../repo/packages/tm-core/src/modules/tasks/services/task-execution-service.ts), lines 48–116 and 140–201, checks for other in-progress work unless forced. It explicitly permits the same already-in-progress target and a subtask whose parent is in progress. It can update the parent status before preparing a coding-agent command, but a persistence error is logged and tolerated. The `started` flag at this layer means a command was prepared, not that an OS process was verified running.

[The CLI launcher](../repo/apps/cli/src/commands/start.command.ts), lines 236–308, then spawns the command, inherits stdio and forwards termination signals. It does not persist an execution attempt ID or lease. [Command preparation](../repo/packages/tm-core/src/modules/tasks/services/task-execution-service.ts), lines 235–259, uses `process.cwd()` rather than deriving the execution directory from the selected project's storage path. Project selection and actual execution directory therefore require attention when invoked outside the project. Successful or failed launch is not an atomic task-status transition with recovery compensation.

## Persistence, concurrency and alternate writers

[New file operations](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-operations.ts), lines 17–211, use `proper-lockfile`, reread JSON inside a modification callback, call a Steno writer and release the lock in `finally`. This is useful protection for callbacks that compute a change from the locked data. The [file-operation tests](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-operations.spec.ts), lines 75–92 and 179–225, assert sequential and concurrent increments against that locked callback. They do not test every higher-level task updater.

[FileStorage saving](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-storage.ts), lines 225–284, replaces the selected tag's tasks with the array supplied by its caller while preserving other contexts in selected format branches. [Update](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-storage.ts), lines 355–415, loads the tag, changes one item and later saves that whole array. [Status update](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-storage.ts), lines 451–603, follows the same load-then-save pattern. A reread at save time does not merge a newer edit within that tag. The source supports the inference that interleaved same-tag changes can be lost despite correct file replacement.

Legacy [writeJSON](../repo/scripts/modules/utils.js), lines 1022–1195, also has locking and temporary-file rename. It rereads current file data for selected resolved-tag merge cases, but still replaces the selected task slice, and accepts whole raw structures supplied by earlier reads. Neither implementation compares an expected task revision or current owner. Multiple requested status IDs are also individual updates: the [MCP loop](../repo/apps/mcp/src/tools/tasks/set-task-status.tool.ts), lines 49–110, can fail after earlier IDs have persisted. A failure response does not mean the batch rolled back.

There is a separate lock-format incompatibility. Legacy [sync locking](../repo/scripts/modules/utils.js), lines 193–303, exclusively creates a regular JSON file at `<tasks path>.lock`, detects staleness by age, renames stale locks and releases with unlink. The newer FileOperations uses `proper-lockfile` at that default path. The [lockfile pin](../repo/package-lock.json), lines 30545–30555, is version 4.1.2. Its primary source uses a directory created with mkdir, periodic mtime updates and directory removal: https://raw.githubusercontent.com/moxystudio/node-proper-lockfile/v4.1.2/lib/lockfile.js

These are different acquire/release/stale-cleanup protocols sharing a path. Seeing `.lock` in both implementations is not proof that they coordinate correctly. Mixed use can cause contention or incompatible stale cleanup. This is a static compatibility finding, not a reproduced race or filesystem certification. The file lock's timeout also must not be credited as an expiring task ownership lease.

## Completion and the TDD workflow

[TaskEntity](../repo/packages/tm-core/src/modules/tasks/entities/task.entity.ts), lines 144–193, defines `canComplete`/`markAsComplete`, including blocked/cancelled and unfinished-subtask checks. The inspected production call inventory contains the method definition rather than a caller in the active status pipeline. [The public task facade](../repo/packages/tm-core/src/modules/tasks/tasks-domain.ts), lines 242–248, forwards to [TaskService status](../repo/packages/tm-core/src/modules/tasks/services/task-service.ts), lines 719–772, which delegates directly to storage. Main-task file status changes do not invoke the entity completion guard. Subtask changes can automatically move the parent to done when all children appear done-like, without a separate acceptance record. Do not credit the entity rule as a universal completion gate.

[Workflow start](../repo/packages/tm-core/src/modules/workflow/services/workflow.service.ts), lines 155–246, checks for an existing workflow, requires a clean Git repository, creates subtask phase context and a branch, and enables persistence/activity. [Workflow state](../repo/packages/tm-core/src/modules/workflow/managers/workflow-state-manager.ts), lines 35–72 and 130–220, is one JSON file under the user's home directory keyed by sanitized absolute project path, with backup methods and a Steno writer. There is no cross-process workflow transaction or expected generation in that save path. A worktree on another path/host does not automatically share this authority.

[Phase transitions](../repo/packages/tm-core/src/modules/workflow/orchestrators/workflow-orchestrator.ts), lines 101–290, reject incorrect phase ordering. RED with zero reported failures treats the subtask as already implemented and advances; GREEN requires zero failures. The [MCP phase tool](../repo/apps/mcp/src/tools/autopilot/complete.tool.ts), lines 11–27 and 95–111, constructs results from caller-supplied counts. It does not execute a test runner or bind the counts to a commit/evidence digest. A [stricter validator](../repo/packages/tm-core/src/modules/workflow/services/test-result-validator.ts), lines 20–105, exists, but the inspected service constructs its orchestrator without installing it; the production setter inventory does not establish use. Its standalone presence does not strengthen these active transitions.

[MCP commit](../repo/apps/mcp/src/tools/autopilot/commit.tool.ts), lines 70–216, verifies COMMIT phase, stages selected files or all changes, creates a Git commit and then advances workflow/task state. Those are separate effects. A commit can exist when a later persistence step fails; retry needs to inspect Git and workflow state. The core [commit service](../repo/packages/tm-core/src/modules/workflow/services/workflow.service.ts), lines 456–499, advances phase and updates subtask status; Git creation occurs in the presentation path, not as a universal core acceptance invariant.

[Finalization](../repo/packages/tm-core/src/modules/workflow/services/workflow.service.ts), lines 501–560, requires FINALIZE and a clean working tree, transitions to COMPLETE, requests main-task done and removes state. [The status helper](../repo/packages/tm-core/src/modules/workflow/services/workflow.service.ts), lines 125–150, catches updater failure and logs a warning. Finalization can consequently remove workflow state even though the task status was not saved. Abort deletes workflow state rather than stopping a distributed worker or reverting Git/task effects. The phase state, task authority, activity log and repository do not share one transaction.

## Agent loop, cancellation and recovery

[Loop execution](../repo/packages/tm-core/src/modules/loop/services/loop.service.ts), lines 113–201, runs a bounded number of iterations, tracks an in-memory running flag and appends progress. Stop changes that flag so the loop ends after the current iteration. [Non-verbose execution](../repo/packages/tm-core/src/modules/loop/services/loop.service.ts), lines 318–370, uses synchronous process spawning without a work-iteration timeout in the inspected options. [Verbose execution](../repo/packages/tm-core/src/modules/loop/services/loop.service.ts), lines 386–510, owns a child and output handlers, but the loop stop method does not signal that child. This is limited cancellation, not a persisted execution supervisor.

[Result parsing](../repo/packages/tm-core/src/modules/loop/services/loop.service.ts), lines 289–307, checks completion and blocked text markers before a nonzero exit code. A completion marker can therefore win over failure status. With no marker, zero exit is counted as a successful iteration, and the loop's task counter increments without verifying a task-record transition. These metrics are not evidence that accepted work completed. The [default prompt](../repo/packages/tm-core/src/modules/loop/presets/default.ts), lines 6–26, instructs the agent to select, test, mark done, commit and signal completion. Those instructions do not become storage-enforced acceptance or ownership rules.

[Command arguments](../repo/packages/tm-core/src/modules/loop/services/loop.service.ts), lines 565–582, use Docker sandbox invocation when selected and `--dangerously-skip-permissions` for the ordinary Claude CLI loop. This is an operational behavior to account for, not proof of effective sandbox isolation. Docker/provider security was not run or certified. A host restart has no inspected durable child-process registry, attempt renewal or stale-result rejection mechanism.

## Remote mode, communication and inspection

[API storage](../repo/packages/tm-core/src/modules/storage/adapters/api-storage.ts), lines 244–270, 558–588 and 672–724, scopes through current brief context and delegates task updates to a repository. Its constructor, lines 75–120, explicitly casts a Supabase repository to the interface while noting incomplete interface implementation. That comment is a completeness limit, not permission to assume every declared storage capability works remotely.

[Supabase update](../repo/packages/tm-core/src/modules/tasks/repositories/supabase/supabase-repository.ts), lines 200–271, validates selected fields, reads metadata, merges it client-side, writes by brief/display ID and fetches the result. The client submits no expected revision/attempt predicate; metadata can be based on an earlier read. [Retry logic](../repo/packages/tm-core/src/modules/storage/adapters/api-storage.ts), lines 1113–1128, retries thrown operations with exponential delay, without an operation key or error-class restriction in that helper. A committed write followed by a failed read can be retried. External server idempotency or RLS is not established here.

[Local watching](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-storage.ts), lines 927–984, debounces filesystem changes and exposes errors. [API watching](../repo/packages/tm-core/src/modules/storage/adapters/api-storage.ts), lines 955–1040, subscribes to brief-filtered PostgreSQL changes, debounces a generic change callback and reports channel errors. Neither inspected interface exposes durable message IDs, recipient acknowledgement or a replay cursor for manager/worker handoffs.

Implementation notes are stored as timestamped additions to details in [subtask update](../repo/scripts/modules/task-manager/update-subtask-by-id.js), lines 347–363 and 398–408. They remain mutable task context and inherit collection-save concurrency limits. [Workflow activity](../repo/packages/tm-core/src/modules/workflow/services/workflow-activity-logger.ts), lines 74–149, subscribes to events and appends JSONL through the [activity writer](../repo/packages/tm-core/src/modules/storage/adapters/activity-logger.ts), lines 43–64. Append failures are logged and do not fail the workflow. This is useful diagnostic history, not an immutable task/actor/attempt journal committed with each transition.

[MCP context creation](../repo/apps/mcp/src/shared/utils.ts), lines 276–307 and 390–445, selects project root from environment/arguments/session, loads project environment and creates a core instance. Local commands inherit the process's filesystem/Git authority. API auth guards for local-only commands do not implement separate manager, worker and reviewer rights. Hosted auth and database authorization need independent verification before deployment to several principals.

## Usability, tests and adoption work

The [extension activation](../repo/apps/extension/src/extension.ts), lines 33–75, wires MCP, a cached repository, polling, terminals and a webview. The [board component](../repo/apps/extension/src/webview/components/TaskMasterKanban.tsx), lines 31–95, groups tasks by status and uses task mutations. Its [status hook](../repo/apps/extension/src/webview/hooks/useTaskQueries.ts), lines 91–130, snapshots optimistic queries, rolls back on failure and invalidates afterward. The [repository](../repo/apps/extension/src/services/task-repository.ts), lines 14–58 and 119–137, caches reads and refreshes after status updates. These are implemented UI paths; they do not prove extension activation, accessibility, latency or large-board behavior at runtime.

The human/agent surface is broad, but users must understand tag versus brief context, newer versus legacy operations, AI/provider configuration, local workflow state versus task state, and current working directory for launch. AI planning and update operations can call external providers; this review does not assign current costs or certify providers. The local file mode is simpler to operate than the external API mode, while parallel agents require additional authority rather than only shared JSON or Git worktrees.

Selected assertions were read for [locked modification](../repo/packages/tm-core/src/modules/storage/adapters/file-storage/file-operations.spec.ts), lines 75–92 and 179–225; [workflow phase/persistence](../repo/packages/tm-core/src/modules/workflow/orchestrators/workflow-orchestrator.spec.ts), lines 78–110 and 373–414; and [loop result parsing](../repo/packages/tm-core/src/modules/loop/services/loop.service.spec.ts), lines 493–551. None ran. These checks do not establish mixed legacy/new lock interoperability, higher-level same-tag update safety, atomic claims, marker/nonzero precedence safety, external authorization or crash-safe finalization.

For the baseline, retain task decomposition, dependency suggestions, structured MCP, notes and useful workflow/Git components. Add one consistent transactional mutation protocol, exclusive claim/capacity/lease authority, attempt generations, stale-write rejection and idempotent retries. Bind test/evidence/results to the reviewed revision, separate reviewer rights, and make task/workflow/Git reconciliation explicit. Durable questions, acknowledged handoffs, cancellation and parent/child acceptance need their own data and enforcement. Task Master is a planning and developer-workflow foundation; the inspected code is not the complete shared coordination authority requested here.
