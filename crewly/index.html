Crewly assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/stevehuang0115/crewly

Local checkout: researchs/crewly/repo. Inspected commit: f05af05be4a8a76e22bfbaa26643e9c4d5ff0ab5; package version 1.21.0 (package.json, lines 1–8). This is a source assessment of that revision, not a claim about the current hosted service. Baseline: Wingman purpose.

Verdict: Crewly provides a strong organization and execution foundation for Wingman. Independent coding agents share durable teams, tasks, project tickets, and chat. Telegram routes messages to an orchestrator. Repair loops address stalled coordination. The source also implements owner decisions, acceptance records, evidence, project autopilot, Cloud messages, team migration, and an owner board.

Wingman still needs its Butler/ProjectMaster hierarchy and separate ProductMaster/TechMaster leadership for each product. Proportionate discovery, complete specifications, integrated acceptance, and enduring executive timelines also need adaptation. Multi-host client code exists. It depends on external Cloud services and separate per-machine state. It does not establish a self-contained shared Wingman registry.

Architecture and execution model

Crewly uses TypeScript/Node, Express, Socket.IO/WebSocket, React, filesystem state, and SQLite-backed chat. The CLI registers start, lifecycle, harness, ticket, team-move, and Cloud commands. See CLI index, lines 65–81, 152–169, and 272–357. The backend creates HTTP and initializes services. It subscribes chat, task history, worktree, and dispatch handlers. It also starts request decomposition and reconciliation. See backend index, lines 535–565, 659–730, 1612–1705, and 1837–1857.

The main execution path is team/member API → _startTeamMemberCore → AgentRegistrationService.createAgentSession → runtime command/prompt → PTY-backed CLI. The session factory implements only pty. Legacy types, names, and comments still mention tmux. See factory, lines 59–123. A started member has a real process and conversation. Adapters cover Claude Code, Codex CLI, Gemini CLI, OpenCode, and Antigravity.

The separate crewly-agent path uses an external executable. Its newline-delimited JSON messages are init, run, abort, get-state, and shutdown. Results and tool events return through stdout. See external runtime, lines 1–9, 74–89, 174–214, and 522–614. Registry APIs retain older in-process names. Those names do not establish that the selected executable runs inside the backend.

Several overlapping work models coexist. Request records represent owner goals; Mission records hold longer-running objectives/OKRs; WorkItem is a concrete execution unit; TaskClaim leases ownership of a WorkItem; project tickets are human-editable Markdown records. The newer project-ticket workflow enforces at most one live WorkItem for a ticket and bridges delegation into tickets when a project can be identified (workflow, lines 1–15, 879–959). This separation is useful: a permanent agent can handle many tasks, a task can be retried or reassigned, and a conversation can be restarted without discarding the ticket. It also creates integration complexity: names such as V2/V3, Requests and project tickets do not denote a single simple tracker schema.

Persistence is local-first, with important boundaries:

  • Team configuration and member prompts live under Crewly home; projects.json is the project registry (storage, lines 76–109, 253–296).
  • Requests resolve to project data directories. The task pool and claim records are in ~/.crewly/task-pool/pool.json, with atomic writes and a 500 ms write debounce (request store, lines 169–195; pool storage, lines 30–95).
  • Project tickets use <project>/.crewly/tickets/, folder locking, fresh reads under lock and atomic writes; cache invalidation detects manual edits/git pulls (ticket store, lines 1–20).
  • Session metadata is saved separately from the runtime's own conversation transcript. A PTY dies with the backend; resuming reconstructs a process and reopens a supported harness conversation (session persistence, lines 1–6, 34–74).
  • CREWLY_HOME and resolveProjectDataDir keep durable records outside replaceable npm package trees. Some memory/role services still derive paths directly from HOME or homedir(). See home resolution, lines 46–53 and 92–118; role service, lines 136–143; and session memory, lines 87–111. One override therefore does not establish isolation of every subsystem.

Agent definitions, creation and lifecycle

What an agent is

A role is reusable definition metadata plus a prompt and default skills. It is not an executing agent. A TeamMember is the durable organizational instance. It has a UUID, display name, role, system prompt, configured runtime/model/effort/tier, skill tags, overrides, status and optional hierarchy/ownership/autonomy fields. Its permanent agentId is also its stable session key; changing a display name should not change references in triggers, work, bots or channels (member types, lines 32–65, 118–183). A live PTY/runtime process is one incarnation of that member. A harness conversation has another ID used to restore context. A WorkItem/claim is work ownership, not a new member. This model is close to Wingman's persistent instances and avoids confusing role prompts with agents.

The definition has multiple layers. Built-in roles come from config/roles; custom roles are stored under ~/.crewly/roles, with validated create/update/delete and skill assignment. Per-member prompts are persisted independently by the storage service. The legacy registration path loads a role prompt, substitutes session/member/project references, prepends the member's prompt, and adds operational capabilities. The default modular path replaces that assembled text with identity, active work, session briefing, standing answers, soul, role boundaries, decision rights, SOPs, risk policy, skills and memory references. Modules have priorities and token budgets; noncompactable operational context survives trimming (role service, lines 95–143, 262–310, 697–704; registration, lines 2635–2756; assembly, lines 45–117, 139–157, 178–204). Soul resolution includes a member override and a delegation-capable leader overlay (soul module, lines 62–119).

An important extension caveat is visible in implementation. RoleService can read custom prompt files, but getPromptFileForRole in registration resolves built-in directories and otherwise falls back to a generic role prompt. Effective runtime skill flags likewise read built-in role.json paths. More importantly, modular prompts are enabled by default: registration prepares the monolithic role/member text, then returns the separately assembled modularPrompt. Its member-config helper forwards job description, ownership, skills, SOP and risk fields, but not the stored systemPrompt; role-specific fragments resolve under built-in config/roles. Thus storing/editing a member prompt is not sufficient evidence that its exact text reaches the default launched context. Structured job/ownership fields, souls and fragments still specialize agents. This source-level propagation mismatch should be validated/fixed before Wingman relies on a new profile. It is not a claim that all custom agents lack specialization (registration, lines 856–904, 1495–1517, 2726–2743, 2925–3033; module-config helper, lines 202–282; fragment loader, lines 298–313).

Materializing and starting a team

POST /teams requires a name and nonempty member array; every member needs name, role and systemPrompt. It validates models, duplicate team names and hierarchy requirements, allocates UUIDs, stores inactive/idle members and derives the single-leader subordinate links. Multiple leaders are permitted; their detailed worker mapping is not automatically inferred. Team/project associations and policy fields persist. The endpoint then starts member sessions (team controller, lines 1213–1376). This is concrete organization creation, not just a proposal for a team.

The start path checks paused teams, role validity, existing live sessions, owner-stop state and running-agent capacity. It fixes/persists stable identity, calls the unified registration service and initializes member memory. A startup watchdog repairs members stuck in starting; deferred starts due to the running-agent cap remain recoverable rather than being declared crashes (same controller, lines 674–713, 847–933, 945–1044). Registration serializes launch flows, resolves model/skill flags, checks usage fallback and creates the PTY with identity and credential environment. It builds a prompt file, starts the harness, recognizes readiness/startup dialogs and verifies registration. The service has recovery of existing sessions before full recreation (registration, lines 3688–3838, 3838–3970, 4060–4180, 4359–4423). “Active” is thus a connection/registration status, distinct from idle/in-progress work status.

Tools, authority and execution boundaries

Most coding tools are supplied by the selected CLI; Crewly supplies Bash skills and local API surfaces for reporting, communication, memory, delegation, tickets and integrations. Model/effort is configurable per member. Default CLI commands grant broad unattended execution (claude --dangerously-skip-permissions, gemini --yolo, codex -a never -s danger-full-access, opencode --auto), not per-member OS sandboxes (settings types, lines 365–393). That enables autonomous coding but means a role boundary in a prompt is not a filesystem isolation boundary.

There are additional enforced controls. Skill permission filtering considers autonomy level, delegation authority and role; “directed” agents cannot delegate/decompose, while higher levels still block production deployment through those named skills (skill permissions, lines 39–68, 107–151). Browser held-action authorization, owner-authenticated APIs, credential guards and git/control-plane guards add targeted protection. These controls should be evaluated by surface: blocking a Crewly skill is not proof that an unrestricted CLI cannot perform an equivalent shell action. A Wingman deployment should retain the useful guards while defining host credentials and filesystem ownership explicitly.

Work routing and concurrency

Messages target stable agent sessions; chat DMs bind to one agent, channel mentions resolve recipients, and huddles fan out to members with required/optional response modes. Busy recipients can hold messages in a persisted per-agent queue. The dispatcher can activate an offline member and defer when the running-agent cap is reached (chat dispatcher, lines 46–128, 139–160). WorkItems can target a member or be claimed by compatible agents. The pool serializes claim operations, checks live sessions and task policy, while claims provide leases/heartbeats rather than relying on a message being seen (pool, lines 343–360, 441–455; claim service). Multiple processes execute in parallel; several queued tasks are not evidence that one member executes multiple model turns concurrently.

Opt-in per-work-item git worktrees improve parallel code work. Creation is serialized per repo; copied/symlinked shared files and branch/base metadata are recorded. Completion can flag work performed outside the assigned tree. Cleanup requires known-clean state and, for successful work, evidence the branch landed. It never forces deletion and retains the branch for cancelled work (worktree service, lines 1–28, 60–86, 268–366, 522–608). This provides useful edit isolation, not automatic integration or product acceptance.

Continuity, wakeups and recovery

Session persistence records cwd, command, runtime, role, team/member and conversation IDs. Claude receives a generated conversation ID before launch, then uses --resume; Codex IDs are discovered from rollout files and restored through codex resume; Antigravity uses its conversation flag. The inspected planner returns no resume support for other runtimes (recovery, lines 97–150). Transcript environment markers inherited from a parent Claude process are stripped so nested launches can still save transcripts. Missing or oversized conversations can start fresh with a handover rather than fail indefinitely.

Memory is complementary to conversation resume: session summaries and agent/project knowledge are saved, while startup active-work context is rebuilt from authoritative Requests and WorkItems. It tells a member what it owes now, rather than trusting an old summary. The orchestrator receives a broader view (session memory, lines 1–12, 87–111; active work, lines 1–28, 93–118). Fresh-task conversation management saves handover/memory before clearing very large idle Claude contexts, respects common retry/review roots and protects active owner conversations. It is runtime-specific context management, not a universal conversation archive/fork feature (fresh conversation, lines 1–47, 104–112).

Proactivity is implemented at several levels. The reconciler has fast/full periodic loops with overlap prevention. It detects stale claims, dead holders, resolved dependencies, due blocked items, unclaimed work and unverified completion, applies corrections and wakes agents. Cron tasks persist per team, respect timezones/pauses and have bounded retries for transient startup failures. Project autopilot, default off, asks the lead to triage backlog or replan toward a goal, with budget, cadence and in-progress brakes. The code wakes a decider rather than making every ticket ready itself (reconciler, lines 299–319, 340–392, 516–534, 661–699; cron, lines 1–10, 34–72; autopilot, lines 1–34). This is strong organizational supervision, but distributed among deterministic services and agent prompts.

Interruption, completion and retirement

Stopping a member uses owner-stop bookkeeping before termination so automation does not immediately resurrect it. Graceful termination and relaunch are separate operations. Team pause persists the pause, stops live members, releases unstarted assignments and prevents automated routing/starts; running work remains visible. Timed pause expiry can resume the team (stop path, lines 1131–1208, 2521–2560; pause service, lines 1–20, 153–245; termination, lines 4491–4608). Idle suspension kills the process while retaining identity/conversation and can rehydrate on a message; its specific metadata and documented resume path are Claude-centric (suspend service, lines 21–49, 120–157).

A worker reporting done does not always close the work. completeItem chooses direct completion or submission for verification; verifier acceptance/rejection records actor, role and timestamp and resolves blocked dependents after acceptance. The completion API checks evidence: malformed evidence, missing/empty/stale local artifacts and reported failing commands are refused; blocked evidence parks work. Enforce is the default, with a warn override and bookkeeping exemptions. HTTP artifacts are accepted without fetching, and supplied command outcomes are not independently re-executed by that evidence validator (completion, lines 2458–2515, 2626–2647; evidence, lines 62–88, 143–173, 264–342; default, lines 1545–1559). Actual quality-gate execution is a separate service. Human acceptance can verify or send back a ticket. A send-back adds a new acceptance criterion. Request closure refuses unfinished children when its task-pool collaborator is wired, but the documented no-collaborator path degrades with a warning (request gate, lines 39–117, 156–168; ticket review, lines 428–475, 495–515).

Team/member deletion and archival are distinct from stopping work; delete routes remove organizational entries, while transcripts, memories, ticket history and git branches have their own lifecycle. There is no demonstrated automatic “whole product accepted → all active implementation/testing stops” invariant. Wingman must connect accepted product delivery to stopping schedules, claims and agents deliberately. Worktree janitors and state cleanup are valuable resource management, not evidence that an accepted product has been retired correctly.

Coordination and a concrete source trace

The system coordinates through persisted records plus messages and events. Chat V2 offers durable rooms and DMs; project-ticket Markdown is shared editable state. The task pool has durable claims/status. The event bus delivers in-process reactions and queued agent notifications. Event handlers are concurrent and errors are caught rather than propagated to the original publisher. This is not a transactional distributed event log (event bus, lines 27–31, 75–125, 227–276). Backend restart can reconstruct work from stored entities even though process-local subscription/dedup maps reset. That distinction explains the importance of reconciler backfill and idempotence guards.

A real implemented request path, traced statically, starts with POST /api/requests carrying an actionable build objective:

  1. The Request router calls createRequestHandler, which validates the body shape, attaches the calling agent's trace when available and calls the Request service. It returns the stored Request as HTTP 201 (request routes, lines 37–47; controller, lines 139–165).
  2. RequestService.create validates/classifies intent, persists the Request and publishes request:created. The decompose subscriber re-reads it, filters for actionable L2 categories and skips already linked work (request service, lines 312–383; decomposer, lines 323–435). This is conditional, not every chat utterance becoming a product project.
  3. planTasksFromObjective chooses keyword/complexity templates. Complex build work becomes design approach, implement and test/verify tasks with generic criteria. It does not conduct domain discovery or make meaningful product choices on the human's behalf (planner, lines 1107–1156). Agent-led technical decomposition can go deeper through delegation skills.
  4. The subscriber builds WorkItems with the Request ID, resolves title-based dependencies into IDs and blocked status, and adds them in plan order. These automatic items initially have no target: the orchestrator is to decide assignment (decomposer, lines 372–425, 530–548). Queue events link children to the Request. Once work is targeted, dispatch pushes a [CREWLY-DISPATCH] notice. An agent polls/claims, or automatic idle claiming gets the next item. Direct leader handovers share a dispatch dedup key and a grace period so a full brief and a push notice do not create duplicate execution (dispatch, lines 1–43, 151–173).
  5. For project-associated delegation, the workflow selects the project, links an existing ticket or creates one, and preserves the one-live-item-per-ticket relationship. Ambiguous multi-project work remains unresolved rather than silently attributed (workflow, lines 879–959). Worker claims and updates become shared tracker state. Optional worktree creation gives the worker an isolated path.
  6. A blocker can become a WorkItem block/escalation or a structured owner question. Decision service persists it, posts a card where supported, records the answer in ticket history, and delivers/queues the answer back to the asking member. This is more robust than leaving a question only in terminal output (decision service, lines 139–168; decision wiring). Browser/mail irreversible actions have additional hold/release semantics.
  7. Worker completion passes evidence checks and optionally creates a lead review. The reviewer accepts/rejects; Request completion/cascade and ticket workflow react. Owner acceptance is a separate path. The dashboards/trace records expose the work, and the reconciler catches a dead agent, stale claim or unreviewed item. A successful task status alone does not prove integrated product behavior was accepted.

Chat V2 processes owner input through ticket intake before dispatch. The controller creates or joins the thread ticket and marks the agent's copy. Source comments say this replaces the older INBOUND-2 Request hook. Request/SLA bookkeeping and agent replies still interact.

Bound-agent and huddle replies retain senderType: agent. They do not automatically enter the user dispatcher. Private agent-to-agent delivery separately wraps sender and owner-route context. A cross-channel agent post can resolve to the channel owner's user identity. It retains authorAgentSession provenance to prevent treatment as owner approval. That path can enter user-message dispatch. See chat service, lines 2013–2034 and 2458–2480; chat controller, lines 399–438 and 945–977; and dispatcher gate, lines 1248–1253.

Telegram follows this route:

  1. Store incoming text in the thread and create a chat owner turn.
  2. Queue the request with Telegram chat, message, and user metadata.
  3. QueueProcessor sends it to the orchestrator.
  4. ResponseRouter invokes a callback.
  5. Send the Telegram reply and mirror it as a chat agent turn.

See Telegram bridge, lines 98–160 and 192–260. The callback has a timeout and handles empty captured replies. Terminal capture remains an operational dependency. Source inspection does not establish Telegram parity with every Slack card or acceptance feature. Wingman needs explicit project/discovery thread identity and question routing above this transport.

Major capabilities beyond the stated Wingman product

Business and personal operations integrations. Crewly includes Google mail/calendar/docs/sheets/slides/drive, Microsoft To Do, Canva, remote MCP and Slack/WhatsApp/Google Chat in addition to Telegram. These make it a broader business-agent operating environment rather than only a software organization. Gmail sends are held as drafts with the agent's authorization claim captured at attempt time, persistent hold records and draft fingerprint/decision linkage (Gmail gate, lines 43–100; Google API client; remote MCP). Wingman could reuse connectors for research and delivery, but would inherit OAuth, permission, privacy and multi-channel identity management far outside its initial coding focus.

Cloud Apps as a deliverable surface. AppsService accepts bundles, publishes versions, rolls back and mediates app data through a Cloud client. Private/public visibility, owner public requests, open links and app comments/wakeups turn generated tools into running owner-facing deliverables (AppsService, lines 1–14, 23–103; app wake). This is materially beyond Wingman's described deliverable records. It could accelerate small internal tools, while binding hosting/data/publication behavior to a separate hosted platform whose server was not inspected.

Voice and mobile owner operation. Briefing/Drive services gather live decisions, unanswered questions and review-ready work, route spoken answers into the same decision/review/chat paths, and require a second token-confirmed call for sensitive answers. MobileApiRelay handles allowlisted REST over the Cloud message queue; board/canvas transport exposes remote live activity and control (briefing, lines 1–33, 75–133; mobile relay, lines 317–365; canvas, lines 43–110). This provides an additional human operating mode, not merely a responsive dashboard. It adds speech/session/privacy and Cloud availability dependencies.

Team transfer between machines. A source/target move protocol carries organization/project state and conversations, checks repositories/secret exposure, stages transfer, imports, stops/archives the source and supports rollback. It has a local journal and an external Cloud coordinator (driver, lines 1–29, 302–358, 405–456; controller, lines 1–12, 96–114). This could move Wingman execution capacity between Mac and Linux while preserving identity, but is relocation, not concurrent active-active execution of one member or automatic replication of every project record.

Outcome experiments and organizational learning. Experiment cards store hypotheses, baseline/observation windows, metric sources, predictions, trace roots and resulting verdicts; periodic processing can evaluate SEO/analytics or autopilot outcomes and write wiki results. Work is measured after delivery rather than only marked complete (experiments, lines 1–23, 75–117; verdict rules). The self-improvement tree also holds task timing, prediction calibration and consolidation. Wingman could use this for product feedback loops, but significance rules and measured metrics are domain-specific and do not establish causal product success.

Cost, account and resource operations. Per-agent model tiers, usage-ledger attribution, daily budget/spend caps, fallback runtimes/accounts, login monitoring and resource-pressure suspension manage long-lived teams. Defaults include a ten-agent cap and lower pressure cap; runtime fallback rebuilds model flags for the runtime actually used (settings, lines 365–393; launch fallback, lines 3950–3985; autopilot brakes, lines 9–25). These are valuable operating controls absent from Wingman's initial narrative. Silent changes of model/runtime must be made visible if Wingman promises specifically Codex agents.

Governed knowledge curation. Beyond basic project memory, wiki queues, schema-gated ingestion, backlink/search/history services, standing answers and curation/maintenance form a reusable knowledge system. An explicit deterministic queue-drain fallback files aged unclaimed evidence into vault logs without spending an LLM turn and leaves unschematized vaults for expiry/dead-letter handling (wiki drain, lines 1–27, 122–167). Wingman could preserve research and operating knowledge here, but should define which artifacts are authoritative scopes/specifications rather than equating all recalled knowledge with approved product direction.

Distinctive mechanisms and their limits

These are grounded mechanisms worth considering, without a claim of historical uniqueness.

  1. A repairable organization built on separate identity, conversation, work and claim records. Persistent member identity is independent of the runtime's transcript ID; active-work briefing reconstructs obligations before injecting memory. Claims/reconciliation repair process failures without pretending the original process survived. This enables standing teams with intermittent execution. Limits include runtime-dependent resume and multiple stores whose consistency is repaired asynchronously (identity, lines 35–45; active work, lines 1–28; reconciler, lines 340–392).
  2. Push delivery combined with pull claiming and stale-message filtering. Targeted WorkItems wake busy/live recipients through dispatch; idle claim logic picks subsequent tasks; direct handovers share dedup state; queued notices are refreshed/dropped when their work finished. This addresses “assigned but never actually seen” and delayed duplicate instructions. Several dedup guards are process-local, so it is not an exactly-once distributed execution guarantee (dispatch, lines 1–43, 151–210).
  3. Completion evidence and reviewer provenance. Local artifacts must exist and pass freshness/nonempty checks. Reviewer records identify the accepting party. Owner rejection adds acceptance criteria for later attempts. The mechanism cannot independently confirm a submitted passing-command claim or retrieve remote artifacts. Product acceptance still depends on a reviewer or owner. See evidence, lines 143–173 and 264–342; pool verdict, lines 2458–2515; and review, lines 495–515.
  4. Budgeted autonomy that wakes an accountable lead. Project autopilot uses deterministic eligibility/caps to request triage/replanning, while the agent performs judgment and readiness decisions. Goal metric references and retros make the loop inspectable. This avoids making a scheduling service the product manager, but also means the quality of autonomous product choices remains prompt/model dependent (autopilot, lines 1–34).
  5. Irreversible-action holds tied to the actual operation. Browser approval persists a specific held action and grants one retry pass after approval instead of blindly replaying a stale click. Mail stores a draft fingerprint and the authorization claim before the disputed action. These mechanisms support accountable human direction. They protect their instrumented surfaces, not every action an unrestricted shell can take (browser approval, lines 1–31; Gmail gate, lines 43–100).
  6. Human-editable tickets connected to process orchestration. Folder-locked Markdown tickets remain usable through git/manual edits while linking to leased execution WorkItems, traces, agents and acceptance. This is especially compatible with Wingman's inspectable shared-record philosophy. Local cache/lock behavior should not be mistaken for a cross-host database consistency protocol (ticket service, lines 1–20; workflow, lines 1–15, 879–959).

Practical fit and remaining build

Crewly can directly supply independent runtime execution, stable team/member identities, configurable member prompts/models/skills, project records, Markdown tickets, leased task execution, persistent chat rooms, active supervision and local operational UI. The Telegram bridge already supplies a usable human transport; worktrees, evidence gates, owner decisions and stop/pause controls are particularly reusable. It is substantially closer to a standing organization than a one-shot coding pipeline.

Wingman's organization can be configured as an orchestrator/Butler-facing entry layer plus portfolio coordination and separate project leadership teams, but the exact routing contract should be made explicit. Add per-project ProductMaster/TechMaster instances, project-linked discovery conversations and versioned scopes/specs/scenarios/DoD. Define when a new request starts a product, revises an existing one, needs research, asks the human, or is ready for technical decomposition. Do not rely on the generic keyword planner to carry that responsibility. Repair the default modular prompt propagation and role lookup so newly added profiles resolve their complete definitions consistently.

For the human environment, connect directory, project tickets, chat, traces and terminal workspaces through stable IDs. Extend board rows with explicit recent outcome and planned next work; persist per-agent summary events with task/chat/change/test/artifact references. Current board activity/step streams are a useful live foundation, but cannot substitute for that history. Provide Telegram parity for open decisions, acceptance and question replies instead of relying on Slack cards for core management.

Cross-device routing is more than a generic message envelope: MessageRouterService searches online heartbeat team/agent lists for a target session, sends an agent_message to that device, and installs a receiver that writes to the local session. The Cloud initializer wires that local delivery and the standard message queue (router, lines 167–248, 277–353; initializer, lines 34–94). This is real remote-agent addressing, while work ownership/persistence still belongs to each backend.

For Mac/Endeavour execution, choose Crewly Cloud or a self-hosted coordination service. Existing clients, device IDs, message envelopes, and team-transfer code provide useful examples. Local file-backed pools and the project registry need shared coordination, explicit placement, and access to required directives. A backend on each host would otherwise create two local organizations linked by messages. Verify recovery, duplicate delivery, host outages, and project access on real machines.

Finally, connect acceptance to the whole product lifecycle: independent functional tests and integrated scenario evidence, a product assessment against DoD, owner acceptance via Butler, and deliberate shutdown of active work/schedules after accepted delivery. Crewly's task evidence and ticket review provide mechanisms, but Wingman still needs the product-level policy and end-to-end verification.
