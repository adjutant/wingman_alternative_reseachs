amux assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/andyrewlee/amux

Local source: researchs/amux/repo. Inspected commit: ce8542b8a2764a14f6dbce2a3ce443f4ac0c5b21. Baseline: WINGMAN_PURPOSE.md.

Fit verdict: amux supplies a substantial local execution and inspection workbench for real coding-agent processes. Its strongest contribution to Wingman is the detailed agent workspace, durable worktree/session association, and a small agent-facing control protocol. It does not supply Wingman's standing organization, discovery process, shared ticket system, organizational chat, Telegram representative, or distributed execution control plane. Building the organization around amux would still require most of Wingman's coordination product.

This distinction should not obscure a useful finding: the current revision is more than a passive terminal grid. Hosted programs can discover siblings, deliver input to one exact session, report meaningful execution states, and wait for state or process outcomes. Those are real coordination primitives, though they are not an implemented organization workflow.

Architecture and execution model

The interactive application is Go with Bubble Tea and an embedded terminal emulator. main.go, lines 64–118, first dispatches private launch helpers and the headless status/agent verbs. The remaining invocation requires a real TTY and starts the TUI. This is not a web or mobile dashboard server. There is no supported headless workspace-creation API in this revision. The bounded verbs are --skill, agent ls, send, report, and wait.

A project is a registered existing Git repository path. AddProject validates both its path and Git identity before registering it. It does not infer a product from natural-language intake. A workspace is principally a branch/worktree and its persisted execution metadata. Creation resolves a base ref, validates names, creates or attaches a branch/worktree, waits for its Git metadata, saves the workspace, and rolls back on failure. See workspace_service.go, lines 23–180, and workspace.go, lines 27–93.

An assistant profile is a named shell command plus interrupt behavior. An agent instance is the running assistant command inside a tmux session, with an amux PTY client attached to it. AgentManager.CreateAgentWithConfig takes an immutable launch configuration, constructs the workspace environment, and launches the configured command. On command exit it resets terminal modes and drops to a login shell. Therefore a surviving pane is not proof that its coding agent is still executing. See agent.go, lines 25–46 and 168–236.

tmux is the process-lifetime and reconnect layer. command.go, lines 26–109, builds create-or-reattach commands, installs settings/tags and the status tap, and attaches without evicting other clients. The command and environment are transferred through a private launch payload rather than being exposed directly in process arguments. amux's terminal client can close while the server-side session continues. The native coding CLI owns the model/tool loop; amux owns shell launch, byte transport, terminal parsing/rendering, workspace association and observation. There is no central model planner dispatching work to these processes.

Durable state consists of the project registry, per-workspace JSON, environment/script registries, port reservations, and script transcript metadata. workspace.go, lines 39–107, shows exactly what survives: branch/base/repository/root, assistant name, scripts, environment, open-tab metadata, and lifecycle flags. It contains neither a task DAG nor an agent organization schema. workspace_store.go, lines 123–194 and 257–303, implements persisted metadata; registry.go, lines 44–73 and 159–230, implements project paths.

The Runtime field contains Docker and cloud-sandbox names. The implementation marks them as legacy/forward-compatible data. Actual execution uses local worktrees. No code selects an execution backend from this field. See workspace.go, lines 10–36. The names do not establish remote, container, or cloud execution.

Agent definition and lifecycle in detail

Definition and identity

The canonical built-in roster includes Claude, Codex, OpenCode, Droid, Cursor, Pi and other harnesses. agents.go, lines 8–36, defines the command and how many Ctrl-C signals to send. A custom profile needs a valid normalized name and command. It is not limited to those built-ins. AssistantConfig contains no system prompt, model policy, tools list, reporting manager, skills, project assignment, token budget or durable persona. Such behavior can be encoded into a wrapper command or the CLI's own configuration, but remains outside amux's agent model.

The workspace's persisted store key is stable even when symlinks or worktree existence change a path-derived identity. This matters because sessions, ports, lifecycle gates and metadata all join on that ID. Tab metadata records assistant/name/session/status/creation time. It does not record a universal native conversation ID. The meaningful durable object is a workspace and its associated terminal sessions, rather than a standing employee with an assignment history. See workspace.go, lines 39–47 and 111–158.

Creation, execution, routing and concurrency

The human creates a workspace through the TUI. The service selects or resolves a base and creates a worktree. It saves metadata and tracks branch ownership for rollback. Cleanup deletes a new branch only if that creation attempt owned it. See workspace_service.go, lines 85–180, and workspace.go, lines 37–106.

Agent creation snapshots the selected assistant configuration before asynchronous work, composes workspace environment and terminal settings, and attaches a real PTY to a named tmux session. This snapshot prevents a concurrent settings update from changing an in-flight launch. Agents have independent processes and can run concurrently, including multiple tabs of one assistant kind. The profile name is not their unique instance address. The exact session name is. Workspace-directed send refuses an ambiguous workspace with multiple sessions and returns candidates rather than guessing. agent.go, lines 158–215; cli_send.go, lines 153–197.

The creation path stamps workspace ID, tab ID, assistant, creation time, amux instance/owner and display labels as tmux tags. New interactive tabs generate an independent tab ID and derive amux-<workspaceID>-<tabID> from it; labels such as codex 1 are UI names rather than business identities. model_tabs.go, lines 22–49 and 112–185. Multiple agents inside the same workspace share its files and branch: independence means separate processes/conversations, not a separate worktree per agent. Independent branch isolation requires separate workspaces.

An optional launch-time “task” is a queued prompt string, not a tracked work item. The tab actor waits until the terminal has seen a private-mode sequence, then admits the prompt through the normal input FIFO with a carriage return. The input binding generation prevents a stale launch prompt being delivered to a replacement session. Only queue-full rejection re-arms the prompt; failed/replaced/missing bindings drop it. tab_actor_write.go, lines 46–61 and 139–147. Readiness here is a terminal-mode heuristic. An arbitrary custom assistant that never emits such modes cannot be assumed to receive a queued first task. This feature neither persists a task identity nor schedules later work.

The environment includes workspace identity and layered user settings. The separate run-script system provides setup/run/archive/on-done hooks and concurrent versus nonconcurrent policy. It is infrastructure for commands, not a task scheduler: nonconcurrent mode stops a previous run; concurrent mode permits overlaps. workspace.go, lines 49–57 and 261–281; lifecycle_coordinator.go, lines 111–205.

Tools and permissions

amux hosts the agent shell command with local filesystem/process access inherited from its environment. Coding tool permissions, model credentials and approval UX belong primarily to the hosted CLI. Worktrees isolate branches and working files, not operating-system authority.

Interactive sessions intentionally receive the inherited environment, injected amux variables, user-owned project environment and workspace overrides, but exclude repository-authored .amux/workspaces.json environment values even after script approval. This keeps script trust from silently widening what an agent process inherits. session_env.go, lines 7–32. The private pane-launch handoff uses an expiring payload in a 0700 attempt directory with a 0600 file, validates it and consumes it before the final shell command. This protects argv/tmux command surfaces, not same-user or privileged inspection of the running process. spec.go, lines 1–17 and 50–54; prepare.go, lines 85–113 and 125–147.

There is nevertheless an explicit amux security boundary around repository-supplied executable workspace configuration. Script trust is bound to a SHA-256 hash of reviewed .amux/workspaces.json bytes. A later config change invalidates approval. It does not hash every file the approved command might execute. script_trust.go, lines 23–68. Git operations additionally neutralize hostile repository execution hooks/drivers as documented in operations.go, around lines 448 onward. These protections do not sandbox the agent's own arbitrary tool calls.

tmux is a shared trust domain. Session tags and name checks are useful ownership hygiene, but same-server actors can forge tags and inject input. An external organizational controller using these primitives must treat the tmux socket as privileged infrastructure. ORCHESTRATION.md, “Trust boundary,” explicitly documents this limitation.

Continuity and resume

Detaching closes the amux PTY client and keeps the tmux session. Restoring saved tabs reattaches running sessions and preserves deliberately detached placeholders. Exiting amux intentionally does not kill server-side sessions: CleanupTmuxOnExit is a no-op. See model_tabs_session.go, lines 16–76 and 245–295; app_tmux.go, lines 98–100.

This is valuable continuity while the original CLI remains alive. It does not imply native conversation reconstruction after machine reboot, tmux loss or agent exit. Because agent exit drops the pane into a shell, amux cannot infer from pane existence alone that the original conversation still exists. Forking, compacting or resuming a native conversation may be possible by typing native CLI commands, but they are not modeled as consistent amux operations.

Persisted tab information contains assistant/name/session/status/creation time; stopped tabs are skipped on normal restore. Reattach and restart are distinct: reattach attempts to bind the existing session; restart is allowed for a nonrunning tab, kills the old session and creates a fresh client/command using a captured profile. If the kill fails, the ensure-session create shape may attach to the surviving old session and logs the discrepancy. Neither path replays an amux-owned conversation transcript into a model. model_tabs_actions.go, lines 227–261; model_tabs_session.go, lines 243–294; model_tabs_session_reattach.go, lines 44–130 and 133–255.

State, supervision, scheduling and completion

Without explicit reports, amux classifies activity from timing/output evidence into working, recently quiet done, then idle. The state machine is carefully separated from its signals, but its semantic limit remains: cessation of output is not product completion. agent_state.go, lines 39–132.

Cooperating programs can instead emit OSC 7501 reports with states idle, working, done, blocked, error, plus a message and blocked reason. The pipe-pane helper parses raw output, keeps a record per hierarchical ID, folds it into one headline, and writes pane options. A blocked child outranks a working root, helping surface attention needs in nested tools. New shell prompts and process exit clear transient working/blocked reports; done/error survive until cleared or the pane dies. tap.go, lines 20–122; records.go, lines 113–182.

The parser supports hierarchical IDs, titles, and percentage progress. It limits the record set to 64 entries. CLI report flags expose progress but no ID or title flag. statusTap.report publishes only state, ID, app, kind, message, and timestamp. It omits title and progress. agent ls emits state/source and session identity.

Records replace earlier snapshots by ID and fold into an urgency summary. They do not provide a durable nested-agent directory, task-progress graph, or timeline. See agentstatus.go, lines 29–67; cli_status.go, lines 54–83; tap.go, lines 54–68; and cli_agent.go, lines 80–92.

Reported state overrides heuristic state during scans. Multiple amux instances share a leased scanning owner and snapshots so followers avoid duplicate work and duplicate completion hooks. The lease has a seven-second TTL, epochs, heartbeat validation and stale-snapshot checks. It is not cross-machine agent supervision. See lease.go, lines 16–100; app_tmux_activity_result.go, lines 61–104 and 143–184.

An on-done script fires only for a working→done edge actually observed by the current scan owner. The baseline deliberately prevents first observation or ownership takeover from replaying an old completion. All eligible hooks are attempted even if one dispatch fails; completed edges are not retried. This favors avoiding duplicate side effects over a durable at-least-once business-event guarantee. It should not be used as the sole product-delivery ledger. app_tmux_activity_result.go, lines 220–250 and 292–332.

amux wait provides reactive supervision for an external script or agent. It can return on matching status, timeout, or a newly observed process exit, with tmux's real numeric exit status when available. It establishes an initial dead-process baseline so historical corpses do not look like fresh completion events. The implementation distinguishes transient scan failures from unusable tmux. These are useful lifecycle semantics, but no periodic agent is assigned to reason about project progress, wake stalled specialists or decide what work comes next. cli_status.go, lines 131–243 and 282–356.

Hosted run sessions retain dead panes and exit codes. An interactive coding command normally returns to its login shell. The coding CLI can therefore exit while the pane process remains alive. wait is not a universal native-agent exit-code API. It checks reports and liveness every 250 ms. Only a pane retained after process exit can supply the numeric exit result. See cli_status.go, lines 102–130 and 164–174; agent.go, lines 177–186; and run_session.go, lines 15–24 and 71–85. Searches found no durable cron-like schedule, goal budget, or timer-triggered reasoning loop. UI refresh, activity monitoring, and hooks do not decide organizational work.

Interruption, recovery and retirement

Interrupt uses profile-specific count and delay, bounded to five Ctrl-C signals and two seconds between signals. Closing an ordinary tab closes its PTY and asynchronously kills its tmux session; closing a borrowed run-session viewer merely detaches. Detach is consequently a separate operation with a materially different effect. agent.go, lines 359–402; model_tabs_actions.go, lines 25–103.

The internal Supervisor recovers and restarts Go background workers with policy/backoff, catches panics, and bounds shutdown waits. It must not be confused with retrying failed coding assignments: the source does not implement a task success/retry policy for hosted coding work. supervisor.go, lines 13–32, 113–143 and 197–279.

PTY recovery is similarly scoped: a stopped reader can restart with bounded backoff while its terminal remains alive; generation checks discard stale reader messages, and exhaustion marks the tab detached. This repairs observation/transport, not a failed model task or lost native conversation. model_input_lifecycle_pty_restart.go, lines 15–103. Product acceptance has no lifecycle state here: done, shell exit, script exit and Git merge are execution outcomes. A definition-of-done gate, successful integrated tests and explicit human acceptance would need records and policy above them.

Workspace deletion follows these steps:

  1. Acquire the lifecycle admission gate.
  2. Cancel and drain local setup and on-done processes.
  3. Stop run scripts and run the archive hook while the tree exists.
  4. Write a deletion tombstone.
  5. Remove the worktree, branch, and metadata.

The archive hook is best-effort. A deletion retry can run it again. Hosted agent-session cleanup has a separate order. Tests cover agent kills after successful tree removal and preservation when removal fails. Do not infer that every agent process stops before its tree disappears. See workspace_service.go, lines 267–345, and workspace_service_delete_kill_order_test.go, lines 16–58 and 133–226.

Tombstone recovery only completes an interrupted delete when the root is proven gone. A present or uncertain root is not blindly destroyed on startup. Shelving separately retains branch/metadata for restoration and is excluded from accidental-archive retention cleanup. These are workspace lifecycle features, not durable employee retirement or conversation archival. workspace_delete_tombstone.go, lines 110–189; workspace.go, lines 94–107.

Coordination mechanics: a concrete request path

The checked-in real-binary test sends the concrete request ping from amux send to a tagged cat pane and checks captured output. It also covers literal dash-leading input, dead destinations and ambiguous workspace selection (agent_cli_test.go, lines 79–124 and 136–198). The following traces that actual supported input operation through production code and explains how an endpoint-implementation request would use the same seam. These paths and the test were read, not executed during this assessment:

  1. The caller invokes amux agent ls --json. hostedAgentRows joins tagged sessions with reported/scan state and supplies workspace/session addresses. A project or business task is not inferred from the text. cli_agent.go, lines 79 onward.
  2. The caller selects an exact session and invokes amux send --session … --text … --enter. Argument validation requires one selector and one input mode; target resolution rejects ambiguity and dead panes. Literal text is sent separately from the carriage return after a 150 ms delay, reflecting real raw-mode input requirements. cli_send.go, lines 23–100 and 153–211.
  3. The native CLI handles the prompt and does the actual model/tool loop. amux transports terminal input/output. It does not decompose the endpoint task, create a ticket or track acceptance criteria.
  4. If the CLI or a wrapper emits blocked with a question, the tap stores/folds it and the next state read surfaces it even if output is otherwise active. A human can inspect the terminal and send an answer. There is no automatic product-manager escalation or durable question-to-ticket association. tap.go, lines 37–68; reported.go, lines 27–85.
  5. A cooperating external supervisor can use wait and inspect the outcome. An on-done hook may run a verifier or notification command. A human can review diffs and explicitly merge the workspace branch. Neither a reported done nor a merge automatically assesses the agreed product definition. cli_status.go, lines 131–243; merge.go, lines 122–211.

Two agents can therefore coordinate by discovering and prompting one another. The transport supplies no messaging acknowledgment beyond attempted terminal delivery, no exactly-once instruction semantics, no durable inbox, and no room history. A CLI might also be busy interpreting input differently. Wingman would need a proper message envelope, project/task association, conversation history and replay/deduplication policy above this seam.

The implementation's events are Bubble Tea messages, local process callbacks and tmux tags/options, with JSON files holding workspace state. These are distinct from tickets and collaboration records: a lifecycleTicket is a cancellable process-admission token, not a task assignment; hierarchical status IDs identify program reports, not durable team members. Dependencies consist of command ordering and lifecycle admission rather than a technical task DAG. Human decision handling is direct attention plus terminal input or hash-bound script trust. There is no source path routing a worker question to project leadership and back with a durable decision ID. lifecycle_coordinator.go, lines 43–85 and 108–175; cli_status.go, lines 54–99.

Major capabilities beyond Wingman's described product

A heterogeneous native-harness workbench. Wingman specifies separate Codex agents. amux intentionally hosts many different native coding CLIs and user-defined commands under one lifecycle/input framework (agents.go, lines 18–33; config.go, lines 218–250). This could let Wingman select different execution harnesses for specialized work without reimplementing each terminal interface. The consequence is that conversation IDs, permissions, context retention, usage and completion still differ by CLI; amux does not normalize those semantics into one agent API.

A branch/worktree operations product. Creating from explicit bases, attaching existing branches, reviewing diffs, merging with conflict handling, shelving/restoring and recovering interrupted deletes provide a substantial repository lifecycle around coding agents. Shelving persists both intent flags before removing the tree, keeps branch/metadata, and restores by attaching the retained branch. It does not fabricate a missing branch from the old base. workspace_service_shelve.go, lines 17–32, 96–157 and 161–165. Wingman describes product workspaces but does not prescribe this branch management machinery. It is useful for parallel isolated implementations, but multiple specialists in one worktree still share files, and an organizational integration queue would need to decide when branches are ready to combine. The merge function deliberately performs --no-ff into current HEAD, leaving verification of the intended base to its caller, and does not fetch, rebase, squash, autostash or push; conflicts remain available for resolution/abort (merge.go, lines 103–191).

A generic program-status and automation surface. OSC status is not limited to an AI harness. A test runner, nested worker, build or deployment command can report a blocked/error/done record and participate in wait and fleet visibility (tap.go, lines 71–121; cli_status.go, lines 47–99 and 131–174). This opens an automation substrate for mixed human, agent and ordinary-process workflows. Wingman could reuse the idea for execution workers, while maintaining a separate durable tracker of business outcomes.

Workspace environment/service lifecycle. Durable port allocation, layered environment, setup/run/archive hooks and script-output persistence support concurrent development servers and test commands alongside agents. Reservations are owned by stable workspace IDs and serialized across local processes, preventing common port collisions after restart. port_reservations.go, lines 31–74 and 174–257. The allocator is local metadata, not a multi-host service allocator or guarantee that another unrelated process cannot occupy a port.

Hosted run scripts are persistent, inspectable tmux sessions with retained exit status and optional simultaneous runs, separate from interactive agent tabs (run_session.go, lines 15–85 and 100–104). Diagnostic persistence retains only the latest setup/archive/on-done output per type, with a 64 KiB tail and finish/error fields. It is not an archive of every execution or a complete native-agent transcript (script_output.go, lines 12–23 and 55–87; script_transcript_store.go, lines 15–54). This is useful for Wingman worker provisioning and service diagnosis, but its acceptance evidence should be stored elsewhere before workspaces are retired.

Distinctive mechanisms and innovation assessment

Semantic status uses the existing terminal stream. Cooperating programs emit a small OSC vocabulary. A pipe-pane tap observes that stream even when the viewer detaches. Hierarchical record IDs can expose a blocked child while its parent remains active. Prompt/exit lifetimes limit obsolete working states. Noncooperating tools still require heuristics. The tap is best-effort and publishes only a folded headline. Records do not provide a durable timeline. See tap.go, lines 20–122, and records.go, lines 42–182.

Shared viewers use one scan owner. Several viewers can attach without evicting each other. A lease and epoch select the owner that publishes activity and fires completion hooks. Takeover republishes current state without inventing a completion transition. This separates observation ownership from execution ownership. It is not distributed consensus or a durable job queue. tmux options lack atomic compare-and-swap. Leases need validation. Missed completion transitions have no replay. See command.go, lines 55–77; lease.go, lines 16–100; and app_tmux_activity_result.go, lines 61–104 and 213–250.

Third, workspace lifetime is treated as a recoverable transaction around real processes and files, rather than a UI delete flag. Stable IDs survive path changes; lifecycle generations prevent stale admitted work from starting after teardown; tombstones record partially completed deletion; rollback distinguishes newly owned branches from existing branches. These details are valuable to Wingman because organization-level agents will eventually hit partial host/process/storage failures. Their innovation is an implementation discipline at the local workbench boundary, not evidence of autonomous product management. workspace.go, lines 111–158; lifecycle_coordinator.go, lines 111–205 and 328–349; workspace_delete_tombstone.go, lines 110–189.

Launch intent uses a captured configuration and generation checks. Dispatch copies the launch settings and binds the initial prompt to an exact input target. Generation checks stop stale reader or reattach results from replacing a newer stream. A later settings edit or slow attach cannot silently redirect admitted work. These controls provide process/UI consistency. They do not provide durable task delivery. A dropped prompt still lacks a business task record for reconciliation. See model_tabs.go, lines 95–155; tab_actor_write.go, lines 46–61; and model_input_lifecycle_pty_restart.go, lines 19–29 and 79–101.

These are distinctive mechanisms in this source. No historical-first or industry-wide uniqueness claim is established by this assessment.

Practical use for Wingman

amux could be used directly as an operator-facing local workstation for agents and development services. Its profile launchers, worktree handling, terminal inspection, detach/reattach, exact input selection, and explicit program status are useful components.

For integration, Wingman would need a durable mapping between its agent identity and amux workspace/session/native conversation; wrappers that report real task states; and a controller that reconciles session death, human steering and task ownership. The supported CLI cannot create/shelve/delete workspaces, so either the organization must provision them independently or amux would need an intentionally supported lifecycle API. Encoding organization actions as raw TUI keystrokes would make lifecycle guarantees harder to maintain.

The cleanest boundary is therefore an optional execution/viewing adapter beneath Wingman's control plane. Wingman should own stable agent/profile/project/task/conversation IDs, the durable inbox and decisions, task retry policy and acceptance records. An amux adapter should own the mapping to each host's exact tagged session. Before send, the adapter would reconcile the expected native harness and live session, because a living fallback shell can otherwise receive a prompt intended for a coding agent. Reported status can raise attention but should update durable tracker state only with a task ID and outcome evidence. A Mac/Endeavour deployment would need separate host adapters and an authenticated cross-host coordination service; sharing one local tmux server or copying JSON files does not supply that behavior. These are proposed integration responsibilities, not features found in amux.

Wingman still needs these product capabilities:

  • Telegram Butler and cross-project routing.
  • A product registry beyond Git paths.
  • ProductMaster/TechMaster workflows and proportionate discovery.
  • Scope, specifications, and acceptance records.
  • Shared tickets and dependencies.
  • Durable rooms, escalation, and proactive coordination.
  • Host placement and recovery.
  • Connected executive summaries and timelines.

amux can provide detailed terminal inspection. Its status model cannot replace these organizational records.

Verification scope and confidence

This was a static source assessment of the pinned local checkout. No dependencies were installed, no service or real agent was launched, and no tests were executed. Runtime correctness, harness compatibility on this host, timing behavior and multi-instance races have therefore not been empirically established here.

The implementation review covered these areas:

  • Public command dispatch and custom assistant configuration.
  • Agent creation, environment, interruption, and tmux creation/attachment/tapping.
  • Tab close, detach, restore, project registry, and workspace storage.
  • Worktree creation/deletion, tombstones, and lifecycle admission.
  • Status parsing, record folding/merging, scan-owner leases, and completion hooks.
  • Wait/send target resolution, durable ports, script trust, background supervision, and merge entry points.

The review compared these paths with STORAGE.md and ORCHESTRATION.md.

Relevant test code inspected includes agent_cli_test.go, lines 28–170, exercising real-binary fleet discovery, reported-state precedence, literal send, carriage return and dead/ambiguous targets; status_protocol_test.go, starting line 19, covering the status protocol against real tmux; and workspace_service_delete_kill_order_test.go, starting lines 16, 95, 133 and 197, documenting deletion ordering/failure boundaries. These tests are evidence of intended coverage, not passing test results from this assessment.

Additional test-source checks covered records_test.go, lines 14–129 (replace/clear, priority fold, lifetime and eviction); model_tabs_launch_config_test.go, lines 86–160 (captured configuration across fresh launch, restore, reattach and restart); and on_done_completion_test.go, lines 92–163 (single-owner hook reaping, nonzero-exit notification and teardown drain). No claim that these tests passed is made.

Negative findings were checked beyond README silence: searches over non-test Go implementation in cmd/ and internal/ for Telegram/Butler, ticket/product leadership, chat rooms, acceptance/definition-of-done, remote-host/SSH execution and scheduling concepts; examination of the complete workspace/profile schemas and main dispatch; and the explicit local-only runtime contract. “Ticket” matches in the lifecycle coordinator refer to in-process admission tokens, not work tickets. Generic UI scheduling and internal goroutine supervision do not implement organizational wake cycles. Native CLI capabilities and user-authored shell wrappers may supply behavior outside this repository, but they are not credited as amux's implemented product features.
