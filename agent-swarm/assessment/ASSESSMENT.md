# Agent Swarm assessment against Wingman

## Identity, revision and verdict

- **Product:** Agent Swarm, Desplega Labs' self-hosted agent company/work orchestration platform. This is not the unrelated OpenAI Swarm library.
- **Repository:** https://github.com/desplega-ai/agent-swarm
- **Local checkout:** `researchs/agent-swarm/repo/`
- **Assessed commit:** `6aff700f53755cb71bd6a1aa2e2fa1da9586b892`.
- **Assessment date:** 2026-11-05.
- **Method:** static source assessment of this checkout; no installation, server, containers, model calls or external integrations were run. Implementation findings below are source-established, not observed deployment outcomes.

**Verdict:** Agent Swarm provides a strong foundation for Wingman's ongoing agent operations. Independent coding workers have durable identities and configurable templates. Shared tasks, internal chat, Telegram, supervision, remote controllers, and human questions support coordination. Session views expose detailed execution records.

Its organization centers on **one lead plus workers**, repositories, task trees, and workflow runs. Wingman needs a product portfolio and separate product and technical leaders for each project. Proportionate discovery and authoritative scope, specification, and acceptance records need explicit workflows. Accepted delivery must stop active product development.

The executive home shows task activity by agent. It does not provide the required plain-language account of recent results, current work, next work, and blockers. Native conversation resume is deprecated. Fresh sessions reconstruct continuity from bounded task ancestry and persistent records.

Evidence links are relative to this report; cited line numbers refer to the assessed revision. Wingman reference: [purpose](../../WINGMAN_PURPOSE.md), especially §§2–7 and §§9–14. Assessment rubric: [guide](../../generic/assessments/ASSESSMENT_GUIDE.md).

## Architecture and actual execution model

The API entry [src/http.ts](../repo/src/http.ts), lines 1–4, installs logging/internal-AI support and imports `http/index`. The latter creates the HTTP server, registers routes and starts integrations, workflows, scheduler, heartbeat and runtime supervisor; see [http/index.ts](../repo/src/http/index.ts), lines 626–748 and 783–891. [server.ts](../repo/src/server.ts) registers the MCP surface. HTTP and MCP are different interfaces to the same server-owned state, rather than separate trackers.

The storage core is SQLite, with migrations and an async DB client. [db/runtime.ts](../repo/src/be/db/runtime.ts), lines 73–136 and 334–359, opens the database, enables WAL and a 5-second busy timeout, and exposes the client. Repository architecture rules explicitly forbid worker imports of SQLite/server DB code: [AGENTS.md](../repo/AGENTS.md), lines 7–27. Workers call HTTP using identity headers and tokens. This allows a worker on another machine to use the same coordination service without sharing the SQLite file. This central API remains an operational dependency. The presence of remote workers does not imply distributed consensus or active-active API availability.

A long-lived worker runner is distinct from a model session. [commands/worker.ts](../repo/src/commands/worker.ts), lines 1–14, passes worker configuration to `runAgent`. [commands/runner.ts](../repo/src/commands/runner.ts), lines 5856–6191, resolves identity/configuration, chooses a provider adapter, establishes concurrency and registers a runtime. Its delivery loop, lines 7116–7738, services completions, config changes, cancellation and triggers, then starts provider sessions. Multiple specialists therefore execute separately. A template alone is only instructions until a runner/runtime is launched.

Provider sessions normalize actual harness behavior into message, tool, result, context and compaction events. The contract in [providers/types.ts](../repo/src/providers/types.ts), lines 91–206 and 265–284, separates an executing session (`waitForCompletion`, `abort`, optional steering) from the adapter and its capability traits. For a concrete coding path, [codex-adapter.ts](../repo/src/providers/codex-adapter.ts), lines 2510–2528, creates either an in-process Codex session or, normally, a `CodexSubprocessSession`, and explicitly refuses native resume. The runner invokes adapter creation around lines 4487–4522, captures/logs events around lines 4614–5011, and settles provider results around lines 5442–5630. This is real coding-harness execution, not a chat-only simulation.

Infrastructure and harness are independent choices. Runtime pools provision Docker/E2B/boxd resources or use static operator-managed workers; remote controllers can execute infrastructure commands from another host. Providers choose the coding harness inside those resources. Confusing those two axes would overstate either model portability or machine portability.

## Agent definition and complete lifecycle

### Definition, templates and identity

The durable `Agent` is a database entity, not a single indefinitely running model conversation. The [schema](../repo/src/types.ts), lines 1307–1390, stores ID, name, lead status, free role, capability tags, provider, credential state, capacity and timestamps. `soulMd` holds behavior/persona, `identityMd` expertise/style, `claudeMd` working instructions, `toolsMd` operational context, `heartbeatMd` standing orders, and `setupScript` environment setup. A default role can be specialized with both persona and operational instructions. A field named capabilities is a declaration used in routing, not evidence that the agent actually possesses or reliably exercises the skill.

Templates bundle defaults and files. [lead/config.json](../repo/templates/official/lead/config.json), lines 11–25, assigns coordination capabilities and capacity two. [coder/config.json](../repo/templates/official/coder/config.json), lines 11–27, assigns implementation/testing capabilities and capacity three. [tester/config.json](../repo/templates/official/tester/config.json), lines 11–26, defines QA, browser, and end-to-end testing specialization. These profiles do not define a product-leadership hierarchy. Instances can share a template while retaining separate agent IDs and histories.

Self-edited identity files persist through [profile-sync.ts](../repo/src/commands/profile-sync.ts), lines 1–80 and 387–409. The file includes baselines and conflict/rejection handling. The API profile handler records budget rejection, conflict and reconciliation events in [http/agents.ts](../repo/src/http/agents.ts), lines 975–1120. This is more than rereading a static persona prompt each launch. It also introduces mutable identity as operational state: Wingman would need to distinguish agent-owned notes from human-approved product directives.

### Creation and activation

There are several different creation paths:

1. `join-swarm` creates a durable row for an existing MCP caller, checks ID/name and lead uniqueness, generates default identity content and updates the profile: [join-swarm.ts](../repo/src/tools/join-swarm.ts), lines 88–161. **It does not itself spawn a worker.**
2. A worker registers/re-registers through `POST /api/agents`. Existing identity is retained. A new registration creates the row and records the process runtime: [http/agents.ts](../repo/src/http/agents.ts), lines 670–795. A missing per-process runtime ID is rejected when multi-runtime mode is enabled. In that mode a restarting process cannot overwrite the logical agent's capacity policy with its own reported slots.
3. A pool can create an initially offline logical agent, store a `TEMPLATE_ID`, and bind it to a pool: [runtime-pools/db.ts](../repo/src/be/runtime-pools/db.ts), lines 531–565. The supervisor later provisions capacity for demand. This separates organization membership from infrastructure availability.
4. Operator-managed Compose/static workers can start independently and register to the same API. The entrypoint initializes workspace/personal folders, repos, MCP configuration and startup scripts: [docker-entrypoint.sh](../repo/docker-entrypoint.sh), lines 472–479, 571–622, 798–870 and 875–955.

The runner reads logical `AGENT_ID` while generating a new runtime instance ID per process boot ([runner.ts](../repo/src/commands/runner.ts), lines 5874 and 6179–6188). Provider session IDs and task IDs are additional identities. A logical agent may survive many worker restarts and provider sessions, and can be served by several runtimes. Treating each runtime as a different permanent specialist would misrepresent the system.

### Assignment, routing, concurrency and execution

`send-task` accepts direct assignments or offers, a capability/lead authorization constraint, priority, repo, `parentTaskId`, `dependsOn`, follow-up instructions and output schema. It requires a reason/note for explicitly choosing an agent. Parent attachment and requester propagation are checked rather than blindly trusting all caller-supplied context: [send-task.ts](../repo/src/tools/send-task.ts), lines 318–420, 482–554 and 656–745. Parent lineage and dependency ordering have different meanings: a child can inherit conversational context without needing to wait for every sibling. A dependency expresses readiness.

All task writes converge on `createTaskExtended`, which validates the options and chooses draft/offered/pending/backlog/unassigned state: [db.ts](../repo/src/be/db.ts), lines 2505–2565. The poll path does transactional capacity and readiness work; offers, assigned work, mentions and eligible pooled tasks are separate trigger types: [http/poll.ts](../repo/src/http/poll.ts), lines 319–414, 520–548 and 548–656. The atomic pool claim is an `UPDATE ... WHERE status='unassigned' RETURNING *`, preventing two claimants from winning the same row ([db.ts](../repo/src/be/db.ts), lines 3107–3159). This is claim atomicity, not a claim that a task's external side effects execute exactly once after crashes.

Capacity has two boundaries: the durable logical agent's `maxTasks`, and the process's available sessions/slots. Multi-runtime registration records process slots without redefining the policy; poll claims check policy atomically. [runtime-pools/demand.ts](../repo/src/be/runtime-pools/demand.ts), lines 5–64, computes ready demand and desired runtimes against slot and pool limits. Local runner capacity independently controls how many sessions start. Two tasks on one logical agent may still use the same repo clone; [runner.ts](../repo/src/commands/runner.ts), lines 289–368, explicitly discusses preserving dirty state when siblings run concurrently. There is no basis to claim automatic per-task worktree isolation from that code.

The runner obtains resolved config, repo/workspace context, provider credentials, prompts and model selection, then creates a harness session. Claim-time model resolution is authoritative. A spawn guard rejects a model from the wrong harness family ([runner.ts](../repo/src/commands/runner.ts), lines 4320–4366). This is suitable for actual Codex specialist work. The common event abstraction also allows heterogeneous harnesses without pretending every provider supports every control.

### Shipped research, planning and implementation practices

These are implemented as seeded reusable skill content, not only hypothetical custom prompts. [seed-skills/index.ts](../repo/src/be/seed-skills/index.ts), lines 117–122, 155–172 and 365–378, imports and registers researching/planning/implementing. Each corresponding `config.json` marks it `systemDefault: true`. [planning/content.md](../repo/templates/skills/planning/content.md), lines 3–13 and 36–48, prescribes iterative human clarification, design-option review, concrete phase deliverables, automated verification/QA and smaller one-shot plans when appropriate. Its [artifact template](../repo/templates/skills/planning/files/template.md), lines 14–20 and 49–73, supplies desired end state, explicit exclusions, success criteria and verification scenarios.

[researching/content.md](../repo/templates/skills/researching/content.md), lines 24–42 and 54–95, coordinates source-backed technical research. Its stated scope is documenting existing code. It limits unrequested critique and web research. [implementing/content.md](../repo/templates/skills/implementing/content.md), lines 119–154 and 176–182, connects approved plans to implementation phases. It prescribes specification/code review, automated checks, and user confirmation of manual verification.

These procedures support technical discovery, definition, and verification. They do not enforce deterministic gates or complete market/domain discovery. They also do not establish product acceptance. Some procedures reference `AskUserQuestion`, Claude Code sessions, background subagents, and external `desplega:*` skills. Check those dependencies for Codex workers and Telegram clarification. The assessment read these files as source artifacts. It did not invoke their instructions.

### Tools and permission boundaries

Tools include task operations, messaging, memory, profiles, skills, repo policy, schedules, workflows, scripts, app/page artifacts, approvals and integrations. Role-based server authorization, scoped session/runtime tokens and resource ownership govern API operations; see [rbac/legacy-policy.ts](../repo/src/rbac/legacy-policy.ts), lines 30–85 and 114–193, and [http/sessions.ts](../repo/src/http/sessions.ts), lines 215–352. Those controls protect coordination actions. They are separate from permissions inside the coding container.

Codex's harness config explicitly sets `approval_policy: never` and `sandbox_mode: danger-full-access`, while disabling account apps/connectors: [codex-adapter.ts](../repo/src/providers/codex-adapter.ts), lines 593–611. Claude's CLI uses permission-bypass arguments in [claude-adapter.ts](../repo/src/providers/claude-adapter.ts), lines 1055–1059. Thus the intended trust boundary is largely the worker environment, credentials and API permissions, not per-command human approval. Wingman should preserve container/host separation when adapting this to the Mac and Endeavour; substituting an unrestricted host worker changes the practical boundary.

### Persistence and resume

Task state, logs, session costs/context, approvals, identity, memory and source/thread keys survive in server storage. Repo clones and personal files survive only according to configured volumes/drives. Persistent API state should not be confused with guaranteed persistence of every runtime filesystem.

Native resume is explicitly removed across adapters. [resume-session.ts](../repo/src/commands/resume-session.ts), lines 1–16 and 57–77, returns skipped candidates; [codex-adapter.ts](../repo/src/providers/codex-adapter.ts), lines 2525–2528, returns false for resume capability. A fresh session receives [context-preamble.ts](../repo/src/commands/context-preamble.ts), lines 31–48 and 136–196: typically a roughly 2,000-token text budget, up to five ancestors, immediate parent subject/output/artifact pointers and older pointer summaries. Resume-task preambles have a larger default budget and use recent session logs. Full records remain retrievable, but the worker must choose to consult them. Some tool descriptions still mention resuming a parent's Claude session. The current implementation takes precedence over that stale wording.

Dashboard “sessions” are also not one native provider session. `GET /api/sessions/{rootTaskId}` groups a root task and descendants, with steering/citations/approvals added to the chain: [http/sessions.ts](../repo/src/http/sessions.ts), lines 785–807 and 1213–1228. This produces continuing human work threads over fresh model sessions, a useful but materially different continuity model from Wingman's requested individual conversation lifecycle controls.

### Scheduling and supervision

The scheduler polls due cron/interval/one-time schedules, claims occurrences and recovers missed work: [scheduler.ts](../repo/src/scheduler/scheduler.ts), lines 350–441 and 557–609. It can drive tasks/workflows rather than keeping a model waiting in a sleep loop.

Heartbeat has two layers. Code-level triage defaults to a 90-second interval. It uses separate thresholds for a missing session, a stale session heartbeat, and absent task progress. Recovery defaults to a three-generation limit. See [heartbeat.ts](../repo/src/heartbeat/heartbeat.ts), lines 118–162 and 448–503.

The lead's editable checklist creates separate supervision tasks, normally every 30 minutes. It removes duplicate open checklists. An optional gate script can suppress quiet ticks. See the same file, lines 219–239 and 1796–1862. The official checklist asks the lead to investigate stranded work and idle capacity. The model and its instructions determine the follow-up decisions.

`defer-task` finishes the current task and books a future child. It can wake early on all/any watched task outcomes while retaining a time ceiling: [defer-task.ts](../repo/src/tools/defer-task.ts), lines 162–215. “Completed” can therefore mean the present execution yielded with future work scheduled, not product delivery. Wingman rollups would have to follow continuation chains rather than count every completed row as an accepted deliverable.

### Interruption, steering and shutdown

Steering is durable and acknowledged with delivery/handling status. The runner dispatches through optional provider capabilities and preserves pending input where a successor must receive it: [runner.ts](../repo/src/commands/runner.ts), lines 609–746. Codex implements native turn interruption/steering in [codex-adapter.ts](../repo/src/providers/codex-adapter.ts), lines 1120–1166. Unsupported providers can report an undeliverable outcome rather than fabricate delivery.

Cancellation changes server task state and the runner requests session abortion, with a settlement grace period so a stuck adapter does not hold a slot indefinitely: [runner.ts](../repo/src/commands/runner.ts), lines 5350–5415. It is not a rollback of commands or external effects already performed. Supersede is a distinct path that terminates old work logically and creates a fresh continuation; workflow-owned tasks instead defer to engine retry policy ([http/tasks.ts](../repo/src/http/tasks.ts), lines 740–756).

Pause/resume buttons exist, but the persistent primitives merely change `in_progress`↔`paused`: [tasks/write.ts](../repo/src/be/db/tasks/write.ts), lines 1003–1088. The runner reconciliation snippet aborts cancelled/terminal tasks, not every paused status. This assessment therefore does not equate the UI pause label with a universal live process freeze. Native fork, archive and manually requested compaction were not established from the task/session API inventory. Compaction event reporting is present; reporting it is not equivalent to an operator command that all adapters can perform.

### Failure, retry and recovery

The heartbeat compares stale work with active session liveness. A worker that reported fresh progress after the sweep read its candidates wins against a stale remediation decision. See compare-and-swap handling in [heartbeat.ts](../repo/src/heartbeat/heartbeat.ts), lines 764–825, and the targeted test discussed below. A crash between supersede and replacement creation is repaired by `repairSupersededWithoutResume`, lines 658–698. Reboot sweep reconciles tasks against the current API boot and sessions instead of assuming every old session is dead (lines 894–1004).

[worker-follow-up.ts](../repo/src/tasks/worker-follow-up.ts), lines 474–662, creates continuation tasks, preserves requester/context/model/routing metadata and prefers eligible original identities for selected recovery reasons. Lead-only authorization survives recovery. A resume pinned to a worker that never reclaims it can become lead rerouting work instead of silently remaining queued (lines 689–779). Workflow tasks are carved out so engine retries do not compete with generic worker retries.

Infrastructure failure has its own recovery loop. [runtime-pools/supervisor.ts](../repo/src/be/runtime-pools/supervisor.ts), lines 96–180, records provisioning errors, increments attempts, backs off, opens pool circuits and eventually fails ready pending tasks with lead follow-up. Remote controller disconnection causes liveness/reconnect behavior rather than local fake execution. These mechanisms improve continuity, but cannot guarantee application-level idempotency of a partially completed deploy, PR action or external write.

### Completion, acceptance, retirement and cleanup

Workers can report progress, finish with an output/failure and optionally attach a reusable learning. `store-progress` checks ownership, idempotent terminal transitions, schema output and citations: [store-progress.ts](../repo/src/tools/store-progress.ts), lines 503–587 and 679–703. The runner has a fallback when a provider exits without completing the task, including structured-output handling ([runner.ts](../repo/src/commands/runner.ts), lines 1605–1637 and 1853–1999). Consequently a successful process exit can produce a completed task without constituting independent product acceptance.

[task-terminal-effects.ts](../repo/src/tasks/task-terminal-effects.ts), lines 27–108 and 155–174, writes completion/failure memory and creates lead follow-up for ordinary tasks; failures in those secondary effects do not undo the terminal task. The official lead template requires repo policy, CI success and human review before merge. Those are instructions and PR policy artifacts, not a universal transactional acceptance gate over arbitrary shell commands. No product-level “accepted; stop development/testing until a new request” state was established.

Logical retirement and infrastructure cleanup differ. Runtime termination/token revocation, idle pool teardown and cache release are supervisor lifecycle concerns; static pools are explicitly operator-managed ([static.ts](../repo/src/runtime-providers/static.ts), lines 4–16). An internal [deleteAgent](../repo/src/be/db/agents.ts), lines 507–522, logs departure and deletes the row, but a complete user-facing retire/archive-product workflow was not found. Wingman would need an explicit retirement policy connecting queued work, conversations, artifact retention and runtime placement rather than deleting an ID alone.

## Coordination mechanics and one end-to-end source trace

The following is a concrete implemented Telegram request path, not a claim to have exercised a live Telegram bot or watched the models complete a product.

1. **Ingress and identity.** `loadAdapter('telegram')` constructs an adapter with verified webhooks and explicit bot-reply recognition ([adapters.ts](../repo/src/integrations/chat-sdk/adapters.ts), lines 67–101). `handleChatInbound` classifies DM/mention/reply/requester follow-up, ignores unrelated group chatter and emits an incoming event ([inbound.ts](../repo/src/integrations/chat-sdk/inbound.ts), lines 118–154). Sender identity is resolved rather than inheriting a previous requester's attribution blindly.
2. **Active steering or buffered intake.** If the thread has a suitable active task, the text can become steering with durable acknowledgment (lines 155–201). Otherwise the input is buffered with attachments and message facts; `!now` requests immediate flush (lines 204–226). This preserves short consecutive human messages as one ask without inventing a task for every fragment.
3. **Route to a real recipient.** [router.ts](../repo/src/integrations/chat-sdk/router.ts), lines 124–201, checks explicit `swarm#<id>`/broadcast, stored channel agent/workflow mapping, reachable thread owner, and lead fallback. Telegram groups expire stale ownership after a configurable default 15-minute window; DMs keep continuing ownership. This is channel/thread continuity, not semantic selection of an existing software product.
4. **Create durable contextual work.** Flush builds `source='chat'`, `taskType='chat-inbound'`, priority 70, a chat context key, requester, message anchor, optional dependency on the latest active task and parent linkage to recent work ([inbound.ts](../repo/src/integrations/chat-sdk/inbound.ts), lines 565–620). Attachments are stored with the task, and a source label is remembered for dashboard grouping.
5. **Claim and run.** The selected runner polls or receives a work nudge, the API atomically reserves eligible work/capacity, and the runner builds a provider session with identity, tool configuration, repo context and preamble. If the recipient is the lead, decomposition into coder/tester/reviewer tasks is a model decision using `send-task`, with a recorded task tree and dependencies. The platform does not deterministically materialize a ProductMaster/TechMaster team just because the incoming message names a new product.
6. **Collaborate and clarify.** Agents post/read internal channel messages and threaded replies; mentions nudge recipients. Ordinary chat is not always a ticket: [db.ts](../repo/src/be/db.ts), lines 4068–4165, creates tasks only for the explicit `/task` prefix with target mentions. A lead/worker can ask the human a conversational question through `chat-reply`; formal questions use a persistent approval request and shareable response URL. Answers generate later follow-up tasks, so waiting for a human need not consume a running model session.
7. **Report and supervise.** The worker writes progress and output; completion memory and lead follow-up run, unless workflow ownership or explicit configuration changes that behavior. The lead's completion follow-up includes the output/failure and cascade impact ([worker-follow-up.ts](../repo/src/tasks/worker-follow-up.ts), lines 269–418). Heartbeat detects silent failures independently of the worker remembering to complain.
8. **Return to the human.** [relay.ts](../repo/src/integrations/chat-sdk/relay.ts), lines 42–92, formats terminal output/failure with a task tag; lines 102–217 process persisted pending relay obligations, retry with backoff and send output attachments. A terminal event causes an early relay tick (lines 220 onward). The human can follow the task/session links into the same state shown on the dashboard. Relay retry is bounded, so “eventually sent forever regardless of platform availability” is not guaranteed.

Internal shared state comprises agent/task rows, dependency edges, channel messages/read cursors, scoped KV, memory, repo policy, workflow runs/steps and approval requests. Workflow events link these components, but a process-local event bus is not by itself durable; persisted task/run/relay/wait state and recovery scans provide the recovery paths. Wingman should carry project identity explicitly through those records rather than rely solely on a chat context key or repo string to imply product ownership.

## Substantial capabilities beyond Wingman's described scope

### Heterogeneous harnesses and portable execution intent

The provider contract normalizes messages, tools, results, context and steering while exposing traits instead of assuming parity. Portable model tiers are resolved at claim time with task pins, config, worker overrides and defaults: [model-tier-resolution.ts](../repo/src/be/model-tier-resolution.ts), lines 1–25, 318–338 and 352–396. This enables a planner to ask for a capability/cost tier without embedding a concrete vendor model into every task. Wingman is specified around Codex, so other providers are optional; adopting them adds testing/auth/context differences, and “regular” across providers does not establish equal quality.

### Durable DAG workflows, structured results and human gates

Workflow steps can be agent tasks, scripts, reusable swarm scripts, waits, foreach, validation, notifications, VCS work and human input; see [executors/index.ts](../repo/src/workflows/executors/index.ts). The engine hydrates completed outputs, persists step state and handles retry/validation routing ([engine.ts](../repo/src/workflows/engine.ts), lines 490–504, 613–641, 1096–1228). Human gates allow explicit approvers and timeout rejection. This is useful for repeatable delivery pipelines beyond informal leadership conversations. It adds a second owner of task progression: generic recovery must defer to engine-owned work, and workflow authors must map upstream outputs explicitly rather than assume every prior result is in scope.

### Agent-authored scripts and programmable policy extensions

Reusable TypeScript scripts are stored/versioned and typechecked; [script-upsert.ts](../repo/src/tools/script-upsert.ts), lines 23–41, exposes source, scope, filesystem mode and executor selection. Native execution runs a child process with configured resource/time/output limits, stdin-delivered configuration and process-group teardown: [native.ts](../repo/src/scripts-runtime/executors/native.ts), lines 190–196 and 245–318. QuickJS is a separate executor. Per-run tokens can bind SDK operations to the invoking agent and are revoked in `finally`: [run-credential.ts](../repo/src/be/scripts/run-credential.ts), lines 24–65. Sentinel/system callers can fall back to operator credentials. This is not a uniform least-privilege guarantee.

Extensions can intercept task creation/routing/steering/remediation and observe post events. [dispatcher.ts](../repo/src/extensions/dispatcher.ts), lines 60–80, 291–321 and 382–496, authenticates bridge origin, applies timeouts and guards against pre-hooks inside DB transactions. This is a practical location for Wingman project routing/authorization rules. Extensions are trusted executable policy, not harmless prompt text; activation, failures, recursion avoidance and policy audit become integration responsibilities.

The extension API permits agent-owned catalog drafts. It separately guards inline installation and activation. Worker edits do not silently replace live code. See [http/extensions.ts](../repo/src/http/extensions.ts), lines 92–114 and 493–519.

[extensions/lifecycle.ts](../repo/src/extensions/lifecycle.ts), lines 125–223, loads hooks under an extension identity. It enables declared assets only after loading succeeds. Disable unloads and deactivates the extension. Version changes reconcile assets transactionally and support rollback restoration. Installation validates and plans assets before the transaction. It creates the identity, rows, and disabled assets together (lines 261–285). Uninstall removes pristine assets and detaches user-edited assets (lines 288–294). Startup reloads enabled records. Shutdown removes registrations and temporary material (lines 371–406).

These controls support reviewable policy packages and controlled rollout. `ext:<name>` identifies an API/system principal. It is not a coding worker. Loaded extensions have API-process privileges. Draft ownership and versioning do not provide an untrusted-code sandbox.

### Searchable institutional memory with retrieval feedback

Memory retrieval combines SQLite full-text search and vector candidates through reciprocal-rank fusion. It also uses reranking and graph-neighbor expansion. See [sqlite-store.ts](../repo/src/be/memory/providers/sqlite-store.ts), lines 135–168 and 619–747. [graph-expansion.ts](../repo/src/be/memory/graph-expansion.ts), lines 46–80 and 155–170, checks visibility. It caps graph scores relative to seed memories. [search-candidates.ts](../repo/src/be/memory/search-candidates.ts), lines 1–46, widens retrieval until chunk collapse yields enough distinct documents. The limit is 4,096 candidates. Completion, citation, and rating records retain links to prior work.

This can improve specialist continuity and retrieve mistakes/decisions across sessions. It requires embedding/retrieval configuration and retention rules, and it is probabilistic recall rather than authoritative product specification storage. Wingman should keep accepted scopes/decisions directly addressable even when memory retrieval misses them.

### Demand-driven runtimes and cross-host infrastructure controllers

The remote controller separates infrastructure credentials/location from central orchestration, with typed provision/status/terminate/renew/pause/resume operations and liveness reconnects. Pools compute demand, apply provisioning backoff/circuit behavior and manage owner-labeled resources. This goes beyond merely running fixed specialists on two machines, enabling elastic capacity. Docker's adapter supports local Unix sockets, so a remote machine uses a controller there rather than arbitrary TCP Docker-host magic ([docker.ts](../repo/src/runtime-providers/docker.ts), lines 16–54). Source coordination is shared; repo clones/volumes and runtime images still need deliberate Mac/Linux placement and artifact transport.

### Generated apps, pages and realtime collaboration

The repository includes versioned data-backed apps, rendered pages, synchronization, migrations, and realtime rooms. [apps/definition.ts](../repo/src/apps/definition.ts), lines 20–26, 251–322, and 460–554, defines models, queries, and actions. It validates model/query relationships. [apps/sync.ts](../repo/src/apps/sync.ts) synchronizes external data. [http/rooms.ts](../repo/src/http/rooms.ts) exposes realtime room operations. Wingman could use this platform for organizational tools and artifacts. It still needs a portfolio schema, migration ownership, access controls, and compatible deployment versions.

### Realtime shared documents, presence and ephemeral channels

Realtime rooms differ from persisted chat transcripts. [realtime/document.ts](../repo/src/realtime/document.ts), lines 44–99, implements Yjs-backed JSON documents. Operations include set, delete, array insertion, increment, and collaborative text. [realtime/rooms.ts](../repo/src/realtime/rooms.ts), lines 403–467, checks versions and generations before changes or resets. Lines 471–519 serialize snapshots into key-value storage and retry failed flushes. Generation checks prevent obsolete snapshots from overwriting current rooms.

Changes publish immediately. Persistence normally follows a one-second debounce (lines 14–21 and 233–246). An acknowledged live edit can therefore remain vulnerable to an abrupt API crash. Snapshot-size and room-count limits bound the collaboration state. The feature is not an arbitrary file store.

[realtime/transport.ts](../repo/src/realtime/transport.ts), lines 328–365 and 490–526, authorizes namespace operations. It supplies WebSocket document synchronization, awareness, presence, and publish/subscribe channels. Channel payloads have a 64 KiB limit. Presence has an 8 KiB limit. Disconnect removes connection presence. Document snapshots persist.

[realtime/bus.ts](../repo/src/realtime/bus.ts), lines 5–33, uses synchronous **ephemeral in-process** delivery. Channels have no durable replay. The bus does not span an API cluster. The browser resynchronizes documents after reconnect. See [realtime/browser.ts](../repo/src/realtime/browser.ts), lines 205–281.

These mechanisms can support shared boards, artifact collaboration, typing presence, and worker nudges. Wingman must distinguish authoritative tracker changes from transient notifications. It needs recovery for missed notifications. Horizontal scaling also needs a distributed transport or a retained single-API boundary.

### Multi-user identity, integrations, budgets and operational accounting

Agent Swarm supports mapped users, tokens, role-based access control, and external issue, VCS, email, and chat integrations. It also records pricing, context, costs, and session sharing. [budget-admission.ts](../repo/src/be/budget-admission.ts), lines 64–133, checks daily spend before work claims. Checks cover the global, agent, and requester budgets. [http/sessions.ts](../repo/src/http/sessions.ts), lines 818–850, exposes session sharing.

Budgets control admission. They do not guarantee an exact task cost. Running tasks can continue spending after the daily threshold. These integrations also add operational work beyond Wingman's minimum personal organization.

## Distinctive mechanisms and grounded innovation assessment

These mechanisms are distinctive within this checkout and relevant to Wingman. This assessment makes no claim of historical or industry-wide novelty.

**Separate logical identity, runtime capacity and model session.** One durable specialist can have multiple process instances, each with reported slots and liveness, while sharing a server-enforced logical capacity policy. Registration does not let competing runtimes redefine that policy. The implementation links staffing continuity to elastic infrastructure without making every restart a new employee. Its limit is shared mutable agent/repo state: concurrent sessions under one identity do not automatically become isolated task workspaces. Evidence: [http/agents.ts](../repo/src/http/agents.ts), lines 709–795; [runtime-pools/demand.ts](../repo/src/be/runtime-pools/demand.ts), lines 31–64.

**Explicit continuation graphs instead of native session resurrection.** Superseded/failed work gets linked fresh tasks with inherited context, and generic preambles reconstruct bounded state across providers. This makes continuity more portable and less dependent on a specific container's native rollout files. The mechanism sacrifices implicit full-conversation context and requires good summaries/retrievable artifacts. Its name “resume” must not obscure that tradeoff. Evidence: [resume-session.ts](../repo/src/commands/resume-session.ts), lines 1–16; [context-preamble.ts](../repo/src/commands/context-preamble.ts), lines 136–196; [worker-follow-up.ts](../repo/src/tasks/worker-follow-up.ts), lines 474–662.

**Deferred work follows logical outcomes, not just the first completed row.** A task can complete to release a session while its continuation remains pending; all/any event waits follow deferred/superseded successors and preserve a single original deadline. This gives agents a durable “check back when these things really settle, or at the ceiling” primitive without occupying model capacity. It is particularly valuable for ProjectMaster supervision and integration gates, but requires outcome rollups to understand deferral and replacement rather than treating any terminal status as business completion. Evidence: [defer-task.ts](../repo/src/tools/defer-task.ts), lines 162–215; [scheduler/deferred-task-waits.ts](../repo/src/scheduler/deferred-task-waits.ts); tests at [deferred-task-wake.test.ts](../repo/src/tests/deferred-task-wake.test.ts), lines 293–343 and 641–721.

**Deterministic supervision with repairable handoff gaps.** The system checks liveness in code, protects freshly progressing tasks with compare-and-swap, repairs superseded parents lacking replacement tasks, and caps recovery generations before leadership triage. The lead's model is then used for the judgment-intensive follow-up rather than being the sole detector of a dead worker. This reduces dependence on polite progress messages while keeping limits explicit. A quiet but healthy computation can still resemble a stall if thresholds/progress reporting are wrong. Evidence: [heartbeat.ts](../repo/src/heartbeat/heartbeat.ts), lines 448–503, 658–698 and 764–825.

**Memory retrieval corrects chunk crowding and records usefulness.** Document-aware widening, rank fusion and visibility-aware graph expansion handle practical failures of naïvely fetching the nearest N chunks. This helps persistent specialists find distinct prior work rather than many fragments of one long answer. It remains bounded, relevance-ranked recall and needs measurement. It does not establish every retrieved memory is correct. Evidence: [search-candidates.ts](../repo/src/be/memory/search-candidates.ts), lines 1–46; [sqlite-store.ts](../repo/src/be/memory/providers/sqlite-store.ts), lines 135–168 and 703–747; [graph-expansion.ts](../repo/src/be/memory/graph-expansion.ts), lines 46–80 and 155–170.

**Human conversational context survives delegation without blindly transferring authority.** Chat thread keys/requester IDs flow into tasks and children, routing checks guard parent attachment, and another sender does not automatically gain the prior requester's attribution. This is useful for Butler handling several conversations without mixing authorization or replies. It models conversational provenance, not product ownership, so Wingman still needs project-aware routing. Evidence: [inbound.ts](../repo/src/integrations/chat-sdk/inbound.ts), lines 565–591; [send-task.ts](../repo/src/tools/send-task.ts), lines 396–420; [chat-sdk-inbound.test.ts](../repo/src/tests/chat-sdk-inbound.test.ts), lines 829–916.

## Practical adoption fit

Use these mechanisms after deployment verification:

- Long-lived Codex worker execution and extensible identities/templates.
- Shared assignments, dependencies, and progress.
- Public and direct-message collaboration channels.
- Telegram intake, replies, and context-aware steering.
- Durable human questions, memory, and artifact records.
- Heartbeat, scheduling, and remote controllers.
- Task/session logs and cost inspection.

**Adapt deliberately:** define Butler as the human-facing role and ProjectMaster as portfolio supervisor; decide whether the platform's privileged lead represents one or both responsibilities. Add ProductMaster/TechMaster as real separately executed workers with project ownership, rather than treating an `isLead` flag as sufficient. Carry immutable project IDs across intake, chat/task context, directives, artifacts, approvals, scheduling and host placement. Establish the intended Mac/Endeavour runtime configuration, source/artifact sharing and placement policy. Keep authoritative accepted product knowledge directly retrievable alongside search memory. Decide whether bounded fresh-session reconstruction meets the required conversation continuity or whether Wingman needs an additional native-session control layer.

Build missing product behaviors and views:

- A product/portfolio registry and intake resolver.
- Project-specific team/leadership relationships.
- Discovery questions/answers with explicit readiness and proportionality.
- Scope/specification/acceptance/DoD artifacts and change control.
- Project rollups and stop-on-accepted-delivery state.
- Room1/Room2 escalation semantics.
- Per-agent briefings for recent results, current work, next work, and blockers, with provenance and freshness.
- A meaningful personal summary timeline.
- Lifecycle and IDE capabilities beyond transcript viewing.

The app and page platform can support these views. Wingman must still define and implement them.

The adoption decision should turn on whether Wingman wants to own a product-organization layer over a broad existing control plane. Replacing the control plane entirely would discard substantial working mechanisms. Treating Agent Swarm as a finished Wingman replacement would leave the core discovery, portfolio, acceptance and executive-reporting requirements implicit in prompts.
