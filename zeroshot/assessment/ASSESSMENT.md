# Zeroshot assessment against Wingman

Assessment date: **2026-11-05**. Repository: https://github.com/the-open-engine/zeroshot. Local checkout: `researchs/zeroshot/repo`. Examined commit: **`3aad736924cb631e0d13f7ed2ab7ef216055cc53`** (read from `git rev-parse HEAD`). Reference requirements: [Wingman purpose](../../WINGMAN_PURPOSE.md); method: [assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md).

## Verdict and product boundary

**A strong candidate for Wingman's bounded coding, verification and delivery execution layer. An incomplete substitute for its persistent development organization.** Zeroshot supplies independently executing coding harness sessions, configurable specialist graphs, parallel execution, durable run history, independent acceptance/code review, repair loops, remote execution targets, retained-workspace recovery, file checkpoints and trusted Git delivery. It would remove substantial execution-engine work from Wingman. It does not supply Butler, Telegram intake, a persistent cross-project organization, a shared ticket tracker, agent rooms, portfolio supervision or executive briefings.

This revision is **the Rust v8 product**, not the older JavaScript implementation associated with earlier Zeroshot descriptions. [The entrypoint](../repo/zeroshot/src/main.rs), lines 45–63 and 84–125, dispatches the Rust CLI into local execution, named targets, ACP or UI. [Workspace Cargo metadata](../repo/Cargo.toml), lines 1–18, lists the Rust engine and protocol/server/client/testkit crates. Node is repository/distribution tooling and the static React UI build. The checked-in package version is a development placeholder. This report does not infer a published release number from it.

Two qualifications materially affect the verdict:

* Zeroshot's installed **planning skill** explicitly includes research, proportionate planning, repeated human clarification and checkable acceptance criteria. Those capabilities deserve credit, but they execute in a host coding agent before a run, not as a resident ProductMaster inside Zeroshot's runtime.
* Remote target execution is implemented. It is more than launching local subprocesses. However, the target is selected for a whole run. The checked-in engine does not distribute the workers of one graph across Mac and Linux hosts while sharing organizational chat and tracking.

All findings below are **source-inspected**, not end-to-end runtime-verified. No dependencies were installed, services launched, model calls made or source files modified.

## Architecture and actual execution model

### The unit of work is an admitted graph run

A submission contains a human-readable title, graph, initial JSON input, runtime bindings and optional source/environment. It is not an organization or project. [The composition contracts](../repo/zeroshot/src/native_v2_contract.rs), lines 43–85, distinguish caller intent from the compiled `AdmittedRun`. [Graph types](../repo/crates/openengine-cluster-protocol/src/graph.rs), lines 143–184 and 269–370, define typed inputs, outputs and bindings plus `Step`, `Verifier`, `Seq`, `Choice`, `Par`, `Loop` and `Map` nodes.

A graph leaf supplies instructions and I/O contracts. A separate [runtime binding](../repo/crates/openengine-cluster-protocol/src/native_v2_run/runtime.rs), lines 264–337, selects agent model, optional lane/effort/native configuration, named credential requirements and session scope, or selects a script, decision or trusted delivery implementation. [RuntimePlan](../repo/crates/openengine-cluster-protocol/src/native_v2_run/wire.rs), lines 20–124, provides the default lane and per-node lane overrides. Different leaves may therefore use different supported harness/provider combinations without changing graph topology.

[Admission](../repo/zeroshot/src/native_v2_admission.rs), lines 154–190 and 226–245, validates bindings, constructs a graph-local worker registry, checks delivery concurrency, and invokes the production graph verifier. It performs no workspace allocation or credential resolution. This separation matters: a well-formed persona prompt alone does not become a running worker, and invalid graph/dataflow contracts are rejected before execution effects.

### Local composition and detachment

The public command selects [LocalCliBackend](../repo/zeroshot/src/native_v2_cli/local.rs), lines 96–115. Submission validation, source resolution, connection resolution and private controller startup are implemented at lines 201–297 and 349–410. A local run uses a selected user workspace. It is not automatically a disposable worktree. Recovery metadata records that workspace and delivery lineage. A private bootstrap transfers the captured invocation environment and private capabilities to a detached controller.

The [foreground execution path](../repo/zeroshot/src/native_v2_cli/execution.rs), lines 396–467, prints the run receipt, optionally detaches, or follows durable status. Ctrl-C during observation detaches. It does not mean force-stop. [The parser](../repo/zeroshot/src/native_v2_cli/parser.rs), lines 151–188, exposes list/status/watch/logs/attach, explicit force-stop, failed-run resume, checkpoints and retained-workspace discard. UI lifetime is likewise separate from run lifetime.

### Deterministic control, real provider execution

The [FullV1Reducer](../repo/zeroshot/src/full_v1_reducer.rs), lines 1–7, 34–95 and 150–206, consumes a verified graph and normalized durable execution history. It emits dispatch, loser-cancellation, state-promotion and terminal decisions. It does not itself invoke models or operate workspaces. The [supervisor](../repo/zeroshot/src/native_v2_supervisor.rs), lines 196–250 and 273–363, repeatedly loads durable state, reduces it, dispatches workers, awaits completions and captures quiescent checkpoints. It detects surviving active executions on initialization as runtime loss rather than pretending their conversations can simply continue.

The [runner](../repo/zeroshot/src/native_v2_runner.rs), lines 431–519 and 551–620, reserves activity, returns a handle before asynchronous provider startup, checks out a session, builds the prompt/response contract and invokes an actual adapter. The maintained [adapter registrations](../repo/zeroshot/src/harnesses/adapters/core/mod.rs), lines 6–21, include Codex, Claude, Copilot and Pi. Contributed [registrations](../repo/zeroshot/src/harnesses/adapters/contributed/mod.rs) add implementations through the same registry boundary; their availability depends on build/placement.

For a concrete execution path, [Codex process exchange](../repo/zeroshot/src/harnesses/adapters/core/codex/process.rs), lines 35–48 and 72–115, starts a provider process, concurrently exchanges prompt/output, waits for cleanup, decodes output and records token usage. These are independently executing harness sessions, not several names in one LLM response.

### Durability, observation and remote placement

[SqliteRunLedger](../repo/zeroshot/src/v2_run_ledger/sqlite.rs), lines 18–34, stores run snapshots plus ordered events. Lines 100–144 and 182–189 serialize connection use and transactional creation/appends. Idempotency keys and submission digests distinguish replaying an accepted request from admitting different work under the same key. The [ledger model](../repo/zeroshot/src/v2_run_ledger.rs), lines 75–104, 219–304 and 371–402, has phases, per-execution snapshots, node events, logs and run summaries. It has no project/ticket/room entities.

Named target execution uses [NamedTargetCliBackend](../repo/zeroshot/src/native_v2_cli/oecp.rs), lines 56–97 and 122–165, and the target connector. [TargetRecord](../repo/zeroshot/src/native_v2_target.rs), lines 62–96, holds endpoint/access identity. It intentionally does not bind a repository. [Production hosting](../repo/zeroshot/src/native_v2_hosting.rs), lines 1–6 and 136–159, composes one target ledger/controller and a capsule allocator. [Candidate composition](../repo/zeroshot/src/native_v2_candidate.rs), lines 1–5, 51–57 and 111–151, places the lane adapters and trusted delivery against one common run workspace.

The UI is a graph/profile authoring and run-observation interface. [Run history services](../repo/zeroshot/src/profile_ui/runs.rs), lines 1–32 and 106–160, read the same durable records and supply live pages with cursors. [RunHistoryView](../repo/ui/src/RunHistoryView.tsx), lines 74–189, selects a run, worker execution and replay cursor. [ExecutionTimeline](../repo/ui/src/ExecutionTimeline.tsx), lines 12–55, links execution states and verdicts; [Transcript](../repo/ui/src/Transcript.tsx), lines 10–39 and 123–140, displays retained logs/activity and timestamps. This is useful drill-down, but is neither a project tracker nor an automatically written executive briefing.

## Agent definition and lifecycle

### 1. Definition, creation and identity

An “agent” in the engine means an executable graph leaf with authored instructions, a typed input/output contract and an agent runtime binding. A reusable profile packages the graph/runtime. It is not itself a running agent. The [protocol leaf definitions](../repo/crates/openengine-cluster-protocol/src/graph.rs), lines 269–306, contain attempts/deadline/worker reference and verifier signals. The [binding definition](../repo/crates/openengine-cluster-protocol/src/native_v2_run/runtime.rs), lines 264–337, contains the execution configuration. Admission requires authored instructions for agent-backed leaves and rejects missing or unexpected bindings ([admission error contracts](../repo/zeroshot/src/native_v2_admission.rs), lines 55–74).

Actual creation occurs when reduction emits `Dispatch`, the supervisor assigns a `NodeRunRequest`, and the runner registers activity and opens the native session. The [execution identity](../repo/zeroshot/src/native_v2_contract.rs), lines 178–220, includes run ID, node name, node-instance ID and execution ID. Node instances survive loop revisits; executions do not. Map/loop occurrences and retry attempts are distinct in [reducer dispatch decisions](../repo/zeroshot/src/full_v1_reducer.rs), lines 48–59. Thus there can be several actual instances of the same specialist task, but no global agent employee ID carrying project memberships indefinitely.

### 2. Execution, tools and permissions

The runner resolves the node role and response contract, leases a session, combines instructions with typed input, optionally prepends host-owned context and calls the adapter ([runner](../repo/zeroshot/src/native_v2_runner.rs), lines 198–247 and 551–620). [Response validation](../repo/zeroshot/src/native_v2_runner/response.rs), lines 18–84 and 99–178, checks worker output or verifier output/signals/diagnostic locally; model compliance is not assumed merely because a schema was supplied.

Tools come from the selected coding harness, native configuration and prepared workspace. Zeroshot is not a replacement editor/tool catalog. The reviewer receives [runtime guidance](../repo/zeroshot/src/native_v2_runner/response/guidance.rs), lines 3–20, to inspect without repairing reviewed material, while workers prepare repository-declared dependencies and await terminal command outcomes. This is a **prompt boundary**, not an OS read-only verifier workspace: the candidate shares one workspace with the agent adapters. A Wingman adoption must not treat a verifier label as an enforced filesystem restriction.

Local native policy is preserved when configured or unavailable; hosted Codex execution applies bypass inside its containment boundary. The actual [Codex permission logic](../repo/zeroshot/src/harnesses/adapters/core/codex/permissions.rs), lines 25–64, shows both branches and suppresses local default bypass when overrides exist. This is precise enough to distinguish autonomous execution policy from a human product-decision channel.

### 3. Routing and concurrency

The graph decides who runs next, with what state and on which success/error/signal route. This is typed orchestration, not free-form agent-to-agent negotiation. [Candidate composition](../repo/zeroshot/src/native_v2_candidate.rs), lines 1–5 and 51–57, binds one adapter per effective runtime lane, all using the same workspace. Parallel branches and mapped work can execute concurrently; [the runner tests](../repo/zeroshot/src/native_v2_runner/tests.rs), lines 29–69, explicitly check overlap.

The graph author coordinates overlapping edits. Zeroshot does not assign separate source worktrees to every specialist or merge their patches automatically. By contrast, delivery must be sequenced after all potentially overlapping agent work: [admission concurrency tests](../repo/zeroshot/src/native_v2_admission/tests/concurrency.rs), lines 88–169, reject delivery parallel with writers or reviewers, and allow delivery after joined work.

A run is placed locally or on one named target. Runtime lanes choose harness/provider, not worker host. Separate product runs could be placed on different targets, but a Wingman layer must own placement policy and common project identity. Locally, [ancestor/root leases](../repo/zeroshot/src/native_v2_portable_controller/lease.rs), lines 33–68, permit sibling workspaces while excluding a parent/child overlap. This is concrete workspace concurrency control, not a distributed locking service.

### 4. Persistence, session reuse and recovery

The template catalog defaults the software worker and research scouts/researcher to node-instance reuse, with reviewers defaulting to fresh execution scope ([catalog](../repo/zeroshot/src/native_v2_templates/catalog.rs), lines 65–72); exact caller-authored runtime settings can differ. `execution` scope opens a fresh native session; `node_instance` scope uses the pool's reusable key. [SessionPool](../repo/zeroshot/src/native_v2_runner/state.rs), lines 223–258 and 285–318, shows these branches and checks that a reused session is live. A passively lost session fails closed instead of silently pretending its conversation survived. [The corresponding tests](../repo/zeroshot/src/native_v2_runner/tests.rs), lines 72–120, distinguish fresh sessions, loop reuse and lost sessions.

Durable ledger state and workspace persistence are independent from model-session persistence. [Failed local resume](../repo/zeroshot/src/native_v2_cli/local/backend.rs), lines 20–105, claims retained work, records successor lineage and launches a new attempt; lines 107–162 resolve fresh environment/credentials. The CLI explicitly states that old services, Docker state and agent conversations are not restored ([resume contract](../repo/zeroshot/src/native_v2_cli/parser.rs), lines 169–177).

A selected checkpoint includes filesystem state and settled execution prerequisites. [Checkpoint interfaces/seeds](../repo/zeroshot/src/native_v2_checkpoints.rs), lines 37–88 and 99–142, keep paths and seeds private while exposing opaque checkpoint IDs. [Supervisor checkpoint capture](../repo/zeroshot/src/native_v2_supervisor.rs), lines 329–340, requires quiescence. An outer parallel/map group is a boundary unit, so the recovery promise is not an arbitrary snapshot taken while workers still write. File checkpoints do not promise restoration of live databases/services or provider conversations.

The experimental [ACP facade](../repo/zeroshot/src/native_v2_cli/acp.rs), lines 1–4, 100–165 and 195–210, is a deliberate exception to normal run-scoped session ownership: an outer local session owns a reusable runner/workspace lease and each prompt is a separate durable run. This gives conversational reuse while that owner survives, not a persistent cross-project organization or restart-proof agent conversation archive.

### 5. Scheduling, interruption and failure

The supervisor schedules admitted graph work until completion or cancellation. It is not an LLM ProjectMaster that sleeps and wakes to inspect organizational state. No cron-like recurring agent wake service or worker-blocker follow-up loop was found in the runtime/CLI/UI paths. Delivery has bounded or cancellable polling for forge readiness. This is technical gate observation.

The [runner handle](../repo/zeroshot/src/native_v2_runner.rs), lines 478–519, owns cancellation/output/completion. [Activity closure](../repo/zeroshot/src/native_v2_runner/state.rs), lines 37–109, tombstones closed runs and signals their active work. The supervisor notices explicit stop/runtime loss, drains workers and requires cleanup before settlement ([supervisor](../repo/zeroshot/src/native_v2_supervisor.rs), lines 241–269 and 273–325; [cleanup verification](../repo/zeroshot/src/native_v2_supervisor/runtime.rs), lines 3–16 and 53–85). Unconfirmed cleanup is fatal, not a harmless retry signal. Stopping observation or closing the UI does not stop background work.

There are distinct recovery levels. Structured output has at most two correction turns ([response constants](../repo/zeroshot/src/native_v2_runner/response.rs), lines 14–16). Native-v2 execution retry applies only to a settled crash with another authored attempt ([leaf evaluation](../repo/zeroshot/src/full_v1_reducer/evaluation.rs), lines 313–331). Rejection by a verifier is a normal signal that an authored graph may turn into repair, not a process crash. Controller restart with recorded active work becomes runtime loss ([supervisor initialization](../repo/zeroshot/src/native_v2_supervisor.rs), lines 228–249). Workspace resume creates a successor. These distinctions avoid crediting “retry” as universal automatic continuation.

### 6. Completion, acceptance and retirement

An execution completes when its adapter returns a validated outcome and cleanup has settled. A run completes when graph reduction yields a terminal result and the supervisor finalizes it. In software-change, both independent reviewers must accept before delivery; ten exhausted rounds fail. Acceptance is therefore code-enforced routing over model verdicts, although the quality of those verdicts remains model/test dependent.

[Finalization](../repo/zeroshot/src/native_v2_supervisor.rs), lines 344–364, latches the primary result, closes run sessions, handles checkpoints, cleans up runtime, appends terminal truth and discards successful checkpoint storage. Failed runs can retain recoverable workspace state. Explicit discard retires abandoned retained target workspaces. Closing a run is not “archiving an employee”; reusable profiles/lessons and history remain separate from runtime resources. Wingman still needs product acceptance by the human, accepted-delivery inactivity policy and organizational agent retirement/archive controls.

## Coordination mechanics and a concrete request trace

### Shared state, feedback and human decisions

Within a run, agents coordinate through **typed graph state and a shared filesystem**. Input bindings select state or map-item values; write bindings promote output, signals or diagnostics to parent state. The engine enforces routing and availability, while prompts define what each agent should do. A rejected acceptance/code result carries actionable diagnostics into the same worker's next visit. There is no room membership, peer mailbox, arbitrary recipient routing or shared ticket discussion service.

Human interaction has three different boundaries: the host-agent planning skill can ask iterative questions. The human submits a ready task/profile and can stop/resume/observe; forge reviews or a host-supplied trusted delivery validator can hold delivery pending. None is an implemented management escalation conversation. In particular, [trusted validator pending loops](../repo/zeroshot/src/native_v2_delivery/adapter/review.rs), lines 114–185, give Wingman a valuable acceptance-gate integration point, but Wingman must supply the decision UI, durable human question, response routing and correlation itself.

### Trace: a software change with failed review and a CI repair

This is a trace of the shipped `software-change` implementation, using “add CSV export” as example input. It is **not a claim that this task was executed during assessment**.

1. **Prepare the product intent.** A human uses `zeroshot-plan` in a host agent. It researches the repository, resolves material choices with the human, and saves a plan with stable AC/Q/D identifiers. The plan is a durable handoff, not a dispatched runtime worker ([planning skill](../repo/npm/zeroshot/skills/zeroshot-plan/SKILL.md), L17–59 and L115–213).
2. **Submit the graph and task.** CLI submission selects the built-in graph, materializes runtime bindings and calls the local or named backend. Locally, admission validates the graph, the workspace/source are resolved and the detached controller is prepared ([local backend](../repo/zeroshot/src/native_v2_cli/local.rs), L201–297). The receipt identifies one run, not a newly registered product.
3. **Implement.** The graph's `change_loop` creates a round containing `worker` then `worker_result`. The worker receives task plus phase/acceptance/code/delivery feedback and performs the change in the shared checkout ([software worker](../repo/zeroshot/src/native_v2_templates.rs), L88–119; [loop](../repo/zeroshot/src/native_v2_templates.rs), L193–223). Initial empty phase means implementation.
4. **Review independently.** Successful worker completion routes to `parallel_reviews`. Acceptance checks observable requested behavior and repository checks; code checks correctness, safety and integration. `Join::All` waits for both. Acceptance also authors the title/description used by delivery when enabled ([reviewers](../repo/zeroshot/src/native_v2_templates.rs), L226–276).
5. **Reject and repair.** A real execution error routes to `review_failed`; ordinary rejection routes to the next loop iteration. An empty map ends that round without adding another model call. The next worker gets both feedback fields and phase identifying the feedback source ([review route](../repo/zeroshot/src/native_v2_templates.rs), L325–362). The checked-in [rejection test](../repo/zeroshot/src/native_v2_templates/tests.rs), L209–230 onward, explicitly asserts repair dispatch contains both diagnostics.
6. **Deliver only accepted work.** On acceptance, the selected delivery worker commits/pushes the deterministic managed branch and opens/observes the review. This is a native trusted adapter, not an LLM told to run `gh` with the delivery secret ([delivery adapter](../repo/zeroshot/src/native_v2_delivery/adapter.rs), L26–35, L67–98 and L175–228). Success requires an authoritative receipt, with merge revision for merge delivery.
7. **CI failure returns through review.** Delivery signals `ci_failed`, `conflict` or `repair_required` route back into the same ten-round loop with delivery feedback. After repair, both acceptance and code review run again before another delivery attempt ([delivery routing](../repo/zeroshot/src/native_v2_templates.rs), L393–433). A reviewer or delivery infrastructure failure is not silently treated as a repairable product defect.
8. **Finalize and observe.** Events and transcript outputs are persisted, status watchers advance by cursor and the UI can replay each worker/review/repair execution. Terminal success follows result/cleanup settlement. The human may inspect the PR or use the retained failure workspace for a successor; no Butler announces the result or updates an organizational ticket automatically.

The concrete coordination benefit is that independent review is a gate in the state machine and every repair re-enters that gate. The main Wingman gap is that all task boundaries, graph structure and higher-level project interpretation must already be provided by a human, skill or external organizational layer.

## Major additional capabilities beyond Wingman's described product

### Typed, preflight-verified workflow language

Zeroshot includes a general, typed workflow language with branching, map/parallel groups, loops, output/signal/error channels and compile-time graph verification. [Graph contracts](../repo/crates/openengine-cluster-protocol/src/graph.rs), L143–184 and L232–370; [admission](../repo/zeroshot/src/native_v2_admission.rs), L171–190; [pure reducer](../repo/zeroshot/src/full_v1_reducer.rs), L150–206, implement this separation. Wingman describes human/agent organizational workflows but does not require this compiler-level contract system. It could make critical delivery workflows predictable and inspectable. Integration requires translating tickets and acceptance rules into graphs/data contracts rather than assuming arbitrary conversational delegation automatically becomes a valid graph.

### Trusted forge delivery and repair feedback

Push, PR readiness and merge are native worker contracts with separated credentials, explicit conflict/CI/repair outcomes and immutable candidate/review identities. [Delivery modes/capabilities](../repo/zeroshot/src/native_v2_delivery.rs), L94–182; [adapter authorization/cleanup](../repo/zeroshot/src/native_v2_delivery/adapter.rs), L141–228; [observation reduction](../repo/zeroshot/src/native_v2_delivery/adapter/review.rs), L28–61, substantiate this. The [source-provider boundary](../repo/zeroshot/src/source_code/mod.rs), L1–4, and maintained [forge registry](../repo/zeroshot/src/source_code/adapters/core/mod.rs), L11–23, separate Git transport from GitHub/GitLab review operations.

This is more operationally specific than Wingman's generic delivery description. It can close the implementation→review→CI→repair→delivery loop without handing source-control write authority to ordinary repair prompts. Wingman would need to decide which project tickets may open PRs or merge, map human acceptance into the external validation boundary and preserve receipt links in ProjectTracker. Source authority is separately owned; local native tools still operate within the invoking user's environment, so the narrow delivery credential design is not a claim that all worker effects are isolated from that user.

### File checkpoints and exclusive recovery lineage

[Checkpoint seeds/catalog](../repo/zeroshot/src/native_v2_checkpoints.rs), L37–88; [local recovery](../repo/zeroshot/src/native_v2_cli/local/backend.rs), L20–105; [lineage metadata](../repo/zeroshot/src/native_v2_cli/local.rs), L75–86, are stronger than merely keeping a chat transcript. A successor can start from retained workspace bytes or continue settled prerequisites from a selected checkpoint; claims prevent competing successors adopting one workspace. The storage implementation uses [Restic-backed snapshots](../repo/zeroshot/src/native_v2_checkpoints/restic.rs).

The value is lower recovery cost after a failed multi-agent run and coherent delivery lineage across retries. The cost is another operational dependency and strict ownership semantics. Wingman must model a successor as a new execution attempt linked to the same task, and avoid promising recovery of external services or old provider conversations.

### Active Memory with scoped discovery, maintenance and deterministic recall

The [lesson model](../repo/zeroshot/src/active_memory/model.rs), L38–115, stores versioned repository or graph/node lessons with evidence references, not just unstructured appended chat. [Retrieval](../repo/zeroshot/src/active_memory/retrieval.rs), L38–66 and L101–205, uses resident indexes for paths, identifiers, keyword conjunctions and graph nodes; ranking and full-card byte budgets are deterministic. [The store](../repo/zeroshot/src/active_memory/store.rs), L33–58 and L85–135, uses private SQLite storage, revision preconditions and deletion tombstones. Workers do not receive writable store authority.

Four postmortem specialist roles independently maintain graph lessons, maintain repository lessons, discover graph procedures and discover repository lessons. [Postmortem planning](../repo/zeroshot/src/active_memory/postmortem/plan.rs), L11–47 and L77–142, partitions scopes, requires evidence and prevents recursive postmortems in the auxiliary runtime. Maintenance, rather than blind accumulation, can adapt or retire outdated advice. This could improve repeated Wingman work, but it is not product memory: compact operational recommendations do not replace requirements, business decisions, ticket ownership or full research. Hosted embedders must select memory storage/backends explicitly ([hosting config](../repo/zeroshot/src/native_v2_hosting.rs), L77–89); cross-host organizational memory does not appear automatically.

### Research experiments and bounded review publication

The `auto-research` template supplies three independent scout perspectives, one researcher and an independent reviewer, with configurable experiment rounds and a bounded revision loop ([implementation](../repo/zeroshot/src/native_v2_templates/auto_research.rs), L8–20, L46–125 and L156–210). This goes beyond ordinary product discovery into repeated experimentation. It is useful for technical optimization/research tasks, but is not a business product owner or portfolio strategist. Authored prompts and repository-specific experimental discipline still determine the scientific quality.

The separate PR-review graph classifies whether reproduction is needed, conditionally executes a reproducer and then runs a final checker ([PR review](../repo/zeroshot/src/native_v2_templates/pr_review.rs), L64–123). Trusted [comment delivery](../repo/zeroshot/src/native_v2_comment_delivery.rs), L1–30 and L63–95, preserves publication identity/body hash and rejects changed-content retries. This is useful as a review service and feedback producer for Wingman; comment publication remains an explicitly authorized delivery effect, not agent chat.

### Multiple native harnesses and non-agent leaf implementations

Runtime lanes support mixed agent tooling/providers while native configuration remains adapter-owned. [Core registrations](../repo/zeroshot/src/harnesses/adapters/core/mod.rs), L6–21; [effective lanes](../repo/crates/openengine-cluster-protocol/src/native_v2_run/wire.rs), L89–124, show the actual composition boundary. Beyond agents, [script commands](../repo/crates/openengine-cluster-protocol/src/native_v2_run/runtime.rs), L218–243, execute bounded argv without a shell, and [decision bindings](../repo/zeroshot/src/native_v2_candidate/decision.rs), L1–26 and L61–75, support stateless externally served classification on existing verifier contracts.

These make the engine broader than a Codex-only organization. Wingman can remain Codex-based while using native script steps for deterministic checks; supporting every harness would impose adapter/version/configuration testing outside its original requirements. The decision service is an external dependency, not a built-in autonomous specialist with tools or durable conversation.

### Prepared execution environments and run-owned services

Contained execution can run setup/startup hooks and keep startup services owned by the run rather than by one short-lived agent. [Environment process handling](../repo/zeroshot/src/native_v2_hosting/environment.rs), L24–44 and L73–151, supplies bounded hooks, cleared explicit environments, process-tree tracking and phase-specific ownership; [allocation ordering](../repo/zeroshot/src/native_v2_hosting/allocator.rs), L290–340, applies setup before source preparation and startup after workspace restoration. This helps several specialists share one prepared application stack and lets the runtime clean it up coherently. Local runs use the invoking environment rather than these contained hooks. Wingman would need environment definitions and idempotent startup rules for each product, especially when checkpoints restore files without restoring services.

### Hosted merge-plan clients and a Python integration surface

The checked-in protocol and clients also describe dependency-gated **merge plans**, distinct from the Markdown planning skill. [Merge-plan types](../repo/crates/openengine-cluster-protocol/src/native_v2_hosted/merge_plan.rs), L11–54 and L107–165, carry up to 64 named runs, `needs` dependencies, source/profile, expiry and aggregate statuses. [CLI contracts](../repo/zeroshot/src/native_v2_cli/parser.rs), L194–232, specify one repository/branch/profile, merge-only delivery, static inputs, no output dataflow between runs and no edit/retry in place. The local implementation provides validation and authenticated [hosted HTTP calls](../repo/zeroshot/src/native_v2_target/controller_authority/hosted_runs/merge_plans_http.rs); actual Platform queue/scheduler operation belongs to the external host and was not established by running this checkout. This is useful staged delivery coordination, not a general project tracker or a locally proven multi-project scheduler.

The [async Python client](../repo/sdks/python/src/zeroshot/client.py), L84–147, exposes local/direct/hosted targets and durable run/plan observation. Its [transport](../repo/sdks/python/src/zeroshot/_process.py), L18–45, L69–107, invokes the native CLI and decodes JSON/NDJSON. It is not a second Python runtime implementing graph semantics. Client closure detaches observation rather than stopping durable runs. This offers a practical Wingman integration route while retaining the native executable/version and process-lifecycle dependency. A Wingman scheduler should retain its own project/task semantics instead of substituting the hosted merge-plan model for its portfolio.

## Distinctive mechanisms and grounded innovation assessment

“Distinctive” here means an implemented mechanism worth studying or adopting. It does **not** assert historical novelty or industry uniqueness.

1. **Independent approval as executable control flow.** Fresh reviewer nodes produce typed verdicts, both acceptance and code must accept, and failed review or CI routes through the same bounded implementation loop. Evidence: [software graph](../repo/zeroshot/src/native_v2_templates.rs), L193–276 and L325–433. This makes review non-optional at execution time. It does not prove reviewers are correct, establish test coverage automatically or provide human product acceptance.
2. **A pure verified reducer shared with recorded observation.** The reducer accepts verified IR and normalized history, emitting deterministic dispatch/void/promotion decisions and optional structural trace ([reducer](../repo/zeroshot/src/full_v1_reducer.rs), L1–7 and L150–206). The UI observes recorded prefixes instead of inventing a second workflow execution semantics. This supports inspectable branching, loops and retries. It still requires correct verifier/reducer implementations and bounded history. It is not deterministic LLM output.
3. **Recovery boundaries correspond to semantic graph units.** Quiescent node/outer parallel/map boundaries combine workspace snapshots with execution prerequisite seeds ([checkpoint contracts](../repo/zeroshot/src/native_v2_checkpoints.rs), L37–88; [capture gate](../repo/zeroshot/src/native_v2_supervisor.rs), L329–340). This prevents a misleading “checkpoint” whose files and scheduler facts describe different moments. Services, remote effects and conversations remain outside that guarantee.
4. **Delivery authority is a native lane with explicit repair outcomes.** Credentials and authoritative forge observations live outside worker prompts; CI/conflict/repair feedback re-enters the authored review process, and successful completion requires appropriate receipts ([delivery adapter](../repo/zeroshot/src/native_v2_delivery/adapter.rs), L67–98 and L175–228; [review state reduction](../repo/zeroshot/src/native_v2_delivery/adapter/review.rs), L28–61). This is a useful separation of implementation and publication authority. It is not a substitute for defining a project's merge/acceptance policy.
5. **Memory maintenance is scoped and revisioned, with receipt-aware recall.** Versioned cards/tombstones, deterministic bounded retrieval and separate discovery/maintenance roles prevent simple append-only memory growth ([memory model](../repo/zeroshot/src/active_memory/model.rs), L52–115; [store](../repo/zeroshot/src/active_memory/store.rs), L56–103; [postmortem roles](../repo/zeroshot/src/active_memory/postmortem/plan.rs), L11–47 and L77–98). This enables controlled operational learning. A supplied-card receipt establishes exposure, not that the model followed the recommendation ([hook boundary](../repo/zeroshot/src/active_memory/hooks.rs), L23–40 and L62–80); model judgment and source verification still constrain admission quality.

The most useful architectural lesson for Wingman is the separation between **organizational state**, **verified execution contracts**, **provider session state**, **workspace bytes** and **trusted delivery effects**. Zeroshot implements the latter four in depth. Collapsing them into one long-lived chat would lose guarantees the code deliberately keeps separate.

## Practical adoption and remaining work

### Use directly within a Wingman integration

Use the engine for a well-scoped ticket or bounded batch after Wingman has established product direction. Submit task context and explicit acceptance criteria using a saved graph/runtime profile; let the built-in or a tailored graph implement, independently verify and repair. Store run IDs, execution references, source revision, checkpoint lineage and delivery receipts against Wingman's ticket. Use durable watch/log/history for execution detail and leave the provider/harness lifecycle to the engine.

For the user's Mac/Endeavour setup, local execution on the Mac and named-target runs on Linux are plausible building blocks. That statement is source-grounded architecture, not a deployment verification. The containing target owns one run workspace and its worker lifetimes. Put parallel Wingman tickets in distinct workspaces/runs and coordinate overlaps explicitly.

### Adapt deliberately

Build an adapter between Wingman task records and Zeroshot runs: task creation/submission keys, status mapping, recoverable failure, successor linkage, result evidence and cancellation must remain coherent. A failed run is not necessarily a blocked product. A model rejection is not a crash. A technical PR-readiness receipt is not human acceptance. Preserve those distinctions in the tracker/dashboard.

Author graph profiles matching actual assignments. Custom BackendCoder/FrontendCoder/TestMaster leaves can run concurrently where interfaces and file ownership permit, but generic graphs do not negotiate interfaces automatically. The shared workspace makes dependency/build artifacts convenient and overlapping edits a coordination responsibility. Reviewers are instructed to avoid repairs rather than independently mounted read-only source.

The planning skill is reusable guidance for ProductMaster, but Wingman must own its multi-project question routing, durable specification lifecycle and acceptance handoff. Active Memory could complement reusable project directives. It should not become the authoritative store for product requirements. Connect external trusted validation to a durable Wingman human decision only after defining the mapping and authorization boundary.

### Build outside Zeroshot

Wingman still needs its organizational identity/directory, Butler/Telegram integration, portfolio registry and intake classifier, per-project ProductMaster/TechMaster continuity, ProjectTracker ticket model, persistent agent rooms/direct collaboration, management escalation, periodic portfolio supervision and business-level completion/accepted-delivery lifecycle.

It also needs executive current/recent/next/blocker summaries with evidence links, permanent per-agent activity timelines, cross-host project placement and shared organizational storage, and the rich conversation controls described in Wingman's detailed workspace. Zeroshot's graph history can be embedded or linked as execution detail, but it does not supply these connected organizational views.

**Recommended fit:** keep Wingman as the continuing product/organization control plane and evaluate Zeroshot as an execution/delivery backend behind it. Replacing the whole organization with Zeroshot would require building most of the missing organizational product around the engine, while repurposing run/node identities as permanent agents would fight its lifecycle model.
