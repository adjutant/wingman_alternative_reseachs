# Orkas assessment against Wingman

Assessment date: **2026-11-05**. Repository: https://github.com/Orkas-AI/Orkas . Local checkout: `research/orkas/repo`. Actual inspected commit: **`c7c0e21fad7ff55f5a72a575b7a464f3cf9bc3a1`**. Package version: `2026.11.4`; license: MIT ([package][package], lines 1–15 and license field). This assessment concerns this source revision, not an independently tested packaged release or the separately operated Orkas service.

**Verdict:** Orkas is a substantial local desktop agent work environment and a strong source of implementation patterns for Wingman's chat, projects, task controls, persistent sessions and Codex integration. It is considerably more than a terminal launcher or a collection of persona prompts. Named agents get separate stateful executions. A Commander delegates actual work; projects have scoped rosters, persistent instructions, files, memory and to-dos; optional auto-advance starts work without a new human message. It nevertheless does not implement Wingman's standing three-level development organization. The source lacks a Telegram Butler channel and an independent portfolio supervisor with per-product ProductMaster/TechMaster pairs. It lacks native peer-agent management rooms and a demonstrated shared Mac/Linux execution plane. It also lacks executive per-agent current/recent/next briefings and linked agent timelines. Adopting it means building those organizational capabilities around an existing desktop execution and collaboration substrate.

No checkout source was changed, dependencies installed, services launched or model calls made. All behavior below is established by static source and test inspection unless explicitly qualified. Searches found no applicable `AGENTS.md` in the checkout. The supplied workspace guidance and assessment guide were followed.

## Architecture and execution model

The application is an Electron desktop monolith with a Node/TypeScript main process, renderer modules, IPC boundaries, native/bundled tools and an embedded TypeScript `core-agent` package. `bootstrap.cjs` is the package entry point; [main entry][main], lines 294 onward, creates windows, and lines 1845–1856 register the automation and project-driver schedulers. The group-chat API is not a remote team service: [group API][group], lines 306–373, seeds reserved actors and enqueues a user message in the process-local message bus. The renderer consumes streamed events and reconstructed persisted snapshots. The application process can run tasks independently of whichever conversation is currently displayed, but it must remain running to schedule or execute work.

The bus is the actual orchestration engine. It owns per-conversation queues, live execution maps, listeners and admission state ([bus][bus], lines 1–29, 1358–1780). The admission loop scans queued work, checks dependencies, keeps the same actor serial within a conversation, bounds named-agent concurrency and starts eligible work ([bus][bus], lines 4028–4250). `runTurn` resolves project scope, actor definition, instructions, tools, memory and backend ([bus][bus], lines 5268–5725 and 6027–6124). An ordinary named agent runs in process through the core-agent model/tool loop. A `runtime.kind: 'cli'` definition instead invokes the local CLI runner. These are real execution alternatives, not merely names shown in chat.

The in-process path also has a concrete execution loop: the application factory assembles a fresh `AgentRunner` with persistent session, providers, visible tools, skill allowlist and active-tool policy ([runner factory][runner_factory], lines 1625–1668). Core `runStream` resolves the provider, flushes pending persisted writes before new work and enters a bounded model/tool loop; parallel-safe tool calls execute under a cap and results commit in declared order ([core runner][core_runner], lines 1505–1548 and 2860–2895). Commander and named agents are configured for up to 500 tool rounds per turn, with convergence/checkpoint/idle controls rather than an unlimited loop ([actor budgets][budgets], lines 1–23). Completed dialogue is rebuilt from the canonical group log for each named actor; private session history is not treated as a separate source of conversation facts ([bus][bus], lines 5780–5838). This gives separate execution contexts a shared, attributable conversation history.

Codex uses an especially useful concrete integration: the backend spawns `codex app-server --listen stdio://`, initializes JSON-RPC, starts or resumes a native thread, starts a turn and normalizes native activity back into Orkas events ([Codex backend][codex], lines 1–26, 335–345 and 1437–1459). Claude, Codex, OpenClaw, OpenCode and Hermes have explicit backend capability declarations for continuation, instruction channels, live steering, memory and permission handling ([CLI registry][registry], lines 44–148). Backend capabilities differ. Codex and Claude support live ingress. OpenClaw does not stream progress. OpenCode cannot pause for an interactive native permission answer. Hermes declares no resumable session handle.

Persistence has several layers with different meanings:

- A **durable agent definition** is an account-scoped custom or installed agent record with an ID, workflow, dependencies, tools and runtime settings. It is not a permanently running daemon.
- A **conversation** is a persistent user-visible discussion, with a roster, routing floor and canonical JSONL messages. Commander and agent sessions within it have different IDs: `gconv`, `gmember` and ephemeral `gworker` session families ([state][state], lines 249–272).
- A **named actor session** is that definition's conversation-scoped execution context, backed by core-agent JSONL history or a native CLI binding. A profile can participate in different conversations. This does not create a new organization-wide worker identity automatically.
- A **conversation task** represents one independent named-actor execution. It has source/result message IDs, parent/dependency links and deterministic host-observed execution status. Its `done` means a normally ended turn, not accepted product quality ([task board][board], lines 1–35 and 98–155).
- A **project to-do** is durable business work, with `todo/progress/review/done`, owner, dependencies and conversation backlink ([project tasks][todos], lines 58–85). It is distinct from an execution task.

Project metadata, bindings, instructions, memory, files and conversations are inspectable local files; `cloud/` in a path is a storage-domain name, not proof of synchronization. [Projects][projects], lines 1–36 and 126–149, describes per-project directories and strict agent bindings. Core-agent sessions use a cached `PersistentSession` loaded from an account-scoped JSONL path ([session store][sessions], lines 1–39 and 178–204). CLI bindings and run diagnostics intentionally remain device-local ([CLI sessions][cli_sessions], lines 1–22; [CLI persistence][persist], lines 1–16). Public app publishing is explicitly a commercial stub in this checkout ([commercial entry][commercial], lines 1–16). The README also marks shared projects/cloud sync as packaged-only ([README][readme], around lines 100–109). These claims are not credited as working open-source coordination infrastructure.

## Agent definition and lifecycle, in detail

**Definition and creation.** Agent definitions are durable configuration plus identity. `Agent` includes stable ID, name, multilingual description, workflow, capability/tool groups, skill allowlist, optional required inputs, interactive behavior, output format and runtime ([agents][agents], lines 215–300). Standards are runtime guidance; knowhow/profile fields can be display-only, so a rich profile is not evidence that every field affects execution. Custom creation holds an account-level lock, checks name/ID uniqueness, resolves dependencies, normalizes guidance/runtime and writes one agent record (lines 1866–1973). CLI creation injects a project-directory input where required. Agents can also be marketplace installs. Human conversational agent-editing emits structured updates, parsed and applied through host code rather than granting arbitrary writes to agent specifications (lines 2625–2850 and 3145 onward).

A new definition does not spawn an employee process. A conversation seeds `commander` and `user`. A named agent joins at its first dispatch ([state][state], lines 1–17). Actor identity is the durable agent ID. Actual context is per conversation/actor, so reusing the same profile in three project conversations gives three execution histories, not one permanently resident conversation with three assignments. Multiple instances of a Wingman specialist are possible by creating separate agent definitions, but automatic profile instantiation, role inheritance and employee/team reporting links would need design work.

**Routing and execution.** User input can choose an agent directly, use mentions, or go to the active floor. Only user mentions are routing signals; agent prose mentioning someone is not executable peer delegation ([router][router], lines 75–96, 228–351). Commander is a special actor with orchestration tools. `hand_off_to` is terminal delegation: the specialist owns the remaining user-visible outcome and can hold the floor for questions. `dispatch_to` is nonterminal: synchronous mode returns the settled result for Commander to consume, asynchronous mode returns an admission receipt and later schedules a follow-up. Both create visible named-actor task executions. Anonymous `run_worker` is a bounded internal helper without a named agent's skills or full evolving conversation context ([bus][bus], lines 9703–10031). It should not be counted as a standing specialist.

The model's decomposition is not blindly treated as runtime truth. Explicit multi-agent user dispatch can use a separate planner returning at most eight tasks; validation checks allowed assignees, nonempty task parts and earlier-task dependencies ([dispatch planner][planner], lines 19–52 and 127–165). The assignment context tells each owner its portion and downstream consumers (lines 186–214). The scheduler releases dependencies only on successful execution completion. Failed/stopped/cancelled predecessors park successors as `blocked` for user action; their results are supplied at admission ([bus][bus], lines 4062–4139). Project backlog dependency eligibility is a separate selector: done prerequisites satisfy it, and a missing prerequisite is treated as resolved ([driver][driver], lines 203–222). Wingman should decide whether that missing-dependency behavior suits its stronger delivery invariants.

**Tools and permissions.** In-process agents have fixed tool-group upper bounds and skill dependencies. They do not inherit arbitrary Commander power ([agents][agents], lines 233–250; [bus][bus], lines 6027–6124 and 6450–6465). Scoped memory tools cannot write another agent/project's memory ([memory][memory], lines 47–62). Local-operation policy and connector mutation confirmations are host-mediated; sensitive connector actions wait for renderer approval and have explicit cancellation scopes ([confirmation][confirm], lines 163–266). Native CLI policy is separate: `inherit/ask/full_access` is applied only for backends that can honor it ([registry][registry], lines 52–148). A full-access external CLI is not transformed into a uniformly sandboxed in-process agent. The local bridge exposes approved Orkas categories to the CLI over a local endpoint; backend capabilities determine which native interactions can be forwarded.

**Concurrency.** Per-conversation same-actor serialization protects a stateful session. Different named actors can proceed concurrently with a default cap of four per conversation ([bus][bus], lines 3950–3963 and 4109–4112). The shared LLM gate has capacity ten; anonymous nested workers use their own default four-slot semaphore so a parent waiting for a child does not deadlock its own global slot ([locks][locks], lines 132–153). There is no automatic worktree isolation; parallel agents can share a coding directory. A per-file edit mutex protects the application's edit-tool read/modify/write sequence (lines 116–129), but it does not serialize arbitrary shell/native CLI changes or replace Git integration/review policy. Concurrency is meaningful execution capacity, with filesystem coordination obligations left to instructions and the workers.

**Persistence, resume and scheduling.** In-process sessions persist JSONL history and bounded projection/checkpoint data ([sessions][sessions], lines 1–39). CLI binding records contain backend/session ID, instruction and memory hashes, cwd fingerprint, permission policy, source message/turn/run identity and history cursor ([cli_sessions][cli_sessions], lines 25–67). Those compatibility fields prevent carrying stale native state across changed instructions, removed memory, working directory or permission settings. Writes are serialized per conversation so concurrent agents cannot overwrite each other's resume binding (lines 121–167). A CLI process may exit after each invocation while its native thread remains resumable; process longevity and conversation longevity are distinct.

Project auto-advance defaults off. Enabling it records a stable owning device. It checks the global backlog and all project IDs at one-minute intervals. The minimum interval is two minutes. The default limit is twenty advances/day, configurable up to two hundred. A stuck lease expires after thirty minutes ([driver][driver], lines 42–82, 119–162 and 229–277; [driver runner][driver_runner], lines 458–553). An assigned task goes directly to its owner; unassigned project work goes to Commander. The lease stops holding up the next task once the advanced item leaves `todo`, allowing concurrent conversations rather than waiting for every long job to finish. Scheduled automations separately support one-time/hourly/daily/weekly/monthly schedules, end conditions, device binding and power suspend/resume restoration ([automations][auto], lines 98–178, 2108–2205 and 2294–2385). These are desktop scheduler jobs, not independent resident supervisor agents.

**Steering, interruption and recovery.** Task controls can cancel one execution, edit/reassign/reorder queued work, or modify dependency relationships ([group][group], lines 824–918). Live steering is capability-dependent; Codex uses native `turn/steer`, with host fallback when an active native turn rejects input ([codex][codex], around lines 633–660). Whole-conversation Stop increments an abort epoch, aborts planner/runtime controllers, cancels queued/blocked work, invokes model-session abort fallback and clears pending connector/bash approvals and orchestration state ([bus][bus], lines 10253–10335). This is more robust than merely hiding a spinner.

Failures retain visible retry targets and provenance. The CLI runner retries rejected resume only before execution, can resend a turn consumed by resume without answering, and permits bounded retries for explicitly safe bootstrap/protocol failures ([CLI runner][cli_runner], lines 2229–2358). Group retries choose resume/restart using persisted work evidence and tell the agent to verify uncertain non-idempotent operations before repeating them ([group][group], lines 375–407 and 466–810). This is evidence-aware recovery, not a transaction system that can guarantee exactly-once side effects.

Durable history does **not** mean durable runnable queues. On process restart the task-board loader converts stale queued/running/blocked rows to cancelled because their execution payloads were in memory. `waiting_input` survives because its form exists in the message history ([board][board], lines 320–345). Chat startup sweeping also reconciles interrupted processing ([chats][chats], lines 2873–3150). A human retry or another explicitly scheduled run can continue from history. The source does not establish transparent restoration of every in-flight team assignment after a crash.

**Completion, acceptance and retirement.** Host execution terminals distinguish completed, stopped, failed, cancelled and waiting-input; conversation board `done` is execution completion. Project to-dos can move to `review`, and a human review action chooses approved→done or changes_requested→progress ([todos][todos], lines 645–668). Auto-advance/run seed text requests verification and ordinary work→review, reserving final acceptance for later user action ([driver runner][driver_runner], lines 280–303). That is a workflow instruction, not a hard universal authorization boundary: the model-facing generic task handler accepts status updates and has a direct complete→done operation ([task handler][todo_handler], lines 160–199). Wingman would need a separate trusted acceptance authority if product completion must be gated on test evidence and human acceptance.

Agent enable/disable controls eligibility; deleting a custom agent removes its definition tree, memory, edit chat/session and local runtime overrides, scoped to the active account ([agents][agents], lines 1466–1475 and 2562–2620). Conversation deletion separately purges associated session/materialized files ([chats][chats], lines 2446–2590). These are concrete cleanup operations, but there is no explicit organizational retirement/replacement workflow that redistributes all outstanding employee duties and retains a long-lived employment history. Forking and user-invoked context compaction were searched in chats, IPC and renderer controls without finding the Wingman control suite; automatic context management should not be confused with those controls.

## Coordination trace: a project to-do becomes actual Codex work

This is a code trace of a supported request path, not a live run executed during this assessment.

1. The human asks Commander to establish work as a project. `project_setup` validates the action; `create` files the current conversation under a new project, writes the supplied short goal as project instructions and creates initial to-dos. `move_conversation` resolves an existing exact ID/name and refuses missing/ambiguous destinations ([setup][setup], lines 29–78 and 88–197). Project bindings determine which agents the conversation may use. There is no mandatory portfolio-intake agent in front of this operation.
2. A backlog item records content, stable `owner_agent_id`, dependencies, due date and latest execution conversation ([todos][todos], lines 64–85). The task handler validates owners against enabled/bound agents so a rename does not transfer ownership accidentally ([task handler][todo_handler], lines 34–85). Both in-process agents and the CLI bridge use this same host-bound handler.
3. If auto-advance is enabled on this device, `advanceProjectIfDue` reads config/state/tasks, evaluates the guardrails and selects an actionable task. `advance` creates a project conversation, selects the assigned actor floor, checks and marks the snapshot `progress`, copies attachments, rechecks opt-in/device ownership and calls `groupChat.send` ([driver runner][driver_runner], lines 202–273 and 458–518). Failure before admission restores the prior status and removes the empty newly created conversation. Successful dispatch records the conversation backlink.
4. `groupChat.send` seeds reserved actors and enqueues the user-visible task text while sending the execution/status contract as model text ([group][group], lines 306–373). Bus admission claims an execution row and dispatches the assigned actor. If Commander owns the item, it can use `dispatch_to` to ask a coding agent for a sub-result or `hand_off_to` for the remaining deliverable ([bus][bus], lines 9703–9991). A sub-result is a visible execution with parent/result links, not an invisible persona change.
5. For a Codex-backed owner, the runner resolves its coding directory, permission setting and compatible native session binding. The backend starts a local app-server subprocess, resumes/starts a thread and sends the current turn ([cli_runner][cli_runner], lines 1345–1418; [codex][codex], lines 335–345 and 1437–1459). Its activity is streamed to the conversation. Run diagnostics persist prompt, events, output and summary locally ([persist][persist], lines 60–139).
6. If clarification is needed, the input-form protocol parks the execution as waiting_input and stores enough floor/ledger/resume metadata to route the answer back to the original owner ([board][board], lines 88–96; [state][state], lines 69–89; [group][group], lines 1172–1309). Commander follow-on work resumes from this relationship. This is a good analogue for keeping Wingman's project question/answer correlation, though the channel is desktop chat and the hierarchy is flatter.
7. A normal terminal settles the conversation execution independently from project quality. The agent updates the durable to-do through `todo_tasks`. The auto-start contract asks for verified work→review. The human can approve or request changes through `decideReview` ([driver runner][driver_runner], lines 280–303; [todos][todos], lines 656–668). A failed dependency blocks downstream conversation work for a decision. A Stop prevents late continuations through abort-epoch gates. None of this automatically proves integrated product acceptance or completion of an organization's definition of done.

This trace illustrates Orkas's strongest connection: a business work record links to a routed conversation, a concrete native coding turn, its visible process evidence and a later review action. The weakest connection for Wingman is above it: nobody in this path is a permanent portfolio leader periodically talking to a ProductMaster, TechMaster and TestMaster across projects.

## Substantial capabilities beyond Wingman's described product

**A general-purpose business/media agent environment.** Wingman focuses on software delivery; Orkas also supplies dedicated research, office, UI, image, video, voice and commerce agents. These are meaningful workflows with specialized host tools, not only alternate names. UIDesigner, for example, distinguishes repository-read authority from requested source edits, persists a canonical artifact and requires delivered evidence ([UI agent definition][ui_agent], lines 4–45). Office tools use one OfficeCLI wrapper for reading/creating/editing/rendering DOCX/XLSX/PPTX and manage detached resident processes ([Office engine][office], lines 1–16 and 40–80). VideoStudio has composition manifests, draft repair budgets, sampled frames, contrast/audio/source-alignment and delivery QA ([video engine][video], lines 1–75). These could extend Wingman's product design and delivery artifacts, but bring native runtimes, media/service dependencies and domain-specific approval/credit flows that are unnecessary for an initial coding organization. Their presence does not establish a general software TestMaster.

**Local application creation and hosting inside the workbench.** Generated apps can be saved, reopened for editing, given isolated storage, and use a manifest-mediated host SDK. Native adapters grant selected file dialogs, model generation, read-only library operations and connector tools rather than arbitrary desktop IPC ([app host][app_host], lines 1–76; [saved apps][saved], lines 570–810 and 1506 onward). This creates operational tools usable beyond a single chat answer and could host project-specific planning/inspection tools. It also adds an application capability/security lifecycle. It should not be mistaken for an out-of-the-box executive dashboard. Public publishing is explicitly unavailable in this source build ([commercial][commercial], lines 1–16).

**Connector platform and approval boundaries.** The connector catalog/manager supports provider-specific integrations, local/remote MCP transport, credential lifecycle and mutations. Some OAuth/managed connector paths use the Orkas server or credit-bearing services, so “local-first” does not mean all capabilities are offline or self-hostable from this checkout ([catalog][catalog], lines 1–14 and 25–47). The host confirmation mechanism binds a pending sensitive action to user/account/conversation or app usage and cancels it on scope closure ([confirm][confirm], lines 163–300). This is useful for Wingman integration with issue trackers, repositories and communications, while requiring deployment decisions about credentials, managed-service dependence and external mutation authority. A Slack connector is not a built-in autonomous agent-room subsystem.

**Knowledge library and evidence-aware research.** Global/project files are indexed through extraction/embedding queues with status, failure and reconciliation pathways ([project files][files], lines 25–58; [KB indexer][kb], lines 1–10, 26–46 and 81–109). DeepResearcher has explicit evidence/contradiction/resume guidance. More significantly, host citation verification loads fetched text by result-store reference instead of trusting text copied into a model argument ([research verifier][verify], lines 1–30 and 319–393). This could help ProductMaster's domain research and source traceability, but it does not decide product requirements or eliminate semantic/source-quality errors.

**Agent adaptation and scheduled operations.** The reflection orchestrator reviews changed activity at startup/periodically, selects at most five eligible agents, uses a four-hour minimum cooldown, two-minute per-agent timeout, failure backoff, and yields to foreground work. Successful reflections can write metacognition or reusable skills ([reflection][reflect], lines 1–40 and 81–115). This is a persistent adaptation loop outside Wingman's specified manual profile expansion. Adopting it would require deciding which role directives may evolve, recording changes and distinguishing learned practices from approved product decisions. It is self-review, not the missing ProjectMaster supervision process. Scheduled recurring business work similarly extends beyond development delivery, while depending on a running desktop process.

## Distinctive mechanisms worth transferring

These are grounded design mechanisms at this revision; no claim is made that they are historically new or unique across other systems.

1. **Two separate kinds of task truth.** Conversation runs have host-observed execution state; project to-dos have business progress/review state. Stable message IDs and parent/backlog links connect them without making a successful model turn equivalent to a completed business objective ([board][board], lines 1–35 and 98–155; [todos][todos], lines 64–85). This prevents a common misleading dashboard model. Its limit is that semantic acceptance remains workflow/model-driven unless a separate trusted gate is added.
2. **A conversation floor plus a suspended-orchestration ledger.** `active_recipient` answers who should receive the next unaddressed user message; `orchestration_ledger` records which larger Commander-owned goal is waiting and how to resume it ([state][state], lines 142–170). This avoids losing a larger goal when one specialist asks a clarification question. It supports one interactive handoff owner, not arbitrary nested management-room conversations or an organization-wide conversation router.
3. **Scheduler-controlled dependency handoff.** The validated planner only points to earlier tasks; host admission waits for all required successful terminals and adds predecessor results at the precise moment a successor starts. A failed predecessor parks work for user judgment ([planner][planner], lines 127–165 and 186–214; [bus][bus], lines 4062–4139). The model proposes structure, while host code enforces ordering. Its limit is execution `done` as the dependency signal and cancellation of pending runtime rows after restart.
4. **Compatibility-aware native session continuation.** Native thread IDs are coupled to cwd, instruction/memory and permission fingerprints, exact failed-turn provenance and canonical-history cursors ([cli_sessions][cli_sessions], lines 25–67; [CLI execution path][bus], lines 10931–11158). Resume fallback is bounded and avoids replay after already-started execution ([cli_runner][cli_runner], lines 2229–2358). This is valuable for Wingman's real Codex agents, but remains machine-local and cannot guarantee exactly-once external operations.
5. **A conservative autonomous backlog driver.** Device-owned opt-in, cooldown, daily caps, actionable selection, status compare-and-write, per-project locking and rechecking opt-in immediately before send limit unintended advancement ([driver][driver], lines 42–82 and 229–277; [driver runner][driver_runner], lines 202–273 and 458–518). This provides practical scheduled autonomy without giving the model an unlimited self-wake loop. It selects new work rather than diagnosing stalled in-progress work or supervising a portfolio leadership team.
6. **Evidence provenance enforced outside the authoring model.** Citation verification resolves fetched evidence from the host result store, marks inline model-supplied text separately and compares exact normalized quotations/DOIs ([verify][verify], lines 1–30, 138–179 and 319–393). This reduces circular self-verification. It only verifies the quoted evidence relationship. It cannot establish that a source is correct, representative or sufficient for the claim's broader interpretation.

## Practical fit and adaptation cost

The highest-value direct reuse is the execution adapter layer, especially Codex app-server integration, supported live ingress/approval handling, native-session fingerprints and local diagnostic capture. The second is the linked chat/run/backlog model, including individual execution controls, input-form resume and conservative auto-advance. The third is the real project shell with bound agents, instructions, memory, files and review UI. These address substantial work Wingman would otherwise implement from scratch.

A plausible adaptation would make Butler a new channel adapter into the same conversation/run APIs, with durable project/question correlation outside the renderer. It would add a real organizational registry separating reusable role profiles from project-specific employee instances and their conversations. ProductMaster/TechMaster/TestMaster definitions could use existing runtime/tool primitives, but their responsibilities must be encoded in trusted workflow/state transitions and durable `DIRECTIVES` records; merely renaming Commander or ProductDeveloper does not create the intended organization. ProjectMaster needs an independent supervision policy that inspects in-progress work and blockers, sends follow-ups and escalates decisions rather than selecting only new to-dos.

The executive overview and agent timeline need new derived records linked to actual tasks, room discussions, source changes and verification evidence. Existing counters/runtime snapshots are useful inputs, not finished summaries. Room1/Room2 and direct peer collaboration need a message and authority model beyond Commander-only routing. Multi-host work requires remote workers, host identity/placement, transport/authentication, shared records/artifacts and failure reconciliation; device labels, remote MCP or commercial sync cannot substitute for that system. A headless always-on coordinator and web/mobile organizational interfaces would also be additions to the desktop-first source.

Finally, Wingman needs stronger product acceptance and concurrency conventions: separate worktrees or an equivalent integration discipline, functional/integration testing ownership, trusted acceptance evidence and a stop-after-accepted-delivery rule. The present tracker permits model-driven completion. Its crash recovery preserves facts and visible interruption but cancels pending executable rows; Wingman must decide which assignments should be resumable/requeued automatically and ensure retries do not duplicate external side effects. These are material architectural adaptations, not configuration-only gaps.
