# Paseo assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/getpaseo/paseo

Local checkout: `researchs/paseo/repo`. Actual inspected commit: `b920243c74e25ec06e523019fb154f78ea9870be`. This assessment describes that checkout, not an earlier release or the current hosted Hub service. Requirements come from [WINGMAN_PURPOSE.md](../../WINGMAN_PURPOSE.md) and [ASSESSMENT_GUIDE.md](../../generic/assessments/ASSESSMENT_GUIDE.md).

**Verdict: a strong candidate for Wingman's execution and individual-agent workbench layer, with substantial real delegation infrastructure. It does not supply Wingman's standing development organization.** Paseo manages independent provider sessions, exposes child creation and direct messages to agents, preserves identities and provider resume handles, delivers completion/permission notifications, schedules recurring prompts, and routes work to other daemons. Its desktop/mobile/web workspace is much closer to Wingman's detailed agent workspace than its portfolio, tracker, room, discovery or leadership requirements. Those organizational behaviors need an application built above the daemon rather than a change of profile names.

Two source findings materially affect the verdict. First, **multi-host delegation is implemented**, not merely remote viewing: agent tools can create and prompt a child on a registered remote daemon and receive its completion. Second, apparent task/room support must not be overcredited: the Markdown `FileTaskStore` is referenced only by its tests, while chat-room schemas explicitly remain for compatibility after feature removal. Neither establishes a working ProjectTracker or Room1/Room2 application at this revision.

## Architecture and execution model

Paseo is an npm-workspace TypeScript system with a Node daemon, protocol package, client SDK, Expo app shared across mobile/web, CLI, Electron desktop wrapper, plugin package and relay cryptography package. The real runtime composition is visible in [bootstrap.ts](../repo/packages/server/src/server/bootstrap.ts), lines 940–1048 and 1448–1530: it creates file-backed project/workspace registries, Git services, provider runtime, `AgentManager`, storage persistence, schedules, finish subscriptions and idle-runtime protection. App and CLI communicate with the daemon through the same typed WebSocket API. The daemon is the owner of agent execution; closing a viewing client does not own or terminate a turn.

Creation reaches a real harness. `AgentManager.createAgentInternal` prepares configuration and launch context, resolves an available provider client, invokes `client.createSession`, then registers/persists/subscribes to that session ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), lines 1386–1444). Provider factories include Claude SDK, Codex app-server, ACP adapters, OpenCode, Pi and OMP, plus plugin providers ([provider-registry.ts](../repo/packages/server/src/server/agent/provider-registry.ts), lines 36–49, 98–114 and 189–225). In the Codex path, the adapter launches the configured executable with `app-server`, pipe transport and an effective environment; creation/resume construct separate `CodexAppServerAgentSession` objects and connect them ([codex-app-server-agent.ts](../repo/packages/server/src/server/agent/providers/codex-app-server-agent.ts), lines 7515–7613). Native `thread/start`, `thread/resume` and `turn/start` calls are present at lines 5554–5561, 4139–4168 and 4481–4493. This is actual process-backed coding, not simulated personas in a shared model completion. Other providers need not map one process to one session. The uniform abstraction is a provider session.

State is local-first. Agent records are Zod-validated JSON; bootstrap places project and workspace JSON beneath `PASEO_HOME/projects`, and `AgentStorage` caches/indexes stored agents. Agent records retain provider-native session handles, not an organization-wide knowledge graph. Normal bootstrap does **not** supply `AgentManager`'s optional durable timeline-store dependency. The live normalized timeline is in memory and history is hydrated through provider persistence. See [agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), lines 1490–1567, 3897–3937 and 4119–4123; [agent-timeline-store.ts](../repo/packages/server/src/server/agent/agent-timeline-store.ts), lines 19–49 and 92–112; [bootstrap.ts](../repo/packages/server/src/server/bootstrap.ts), lines 1014–1028. Wingman should explicitly own durable task/decision/summary records instead of relying on the process timeline as its tracker.

## Agent definition, creation and lifecycle

### Definition, configuration and identity

An agent is a durable **session identity** whose runtime can be loaded, unloaded and reconstructed. It is neither a constantly resident employee process nor only a prompt. Configuration contains provider, cwd, creation-time system instructions, model, mode, thinking, features, provider options, exact MCP preapprovals and external MCP servers ([agent-types.ts](../repo/packages/protocol/src/agent-types.ts), 505–535). Stored metadata adds title, labels, timestamps, workspace, background/internal distinctions, attention, archive state, owner and native persistence handle ([agent-storage.ts](../repo/packages/server/src/server/agent/agent-storage.ts), 13–81).

Profiles intentionally do not carry a system prompt: they can also be applied to an already running session, whereas system instructions are creation-only. The `list_profiles` tool tells an orchestrator to read profile notes and copy fields into `create_agent`; no `profile` argument binds the resulting agent to a profile ID ([agent-profile.ts](../repo/packages/protocol/src/agent-profile.ts), 3–29; [paseo-tools.ts](../repo/packages/server/src/server/agent/tools/paseo-tools.ts), 3088–3110). Wingman could reuse profiles to choose execution settings, but needs separate durable role/profile membership and instructions. A title such as “TechMaster” alone does not establish that relationship.

### Creation and first execution

The app/WebSocket session resolves workspace placement and intent, validates cwd, and calls the shared `createAgentCommand`. Its session branch builds attachments and provider mode/features, passes the workspace/labels/environment, and treats a first-turn failure as belonging to the already created agent ([session.ts](../repo/packages/server/src/server/session.ts), 4598–4648; [create-agent/create.ts](../repo/packages/server/src/server/agent/create-agent/create.ts), 229–280).

An agent-scoped `create_agent` selects explicit provider/model and initial prompt, inherits applicable configuration, resolves its own or requested workspace and adds parent identity. It invokes the same command and returns the new ID/status promptly. The shared command first creates/registers the session, then persists a finish subscription before starting the initial prompt, accepting/rejecting that subscription according to dispatch ([paseo-tools.ts](../repo/packages/server/src/server/agent/tools/paseo-tools.ts), 1605–1694; [create-agent/create.ts](../repo/packages/server/src/server/agent/create-agent/create.ts), 169–226). This ordering avoids missing a very fast child's completion. Initial prompt creation is a launch operation, not automatic task decomposition.

Registration builds the managed state, primes provider history where applicable, records it, changes lifecycle to idle, subscribes to provider events and drains pending events ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 3853–3964). Runs consume provider events; `runAgent` collects timeline/usage/final response, throws on `turn_failed` and returns an explicit canceled flag ([same file](../repo/packages/server/src/server/agent/agent-manager.ts), 2616–2652). Lifecycle values are initializing, idle, running, error and closed; attention is a separate finished/error/permission signal. An idle agent can be waiting for its next assignment rather than a completed product.

### Tools, permissions, routing and concurrency

Paseo exposes a transport-neutral tool catalog with an MCP adapter, plugin tools and provider-native tooling. Core tools cover workspace creation, agents, prompts/status/activity, permissions, providers/profiles and schedules. Per-provider Paseo-tool policy can disable tools; exact external MCP preapproval is separately represented by server/tool names. Provider contracts mark exact MCP preapproval support for Claude, Codex and OpenCode and reject unsupported blanket assumptions ([provider-registry.ts](../repo/packages/server/src/server/agent/provider-registry.ts), 148–186; [paseo-tool-policy.ts](../repo/packages/server/src/server/agent/paseo-tool-policy.ts), 15–28). Daemon session authorization maps operations to semantic grants ([operation-permissions.ts](../repo/packages/server/src/server/authorization/operation-permissions.ts), 1–140). These controls are execution authority, not product-management authority.

Addressing is `(serverId, agentId)` for remote relationships. Daemon-owned host registrations and routed API scopes are separate from the app's saved host connections. Remote creation requires an existing destination workspace and provider/model, so the parent cannot accidentally reuse its local filesystem path on another host. `createHostResolver` executes local operations directly or creates a routed destination client; remote messages carry caller agent/server identity ([host-operations/index.ts](../repo/packages/server/src/server/agent/host-operations/index.ts), 177–299). Connected-host routes are one hop, grant-bounded and scope-owned. They are not an automatic fleet scheduler or shared-filesystem service ([connected-hosts.md](../repo/docs/connected-hosts.md), “Ownership and authority” and “Connections and recovery”).

Multiple managed agents run independently. Per-agent lifecycle mutation tails serialize archive/detach/label/restore changes; foreground-run mutation paths mediate run replacement/cancellation ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 2598–2613 and 3414–3489). Agent messages are recipient-owned batches with a two-second quiet window and ordered dispatch groups when mode/interrupt options conflict; different recipients have independent queues ([agent-messages/delivery.ts](../repo/packages/server/src/server/agent/agent-messages/delivery.ts), 54–163). This reduces conflicting prompts but is not a ticket lock or dependency claim. Two agents in the same cwd still share filesystem writes; worktree isolation must be selected explicitly.

### Persistence, resume, scheduling and supervision

Agent storage retains serializable configuration, native session IDs/handles, labels/workspace and visibility/attention metadata. `resumeAgentFromPersistence` reloads persisted config/environment, resolves interactive versus history purpose, verifies provider availability, creates launch context and invokes native `resumeSession` ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 1455–1567). History-purpose loading accommodates archived agents whose cwd may be gone. Runtime reloading preserves the stable Paseo identity; provider-native history is still a dependency. Descriptor-based provider children have a separate lifecycle/transport and may be read-only in the UI. They cannot be given the same independent lifecycle controls as managed children. One documentation section still describes OMP `child_session` events being imported as managed agents ([agent-lifecycle.md](../repo/docs/agent-lifecycle.md), lines 180–184). The current inspected OMP implementation instead maps `subagent_lifecycle`, progress and event messages into `provider_subagent` upserts/timelines ([omp/agent.ts](../repo/packages/server/src/server/agent/providers/omp/agent.ts), lines 1672–1701; [omp/subagent-index.ts](../repo/packages/server/src/server/agent/providers/omp/subagent-index.ts), lines 24–64 and 104–120). The assessment follows that code and treats the older prose as a documentation discrepancy, rather than crediting independently managed OMP children.

Restart recovery distinguishes reconnecting history from continuing interrupted work. Startup repairs running/initializing records to closed and selects eligible running agents for an optional configured resume prompt; owned/internal/archived agents are excluded. Recovery dispatches each candidate independently and clears `resumeOnStartup` before dispatch ([restart-recovery/index.ts](../repo/packages/server/src/server/agent/restart-recovery/index.ts), 9–64). This is continuation policy, not restoration of the exact in-flight process instruction. The workbench protects callers with pending child notices or queued messages from idle-runtime cleanup ([bootstrap.ts](../repo/packages/server/src/server/bootstrap.ts), 1509–1515).

Schedules are durable daemon objects. A heartbeat targets an existing agent. A normal schedule launches a new agent/workspace with stored configuration. Cron cadence, timezone, maximum runs and expiry are supported, along with pause/resume/run-once/history. Due slots are claimed and advanced within one serialized store update. A running-schedule set prevents overlapping invocation of the same schedule ([schedule/service.ts](../repo/packages/server/src/server/schedule/service.ts), 570–587 and 714–824). Existing-agent execution refuses a currently active run and fails on permission/error; new-agent runs can create a worktree and archive their workspace afterward ([same file](../repo/packages/server/src/server/schedule/service.ts), 927–1058). An interrupted persisted schedule run becomes failed on daemon restart, with an explanatory error, rather than automatically replaying its side effects (613–647). Wingman can implement periodic ProjectMaster review with this primitive, but must write the review policy, tracker queries, blocker detection and escalation behavior.

### Interruption, failure, recovery and completion

Prompt dispatch distinguishes out-of-band commands, native steering and replacement of an active turn. If a provider cannot steer, the manager may replace through its existing behavior. This is not a guaranteed cross-provider concurrent conversation model. Stale plugin sessions are reopened from persistence and the start path retried ([agent-prompt.ts](../repo/packages/server/src/server/agent/agent-prompt.ts), 91–192). Cancellation asks the provider to interrupt, waits for settlement and reports not-running/settled/refused. Acknowledged but non-settling runs are force-terminalized in manager state after timeout; refused cancellation blocks reload/replace/rewind ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 3414–3489). This prevents pretending a refused interrupt succeeded, but it is not rollback of commands already executed.

Creation recovery and message recovery have explicit uncertainty boundaries. `CreationService` fingerprints a request, persists resource identity before provisioning, shares an in-flight operation across retries and records milestones. A crash during an uncertain stage yields an outcome-unknown record requiring reconciliation rather than another blind launch ([creation/index.ts](../repo/packages/server/src/server/creation/index.ts), 49–119 and 151–208). A keyed legacy create rejects an inline prompt and requires sending it separately ([session.ts](../repo/packages/server/src/server/session.ts), 4486–4503). Message receipts write pending before provider dispatch and completed after it. A pending receipt after recovery returns `agent_request_outcome_unknown`, while changed arguments conflict and completed retries do nothing ([message-receipts/index.ts](../repo/packages/server/src/server/message-receipts/index.ts), 25–55). This is useful automation infrastructure, not an exactly-once guarantee over arbitrary provider side effects.

Child observation is a separate recovery mechanism. Finish subscriptions persist observation intent until delivery to the parent has been acknowledged, restore after restart and notify on permission, error, completion, closed or unavailable states. Remote observation retries have capped backoff; three failed non-connecting observations terminate with an unknown/unreachable notice, not a claim that remote execution stopped ([finish-subscriptions/index.ts](../repo/packages/server/src/server/agent/finish-subscriptions/index.ts), 16–58, 170–215 and 233–253). Parent prompts still need to decide what to do with the result. No automatic semantic bug-fix retry, TestMaster acceptance loop or proof that the product definition is satisfied is imposed by the daemon.

### Retirement and cleanup

Archive is soft retirement, distinct from process residency and client layout. Managed archive snapshots state, stamps `archivedAt`, closes runtime, synchronizes provider archive state where supported and handles children. Parent archive cascades to labeled children, detaching children in another workspace or open in a client tab; detached agents no longer belong to that parent cascade ([agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 2024–2128). Internal helpers are not persisted by Paseo and are retired in memory. Codex's adapter explicitly documents that `persistSession=false` is a no-op at the native app-server level, so “Paseo internal” must not be read as guaranteed provider-side ephemerality ([codex-app-server-agent.ts](../repo/packages/server/src/server/agent/providers/codex-app-server-agent.ts), 7542–7552).

A managed subagent's tab can close without archiving it; detach clears parent lifecycle labels, while provider-child tabs are read-only layout. See [agent-lifecycle.md](../repo/docs/agent-lifecycle.md), “Tabs vs archive” and “The subagents track.” Wingman's standing leaders should not be accidentally tied to disposable parent-tab cleanup. Host-qualified remote relationships also require deliberate distributed retirement policy. The local registry scan in parent cascade should not be assumed to archive a child stored only on another daemon. Workspace archival may additionally remove managed worktree resources through its archive path, so agent archive and workspace cleanup are separate controls.

## Coordination mechanics and one request trace

The delivered shared coordination surfaces are agent/workspace metadata, provider timelines, point-to-point agent messages, finish/permission events, schedules and routed host operations. They are useful orchestration primitives, not a native persistent room/ticket organization.

A concrete code path for “ask a second agent to investigate this bug, then continue when it reports” is:

1. The caller uses `list_profiles` to read configured execution bundles and notes, then `create_agent` with provider/model, title, initial briefing and optional destination/workspace. The tool is agent-scoped; its caller identity is supplied by Paseo. [paseo-tools.ts](../repo/packages/server/src/server/agent/tools/paseo-tools.ts), 1605–1672 and 3088–3110.
2. For a local child, `createAgentCommand` resolves parent/placement and launches a real managed session, registers durable finish intent before the prompt and returns the child's ID/status. [create-agent/create.ts](../repo/packages/server/src/server/agent/create-agent/create.ts), 169–226 and 284–300. For a remote child, the tool's host resolver calls the destination's normal agent API with its workspace and host-qualified parent labels. [host-operations/index.ts](../repo/packages/server/src/server/agent/host-operations/index.ts), 222–260.
3. The provider performs the investigation and emits normalized message/tool/turn events. The child's agent panel streams the same detailed session if the human opens it. The parent child-track selector finds its relationship by server and agent identity. [agent-panel.tsx](../repo/packages/app/src/panels/agent-panel.tsx), 1390–1442; [subagents/select.ts](../repo/packages/app/src/subagents/select.ts), 74–100.
4. The child can send an intermediate report or question with `send_agent_prompt`. Paseo queues it per recipient, qualifies the sender, combines compatible messages after two quiet seconds and steers/replaces the recipient according to provider behavior. [paseo-tools.ts](../repo/packages/server/src/server/agent/tools/paseo-tools.ts), 1982–2051; [agent-messages/delivery.ts](../repo/packages/server/src/server/agent/agent-messages/delivery.ts), 67–163. A queued receipt acknowledges admission, not provider delivery or completion.
5. On finish/error/permission, the durable observer formats a system-origin child notification including the last response or permission payload and dispatches it through the same recipient queue. Permission notices retain observation for later completion; archived parents suppress delivery and detached creation children can lose ownership-based notifications. [finish-subscriptions/index.ts](../repo/packages/server/src/server/agent/finish-subscriptions/index.ts), 149–215. The parent resumes by accepting this prompt, not by a centralized ticket transition.
6. Human approval is available in the child's pane or through permission tools. The parent may revise its plan, send a follow-up, create another worker or report to the human. The daemon does not automatically update a project ticket, append a Room2 decision, ask Butler, or evaluate an acceptance gate. Those last steps are the Wingman layer.

This trace follows an implemented request path. It was not executed for this assessment. The bundled committee/advisor/handoff skills are concrete orchestration instructions using these tools. The committee requires two contrasting profiles, fresh context, analysis-only prompts, finish notifications and resolving disagreements. The handoff requires a self-contained briefing because the new agent has zero context. These skills demonstrate feasible patterns without proving a general autonomous organization or native inherited conversation fork ([paseo-committee/SKILL.md](../repo/skills/paseo-committee/SKILL.md), 8–48; [paseo-handoff/SKILL.md](../repo/skills/paseo-handoff/SKILL.md), 8–68).

### Why task and room remnants do not count as delivered coordination

The standalone task library is substantial: Markdown documents support dependencies/parents/assignees/priorities, acceptance criteria, notes, status transitions and ready/blocked graph queries. It is a possible reuse source for a lightweight Wingman tracker ([tasks/types.ts](../repo/packages/server/src/tasks/types.ts), 12–64; [task-store.ts](../repo/packages/server/src/tasks/task-store.ts), 17–177). However, repository-wide searches for `FileTaskStore`, imports from `tasks/` and `taskStore` found no production entry point constructing it. Its tests instantiate it. The daemon does not. There is no durable mapping from a task assignee string to a managed agent/host or a product acceptance controller.

Chat types and permission names remain parseable for backward compatibility, but their schema comments explicitly state removal after v0.3.0. No chat service/store or production room handlers were found in the daemon/session/tools/CLI/app paths searched. A transcript between a human and one agent, or a direct prompt from one agent to another, is not a shared room with membership and browsable decisions. The corresponding legacy agent-loop schemas also mark feature removal ([chat/types.ts](../repo/packages/protocol/src/chat/types.ts), 3; [chat/rpc-schemas.ts](../repo/packages/protocol/src/chat/rpc-schemas.ts), 4; [loop/rpc-schemas.ts](../repo/packages/protocol/src/loop/rpc-schemas.ts), 4). Current cron schedules should be credited on their own implemented behavior.

## Major capabilities beyond Wingman's described product

**Harness diversity and provider extensibility.** Wingman specifies Codex agents; Paseo abstracts Claude, Codex, ACP, OpenCode, Pi/OMP and plugin providers, including modes/features/model catalogs and provider-native child execution display. This lets an organization choose different execution environments and cross-provider second opinions. Integration needs a capability-aware role launcher: steering, permission modes, native persistence, exact MCP preapproval, goal support and ephemeral behavior are not identical across providers. Provider registrations and factories are code-backed in [provider-registry.ts](../repo/packages/server/src/server/agent/provider-registry.ts), 68–114 and 148–225.

**Encrypted remote access, distinct from multi-host delegation.** The relay package negotiates protected record channels and handles encrypted application framing. The external production relay service is not the legacy relay server in this checkout. Pairing and direct/relay/SSH access make phone operation feasible without moving repositories to a hosted coding workspace. [protected-records.ts](../repo/packages/relay/src/protected-records.ts), 1–51 and 125–203; [relay-endpoint-security.md](../repo/docs/relay-endpoint-security.md). Wingman could use this for mobile workbench access while keeping Telegram as the primary conversational channel. Relay compatibility/fallback policy and host authentication must be configured intentionally. This inspection is not a cryptographic audit or live relay verification.

**Detached, restart-surviving terminals.** The terminal-worker launcher deliberately spawns a worker outside the daemon's process tree and reads a private ownership record after launch. PTYs can survive daemon restarts/upgrades rather than disappearing with the manager ([terminal-worker-launch.ts](../repo/packages/server/src/terminal/terminal-worker-launch.ts), 22–92). This is useful for long builds/dev servers and human intervention. It is separate from agent-turn persistence: terminal survival does not imply the model process continues, and Wingman must associate command outcomes with its own tasks/evidence.

**Agent-scoped voice and selectable speech processing.** Paseo has streaming dictation and voice mode targeting an existing managed agent, with speech-to-text, text-to-speech and turn-detection readiness modeled independently. Local and OpenAI speech services are reconciled through one service boundary ([voice-session.ts](../repo/packages/server/src/server/session/voice/voice-session.ts), lines 124–149, 255–293 and 354–397; [speech-runtime.ts](../repo/packages/server/src/server/speech/speech-runtime.ts), lines 21–73 and 485–511). This provides hands-free control beyond Wingman's Telegram text conversation. Adopting it needs model/credential/resource configuration and an explicit choice of voice target. It does not add Butler routing or organizational intake semantics.

**Workspace service exposure.** A workspace script's local port can be registered with project/branch/script identity and projected local/public proxy addresses. The proxy forwards HTTP and WebSocket traffic to the local service ([service-proxy.ts](../repo/packages/server/src/server/service-proxy.ts), lines 15–60, 142–155, 319–378 and 431–446). This helps review running product previews from other devices. Public DNS/reverse-proxy setup remains deployment work, and the proxy is not a product hosting/acceptance pipeline. The implementation explicitly treats forwarded authority headers as client-influenced (same file, lines 290–311), so Wingman should not turn those headers into trusted tenant or project identity.

**Plugins and a composable SDK/UI surface.** Plugins can contribute providers, usage sources, exact agent tools, RPC subscriptions, lifecycle hooks and native client screens/panels. The public contracts expose workspace/agent/file panel context and navigation back into ordinary sessions ([plugin/server/index.ts](../repo/packages/plugin/src/server/index.ts), 1–37; [plugin/client/contracts.ts](../repo/packages/plugin/src/client/contracts.ts), 30–55 and 107–165). This is a practical place to implement a Wingman directory/tracker/executive surface without forking every client view. Plugins are trusted, unsandboxed code, including server preparation and client contributions; extensions are not isolated tenant apps ([docs/plugins.md](../repo/docs/plugins.md), 3–7 and 459–475). Organizational authorization and data ownership must therefore be designed above that seam.

**Optional external Hub event-consumer relationship.** Daemon code supports explicit enrollment, durable relationship credentials, outbound connectivity/recovery and grant-bounded execution by a Hub. CLI deploy/export commands and public guides describe external event workflows, but the service owning conversation keys, triggers and execution records is Paseo Cloud, outside this checkout ([hub/relationship-controller.ts](../repo/packages/server/src/server/hub/relationship-controller.ts), 212–294; [docs/hub.md](../repo/docs/hub.md), “Session grants and agent operations” and “Cross-repository compatibility”). It could supply an integration consumer model for Wingman, but its end-to-end policy is **unclear here**. Connecting is not permission to execute; `hub.execute` is a distinct grant. Do not infer Telegram, organizational intake or reliable output routing from the daemon half alone.

## Distinctive mechanisms and grounded innovations

These are notable design mechanisms in this checkout, not claims of industry-first invention.

1. **Durable notification intent around asynchronous delegation.** A child-completion watch is registered before initial prompt dispatch, preserved until the parent accepts notification delivery and superseded only by accepted follow-ups. Permission checkpoints retain the watch. This enables a parent to stop polling, do other work or reload while still receiving a child's outcome. It also distinguishes “remote observation failed” from “child stopped.” Limits: notifications concern agent state/last response, not task acceptance, and retries can redeliver when acknowledgement was lost. [create-agent/create.ts](../repo/packages/server/src/server/agent/create-agent/create.ts), 192–215; [finish-subscriptions/index.ts](../repo/packages/server/src/server/agent/finish-subscriptions/index.ts), 44–58, 170–253.
2. **Recipient-owned message batching with explicit dispatch boundaries.** Agent messages/finish notices converge through the same two-second quiet-window queue. Compatible reports can reach a busy coordinator in one steer; conflicting mode/interrupt requests retain ordered groups. Completion waits include admitted delivery. Limits: this queue is in-memory pending state with drain-on-close, not a general durable room/event bus, and a queued receipt does not establish execution. [agent-messages/delivery.ts](../repo/packages/server/src/server/agent/agent-messages/delivery.ts), 54–190; [delivery.test.ts](../repo/packages/server/src/server/agent/agent-messages/delivery.test.ts), 26–79.
3. **Host-qualified delegation over ordinary APIs and isolated virtual sessions.** Remote workers use the destination's normal workspace/agent operations, while links pin host identity and route scopes retain caller authority and cleanup ownership. The UI can display a remote child as an ordinary child address. This enables Mac-to-Linux delegation without inventing a second worker protocol. Limits: one hop, explicit destination workspace/configuration, no code/knowledge replication and ambiguous mutation outcomes requiring inspection. [host-operations/index.ts](../repo/packages/server/src/server/agent/host-operations/index.ts), 84–171 and 201–299; [connected-hosts/session.ts](../repo/packages/server/src/server/connected-hosts/session.ts), 177–200; [subagents/select.ts](../repo/packages/app/src/subagents/select.ts), 74–100.
4. **Separation of resource identity, runtime residency and presentation.** A stored agent may be unloaded yet resumable. A provider child has a timeline but no managed lifecycle; closing a child tab can leave execution intact; archive and detach change durable relationship semantics. This is useful for Wingman's long-lived management agents and disposable helpers. Limits: Wingman must choose which entities survive a leader's retirement and handle remote children deliberately. [agent-manager.ts](../repo/packages/server/src/server/agent/agent-manager.ts), 1490–1567, 2024–2128 and 2366–2423; [agent-lifecycle.md](../repo/docs/agent-lifecycle.md).
5. **Creation/message receipts that preserve uncertainty.** Resource IDs are journaled before side effects; concurrent retries share creation; completed messages deduplicate; unresolved pending delivery is reported unknown rather than retried as fresh work. This enables safer external automation and reconnection. Limits: the provider is outside the journal transaction, so the design honestly requires reconciliation instead of promising exactly-once work. [creation/index.ts](../repo/packages/server/src/server/creation/index.ts), 49–119 and 151–208; [message-receipts/index.ts](../repo/packages/server/src/server/message-receipts/index.ts), 25–55.

## Practical fit for Wingman

**Use directly:** Paseo's daemon-backed independent Codex sessions, workspace/worktree placement, persistent identity/resume, app/CLI detailed workspaces, live tool activity and permissions, local/remote child creation, point-to-point prompts, completion observation and recurring heartbeat primitive. These address a substantial portion of execution, operator visibility and background continuity. The cross-host implementation is especially relevant to the MacBook/Endeavour split. It has stronger foundations than merely opening a remote terminal.

**Adapt:** Build a Wingman service/plugin using the SDK and lifecycle/tool seams. Assign durable organization IDs and role/profile/project/team relationships separately from Paseo launch presets; bind them to `(serverId, agentId)` and reconcile runtime/archive events. Define worktree and host-placement policy explicitly. Route Telegram requests and replies through a Butler service, retaining project/question IDs rather than relying on the latest chat. Build summary production from meaningful task transitions and verification evidence. The existing activity curator is a useful drill-down source, not the executive feed. Add room and tracker writes as controlled shared operations, and make approval/escalation decisions durable.

Still build:

- The portfolio intake router.
- Standing Butler/ProjectMaster and per-project ProductMaster/TechMaster responsibilities. A project registry carrying goals/leadership/delivery status.
- Proportionate discovery and unanswered-question state.
- SCOPES/SPECS/HARNESS conventions and retrieval.
- Shared tickets with ownership/dependencies/blockers.
- Room1/Room2 membership/history and escalation.
- Executive current/recent/next/blocker summaries linked to evidence.
- Periodic supervision policy.
- Integrated testing/definition-of-done and human acceptance gates.
- Cross-host access to shared organizational records. Paseo's dormant task library can inform a tracker, but production wiring, atomic concurrent mutation policy, host-qualified assignees and views would still need implementation.

The architectural choice is therefore whether to adopt Paseo as a capable lower layer and compose Wingman above it. That is plausible and materially reduces workbench/runtime work. Adopting Paseo alone would leave the main organizational behavior undefined. Adopting external Hub as a replacement for that layer cannot be recommended from this checkout alone because the consumer's routing and policy implementation is not present.

## Verification scope and limitations

This was a read-only static source assessment. No dependencies were installed, no service or agent was launched, no provider was authenticated, and no tests were executed. All runtime descriptions above are implementation-supported, not live-verified behavior. The checked-out source was left unchanged; only this assessment was written.

The review read applicable Paseo `AGENTS.md`, listed `docs/`, and consulted architecture, product, agent lifecycle, data-model, connected-host, Hub and plugin documentation.

Implementation inspection followed:

- bootstrap → registries/provider runtime → session/create command → `AgentManager` → Codex process/session/turn path.
- agent prompt/steer/cancel/resume/archive paths.
- storage/restart recovery.
- message batching/finish subscriptions.
- host resolver and routed sessions.
- scheduling.
- creation/message receipts.
- provider/profile configuration.
- agent/subagent/workspace panels.
- the standalone task/legacy chat code.

Relevant tests were inspected as source evidence, with these boundaries:

- [finish-subscriptions.test.ts](../repo/packages/server/src/server/agent/finish-subscriptions/finish-subscriptions.test.ts), 135–164, explicitly asserts persisted intent remains until parent dispatch acknowledgement and that restart coalesces duplicate candidate intent; named cases at 208–390 cover remote retries, permission checkpoints, detach and storage failures.
- [agent-messages/delivery.test.ts](../repo/packages/server/src/server/agent/agent-messages/delivery.test.ts), 26–79, asserts a child report plus finish notice become one sender-preserving batch after two quiet seconds; subsequent named cases cover recipient independence, conflicting modes, errors and wait cancellation. These are deterministic unit tests, not proof of live provider steering.
- [connected-hosts/hosts.e2e.test.ts](../repo/packages/server/src/server/connected-hosts/hosts.e2e.test.ts), 140–184, constructs two test daemons and checks one physical link, isolated routed clients, one-hop rejection and disable/re-enable recovery. Other named cases inspect authority, identity pinning, lost mutation replies and capability recovery. Reading a two-daemon fixture does not verify the user's physical machines.
- [schedule/service.test.ts](../repo/packages/server/src/server/schedule/service.test.ts), cases beginning at 340, 536, 685, 725, 834, 902, 1279 and 1779, cover persisted due runs, restart interruption, fake-client execution, active-agent targeting, workspace cleanup, cancellation and prompt-start errors. These tests were inspected for intended cases. They were not run and fake-client execution is not live-model verification.
- The task library test references establish that the module is exercised in isolation. They do not establish production integration. Searches of server bootstrap/session/tools, CLI, app and protocol found no production `FileTaskStore` constructor/import; room schemas explicitly document removal. Searches for Telegram/Butler/ProjectMaster/ProductMaster/TechMaster, project-ticket/room service paths, acceptance/discovery controllers and executive summary state did not reveal corresponding product implementations. Incidental fixture strings and legacy permission/schema names were not treated as features.

Provider capability parity, deployment setup, external Hub behavior, production relay operation, real Mac/Linux delegation, long-running unattended reliability, cryptographic correctness and mobile UX were not exercised. The report consequently credits concrete primitives and identifies application-level gaps without claiming operational validation.
