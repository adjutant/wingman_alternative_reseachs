# Omnigent assessment

- Repository: https://github.com/omnigent-ai/omnigent
- Checkout: `research/omnigent/repo`
- Assessed commit: `539fe5da7769fde0f6d2ed48fca10ef93e174a23`
- Assessment date: 2026-11-05
- Basis: local implementation review against [Wingman purpose](../../WINGMAN_PURPOSE.md); no services, models, installations or tests executed.

**Verdict: a strong candidate for Wingman's execution substrate and detailed agent workbench, with meaningful coordination primitives, but not a ready standing development organization.** Omnigent does execute independent coding sessions across real hosts, retains their histories, makes child relationships visible, supports steering and approvals, and supplies an instructive multi-harness coding orchestrator, Polly. Its first-class projects group sessions rather than describe products, its task page is an automation scheduler rather than ProjectTracker, and its management relationships are mostly spawn trees rather than portfolio/product/technical leadership. Wingman would still need the organizational domain, Telegram Butler, discovery-to-acceptance workflow, shared tickets and rooms, and executive summaries.

The distinction is consequential: a durable **registered agent** is a versioned definition/bundle. An actual working **instance** is a conversation/session bound to that definition and an execution host. A Polly worker is a real child coding session, not just a persona in one model response. Neither the bundle nor a surviving transcript automatically constitutes an employee with a project, reporting line and continuing remit. See [agent entity](../repo/omnigent/entities/agent.py), lines 11–57, and [conversation entity](../repo/omnigent/entities/conversation.py), lines 41–95 and 173–219.

## Architecture and actual execution model

The package exposes both `omni` and `omnigent` through `omnigent.cli:main` ([pyproject.toml](../repo/pyproject.toml), lines 409–417). Relevant CLI paths are `server` (`cli.py`, line 4687), `run` (line 9134), and `host` (line 9813). The server command wires SQLAlchemy conversation, agent, comment, policy, permission, scheduled-task and project stores, plus an artifact store and `AgentCache`. It then initializes runtime capabilities and constructs the application. The local default is a SQLite `chat.db`; external store configuration is an implementation option, not evidence that this review exercised a distributed deployment ([CLI wiring](../repo/omnigent/cli.py), lines 1304–1314, 4899–4960; [database models](../repo/omnigent/db/db_models.py), tables at lines 190, 635, 731, 817, 932, 1045, 1329, 1510 and 1633).

The control plane is a FastAPI server with routes for sessions, agents, projects, hosts, sharing, resources, policies, MCP, usage and automations ([server assembly](../repo/omnigent/server/app.py), lines 120–155 and 1549 onward). The browser workbench consumes persisted snapshots and streamed events; terminals and native harness transcripts are additional views over the same session. It is not necessary for the human to keep that UI open for an already launched runner to execute.

Execution is deliberately separated into three layers:

1. A **host daemon** on a machine establishes an outbound WebSocket, advertises readiness, and receives launch/stop controls. The server retains host metadata and an active connection registry. This is actual remote-machine infrastructure, not a local process relabeled as a host ([host tunnel](../repo/omnigent/server/routes/host_tunnel.py), lines 1–15; [host implementation](../repo/omnigent/host/connect.py), lines 2215–2240 and 2358–2455).
2. A **runner** is launched on that host and connects to the server through its own outbound tunnel. Framed HTTP requests are dispatched to its ASGI application; session data retains `host_id` and `runner_id` affinity. A disconnected host cannot magically execute queued work ([runner tunnel](../repo/omnigent/server/routes/runner_tunnel.py), lines 1–14; [runner application](../repo/omnigent/runner/app.py), lines 1298–1367).
3. A **harness adapter/process** drives the selected native CLI or SDK and transports model output, tool calls, approval requests and lifecycle events. The process manager describes and implements per-conversation subprocess allocation, IPC, idle reaping and crash cleanup. Native terminal-backed sessions additionally involve tmux/bridges; different harnesses do not have identical controls or recovery semantics ([process manager](../repo/omnigent/runtime/harnesses/process_manager.py), lines 1–17 and 99–140; [harness scaffold](../repo/omnigent/runtime/harnesses/_scaffold.py), lines 1–33, 87–150).

A session create first resolves a project/defaults, authorizes its agent, resolves routing/placement and binds a persisted conversation. It may use a registered agent or uploaded bundle. The route does not infer a business product or instantiate a fixed managerial hierarchy ([create route](../repo/omnigent/server/routes/sessions/routes_core.py), lines 926–1083; [creation orchestration](../repo/omnigent/server/routes/_sessions/orchestration.py), lines 11493–11583). Bundle and transcript durability are distinct from process liveness. A live process can be reaped while its conversation remains available. A resumed native session may also need its vendor's native transcript, recorded by `external_session_id`.

## Agent definition, creation and lifecycle

### What is defined and what is instantiated

`AgentSpec` is a parsed executable definition containing model/executor settings, instructions, tools, skills, MCP servers, nested agents, history-passing controls, concurrency settings, compaction, guardrails, OS environment, terminals, timers and spawning rights. The directory parser reads `config.yaml`, resolves executor configuration, discovers instruction/skill/tool files and recursively discovers children under `agents/`. The loader also accepts portable single-file YAML and tarball/byte bundles, validates them, and distinguishes trusted operator-authored input from tenant input ([spec types](../repo/omnigent/spec/types.py), lines 1473–1602; [parser](../repo/omnigent/spec/parser.py), lines 202–264 and 3324–3358; [loader](../repo/omnigent/spec/__init__.py), lines 159–245).

Registration gives that definition an `ag_…` identity, content-addressed bundle location, ownership, version and timestamps. Server agents are shared definitions; user agents are reusable owner-scoped installations, while session-scoped copies can share a name across sessions. These records are not themselves live model processes. Starting a session creates a conversation, authorizes the chosen definition/parent, selects placement and workspace, and binds the runner/harness ([agent entity](../repo/omnigent/entities/agent.py), lines 16–57; [agent routes](../repo/omnigent/server/routes/builtin_agents.py), lines 1–15; [create orchestration](../repo/omnigent/server/routes/_sessions/orchestration.py), lines 11493–11583).

A named worker is addressed by `(agent, title)`. Its first `sys_session_send` creates a child session. A later call to the same address continues the existing history. The runner first checks that the named type is present in the parent specification. Inline children normally share the parent's registered bundle identity, with `sub_agent_name` selecting the nested definition, but have their own conversation IDs, turn state and execution. This is precisely the useful distinction between **profile**, **instance**, and **dispatch** that Wingman needs, although it lacks an employee record independent of conversations ([send tool](../repo/omnigent/tools/builtins/spawn.py), lines 65–113; [dispatch](../repo/omnigent/runner/tool_dispatch.py), lines 2618–2654 and 3064–3079).

### Tools, authority and routing

The runtime derives the exposed tool surface from the definition. Declared child agents grant `sys_session_send` and `sys_session_close`; `spawn: true` separately grants creation outside that declared set. Tool groups can suppress whole categories. Session sharing is another distinct authority, not an accidental consequence of being able to spawn. Model and harness overrides are validated against child capabilities rather than indiscriminately inheriting the parent's choices ([tool registration](../repo/omnigent/tools/manager.py), lines 470–525; [spec grants](../repo/omnigent/spec/types.py), lines 1572–1602; [override validation](../repo/omnigent/runner/tool_dispatch.py), lines 2787–2911).

Policies compose ALLOW, ASK and DENY around execution. State/label updates associated with ASK are withheld until the human approves; DENY takes precedence in composition. OS environment/sandbox configuration controls the underlying execution boundary, separately from these model-facing permissions. It would be a mistake to infer that every supplied example is conservatively sandboxed: Polly's Codex worker explicitly uses `yolo: true` and `sandbox.type: none`, with a blast-radius policy retaining a narrower destructive-command guard. That is an example configuration choice Wingman would need to revisit ([policy engine](../repo/omnigent/runtime/policies/engine.py), lines 302–415; [Codex worker](../repo/examples/polly/agents/codex/config.yaml), lines 5–12 and 48–65; [blast-radius implementation](../repo/omnigent/policies/builtins/orchestration.py), lines 352–400).

Host and runner IDs route execution, and the workspace is an immutable, canonical host path for a host-bound conversation. Smart routing can choose a compatible model/harness using provider and host availability; native child hooks can consult an authenticated loopback routing relay. Routing is advisory and can fall back unchanged on failure. This is infrastructure/model selection, not business-project intake ([conversation fields](../repo/omnigent/entities/conversation.py), lines 70–82, 148–163 and 202–219; [native routing](../repo/omnigent/runner/subagent_routing.py), lines 1–21 and 97–145; [creation routing](../repo/omnigent/server/routes/_sessions/orchestration.py), lines 11380–11489).

### Concurrency and coordination state

Independent child titles support concurrent workers. Sending a continuation while a child is already running steers that existing turn at a step boundary rather than starting two concurrent turns in one session. An agent blocked inside one long tool step cannot consume the nudge until it yields. A transient “still starting” state is distinguishable from a running turn. Child work receives a dispatch ID distinct from the durable child session ID, allowing later turns of the same child to produce separate results ([send contract](../repo/omnigent/tools/builtins/spawn.py), lines 96–107 and 138–159; [work registry](../repo/omnigent/runner/subagent_work.py), lines 85–90 and 107–162).

The create path explicitly documents an unresolved race: automatic ordinal collisions receive bounded 409 retries, but the server’s parent/title check can still admit concurrent creates because it is SELECT-then-INSERT without a database uniqueness constraint. Stable addressing should therefore not be interpreted as an atomic, globally unique work-claim protocol ([dispatch](../repo/omnigent/runner/tool_dispatch.py), lines 2913–2935; [current database model](../repo/omnigent/db/db_models.py), lines 880–889).

The schema exposes `max_sessions`, but the report does not assume that field alone globally enforces resource capacity. The `spawn_bounds` policy counts selected dispatch tools and denies excess dispatches. It persists the counter in session state because each call can recreate the policy engine. Request events, including completion wakes, reset the counter. This bounds a wave, not lifetime fleet size or an organization's total simultaneous spend. Polly opts into policy-backed fanout and purpose declarations; choosing disjoint files/worktrees and honoring dependencies remains a skill/prompt responsibility ([spawn policy](../repo/omnigent/policies/builtins/orchestration.py), lines 425–562; [Polly skill](../repo/examples/polly/skills/fanout/SKILL.md), lines 8–34 and 48–62).

### Continuity, scheduling and stopping

The database stores conversation items, labels, policy state, usage, relationships and native session references. Runner-local inboxes are ephemeral, so durable child labels record dispatch and delivered IDs. Recovery scans server child/history records and requeues undrained terminal results. It also retains results when the parent's local inbox has not yet been recreated. A transcript is therefore more than an audit log: it helps reconstruct pending coordination after runner restart. This is still recovery logic with explicit failure cases, not an unconditional exactly-once distributed-execution guarantee ([work registry](../repo/omnigent/runner/subagent_work.py), lines 85–104 and 187–198; [recovery](../repo/omnigent/runner/subagent_recovery.py), lines 82–158; [history](../repo/omnigent/runner/session_history.py), lines 31–94).

Recurring automations save an RFC 5545 RRULE, timezone, agent, host/managed target, workspace, budget and new-vs-continue-session mode. The default scheduler reloads active saved tasks and arms process-local timers, skipping invalid rules and preventing overlapping local firing of a running job. A newer persistent scheduler adds database polling, startup leases and recovery. **It is important to retain the release boundary:** `AUTOMATIONS_V2` defaults false, while `SESSION_ORCHESTRATION` defaults true; application lifespan selects one scheduler, so the persistent scheduler must not be credited as unconditional default behavior. Either scheduler can repeatedly instruct a manager, but a saved prompt is not a prebuilt ProjectMaster supervision policy ([scheduled entity](../repo/omnigent/entities/scheduled_task.py), lines 45–127; [default scheduler](../repo/omnigent/server/scheduled/scheduler.py), lines 138–172 and 267–341; [persistent scheduler](../repo/omnigent/server/scheduled/dispatch_scheduler.py), lines 1–39 and 152 onward; [feature defaults](../repo/omnigent/server/feature_flags.py), lines 43–85; [scheduler selection](../repo/omnigent/server/app.py), lines 2063–2125).

There is also **built-in unattended blocker follow-up**, independent of recurring automation prompts. Server lifespan installs `SubagentBlockNotifier` on `pending_elicitations.record_publish`, so published child elicitation requests and resolutions reach it. The notifier arms a process-local `(conversation_id, elicitation_id)` record and waits 120 seconds. It checks whether the same block remains unanswered. It then resolves the child's recorded **immediate parent** and sends a wake notice through the session event/runner path. Top-level sessions have no parent to wake. Delivery makes one initial attempt plus two retries with 0.5-second backoff. An exhausted failure releases its debounce arm so a later republish can retry. Resolution during the grace or retry suppresses stale notices. After a confirmed wake it waits for the matching resolution and sends a follow-up carrying `accept`, `decline` or `cancel`. An absent verdict is explicitly treated as not approved. Thus a parent can follow up on a stalled approval without polling, and is told when that specific block clears ([notifier](../repo/omnigent/runtime/subagent_block_notifier.py), lines 45–55, 143–207, 250–396 and 430–477; [publish hook](../repo/omnigent/runtime/pending_elicitations.py), lines 152–180; [server wiring](../repo/omnigent/server/routes/_sessions/orchestration.py), lines 10612–10724; [lifespan installation](../repo/omnigent/server/app.py), lines 1967–1980). This is a concrete supervision capability, but its debounce/timer state is process-local and its trigger is an elicitation, rather than arbitrary product/ticket stagnation. It does not itself implement a portfolio-wide management escalation ladder.

Interrupts and input steering travel through the harness event interface. Signals set cancellation state and drain pending work within a grace window. Native subprocess cancellation has harness-specific edges: the work registry distinguishes a requested/provisional cancellation from a confirmed abort and allows a later genuine completion to correct a provisional report. Launch timeouts similarly report uncertainty and may be corrected when a child eventually reports its actual outcome ([scaffold](../repo/omnigent/runtime/harnesses/_scaffold.py), lines 17–27 and 87–150; [work-entry states](../repo/omnigent/runner/subagent_work.py), lines 135–162). This is a stronger account of failure than equating a missing heartbeat with task failure.

Failure handling also exists below orchestration: the common LLM retry helper classifies permanent versus retryable failures, applies configured bounded backoff and emits retry events; unknown context-overflow shapes are kept out of automatic compact/retry loops. The common tool helper retries timeout failures but stops on other exceptions and returns an error string for the model to handle. A timeout is not proof that an arbitrary side-effecting operation failed before taking effect. These helpers do not establish identical vendor-internal retry behavior across every native harness. The process manager detects dead processes/missing sockets and lazily respawns under a per-conversation lock; that reconstructs execution capacity, while transcript/receipt recovery restores context and pending results ([LLM retries](../repo/omnigent/runtime/llm_retry.py), lines 50–57 and 289–385; [tool retries](../repo/omnigent/runtime/tool_retry.py), lines 61–90 and 120–145; [process recovery](../repo/omnigent/runtime/harnesses/process_manager.py), lines 726–750).

A child turn completing means its execution returned terminal output. It does not mean a product passed acceptance. Polly adds deterministic gates, independent review and a human-merged PR convention. Retirement is explicit: `sys_session_close` scope-checks the target, writes `omnigent.closed=true`, renames its internal address and archives it so future sends can create a fresh child. Archiving triggers best-effort stop of the execution tree, intentional host-runner teardown where owned, and optional worktree cleanup after stopping. Processes can also be idle-reaped without deleting history ([close implementation](../repo/omnigent/runner/tool_dispatch.py), lines 6775–6831; [archive stop](../repo/omnigent/server/routes/_sessions/orchestration.py), lines 945–1047; [process reaping](../repo/omnigent/runtime/harnesses/process_manager.py), lines 125–140).

## Coordination mechanics and a concrete request trace

There are three different communication mechanisms, which should not be collapsed into “agent chat.” A parent sends an assignment or nudge to a child and receives a completion through an inbox. Independent sessions under one owner can send one another ordinary messages through the normal steering/queue path. Humans can also share and co-drive a session with ACL-governed access. None creates a room whose membership comprises product and technical leadership plus all workers.

The independent-message path is particularly bounded. The server verifies the sending session is owned, available and private or read-only shared. It checks the sender's bound runner token and the destination's ownership. The delivered text becomes a normal input message with a display label. It does not change session parentage, forward replies automatically, or prove that queued input has executed; destination policy can still reject it. This is useful for Wingman agent-to-agent questions, provided an organization layer supplies addressing, membership, decision correlation and acknowledgment rules ([message tool](../repo/omnigent/tools/builtins/session_message.py), lines 8–40; [authorization/message construction](../repo/omnigent/server/session_orchestration.py), lines 36–123).

A representative **Polly coding request** follows an actual code/definition path. This is a static trace, not a claimed observed model run:

1. The human starts the registered/uploaded Polly bundle on a chosen host. `POST /v1/sessions` validates ownership, resolves the project/defaults and creates the conversation. The host launches a runner and its selected harness. Polly's prompt directs a first-turn harness-readiness check so unavailable workers are excluded ([create route](../repo/omnigent/server/routes/sessions/routes_core.py), lines 926–1083; [Polly definition](../repo/examples/polly/config.yaml), lines 66–105).
2. Polly decomposes independent work, creates one git worktree per task and records paths/branches in `.polly/registry.json`. This is an instruction-following orchestration workflow, not a database transaction that atomically assigns tickets. It passes the task, acceptance contract and worktree in `sys_session_send(agent="codex", title="auth-refactor", args={purpose:"implement", input:…})` ([fanout](../repo/examples/polly/skills/fanout/SKILL.md), lines 12–34).
3. The registered tool advertises the allowed child names dynamically. Runtime dispatch verifies the child exists, resolves the parent's bundle, finds an existing matching child or posts a create request, validates overrides and registers child→parent state plus a fresh work ID ([tool schema](../repo/omnigent/tools/builtins/spawn.py), lines 213–246; [runtime](../repo/omnigent/runner/tool_dispatch.py), lines 2618–2654, 2921–2986 and 3018–3079).
4. The child executes its actual coding harness, test commands and PR work. Source edits and tests are the worker's tool operations; Omnigent does not independently establish correctness merely because the session ends. The worker prompt requires exact test evidence and confines review/exploration behavior ([Codex worker](../repo/examples/polly/agents/codex/config.yaml), lines 14–45).
If that worker instead blocks on a human elicitation, the server observer arms the 120-second unanswered-block follow-up and wakes Polly as its immediate parent only if the block persists. A delivered block notice is paired with a verdict-bearing resolution notice when answered. This branch can wake the orchestrator before any child completion ([block notifier](../repo/omnigent/runtime/subagent_block_notifier.py), lines 250–329).

5. Child terminal state/output enters the work registry, is delivered to the parent's inbox and causes a runtime completion wake. The parent's composed instructions explain the known wake shape and tell it to drain `sys_read_inbox`; persisted dispatch/delivery receipts support restart recovery ([work registry](../repo/omnigent/runner/subagent_work.py), lines 857–912; [framework prompt](../repo/omnigent/runtime/prompt.py), lines 25–42 and 62–86; [recovery](../repo/omnigent/runner/subagent_recovery.py), lines 125–158).
6. Polly runs deterministic gates, saves an immutable diff snapshot plus base/head SHAs, and dispatches another vendor to review only that contract/diff. Blocking findings go back to the same implementation conversation, preserving its branch/context. A passing PR is marked ready for human merge; Polly does not merge. A few failed loops lead to human escalation ([cross-review](../repo/examples/polly/skills/cross-review/SKILL.md), lines 13–69).
7. The workbench surfaces the worker's tree/status and lets the human open its conversation/workspace. Cleanup removes an eligible finished worktree under the skill's rules; closing a session invokes the runtime archive/reaping path ([SubagentsPanel](../repo/web/src/shell/SubagentsPanel.tsx), lines 1–15 and 83–126; [fanout cleanup](../repo/examples/polly/skills/fanout/SKILL.md), lines 40–59; [close](../repo/omnigent/runner/tool_dispatch.py), lines 6804–6818).

Dependencies here are primarily the orchestrator's plan and file-scope decisions. The code does not supply a shared task DAG with dependency transitions, organization-wide assignees or enforced integrated acceptance. Shared files must actually be accessible: the cross-review skill explicitly requires transferring its snapshot for another host/sandbox. Likewise, project ownership is private to the human rather than a shared project ACL carried by agents ([project entity](../repo/omnigent/entities/project.py), lines 21–34; [cross-review](../repo/examples/polly/skills/cross-review/SKILL.md), lines 13–20).

## Major additional capabilities and integration consequences

**A meta-harness over heterogeneous execution stacks.** Wingman is described around Codex agents. Omnigent's adapter/scaffold and portable definition boundary let an orchestrator mix Codex, Claude and other native/SDK workers, with model/provider configuration independent of the role prompt. This enables cross-vendor review and task-specific model choice. It also introduces a capability matrix Wingman must respect: terminal takeover, native tools, MCP, fork/resume and policy enforcement are harness-specific, so role contracts need minimum supported capabilities rather than assuming interchangeability ([workflow provider adapters](../repo/omnigent/runtime/workflow.py), lines 605–773 and 1269–1323; [scaffold](../repo/omnigent/runtime/harnesses/_scaffold.py), lines 1–33; [Polly workers](../repo/examples/polly/config.yaml), lines 45–64).

**Managed disposable execution and remote-host operation.** Besides connected personal machines, session creation can select a managed host; automations can provision a fresh managed sandbox for each occurrence. Wingman could isolate product work and avoid requiring the viewing computer to execute agents. Integration needs repository/bootstrap access, credentials, durable artifacts and a policy for sandbox deletion versus resumable product work. Multi-host coordination is real, but it does not replicate local worktrees automatically ([scheduled placement](../repo/omnigent/entities/scheduled_task.py), lines 72–86; [managed-host implementation](../repo/omnigent/server/managed_hosts.py), lines 3828–3895; [host tunnel](../repo/omnigent/server/routes/host_tunnel.py), lines 1–15).

**Programmable governance and spend-aware execution.** Policy phases, persisted state and compositional ASK/DENY provide operational controls beyond Wingman's broad human-judgment description. Spawn bounds and cost-policy attachment can cap delegation/spend and surface approvals. This is valuable for an unattended organization, but policy deployment and permissions need explicit ownership. Child budget-policy installation is non-fatal in the dispatch code. If attachment fails, the requested child budget is not guaranteed. Wingman must decide whether its unattended runs must fail closed ([engine](../repo/omnigent/runtime/policies/engine.py), lines 302–415; [spawn bounds](../repo/omnigent/policies/builtins/orchestration.py), lines 425–492; [budget attachment](../repo/omnigent/runner/tool_dispatch.py), lines 2988–3016).

**Multi-person co-driving, review comments and portable forks.** Session permissions and ownership support shared viewing/editing, and source-anchored comments can be formatted and sent directly as an agent instruction. Fork routes copy history and remap attachment ownership while preserving appropriate project filing and selecting a new harness/host. Wingman could use these for expert review or branching an investigation, but must define how a fork relates to the canonical agent identity, project decisions and accepted deliverable ([review comments](../repo/omnigent/server/routes/comments.py), lines 1–4 and 31–55; [fork implementation](../repo/omnigent/server/routes/sessions/routes_core.py), lines 4209–4255 and 4303–4488; [sharing authority](../repo/omnigent/entities/conversation.py), lines 164–172).

**Scheduled external-work intake templates and Slack service.** Trigger templates construct manager prompts for Jira, Slack, GitHub and Linear, including conditions, scopes and worker placement. This is an agent polling pattern, not proof of a native event-ingestion engine for each external system. The separate Slack integration does implement thread/session routing, streamed answers and elicitation coordination. Both are valuable examples for a Telegram Butler adapter, but require the appropriate external credentials/tools and Wingman's project/decision correlation ([trigger definitions](../repo/web/src/components/scheduled/triggerTemplates.ts), lines 1–49 and 114 onward; [Slack service](../repo/integrations/slack/src/omnigent_slack/service.py), lines 203–236, 309–376 and 606–698).

**Optional semantic long-term memory.** Hindsight retain/recall/reflect tools can persist and retrieve knowledge across runs, with bank identity resolved from agent configuration or agent ID. This complements files and transcripts and could support reusable domain learning. It is an optional external dependency/service, and bank ownership/isolation should match Wingman products and roles instead of accepting an incidental definition-level default ([Hindsight implementation](../repo/omnigent/tools/builtins/hindsight.py), lines 1–31 and 63–85).

## Grounded mechanisms worth carrying forward

These are distinctive implementation choices in this checkout, not claims of historical novelty.

- **Stable session addresses plus per-dispatch receipts.** `(agent, title)` preserves a worker conversation, while dispatch and delivered IDs distinguish successive assignments. The parent inbox can be reconstructed from durable server records after a local queue disappears. This enables continuing specialists without losing unfinished coordination; stale-dispatch/cancellation races still require explicit handling ([send contract](../repo/omnigent/tools/builtins/spawn.py), lines 65–113; [receipts](../repo/omnigent/runner/subagent_work.py), lines 85–90; [recovery](../repo/omnigent/runner/subagent_recovery.py), lines 125–158).
- **Event-driven parent wake instead of constant model polling.** A terminal child result queues an inbox payload and posts a known runtime notice, starting the parent if idle. Separately, unanswered child elicitations wake the immediate parent after a 120-second grace, with bounded retries, stale-block suppression and a verdict-bearing resolution follow-up ([block notifier](../repo/omnigent/runtime/subagent_block_notifier.py), lines 250–396 and 430–477). Framework-owned prompt composition teaches the parent how to handle it separately from portable user-authored role instructions. This reduces supervisory polling and makes the orchestration contract explicit. The model must still drain/process the inbox correctly ([prompt composition](../repo/omnigent/runtime/prompt.py), lines 25–42 and 62–95; [work registry](../repo/omnigent/runner/subagent_work.py), lines 93–104).
- **Completion truth can correct a provisional cancellation.** Work entries retain `cancellation_confirmed`, `corrected_status` and `launch_timed_out`, rather than treating requested cancellation or a launch acknowledgment timeout as definitive proof. This makes supervision more honest under distributed/native-process uncertainty. It does not itself undo side effects from a worker that outlived its intended cancellation ([work-entry model](../repo/omnigent/runner/subagent_work.py), lines 135–162).
- **Cross-vendor review of an isolated diff contract.** Polly deliberately separates implementer workspace/transcript from reviewer input and ties fixes to the same continuing implementer. This can lower shared-context bias and preserve task continuity. Vendor independence, file-scope isolation and the decision to accept a review are workflow instructions, not a mathematically enforced guarantee of reviewer independence or product correctness ([cross-review](../repo/examples/polly/skills/cross-review/SKILL.md), lines 13–20 and 29–75).
- **Persisted policy counters across recreated evaluators.** Spawn bounds uses a stored counter and incremental writes so a newly constructed engine cannot reset delegation limits and delayed ASK approval cannot overwrite intervening increments. This is a useful pattern for Wingman governance, while remaining a per-turn wave limit rather than full resource scheduling ([policy code](../repo/omnigent/policies/builtins/orchestration.py), lines 425–506).

## Practical fit and remaining construction

Wingman could directly reuse the registered-agent/spec/bundle layer, child conversation execution, host/runner transport, live workbench, lifecycle controls, structured questions and policy hooks. Polly is a useful technical-team prototype, and its receipt-backed inbox/wake model is especially relevant for manager-to-worker delegation. A Codex-only Wingman could initially narrow the supported harness set rather than carrying every adapter into its product contract.

Adaptation is needed to make an agent instance an organizational actor:

- Introduce an employee/role/project identity above conversations.
- Preserve that identity across forks, task sessions, host changes and retirement.
- Select secure role defaults.
- Connect every delegated session to a real ticket.
- Arrange actual cross-host artifact access. Agent definitions can remain reusable profiles, but neither their ID nor their active session title should be the sole record of a person's responsibilities.

The major new work remains:

- Butler's Telegram transport and correlation.
- ProjectMaster's registry/intake and portfolio-wide supervision policies beyond the existing child-elicitation follow-up.
- per-project ProductMaster/TechMaster leadership.
- proportionate discovery and scope/spec/DoD records.
- ProjectTracker with dependencies/assignees/blockers.
- shared room histories and decision routing.
- integrated TestMaster acceptance.
- executive current/recent/next briefings with evidence-linked timelines.

The existing UI could host those views, but a session tree, todo panel or automation list should not be presented as though those domains already exist.

A practical architecture is therefore **Wingman organizational services over Omnigent execution/workspaces**, with explicit links among project, ticket, role instance, conversation, host and artifact. Replacing Wingman wholesale with a Polly prompt would lose the product/portfolio continuity and shared human-facing records that define the target.
