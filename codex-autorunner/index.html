Baseline: Wingman purpose

Fit verdict

CAR is a strong candidate for Wingman's execution and operator-control foundation. It already combines coding-agent backends, durable managed conversations, repository/worktree scope, ticket execution, Telegram/Discord interaction, a web hub and scheduled/event-driven follow-up. Its PMA is a genuine model-driven management interface that can spawn and message other managed threads.

Its organizing model is a hub of resources, managed threads and ticket flows. Wingman's standing organization, per-project ProductMaster/TechMaster relationship, agent collaboration rooms and executive employee briefing would still need explicit product work. In particular, CAR's rich timeline is an execution projection. It is not the complete current/recent/next-work summary for each enduring employee that Wingman describes.

This revision is substantially broader than a simple loop over Markdown tickets. The execution, conversation and delivery machinery deserves separate consideration from the organizational behavior supplied through PMA prompts.

Architecture and implementation evidence

The implementation has a Python engine, runtime adapters, FastAPI surfaces and a SvelteKit frontend. Repository-local files hold tickets and context; orchestration has SQLite-backed identities, executions, queues and delivery records. A managed thread is an orchestration-owned conversation bound to an external agent runtime, not an always-running employee process.

The executable entry is car/codex-autorunner → Python CLI (package scripts, lines 65–67). car serve loads hub configuration and creates the FastAPI hub under Uvicorn (serve command, lines 702–739). The service factory, lines 19–58, binds a runtime descriptor catalog and harness factory to the managed-thread execution store, and exposes ticket flow as a separate flow target. This is a shared orchestration service consumed by operator surfaces, not a frontend that independently owns workers.

Ticket execution follows another concrete entry: runtime helpers, lines 53–92 and 115–154, load repository configuration, build the backend/pool, construct a validated ticket-flow definition and FlowController, persist a run, then ensure a background worker. Closing a temporary controller session does not imply ending the work: the spawned worker drives subsequent steps. The flow database/artifacts are repository-scoped, while managed identities, execution queues, automation and delivery use the hub orchestration store. State roots, lines 7–38 and 99–116, explicitly distinguish repo, hub and global roots; SQLite startup, lines 377–469, owns migration preparation and compatibility metadata. “Filesystem truth” therefore includes both inspectable Markdown work and durable database control state.

Agent definition and lifecycle

Definition, creation and identity

There are three distinct concepts. A registered backend descriptor identifies a runtime such as Codex or an ACP agent. A profile specializes configuration such as binary, command, endpoint and subagent models. A ThreadTarget is a durable conversation with an orchestration-owned ID, optional profile, resource scope, backend conversation ID and runtime instance binding.

The separation is useful: CAR can retain the managed conversation even when a backend process is replaced or its binding becomes suspect. It also prevents calling the runtime catalog an employee directory. To model Wingman, an employee would need an explicit association with role, team, project responsibilities and potentially more than one managed conversation.

The executable backend boundary is concrete. AgentHarness, lines 36–178, defines new/resume conversation, start/wait turn, interrupt, transcript and event-stream capabilities. The registry, lines 39–79, supports built-in descriptors and Python entry-point plugins with an API version and validated capabilities. CodexHarness, lines 118–165, connects those operations to a workspace app-server supervisor. Thus adding a runtime backend and adding an organizational role are different extension operations.

Creation is deliberately split between durable identity and live runtime allocation. Thread service creation, lines 185–219, checks that the named definition exists and supports durable threads, then asks the store to create a target. The concrete store, lines 656–702 and 761–846, generates/validates a UUID, resolves agent/profile/scope metadata, inserts orch_thread_targets, and emits a lifecycle event. Merely creating that record does not launch a model or create a specialist role.

When a message arrives, execution preparation, lines 784–919, resolves the thread/workspace/capabilities, constructs the canonical request, records visible prompt separately from assembled runtime context, and persists execution/queue state. Runtime startup, lines 376–563, ensures the harness is ready, inspects runtime binding, resumes an existing backend conversation or starts a new one, and persists its new binding. Recoverable resume failure invalidates the old binding and retries fresh. CodexHarness, lines 191–205, actually calls app-server thread_start. This is a real coding session, not a role string repeated in one chat.

DefaultAgentPool uses these owned targets for ticket work, with run/ticket metadata allowing the same ticket conversation to be found again (binding lookup, lines 433–478). Roles can be supplied as instructions and project files, but the inspected profile schema contains runtime settings rather than a reusable organizational job description. A ticket is a file-backed assignment. An execution is a single turn. A managed thread is durable conversation continuity. A supervisor handle is an OS-runtime resource. None alone is the enduring Wingman employee spanning many assignments. Multiple threads of the same runtime/profile give independent specialist instances only after that organizational meaning is supplied.

Permissions, execution and concurrency

Permissions and model options are resolved by backend/runtime capabilities. The configuration is not a universal permission sandbox. For example, the multi-agent review service defines restrictive read-subagent permissions for OpenCode, while ordinary agent execution can have broader permissions. Integration must preserve backend differences rather than assuming every agent supports every control.

Within a managed thread, busy policies distinguish queuing, interrupting and rejection. Across threads, independent workers permit concurrency. A ticket directory, however, uses a single selected ticket and ordered advancement. A depends_on field is explicitly not the runtime ordering contract in PMA's instructions; filenames determine order. Parallel projects would use distinct flows/threads/worktrees with an additional coordination policy.

The ordinary MessageRequest path, lines 798–914, builds a canonical turn request. An unspecified sandbox defaults to dangerFullAccess. The path validates the caller's model against runtime capabilities. It stores the visible prompt separately from the assembled runtime prompt. Interrupt-on-busy attempts to stop the active execution. It refuses the new request if that execution still exists. These are execution policies. They do not establish isolated worker permissions.

The pool's _ensure_thread_worker and _drain_thread_queue, lines 924–983, ensure one drain task per managed thread and advance queued turns sequentially. Exceptions become failed execution records rather than escaping the worker loop. Ticket metadata links conversations to flow-run and ticket IDs, allowing a resumed ticket to find its existing managed target. The unit of continuity here is often the ticket conversation, which reinforces why Wingman needs a separate enduring employee identity.

Process ownership is also workspace-based. WorkspaceAppServerSupervisor, lines 210–330, canonicalizes workspace roots, reuses handles, prunes idle handles, applies LRU eviction/process budgets and builds clients with restart and stall-recovery options. Several agent conversations can therefore use a supervised runtime process; independent conversations do not imply one permanent OS process per employee.

Tool use remains backend-owned: the harness passes prompt, model, reasoning, input items, approval and sandbox options to the runtime (harness interface, lines 90–103). CAR normalizes tool/progress events for the operator, but does not implement one universal coding tool sandbox. Ordinary message conversion defaults approval policy to never (request conversion, lines 390–417); unattended automation has a different policy path and may pause or auto-decline (executor, lines 121–145). Wingman integration must make the intended policy explicit across these entry points.

Scheduling, steering and cancellation

The hub lifecycle orchestrator, lines 354–385 and 442–462, wires scheduler, worker and child reconciliation into the hub cycle. The automation scheduler, lines 36–85, uses due timestamps to generate stable schedule.fire:<schedule>:<time> events, invokes the rule engine and advances the schedule. This supports interval/daily/weekly and one-shot wakeups. The worker, lines 90–173 and 246–295, leases jobs, releases stale claims, defers concurrency blockers, records attempts and retries with capped exponential backoff; exhausted jobs can generate deduplicated failure-escalation jobs. PMA instructions add terminal subscriptions and idle watchdogs, but a product manager’s judgment about stalled development is supplied by the model and authored rules.

This is more than a timer that reports success after enqueueing a prompt. The managed-turn automation executor, lines 303–374, creates the queued turn, records an authoritative parent-job/child-execution edge with requested runtime, checks that edge is durable, and requests the queue worker. The execution graph projection, lines 21–88, connects jobs to agent tasks, PMA queue entries, ticket flows and publication operations. This is execution lineage/concurrency and completion accounting. It does not make ignored ticket depends_on fields into a general product task dependency graph.

Human steering uses a target ID and queue policy. Busy-thread queue/interrupt/reject semantics avoid treating every new instruction as an unrelated session; interrupted work must durably leave the running state before replacement execution proceeds. Service controls, lines 1057–1087 and 1278–1333, separate interrupt/stop from cancelling or promoting queued turns. Stop handling, lines 502–517, has an explicit cancel_queued switch. Fork and compact are exposed by the managed-thread CLI, lines 1906–1944 and 2190–2216; compaction stores a seed and should not be confused with an executive accomplishment summary.

Persistence, retry and restart

CAR stores execution state separately from runtime progress and surface delivery. Recovery classification, lines 76–105 and 177–207, examines execution phase/age and canonical request context, classifies a recovery action and records the decision. It can mark runtime bindings suspect or invalid rather than treating any old provider session ID as resumable.

The delivery ledger separately stores final-delivery intent with idempotency keys, claim expiry, attempt state and retry backoff. This matters because “agent finished” and “Telegram received the answer” are different events. Failed delivery can be retried without automatically redoing the coding turn.

The managed-turn lifecycle contract, lines 6–95, makes the boundary precise:

accepted → queued/runtime_starting → runtime_running
    → runtime_terminal_observed → terminal_recording → terminal_recorded
    → delivery_enqueued / side_effects_pending → side_effects_complete

terminal_recorded is the queue-unblocking boundary. Timeline writes, delivery, transcript projection, archive cleanup and other optional effects have their own later completion. Duplicate terminal recordings are recognized. A conflicting late outcome preserves the first durable result. This avoids making downstream transcript or notification failure indistinguishable from a coding turn failure. The inspected lifecycle tests cover those distinctions, although they were not run during this assessment.

Ticket retries also distinguish network failure, invalid ticket frontmatter, commit-resolution failure and no-progress loops. TicketRunConfig, lines 84–98, supplies separate limits; reaching the overall turn budget pauses for review (runner, lines 96–109 and 387–443). These are operational safeguards around file-backed work, not a guarantee that the model has correctly understood a business product.

Completion, retirement and cleanup

After a turn, post-turn processing, lines 47–126 and 630–718, rereads ticket frontmatter, archives dispatches, creates a turn summary and checks worktree/commit state. A done ticket with unresolved dirty changes remains pinned behind the commit barrier; exhausted resolution pauses rather than advancing silently. When no incomplete ticket remains, the run completes.

A managed thread can be archived/retired independently of a run. PMA's fast path protects chat-bound threads from broad cleanup instructions by default. This is a useful continuity policy for Wingman's ongoing human relationship, although retaining a conversation alone does not implement product-team membership.

Pool shutdown cancels drain tasks, cancels unresolved execution waiters, clears emitters and closes supervisors it owns while leaving externally supplied shared runtime services alone (close_all, lines 481–518). Runtime-process cleanup, managed-thread retirement and completed product work are therefore separate lifecycle concerns.

Coordination trace: a blocked ticket and Telegram reply

This is a source-traced scenario, not an executed Telegram session. Assume a configured repository flow is implementing a ticket and needs a product decision:

  1. Ticket-flow startup, lines 115–130, persists the run then ensures a worker. TicketRunner.step, lines 119–149, archives any user reply and invokes selection. Selection, lines 168–199, finds the next incomplete numbered ticket. No agent votes on a shared backlog here. The file order and done flag decide.
  2. The runner builds prompt/options and attaches run ID, ticket ID/path/profile before calling execute_turn_with_thread_binding_retry (runner, lines 285–322). The pool resolves/reuses a managed conversation and drains its runtime queue. Project knowledge and reply history enter the worker prompt; task coordination is carried by files plus durable execution records.
  3. The worker writes a Dispatch(mode="pause") artifact. Post-turn archival, lines 47–126, archives dispatch and agent-output summary; lines 642–653 return a paused ticket result. The pause is a durable handoff rather than a transient question printed to a terminal.
  4. Telegram bridge, lines 236–329, loads the pause, chooses a bound topic, records a run/dispatch dedupe marker and sends the full dispatch, restoring prior markers on caught failure. Lines 549–634 send chunked text, configured attachments and a mirrored outbound chat record. A preferred Discord binding can suppress Telegram delivery, so this behavior depends on configured routing.
  5. Reply submission, lines 40–81, accepts the resolved paused run and media, writes the user reply, acknowledges it and attempts resume only on success. Bridge resume, lines 411–431, resumes the controller and spawns a worker; caught failures are logged, so successful reply persistence does not by itself prove successful continuation.
  6. The next runner step archives/loads reply context and continues that ticket. Completion is still reread from the ticket file, with dirty done tickets pinned behind the commit gate (post-turn, lines 655–718; selection, lines 103–175). A model answer, terminal runtime result, ticket completion, flow completion and delivered Telegram answer are distinct states. This is strong ticket-mediated coordination and human escalation. It does not automatically create a conversation among a backend employee, a frontend employee and a ProductMaster in a shared project room.

Major additional capabilities

A provider-independent meta-harness. The registry, lines 15–57, connects Codex, OpenCode, Hermes, OMP and ACP-related adapters and admits entry-point backends; catalog construction, lines 44–75, normalizes capabilities. Wingman currently names Codex. This could expand its workforce, at the cost of runtime-specific lifecycle and permission testing. A normalized API is not operational parity.

Programmable ticket execution and worktree lifecycle. Ticket frontmatter, lines 20–38, combines runtime/profile/model with contextual file includes, and selection, lines 103–175, enforces a clean-commit barrier. PMA guidance, lines 55–73, chooses bounded conversational work versus ordered ticket work and PR-mode worktrees. This enables a light path for small requests and a durable delivery queue for larger changes. Integration must preserve that distinction and supply cross-worktree integration ownership.

Durable communication delivery. The ledger and engine, lines 49–79 and 409–469, register idempotent final-delivery intent, claim work, recover expired claims and apply retry budgets. A failed send need not rerun coding. The model's successful completion and the human receiving the result remain separately observable states, with backend/surface integration still requiring runtime validation. This is substantial infrastructure beyond connecting a bot handler.

Generalized automation with execution lineage. Scheduling, lines 36–85, job execution, lines 90–173, and authoritative child edges, lines 303–374, distinguish starting work from completing it. Follow-up can be event-driven as well as periodic, with concurrency, attempts and escalation inspectable. Wingman could use this for supervision; business priorities, escalation recipients and rules must still be configured.

Multi-agent code-review workflow. The review service, lines 104–160 and 213–259, supplies coordinator/scratchpad and independent exploration/pruning instructions. Lines 943–985 configure OpenCode read subagents with edit/write/bash/task denied and restrict the coordinator's Task targets. This adds a concrete review workflow beyond Wingman's developer/tester baseline. Delegation strategy is model-directed within those constraints, not a deterministic independent-review guarantee; adoption must test each backend and keep code review distinct from product acceptance.

Installable workflow applications. App manifests, lines 12–91, define templates, executable tools, typed outputs, hooks and declared permissions. Hook execution, lines 148–239, attaches behavior after a ticket, terminal flow, archive or before chat wrap-up, with warn/pause/fail outcomes. This packages repeatable workflows and generated evidence beyond another worker profile. The tool runner, lines 94–164 and 216–240, refuses untrusted or modified bundles and checks ticket provenance before running the declared subprocess. Those are useful trust controls; manifest read/write/network declarations alone do not establish a process sandbox.

SCM feedback automation. SCM automation, lines 1502–1540, 1755–1843 and 2082–2098, connects PR bindings, CI failures and review comments to managed turns, chat notification and a publication journal. Review comments can be batched by time window and failed/no-target routing has durable audit evidence. Wingman describes delivery generally; CAR supplies a specific external code-review/CI feedback loop. Adoption requires provider authentication, PR/thread ownership and publication/escalation policy rather than simply enabling a generic supervisor timer.

Managed previews and demonstration evidence. PreviewServiceSupervisor, lines 144–240, 324–423 and 450–503, registers static/loopback previews and manages command services with ports, health checks, logs, restart and teardown. Browser workflow orchestration, lines 116–166 and 236–324, combines service readiness, scripted capture, video/trace settings, artifact export and outbox publishing. This could give Wingman a delivery-preview/evidence product, while remaining local-process infrastructure; capture success is not a proof of every acceptance scenario.

Distinctive mechanisms and innovation

The most useful combination is file-authoritative work plus a durable orchestration ledger (selection, lines 103–175; managed identity insert, lines 761–846). Tickets remain editable and inspectable while execution, transcript and delivery have stable identities. The limit is that files and database projections must remain reconciled, and neither validates the business truth of a done flag.

The managed-thread/flow split (service factories, lines 19–58; PMA policy, lines 55–73) gives a bounded task conversational execution and structured work an ordered ticket state machine. Wingman could avoid imposing a large process on every request. The choice is guided by the PMA prompt, so a team policy must make its use predictable.

Attention projection and targeted automation (attention, lines 317–378; scheduler, lines 36–85) turn management input into a bounded actionable list with freshness, supersession, background counts and drill-downs. This reduces the context needed on a wake. It is useful supervision infrastructure, not the full executive current/recent/next briefing per employee.

The terminal-record boundary (lifecycle contract, lines 42–90 and 102–140) first records execution outcome/unblocks the queue, then repairs delivery/transcript/other side effects separately. With runtime-binding invalidation and transcript-seeded rehydration, it enables continuity without asserting that a restarted provider is the same live session. Its limit is semantic continuity: a bounded transcript and compact seed cannot prove retention of everything the previous model knew.

These are distinctive mechanisms in this checkout, not a claim that CAR originated them industry-wide.

What to reuse, adapt and build

Reuse candidates include managed conversation ownership, adapter boundaries, ticket execution, worktree setup, Telegram delivery and scheduled/event follow-up. Adapt scope identities into Wingman projects and add an enduring agent/team layer above conversations. Keep the useful distinction between lightweight conversational work and ordered delivery flows.

Build the explicit Butler/ProjectMaster separation, per-project ProductMaster/TechMaster collaboration, discovery-readiness workflow, agent room membership and executive agent briefing. Multi-host execution needs a real placement/shared-context design rather than relabeling a Docker destination. Product acceptance must assess integrated behavior and the product DoD above file status and commit cleanliness.

Retained CAR research findings

Scope

The older research used commit 3bedfe817e6fc70eb16650f216eca93cd37fa411. Its narrative reports 237 focused passes in groups of 102, 99, 20, and 16. No separate raw test log was retained. Treat that count as a historical narrative claim. The current technical assessment governs the Wingman fit verdict.

Findings that remain useful

CAR has two separate execution models. An ordered ticket flow selects unfinished work and evaluates its outcome. A managed thread retains a conversation binding and execution records. PMA can direct several managed threads independently. Do not describe the whole product as one serial ticket loop.

The message contract has queue, reject, and interrupt policies. Queue admits later work. Reject refuses work while the target is busy. Interrupt stops the current execution before it prepares another execution. This path does not establish native in-flight turn/steer behavior.

A done ticket can encounter a commit barrier when the working tree remains dirty. Persisted retry and pause state supports recovery. A stale-worker cleanup observation cannot replace the user's requested lifecycle state. Completion delivery and autonomous PMA follow-up also have separate conditions.
