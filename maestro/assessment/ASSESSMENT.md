# Maestro assessment

## Identity and fit verdict

- **Product:** Maestro, package version 1.0.3. A multi-provider coding-agent workbench with desktop, browser/mobile, CLI and opt-in automation subsystems.
- **Repository:** https://github.com/RunMaestro/Maestro
- **Local checkout:** `research/maestro/repo/`.
- **Actual checked-out commit:** `5b4d5e4f190a1701024d0567fa85aad458c59104`.
- **Assessment date:** 2026-11-05.
- **Method:** read-only source and test inspection. No dependencies installed, application launched, services started, model calls made or SSH connections exercised. The checkout was not modified.

**Verdict: a substantial execution, collaboration and visibility foundation for Wingman, with more organizational machinery than a terminal manager, but not a ready-made Wingman organization.** It runs independent coding providers and persists identities and conversations. Group chats support delegation. SSH hosts supply remote execution. It generates cross-agent briefings. Its optional Pianola manager supplies durable task dependencies, polling supervision and human escalation. These deserve credit as implemented mechanisms rather than roadmap promises. The missing center is Wingman's product organization: Telegram/Butler intake, an explicit product registry, separately accountable ProductMaster and TechMaster instances, discovery-to-specification ownership, and integrated product acceptance.

Several limits materially affect adoption. Pianola's automatically created manager is Claude Code, not Codex. Agent specialization is chiefly configuration and prompts rather than a reusable role/profile domain model. Some supervision and dashboards are opt-in Encore features. Background execution is owned by the desktop process, not an independently deployed organizational service. A process returning idle or checking off Markdown can still mean completion without independent acceptance evidence. The Pianola auto-merge hook explicitly records a skipped merge because no merge execution path is available there. These are boundaries of this revision, not claims about all future releases.

The comparison uses [Wingman's purpose](../../WINGMAN_PURPOSE.md) and the full [assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md). The checkout's `AGENTS.md` is a symlink to [CLAUDE.md](../repo/CLAUDE.md); its terminology distinguishes a user-visible Maestro agent from provider sessions (lines 398-405). That distinction is essential throughout this report.

## Architecture and actual execution model

### One local control plane, several execution paths

The application entry is the Electron main process declared in [package.json](../repo/package.json), lines 1-21. [main/index.ts](../repo/src/main/index.ts), lines 304-347, 985-1012, 1267 onward and 2882-3009, initializes persisted stores, constructs `ProcessManager`, constructs Cue, initializes history/stats, wires IPC, and attaches run capture. A React renderer owns the active workspace and substantial session, tab, queue and batch-run behavior. The preload namespaces expose main-process functions to that renderer. This is a desktop application with a main-process automation substrate, not a server fleet that happens to have a desktop client.

A named sidebar agent is represented by the historically named `Session` interface. It contains an ID, name, provider, working directory/project root, group, logs, execution queue, AI tabs, terminal/browser/file tabs, worktree relationships, model/environment overrides and SSH configuration. See [renderer/types/index.ts](../repo/src/renderer/types/index.ts), lines 1317-1575. Each AI tab can bind a different provider conversation. Creating an agent initially allocates a durable configuration/workspace record and idle tab. It does not launch an always-running intelligent process.

When prompted, main-process spawn handlers resolve provider arguments and account/model settings and call `ProcessManager`. [ProcessManager.ts](../repo/src/main/process-manager/ProcessManager.ts), lines 43-91 and 208-274, chooses a PTY for terminals, a child-process runner for ordinary agent turns, or an opt-in OpenCode SDK server path. Output parsers translate provider-specific JSON streams into text, tool activity, usage, session IDs and error events. An agent therefore has independent execution when active, but many provider turns are short-lived processes resumed by provider session ID rather than a resident process with a durable brain.

The command line has two meanings. Commands such as `create-agent` use `withMaestroClient` to send WebSocket commands into the running desktop control plane: [create-agent.ts](../repo/src/cli/commands/create-agent.ts), lines 129-168. Batch playbook/goal execution also has CLI-owned spawn loops that can execute providers and record their activity: [batch-processor.ts](../repo/src/cli/services/batch-processor.ts), lines 58-112, and [goal-runner.ts](../repo/src/cli/services/goal-runner.ts), lines 125-137. “Has a CLI” consequently does not mean every organizational action is available with the desktop shut down.

The browser desktop reuses renderer behavior through a WebSocket IPC bridge. The main [WebServer.ts](../repo/src/main/web-server/WebServer.ts), lines 1-25 and 33-65, is Fastify plus WebSocket, token-scoped routes, origin validation, optional login and a live-session manager. Its current header describes loopback binding for the always-on CLI channel and optional LAN access for Live Mode. A phone is a remote viewing/control surface. It is not a separate execution host. The desktop can keep running when the viewer disconnects, while app exit ends desktop-owned processes.

### Persistence is deliberately split

The identity/session registry and settings use Electron stores, while append-oriented history, group-chat logs, provider-native conversations, Cue state and run ledgers have distinct stores. [persistence.ts](../repo/src/main/ipc/handlers/persistence.ts), lines 501-513 and 545-597, exposes bootstrap/deferred-content reads and serialized incremental merge/removal writes. [useDebouncedPersistence.ts](../repo/src/renderer/hooks/utils/useDebouncedPersistence.ts), lines 68-82, 107-158 and 234-246, resets ordinary runtime busy state to idle, preserves special quota pauses and the execution queue, and excludes temporary wizard state. Persisted state is not proof that a process is still working.

[history-manager.ts](../repo/src/main/history-manager.ts), lines 489-514, appends per-agent JSONL history under serialized writes. Group chat has `metadata.json`, `chat.log` and image attachments, with per-chat write queues plus atomic JSON replacement: [group-chat-storage.ts](../repo/src/main/group-chat/group-chat-storage.ts), lines 20-34, 47-95 and 120-162. Provider transcripts remain provider-specific; Maestro adds navigation, names, usage and context operations rather than replacing them with one universal conversation store.

The AgentRun ledger binds executions to provider, agent, session/tab, cwd/worktree, branch, prompt, artifacts, touched files, checks, reviews, PR and merge outcome. Its record is richer than a log line: [agent-run/types.ts](../repo/src/shared/agent-run/types.ts), lines 1-12 and 109-150. Capture is attached to spawn/exit, uses unique run IDs, and explicitly excludes terminal and group-chat processes: [capture-service.ts](../repo/src/main/agent-run/capture-service.ts), lines 2-19 and 71-84. Thus even this useful ledger is not a comprehensive transcript of every collaboration process.

### Three coordination engines coexist

1. **Group Chat:** a moderator provider emits actionable participant mentions. The router spawns participant turns and then a moderator synthesis. It is a real model-mediated communication and delegation mechanism, with persistent room metadata and message history.
2. **Pianola:** a pinned Claude manager uses the CLI; separate supervised watcher/orchestrator processes apply policies and run durable task DAGs. The reasoning agent and the deterministic supervisor are distinct components.
3. **Cue:** project-local YAML subscriptions turn time, filesystem, task, GitHub, webhook and completion events into prompts, commands or notifications. It has its own subprocess lifecycle, concurrency limits, persistent queue and SQLite event history.

The [Campaign model](../repo/src/shared/campaign/types.ts), lines 26-57, also persists objectives, task dependencies, run IDs, worktree/branch and check/review/merge summaries. Pianola projects its plan into a campaign, and the [campaign list](../repo/src/renderer/components/AgentRunDashboard/CampaignList.tsx), lines 28-51, presents titles, status, objectives, run/task counts and drill-down. This is a real effort-level dashboard primitive, not merely a terminal grid. Campaigns still lack the continuing product registry, leadership, discovery records and accepted specification ownership Wingman requires.

These mechanisms can cooperate, but their task/message/run identities are not one unified Wingman tracker. An adoption plan needs explicit mappings rather than assuming a room mention, a playbook checkbox, a Pianola task and an AgentRun are interchangeable.

## Agent definition, creation and lifecycle

### What is actually an agent?

There are at least six different objects that must not be collapsed:

| Concept | Actual meaning and durability |
|---|---|
| Provider definition | A built-in executable/argument/capability description, such as `codex` or `claude-code`. It is neither a worker instance nor a persona. |
| Maestro agent (`Session`) | Durable named workspace/configuration, with group, project root, tabs and overrides. It is independently executable when prompted. |
| AI tab/provider session | A conversation context; its provider-issued ID permits resume. A tab is not a new organization-wide role by itself. |
| Process session | An execution handle used by ProcessManager, Cue or room/consult routers. It may live for one turn. |
| Pianola task / playbook checkbox | A work unit assigned to an agent or executed by a runner. It is not an independent agent. |
| AgentRun | A durable execution/evidence record, not a continuously running person or a project specification. |

[AgentConfig](../repo/src/main/agents/definitions.ts), lines 85-162, specifies binary, mode arguments, resume/read-only/model/working-directory/image/prompt builders and capability behavior. Codex's particular definition, lines 258-290, shows the consequence: a normal batch turn uses `exec --json` with approval/sandbox bypass, while read-only turns use a different sandbox argument set. Provider “supports read-only” is executable-specific behavior. Additional directory access is explicitly provider-dependent or prompt-only, lines 109-124. One cannot treat a named specialist as a sandbox boundary simply because its instructions mention a directory.

Role specialization is possible through name, `nudgeMessage`, `newSessionMessage`, configurable system prompts, cwd, environment/model/effort and external instructions. The `Session` model has no required role ID, responsibility taxonomy, project leader linkage or declared team membership beyond generic groups and room/worktree relationships. A Wingman implementation could add those while reusing the execution objects, but a “BackendCoder” name alone would not provide the ownership semantics Wingman expects.

### Creation and identity

Manual/wizard creation converges on `createNewSession`: it looks up a provider, validates name/path, generates agent and initial-tab IDs, probes local Git state unless remote, then builds an idle record with `aiPid = 0`. The implementation is [useSessionCrud.ts](../repo/src/renderer/hooks/session/useSessionCrud.ts), lines 152-280. [sessionValidation.ts](../repo/src/renderer/utils/sessionValidation.ts), lines 16-69, makes names globally case-insensitive unique and allows same-host same-directory sharing with a warning. Multiple specialists can run in one repo, but worktree separation is preferable because the directory warning does not coordinate writes.

CLI creation sends a `create_session` command including provider, cwd, group and optional nudge, environment, model, effort, SSH and runner-folder settings. [create-agent.ts](../repo/src/cli/commands/create-agent.ts), lines 37-48 and 101-168, validates the provider against built-in `AGENT_IDS`. Its successful return has the new `agentId`; execution is a separate dispatch. An important extension boundary follows: a plugin runtime provider descriptor is not automatically accepted by this built-in-only creation validation.

Pianola creation is special rather than a generic manager-role template. [usePianolaAgent.ts](../repo/src/renderer/hooks/session/usePianolaAgent.ts), lines 32-83 and 85-137, waits for hydration, gates on `encoreFeatures.pianola`, deduplicates and creates one `isPianola: true`, `toolType: 'claude-code'` agent. Disabling the feature hides the persisted manager and halts its supervised targets, rather than erasing its history. Wingman's Codex-only standing-manager requirement would require a deliberate provider-neutral manager change.

### Execution, tools and routing

Normal interactive work follows renderer input/queue -> main spawn handler -> provider argument builder -> ProcessManager -> provider parser -> renderer events and persisted tab/session. Batch providers spawn per turn and resume their provider-native context using the stored conversation ID. Terminal tabs use PTYs. Optional OpenCode server execution is another adapter, not evidence that all providers have a persistent server runtime.

Maestro delegates actual coding tools to the installed provider CLI and its account/config. The application can supply working directory, mode, environment, additional directories, model and system instructions. It also has approval/question relay infrastructure: [PermissionRelayServer.ts](../repo/src/main/permission-relay/PermissionRelayServer.ts), lines 1-16 and 94-131, creates a per-user local socket with per-spawn tokens and forwards requests to a renderer callback. This is a separate channel from Pianola's transcript-classification policy. Default unattended coding arguments can bypass provider approvals, so a permission relay is not proof every automated action awaits user authorization.

Direct `@mention` consultation intentionally launches a fresh ephemeral process for the target, not a write into its active user conversation. [cross-agent-router.ts](../repo/src/main/cross-agent/cross-agent-router.ts), lines 6-31 and 164-182, forwards source context and defaults consults to read-only. A dedicated target consult tab/provider ID preserves the source-tab-to-target relationship across calls. Writable consults require the corresponding setting. Group chats instead use participant metadata and moderator routing. They do not run the same conversation as a user's direct tab merely because the participant has the same name.

For SSH, per-agent host config is resolved centrally and the spawn is wrapped with remote cwd/environment/prompt delivery. `spawnGroupChatAgent` explicitly fails if SSH is enabled without a store or the wrapper returns no resolved remote, lines 179-239. This prevents the wrong-host fallback identified by comments in that code. The remote provider is a real process on that host; central logs/room state remain local to the controlling Maestro instance unless separately mirrored.

### Concurrency, scheduling and supervision

Different agents/tabs can execute concurrently. A session also has an execution queue for sequential input. Shared-directory safety is not automatic. Group Chat normally waits when a target agent is busy, polling until it is free and giving up after 15 minutes: [group-chat-router.ts](../repo/src/main/group-chat/group-chat-router.ts), lines 1245-1359 and 2140-2166. That protects a delegated turn from overlapping the person's own conversation by default, but it is not a repository-wide transaction/merge scheduler.

Pianola's task DAG has explicit readiness and blocked propagation. [pianola-orchestrator.ts](../repo/src/shared/pianola/pianola-orchestrator.ts), lines 147-205 and 263-310, polls live tasks first, updates outcomes, blocks dependents and fills available concurrency slots. Creation/dispatch failures leave tasks pending. A failed dispatch preserves the chosen agent ID so the next poll does not create orphan workers. The CLI default concurrency is 3 and default polling cadence is 5 seconds: [pianola-orchestrate.ts](../repo/src/cli/commands/pianola-orchestrate.ts), lines 170-183 and 744-791. If a task has no pinned provider, the CLI counts live provider types and the plan's in-flight load. It selects a ready type before creating a fresh task agent. But all candidates are assigned the same `DEFAULT_CAPABILITIES`, and an empty/busy pool falls back to Claude Code rather than a validated Codex-only resource pool: [pianola-orchestrate.ts](../repo/src/cli/commands/pianola-orchestrate.ts), lines 600-658. This is load-aware provider allocation, not specialist skill matching or a host placement policy. These tasks are durable plans, not a guaranteed portfolio scheduling policy.

The watcher acts when agents await input. It combines structured signals/transcript heuristics with scoped rules; high-risk always escalates, low-confidence classifications do not auto-answer, and broad rules without narrowing predicates are rejected by policy. [pianola-policy.ts](../repo/src/shared/pianola/pianola-policy.ts), lines 121-190. The watcher can hand uncovered non-high-risk asks to Pianola with a learned project decision profile, then escalate if the manager does not answer. Its dispatch attempt limit is 3, handoff timeout is 12 polls, missing-tab grace is 2 minutes and default idle retirement is 6 hours: [pianola-watcher.ts](../repo/src/shared/pianola/pianola-watcher.ts), lines 25-49 and 102-145. This is actual blocker follow-up, with heuristic limits, rather than a guaranteed product-management judgment.

A desktop-owned supervisor stores enabled watcher/orchestrator targets and reconciles them at startup and on store changes. It caps consecutive crash restarts at 5, exponentially backs off from 1 second to 30 seconds, and escalates termination after 5 seconds: [pianola-supervisor.ts](../repo/src/main/pianola/pianola-supervisor.ts), lines 34-51 and 134-209. It distinguishes long-running watches from orchestrations that have cleanly completed. Its children are explicitly not detached and die with the app. The environment survives a closed browser view. It does not become an unattended service independent of the Electron app.

Cue provides a second scheduling substrate. [contracts.ts](../repo/src/shared/cue/contracts.ts), lines 24-51, 115-154 and 349-393, defines trigger/action types, per-session concurrency and queue defaults. [cue-run-manager.ts](../repo/src/main/cue/cue-run-manager.ts), lines 255-380, guards root-trigger self-overlap, honors concurrency and expires stale queue entries. Cue triggers spawn their own background process via [cue-executor.ts](../repo/src/main/cue/cue-executor.ts), lines 1-27 and 34-61. It is not necessarily an interruption/steering into the visible active tab.

### Continuity, interruption and failure recovery

Persistence keeps agent identity, tab/provider-session bindings, logs, settings and queued work. It deliberately does not serialize live PIDs as proof of continued execution. [useDebouncedPersistence.ts](../repo/src/renderer/hooks/utils/useDebouncedPersistence.ts), lines 68-82 and 107-158. Resume is often a new process using a native provider conversation ID, such as the Codex resume builder in [definitions.ts](../repo/src/main/agents/definitions.ts), line 275. Memory edits and context grooming are additional continuity aids, not a substitute for a shared product specification.

Conversation lifecycle controls have concrete, different semantics. [useForkConversation.ts](../repo/src/renderer/hooks/agent/useForkConversation.ts), lines 24-114 and 184-220, slices displayed conversation logs at a raw message ID, formats the retained user/assistant/tool text into a context prompt, creates a new tab and spawns a fresh provider turn. This is a transcript-seeded fork, not a native provider state snapshot or a new organizational worker identity. [useSummarizeAndContinue.ts](../repo/src/renderer/hooks/agent/useSummarizeAndContinue.ts), lines 1-15, 51-68 and 269-282, summarizes context into a new compacted tab while retaining the source. [tab.ts](../repo/src/cli/commands/tab.ts), lines 116-138, exposes close and rename through the shared control plane. Group-chat archival is distinct from closing a coding tab or deleting an agent.

Stop is implemented as process control. [ProcessManager.ts](../repo/src/main/process-manager/ProcessManager.ts), lines 361-448, marks interruption before signaling, sends Ctrl+C or SIGINT/SDK interruption, signals remote execution and escalates if the process remains alive. Kill handles PTY and process-tree cases. Cross-agent fan-out cancellation has an authoritative main-process registry keyed by source agent so an early stop cannot miss consults that have started but not yet been returned to the renderer: [cross-agent-router.ts](../repo/src/main/cross-agent/cross-agent-router.ts), lines 91-130. Group-chat stop clears both active processes and queued delegation state: [groupChat.ts](../repo/src/main/ipc/handlers/groupChat.ts), lines 779-814.

Recovery is deliberately honest about lost executions. [recover-runs.ts](../repo/src/main/agent-run/recover-runs.ts), lines 35-65, marks nonterminal run records with no live session as failed and appends a recovery event. Its header mentions stale, but the actual implementation targets `failed` for all those ambiguous nonterminal states. [cue-recovery-service.ts](../repo/src/main/cue/cue-recovery-service.ts), lines 86-106 and 110-155, marks orphaned running events failed and reconciles missed time events after sleep gaps. Queue persistence can restore waiting work. An interrupted active execution is not silently certified or necessarily replayed. Pianola watcher rehydration reads its decision audit to avoid answering the same waiting prompt twice after restart, while allowing failed auto-answer attempts to retry: [pianola-watcher.ts](../repo/src/shared/pianola/pianola-watcher.ts), lines 172-227.

Provider failures also have a separate resilience layer. [retryClassification.ts](../repo/src/shared/retryClassification.ts), lines 1-26, 34-66 and 118-161, separates upstream availability from exhausted account quota, with exponential availability backoff and quota/reset-aware polling while excluding permanent request/auth/model failures. [useAutoResumeCoordinator.ts](../repo/src/renderer/hooks/agent/useAutoResumeCoordinator.ts), lines 1-25, 47-64 and 153-179, resumes paused standard queries or in-memory spec/goal loops and retains a give-up anchor across restarts. Claude local quota can be probed, whereas non-Claude and SSH-backed sessions use the retry itself as a probe. This helps continuity but requires the relevant renderer/app and does not make already-executed tool effects idempotent.

Group chats have liveness-aware watchdogs plus a hard 30-minute turn ceiling, distinguish silence from long active tool work, queue busy targets, and move toward synthesis even when a participant times out. See [group-chat-router.ts](../repo/src/main/group-chat/group-chat-router.ts), lines 247-264, 316-365 and 412-525. These bounds prevent leaked work. They cannot decide whether a timed-out specialist's product change is correct.

### Completion, acceptance and retirement

Pianola's baseline completion detector considers errors and latest output failure markers, then a working/connecting -> idle transition as done. A waiting-for-input state remains working, leaving the ask to the watcher: [pianola-completion-detector.ts](../repo/src/shared/pianola/pianola-completion-detector.ts), lines 131-169. The orchestrator enriches this with a ledger: critical/high findings or failing checks route a task to `needs_review`; opt-in autopilot can dispatch up to 3 fix attempts and then fail/escalate. The check/reviewer feeds are not wired: production searches find `recordCheck` and `ingestReviewFindings` only at their definitions, and their comments explicitly defer runner/feed wiring. The actual completion enrichment gathers only touched files, usage and PR data, [producers.ts](../repo/src/main/agent-run/producers.ts), lines 225-276 and 340-361. Generic record APIs can store supplied evidence, but no automatic test runner/reviewer ingestion was established. Missing checks are `undefined`, not failure, so an idle task without recorded evidence may complete. [pianola-orchestrate.ts](../repo/src/cli/commands/pianola-orchestrate.ts), lines 125-143; [orchestrator](../repo/src/shared/pianola/pianola-orchestrator.ts), lines 175-253.

The manual AgentRun merge button also only records `skipped`, [agent-run.ts](../repo/src/main/ipc/handlers/agent-run.ts), lines 275-297. The Pianola merge hook is a particularly important partial implementation: even after green checks and risk screening, [pianola-orchestrate.ts](../repo/src/cli/commands/pianola-orchestrate.ts), lines 705-740, says no git-merge path is reachable and records `skipped`. The pure engine can then mark the reviewed task done regardless of merge outcome, lines 215-232. A done task therefore does not establish merged code or accepted delivery. Goal mode has a similar honesty boundary: completion is the agent's self-reported complete/100% marker, with deterministic deadlock/iteration/stall exits, not an independently executed acceptance oracle. [goalExitEvaluator.ts](../repo/src/shared/goalDriven/goalExitEvaluator.ts), lines 60-131.

Retirement occurs at multiple scopes. A finished orchestration stops its loop; idle/missing watcher targets retire with a designated exit code rather than endlessly restarting; disabling/removing supervised targets terminates them. Group chats support archive/delete with participant/moderator stop, [groupChat.ts](../repo/src/main/ipc/handlers/groupChat.ts), lines 407-432. Agents are explicitly removable. The delete UI distinguishes agent-only removal from also trashing its directory and requires the name before directory deletion: [DeleteAgentConfirmModal.tsx](../repo/src/renderer/components/DeleteAgentConfirmModal.tsx), lines 74-100 and 112-145. History may outlive the sidebar agent, as [Director's Notes corpus handling](../repo/src/main/ipc/handlers/director-notes.ts), lines 154-167, explicitly accounts for deleted agents with retained history. There is no organizational rule that automatically retires a project team after human product acceptance.

## Coordination mechanics and a concrete request trace

Consider a user writing a Group Chat request that explicitly names existing agents `@Backend` and `@Frontend` to resolve an API/UI integration issue. The names are illustrative. This trace follows the implemented production path rather than claiming a runtime experiment.

1. **Receive and locate the room.** Desktop/CLI/web entry reaches the Group Chat main handler. [groupChat.ts](../repo/src/main/ipc/handlers/groupChat.ts), lines 636-707, ensures the moderator is available and forwards to `routeUserMessage`. [group-chat-router.ts](../repo/src/main/group-chat/group-chat-router.ts), lines 818-895, loads room metadata, verifies active moderator state, resolves mentions and auto-adds matching registered agents with their provider/cwd/config/SSH overrides. Ambiguous names do not arbitrarily choose a worker.
2. **Retain conversation and ask the moderator.** The router supplies the persistent room log and participant context to a batch moderator turn. `spawnGroupChatAgent` applies the configured provider, token-source/Windows handling and SSH wrapper, [spawnGroupChatAgent.ts](../repo/src/main/group-chat/spawnGroupChatAgent.ts), lines 119-177, 179-239 and 253-270. Log append is an actual append-only pipe-delimited record with escaped content and optional images/read-only flag, [group-chat-log.ts](../repo/src/main/group-chat/group-chat-log.ts), lines 85-108.
3. **Interpret actionable delegation.** When moderator output arrives, `routeModeratorResponse` extracts mentions and internal `!autorun` directives, resolves/auto-adds participants and classifies the round as delegation, response or synthesis. It also checks that an explicitly requested set of targets was actually included rather than accepting a prose-only acknowledgment, [group-chat-router.ts](../repo/src/main/group-chat/group-chat-router.ts), lines 1533-1578, 1686-1764. That is a notable defense against “I delegated” text that never dispatches anything.
4. **Spawn or wait for each specialist.** A valid ordinary handoff starts a participant provider process in its matching agent's cwd with its overrides. If the user's direct agent is already busy, the router queues instead of racing a second write process, lines 2135-2166. Each participant has watchdog/pending tracking. `!autorun` is different: it emits an event to the renderer's full batch runner and later expects `reportAutoRunComplete`, lines 1797-1849. This path depends on renderer batch orchestration as well as main-process routing.
5. **Record answers and synthesize.** `routeAgentResponse` appends the participant's content, emits the message immediately, extracts a first-sentence summary, updates activity/message counts and adds a response-history entry, lines 2277-2333. After pending participants finish, a new moderator synthesis process summarizes the room. The moderator is not a resident process receiving writes while the workers run.
6. **Surface intervention or follow-on work.** The human sees the room and participant state. Separately enrolled Pianola watchers can recognize blocked/waiting tabs, auto-answer a covered low-risk request or escalate through notifications/judgment handoff. This is not an automatic Room2-to-Room1-to-Telegram chain. A room conversation does not inherently create a durable ticket or test scenario. An Auto Run document or Pianola plan must be authored/bound for that work-tracking layer.

The two other coordination data paths offer useful complementary semantics. A Pianola DAG expresses “API must finish before integration tests”; its pure task model validates cycles/dependencies and propagates blocked tasks. Cue expresses “when both backend and frontend runs complete, prompt the verifier.” [cue-fan-in-tracker.ts](../repo/src/main/cue/cue-fan-in-tracker.ts), lines 97-119 and 122-175, resolves/deduplicates source identities and permits configurable partial continuation on timeout. [cue-dispatch-service.ts](../repo/src/main/cue/cue-dispatch-service.ts), lines 99-158, fans a subscription out to stable agent IDs with per-target prompts. These are events/dependencies, not themselves acceptance criteria or a team chat.

## Major additional capabilities and integration consequences

### Provider and context portability

Maestro is substantially broader than Wingman's stated Codex execution choice. The provider definition/configuration system supports different binaries, parsers, mode arguments, resume methods, models and capability differences. It also supports cross-agent consultation without polluting the user's normal target conversation, with provider-ID continuity in dedicated consult tabs. See [definitions.ts](../repo/src/main/agents/definitions.ts), lines 85-162, and [cross-agent-router.ts](../repo/src/main/cross-agent/cross-agent-router.ts), lines 1-31. This enables a heterogeneous organization and targeted second opinions. Integrating it requires treating provider-specific permissions, storage, model selection and session capabilities as real differences. Existing Pianola creation still selects Claude, so provider agnosticism of the overall workbench does not imply a Codex-neutral manager.

### Event-driven pipelines beyond periodic management

Cue can respond to file/task changes, completion, recurring or one-shot time, app startup, GitHub events and webhooks, and can run direct shell/CLI commands or notifications as well as model prompts. [contracts.ts](../repo/src/shared/cue/contracts.ts), lines 24-51 and 115-168. Fan-out, fan-in, source-output propagation and chain lineage allow reproducible workflows richer than Wingman's periodic supervisory wake. Persistent queueing, self-overlap guards and sleep reconciliation are valuable engineering building blocks. They also introduce another authority for launching work and another durable store. Wingman would need explicit ownership, idempotency, permission and tracker-update rules so the same product task is not launched by a manager, room and pipeline independently.

### Goal-driven fresh-context execution

Goal Auto Run supplies a goal/exit criteria and repeatedly invokes fresh agent contexts with progress markers, keeping a short predecessor handoff. [goal-runner.ts](../repo/src/cli/services/goal-runner.ts), lines 1-10, 83-115 and 125-137, shares pure exit logic with desktop. [goalExitEvaluator.ts](../repo/src/shared/goalDriven/goalExitEvaluator.ts), lines 60-131, deterministically stops on self-reported completion, deadlock, iteration limit or stalled progress. This is useful for bounded autonomous improvement where a fixed ticket sequence is inadequate. Wingman should label the progress as self-reported and add independent tests/product acceptance before translating it into delivered status.

### Learned decision profiles and auditable delegation policy

Pianola can mine ask/reply pairs from provider history, maintain per-project decision profiles and stage new suggestions rather than silently overwrite live rules. [pianola-lifecycle.ts](../repo/src/main/pianola/pianola-lifecycle.ts), lines 25-77 and 121-143, wires transcript mining and scheduled proposal generation. Policy and watchers combine hard rules with manager judgment, bounded retries, a decision log and escalation. This can reduce repetitive human questions while preserving a reviewable record of delegated judgment. It is not historical proof of what a user will want in a new domain; classifiers and profile inference need evaluation, and a product organization needs explicit consent/decision semantics across the Telegram boundary.

### Cross-provider evidence ledger and repair workflow

AgentRun separates execution identity from a conversation and attaches files, checks, findings, usage, PR and next action. [types.ts](../repo/src/shared/agent-run/types.ts), lines 109-150, [producers.ts](../repo/src/main/agent-run/producers.ts), lines 1-21 and 82-103, and [RunDetail.tsx](../repo/src/renderer/components/AgentRunDashboard/RunDetail.tsx), lines 35-117, provide the record, enrichment and navigable UI. This is stronger delivery evidence than a plain ticket status. Check/review types and mapping functions exist, but their production feeds remain unwired. Completion enrichment at lines 340-361 collects files, usage and PRs only. Git touched-file collection uses a repository snapshot/branch diff. It cannot attribute each write precisely. Producer failures can return empty information. The system excludes group-chat processes. Green merge orchestration remains incomplete. Wingman would need mandatory evidence producers for TestMaster and distinguish unknown from passed.

### Provider-limit resilience and resource observability

The retry system distinguishes an overloaded upstream from spent account quota and permanent configuration failures rather than blindly retrying everything. [retryClassification.ts](../repo/src/shared/retryClassification.ts), lines 1-26 and 118-161, has distinct schedules and permanent-failure exclusions. [useAutoResumeCoordinator.ts](../repo/src/renderer/hooks/agent/useAutoResumeCoordinator.ts), lines 1-25 and 153-179, resumes the correct query/spec/goal pathway and avoids treating a local Claude account's usage as the remote account's state. This is useful for a standing organization running long unattended jobs. Wingman would need resource-aware placement and clear replay semantics. A renewed prompt is not a transaction rollback, and retry modes do not all share one attempt cap or service-independent scheduler.

### A permission-brokered plugin platform

The plugin system includes runtime discovery/contributions, signed identity/grants hooks and code-tier execution in separate Electron utility processes. [plugin-manager.ts](../repo/src/main/plugins/plugin-manager.ts), lines 57-102, wires lifecycle and verified grant/identity checks; [plugin-sandbox-host.ts](../repo/src/main/plugins/plugin-sandbox-host.ts), lines 1-12 and 81-96, mediates host requests and bounds message size/concurrency/rate. This is a possible place to add organizational adapters without forking all core UI. It also creates a host API/security maintenance obligation. A runtime agent registration is explicitly not a fully launched provider integration. This assessment inspected these mechanisms but did not conduct a complete sandbox security audit.

### Open-source contribution workflow

Symphony is an issue/contribution workflow beyond the described personal product organization. [symphony-runner.ts](../repo/src/main/services/symphony-runner.ts), lines 42-69, 97-138 and 157-160, clones, branches, pushes and creates a draft PR using GitHub CLI, including fork setup. It uses draft PR claiming and Auto Run documents rather than merely opening an editor on a repository. This could serve Wingman's external maintenance/contribution work, but it adds GitHub credentials, fork/claim conventions and a workflow distinct from internal product intake. It is not evidence that all Wingman delivery flows already have accepted PRs.

### Shared provider memory and host-aware history

The memory editor manipulates Claude project memory and Codex account memory layouts and detects orphaned entries, [memory-manager.ts](../repo/src/main/memory-manager.ts), lines 1-18, 93-125 and 342-381. Director's Notes also reads project `.maestro/history/history-<hostname>.jsonl` from peer instances or SSH locations with a time-budgeted cached fallback, [director-notes-shared-history.ts](../repo/src/main/utils/director-notes-shared-history.ts), lines 1-32 and 79-155. These provide interoperability and visibility beyond a single application history store. Neither grants shared-memory consistency: provider scopes differ, peer files need actual shared/synchronized availability, and offline-host summaries may be stale.

## Distinctive mechanisms and grounded innovation

The following are strong design mechanisms in this checkout. No claim of historical novelty or industry uniqueness is implied.

**A conversational manager with a separate deterministic supervision substrate.** Pianola does not require a model to stay alive and repeatedly decide whether a process exists. A real manager conversation proposes/dispatches work through CLI, while task readiness, polling, backoff, target retirement and policy are explicit code. The same pure orchestration core is used by the CLI loop and tested with injected I/O. This allows transparent task dependencies and recoverable management without hiding all behavior in a large prompt. Its limit is that product intent, task decomposition and many judgments remain model-authored, and the desktop remains the lifecycle owner.

**Audit-aware decision recovery.** A restarted watcher seeds its handled cursor and pending handoff from decision records instead of answering the same still-visible question again. Failed auto-answer dispatch is deliberately not treated as handled. [pianola-watcher.ts](../repo/src/shared/pianola/pianola-watcher.ts), lines 172-227. This is a concrete continuity design for an agent manager, not simply “logs are saved.” Its boundary is at-least-retry behavior under recorded failures. It does not establish a distributed exactly-once transaction between log and provider message delivery. Likewise the orchestration auto-action audit function catches logging failure and continues, [pianola-orchestrate.ts](../repo/src/cli/commands/pianola-orchestrate.ts), lines 146-167, so that particular hook is best-effort rather than a fail-closed audit guarantee.

**Executable handoff validation in model-mediated rooms.** Group Chat interprets moderator output as commands but checks an explicitly requested target set before treating the response as successful delegation. It also waits for busy agents and uses liveness-aware watchdogs instead of killing long tool use merely because one timeout elapsed. [group-chat-router.ts](../repo/src/main/group-chat/group-chat-router.ts), lines 1691-1764, 1245-1359 and 412-525. This bridges natural-language collaboration and concrete processes with useful checks. Output syntax, naming ambiguity, non-enrolled agents and shared-directory collisions remain limits.

**Separate consult continuity without contaminating the target's main conversation.** Source-tab/target pairings get dedicated resumable consult tabs while a fresh process carries each new forwarded source transcript. [cross-agent-router.ts](../repo/src/main/cross-agent/cross-agent-router.ts), lines 18-31. It enables repeated specialist advice with both local history and current caller context. This is not a free-standing peer organization: a consultation still has a source/caller, a bounded process and explicit permission mode.

**Event pipelines with identity-stable fan-out and failure-aware fan-in.** Cue targets stable IDs where available, deduplicates source names/IDs, records parent/root lineage, protects root self-overlap, persists waiting events and supports partial continuation on timeout. [cue-dispatch-service.ts](../repo/src/main/cue/cue-dispatch-service.ts), lines 99-158; [cue-fan-in-tracker.ts](../repo/src/main/cue/cue-fan-in-tracker.ts), lines 97-175; [cue-run-manager.ts](../repo/src/main/cue/cue-run-manager.ts), lines 255-380. This supplies explicit coordination semantics beyond prompt chains. A completed event still describes execution outcome rather than functional correctness, and partial fan-in must not accidentally satisfy a mandatory verification dependency.

**Semantic briefings separated from deterministic counts.** Director's Notes aggregates history, asks a provider for agent-attributed accomplishments/challenges/next steps, and renders usage/volume statistics from deterministic data. The [synopsis prompt](../repo/src/prompts/director-notes.md), lines 29-35, 37-88 and 95-108, requires reading actual history and forbids inferring work from agent names. This is directly relevant to Wingman's executive briefing goal. It is a prompt/output contract, not a proof of factual grounding; source completeness, model compliance and stale remote reads still bound trust. Pianola's “recently done” data should not be mistaken for independently verified accomplishment.

## Practical adoption fit

**Usable directly as infrastructure:**

- per-agent coding workspaces.
- installed Codex execution.
- provider-session history/navigation.
- local and SSH worker launching.
- project directories and worktrees.
- room transcripts and moderator delegation.
- live process/tool/output visibility.
- per-run evidence objects.
- browser/mobile access.
- CLI automation.

Cue and Pianola's pure policy/DAG components are credible substrates for periodic supervision and task orchestration, subject to exercising them in the intended deployment.

**Needs adaptation:**

- replace or generalize Pianola's Claude-specific auto-created manager and prompts.
- add an explicit project ID/registry independent of cwd/name.
- distinguish role profile from agent instance.
- persist project/leadership/team relationships.
- map tracker tasks to run IDs, room messages and provider tabs.
- define common specification/acceptance artifact links.
- build a uniform executive current/recent/assigned-next record.

A Telegram adapter would need identity and project/conversation correlation, attachments, pending questions/decisions and durable answer routing into the correct agent/tab rather than simply broadcasting bot messages into one manager conversation.

**Still needs product work:**

- Standing Butler and ProjectMaster responsibilities.
- A per-project ProductMaster/TechMaster pair and proportionate discovery ownership.
- Direct specialist discussion and prescribed escalation across management/project rooms.
- A shared lightweight ProjectTracker.
- TestMaster execution bound to product scenarios and definition of done.
- Product delivery, acceptance and team quiescence.
- Placement and continuity policy for Mac and Endeavour.
- Service operation if the organization must remain active independently of the desktop app. Existing primitives reduce construction effort, but these are domain behaviors rather than renames of tabs.

A practical integration should preserve the distinction between execution success, evidence availability, task completion and accepted product delivery. Maestro already exposes enough real state to implement that distinction. Treating “idle,” “all checkboxes checked,” “goal 100%,” “recently done” and “merged” as synonyms would erase exactly the organizational accountability Wingman describes.

There is also a licensing consequence if code is reused: [package.json](../repo/package.json), line 11, declares AGPL 3.0 and the checkout includes [LICENSE](../repo/LICENSE). This is a repository fact, not a legal interpretation. The reuse/distribution model should be evaluated separately from technical fit.
