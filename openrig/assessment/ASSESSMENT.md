# OpenRig assessment against Wingman

Repository: https://github.com/mvschwarz/openrig  
Checkout: `researchs/openrig/repo`  
Revision inspected: `fa3262d360fbb8d785acfa9bd8f1b40439325b4f`  
Assessment date: November 5, 2026 (fresh implementation audit)  
Baseline: [Wingman purpose](../../WINGMAN_PURPOSE.md). This assessment concerns this local source snapshot, not the current hosted service or the behavior of an installed release.

OpenRig is a substantial foundation for Wingman's standing organization. It implements separate coding-agent processes, durable organizational seats, extensible team specifications, cross-host execution, persistent work queues, direct messaging, rig chat, supervision policies, project records, review and proof surfaces. These are implementation mechanisms, not simply roles described in a prompt. Its most useful contribution is the separation of **a continuing responsibility and address** from **the replaceable conversation currently doing that work**.

It is not the complete Wingman experience out of the box. Its shipped person-facing connector is Slack, the factory team has a lead and an advisor rather than Wingman's full portfolio/product/technical hierarchy, and the default factory advisor deliberately does not run the full PM discovery procedure. Its seat pages provide operational facts and recent events. They do not establish Wingman's full plain-language, current/recent/next agent briefing and linked personal summary timeline. A remote agent can participate in shared coordination, but the central UI explicitly refuses to pretend its local terminal stream is a remote terminal.

The practical fit is therefore **strong orchestration and continuity substrate, with meaningful organizational and experience work remaining**. This is a much closer match to a persistent development organization than a terminal-session launcher alone. That judgment is based on the source mechanisms below. It is not a runtime reliability endorsement.

## Architecture and what actually runs

The repository contains daemon, CLI, TUI and React web UI workspaces. The daemon owns a SQLite database and HTTP services. The interfaces consume those services. [Database connection](../repo/packages/daemon/src/db/connection.ts), lines 1–15, enables WAL and foreign keys. [Server composition](../repo/packages/daemon/src/server.ts), lines 849–905, mounts separate seat, chat, stream, queue, projects, workflow, terminal, review, proof, steering, health and gateway routes. [Startup composition](../repo/packages/daemon/src/startup.ts), notably lines 387, 502–532, 1601–1615 and 2299–2467, constructs persistent coordination stores, classification, stream intake and watchdog services. This is a control plane around existing coding harnesses. It does not replace their model/tool loops.

The concrete entry path is `rig up` → daemon launch/status check → `POST /api/up` → RigSpec resolution/materialization → startup orchestrator → runtime adapter → native CLI in its execution binding. The [CLI up command](../repo/packages/cli/src/commands/up.ts), lines 270, 326 and 560 onward, has separate remote HTTP, start-daemon and local API branches. The [daemon entry](../repo/packages/daemon/src/index.ts), lines 321–365, calls `createDaemon`, starts Hono listeners and only after listening starts context monitoring, wake recovery, watchdogs and network gateway services. Closing a dashboard is therefore not the execution lifecycle boundary. SQLite stores control-plane truth; native harness history, projected instructions/skills and authored project artifacts remain separate persistence domains. A database backup alone is not proof of complete conversation or source-workspace recovery.

Its principal objects have materially different meanings:

| Object | Actual meaning and significance for Wingman |
|---|---|
| AgentSpec | A reusable definition: defaults, profiles, imported resources, guidance, skills/plugins, startup and lifecycle settings. It is not itself a running agent. |
| RigSpec / rig | A declared and persisted team topology. Pods group bounded responsibilities; members and edges declare seats and relationships. Multiple rigs can coexist. |
| Node / seat | A durable responsibility/address with role, runtime, model, cwd, profile, restore policy and occupant lineage. This is closest to Wingman's continuing agent identity. |
| Session | A concrete harness conversation occupying a node: native resume token, status, startup state and binding. It can be replaced while the seat remains. |
| Binding | The execution attachment, commonly a tmux session/window/pane; externally attached CLI sessions are represented separately. |
| Queue item | A durable assignment, question, handoff or decision with owner/destination, status, lineage, blocker, evidence reference and wake/delivery information. |
| Project / mission / slice | Filesystem-authored product/work hierarchy, with lifecycle, workflow, scope, acceptance and proof views. A rig is not automatically identical to a product. |

The first five distinctions are visible directly in [domain types](../repo/packages/daemon/src/domain/types.ts), lines 3–131, and the parsing/resolution is implemented by [agent manifest](../repo/packages/daemon/src/domain/agent-manifest.ts), [profile resolver](../repo/packages/daemon/src/domain/profile-resolver.ts), and [rig instantiator](../repo/packages/daemon/src/domain/rigspec-instantiator.ts), particularly `PodRigInstantiator` at line 506.

The shipped [factory topology](../repo/packages/daemon/specs/rigs/launch/factory/rig.yaml), lines 1–102, demonstrates that the roles correspond to independent members. It has a Codex lead; Claude PM advisor, builder and designer; Codex QA; and two reviewers, one Claude and one Codex. Edges express delegation, collaboration and observation. Both reviewers use the same reusable reviewer definition but are separate instances. This is a concrete model for several BackendCoders or TestMasters sharing a profile without sharing a conversation.

## Agent definition, creation and lifecycle

### Definition and identity

An authored AgentSpec is a reusable recipe. The PM [agent definition](../repo/packages/daemon/specs/agents/product-management/pm/agent.yaml) is particularly informative: it imports shared resources; its default profile selects office-hours, context-builder, requirements-writer, mockup, review, summary and backlog skills; its advisor profile instead selects orchestration-team. Both profiles share role guidance but have different capabilities. Merely recognizing the role name "PM" would overstate behavior: the factory explicitly uses the lighter advisor variant and tells it not to execute the eight-step procedure.

The RigSpec chooses a member's `agent_ref`, runtime, profile, cwd and startup overlays. Resolution combines reusable defaults and more specific member choices. [Profile resolver](../repo/packages/daemon/src/domain/profile-resolver.ts), lines 580–667, separately handles compaction strategy, continuity mechanic and restore-policy narrowing. Compaction modes use most-specific precedence; restore policy has a narrowing constraint. Wingman could define ProductMaster and TechMaster once and instantiate each under several project rigs without conflating their identities.

A durable node has its own database ID and logical identity. A session has a separate ID, native token and runtime attachment. Occupant-generation information lets the system distinguish today's conversation from a predecessor using the same organizational address. Edges, queue assignments and the continuing seat survive operations that replace the conversation. This is stronger than persisting a terminal title, but it is not preservation of a model's entire private state: native resumption depends on the underlying harness history, while reconstruction depends on durable artifacts and recaps.

For a concrete instance, the factory member `dev.qa` selects the QA AgentSpec, default profile, Codex runtime and working directory `.`. Its organizational address is `dev-qa@factory`: [canonical name derivation](../repo/packages/daemon/src/domain/session-name.ts), lines 1–18, combines pod, member and rig. A second QA member needs a distinct member ID and gets a separate node, native conversation and generation. It need not copy the QA definition. [Member addition](../repo/packages/daemon/src/domain/rigspec-instantiator.ts), lines 1090–1155, explicitly mints new identity, reuses validation/preflight and retains duplicate-ID checks. Creating a role file, materializing a node and launching its conversation are three different operations.

### Materialization and launch

[PodRigInstantiator](../repo/packages/daemon/src/domain/rigspec-instantiator.ts), lines 506 onward, separates materialization, structured validation, first-node launch, launching materialized topology, adding a member, retrying first start and ordinary instantiation. Materializing a seat does not mean a harness is already running. This distinction allows topology and work ownership to remain visible even while execution is stopped or awaiting a startup decision.

[StartupOrchestrator](../repo/packages/daemon/src/domain/startup-orchestrator.ts), lines 344–530, acquires lifecycle custody, reconciles contained environments when applicable, applies saved permission choices, resolves rig settings and seat storage, marks startup pending, projects runtime resources and partitions startup input. Guidance and skill files are delivered before the native harness starts; conversational startup text is delivered after it is ready. The remaining orchestration persists replay context, launches through the adapter, records native identity, waits for readiness and submits startup actions. Projection failure is returned as failure rather than being called a successful agent launch.

The Codex [runtime adapter](../repo/packages/daemon/src/adapters/codex-runtime-adapter.ts), lines 884–987, explicitly separates fresh, resume and fork. A fork launches a native child and captures that child's identity. It does not store the parent's thread ID as though it belonged to the new worker. Fresh startup can stop at trust/authentication/native prompts. `continueStartup` in [seat lifecycle](../repo/packages/daemon/src/domain/seat-lifecycle-service.ts), line 1247 onward, exists to deliver pending context to that same conversation after attention is resolved, rather than launching a duplicate agent.

### Tools and permissions

OpenRig provisions capabilities into the native harness: guidance, skills, plugins, runtime configuration and activity hooks. The harness remains the executor of file edits, shell commands, browser tools and other model actions. OpenRig does not make a YAML role a security boundary. [Startup](../repo/packages/daemon/src/domain/startup-orchestrator.ts), lines 363–403, applies native permissions and seat-specific storage; [seat lifecycle permissions](../repo/packages/daemon/src/domain/seat-lifecycle-service.ts), lines 825–1005, manage explicit choices and policy references. The launch adapter computes actual native command arguments.

The repository distinguishes ordinary team defaults, explicit member choices, named Codex profiles and non-interruptive/bypass settings. Wingman should reuse that explicit native-policy plumbing rather than treating its management hierarchy as authorization. Changing a saved permission choice is also not evidence that an already running native process changed its effective sandbox. The types and events distinguish future-launch effects from observed execution.

Resource selection is more than prompt concatenation. [Profile resolution](../repo/packages/daemon/src/domain/profile-resolver.ts), lines 152–192 and 236–340, resolves runtime/model/cwd before runtime-specific skill lookup, composes system/topology/project selections and detects conflicting skill identity/content. Dirty catalog skills are omitted with a named warning while selected bundle content can retain precedence. Two specialists can have different capabilities in one project. Wingman must preserve capability provenance. Authored skill selection, successful projection and native harness loading are separate outcomes.

### Routing, concurrency and work pickup

Agents address seats, not anonymous model calls. Rig/pod/member identities, host references, rosters and edges provide organization discovery. Queue entries direct work to a destination; claim and generation records represent pickup. Direct transport handles conversational input. Rig chat persists discussion, but assigning a queue task is a separate action. The [chat send route](../repo/packages/daemon/src/routes/chat.ts), lines 28–61, stores a message and emits an event. It does not create a task as a side effect.

Native harness processes can execute concurrently across members and rigs. The daemon serializes particular lifecycle/delivery operations using a guard, and the watchdog intentionally runs one tick at a time. Neither fact imposes a global single-agent execution loop. Conversely, declaring independent seats does not give them independent Git worktrees automatically in every topology: the shipped factory points its members at `.`. Wingman still needs an explicit shared-file/worktree policy for simultaneous backend/frontend/test changes.

### Persistence, resumption and replacement

The persistence story spans SQLite node/session/work/event records, authored project files, native harness histories and optional transcript/capture facilities. [Restore orchestration](../repo/packages/daemon/src/domain/restore-orchestrator.ts), lines 178–196 and 340 onward, predicts and performs policy-dependent restore. It can resume, start fresh under allowed conditions, hold a seat pending a decision, or report failure/attention. A running process is weaker evidence than a joined native resume identity. The native adapter performs additional verification. The selected-history path rechecks that a historical row still belongs to the intended seat before dispatch.

[Seat handover](../repo/packages/daemon/src/domain/seat-handover-service.ts), line 312 onward, supports replacing the occupant, including rebuild and fork cases; `buildRestorePacket` at line 1481 assembles predecessor context. This preserves responsibility and work routing while acknowledging a conversation boundary. A restored/forked/rebuilt agent is not necessarily the same conversation, and the implementation makes those outcomes distinguishable.

The more ambitious [runtime switch service](../repo/packages/daemon/src/domain/seat-runtime-switch-service.ts), lines 40–49 and 139 onward, starts a successor beside the predecessor, waits for the successor's handover confirmation, then commits settings and transfers queue claims before retiring the predecessor. Its durable switch record supports recovery of partial transitions. This can replace a Claude occupant with a Codex occupant without abandoning the organizational seat, but does not translate the entire native conversation losslessly between providers.

The switch's costs are explicit in that same [service](../repo/packages/daemon/src/domain/seat-runtime-switch-service.ts), lines 146–154 and 254–267: Codex/Claude Code only, one window/pane, a temporary second native process, changed scrollback and no native history conversion. Imported YAML is not rewritten; later convergence can report a deferred runtime change. Direct messages held during the switch need deliberate follow-up rather than an assumed replay. The [commit/finish path](../repo/packages/daemon/src/domain/seat-runtime-switch-service.ts), lines 550–628, moves generation-bound claims and snapshots the new runtime transactionally, then separately retires the predecessor and delivers activation. A committed switch may still carry `recoveryPending` if those external effects cannot be confirmed. Successor confirmation establishes a protocol acknowledgment, not independent proof that the successor understood every product decision.

### Scheduling, failure, interruption and retirement

[WatchdogScheduler](../repo/packages/daemon/src/domain/watchdog-scheduler.ts), lines 5–32, persists schedule state in SQLite, uses due-time evaluation, avoids overlapping ticks and awaits in-flight evaluation on shutdown. [WatchdogPolicyEngine](../repo/packages/daemon/src/domain/watchdog-policy-engine.ts), lines 17–40 and 134–180, supplies skip/send/terminal outcomes, active-wake throttling, optional generation checks and queue-wait integration. This gives Wingman's ProjectMaster a place to schedule supervision. It does not itself decide whether the LOS project's implementation strategy is sound.

Failure is represented at several levels: startup failure, attention at a native prompt, hard delivery failure, ambiguous send, stale occupant generation, blocked queue work and incomplete restore. These distinctions matter because retrying an unobserved delivery can duplicate an action, whereas declaring an unanswered human decision complete can lose work. Queue wake intent and delivery status are stored separately from the task's closure. Tests explicitly exercise indeterminate transport outcomes, not only happy-path sends.

Retries are deliberately bounded by the domain, not a universal promise that every failure retries forever. [Nudge failure classification](../repo/packages/daemon/src/domain/queue-repository.ts), lines 148–174, distinguishes unresolvable topology, positively matched transient errors and unknown errors; that classifier is read-side labeling. [Wake draining](../repo/packages/daemon/src/domain/queue-repository.ts), lines 1398 onward, treats existing claims, known success and manual holds differently from failed/uncertain attempts. [Restore preflight](../repo/packages/daemon/src/domain/restore-orchestrator.ts), lines 410–446, refuses possibly live conflicting sessions and uses per-rig restore custody. A missing required startup file may hold just its seat while other seats restore. These are useful recovery mechanisms, but stale addresses, missing native histories and unresolved login prompts still require correction.

[Seat lifecycle](../repo/packages/daemon/src/domain/seat-lifecycle-service.ts), lines 1069–1247, implements stop/cleanup/continue; later sections implement fresh launch and in-place restart. Stop ends an execution; cleanup clears settled attachment state. Neither should be confused with accepted product completion. [Rig teardown](../repo/packages/daemon/src/domain/rig-teardown.ts), lines 104–275, refreshes resume metadata and takes a best-effort pre-down snapshot, then confirms termination before cleaning individual nodes. Snapshot failure is reported but does not necessarily prevent stopping. Externally attached CLI seats are left running because OpenRig did not launch them. Delete can be refused when owned sessions could not be killed. This is careful resource ownership rather than a blanket kill-and-forget operation.

Cancellation has two scopes. Queue records support `canceled` ([queue states](../repo/packages/daemon/src/domain/queue-repository.ts), lines 53–83), whereas stopping a seat controls its native execution. A canceled assignment is not by itself evidence that a process or shell child has stopped. Conversely, [stop/clean checks](../repo/packages/daemon/src/domain/seat-lifecycle-service.ts), lines 1088–1094 and 1173–1207, refuse adopted sessions and require positive absence before clearing state. Wingman should expose task withdrawal and execution termination separately and reconcile work ownership after interruptions.

Product completion is a separate domain: queue closure requires a reason, proof readiness derives from judgments, and delivery approval has its own audit record. Wingman must still define when accepted work stops future development/testing and when a new human request reactivates it; keeping a rig alive is not the same as having ongoing authorized product work.

## Coordination traced through a real implemented path

Consider a human asking the shipped factory for one useful product change. This trace joins actual handlers and shipped instructions. It was inspected, not executed.

1. **Intake:** The Slack connector turns a registered human message into durable queue work directed to its mapped seat or configured kernel operator. [Slack inbound execution](../repo/packages/daemon/src/domain/gateway/slack/inbound.ts), lines 357–476, resolves the thread route, creates a stable-ID queue item with the human's canonical source, records reply correlation and only marks the event seen after the durable row exists. Top-level messages can mint thread roots. Recovered thread replies and shared-channel correspondence do not automatically answer existing decisions; typed human answers can resume their exact gate. The instruction at lines 365–368 explicitly separates a decision closing from approval of its proposed action.
2. **Organize:** The operator hands the goal to the project team. [Factory lead first move](../repo/packages/daemon/specs/rigs/launch/factory/guidance/lead-first-move.md), lines 1–35, tells the lead to inspect/claim that row, reuse an existing mission where appropriate, otherwise create a mission and first slice, then plan and route work. This is agent procedure on top of an implemented queue and scope API, not a parser guaranteed to make correct product judgments.
3. **Assign and claim:** `POST /api/queue/create` in [queue routes](../repo/packages/daemon/src/routes/queue.ts), lines 540–641, resolves sender identity, validates destination/body and repository scope, creates the row and may nudge the destination. The row exists independently of whether the worker immediately receives usable terminal input. The worker claims through the next route; [repository claim](../repo/packages/daemon/src/domain/queue-repository.ts), lines 2799–2868, checks that the claimant matches the destination and the row is claimable, then transactionally marks it in progress, stamps the occupant generation and records a transition. Reading a notification or chat message is not that ownership act.
4. **Execute remotely if placed there:** When `hostId` resolves remotely, the forwarding side uses the supplied `qitemId` or mints one before sending, then drops the forwarding host field. It forwards the full assignment to the remote daemon and stores no pretend local task. The destination daemon owns the row and wakes its own local harness. The retry boundary matters: [queue route](../repo/packages/daemon/src/routes/queue.ts), lines 593–607, mints a new ID on each new API request that omits `qitemId`; repeated raw POSTs are not automatically one operation. The [CLI create command](../repo/packages/cli/src/commands/queue.ts), lines 947 and 1094–1114, allocates/prints the ID before dispatch, accepts `--id` and instructs the caller to reuse it with unchanged inputs after an unknown outcome. That ID is a request identity, not proof of persistence. [Remote transport](../repo/packages/daemon/src/domain/hosts/remote-daemon-http.ts), lines 113–198, bounds the request and response-body wait and reports structured uncertainty/errors. This fits Mac coordination plus Endeavour execution, provided both daemons, paths and credentials are configured and callers preserve retry identity.
5. **Collaborate:** Workers can discuss in rig chat and use direct seat transport. Chat history retains attribution/topics. Durable assignments and questions remain queue items, so an informal discussion is not the only record of who owes the next action.
6. **Hand off:** A worker hands implementation to QA/review through [repository handoff](../repo/packages/daemon/src/domain/queue-repository.ts), lines 2250–2290 and 2353–2424: it rejects an already-terminal source, validates the new destination, inherits or replaces work context, records successor lineage, propagates blocker completion and persists events. It normally stages a wake intent in that same transaction and checks it before commit. Delivery is attempted after commit. A crash between commit and delivery therefore need not erase the successor's wake obligation. There are explicit boundaries: `nudge:false` requests no wake, and [wake staging/guard](../repo/packages/daemon/src/domain/queue-repository.ts), lines 1274–1279 and 1388–1390, permit the successor to stand with a recorded `failed:wake not retained` when a held-message quota is full. Ownership persists, but automatic pickup is not guaranteed in that case.
7. **Wait or escalate:** A worker can park work against another item or a human gate. [Closure validation](../repo/packages/daemon/src/domain/hot-potato-enforcer.ts), lines 63–115, refuses `done` with `blocked_on` and requires a target for handoff/escalation. Watchdog policies re-present actionable waits. Human replies are recorded against the appropriate ask and episode rather than being indistinguishable generic chat.
8. **Verify and accept:** QA and independent reviewers produce evidence; [proof judgments](../repo/packages/daemon/src/domain/proof/judgments.ts) evaluate recorded requirement/evidence revisions. [Scope approval](../repo/packages/daemon/src/domain/scope/scope-approve.ts), lines 29–99, records specification or delivery acceptance with real actor/delegation metadata. Approval is explicitly separate from test proof. The lead closes the original goal with the result.

This is both **chat coordination** and **ticket coordination**, with ticket/wake custody carrying the stronger reliability contract. Wingman could keep Room1/Room2 discussions readable while adopting the queue as the durable record of responsibility. It should not assume that observing a discussion means its assignment has been claimed, that a nudge proves pickup, or that a completed task proves accepted product delivery.

## Major capabilities beyond Wingman's described scope

**Provider-neutral organizational continuity and live runtime replacement.** Wingman describes Codex agents on two hosts. OpenRig explicitly makes a seat independent of Claude/Codex occupant choice, supports additional runtime adapters, and can perform a successor-first runtime switch. That is a product-level capability: move responsibility to another harness/provider while preserving addresses, relationships and claims. Integration requires Wingman to distinguish seat, generation and native conversation in its directory/UI; one `agent_id` standing for all three would lose the benefit.

**Auditable delivery and evidence judgments.** Wingman requires acceptance scenarios and delivery; OpenRig adds a concrete revision-sensitive proof/judgment system, staged specification versus delivery approval, and review composition. [Proof types](../repo/packages/daemon/src/domain/proof/judgments.ts), lines 13–40, include policy revision, item revision, previous judgment, actor/provenance, evidence hashes and subject kind. This lets an approval of one candidate remain distinguishable from approval of later changed work. Wingman would need to adopt the artifact conventions and establish who may judge which obligation; simply writing `done: true` would bypass the mechanism.

**Reusable organization packages and runtime resource projection.** The [package install service](../repo/packages/daemon/src/domain/package-install-service.ts), lines 35–115, composes planning, conflict detection, policy, name/version/hash checking, apply and verification; profile/startup projection then delivers selected capabilities. Wingman could ship a versioned organization recipe with its Butler/ProductMaster/TechMaster profiles. The [skill catalog](../repo/packages/daemon/src/domain/skill-catalog.ts), lines 20–85 and 101–120, records source revision, digests, per-file hashes, selection source and projection status, including shadowed/stale/conflicting states. This supports inspectable capability distribution across teams and seat-specific storage. It introduces configuration provenance, compatibility and workspace-write ownership concerns; imported team configuration should not be treated as only inert prose. A verified file installation remains different from a verified model behavior.

**Managed execution environments and service lifecycle.** [Environment lifecycle](../repo/packages/daemon/src/domain/environment-lifecycle.ts), lines 8–25 and 84–172, distinguishes closing a viewer, stopping native execution, stopping compute and deleting owned resources; later methods support checkpoints/recreate. Rig teardown also coordinates associated services. This goes beyond Wingman's stated host placement into managing the execution environment itself. Generation/resource guards and operation receipts protect against killing a replacement or mistaking an unconfirmed external effect for completed cleanup. The concrete checkpoint/native type in this path is `community:openshell-claude` (lines 20–23 and 78–81). It is not evidence of a universally portable Codex VM snapshot facility. Wingman would need to choose and exercise a driver before relying on reproducible test environments or account-independent recovery.

**Human attention and decision operations as a separate product surface.** The [For You feed](../repo/packages/ui/src/components/for-you/Feed.tsx), lines 15–104, merges attention, queue-derived progress and approvals, while [queue decision types](../repo/packages/daemon/src/domain/queue-repository.ts), lines 182–201, record delegated decisions separately from a person's answers. Wingman's Butler could use this as a durable attention inbox rather than relying only on conversational notifications. The original human channel remains Slack until a Telegram connector is built.

**Hosted assistants and scoped MCP participation.** An organization member need not live in an OpenRig terminal. [Roster types](../repo/packages/daemon/src/domain/rosters.ts), lines 8–38 and 95–110, support `hosted` members, host references and an optional webhook wake. The [MCP operations surface](../repo/packages/cli/src/mcp-server.ts), lines 490–547, maps queue, chat, team, artifact and context tools to the same daemon APIs, while lines 550–584 give members an explicit claim/work/close-or-handoff inbox protocol. [HTTP MCP](../repo/packages/cli/src/mcp-http.ts), lines 1–37, binds each authenticated request to its grant's seat, rigs, roots and access class rather than sharing one caller identity. This could let an external research assistant or human-facing client join Wingman without pretending it is another native Codex process. Its lifecycle and wake guarantee differ: the shipped MCP instructions explicitly tell hosted members to poll their inbox because a ring does not promise pickup. Wingman's directory should show that distinction, and grants must match actual intended data access.

## Distinctive mechanisms worth studying

These mechanisms are distinctive within this implementation. The evidence does not establish historical novelty or industry-wide uniqueness.

**Durable responsibility, replaceable cognition.** The node/session/generation split and successor-first runtime switch model an organizational job as more durable than a model context. A successor demonstrates readiness before replacing the predecessor; claims move with a recorded transition. The enabling idea is continuity of responsibility without falsely claiming perfect memory continuity. Its limit is that rebuilding/handover preserves selected records and explanations, not an identical mental state.

**Closure is an obligation transfer, not only a status change.** The hot-potato closure validator demands an explicit reason and target where appropriate. Queue transactions normally join predecessor closure, successor creation and wake intent, with an explicit post-commit delivery seam. [Transactional-closure tests](../repo/packages/daemon/test/queue-transactional-closure.test.ts), lines 103–239 and 280–349, exercise split-database rejection, missing-outbox rejection, atomic rollback, crash recovery and ambiguous delivery. This addresses the failure where one agent announces handoff and goes idle while nobody owns the next step. The mechanism provides durable ownership and an inspectable notification outcome. It does not guarantee exactly-once execution. Explicit no-nudge handoffs or full retained-message quotas can leave a valid successor without a retained wake. An indeterminate send can require a new attempt. Durable custody cannot force an LLM to understand or complete the task correctly.

**Readiness is tied to authored obligations and revisioned evidence.** The proof system models accept/reject/withdraw separately from human sign-off and keeps item/policy/evidence revisions. The [lifecycle compiler](../repo/packages/daemon/src/domain/project-lifecycle-compiler.ts), lines 56–180, derives workflow structure from authored project/mission/slice contracts and retains input digests. Required project steps can constrain mission-specific extensions/overrides. This provides an inspectable contract connecting product records to workflow eligibility, rather than an independent workflow database silently becoming the source of product truth. It still depends on correctly written proof contracts and truthful evidence producers.

**Uncertainty is first-class operational state.** The system repeatedly distinguishes ready from oriented, sent from verified, claimed from merely nudged, resumed from fresh/rebuilt, and failed from indeterminate. The [Codex launch adapter](../repo/packages/daemon/src/adapters/codex-runtime-adapter.ts), lines 905–980, refuses to assign an unproven fork identity and verifies requested resumption. [Remote HTTP](../repo/packages/daemon/src/domain/hosts/remote-daemon-http.ts), lines 61–83 and 175–198, can report uncertain outcomes rather than promise that timeout means no remote work occurred. This would improve Wingman's executive dashboard only if its summaries preserve those distinctions instead of reducing them to reassuring green badges.

**Federated coordination preserves record ownership.** Remote rigs run on remote daemons, and receiver-side create deduplication works when retries reuse the same queue ID. The [API forwarding branch](../repo/packages/daemon/src/routes/queue.ts), lines 593–607, preserves a supplied ID but generates a fresh one when omitted. The [CLI](../repo/packages/cli/src/commands/queue.ts), lines 947 and 1094–1114, makes recovery practical by printing the ID before sending and accepting `--id` for reconciliation. The caller must carry that identity across separate invocations. The cross-host tests distinguish a destination-owned record from a local projection. This is useful for Mac/Endeavour placement and failure isolation, with an explicit caller contract rather than automatic exactly-once delivery. It is not transparent database replication: offline hosts can make parts of the portfolio unavailable, and remote execution does not imply central remote terminal streaming.

**Semantic uncertainty stays separate from activity.** The [current-work derivation](../repo/packages/daemon/src/domain/current-work.ts), lines 361–403, distinguishes one established work node from merely tagged/ancestral candidates, possible next work and held blocked work. Body text alone does not establish mission identity and pending candidates carry no inferred priority. Together with revision-bound proof, this gives Wingman useful raw material for trustworthy summaries: summarize evidence with its status, and let an agent select intent where the records are ambiguous. Its limit is equally useful: those derivations are not themselves a natural-language executive briefing or an assurance that every active process is pursuing its recorded assignment.

## What Wingman could reuse and what remains

Use directly as architectural material:

- The durable-seat model.
- Reusable role/profile/team schema.
- Native launch/resume/fork adapters.
- Queue ownership/closure/handoff.
- Transactional wake custody.
- Generation-aware lifecycle guards.
- Persistent watchdog scheduling.
- Project/mission/slice records.
- Proof/approval separation.
- Genuine daemon-to-daemon task/launch coordination. These features map to difficult infrastructure requirements already present in Wingman's purpose.

Adapt the organization explicitly.

Create all-Codex profiles for:

- Butler, ProjectMaster, ProductMaster, TechMaster and the specialists.
- decide whether one project maps to one rig or several pods/rigs.
- configure product roots and directives.
- preserve distinct human clarification threads and project intake.
- define the supervision/acceptance procedures.

Do not rename the factory advisor ProductMaster and assume the eight-step PM capabilities are available: its shipped profile and guidance state otherwise.

Build the remaining experience:

- A Telegram inbound/outbound and ask-answer connector with stable project/conversation correlation.
- Wingman's Room1/Room2 management/collaboration convention. The complete portfolio-routing policy.
- Semantic per-agent current/recent/next summaries and linked personal timelines.
- A detailed remote workspace experience. The existing seat terminal is explicitly local-only in the central UI, so Endeavour execution requires additional remote drill-down/routing work. Plan a source isolation/integration policy for concurrently editing specialists and an explicit accepted-delivery-to-idle transition.

OpenRig is therefore a credible base to investigate for the organization/control plane, especially if Wingman values durable responsibility and accountable handoff. The fit does not eliminate product work: the particular human relationship, leadership duties, discovery proportionality and executive experience remain Wingman's responsibility.
