Munder Difflin assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/HarnessMD/munder-difflin

Local checkout: research/munder-difflin/repo. Inspected commit: 83acdc1de9eacf23f42df7a5d31b36d023ae64ec. Baseline: WINGMAN_PURPOSE.md. This is a static assessment of this source snapshot, not a claim about the current hosted product. The README advertises 0.5.6 while this checkout's package.json, lines 1–18, declares 0.4.6; revision evidence is therefore more useful than the marketing version.

Fit verdict: a substantial local standing-agent organization and coding workbench, with unusually concrete continuity and supervision mechanisms. It could supply much of Wingman's local agent floor, mailbox, task board and detailed workspaces. It does not supply Wingman's distributed, Telegram-led product-development organization as described. One local Electron main process owns the hive. The manager combines several responsibilities. Product discovery and acceptance remain instructions rather than a modeled workflow. No host scheduler connects Mac and Linux execution agents.

The office graphics are incidental to the assessment. The important product is a manager supervising real CLI processes with durable identities, per-agent memory, message mailboxes, a shared task ledger, live usage signals and direct operator control. This is considerably more than a terminal grid, although it is less structured than Wingman's portfolio of separately led product teams.

Architecture and execution model

The application is Electron with a React renderer, a preload IPC bridge, node-pty processes and xterm terminals. The execution spine is src/main/index.ts, especially spawnAgentCore, lines 2627–3033. UI hires, restored agents, voice hires and manager-created ephemeral workers converge on this path. It resolves the provider, prepares isolation, injects the hive protocol and environment, selects resume behavior, then calls the actual PTY manager. src/main/pty.ts, lines 331–387 and 553 onward, owns the live process map, window ownership, byte streams and exit callbacks. An agent is consequently an independent coding CLI process, not a persona simulated inside a single conversation.

The organization has one special manager, called GOD or Michael in the source, plus ordinary agents and an optional send-only preparation assistant. The manager is itself a real provider-backed agent. Its responsibilities—maintain situational awareness, prefer existing workers, decompose, delegate, resolve conflict, integrate branches and do final QA—are injected instructions in hive.ts, lines 1530–1607. The application supplies coordination rails; deciding what work means and who should do it largely remains model behavior. There is no hard-coded ProductMaster/TechMaster state machine.

The shared coordination substrate is <harnessHome>/hive/, initialized by ensureHive in hive.ts, lines 618–681:

hive/
  registry.json          durable agent metadata and provider session IDs
  board.md               free-form plan, manager as intended sole scribe
  tasks.json             structured kanban, assignees, dependencies, human Q&A
  log.jsonl              coordination/lifecycle events
  fleet.json             current usage, activity and context snapshot
  agents/<agent-id>/
    identity.md          role and identity refreshed on spawn
    memory.md            durable notes preserved across ordinary respawns
    inbox/ + .done/      incoming and handled messages
    outbox/ + .sent/     authored and routed messages
    provider config      hooks, settings and isolated provider home as needed

The main process alone commits the hive Git repository, reducing Git-index contention between agents. This is not versioning of every continuity file: per-agent ignore rules exclude inbox/outbox mail and private Codex homes, while live fleet state, crash tails and the growing cost ledger are also excluded. Mail remains on disk, with .done/.sent archives; Git history principally preserves the tracked shared records and notes. hive.ts, lines 640–653 and 2856–2904; memory.ts, lines 21–35. The application also uses SQLite through db.ts, lines 1–175, for auxiliary durable application records, and a separately protected roster.json, lines 1–35 and 83–204, for UI cards, notes, queues and restoration recipes. These are different continuity layers: the hive registry is the agent-facing organization. The roster is the user's saved floor. The provider transcript is the actual model conversation.

The system remains a local desktop runtime. Its hook socket, process management, shared filesystem and integration broker are local. Multiple windows/floors are not multiple execution hosts. Claude remote control and Codex daemon integration expose local sessions through provider mobile tooling. They do not schedule a worker on another machine. The distinction is visible in the local spawn path and index.ts, lines 3008–3016, which enable Codex Remote and then still spawn through the local PTY manager. There is also an organization-peer trigger settings surface, but its implementation explicitly persists configuration only: the peer messaging service and transport do not exist in this snapshot (index.ts, lines 4263–4278; shared/triggers.ts, lines 1–14). This is a planned extension, not operational cross-machine collaboration.

Agent definition and complete lifecycle

Definition, creation and identity

A durable agent has an ID, name, provider, role, capability tags and cwd in AgentMeta. The registry adds live status, last-seen time, archived/held state, provider session ID and cwd validity. A saved renderer agent also has its standing goal, spawn recipe and worktree path. See hive.ts, lines 146–185, and store.ts, lines 42–118. This separates a person's intended job from temporary activity: preferredAgentRole preserves the durable role instead of accidentally replacing it with a status caption on restart.

There are three important creation routes. A human hires through the Add Agent flow; restoring a previous team replays saved recipes under the same IDs; and Michael can publish a JSON spawn request to spawn-requests/. A portable hire manifest is an importable role template, not an already-running agent or arbitrary executable. Its loader only pre-fills a reviewable hire, and its allowed providers and flags are intentionally restricted. Runtime provider support is broader than manifest import support. See shared/hire.ts, lines 1–95, and main/hire.ts, lines 149–273.

The concepts should be kept separate. A hire manifest describes a reusable configuration. A registry agent is a durable identity and mailbox. A provider session is the external CLI's conversation, referenced by session ID. A PTY is one live local process incarnation. A task card describes work; and an ephemeral worker record is an in-memory controller entry for one manager-authorized hire. These do not have a one-to-one lifecycle. One identity can resume several times, one process can handle several task cards, and a task can remain after its assignee exits. Restored ephemeral worker cards become ordinary agents and do not re-enter liveWorkers, so their old idle/token reaping policy is not automatically reinstated. index.ts, lines 4580–4615 and 4778–4808; hive.ts, lines 119–185.

ensureAgent provisions the mailbox tree, refreshes identity, preserves existing memory, merges the previous registry record and clears the archive flag before generating provider-specific injection. Preserving the previous record matters: it keeps sessionId available for the later resume lookup. Agent identity can outlive one PTY, but a live process is still what makes an agent active. A saved registry entry alone does not mean someone is working. The source expressly distinguishes archived agents from living terminals and records invalid execution directories. hive.ts, lines 715–814.

Execution, tools and permissions

The runtime supports Claude, Codex, Grok, Kimi, Gemini/Antigravity, Qwen, OpenCode, Crush, Pi, Copilot, Cursor and custom commands through provider presets. These presets declare command syntax, resume behavior, initial-prompt delivery and hook/proxy bridges; see agentProvider.ts, lines 1–95 onward. Do not interpret the common floor UI as proof of equal provider capabilities. Claude's native hooks support the richest control path; hookless/custom providers need terminal work-order handoff, and proxy bridges can infer activity but cannot necessarily enforce an upstream tool-permission contract.

Tools principally belong to the chosen external coding CLI. The harness adds skills, default MCP references and hive files. autoMode changes provider-specific approval posture. It is not a role-specific capability system. The source gives Codex its own home/session configuration and prepares resumable session data, while Claude can receive prompt/settings flags. Provisioning is best effort: a hive setup error is logged without automatically blocking the PTY spawn. That improves availability but means “process started” does not prove “fully functioning hive citizen.” index.ts, lines 2778–2820 and 2823–3016.

An additional integration broker grants a worker a token limited to enabled integration IDs. API secrets remain in the main process; dead-worker teardown revokes the capability. This is an application-integration boundary, separate from filesystem and shell permission policy. See integrationBroker.ts, lines 1–35 and 110–180, and index.ts, lines 443–453 and 4758–4774.

Routing, concurrency and workspaces

Messages are JSON envelopes with conversation and reply IDs and acts such as request, query, inform, propose, refuse and done. Agents author outbox files. The router polls approximately every 1.5 seconds, normalizes them, makes the containing agent directory authoritative for the sender, delivers to inboxes and archives sent files. Michael and human aliases resolve to the manager. Broadcast excludes the sender, archived agents and the send-only prep assistant. Unknown, unavailable and special recipients receive explicit handling instead of silent optimistic delivery. hive.ts, lines 1619–1889.

Optional Git worktrees isolate concurrent repository edits. This is branch/filesystem separation, not process sandboxing or multi-host placement. Ordinary agents can share a cwd; parallel ownership and integration discipline then depend on instructions. Ephemeral workers default to isolation, are admitted under a configurable cap (fallback four), and leave excess spawn requests queued. Turning off orchestratorMaySpawn stops consuming new requests while allowing existing workers to finish or be reaped. index.ts, lines 2725–2758, 4739–4778 and 4889–5015.

Isolation is best effort, including on the ephemeral path: a Git worktree creation error is logged and spawning continues in the shared cwd. Dependency linking is also best effort. Consequently, isolate:true expresses intent rather than an invariant that the caller may safely assume. Wingman would need a fail-closed isolation option before assigning concurrent edits on the strength of that flag. index.ts, lines 2720–2758.

Persistence, resume and scheduling

Normal restart continuity combines stable agent IDs, durable memory/mail, saved worktree paths and provider transcript resume. Claude resume verifies or seeds a transcript in the target cwd before attaching --resume; Codex resume searches the home that owns the indexed session and orders its resume subcommand/session correctly. Explicit IDs take priority over the last recorded session. A requireResume request can refuse a replacement process when the original conversation cannot be resumed. These details are actual implementation, not merely “agents remember.” index.ts, lines 2856–2942.

The restore hook re-enters an existing worktree rather than generating another one. If the worktree vanished, it falls back to the base repository and surfaces that fact. It retains failed restores for retry and preserves roster order. useRestoreTeam.ts, lines 57–191. Disk-backed roster writes use temp-file replacement, append-only backups and an empty-first-write guard so a blank renderer cannot erase a populated floor: roster.ts, lines 118–204.

Scheduled missions persist their last-fired time and support interval and weekly delivery. The seeded hourly ops standup is enabled. It mails Michael instructions to review every agent, task ownership and blockers. The separate adaptive manager heartbeat ships disabled and adds active re-engagement based on quietness or actionable mail. Context maintenance queues compact/clear commands for idle-safe delivery instead of injecting them mid-command. Independently, an always-on worker watchdog notices pending mail, respects boot grace, busy output, operator pause and recent human-permission prompts, and re-nudges an observable stalled worker. It is edge-triggered to avoid repeating the same mailbox reminder forever. config.ts, lines 61–110; index.ts, lines 699–780, 937–947, 1331–1365 and 5278–5291; workerWake.ts, lines 188–309.

Actual current Stop behavior matters because several comments still describe an older Stop-to-inbox-drain design. The hook handler explicitly returns an ordinary idle Stop and does not force continuation for unread mail. The renderer instead enqueues an inbox nudge, rechecks that mail still exists at delivery time, respects idle/boot/draft/menu controls, and removes queued input after acknowledged PTY writes. This is deliberately asynchronous mail handling, not immediate message interrupt semantics. hooks.ts, lines 490–499; useHive.ts, lines 678–729 and 778–885. Renderer draft/menu protections have a half-hour expiry; source comments state that subsequent automation types after existing text rather than clearing it. These heuristics warrant runtime testing before treating unattended terminal delivery as proven safe.

Steering, interruption and failure handling

Operator control is not limited to typing into a terminal. ControlRegistry queues steering guidance, denies selected tools or all tools while paused, requests a clean halt, and separately pauses automatic input delivery. HookServer consumes those decisions at tool/prompt boundaries. See control.ts, lines 1–128, and hooks.ts, lines 502–565. This is stronger than relying on a model to obey “stop,” but the fine-grained guarantee is bounded by the provider bridge. Hard process termination remains available independently.

The circuit breaker combines repeated identical tool calls, error storms, token velocity, usage budgets and progress evidence. It escalates one level at a time through steer→constrain→stop and recovers gradually. hardStop defaults false; without it, “constrain” is a corrective message rather than an enforced kill. The manager is excluded from worker-breaker inputs and supervised through the heartbeat instead. Progress detection considers coordination, work activity and tool evidence to reduce false positives. breaker.ts, lines 1–120 and 167 onward; enforcement in index.ts, lines 1195–1272.

Routing has narrow malformed-JSON repair, quarantine for irreparable outbox files, atomic inbox writes, sender identity normalization and a relay-hop fuse. Mail to an archived worker is preserved, but a sender expecting an answer is told that no one is there. These mechanisms protect coordination state. They are not an exactly-once distributed task queue. Crashed processes produce exit records and restoration options; semantic retries or reassignment are generally manager decisions, not a universal retry policy.

There are specific recovery boundaries. Queue delivery retries failed PTY writes only three times, then removes the queue item and logs a warning. It does not establish that the model accepted or completed the instruction. A successfully created worker whose initial hive.send throws is still registered and its spawn request archived as successful, leaving the idle reaper as a backstop. Abnormal process exits retain structured code/signal metadata and a restricted local output tail. They do not automatically replay unfinished work. useHive.ts, lines 778–885; index.ts, lines 4798–4827; hive.ts, lines 2680–2748.

Completion, acceptance and retirement

For an ephemeral worker, completion is an authored act:done message after its current spawn time. The controller rejects stale prior-incarnation done signals, settles only inbox mail from before the completion cutoff, reports unhandled requests to Michael, then kills and tears down the worker. Idle and token-limit reap paths do not claim success and retain pending mail. index.ts, lines 4635–4681 and 4906–4981. This is a credible worker lifecycle, but the harness does not inspect test evidence or enforce a product definition of done before honoring the signal.

All teardown paths revoke broker grants, clear live mappings/watchdog/breaker/usage state, stop proxy sidecars and archive the registry entry. A material distinction: ephemeral-worker worktrees receive a safety gate preserving unintegrated work for Michael. The ordinary-agent worktree branch in the same teardown uses immediate removal. The safe ephemeral-worker behavior should not be generalized to every agent-close path. index.ts, lines 443–504 and 528–567. A later GC sweep removes preserved worker worktrees only when clean and integrated, and worker scratch directories can eventually be reclaimed. Durable ordinary-agent records and short-lived ephemeral scratch therefore have different retention expectations.

Finally, “Closing Time” is a coordinated graceful shutdown product. The manager broadcasts a save/park request, workers append state and next steps and acknowledge, and the harness independently checks live workers' acknowledgments before accepting the manager's complete signal. Cancellation and timeout are explicit. This protects continuity when closing the desktop, although acknowledgments are still statements from agents rather than proof of every change's correctness. closingTime.ts, lines 1–27, 85–145 and 149–226.

Coordination in practice: one implemented intake-to-result path

The generic webhook path makes the boundary between application guarantees and model responsibilities clear:

  1. An external caller posts to a configured endpoint. WebhookServer validates endpoint secret, body and schema; endpoint mode may hold the request for operator approval. It returns a capability token for polling that request's status. Only a hash is persisted. webhook.ts, lines 1–38 and 292–390.
  2. handleWebhookMessage classifies or accepts the inbound kind, applies trigger mode, records history and either holds it or calls dispatchWebhookWork. That function adds a real kanban card before routing an inbox request to Michael. The request includes the card ID and instructions to populate its result. index.ts, lines 1850–1960. A recorded/pollable card does not prove successful dispatch: manager mail delivery is best effort after card creation.
  3. Michael's injected policy tells it to check the roster, prefer an existing suitable agent and dispatch a four-part contract. It can send directly, or publish a spawn request when enabled. This reasoning/selection step is prompt-driven. The application guarantees routing and worker admission, not quality of decomposition. hive.ts, lines 1586–1607; index.ts, lines 4689–4827.
  4. The worker receives durable inbox mail and is woken when appropriate. It can ask another agent directly. A need for the human is represented as a blocked card with a humanQA entry, and Ask Me shows downstream tasks waiting on it. The human's answer is written back onto that card and mailed to Michael, which must interpret it and unblock/delegate further. AskMeTab.tsx, lines 11–45 and 98–140.
  5. The worker edits its isolated repository and reports completion; Michael performs integration and updates the original task's status/result. The webhook status API exposes that result only to the holder of the corresponding token. The worker controller preserves unintegrated branches, but it does not itself certify the result or merge the work. index.ts, lines 528–567, 4906–4981; webhook.ts, lines 292–308.

Two distinct coordination products coexist. Mailbox coordination carries questions, proposals, dispatches and reports between real agents. Ticket coordination preserves assignees, dependencies, blocked human decisions and outcomes. They are connected by model-authored references and UI actions rather than a mandatory task↔conversation relational schema. This flexibility is useful for general office work, but Wingman would need stronger project/task/message linkage for reliable cross-project decisions.

The shared ledger has useful protection without database transaction semantics. Main-process addTask/patchTask/deleteTask reread the latest collection, and shallow merging preserves fields unknown to the renderer. Agents nevertheless directly author the same file, and the writer uses ordinary writeFileSync, not compare-and-swap or an interprocess lease. Ask Me sends a replacement humanQA array derived from its polled snapshot; patchTask protects unrelated cards but does not check a question revision or merge concurrent changes within that array. The code therefore does not establish the stale-question protection promised by the comment above sendAnswer. This is a static concurrency limitation, not an observed data-loss incident in this assessment. hive.ts, lines 1910–1966 and 2797–2806; AskMeTab.tsx, lines 87–140; taskLedger.ts, lines 37–67. Its regression test verifies preservation of an independently appended webhook card, not concurrent edits to the same question history: hive-task-mutation.test.cjs, lines 40–60.

Major additional capabilities beyond Wingman's described scope

Heterogeneous agent and model operations. Wingman specifies Codex agents; Munder is an operator layer over numerous independent commercial/open-source CLIs plus BYOK/local-model configurations for supported engines. The benefit is choosing cost, context and tooling per worker while retaining common communication. The cost is a capability matrix rather than one uniform execution contract: hooks, resume, permissions, telemetry and prompt injection differ by provider. agentProvider.ts, lines 1–95 onward; index.ts, lines 2896–3016.

Voice-directed agent organization. Realtime Michael is more than dictation. Its tools can inspect organization state, dispatch, change tasks, steer, hire, pause, stop and modify schedules through the existing action spine. Destructive/expensive actions have a two-step verbal echo-back with a distinct confirmation token, idle-mic check and hard prohibitions on manager/mass-agent destructive operations. realtimeActions.ts, lines 1–129; token minting in realtime.ts, lines 52–104. This is a new control interface, requiring additional audio/session reliability, costs and action authorization semantics. The open-source freeflow.ts, lines 1–113, implements Groq transcription; README claims about additional local meeting/transcription products are not established by this source path and are not credited as verified implementation here.

External automation intake and bounded result access. Multiple secret-gated webhook endpoints, trigger modes, approval history, status tokens and Slack threads turn the local team into an automation endpoint for other systems. This is broader than Wingman's personal Telegram channel. It could receive organizational work without giving callers the whole task ledger. Integration consequences include exposure/tunnel lifecycle, authentication and avoiding confusing a queued card with work actually accepted by a live manager. webhook.ts, lines 1–38, 292–390; index.ts, lines 1775–1960.

Capability-brokered business integrations. The loopback broker mediates access to enabled REST integrations without handing raw service credentials to every ephemeral worker. This can support operational roles beyond coding. Wingman would benefit if adding purchasing, reporting or internal-service agents, but must decide project-specific grant scope and tool policy instead of assuming every enabled integration is appropriate for every worker. integrationBroker.ts, lines 1–35 and 110–180.

Shared semantic memory and document retrieval. MemPalace mining shares durable agent notes by semantic recall, with an optional independent enterprise-document store. The store called “Knowledge Graph” exposes document ingestion, chunk ranking and retrieval; its name should not be read as proof of a full entity/relation reasoning system. memory.ts, lines 1–15, 63–80, 118 onward; knowledge.ts, lines 1–130. This is a major memory product beyond simple directives. It adds indexing dependencies and staleness/failure modes: markdown continues to work when MemPalace is missing, and mining is periodic rather than immediate.

Fleet economics and automated behavioral guardrails. Usage/cost ledgers, live context occupancy, incremental lifetime-cost aggregation and a graduated breaker are substantial operating infrastructure. They help distinguish a worker doing expensive useful work from one looping or waiting on a human. They do not establish quality: an economical agent can still be wrong, and a productive long-running agent may need careful thresholds. breaker.ts, lines 1–120; index.ts, lines 1195–1329; costLifetime.ts.

Distinctive mechanisms and innovation

These are mechanisms worth studying, not claims of historical novelty across the industry.

Ordinary coding CLIs become durable organizational peers through filesystem mail. The application preserves the provider's authentic terminal while injecting identity, long-term notes and a simple message protocol. Agents can communicate with only file operations. The harness alone handles delivery and Git commits. That is a pragmatic way to turn incompatible harnesses into a common team. Its limit is behavioral adherence and provider bridge variance. It does not create a general distributed actor runtime. hive.ts, lines 715–840 and 1619–1889.

Live routing context is injected separately from stable identity. Michael receives fresh roster/context information at session/prompt boundaries so a resumed transcript does not keep dispatching to dead agents. Standing goals are delivered when new or changed rather than repeated in a stable system prompt. The distinction helps preserve prompt-cache stability while keeping organizational state current. hooks.ts, lines 532–565. Wingman could apply this distinction to immutable profile instructions versus live project/team state.

Human decisions live on the work they unblock. humanQA preserves both question and answer history on a task; Ask Me shows dependent work and sends the answer back into management coordination. This avoids a disconnected approval inbox that loses product context. Its limit is that no typed decision owner, project key or automatic outcome transition enforces correct routing. AskMeTab.tsx, lines 11–45 and 98–140.

Worker release is coupled to integration safety. The system distinguishes current-incarnation done signals, unread mail crossing completion, dead recipients and unintegrated branches. It frees compute without necessarily destroying work, then informs the sole integrator and later reclaims proven-safe worktrees. That is directly relevant to a persistent development organization. The limitation is that integration safety is not acceptance safety, and the strongest retention gate is specific to ephemeral workers. index.ts, lines 443–567, 4635–4681 and 4847–4981.

Memory condensation is verified before replacing durable notes. Reflection splits memory into pinned facts, condensed history and recent verbatim sections, backs up first, asks a hidden summarizer for a framed response, checks invariants and size, then atomically swaps. This is a concrete attempt to keep continuing agents' working notes bounded while retaining recoverability. It protects structural retention, not semantic truth: a model can still summarize incorrectly. reflect.ts, lines 156–265 and 390–417.

Shutdown is an organizational protocol with a harness-side completion gate. Closing Time reuses actual agent messages to coordinate save/park/acknowledge and independently rejects a premature manager completion. This pattern is stronger than trusting “everyone saved” in prose. It suggests a reusable Wingman principle: let agents perform flexible work, but make critical lifecycle transitions depend on observable state. The observable ACKs still cannot prove semantic completeness. closingTime.ts, lines 85–145 and 175–224.

Practical use for Wingman

The agent floor and coordination design supplies several reusable mechanisms. These include stable identities with per-provider resume, file-backed mail, a shared kanban and task-bound human answers. It also supplies per-agent terminals/IDE, live fleet usage and worker retirement. A Codex-only Wingman could simplify the provider abstraction substantially while preserving these ideas. The MIT license in this checkout makes code reuse a practical possibility, subject to checking individual dependency and asset licenses if shipping it.

Adapting it into Wingman would require substantive product work:

  • Introduce first-class projects, project IDs and workspace placement, with explicit product/technical leaders and specialist assignments. Current project labels and cwd references are insufficient as routing authority.
  • Add Telegram Butler as a separate durable representative; preserve source message, project, question and recipient IDs across every answer. Replacing Slack UI text alone would not produce Wingman's routing semantics.
  • Model project discovery, specification readiness, acceptance scenarios and completed delivery. Make integration/testing evidence and human acceptance distinct from a worker's done signal or task status.
  • Build durable project rooms and participant membership, plus explicit task↔conversation↔agent↔artifact links. Existing mail is a useful transport primitive, but cannot by itself provide Room1/Room2 navigation and escalation context.
  • Add host agents/executors on Mac and Endeavour, authenticated shared coordination, leases/liveness, durable request ownership and host placement. Local filesystem polling and node-pty cannot be promoted to this by labeling provider Remote Control “distributed.”
  • Add an executive briefing/timeline layer that records meaningful outcomes and planned next work, linking entries to authoritative tasks, changes, test results and the detailed session. Raw event logs and latest assistant text remain useful drill-down signals.
  • Review provider-control parity and make the chosen Codex bridge's pause/steer/halt semantics explicit. Also unify retention policy so ordinary-agent teardown has the same protection Wingman expects from ephemeral-worker integration safety.

I would treat this codebase as a strong local organization/workbench reference or component base, rather than a finished Wingman replacement. Its most useful lessons are state separation, task-bound human feedback, provider session continuity and lifecycle gates. Its largest missing piece is the product/portfolio model linking discovery, leadership, execution and acceptance across machines.
