## AX: verified execution boundaries

**F04/F11/F15:** The complete [service and resource schema](../../../ax/repo/pkg/apis/v1alpha1/ax.proto), lines 24–208, exposes Task, Workspace and Model CRUD/lifecycle operations, with no message, room, project, approval or supervision resource. [Server startup](../../../ax/repo/cmd/ax-server/main.go), lines 113–141, constructs the reconciler and request server, then waits for shutdown. Readiness polling inside an explicit lifecycle request is not a continuing ProjectMaster. The report's Absent verdicts are supported by the inspected implementation boundary and scoped absence searches.

**F17:** Real remote provisioning is present through Agent Substrate, rather than a local subprocess being called distributed. The [reconciler](../../../ax/repo/internal/controller/reconciler.go), lines 154–239, ensures the atespace/template/actor; [Substrate template construction](../../../ax/repo/internal/substrate/client.go), lines 364–396, requests VOLUMES snapshot fidelity and a durable `/workspace`. The report gives Similar credit while retaining the external worker scheduler/isolation dependency and missing Wingman host/project/room semantics. No two-machine runtime was claimed.

**F18/F19/F22:** [TaskStatus](../../../ax/repo/pkg/apis/v1alpha1/ax.proto), lines 111–126, is current phase/actor/worker/conditions, not a narrative feed. [Status overlay](../../../ax/repo/internal/server/server.go), lines 461–507, derives readiness from actor state plus workspace condition. The [runner](../../../ax/repo/runner/runner.go), lines 158–201, logs/calls an optional local exit hook and deliberately remains alive after command exit. Thus Running/Ready neither means useful coding progress nor accepted delivery. The supplied [test](../../../ax/repo/runner/runner_test.go), lines 71–90, explicitly expects continued health after command exit. The report correctly separates workload completion from sandbox lifetime.

The report also includes important lifecycle caveats beyond its feature matrix: [CreateTask](../../../ax/repo/internal/server/server.go), lines 199–217, starts suspended; initialization uses a marker outside the declared durable volume; Git setup failure can return nil and still let the runner mark readiness ([setup.go](../../../ax/repo/internal/workspace/setup.go), lines 85–108; [runner.go](../../../ax/repo/runner/runner.go), lines 126–150). The marker/custom-path consequences are properly marked source-grounded risks, not reproduced data-loss claims. Production launch wiring does not consume `internal/model` or use Model resources as an automatic coding-engine backend; the report explicitly avoids credit from that disconnected API/client surface.

Extras and innovations are sufficiently broad: declarative resource sizing, snapshot capacity/recovery, remote guest operations, PostgreSQL resource/lease state, runner extension and model integration boundaries. The actor-observed versus AX-owned state split and content-derived template are grounded mechanisms, without unsupported historical novelty claims.

## Open Multi Agent: verified SDK and run boundaries

**F04/F11:** Core is an embeddable runtime with library/CLI entry points. Its real [Team messaging API](../../../open-multi-agent/repo/packages/core/src/team/team.ts), lines 181–239, supports directed messages, broadcasts and read state. Importantly, the bus is not wholly unwired: [task prompt construction](../../../open-multi-agent/repo/packages/core/src/orchestrator/task-execution.ts), lines 1875–1883, injects all addressed messages at task start. The report correctly credits this while explaining that the [built-in registry](../../../open-multi-agent/repo/packages/core/src/tool/built-in/index.ts), lines 37–73, has no agent chat send/read tools, and no room application or automatic wake mechanism exists. Custom application tools are required for autonomous sending. The initial audit search missed `getMessages`; the completed audit and report use the corrected boundary.

**F15/F17:** [Lease heartbeat](../../../open-multi-agent/repo/packages/core/src/run/ledger.ts), lines 464–480, renews execution ownership; [queue dispatch](../../../open-multi-agent/repo/packages/core/src/orchestrator/task-execution.ts), lines 940–1015, reacts to runnable DAG tasks. Neither is portfolio supervision. The [process backend](../../../open-multi-agent/repo/packages/core/src/agent/process-backend.ts), lines 53–77, starts local processes. [FileStore](../../../open-multi-agent/repo/packages/core/src/memory/file-store.ts), lines 28–31 and 128–134, explicitly has no cross-process lock. Custom CAS/run-store abstractions are meaningful extension points, but no shipped host dispatcher/shared multi-host deployment follows from them. The report correctly says Absent for the delivered F17 capability.

**F18/F19/F21:** [Viewer input/model](../../../open-multi-agent/repo/packages/core/src/dashboard/run-viewer-model.ts), lines 35–170, represents one run's tasks/spans/events/causal links. [HTML rendering](../../../open-multi-agent/repo/packages/core/src/dashboard/render-run-viewer.ts), lines 1–27, is self-contained with `connect-src 'none'`. This is useful forensic visibility, not a live executive application or a per-employee semantic history. [getStatus/shutdown](../../../open-multi-agent/repo/packages/core/src/orchestrator/orchestrator.ts), lines 3000–3032, fixes activeAgents at zero because pools are ephemeral, and shutdown clears registrations without cancelling in-flight runs. Both limitations are reported.

**F22:** The report expressly preserves the most material acceptance boundary. [Consensus](../../../open-multi-agent/repo/packages/core/src/orchestrator/consensus.ts), lines 427–453, records rejected verdicts but only replaces output for an accepted revision. [Task completion](../../../open-multi-agent/repo/packages/core/src/orchestrator/task-execution.ts), lines 1573–1614, can still complete the original successful result. The [consensus test](../../../open-multi-agent/repo/packages/core/tests/consensus.test.ts), lines 450–478, corroborates original-output retention and dissent. Optional repair policy may react, but judge rejection alone is not a hard product gate.

The report covers major extras beyond the main DAG API. These include durable content-bound approvals, lease/fencing ownership, checkpoint restoration and context-lineage journal verification. It also covers topology receipts, bounded plan repair, consensus, offline/online evaluation, egress/tool integration, and separate OTEL and image pipelines. The report consistently separates implemented SDK machinery from application-owned storage, identity, telemetry export, external coding runtimes and example-only releases. Its durable-approval trace explicitly uses a mock model and does not claim an actual deployment.

## Plano: verified network and telemetry boundaries

**F01/F04/F11:** An [Agent](../../../plano/repo/crates/common/src/configuration.rs), lines 53–68, is a configured endpoint. The [ordered executor](../../../plano/repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 279–398, awaits selected services sequentially, prepends a named intermediate assistant response before the original ask and streams the last response. There is contextual handoff, but no direct room messaging or worker provisioning. The report also catches the real [Codex/Claude launch path](../../../plano/repo/cli/planoai/core.py), lines 187–299, instead of incorrectly dismissing every coding integration as a README example. External CLI session/tools/approvals remain external. Telegram is attributed to the external OpenClaw demo rather than Plano.

**F15/F17:** Routing models, signal detection, metric refresh, cache expiration and daemon management are not autonomous project supervision. The [memory cache interval](../../../plano/repo/crates/brightstaff/src/session_cache/memory.rs), lines 24–35, is expiration GC. URL/DNS/TLS service routing can cross hosts; it does not place or manage a Codex agent on Mac versus Linux. [Optional conversation storage initialization](../../../plano/repo/crates/brightstaff/src/main.rs), lines 450–486, and [response state](../../../plano/repo/crates/brightstaff/src/state/mod.rs), lines 15–34 and 63–77, persist response-ID history, not project work ownership. The report correctly preserves these scopes.

**F18/F19/F22:** [Observability TUI](../../../plano/repo/cli/planoai/obs_cmd.py), lines 143–173, refreshes an in-memory collector; [aggregate fields](../../../plano/repo/cli/planoai/obs/render.py), lines 22–51, are tokens/cost/latency/errors. Named spans and behavioral summaries do not deliver Wingman's agent current/recent/next briefings or task-linked narrative history. Repository protocol tests are not generated-product verification or acceptance. The [chain tests](../../../plano/repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 531–707, test message order/final-only response/error behavior, supporting the report's actual request semantics.

Major extras cover API/provider translation, semantic/metric ranking, cache-aware switch budgets and warm-return history, HTTP/MCP filters, heuristic signals, OTEL/Prometheus/TUI, response continuation and remote network deployment. Limits are carefully stated: hosted classifier quality is external, signal events do not remediate, cache budgets estimate switching overhead rather than a total bill cap, and middleware does not create organizational permissions or acceptance.

Optional coverage suggestion sent to the author: the concrete ChatGPT subscription device-flow commands and credential lifecycle deserve a compact mention within provider integration. [CLI commands](../../../plano/repo/cli/planoai/chatgpt_cmd.py), lines 20–85, expose login/status/logout; [auth storage](../../../plano/repo/cli/planoai/chatgpt_auth.py), lines 19–55 and 264–289, stores local tokens and refreshes when requested; [startup injection](../../../plano/repo/cli/planoai/main.py), lines 128–147, supplies provider environment values. This is a source-described capability, with external service compatibility and running credential rotation unverified, not a feature-grade correction.
