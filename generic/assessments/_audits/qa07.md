## Golutra: verified material boundaries

- **F01–F03/F14/F16/F20–F21/F24:** The report correctly separates persisted members, external CLI sessions and in-memory PTYs. `src/features/chat/types.ts:6–30` defines four structural role buckets and free-text role; it is not an extensible responsibility-profile engine. Native PTY execution in `src-tauri/src/runtime/pty.rs:152–204` provides separate local processes. Codex-specific resume belongs to `terminal_engine/default_members/codex.rs:5–29` and `session/commands.rs:103–124`; member persistence alone is not a universal agent checkpoint.
- **F04/F17:** Absent Telegram and absent shared multi-host execution are supported by searches of frontend/backend, positive local PTY execution and local socket/named-pipe IPC (`runtime/command_ipc.rs:16–20`). SSH hits in frontend are repository URL hints, not remote execution.
- **F05–F10/F13/F22–F23:** The persisted roadmap really is only ID/number/title/status (`src/features/chat/types.ts:130–137`). It cannot supply assignees, product discovery, scope/spec/test-case readiness, dependency scheduling, acceptance or portfolio supervision. External CLI ability to write documents/run tests is correctly separated from an implemented product-development workflow.
- **F11/F12:** Important negative boundary independently confirmed: `application/command.rs:63–133` implements both CLI room sends and DMs with append-only `chat_send_message`; `application/chat.rs:60–82` forwards to the DB writer. Execution wake-up is the different `chat_send_message_and_enqueue` entry point at `application/chat.rs:84–104`. DB `write.rs:331–379` distinguishes already-sent append from sending-for-dispatch. UI-directed targets resolve by DM membership/mentions (`orchestration/dispatch.rs:198–227`). Agent-published messages therefore must not be credited as automatically waking peer agents.
- **F15/F18/F19:** Timer-based polling supervises terminal conditions, not product blockers. Semantic flush tests output silence/forced timeout (`terminal_engine/session/polling/rules/semantic_flush.rs:14–81`); its gate is not successful task acceptance. Status indicators and conversation recency are not semantic executive briefings or per-agent outcome timelines. Report classifications preserve this distinction.
- Extras/innovation claims are appropriately scoped: heterogeneous terminal adapters, local skills, fidelity audit and socket publication are implemented; EverOS, golutra-mcp and workflow/template marketing are not silently attributed to this checkout. Empty marketplace and local skill symlinks do not establish a deployed extension ecosystem or distributed knowledge store.

## Munder Difflin: verified material boundaries

- **F05–F10/F13/F22–F23:** `hive.ts:1582–1607` is explicit injected manager/worker policy, including delegation, DoD, board maintenance and human questions. This warrants credit for organizational behavior but does not create modeled per-product leadership, project registry, discovery readiness or product acceptance. `hive.ts:1902–1966` supplies a genuine shared board/ledger with targeted updates. Acceptance remains a prompt/model responsibility.
- **F11/F12:** Real durable mailbox routing and speech acts are verified (`hive.ts:1647–1738` and surrounding router). `to:human` resolves to the manager; broadcast excludes unsuitable recipients. The thread view's inbox API reads only the live mailbox (`hive.ts:1988–1989`, `2670` onward), not its handled `.done` archive. The separate voice read layer can include archives (`hive.ts:1998–2013`); that does not make the thread UI a persistent room transcript. Report's room/history limitation is correct.
- **F15:** Default behavior is correctly distinguished: hourly ops standup enabled (`config.ts:65–85`), adaptive active heartbeat disabled (`config.ts:98–109`). - **F17:** Strong dormant-code boundary independently verified: `index.ts:4263–4278` labels organization triggers persistence-only and explicitly says the peer messaging service does not exist. Local `node-pty`, shared local hive and provider Remote Control do not implement Mac/Linux worker placement. Absent is justified.
- **F18/F19:** Renderer feed is `Record<string,string[]>` (`store.ts:183`) and `pushFeed` appends in memory (`762–763`). Current activity/usage is substantial, but no durable semantic current/recent/next/outcome timeline follows from this. The report appropriately credits partial executive visibility and downgrades semantic timeline coverage.
- **F22/lifecycle:** Worker `done` is self-report. `index.ts:4909–4949` observes done, settles pre-done inbox messages and releases the process; `4951–4980` separately handles token/idle reaping. There is no test-evidence inspection in that release gate. Report correctly distinguishes integration-safe worktree retention from product acceptance and warns that ordinary-agent teardown has weaker worktree retention.

Latest-card reads preserve unrelated cards but do not provide question revision checks or interprocess compare-and-swap.
- Extras/innovation coverage is substantial and proportionate: voice action confirmation, capability-brokered integrations, webhook result authority, semantic/document memory, economics/breaker, reflection, live context injection and graceful shutdown. Source does not justify promoting Pro meeting/local transcription marketing to verified open-source implementation; report correctly withholds that credit.

## Paseo: verified report and source boundaries

- **F04:** No Telegram implementation found in server/app source or repository-wide Telegram searches. Hub consumer routing is expressly external to this repository (`docs/hub.md`, cross-repository compatibility section); local Hub relationship/execution RPCs are not evidence of a shipped Telegram Butler, product discovery or project organization.
- **F11:** `agent/tools/paseo-tools.ts` supplies real agent creation and direct prompt delivery, with provenance and completion subscriptions. Credit agent-to-agent collaboration; do not equate this with durable group rooms/membership or Wingman's management/product chat application.
- **F15:** Scheduling is real production code, not a plugin example or dormant service. `bootstrap.ts:1448–1458` constructs and starts `ScheduleService`. `schedule/service.ts:714–768` reserves/runs/persists successful or failed runs; `928–969` loads an existing agent, rejects an active run, starts a notification prompt and waits for completion/permission/error. Generic recurring work can build supervision; no built-in ProjectMaster responsibility follows merely from having a scheduler.
- **F17:** Real cross-host execution is implemented. `agent/host-operations/index.ts:84–174` opens routed remote daemon clients; `201–251` selects local versus remote destination and creates an actual remote agent in a destination workspace; `262–323` sends prompts with source agent/server identity and reads remote status/activity. `agent/tools/paseo-tools.ts:710–772` routes tool operations, and `1384` onward exposes host discovery. Host docs and `connected-hosts/hosts.e2e.test.ts:140–236,467–528,657–701,976–1033` corroborate one-hop routing, scope isolation, identity pinning, capability boundaries and non-replay of ambiguous mutations. Tests read as intended contract; not run. This must receive substantial F17 credit, though it does not synchronize all project files or supply a standing distributed organization by itself.
- **F18/F19:** `get_agent_activity` is advertised as curated summary (`paseo-tools.ts:3173–3206`), but its implementation is deterministic timeline projection. `activity-curator.ts:159–189` emits assistant text, tool displays, todos, errors and compaction; `216–231` limits/concatenates them. It is not a generated executive current/recent/next/blocker briefing or evidence-linked outcome feed. The report further correctly qualifies persistence: normal `bootstrap.ts:1014–1028` passes the agent registry but no optional durable timeline store. Detailed history recovery relies on provider persistence rather than a daemon-owned durable executive event history.
- **F22:** Schedule status success means its runner ended without the enumerated errors (`schedule/service.ts:746–768`); it does not mean a software product passed acceptance. Pi subagent fixture artifacts contain an `acceptance` object, but fixture output is not an enforced product acceptance engine. Do not credit it as one without tracing its actual provider/runtime dependency.
- **F01–F03/F14/F16/F20–F21/F24:** Stored-agent schema (`agent-storage.ts:45–80`) persists IDs, provider/cwd/workspace, status, config, persistence handle, attention and archive state; manager implements create/resume/archive and cancellation. Profiles are named human-configured provider/model/mode bundles (`paseo-tools.ts:3087–3108`), not standing organizational role instances. Source-backed lifecycle/UI details should distinguish supported provider operations and daemon independence from arbitrary organizational policy.
- **F05–F10/F12/F13/F23:** Workspace/provider/delegation primitives provide material building blocks; no first-class Butler/ProjectMaster/ProductMaster/TechMaster hierarchy, proportionate discovery workflow or acceptance-linked project tracker was found in the checked likely paths. Knowledge can persist in project files/provider transcripts, but this does not itself implement scoped directives or portfolio intake.

- **Dormant tracker and removed chat:** The final report identifies the important shipped-versus-present boundary correctly. Production-only search for `FileTaskStore`/`taskStore` finds the class definition in `packages/server/src/tasks/task-store.ts:17`, with test construction outside that search. No production constructor was found. `packages/protocol/src/chat/types.ts:3` and `chat/rpc-schemas.ts:4` explicitly retain chat schemas only after v0.3.0 feature removal. These must remain `Resembles` primitives/remnants rather than shared tracker/room implementation.
- **Lifecycle and innovations:** The report covers configuration, creation, identity, tools/permissions, routing/concurrency, persistence/resume, schedules, cancellation, recovery/uncertainty, completion and retirement. Its request trace reaches actual shared creation/remote routing/recipient delivery and finish subscription code. Major extras—heterogeneous providers, encrypted remote access, restart-surviving terminal workers, trusted plugins/SDK and external Hub relationship—are covered with clear boundaries. The report avoids calling automation receipt deduplication exactly-once provider work and avoids historical novelty claims.
