## Outcome

No material correction to the three reports' capability boundaries was found. The reports are unusually careful about the required distinctions: independent processes versus durable employees, health repair versus semantic supervision, activity history versus an executive timeline, and worker completion versus product acceptance. Their lifecycle and coordination sections describe the actual implemented surfaces rather than assuming README promises are runtime behavior.

One small clarification would strengthen Orca's concurrency discussion: the legacy polling `Coordinator` is **one globally active coordinator**, not one independent polling manager per run/product. [`gates.ts`](../../../orca/repo/src/main/runtime/rpc/methods/orchestration/gates/gates.ts), lines 14–28, holds a module-level `activeCoordinator` and rejects startup if `getActiveCoordinatorRun()` returns an existing run. Lines 32–55 show actual RPC construction and background loop wiring. The report already warns that the class uses unscoped task lists and is unsuitable as the portfolio isolation model, so this is a precision improvement, not a verdict reversal. Run-aware model coordinators and independently launched workers are a distinct path.

## Verified high-risk boundaries

### Happy

Repository: https://github.com/slopus/happy

- **External runtime scope is correct.** [`README.md`](../../../happy/repo/README.md), lines 41–55, separates this mobile/CLI/relay repository from desktop and Happy Agent. Native [`AgentClient.swift`](../../../happy/repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 122–172, implements actual `/v0/bots` and `/v0/tasks` clients, including supplied identity and mutation IDs. The relay's [`api.ts`](../../../happy/repo/packages/happy-server/sources/app/api/api.ts), lines 101–118, registers session/project and other relay routes, not those agent runtime controllers. Crediting the native client while withholding backend execution guarantees is appropriate. Client wait/retry fields cannot establish external wake/recovery policy: [`Wire.swift`](../../../happy/repo/packages/happy-ios/Sources/HappyCore/Agents/Wire.swift), lines 135–168 and 176–195.
- **F15 remains absent in the inspected local organization sense.** [`daemon/run.ts`](../../../happy/repo/packages/happy-cli/src/daemon/run.ts), lines 1040–1132, checks PIDs, detects replacement CLI code, performs daemon handoff and writes a heartbeat. It never reviews project tickets or asks a blocked specialist for progress. This supports the report's refusal to credit operational liveness as ProjectMaster supervision.
- **F17 is real remote execution infrastructure.** [`apiMachine.ts`](../../../happy/repo/packages/happy-cli/src/api/apiMachine.ts), lines 184–207, registers the machine spawn RPC and forwards decoded options to the daemon. [`daemon/run.ts`](../../../happy/repo/packages/happy-cli/src/daemon/run.ts), lines 278–325 and 601–675, validates/creates the selected directory, launches an independently detached Happy process and waits for registration. This proves host-side execution wiring; it does not prove shared organizational rooms/tracker or cross-host filesystem consistency. The report's Similar boundary is defensible.
- **F18/F19 distinguish useful status from a briefing feed.** [`Wire.swift`](../../../happy/repo/packages/happy-ios/Sources/HappyCore/Agents/Wire.swift), lines 160–168, defines one latest `set_status` line, not current/recent/next summaries with a linked chronology. The report correctly acknowledges the status line without treating it as the required executive feed.
- **F04/F11/F22/F24 are scoped honestly.** The report credits native collaborator/task rendering and provider subagent events while retaining the lack of a locally established autonomous room/tracker/acceptance organization. Its explicit external-runtime caveat should remain attached to any comparative summary; “Absent locally” must not become “the external Happy Agent product cannot do this.”

### Orca

Repository: https://github.com/stablyai/orca

- **F15 is scheduled dispatch plus mechanical coordination, with stated gaps.** [`coordinator.ts`](../../../orca/repo/src/main/runtime/orchestration/coordinator.ts), lines 142–153, explicitly requires pre-created tasks. Lines 155–160 wire message/escalation processing into ticks, but line 218 is an empty higher-level `processEscalations()`. [`automations/service.ts`](../../../orca/repo/src/main/automations/service.ts), lines 118–133, starts a real periodic evaluator and startup catch-up, including headless operation. The report correctly distinguishes this usable scheduling foundation from implemented portfolio/blocker supervision.
- **F17 is implemented federation, not only SSH/session discovery.** [`federated-worker-start.ts`](../../../orca/repo/src/main/runtime/rpc/methods/orchestration/federation/federated-worker-start.ts), lines 43–112, requires durable retry identity, exact remote placement and compatible runtime/federation capabilities. Lines 114–165 record the home dispatch and peer identity before calling remote `orchestration.federationAttachStart`. This supports credit for actual remote execution with coordination, within pairing/version constraints and without a runtime-test claim.
- **F11's remote group limitation is literal code.** [`send-group.ts`](../../../orca/repo/src/main/runtime/rpc/methods/orchestration/messaging/send-group.ts), lines 35–54, excludes federated dispatches from local group candidates and tells callers to address the dispatch directly. The report appropriately avoids calling this transparent distributed Room1/Room2 chat.
- **F18/F19 do not overclaim the UI contract.** [`dashboard-snapshot.ts`](../../../orca/repo/src/shared/dashboard-snapshot.ts), lines 84–137, carries task/latest messages, parent/subagent relation, host/workspace, state/finish times, questions and review. It has neither a planned-next-work field nor a sequence of semantic accomplishment summaries. Similar F18 and Resembles F19 are supported.
- **F22 maintains the attempt/product distinction.** [`orchestration-fleet-outcome-resolution.ts`](../../../orca/repo/src/shared/orchestration-fleet-outcome-resolution.ts), lines 3–8, explicitly includes `finished_unverified`. Task reporting/settlement can account for a dispatch without independently verifying product scenarios. The report's Resembles verdict does not mistake process or provider completion for business acceptance.

### Paradev

Repository: https://github.com/ParadevAI/Paradev

- **The durable Dev layer must remain separate from interactive Codex.** [`agent.ts`](../../../paradev/repo/packages/trpc/src/router/agent/agent.ts), lines 226–275, persists organization agent identity/instructions. The worker [`main.ts`](../../../paradev/repo/apps/agent-worker/src/main.ts), lines 26–35, actually executes an external `pdev --version` preflight and rejects versions without remote mode. [`createActivities.ts`](../../../paradev/repo/apps/agent-worker/src/activities/createActivities/createActivities.ts), lines 139–165, sets pdev gateway/permission and remote host/workspace variables, or `PDEV_NO_WORKSPACE`. The report correctly avoids merging the interactive Codex adapter with the autonomous standing-agent engine.
- **An additional explicit dependency caveat is available.** [`temporal.ts`](../../../paradev/repo/packages/trpc/src/lib/agent-runtime/temporal.ts), lines 7–14, rejects agent operation when `TEMPORAL_ADDRESS` is absent. The report already describes Temporal operational weight, but this shows the feature is disabled without configuration rather than falling back to an embedded local agent loop.
- **F11 peer activation limitation is verified at the mutation boundary.** [`channel-message.ts`](../../../paradev/repo/packages/trpc/src/router/channel/channel-message.ts), lines 446–519, persists/announces human or Dev posts, but only `principal.kind === "person"` calls `startTurnsForMessage` (511–517). Shared rooms and durable authorship are real; agent-authored messages do not wake peer Devs. This is a significant and correctly reported gap from Wingman's autonomous Room2 discussion.
- **F15 is genuinely wired, while semantic supervision is policy.** [`main.ts`](../../../paradev/repo/apps/agent-worker/src/main.ts), lines 154–170, creates a Temporal `devs-reconcile` schedule every minute. [`agent-worker.ts`](../../../paradev/repo/packages/trpc/src/router/agent/agent-worker.ts), lines 66–72, wires reconciliation and due routines. Those are not dead schema fields. They still do not establish a ProductMaster/ProjectMaster organization or blocker review policy, as the report says.
- **F17 cloud task placement is narrower than generic personal-host control.** [`turn-host.ts`](../../../paradev/repo/packages/trpc/src/router/agent/turn-host.ts), lines 37–95, resolves a cloud-workspace row, checks both agent and acting-human permissions, wakes it and issues the remote target. The report correctly separates that durable Dev task path from registered-host interactive Codex and does not claim direct Mac/Arch standing-agent placement already works.
- **F18/F19 retain the executive-summary gap despite navigable activity.** [`agent.ts`](../../../paradev/repo/packages/trpc/src/router/agent/agent.ts), lines 94–152 and 155–223, returns current running reason and historical turn status/time/channel/thread links. This is more useful than an unlinked transcript, but does not produce accomplishments, next work or blocker summaries. The report credits the linked activity without upgrading it to Wingman's semantic timeline.
- **F22 is a real instruction-driven writer/reviewer loop, without a forced product gate.** [`createActivities.ts`](../../../paradev/repo/apps/agent-worker/src/activities/createActivities/createActivities.ts), lines 553–570, explicitly requests delegation, PR checks, independent reviewer, fixes and reporting. It is appropriate to credit substantial review/delivery behavior while noting that the prompt is not a typed test/verdict/DoD acceptance transition. Main/task distinctions and inherited instructions also substantiate the F24 boundary: arbitrary Dev identities do not automatically add agent-valued tracker assignees or a reusable role/team graph.

## Coverage and remaining uncertainty

The reports cover definition/configuration, creation, identity, tools/permissions, routing, concurrency, persistence/resume, schedules, interruption, retry/recovery, completion and cleanup. Each traces a concrete source path and discusses substantial additional capabilities and mechanisms without claiming historical novelty. Their explicit source-only verification language is appropriate.

No major omitted product capability requiring a new report chapter emerged from this audit. Happy already covers the external runtime/native-client split, encryption, voice, browser/artifacts and collaborative todos. Orca covers federation, durable dispatch/messaging, plugins, browser control, issue integrations and session search. Paradev covers standing Devs, writer/reviewer delegation, actor/channels, routines, remote engine, Pages, plugins, automations and detailed interactive controls. This is not an exhaustive verification of every repository subsystem or external engine. Runtime correctness, external hosted services and interoperability with Wingman's actual machines remain unverified.
