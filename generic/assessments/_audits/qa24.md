## Material findings and corrections

### Bernstein: default Telegram task intake is broken before persistence

This was reported to the author and root and is now explicitly included in the assessment. [chat_cmd.py](../../../bernstein/repo/src/bernstein/cli/commands/chat_cmd.py), lines 504–533, builds its own local `TaskStore` and passes `scope="chat"`, `task_type="feature"`. [task_store_core.py](../../../bernstein/repo/src/bernstein/core/tasks/task_store_core.py), lines 1555–1573, constructs both enums. [models.py](../../../bernstein/repo/src/bernstein/core/tasks/models.py), lines 175–178 and 224–231, allows only small/medium/large scopes and standard/upgrade_proposal/fix/research task types. The stock `/run` path therefore reaches a `ValueError`, caught at chat_cmd.py lines 254–257; it must not be described as working task enqueue or a Butler channel. [test_chat_session.py](../../../bernstein/repo/tests/unit/test_chat_session.py), lines 71–84, replaces the dispatcher to avoid the real store, so the successful `/run` fixture cannot disprove this integration defect.

Repairing the enum strings still leaves integration work. The dispatcher discards the requested adapter (chat_cmd.py lines 177–184). It opens another JSONL-backed store instead of using the authoritative running server. It returns a constructed chat session ID without starting a coding session. `/status` at lines 273–287 renders saved binding metadata. `run_forever` at lines 225–231 starts the bridge then waits; `stream_progress` at lines 485–496 is a helper with no production caller found. Telegram transport itself is real: [telegram.py](../../../bernstein/repo/src/bernstein/core/chat/drivers/telegram.py), lines 112–131, installs slash handlers and callback buttons and starts polling, but installs no ordinary free-text intake handler. The report's F04 **Resembles** is appropriate.

### Bernstein: Fleet search is a parsed empty response, not cross-project search

Also reported to the author and included in the report revision. [routes/fleet.py](../../../bernstein/repo/src/bernstein/core/routes/fleet.py), lines 48–85, can return genuine project snapshots with an attached aggregator and explicitly returns an empty stub otherwise. However, lines 89–125 always return `matches: []` for `/fleet/search`; aggregator presence only changes the `stub` boolean. Neither a visible search control nor `stub=False` proves search execution. The separately implemented Fleet application/aggregator remains creditable; the source boundary should stay explicit.

### Bernstein: remote terminal outcome delivery is best-effort

Additional lifecycle clarification sent to the author and incorporated in the final report. [worker_cmd.py](../../../bernstein/repo/src/bernstein/cli/commands/worker_cmd.py), lines 609–624, removes the whole `_pending_reports` queue before posting terminal outcomes. Completion/failure methods at lines 552–589 do not check the HTTP response status and catch/log transport errors without requeuing. A network error or non-success response can therefore lose the worker's terminal report unless another independent recovery path resolves the central task. The genuine remote worker implementation still supports F17; this limits claims of reliable remote completion/recovery rather than making it a local-only system. Lines 344–362 also begin with `ok=True` and can classify `ChildProcessError`/unavailable status as successful before branch delivery; a process disappearing is not universally evidence its work succeeded.

### Nasiko: distinguish a wired MAF worker from unconditional execution

The author added the precondition after QA notification. [server/lib.rs](../../../nasiko/repo/server/src/lib.rs), lines 172–216, starts the MAF Redis worker only with an OpenAI API key. Without it the workflow routes remain available and can queue work that is not consumed. [maf/worker.rs](../../../nasiko/repo/orchestrator/src/maf/worker.rs), lines 85–125 and 333–355, awaits execution inline; [maf/executor.rs](../../../nasiko/repo/orchestrator/src/maf/executor.rs), lines 422–458 and 580 onward, performs sequential steps. Multiple independently running consumers are conceptually separate from this single consumer's concurrency. The report distinguishes hosted-service concurrency, sequential workflows and product-team allocation correctly.

### Swarm: source citations and supervision boundary were corrected

The initial report used several worker-hub line ranges beyond the 182-line source file. The author corrected those after notification. Actual [worker-hub.tsx](../../../swarm/repo/web/src/features/desktop/orchestrate/worker-hub.tsx) lines 65–99 contain worker summary, 127–161 run history and session links, 156–161 acknowledged cancellation, and 171–182 revision history. The report now credits these operational views while retaining the missing semantic executive briefing/timeline boundary.

The author also added [automation_context.go](../../../swarm/repo/swarmd/internal/run/automation_context.go), line 26, which explicitly warns against claiming unsupported blocker supervision. Real [worker_wake_scheduler.go](../../../swarm/repo/swarmd/internal/run/worker_wake_scheduler.go) machinery at lines 58–81 and 155–158 supplies scheduled admission/reconciliation, not an installed ProjectMaster that discusses portfolio blockers. The report's qualified F15 **Similar** credits periodic work and watchdog capabilities without treating the management policy as shipped.

Their lifecycle chapters cover configuration/creation, identity, tools/permissions, routing, concurrency, persistence/resume, scheduling, interruption, recovery, completion and cleanup. Each contains a real entry-to-execution trace, substantive extras with integration costs, code-grounded distinctive mechanisms and explicit static verification limits.
