## Antfarm: verified claims and boundaries

The report's distinction between durable installed OpenClaw role configurations and disposable execution sessions is supported by `src/installer/agent-provision.ts`, `install.ts`, `run.ts` and `agent-cron.ts`. Antfarm is not merely a collection of prompt files, but session spawning is instructed to the external polling model rather than issued directly by Antfarm TypeScript. This makes the report's external-runtime qualification essential.

The F04/F11/F17 boundaries are well grounded. `src/installer/install.ts:49–51` denies workflow agents `message`, `sessions_send` and `nodes`; run context and verifier feedback provide handoff, not rooms or peer chat. `src/db.ts:6–23` opens a home-directory SQLite database; there is no host-aware shared coordination. `src/installer/events.ts:64–83` provides outbound fire-and-forget webhooks, not Telegram intake or correlated human-answer routing. The main OpenClaw session can supply an external human channel, but that is not an implemented Butler service.

F15 deserves positive credit and the report provides it. `src/medic/medic-cron.ts:65–90` installs a five-minute isolated watcher agent; lines 13–30 instruct it to run concrete diagnostics and alert the main session about critical unresolved findings. `checks.ts:34–209` implements stuck steps, stalled runs, dead runs and orphan cron checks. `medic.ts:39–125` executes remediation, and lines 142–206 persist findings/actions. This is real periodic technical supervision, with a prompt-mediated alert, below Wingman's portfolio/leadership/blocker follow-up.

The report correctly avoids promoting visibility into executive summaries. `src/server/dashboard.ts:73–148` exposes workflows/runs/stories/events/medic APIs and HTML; `events.ts:10–26,101–116` records run transitions, not an individual agent's summary timeline linked to underlying commands, conversations and test evidence. Thus F18/F19 are only related primitives. Dashboard definitions are read from bundled workflow YAML (`dashboard.ts:21–37`), while running definitions are installed separately; the report explicitly notes this extensibility limit.

F22's operational caveats are important and verified directly. `step-ops.ts:679–774` never reads `expects` when completing an ordinary step. `handleVerifyEachCompletion` at lines 785–798 treats any status except literal `retry` as successful verification. More fundamentally, implementation completion leaves its loop step `running` while setting verification pending (716–744), but the verifier claim query requires all predecessors done/skipped (494–505). The report describes this conflict as static source evidence, not a runtime reproduction. Its explanation of acceptance/PR prompts versus mechanically enforced acceptance is accurate.

The major extras—security remediation workflow, separate defect investigation, webhooks, Medic remediation, and install/uninstall packaging—are covered. No major additional product surface was found missing in this checkout. All named lifecycle dimensions appear, including the incomplete cancellation guard, retention, retries, terminal-state mutation, resume, scheduling and destructive workflow retirement.

## myclaude: verified claims and one recommended addition

The report correctly distinguishes the npm/Python installer, host-interpreted development protocols, Go local subprocess wrapper, and optional harness state. `codeagent-wrapper/internal/application/runtaskset/runtaskset.go:47–118` builds topological layers and aggregates execution results; `internal/executor/executor.go` starts real CLI processes and preserves backend session IDs. This supports F01/F02/F14/F16 while not proving standing organizational identity.

F04 and F11 absence is supported by the local CLI/host workflow and prompt/result routing paths. F15 remains a hook/event continuation primitive: `skills/harness/hooks/hooks.json` registers Stop, SessionStart, TeammateIdle and SubagentStop, not an independent timer. `harness-teammateidle.py:75–156` only blocks idle in an active harness; `harness-sessionstart.py:123–181` injects counts/next/log context. The report properly refuses to equate that with a persistent supervisor.

F17 correctly remains absent. `harness-claim.py:271–285` records a caller worker ID or `hostname:pid`, but does not supply remote execution. Local filesystem locks, local PID checks and a hostname-bearing lease are not a multi-host scheduler. Claims/reaping are real concrete local coordination: `harness-claim.py:236–297` locks state, reaps expired leases, chooses eligible work and atomically writes ownership. Those are correctly credited without creating an imaginary server or chat app.

F18/F19 are scoped correctly: task counts/next hints, wrapper result summaries and SPARV/harness journals do not provide current/recent/next/blocker briefings for persistent individual agents or cross-linked personal timelines.

The report already captures the material dormant-wiring defect in `/do`: `skills/do/scripts/task.py:27,152–200` writes `task.md`, while `hooks/stop-hook.py:16,44–60` and `hooks/verify-loop.py:29,59–67` read `task.json`. `scripts/get-context.py:16,93–98` uses the same stale JSON reader. The report's bounded temporary-fixture reproduction is explicitly identified as the author's runtime check; this audit independently confirms only the static source mismatch.

Recommended additional sentence for F22/completion: even with a legacy `task.json`, `verify-loop.py:153–156` permits exit when no commands are configured, and `185–194` returns `decision: allow` at `MAX_ITERATIONS` before running verification. Therefore the hook is a bounded retry aid, not a fail-closed quality or acceptance gate. This detail reinforces the existing verdict and does not overturn it.

The report covers major additional capabilities: four backend adapters, worktrees, budgeted skill injection, local leases, multiple development protocols, host-event continuation and reflection. It also explains layer-barrier scheduling, lack of automatic predecessor-output injection, backend-specific permissions, default bypass flags, interrupted-process behavior, ignored timeout parameters, temporary evidence retention, completion and cleanup. These satisfy the guide's deep lifecycle requirement rather than merely listing features.

## oh-my-openagent: final report review and source boundaries

F04 must not be called absent without qualification. `packages/openclaw-core/src/reply-listener-telegram.ts:30–91` polls Telegram and requires a reply to a previously mapped message, a matching chat and text. It looks up the message-to-session mapping (62–63) and injects into the tmux pane (71). `reply-listener-injection.ts:43–74` checks pane confidence, sanitizes/truncates text and uses `sendToPane`. Startup is wired by `packages/omo-opencode/src/testing/create-plugin-module.ts:256` and session dispatch by `plugin/event.ts`. This is a genuine bidirectional external session bridge; it does not perform Butler's natural-language portfolio intake, project registry routing or durable question/answer ownership. A further precision boundary: the Telegram reader checks chat ID and reply mapping, not individual sender IDs; do not uncritically repeat AGENTS.md's generic authorized-user claim for Telegram.

F11 also has actual execution wiring: `packages/omo-opencode/src/plugin/tool-registry.ts:62` composes team tools, and `tool-registry-team-tools.ts:17–48` registers lifecycle, messaging and shared-task tools only when `team_mode.enabled`. The `team-mode/AGENTS.md` and underlying source describe file-backed mailboxes, atomic task claims, member sessions and worktrees. It is materially more than template personas, although disabled by default and distinct from Wingman's human-browsable Room1/Room2 application.

F15 must separate several concepts: background-manager polling/staleness recovery, team idle-wake/orphan events, and optional command monitoring. `features/background-agent/manager.ts:2623` starts the polling interval; `task-poller.ts:135–190` interrupts stale work and notifies the parent. `create-managers.ts:102–108` creates MonitorManager only when enabled. `config/schema/monitor.ts:4–5` defaults monitor and live mode off; `features/monitor` manages watched subprocess output, not a project-management supervisor. Legacy ralph-loop code must not be credited merely because its directory exists; current root guidance marks it no longer wired and points to the gated goal hooks.

F17 should not be inflated by `RpcHostRunner`/`host-session` names. `packages/senpi-task/src/runners/rpc-host/socket-client.ts:14–39` resolves a local socket/Windows pipe and calls `createConnection(endpoint)`; `shard-socket.ts:76–102` constructs local agent-dir/rpc/shards socket paths. It supplies resilient local engine-host continuity, not Mac/Linux shared multi-host execution.

F18/F19 should credit but bound the TUI. `packages/omo-opencode/src/features/tui-sidebar/snapshot-builder.ts:39–52` publishes active agents, a background job board and loop counters. Lines 92–98 contain title/status/tool-call/last-tool fields; `snapshot-schema.ts:24–54` contains no recent-accomplishment/next-work/blocker narrative or personal timeline. It is an execution status view, not the specified executive briefing. The explicit per-project mirror path/schema likewise does not establish a portfolio service.

The current tree has multiple substantial editions/components beyond OpenCode. A final report should cover Codex Light/lazycodex and Senpi/native task, team and DAG execution. It should also cover isolation, retained host execution, memory-core and shared MCP/LSP tools. The OpenCode plugin README and historical root src paths alone do not establish the full capability set. Behavior is edition-specific; a core package's presence alone is insufficient to claim it is published, enabled or wired in every edition.


### Required correction: native member taskboard trace crosses edition boundaries

The report's native team request trace, step 3, says a member claims work through the core claim primitive (E06). The underlying primitive exists, but this is not the shipped native member tool path. `packages/omo-senpi/src/components/task/index.ts:74–81` explicitly returns before registering the task engine/tools when the session role is `member` or `isTeamMemberProcess()` is true. `packages/senpi-task/src/tools/team/index.ts:77–85` builds the six lead tools, including `task_create/get/list/update`. The member bundle's `team/member-extension/index.ts:86–93` registers only scoped `task_send`; `index.test.ts:74–76` asserts the registered names equal `["task_send"]`.

Revise the native trace so the lead creates/assigns/updates taskboard records through the team service and members report progress through messages, or supply an actual additional exposed member-tasklist route. The native `runTeamTaskUpdate` path (`tools/team/tasks.ts:114–123`) passes an explicit owner into the lead service; it does not identify an independently calling member. Wording elsewhere that a native team task's completion is necessarily an "owner-authored tracker update" should likewise be qualified. OpenCode's member tool exposure and core guarded claims remain substantive; they must not be silently transplanted into the native trace. This is a source-trace correction, not a claim that all F09 shared tracking is absent.
