## Material boundaries independently verified

### oh-my-codex

1. **F04: bidirectional Telegram session replies are real, but this is not Butler/new-product intake.** [Reply listener](../../../oh-my-codex/repo/src/notifications/reply-listener.ts), lines 768–813, skips messages without `reply_to_message`, requires configured chat ID, resolves an existing notification-to-session mapping and injects text into its tmux pane. Lines 466–489 inspect Codex pane content before injection. This deserves primitive/session-steering credit; arbitrary new-product requests in a continuing Butler conversation require separate intake/routing semantics.
2. **F15: actual monitoring and nudge mechanics must be credited within a live local team boundary.** [Runtime](../../../oh-my-codex/repo/src/team/runtime.ts), lines 4676–4717, derives dead/non-reporting worker recommendations and reclaimed claims. [Leader nudge](../../../oh-my-codex/repo/src/scripts/notify-hook/team-leader-nudge.ts), lines 797–891, tracks previous progress and selects stale-leader/mailbox attention reasons. Recommendations alone do not perform semantic blocker resolution or portfolio supervision. [Auto-nudge](../../../oh-my-codex/repo/src/scripts/notify-hook/auto-nudge.ts), lines 644–847, adds deduplication, cooldown and bounded permission-stall response; this is another distinct mechanism.
3. **F22: the code-change completion gate is stronger than a prompt, but it checks reported evidence rather than rerunning acceptance tests.** [Task transition](../../../oh-my-codex/repo/src/team/state/tasks.ts), lines 219–242, rejects completion without required delegation/coordination evidence and calls `validateCompletionEvidence` for `requires_code_change` tasks. [Validator](../../../oh-my-codex/repo/src/team/completion-evidence.ts), lines 15–46, requires an in-workspace, nonsymlink, bounded JSON artifact; current team/task/claim hash; freshness; summary; nonempty command/output rows marked `passed`; an `unverified` array; and structured Verification text. It neither executes those commands nor establishes independent integrated product acceptance. The artifact is worker-authored.
4. **Autoresearch reachability correction: do not infer a current detached evaluator product from the old runtime module alone.** [Legacy runtime](../../../oh-my-codex/repo/src/autoresearch/runtime.ts), lines 458–524 and 538–618, contains evaluator/keep/discard machinery, but caller search found only internal calls within that old module. The actual [CLI](../../../oh-my-codex/repo/src/cli/autoresearch.ts), lines 4–30 and 104–110, hard-deprecates execution and directs the user to the hook-native skill. The final report correctly describes [current skill validation](../../../oh-my-codex/repo/src/autoresearch/skill-validation.ts), lines 133–178, and the [skill](../../../oh-my-codex/repo/skills/autoresearch/SKILL.md), lines 8–66. This supersedes my initial suggestion to promote the old runtime as a current extra capability.
5. **Substantial extra capability: native local API gateway has an explicit mock default.** [CLI](../../../oh-my-codex/repo/src/cli/api.ts), lines 22–34, exposes native API sidecar serve/status/stop/text/image commands. [Rust implementation](../../../oh-my-codex/repo/crates/omx-api/src/lib.rs), lines 87–99, defaults `backend` to Mock. Lines 509–521 route models/responses/chat/image. Lines 679–710 and 813–880 gate real-private upstream generation. Do not count an API listener or private upstream inference as multi-host coding execution, and do not claim all gateway generation is real by default.

### oh-my-claudecode

1. **Critical lifecycle path: legacy `startTeam` is disabled, so it cannot substantiate current creation behavior.** [Legacy runtime](../../../oh-my-claudecode/repo/src/team/runtime.ts), lines 113–123, always throws `team_start_unsafe_runtime_v1`. [Public CLI](../../../oh-my-claudecode/repo/src/cli/team.ts), lines 675–691, imports v2 and rejects disabled v2 before effects. Actual lifecycle evidence must follow [runtime-v2](../../../oh-my-claudecode/repo/src/team/runtime-v2.ts), `startTeamV2` beginning line 3987, and [runtime-cli](../../../oh-my-claudecode/repo/src/team/runtime-cli.ts), lines 1133–1207. Author notified.
2. **F04/F12: mapped Telegram replies and structured approval resolution are both real.** [Listener](../../../oh-my-claudecode/repo/src/notifications/reply-listener.ts), lines 781–808, requires an existing reply/session mapping; an `approvalRef` resolves an approval gate rather than typing a command. Lines 868–873 persist offset before ordinary pane injection. This is useful channel transport and explicit human decision machinery, without semantic new/existing-project Butler routing.
3. **F15: do not misread “no watchdog” as no periodic monitoring, or factory watchdog as a standing organization supervisor.** [Runtime CLI](../../../oh-my-claudecode/repo/src/team/runtime-cli.ts), lines 1183–1245, explicitly waits `pollIntervalMs`, processes recovery intents, refreshes ownership/pane evidence, calls `monitorTeamV2`, and derives/logs leader guidance. [Factory watchdog](../../../oh-my-claudecode/repo/src/factory/watchdog.ts), lines 1–13, is a pure detection/one-shot flagging module; its caller supplies scheduling. Team execution supervision and factory-chain maintenance need separate treatment.
4. **F18/F19: mission board is more than raw counters, but lacks Wingman's complete executive/linked personal timeline.** [Board model](../../../oh-my-claudecode/repo/src/hud/mission-board.ts), lines 27–66, contains per-agent currentStep/latestUpdate/completedSummary, updatedAt, status and mission timeline. Lines 329–398 record agent-start task descriptions and agent-stop output summaries as bounded chronological events. Lines 495–529 derive team worker status/current task/recent completed-task summary from task records. Lines 694–717 render per-agent details and timeline in HUD text. This is a substantive summary primitive deserving explicit discussion, not an absent timeline claim. It remains a bounded mission/session view, has no explicit planned-next agent field, and rendered source keys are not clickable links to underlying task/conversation/edit/test evidence. Author notified.
5. **F22: reviewer output is consumed by actual runtime transitions, not solely prompt text.** [Runtime v2](../../../oh-my-claudecode/repo/src/team/runtime-v2.ts), lines 4912–4928, specifies assignment-scoped verdict consumption. Lines 5156–5236 reject malformed/stale/mismatched verdicts. Lines 5387–5440 translate approve/reject into terminal task status and persist verdict summary/findings/claim/version metadata. This is grounded review machinery, while full independent integrated product acceptance still needs its own evidence and organization semantics.
6. **Substantial extra: factory webhook intake and CI-failure session chains.** [Factory listener](../../../oh-my-claudecode/repo/src/factory/listener.ts), lines 22–26, has separate tracker-intake and CI failure route tables. Lines 43–74 verify signatures and whitelist/label routing. Lines 187–221 prewrite a chain ledger and spawn a headless Claude session. Lines 225–278 route tracker/CI events. This supports real externally triggered execution and should not be reduced to the skill catalogue. Resulting product discovery and delivery behavior still depends on invoked skill instructions.

### Ruflo

1. **F01/F14: distinguish four things: role registration, provider call, Claude coding process and persistent task record.** [Agent tool](../../../ruflo/repo/v3/@claude-flow/cli/src/mcp-tools/agent-tools.ts), lines 517–562, now exposes real `agent_execute`; [shared execution core](../../../ruflo/repo/v3/@claude-flow/cli/src/mcp-tools/agent-execute-core.ts), lines 257–305, sends a real Anthropic request with user/system content and extracts response text. This is not a coding tools loop. Conversely [hive worker](../../../ruflo/repo/v3/@claude-flow/cli/src/commands/hive-mind-worker.ts), lines 142–188, actually spawns `claude -p`, passes MCP/plugin configuration, supplies prompt on stdin and handles errors/timeout/JSON result. Lines 223–266 select a pending task and idle worker, assign, execute and complete/fail it. The root checkout's “coordination records only” instructions are incomplete for the current implementation; do not generalize them over this path. `work` starts execution; spawning a record alone does not.
2. **F17: transport/federation is implemented, but receiving an envelope is not remote coding execution.** [Federation plugin](../../../ruflo/repo/v3/@claude-flow/plugin-agent-federation/src/plugin.ts), lines 459–498, connects authenticated transport messages to the inbound dispatcher, warning when transport has no callback. [Dispatcher](../../../ruflo/repo/v3/@claude-flow/plugin-agent-federation/src/application/inbound-dispatcher.ts), lines 8–19, explicitly says it emits typed events for an integrator and does not execute inbound tasks. Lines 479–480 generate `federation:inbound:<message.type>`. Searches for this prefix, `FEDERATION_INBOUND_EVENT_PREFIX`, and `inbound:task-assignment` across checkout TS/JS/MJS found producer and tests, without a production remote-task consumer. Credit federation networking/coordination as an extra/primitive; end-to-end shared remote coding assignment remains unestablished. Author notified.
3. **F19: `agent_logs` is explicitly synthetic, including its result timestamp.** [Handler](../../../ruflo/repo/v3/@claude-flow/cli/src/mcp-tools/agent-tools.ts), lines 1012–1056, emits agent-created and optional last-task-result entries; both use `agent.createdAt`. Returned note explicitly states per-agent activity logging is not yet wired. Mission event ledgers are separate product concepts, not evidence for an agent's linked meaningful summary timeline. Author notified.
4. **Termination bookkeeping is not execution cancellation.** The same [agent tool](../../../ruflo/repo/v3/@claude-flow/cli/src/mcp-tools/agent-tools.ts), lines 578–611, marks a record terminated, persists it and optionally promotes/discards memory branches. No child kill or provider AbortController appears in this path. It must not be described as proof that ongoing CLI/model work is interrupted. The hive worker's own timeout handler sends SIGTERM at line 164, which is a distinct bounded local process mechanism.
5. **F22: successful process/provider outcome is execution completion, not product acceptance.** [Hive worker](../../../ruflo/repo/v3/@claude-flow/cli/src/commands/hive-mind-worker.ts), lines 173–185, defines success as exit 0 and `!is_error`. Lines 261–266 write completed/failed accordingly. [Execution core](../../../ruflo/repo/v3/@claude-flow/cli/src/mcp-tools/agent-execute-core.ts), lines 801–822, explicitly calls its learning `resolved` proxy the weakest “API success” signal. Any richer validation/delivery mechanism must be separately traced.
6. **External extra boundary:** README lines 66–74 advertises optional ruOS desktop at https://ruos.cognitum.one/mcp; this does not establish a bundled project dashboard or coding workspace. The local CLI also has an optional terminal console route (commands/index.ts line 108). Local mission schemas/store/fold/service represent substantial event-sourced lifecycle machinery and warrant coverage, distinct from actual execution and external UI.
