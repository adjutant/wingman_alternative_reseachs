## Findings requiring additions

### Omnigent: include real unanswered-child-block escalation in F12/F15 and lifecycle

The report currently describes F15 primarily through recurring prompts and trigger templates. This misses an implemented, wired blocker-follow-up mechanism that is closer to Wingman's requirement than a timer alone.

`SubagentBlockNotifier` observes pending child elicitations. It waits **120 seconds** and suppresses a wake if the human answered within that interval. It resolves the stored immediate parent and sends a wake with bounded retries. After confirmed delivery, it waits for resolution and sends the parent a resolution notice. Failed delivery releases the debounce so a republished request can retry. Top-level sessions have no parent and are a no-op. The notifier's Maps and pending futures are process-local, so this is not a durable portfolio sweep or general semantic blocker detector.

Evidence:

- [notifier implementation](../../../omnigent/repo/omnigent/runtime/subagent_block_notifier.py), lines 55, 250–329 and 336–396: grace, parent resolution, resolution signal and retries.
- [observer wiring](../../../omnigent/repo/omnigent/server/routes/_sessions/orchestration.py), lines 10661–10724: actual pending-elicitation observer registration and teardown. Its older docstring says “immediately”; the notifier body establishes the 120-second agent-wake grace.
- [application lifespan](../../../omnigent/repo/omnigent/server/app.py), lines 1967–1980: this configuration function is actually invoked, rather than merely exported.
- [notifier tests](../../../omnigent/repo/tests/runtime/test_subagent_block_notifier.py), lines 499–585: real conversation store plus gated timing/recorded dispatch checks for answered-within-grace suppression and unanswered-parent wake. Read, not run.

Recommended report addition: credit this immediate-parent approval/block follow-up under F12/F15, mention its process-local state and limited trigger scope, and retain the missing organization-wide ProjectMaster boundary. An upgrade of F15 from Resembles to Similar is a defensible editorial choice, but the necessary correction is the behavioral omission, not a forced label change. Notify readers that the immediate human-facing mirrored prompt and delayed parent-agent wake are different effects.

### Routa: the major-extras section omits a concrete review-analysis product

The report already describes prompted GATE/QA and Kanban verification. It should also cover the separately wired three-stage review API, rather than letting all review behavior appear to be a specialist prompt.

[POST review analysis](../../../routa/repo/src/app/api/review/analyze/route.ts), lines 7–19, invokes `analyzeReview`. [Review analysis](../../../routa/repo/src/core/review/review-analysis.ts), lines 43–77, runs context, candidate-finding and validator stages sequentially; lines 80–106 build the Git diff/config/graph/history payload; lines 142–200 make actual Anthropic-compatible model requests. These are sequential model invocations under one public specialist, not three durable coding agents. The call requires `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY`, accepts configurable base/model/validator model, defaults to `GLM-4.7`, and returns loosely parsed results. It does not execute functional acceptance or prove that a validator model is independently correct.

Recommended addition: a compact extra capability describing multi-stage code review, configurable model endpoint/credentials, repository context enrichment and its separation from integrated product acceptance. This is a report-coverage issue, not a reason to change F22's Similar verdict.

### Routa: mention repository-to-presentation output with its availability boundary

RepoSlide is a visible end-user workflow beyond the target's coding organization, with launch and download wiring; it is not merely a documentation screenshot.

- [RepoSlide UI](../../../routa/repo/src/app/workspace/[workspaceId]/codebases/[codebaseId]/reposlide/reposlide-page-client.tsx), lines 124–173, checks provider and skill availability, creates a real ACP execution session, stores a pending skill prompt and navigates into its result-aware session viewer.

Availability is conditional; do not present a complete standalone slide engine as always shipped.
- [PPTX download](../../../routa/repo/src/app/api/sessions/[sessionId]/reposlide-result/download/route.ts), lines 17–51, proxies runner-owned sessions, resolves the allowed deck artifact and serves a real PPTX file.

A short extras paragraph is sufficient: repository briefing/deck generation can help Wingman create technical handoff artifacts, but needs the skill/provider and artifact access, and is not product discovery or accepted delivery. Related [RepoWiki builder](../../../routa/repo/src/core/repowiki/build-repowiki.ts), lines 37–84, produces a repository map/storyline from tree heuristics; [wiki API](../../../routa/repo/src/app/api/workspaces/[workspaceId]/codebases/[codebaseId]/wiki/route.ts), lines 12–25, wires it to a workspace/codebase.
