### Symphony: confirmed implementation boundaries

[AgentRunner](../../../symphony/repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 21–51 and 88–139, chooses a worker host for one attempt, creates/reuses its workspace and opens a real app-server session. [AppServer](../../../symphony/repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 216–218, calls `SSH.start_port` for a remote host; [Workspace](../../../symphony/repo/elixir/lib/symphony_elixir/workspace.ex), lines 54–84, actually prepares the remote directory. F17 must retain this positive credit. Cross-host replication, durable product placement and peer-room coordination do not follow.

[Orchestrator](../../../symphony/repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 208–265, 310–355 and 581–778, differentiates normal continuation, retry, stall and human-input blocking. The report correctly says active blocked records do not become a conversational question/answer loop; changing a workpad comment alone is not a resume protocol. [Routes](../../../symphony/repo/elixir/lib/symphony_elixir_web/router.ex), lines 31–40, expose state, refresh and issue details; there is no approval-response/steering/session-management endpoint. [Presenter](../../../symphony/repo/elixir/lib/symphony_elixir_web/presenter.ex), lines 66–88 and 210–220, explicitly leaves session logs empty and emits only the latest event. F18/F19/F20/F21 limits are well supported.

The report's F22 credit is carefully qualified. [Sample workflow](../../../symphony/repo/elixir/WORKFLOW.md), lines 67–97, 107–129 and 149–169, supplies unattended behavior, external review states and acceptance/check instructions. These are prompted agent responsibilities. Ending a turn or changing issue state does not independently prove passing tests, human review provenance or product acceptance. The report correctly separates same-thread turns from new `thread/start` on another attempt and explains memory-only scheduler recovery.

Innovation coverage is grounded: OTP scheduler/worker ownership, versioned workflow, session-bound tracker tools, input-block classification and hot reload. The [restart test](../../../symphony/repo/elixir/test/symphony_elixir/core_test.exs), lines 351–472, was inspected as source; its local supervisor fixture is not evidence of distributed fencing or a live SSH deployment.

### OpenHands: actual client wiring and omitted managed-host product

The report correctly identifies this revision as Agent Canvas rather than importing historical monolithic backend claims. [Repository ownership](../../../openhands/repo/AGENTS.md) explicitly assigns SDK/Agent Server/conversations/events, reusable extensions and automation scheduling to separate repositories. The checkout can establish client integration, not the external implementation's crash, concurrency, sandbox or scheduler guarantees.

Child creation is nevertheless a concrete local implementation: [WebSocket context](../../../openhands/repo/src/contexts/conversation-websocket-context.tsx), lines 922–929, dispatches the received client tool; [child launcher](../../../openhands/repo/src/services/child-conversation-launch.ts), lines 265–343 and 511–550, creates the independent conversation, supports worktree/shared modes, reports fallback isolation and returns a launch result. The report correctly explains that eventual child output is not joined into the parent. [Replay ledger](../../../openhands/repo/src/utils/claim-client-tool-call.ts), lines 10–33, uses browser storage and proceeds on storage failure. This is not durable distributed exactly-once dispatch. [Behavioral tests](../../../openhands/repo/__tests__/services/child-conversation-launch.test.ts), lines 278–325 and 710–751, corroborate payload/replay/goal-loop behavior in mocks; they were read, not executed.

[Automation API](../../../openhands/repo/src/api/automation-service/automation-service.api.ts), lines 127–173 and 635–670, resolves the selected backend and sends dispatch/cancel requests to the separate sidecar/API. It does not implement scheduling itself. Existing run summaries are real: [pinned card](../../../openhands/repo/src/components/features/home/featured-automations/pinned-automation-card.tsx), lines 95–102 and 274–316, derives and displays a short/full summary, phase, status and conversation navigation. The F18 organizational gap remains, but the report should avoid implying no summarized outcomes exist anywhere.

**Substantial omission requested for correction:** [MARS launch hook](../../../openhands/repo/src/hooks/use-launch-mars-session.ts), lines 63–128, actually creates hosted sessions/configurations and reconnects an agent's latest live session. [MARS bridge](../../../openhands/repo/scripts/mars-tunnel-bridge.mjs), lines 355–416, owns destroy/delete/create/open-tunnel calls. [Manifest builder](../../../openhands/repo/scripts/mars-api.mjs), lines 48–82, pins OpenHands/template, sets `keep_warm: false`, validates sandbox size and excludes LLM keys. [Management view](../../../openhands/repo/src/components/features/backends/managed-agents/managed-agents-view.tsx), lines 205–267, wires open, launch, pause and confirmed destructive lifecycle actions. Node/Electron or the web bridge owns credentials and tunnels, exposing a normal backend to Canvas. This is a meaningful remote infrastructure product beyond Wingman, with provider/auth/tunnel/billing/cleanup implications; the DigitalOcean microVM implementation is external and no shared organizational bus is established.

### SwarmOS: verified task authority and acceptance limits

[Node pool](../../../swarmos/repo/internal/cli/node.go), lines 177–328, invokes the engine under a claim lock, supports `--all`, concurrent goroutines, watch delay and optional automatic use of the same submit command. The loop returns on failures. [Heartbeat](../../../swarmos/repo/internal/lease/heartbeat.go), lines 23–104, rechecks state/claim/budget and renews or cancels; it is not a model checking in with leadership. The report makes this distinction accurately.

[Git CAS](../../../swarmos/repo/internal/coordination/store.go), lines 303–328, uses the captured remote revision with `--force-with-lease`; lines 527 and 577 perform atomic state/checkpoint or state/PR publication. [Race/fence test](../../../swarmos/repo/internal/coordination/store_test.go), lines 19–100, creates two clones and a local bare remote, asserts one claim winner and stale publication refusal. This supports the mechanism's distributed authority design, while correctly not claiming a live two-machine GitHub test passed.

[Validation execution](../../../swarmos/repo/internal/workflow/execute_validation.go), lines 17–122, launches the tester, rejects tester fail/blocked declarations, then independently invokes coordinator validation with approved `BaseSHA` and `ClaimID`, captures acceptance evidence and records trusted validation. This is stronger than prose instructions to test. [Acceptance evidence](../../../swarmos/repo/internal/validation/acceptance_evidence.go), lines 17–20 and 50–86, explicitly defines the parsed block as advisory; syntactic validity cannot prove criterion satisfaction. The report correctly preserves that limit and Draft PR versus accepted product distinction.

Extras are substantial and appropriately evidenced: untrusted fork contribution, qualified harness isolation, trusted dependency prep/browser testing, PR continuation, lessons, backlog planning and storage accounting. Innovation discussion is code-supported and claims no historical uniqueness. Four workflow roles, ephemeral harness sessions, claim/task identity and same-machine versus Git-remote authority are consistently separated.

## Remaining features and verification limits

F01–F03/F05–F10/F12–F14/F16/F20–F21/F23–F24 were checked in each report for evidence and compatibility with the full purpose. The audit kept these distinctions: a persona is not a live worker, and a profile is not a standing employee. A startup task is not a project ticket. A conversation grid is not a project dashboard. Raw logs do not supply executive summaries. Local goroutines/processes do not establish multi-host execution. Lifecycle prose covers definition, creation, execution, permissions, routing, concurrency, persistence/resume, scheduling, cancellation, recovery, completion/acceptance and cleanup. All reports explicitly retain Wingman's major missing organization concepts and explain practical integration boundaries.

This audit is independent static review with deeper inspection of the priority paths; it is not an exhaustive security review or runtime certification of every harness/provider/platform combination. Only this audit file was authored by QA16. Report changes belong to their respective authors.
