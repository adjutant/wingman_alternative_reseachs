## Material source-backed boundaries for report authors

### hcom

- **F17 is implemented transport and remote execution, not a local-process approximation.** `research/hcom/repo/src/relay/control.rs` lines 450-480 registers remote launch/kill/resume/terminal/transcript/events/subscription RPC handlers. Lines 788-826 call the actual launcher on the receiving device; lines 814-815 explicitly describe running inside the relay worker. Lines 662 onward require a remote working directory. Credit real distributed coordination/launch, while explaining that project placement, replicated source trees and a product-management organization are additional work.
- **F04 uses an external Hermes gateway bridge.** `research/hcom/repo/README.md` lines 212-222 requires a Hermes gateway chat and plugin, then `/hcom start`. `src/hermes_plugin/__init__.py` provides real gateway integration, heartbeat and incoming/outgoing forwarding; this is more than a Telegram keyword or token field. It is not a bundled Butler/project-registry routing service. Distinguish that external dependency explicitly.
- **F15 has event-triggered automation, not standing project supervision.** `src/scripts/bundled/onidle.sh` lines 189-238 waits for listening/idle events, times out, and then launches or injects instructions. It does not inspect project trackers and resolve blockers itself. Do not promote this primitive to an exact periodic ProjectMaster cycle.
- **F11 is real agent messaging but not the full human-facing room application.** `src/messages.rs` performs targeting and message formatting; `src/tui/model.rs` lines 8-9 defines agent/message pane layouts; tagged identities and recipient scoping are not project rooms with leadership membership. Tool transcript previews and event lists should not be presented as F18 executive briefings or F19 linked meaningful-outcome timelines.

### Mission Control

- **F15 must credit substantive implemented supervision machinery.** `src/lib/scheduler.ts` lines 391-425 schedules dispatch, Aegis review and stale-task requeue; lines 479-487 calls routing/reconciliation/dispatch/review/requeue. It is not heartbeat-only. `src/lib/task-dispatch.ts` lines 1640-1724 requeues work when an assignee goes offline, caps attempts and escalates failed work. This remains task automation, not ProductMaster/TechMaster leadership and semantic blocker resolution.
- **F22 Aegis is bounded review, not integrated product acceptance.** `src/lib/task-dispatch.ts` lines 1429-1439 asks the reviewer whether an agent response adequately addresses the task. Lines 1445-1449 parses an approval string; lines 1540-1542 moves approved work to `done`; lines 1552-1592 retries rejected work and records feedback. A configured gateway or tool-capable CLI may do testing when prompted, but the automatic review itself does not establish test execution against a definition of done. Direct model-API execution paths must not be called independent coding agents with repository tools.
- **F18 has a substantial standup equivalent.** `src/app/api/standup/route.ts` lines 42-126 collects per-agent completed-today, in-progress, assigned, review and blocked tasks; lines 163 onward returns dated reports. Its blocker detection is heuristic: urgent priority or metadata containing `blocked` (75-82), and assigned work is not a guaranteed next assignment. A report claiming merely raw logs would undercredit this; an Exact verdict would overstate it.
- **F19 must separate the agent activity feed from linked semantic timelines.** `src/components/panels/agent-detail-tabs.tsx` lines 692-732 links task cards to tasks. The Recent Activity renderer around 785-810 displays descriptions, types and timestamps, without links to the underlying task/conversation/result for each activity entry. This is useful chronology, not the whole Wingman linked briefing requirement.
- **F11 delivery is conditional and external-runtime dependent.** `src/app/api/chat/messages/route.ts` lines 376-416 stores messages and creates notifications. Only `body.forward` (418-420) attempts gateway delivery; lines 513-557 calls `chat.send` or gateway agent invocation, and lines 481-508 reports missing runtime sessions. Persisted chat alone does not guarantee agents received anything. Coordinator “I am coordinating downstream agents now” at 594-609 is an immediate generated status string, not evidence that downstream delegation happened.
- **F17 gateway registry is not per-agent host placement.** `src/lib/openclaw-gateway.ts` lines 82-94 uses global `config.gatewayHost`/`gatewayPort`; task dispatch does not select a registered gateway ID. A remote configured gateway can execute elsewhere, and connected agents can report to the dashboard, but the checked-out dispatch path does not establish a Mac/Endeavour distributed placement scheduler. Host Claude/Codex paths spawn locally.
- **F04 Telegram configuration/testing is not Butler routing.** `src/app/api/integrations/route.ts` lines 68-69 declares the Telegram integration and lines 698 onward checks `getMe`; OpenClaw channel configuration can enable Telegram externally. These paths alone do not implement contextual inbound project intake and question/answer routing.

### CompanyHelm

- **F11 has actual two-party agent delivery.** `apps/api/src/services/conversations/delivery_planner.ts` lines 79-175 queues/steers an existing target session or creates a new session for the target agent; lines 196-222 stores a conversation and two participants. This deserves credit beyond bookkeeping. It is not arbitrary project group rooms with Room1/Room2 management memberships.
- **Conversation-loop guard is a material distinctive mechanism.** `apps/api/src/services/conversations/loop_guard.ts` lines 6-40 blocks repeated low-information acknowledgments across two sessions; lines 43-79 uses a narrow length/question/link/phrase heuristic. Explain both reduced ping-pong and heuristic false positives/limited coverage; avoid claims of historical novelty.
- **F17 is real cloud sandbox execution, with a strong provider boundary.** `apps/api/src/services/environments/providers/provider_registry.ts` lines 14-19 registers only E2B. `providers/e2b/e2b_provider.ts` lines 103-123 creates actual remote sandboxes, configured for autoresume and timeout pause; 125-141 captures provider IDs and cleanup. This is a substantial cloud execution equivalent, but not arbitrary user-owned Mac and Endeavour host registration/placement. Redis/BullMQ worker distribution must be distinguished from where terminal/computer tools execute.
- **F15 has durable recurring prompts, not an implemented portfolio supervisor.** `apps/api/src/services/schedules/queued_agent_message_service.ts` lines 129-184 inserts a durable session message and wakes it; 185-190 marks the schedule run done after queuing, not after the requested agent work succeeds. Archived sessions are skipped at 197-208/261-280. Workflows similarly have scheduled runs. Do not infer automatic blocker diagnosis from transport scheduling.
- **Real sessions and lifecycle are substantial.** `apps/api/src/services/agent/session/process/execution.ts` lines 66-69 defines one queued turn per wake with Redis lease; 131-184 acquires/heartbeats lease and aborts on loss; 186-237 handles steering and interrupts. `process/queue.ts` lines 45-65 retries wake jobs three times with exponential backoff. Worker-job retries are not guaranteed safe retry of arbitrary external coding effects.
- **F22 task execution/history is not acceptance.** `apps/api/src/services/task_run_service.ts` lines 106-237 validates assignee, creates a task-backed session and persistent run, updates task status and wakes execution. `task_service.ts` supports explicit completion transitions and run synchronization. These are real execution/status mechanisms, but source inspection found no mandatory integrated-test or human-acceptance gate. Terminal/computer tools can run tests when directed.
- **F18/F19 require conservative framing.** `apps/web/src/pages/dashboard/dashboard_page.tsx` lines 16-65 queries tasks, workflow runs and environments; 188-209 renders assignee/status/task/workflow summaries. This is a useful operational dashboard, not per-agent current/recent/next/blocker executive briefing. Agent detail is principally configuration, sessions and usage; session transcripts and task runs must not be relabeled a per-agent summarized outcome timeline.
- **F04 absent within inspected product source.** Searches over API and web source for Telegram, Discord and Slack found no native messaging integration; “signal” matches were abort signals. An external MCP server is a possible adaptation, not an existing bundled Butler route.

The author applied this clarification, and the final wording was reread. The author also corrected ordinary dispatch failure retries to five, verified against `task-dispatch.ts` lines 2033-2039; Aegis rejection threshold is three. Neither changes the report's overall fit verdict.
