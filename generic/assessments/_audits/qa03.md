## Findings requiring correction or expansion

### Q03-1: Scion rooms are real, but project-bound (corrected in current report)

The initially read F11 was **Exact** and said rooms could be arranged for management and specialists. The source supports actual multiparty chat, not merely terminal messages: [conversation and participant records](../../../scion/repo/pkg/store/models.go), lines 3495–3522, and the [native Chat page](../../../scion/repo/web/src/components/pages/chat.ts), lines 18–38, establish shared project spaces, multi-participant threads, DMs and conversation navigation.

However, [conversation creation](../../../scion/repo/pkg/hub/handlers_conversations.go), lines 740–748, requires a project for every group; lines 1070–1097 reject adding an agent from another project. [Group dispatch](../../../scion/repo/pkg/hub/handlers_agent_messaging.go), lines 3420–3450, rejects cross-project group references, and broadcast lines 3905–3920 explicitly retain the project boundary. Wingman's Room1 combines organization-wide agents with product/technical leaders from different products. Project-local Room2 is straightforward; a shared cross-project Room1 is an adaptation, not just a room name.

The current F11 is now **Similar** with these exact boundaries. That correction is verified. Preserve native chat credit and distinguish cross-project DMs/authorization from cross-project shared rooms. The prose coordination/practical sections should maintain the same boundary wherever they describe arranging management rooms.

### Q03-2: Multica agent history is not a semantic summary timeline (corrected in current report)

The initially read F19 was **Similar**, describing an “actual task-linked activity summary.” The [activity component](../../../multica/repo/packages/views/agents/components/tabs/activity-tab.tsx), lines 100–147, filters out chat tasks and orders current/terminal runs. Lines 451–537 derive the row title from the issue, add status/failure/cancellation information and show trigger context on hover. [RecentTaskRow](../../../multica/repo/packages/views/agents/components/tabs/activity-tab.tsx), lines 682–750, renders the issue title, status, time, duration, attribution and issue/transcript links. It does not render an accomplishment/result summary, test result, question, decision or planned-next-work narrative.

Wingman's purpose, section 12, requires meaningful plain-language updates linked to underlying work; the assessment guide explicitly says not to label event history an executive summary. The current F19 is now **Resembles** and accurately calls this linked execution history. That correction is verified. F18's **Similar** is defensible for substantial Now/Recent/queued workload visibility as long as the report retains its explicit missing-next/business-blocker/executive-narrative boundary. The task status `completed` cannot by itself stand for an accepted accomplishment.

### Q03-3: Scion artifact product is substantially broader than its notification hook, and is experimental (expanded in current report)

The report's additional-capability paragraph primarily cites [artifact review notification](../../../scion/repo/pkg/hub/artifacts_review.go), lines 42–105. That is accurate but leaves a substantial product underassessed. The implementation includes stable versioned bundles, a manifest with file sizes/hashes, pending upload state, finalize/claim, grants, browser views and version-bound review. Evidence:

- [Artifact API](../../../scion/repo/pkg/artifacts/api.go), lines 117–165: create/append version, file manifest/SHA-256 and required-upload response.
- [Finalize implementation](../../../scion/repo/pkg/artifacts/versions.go), lines 745–845: required review base, missing-file refusal, current limits, durable finalize claim, review validation and stale/current-version checks.
- [Review validation](../../../scion/repo/pkg/artifacts/review.go), lines 30–50 and 87–150: CriticMarkup review must preserve the baseline outside marks; non-text files and manifest membership cannot silently change. Stale review and base-required are explicit outcomes.
- [Server route wiring](../../../scion/repo/pkg/hub/server.go), lines 7613–7622: the actual artifact API is mounted.

The important availability boundary is [experiment registry](../../../scion/repo/pkg/experiments/registry.go), lines 503–512: `hub.artifacts` is alpha, defaults false, and its API answers 404 while off. The report should expand its extras/innovation discussion to the actual versioned publication/review mechanism and state that gate, rather than presenting the notification alone as the artifact product. Value to Wingman: inspectable specifications/deliverables and review lineage. Integration consequence: adopt artifact identity/version/grant/storage rules and enable the optional feature. This does **not** require upgrading F22: markup review and self-reported completion are still not integrated product testing/acceptance. On final recheck, the current Scion report expands the complete versioned artifact mechanism, explicitly identifies its default-off alpha/settings gates, and retains the acceptance boundary. The additions resolve this finding.

### Q03-4: Paperclip extras omit company portability and substantially underdescribe the connected-tool gateway (expanded in current report)

The report covers budgets, lifecycle plugins, catalogs, status cards, work products, routines and experimental Cases well. Two further major implemented products merit explicit short paragraphs:

**Company export/import.** [Company routes](../../../paperclip/repo/server/src/routes/companies.ts), lines 1125–1175, expose actual export/preview/import/apply calls with CEO-or-board checks, company-target restrictions and a safe-route refusal of replace collisions. [Portability service](../../../paperclip/repo/server/src/services/company-portability.ts), lines 3879–3893, selects agents/projects/issues/skills, and lines 5257 onward apply validated imports. This goes beyond installing a catalog team: portable organizations and operating setups can be inspected/recreated. Wingman could package its standing team plus project/workflow setup. The report should distinguish selective operating-setup portability from full live process/session/database backup, and describe collision, permissions, repository and credential reconfiguration consequences rather than promising transparent migration.

**Accountable connected tools.** The report mentions assigned MCP and run-scoped credentials, but the gateway is a substantial execution/governance product. [App wiring](../../../paperclip/repo/server/src/app.ts), line 981, mounts its routes. [executeTool](../../../paperclip/repo/server/src/services/tool-gateway.ts), lines 10319–10325, authenticates an active gateway session; lines 10872–10920 revalidate the approval target snapshot and signed reviewed arguments; lines 11060 onward branch on policy-required approval before execution. This gives human/agent/tool authority and reviewed action identity practical meaning beyond a connection catalog. Wingman could use it for controlled external integrations; it must retain responsible-user/run identity and action approval/revocation rules. It is not a guarantee about shell operations that bypass the gateway.

These omissions did not overturn the fit verdict or existing F01–F24 scores. They were guide item 6 depth/completeness issues for a very broad product. On final recheck, the current Paperclip report now contains substantial portable-company and governed-tool-gateway sections with these sources and appropriate operational limits. The additions resolve this finding.

### Q03-5: Scion's optional A2A bridge merits an additional-capability boundary

The report discusses heterogeneous harnesses but does not assess the sizeable separate A2A bridge. It has real protocol entry points: [bridge HTTP routing](../../../scion/repo/extras/scion-a2a-bridge/internal/bridge/server.go), lines 218–275, mounts agent cards and per-agent JSON-RPC routes plus auth/rate-limit middleware. [SDK executor](../../../scion/repo/extras/scion-a2a-bridge/internal/bridge/executor.go), lines 55–75, translates SDK messages into Hub messages and Hub event-log responses back into SDK events. Lines 471–518 implement cancellation as a Hub interrupt where authorized, and explicitly avoid that interrupt for federated users. The bridge also keeps its own task/context state.

This is interoperability with other agent systems, not Scion's missing ProjectTracker: an A2A protocol task is not a product ticket with decomposition/ownership/acceptance. A short extras paragraph should state it is a separate optional service and carries its own discovery/auth/task-stream/cancellation contracts. Value: exposing selected Wingman specialists to external agent systems. Consequence: intentional authority, conversation and cancellation mapping; an A2A canceled response does not universally prove a container stopped. No bridge service or external client was exercised here.

## Lifecycle and request-wiring checks

### Multica

The report correctly distinguishes durable named agent, runtime binding, task attempt, provider session and live backend Session. [CreateAgent request/config](../../../multica/repo/server/internal/handler/agent.go), lines 1372–1408 and 1683–1704, supports creation as a durable runtime-bound identity. Mika's [shipped instructions](../../../multica/repo/server/internal/service/builtin_agents/mika/INSTRUCTIONS.md), lines 6–28, actually route goals among chat/issues/projects/teammates/squads/autopilots and explicitly require previews for team/automation creation. These are instructions, not an enforced Wingman discovery organization.

The assignment trace has real mechanical dispatch: [WillEnqueueRun](../../../multica/repo/server/internal/service/issue_trigger.go), lines 102–208, chooses direct agent or squad leader with parking/triage guards. [Claim SQL](../../../multica/repo/server/pkg/db/queries/agent.sql), lines 760–821, binds runtime, checks health/current binding and serializes agent+issue/chat, rather than globally serializing all agents. [Daemon](../../../multica/repo/server/internal/daemon/daemon.go), lines 8820–8865, resolves the backend; [Codex args](../../../multica/repo/server/pkg/agent/codex.go), lines 375–387, select an actual app-server subprocess. Thus the multi-host/concurrent-agent claims are not inferred from local personas.

The [squad brief](../../../multica/repo/server/internal/handler/squad_briefing.go), lines 36–95 and 114–157, establishes delegate/evaluate/end-turn/reactivate behavior and the distinction between successful dispatch and review. The inspected [guest-routing test](../../../multica/repo/server/internal/handler/squad_worker_comment_wakes_leader_test.go), lines 24–61, asserts the exact guest leader route and skips without its database. Report correctly labels tests as read, not run. [Telegram resolvers](../../../multica/repo/server/internal/integrations/telegram/resolvers.go), lines 68–79 and 104–156, bind bot installation/agent, isolate chat/topics and check current human workspace membership. This verifies F04 transport boundaries; it does not prove a live Butler request.

Scheduling is genuinely wired at [server startup](../../../multica/repo/server/cmd/server/main.go), lines 835–860. [Failure/retry](../../../multica/repo/server/internal/service/task.go), lines 5074–5150, classifies reasons/budgets and prepares a retry for the same durable transition. [Terminal outbox](../../../multica/repo/server/internal/daemon/terminal_report_queue.go), lines 34–104, is a file-backed terminal-report mechanism distinct from provider execution. [Archive/restore](../../../multica/repo/server/internal/handler/agent.go), lines 2812–2903, preserves the agent and requests task cancellation, refusing built-in system agents. Cancellation during archive is best effort if the cancel service fails (lines 2852–2853 log rather than roll back archival); avoid treating it as unconditional immediate process termination. Report overall separates interruption, resume, retry, acceptance and host GC adequately.

### Paperclip

The report's deepest strength is distinguishing organization identity, task, run, provider session, permission, result, workspace preservation and termination. [Lifecycle policy](../../../paperclip/repo/server/src/modules/agent-lifecycle/domain/policy.ts), lines 21–67, implements approval/preparation/verification/pause/resume/termination/cleanup and restricts purge to terminated/rejected identities. [Queue](../../../paperclip/repo/server/src/services/heartbeat/queue.ts), lines 1911–1937, rechecks invokability and slots. The report does not confuse a durable member with a resident subprocess.

[Channel service](../../../paperclip/repo/server/src/services/chat-channels.ts), lines 2184–2247 and 2377–2384, really saves external-thread binding, reopens completed/cancelled tasks and stages an inbound wake transactionally. [Task Markdown](../../../paperclip/repo/server/src/services/heartbeat/task-markdown.ts), lines 221–224, injects the chat directive, whose [handoff policy](../../../paperclip/repo/server/src/services/agent-conversations.ts), lines 106–108, defaults assignment to the conversational agent and requires explicit human owner selection for a different assignee. The report correctly identifies this as a Wingman autonomous-routing adaptation and scopes the restriction to human Agent Chat.

[Agent chat sender](../../../paperclip/repo/server/src/services/agent-chat-messages.ts), lines 41–83 and 109–120, requires a current ordinary task-bound run, current issue ownership, experimental enablement and responsible human; it creates that human's conversation, not a peer room. [Timer policy](../../../paperclip/repo/server/src/services/heartbeat-policy.ts), lines 4–11, excludes generic unscoped runner heartbeats. [SSH execution](../../../paperclip/repo/packages/adapter-utils/src/ssh.ts), lines 44–79, builds and executes a remote command with working directory/environment, substantiating real remote execution beyond a URL/config field.

[Required review](../../../paperclip/repo/server/src/services/required-quality-review.ts), lines 11–31, 44–70 and 81–117, is opt-in, human-protected and tied to current output document/attachment identity. The report correctly avoids universal TestMaster/product-acceptance claims. [Recovery test](../../../paperclip/repo/server/src/services/heartbeat/recovery.test.ts), lines 527–548, rejects mismatched remote termination evidence and treats remote identity retirement separately from local PID liveness. These source/test contracts justify the bounded lifecycle/recovery analysis, not operational reliability certification. Portability/tool gateway omissions are expansions, not reasons to discard the otherwise strong assessment.

## Disposition

The three reports meet structural and lifecycle depth requirements and have credible source-path traces. The two material scoring/semantic overclaims found during this audit have already been corrected in the current report files. The current reports also resolve the artifact/gating and Paperclip portability/gateway expansion findings. The remaining recommended addition at this recheck is Scion's optional A2A bridge. Current Scion practical guidance now explicitly calls for a management-room bridge or additional cross-project layer. No runtime behavior was independently exercised, and no industry-first novelty claim is warranted or made.
