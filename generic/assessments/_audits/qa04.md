## Recommended precision improvements

### 1. TinyAGI collaboration tags have a final-output boundary

The report correctly credits real parser/queue-backed DMs and rooms, but its collaboration explanation can be read as covering all assistant text emitted during a coding run. The production path only calls `handleTeamResponse` after `invokeAgent` resolves: [main/index.ts](../../../tinyagi/repo/packages/main/src/index.ts), lines 101–108 and 130–136. Streaming progress is recorded and sent directly to the original channel during the call. The Codex adapter replaces `response` on each `agent_message`, then returns only the last one: [codex.ts](../../../tinyagi/repo/packages/core/src/adapters/codex.ts), lines 32–47 and 63. Room/DM extraction reads that returned response: [conversation.ts](../../../tinyagi/repo/packages/teams/src/conversation.ts), lines 71–104.

Suggested addition to F11/coordination or verification: “For Codex, collaboration tags are interpreted from the last returned assistant message after the CLI exits. Earlier streamed assistant messages are displayed/sent but are not independently dispatched to teammates; a tag emitted only there can be lost as a handoff.” This is a source-visible dispatch boundary, not a runtime-reproduced failure. Retain F11 Similar and the existing warning that prompt compliance does not provide workflow closure.

### 2. OpenRig retry identity depends on retaining the request ID

The report's statement that remote queue writes retain stable IDs across retries should distinguish the shipped CLI path from arbitrary direct HTTP callers. [queue.ts](../../../openrig/repo/packages/daemon/src/routes/queue.ts), lines 593–607, uses `body.qitemId ?? newQitemId()` per incoming create request. The forwarding helper performs one transport call and returns a structured indeterminate result on timeout, with no local task record: lines 285–365. Repeating a direct HTTP request without `qitemId` can therefore mint new work. This is not a durable universal retry identity automatically reconstructed from body text.

The shipped CLI does handle this deliberately: [CLI queue.ts](../../../openrig/repo/packages/cli/src/commands/queue.ts), line 947, exposes `--id`. Lines 1099–1107 generate/print the ID before sending and explicitly tell the caller to reconcile and reuse it. Lines 1163 and 1180 perform read-back. Suggested refinement: “The shipped CLI creates and prints a stable request ID before send; retries must reuse that ID. Direct API callers must supply and preserve `qitemId` themselves.” This narrows reliability wording without changing F17 Exact or denying real federation.

### 3. OpenRig's inspected cross-host queue transport is HTTP

The report correctly requires configured daemons, paths and credentials and does not claim SSH workers. Add an explicit transport boundary if practical: [queue.ts](../../../openrig/repo/packages/daemon/src/routes/queue.ts), lines 323–327, rejects SSH-declared host entries for cross-host queue writes. [queue-cross-host-create.test.ts](../../../openrig/repo/packages/daemon/test/queue-cross-host-create.test.ts), lines 288–293, asserts this rejection and zero local writes. A host registry supporting an SSH entry is not proof the shared queue path executes through SSH.
