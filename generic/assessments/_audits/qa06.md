## amux: verified boundaries

**F04/F11:** No Telegram/Butler implementation was found in `cmd` or `internal`. Peer delivery is real terminal input rather than a role prompt or README aspiration. [cli_send.go](../../../amux/repo/cmd/amux/cli_send.go), lines 27–96, validates selectors/input and sends text plus a separately delayed carriage return. Lines 153–197 resolve exact hosted sessions, reject ambiguous workspace addresses and reject dead panes. This justifies F11 Resembles: another process can be contacted, but there is no durable sender/recipient envelope, room membership, room history or acknowledged business-message processing.

**F15/F18/F19:** [cli_agent.go](../../../amux/repo/cmd/amux/cli_agent.go), lines 80–92, exports workspace/session/profile and current state/source, with no current/recent/next/outcome summary fields. [tap.go](../../../amux/repo/internal/tmux/tap.go), lines 54–68, actually constructs only the folded state/ID/app/kind/message/timestamp report; title/progress supported by the parser are not propagated here. Lines 101–121 hold an in-process record set while publishing snapshots. [app_tmux_activity_result.go](../../../amux/repo/internal/app/app_tmux_activity_result.go), lines 220–250 and 292–332, establishes the first-observation baseline and fires hooks only on observed working→done edges, without replay. These are operational observation and external-supervisor primitives, not executive work summaries or a durable agent timeline. The report explicitly preserves these distinctions.

**F17:** [workspace.go](../../../amux/repo/internal/data/workspace.go), lines 9–37 and 73–77, explicitly states that backend selection does not exist and all execution is local worktrees. Docker/cloud enum names cannot support distributed-execution credit. SSH matches found in Git protection logic concern Git transport/environment, not host placement.

**F22 and lifecycle:** [agent.go](../../../amux/repo/internal/pty/agent.go), lines 177–198, launches the native assistant followed by terminal reset and a login shell. The report correctly warns that pane liveness is not coding-agent liveness or a universal agent exit-code signal. The workspace schema at [workspace.go](../../../amux/repo/internal/data/workspace.go), lines 40–106, contains tabs, branch/worktree identity, scripts and lifecycle flags, not tickets, acceptance or an employee's history. The report credits explicit scripts and branch integration without converting `done` into accepted delivery.

**Completeness:** Architecture, durable ID versus native conversation, launch-config capture, branch sharing within a workspace, tools/trust, detach/restart, interruption, process/transport recovery, deletion/shelving and coordination are all substantially covered. Its major extras—heterogeneous harnesses, worktree operations, status protocol, service/script environment—are substantive. The innovation discussion explains concrete terminal-stream status, observation ownership and recoverable local lifecycle mechanisms without claiming industry uniqueness.

## Automaker: verified boundaries

**F04/F11/F17:** Broad searches of server implementation and shared types found no Telegram/Butler, peer-room, addressed mailbox, standing-team or remote-worker-host implementation. Native `agent_message` events are provider output, not an agent-to-agent message bus. Session messages are user/assistant history, while feature records and process-local maps coordinate board jobs. Local provider execution and a remotely accessible UI do not amount to multi-host dispatch. The report's negative judgments remain appropriately scoped.

**Actual specialist wiring:** The report's warning about differing interactive and automatic paths is supported. [agent-service.ts](../../../automaker/repo/apps/server/src/services/agent-service.ts), lines 385–394, loads enabled custom definitions; lines 481–523 add the Task tool where needed; lines 549–565 pass `agents: customSubagents` into provider options. The automatic [facade.ts](../../../automaker/repo/apps/server/src/services/auto-mode/facade.ts), lines 283–362, constructs and forwards execution options without those definitions. Role prompts are therefore not automatically wired into all feature executions.

**F15:** [auto-loop-coordinator.ts](../../../automaker/repo/apps/server/src/services/auto-loop-coordinator.ts), lines 166–255, polls capacity, loads pending work, checks dependency readiness and dispatches a feature. Lines 258–276 stop the dispatcher and return the running count rather than aborting all workers. This is real unattended execution control, but no manager reads discussions or negotiates blocker resolution. F15 Resembles is justified.

**F18/F19:** [running-agents-view.tsx](../../../automaker/repo/apps/ui/src/components/views/running-agents-view.tsx), lines 167–220, displays feature title/description, model, project and log/project links. [overview.ts](../../../automaker/repo/apps/server/src/routes/projects/routes/overview.ts), lines 299–312, returns aggregate state and an explicitly empty `recentActivity` placeholder. Existing phase summaries/logs do not establish the requested per-employee chronological outcomes and planned-next feed.

**F22, including wiring:** The report correctly distinguishes two paths. [execution-service.ts](../../../automaker/repo/apps/server/src/services/execution-service.ts), lines 443–478, sets automatic `verified` using a tool marker and output-length threshold; lines 402–413 can continue to final status with unfinished tasks and lines 516–527 emit `passes: true` independently of actual acceptance. The inspected [execution-service.test.ts](../../../automaker/repo/apps/server/tests/unit/services/execution-service.test.ts), lines 1688–1722, confirms the intended 200/199-character boundary.

The separate verification action is actually reachable, not an unused helper: [verify-feature.ts](../../../automaker/repo/apps/server/src/routes/auto-mode/routes/verify-feature.ts), lines 9–26 → [compat.ts](../../../automaker/repo/apps/server/src/services/auto-mode/compat.ts), lines 181–183 → [facade.ts](../../../automaker/repo/apps/server/src/services/auto-mode/facade.ts), lines 780–837, executes four npm checks with timeout and early failure. [use-board-actions.ts](../../../automaker/repo/apps/ui/src/components/views/board-view/hooks/use-board-actions.ts), lines 703–726, connects the result to explicit board verification. Conversely, searching all server production source finds `executeTestStep` only at its definition. [pipeline-orchestrator.ts](../../../automaker/repo/apps/server/src/services/pipeline-orchestrator.ts), lines 99–158, normally executes instruction prompts and then attempts merge; it does not call that command/fix helper. This substantiates the report's central testing caveat.

**Lifecycle/extras/innovation:** Source checks confirm that archive/delete do not themselves abort interactive sessions ([agent-service.ts](../../../automaker/repo/apps/server/src/services/agent-service.ts), lines 989–1034), pipeline merge retains worktree/branch and returns conflicts without launching a new resolver (pipeline orchestrator, lines 579–629), and maintenance status is explicitly declared in [LICENSE](../../../automaker/repo/LICENSE), lines 1–9. The report covers the meaningful extras and provides bounded mechanisms for leases, stream-to-plan state, approval recovery and memory selection. No additional material capability requiring a matrix change was found.

## Emdash: verified boundaries

**F04/F11 and identity:** Searches across desktop features, core runtime APIs and plugin integrations found no Telegram/Butler or built-in room/direct-peer messaging. The [agents contract](../../../emdash/repo/apps/emdash-desktop/src/core/features/agents/api/contract.ts), lines 41–123, concerns host-targeted provider metadata/installations/settings, not employees. The [task type](../../../emdash/repo/apps/emdash-desktop/src/core/primitives/tasks/api/tasks.ts), lines 39–81, includes human workflow status, issue/PR/conversation/workspace links and automation metadata, with no specialist assignee or dependency edges. “Participants” found in task services are software lifecycle participants, not room members. The report correctly avoids inflating these names into organizational collaboration.

**F15/F22:** [executor.ts](../../../emdash/repo/packages/core/src/runtimes/automations/node/runs/executor.ts), lines 22–60, really does provision, start a session and mark `done` immediately after start returns. The inspected [executor.test.ts](../../../emdash/repo/packages/core/src/runtimes/automations/node/runs/executor.test.ts), lines 107–125, asserts that transition using fake ports. [scheduler.ts](../../../emdash/repo/packages/core/src/runtimes/automations/node/scheduling/scheduler.ts), lines 16–18 and 86–128, supplies periodic durable scheduling and a default four-worker startup limit. These are real recurring execution mechanisms; neither test completion nor product acceptance is awaited. No built-in progress investigator or blocker-follow-up organization was found.

**F17:** Genuine multi-host execution is established beyond launch strings. [ssh-streamlocal-transport.ts](../../../emdash/repo/apps/emdash-desktop/src/core/services/hosts/node/workspace-server/connect/ssh-streamlocal-transport.ts), lines 6–13, forwards the workspace-server socket over the selected SSH connection. The remote [worker-manifest.ts](../../../emdash/repo/apps/workspace-server/src/gateway/worker-manifest.ts), lines 30–91, wires ACP, TUI, automations, files, Git, terminals and registry workers into that host. F17 Similar appropriately credits one desktop coordinating host-owned execution while reserving shared organizational chat/tracking and cross-host team dispatch as future work.

**F18/F19:** [activity-badge.tsx](../../../emdash/repo/apps/emdash-desktop/src/core/features/tasks/browser/components/activity-badge.tsx), lines 26–41 and 122–185, explicitly presents workspace lifecycle/script steps, derived descriptions and timestamps. The [ACP contract](../../../emdash/repo/packages/core/src/runtimes/acp/api/contract.ts), lines 118–136, exposes session state, options, usage, plan, subagents and terminals. Neither is a semantic per-employee accomplishment/next-assignment feed. Resembles grades preserve that distinction.

**Deep lifecycle:** [source.ts](../../../emdash/repo/packages/core/src/runtimes/acp/node/connection/source.ts), lines 60–105 and 128–174, independently confirms cache identity includes provider/cwd/environment and process generations. [session-materializer.ts](../../../emdash/repo/packages/core/src/runtimes/acp/node/runtime/session-materializer.ts), lines 93–218, preserves unsupported/ambiguously failed restore pointers, restricts missing-session fresh fallback to an untouched session without replayed history, and applies configuration before activation. [session-manager.ts](../../../emdash/repo/packages/core/src/runtimes/acp/node/runtime/session-manager.ts), lines 283–314, commits materialization and initial-queue consumption before dispatch. Lines 323–392 separate accepted prompt response from turn completion and retain the activation lease during the work. The report discusses the exact limits—no arbitrary exactly-once task processing, no durable live outbox—and does not mistake a cached conversation for a dedicated OS process.

**Completeness:** The report covers both ACP and TUI execution paths, native restore differences, tools/permissions, steering, scheduling, failure recovery, cleanup, host ownership and automation outcome semantics. Its extras include substantial provider, work-system, remote-runtime, skill/MCP and code-review functionality. Its innovation assessment explains concrete lifecycle/state mechanisms with enabling behavior and limitations. The only recommended amendment is the archive failure qualification above.

## Verification limits

This audit inspected source paths and selected test implementations, not runtime behavior. Absence searches are bounded to the likely application/schema/provider/runtime paths described above; custom MCP services, shell wrappers, native harness capabilities or externally supplied agent prompts may add behavior outside the repository. No conclusion here establishes successful startup, live provider compatibility, remote daemon survival, concurrency timing, or product delivery on the user's machines.
