## Material correction: gstack remote compute is omitted

The initial 249-line gstack report covers remote browser/device access, GitHub CI, Git-note recovery and externally hosted Capy machines, but omits the shipped `/ubicloud` product surface and executable remote VM runner. This is a substantial additional capability and materially affects how readers understand F17. It does not require upgrading the feature verdict: bounded remote jobs still do not establish standing Codex host placement or shared organizational conversations.

Evidence:

- [ubicloud skill](../../../gstack/repo/ubicloud/SKILL.md.tmpl), lines 20–37: `/ubicloud` is an ephemeral heavy-run service surface, invoking `scripts/ubicloud/ubi-runner.sh` through `gstack-ubi`.
- [ubi-runner.sh](../../../gstack/repo/scripts/ubicloud/ubi-runner.sh), lines 19–24: copies tracked/unignored checkout content plus Git state, runs setup and a command, retrieves requested artifacts and tears down the VM. This is executable remote compute, rather than a documentation-only host suggestion.
- Same file, lines 26–66: owner-scoped VM naming, TTL/reaping, quota preflight, teardown confirmation and cleanup-result reporting.
- Same file, lines 68–92: output watchdog, detached remote phases, content/run-key matching, SSH reconnection, lost-phase outcomes and TTL-bound reattachment.
- Same file, lines 226–317 and 971–1017: actual SSH invocation/watchdog and VM readiness/SSH-key paths corroborate the introductory mechanism descriptions.

Requested report change: add a substantial extras paragraph describing remote VM verification/build/eval execution and its costs/provider credentials, repository-copy, artifact and cleanup implications. Add a short F17/practical-fit qualification that real remote compute exists, while the Wingman organizational host-placement and communication layer remains missing. Root was notified with this evidence. The report's engineering-gate, external-host and prompt/runtime distinctions otherwise withstand the focused audit.

## Clarification: Squad communication adapters are library surfaces

The Squad report carefully says adapters exist and does not claim Room1/Room2. It should additionally state that the inspected built-in shell/watch paths do not call the communication factory. This avoids readers assuming the SDK interfaces automatically deliver ongoing agent updates and consume human replies.

[platform/comms.ts](../../../squad/repo/packages/squad-sdk/src/platform/comms.ts), lines 44–115, builds GitHub Discussions, ADO, Teams and file-log adapters. A production-tree search for `createCommunicationAdapter`, `postUpdate(` and `pollForReplies(` across `packages/squad-cli/src` and `packages/squad-sdk/src` found the factory, export, interfaces and adapter method definitions, but no shell/watch integration caller. [File-log adapter](../../../squad/repo/packages/squad-sdk/src/platform/comms-file-log.ts), lines 29–83, really writes attributed Markdown and reads manual reply text; it is not merely a type declaration. It also ignores the `since` filter and returns the whole reply suffix, as the report already explains.

The WorkIQ watcher is separate: [monitor-teams.ts](../../../squad/repo/packages/squad-cli/src/cli/commands/watch/capabilities/monitor-teams.ts), lines 16–46, starts a coding agent with instructions to query WorkIQ and create deduplicated issues. That is model-mediated external intake, not proof that the communication adapters are automatically wired into agent conversations. The existing F11 **Resembles** verdict is appropriate; this is a precision improvement to architecture/coordination prose.
