Open Multi Agent assessment against Wingman

Identity and verdict

  • Repository: https://github.com/open-multi-agent/open-multi-agent
  • Local checkout: research/open-multi-agent/repo
  • Assessed commit: a2fe43ce3414f106f2e57366c55b244ecea7a74b
  • Assessment date: 2026-11-05.
  • Product: MIT-licensed, self-hosted TypeScript agent runtime. The checked-out core package is @open-multi-agent/core 1.23.0. Package identity and public entry points are in core/package.json, lines 1–78.

Fit verdict: useful execution and recovery infrastructure, with a large organizational application still to build. OMA can execute distinct tool-using agents, coordinate dependency graphs, invoke local coding CLIs, save and resume work, suspend for durable approval, and produce a detailed run viewer. These are substantive foundations. It does not implement Wingman's persistent Codex organization, Telegram Butler, project registry and discovery conversation, management rooms, portfolio supervision, or connected executive and individual coding workspaces. Its durable unit is principally a run and its tasks, rather than a continuing employee-like agent assigned to a product.

The distinction matters operationally: Team retains named agent configurations, while the orchestrator creates fresh execution pools for runs. getStatus() literally reports activeAgents: 0 because those pools are ephemeral (orchestrator.ts, lines 3000–3032, 3616–3652). Adding role prompts named Butler or ProductMaster would not supply the missing routing, ownership, communication and continuity services.

This is a source assessment of the local revision, not a claim about the current hosted project or released package. No dependencies were installed, services launched, model requests made, or runtime tests executed.

Architecture and actual execution model

OMA is an npm-workspaces monorepo with core, an optional OpenTelemetry adapter, a scaffolder, and a private release bot. The main product is an embeddable library, with a thin oma CLI. There is no long-running organization server or application database included in the inspected production paths. The CLI expressly describes itself as a shell/CI wrapper without an interactive session, approvals or persistence (oma.ts, lines 1–5); programmatic APIs provide the richer capabilities.

The execution paths are:

Application / JSON CLI
  → OpenMultiAgent
      → runAgent: construct a one-off Agent
      → runTeam: route single/team, or apply declared governance topology
                   → coordinator decomposes goal into validated task DAG
      → runTasks: load application-supplied task DAG
      → runFromPlan: replay a frozen plan
      → restore: rebuild checkpointed run
  → event-driven executeQueue + Scheduler + per-run AgentPool
  → Agent
      → AgentRunner → provider adapter → model/tool loop
      → ProcessBackend → local child process
      → AcpBackend → local ACP subprocess/session
  → result, optional synthesis, checkpoint/approval/run ledger, journal and traces

OpenMultiAgent owns configuration and a map of teams (orchestrator.ts, lines 481–589, 1015–1024). A Team is an agent-config roster plus an in-process message bus, its own task queue, optional shared memory, and local event listeners (team.ts, lines 94–156). Team configuration is not a collection of already-running agents. The orchestrator constructs Agent objects when building each pool. runTasks() also creates a new run-local queue, rather than executing the queue returned by team.getTasks() (orchestrator.ts, lines 2751–2792; team.ts, lines 252–284). A tracker integration must therefore follow the actual run results/progress/checkpoints; assuming Team's queue is the live organizational tracker would be wrong.

runTeam() can route directly to one agent for suitable work. A team object does not guarantee multiple workers execute. It accepts an explicit mode, declared governance roles/topology, deterministic routing, and an optional hybrid semantic profiler. Required governance cannot silently become a simple topology, whereas preferred governance can be configured to degrade under budget (orchestrator.ts, lines 1201–1358). In the coordinator path, a bounded structured manifest exposes roles, capabilities and tools. The planner produces task descriptions, assignees, prerequisites and optional hard requirements. The framework validates the plan and maps title references to UUID task IDs before dispatch (coordinator.ts, lines 349–473, 711–775; orchestrator.ts, lines 1808–1895). This is task planning, not a persistent product leadership hierarchy.

Execution is asynchronous concurrency inside Node, with child processes only for external backends. AgentPool combines an overall semaphore with per-agent locks; duplicate concurrent tasks on one registered agent serialize without occupying a pool slot while waiting (pool.ts, lines 57–180). The orchestrator/team concurrency limits resolve into each run's pool. Since pools are per-run, this is not an organization-wide resource allocator across independently launched product runs.

There are four distinct records, with different guarantees:

  1. Shared memory/checkpoint store: a configurable MemoryStore; default memory dies with the process. FileStore persists a whole JSON store through temporary-file write/fsync/rename and serializes mutations within one instance, but has no cross-process locking (file-store.ts, lines 1–31, 80–130).
  2. Execution checkpoint: queue state, shared memory or its turn counter, message bus, completed results, in-flight runner continuations and approvals. Version 5 additionally carries the journal watermark; unjournaled runs use version 4 (task-execution.ts, lines 189–305).
  3. Authoritative run/approval ledgers: opt-in run ownership and content-bound decisions. These are execution facts, not telemetry. Run ownership uses compare-and-set, lease expiry and fencing tokens. The shipped memory/file adapters have only process atomicity; cross-process correctness requires a genuinely atomic external implementation (run/store.ts, lines 28–99; run/ledger.ts, lines 136–201, 333–445).
  4. Journal and telemetry: optional append-only conversation/context lineage and best-effort traces. Trace materialization feeds the static DAG/waterfall viewer. These records explain a run but do not establish a continuing project's business state (journal.ts, lines 1–46; run-viewer-model.ts, lines 35–170).

Agent definition and lifecycle in detail

Definition, creation and identity

An AgentConfig is a blueprint: name, optional description/capabilities/cost/latency/permission tags, model/provider or external backend, role prompt, custom tools, grants, workspace, budgets, context strategy, timeout, history and hooks. Capability and permission tags are explicit application facts; OMA does not infer a trust boundary from a role prompt (types.ts, lines 982–1075). A standalone agent requires a model or backend; orchestrated agents can inherit defaults. Constructor validation and history copying happen before execution, while provider/backend initialization is lazy (agent.ts, lines 127–180).

Creation is explicit in application code: construct a Team/config roster, then ask the orchestrator to run it. A named config does not create a daemon or Codex chat. runAgent() creates a one-off unregistered instance (orchestrator.ts, lines 1031–1067). Team execution builds fresh pool agents from effective defaults. A task receives a UUID and timestamps from createTask() (task.ts, lines 36–74). Run identity and trace identity track executions/attempts, not a durable personal identity across an organization.

Separate specialist instances should have distinct names/configurations. AgentPool rejects duplicate registration, but Team initially indexes configs in a Map. A profile and an instance are not separate domain entities (pool.ts, lines 105–119; team.ts, lines 104–110). Wingman would need stable agent IDs independent of display names, profile versions, manager/project membership and host/session bindings.

Execution, sessions and tools

The API deliberately separates run()/stream(), which start from a supplied fresh message sequence, from prompt(), which appends to the instance's persistent in-memory history. Applications can save getHistory() and restore it through config. A name alone restores nothing (agent.ts, lines 311–388). Orchestrated task calls use pool.run(), so ordinary LLM workers do not accumulate one continuous personal conversation across all tickets. They receive task description, explicit prerequisite outputs or opt-in shared-memory summary, and addressed team messages. Default context injection is dependency-scoped, not all previous team work (task-execution.ts, lines 1789–1886).

The built-in backend is a bounded model/tool loop. It performs context management, sends a model request, validates and executes requested tools, appends results, and repeats. It stops on an answer, budget/abort/loop condition or maxTurns (default ten). At turn exhaustion it can return the most recent assistant text; turn exhaustion is not evidence that a product is done (runner.ts, lines 638–639, 1493–1520, 1759–1777). Agent state transitions idle → running → completed/error; semantic acceptance is a separate application responsibility (agent.ts, lines 422–449, 608–650).

Built-in tools are file read/write/edit, grep, glob and bash; delegation is registered only in orchestrated worker contexts. Built-ins are default-deny without positive grants. Presets and explicit tools intersect; deny lists also constrain registered custom/runtime tools (grants.ts, lines 10–15, 33–88). The executor validates tool input before invoking onToolCall. A denied, throwing or malformed gate produces an error result and cannot execute the tool (executor.ts, lines 188–293). Tool execution exceptions are converted into ToolResult.isError; provider failures follow a separate classification/retry path.

Filesystem tools resolve paths and symlinks under the configured sandbox, defaulting to .agent-workspace. This is not an OS sandbox for bash. Explicit cwd: null widens filesystem access. The checkout makes the distinction explicit in sandbox-and-shell.md, and implementation resolution is in path-safety.ts, lines 29–92. A Wingman integration must preserve real per-product worktree/host boundaries rather than infer them from these tool grants.

External backends replace the runner. Generic process execution sends a prompt by stdin/argument, collects stdout/stderr and exit status, and reports zero token usage. It does not inspect a coding CLI's internal tools (process-backend.ts, lines 53–143). ACP lazily creates and reuses a subprocess/session, maps notifications to output/tool/usage records, and forwards cancellation. ACP's session can therefore retain state even though OMA's outer run() supplies fresh input. The “fresh conversation” semantics are strongest for the LLM runner, not a guarantee that an external program forgets its session. ACP permission policy defaults to auto-approve, preferring one-time permissions when available (acp-backend.ts, lines 100–118, 174–204, 365–393). Neither backend receives the runner's filesystem protection, internal tool gates, context compaction or mid-task runner checkpoints. This boundary is documented and source-grounded in external-agents.md, lines 210–240.

Routing, delegation, concurrency and scheduling

runTeam() topology selection is separate from task-to-agent assignment. The coordinator sees a bounded roster rather than full private system prompts; tasks may carry hard requirements for tools, capabilities, backend and provider. Scheduler strategies include round-robin, least-busy, capability-match, dependency-first and composite fit/load/criticality (scheduler.ts, lines 30–63, 176–240, 365–409). This is a useful routing kernel, but workload size is only one part of Wingman's organizational decisions.

The normal execution loop subscribes to readiness/completion and admits newly ready tasks as capacity becomes free. It does not wait for an entire batch to finish; legacy onApproval round mode is a separate path and is incompatible with runtime repair (task-execution.ts, lines 744–878, 941–999). “Scheduling” here means ordering an active DAG, not calendar wakes or management polling.

Granted delegate_to_agent rejects unknown targets, self delegation, cycles, excessive depth and saturated pool capacity. It invokes a fresh temporary agent, returns its result and charges child usage through tool metadata. A delegated call is not a durable new organizational hire or a queued message delivered to a running colleague (delegate.ts, lines 30–107; task-execution.ts, lines 85–185). Delegation avoids per-agent locks because fresh child objects prevent the mutual-lock deadlock of two parents delegating to each other. It still uses the pool semaphore.

Persistence, resume and approvals

Persistence is deliberately opt-in. An in-memory checkpoint cannot survive process loss. A FileStore supports sequential restart, and custom MemoryStore/RunStore implementations can supply database durability. A snapshot includes in-flight runner messages and pending/committed tool state as well as task results; restore rehydrates shared memory and message bus, resets in-progress queue states and supplies runner continuation state (task-execution.ts, lines 189–275; orchestrator.ts, lines 2476–2498). Applications must recreate agents, live adapters, tools, hooks and coordinator wiring; checkpoints are not serialized processes. A restored team run can rerun synthesis, falling back to raw outputs with a visible synthesis failure if the required coordinator cannot be restored (orchestrator.ts, lines 2327–2342).

Ordinary checkpoint saves are best-effort. Approval suspension, ownership writes and durable plan revision boundaries tighten that contract. Approval request hashes bind canonical JSON content and boundary; decisions include reviewer identity and reject conflicting/stale content. Tool restore revalidates the current invocation's hash after schema validation (durable.ts, lines 54–130, 366–435; executor.ts, lines 213–247). Suspending a task with live verification wiring is rejected because the checkpoint cannot reconstruct its judges/schema/callbacks (durable.ts, lines 133–144). These constraints must be designed into an approval UI instead of treating every callback as restart-safe.

With a RunStore, a worker acquires a lease, renews it, and fences checkpoint/lifecycle writes; lost ownership stops further advancement. Without it, two processes can restore the same checkpoint. With the shipped process-atomic backends, ownership still does not establish multi-machine exclusion. The run row and snapshot are separate writes, and neither transactionally includes an external tool side effect. A crash after an external commit but before recording the tool result can repeat that effect on recovery; stable external idempotency keys remain necessary (run/ledger.ts, lines 136–201, 390–445; run-store.md, lines 144–151). A durable run is therefore substantially more than a saved chat, but less than an exactly-once distributed workflow system.

Interruption, failure, recovery and completion

Callers pass an abort signal. There are whole-run and per-model-call timeouts. The queue stops admitting work, drains already admitted work as needed, and skips remaining tasks. Generic processes wire abort to process-tree termination; ACP sends session cancellation and depends on the external agent/protocol responding (task-execution.ts, lines 783–870, 917–939; process-backend.ts, lines 75–77, 149–157; acp-backend.ts, lines 174–190). RunLedger.cancel() bumps the fencing token and marks authoritative cancellation. It is not a remote process manager (run/ledger.ts, lines 242–265).

Retries are bounded by task configuration, classified errors and abort state, with exponential delay and equal jitter. Suspension returns without retry; terminal validation/auth/cancellation failures avoid extra attempts. Provider model fallback can advance after retryable provider errors (retry.ts, lines 75–135; task-execution.ts, lines 1423–1486). A task failure cascades to its dependents, while unrelated work can continue (queue.ts, lines 447–543).

Optional repair receives an outcome and proposes a bounded plan patch: add tasks, retarget pending tasks or supersede pending branches. It validates agent eligibility and graph changes, optionally seeks patch approval, checkpoints the revision, rolls it back on checkpoint failure, and only then publishes readiness events (recovery.ts, lines 20–67, 99–149; task-execution.ts, lines 485–737). Default behavior is a fixed DAG; no hidden supervisor autonomously invents repairs unless the application supplies policy/replanner.

A successful worker result can be checked by consensus judges before writing shared memory, completing the queue task and saving a checkpoint. Accepted revisions replace the result. A rejected revision leaves the original successful result and records dissent. Thus optional judge rejection is an observation usable by repair policy, not by itself a hard acceptance barrier (consensus.ts, lines 427–453; task-execution.ts, lines 1573–1614). Wingman must explicitly gate product completion on real tests, integrated acceptance evidence and the agreed definition of done. A final coordinator answer is a synthesis of outputs, not proof that a deliverable was accepted.

Retirement is minimal. Agent.reset() clears history/state but retains the backend; AgentPool.remove() unregisters; AgentPool.shutdown() resets agents. OpenMultiAgent.shutdown() clears teams/counters and explicitly does not cancel in-flight runs (agent.ts, lines 376–388; pool.ts, lines 121–133, 347–362; orchestrator.ts, lines 3020–3032). ACP has its own dispose() to kill the subprocess, but the inspected top-level Agent/Orchestrator reset/shutdown APIs do not expose a general archive/drain/dispose lifecycle (acp-backend.ts, lines 304–321). Host-process lifecycle and retention need deliberate application ownership; no running-process leak was exercised or measured in this assessment.

Coordination mechanics and a source-traced request

The actual mechanisms are task dependency edges, prompt handoff, shared memory, local message retention, queue events, application callbacks and durable decision rows. MessageBus supports direct and broadcast recipients, per-agent read state and snapshots, but subscribers are callbacks in the current process, not persisted actors (messaging.ts, lines 1–127). A task prompt includes all addressed messages, not merely unread ones; no delivery wakes a dormant worker automatically. Agents cannot call an included chat tool to start a room conversation. An embedding application would need to expose messaging as custom tools and decide when messages create turns/tasks.

A concrete checked-in example traces a release request through suspension and resume: durable-approval.ts, lines 46–104. This walkthrough follows source. The example was not run and its model is a deterministic mock, so “released” is output text, not a deployment.

  1. The application defines release-operator and submits the explicit task “Release build 42”, with critical priority and a checkpoint store (example lines 46–72). runTasks() builds the local queue and resolves task configuration/assignees (orchestrator.ts, lines 2751–2792). There is no Telegram intake or project lookup.
  2. At dispatch, onTaskDispatch returns suspend. The executor makes a content-bound task_dispatch request and persists its pending continuation before returning suspended status (task-execution.ts, lines 997–1099; pending persistence at lines 387–415). No worker is admitted for that boundary before approval.
  3. The caller takes the pending request and invokes decideApproval() with request ID/hash and a named reviewer (example lines 78–87). DurableApprovalLedger uses CAS and validates request binding, rather than trusting a UI string or an event log (durable.ts, lines 414–458, 483–578).
  4. The application constructs a fresh orchestrator and Team, supplying live worker dependencies again. Its new gate would deny an unapproved task, but restore() consumes the already-approved exact boundary (example lines 89–97; orchestrator.ts, lines 2492–2608). The example's memory store only simulates restart. A durable store is required across real processes.
  5. The worker runs and returns “Build 42 released.” The executor records usage, completes the task, checkpoints, and emits completion; returned approval history carries the reviewer (example lines 99–104; task-execution.ts, lines 1510–1628). The framework has verified its own execution boundary, not actual production health or product acceptance.

For a real dependency handoff, external-agent-process.ts, lines 30–58, defines extractor and summarizer child-process agents. “Summarize notes” depends on “Extract notes”; completion makes the successor ready, and buildTaskPrompt() injects the prerequisite result. This demonstrates the mechanism a backend/frontend/test chain could use. It does not add a shared organizational ticket board, asynchronous negotiation, merge/worktree strategy or integration contract automatically.

Major additional capabilities

Durable review with content integrity. Approval requests are canonicalized/hashed, reviewed separately from traces and resumed against the exact boundary. This is stronger than an ephemeral yes/no prompt and is directly valuable for Wingman's delivery or consequential actions. Integration requires reviewer authentication/authorization, Telegram/UI notification and routing, durable storage and a policy for unsupported live verification callbacks. A recorded reviewer ID is not an identity provider (durable.ts, lines 125–144, 366–435).

Run ownership and crash recovery. Leases and fencing distinguish “there is a saved snapshot” from “this worker is authorized to advance it.” This would help Wingman avoid competing recoveries and stale completions. The integration consequence is substantial: supply a truly cross-process CAS backend, stable run IDs, worker lease policy, host dispatch and external effect idempotency. The file store alone cannot coordinate Mac and Linux workers (run/store.ts, lines 28–99; run/ledger.ts, lines 333–445).

Context-lineage journal and verification. verifyRun() checks monotonic sequence, prior-event references and whether recorded input-block hashes can be reproduced from their source events. Missing retained events become inconclusive rather than fabricated failures; forward/mismatched references fail verification (verify.ts, lines 143–215, 250–309). It can explain what the model saw after context replacement, a valuable debugging/audit layer beyond Wingman's described user-facing timeline. It is opt-in and best-effort, not signed proof, semantic truth or deterministic replay of provider inference. Storage retention and sensitive content capture need application policy. Tail replay extends a checkpoint only when consistency checks succeed, otherwise falls back to the checkpoint (tail-replay.ts, lines 1–9).

Execution routing, governance and receipts. Deterministic selection, optional semantic profiling, declared independent roles, model routing/fallback, budgets and execution receipts help an application explain the topology it actually used instead of equating roster size with collaboration. Receipts derive facts such as executed roles, dependency edges and reviewer decisions. They are not themselves authoritative execution storage (execution-receipt.ts, lines 8–58, 110–145; orchestrator.ts, lines 1201–1358). Wingman could use this for cost-aware work assignment, while retaining explicit ProductMaster/TechMaster roles when organizational accountability is required.

Bounded plan repair and multi-judge critique. Repairs can alter an unfinished DAG in response to success, failure or verification rejection, with revision/task limits and durability-before-dispatch. Consensus supports proposer/judge rounds, quorum, dissent and revision. These could drive defect investigation and alternate implementation paths. The application must define policy, evidence standards and a hard acceptance gate. An LLM quorum is not functional test coverage, and rejected critique does not automatically fail tasks (recovery.ts, lines 20–67; consensus.ts, lines 293–325, 436–453).

Offline/online evaluation infrastructure. Eval sets, scorer records, scorer/target error accounting, threshold policies and baseline regression checks support measurement of agent configurations. Online evaluation has sampling, bounded queues/concurrency, rate/cost budgets, explicit flush/shutdown and isolated failures (online.ts, lines 24–85; gate.ts, lines 251–339). This could benchmark Wingman's intake/routing/review behavior before changing it. Scorers and meaningful datasets must be supplied, and these agent evaluations do not replace product acceptance tests.

Provider/tool integration and outbound policy. OMA normalizes multiple provider adapters, supports custom/AI SDK adapters and local compatible endpoints, and imports optional SDKs lazily. MCP tools can be discovered through a local stdio connection with prefixing and timeout configuration (adapter.ts; tool/mcp.ts, lines 59–95). Provider egress policies intersect and constrain exact origins; guarded fetch rejects redirects (egress.ts, lines 101–188). Wingman could reuse these connectors, but provider egress is not comprehensive network containment for shell/custom tools/external agents. Codex-specific controls and host isolation remain adapter responsibilities.

Operational telemetry and image generation. OpenTelemetry lives in a separate package with application-owned tracer/provider lifecycle, optional batching and explicit content-capture policy. The run viewer visualizes trace detail without becoming execution state (otel/exporter.ts, lines 50–98). A separate image pipeline supports ordered model attempts, deadlines/retries and output validation (run-image.ts, lines 1–21, 39–79). These expand the runtime into measurable multimodal workflows, but require application artifact storage, attribution and presentation. Neither creates Wingman's agent workspace or project asset lifecycle.

Distinctive mechanisms and grounded innovation assessment

The most valuable design choice is the separation of recovery snapshot, authoritative ownership/approval facts, and observation. Checkpoint presence alone grants no distributed execution authority. A stale lease cannot write terminal success; telemetry failure does not become business failure. This separation makes the runtime easier to embed in a durable service without conflating dashboards with truth. Its limit is equally explicit: custom atomic storage and idempotent external operations are still required. This is an implementation strength, not evidence of historical novelty.

Content-bound approval is another concrete mechanism: canonical JSON plus a request hash binds the decision to a specific plan/task/tool boundary, and revalidation rejects a changed tool invocation. It enables useful offline review and restart recovery without asking a new callback to reinterpret an old approval. It cannot defend against a party who can rewrite both trusted execution stores, and it supplies neither reviewer authentication nor a review product.

The journal's block-level source references and hashes make context transformation inspectable. Recording context/replace and checking input reproducibility is a deeper diagnostic mechanism than a flat transcript, especially when tool-output compression and provider reasoning conversion change the request. It establishes internal lineage consistency, not the truth of reasoning, tamper-proof provenance or model-output reproducibility.

The repair path publishes patch readiness only after its checkpoint survives. Checkpoint failure causes rollback. Delegated calls use fresh instances to avoid target-agent mutex deadlocks. The pool rejects calls when capacity is exhausted. These are useful mechanisms for Wingman's parallel specialists. They do not amount to a distributed actor model, and their bounded local scope should remain visible in any integration.

Practical adoption path and remaining work

OMA is best considered as an optional run engine inside Wingman, not as the product shell. The reusable surfaces are explicit task DAGs, configurable worker backends, safe tool-grant resolution, application hooks, checkpoint/restore, durable approvals, run leases, provider routing, structured results, run traces and evaluation. Its explicit-task path is particularly suitable when Wingman's own TechMaster already owns decomposition and tickets; allowing another coordinator to reinterpret that plan would add an unnecessary authority boundary. Frozen plan replay can preserve an approved topology (orchestrator.ts, lines 2283–2324).

A practical adaptation would map Wingman project tickets to durable OMA run/task IDs, retain product scope and acceptance outside run memory, and route events into ProjectTracker and agent timelines. Agent identity must live above ephemeral pools. Codex workers need an explicit process/ACP adapter with native conversation/session IDs, permissions, usage and cancellation semantics; generic stdout adapters cannot deliver the desired detailed Codex workspace. Persistent direct collaboration needs durable messaging tools and wake/turn scheduling, not only Team.sendMessage().

For the Mac/Endeavour architecture, add host registration, authenticated dispatch, workspace placement, code/artifact synchronization or a shared repository strategy, and a remote worker service. Supply a database-backed CAS RunStore and a durable coordination store; do not share FileStore between machines and call that distributed execution. Apply a cross-product capacity controller above each per-run pool. Plan safe ownership transfer and side-effect idempotency explicitly.

The larger remaining application is the user experience and organization:

  • Telegram Butler.
  • project intake/registry.
  • ProductMaster discovery and questions.
  • TechMaster tickets.
  • standing agent/profile directory.
  • management/project chat rooms.
  • periodic ProjectMaster supervision.
  • linked portfolio/executive views.
  • meaningful per-agent summary feeds.
  • individual live coding sessions.
  • attachments/queued steering.
  • fork/rename/archive lifecycle.
  • product verification/acceptance/delivery.
  • organizational retention.

Most of Wingman's differentiation resides in this layer. OMA's durability and observability could reduce infrastructure risk underneath it, but adopting the runtime would not materially eliminate that product work.
