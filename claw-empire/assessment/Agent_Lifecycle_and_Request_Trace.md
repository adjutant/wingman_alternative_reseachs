# Claw-Empire: agent lifecycle and request trace

Companion to the [assessment](ASSESSMENT.md). Static inspection of commit `66a24ea7df2435ef897c48c147deb7ec572c01c2`, 2026-11-05. Paths below are relative to this chapter; ranges identify the inspected implementation. No application, provider, Telegram integration or test was run.

## What an agent actually is

The durable object is the SQLite `agents` row. It holds a UUID, names, department, one of four ranks, workflow pack, planning-leader flag, provider/account/model, personality, status, current task and statistics. There is no native Codex conversation identifier in that row. A department supplies another prompt and organizational grouping. A workflow pack supplies domain guidance and routing. These compose a reusable employee profile, rather than defining a daemon that continually reasons. See [base schema](../repo/server/modules/bootstrap/schema/base-schema.ts), lines 7–107.

Three other objects must remain distinct. A **task** is a durable work item with assignee, project, description, status and result. A **task execution session** is an application UUID in an in-memory map, reused only while its task/agent/provider combination matches. A **run** is a new local process or HTTP request with a prompt and output log. A meeting contribution is another one-shot invocation using an employee's persona. Provider-internal Codex/Claude subagents can be projected into tracker subtasks, but are not thereby employee rows. See [session tools](../repo/server/modules/workflow/orchestration/session-review-tools.ts), 30–67; [CLI runtime](../repo/server/modules/workflow/agents/cli-runtime.ts), 41–155 and 220–256; [one-shot runner](../repo/server/modules/workflow/core/one-shot-runner.ts), 81–103.

## Definition, creation and retirement

`POST /api/agents` validates the name, pack and department, chooses a permitted rank/provider and inserts a new UUID. It broadcasts `agent_created` for the generic UI. It does not start a process. `PATCH /api/agents/:id` updates the profile, validates provider-specific account/model options and handles planning-leader conflicts. Those settings influence later prompts/runs; editing personality does not rewrite a currently running provider conversation. See [agent CRUD](../repo/server/modules/routes/core/agents/crud.ts), 293–409, 447–585 and 594–615.

Creation is human/control-plane CRUD, not evidence that a ProjectMaster autonomously hires a durable employee. Runtime fan-out through `spawn_agent` is a separate provider mechanism. Multiple rows can share a department and model, so several backend specialists can exist, although their domain role comes from department/personality rather than an unconstrained role type.

Deletion refuses a `working` employee, nulls task/subtask/minute/report/planner references transactionally, then deletes the row and broadcasts it. There is no first-class archived agent identity or recoverable retirement lifecycle in this path. See [deletion](../repo/server/modules/routes/core/agents/crud.ts), 416–440.

## Assignment, routing and concurrency

Delegation resolves project metadata and workflow pack, constrains candidate agents by project/pack, chooses a subordinate from the leader's department and creates the planned task. The task description contains CEO instruction, project core goal and round goal. After planning, callbacks reassign the task to the subordinate and start execution, with leader self-execution as fallback. Acknowledgement/delegation speech is partly server-built template text with randomized delays. It is not all autonomous reasoning. See [delegation](../repo/server/modules/routes/collab/task-delegation.ts), 125–222 and 390–478.

The explicit task-run route rejects another live process on the same task and rejects an employee whose current working task still has an active process. Different task IDs and employees can have distinct processes and worktrees across projects. This is local concurrency, with no host-placement or remote-runner protocol. Foreign-department subtasks are intentionally grouped into queues and dispatched one department batch at a time; origin-team work can defer that dispatch until review. See [task-run checks](../repo/server/modules/routes/core/tasks/execution-run.ts), 87–125 and 271–283; [department dispatcher](../repo/server/modules/routes/collab/subtask-delegation.ts), 280–345.

## Starting a coding run and tool authority

`startTaskExecutionForAgent` sets task `in_progress` and employee `working`, obtains an application session, and loads pending interruption prompts. It creates an isolated Git worktree; failure rolls status back to pending and releases the employee. The prompt combines recent changes, task/pack, continuation brief, recent conversation, employee/personality, department constraint/shared prompt and injected direction. Provider routing then chooses CLI, generic API or OAuth HTTP execution. See [execution start](../repo/server/modules/workflow/orchestration/execution-start-task.ts), 76–92, 129–247 and 249–307.

For CLI workers the backend writes a temporary prompt file, inherits the server environment with selected CLI-related adjustments, starts a local detached child in the worktree and sends the prompt through stdin. Output goes to a file, WebSocket events and subtask parsing. Idle/hard timeouts kill the process tree. The worktree is a source isolation mechanism, not a separate OS user/container or a filesystem/network sandbox. See [CLI execution](../repo/server/modules/workflow/agents/cli-runtime.ts), 220–368.

Tool authority is provider dependent. Codex coding uses `--enable multi_agent --yolo exec --json`; Claude uses `--dangerously-skip-permissions`; Gemini coding uses `--yolo`. Meeting calls can request `noTools`, causing read-only/plan/no-tool arguments where supported. The one-shot runner also detects tool-like output and aborts a violation. Rank and department constraints are instructions, not independent authorization boundaries. See [argument construction](../repo/server/modules/workflow/core/cli-tools.ts), 48–108; [one-shot safeguards](../repo/server/modules/workflow/core/one-shot-runner.ts), 40–46 and 126–137.

The generic API adapter sends a streamed user/system text request to Anthropic, Google or a chat-completions endpoint, then consumes the stream. It declares no filesystem/shell tools or tool-execution loop. A project path mentioned in its system message does not make that employee a coding process. See [API adapter](../repo/server/modules/workflow/agents/providers/api-provider-tools.ts), 119–241. OAuth-backed implementations are separate adapters; their capability must be evaluated individually rather than inferred from the common employee selector.

## Persistence, continuity and interruption

SQLite preserves employee/task/message/minute/revision/report records, while logs preserve output. On a later run, `getRecentConversationContext` retrieves ten agent-related messages, including broadcasts, and `getTaskContinuationContext` builds bounded excerpts of result tail, review notes, minutes and project memo. This is useful retrieval but is neither full conversation history nor strictly project-scoped retrieval. See [context tools](../repo/server/modules/workflow/core/conversation-context-tools.ts), 19–50 and 67–164.

The application reuses a session UUID in memory and prints it into the prompt. The Codex argument builder passes neither a native thread ID nor `resume`. A resumed task starts another `exec`. Session preservation therefore means workflow continuity. It does not establish native Codex conversation continuity.

Restart loses the in-memory session map. Durable interruption rows use that application UUID. These paths do not establish restart-safe delivery of an old pending instruction. See [session map](../repo/server/modules/workflow/orchestration/session-review-tools.ts), 30–67; [injection schema](../repo/server/modules/bootstrap/schema/base-schema.ts), 154–163; and [CLI arguments](../repo/server/modules/workflow/core/cli-tools.ts), 56–64.

Pause signals SIGINT (or abort for HTTP), sets pending and releases the employee while preserving application workflow/session state. Injection requires pending status, session proof and a control token. It sanitizes and durably queues the instruction. Resume validates status, rejects an active process and schedules a fresh start for the assigned online employee. The next start incorporates and consumes injections. Cancel kills rather than interrupts, rolls back worktree changes, blocks linked delegated subtasks and clears workflow/session state. Late completion callbacks are ignored for stopped/deleted/non-running tasks. See [execution controls](../repo/server/modules/routes/core/tasks/execution-control.ts), 139–206, 229–259, 303–405 and 467–529; [late-result handling](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), 56–93.

Each restarted `startTaskExecutionForAgent` calls `createWorktree`. Its candidate loop recursively removes an existing worktree directory before re-adding the branch. Committed branch state may survive. Paused uncommitted or untracked files can be lost. The control-route tests mock startup. They do not establish filesystem preservation across the full pause/resume cycle. See [restart call](../repo/server/modules/workflow/orchestration/execution-start-task.ts), 129–130; [candidate cleanup](../repo/server/modules/workflow/core/worktree/lifecycle.ts), 162–188; and [resume control](../repo/server/modules/routes/core/tasks/execution-control.ts), 514–529.

## Scheduling, supervision, failure and recovery

There is no inspected enduring employee loop waking to reason about its portfolio. The server schedules workflow callbacks and mechanical sweeps: startup interrupted-workflow repair, orphan tasks/employees and pending subtask dispatch. Defaults include a ten-minute orphan grace, thirty-second orphan sweep and fifteen-second delegation sweep. See [runtime constants](../repo/server/db/runtime.ts), 44–55; [lifecycle scheduling](../repo/server/modules/lifecycle.ts), 455–461.

Recovery consults process handles/PID liveness, recent DB logs and terminal-file modification time before treating work as orphaned. It can replay a recorded successful/failed completion or return unknown orphan work to inbox, release the employee and notify the CEO. Startup also reconciles delegated work and duplicate review meetings. It repairs organization state. It does not reconnect a lost native agent conversation. See [recovery](../repo/server/modules/lifecycle.ts), 170–361.

Ordinary unsuccessful execution resets to inbox, cleans the failed worktree, reports an error and allows departmental queues to continue. The failure notice requests reassignment/revision/retry. This is not a demonstrated general autonomous retry policy. Bounded meeting retries and workflow remediation are separate mechanisms. Cleanup force-removes worktrees and deletes their branches, so intermediate failed code can be lost while logs survive. See [failure handling](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), 650–752; [cleanup](../repo/server/modules/workflow/core/worktree/lifecycle.ts), 234–268.

## Completion, review and delivery

Ordinary exit-zero work moves to review; child work can wait for parent consolidation. Meetings produce persisted leader feedback and remediation. Review policy explicitly moves through remediation, synthesis and final decision, with later prompts disallowing new remediation and offering approval with residual risk. This bounds debate but does not enforce satisfaction of a product definition of done. See [successful completion](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), 485–567; [review mode](../repo/server/modules/workflow/orchestration/session-review-tools.ts), 98–139; [review prompts](../repo/server/modules/workflow/orchestration/meetings/review-consensus.ts), 310–443.

Finalization attempts a local merge or GitHub development-branch/PR workflow. Successful cleanup precedes the done record and session closure. The merge-failure branch notifies the CEO that manual resolution is needed. It then reaches the same `done` update. Done therefore does not establish successful integration.

The GitHub PR request also runs asynchronously after push. Finalization does not await its success as the synchronous merge result. See [finalization](../repo/server/modules/workflow/orchestration/review-finalize-tools.ts), 526–612, and [GitHub delivery](../repo/server/modules/workflow/core/worktree/merge.ts), 204–310.

The video pack has stronger concrete gates: missing/empty video or missing/invalid Remotion execution evidence holds approval. Report tasks have separate design-checkpoint/PPT completion paths which can skip review. These are distinct domain policies, not a universal software acceptance contract. See [video finalization](../repo/server/modules/workflow/orchestration/review-finalize-tools.ts), 344–515; [report branches](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), 412–480.

## Trace: an ordinary Telegram coding request

This traces an implemented code path, not an observed successful run. Assume a configured token, allowed chat, inbox secret, session-to-agent mapping and suitable employee/provider.

1. The receiver polls Telegram, rejects bot/disallowed/empty updates and posts source, message ID, author, chat and text to the local inbox with the shared-secret header. Successful forwarding advances persisted offsets. See [receiver](../repo/server/messenger/telegram-receiver.ts), 306–350 and 408–468.
2. Inbox authenticates the shared secret, resolves the mapped employee for ordinary text and rejects unconfigured session routing. It inserts an idempotent message, first offers a reply to the workflow decision bridge, and otherwise calls `scheduleAgentReply` with messenger routing metadata. See [inbox](../repo/server/modules/routes/ops/messages/directives-inbox-routes.ts), 407–458, 506–540, 600–612 and 690–738.
3. Direct chat classifies task intent and manages project binding. When needed it asks existing/new, lists recent projects or requests new name/path, and later hands off through its task flow. Pending binding is an in-memory map keyed by employee, expiring after an hour; two independent chat/project dialogues for the same employee are not separate durable conversations. See [direct chat](../repo/server/modules/routes/collab/direct-chat-handlers.ts), 42–55, 79–224 and 492–537; [task flow](../repo/server/modules/routes/collab/direct-chat-task-flow.ts), 51–98 and 167–193. To follow the planning branch below, assume the mapped employee is a departmental team leader. A specialist can receive a direct task without that leader meeting.
4. A delegated task records project/core/round goals and the messenger destination. A planning meeting calls one-shot leader personas with a transcript, collects executable action items, appends a project memo and invokes its approval callback. Planning is explicitly told not to block kickoff. See [delegation](../repo/server/modules/routes/collab/task-delegation.ts), 141–219 and 390–445; [planning meeting](../repo/server/modules/workflow/orchestration/planned-approval.ts), 213–333.
5. The subordinate starts a worktree-scoped provider run; its stream updates terminal logs and can create subtasks from provider events. Other departments receive batched delegated tasks and completion callbacks. Shared DB state and task IDs coordinate them, rather than arbitrary project rooms. See [execution](../repo/server/modules/workflow/orchestration/execution-start-task.ts), 129–307; [subtask parsing](../repo/server/modules/workflow/agents/cli-runtime.ts), 44–155 and 333–350; [dispatch](../repo/server/modules/routes/collab/subtask-delegation.ts), 294–345.
6. Exit success moves ordinary work to review; failure returns it to inbox. Review/timeout choices are exposed through the decision inbox and messenger. A numeric reply resolves the latest decision for that route unless an explicit decision token identifies another; validated options are applied to workflow state. This is a concrete answer-routing mechanism, but latest-choice fallback can be ambiguous when several questions share a channel. See [completion](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), 485–567 and 650–752; [decision reply bridge](../repo/server/modules/routes/ops/messages/decision-inbox/messenger-bridge.ts), 403–491.
7. Approved work reaches merge/report/done as described above. The task's stored messenger route enables follow-up notification. This does not establish human acceptance against maintained scope/scenarios, and merge failure can still reach done.

The `$` directive route requires an explicit project ID by default. Without it, the route returns HTTP 428. The native Telegram receiver does not include a project ID in its forwarded body. The source therefore does not establish default delegation for a raw `$...` received through that path.

Documented OpenClaw orchestration supplies project-binding metadata. Ordinary mapped chat can ask binding questions. These are separate intake paths. See [default policy](../repo/server/modules/routes/ops/messages.ts), 9–10; [directive requirement](../repo/server/modules/routes/ops/messages/directives-inbox-routes.ts), 490–503; and [forwarded fields](../repo/server/messenger/telegram-receiver.ts), 335–347.
