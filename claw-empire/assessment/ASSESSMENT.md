# Claw-Empire assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/GreenSheep01201/claw-empire

Local checkout: `research/claw-empire/repo`. Inspected revision: `66a24ea7df2435ef897c48c147deb7ec572c01c2`. Package version: `2.0.4` (`climpire`). Baseline: [Wingman purpose](../../WINGMAN_PURPOSE.md).

**Fit verdict:** Claw-Empire is a substantial candidate for Wingman's organizational control plane. It implements real project records, configurable agent employees, departmental delegation, a task board, CEO messaging, Telegram ingress and replies, planning/review meetings, isolated coding runs and workflow recovery. Its central abstraction is a company of durable employee records executing task-scoped jobs. It does not establish Wingman's full model of persistent, independently conversational Codex colleagues, per-project ProductMaster/TechMaster pairs, arbitrary collaboration rooms, a research-led product discovery cycle, or execution shared across the Mac and Endeavour.

The office simulation sits above a substantial execution and coordination implementation. Some speech and status text comes from server templates or one-shot persona calls. That text does not establish an agent's reasoning about its work.

The source review identified four material integration risks:

- A merge failure can still lead to `done`.
- Pause/resume does not establish retention of uncommitted work.
- Native Telegram `$` intake lacks project metadata that the default path requires.
- The five-minute progress timer reports smooth progress after checking only task status.

These are source findings. The assessment did not reproduce them at runtime.

Detailed companion: [Agent lifecycle and one end-to-end request](Agent_Lifecycle_and_Request_Trace.md).

## 1. Architecture and actual execution model

`server/index.ts` imports the server main module. The package starts it through `tsx`. Main initializes the database, schema, migrations and seeds before wiring workflow helpers, Express routes and lifecycle services into one runtime context. SQLite is the durable source of organizational state; WebSocket broadcasts update the React application. Source: [entry point](../repo/server/index.ts), line 1; [server-main.ts](../repo/server/server-main.ts), lines 46–59 and 122–129; [database runtime](../repo/server/db/runtime.ts), lines 58–105, enables WAL, foreign keys and busy timeout. This is a single server control plane with local execution and process/session/worktree maps, rather than a distributed agent service.

The [base schema](../repo/server/modules/bootstrap/schema/base-schema.ts) is more informative than the simulation framing:

- `agents`, lines 37–61: employee identity, department, workflow pack, seniority, planning-leader flag, provider/model/account, personality, status, current task and accumulated statistics.
- `projects`, lines 63–72: named persistent project, source path, core goal and default workflow pack. Later migrations extend project assignment and GitHub fields.
- `tasks`, lines 88–107: project, department, assignee, status, priority, task type, output format, execution path and result.
- `messages`, lines 133–144: sender, receiver (`agent`, `department`, `all`), content, message type and optional task link.
- `meeting_minutes` and entries, lines 165–188: task-specific planning/review conversations with explicit speakers and sequence.
- `subtasks`, lines 258–270: assignments, blocked reason and CLI tool correlation; migrations add delegated-task/department relationships.
- Report archives and review-decision records, lines 272 onward: durable summaries and decision history.

This is principally **ticket coordination with orchestrated chat**, rather than a free-form agent society whose members independently choose whom to message. `handleTaskDelegation` creates and routes task work; planned meetings collect additions. The subtask dispatcher turns departmental work into delegated execution jobs. A meeting speaker is selected by the server, given a prompt containing the transcript and called through `runAgentOneShot`. The speaker is not necessarily an already-running worker being interrupted to participate. Source: [delegation](../repo/server/modules/routes/collab/task-delegation.ts), lines 125–209 and 400–474; [planned meeting](../repo/server/modules/workflow/orchestration/planned-approval.ts), lines 213–333.

For coding, `startTaskExecutionForAgent` updates task and employee status, creates an isolated Git worktree, assembles context and invokes the chosen provider. CLI providers are separate local child processes with their own current directory, output stream and timeout. This is genuine independent execution, not merely labels on one model's output. However, the employee row is the durable identity. The process is a run. The UUID called an execution session is held in an in-memory map. Codex starts through `codex ... exec --json`. The inspected argument builder does not attach a native Codex resume/thread ID. Continuity is reconstructed through stored messages, logs, prior result tails and review notes. Sources: [execution start](../repo/server/modules/workflow/orchestration/execution-start-task.ts), lines 76–92, 129–247; [CLI runtime](../repo/server/modules/workflow/agents/cli-runtime.ts), lines 220–256; [session tools](../repo/server/modules/workflow/orchestration/session-review-tools.ts), lines 30–67; [arguments](../repo/server/modules/workflow/core/cli-tools.ts), lines 48–108.

Provider choice materially changes capability. The generic `api` path constructs a streamed text request to Anthropic, Google or a chat-completions endpoint. It supplies a project path in text but declares no filesystem or command tools and contains no tool-execution loop in that implementation. A configured API employee is therefore not automatically equivalent to a Codex coding worker. See [API provider tools](../repo/server/modules/workflow/agents/providers/api-provider-tools.ts), lines 119–241. CLI support, OAuth-backed support and arbitrary API text generation should be assessed separately when selecting Wingman's execution backend.

## 3. Agent definition, management and lifecycle findings

An employee profile is a combination of stable database identity, department shared prompt, rank, personality, workflow pack, provider/model/account and current assignment. This is stronger than a reusable prompt file: it has persisted relationships and server-managed state. It is weaker than an always-present conversational colleague: execution and participation are recreated as jobs and one-shot calls.

Creation writes a UUID-backed employee record; configuration edits affect subsequent execution. A planning-lead flag can nominate the pack's coordinator. Task routing selects leaders/subordinates from department and project scope. The system can show provider-internal subagents by interpreting CLI output, but those subtasks are not automatically equivalent to persistent employee profiles in the directory. The CLI parser correlates Claude `Task` and Codex `spawn_agent`/`close_agent` events to tracker subtasks. See [CLI runtime](../repo/server/modules/workflow/agents/cli-runtime.ts), lines 41–155.

Execution uses a separate worktree and process. Rank/personality/department constraints are prompt-level guidance; tool permissions largely come from the provider invocation. The Codex coding invocation enables multi-agent support and uses `--yolo`; Claude uses `--dangerously-skip-permissions`. Worktrees reduce accidental source collisions but are not OS or network sandboxes. Meeting calls request `noTools`, and CLI one-shot code also observes tool signals to abort violations. Generic API calls are text-generation requests. These differences must be preserved in any Wingman adapter: a common employee UI should not imply uniform execution capabilities or isolation.

Pause stops a run while keeping task workflow continuity; injection persists instructions under a task/session ID and consumes them in the next execution prompt; resume starts another run. Retirement rejects deletion of a working agent, detaches task/subtask/review references and removes the employee row rather than archiving its conversation as an enduring identity.

## 4. Coordination, project continuity and human decisions

Claw-Empire combines three mechanisms that Wingman also needs: a shared tracker, readable organizational conversation and a human escalation surface. Its design is valuable because those mechanisms are connected by task IDs and project references rather than being unrelated widgets.

The **tracker** is authoritative workflow state. Assignment is not only a chat message. It changes task and employee fields, creates execution work and emits updates. Delegated tasks link back to source tasks and subtasks. Parent review waits for consolidation and handles child jobs in the same review/merge process. One caution for Wingman is that external-department queues are sequential by design. This gives an understandable order and avoids uncoordinated repeated dispatch, but BackendCoder/FrontendCoder/TestMaster parallelism would need a more explicit dependency graph and capacity scheduler.

The **chat** provides direct CEO→agent messages, department/broadcast messages and meeting transcripts. It does not provide explicit arbitrary room objects with membership and project scoping in the inspected message schema. Meeting conversations are server-orchestrated turns: prompt construction, selected speakers, transcript, status changes and action-item collection. That is useful coordination, but it differs from workers independently using a shared room to settle API contracts while continuing separate coding conversations.

The **decision inbox** is notably practical. Pending project/review/timeout choices become messenger notices. The bridge reserves sends to suppress duplicates, associates decisions with channel targets, accepts numeric/explicit replies and applies the selected option to workflow state. This is a strong pattern for Butler carrying questions and returning answers. Its native decision kinds are operational workflow choices, however, not a general product discovery question model. Multiple domain-clarification threads with durable ownership, answers and resulting product decisions would need expansion.

Continuity also deserves scrutiny: `getRecentConversationContext` pulls ten messages for an agent, including organization broadcasts. The continuation brief clips result/memo/review excerpts. This is a useful bounded retrieval mechanism, but the same employee working across products can receive broadly agent-scoped conversation material. Wingman should make project ID, task ID, native session ID and question ownership explicit rather than relying on a prompt instruction not to mix projects.

A concrete implemented request path is **ordinary Telegram text → mapped employee → project binding → task → optional leader planning → provider run → review/decision → delivery attempt**. The receiver forwards allowed human text to the authenticated inbox ([receiver](../repo/server/messenger/telegram-receiver.ts), 306–347). Inbox resolves the session employee and offers decision replies before normal direct chat ([inbox](../repo/server/modules/routes/ops/messages/directives-inbox-routes.ts), 506–540 and 690–738). Direct chat asks existing/new when task intent lacks a project, then either delegates a departmental leader's request or directly creates/runs a specialist task ([binding](../repo/server/modules/routes/collab/direct-chat-handlers.ts), 492–537; [task flow](../repo/server/modules/routes/collab/direct-chat-task-flow.ts), 51–98 and 167–193). Planning converts transcript actions into memo/subtasks; execution streams output; completion moves to review and decision replies apply concrete workflow options. The [companion trace](Agent_Lifecycle_and_Request_Trace.md) follows those transitions and their failure paths in detail. This trace describes source behavior under its configuration prerequisites, not an exercised end-to-end integration.

Two acceptance boundaries are particularly material. First, source-wide searches found `requireTestEvidence`/`enforceTests` only as pack declarations, while QA JSON is persisted/exposed by configuration routes. It is not evidence of an enforced test-result validator. Second, the merge-failure branch alerts the CEO but does not return before the unconditional `done` update ([finalization](../repo/server/modules/workflow/orchestration/review-finalize-tools.ts), 538–608). Wingman must make test evidence, successful integration and human acceptance separate states rather than trusting this terminal label.

## 5. Major additional capabilities beyond Wingman's described scope

### A configurable production organization for multiple output domains

Workflow packs cover development, novel writing, structured reports, video production, web research reports and roleplay. They carry input schemas, prompt presets, output templates, routing keywords, QA declarations and cost profiles; office-pack department prompts and agent scopes change the operating team. This extends the product from a software organization into a general production company. Source: [pack definitions](../repo/server/modules/workflow/packs/definitions.ts), lines 1–27 and 35–175; [office-pack hydration](../repo/server/modules/routes/collab/office-pack-agent-hydration.ts).

For Wingman this could support ProductMaster research or a content/launch team as a later product expansion. It also means copying the entire orchestration policy imports assumptions from non-software workflows. Some pack fields are configuration declarations rather than independently proven validators. They must be traced to execution enforcement individually.

### Actual video production and artifact-constrained handoff

The video pack is not merely a script-writing persona. It separates planning/documentation from final rendering, delegates `[VIDEO_FINAL_RENDER]`, discovers and synchronizes output files, and blocks review/merge when the video is missing or nonempty-file/render-engine evidence is insufficient. The code specifically checks Remotion evidence. Source: [subtask dispatcher](../repo/server/modules/routes/collab/subtask-delegation.ts), lines 348–393; [run completion](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), lines 114–235; [review finalization](../repo/server/modules/workflow/orchestration/review-finalize-tools.ts), lines 404–515.

This is a distinct deliverable-production capability absent from Wingman's software-only purpose. More generally, its strongest reusable idea is making artifact existence and execution provenance gate completion. The current checks are specialized and do not prove that the video's content meets user intent; adapting the pattern to Wingman would require software artifact, integration-test and acceptance evidence.

### Structured report and presentation production pipeline

Report routing can create a design checkpoint, wait for it, regenerate a final PPT and complete report work through its own path. This is a multi-stage artifact workflow rather than a minor export button. Source: [run completion](../repo/server/modules/workflow/orchestration/run-complete-handler.ts), lines 412–480; [report workflow tools](../repo/server/modules/workflow/orchestration/report-workflow-tools.ts). For Wingman it could become research/decision-brief delivery, but report-specific automatic completion and skipped reviews should not leak into code acceptance policy.

### Multi-provider employee and account operating layer

Per-agent CLI/model/reasoning/OAuth choices, encrypted provider records, account status and usage views make the organization heterogeneous. This can distribute suitable work across toolchains or accounts. Wingman currently defines Codex employees, so this is a major expansion in execution/provider management. Integration needs explicit capability negotiation: the generic API text path cannot replace a filesystem-enabled Codex worker simply by choosing a model name. Sources: [agent detail configuration](../repo/src/components/AgentDetail.tsx), lines 60–109 and 213 onward; [schema](../repo/server/modules/bootstrap/schema/base-schema.ts), lines 205–255; [API path](../repo/server/modules/workflow/agents/providers/api-provider-tools.ts), lines 119–241.

### Provider-targeted skill acquisition and reuse

The Skills Library is an operating capability rather than merely a prompt catalog. A learn job maps selected providers to agents and runs the skills CLI installer, recording queued/running/completed history; custom skill uploads persist content and per-provider success records. Later execution prompts retrieve recent successful provider-matched skills and instruct the worker to prioritize them alongside global/runtime skills and MCP tools. See [learning job](../repo/server/modules/routes/ops/skills/learn-core.ts), 276–323; [custom upload](../repo/server/modules/routes/ops/custom-skills.ts), 41–109; [prompt retrieval/policy](../repo/server/modules/workflow/core/prompt-skills.ts), 83–128. This could grow Wingman's specialist capabilities without changing every role prompt. Integration must distinguish installed executable/provider skills from a DB success label or skill-name hint; uploaded text recorded as succeeded is not proof every provider loads its full content.

### Automated repository bootstrap and GitHub delivery

The execution layer can initialize a non-Git project, add/commit its contents and create task worktrees; GitHub-linked projects can merge into `dev`, push and create/update a PR to `main`. See [bootstrap](../repo/server/modules/workflow/core/worktree/lifecycle.ts), 28–115; [GitHub merge/PR](../repo/server/modules/workflow/core/worktree/merge.ts), 204–310. This turns organizational work into repository artifacts beyond Wingman's currently described coordination interface. It also imports consequential delivery policy: automatic commits, branch checkout/push, credential use and asynchronously requested PR creation. Wingman needs an explicit repository/delivery contract and should not infer a successful PR or integrated release from `done`.

## 6. Distinctive mechanisms and innovation assessment

These are grounded mechanisms that are distinctive in this checkout. This assessment makes no claim of industry-first invention.

**A meeting is a workflow transition with a persistent transcript.** Planned meetings gather contributions, collect action items, append project memos and invoke the execution callback. Review meetings take the consolidated result through remediation, synthesis and decision. The important mechanism is conversion of dialogue into state and work, not animated characters taking turns. This could give Wingman inspectable ProductMaster/TechMaster discussions whose decisions create tickets. The limit is that meetings are orchestrated one-shot turns with bounded context. They are not proof of persistent peers carrying out deep research together. [Planned meeting](../repo/server/modules/workflow/orchestration/planned-approval.ts), 213–333.

**Bounded disagreement is an explicit execution policy.** `getReviewRoundMode` maps round one to parallel remediation, round two to merge synthesis and round three to final decision. Review prompts constrain later rounds from creating endless new remediation and ask for residual-risk documentation. This is an operational answer to endless agent debate, with caps also visible in database runtime configuration. Sources: [session review tools](../repo/server/modules/workflow/orchestration/session-review-tools.ts), lines 98–139; [review consensus](../repo/server/modules/workflow/orchestration/meetings/review-consensus.ts), lines 310–445; [runtime guardrails](../repo/server/db/runtime.ts), lines 22–43. For Wingman, retain bounded discussion but preserve a separate invariant that unmet product acceptance criteria remain unmet regardless of round count.

**Provider subagents become visible tracker objects.** The CLI stream parser recognizes Claude and Codex collaboration events and creates/completes corresponding subtasks. This bridges a provider's internal agent behavior to an organizational tracker, reducing opaque fan-out. It is an attractive observability adapter for Wingman. Correlation is provider-format-dependent and some mappings are in memory. A detected nested task is not automatically a managed employee with its own enduring workspace. [Parser](../repo/server/modules/workflow/agents/cli-runtime.ts), 41–155. It parses each output chunk line-by-line without a visible partial-line buffer in this function, so robust correlation across chunk boundaries is not established.

**A messenger decision is tied to concrete workflow identity.** The decision bridge handles channel routing, pending-choice selection, deduplicated notices and applying the reply. This is more robust than forwarding an arbitrary chat reply to whichever model last spoke. It is directly relevant to concurrent Butler questions, though Wingman should extend identity to durable product questions and avoid ambiguous latest-decision behavior where several independent decisions share one channel. [Reply application](../repo/server/modules/routes/ops/messages/decision-inbox/messenger-bridge.ts), 403–491, explicitly chooses the latest routed decision when no decision token is present.

**Recovery distinguishes process liveness from presentation state.** The watchdog checks active process handles, OS PID liveness, task-log recency and terminal-file modification times before recovering an orphan. This explicitly addresses backend restart and stale employee/task state. It is a substantial operational mechanism, not a timer that blindly restarts everything. It still recovers workflow by logs/state and does not reconnect to all lost native agent sessions. Source: [lifecycle](../repo/server/modules/lifecycle.ts), lines 215–348.

**Domain-specific evidence gates show a path toward outcome-aware autonomy.** Video finalization checks both a produced file and execution evidence, whereas generic coding initially uses process exit and leader review. That contrast is useful: Wingman could generalize the artifact gate idea into product-specific delivery contracts, rather than treating agent completion text as product success. [Artifact/engine gates](../repo/server/modules/workflow/orchestration/review-finalize-tools.ts), 344–515. These checks establish file/log conditions, not semantic correctness of the produced video.

## 7. What Wingman could reuse and what remains

| Layer | Reuse/adaptation judgment |
|---|---|
| Project and task control plane | Reuse the project/core-goal/task/subtask schema, linked reports/minutes and state transitions as a starting model. Add product-specification versions and explicit leadership assignments. |
| Agent directory and organization UI | Adapt generic employee creation, department prompts, assignments and provider configuration. Replace four-rank assumptions where role profiles need arbitrary responsibilities. |
| Telegram and human decisions | Reuse receiver offset/idempotency handling, channel routing and choice application patterns. Bind Butler requests/questions to durable project and conversation IDs. |
| Coding execution | Reuse worktree/output adapter concepts after fixing pause/recreation preservation and failure cleanup policy. Implement native Codex thread persistence, live steering, fork/compact/archive and capability-aware controls. |
| Supervision | Reuse process/log-aware recovery and pending dispatch reconciliation. Add an actual portfolio supervisor reasoning over stale work, blockers, outstanding questions and definitions of done. |
| Chat and collaboration | Retain messages/minutes as evidence but add project-scoped rooms, participant membership and agent-accessible collaboration tools, including cross-host workers. |
| Executive view | Build evidence-derived individual current/recent/next/blocker summaries and linked timelines; source them from actual task/tool/test/decision events. |
| Distributed execution | Build host registry, remote runners, placement, native-session routing, authentication and cross-host project/artifact access. Current local spawn and model HTTP integrations do not supply this. |
| Acceptance | Introduce maintained product scope/spec/scenario/DoD records and enforce test/acceptance gates independently of bounded meetings. Keep failed integration out of done; await and verify delivery artifacts/PR creation. |

For a practical Wingman prototype, Claw-Empire can supply a large fraction of the visible organization and task engine. For the full purpose, it is an architectural reference and adaptation base, not a verified drop-in implementation. The most valuable portions are its persistent organizational records, connected approval flows and workflow-to-execution bridges. The largest gaps concern the meaning of an enduring agent, genuine product discovery, distributed execution and executive truthfulness.
