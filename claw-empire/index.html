Claw-Empire assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/GreenSheep01201/claw-empire

Local checkout: researchs/claw-empire/repo. Inspected revision: 66a24ea7df2435ef897c48c147deb7ec572c01c2. Package version: 2.0.4 (climpire). Baseline: Wingman purpose.

Fit verdict: Claw-Empire is a substantial candidate for Wingman's organizational control plane. It implements real project records, configurable agent employees, departmental delegation, a task board, CEO messaging, Telegram ingress and replies, planning/review meetings, isolated coding runs and workflow recovery. Its central abstraction is a company of durable employee records executing task-scoped jobs. It does not establish Wingman's full model of persistent, independently conversational Codex colleagues, per-project ProductMaster/TechMaster pairs, arbitrary collaboration rooms, a research-led product discovery cycle, or execution shared across the Mac and Endeavour.

The office simulation sits above a substantial execution and coordination implementation. Some speech and status text comes from server templates or one-shot persona calls. That text does not establish an agent's reasoning about its work.

The source review identified four material integration risks:

  • A merge failure can still lead to done.
  • Pause/resume does not establish retention of uncommitted work.
  • Native Telegram $ intake lacks project metadata that the default path requires.
  • The five-minute progress timer reports smooth progress after checking only task status.

These are source findings. The assessment did not reproduce them at runtime.

Detailed companion: Agent lifecycle and one end-to-end request.

1. Architecture and actual execution model

server/index.ts imports the server main module. The package starts it through tsx. Main initializes the database, schema, migrations and seeds before wiring workflow helpers, Express routes and lifecycle services into one runtime context. SQLite is the durable source of organizational state; WebSocket broadcasts update the React application. Source: entry point, line 1; server-main.ts, lines 46–59 and 122–129; database runtime, lines 58–105, enables WAL, foreign keys and busy timeout. This is a single server control plane with local execution and process/session/worktree maps, rather than a distributed agent service.

The base schema is more informative than the simulation framing:

  • agents, lines 37–61: employee identity, department, workflow pack, seniority, planning-leader flag, provider/model/account, personality, status, current task and accumulated statistics.
  • projects, lines 63–72: named persistent project, source path, core goal and default workflow pack. Later migrations extend project assignment and GitHub fields.
  • tasks, lines 88–107: project, department, assignee, status, priority, task type, output format, execution path and result.
  • messages, lines 133–144: sender, receiver (agent, department, all), content, message type and optional task link.
  • meeting_minutes and entries, lines 165–188: task-specific planning/review conversations with explicit speakers and sequence.
  • subtasks, lines 258–270: assignments, blocked reason and CLI tool correlation; migrations add delegated-task/department relationships.
  • Report archives and review-decision records, lines 272 onward: durable summaries and decision history.

This is principally ticket coordination with orchestrated chat, rather than a free-form agent society whose members independently choose whom to message. handleTaskDelegation creates and routes task work; planned meetings collect additions. The subtask dispatcher turns departmental work into delegated execution jobs. A meeting speaker is selected by the server, given a prompt containing the transcript and called through runAgentOneShot. The speaker is not necessarily an already-running worker being interrupted to participate. Source: delegation, lines 125–209 and 400–474; planned meeting, lines 213–333.

For coding, startTaskExecutionForAgent updates task and employee status, creates an isolated Git worktree, assembles context and invokes the chosen provider. CLI providers are separate local child processes with their own current directory, output stream and timeout. This is genuine independent execution, not merely labels on one model's output. However, the employee row is the durable identity. The process is a run. The UUID called an execution session is held in an in-memory map. Codex starts through codex ... exec --json. The inspected argument builder does not attach a native Codex resume/thread ID. Continuity is reconstructed through stored messages, logs, prior result tails and review notes. Sources: execution start, lines 76–92, 129–247; CLI runtime, lines 220–256; session tools, lines 30–67; arguments, lines 48–108.

Provider choice materially changes capability. The generic api path constructs a streamed text request to Anthropic, Google or a chat-completions endpoint. It supplies a project path in text but declares no filesystem or command tools and contains no tool-execution loop in that implementation. A configured API employee is therefore not automatically equivalent to a Codex coding worker. See API provider tools, lines 119–241. CLI support, OAuth-backed support and arbitrary API text generation should be assessed separately when selecting Wingman's execution backend.

3. Agent definition, management and lifecycle findings

An employee profile is a combination of stable database identity, department shared prompt, rank, personality, workflow pack, provider/model/account and current assignment. This is stronger than a reusable prompt file: it has persisted relationships and server-managed state. It is weaker than an always-present conversational colleague: execution and participation are recreated as jobs and one-shot calls.

Creation writes a UUID-backed employee record; configuration edits affect subsequent execution. A planning-lead flag can nominate the pack's coordinator. Task routing selects leaders/subordinates from department and project scope. The system can show provider-internal subagents by interpreting CLI output, but those subtasks are not automatically equivalent to persistent employee profiles in the directory. The CLI parser correlates Claude Task and Codex spawn_agent/close_agent events to tracker subtasks. See CLI runtime, lines 41–155.

Execution uses a separate worktree and process. Rank/personality/department constraints are prompt-level guidance; tool permissions largely come from the provider invocation. The Codex coding invocation enables multi-agent support and uses --yolo; Claude uses --dangerously-skip-permissions. Worktrees reduce accidental source collisions but are not OS or network sandboxes. Meeting calls request noTools, and CLI one-shot code also observes tool signals to abort violations. Generic API calls are text-generation requests. These differences must be preserved in any Wingman adapter: a common employee UI should not imply uniform execution capabilities or isolation.

4. Coordination, project continuity and human decisions

Claw-Empire combines three mechanisms that Wingman also needs: a shared tracker, readable organizational conversation and a human escalation surface. Its design is valuable because those mechanisms are connected by task IDs and project references rather than being unrelated widgets.

The tracker is authoritative workflow state. Assignment is not only a chat message. It changes task and employee fields, creates execution work and emits updates. Delegated tasks link back to source tasks and subtasks. Parent review waits for consolidation and handles child jobs in the same review/merge process. One caution for Wingman is that external-department queues are sequential by design. This gives an understandable order and avoids uncoordinated repeated dispatch, but BackendCoder/FrontendCoder/TestMaster parallelism would need a more explicit dependency graph and capacity scheduler.

The chat provides direct CEO→agent messages, department/broadcast messages and meeting transcripts. It does not provide explicit arbitrary room objects with membership and project scoping in the inspected message schema. Meeting conversations are server-orchestrated turns: prompt construction, selected speakers, transcript, status changes and action-item collection. That is useful coordination, but it differs from workers independently using a shared room to settle API contracts while continuing separate coding conversations.

The decision inbox is notably practical. Pending project/review/timeout choices become messenger notices. The bridge reserves sends to suppress duplicates, associates decisions with channel targets, accepts numeric/explicit replies and applies the selected option to workflow state. This is a strong pattern for Butler carrying questions and returning answers. Its native decision kinds are operational workflow choices, however, not a general product discovery question model. Multiple domain-clarification threads with durable ownership, answers and resulting product decisions would need expansion.

Continuity also deserves scrutiny: getRecentConversationContext pulls ten messages for an agent, including organization broadcasts. The continuation brief clips result/memo/review excerpts. This is a useful bounded retrieval mechanism, but the same employee working across products can receive broadly agent-scoped conversation material. Wingman should make project ID, task ID, native session ID and question ownership explicit rather than relying on a prompt instruction not to mix projects.

A concrete implemented request path is ordinary Telegram text → mapped employee → project binding → task → optional leader planning → provider run → review/decision → delivery attempt. The receiver forwards allowed human text to the authenticated inbox (receiver, 306–347). Inbox resolves the session employee and offers decision replies before normal direct chat (inbox, 506–540 and 690–738). Direct chat asks existing/new when task intent lacks a project, then either delegates a departmental leader's request or directly creates/runs a specialist task (binding, 492–537; task flow, 51–98 and 167–193). Planning converts transcript actions into memo/subtasks; execution streams output; completion moves to review and decision replies apply concrete workflow options. The companion trace follows those transitions and their failure paths in detail. This trace describes source behavior under its configuration prerequisites, not an exercised end-to-end integration.

Two acceptance boundaries are particularly material. First, source-wide searches found requireTestEvidence/enforceTests only as pack declarations, while QA JSON is persisted/exposed by configuration routes. It is not evidence of an enforced test-result validator. Second, the merge-failure branch alerts the CEO but does not return before the unconditional done update (finalization, 538–608). Wingman must make test evidence, successful integration and human acceptance separate states rather than trusting this terminal label.

5. Major additional capabilities beyond Wingman's described scope

A configurable production organization for multiple output domains

Workflow packs cover development, novel writing, structured reports, video production, web research reports and roleplay. They carry input schemas, prompt presets, output templates, routing keywords, QA declarations and cost profiles; office-pack department prompts and agent scopes change the operating team. This extends the product from a software organization into a general production company. Source: pack definitions, lines 1–27 and 35–175; office-pack hydration.

For Wingman this could support ProductMaster research or a content/launch team as a later product expansion. It also means copying the entire orchestration policy imports assumptions from non-software workflows. Some pack fields are configuration declarations rather than independently proven validators. They must be traced to execution enforcement individually.

Actual video production and artifact-constrained handoff

The video pack is not merely a script-writing persona. It separates planning/documentation from final rendering, delegates [VIDEO_FINAL_RENDER], discovers and synchronizes output files, and blocks review/merge when the video is missing or nonempty-file/render-engine evidence is insufficient. The code specifically checks Remotion evidence. Source: subtask dispatcher, lines 348–393; run completion, lines 114–235; review finalization, lines 404–515.

This is a distinct deliverable-production capability absent from Wingman's software-only purpose. More generally, its strongest reusable idea is making artifact existence and execution provenance gate completion. The current checks are specialized and do not prove that the video's content meets user intent; adapting the pattern to Wingman would require software artifact, integration-test and acceptance evidence.

Structured report and presentation production pipeline

Report routing can create a design checkpoint, wait for it, regenerate a final PPT and complete report work through its own path. This is a multi-stage artifact workflow rather than a minor export button. Source: run completion, lines 412–480; report workflow tools. For Wingman it could become research/decision-brief delivery, but report-specific automatic completion and skipped reviews should not leak into code acceptance policy.

Multi-provider employee and account operating layer

Per-agent CLI/model/reasoning/OAuth choices, encrypted provider records, account status and usage views make the organization heterogeneous. This can distribute suitable work across toolchains or accounts. Wingman currently defines Codex employees, so this is a major expansion in execution/provider management. Integration needs explicit capability negotiation: the generic API text path cannot replace a filesystem-enabled Codex worker simply by choosing a model name. Sources: agent detail configuration, lines 60–109 and 213 onward; schema, lines 205–255; API path, lines 119–241.

Provider-targeted skill acquisition and reuse

The Skills Library is an operating capability rather than merely a prompt catalog. A learn job maps selected providers to agents and runs the skills CLI installer, recording queued/running/completed history; custom skill uploads persist content and per-provider success records. Later execution prompts retrieve recent successful provider-matched skills and instruct the worker to prioritize them alongside global/runtime skills and MCP tools. See learning job, 276–323; custom upload, 41–109; prompt retrieval/policy, 83–128. This could grow Wingman's specialist capabilities without changing every role prompt. Integration must distinguish installed executable/provider skills from a DB success label or skill-name hint; uploaded text recorded as succeeded is not proof every provider loads its full content.

Automated repository bootstrap and GitHub delivery

The execution layer can initialize a non-Git project, add/commit its contents and create task worktrees; GitHub-linked projects can merge into dev, push and create/update a PR to main. See bootstrap, 28–115; GitHub merge/PR, 204–310. This turns organizational work into repository artifacts beyond Wingman's currently described coordination interface. It also imports consequential delivery policy: automatic commits, branch checkout/push, credential use and asynchronously requested PR creation. Wingman needs an explicit repository/delivery contract and should not infer a successful PR or integrated release from done.

6. Distinctive mechanisms and innovation assessment

These are grounded mechanisms that are distinctive in this checkout. This assessment makes no claim of industry-first invention.

A meeting is a workflow transition with a persistent transcript. Planned meetings gather contributions, collect action items, append project memos and invoke the execution callback. Review meetings take the consolidated result through remediation, synthesis and decision. The important mechanism is conversion of dialogue into state and work, not animated characters taking turns. This could give Wingman inspectable ProductMaster/TechMaster discussions whose decisions create tickets. The limit is that meetings are orchestrated one-shot turns with bounded context. They are not proof of persistent peers carrying out deep research together. Planned meeting, 213–333.

Bounded disagreement is an explicit execution policy. getReviewRoundMode maps round one to parallel remediation, round two to merge synthesis and round three to final decision. Review prompts constrain later rounds from creating endless new remediation and ask for residual-risk documentation. This is an operational answer to endless agent debate, with caps also visible in database runtime configuration. Sources: session review tools, lines 98–139; review consensus, lines 310–445; runtime guardrails, lines 22–43. For Wingman, retain bounded discussion but preserve a separate invariant that unmet product acceptance criteria remain unmet regardless of round count.

Provider subagents become visible tracker objects. The CLI stream parser recognizes Claude and Codex collaboration events and creates/completes corresponding subtasks. This bridges a provider's internal agent behavior to an organizational tracker, reducing opaque fan-out. It is an attractive observability adapter for Wingman. Correlation is provider-format-dependent and some mappings are in memory. A detected nested task is not automatically a managed employee with its own enduring workspace. Parser, 41–155. It parses each output chunk line-by-line without a visible partial-line buffer in this function, so robust correlation across chunk boundaries is not established.

A messenger decision is tied to concrete workflow identity. The decision bridge handles channel routing, pending-choice selection, deduplicated notices and applying the reply. This is more robust than forwarding an arbitrary chat reply to whichever model last spoke. It is directly relevant to concurrent Butler questions, though Wingman should extend identity to durable product questions and avoid ambiguous latest-decision behavior where several independent decisions share one channel. Reply application, 403–491, explicitly chooses the latest routed decision when no decision token is present.

Recovery distinguishes process liveness from presentation state. The watchdog checks active process handles, OS PID liveness, task-log recency and terminal-file modification times before recovering an orphan. This explicitly addresses backend restart and stale employee/task state. It is a substantial operational mechanism, not a timer that blindly restarts everything. It still recovers workflow by logs/state and does not reconnect to all lost native agent sessions. Source: lifecycle, lines 215–348.

Domain-specific evidence gates show a path toward outcome-aware autonomy. Video finalization checks both a produced file and execution evidence, whereas generic coding initially uses process exit and leader review. That contrast is useful: Wingman could generalize the artifact gate idea into product-specific delivery contracts, rather than treating agent completion text as product success. Artifact/engine gates, 344–515. These checks establish file/log conditions, not semantic correctness of the produced video.

7. What Wingman could reuse and what remains

Layer Reuse/adaptation judgment
Project and task control plane Reuse the project/core-goal/task/subtask schema, linked reports/minutes and state transitions as a starting model. Add product-specification versions and explicit leadership assignments.
Agent directory and organization UI Adapt generic employee creation, department prompts, assignments and provider configuration. Replace four-rank assumptions where role profiles need arbitrary responsibilities.
Telegram and human decisions Reuse receiver offset/idempotency handling, channel routing and choice application patterns. Bind Butler requests/questions to durable project and conversation IDs.
Coding execution Reuse worktree/output adapter concepts after fixing pause/recreation preservation and failure cleanup policy. Implement native Codex thread persistence, live steering, fork/compact/archive and capability-aware controls.
Supervision Reuse process/log-aware recovery and pending dispatch reconciliation. Add an actual portfolio supervisor reasoning over stale work, blockers, outstanding questions and definitions of done.
Chat and collaboration Retain messages/minutes as evidence but add project-scoped rooms, participant membership and agent-accessible collaboration tools, including cross-host workers.
Executive view Build evidence-derived individual current/recent/next/blocker summaries and linked timelines; source them from actual task/tool/test/decision events.
Distributed execution Build host registry, remote runners, placement, native-session routing, authentication and cross-host project/artifact access. Current local spawn and model HTTP integrations do not supply this.
Acceptance Introduce maintained product scope/spec/scenario/DoD records and enforce test/acceptance gates independently of bounded meetings. Keep failed integration out of done; await and verify delivery artifacts/PR creation.

For a practical Wingman prototype, Claw-Empire can supply a large fraction of the visible organization and task engine. For the full purpose, it is an architectural reference and adaptation base, not a verified drop-in implementation. The most valuable portions are its persistent organizational records, connected approval flows and workflow-to-execution bridges. The largest gaps concern the meaning of an enduring agent, genuine product discovery, distributed execution and executive truthfulness.

8. Verification scope and limits

This is a static code assessment of the pinned local checkout. No dependency installation, application launch, provider login, external API call, Telegram message, coding job, merge, build or test suite was performed. Source files remained unchanged. Git status was checked before completion. Runtime success, production reliability, external service availability and missing submodule behavior are not established.

The implementation review covered these areas:

  • Schema, runtime startup, employee CRUD, process creation, and task controls.
  • Telegram receipt, session routing, chat/project binding, and runtime replies.
  • Task and cross-department delegation, planning, reviews, and decisions.
  • Worktree creation, CLI/API execution, context reconstruction, and orphan recovery.
  • Terminal, detail, and project UI.

Searches covered DIRECTIVES, SCOPES, definition of done, acceptance, discovery, and clarification. They also covered host/SSH/remote execution and individual timelines. The review traced matches through the relevant control, execution, and UI paths. Agents can write arbitrary files when prompted. That possibility does not establish a built-in product workflow.

Relevant tests were inspected as evidence of intended contracts, not reported as passing. Control tests mock startup/process effects, and Telegram tests mock HTTP. These do not prove full provider or messenger integration:

  • Execution-control tests, lines 364, 416, 448 and 493: pause interruption, cancellation cleanup, same-session resume and pause→inject→resume sequence.
  • Telegram receiver tests, lines 51, 143 and 216: allowed inbound chat forwarding/offset storage, bot suppression and multiple token routing.

  • Worktree lifecycle tests, lines 38–85: existing branch reuse and occupied-branch suffix fallback.
  • Leader selection tests, lines 134–184: workflow-pack scope and manual-assignment meeting leadership.
  • Video review gate tests, lines 38 and 108: blocking approval without an artifact or without Remotion evidence.

A material interpretation risk is accepting simulated office behavior as execution evidence. rotateBreaks changes idle/break status probabilistically (lifecycle, lines 110–129). The five-minute reporter claims smooth progress based only on status (progress notifications, lines 7–38). Claw-Empire: agent lifecycle and request trace

Companion to the assessment. Static inspection of commit 66a24ea7df2435ef897c48c147deb7ec572c01c2, 2026-11-05. Paths below are relative to this chapter; ranges identify the inspected implementation. No application, provider, Telegram integration or test was run.

What an agent actually is

The durable object is the SQLite agents row. It holds a UUID, names, department, one of four ranks, workflow pack, planning-leader flag, provider/account/model, personality, status, current task and statistics. There is no native Codex conversation identifier in that row. A department supplies another prompt and organizational grouping. A workflow pack supplies domain guidance and routing. These compose a reusable employee profile, rather than defining a daemon that continually reasons. See base schema, lines 7–107.

Three other objects must remain distinct. A task is a durable work item with assignee, project, description, status and result. A task execution session is an application UUID in an in-memory map, reused only while its task/agent/provider combination matches. A run is a new local process or HTTP request with a prompt and output log. A meeting contribution is another one-shot invocation using an employee's persona. Provider-internal Codex/Claude subagents can be projected into tracker subtasks, but are not thereby employee rows. See session tools, 30–67; CLI runtime, 41–155 and 220–256; one-shot runner, 81–103.

Definition, creation and retirement

POST /api/agents validates the name, pack and department, chooses a permitted rank/provider and inserts a new UUID. It broadcasts agent_created for the generic UI. It does not start a process. PATCH /api/agents/:id updates the profile, validates provider-specific account/model options and handles planning-leader conflicts. Those settings influence later prompts/runs; editing personality does not rewrite a currently running provider conversation. See agent CRUD, 293–409, 447–585 and 594–615.

Creation is human/control-plane CRUD, not evidence that a ProjectMaster autonomously hires a durable employee. Runtime fan-out through spawn_agent is a separate provider mechanism. Multiple rows can share a department and model, so several backend specialists can exist, although their domain role comes from department/personality rather than an unconstrained role type.

Deletion refuses a working employee, nulls task/subtask/minute/report/planner references transactionally, then deletes the row and broadcasts it. There is no first-class archived agent identity or recoverable retirement lifecycle in this path. See deletion, 416–440.

Assignment, routing and concurrency

Delegation resolves project metadata and workflow pack, constrains candidate agents by project/pack, chooses a subordinate from the leader's department and creates the planned task. The task description contains CEO instruction, project core goal and round goal. After planning, callbacks reassign the task to the subordinate and start execution, with leader self-execution as fallback. Acknowledgement/delegation speech is partly server-built template text with randomized delays. It is not all autonomous reasoning. See delegation, 125–222 and 390–478.

The explicit task-run route rejects another live process on the same task and rejects an employee whose current working task still has an active process. Different task IDs and employees can have distinct processes and worktrees across projects. This is local concurrency, with no host-placement or remote-runner protocol. Foreign-department subtasks are intentionally grouped into queues and dispatched one department batch at a time; origin-team work can defer that dispatch until review. See task-run checks, 87–125 and 271–283; department dispatcher, 280–345.

Starting a coding run and tool authority

startTaskExecutionForAgent sets task in_progress and employee working, obtains an application session, and loads pending interruption prompts. It creates an isolated Git worktree; failure rolls status back to pending and releases the employee. The prompt combines recent changes, task/pack, continuation brief, recent conversation, employee/personality, department constraint/shared prompt and injected direction. Provider routing then chooses CLI, generic API or OAuth HTTP execution. See execution start, 76–92, 129–247 and 249–307.

For CLI workers the backend writes a temporary prompt file, inherits the server environment with selected CLI-related adjustments, starts a local detached child in the worktree and sends the prompt through stdin. Output goes to a file, WebSocket events and subtask parsing. Idle/hard timeouts kill the process tree. The worktree is a source isolation mechanism, not a separate OS user/container or a filesystem/network sandbox. See CLI execution, 220–368.

Tool authority is provider dependent. Codex coding uses --enable multi_agent --yolo exec --json; Claude uses --dangerously-skip-permissions; Gemini coding uses --yolo. Meeting calls can request noTools, causing read-only/plan/no-tool arguments where supported. The one-shot runner also detects tool-like output and aborts a violation. Rank and department constraints are instructions, not independent authorization boundaries. See argument construction, 48–108; one-shot safeguards, 40–46 and 126–137.

The generic API adapter sends a streamed user/system text request to Anthropic, Google or a chat-completions endpoint, then consumes the stream. It declares no filesystem/shell tools or tool-execution loop. A project path mentioned in its system message does not make that employee a coding process. See API adapter, 119–241. OAuth-backed implementations are separate adapters; their capability must be evaluated individually rather than inferred from the common employee selector.

Persistence, continuity and interruption

SQLite preserves employee/task/message/minute/revision/report records, while logs preserve output. On a later run, getRecentConversationContext retrieves ten agent-related messages, including broadcasts, and getTaskContinuationContext builds bounded excerpts of result tail, review notes, minutes and project memo. This is useful retrieval but is neither full conversation history nor strictly project-scoped retrieval. See context tools, 19–50 and 67–164.

The application reuses a session UUID in memory and prints it into the prompt. The Codex argument builder passes neither a native thread ID nor resume. A resumed task starts another exec. Session preservation therefore means workflow continuity. It does not establish native Codex conversation continuity.

Restart loses the in-memory session map. Durable interruption rows use that application UUID. These paths do not establish restart-safe delivery of an old pending instruction. See session map, 30–67; injection schema, 154–163; and CLI arguments, 56–64.

Pause signals SIGINT (or abort for HTTP), sets pending and releases the employee while preserving application workflow/session state. Injection requires pending status, session proof and a control token. It sanitizes and durably queues the instruction. Resume validates status, rejects an active process and schedules a fresh start for the assigned online employee. The next start incorporates and consumes injections. Cancel kills rather than interrupts, rolls back worktree changes, blocks linked delegated subtasks and clears workflow/session state. Late completion callbacks are ignored for stopped/deleted/non-running tasks. See execution controls, 139–206, 229–259, 303–405 and 467–529; late-result handling, 56–93.

Each restarted startTaskExecutionForAgent calls createWorktree. Its candidate loop recursively removes an existing worktree directory before re-adding the branch. Committed branch state may survive. Paused uncommitted or untracked files can be lost. The control-route tests mock startup. They do not establish filesystem preservation across the full pause/resume cycle. See restart call, 129–130; candidate cleanup, 162–188; and resume control, 514–529.

Scheduling, supervision, failure and recovery

There is no inspected enduring employee loop waking to reason about its portfolio. The server schedules workflow callbacks and mechanical sweeps: startup interrupted-workflow repair, orphan tasks/employees and pending subtask dispatch. Defaults include a ten-minute orphan grace, thirty-second orphan sweep and fifteen-second delegation sweep. See runtime constants, 44–55; lifecycle scheduling, 455–461.

Recovery consults process handles/PID liveness, recent DB logs and terminal-file modification time before treating work as orphaned. It can replay a recorded successful/failed completion or return unknown orphan work to inbox, release the employee and notify the CEO. Startup also reconciles delegated work and duplicate review meetings. It repairs organization state. It does not reconnect a lost native agent conversation. See recovery, 170–361.

Ordinary unsuccessful execution resets to inbox, cleans the failed worktree, reports an error and allows departmental queues to continue. The failure notice requests reassignment/revision/retry. This is not a demonstrated general autonomous retry policy. Bounded meeting retries and workflow remediation are separate mechanisms. Cleanup force-removes worktrees and deletes their branches, so intermediate failed code can be lost while logs survive. See failure handling, 650–752; cleanup, 234–268.

Completion, review and delivery

Ordinary exit-zero work moves to review; child work can wait for parent consolidation. Meetings produce persisted leader feedback and remediation. Review policy explicitly moves through remediation, synthesis and final decision, with later prompts disallowing new remediation and offering approval with residual risk. This bounds debate but does not enforce satisfaction of a product definition of done. See successful completion, 485–567; review mode, 98–139; review prompts, 310–443.

Finalization attempts a local merge or GitHub development-branch/PR workflow. Successful cleanup precedes the done record and session closure. The merge-failure branch notifies the CEO that manual resolution is needed. It then reaches the same done update. Done therefore does not establish successful integration.

The GitHub PR request also runs asynchronously after push. Finalization does not await its success as the synchronous merge result. See finalization, 526–612, and GitHub delivery, 204–310.

The video pack has stronger concrete gates: missing/empty video or missing/invalid Remotion execution evidence holds approval. Report tasks have separate design-checkpoint/PPT completion paths which can skip review. These are distinct domain policies, not a universal software acceptance contract. See video finalization, 344–515; report branches, 412–480.

Trace: an ordinary Telegram coding request

This traces an implemented code path, not an observed successful run. Assume a configured token, allowed chat, inbox secret, session-to-agent mapping and suitable employee/provider.

  1. The receiver polls Telegram, rejects bot/disallowed/empty updates and posts source, message ID, author, chat and text to the local inbox with the shared-secret header. Successful forwarding advances persisted offsets. See receiver, 306–350 and 408–468.
  2. Inbox authenticates the shared secret, resolves the mapped employee for ordinary text and rejects unconfigured session routing. It inserts an idempotent message, first offers a reply to the workflow decision bridge, and otherwise calls scheduleAgentReply with messenger routing metadata. See inbox, 407–458, 506–540, 600–612 and 690–738.
  3. Direct chat classifies task intent and manages project binding. When needed it asks existing/new, lists recent projects or requests new name/path, and later hands off through its task flow. Pending binding is an in-memory map keyed by employee, expiring after an hour; two independent chat/project dialogues for the same employee are not separate durable conversations. See direct chat, 42–55, 79–224 and 492–537; task flow, 51–98 and 167–193. To follow the planning branch below, assume the mapped employee is a departmental team leader. A specialist can receive a direct task without that leader meeting.
  4. A delegated task records project/core/round goals and the messenger destination. A planning meeting calls one-shot leader personas with a transcript, collects executable action items, appends a project memo and invokes its approval callback. Planning is explicitly told not to block kickoff. See delegation, 141–219 and 390–445; planning meeting, 213–333.
  5. The subordinate starts a worktree-scoped provider run; its stream updates terminal logs and can create subtasks from provider events. Other departments receive batched delegated tasks and completion callbacks. Shared DB state and task IDs coordinate them, rather than arbitrary project rooms. See execution, 129–307; subtask parsing, 44–155 and 333–350; dispatch, 294–345.
  6. Exit success moves ordinary work to review; failure returns it to inbox. Review/timeout choices are exposed through the decision inbox and messenger. A numeric reply resolves the latest decision for that route unless an explicit decision token identifies another; validated options are applied to workflow state. This is a concrete answer-routing mechanism, but latest-choice fallback can be ambiguous when several questions share a channel. See completion, 485–567 and 650–752; decision reply bridge, 403–491.
  7. Approved work reaches merge/report/done as described above. The task's stored messenger route enables follow-up notification. This does not establish human acceptance against maintained scope/scenarios, and merge failure can still reach done.

The $ directive route requires an explicit project ID by default. Without it, the route returns HTTP 428. The native Telegram receiver does not include a project ID in its forwarded body. The source therefore does not establish default delegation for a raw $... received through that path.

Documented OpenClaw orchestration supplies project-binding metadata. Ordinary mapped chat can ask binding questions. These are separate intake paths. See default policy, 9–10; directive requirement, 490–503; and forwarded fields, 335–347.
