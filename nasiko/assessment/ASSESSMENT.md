# Nasiko assessment against Wingman

## Identity and fit verdict

- **Upstream:** https://github.com/Nasiko-Labs/nasiko
- **Checkout:** `research/nasiko/repo`
- **Assessed commit:** `10a085818d585fcc487487df89d09c87f74bd577`
- **Assessment date:** 2026-11-05.
- **Scope:** the checked-out open-source edition, not the enterprise implementation referenced by extension interfaces and comments. Apache-2.0 license: [LICENSE](../repo/LICENSE).

**Nasiko is a useful infrastructure candidate underneath Wingman, but a poor direct replacement for Wingman's product.** It hosts separately executing A2A agents, registers and observes existing coding harnesses, controls model/tool access, stores conversations and agent state, and executes reusable multi-agent workflows. Its strongest implemented concerns are deployment, authorization, attribution, cost optimization and human-in-the-loop continuation. It does not supply Wingman's portfolio intake, standing product/technical leadership, product discovery process, shared engineering tickets, collaboration rooms or supervisory organization.

Two distinctions materially change the fit. A hosted agent is a deployable service with a durable catalog identity. A recorded Codex/Claude/OpenCode/Cursor session is activity reported by an independently operated harness, not a process Nasiko created and now supervises. Also, the open-source runtime is Docker on one local daemon, with one replica per deployed agent. Kubernetes, organizational context/memory, org-aware controls and richer scaling references do not establish those capabilities in this checkout. See [main.rs](../repo/server/src/main.rs), lines 106–124; [agent_scaling.rs](../repo/server/src/agent_scaling.rs), lines 1–8 and 66–108; [prompt_context.rs](../repo/server/src/prompt_context.rs), lines 75–87.

## Architecture and execution model

The executable is a Rust/Tokio/Axum control plane. Startup loads configuration, connects PostgreSQL, constructs authentication and S3-compatible OCI storage, selects Docker or the explicit simulated runtime, runs migrations, initializes shared state and serves the embedded web UI and API. The UI build is embedded by `rust-embed`. It is not a separately required public gateway. [main.rs](../repo/server/src/main.rs), lines 17–19 and 60–130. [lib.rs](../repo/server/src/lib.rs), lines 317–384 and 413–433, mounts catalog, chat, workflow, observability, HITL, MCP, state, agent proxy and LLM router routes.

There are three execution paths worth separating:

1. **A2A chat orchestration.** The dispatcher identifies the user, resolves a named/UUID target or the orchestrator, selects stored conversation context, and streams A2A events. A direct target gets a guarded HTTP call. The routed chat implementation enumerates active, accessible agents and constructs a ReAct orchestrator with each agent exposed as an A2A tool. The model reasons, delegates, consumes responses and eventually produces text. This is a per-request orchestration loop, not a persistent ProjectMaster agent. [a2a_dispatch.rs](../repo/server/src/router/a2a_dispatch.rs), lines 189–290, 467–565 and 786–824; [react_loop.rs](../repo/react-agent/src/react_loop.rs), lines 263–286.
2. **Reusable Multi-Agent Flows (MAF).** PostgreSQL stores workflow definitions and execution snapshots; Redis Streams carries execution jobs. A background worker consumes one job at a time within its loop. Each workflow is a sequence of assigned agent steps, with LLM-generated prompts, extraction goals and final synthesis. Successes are persisted and reused across ordinary retries. This is durable workflow execution, not a ticket board or general dependency DAG. The worker starts only when `OPENAI_API_KEY` is configured; otherwise the API can accept runs whose Redis jobs remain unprocessed. [lib.rs](../repo/server/src/lib.rs), lines 172–216. [maf/types.rs](../repo/orchestrator/src/maf/types.rs), lines 5–25; [maf/worker.rs](../repo/orchestrator/src/maf/worker.rs), lines 23–26 and 85–125; [maf/executor.rs](../repo/orchestrator/src/maf/executor.rs), lines 297–329 and 385–473.
3. **Existing coding harness reporting/routing.** CLI adapters discover supported local tools and install reporting hooks; completed turns are queued and sent to the control plane. Registration and reporting preserve the harness's own operating interface. They do not establish central dispatch, stop, fork or live steering of that harness. Separate routing configuration redirects its LLM traffic through Nasiko. [integration/mod.rs](../repo/cli/src/commands/integration/mod.rs), lines 1–9 and 81–149; [coding_agent_telemetry.rs](../repo/server/src/coding_agent_telemetry.rs), lines 39–54 and 90–126.

The semantic agent selector is another component, used for routing decisions such as assigning unspecified MAF steps. It fetches authorized agents and context, optionally shortlists by embeddings, reranks with conversation context and asks an LLM to select. Provider/parsing failures can fall back to the first candidate. An explicit policy refusal is propagated. This selector should not be confused with either the ReAct delegation loop or the LLM **model** router. [engine.rs](../repo/orchestrator/src/engine.rs), lines 127–153, 166–243 and 245–299.

Persistence is deliberately split. PostgreSQL holds catalog identities, grants, versions/builds, chat rows, workflow snapshots, HITL decisions and encrypted agent task/KV rows. Redis holds flow counters, routing caches and workflow queue state. S3 stores OCI blobs and uploaded artifacts. Optional OTel/Tempo/Loki paths add traces, logs and usage inspection. The main process also launches build recovery, HITL delivery, telemetry materialization and state cleanup workers: [state.rs](../repo/server/src/state.rs), lines 342–459. This creates meaningful operational machinery and an equally meaningful deployment burden compared with Wingman's proposed lightweight shared tracker and Markdown knowledge.

## Agent definition and lifecycle in detail

### What the identities actually mean

The durable **agent** is a catalog row containing UUID, owner, endpoint, version, protocol metadata, capabilities and skills. A deployed image is one implementation of that identity. An A2A **task** is a single execution/continuation addressed through that service. A **context/session** groups conversation and traces. A MAF **workflow** is a reusable ordered definition, and a MAF **execution** is one durable run. A ReAct orchestrator is constructed for a turn and uses its own model to call registered agents as tools. None of these types intrinsically represents a permanently employed ProductMaster or a Codex conversation with a role and product assignment. [catalog/models.rs](../repo/server/src/catalog/models.rs), lines 8–50; [chat/models.rs](../repo/server/src/chat/models.rs), lines 15–25; [maf/types.rs](../repo/orchestrator/src/maf/types.rs), lines 5–25 and 98–124.

### Definition, creation and deployment

The CLI reads `AgentCard.json` and a buildable image/source project. Its `.nasiko/agent.json` binding remembers the catalog UUID. A stale/missing binding falls back to lookup by name. The deploy path then creates or updates the registered agent and deploys/restarts the workload. This allows code/version replacement while retaining identity and history. It does not clone a conversation. [deploy.rs](../repo/cli/src/commands/deploy.rs), lines 14–24, 102–130 and 163–196.

Source uploads, updates and rollbacks can enter a durable build queue. The worker polls every five seconds and wakes on notifications, runs a configured number of jobs concurrently and serializes jobs targeting the same agent/connector. It tracks attempts, recovers abandoned work and isolates panics. These jobs build and deploy agents, not software-product tickets assigned to autonomous engineers. [build_worker.rs](../repo/server/src/agents/build_worker.rs), lines 40–163 and 257–339. The live backend maps an agent UUID to `nasiko-agent-{id}` on the local Docker daemon, discovers its ephemeral endpoint, and applies CPU/memory limits. Docker explicitly clamps replicas above one: [docker/mod.rs](../repo/runtime/src/docker/mod.rs), lines 108–138 and 475–512.

Registering a coding harness is a different lifecycle. `agents install` registers/fetches an agent record and installs native hooks. It does not provision Codex itself. `agents uninstall` removes local reporting and preserves the remote agent/history. A harness's own subagents are stored as linked child sessions under the same harness agent, not automatically separate catalog employees. [integration/mod.rs](../repo/cli/src/commands/integration/mod.rs), lines 81–144; [coding_agent_subagents.rs](../repo/server/src/coding_agent_subagents.rs), lines 1–43.

### Execution, tools and permissions

The bundled Rust coding agent demonstrates genuine tool execution: it constructs model messages, exposes read/list/search/write/edit/command/test tools and iterates up to twelve model rounds. Its private tools execute against a `Sandbox` trait. Today only `LocalSandbox` is implemented; `SANDBOX_MODE=remote` returns an error. Its file-path helper rejects lexical traversal, but shell execution is simply `sh -c` in the workspace directory. A changed current directory is not an OS-level shell sandbox; deployment/container policy must supply the stronger boundary. [coding main](../repo/agents/coding/src/main.rs), lines 15–27 and 302–448; [sandbox selection](../repo/agents/coding/src/sandbox/mod.rs), lines 65–80; [local implementation](../repo/agents/coding/src/sandbox/local.rs), lines 31–59 and 180–211.

At the platform layer, all deploy paths compose secrets and caller environment with platform-generated state, MCP and model-routing credentials. Credential keys override user-supplied values. State access has a separate scoped token; missing configuration can leave an agent in memory mode. MCP connectors have reachability/permission filtering; tool approvals are represented as durable HITL requests. Runtime hardening is a flag with real effects: read-only root, optional per-agent persistent mount, capability dropping and no-new-privileges where enabled. An ordinary unhardened deployment does not inherit those settings merely because the agent is called “sandboxed.” [deploy_env.rs](../repo/server/src/agents/deploy_env.rs), lines 62–120 and 129–156; [MCP authorizer](../repo/mcp-gateway/src/authorizer.rs), lines 19–65; [Docker host config](../repo/runtime/src/docker/mod.rs), lines 439–537.

### Routing and concurrency

Named and UUID direct targets are resolved before authorization. Routed chat enumerates agents visible to the caller and exposes them as tools, with `CpCallGuard` tracking per-leg authorization/flow participation and usage. MAF can use explicit assignments or the semantic routing engine. The control plane is concurrent; unrelated agent services can execute requests independently. However, the bundled ReAct protocol asks for sequential delegation, MAF's execution loop is sequential, and its one worker awaits each workflow before reading the next job. Adding backend replicas is also distinct from adding role instances with independent assignments. [a2a_dispatch.rs](../repo/server/src/router/a2a_dispatch.rs), lines 215–234, 507–565 and 786–824; [MAF worker](../repo/orchestrator/src/maf/worker.rs), lines 85–119; [MAF loop](../repo/orchestrator/src/maf/executor.rs), lines 422–458.

### Persistence, resume and scheduling

Chat sessions/messages are durable server records. Subsequent turns can retrieve history through configurable context selection. This restores conversational input, not the old model process. MAF persists a fixed workflow snapshot, per-step plans, progress and synthesis guidance. Completed steps survive ordinary retries. A human continuation resumes the specific A2A task using stored plans rather than re-running discovery/planning from scratch. [a2a_dispatch.rs](../repo/server/src/router/a2a_dispatch.rs), lines 242–261 and 484–505; [MAF executor](../repo/orchestrator/src/maf/executor.rs), lines 297–329, 401–430 and 476–483.

For agent-internal persistence, the state API provides encrypted opaque task snapshots and KV rows with optimistic versions, expiry, pagination and per-agent limits. SDK task-store adapters make status-changing saves synchronous and coalesce artifact updates, by default into 500 ms windows. This does not persist every arbitrary framework cache or heap object. Nor is it permanent project knowledge: retention applies from the last write, and the platform explicitly warns when state expires before HITL questions. [agent_state/mod.rs](../repo/server/src/agent_state/mod.rs), lines 21–50 and 87–97; [nasiko_state.py](../repo/agents/common/nasiko_state.py), lines 1028–1088.

“Scheduling” here is queue consumption, polling/recovery, background telemetry and cleanup. No user/product cron or periodic ProjectMaster reasoning loop was found. The startup reconciliation pass redeploys ordinary agents recorded as running when their runtime resource is missing. It is not repeated project progress supervision. [reconcile.rs](../repo/server/src/agents/reconcile.rs), lines 31–59; [state initialization](../repo/server/src/state.rs), lines 469–505.

### Interruption, cancellation and recovery

Operators can stop/start a service by scaling to zero/one and restart it with resolved environment. This controls the container, not a single conversation task. The UI's direct-chat Stop action says exactly what it does: abort receiving the stream and save the partial response. The agent may continue running. Routed chats hide this control. The bundled coding executor's `cancel` merely returns completed status and does not wire a cancellation token into its active model/shell loop. HITL cancellation is separately available for pending human requests. [admin/routes.rs](../repo/server/src/admin/routes.rs), lines 408–459; [turnRegistry.ts](../repo/ui/common/src/features/chat/turnRegistry.ts), lines 75–100; [coding main](../repo/agents/coding/src/main.rs), lines 454–459; [HITL router](../repo/server/src/router/hitl.rs), lines 35–42.

Ordinary MAF failures retry up to the stored attempt cap (default three at enqueue); earlier successful steps are skipped. Failed human-resume jobs are terminal rather than silently restarting from step zero and discarding the answer. Redis pending jobs can be reclaimed on worker startup after a ten-minute idle threshold. The generic HITL delivery machinery distinguishes permanent errors from retryable transport/endpoint problems, leases deliveries and permits explicit operator handling of ambiguous outcomes. These are valuable recovery mechanics, but not an exactly-once guarantee for external agent side effects: a process can fail after a side effect and before persisting successful progress. [maf.rs](../repo/server/src/maf.rs), lines 1803–1820; [MAF worker](../repo/orchestrator/src/maf/worker.rs), lines 23–26, 69–81 and 533–558; [HITL dispatcher](../repo/hitl/src/dispatcher.rs), lines 27–80 and 94–149.

### Completion, acceptance and retirement

The coding agent emits an artifact then A2A completed status. Reaching its turn limit can still produce a completed artifact explaining that it exhausted steps; completion is not an independently checked acceptance decision. MAF records `success` after obtaining final synthesis. Wingman would need its own test evidence, definition-of-done and human acceptance transition above these protocol states. [coding main](../repo/agents/coding/src/main.rs), lines 428–448; [MAF worker](../repo/orchestrator/src/maf/worker.rs), lines 469–492.

Retirement is implemented: deleting an agent atomically soft-deletes its row, revokes gateway/state credentials, invokes a deletion hook and attempts runtime teardown, returning runtime errors rather than pretending rollback. Historical builds, usage and chat associations remain. State sweepers remove deleted-agent state. This is service deregistration with audit retention, not archiving/forking a Codex conversation. [catalog/routes.rs](../repo/server/src/catalog/routes.rs), lines 1110–1234; [state API](../repo/server/src/agent_state/mod.rs), lines 35–40; [delete tests](../repo/server/tests/agent_delete.rs), lines 1–17.

## Coordination trace: a saved two-agent workflow with a human pause

This is a code-path trace of supported behavior, not a claim that a live run was executed during assessment. Consider a saved instruction split into research and summarization steps, with the first agent asking a question.

1. `POST /api/maf/workflow/from-instruction` authenticates the caller and sends the compound instruction to the configured decomposer service. The server rejects an unconfigured service with 503. Each resulting task is assigned an accessible agent, either explicitly or using semantic routing, and becomes an ordered `MafStep` with stable step and agent IDs. [maf.rs](../repo/server/src/maf.rs), lines 938–1063 and 1142–1204. This produces a workflow draft/definition, not a new product/project.
2. `POST /api/maf/workflow/{id}/run` verifies ownership, rechecks current access to every distinct step agent and rejects empty/invalid definitions. It inserts a `maf_executions` row containing the exact workflow snapshot and enqueues that same definition to `nasiko:maf:execute`, returning 202 and an execution ID. [maf.rs](../repo/server/src/maf.rs), lines 1725–1877.
3. The Redis consumer marks the run running and increments its attempt count. The executor registers the execution as a platform session, asks its LLM to generate step prompt templates/extraction goals, persists the plans and begins step zero. It combines extracted output from preceding successful steps into the next step's context. There is no room broadcast or shared editable ticket. [worker.rs](../repo/orchestrator/src/maf/worker.rs), lines 263–355; [executor.rs](../repo/orchestrator/src/maf/executor.rs), lines 331–420 and 422–458.
4. When the first A2A agent returns input-required, the executor yields `AwaitingHuman` with that agent's actual task ID. The worker records awaiting-human, creates a durable HITL row and acknowledges the current queue item without automatically retrying the question. Failure to persist the question makes the run failed rather than leaving an unanswerable pause. [types.rs](../repo/orchestrator/src/maf/types.rs), lines 106–124; [worker.rs](../repo/orchestrator/src/maf/worker.rs), lines 494–529.
5. The human answers through the pending-question UI/CLI/API. The generic resolution route checks identity, answer shape and the pending request; server delivery then enqueues a continuation targeting the same paused step/task with the saved workflow snapshot. The worker loads stored plans/results and calls `run_maf_from`. [HITL router](../repo/server/src/router/hitl.rs), lines 329–353 and 512–546; [MAF resume enqueue](../repo/server/src/hitl/mod.rs), lines 820–930; [worker continuation](../repo/orchestrator/src/maf/worker.rs), lines 358–379; [resume contract](../repo/orchestrator/src/maf/executor.rs), lines 476–483.
6. After the answer, the executor extracts the first step's result, runs the second step and synthesizes the final output. The worker saves output, per-step state, tokens, cost and completion time; execution and usage endpoints feed the runs UI. [worker finalization](../repo/orchestrator/src/maf/worker.rs), lines 469–492; [MAF API](../repo/server/src/maf.rs), lines 68–71. No product DoD, independent test acceptance, management escalation or Telegram delivery is inserted by this pipeline.

Ordinary chat uses a different human-decision path. A server-side resume dispatcher drives the resumed A2A exchange independently of the browser. A bounded in-memory continuation buffer lets a tab replay or tail events. That buffer is process-local and capped at 500 events/1 MiB. It is not a durable distributed session event bus. [continuation.rs](../repo/server/src/hitl/continuation.rs), lines 1–17 and 26–40.

## Major capabilities beyond Wingman's description

**Provider-neutral model governance and attribution.** The LLM router verifies an agent identity token, resolves credentials server-side and translates inbound protocols to provider-specific requests. It includes model catalogs, price resolution, per-agent usage and cost, and independently opt-in coding-harness routing. This could give Wingman an infrastructure cost layer without replacing the native coding harness. It also makes Nasiko part of the critical request path: provider compatibility, credentials, trace propagation and gateway availability become operational responsibilities. [llm-router/lib.rs](../repo/llm-router/src/lib.rs), lines 1–15 and 62–93; [provider modules](../repo/llm-router/src/providers/mod.rs).

**A permission-filtered MCP estate.** Custom connectors and Composio toolkits can be exposed through one gateway with agent/user reachability and allow/ask/block behavior. Approvals persist and are later delivered rather than being transient browser popups. This is useful for giving workers differentiated access while keeping tool credentials centrally managed. Integration requires choosing which Wingman identity maps to each deployed agent and preserving trace/user correlation. It does not create project-room access semantics automatically. [authorizer.rs](../repo/mcp-gateway/src/authorizer.rs), lines 19–65; [tool approval test](../repo/mcp-gateway/tests/tool_approval.rs), lines 7–11 and 64–104; [deployment credentials](../repo/server/src/agents/deploy_env.rs), lines 93–120.

**Packaging and operational deployment.** The embedded OCI registry, server-side source builds, version history/rollback, encrypted deployment secrets and recoverable build queue form an agent distribution platform. Wingman's purpose does not require an OCI supply chain. GitHub OAuth/repository listing and queued clone-to-build/deploy are also implemented. This is agent-service deployment rather than issue-to-PR engineering execution: [github.rs](../repo/server/src/github.rs), lines 35–43 and 659–898. This would be useful if roles are independently deployed A2A services, while adding little to a design based entirely on native Codex processes until adapters exist. [runtime wiring](../repo/server/src/runtime.rs), lines 50–81; [build worker](../repo/server/src/agents/build_worker.rs), lines 40–163; [version model](../repo/server/src/catalog/models.rs), lines 159–171; [update/rollback implementation](../repo/server/src/agents/update.rs).

**Cross-harness accounting and historical ingestion.** Adapters can observe already-running supported harnesses, import stored history, queue completed turns while offline and merge native subagent ancestry. The server makes ingestion replay-safe and exposes turn/tool ledgers with cost/trace links. This could supply visibility into Wingman agents even before a deeper harness-control integration is built. Historical/finished-turn reporting must not be presented as live process supervision. [integration/mod.rs](../repo/cli/src/commands/integration/mod.rs), lines 1–9 and 128–175; [ingestion](../repo/server/src/coding_agent_telemetry.rs), lines 49–54 and 90–126; [subagents](../repo/server/src/coding_agent_subagents.rs), lines 1–43.

**Cost-oriented context and wire transformations.** PACMS selects diverse relevant history under an estimated token budget; structural compression elides portions of JSON/log/diff/search payloads; compact tools replace verbose schemas with signatures and decode validated calls. These are substantive optimization mechanisms beyond Wingman's specification. They should be evaluated against representative coding tasks because reduced payload size can change what a model sees; token savings are not evidence of preserved acceptance quality. [pacms_selector.rs](../repo/orchestrator/src/pacms_selector.rs), lines 8–24 and 33–47; [compress/lib.rs](../repo/compress/src/lib.rs), lines 1–17; [tool-compact/lib.rs](../repo/tool-compact/src/lib.rs), lines 1–7 and 83–120.

**Operational estate analysis.** Overview computes problems and opportunities over observed agents/flows and retains human assignments, snoozes and handled decisions. It can help an operator triage expensive/unhealthy infrastructure. It does not know whether an LOS acceptance scenario is blocked. [overview/mod.rs](../repo/server/src/overview/mod.rs), lines 1–12 and 74–117. This is a useful separate view to connect to Wingman's product/agent briefings.

## Distinctive mechanisms and innovation assessment

These are concrete engineering mechanisms, not claims of historical novelty.

- **Two identities at tool-call time.** A deployed agent carries its own gateway credential while the user's identity rides the propagated flow trace and participation record. That separates “which agent is calling” from “on whose work it is acting.” It enables per-user attribution and tool authorization across delegated agent hops. The constraint is mandatory propagation by heterogeneous agents; simply hosting an A2A endpoint is insufficient. [a2a_dispatch.rs](../repo/server/src/router/a2a_dispatch.rs), lines 795–810; [state credentials](../repo/server/src/agent_state/mod.rs), lines 23–29. Wingman could reuse this concept for distributed specialists, but would still need project/task identity alongside it.
- **Flow-aware delegation guards.** Redis tracks recursion depth, call chains, fan-out, total tokens and elapsed time; admission rejects cycles and exhausted budgets. This constrains runaway cascading requests across agents instead of relying solely on each agent's prompt. It is flow-local operational control, not a persistent organizational budget or supervisor that can reason about a stalled product. Accounting and admission also depend on correct flow initialization and trace participation. [flow/guard.rs](../repo/flow/src/guard.rs), lines 18–34 and 174–233.
- **Human pause as durable execution continuation.** A question binds an owner, agent, task/context and origin, and resolution feeds a background dispatcher. MAF resumes from saved plans; resumed chat replays actual agent events without depending on an open tab. This is more useful than an approval notification alone. Its limits include agent task durability, expiry, ambiguous delivery outcomes and the process-local bounded replay buffer. [maf/types.rs](../repo/orchestrator/src/maf/types.rs), lines 106–124; [maf/executor.rs](../repo/orchestrator/src/maf/executor.rs), lines 476–483; [continuation.rs](../repo/server/src/hitl/continuation.rs), lines 1–40.
- **Boundary-safe, learned model-tier routing.** Model selection can reuse a conversation/agent decision, classify only at safe boundaries, avoid pinning a session to a greeting and update provider-specific quality cells from later feedback. This enables cost/quality adaptation across conversations while keeping tool-loop continuations sticky. It requires valid boundary signals and heuristic feedback, so it is not evidence that a cheap tier meets a product's correctness requirement. Pinned/configured fallbacks remain distinct. [routing/mod.rs](../repo/llm-router/src/routing/mod.rs), lines 103–128, 166–206 and 228–277.
- **Optimistic encrypted state with bounded write coalescing.** The task-store adapter synchronously commits status changes but batches high-frequency artifact updates, using versions to prevent stale replicas overwriting newer snapshots. This balances restart survivability against write volume and explicitly bounds some crash loss. It does not preserve arbitrary in-process framework state, and default expiry makes it unsuitable as Wingman's sole permanent product knowledge. [agent_state/mod.rs](../repo/server/src/agent_state/mod.rs), lines 30–50; [nasiko_state.py](../repo/agents/common/nasiko_state.py), lines 1028–1078.
- **Instruction provenance kept outside the live prompt.** The bundled coding agent can annotate instructions with a trigger, hypothesis and pending/confirmed/revoked outcome. It strips metadata before prompt injection and excludes revoked instructions, while opt-in maintenance/pruning can update the source file. That offers a concrete pattern for auditable evolving directives without continually expanding the model-facing rationale. It is workspace-local and model-assisted, not a validated organizational knowledge system. The source explicitly attributes the prompt-comments method to prior work. [prompt_comments.rs](../repo/agents/coding/src/prompt_comments.rs), lines 1–17 and 67–81; [instructions.rs](../repo/agents/coding/src/instructions.rs), lines 49–85, 204–243 and 287–298.
- **Strict tool-schema compaction with bypass.** The compact tool grammar has a decoder that validates against original schemas; unsupported schema features bypass transformation instead of being silently lost. That makes an optimization boundary inspectable. Literal compact-call markers, unsupported JSON Schema constructs and provider/model behavior still constrain applicability. [tool-compact/lib.rs](../repo/tool-compact/src/lib.rs), lines 76–120. Structural compression explicitly credits Caveman's published behavior and PACMS describes a port. Neither should be claimed as an invention of this repository. [compression attribution](../repo/compress/src/lib.rs), lines 25–30; [PACMS provenance](../repo/orchestrator/src/pacms_selector.rs), lines 1–6.

## Practical adoption path and remaining work

**Use directly where infrastructure is the problem:** catalog/skill discovery for A2A services, container deployment, central secrets and tool grants, provider routing, usage accounting, per-agent operational drill-down, durable A2A task state and reusable sequential workflows. Native harness reporting could be useful early for consolidated visibility into Codex/Claude sessions, with the UI explicitly labeling the distinction between recorded activity and managed execution.

Before use as Wingman's control plane, adapt these interfaces:

- Map role profiles to independent catalog instances.
- Bind each instance to a project and an actual Codex conversation.
- Add a harness adapter for execution and control.
- Propagate host, project, task and session IDs.
- Connect HITL continuation to Butler/Telegram.
- Connect agent, session and trace views to a shared tracker and rooms. Decide which tasks are A2A workflows and which are long-lived coding sessions. They have different resume, cancellation, concurrency and acceptance semantics; wrapping both behind an “agent” label will obscure control gaps.

Build the core organization:

- Multi-product registry and intake routing.
- Butler, ProjectMaster and per-product leadership.
- Proportionate product research/clarification.
- Scopes/specifications/acceptance evidence.
- Shared tickets and dependencies.
- Room membership and multi-agent discussion.
- Autonomous periodic blocker supervision.
- Multi-host enrollment/placement and coherent workspaces.
- Executive current/recent/next briefings.
- Full per-agent coding session controls. The bundled coding agent is a tool-using example, not a substitute for those organizational capabilities.

The main integration tradeoff is architectural. Nasiko is well aligned with **A2A agent services governed through a central gateway**. Wingman specifically wants **standing autonomous Codex agents across two hosts**, carrying project identity and native session continuity. A deployment of Nasiko alone does not bridge those execution models. Borrowing its governance/telemetry patterns or placing it under the organization is more plausible than repurposing its workflow/estate UI as the whole product.
