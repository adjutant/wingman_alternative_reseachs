## Fit verdict

**Verdict:** Emdash provides a strong individual coding workspace and distributed execution foundation for Wingman. It runs external coding harnesses and links conversations to projects, tasks, and Git workspaces. It supports local/SSH hosts, structured tool activity, permissions, issue intake, code review, and pull requests.

The ACP lifecycle retains conversation identity across provider-process eviction. Restore errors preserve saved history pointers. Activation coordinates concurrent callers. Initial prompt delivery has an explicit persistence boundary. These mechanisms do not supply Wingman's standing organization.

The organizing unit is a human-created **task workspace with one or more provider conversations**, not an employee-like agent with a persistent organizational role. There is no built-in Butler, project-routing conversation, ProductMaster/TechMaster hierarchy, team roster, shared agent rooms, specialist assignment/dependency scheduler or product definition-of-done workflow. Users can ask a provider to act as a specialist and can schedule recurring prompts, but these are ingredients for building that organization rather than its implementation.

Two distinctions matter especially for Wingman. First, independent ACP conversations can share one provider process when provider, working directory and environment match; separate agent conversations do not imply one OS process per agent. Second, an automation run becomes `done` after it provisions a workspace and starts a session. That status does **not** establish that the coding request, tests or product delivery succeeded. A Wingman supervisor must observe work outcomes separately.

## Architecture and evidence map

The checkout is a TypeScript monorepo. The Electron desktop owns project/task entities and annotations in SQLite. A host owns the repository, worktree, process and conversation records physically resident on that machine. Desktop rows mirror host observations and link them to human-facing tasks. The React UI reaches typed domain controllers through Wire. These delegate to runtime workers, Git services and the database. The `packages/core` runtimes are transport-independent; provider behavior is injected from `packages/plugins`.

The executable path is visible in [desktop main](../repo/apps/emdash-desktop/src/entry/main.ts), lines 16–36: bootstrap is dynamically loaded, with a recovery entry on failure. [Desktop Wire](../repo/apps/emdash-desktop/src/main/gateway/desktop-wire.ts), lines 16–40 and 48–69, grants the renderer a message port, queues calls until the controller bundle is ready and routes typed calls/live subscriptions to domain controllers. [Preload](../repo/apps/emdash-desktop/src/entry/preload.ts), lines 8–35, exposes this port plus file-path and boot-recovery/reporting escape hatches. ACP runs through a separate [Wire component worker entry](../repo/apps/emdash-desktop/src/main/gateway/entries/acp.ts), lines 1–7. Thus the rich renderer is a client of domain/runtime services, rather than the authority for a running agent's process.

There are two execution paths. TUI conversations run provider CLIs through terminal/PTY services. Structured chat conversations use ACP and a session manager, with provider adapters where necessary. Local and remote workspace servers expose the same runtime vocabulary. SSH forwards the workspace server's Unix socket rather than turning every operation into a one-off SSH shell command. This is genuine remote execution with host-owned state, although it is not a shared multi-agent organization spanning hosts.

## Agent definitions and lifecycle

### What an “agent” actually is

Emdash uses several different identities that should remain separate in a Wingman design:

- A **provider** is an implementation plugin such as Codex or Claude, with metadata and capabilities. It describes how to authenticate, detect/install a CLI, launch it, observe hooks, configure models, integrate MCP and restore a native session. It is not a worker instance or organizational profile.
- A **project** binds desktop metadata to a repository workspace on a host. It is not an automatically discovered product organization.
- A **task** is a named human work item with lifecycle state, issue/PR associations and a workspace binding.
- A **conversation** has an Emdash UUID, provider/transport, configuration, working directory, host and optional provider session pointer. A task can have multiple conversations. This is the durable identity closest to Wingman's detailed agent session.
- An **activation** is the currently materialized runtime state for a conversation. It owns transient prompt/permission/terminal/transcript state and can be evicted while its conversation remains resumable.
- A **provider process** hosts the actual ACP server and may host multiple conversations. The process cache and conversation directory are deliberately different layers.

These distinctions are explicit in E01/E03/E06–E09. They make Emdash a useful foundation but do not give each conversation an employee identity with manager, specialty, project responsibilities and a queue of independently assigned tickets.

### Definition, creation and placement

The human selects an installed provider, task configuration, workspace/Git choice, prompt and transport. The provider plugin advertises capabilities rather than every UI assuming the same controls. Codex, for example, declares ACP, usage probing, hooks, resumable sessions, MCP and TUI auto-approval support (E04). Reusable prompt-library entries can supply role instructions, but there is no separate persistent ProductMaster profile automatically instantiated per project.

`prepareCreateTask` first requires an attached project and resolves its workspace target. For a new worktree it compiles a Git plan, resolves base/push remotes, derives the host from the project, allocates a path and checks pending-deletion conflicts before registering resources (E02). The task can instead reuse a repository instance. This means worktree isolation is a primary default/workflow, not an invariant that every conversation owns a different checkout: multiple task conversations can share a workspace, and the configuration supports existing repository workspaces.

Conversation creation freezes a host/workspace association and refuses new remote conversations when that host is offline. It registers the host record before committing the desktop registry link. If registration or launch fails, compensating deletion/untracking avoids claiming an active conversation that was never established. `providerSessionId` starts null and becomes a native resume pointer only after successful session creation (E03). ACP sessions materialize when the chat starts them; TUI conversations launch through the TUI path during creation. This provides a clean distinction between a persistent record and a running process.

Initial task creation commits before background worktree preparation finishes. [createTask](../repo/apps/emdash-desktop/src/core/features/tasks/node/operations/createTask.ts), lines 415–468, registers the initial host conversation and commits desktop rows. It starts the registry worktree operation in the background, then returns. If worktree creation fails, the task remains with a provisioning failure.

[createTask.test.ts](../repo/apps/emdash-desktop/src/core/features/tasks/node/operations/createTask.test.ts), lines 788–818, asserts successful task creation alongside failed pending worktree preparation. This is test-source evidence. A task UUID establishes durable intent. It does not prove workspace or agent readiness.

### Execution, tools, permissions and routing

ACP process acquisition resolves the provider adapter and executable for that host, builds its spawn specification and initializes a connection. Cache identity combines provider, normalized cwd and a hash of the requested environment (E06). Therefore sessions with different environments are not indiscriminately pooled. Route ownership also includes process generation, preventing a delayed old-process callback from mutating a replacement session.

The materializer loads an existing native session when one is present and supported; otherwise it creates a native session. It injects session MCP configuration and applies desired provider options before releasing the prompt (E08). Session routing correlates provider notifications, permissions and terminal requests to the Emdash conversation. Provider subagent activity is represented in live models, but these observations are not a fleet-wide employee directory or authority for Emdash-level task assignment.

The permission broker holds requests until a selected option or cancellation resolves them, and drains outstanding requests on teardown (E10). ACP requests reaching the app remain interactive; TUI auto-approval is a separate provider launch setting. Native harness/tool access still determines what the coding agent can do. The presence of a Git worktree is isolation of edits and branches, not evidence of an OS security sandbox or a least-privilege organizational policy.

The distinction is concrete in E24: ACP's filesystem port delegates read/write calls to its host filesystem. The port itself is not a per-role access-control policy. Codex's optional TUI auto-approval command explicitly sets approval policy to `never` and sandbox mode to `danger-full-access`. Wingman would need to select and enforce the appropriate native harness policy rather than assume Emdash's role prompt or separate worktree supplies permissions. Host-targeted MCP and skills controllers provide useful configuration seams (E23), but MCP's `providerId` is a harness identifier, not a specialist employee identifier.

### Concurrency, steering and queues

Independent tasks/conversations can execute concurrently. ACP's process-sharing optimization keeps session state separate from process allocation. Materialization is coordinated per conversation so concurrent startup or prompt submission joins an activation instead of launching duplicate sessions; materializer load handshakes are serialized per process generation (E08). Prompt submission wakes a suspended conversation, resolves attachments and enters the session's prompt machinery (E07).

The public API includes send, edit/delete/reorder queued prompts, cancel the current turn, set a provider-native option and terminate (E05). These are meaningful steering controls. Queued human input inside a conversation is not a shared project backlog: it has no specialist assignment or inter-agent dependency semantics. Likewise, a session plan is provider execution context, not the common ProjectTracker contract described by Wingman.

Prompt acceptance is separate from turn completion. `sendPrompt` resolves its caller through an acceptance callback while the host retains the activation lease until prompt execution finishes ([session manager](../repo/packages/core/src/runtimes/acp/node/runtime/session-manager.ts), lines 323–392). A client disconnect therefore need not cancel accepted work. The inspected [Wire acknowledgment test](../repo/packages/core/src/runtimes/acp/node/runtime/prompt-acknowledgement.wire.test.ts), lines 16–76, encodes both delivered and lost acknowledgments while the fake provider continues. This matters for mobile/desktop reconnection: uncertain delivery must be reconciled against live/history state, not blindly sent again. It does not establish a durable receipt journal or completion acknowledgment for organizational tickets.

### Persistence, suspension, restart and recovery

The durable conversation record and retained wake intent outlive a live activation. The handle can present closed, suspended, materializing and active states while preserving desired settings and selected presentation. In the ACP path, a provider-process exit suspends affected conversations. It does not automatically retry an interrupted coding turn or decide that a product is blocked; explicit start/prompt materializes work again. The implementation tests directly assert that an ACP mid-turn crash does not call load/new-session automatically.

Restoration is conservative (E08): if a provider cannot load a saved session, its pointer is preserved and an error is returned. If loading fails for an ambiguous reason, the app does not silently replace the session with an empty chat. Automatic replacement is limited to a provider-confirmed missing session that is known to be untouched and has no replayed history. A used/missing session produces `session_not_found`. The human can retry or explicitly start fresh. This avoids treating a transient transport or configuration error as proof that previous work should be discarded.

The session manager persists a materialized native pointer and then prepares the initial queue. It durably marks the initial queue consumed before releasing dispatch (E07/E09). This reduces accidental replay of the original task on later attachment. It is not an exactly-once work guarantee: a crash after the consumption commit can leave delivery uncertain, and live accepted queues are not a durable job outbox. Wingman must retain task intent and delivery/acknowledgment state above this layer if it needs reliable automatic redispatch.

History and exports are deliberately non-waking reads. A suspended session can report retained presentation while its live transcript is unavailable. A historical replay is not shown as a newly executing agent turn. Tests inspect these boundaries, pooling, TTL release, stale callbacks and restore preservation. The design is useful for an executive dashboard because merely viewing an old agent must not unexpectedly launch expensive coding work.

**TUI recovery has different guarantees.** The [TUI launcher](../repo/apps/emdash-desktop/src/core/features/conversations/node/launch-tui-conversation.ts), lines 40–85, serializes starts by conversation ID, chooses start versus resume from the stored provider pointer and relies on host reports to converge that pointer. The runtime installs provider hooks for status/native-ID capture and uses a PTY, optionally attached to tmux (E21). Its [exit handling](../repo/packages/core/src/runtimes/tui-agents/node/runtime/runtime.ts), lines 612–644 and 680–695, treats a resume CLI exiting within three seconds as an unsuccessful restore, then launches fresh and reports `replaced-by-new`. This uses an exit-timing heuristic, including an early zero exit. It is less conservative than ACP's provider-confirmed missing-session policy. Separately, lines 1038–1076 allow one unexpected non-tmux respawn after 500 ms, using a known native session ID where available. This is limited process recovery, not acceptance-aware replay of a worker's assignment. A tmux client detaching can leave its agent running; stop/kill/delete must operate on the tmux resource, not merely close the visible terminal.

### Scheduling and supervision limits

Automations persist project, schedule, prompt, provider configuration and workspace choice, then compile a host-bound deployment (E12). The host scheduler ticks at a default minute interval and limits concurrent startup workers to four. It reconciles queued/due work, respects enabled/deleted deployments, supports manual runs and cancellation, and marks interrupted provisioning/session-start work during scheduler startup (E13).

The executor's state machine is narrowly scoped: provision workspace → start session → `done`. It does not wait for the agent's turn to end, tests to pass or a PR to merge. Its concurrency limit bounds these startup workers, not all coding conversations still running after startup. A recurring “inspect all projects” prompt could serve as a custom supervisor only after Wingman supplies project/agent context and communication tools; Emdash does not supply the organizational behavior or prove that supervisor completed its review.

### Completion, acceptance, retirement and cleanup

Task states include todo, in progress, review, done, cancelled, backlog, duplicate and triage (E17). They support human workflow, but the inspected code does not connect `done` to an executable product definition of done. A provider's stopped turn, an automation's completed launch, a task's status and a merged PR are different outcomes. A Wingman TestMaster must attach acceptance evidence and a product-level delivery decision rather than infer one from these signals.

Archiving a task commits `archivedAt` before attempting session teardown in archive mode, keeping the worktree and persisted session identity for restoration (E15). The teardown can time out or return an error; archive catches/logs failures without undoing the archived timestamp. Archived state therefore records the user's archive intent and cleanup attempt, not proof that execution terminated. Termination removes active ACP intent while leaving the conversation record manually resumable (E05). Deletion supports explicit worktree/branch/conversation options and avoids deleting a workspace shared with another live task. Declining conversation deletion unlinks rather than destroys the records. Host deletion intent uses tombstones and later reconciliation, so an offline machine is not confused with an already removed resource. These are substantial lifecycle mechanics, but they retire conversations/resources rather than employees or organizational assignments.

## A concrete coordination trace

Consider a human importing an existing issue and asking Codex to implement it on a remote project.

1. The project already identifies a repository workspace and SSH host. The human chooses that project and provider in the [creation callback](../repo/apps/emdash-desktop/src/core/features/tasks/browser/create-task-modal/use-create-task-callback.ts), lines 24–54. An external integration supplies issue data. For ACP, [buildInitialQueue](../repo/apps/emdash-desktop/src/core/features/tasks/browser/create-task-modal/build-create-task-params.ts), lines 10–31, preserves the human text and adds issue/mention details as `hiddenContext`. The TUI branch concatenates issue context and prompt through `buildFinalPrompt`, lines 45–48 (E16/E22). There is no Butler or semantic product-routing step.
2. Task preparation validates the attached project and selected target, resolves remote Git settings, compiles a worktree plan and reserves a UUID/path subject to pending-deletion conflicts (E02). The workspace physically belongs to that host.
3. `createTask`, lines 415–468, registers the initial host-side conversation before its desktop transaction adds task/conversation links and starts background worktree creation (E02). Separate additional conversations use `createConversation` (E03). Post-commit conversation events and database pokes update subscribed desktop views (createTask, lines 382–412). The remote workspace server is reached through the SSH-forwarded socket (E11).
4. Starting structured chat acquires the provider process, creates/loads the native session and applies options/MCP before dispatch (E06–E08). The remote agent edits files and runs its tools on the remote host. Wire models bring transcript, terminal/tool activity, plans, usage and permission requests back to the desktop (E05).
5. If a permission request occurs, the human selects an option. If further instructions are needed, the human sends or queues another prompt. There is no automatic ProductMaster consultation or peer-room exchange (E05/E10).
6. The human inspects changes, tests and PR state and can create/merge a PR through the workbench integration (E19). Task state provides organization for this workflow. Emdash does not enforce product acceptance or send Butler's delivery report.
7. Archive records the task as archived and attempts to stop its execution while retaining the worktree/session identity; teardown failure can leave the archived timestamp in place, so the timestamp alone does not confirm termination. Deletion can later remove selected host resources or retain conversations (E15). Future work can resume the conversation when provider data remains available.

The coordination mechanism is therefore **human-to-task-to-provider plus external issue/PR systems and host RPC**. It is more than a launcher, but it is not either chat-based agent teamwork or autonomous ticket-based agent coordination. Those are major product gaps, not missing UI polish.

The typed event stream coordinates software views and runtime observations. It is not an addressed agent mailbox. Tasks store status, workspace and linked issue data but have no built-in specialist assignee or task dependency edges in the inspected schema (E01/E17). External issue adapters can expose external assignees; that does not make an Emdash conversation the assigned employee or cause dependency-ready work to be dispatched. Shared files in one workspace allow indirect coordination, but do not supply room participants, delivery acknowledgment, leadership decisions or conflict-resolution policy. Permission promises correlate an execution decision to its requesting session, while product questions are handled through human follow-up chat rather than organizational escalation.

## Major capabilities beyond the Wingman purpose

### A multi-provider coding platform

Wingman's purpose centers on Codex employees. Emdash implements a large provider registry with explicit capability negotiation and different launch/auth/hooks/MCP/session behavior (E04). This allows experiments across coding harnesses and models without rebuilding every workspace control. The consequence is genuine normalization work: feature availability and history/resume semantics vary, so Wingman must retain provider capability boundaries rather than promise identical lifecycle controls everywhere.

### External work-system and source-control operations

The integration registry includes GitHub, GitLab, Linear, Jira, Forgejo, Asana, Monday, Notion, Plane, Trello, Featurebase, Plain and YouTrack (E16). These are substantial bridges to existing organizational work rather than a new isolated Markdown-only tracker. PR create/merge and task-to-PR associations connect imported work to delivery review (E17/E19). Wingman could keep external tickets authoritative while using a separate agent assignment/knowledge layer. It would still need reliable state synchronization and avoid equating external assignees with its AI employees.

### A host-owned remote developer environment

The remote workspace server supplies an execution location with durable resource identity, typed RPC, deployment/start controls and SSH transport (E11). This is a meaningful product beyond “send an agent an SSH command.” It can place heavy builds and coding on Endeavour while the Mac remains the viewing/control machine. Wingman still needs organizational messages, shared knowledge and job delivery across those hosts; Emdash's host and desktop state authorities should be preserved rather than replaced with two writers racing over one resource.

### Scheduled headless coding starts

Automations deploy recurring prompt/workspace configurations to a runtime rather than requiring a mounted chat view (E12–E14). That supports maintenance, recurring review or research jobs. The limiting semantics are explicit: launch completion, no product outcome gate, and startup concurrency rather than a budget for every running agent. Wingman can borrow scheduling while adding outcome tracking, retry policy and supervision.

### Host-side tool and skill configuration

Emdash has substantive configuration machinery beyond a list of model names. The [skills manager](../repo/packages/core/src/runtimes/agent-config/node/runtime/skills.ts), lines 53–119, installs or generates `SKILL.md` files under the host's `.agentskills`, keeps catalog provenance and publishes installed state. The [MCP manager](../repo/packages/core/src/runtimes/agent-config/node/runtime/mcp.ts), lines 32–63 and 120–171, maps canonical server definitions into provider registrations, aggregates installations and serializes configuration writes. Desktop controllers route these actions to a selected host. This could distribute Wingman's tracker/chat tools and reusable operating instructions to each machine. The limit is configuration scope: selecting providers is not selecting distinct BackendCoder instances; same-name aggregation is not organizational identity, and the cross-provider save loop is not an atomic fleet-wide deployment transaction. Wingman needs per-role policy and version/provenance records above this mechanism.

### Integrated code investigation and review

The application combines files/editor, terminal execution, structured transcript, diff review, preview-server features and source-control/PR work in a task environment. These are substantive developer-workbench capabilities, especially when linked to remote execution, rather than cosmetic additions. Wingman's description requests access to such a workspace but does not specify its implementation; Emdash supplies reusable depth in that part of the product while leaving executive synthesis and standing team coordination to be built.

## Distinctive mechanisms and innovation assessment

These are distinctive engineering choices visible in this checkout, not claims that Emdash invented them or is unique across all alternatives.

**Conversation identity independent of the running provider.** A retained handle, native session pointer, activation record and pooled process are different objects (E06–E09). This enables idle resource reclamation without deleting the identity the human is inspecting. Wingman benefits directly: persistent employees should likewise survive replacing their current process. The limit is that Emdash preserves a conversation, while an employee's role, ticket queue and cross-session knowledge still need a higher-level record.

**Conservative restoration with explicit evidence of loss.** Materialization preserves old pointers on unsupported or failed load, only treating a provider-confirmed missing untouched session as replaceable (E08). This prevents a transient failure from silently producing a new conversation that falsely appears continuous. It enables trustworthy “resume” behavior. It cannot recover history that the provider genuinely lost, and successful loading alone does not prove that an interrupted edit or shell command is safe to replay.

**Durable commit before initial prompt dispatch.** The pointer and queue-consumption writes precede the effects that send the original request (E07/E09). The mechanism addresses repeated attachment/startup races rather than simply checking an in-memory boolean. It reduces duplicated starts across runtime reactivation. It deliberately does not solve arbitrary exactly-once agent work or make live prompt queues durable; Wingman should not use it as a substitute for acknowledged ticket delivery.

**Generation-aware pooling and routing.** Cache identity incorporates environment without persisting it as plain identity text, while routed events carry a process generation (E06). Conversations can share useful resources without stale process events being attributed to replacements. This helps scale a workspace containing many live agents. Shared process failure can still affect all sessions on that connection, so organizational availability cannot be inferred from a single conversation's record existing.

**Single-authority host resources and deletion as data.** Host resource records, desktop annotations and pending deletion are separated (E01/E15/E26; E20 explains the design). Tombstones retain intent when a machine is unreachable. A later sweep invokes idempotent host removal. The sweep only purges after the mirror confirms disappearance and can record a terminal failure rather than spin forever. This is particularly relevant to a Mac/Linux organization: a disconnected host is not “empty,” and a local UI update is not proof of remote cleanup. The tradeoff is a more explicit eventual state model and a need to show pending/retry/untrack decisions clearly.

**Protocol-level live projections rather than only scraped terminal text.** ACP exposes transcript, plans, tools, subagent activity, terminals and usage as typed models while retaining TUI compatibility (E05). This enables rich drill-down and future executive summaries grounded in source events. It does not itself create semantic progress summaries, shared rooms or a trustworthy completion criterion. Those interpretations must be added deliberately.

## Practical use in Wingman

The **individual workspace and host execution subsystem** offers the most direct reuse:

- Project/host bindings, stable conversation identity, and native Codex sessions.
- Remote execution, live tools/terminal output, permissions, and queued steering.
- Code review and controlled resource cleanup.

Use the ACP runtime and Wire contracts for integration. They avoid dependence on Electron automation or terminal scraping.

Adaptation should introduce a durable Wingman agent-instance record that references an Emdash conversation and host instead of treating the conversation title or provider ID as the employee. A role/profile record needs responsibilities, tools, project/team membership and staffing policy. A conversation can then be resumed, replaced or archived while the employee retains its identity, assignment history and executive timeline. Tasks should distinguish product tickets from execution workspaces and from automation-start records.

Wingman still needs these organization capabilities:

- Telegram Butler intake with correlated replies.
- Portfolio registry and product-aware request routing.
- Project discovery and separate product/technical leadership.
- Product artifacts, acceptance contracts, shared rooms, tickets, and dependencies.
- Shared cross-host organization state and proactive supervision.
- Executive summaries of recent results, current work, next work, and blockers.
- Product acceptance that stops active development until another request arrives.

For a first integration, preserve Emdash's resource lifecycle boundary, build agent/tracker/chat services beside it, and use native events to attach evidence to Wingman records. A scheduled review prompt can be useful only after those records and tools exist. Keep “conversation started,” “agent turn ended,” “tests passed,” “ticket accepted” and “product delivered” as separate states. The source explicitly demonstrates why collapsing them would make Wingman's dashboard misleading.

The built-in human interface is an Electron desktop. This review did not establish a mobile/web executive client or standalone public orchestration API for Telegram Butler. Core/Wire interfaces provide possible adaptation points. Extraction must preserve provider packaging, host identity, configuration, and protocol-version behavior. Source reuse must follow the Apache-2.0 terms. External provider CLIs, credentials, and compatibility remain separate dependencies.
