Paradev assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/ParadevAI/Paradev . Local checkout: research/paradev/repo. Actual inspected commit: 3b5472d2fd07f9067f380a79525cf1200900f693. The implementation still uses the Superset package namespace and superset CLI; Paradev is the product name. This is a source assessment of the local revision, not a claim about the current hosted service.

Verdict: a strong candidate for Wingman's execution and collaboration substrate, and substantially more than a terminal-grid IDE. This revision contains durable organization agents called Devs, human/Dev channels, persistent main conversations, delegated writer/reviewer task sessions, event/schedule routines, memory, real remote execution, a shared task tracker, and detailed coding workspaces. It does not implement Wingman's complete operating organization: Telegram/Butler intake, prescribed portfolio/product/technical leadership, proportionate product discovery, acceptance governance, autonomous peer-to-peer room discussion, and executive semantic summaries remain work. Crucially, the autonomous Dev service runs an external pdev engine; Codex support exists in the separate interactive host session/terminal stack. Those capabilities should not be conflated into an already functioning all-Codex organization.

This report follows Wingman's purpose and the assessment guide. The checkout was read without installation, service startup, or source modification. Links below are relative to this report; line references are for the inspected commit.

1. Architecture and actual execution model

Three distinct meanings of “agent”

  1. Organization Dev: a durable PostgreSQL agents row with UUID, organization, name, description, instructions, avatar, main-session reference, optional default repository environment, pause and archive timestamps. The Dev schema, lines 31–71, is an actual standing identity, not just a model persona. A Dev is also an actor, lines 6–32, enabling membership, authorship and mentions alongside humans.
  2. Delegated Dev task session: a child conversation associated with that Dev, a tracker task, a writer/reviewer role and its own cloud workspace. It is independent execution with a parent report path, but it does not become a separately named standing Dev. Session schema, lines 94–159, and task launch, lines 45–89 and 330–385, establish this distinction.
  3. Host-configured coding agent / interactive session: a local configuration selects a CLI command, argv, prompt transport, resume/fork args and account environment. A launch starts a terminal process or a chat harness session on a particular host workspace. Host config resolution, lines 6–17 and 68–105, and interactive agent launch, lines 57–114 and 138–169, describe this machinery. A saved CLI preset is not itself a standing organization worker.

Control plane, durable orchestration and execution plane

The TypeScript/Bun/Turborepo repository has Electron desktop, Next.js web/API surfaces, an Expo iOS client, Cloudflare realtime/relay services and a Temporal worker. The root package manifest, lines 1–88, establishes the package/workspace topology. The cloud tRPC layer owns organizations, actors, channels, tasks, projects, environments, cloud workspaces, automations and agent metadata in PostgreSQL via Drizzle. Hosts own machine/worktree/terminal state in SQLite; interactive chat has its own chat.db containing an event journal and provider-session bindings (chat schema, lines 10–40).

For Devs, a human channel message becomes a durable turn, then a Temporal session workflow. Turn submission, lines 59–185, first records an idempotent turn and either starts, steers or queues it. The workflow, lines 71–144 and 230–275, serializes work within a session, accepts steers, handles cancellation, and rolls its history over with continueAsNew. A workflow can exit after ten idle minutes without deleting the agent or its conversation.

The worker entry point, lines 26–88, checks an externally installed pdev binary for remote-mode support, connects to Temporal and registers activities. A turn activity creates a temporary per-session home, restores the saved engine conversation, launches pdev acp, streams ACP updates into a session store, and deletes/reconstructs transient local state on later attempts (activities, lines 217–289). The engine process is on the worker machine, while task filesystem/command tools are directed to an authenticated remote workspace using PDEV_REMOTE_* variables (same file, lines 139–165). Main sessions have no development machine and delegate code work to task sessions.

The durable Dev transcript is served by a Cloudflare Durable Object per session. AgentSessionHub, lines 18–74 and 76–130, accepts idempotent appends, stores events/transcript, and replays a cursor before streaming live updates. This separates conversation durability from a worker process and from a viewing desktop.

Interactive sessions follow a different path: host chat mounting, lines 61–115 and 130–185, builds Claude, Codex and ACP adapters. The registry creates a live adapter per session and journals its events (registry, lines 130–170). The host Hono application, lines 147–217, combines local DB, filesystem, Git watcher and pull-request runtime. Host chat exposes a tRPC command surface and resumable WebSocket stream (mount, lines 188–230).

Distribution is real, but its boundaries matter

Host relay registration, lines 50–110, registers stable machine identity, platform and version, then connects an outbound authenticated tunnel. The relay server, lines 129–168 and 177–206, handles control registration, dialing and presence by host routing key. This supports remote machines behind network boundaries, not just child processes on one laptop. Cloud Dev tasks additionally get provisioned/woken cloud workspaces; turn-host resolution, lines 37–95, checks both the agent's grant and the human's continuing access before returning a host target. Remote jobs, lines 103–161, expose workspace execution, output and kill operations. The client retry layer, lines 15–46, retries transient host outages.

However, the standing Dev task scheduler chooses cloud environments, not arbitrary registered Mac/Arch hosts. Interactive Codex work can use registered hosts; making Wingman's durable organization dispatch its workers directly onto the two requested personal machines needs an explicit adapter/routing policy.

3. Agent definition, creation and lifecycle in depth

Definition and configuration

The Dev identity lives in agents, independently of any process. description gives the main model and router a responsibility hint, and instructions is appended as “Your team's instructions for you” to main, writer and reviewer system prompts (systemFor, lines 545–572). These are powerful customization points but they are unstructured instructions. There is no separate role-profile table, typed competence matrix, per-project role instantiation policy, or organization hierarchy. Multiple durable Devs can use equivalent instructions, but they are independently configured rows.

The model choice for this service is worker configuration (AGENT_MODEL and AGENT_MAIN_MODEL), not a per-Dev model field (worker main, lines 38–48 and 75–81). This differs from interactive agent presets, where command, arguments, account home and model/mode/effort selection form the launch configuration. The shared definition, lines 16–67, is an extensible CLI template; host resolution, lines 68–105, prefers an instance UUID then a preset slug. These templates must not be mistaken for the Dev identity database.

Creation, identity and first activation

A human organization member calls agent.create to insert name, description, avatar and creator; agent.update adds instructions (agent router, lines 226–275). Actor identity matches agent UUID, making new Devs valid room participants. The creator or organization administrators manage the Dev; other members can interact subject to channel access. A main conversation is created lazily under a database row lock and stored once on agents.mainSessionId (ensureMainSession, lines 319–347). This is a genuine persistent agent identity/conversation pairing.

Creating a Dev does not immediately run a permanent model loop or create a team. A human DM, mention, router-selected message, routine, or child-task event supplies work. Main session inputs carry sender, channel description, project, optional recent/thread context and a reply target. This gives conversational context routing without a Butler or product-registry intake role.

Routing, turns and concurrency

Message routing, lines 366–461, loads unpaused/unarchived member Devs. A DM reaches its Dev. An explicit mention reaches mentioned Devs; otherwise a model router picks relevant Devs from names/descriptions and recent messages. Failed/uncertain routing can fall back to thread participants (same file, lines 464–515). This selects a teammate within a room, not a new-vs-existing-product decision across the portfolio.

submitPrompt uses prompt IDs and a running-turn uniqueness mechanism to deduplicate delivery. A message for the same human joins a running turn as a steer; work for another human queues (turn recording, lines 59–160). This is a meaningful authority boundary: a turn acts for one person. The main conversation nevertheless persists across those turns and people. It is not a separate memory per requestor. The main/task transcript viewer is therefore restricted to managers (agent router, lines 371–424 and 461–476).

Task execution creates an agentSessions.kind = task child and optionally a new tracker task. It chooses a repository environment explicitly, from the Dev default, or from the sole environment available; ambiguous selection returns an error asking for an environment (tasks, lines 50–89 and 138–174). The queue nominally runs three tasks per Dev, oldest first, with each task in its own box. A database unique partial index prevents multiple queued/running writers on a tracker task; reviewers can be separate sessions. The count-then-claim slot implementation is visible in fillSlots, lines 244–277. This assessment did not establish a globally serialized capacity allocator under competing callers, so the configured limit should not be treated as proven strict concurrency control under all races.

Workers are independent conversations with their own execution environment, but inherit the parent Dev's name/instructions rather than a separately provisioned BackendCoder or TestMaster identity. A reviewer receives the existing task, PR and latest writer report (brief, lines 176–198). This is a concrete writer/reviewer pattern that Wingman could adapt into specialist roles.

Tools and permissions

The main Dev has no machine or native subagents. Its MCP tools provide room reply/read, channel tasks, work list/read/start/message/stop, environment discovery, routines and memory (dev tools, lines 93–300; channel tools, lines 36–64 and 107–211). writeAgentSettings denies the engine's native Task tool when main MCP tools are supplied, keeping delegation in the product's durable task model (activities, lines 503–540).

Task sessions get a cloud box and engine remote command/filesystem capabilities. Credential resolution, lines 137–213, only hands out credentials for a running turn and an unarchived Dev. Turn-host access, lines 37–95, intersects agent and human workspace rights. Tool tokens refresh during execution. This is stronger than trusting a prompt to enforce project access.

It is not a human approval workflow in the Dev engine: the worker sets PDEV_PERMISSION_MODE=bypassPermissions (activities, lines 139–165), and ACP permission requests select an allow option while elicitation is declined (PdevSession, lines 205–226). Product questions must be normal messages/reports. The interactive Codex/Claude chat stack separately exposes actual approval response controls. Wingman needs to decide which authority/approval model applies to each role and operation.

Persistence, resume and process boundaries

A Dev is durable. A Temporal session workflow is restartable. A pdev acp process is per turn/attempt. A cloud workspace persists independently. PdevSession, lines 25–29 and 82–143, either resumes a saved engine session or creates a fresh one before prompting. The activity restores the session file from the remote transcript and maintains delivery markers so retried attempts resume rather than resend already delivered inputs. It recreates the temporary home each attempt (activities, lines 233–280). Thus durable context is in the remote store, not in a worker's temporary directory.

The workflow history holds turn IDs/outcomes, not the complete model conversation; idle exit and continueAsNew reduce orchestration-history growth. This is a sensible long-lived-agent design. It does not guarantee exactly-once external side effects: after a crash the engine is instructed to check current state before repeating actions (activities, lines 99–100), while the remote job protocol deduplicates command launches by call ID. The job runner, lines 79–120, derives stable job IDs and starts shell processes. Model/tool behavior beyond the included adapter and RPC contract belongs to the external pdev binary and was not audited here.

Interactive sessions have a different persistence mechanism: SQLite journal plus provider session ID, native-session discovery, resume/fork where supported, and update-resume bookkeeping (chat DB, lines 12–40; mount, lines 163–183). Provider capability differences remain real. A custom terminal command with resume args is not guaranteed to support the full chat lifecycle.

Scheduling and active supervision

A routine belongs to a Dev, includes a prompt, optional schedule and event triggers, and records next/last run. It wakes the same main conversation, preserving organizational context and the location where a reply belongs (routine schema, lines 164–209; fireRoutine, lines 171–200). The schedule validation reports a minimum interval of an hour (routines, lines 46–65). Missed scheduled work is coalesced rather than replayed once for every missed occurrence (lines 35–36 and 77–85).

The Temporal worker also installs a minute-based reconciliation schedule. Its purpose is delivery/execution repair: redeliver messages, restart stranded queued turns, detect wedged workflow tasks, settle lost turns and notify task parents (reconciler, lines 32–91). It is not a manager reasoning over product blockers. A Wingman ProjectMaster routine could be built on these primitives, but its tracker review, check-in policy, escalation and meaningful progress updates would be new behavior.

Steering, interruption and cancellation

Running and queued turns accept steers, with prompt-ID deduplication and explicit settlement checks to avoid losing inputs that arrive during completion (workflow, lines 98–144 and 146–227). Human managers can prompt or interrupt a Dev session (agent router, lines 360–369 and 426–458). stopTask marks active child sessions stopped, signals running workflows and refills slots (dev tools, lines 238–258). Engine cancellation sends ACP session/cancel, waits up to a grace interval and closes its transport (PdevSession, lines 160–171). Cancellation is not proof that every externally started effect has rolled back.

Pause prevents new routed/routine turns. It is not a stop-current-work command (agent pause/resume, lines 277–300). Wingman should distinguish pausing scheduling, interrupting a session, stopping a child task and retiring a standing worker.

Failure, retry and recovery

Temporal short control activities retry at most ten times. Execution activities send heartbeats and have a two-hour attempt timeout. They retry recoverable errors without a fixed attempt count. Exponential backoff is capped at five minutes (workflow retry policy, lines 32–56). Bad request/session failures are nonretryable. An engine startup or provider failure can therefore consume time and repeated attempts until stopped; Wingman's budget/goal accounting would need to sit above this.

Task launch itself gets two attempts and can clear a failed/deleted box binding before recreating it. A first task-start turn whose box never came up can be requeued once without reporting a work failure to the parent (tasks, lines 293–327 and 422–455). Infrastructure failure is usefully distinguished from task failure. Final failure is reported to the main session. The main prompt explicitly tells the Dev not to restart failed work unchanged, but this is a model instruction rather than an enforced semantic retry policy.

Completion, acceptance and retirement

The writer prompt asks for a branch, commit, push, PR, waiting for CI and fixing failing checks. The main prompt asks for a reviewer once a writer reports a PR. A reviewer should inspect the request, run relevant tests and return APPROVE or CHANGES REQUESTED (systemFor, lines 558–570). These are concrete quality instructions, not a complete autonomous acceptance pipeline. There is no parser in the inspected task-settlement path enforcing the review verdict or product DoD before declaring successful delivery.

When the engine goes idle and no tracked background tasks remain, a turn settles. Task afterTaskTurn maps completed/interrupted/failed turn states to done/stopped/failed session state, records a PR from the workspace or reply, wakes the parent with an idempotent event, and fills the next slot (tasks, lines 388–419 and 458–542). A completed model turn is therefore not independent evidence of passing tests, accepted business behavior or merged delivery. The shared tracker task's final acceptance/status is a distinct concern.

Archiving a Dev marks it archived and settles running turns as interrupted, revoking continued grants/credential acquisition (archive, lines 302–324). The UI, lines 97–106, explicitly retains chats and work. The archive handler does not itself demonstrate immediate destruction of every task workspace or process; cleanup and durable history retention are separate lifecycles. Wingman should retain that separation but make stop/retire semantics explicit.

4. Coordination mechanics and one complete request trace

Consider a human posting “Implement the export API” in a channel that contains a Dev and is linked to a project. This is a trace of the implemented code path, not a runtime experiment.

  1. Durable message and access: sendChannelMessage, lines 451–519, validates posting authority and mentions, deduplicates a client ID, appends the message, anchors attachments, updates thread following and publishes it. The channel has ordered sequence numbers and a thread root rather than an unstructured terminal transcript.
  2. Recipient and context: startTurnsForMessage, lines 366–461, selects DM/mention recipients or routes an unmentioned human message. The request includes channel description, linked project context and nearby/thread messages (lines 521–625). The Jev router uses recent conversation plus Dev descriptions. It does not instantiate product leadership.
  3. Durable identity and delivery: ensureMainSession gives that Dev one continuing conversation. submitPrompt records the prompt and acting human before Temporal delivery (turns, lines 59–185 and 319–347). Same-person concurrent input becomes steering; another person's input queues. Failure to deliver is undone so a resend can retry.
  4. Decision and decomposition: the main Dev is instructed to inspect existing work and use start_task for code work. startTask, lines 50–89, creates or reuses a real tracker task and queues a child session. Multiple calls can decompose a request, but dependencies and acceptance criteria are whatever instructions the model supplies, not a typed project plan.
  5. Environment and execution: a selected/default environment becomes a cloud workspace. launchTask persists that box binding before provisioning and moves writer work into a started tracker state (tasks, lines 330–385). The Temporal worker obtains scoped credentials, restores the conversation and launches the engine; remote jobs run against the box, with output in the coding session stream.
  6. Review and follow-up: completed writer execution records its PR and wakes the main session (tasks, lines 388–419 and 498–542). The main prompt requests a reviewer for the same task. Review findings can be sent back to the writer through messageTask (dev tools, lines 198–235), continuing its existing task conversation. There is no automatic scheduler gate requiring a reviewer or passing verdict. The model is responsible for this loop.
  7. Human result: the main Dev replies using an explicit channel/thread target, or a completed final reply is posted if no reply tool was used (reply tool, lines 99–115; fallback posting, lines 167–180). Human history remains in the room, task state in the tracker, engine activity in the session store and code in the workspace/PR.

These coordination mechanisms are substantial: durable shared chat, project-linked task context, idempotent events, parent/child work reports and human-origin authority. The critical limitation is peer activation. The message sender path only invokes startTurnsForMessage for a human principal. A Dev replying to another Dev in a shared room does not itself cause a turn in the recipient. The main reply tool also supplies target/body rather than a peer-directed wake operation. This avoids uncontrolled reply loops but prevents Wingman's autonomous Room2 conversations from emerging merely by adding members. A deliberate peer-message/event API, loop policy, participant authorization and escalation contract would be required.

There is also no first-class dependency edge in the inspected task schema/start tool: writer exclusivity is a contention control, not technical dependency resolution. Human task assignment and Dev session ownership coexist. A dashboard must join them carefully to avoid presenting the human assignee as the executing agent.

5. Major additional capabilities beyond Wingman's description

Heterogeneous agent engine workbench

Paradev supports terminal presets with custom command/prompt/resume/fork behavior, native Codex and Claude chat adapters, and additional ACP harnesses. Definition contract, lines 16–67, and registry mounting, lines 61–115, make multi-provider execution a substantive product capability. Wingman could compare or route specialized workloads across engines rather than committing its UI to one protocol. Integration cost is maintaining capability differences and refusing to assume that arbitrary custom CLIs support structured tools, approvals, checkpoints or native history.

Versioned, shareable Pages and artifact feedback

Page publication, lines 62–97 and 154–213, validates uploaded artifacts, reserves versions and retries publication conflicts. Pages can be linked to workspaces; page comments, attachments and tool routes exist under the page routers. This is a real artifact publishing/feedback layer, useful for demos and generated deliverables beyond Wingman's requested internal project records. It introduces object storage, access/sharing and public-content boundaries. It should not be substituted automatically for source-controlled specifications.

Connector/plugin marketplace and credential proxy

The repository has manifest-defined plugins and a hosted MCP proxy. Plugin server, lines 28–143, exposes an authenticate tool when disconnected, serves first-party tool implementations or forwards to remote MCP servers, and marks credentials for reauthentication on rejection. Its multi-account layer dynamically handles account arguments (same file, lines 145–180 onward). This could give organizational agents domain integrations for research and delivery without distributing vendor secrets into every workspace. It also adds a large permission/credential lifecycle and hosted-provider dependency beyond Wingman's basic Codex/Telegram organization.

General automation platform beyond agent routines

Separate automations target host or cloud workspaces, can reuse their own prior chat/terminal session, and pin a workspace safely to later runs. Automation session continuation, lines 10–77 and 102–132, intentionally avoids injecting scheduled work into an unrelated human session. GitHub-event dispatch distinguishes safe same-repository PR heads from unproven/fork heads (lines 134–159). This is valuable for recurring issue/PR/event jobs and complements Dev routines. Wingman would need to unify automation jobs with its tracker and supervision semantics, because “dispatched” automation is not product work accepted or delivered.

Browser and mobile development environment integration

The host exposes authenticated browser CDP forwarding through a desktop browser-pane bridge (browser route, lines 22–49). The host also tracks iOS simulator and Android emulator ownership, pane holds, timeout and cleanup (device lifecycle, lines 16–40 and 66–115). These go beyond a generic agent chat application and can support real development/test environments. They require platform-aware hosts and resource ownership. The Paradev mobile control application itself is explicitly iOS-only (mobile instructions, lines 64–67).

File-change checkpoints, rewind and detailed interactive controls

Chat router commands, lines 149–240, include subagent steering/backgrounding, provider approvals, rewind/fork, turn-change inspection and undoing turn files with workspace validation. Checkpoint binding, lines 50–69 and 149–157, attaches Git checkpoint capture to live sessions. This is a useful review/recovery layer beyond Wingman's high-level organization. Wingman would need to coordinate rewinds with shared branches, task history and other workers; undoing one agent's files does not roll back external APIs or an organization's decisions.

6. Distinctive mechanisms and grounded innovation

The following are useful engineering mechanisms in this checkout, not claims of historical novelty.

Standing teammate separated from coding execution. A persistent main Dev conversation handles intake, context, memory, communication and delegation while code work uses task-specific cloud boxes and conversations. The main engine's native Task tool is disabled in favor of product-owned task sessions (activities, lines 503–570). This makes delegation inspectable, associates it with tracker tasks and lets review happen independently. Its limit is a comparatively fixed writer/reviewer child model and an external engine, rather than Wingman's named independent specialist organization.

Permission-aware conversational steering. Same-human messages can steer an active turn, whereas another human's request queues, even though the Dev retains one main history (turns, lines 59–160). Combined with current agent/human access checks at credential issuance, this reduces authority mixing during execution. It does not create memory isolation between humans: managers can inspect a main conversation containing all addressed work, so Wingman would need an explicit policy for private/business-sensitive cross-project context.

Crash-resumable engine transcript plus durable orchestration. Temporal contains only control state and retry semantics. The external session store contains ACP events and native engine-session material. An activity rebuilds its temporary home from that store, and saved delivery markers prevent simple prompt duplication (workflow, lines 41–55 and 269–274; restore/delivery, lines 265–280). This enables worker replacement without losing the conversation. Its limits include external engine serialization compatibility and the inability to make arbitrary tool side effects exactly once.

Completion/steer race handling and repair. Settlement checks that the number of consumed steers matches the database. The workflow reruns if a newly recorded steer is still in flight. A minute reconciler repairs lost channel messages and stranded or wedged sessions (settler, lines 216–278; workflow, lines 173–227; reconciler, lines 32–91). This addresses real distributed-state failure modes. It is infrastructure supervision, not evidence that tasks meet their business intent.

A common human/Dev actor and room model. A Dev receives the same actor-ID treatment as a person; ordered channel messages, membership and visibility work without hardcoding specialist roles (actors, lines 6–32; channels, lines 50–179). This is directly relevant to Wingman's growing roster. The limitation is that the current automatic activation path is deliberately human-only, so a communication storage model is ahead of autonomous peer orchestration.

Remote-host identity and continuation-aware automation. Machine registration and relay transport make remote hosts usable without exposing their service ports directly, while automation continuation reuses only that automation's own preceding session (tunnel, lines 50–92; automation, lines 40–76). This is useful for Wingman's distributed background work and avoids accidental session cross-talk. It still needs a product/role-aware placement scheduler and explicit connection to the standing Dev layer.

7. Practical fit: adopt, adapt and build

Use directly as engineering reference or substrate:

  • Durable agent/actor/channel models.
  • Task and project CRUD/dashboard.
  • Host registration/tunnels.
  • Worktree/terminal/chat execution.
  • Codex interactive adapters.
  • Session replay, streaming and checkpoints.
  • Parent/task update events.
  • Routine scheduling and delivery reconciliation. These cover a considerable amount of infrastructure Wingman would otherwise build. The source demonstrates real backend paths, not merely UI claims.

Adapt deliberately:

  • Replace or abstract the autonomous pdev worker with Codex while preserving its durable task/session contracts.
  • Add role profiles and reusable specialist instances.
  • Support Dev task dispatch to registered personal hosts as well as cloud boxes.
  • Unify task assignees with agent actors.
  • Connect main-agent overviews to live detailed sessions and artifacts. The shared “one main session” model may be useful for Butler/ProjectMaster continuity, but per-project leadership should have deliberate isolation and permissions rather than using one unrestricted memory for all projects.

Still build:

  • Telegram transport and correlated Butler conversations.
  • Portfolio intake identifying new/existing projects.
  • ProductMaster/TechMaster responsibilities and lifecycles.
  • Discovery proportional to request scope/risk.
  • Required product scope/specifications/scenarios/DoD.
  • Dependency-aware technical planning.
  • Peer-directed agent messages with safe activation and escalation.
  • Semantic ProjectMaster progress/blocker supervision.
  • Executive current/recent/next/blocker briefings and accomplishment timelines.
  • Product acceptance, delivery and stop-after-acceptance policy. A prompt can request these behaviors, but that alone does not make them a reliable product capability.

The most consequential tradeoff is operational weight. Reusing the whole product brings Electron, API/PostgreSQL, realtime Durable Objects, relay, Temporal, object storage, cloud provisioning, authentication and external engines into scope. Extracting the contracts is lighter but forfeits the connected UI and recovery implementation. For a local personal Mac/Arch organization, the host/interactive session and actor/channel/task patterns are especially useful. The cloud-first Dev worker should be evaluated as a separate subsystem rather than assumed necessary.

Confidence is high in the architectural distinctions and identified feature boundaries, moderate in unexercised distributed recovery guarantees, and intentionally limited for external engine/hosted-service behavior.
