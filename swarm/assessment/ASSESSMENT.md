# Swarm assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/swarm-agent/swarm. Local checkout: `researchs/swarm/repo`. Assessed commit: `25699c00e8d56c51117589ccdd0bf2ab843a9a2b`. The checkout was clean when inspected. This is a source assessment, not a live product qualification. The repository's applicable [AGENTS.md](../repo/AGENTS.md), Wingman purpose and assessment guide were read; no dependencies were installed, services launched, tests executed or checkout files modified.

## Fit verdict

Swarm is a substantial candidate for Wingman's **local execution, durable task coordination and individual coding workspace substrate**. It supplies account-scoped projects and task cards, independent delegated coding/research/design sessions, and custom agent instructions and tools. Persistent background workers execute structured plans and parallel task programs. User approvals, Git integration and usage budgets control work. A worker directory and desktop views expose execution. These are concrete backend services and UI paths, rather than role names in a README.

It does not supply Wingman's complete standing development organization. There is one general Orchestrator and code-owned execution roles, rather than a built-in Butler → ProjectMaster → per-project ProductMaster/TechMaster hierarchy. No incoming Telegram conversation adapter or multi-party agent room application was found. Remote worker placement explicitly refuses execution. Worker summaries and run history are useful operational views, but do not yet amount to Wingman's plain-language, linked current/recent/next executive briefings. Product discovery, domain acceptance and organizational supervision would require explicit application policy and workflow construction.

The practical proposition is therefore to reuse Swarm as a headless product through its HTTP API/SDK and extend the organizational application around it. Reproducing its daemon, stores and execution UI inside Wingman would inherit a very large, evolving product surface. Its source contains legacy compatibility paths beside V3 authorities, so integration should target the supported V3 boundaries and independently qualify the exact flows Wingman will depend on.

## Architecture and execution authority

The installed launcher/TUI and React desktop are clients of a Go daemon. The daemon entry point parses configuration, constructs `runtime.New`, then calls `Run`; see [daemon main](../repo/swarmd/cmd/swarmd/main.go), lines 13–42. Composition in [runtime/daemon.go](../repo/swarmd/internal/runtime/daemon.go), lines 304–397 and 442–557, opens/wires event storage, authentication, provider clients, tool runtime, system agents, sessions, artifacts, permissions, workspaces, sandbox and worktrees. The role of the daemon is important: agents are not separate terminal panes driven by a UI. Their conversations, execution intents and authority live behind the daemon, so a viewing client need not remain open.

The principal data planes are:

* **Sessions and runs:** V3 session snapshots, messages, event/projection records and durable run intents. Session mutations go through [session/session_events.go](../repo/swarmd/internal/session/session_events.go), lines 92 onward, into [ApplyV3SessionMutation](../repo/swarmd/internal/store/pebble/session_event_store.go), lines 688–745. Its coordinator explicitly assembles records, event, projection, idempotency and outbox before publication; see [session_mutation_coordinator.go](../repo/swarmd/internal/store/pebble/session_mutation_coordinator.go), lines 53–77 and 199–260. Pebble is the durable authority, not the websocket or a React cache.
* **Projects and tasks:** [ProjectRecord](../repo/swarmd/internal/store/pebble/project_store.go), lines 44–63, associates repositories/directories, synthesized project context and conversations. `ProjectTaskRecord`, lines 423–523, links a task to source identity, worker/run, session, attempts, review, plans, program, artifacts and actual Git/delivery state. These are application records, not just messages or todos.
* **Workers:** [worker_store.go](../repo/swarmd/internal/store/pebble/worker_store.go), lines 30–198, defines a versioned standing worker with instructions, role, optional custom agent, accepted bindings, scheduled automations and durable execution receipts. A worker persists between jobs. A worker run creates/uses a V3 execution session. It is not one immortal OS process.
* **Task programs:** [task_program_store.go](../repo/swarmd/internal/store/pebble/task_program_store.go), lines 16–103, persists declared stages, dependencies, jobs, child-session references, repository lanes and blockers. The scheduler launches ready cohorts and integrates each stage before advancing. This storage is separately revision-guarded. It is not automatically in the same atomic transaction as the session event/outbox mutation.

The execution queue in [sessions_v3_executor.go](../repo/swarmd/internal/api/sessions_v3_executor.go), lines 311–418, admits only matching durable pending run intents, maintains active execution ownership and bounds its in-flight bookkeeping. Provider request/tool continuation processing is in the same executor, with provider-neutral run services and provider-specific adapters. A child coding agent is a genuine independent conversation and tool execution loop, usually running concurrently as a Go goroutine inside the daemon, with an allocated Git worktree. It is not necessarily another Codex CLI process. Swarm supports multiple model providers; Wingman's requirement that the standing organization specifically comprise Codex agents would need a provider/model policy and qualification of the selected adapter.

Desktop consumes bootstrap/hydration plus scoped V3 realtime. [v3-realtime-controller.ts](../repo/web/src/features/desktop/realtime/v3-realtime-controller.ts), lines 107–195 and 291–305, shows bootstrap, rehydration and opaque endpoint-cursor handling. This supports reconnection and makes the frontend a view of backend authority, but does not prove every reconnect/crash case works at this revision without executing it.

## What an agent is, and its complete lifecycle

### Definition, identity and creation

Swarm has several distinct entities that should not be conflated. A **system agent definition** is compiled policy and prompt, materialized through a registry. A **custom agent profile** is account-owned instructions plus a bounded explicit tool contract. A **session** is a durable conversation/execution context with a captured agent/model configuration. A **task** is a project assignment/card that can have several attempts and linked sessions. A **worker** is a durable standing job definition with lifecycle, revision, role, bindings and automations. A **run** is one admitted execution receipt. A **task program job** is a declared DAG node that may launch a real child session. None of the profile/prompt records by themselves is an independently running agent.

[BuiltinSystemAgentRegistry](../repo/swarmd/internal/agent/system_agent_registry.go), lines 354–359, reconstructs code-owned definitions from the shipped binary. The main Swarm session has research, editing, Bash and delegation tools but cannot create standing workers by default; its contract at lines 374–414 explicitly disables those management capabilities. The separate Orchestrator contract at lines 452–483 includes project, custom-agent, worker, workflow and memory management. This is an actual division of runtime authority, not merely different descriptions of the same role.

Custom agent creation at [custom_agents.go](../repo/swarmd/internal/api/custom_agents.go), lines 16–120, validates identity, refuses reserved/system names and saves only allowed tools. It allows practical specialist instructions such as backend coding or test preparation. [ApplyWorkerAgent](../repo/swarmd/internal/run/worker_agent.go), lines 15–111, preserves the authoritative runtime role while applying custom instructions and narrowing tools; reviewer profiles enabling write/delegation effects are rejected. Creating a custom profile does not authorize unsupervised work or broaden a worker into an organizational administrator.

Application agents are another layer. [application_agents.go](../repo/swarmd/internal/api/application_agents.go), lines 78–150, validates expected revision, principal-owned context/instructions, project and explicitly linked workers; its linked-resource routes delegate into canonical task/worker handlers rather than duplicating their rules. This is attractive for a Wingman gateway identity, but it is not permission to replace the system agents or reinterpret a context string as new execution authority.

A task child receives its own session ID, parent-session/task/run references and captured profile. [prepareDelegatedSubagentLaunchWithProfile](../repo/swarmd/internal/run/service_tools.go), lines 1243–1340, resolves the agent/model and sets lineage. For Coders, lines 1482–1530 demand a worktree service and captured source base before allocation. Lines 1623–1665 persist a canonical V3 child and establish generation-one ownership. If persistence may have occurred before an error, the implementation preserves the possible durable child/allocation instead of destructively pretending the create never happened. This improves inspectability, while also creating explicit repair cases operators must understand.

Standing workers follow a different creation/acceptance lifecycle. [worker_store.go](../repo/swarmd/internal/store/pebble/worker_store.go), lines 30–39 and 105–144, defines pending, idle, active, stopping, paused, archived and deleted states with revision history. [Accept](../repo/swarmd/internal/run/worker_execution.go), lines 190–246, validates the exact proposed revision, workspace authorization and model before activation. Accepting the worker does not dispatch unsolicited work. AI/native management is separated from explicit owner approval in [authorizeWorkerControl](../repo/swarmd/internal/run/worker_control.go), lines 17–58. An agent must resolve to a real Orchestrator session to control workers. A worker cannot simply approve itself.

### Routing, execution, tools and concurrency

[taskrouter/service.go](../repo/swarmd/internal/taskrouter/service.go), lines 51–125, first derives the execution contract from structured intent, agent and feature-size parameters. An optional model elaborates titles, mission or plans but cannot silently change that authoritative route. This is a useful limit on a probabilistic router. Project execution still validates account/project/source identity; selection of a project is not implicit authority to write any directory associated with it.

Worker [Dispatch](../repo/swarmd/internal/run/worker_execution.go), lines 248–360, rejects remote placement, pending/unaccepted workers and unsupported capabilities; resolves the actual workspace/project; captures the exact model and worker revision; admits an idempotent receipt; then starts it. [Start](../repo/swarmd/internal/run/worker_execution.go), lines 365–475, re-reads that receipt, checks cancellation/budget/admission state and current automation availability, loads the accepted revision, and constructs a plan or direct job. A direct job gets a small checkpoint document rather than a fictional permanent human-like agent loop. System roles determine whether work uses plan execution or a direct session. Worker executions use the existing V3 engine, not a parallel transcript store.

Permission checks and tool scopes are enforced separately from prompts. Child launch builds an approval manifest in [service_task_launch.go](../repo/swarmd/internal/run/service_task_launch.go), lines 4141–4445, capturing targets, resolved tools, profile and scope. The same file rejects model-supplied trust fields at lines 2594 onward and overlapping concurrent owned scopes at lines 1274–1278. Sandbox execution is another layer, with manager state and command admission in [sandbox.go](../repo/swarmd/internal/sandbox/sandbox.go), lines 31–107, 213–289 and 943–1033, plus scoped Git protection. These mechanisms warrant qualification on Wingman's actual macOS/Linux configurations. This inspection does not establish sandbox protection merely because policy text requests it.

Independent launches genuinely execute concurrently via the goroutine/wait-group implementation at [service_tools.go](../repo/swarmd/internal/run/service_tools.go), lines 5214–5233. Task programs select only nodes whose declared dependencies are completed/integrated, choose a bounded cohort and launch it in [service_task_program_scheduler.go](../repo/swarmd/internal/run/service_task_program_scheduler.go), lines 79–172 and 228 onward. This is local concurrency subject to account capacity, budget and sandbox admission. Neither a configured maximum nor test-fixture job counts is evidence of observed provider-backed scale.

### Continuity, scheduling, interruption and recovery

Session mutations and the durable outbox retain conversation/work state. Worker history pins the definition used by each run, so changing today's worker does not silently rewrite yesterday's receipt. The worker itself carries continuity across separate job sessions; Wingman would need to decide which project knowledge goes into standing instructions/memory and which conversation should remain the long-term individual identity.

Scheduling is real runtime code. [WorkerScheduler.Run](../repo/swarmd/internal/run/worker_wake_scheduler.go), lines 283–365, combines timer-driven due work with committed change signals. [TickWorker](../repo/swarmd/internal/run/worker_scheduler.go), lines 41–138, computes interval/cron slots, checks active state and budget, avoids overlapping unfinished runs of the same automation, and uses an occurrence identity for admission. Offline/missed slots are skipped rather than replayed. This offers a periodic execution primitive, not built-in management supervision: [automation_context.go](../repo/swarmd/internal/run/automation_context.go), line 26, expressly warns against claiming unsupported blocker supervision. A separately authored periodic inspection workflow would still skip missed slots after a host outage.

User stop goes through [CancelRun](../repo/swarmd/internal/api/sessions_v3_executor.go), lines 701–811, recording the durable outcome and cancelling owned runtime context. Worker stop/pause coordinates state with unfinished runs through [ReconcileStop](../repo/swarmd/internal/run/worker_execution.go), line 1082 onward; resume and explicit run cancellation are at lines 2071–2133. UI text correctly exposes stopping/cancellation as awaiting acknowledgement, [worker-hub.tsx](../repo/web/src/features/desktop/orchestrate/worker-hub.tsx), lines 101–108 and 156–161. It does not immediately label a still-running process stopped.

Restart is not magical continuation from an arbitrary CPU instruction. [recoverDurableRuns](../repo/swarmd/internal/api/sessions_v3_executor.go), lines 980–1050, scans durable running intents and marks interrupted execution, then refills pending work. Worker reconciliation at [worker_execution.go](../repo/swarmd/internal/run/worker_execution.go), lines 1497–1595, reconciles receipts, budget holds, cancellation, review restore and execution intent. [worker_watchdog.go](../repo/swarmd/internal/run/worker_watchdog.go), lines 63–100, avoids falsely declaring a quiet provider run stalled when an executor still owns it. Pending/recoverable work, interrupted runs, explicit task reopen and model context reconstruction are distinct. The presence of a scheduler/reconciler does not imply safe automatic replay of arbitrary external tool side effects.

Task-program records retain stages/jobs/lanes across store reopen, but their transitions are a separate authority from V3 event batches. Owning-run termination and stage blockers require reconciliation. The code does not justify claiming exactly-once provider calls or seamless recovery across every filesystem/Git/store crash window. Later semantic work requires an explicit declared revision rather than the scheduler inventing new nodes to escape a blocked graph.

### Completion, acceptance, retirement and cleanup

Execution completion is several things. A provider run can finish; its worker receipt can succeed. A project task can become `needs_review`; Git commits can be present; integration can succeed. The user can accept the product. Swarm represents these separately enough to avoid treating a finished stream as delivery. [projects_task_git.go](../repo/swarmd/internal/api/projects_task_git.go), lines 25–108, uses captured source/session/Git evidence and delivery classification. [task-card-summary.tsx](../repo/web/src/features/desktop/orchestrate/task-card-summary.tsx), lines 28–57, explicitly reports missing inspection/integration evidence instead of inferring success from clean files.

The independent reviewer examines the exact base/head, requirements, report and actual command receipts; see [system_reviewer.go](../repo/swarmd/internal/agent/system_reviewer.go), lines 9–41. Its ordinary role is read-only and expressly does not execute tests. It judges the producing job's evidence. The opt-in security-fixer role at lines 55–95 can make bounded fixes under a different contract. Neither should be confused with Wingman's functional TestMaster running integrated business acceptance scenarios.

Post-job workflows can review, reopen/send feedback, run operator-owned scripts and deliver. [jobautomation/runner.go](../repo/swarmd/internal/jobautomation/runner.go), lines 17–26 and 74–125, carries exact job result/head and suppresses recursive automation spawning via the request-source distinction. [deliver.go](../repo/swarmd/internal/jobautomation/deliver.go), lines 11–31 and 44–99, supports folder copies, merges, PR publication and outbox exports with bounded path rules. Wingman can use those as acceptance/delivery building blocks after defining its own acceptance policy.

Retirement is durable state, not just hiding a UI row. Worker lifecycle includes archive/delete; stop reconciliation waits for executions. Session ending at [sessions_v3_agent_sessions.go](../repo/swarmd/internal/api/sessions_v3_agent_sessions.go), lines 23–40 and 95 onward, closes confirmations, stops runs and prevents subsequent messages/takeovers. Session archive has its own V3 path in [sessions_v3_primary.go](../repo/swarmd/internal/api/sessions_v3_primary.go), lines 1499–1625. Review cleanup is separately retried and tracked in [worker_cleanup.go](../repo/swarmd/internal/run/worker_cleanup.go), lines 10–73; program worktree cleanup occurs after integration, [service_task_program_scheduler.go](../repo/swarmd/internal/run/service_task_program_scheduler.go), lines 1290–1350. Wingman should preserve artifacts and unresolved dirty work before selecting destructive cleanup operations.

## Coordination mechanics and one traced request

The primary coordination medium is **durable project tasks plus conversation lineage and events**. Agents hand off source commits, bounded reports and artifacts. A task program carries explicit dependency evidence; ordinary child delegation supplies self-contained assignments. Source membership, the integration destination and the captured child base are checked independently. A project chat can coordinate multiple sources without acquiring an ambient writable checkout.

There is no verified shared multi-agent room conversation here. `manage-sessions send_message` is a controlled session-feedback facility; task-to-Orchestrator reports and wakeups deliberately use `manage_projects report_task`/`wait_tasks`. That distinction prevents a child's arbitrary message from masquerading as a new user request or causing duplicate work. [runtime_manage_sessions.go](../repo/swarmd/internal/tool/runtime_manage_sessions.go), lines 39–47, explicitly separates saved/queued, delivered and incorporated feedback; successful storage alone does not prove the model used an instruction.

The following is an implementation trace of an Orchestrator request to make two independent changes under one task card. It was not executed during this assessment.

1. **Research/select the authorized source and propose.** The native `manage_projects` tool supports source inspection and `propose_task`. The executable dispatch at [runtime_manage_projects.go](../repo/swarmd/internal/tool/runtime_manage_projects.go), lines 835–1040, assembles structured input and calls the canonical lifecycle. A proposal can include `coder_assignments` with exact repository, owned scope, deliverable and acceptance criteria. The prompt documents this intended workflow, but the server validates it.
2. **Create one real task.** [CreateProjectTask](../repo/swarmd/internal/api/project_task_program.go), lines 110–230, checks principal/project/origin and existing idempotent admission. Lines 203–217 reject combining small parallel assignments with incompatible plans/programs and select a Swarm parent. Source identity is resolved before reservation. The task record persists the proposal. It is not itself evidence execution launched.
3. **Review/approve the current proposal.** [ApproveProjectTask](../repo/swarmd/internal/api/project_task_program.go), line 1128 onward, validates pending state and supplied plan/revision guards. A structured plan always retains its card-review requirement; direct delegation can have different authorized auto-approval behavior. The deployment boundary at lines 1607 onward launches against the authorized source, not an arbitrary UI-selected folder.
4. **Allocate children and run concurrently.** Swarm's task tool resolves profiles/model policy, checks the approved launch manifest and non-overlapping scopes, creates V3 child sessions and separate worktrees, then invokes parallel launches. The relevant authority is [service_tools.go](../repo/swarmd/internal/run/service_tools.go), lines 1243–1665, 5214–5233 and 5782–6251. Each child produces its own tools/messages/commits and remains separately inspectable through lineage.
5. **Release coordination capacity while waiting.** For project-level delegated outcomes, `wait_tasks` in [runtime_manage_project_tasks.go](../repo/swarmd/internal/tool/runtime_manage_project_tasks.go), lines 49–83, requires trusted current run context and 1–16 task IDs. It mutates the V3 run to `waiting_tasks` and yields rather than keeping a provider call polling. [project_task_wait.go](../repo/swarmd/internal/api/project_task_wait.go), lines 22–43, reconciles task outcomes, publishes the committed outbox and enqueues a continuation with preserved identity.
6. **Surface actual outcomes, review, integrate.** [project_store.go](../repo/swarmd/internal/store/pebble/project_store.go), lines 423–523, links worker/session/attempt and delivery facts. Task cards render live focus and verifiable Git/outcome facts. The native and HTTP integration paths converge on one service. The inspected [project_task_integration_test.go](../repo/swarmd/internal/api/project_task_integration_test.go), lines 39–150, constructs real temporary Git commits/worktrees, first rejects stale selection without changing the target, then exercises both ingress paths. This is test-source evidence of intended contract, not a test result from this assessment.

For staged dependencies, a Task Program replaces step 4's ordinary parallel call: readiness, artifact/source handoff, per-repository integration and next-stage launch are explicit. A completed sibling task is insufficient if its commit is absent from the next child's actual source base. That is a particularly consequential difference from simplistic “share a task ID and continue” orchestration.

## Major capabilities beyond the Wingman description

**Provider and execution-policy infrastructure.** Swarm resolves account-specific system-agent model assignments and snapshots policy at admission. It separates role authority, model preference, tools, source binding and runtime sandbox. Usage budgets can close admission and cancel/follow up through durable receipts rather than relying on the UI. See [worker_execution.go](../repo/swarmd/internal/run/worker_execution.go), lines 296–331 and 393–475, and [worker_budget.go](../repo/swarmd/internal/run/worker_budget.go), lines 23–64. This is valuable for cost-controlled autonomous work, but Wingman must translate its own goal budgets, model policy and host constraints into those contracts and qualify late-provider-receipt behavior.

**Multimodal production and browser-checked design.** The code includes image/video/audio generation, artifact storage and a bounded standalone-HTML design pipeline. [design/pipeline.go](../repo/swarmd/internal/design/pipeline.go), lines 17–89, 101–125 and 219–258, validates the request, limits concurrency, runs structural/browser checks and permits a bounded repair. An unavailable check remains an unavailable result. Wingman can use this for deliverable mockups and media without making a separate product team build those services. Integration entails handling native artifacts, provider credentials and explicit verification status; design checks are not general application acceptance tests.

**External-AI control and embedded consumer applications.** [control_mcp_tools.go](../repo/swarmd/internal/api/control_mcp_tools.go), lines 23–45 and 78–127, maps bounded MCP tools through canonical HTTP routes; [control_mcp.go](../repo/swarmd/internal/api/control_mcp.go), lines 352–398, applies read/write/approve/manage levels in addition to underlying scopes. Application agents add revisioned principal-owned instructions, scoped sessions and links to canonical tasks/workers. Wingman can remain its own organizational app while using Swarm execution, rather than making every workflow an internal daemon patch. This still requires a gateway and consistent identity mapping; MCP control is not a Telegram adapter.

**Post-job workflow and delivery engine.** `jobautomation` can consume terminal signals and run reviewer/agent/script/reopen/delivery steps. Delivery includes PR publication and exportable outbox manifests, beyond the Wingman purpose's high-level delivery statement. Operator-owned script execution is a distinct powerful surface, [jobautomation/runner.go](../repo/swarmd/internal/jobautomation/runner.go), lines 43–73, so integration should use the accepted workflow authority rather than allowing specialist prompts to define arbitrary publishing operations.

**Memory with provenance and bounded extraction.** [memory/service.go](../repo/swarmd/internal/memory/service.go), lines 1–39, gives memory extraction a tool-free role; source fragments are untrusted facts and cannot mint permissions/rules. Explicit edits preserve provenance at lines 76–104. This can help long-running project continuity while avoiding uncontrolled promotion of chat text into organizational directives. It is not a substitute for Wingman's reviewed scope/specification files.

## Distinctive mechanisms worth carrying forward

These are grounded design mechanisms, not claims that Swarm invented them or is unique in the industry.

1. **Durable yield on task outcomes.** `wait_tasks` persists a waiting intent and the exact selected task/attempt context, then resumes through canonical reconciliation. It avoids repeated model polling while preserving an accountable parent conversation. Its boundary is project task outcomes. It does not create general multi-party rooms, and superseding user/stop/archive actions need to invalidate the waiting continuation correctly. The production path is [runtime_manage_project_tasks.go](../repo/swarmd/internal/tool/runtime_manage_project_tasks.go), lines 49–83, and [project_task_wait.go](../repo/swarmd/internal/api/project_task_wait.go), lines 22–59.
2. **Separate source materialization from mutation ownership.** Task-program jobs carry narrow `owned_scope` while source/dependency hydration and repository integration lanes preserve the committed prerequisites needed to build. Stage launch is gated on completed/integrated dependencies; separate repositories get separate lanes rather than one accidental parent checkout. See [service_task_program_scheduler.go](../repo/swarmd/internal/run/service_task_program_scheduler.go), lines 148–172, 851–1083 and 1098–1289, with [task_program_store.go](../repo/swarmd/internal/store/pebble/task_program_store.go), lines 46–103. This enables staged specialist work with reviewable authority. Unsupported source/artifact handoffs and absent prerequisites still block. A program lane does not itself promote the user's source branch.
3. **One durable authority across transports.** Session changes carry idempotency and outbox through the mutation boundary, while native tools and MCP/HTTP use shared lifecycle services. This reduces divergence between “the UI says done” and actual stored execution. It does not make Git/filesystem operations and every project/program store transition one distributed transaction. Preserving the separate reconciliation limits is part of the design's value.
4. **Accepted standing definitions with pinned execution receipts.** Worker definition revisions, binding/model capture, runtime admission checks and acknowledgement-based stopping distinguish what was approved from what is executing now. Custom instructions overlay a code-owned role without inheriting administrative power. See [worker_store.go](../repo/swarmd/internal/store/pebble/worker_store.go), lines 105–198, [worker_execution.go](../repo/swarmd/internal/run/worker_execution.go), lines 190–475, and [worker_agent.go](../repo/swarmd/internal/run/worker_agent.go), lines 15–111. This is a strong basis for a standing organization, but the enduring worker is a job identity with many sessions, not automatically the exact personal conversational identity Wingman describes.
5. **Evidence-aware status instead of optimistic completion labels.** Task views distinguish unknown Git state, unintegrated commits, missing validation, blockers and delivery. Independent review consumes actual command evidence rather than simply accepting a model's success claim. See [task-card-summary.tsx](../repo/web/src/features/desktop/orchestrate/task-card-summary.tsx), lines 28–57, and [system_reviewer.go](../repo/swarmd/internal/agent/system_reviewer.go), lines 9–24. The implementation still depends on proper capture and validation; displaying a report cannot prove a product is accepted.

## Practical adoption boundary

Wingman could use the following directly after revision-specific qualification: V3 conversation/run storage and streaming; independent Coder/Finder/Designer jobs; authenticated project/task APIs. The worker catalog, schedules, histories and budgets; structured plan approval; source-scoped worktrees and Git integration; and session drill-down UI patterns. The native app and external-control paths make Swarm a plausible backend for an organizational frontend.

Adaptation is needed for specialist profiles and team lifecycle. BackendCoder/FrontendCoder/MobileCoder/TestMaster can be custom instructions with appropriately narrowed execution contracts, but their role, project and reporting relationships need an explicit Wingman record. ProductMaster/TechMaster should be actual independently addressed conversations/work identities with approved tools, not renamed labels on a single Orchestrator. Projects need Wingman's DIRECTIVES knowledge conventions and defined links among specifications, tickets, conversations, review evidence and deliverables. Worker job sessions versus enduring agent conversations needs a deliberate mapping.

Still to build are:

- the incoming Telegram Butler gateway and correlation of human answers.
- portfolio intake/routing policy.
- automatic per-product leadership/team establishment.
- real Room1/Room2 membership/history and agent-to-agent discussion.
- periodic management reasoning/follow-up policy.
- executive summaries and curated agent timelines.
- functional acceptance against business scenarios.

Most critically, **shared Mac/Endeavour execution is not a supported completed worker path in this revision**. A production distributed coordinator would need authenticated dispatch, remote source/artifact transport, executor fencing/heartbeats, cancellation, durable outcome reconciliation and explicit host routing. Existing target descriptors and SSH probes are preparatory primitives only.

The repository's breadth is both a benefit and a cost. A focused adapter can reuse a large amount of machinery, while a fork would inherit a daemon/TUI/desktop/media/security/storage/release platform. The best initial fit is a bounded local Wingman slice—one project, approved independent specialists, durable tracking and session visibility—followed by qualification of continuity and integration before expanding into autonomous portfolio management or remote execution.
