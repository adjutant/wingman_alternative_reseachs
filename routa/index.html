Routa assessment against Wingman

Identity, revision and verdict

  • Product: Routa.js, a workspace-oriented multi-agent development workbench; package version 0.19.0, MIT licensed (package.json, lines 1–18; LICENSE, lines 1–21).
  • Upstream: https://github.com/phodal/routa
  • Local checkout: research/routa/repo.
  • Actual inspected commit: 9dc7b7be8fa92b760f6ebf0ac7f8b44db1b4dc34.
  • Assessment date: 2026-11-05.
  • Target: Wingman purpose; method: assessment guide.

Verdict: a substantial execution, coordination and inspection substrate for Wingman, but not the standing personal development organization itself. Routa does run independently executing coding agents, rather than simply switching personas inside one model call. It combines those sessions with specialist configurations, task contracts, shared notes, a real task board, parent/child delegation, verification roles, periodic automation supervision, persistence and detailed session inspection. These are directly relevant building blocks. Its Team experience is organized around a lead session and temporary execution waves; its canonical lead instructions explicitly discourage creating the future roster in advance. Wingman's persistent organization, portfolio-level ProjectMaster, separate per-product ProductMaster/TechMaster, Telegram Butler, room-based organizational communication and executive current/recent/next briefings still need substantial product and orchestration work.

The strongest reason to study Routa is the connection between task state, execution attempts, evidence and recovery. The largest adoption risk is treating all of its completion and persistence paths as equivalent. A basic child report can directly mark a task complete. A separate Kanban path adds contract, delivery and transition gates. Persistent task/session rows coexist with process-local orchestration maps, queues, permissions and workflow-run records. Dual-backend semantic parity is an explicit design goal, not something this assessment has established by running both backends.

Architecture and actual execution model

Entry points, runtime boundaries and storage

The web surface is a Next.js application. /api/acp handles session creation, prompting, loading and cancellation; session CRUD and transcript routes support the workbench around that execution interface. The creation handler resolves specialist/provider/role/model settings, assembles contextual instructions and registers execution metadata. It then chooses an ACP CLI, Claude adapter, SDK adapter, Docker adapter or native workspace agent. See ACP route, lines 452–500 and 501–792, and creation handler, lines 270–380 and 532–866. Native workspace agents are model/tool execution adapters, not necessarily a separate operating-system process. The CLI-backed path does spawn one.

For standard CLI execution, AcpProcessManager, lines 223–295, prepares session-specific MCP configuration, builds a provider command, starts an AcpProcess, initializes it, calls newSession, sets execution context and stores the process under the Routa session ID. The orchestrator's child-spawn path dispatches the initial task prompt and normalizes updates for both the child's history and its parent's stream (orchestrator, lines 815–1038). External CLI/SDK runtimes perform coding; Routa supplies coordination and a uniform transport/view of their work.

RoutaSystem, lines 63–124, 131–201 and 212–275, assembles stores and domain services. Postgres stores persist agents, conversations, tasks, notes, workspaces, codebases, worktrees, schedules, boards, artifacts and background tasks. Local SQLite provides corresponding stores; unavailable SQLite native modules cause a fallback to in-memory stores. Even the Postgres and SQLite factories instantiate InMemoryWorkflowRunStore and an in-memory PermissionStore (lines 154–158 and 226–229). Event buses and CRDT document managers are process-local. Therefore “persistent mode” does not mean every coordination concern survives server restart or is shared between application instances.

Desktop normally starts an embedded Rust/Axum backend, opens SQLite and shares one AppState between HTTP routes and Tauri JSON-RPC IPC. It serves the exported frontend with placeholder-route resolution. The shell also retains legacy embedded Next-server and external-server modes. These are actual alternative bootstrap branches, not just README deployment suggestions: desktop bootstrap, lines 64–79, 651–710, 793–843 and 1146–1238; server bootstrap, lines 74–99; Rust state assembly, lines 54–84. Rust has its own agent/task stores, ACP manager, orchestration, sandbox and workflow implementations. The report traces the TypeScript paths most deeply and samples the Rust implementations. It does not silently transfer every TypeScript finding to the Rust backend.

Domain objects that must not be conflated

Concept Actual meaning in this checkout
Specialist/profile Reusable behavior configuration: ID, display name, a core role, model tier/model, prompt/reminder and optional provider/adapter defaults. It is not itself a running agent.
Agent An independently identified coordination record with workspace, parent, status, timestamps and metadata; creating the record alone does not start execution.
Session A live or historical execution thread, with provider/session identity, cwd, workspace, role, parent session and history. It can outlive the process used for one run.
Process/adapter The live execution resource. CLI processes, SDK streams and native workspace-agent adapters have different capabilities and cancellation/resume behavior.
Task/card Durable work with objective, scope, acceptance criteria, verification commands, dependencies, assignee, evidence, board position and execution-attempt history.
BackgroundTask/workflow run Automation dispatch state, distinct from the user-facing task/card. Workflow steps become background tasks with dependency edges.
Team A lead run plus related spawned members and their records/UI projections. It is not a separate durable organizational hierarchy with permanent product leadership.

Evidence: agent model, lines 7–69; specialist type, lines 3–20; task model, lines 122–168 and 835–900; workflow executor, lines 43–93 and 125–151. This distinction matters for Wingman: durable records provide identity continuity, but do not by themselves constitute continuously responsible autonomous employees.

Agent definition, creation and lifecycle

Definitions and the difference between template and person

The reusable specialist schema includes id, name, role, defaultModelTier, systemPrompt, roleReminder, optional model/provider/adapter, source and locale. The current file loader scans YAML/YML recursively; its header and implementation should take precedence over an older ADR's Markdown-plus-YAML description. It resolves four allowed core roles and supports user profiles under ~/.routa/specialists/, bundled resources and fallback definitions. Same-source duplicate IDs throw rather than silently overwriting. See file loader, lines 89–151, 181–189 and 210–240; specialist type, lines 3–20. Postgres supports profile CRUD, but local SQLite web API profile writes explicitly return 501. A new BackendCoder-like profile can be represented as a named CRAFTER specialist without changing the role enum; adding a fundamentally new runtime role requires code/schema/API/UI adaptation.

Runtime identity is separate. createAgent allocates a UUID and persists name, workspace, parent, role/tier and metadata with status PENDING, emitting AGENT_CREATED. It does not launch a runtime (agent tools, lines 348–396). The Team lead's profile instructs the model to keep names as metadata and instantiate only members with ready work. It calls the roster templates protected definitions and runtime labels ephemeral (lead, lines 28–40 and 68–76). This is a deliberate temporary team model. A record can be durable without representing the permanent Butler or ProductMaster relationship Wingman needs.

Creation and dispatch

Session creation resolves requested specialist and provider, role/model overrides, tool policy, workspace and cwd, then persists and starts the selected backend. In the Claude SDK path, effective model selection has an explicit chain: supplied model, specialist model/tier, role model override, then adapter defaults (instance factory, lines 114–166). Do not assume every child-spawn branch applies every factory setting: the direct delegated Claude SDK branch passes only its provider option, while the delegation prompt includes specialist instructions (orchestrator, lines 978–985). Configuration behavior is path-dependent.

The enhanced delegation tool validates recursion depth and specialist, then loads a task. It creates a child identity with parent, roster and depth metadata. Parent traces and learned playbooks enrich context. The tool builds the task prompt and assigns the task. It marks the identity ACTIVE and creates a child session. It registers the child for independent UI access, stores parent/child relationships and emits TASK_ASSIGNED. Those are materially stronger semantics than the low-level delegate, which just changes assignee/status and appends a message. See orchestrator, lines 494–749; basic delegation, lines 401–455. Neither the creation of an identity nor a text delegation should be mistaken for successful execution startup.

Tools, permissions and human questions

Routa supplies MCP collaboration tools for tasks, notes, agents, messaging, artifacts and workspace operations. CLI adapters also retain provider-native coding tools. The native/SDK execution interfaces are not one uniform security boundary. For example, the Claude SDK adapter defaults to Skill, Read, Write, Edit, Bash, Glob, Grep. It builds an SDK allowlist, denies unlisted native tools and routes AskUserQuestion through an interactive handler. At the same time it sets SDK bypassPermissions and permits attached mcp__* tools in its callback (SDK adapter, lines 213–225, 256–278 and 372–421). The lead-specific session-creation policy returns an empty native-tool list, making lead delegation more concrete than a prompt-only “never implement” rule for that path (creation handler, lines 148–160).

Worker permission requests are stored, appended to the designated coordinator conversation and emitted as events. The designated coordinator may respond, optionally applying sandbox constraints. That is agent escalation, not automatic human escalation (agent tools, lines 1421–1536). Rust sandbox permission constraints model read-only/read-write paths, environment allowlists, capabilities, network mode and linked worktrees, and merge them into resolved policy (permission constraints, lines 10–86). Wingman would need an explicit policy deciding which requests a TechMaster can resolve and which Butler must put before the human.

Routing, concurrent execution and dependency ordering

Workspace IDs scope durable records; agent IDs identify coordination actors; Routa session IDs identify viewer/history threads; provider session IDs identify native runtime conversations. Parent agent and parent session are separate fields. Team members are registered with both, enabling navigation from lead to worker. The orchestrator can notify the parent immediately per completion or accumulate after_all groups and wake it when all children finish (orchestrator, lines 686–734 and 1298–1404).

Board automation uses an in-memory per-card/per-board queue and a configurable concurrency resolver. It deduplicates running/queued cards, removes stale entries after card movement and drains capacity on lifecycle events (queue, lines 29–110, 134–194 and 223–247). Workflow parallel groups have a different implementation: each contiguous group becomes background tasks depending on all tasks of earlier groups. The background worker runs at most two tasks and calls listReadyToRun before dispatch (workflow executor, lines 57–122; background worker, lines 25–26 and 64–112). These are multiple concurrency mechanisms, not one global organizational scheduler. Direct spawned delegation loads a task but does not check that its dependencies are completed. The lead must choose ready tasks or the execution path must be strengthened.

Remote execution is concrete but bounded. A configured runner receives HTTP-proxied session operations; embedded ownership leases prevent taking a still-owned session onto another instance, and even an expired embedded lease is reported as non-resumable on another instance (execution backend, lines 47–97). A2A lane steps send a structured task to a remote agent card/RPC endpoint, poll its status and convert completion/failure to local events. This is real remote work, but repository availability, artifact transfer, agent identity mapping and cross-host conversational rooms are not supplied simply by selecting A2A.

Persistence, resume and scheduling

Session lists hydrate metadata from database, then derive active/interrupted/restorable/stale labels from process presence, provider capability and age (sessions API, lines 16–69 and 144–195). session/load looks in memory, database and local storage, checks ownership, attaches an existing process or attempts native provider resume, falling back to recreation (ACP route, lines 501–635). History persistence and runtime continuity are therefore different guarantees. The provider's own context recovery matters; displaying the old transcript does not prove a new process possesses all previous reasoning or tools state.

The orchestrator's child registry, agent-to-session map, wait groups, report watchers and event bridges are Maps (orchestrator, lines 223–263). Persistent agent/task rows do not reconstruct all of those relationships automatically. Conversely, Kanban has explicit restart recovery: it sanitizes stale trigger/lane sessions using process/lease ownership, retains their attempt history and revives entry automation or resumes the next review step (restart recovery, lines 21–118 and 180–210). This is valuable scoped recovery, not universal restoration of a whole organization.

Node startup explicitly starts a minute-level scheduler and background worker after a delay (instrumentation, lines 20–62). Schedules create new BackgroundTasks with prompt, specialist/agent selector and workspace, then update nextRunAt. They do not necessarily wake the same durable agent conversation (schedule tick, lines 15–48). This can implement scheduled supervision jobs, but the ProjectMaster review/follow-up behavior is still application logic to supply.

Interruption, failure, retries and recovery

Cancellation forwards to the active provider's cancel operation; disconnect first saves consolidated history, then kills its execution resource. These are distinct operations (ACP cancellation, lines 744–792; disconnect, lines 37–45). Killing includes removing the appropriate managed process/adapter and session MCP cleanup; Docker also stops the container (process manager, lines 1154–1207). A graceful shutdown tool only appends instructions/emits events to active children; acknowledgement changes their agent records to COMPLETED. Its timeoutMs is returned/emitted, not a kill deadline enforced in that function (agent tools, lines 1563–1626).

Spawn failure marks the new agent ERROR and task BLOCKED. A running child's error marks ERROR/NEEDS_FIX, records an error summary and wakes the parent to decide what follows (orchestrator, lines 675–682 and 1496–1525). Board supervision goes further: configurable watchdog/loop mode, inactivity threshold, recovery-attempt bound and completion requirement determine whether to restart a lane session. Defaults are ten minutes, one recovery attempt and turn completion; ralph_loop can demand a completion summary or verification report (supervision config, lines 7–24 and 42–65; workflow orchestrator, lines 548–674 and 746–812). It is bounded automation, not infinite persistence until product acceptance. A separate failed-background-task retry endpoint checks attempts/maxAttempts before resetting to PENDING (retry route, lines 20–47).

Completion, acceptance and retirement

reportToParent changes a task to COMPLETED or NEEDS_FIX according to the supplied success, saves its summary, marks the worker COMPLETED and appends a parent report. The orchestrator also waits two seconds after an apparently successful turn and auto-submits a success report if the worker omitted one (agent tools, lines 499–548; automatic report, lines 1045–1079). The wake-up message asks the parent to review results and suggests delegating GATE. It does not make independent verification mandatory in this path (lines 1360–1383). The lead prompt's stronger verification requirements are instructions, not proof that this lower-level task status represents accepted product delivery.

Kanban adds stronger, configurable boundaries: checked checklist labels, verdict-based approval, textual validator evidence, artifacts, and real Git branch/cleanliness/commit readiness. However the validator gate parses task text for a command plus pass-like wording. It does not execute that validator. The “required human approval” condition tests verificationVerdict === APPROVED, while updateTask itself accepts a verification verdict from an agent. It therefore establishes a shared verdict requirement rather than authenticated human acceptance (transition gates, lines 58–76 and 127–140; task update, lines 849–905). Git delivery checks are operationally stronger but can permit missing repo linkage in the no-linked-repository case (delivery readiness, lines 167–198). Wingman should explicitly separate “worker turn finished,” “ticket verified,” “integrated product accepted” and “development stopped.”

Retirement is likewise split. Session rename/delete persists metadata changes; delete removes session history/buffers/SSE state from the HTTP store but does not call the process manager's kill routine. Disconnect is the explicit kill path. Fork creates a new linked metadata record with inherited provider/cwd/role/model, without copying the parent's transcript or starting a runtime in that handler (session CRUD, lines 106–194; HTTP store, lines 280–293; fork, lines 77–119). These controls should not be presented as full native conversation fork/archive/retirement parity. Agent histories, tasks, worktrees and project knowledge need a coordinated retention/cleanup policy when adopting this model.

Coordination mechanics and a traced request

The principal coordination channels are persisted task/note/conversation stores, in-process events, execution streams and direct prompts. messageAgent appends to the recipient's conversation and emits MESSAGE_SENT; that function alone does not send a prompt into a live adapter. Event subscriptions buffer matching events until drained. The EventBus stores subscriptions, pending events and wait groups in memory. It filters by event type and self exclusion. Events contain a workspace ID, but emit does not use it as a subscription filter (event bus, lines 47–67 and 82–179). Wingman should require explicit workspace/recipient routing and durable delivery semantics, especially when expanding beyond one server process. This is a boundary finding, not a full security audit.

Shared notes supply a specification space rather than chat rooms. Note tools provide spec/task/general notes, automatic spec creation and optional conversion of embedded task blocks; replacing a spec also removes stale PENDING derived task notes from the same session (note tools, lines 118–166). CRDTNoteStore updates Yjs-backed documents and broadcasts real-time changes, but its own backing notes Map is memory-resident; persistent factories substitute database note stores (CRDT store, lines 1–23; RoutaSystem, lines 144–168). The existence of a CRDT manager should not be read as identical durable concurrent editing semantics in every storage mode.

The following is a code trace of the implemented Team delegation request, not an executed product demonstration:

  1. The human creates a workspace-scoped lead session. session/new loads team-agent-lead, derives role/provider and applies its no-native-coding-tools policy. It registers the root session and initializes orchestration (creation handler, lines 103–160, 270–380 and 744–813).
  2. The lead receives the human's request through session/prompt. Its profile tells it to create tasks with goals/scope/acceptance criteria, research unknown context and dispatch a small wave. Those choices remain model behavior (lead profile, lines 55–79). create_task actually saves the structured record (agent tools, lines 224–250).
  3. A delegate_task_to_agent MCP call is routed into delegateTaskWithSpawn, carrying task, caller, session, workspace, specialist and wait mode (MCP executor, lines 411–437). It creates the child identity and execution session, assigns the task and emits TASK_ASSIGNED. This is the point at which a conceptual specialist becomes an independently executing worker.
  4. The child receives objective/scope/Definition of Done/tests/commands plus relevant parent trace/playbook context. Its runtime calls tools and streams updates. Normalized notifications are retained under its own session and forwarded to the parent with child identifiers (orchestrator, lines 590–649 and 851–887). The human can open that child separately.
  5. During work, task changes and notes provide shared state; send_message_to_agent appends direct collaboration, artifact request/provision tools exchange structured outputs, and a permission request can be addressed to the coordinator (agent tools, lines 461–494, 1050–1180 and 1421–1475). This supports a backend/frontend contract discussion, but a message append is not proof of immediate peer processing.
  6. On report_to_parent, task outcome and conversation history are updated and REPORT_SUBMITTED is emitted. The orchestrator deduplicates completion handling, writes completion/outcome memory, cleans event bridges/watchers, and either waits for the group or prompts the parent (orchestrator, lines 392–450 and 1251–1404). The parent can dispatch QA/review or corrective work. A reviewer can update verdict/report, but ordinary completion itself is not independent product acceptance.
  7. Team UI combines lead messages, child lanes, task tree, member previews and deliverables, with viewer links and question responses (Team sections, lines 24–249; Team client, lines 1057–1131 and 1196–1283). This connects work to inspection without creating Wingman's permanent management/project rooms.

Kanban is an additional orchestration entrance: column transitions resolve source exit automation before target entry automation, enqueue sessions, run lane steps, supervise inactivity and converge review verdicts back to development/done. The transition policy is code, not merely visual drag-and-drop (column transition, lines 53–76; workflow orchestrator, lines 278–399 and 405–539). Wingman could use this as a ticket execution engine while retaining conversational product/technical leadership above it.

Major additional capabilities beyond the Wingman description

Three-stage automated Git review service

Routa has a concrete review product separate from asking a spawned GATE agent to review a task. POST /api/review/analyze accepts a repository, base/head, rules file and analysis/validator model overrides, then calls analyzeReview. That service gathers the Git diff, configuration snippets, optional graph context and historical related files, and makes three sequential model calls: context gathering, candidate findings, then finding validation using the previous outputs (review route, lines 7–19; review analysis, lines 43–107). These internal review workers are stateless model invocations under one reviewer specialist, not three persisted independent agent sessions. They call an Anthropic-compatible /v1/messages endpoint directly; ANTHROPIC_AUTH_TOKEN or ANTHROPIC_API_KEY is required, base URL is configurable, and the fallback model is GLM-4.7, so endpoint/model compatibility must be configured rather than assumed from an existing Codex login (lines 142–200). The diff is truncated at 40,000 characters and output parsing tolerates unparseable text as a raw object (lines 97 and 203–221). This can give Wingman a reusable review pipeline and a distinct validation pass, but integrating it requires credentials, context-size handling and an explicit mapping from findings into tickets/acceptance. Model-mediated validation is not a test execution result or authenticated human approval.

Repository-to-PowerPoint artifact workflow

RepoSlide is another substantive product surface: its repository page launches a workspace-scoped DEVELOPER ACP session, passes a generated repository-presentation prompt plus the selected slide skill as pending input, and navigates to the detailed session (RepoSlide client, lines 124–173). Launch context scans repository structure and resolves slide-skill from tools/ppt-template/.agents/skills/slide-skill/SKILL.md; missing skill resources or an unavailable provider block launch (launch builder, lines 99–135; client, lines 135–140). The prompt asks the coding agent to inspect local evidence, produce a concise six-to-eight-slide PPTX and report its path (builder, lines 159–189). A session-result reader extracts that result from history/traces, and an explicit download route proxies runner-owned sessions or serves the resolved deck with a PPTX content type (result reader, lines 13–26; download route, lines 17–51). Artifact resolution requires an existing absolute .pptx file whose real path lies within session cwd or the system temporary directory (artifact boundary, lines 17–46). This could support Wingman's engineering briefings and onboarding deliverables, beyond its specified coding workflow. Generation depends on provider/model capability, provider credentials and the skill/tool environment. The UI/download plumbing does not establish slide factual accuracy, rendering quality or successful deck generation in this assessment. Repository tree heuristics provide launch hints, not autonomous product research.

Heterogeneous provider/protocol orchestration and remote task interoperability

Routa can mix ACP-compatible CLIs, special Claude adapters, SDK-backed execution, Docker OpenCode and a native workspace agent behind normalized session updates. Provider presets describe native/replay resume and suitable roles, rather than assuming all providers behave like Codex (presets, lines 30–85 and 91–130). A2A outbound dispatch/polling connects remote services into local board lifecycle (outbound client, lines 103–215; lane adapter, lines 749–839). This expands Wingman's initial Codex-only organization toward mixed runtimes and specialist services. Integration costs include capability-aware controls, adapter-specific context restoration, remote artifact/repository contracts and explicit identity/authority boundaries. A2A status polling is not a shared host filesystem or distributed chat system.

Multi-user shared execution with host-controlled prompt injection

Shared sessions have host/collaborator/viewer roles, invite and participant tokens, view/comment/prompt modes, prompt approvals, messages and SSE lifecycle events. Non-host prompts can wait for host approval before being dispatched to the host execution session (shared-session types, lines 1–79; service, lines 355–519). This enables a teammate or reviewer to participate in one live coding session, beyond Wingman's single-human Butler entry point. Its TypeScript state is held in Maps (lines 94–98), so durable membership, approval history and organizational authorization need additional work before treating it as Wingman's persistent communication system.

Repository harness assessment and verified harness evolution

The Rust CLI can evaluate repository harness maturity and propose/apply bounded harness changes, then run verification and compare the resulting maturity snapshots against previous baselines. The implementation snapshots selected changes, rolls back patch/verification/ratchet failures and requires force for medium/high-risk candidates (harness apply, lines 235–362). The ratchet evaluates generic and agent-orchestrator profiles without immediately saving, then compares outcomes before persistence (ratchet, lines 36–110). This can improve the operating environment in which autonomous coders work, beyond storing product harness instructions. Wingman would need product-specific harness rules, authority to modify governance files and review of heuristic scoring. A maturity baseline is not proof of functional correctness or product acceptance.

Execution-derived learning and contextual work handoff

The orchestrator summarizes parent traces for a delegated role, records outcomes and derives reusable playbooks. At least two related outcomes are required for the TypeScript playbook. It weights tools/files from successful runs more strongly, records verification pass history and extracts failure/churn anti-patterns with source-session provenance (trace playbook, lines 49–90 and 93–197). It writes artifacts beneath docs/fitness/playbooks and injects learned guidance into later delegations (orchestrator, lines 590–629 and 1262–1284). This could reduce repeated repository investigation and help workers avoid known failure modes. Integration requires retention, provenance and confidence policies; repeated prior success is correlated evidence, not a validated causal policy. A basic auto-success report can also weaken the outcome labels feeding this loop.

Execution sandbox policy and evidence-aware Git delivery

Routa exposes workspace-aware sandbox controls including path permissions, environment and network capabilities, plus runtime permission escalation. It also attaches task delivery to repository/worktree truth, branch state, commits and PR readiness (Rust constraints, lines 10–86; delivery readiness, lines 48–84 and 87–198). These are useful mechanisms beyond Wingman's described roles and dashboards: they can bound worker environments and prevent “done” cards with uncommitted changes. Adoption must distinguish container-enforced restrictions from SDK/tool allowlists and decide what constitutes sufficient integration/delivery evidence. Branch cleanliness alone does not establish accepted behavior.

Distinctive mechanisms and grounded innovation

The board acts as a state machine that launches and supervises agents. Entry/exit automation is resolved by code, multi-step lane execution is tied to task/session attempt records, queue state is reconciled against current task location, and watchdog recovery records the replaced session and reason. This turns a task board into an operational control plane. Its practical value for Wingman is stable work progression visible to both agents and human. Its limits are process-local queues/active-automation state, separate persistence recovery and configuration-dependent completion semantics. Evidence: transition resolution, lines 53–76; queue, lines 78–110 and 160–194; lane-session model, lines 122–168; restart recovery, lines 65–118.

Delegation is paired with outcome context and explicit parent wakeup. Parent trace digests tailor handoff context, child streams remain independently inspectable, completion writes update memory, and group completion triggers a new parent prompt. The mechanism supports a lead that can end its turn while children work, then resume coordination. It is more substantial than a function that merely returns several model answers. Limits include process-local relationship maps, best-effort contextual enrichment and automatic success reporting when a worker finishes without reporting. Evidence: orchestrator, lines 590–629, 851–887, 1045–1079 and 1298–1404.

Harness improvement has a rollback-and-ratchet boundary. Proposed operating-environment changes are applied under a risk policy, verified, then rejected if the baseline regresses. That is an inspectable feedback mechanism which could support Wingman's self-maintenance. It is limited to implemented patch candidates and maturity criteria. It is not unrestricted self-improvement or an independent quality oracle. Evidence: apply, lines 235–350; ratchet, lines 36–110.

Execution history becomes attributed reusable guidance. Trace outcomes feed task fingerprints/playbooks with tools, files, verification signals and anti-patterns; future workers receive role-oriented guidance linked to prior sessions. This connects observability to future execution instead of keeping traces solely for debugging. It remains a small-sample heuristic with fallible outcome labels, not learned model weights or evidence of universally improved performance. Evidence: playbook construction, lines 93–197. These are distinctive implementation choices in this checkout; no claim of historical novelty or industry-wide uniqueness is made.

Practical fit for Wingman

Use directly as reference or substrate:

  • Workspace/task/codebase/worktree schemas.
  • Specialist-versus-instance separation.
  • Actual spawned ACP/SDK sessions.
  • Child/parent stream association.
  • Task acceptance/test fields.
  • Kanban dispatch, queueing, retry and attempt history.
  • Notes/artifacts.
  • Session inspection and provider-aware resume. The MIT license permits reuse subject to its notice requirements. The repository is large and contains two independently implemented backends, so adopting a focused vertical slice is more tractable than assuming the whole application is already Wingman.

Adapt deliberately:

  • Choose a canonical runtime and durable coordination store.
  • Map Wingman roles onto stable agent identities separate from run/session IDs.
  • Persist event delivery, parent relationships, wait groups, approvals and workflow runs where required.
  • Extend profile taxonomy/UI beyond its fixed team/core-role assumptions.
  • Route tasks through one dependency/readiness policy.
  • Ensure spawned paths preserve intended provider/model/tool settings.
  • Define host assignment and repository/artifact movement for runner/A2A execution. Separate model-produced verdicts from authenticated human decisions. Use real test-run artifacts and integrated acceptance evidence for completion, not pass-like text or successful turn termination.

Build above it:

  • Telegram Butler and conversational project resolution.
  • Portfolio ProjectMaster and proactive organizational supervision.
  • Durable per-product ProductMaster/TechMaster collaboration.
  • Proportionate business/domain/market discovery and question routing.
  • Explicit product scope/spec/DoD records and accepted-delivery stop/resume policy.
  • Persistent management/project chat rooms. A cross-project agent directory and plain-language current/recent/next/blocker briefings with per-agent summary feeds. These gaps were assessed from actual route/model/profile/orchestration surfaces, not merely missing README promises.

Routa is strongest as the place workers execute and humans inspect their work. Wingman must supply the enduring organization and product-development responsibility around that workbench. The source offers useful concrete mechanisms for that implementation, while also demonstrating why task completion, persistent identity and a standing organization must remain distinct concepts.
