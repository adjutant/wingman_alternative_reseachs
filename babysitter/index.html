Babysitter assessment against Wingman

Identity and fit verdict

  • Repository: https://github.com/a5c-ai/babysitter
  • Local checkout: researchs/babysitter/repo
  • Inspected commit: feb68abe397acc14f32b34984975c48fedba2b33 (git rev-parse HEAD); root package version 6.0.3.
  • Assessment date: 2026-11-05.
  • Baseline: Wingman purpose; assessment guide.
  • Method: read-only source assessment. No dependency installation, services, model calls, Kubernetes deployment, browser session, or runtime test execution.

Verdict: a strong implementation source for Wingman's execution and governance substrate, and a substantial partial organizational platform, but not a ready-made Wingman organization. This checkout is considerably broader than a workflow plugin. Alongside the Babysitter event-sourced workflow SDK it contains Genty's tool-capable sessions and autonomous orchestration, adapters for coding harnesses, and Kradle's Kubernetes-backed identities, dispatch runs, projects, boards, approvals, memory records and web views. Those implementations deserve credit independently of the older “workflow layer” classification.

The components do not establish Wingman's complete management chain. Telegram Butler, portfolio supervision, separate product/technical leaders, and a standing specialist organization remain application work. Durable persona records and executable coding processes exist. The default progress unit is a workflow run or dispatch. It does not represent an enduring employee responsibility with a maintained executive briefing.

Wingman still needs project-aware intake, management rooms, and summaries of recent results, current work, and next work. Several Kradle paths also need verification before adoption. Cancellation updates status without stopping the Kubernetes Job. Identity-targeted HTTP dispatch loads fewer permission resources than stack-targeted dispatch. Detailed session workspace panels contain placeholders.

Architecture and actual execution model

Three layers with different meanings of “agent”

The root package manifest lists SDK, Genty, adapters, Atlas, KIP and Kradle workspaces (lines 1–50). The metapackage is only an entry surface. The execution boundary is inside those packages. The short runtime reference accurately describes the core replay contract, but it is important to inspect the implementation rather than infer a whole organization from that description.

Babysitter SDK: a process is an imported JavaScript/TypeScript function with (inputs, ctx). A run stores metadata, inputs, tasks, results, and an append-only journal. createRun, lines 16–70, allocates a ULID by default and resolves the runs root. It records the process entry point and optional nested ancestry. It validates inputs and hashes process code. Lines 72–107 append RUN_CREATED under a lock. This creates durable work state. It does not launch an LLM worker.

orchestrateIteration, lines 47–92, acquires the run lock and initializes replay. It rejects unassigned bare runs, loads the process function, and executes it in process context. The task intrinsic, lines 68–105, derives an invocation identity and looks for a journal effect. It returns a recorded result or throws a pending-effect exception. New effects serialize task descriptors, pass hooks and policy, and receive an effect ID (lines 108–180 onward).

Replay can execute the process body again while reusing resolved effect results. Actual side effects must remain behind task boundaries. The mechanism replays workflow decisions and returned values. It does not replay arbitrary external tools or guarantee exactly-once external mutations.

Genty runtime/platform: connects pending effects to executable workers. Effect resolution, lines 252–283, handles MCP tasks. It separately gates cross-agent dispatch and shell/Node execution. Plugin and host contexts default to pending work. The standalone create-run entry, lines 56–63, sets two flags for autonomous dispatch when they are unset.

Delegated execution, lines 101–174, creates fresh tool-capable sessions. It loads skills, checks policy, prompts the session, and disposes it. Lines 177–187 invoke an external harness when selected. These are independent execution contexts. The common internal delegated worker is temporary. AgentCoreSessionHandle, lines 1291–1358, owns its history, session ID, listeners, and provider/tool loop. It rejects overlapping prompts to one handle. Separate handles or processes provide parallel execution.

Kradle control plane: provides organization resources and cloud execution. resource model lines 32–77 distinguishes persona/definition/stack configuration, dispatch run, execution attempt, adapter session, context bundle, workspace and transcript. Its declared storage split is etcd for configuration and Postgres for aggregated operational records. The concrete HTTP dispatch path inspected here goes through Kubernetes resource APIs and status subresources. Do not assume every returned object in a pure controller helper has been durably saved merely because its kind declares a storage class. API dispatch lines 252–318 explicitly applies the run and its status, memory snapshot and optional PVC after calling the dispatch controller.

The dispatch controller lines 296–348 resolves identity and stack, runs permission review, snapshots context/memory, optionally returns AwaitingApproval, provisions/reuses workspace, and creates run/attempt records (lines 350–510). It builds and submits an actual Kubernetes Job (lines 512–618). Job client lines 417–579 constructs an agent container with harness/provider/model, task, org/run identity, service account, granted model secret, resources and either a PVC or ephemeral emptyDir. Lines 588–595 applies the Job through a resource gateway. This is real cluster execution infrastructure capable of using multiple nodes. It is not merely a local subprocess described as distributed execution.

A fourth, complementary surface is the Observer dashboard, which discovers configured filesystem run sources and groups them by project (source discovery, lines 12–25, 90–97 and 112–135). Its executive banner, lines 7–14 and 37–91, summarizes active/failed/stale runs and pending approvals. This is a useful portfolio alarm, but its name does not make it a Wingman per-agent current/recent/next briefing. Its approval action, lines 52–129, resolves a run directory and checks both task metadata and journal kind before recording a breakpoint answer through the SDK. It supplies a concrete human interaction surface for local workflow runs independently of Kradle.

The runtime container entrypoint clones a target repository, creates a branch, launches the coding harness, stages/commits/pushes edits and opens a Gitea PR (lines 93–164, 216–253, 281–324). Results return through a per-run callback. Kubernetes, registry images, model credentials, git backend and callback connectivity are actual deployment dependencies, not bundled guarantees.

Gateway Kanban, remote adapters and Commander are separate product surfaces

The adapters gateway is not simply a proxy for Kradle or a copy of the Observer's run list. Gateway server lines 172–196 constructs its own run manager, workspace service, HTTP/WebSocket server and Kanban routes. Authenticated session creation dispatches through runManager.start, optionally carrying a source session for a fork (lines 381–414); authenticated dispatch/stop routes call the live manager (lines 484–535). The stop implementation actually aborts its active handle (gateway run manager, lines 214–219), unlike Kradle's status-only cancel route. Its static WebUI loader, lines 37–58 and 76–84, searches an optional installed genty-webui package or configured build directory and returns 404 if absent. This assessment establishes the checked-out backend and its UI-serving seam. It does not assert that an installable UI build was present or rendered.

The gateway owns separate project, backlog, review, and automation records. Backlog service, lines 109–164, accepts project/parent IDs, assignees, typed dependencies, acceptance criteria, and decomposition. It also links sessions and runs. Lines 1653–1695 create and normalize an issue in its project. Lines 1774–1786 persist and reload it. Lines 1790–1835 check board movement and reject policy violations. Lines 2502–2535 reject a session link to a second issue before persisting dispatch links.

Kanban storage, lines 23–58, stores projects, issues, tags, context labels, automation rules, and executions. The default path is ~/.a5c/kanban-backlog.json. Lines 73–92 read and write the whole JSON file. This provides a local tracker independent of Kubernetes. It does not establish transactional multi-writer or cross-host storage.

Automation service lines 37–65 defines draft/active/paused/disabled/archived rules with timer/webhook triggers; lines 841–863 validates target and route before creation, lines 925–960 enforces lifecycle transitions, and lines 977–1043 records rejected events for inactive rules or missing routing. Lines 1068–1085 materialize an issue with configured assignees, criteria and decomposition, and lines 1101–1133 append execution/audit records. Kanban routes lines 974–1045 expose rule CRUD, lifecycle and webhook delivery. This is a configurable recurring/event-driven work intake plane. It does not itself prove that materialized issues autonomously become staffed specialist work or that the HTTP server alone runs cron without the daemon/timer execution component.

Gateway review service, lines 39–87, models decisions, anchored comments, follow-up targets, linked PRs, and CI status. Lines 530–555 record submitted reviews. Lines 580–599 reopen approved work when comments arrive. Without stored artifacts, readArtifacts() returns seeded review data (lines 501–519). The create-pull-request branch constructs a local linked-PR record with an incremented number and pending CI gates (lines 609–641). That branch makes no provider HTTP call. Actual Gitea publication belongs to the pod entry point.

Wingman could reuse these review and tracker mechanisms. It still needs real artifact/provider ingestion, explicit authoritative-record rules, and reliable persistence.

The remote runner is another execution route besides local spawn and Kubernetes Jobs. Remote runner lines 78–110 calls a RemoteAdapter.connect, binds supported live user-message injection and interaction responses, and streams received events onto the run handle. Lines 43–69 apply inactivity/run timeouts and disconnect on abort; lines 112–127 finalize completion/crash and cleanup. This is executable remote-session plumbing, but the connected adapter, endpoint, authentication and host-specific filesystem continuity still determine what a given deployment can do. It does not automatically create the Mac/Endeavour host registry or synchronize their projects.

Commander is an additional board/inspection/control client, not evidence that every visible simulated control is live. WarRoom lines 46–66 composes board, inquiry/chat dock, review, steering, registry, run, memory and IDE overlays. Backend factory lines 56–66 explicitly selects a real gateway backend only for configured real mode; otherwise it creates a seeded mock. In Kradle-only real mode the gateway transport is inert (lines 19–53) and the separate Kradle snapshot/client path supplies resources. Real backend lines 551–576 fetches authenticated agent/session/run lists, while lines 579–609 returns an empty task list and no-ops gateway-only board mutations. Kradle orders lines 126–167 resolves actual stack/definition targets, and lines 571–611 dispatches tasks through the controller client, but roster creation/assignment remain documented no-ops at lines 686–763. Commander is a useful operational console and UX reference; simulated employee/team behaviors must not be counted as implemented standing-organization capabilities.

Agent definition and lifecycle

Definition, creation and identity

There are three different definitions to keep separate. A library AGENT.md and a task's agent.prompt.role describe behavior. Neither creates a running agent. An AgentStack defines executable harness/model/tool/skill/permission settings. AgentPersona adds a durable identity profile, and AgentDefinition binds that persona to a stack and role context. Persona controller lines 88–113 resolves references within organization scope and reports missing resources instead of fabricating identity. Directory routes lines 29–36 supplies UI creation over discovered stacks and skills. These constructs could represent multiple BackendCoders and project leaders, but instance responsibility/assignment history must be attached by a Wingman application.

A run has a separate ID. Core runs use a ULID unless specified; Kradle manual dispatch currently uses dispatch-${Date.now()} and an attempt-1 name (dispatch, lines 459–509). An attempt snapshots stack/persona/definition specifications, making a later profile edit distinguishable from what a run actually used. This is valuable provenance, but timestamp IDs and pure object helpers should not be mistaken for a globally transactional identity service.

Execution, tools, permissions and routing

In core mode the process requests effects. The executor chooses who resolves them. Genty can route through task adapters, execute a fresh internal worker with coding or readonly tools, invoke an external harness, or leave effects pending. Delegated execution lines 116–158 explicitly builds file/bash tools: toolsMode alone does not magically give an LLM filesystem access. Tool scope and permission enforcement must exist at the executing harness, not only in a persona description.

Kradle dispatch reviews permissions before constructing the Job, resolves a model-provider secret by grant, assembles context, and sets a service account and resource limits (dispatch, lines 343–348, 530–594; Job client, lines 502–575). The broader proof-policy layer has a meaningful activation boundary: tool gate wiring lines 29–33 and 111–139 requires a pinned POLICY_CONFIG_ROOT_FP for enforcement. An unpinned deployment keeps backward-compatible execution. With an anchor pinned, missing policy infrastructure produces deny-all rather than silently dropping the gate. Wingman would have to choose and configure this trust model.

Routing can use named definitions or stacks, task role lookup, selected harness/model and task-adapter responder hints. The generic subagent helper lines 84–117 creates a queued dispatch record, not an execution session; its scope explicitly excludes adapter-session ownership. Its role-match method also does not consume taskKind to make an elaborate staffing decision. The executable job path is the separate dispatch controller.

Concurrency and project/workspace isolation

A single run's journal transitions are locked. Parallel intrinsics emit pending groups, and Genty's dispatcher lines 94–120 groups them only when concurrency is enabled. Lines 136–176 execute a bounded pool and return results in original index order. There is no reason to equate simultaneous effect requests with proven simultaneous coding sessions unless the host actually dispatches them. Separate Kubernetes Jobs are independently schedulable. The manifest uses restartPolicy: Never and backoffLimit: 0 (Job client, lines 559–571).

Kradle reuses a matching reusable workspace when available and otherwise creates ephemeral storage (dispatch, lines 414–450). That keeps one-shot runs isolated and cheap, but work in emptyDir is lost with the pod unless published. PVC-backed reuse can retain a workspace; coherent per-product host affinity and multi-worker source integration remain policies to define. The container's repository branch/PR path supplies a concrete delivery boundary, which is safer to integrate than treating transient pod files as the durable product.

Persistence, resume and scheduling

Workflow continuity is strongest at the effect boundary. Effect commit lines 24–42 rejects unknown/already-resolved effects, validates outputs and signed breakpoint answers, persists result references, appends EFFECT_RESOLVED and rebuilds derived state (lines 63–107). A restarted orchestrator can replay these records and advance. This preserves completed work decisions, but a tool side effect that succeeded just before result posting failed can still need reconciliation or idempotency in the adapter/application.

Conversation continuity is different. Core session lines 1291–1298 stores history in memory; dispose() clears it (lines 1672–1677). Genty's persistent session store separately saves findings, preferences, modifications and breakpoint patterns atomically via temporary-file rename, rather than automatically serializing a live employee's full mind. Kradle transcript resources persist messages, and identity/configuration can outlive executions. Wingman needs a deliberate resume assembler joining these objects by project, role, assignment and conversation.

Periodic work is available through cron, file and webhook triggers. Daemon loop lines 44–79 and 98–123 uses a durable queue when a log directory is provided, claims due work, acknowledges success and records/retries failure. An injected onTrigger callback performs actual work (lines 92–95). The queue is not itself a product manager. Automation executor lines 208 onward creates tracked issues from templates. A scheduled supervision workflow can be authored, but the system does not inherently know to inspect all product blockers and contact the correct leaders.

Interruption, steering, failure and recovery

Core steer() and followUp() merely append strings to queuedFollowUps. The next prompt() consumes them (core session, lines 1323–1325 and 1598–1604). That is queued next-turn input, not guaranteed immediate injection into an active tool loop. abort() signals the current provider request; dispose() also clears listeners/history. Durable SDK cancellation is another operation: commitEffectCancellation, lines 129–165 onward records a cancelled result under the run lock. Recording cancellation does not by itself kill a remote process.

This distinction is particularly visible in Kradle: HTTP cancel lines 12–27 sets Cancelled on the run status, with no Job deletion or adapter stop call. A subsequent callback lines 52–64 can write terminal completion/failure without checking whether the run was already cancelled. Execution interruption and terminal-state arbitration need hardening before this path controls expensive autonomous workers.

Iteration handling lines 162–213 separates waiting, explicit halt, process runtime error and run failure. Unexpected process-code errors get PROCESS_RUNTIME_ERROR with a recovery command and last-effect context; explicit RunFailedError produces RUN_FAILED. The runtime reference identifies rebuild-state, recover-process-error and journal-repair operations. These are practical recovery seams, but repairing process code/journal is an operator action, not autonomous evidence that the original product outcome was recovered. Pod job submission failure leaves a queued run with a failure condition (dispatch, lines 611–619); Kubernetes does not retry that job automatically with the current zero-backoff setting. Trigger retry and model retry are separate mechanisms and should not accidentally duplicate partially completed repository work.

Completion, acceptance, retirement and cleanup

A core process returning a value writes output and RUN_COMPLETED (iterate, lines 127–159). A declared output-schema mismatch at that top-level return is logged as a warning (lines 127–131). It is not a universal hard acceptance test. An effect's output validation is a separate commit-time path. In Kradle, a completion event sets phase completed (dispatch, lines 237–256), or the pod callback does so after exit/publish processing. None establishes that ProductMaster accepted the integrated product unless the process explicitly encoded the relevant checks and decision gate.

The TDD workflow demonstrates how to encode that policy: bounded refinement, real check effects, integration verification, a final review and a human merge decision. It can return success: false after exhausting iterations while the workflow itself completes normally (lines 214–221). Wingman should distinguish process execution success, test evidence and product acceptance in its tracker.

Retirement is also layered: ephemeral workers are disposed after their delegated task, Jobs terminate, workspaces follow retention/volume policy, and directory personas remain configuration. Run archive lines 39–93 writes compressed archive data/manifests. It does not remove the original run. Lines 99–121 restores files. Fork helper lines 51–85 only validates a fork point and prepares IDs/metadata. This file alone is not an implemented clone of run directories or an end-to-end conversation fork. Iteration cleanup lines 214–219 runs process-local cleanup on non-waiting outcomes and checks scratch leaks. Wingman still needs explicit policy for archiving employees/conversations, retaining audit records and stopping development after accepted delivery.

Coordination mechanics and a concrete request trace

The core coordination mechanism is not chat: it is a serializable effect graph and append-only result journal. Process code determines dependencies through awaited return values; parallel groups expose independent work; breakpoints and sleeps are effects that suspend progress; result posting allows a later iteration to continue. Task adapters add responder routing and escalation. The channel runtime, lines 117–155, resolves extensible backends and routes replies by the originating source token. This is useful inbound-event/reply plumbing, distinct from multi-agent chat-room membership and discussion history. Projects/issues/boards add shared tracking. Cross-run mailboxes add explicitly addressed messages. These mechanisms are complementary, but the inspected code does not show them as one unified employee-room-tracker system.

The mailbox is also a small local primitive with a real limit: send() appends JSONL, but receive() reads all messages and rewrites only the unconsumed remainder (lines 42–67, 89–103). No lock or transactional compare-and-swap is used there. Concurrent append/receive consumers require protection before treating this as a reliable distributed organizational bus. Its “append-only” header describes sending, not an immutable complete history after consumption.

A concrete implemented workflow is gsd/new-project, beginning with {projectName, projectType, initialIdea}:

  1. Process lines 46–62 requests vision capture. Its task definition at lines 176–233 contains an agent prompt, result schema and effect-specific I/O. This is a worker task, not creation of a standing ProductMaster.
  2. Task intrinsic lines 76–105 derives invocation identity. On the first pass it serializes a new effect and the runtime reports waiting; on later passes it returns the recorded result instead of creating another vision task.
  3. Genty resolver lines 257–275 either leaves the effect pending under host defaults or dispatches through a task backend; delegation lines 135–174 shows the concrete internal tool-capable worker alternative. External host orchestrators may instead perform it and post the result.
  4. Result commit lines 24–107 verifies the requested effect, writes result artifacts and appends the resolution. The next iteration replays vision capture and reaches the human vision review (process, lines 65–74). The durable pending breakpoint is distinct from the answering UI or a Telegram channel.
  5. After review, four research effects run through ctx.parallel.all (process, lines 80–91). Their returned values become explicit inputs to requirements scoping, then roadmap generation (lines 104–131). The executor's capability and concurrency configuration determine actual simultaneous work.
  6. Requirements review and final initialization review expose artifact links and human questions (lines 110–145). The process returns structured vision/requirements/research/roadmap data and artifact paths (lines 148–164), causing the runtime's completion path. These references and prompt instructions should not be assumed to prove every promised Markdown file was written; that must be verified in execution.

The cloud execution path has these stages:

  1. The dispatch HTTP route, lines 7–43, authenticates and loads organization-scoped target resources. It passes task, repository, and ref to dispatchAgent.
  2. The API controller, lines 252–318, invokes manual dispatch. It applies run/status and workspace resources.
  3. The Job client, lines 546–595, submits a Kubernetes Job.
  4. The pod entry point launches the harness and posts final output.
  5. The callback, lines 38–98, updates run status and persists the transcript.

The implementation supports this trace. The assessment did not deploy a cluster.

Two boundaries in that path deserve attention. The route's loadIdentityResources loads only six identity/stack kinds (lines 56–58), while the stack path includes service accounts, role bindings, grants and workspace policy (lines 67–76). Since permission review consults these objects, identity dispatch may be denied despite valid configured grants; source inspection identifies the mismatch, while a live failure was not reproduced. Also, the callback is intentionally not session-authenticated and relies on knowing the org/run binding (lines 6–8, 25–43). The inspected handler contains no callback-token/signature check. Deployment isolation and authenticated result provenance should be designed before exposing that endpoint.

Major capabilities beyond Wingman's described product

Replayable workflow programming and repair tooling. Wingman describes persistent agents and shared records, but does not prescribe deterministic replay. Babysitter offers an explicit effect journal, invocation identity, input/output schemas, process code hashes, replay caches and typed repair paths. This can make long discovery/build/test workflows restartable and inspectable. The integration cost is architectural: arbitrary side effects in process functions are unsafe, workflow evolution must preserve invocation meaning, and tool side effects/result posting need reconciliation. Replay is an execution kernel to adopt deliberately, not a wrapper that makes any chat organization durable.

Proof-bound command governance. Policy wiring lines 44–82 binds decisions to actual executing tool-call/run/session IDs and denies exceptions; lines 111–139 gates activation on the external trust anchor. This goes beyond ordinary UI approvals toward signed evidence and configuration integrity. It could let Wingman enforce a review/test/approval chain before a command runs. It also introduces key/configuration management and policy-coverage work; unpinned environments are pass-through, and an enforced gate covers only what the configured matching rules describe. No end-to-end cryptographic enforcement was exercised here.

Independent local tracker, review and automation plane. The gateway Kanban backend described above is a substantial alternative to adopting Kradle wholesale. It combines issue dependencies/acceptance/decomposition, run/session/workspace references, policy-checked board moves and automation-rule audit state in local JSON stores. That supplies much of the tracker vocabulary Wingman needs while allowing local harness execution. Its review artifacts and PR/CI projections need real evidence/provider ingestion; seeded defaults and local “create PR” metadata are not equivalent to delivered changes. The principal integration consequence is choosing whether the gateway backlog, Kradle issues or another tracker is authoritative and designing safe writes/synchronization; adopting every surface together would multiply overlapping state.

Event-origin-preserving agent activation. The channels package contains executable GitHub polling/reply, lines 376–406, and Jira polling/reply, lines 237–294, with cursors/seen sets and HTTP comment posting. SessionSpawner, lines 148–219, turns a surviving event into worker launch options and injects the same channel MCP server/config plus origin reply_to token. Lines 383–428 launches through the adapter client under a semaphore so the worker can answer the original issue without losing its routing coordinates. This is a meaningful foundation for proactive issue-driven agents and escalations beyond a passive event log. Its at-most-once dispatch stance marks events before launch settles (lines 392–399), so failed launches are not automatically redelivered. The generic webhook backend, lines 191–229, consumes normalized inline/directory queues and explicitly rejects reply (lines 232–244); generic webhook input is not a two-way conversation. A Telegram Butler would still need a Telegram-specific backend, project/conversation correlation and organizational routing.

Cloud development platform and git/CI integration. Kradle adds Kubernetes jobs, identity/grants, ephemeral/PVC workspaces, organization scoping, external git/issue/CI provider contracts and artifacts. GitHub issue adapter lines 19–56 is executable HTTP integration with injected fetch and normalized records, not just a provider name. Pod publishing lines 141–164 turns successful repository work into a pushed branch and PR. Wingman could use this for distributed execution and reviewable delivery, at the cost of operating Kubernetes, storage, secrets, images and git services. It is a much heavier substrate than running two Codex hosts and appending local Markdown records.

Versioned knowledge graph SDK. KIP provides signed facts and temporal retrieval, independently of Kradle's simpler memory-resource projection. KIP implementation lines 1482–1533 publishes sorted fact snapshots into Git and advances a durable tip; lines 2235–2277 implement as-of recall and validation; lines 3122–3141 merge admitted fact sets; lines 3736 onward perform authorized excision. This could support provenance-aware product decisions and cross-agent memory. It is not evidence that every Kradle dispatch automatically retrieves useful company knowledge: the inspected dispatch initializes snapshot records with empty selected-record/document arrays (dispatch, lines 350–369). KIP recall also explicitly documents a scope/tenancy filtering gap (lines 2264–2268), so it should not become Wingman's cross-project isolation boundary without further evaluation.

Discovery and reusable process library. Atlas discovery types, lines 18–61, describe processes, skills, and agent roles with paths, expertise, and metadata. The index builder, lines 361–420, reads graph YAML and merges patch records. It accumulates edges and counts. AtlasGraph, lines 43–75 and 115–169, supports record/kind lookup and relationship maps. Ranked text search can filter by kind or cluster.

The catalog can help select compatible harnesses, models, processes, and skills with traceable evidence. The library includes GSD-style discovery and TDD convergence code. These procedures can guide product-work depth and reuse specialist knowledge. A catalog agent remains instructions until dispatch. Metadata and graph edges do not establish an active team. Wingman must curate the processes and align their artifacts and gates with project contracts.

Synchronous meeting participation. Kradle's meeting bridge lines 24–37 and 77–108 binds a dispatched agent to a meeting; Job client lines 498–500 and 542–544 mounts a shared socket and adds a Jitsi sidecar. Sidecar construction lines 144–155 includes resource settings and a graceful-leave hook. This offers a different human/agent collaboration medium beyond Telegram/text dashboards. It brings realtime media, meeting authentication and resource dependencies and should not be credited as persistent management/project chat rooms.

Distinctive mechanisms and grounded innovation

The strongest mechanism is separating process replay from effect execution. Task identity and persisted return values let a process use ordinary control flow while suspending for agent work, human decisions and time. The result is particularly useful for a Wingman clarification cycle that might last days. Its limit is the boundary: the system only knows about journaled effects, and process-side filesystem/network mutation is outside its replay discipline. This is a noteworthy implementation choice, not a claim of historical novelty.

A further useful mechanism is event-origin self-association: channel-spawned sessions inherit the MCP reply server and opaque origin token rather than having to rediscover where a question came from. This preserves response routing across a fresh worker context. The at-most-once launch policy trades duplicate prevention against automatic recovery from launch failure, so supervisory retry must be designed deliberately.

A second useful mechanism is concurrent resolution with ordered commit. Dispatcher lines 46–84 resolves configured groups concurrently and posts results in original action order; lines 136–176 bounds workers. This helps make parallel specialist work reproducibly visible even when completion order varies. It does not automatically merge source changes, resolve interface conflicts or impose task dependency semantics across independently created projects.

A third is identity/configuration/run/attempt separation. Persona and definition resources survive beyond a run, while attempt snapshots preserve the configuration actually executed. That offers a practical path toward Wingman agent identity without conflating a profile with a process. The limit is that durable organizational responsibility still has to be modeled, and the inspected API persistence path explicitly saves some returned resources rather than all helper outputs.

A fourth is human decisions as durable work objects with optional trusted proofs. SDK breakpoint answers can be checked before effect commit; Kradle approval resources retain action, requester, decision and reason. This can support auditable acceptance and escalation. It does not determine which product decisions need the human or how to correlate answers across concurrent Telegram conversations.

Finally, hard command outcomes alongside model-scored convergence is a useful combination. The library's deterministic gate lines 134–170 emits per-check exit evidence, whereas TDD convergence lines 114–151 uses an agent's score to guide improvement. Wingman should retain that distinction: an agent score can guide prioritization but should not substitute for acceptance scenarios or passing integrated tests. The checked-out processes make these mechanisms explicit, but process naming and declared “hard” behavior still require validation against the chosen executor.

Practical adoption path and remaining work

Use the SDK execution kernel directly for a bounded pilot: intake/discovery → requirements approval → technical plan → specialist effects → test gates → delivery decision. Its run journal, result posting, typed waiting/errors and cleanup give a better recovery foundation than a free-running manager prompt. Consider the gateway JSON-backed backlog/review/automation API as a lighter tracker starting point if Kubernetes is unnecessary, and use Commander only with its configured real backend and documented live controls. Use the Observer dashboard for inspecting local run state and answering workflow breakpoints, while retaining the distinction between run health and employee summaries. Use Genty workers/adapters where their supported coding sessions meet the desired Codex integration; verify tool availability, cancellation and model/harness continuity in the actual host combination.

Reuse Kradle's persona/definition, project/issue and approval concepts if adopting its deployment model. The directory and project board are meaningful UI starting points. Before taking the cloud path, test persona-targeted dispatch permissions, run/attempt/context/session persistence, stop propagation, callback authentication, artifact resource kinds and terminal-state races. The callback creates AgentArtifact (lines 104–119), whereas the inspected resource catalog declares KradleArtifact (resources, line 55). This is another concrete contract to validate rather than assuming artifact publication is complete. The placeholder workspace UI also needs actual file/git/review integration.

Build the organizational application around these primitives:

  • Telegram bot and Butler conversation correlation.
  • Semantic new/existing-project routing.
  • Project leadership identities.
  • Staffing and assignment policy.
  • Management/project rooms with dependable shared messaging.
  • Durable DIRECTIVES knowledge layout.
  • Periodic portfolio supervision that acts on blockers.
  • Current/recent/next executive summaries linked to source events. These should be explicit state/contracts, with role prompts supplying judgment inside them.

For Mac plus Endeavour, decide whether to adopt Kubernetes or build a smaller host dispatcher. Current cluster Jobs are a credible multi-node mechanism, but they do not route into existing host-resident Codex conversations or preserve product location across those two machines. A lightweight two-host approach could reuse the journal/protocol while replacing cloud workspace and scheduler assumptions. Avoid splitting source of truth among SDK effects, task-adapter tasks and Kanban issues without clear IDs and synchronization rules.

The most appropriate short-term position is therefore selective infrastructure adoption and architectural reference, with a possible heavier Kradle platform evaluation. A direct replacement claim would overstate the conversational organization, room collaboration, employee continuity and executive visibility currently established by source.

Verification scope and limits

All findings refer to the local commit above. Repository instructions were read: AGENTS.md explicitly exempts agent-to-agent delegated requests from the mandatory Babysitter-skill workflow. No source file in the checkout was modified. Only this report was written.

  • Run creation, iteration, task identity, result commits, and replay contracts.
  • Delegated coding sessions, execution flags, parallel dispatch, history, steering, abort, and disposal.
  • Daemon queues, timers, automation, and persona/definition/stack resolution.
