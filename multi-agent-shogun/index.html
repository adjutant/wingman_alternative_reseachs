multi-agent-shogun assessment for Wingman

Repository: https://github.com/yohey-w/multi-agent-shogun
Local checkout: research/multi-agent-shogun/repo
Inspected commit: aff8dc8495da26a2aad582257457655fa953b57e
Assessment date: November 5, 2026
Baseline: WINGMAN_PURPOSE.md

Verdict: A useful reference implementation for a persistent, human-directed hierarchy of real coding agents, especially its mailbox delivery, task recovery and explicit separation of management from execution. It is a partial organizational foundation for Wingman, rather than a complete implementation. Its center is a local tmux formation with agent-authored YAML and Markdown records. Wingman still needs project-specific product/technical leadership, Telegram routing, navigable agent collaboration rooms, distributed execution and connected executive/project/session views.

The strongest match is the organization operating through its own independent CLI agents. The most consequential difference is that much of the organization is a prompt protocol. Bash/Python infrastructure launches processes and delivers messages, but an LLM reads and changes tasks, resolves dependencies, performs acceptance and writes summaries. That is real executable behavior when the agent follows its instructions. It is not equivalent to a server enforcing those transitions transactionally.

This is a static assessment of the pinned source. No CLI agents, services, Android application or tests were launched. Findings describe implementation and inspected test intent, not measured operational reliability. External service and provider behavior was not independently exercised.

The supporting execution and protocol audit traces creation and identifies reuse limits. Dynamic worker IDs can conflict with fixed panes. Recovery status schemas and generated instructions differ. Mailbox readers and writers do not share one transaction boundary. These qualify the strengths below. They do not change the fact that this is a real multi-process agent formation.

1. Product and execution architecture

The standard formation is Lord (human) → Shogun → Karo → seven Ashigaru workers plus Gunshi. Shogun takes direction and issues purpose/acceptance contracts; Karo decomposes and schedules; Ashigaru execute; Gunshi handles strategic analysis and qualitative review. These are separate processes, not one model role-playing a conversation. Roles may use different coding CLIs and models, while sharing the filesystem and message protocol.

The launch path is shutsujin_departure.sh, notably lines 335–454, 552–672 and 700–939. It replaces the named tmux sessions and preserves previous queue files by default. It initializes them under --clean, creates a Shogun session and a 3×3 multiagent window, attaches stable @agent_id, @model_name and @current_task pane metadata, builds CLI commands and starts inbox watchers. The default topology is therefore ten agent processes on one machine.

The source has some dynamic formation support but it is not an unconstrained agent factory. lib/agent_registry.sh, lines 11–125, reads ordered cli.agents, falls back to the historical formation when Karo is absent, and maps identities to panes. Separately, the CLI adapter, lines 1445–1467, extracts IDs beginning with ashigaru. The launcher still constructs nine subordinate panes and explicitly builds Karo/Ashigaru/Gunshi arrays. Its execution loops use contiguous ashigaru1..count, which can disagree with sparse/custom configured IDs. Arbitrary additional identities in a registry do not by themselves gain a generated role, process, workspace and complete UI integration. This distinction matters for Wingman's extensible profiles and many specialist instances.

The adapter lib/cli_adapter.sh, lines 170–374 and 433–497, translates agent configuration into a CLI type, model and command. It includes branches for Claude, Codex, Copilot, Kimi, OpenCode, Cursor and Antigravity, but the file has overlapping allowed-CLI declarations and substantial CLI-specific behavior. Compatibility should be established per branch rather than inferred from the README's count of supported CLIs. Native coding, command execution, browsing and provider conversation storage come from those external CLIs; Shogun adds organization around them.

The coordination state is deliberately inspectable:

Record Actual responsibility
queue/shogun_to_karo.yaml Purpose-bearing commands and their state.
queue/tasks/ashigaruN.yaml, gunshi.yaml Current assignments associated with an agent slot.
queue/tasks/pending.yaml Work awaiting prerequisites before assignment.
queue/reports/*_report.yaml Worker outcomes, evidence paths and skill proposals.
queue/inbox/{agent}.yaml Durable addressed notifications with sender, type, timestamp and unread state.
projects/{id}.yaml, context/{id}.md Project metadata and knowledge. Actual project configuration is ignored/private, not present as an operational registry in this snapshot.
dashboard.md, logs/daily/ Agent-written secondary summaries and completed-command history.

The distinction between primary YAML and secondary dashboard is explicitly documented in AGENTS.md, especially the recovery and context sections. A stale Markdown summary is not intended to override task state.

3. What an agent actually is, and how its lifecycle works

Definition and creation

An agent is a long-running interactive coding CLI in a named tmux pane, coupled to an agent ID, instruction file, task slot, report slot and inbox. A task persona such as database engineer changes a worker's expertise instructions. It does not create a separate agent. The Shogun/Karo/Gunshi roles are standing identities, while ashigaruN is a reusable executor identity across projects.

Concept What is durable or independent
Role/profile Instruction text for one of four recognized roles, combined with CLI configuration.
Agent instance A named slot with its own interactive CLI process, task/report/inbox files and pane metadata. It is independent while running; its identity is not a separate database entity.
Session CLI-owned conversation plus tmux terminal lifetime. Resetting a conversation need not change the slot or assignment.
Task A purpose-linked YAML assignment; overwriting a slot changes its assignment without creating a worker.
Persona Per-task expertise requested in instructions. Neither a process nor an independent identity.

scripts/build_instructions.sh, lines 53–150, attempts to extract role front matter and composes instructions/roles/*_role.md, common protocol/task flow/forbidden actions, and CLI-specific instructions. It enumerates role×CLI variants, including generated Codex role files. This is more substantial than naming personas in a README: it produces concrete role instruction artifacts, although the checked-out Codex Karo artifact omits the original front-matter workflow. The agent creation boundary is a shell launch, not an API transaction that creates a project-scoped identity and all linked resources.

Configuration selects the CLI, model and optional environment/effort. The launcher stamps pane metadata before sending launch commands. The stable ID avoids confusing pane index with identity after pane rearrangement, a failure explicitly addressed by instructions/ashigaru.md, lines 152–168. All workers start from the coordination repository and may be directed to external project paths. There is no automatic per-worker worktree or filesystem isolation in this launch path; conflicting writes are handled by the RACE-001 instruction to serialize or block.

Tools, permissions and authority

Tools are primarily the capabilities of the chosen CLI and installed MCP integrations. Shogun does not implement its own coding-tool engine. The adapter defaults are highly autonomous: lib/cli_adapter.sh, lines 246–274, uses a skip-permissions default for Claude and launches Codex with search plus approval/sandbox bypass. OpenCode has generated/configured permission support, but there is no uniform isolation policy applied to every CLI branch.

The command hierarchy, prohibition on contacting the human directly, per-worker file ownership and restrictions on destructive commands are largely instruction-level policy. There is some tool-level enforcement: OpenCode permission configuration, lines 7–108, defines role-specific read/edit boundaries and denies direct inbox edits in favor of a tool. The inbox writer itself accepts arbitrary nonempty sender/type/target values and rejects self-send. It does not authenticate a process as the declared sender or enforce role authorization. On a trusted personal machine that may be a deliberate simplification. For Wingman it means the organizational policy layer and actual process/tool privilege need to be assessed separately, and permissions must be checked for each CLI.

Assignment, scheduling and concurrency

Shogun writes a command with north_star, purpose, acceptance_criteria, project and priority. Karo acknowledges it, creates subtasks with parent_cmd, target path, Bloom level and prerequisites, and wakes available workers. Scheduling is agent reasoning over files, not a daemon acquiring task leases. A worker checks its own assignment, executes, writes a report and notifies the review/management chain.

The current common task protocol distinguishes pending work from assigned work and says prerequisite-blocked tasks must remain in pending.yaml until ready. Older Karo examples also show blocked tasks prewritten into worker slots. This is a meaningful consistency limitation: instructions/common/task_flow.md, lines 72–101, and instructions/roles/karo_role.md, lines 74–83, preserve both patterns. A Wingman adaptation should make one schema and dispatcher authoritative rather than relying on agents to reconcile instructions.

Independent work can run concurrently, including commands for different projects. There is no separate concurrency budget per project and no elastic creation of new BackendCoders. Capacity is bounded by the configured/launched formation, model limits and manager/reviewer availability. Shared Karo and Gunshi can become serialization points even while workers are independent.

Durable delivery versus process wake-up

The mailbox implementation is a particularly useful mechanism. scripts/inbox_write.sh, lines 40–145, assigns a timestamp/random ID, obtains a mkdir lock and optional flock, loads YAML, appends an unread message, writes a temporary file and renames it atomically. It retries lock/write failures up to three times. Beyond 50 messages it retains all unread messages and the newest 30 read entries, so unread work is prioritized over an absolute size cap.

The message itself stays in the file. scripts/inbox_watcher.sh, lines 875–968, sends only an inboxN nudge through the terminal. The receiving agent reads the actual content and marks it read. This decouples persistent communication from a potentially lossy keystroke channel. It is not exactly-once task execution: a delivered notification, a read flag and a correctly committed task outcome are different operations. Nor is the writer a durable room archive: old read messages can be pruned unless archival happens first.

Locking covers cooperating inbox writers, not every possible mutation. The common protocol instructs agents to mark messages read using Edit; OpenCode improves this through a dedicated acknowledgment tool, lines 146–208, that checks current-agent identity and shares the writer's directory lock. However, the archival utility, lines 298–349, reads then rewrites the inbox through save_yaml without that inbox lock or atomic replacement. Its wrapper has a separate slimming lock. Concurrent arrival versus acknowledgment/archive is therefore not protected end to end. The writer also inserts message content into Python source rather than passing it as data (lines 80–101); its handling of arbitrary text deserves correction before reuse. The supporting audit explains these static findings without claiming a runtime reproduction.

The watcher combines Linux inotify/macOS fswatch events with a 30-second safety-net check (lines 1296–1359), active/self-watch detection, input throttling and CLI-specific recovery. Therefore “no polling” is best understood as avoiding repeated LLM supervision calls. The infrastructure does perform timed checks. This is sensible for token cost, but it is not a literal absence of polling or coordination overhead.

Persistence and resume

Persistent work continuity comes from YAML/context reconstruction, while session conversation storage is delegated to the CLI. The default launcher preserves queues but kills and recreates named tmux sessions. It does not prove that a prior provider conversation is resumed. A restart can therefore preserve the work assignment while losing unrecorded conversational detail.

scripts/session_start_hook.sh, lines 37–89, injects deterministic identity and recovery instructions for Claude startup/resume/clear/compact. Managers reread their persona and primary state; workers perform a lighter task/context recovery. Codex uses startup prompts and CLI-specific reset handling instead of that Claude hook. A stable agent ID survives as a slot identity. A single unbroken conversation is not guaranteed.

The reset mechanism deliberately trades conversational continuity for a clean task context. On new assignments or redo, the watcher may send /clear, /new or /new-chat according to CLI. A new task ID and redo_of distinguish corrections from the prior outcome. This can prevent stale instructions contaminating a retry, but requires complete task/context records to avoid losing useful reasoning.

Interruption, failure, retry and recovery

The watcher avoids clearing a busy agent, translates reset commands per CLI, and attempts to guard cancellation/idle states when generating recovery notifications. See scripts/inbox_watcher.sh, lines 330–412, 532–800 and 1101–1265. The recovery guard reads top-level status (lines 369–375), whereas the launcher and role examples write nested task.status. This protection is not established for both schemas. Unread messages trigger increasingly forceful recovery, with different paths for Codex and command-layer agents. Busy state is derived from pane output and flags, not a structured execution event stream: lib/agent_status.sh, lines 33–128, inspects prompt/spinner/status text. The watcher also contains stale-busy recovery. These are substantial operational protections and also sources of CLI-version sensitivity.

For Claude, scripts/stop_hook_inbox.sh, lines 42–194, lets Shogun stop freely, recognizes certain completion/error phrases for notifications, checks unread messages and can block a stop with inbox instructions. It bounds recursive stop-hook handling and uses idle flags to avoid delivery deadlock. Its optional 55-second event wait is infrastructure waiting, not an agent repeatedly spending tokens to check its inbox. Other CLI paths do not inherit this exact behavior.

Failures are recorded in reports and reviewed by Gunshi/Karo; semantic task retries are management decisions. There is no general automatic retry budget, backoff policy, execution lease expiry or dead-letter task queue. The optional standalone scripts/watcher_supervisor.sh, lines 34–92, restarts missing inbox watchers for existing panes when separately run. Searches found no non-test invocation. The standard launcher, lines 893–939, starts watchers directly without wiring this supervisor. Even when enabled separately, it does not recreate dead coding agents, restore a lost conversation or decide that an apparently busy agent is failing its product assignment.

Live steering is possible by entering instructions in a terminal or through Android's pane input. scripts/switch_cli.sh, lines 316–390, exits the current CLI and detects the shell before switching. This is process control and fresh recovery, not transparent migration of a conversation between model providers. There is no uniform managed pause/fork/rename/compact/archive API or persistent input queue joined to task lifecycle.

Completion, acceptance and retirement

Worker done is not intended to be sufficient for command completion. Gunshi performs qualitative review; Karo verifies the combined output against the original purpose, creates more work if the goal is unmet, records a daily summary and notifies the human. The mechanism is in instructions/roles/karo_role.md, lines 180–260. Bloom-based QC distinguishes mechanical checks from qualitative judgment and adds Lord approval for L6. These are strong behavioral contracts but are not parser-enforced acceptance gates.

There is no native delivered-product lifecycle that stops a project's development/testing team after human acceptance. Completed commands are archived and worker slots become available. Projects can be archived through metadata conventions; agent retirement is effectively changing formation/configuration or terminating sessions. scripts/slim_yaml.py, lines 18–25, 186–292 and 300–413, archives terminal task/report/command/read-message state. Its canonical worker slot sets are still hardcoded, another limit on arbitrary profile expansion. --clean backs up selected prior records then resets task/report/inbox/dashboard files. This is an operational reset, not a per-agent audited retirement workflow.

4. One request through the actual coordination paths

Consider a human mobile request to add an API endpoint to an existing project. The following is an implementation trace, not a request executed during this assessment:

  1. ntfy delivers the message to a long-lived JSON stream. ntfy_listener.sh filters outbound/nonmessage events, appends the request to queue/ntfy_inbox.yaml under a lock with atomic replacement, and writes a ntfy_received notification to Shogun's inbox (lines 142–173).
  2. A watcher notices the inbox change and nudges Shogun. Shogun's role instructions classify it as a delegated command, read relevant project context, write the command contract and notify Karo. The classification/decomposition is performed by the live agent, not hardcoded NLP routing.
  3. Karo acknowledges the command, decomposes the change into implementation and verification assignments, checks dependencies and available workers, and writes task YAML. It uses inbox_write.sh to notify the chosen worker. Any prerequisite work stays unassigned until ready under the current common protocol.
  4. Worker recovery identifies its pane ID, reads its own task and project context, then uses its coding CLI's tools. It updates task/report records with outcome and evidence and notifies Gunshi for review. Integration conflicts are supposed to block for management rather than cause simultaneous writes to the same file.
  5. Gunshi reviews the evidence, records findings and notifies Karo. Karo can reassign correction work with a new task ID/context reset, release dependent work or judge the aggregate result against the original acceptance contract.
  6. Karo updates the dashboard, appends completed-command history and sends a mobile notification. Shogun reads the summary when answering the human. The normal protocol explicitly avoids Karo inbox notifications to Shogun, preserving the human-facing input pane.

The coordination product is thus hierarchical command/task/report orchestration over addressed mailboxes. It is neither chat-room-first collaboration nor a conventional ticket product. Wingman could reuse the durable-message separation, but its desired worker↔worker product discussion, participant-based management rooms and question routing need additional semantics and UI. The repository's hierarchy intentionally limits direct communication; Wingman's collaboration model deliberately permits richer lateral discussion.

5. Major capabilities beyond Wingman's stated product

Heterogeneous CLI and model fleet

Wingman specifies Codex agents. Shogun can mix coding CLIs and model tiers, select a model for an agent, and switch an existing slot's CLI. Its Bloom-level routing helpers map task cognitive demands to configured capability tiers and subscription/cost groups. lib/cli_adapter.sh, lines 649–883, implements capability/cost lookup and recommendation: configured preferences take priority, allowed cost groups filter candidates, and a fallback selects a sufficient capability tier or warns when insufficient. This is a substantial fleet-allocation capability rather than cosmetic model selection.

It would let Wingman reserve stronger models for design/review and use cheaper capacity for known procedures. Integration would require a provider-neutral execution and evidence schema; CLI-specific reset, permissions and activity behavior make this more than changing a model field. Bloom class and capability tiers are operator/agent assessments, not measured proof that a model can complete a task. There is also no demonstrated end-to-end cost optimum or hard organization spending cap.

The routing helpers do not own a scheduler: find_agent_for_model, lines 1291–1442, returns a matching idle Ashigaru, falls back to another idle worker, or returns QUEUE. It expressly leaves restart decisions to Karo. A missing pane is also allowed to return the configured candidate (lines 1372–1375). Moreover, generated Codex instructions omit the original Karo front-matter workflow containing dynamic routing Step 6.5. The helper implementation is concrete, but uniform automatic routing across all CLI/instruction variants is unverified.

General white-collar delegation and a personal task system

The worker personas and templates support content, research, translation, operations and analysis as well as code. Shogun's SayTask path separates work delegated to agents from the human's own natural-language TODOs, including dates/categories and intent clarification. See instructions/shogun.md, lines 196–228 and following task-management sections, plus saytask/ samples. This is a different product surface from Wingman's software-development portfolio.

Its operational depth should not be overstated: much of SayTask is an agent instruction/data convention, and some input paths are explicitly marked future work. The value for Wingman is an optional distinction between “build this” and “remind me to do this,” not a prerequisite for the software organization. Streaks/frog displays themselves are minor and should not drive adoption.

Mobile remote control of the actual coding fleet

The Android application uses SSH to enumerate and capture all subordinate panes, polls every five seconds, displays CLI output, and sends selected-agent input. It also renders the shared dashboard. AgentsViewModel.kt, lines 71–168; DashboardViewModel.kt, lines 30–58. The combination of mobile command intake, notifications and terminal access is substantial operational capability.

Wingman already wants mobile visibility and workspace control, so this is an implementation example more than a missing Wingman product. What extends its Codex-centric formulation is direct SSH access to heterogeneous CLI panes without building a session-rendering server. The consequence is a weaker structured artifact/task integration and dependence on shell/tmux output. The SSH client is remote access to a host. It does not establish distributed agents across hosts.

Bottom-up organizational learning

Workers include skill_candidate in reports, managers aggregate proposals and the human approves promotion into reusable skills. instructions/ashigaru.md, lines 126–128, 188–210; Shogun role, lines 146–152. This is a concrete organizational-learning loop beyond merely preserving project specifications. It can turn repeatedly successful execution patterns into reusable procedures across products.

Discovery and promotion are agent/human judgments, not automated skill mining or a validated learning algorithm. Wingman could adopt the report field and approval path directly, then connect the resulting skill to versioned provenance, evaluations and affected profiles.

6. Distinctive mechanisms and their limits

Persist content, nudge only the count. The mailbox is independent of the terminal wake-up signal. This addresses real failure modes of typing long tasks into a busy TUI and enables recovery after missed signals. The design is small enough to inspect and change. Its limits are shared-filesystem scope, nontransactional task outcome/read acknowledgments, and terminal-based wake/recovery heuristics.

Management is kept responsive by ending agent turns. Shogun delegates immediately, Karo dispatches then stops, and events wake the next useful action. This avoids burning inference on repeated “are you done?” checks and leaves the human-facing agent available. It also means semantic supervision only runs when something wakes management. A silent worker failing without a report is not automatically equivalent to a project blocker review. Wingman needs to add its periodic ProjectMaster wake cycle deliberately.

Identity and role recovery are treated as infrastructure concerns. Pane metadata, generated role instructions, startup hooks and task-file reconstruction address role confusion after resets/compaction. This is more operationally specific than simply assuming a long-lived conversation remembers who it is. It still preserves identity as an execution slot rather than a first-class project/team entity independent of tmux.

Quality and scheduling are separated. Karo is a traffic controller, Gunshi provides qualitative review, and workers execute. Purpose acceptance is checked after constituent tasks complete, with north-star alignment explicitly carried into analysis reports. Gunshi role, lines 59–74, makes business-goal alignment an output field rather than an implicit expectation. This is a useful response to “all subtasks done, goal still unmet.” It remains vulnerable to agent protocol drift and does not prove independent product acceptance.

Cognitive-level routing connects organization and capacity. Task Bloom levels influence both who should reason about work and which model is recommended. That ties review depth, strategy delegation and resource use together. The interesting innovation is this concrete connection, not a claim that Bloom routing or multi-agent hierarchies are historically unique. Capability tables and task labels need empirical calibration; defaulting unknown capability to a high ceiling does not itself establish safety or quality.

These are distinctive mechanisms within this checkout. This assessment makes no claim of worldwide priority, uniqueness or superiority over uninspected products. The README also records that the author later moved their personal practice toward a single-agent successor; that is project context, not evidence that the pinned code cannot operate or that the successor has been assessed here.

7. Practical adoption for Wingman

Useful directly as design/code reference:

  • durable addressed mailboxes.
  • event-triggered wake-up.
  • stable agent identity independent of pane index.
  • lightweight YAML task/report contracts.
  • explicit outcome versus purpose acceptance.
  • role-recovery hooks.
  • separation of scheduling and qualitative review.
  • skill-candidate reports.

These match the user's preference for an inspectable, lightweight coordination record.

Requires adaptation:

  • replace Shogun's combined representative/strategist role with Butler and ProjectMaster.
  • create project-scoped ProductMaster/TechMaster identities.
  • map worker slots into persistent role instances and project teams.
  • replace ntfy input with a Telegram adapter preserving question/project correlation.
  • give all CLI work a consistent permission/host model.
  • create authoritative state transitions instead of relying on multiple instruction variants.

A Codex-only implementation could substantially simplify the many provider-specific reset and screen-detection paths.

Still to build:

  • The product discovery/clarification lifecycle.
  • Project knowledge conventions with scope/spec/harness evidence.
  • Room-based agent discussion and lateral collaboration. A real portfolio/project task application.
  • Connected per-agent executive summaries/timelines and structured session workspaces.
  • Distributed Mac/Linux worker placement with durable shared coordination.
  • Semantic periodic supervision. A delivered-product acceptance/stop/resume lifecycle. The existing Android/tmux view can supply early operational access, but it does not fill those product surfaces.

For Wingman's target, this is best treated as a coordination-protocol and operational-recovery reference, with a potentially useful local execution bootstrap. Reusing the entire formation unchanged would force Wingman into a shared commander/reviewer and fixed-worker model that differs from its per-product leadership and extensible organization.

multi-agent-shogun: execution and protocol audit

This chapter supports the main assessment. It concerns checkout commit aff8dc8495da26a2aad582257457655fa953b57e, inspected November 5, 2026. Findings below come from reading source and test fixtures. No live CLI, watcher, Android app, dependency installation or source test execution was involved.

Creation is a shell process plus durable files

The execution path is more specific than “agents configured in YAML.” The launcher, lines 335–454, first removes the named old tmux sessions. It preserves coordination queues by default and resets them only under --clean. It then creates the Shogun session, constructs the subordinate terminal grid and stamps @agent_id, @model_name and @current_task before launching each CLI (lines 552–672, 700–800). Its watchers are separate background processes (lines 892–939). A worker is therefore an actual independently running process, while an assignment is a record read by that process.

config/settings.yaml
   ├── agent IDs/models ──> launcher ──> named tmux panes ──> interactive coding CLIs
   ├── model tiers ──────> CLI adapter helpers <─────────── Karo's reasoning
   └── ntfy topic ───────> input listener

role + common + CLI instruction parts ──> generated instruction text

command/task/report YAML <──────────────> agent reads/edits shared files
inbox YAML ──> watcher ──> inboxN terminal nudge ──> agent reads actual message
dashboard.md <────────────────────────── Karo/Gunshi summary

Native coding tools, shell execution, provider credentials and transcript persistence belong to the selected CLI. Shogun's shell scripts do not implement a provider conversation engine or a server-side agent actor. Replacing a CLI preserves a slot ID and assignment records. It does not migrate its provider conversation. switch_cli.sh, lines 322–396, sends an exit sequence and detects shell output before relaunching. It proceeds after a shell-detection timeout, so switching is best understood as operational process replacement with recovery, not a proven seamless handoff.

Formation extensibility has three different boundaries

agent_registry.sh, lines 25–125, parses ordered cli.agents entries. It treats them as a full formation only if Karo is present, otherwise retaining the historical ten-agent set for backward-compatible partial overrides. It maps subordinate IDs to panes by list position. That makes the supervisor configurable, but does not create agent processes itself.

cli_adapter.sh, lines 1445–1467, separately extracts IDs whose names start with ashigaru. The launcher reads that list and count (lines 65–71), labels panes with the listed IDs (lines 621–632), but launches workers and watchers with ashigaru${i} for i=1..count (lines 750–783, 924–928). Sparse IDs such as ashigaru2 and ashigaru5 therefore cannot be assumed to retain a consistent identity across these paths. More than seven workers also encounter the fixed nine-pane subordinate grid (lines 602–619) and Gunshi's offset count+1 (line 787). Fewer workers leave extra panes; arbitrary additional role names are not incorporated into the launch arrays.

The third boundary is role definition. get_instruction_file, lines 347–373, recognizes Shogun, Karo, Gunshi and ashigaru*; other IDs return failure. build_instructions.sh, lines 122–161, explicitly enumerates those four roles for each CLI. A new ProductMaster profile consequently needs coordinated changes to instruction generation, role dispatch, launch, permissions, report routing and archival treatment. A new inbox filename alone is not a new fully managed agent profile.

This is why F02/F24 are partial matches. The useful abstraction is a configurable fleet of known roles. The desired Wingman abstraction is an extensible directory of profiles and project-scoped instances whose tools, tracker and dashboards grow together.

Model routing is executable assistance to management

cli_adapter.sh, lines 649–883, reads configured Bloom capability ceilings, cost groups and preferred models, filters candidates and recommends a model. Unconfigured capability defaults to level 6. This maximizes compatibility but does not validate competence. find_agent_for_model, lines 1291–1442, searches matching workers, then any idle worker, and returns QUEUE when none is available. It returns an ID, not a task lease or a launched agent. Missing panes can still return configured candidates, a convenience explicitly described for test environments in lines 1372–1375 and 1424–1427.

The command to switch a worker remains an instruction-driven Karo decision. That is a meaningful division of responsibility, but it also limits claims that routing is a self-contained automatic scheduler. The original Karo instructions, lines 55–106, prescribe Bloom labeling and Step 6.5 dynamic routing. The generated Codex Karo file, lines 1–86, starts with the prose role and task examples, without that original front-matter workflow. The source builder intends to extract front matter using exact delimiter matching (lines 62–65). The checked-out generated artifact should be assessed as it exists rather than assuming every source workflow instruction arrived in every variant.

The adapter has another concrete compatibility issue: its allowed CLI string is assigned twice (lines 21–23), with the latter omitting Cursor even though the Python parser and launch case include it (lines 183, 317–324). get_cli_type validates against that shell list (lines 220–228). Thus the presence of a launch case does not establish that normal configuration reaches it. These inconsistencies are reasons to establish one authoritative provider/role capability description before adopting the whole adapter.

Communication persistence and acknowledgment are different operations

inbox_write.sh, lines 40–145, generates IDs, serializes cooperating writers with a directory lock plus optional flock, appends an unread message and replaces the file atomically. Retries are bounded. It keeps all unread messages when pruning older read entries. The strong design idea is storing payloads in YAML while sending only a count through the TUI. The recipient can recover the payload after a missed nudge.

There are practical limits to the “guaranteed” wording in the instructions:

  • Message content is interpolated into a Python triple-quoted literal inside python -c (lines 80–101), with no data serialization step. Payloads containing that delimiter or Python escape sequences are not handled as arbitrary opaque text. The special-character test test_inbox_write.bats, lines 382–405, covers ordinary quotes/newlines/YAML syntax, not all Python literal delimiters. By contrast, ntfy_listener.sh, lines 61–81, passes mobile message text through an environment variable to Python. This is a source-level reliability and boundary finding, not a live injection experiment.
  • The writer serializes its own writes, while the common protocol, lines 67–74, tells the agent to acknowledge by directly editing the YAML. That generic operation has no shared locking contract enforced by this script. OpenCode supplies a stronger specific path: mark-as-read.ts, lines 129–208 and 233–255, performs atomic replacement under the same directory lock, verifies the target equals OPENCODE_AGENT_ID and treats an already-read message idempotently. That is useful implementation work, though not a universal CLI acknowledgment path.
  • slim_yaml.py, lines 40–48 and 298–349, loads an inbox, archives read entries and rewrites the inbox through ordinary file writes. Its wrapper, lines 15–16 and 32–54, takes a separate .slim_yaml.lock, not the per-inbox writer lock. An arrival concurrent with that read-modify-write may be overwritten. The mailbox's atomic append is therefore not an end-to-end transaction spanning archive and acknowledgment.
  • Inbox success, read: true, task done, report publication and command acceptance are separate updates. There is no broker acknowledgment, lease, transactional outbox or exactly-once work execution protocol joining them. An agent must reconstruct state carefully after interruption.

These limits do not negate the useful durable-payload design. Wingman can retain it while making all mutations use a single append/ack/archive API, passing payloads as data and explicitly deduplicating task execution by ID. Locks also need an operational recovery policy after abrupt process loss. A temporary pathname or lock directory by itself is not a distributed coordination protocol.

Recovery is substantial, but schema-sensitive

The session hook, lines 22–89, reads identity from tmux and injects role recovery instructions. Its headers identify it as a Claude hook (lines 15–18), and .claude/settings.json, lines 3–25, wires SessionStart and Stop commands. Codex instead receives a startup prompt from cli_adapter.sh, lines 594–641, and /clear is translated into /new by the watcher, lines 549–575. Role recovery and continuity are thus CLI-dependent mechanisms.

The watcher deduplicates unread auto-recovery hints (lines 353–362), checks for cancellation/idle (lines 364–380), then enqueues another task-assigned hint (lines 382–409). The guard reads only task_data.get('status'). The launcher clean template (lines 398–406) and Karo task example (role lines 63–84) put that state in task.status. The archival utility already accommodates both schemas through get_item_status (lines 63–72), but this guard does not. test_send_wakeup.bats, lines 859–915, uses flat status fixtures, so its cancellation/idle intent does not establish the guard for nested clean-start/role records. This does not prove that a cancelled task will execute: the receiving agent is still instructed to reread and obey its task. It means one layer of the claimed prevention may fail to suppress an unnecessary recovery hint.

Busy detection is also not a provider event stream. agent_status.sh, lines 33–128, reads terminal text and matches idle prompts, interrupt hints, animation rows and spinner phrases. Unknown text defaults toward idle. The watcher adds flags, throttling, clear deferral and CLI-specific key sequences. These mechanisms directly address operational failure modes; their effectiveness depends on the CLI's rendered interface and version. They should not be mistaken for a structured cancellation acknowledgment or a committed task boundary.

Finally, watcher_supervisor.sh, lines 34–92, is an optional standalone program that periodically restarts watchers for existing panes when separately run. A checkout-wide search found test references and changelog documentation, but no non-test invocation. The standard launcher, lines 893–939, starts individual watchers directly without wiring this supervisor. Its five-second restart loop should therefore not be credited as standard-launcher behavior. Even with the supervisor enabled, a pane can contain a shell after its CLI crashes. A live pane does not prove that a coding agent works or its conversation resumed. It also does not prove that an agent interpreted a product blocker. Wingman needs semantic supervision in addition to process supervision.

Instruction variants leave several coordination choices unresolved

The role/common files are operational prompts, not schemas validated by a task server. Their inconsistencies matter because agents are expected to act on them:

Concern Concrete source tension Assessment consequence
Dependency ownership Common task flow, lines 80–101, supports a blocked worker slot while also requiring blocked prerequisites to remain unassigned in pending.yaml; Karo role, lines 74–84, shows a blocked assignment. Credit dependency-aware agent coordination, not a single enforced scheduler.
Report recipient Ashigaru role, lines 65–70, routes completion to Gunshi; common protocol, lines 16–17, 97–104 and 120–125, still routes reports to Karo. The main trace follows the newer role/AGENTS intent; common examples may wake a different manager.
Supplemental completion notification Stop hook, lines 95–114, can notify Karo after matching natural-language completion/error phrases. Completion signals can also arrive outside the worker→Gunshi review route. They are notifications, not review certificates.
Command statuses Task flow, lines 13–19, omits paused; lines 46–65 then include it in the exhaustive command set. Pause/resume is a management convention with archival behavior, not a uniformly enforced state machine.
Human input protection Common protocol, lines 37–39, prohibits keystrokes when the Shogun pane is active; watcher wake-up, lines 895–917, explicitly delivers Shogun nudges even while busy. Protection against destructive resets is stronger than a blanket guarantee that human input is never touched.

What a traced request does and does not prove

An ntfy request has a concrete entry: stream JSON, filter outbound messages, persist pending input and notify Shogun (listener, lines 142–179). After that, the human intent interpretation, project matching, decomposition and acceptance are LLM actions instructed by files. The script does not itself understand “add this API endpoint” or decide which existing project is meant. That is the proper boundary for assessing this as an autonomous organization.

The most relevant end-to-end test e2e_basic_flow.bats, lines 5–12 and 120–155, uses mock CLIs and explicitly sends nudges. It verifies the protocol-shaped integration scenario as test intent, with worker completion going directly to Karo. e2e_blocked_by.bats, lines 74–89, simulates Karo unblocking via direct fixture editing. Neither demonstrates a live model obeying the latest quality-review chain, a daemon interpreting dependencies, or the complete human request→delivered product lifecycle.

The adoption implication is practical: borrow the inspectable task/command contracts, purpose validation, role recovery and separation of durable payload from wake-up. Establish authoritative schemas, mutation APIs and role generation before treating this as Wingman's organization runtime. Product discovery, Telegram conversation correlation, project leadership instances, collaboration rooms and connected executive/project/agent views remain application work beyond this shell formation.
