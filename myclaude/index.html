myclaude assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/stellarlinkco/myclaude

Local checkout: researchs/myclaude/repo. Assessed commit: f2e75c1263a2d5f09cdc4bb3dfe3635c635ff296. Package metadata identifies version 6.7.0 and an AGPL-3.0 license (package.json, lines 1–9). This is a local-revision assessment, not a claim about the upstream project's current release.

Verdict: myclaude is a useful source of execution-adapter, development-workflow and local continuation-harness mechanisms for Wingman. It is not an implementation of Wingman's persistent development organization. It can launch real independent CLI coding processes, select named specialist presets, run dependency-ordered parallel batches, retain backend session identifiers, and supply product/architecture/QA workflows. Its product is principally installable Claude Code prompts, skills and hooks plus a Go CLI wrapper. There is no implemented Telegram representative, portfolio intake service, standing agent directory, collaboration-room application, executive dashboard or multi-host control plane in this checkout.

The distinction matters: a develop preset becomes a real independently executing process when invoked, but it is not a standing BackendCoder identity with its own durable organizational membership and inbox. BMAD's Product Owner and Architect are substantive role definitions and delegated workflow participants. They are not permanently assigned ProductMaster and TechMaster instances. The optional harness adds persistent work state and local ownership leases, not an organization server. The five-phase /do loop also has a reproducible state-format mismatch that weakens its advertised completion enforcement.

Architecture and actual execution model

There are three separable layers rather than one unified platform.

  1. Installation and host integration. The npm entry point is bin/cli.js; its defaults and help describe installation, update, module selection and uninstall, not a running orchestration service (CLI, lines 13–79). install.py copies or merges module resources into the user's Claude configuration, discovers module hook manifests, replaces plugin-root variables and merges hook registrations into settings.json. It also merges agent/model presets into ~/.codeagent/models.json (installer, lines 130–219, 248–293 and 894–977). This is configuration deployment into another agent product. It was read, not executed, for this assessment.
  2. Prompt-driven workflow orchestration. /do instructs the active Claude session to initialize a local task and coordinate explorers, an architect, developers and reviewers. The human-facing orchestrator passes context and decides phase transitions. /omo offers conditional routing among exploration, documentation research, architectural advice and implementation instead of a fixed pipeline. BMAD uses the host's Task tool and supplies explicit product/architecture/planning approval gates. These transitions are primarily instructions executed by the host LLM, not a compiled business-process state machine (do, lines 9–75 and 91–168; omo, lines 8–66; BMAD pilot, lines 80–98).
  3. Real CLI execution and optional persistence hooks. The Go executable enters bootstrap, calls Cobra, resolves single/parallel execution, builds a task plan and invokes the shared executor (bootstrap, lines 3–12; app wiring, lines 39–57, 113–145 and 148–208). Backend adapters produce local commands for Codex, Claude Code, Gemini or OpenCode. The executor creates subprocesses with pipes, parses their structured output and returns TaskResult values. Optional harness scripts independently operate on harness-tasks.json, progress files and marker files through host hook events. They are not automatically the state store for every wrapper invocation.

An agent preset has backend, model, prompt file, reasoning, endpoint/key and permission-related fields. models.json is loaded once per wrapper process. Named dynamic agents can also be discovered as Markdown files under ~/.codeagent/agents/, using default backend/model settings (agent configuration, lines 18–38, 58–100, 136–153 and 181–248). Prompt contents are wrapped in an <agent-prompt> block. Installed skills can be injected into the task explicitly or selected from file fingerprints in the work directory (prompt implementation, lines 129–171 and 174–227). A preset is therefore executable configuration plus prompt text. The engine supplying reasoning, tools and conversation storage remains the selected external CLI.

The parallel execution format is text with ---TASK--- and ---CONTENT--- separators. Parsing resolves agent defaults, checks duplicate IDs and required contents, accepts dependencies, skills, worktree and resume-session fields, and produces specs (parser, lines 14–154). A topological sort rejects missing dependencies and cycles and groups tasks into layers (topology, lines 9–72). The executor runs each layer concurrently, using a semaphore when a positive worker cap is supplied, waits for the whole layer, then progresses. Failed dependencies suppress downstream tasks; unrelated tasks can continue. There is no general mailbox, conversational peer network or runtime task brokerage in this batch mechanism (executor, lines 439–623).

Persistence is deliberately fragmented: user-global presets, external-backend sessions, local /do task Markdown, optional harness task JSON/progress, optional SPARV YAML/journals/history, temporary wrapper logs, and explicitly requested JSON output. There is no common entity model connecting projects, people/agents, rooms, tasks and sessions. A Wingman integration would need that model above these components.

Agent definition and complete lifecycle

Definition, creation and identity

There are at least four meanings of “agent” here. A BMAD agent is a Markdown role definition loaded through Claude Code's Task facility. A codeagent preset is a named configuration entry or dynamic prompt file. A running worker is a newly spawned external CLI process handling one task or resumed conversation. A harness worker is an identity string that owns a JSON task lease. These meanings can be combined by the orchestrating LLM, but the repository does not make them one durable entity.

Presets choose backend/model and optionally prompt/reasoning/tool fields. Empty models on explicit configured agents cause resolution errors; dynamic agents require both global default backend and model (resolver, lines 194–241). This matters operationally because the checked-in optional module defaults include empty models for several roles: installing modules is not itself proof that those agents can run without user configuration (module config, do agent definitions). No backend was authenticated or invoked here.

Creation consists of parsing a task, resolving its preset, constructing/injecting the prompt and starting a process. Task ID, backend session ID, preset name and process PID have different purposes. A batch requires unique task IDs. A backend emits a session identifier. A worktree gets a separate date/random identifier and branch. None of these establishes persistent organizational role membership. Harness concurrent mode requires an explicit stable HARNESS_WORKER_ID; exclusive mode falls back to hostname:pid (claim, lines 265–293).

Execution, tools, permissions and routing

The wrapper sends task text as argument or stdin, launches the chosen local executable, drains stderr and parses stdout concurrently. It relies on the external CLI for tools and actual code editing. Backend endpoint/key overrides are injected into subprocess environments. The wrapper masks injected secrets in logs. Claude receives a dedicated temporary directory and has CLAUDECODE removed to support nested invocation (executor, lines 1083–1136 and 1171–1268). This is adapter engineering, not an independent tools platform.

Permission behavior must be adapted before reuse. Codex defaults to --dangerously-bypass-approvals-and-sandbox unless its bypass environment flag is disabled; Claude defaults to skipping permission prompts unless configured otherwise; Gemini is given -y. Claude forwards allowed/disallowed tool lists, whereas the Codex/Gemini/OpenCode argument builders do not implement an equivalent common permission policy (Codex adapter, lines 47–78; Claude adapter, lines 112–148; Gemini adapter, lines 85–109; OpenCode adapter, lines 14–28). These settings are execution privileges, separate from product clarification and organizational approval gates. Read-only role descriptions are not, by themselves, an OS sandbox.

Routing is explicit: a command/task names a backend or agent, and the orchestrator selects roles by prompt rules. OmO's routing signals include uncertainty about code location, external APIs and architectural risk. There is no automatic incoming-message matching against projects and no persistent recipient inbox. Context handoff is a freshly constructed prompt containing original request and previous outputs (OmO, lines 18–63).

Concurrency, isolation and dependencies

The Go scheduler is a layer-barrier executor. It does not launch a dependent immediately when its particular predecessor finishes if another task in the same layer is still running. Concurrency is controlled by a positive semaphore limit; zero means no semaphore limit in this implementation. Failure is isolated enough to retain unrelated results and skip tasks whose dependencies failed (executor, lines 481–623). Dependencies encode readiness, not automatically injected predecessor output: the code uses them for topology and failure checks, while cross-agent content transfer remains the coordinator's responsibility.

Worktree creation uses git worktree add -b do/<id> .worktrees/do-<id> (worktree helper, lines 58–96). DO_WORKTREE_DIR overrides each task's working directory before optional new-worktree creation (executor, lines 946–961). A batch inheriting one such environment variable therefore shares that worktree; per-task isolation must be arranged deliberately. Separate worktrees are not automatically merged, and dependency ordering does not synchronize changes between different worktrees.

Harness concurrent mode is a different mechanism. A short local lock protects task-state transactions, a claim records owner and lease deadline, and a renewal script can extend the lease. Expired claims become failed attempts when another claim operation runs. There is no independent reaper daemon (claim, lines 207–285). Local /tmp locks and kill(pid,0) cannot be treated as a distributed lock implementation. The harness itself instructs separate worktrees/clones to prevent rollback from destroying another worker's changes (protocol, lines 188–197).

Persistence, resume and scheduling

Wrapper results preserve backend session IDs. Codex uses e --json resume <id>, Claude uses -r, Gemini uses -r, and OpenCode uses -s. The wrapper does not own those conversations or verify their long-term retention. Resume working-directory semantics also belong substantially to the backend: the executor avoids setting a new directory in resume mode (Codex adapter, lines 37–78; executor, lines 1139–1143).

/do stores task.md frontmatter plus requirements/context/progress and a .current-task pointer; list/start/finish/update-phase manipulate that local record. finish_task clears the pointer rather than deleting historical artifacts or retiring a worker (task script, lines 152–261 and 318–343). It does not guarantee the original worker process is resumable.

The optional harness uses two durable files, task JSON and append-only progress, and an activation marker. On startup/resume/compact, a SessionStart hook injects counts, next eligible task and a recent progress line. The host still has to start/resume the session and execute the prescribed recovery protocol. Hook configuration registers Stop, SessionStart, TeammateIdle and SubagentStop events, not a timer or background session-spawn service (manifest, lines 1–60; SessionStart, lines 123–181). Claims/Stop retries do not create future wakeups after all processes have exited. The word “infinite loop” describes continuing host-agent behavior, not durable scheduling infrastructure.

Interruption, cancellation, failure and recovery

The executor listens for SIGINT/SIGTERM and cancellation. It attempts graceful termination, escalates to process kill, drains/ closes streams and returns exit code 130 on cancellation. Non-zero backend exits retain parsed message/session data where available; missing executables produce 127. A successful process without an agent message is treated as failure (executor, lines 1204–1220 and 1286–1389). There is no exposed per-task cancellation API or queued steering route; users control the wrapper/host process. The implementation explicitly ignores timeoutSec and parallel timeout. It relies on cancellation rather than an automatic wrapper timeout (lines 439–440 and 886–887). A stalled backend therefore needs external interruption or backend behavior to end it.

The core executor does not automatically retry failed tasks. /do tells its orchestrator to retry narrower work, and harness protocol adds attempts, maximum attempts, checkpoint validation and recovery decisions. The protocol instructs objective validation and potentially destructive rollback to a recorded Git baseline plus untracked-file cleaning (harness protocol, lines 224–274). Those actions are agent instructions, not automatically executed by the claim or SessionStart scripts. The scripts provide real state/ownership and continuation gates but do not themselves establish that every checkpoint, validation result, rollback or task completion is truthful.

Stop enforcement is bounded. Harness Stop permits stopping at session/task limits and has a no-progress block-counter safety valve. SubagentStop returns immediately if stop_hook_active is already set; TeammateIdle can reject idleness when tasks are eligible. A corrupt/unavailable state file can yield context/error handling or allow exit depending on the hook (stop, lines 204–233 and 274–315; subagent stop, lines 71–133; idle, lines 75–156). These are useful host-event controls, but neither unstoppable autonomy nor a supervisor guaranteeing eventual progress.

Completion, acceptance and retirement

Core completion is backend process success plus a parsed message; optional JSON output contains per-task results and success/failure counts (output, lines 44–62 and 79–120). Generated summaries and extracted test/coverage fields are reporting aids, not independent functional acceptance. /do prescribes reviews and a completion phase. Its Stop/verification hooks, however, still load task.json, while creation/update code writes task.md. In an isolated test using the checked-in scripts, creating an in-progress task produced one task.md, zero task.json, and the Stop hook exited 0 with no block. This is a verified integration gap, not merely a concern inferred from documentation (creator, lines 152–200; Stop reader, lines 14–16 and 44–60; verify reader, lines 59–73).

Harness considers no eligible pending/retryable/owned in-progress work sufficient to stop. It removes .harness-active, creates .harness-reflect, then optionally asks for bounded self-reflection using the original transcript request. “No eligible work” can also mean blocked/exhausted work, so this must not become Wingman's product-accepted state (stop, lines 235–272; reflection, lines 143–211). Reflection is another model prompt, not an external acceptance test.

Processes exit after a task. There is no durable agent retirement operation. Worktrees/branches are left to the surrounding workflow. SPARV archives session state/journal under history. Wrapper startup schedules old-log cleanup, and the cleanup can remove logs when their owning process is no longer running (app lifecycle, lines 66–102; logger cleanup, lines 408–478). Consequently returned temporary log paths should not be adopted as Wingman's permanent evidence store without copying/indexing them and changing retention policy.

Coordination trace: one feature request through actual paths

A representative /do add a backend endpoint and frontend flow request follows the shipped workflow below. This is a code/protocol trace, not a claim that this feature was run against a model during assessment.

  1. The active Claude conversation loads /do. The skill directs setup-do.py to create .claude/do-tasks/<id>/task.md and select it as current. Metadata starts at phase 1, in_progress, and carries a completion promise (setup, lines 22–54; creation, lines 152–207).
  2. The orchestrator constructs four task blocks: requirements analysis plus codebase similarity, architecture and convention exploration. This is where logical assignments originate. They are prompts, not tickets handed out by a persistent TechMaster (do phase 1, lines 93–137).
  3. codeagent-wrapper --parallel reaches BuildParallelInput, parses stdin and builds a dependency plan. Presets resolve from the user's models configuration, and per-task fields flow into execution. Topological sorting validates that dependency IDs exist (CLI input, lines 20–77; plan, lines 47–99).
  4. The shared executor gives each running task a logger and context, resolves/injects prompt and skill contents, launches the local backend and collects results. All four phase-1 tasks can execute concurrently subject to worker limit. The orchestrator receives the output summaries and decides whether the completeness score/questions justify direct human clarification (executor, lines 388–431 and 517–600; clarification, lines 140–147).
  5. A design invocation produces file touch list, build sequence, test plan and risks. The orchestrator asks about worktree use before implementation. If enabled, setup creates/selects a worktree and the coordinator supplies its path through DO_WORKTREE_DIR (do, lines 149–186). No project registry or host-placement decision occurs.
  6. The shipped full-stack example contains p4_backend and p4_frontend, with frontend depending on backend. The dependency causes frontend to be held for a later layer. A backend failure yields a skipped-dependency result. The caller must supply design/backend context or shared files explicitly. The scheduler does not turn backend output into a frontend message (example, lines 212–237; dependency skip, lines 607–623).
  7. The coordinator starts correctness/simplicity reviews and sends minor findings back to a developer; blocking findings go directly to the user with a “Fix now / Proceed as-is” choice. Phase state updates happen through task.py, rather than automatically from successful subprocess exits (review flow, lines 244–273; update phase, lines 318–343).
  8. Wrapper results can be persisted as JSON and include backend session IDs/log paths. The host completes the human conversation. Its /do Stop enforcement currently misses newly created Markdown tasks as described above. No chat-room event, portfolio status change, Butler delivery or product acceptance transition is emitted.

The harness can add a shared local work queue around such work, but it is not implicitly present in this trace. When deliberately activated, agents claim JSON tasks, renew leases and react to Stop/Idle hooks. Claims are coordination records, while discussion and human decisions remain in the host conversation or coordinator-supplied context. There is no coherent event stream joining this task state to BMAD artifacts and wrapper execution results.

Substantial additional capabilities

Heterogeneous backend routing. Wingman describes autonomous Codex agents; myclaude can route individual roles/tasks to Codex, Claude, Gemini and OpenCode, using per-agent models/reasoning and backend endpoint/key settings. This could broaden specialist execution and permit provider/model experiments. The integration consequence is a capability-normalization layer: tools, approval switches, resume semantics, emitted events, environment handling and usage accounting differ. The OpenCode adapter ignores endpoint/key injection, for example, while Claude and Codex implement it (backend adapters, lines 9–28; agent resolver, lines 181–241).

Optional Git worktree provisioning and bounded-context skill injection. These are significant worker-execution concerns not specified as Wingman product capabilities. The implementation can create isolated branches/worktrees and can inject installed domain guidance, selecting Go/Rust/Python/JS/Vue-related skills from file fingerprints. Injection strips frontmatter and enforces a default 16,000-character budget. This can make cross-backend specialist prompts portable, but fingerprint detection is coarse (package.json implies React-oriented guidance), missing skills are skipped, and injection truncation can drop instructions. It does not provision tools, dependencies or a sandbox (worktree, lines 58–96; skill injection, lines 133–227).

Transactional local claims with expiring ownership. Harness claim/renew scripts provide concrete protection against two local worker sessions taking the same eligible task. Backup/temp/replace JSON writes, lock acquisition and stale-lease handling supply more than an informal TODO file. This is useful for Wingman's assignment layer, but needs transactional shared storage or remote coordination before multiple hosts participate. It also needs schema/version rules and immutable result evidence; mutable local JSON can only tell the truth its writers record (claim, lines 105–161 and 207–297; common utilities, lines 162–171 and 191–254).

Several development-process policies. BMAD's product/architecture gates, OmO's conditional delegation, SPARV's small-change/full-flow routing, and /do's codebase-first planning are alternative process choices. They should not be mistaken for modes of one shared state engine. SPARV additionally specifies risk escalation, three-failure escalation, TDD and regular journaling, with supporting scripts. This offers a library of policies that Wingman could translate into its own role instructions, but activating several together can yield duplicate stop gates, unrelated artifact formats and competing completion criteria (SPARV, lines 12–45 and 97–149; BMAD, lines 80–98).

Host-event continuation and post-work reflection. TeammateIdle/SubagentStop hooks can keep an existing host team active, while a separate reflection marker prevents historical task state from triggering reflection arbitrarily. Bounded reflection reuses the original request from the transcript and prompts a requirement-by-requirement check. This can complement acceptance evidence, but cannot replace it. The stop path can reach reflection when all work is exhausted/blocked, and reflection itself does not execute objective validation (reflection implementation, lines 100–140 and 143–211).

Distinctive mechanisms and grounded innovation assessment

The most valuable combination is prompt-level specialization with a real heterogeneous execution substrate. An orchestrating Claude session selects roles, and the wrapper makes those roles concrete local processes with backend-specific JSON parsing, session IDs and isolated task log handles. It bridges flexible high-level delegation and operational subprocess control without requiring each specialist to be a custom agent server. Its limitation is precisely that flexibility: organizational identity, context transfer and process correctness still depend on the host LLM and external CLI contracts.

The two-tier dependency approach is also instructive. Batches use deterministic topological layers and failure propagation. The optional multi-session harness uses persistent eligibility, attempts, leases and recovery prompts. They address different timescales: scheduling one invocation versus carrying work across contexts. Wingman could borrow that separation, but should unify identifiers/results so a task lease can be traced to a particular run, conversation, commit, validation outcome and next decision. As shipped, these tiers are not one durable workflow engine.

The active/reflect marker protocol is a concrete guard against over-eager hooks: harness state may remain on disk, but .harness-active determines whether normal continuation hooks run and .harness-reflect authorizes the reflection pass. The accompanying tests exercise false-positive prevention for stale files and reflection limits (tests, lines 650–794). This is a useful adaptation pattern for introducing automation into an existing coding client without intercepting every unrelated task. Its limit is lifecycle dependence on host hook ordering and mutable marker files.

The budgeted per-task skill injection is a restrained way to carry domain guidance across otherwise unrelated backends. A developer can receive backend-specific and frontend-specific standards in one task set without assuming every CLI shares Claude's skill loader. However, skills are inserted as text, not installed capabilities, and automatic detection/truncation can select or omit consequential instructions. This should be visible in Wingman's execution evidence rather than silent model context.

These are distinctive mechanisms worth evaluating and adapting. The repository itself describes the harness as synthesized from existing engineering practices. This assessment makes no claim of historical novelty or industry uniqueness. Names such as “UltraThink” and numerical self-scores are prompt conventions rather than independently validated algorithms or assurance levels.

Practical fit for Wingman

The most direct reuse candidate is a hardened worker adapter: named presets, explicit backend selection, stdin-safe tasks, process supervision, session-ID extraction, worktree creation and structured output. Wingman could invoke a wrapper-like service from BackendCoder/FrontendCoder assignments while retaining ownership of task/project identity. The harness claim/renew logic and activation guards are useful reference implementations for local ownership and continuation. Product Requirements, BMAD PO/Architect/QA and OmO role-selection prompts provide a substantial starting point for role behavior, product clarification and verification guidance.
