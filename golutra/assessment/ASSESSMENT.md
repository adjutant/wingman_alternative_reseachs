- Basis: [Wingman purpose](../../WINGMAN_PURPOSE.md), all F01–F24 requirements in [assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md), and fresh read-only source inspection. No checkout-local `AGENTS.md` was present. The supplied global instructions applied.

**Verdict:** golutra is a useful local desktop foundation for Wingman's chat-connected agent workspaces, with real independent CLI processes, persistent member identities, group/direct conversations, prompt dispatch, terminal inspection and Codex session resumption. It does not implement Wingman's standing software organization. Its coordinator is primarily deterministic message routing and terminal state management, rather than an autonomous ProjectMaster. Product discovery, product/technical leadership, a shared assigned-ticket system, acceptance gates, Telegram intake, distributed hosts and executive summaries would remain substantial new work.

The distinction matters because the README advertises analysis-to-deployment orchestration and workflow template import/export, while the inspected source implements a smaller, concrete local workbench. The README itself places CEO Agent, automatically expanding agent networks, cross-device migration and mobile control in the future ([README](../repo/README.md), lines 164–178). Those claims receive no implemented-feature credit here.

## Architecture and execution model

The Tauri desktop uses Vue 3/Pinia for chat, friends, settings, skills, and a terminal workspace. [App.vue](../repo/src/app/App.vue), lines 79–112, selects these views. Rust startup creates `TerminalManager`, `ChatDbManager`, a command-result center, and storage. It connects message transport and repository ports. It starts status-trigger, snapshot, chat-outbox, and local command-IPC workers. See [lib.rs](../repo/src-tauri/src/lib.rs), lines 48–113. One host process supervises local children. It does not provide a web service or distributed agent cluster.

A project is an existing directory opened as a **workspace**. Desktop state holds recent workspaces and an ID-to-path registry, with local machine metadata and move/copy conflict handling ([app.rs](../repo/src-tauri/src/ui_gateway/app.rs), lines 48–55, 78–135). Project data is JSON in `.golutra/workspace.json`, falling back to app-data `<workspaceId>/project.json` when needed. Reads prefer the workspace copy; writes fall back with a warning, or use app data for read-only workspaces ([project_data.rs](../repo/src-tauri/src/message_service/project_data.rs), lines 8–28, 35–85, 91–134). Its defined contents are members, member-name sequence, recently closed terminal tabs, a roadmap objective/task list and skills ([projectStore.ts](../repo/src/features/workspace/projectStore.ts), lines 30–45). This registry selects folders. It does not infer the project from an incoming product request.

Conversation persistence uses **redb**, not SQLite. Per-workspace `chat.redb` files in app data contain users, conversations, memberships, messages, attachment indexes, a conversation timeline index, terminal-session mappings and chat outbox tasks/schedule. IDs are ULIDs and records are bincode encoded ([store.rs](../repo/src-tauri/src/message_service/chat_db/store.rs), lines 21–45, 91–108, 128–132). `TIMELINE_INDEX` orders conversations by recent activity. It is not a semantic agent work timeline. App-data chat and workspace JSON also have different portability boundaries: copying a source folder alone does not carry its chat database and live process state.

Each executing member wraps a native PTY child. A CLI type/command/path determines which executable launches. The backend creates a PTY, sets `cwd`, ensures `TERM`, spawns the child and keeps reader/writer/killer handles ([pty.rs](../repo/src-tauri/src/runtime/pty.rs), lines 152–204). The shim inherits terminal IO, reports OSC readiness and exit status, and waits for the command ([shim.rs](../repo/src-tauri/src/bin/shim.rs), lines 27–76). Built-in types are Codex, Claude, Gemini, OpenCode, Qwen and shell, while custom commands can run through the terminal path. These are tool adapters, not product-role profiles ([state.rs](../repo/src-tauri/src/terminal_engine/session/state.rs), lines 115–159; [terminalCatalog.ts](../repo/src/shared/constants/terminalCatalog.ts), lines 13–67).

The coding model, tools, authentication and most agent reasoning belong to those external CLIs. Golutra feeds terminal text, observes screens and maintains UI/conversation context. A non-shell direct launch failure may fall back to a shell, explicitly changing the runtime terminal type ([launch.rs](../repo/src-tauri/src/terminal_engine/session/launch.rs), lines 237–315). A member therefore being present or a fallback terminal being usable does not establish that an AI agent is running successfully.

## Agent definition, creation and full lifecycle

### What is an agent here?

A **member** is a persisted project participant record. It has identity/name/avatar, one of four structural roles, optional role text, status and terminal configuration. A **terminal session** is an in-memory execution wrapper with PTY handles, screen emulator, routing context and status. A **CLI session ID** is external-agent conversation identity, presently integrated most concretely for Codex. A **conversation** is a durable golutra room/DM. A **roadmap task** is a small persisted UI record. These concepts are not interchangeable: adding a member does not by itself create a durable autonomous specialist, and sending a message does not create a tracked product ticket.

Golutra does launch independent agents when the configured command is an agent CLI. It is not merely multiple personas in one model call. However, the default onboarding instruction only tells a CLI its name and that it is working with the team ([onboarding.rs](../repo/src-tauri/src/terminal_engine/default_members/onboarding.rs), lines 10–27). There is no built-in product-manager, architect, backend, frontend or tester definition, instruction bundle or division of authority.

### Definition and creation

The invite modal selects a built-in/custom CLI, instance count and access settings. It defaults unlimited access on and sandboxed off, with a per-invitation UI maximum of 20 ([InviteAssistantModal.vue](../repo/src/features/chat/modals/InviteAssistantModal.vue), lines 224–228, 294–305). `useFriendInvites` invokes backend creation, applies the returned roster, adds members to the default channel and starts sessions without opening terminal tabs ([useFriendInvites.ts](../repo/src/features/chat/useFriendInvites.ts), lines 145–215). The backend permits creation roles assistant/member, generates an independent ULID and sequenced name for each instance, initializes role text empty, stores terminal/access fields and writes project JSON ([project_members.rs](../repo/src-tauri/src/message_service/project_members.rs), lines 48–168). An invited admin is instead a local offline contact, not a newly launched management agent ([useFriendInvites.ts](../repo/src/features/chat/useFriendInvites.ts), lines 117–142).

### Identity, execution, tools and permissions

A member's terminal ID is normally `member-<workspaceId>-<memberId>`, preventing identity confusion across projects. Creation rejects duplicate live IDs, registers the PTY and starts reader/semantic handling ([commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 75–89, 157–175, 222–245, 317 onward). CLI executable resolution and local working directory govern actual capabilities. All workers in a workspace normally receive that same source directory; no automatic per-agent git worktree or merge system was found in launch/runtime/project paths.

`unlimitedAccess` has concrete CLI effects: the Codex adapter supplies `--dangerously-bypass-approvals-and-sandbox`. The registry only appends a flag when the command matches its default form ([codex.rs](../repo/src-tauri/src/terminal_engine/default_members/codex.rs), lines 5–10; [registry.rs](../repo/src-tauri/src/terminal_engine/default_members/registry.rs), lines 82–121). By contrast, `sandboxed` is stored and passed as invitation/diagnostic metadata. The terminal creation signature documents it as metadata and the local PTY spawn has no corresponding container/sandbox implementation ([commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 40–68, 255–268; [pty.rs](../repo/src-tauri/src/runtime/pty.rs), lines 152–204). Golutra's message policy also currently allows all messages. Tool permissions and meaningful approvals therefore chiefly come from the child CLI's configuration, not an organizational policy layer.

### Readiness, routing and concurrency

During invite, a terminal is locked in connecting state while a post-ready plan waits for a stable display and injects adapter-specific steps. Codex receives `/status`, waits for `model`, extracts `session:`, then receives its name introduction ([codex.rs](../repo/src-tauri/src/terminal_engine/default_members/codex.rs), lines 11–29). Stability uses recent byte-rate samples and a short fallback timeout, not a typed agent readiness protocol ([stability.rs](../repo/src-tauri/src/terminal_engine/session/stability.rs), lines 6–15, 36–84).

For human messages, a DM picks the other participant. A room picks mentioned member IDs or everyone for mention-all, excludes the sender and deduplicates. The backend verifies membership and terminal configuration, ensures sessions and batches dispatch per target ([dispatch.rs](../repo/src-tauri/src/orchestration/dispatch.rs), lines 84–180, 198–227). This is explicit addressing, not intent-based skill selection or delegation. Distinct PTYs can progress simultaneously, while one terminal's batches are serialized until semantic output flush. Consecutive pending messages with the same room/sender context merge with blank-line separators ([chat_dispatch_batcher.rs](../repo/src-tauri/src/orchestration/chat_dispatch_batcher.rs), lines 18–47, 68–149). Queueing is operational input flow, not a ticket dependency graph.

### Persistence and resume

Member identity, configuration, and messages survive application restart. Process handles, screen/semantic workers, and batcher queues remain in memory. Codex onboarding parses a native session ID from terminal lines and stores it against the workspace/member. A later non-invite creation appends `resume {session_id}`. See [post_ready.rs](../repo/src-tauri/src/terminal_engine/session/post_ready.rs), lines 173–225; [commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 103–124; and [registry.rs](../repo/src-tauri/src/terminal_engine/default_members/registry.rs), lines 141–177. Other inspected built-in adapters have no resume template. This is CLI-assisted continuity, not a universal checkpoint.

`ensureMemberSession` reuses a live session, synchronizes status, deduplicates simultaneous starts with an in-flight promise, and closes/recreates a disconnected session ([terminalMemberStore.ts](../repo/src/features/terminal/terminalMemberStore.ts), lines 565–639). Keep-alive sessions are not owned by a viewing window; ordinary ephemeral sessions are. Window destruction cleans ephemeral sessions, but application exit explicitly shuts sessions down ([commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 160–166; [lib.rs](../repo/src-tauri/src/lib.rs), lines 167–205). Closing the viewer is therefore different from surviving app/host termination.

### Scheduling, supervision, interruption and recovery

The trigger scheduler wakes on terminal facts and timer deadlines to assess readiness, output silence and status fallback ([poller.rs](../repo/src-tauri/src/terminal_engine/session/poller.rs), lines 27–95, 108–150). There is no business schedule that wakes a manager to inspect assignments or ask workers about blockers. The durable outbox is a delivery retry schedule, not autonomous project supervision.

Direct terminal write permits steering and CLI-native interruption. Backend close takes a process killer, can preserve an offline session entry or fully remove it, flushes pending semantic text and optionally deletes its CLI session mapping ([commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 1246–1440). There is no independent cancellation state attached to a ticket, execution budget or organizational goal. Native compact/fork/resume commands may be entered into a CLI, but only Codex resume is explicitly modeled in the adapter registry; no common fork/archive/compact lifecycle exists.

Recovery includes alternate-shell fallback, session-ID extraction retries/restarts, explicit offline status, recreation, and a persistent outbox. The outbox polls every 280 ms. It claims at most eight items per workspace with an eight-second lease. It retries up to six attempts with exponential backoff capped at 30 seconds. Exhausted messages become failed. See [chat_outbox.rs](../repo/src-tauri/src/orchestration/chat_outbox.rs), lines 22–27, 103–189, and 211–215; and [outbox.rs](../repo/src-tauri/src/message_service/chat_db/outbox.rs), lines 93–177. Session-ID extraction can time out and skip onboarding. It does not guarantee recovery of the conversation. See [post_ready.rs](../repo/src-tauri/src/terminal_engine/session/post_ready.rs), lines 228–291.

The human-message write and outbox enqueue are separate operations. They do not share one database transaction. An outbox item becomes sent when orchestration accepts or queues it. Later terminal batches remain in memory. A DND target returns success without dispatch. Reply paths still have TODOs for reliable queues and persistence retry. Semantic-write failure also releases the next input batch. See [chat.rs](../repo/src-tauri/src/application/chat.rs), lines 84–105; [chat_dispatch_batcher.rs](../repo/src-tauri/src/orchestration/chat_dispatch_batcher.rs), lines 68–109; [reliability.rs](../repo/src-tauri/src/message_service/pipeline/reliability.rs), lines 20–21 and 61–69; and [semantic_worker.rs](../repo/src-tauri/src/terminal_engine/session/semantic_worker.rs), lines 166–217. These paths do not establish exactly-once task delivery or crash-safe completion tracking.

### Completion, acceptance and retirement

Completion is predominantly inferred from terminal silence/output processing. Working status falls back after 4.5 seconds silence plus debounce. A chat block flushes after three seconds silence plus one-second debounce, with a 30-second forced flush fallback ([session/mod.rs](../repo/src-tauri/src/terminal_engine/session/mod.rs), lines 57–76; [semantic_flush.rs](../repo/src-tauri/src/terminal_engine/session/polling/rules/semantic_flush.rs), lines 9–81). That can release queued prompts even when the CLI is still performing a long tool call or continuing work. It is an output-boundary heuristic, not evidence that implementation passed tests or met a definition of done.

There is no modeled product acceptance/delivery transition or rule to stop active product development after acceptance. Retirement is manual member/session cleanup: close, remove member or purge terminal members. Backend purge closes sessions, deletes CLI mappings and cleans associated conversations, collecting warnings rather than aborting the whole purge ([ui_gateway/project_members.rs](../repo/src-tauri/src/ui_gateway/project_members.rs), lines 38–76). That is resource cleanup, not archival retention of an accepted project's complete work record.

## Coordination mechanics and a concrete request trace

Consider a human sending `@Coder implement the API and report the test result` into a workspace channel. This is a source trace, not an executed demonstration:

1. `chatStore.sendMessage` resolves workspace, room, sender, mentions and trace IDs, then calls the send-and-dispatch bridge ([chatStore.ts](../repo/src/features/chat/chatStore.ts), lines 607–646).
2. The application saves the message with sending status, replaces the payload's message ID with the persisted ID, and separately adds it to the redb outbox ([chat.rs](../repo/src-tauri/src/application/chat.rs), lines 84–105).
3. The worker claims due messages across workspace databases. It needs an existing dispatch window and invokes backend orchestration ([chat_outbox.rs](../repo/src-tauri/src/orchestration/chat_outbox.rs), lines 29–117).
4. Orchestration loads room membership and project-member configuration. It selects the addressed member and ensures its local PTY exists. It sends text and sender/room/message context to the terminal batcher. See [dispatch.rs](../repo/src-tauri/src/orchestration/dispatch.rs), lines 84–180, 198–227, and 332–367.
5. The batcher deduplicates message IDs, serializes one in-flight block per terminal, writes the prompt and follows with carriage return after 100 ms ([chat_dispatch_batcher.rs](../repo/src-tauri/src/orchestration/chat_dispatch_batcher.rs), lines 68–113, 153–198). The child CLI now performs its own reasoning/tools; Golutra has not created a ticket or acceptance plan.
6. Output feeds the semantic worker's emulator/filter. It emits throttled streams, then after flush creates a final terminal message containing workspace/member/room/sender/span context ([semantic_worker.rs](../repo/src-tauri/src/terminal_engine/session/semantic_worker.rs), lines 26–40, 61–129, 166–217; [semantic.rs](../repo/src-tauri/src/terminal_engine/semantic.rs), lines 135–190).
7. The message pipeline validates required identifiers and appends the reply under the member identity to the original conversation. The database writer emits `chat-message-created` and unread updates. The dispatch gate then releases the next prompt ([reliability.rs](../repo/src-tauri/src/message_service/pipeline/reliability.rs), lines 25–69; [write.rs](../repo/src-tauri/src/message_service/chat_db/write.rs), lines 437–505).

This is a valuable prompt/result loop with human-visible room context. It is not an agent organization autonomously negotiating a ticket. There are no task dependency edges, ownership transitions or management escalation events in this path. The roadmap is shared JSON with simple task states; comments and blockers can be typed into chat but have no enforced link to a roadmap task.

An agent can invoke `golutra-cli` to publish to a conversation or direct target. The CLI talks to `/tmp/golutra-command.sock` or the named pipe; parsing requires workspace/sender plus room/target and supports arrow notation. However, `execute_terminal_command` uses append-only `chat_send_message`, whereas terminal wake-up is implemented in the separate send-and-enqueue entry point. Neither ordinary CLI send nor appended terminal replies automatically traverse that wake-up path ([command.rs](../repo/src-tauri/src/application/command.rs), lines 14–61, 63–133; [write.rs](../repo/src-tauri/src/message_service/chat_db/write.rs), lines 331–379, 437–505). The local CLI is thus a useful publication bridge, but the inspected implementation does not establish a self-running request/reply network between agents. No automatic room-history retrieval/injection or agent-side ticket/chat read command appears in the command enum; new instructions carry the immediate text/context rather than the whole organization's current records.

## Major additional capabilities and adjacent products

**A heterogeneous CLI execution shell.** Wingman specifies Codex agents, while golutra's real backend adapters and custom shell/command paths allow multiple vendor CLIs in one roster. This could widen worker selection and let existing command-line tooling participate without rewriting it. Integration costs include different permission semantics, readiness patterns, output filtering and session-resume support. A single displayed status cannot hide those differences. ## Distinctive implemented mechanisms

These are grounded design ideas, not claims of historical novelty.

1. **Screen-derived chat replies preserve a familiar CLI while adding rooms.** Separate PTY screen handling and semantic emulation/filtering let output appear in chat without replacing the CLI with a proprietary agent SDK. A span connects streamed/final output to the originating room, and processing clears semantic state between blocks ([semantic_worker.rs](../repo/src-tauri/src/terminal_engine/session/semantic_worker.rs), lines 61–129, 166–217). This enables integration of interactive CLIs, with the limit that screen fragments, quiet periods and filter behavior are weaker evidence than typed tool/result events.
2. **Semantic-flush-gated prompt serialization.** One in-flight batch per terminal, message-ID deduplication and same-sender/room pending-batch merging reduce prompt collision while multiple terminals run independently ([chat_dispatch_batcher.rs](../repo/src-tauri/src/orchestration/chat_dispatch_batcher.rs), lines 50–175). Its gate follows a heuristic output flush, including forced timeout and failure-release, rather than agent acknowledgment of successful task completion. Persistent outbox acceptance also does not persist this in-memory queue.
3. **Adapter-specific onboarding extracts Codex continuity from its existing UI.** Instead of requiring a new agent protocol, `/status` screen parsing obtains an external session ID and persists it for later resume ([codex.rs](../repo/src-tauri/src/terminal_engine/default_members/codex.rs), lines 11–29; [post_ready.rs](../repo/src-tauri/src/terminal_engine/session/post_ready.rs), lines 173–267). It provides practical continuity but depends on upstream output formatting and does not generalize automatically to all CLI adapters.
4. **Independent process/view lifetime plus an explicit fidelity check.** Keep-alive terminals decouple CLI execution from an open tab. The three-way snapshot audit checks the frontend/backend/reopened boundary. This is a useful model for Wingman's drill-down views, provided app-exit behavior and distributed persistence are strengthened ([commands.rs](../repo/src-tauri/src/terminal_engine/session/commands.rs), lines 160–166; [terminalSnapshotAuditStore.ts](../repo/src/stores/terminalSnapshotAuditStore.ts), lines 504–565).

## Practical fit and remaining engineering

Golutra can directly inform a **local desktop observation/control layer**: member directory, group/direct chat persistence, prompt-to-terminal routing, background Codex sessions, reattachment and terminal output inspection. Its message/repository/event ports provide reasonable seams for replacing local implementations, and the existing Codex session mapping is especially relevant to Wingman's persistent identity requirement.

Adoption would still need a semantic agent registry above `Member`, with reusable profile instructions and independent durable instance state. A durable assigned-ticket/dependency tracker; per-project product and technical leadership; and a ProjectMaster loop that reasons over actual work rather than terminal silence. To support autonomous collaboration, agent publications must reliably wake intended peers, agents need read/write access to shared project records and room history, and task completion must be acknowledged separately from output flush. The current CLI enum is not a full organizational API.

Telegram/Butler intake, project disambiguation and clarification routing, scope/spec/acceptance artifacts, definition-of-done verification and accepted-delivery shutdown would all be new product workflows. Executive summaries and agent timelines require a new semantic event/evidence layer connected to tasks, changes and tests. A terminal stream alone does not provide those summaries. Full Codex-style fork/compact/archive, structured approvals, usage/budget/goal tracking, artifact and diff review also need explicit implementation or a richer harness adapter.

For Mac plus Endeavour operation, replace or supplement the native-only PTY executor with authenticated host workers, durable host/project placement and cross-host message/task storage. Local socket IPC, app-data redb and skill symlinks cannot provide that shared coordination by themselves. Wingman also needs a web/mobile surface or remote gateway; CSS-responsive desktop views and Tauri's mobile entry annotation do not establish phone-accessible remote operation.

Before treating this as a reusable code base, reconcile the repository's licensing statements. The README says commercial software development with the tool is allowed, while the checked-in [LICENSE](../repo/LICENSE), lines 4–18, names BSL 1.1, `Additional Use Grant: None`, a 2030-02-25 change date and GPL-2.0-or-later as change license. This report records the source text and the discrepancy. It does not establish permission for a particular production integration. No external licensing interpretation was performed.
