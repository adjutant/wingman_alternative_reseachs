# hcom assessment

Assessed on **2026-11-05** against [Wingman's purpose](../../WINGMAN_PURPOSE.md). Product: **hcom 0.7.31**, an MIT-licensed communication, observation and process-control layer for existing coding-agent CLIs. Repository: https://github.com/aannoo/hcom . Local checkout: `researchs/hcom/repo`. Actual inspected commit: **de33e31a0cdbba4c5863f7cc050d8b79aa50bcdf**. Package identity and version are in [Cargo.toml](../repo/Cargo.toml), lines 1–16.

**Verdict: a strong infrastructure candidate for Wingman's agent communication and distributed execution substrate, but a poor substitute for Wingman as a complete product.** Its agents are real independently running coding tools; its MQTT relay really connects machines and supports remote process control; its message handling is considerably more developed than an appended chat file. It does not implement the portfolio registry, product-discovery process, leadership structure, tickets, executive briefings, product acceptance or web/mobile workspaces that define Wingman's organizational experience. Those would be application layers built above hcom. Adopting it means accepting tool-specific hooks and terminal delivery as a core integration surface.

This is a source assessment, not a runtime certification. No dependencies were installed, services launched, agents started or external relay connections made. Checkout sources were unchanged. No applicable on-disk `AGENTS.md` was found in the checkout or its inspected ancestor/report directories. The supplied global instructions were followed.

## Architecture and actual execution model

The executable is Rust, with small JavaScript/TypeScript and Python adapters for tools that expose plugin APIs. [main.rs](../repo/src/main.rs), lines 47–91, scrubs inherited identity for nested agents, initializes configuration, installs logging and hands execution to the router. [router.rs](../repo/src/router.rs), lines 23–48 and 119–163, separates ordinary commands, launch/resume/fork aliases and tool hook handlers. Running `hcom` also provides a Ratatui terminal interface. This is not a web control server.

There are four cooperating execution paths:

1. **CLI launch and control.** The launch command parses hcom flags while retaining the underlying tool's arguments. `LaunchParams` carries the tool, process count, working directory, initial/system prompt, tag, name, background mode, prior session and unread-message cursor. The launcher validates installed tool availability and arguments, builds the environment and per-run hook configuration, reserves names and starts real terminal or background processes. See [commands/launch.rs](../repo/src/commands/launch.rs), lines 1–23 and 516–674; [launcher.rs](../repo/src/launcher.rs), lines 147–213, 1735–1845 and 1969–2100. hcom does not itself call a language model or implement coding tools: the launched CLI owns the model interaction and coding loop.
2. **Local coordination.** Hooks, plugins and CLI commands use SQLite. The database has event, instance, process-binding, session-binding, notification-endpoint, Claude actor-capability and generic key/value records. It has no project/ticket/product schema. SQLite uses WAL, foreign keys and a five-second busy timeout. See [db/mod.rs](../repo/src/db/mod.rs), lines 158–164 and 329–420. Defaults live under `~/.hcom`, with `HCOM_DIR` providing namespace selection; [paths.rs](../repo/src/paths.rs), lines 1–38. Event insertion invokes subscription processing after the record is written, so watches are part of the coordination path, not just a TUI filter: [db/events.rs](../repo/src/db/events.rs), lines 450–526.
3. **Agent observation and message delivery.** Tool hooks record status, commands and file activity, bind the tool's session to an hcom identity and deliver unread messages as model context. Idle delivery may use a native plugin/mod, a blocking hook or a PTY submission, depending on the integration. The PTY wrapper proxies the real CLI, tracks its screen and runs a delivery state machine with prompt-readiness, user-typing and approval gates. Its states include idle, injecting, submitting, verifying and retry delay; [delivery.rs](../repo/src/delivery.rs), lines 1552–1605 and 2042–2139. The per-tool configuration registry explicitly distinguishes hooks, gates, background launch mode and prompt shape; [integration_spec.rs](../repo/src/integration_spec.rs), lines 1–17 and 43–135. Adding a new CLI still requires behavioral adapter code, not merely a registry row.
4. **Cross-machine relay.** A separate relay worker is automatically started when relay is enabled, including on a machine with no local agents so it can receive remote launch requests. Each device retains its own local database. State snapshots and event batches travel through MQTT, are imported into the receiving database and acquire device-qualified identities. Remote commands use request/result RPC. [relay/worker.rs](../repo/src/relay/worker.rs), lines 1–31; [relay/push.rs](../repo/src/relay/push.rs), lines 288–378; [relay/pull.rs](../repo/src/relay/pull.rs), lines 190–213, 620–888 and 930–951; [relay/control.rs](../repo/src/relay/control.rs), lines 435–495. This is real remote execution control, not a local subprocess labeled remote. It does not synchronize repositories, deliver artifacts or choose where projects should live.

The TUI reads the same coordination data and dispatches actions through subprocess calls to the same executable, with no mandatory local daemon for ordinary TUI operation. [tui/rpc.rs](../repo/src/tui/rpc.rs), lines 1–4 and 49–55. The relay daemon is specifically an MQTT worker, not a persistent project manager: [commands/daemon.rs](../repo/src/commands/daemon.rs), lines 1–17.

## Agent definition and complete lifecycle

### What an agent is

An ordinary hcom agent is a **bound participant representing an external coding-tool session and usually a running process**. The live `instances` row is operational state. A tool session ID names the conversation; `HCOM_PROCESS_ID` is hcom's routing/binding token. The OS PID identifies execution. These are deliberately separate. Parent session/name fields identify relationships, and a tag decorates/group-selects an instance. A launch batch identifies a group of launches, not a product or task. A message request is free text with metadata, not a durable ticket. [db/mod.rs](../repo/src/db/mod.rs), lines 349–402; [launcher.rs](../repo/src/launcher.rs), lines 2023–2100.

There are important exceptions: an ad-hoc participant may be a process using `hcom start/listen`, and a Hermes gateway bridge represents a chat route with no hcom-owned coding subprocess. The bridge explicitly documents that stopping it leaves the gateway/chat running; [hooks/hermes_bridge.rs](../repo/src/hooks/hermes_bridge.rs), lines 1–13 and 108–125. Thus not every directory entry proves a separate autonomous coding agent. For Codex, native internal subagent/consolidation hooks are deliberately excluded from rebinding and driving the parent session's status; [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 763–790. The independently launched CLI instances are the strongest match to Wingman workers.

### Definition, creation and identity

The user or an already-running agent selects tool, count, cwd, explicit/generated name, tag, initial task prompt, system prompt, environment, tool flags and terminal/background mode. Global TOML/environment supplies timeout, notes, tool defaults, delivery mode and relay settings. This is configuration for an invocation, not a reusable first-class organizational role. [config.rs](../repo/src/config.rs), lines 299–363; [commands/launch.rs](../repo/src/commands/launch.rs), lines 618–674.

Launch validates the executable and arguments, rejects an hcom data directory inside metadata directories that agents cannot write, canonicalizes cwd and configures tool-specific integration. It saves the original user/config arguments before injecting per-run hooks, trust settings or initial prompts, so resume does not blindly replay stale path-specific flags. Each requested instance gets a separate environment and process token. The launch metadata and placeholder identity allow control before the tool's first hook. Initial task prompts launched by another hcom participant receive a reply-to-launcher instruction. [launcher.rs](../repo/src/launcher.rs), lines 1735–1845, 1969–2100. The hook-facing binding layer reconciles placeholder, process and session identities and records terminal launch context; [instance_binding.rs](../repo/src/instance_binding.rs), lines 1–18 and 24–82.

The injected bootstrap tells an agent its hcom name, human authority, command syntax, intent/reply conventions and available peers. It explicitly says this is session context, not an immediate task, and does not replace native subagents. [bootstrap.rs](../repo/src/bootstrap.rs), lines 68–125. These are prompt instructions, so delivery acknowledgments cannot prove the model obeyed the organization's intentions.

### Execution, tools and permissions

Each external CLI executes its own model loop and tools. hcom launches the CLI in the current/new terminal or runs it detached with a PTY. Default background Claude uses a live PTY. An explicit print-mode invocation uses a separate native-print path kept alive via stop-hook behavior. [launcher.rs](../repo/src/launcher.rs), lines 1735–1774; [integration_spec.rs](../repo/src/integration_spec.rs), lines 89–113. Headless therefore means “without a visible terminal,” not an ephemeral one-shot text generation.

Permissions largely follow the underlying CLI and host account. hcom can add tool-specific communication permissions. Its safe-command recognizer rejects shell composition, backticks, expansion and extra commands. The safe list includes communication, inspection and configuration operations ([hooks/common.rs](../repo/src/hooks/common.rs), lines 52–118). Automatic approval and workspace trust are configurable. See [config.rs](../repo/src/config.rs), lines 319–324, and [launcher.rs](../repo/src/launcher.rs), lines 1984–1990. Wingman still needs central capabilities for product roles. These must define who can deploy, alter infrastructure, read secrets and approve decisions.

### Routing and concurrency

An agent sends with explicit identity or a validated live binding. Recipients resolve to instance names/tags, broadcast scope or thread members. `--intent request|inform|ack`, reply references and threads shape conversation but do not create a scheduler task. Separate CLI processes execute concurrently; hcom does not serialize their repository writes. SQLite WAL and binding/cursor rules coordinate control-plane updates, while file-collision watches merely detect activity overlap. [commands/send.rs](../repo/src/commands/send.rs), lines 258–338 and 389–489; [db/mod.rs](../repo/src/db/mod.rs), lines 158–164; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 1237–1244 and 1368–1391.

Device suffixes route remote control through MQTT RPC to the machine holding the real process. A remote fork requires an explicit target working directory. The code cannot assume the local cwd exists remotely. [commands/resume.rs](../repo/src/commands/resume.rs), lines 124–181. There is no built-in worktree/branch reservation, integration queue or placement optimizer. Independent specialists still need workspace and merge discipline.

### Persistence, resume and fork

While live, the instance record holds status and unread position; events preserve communication/activity. The underlying CLI's transcript remains the conversation store. Stop captures the tool/session/cwd/launch args/parent/tag/background metadata and unread cursor before deleting the live record. Resume loads a stopped snapshot or adopts an existing transcript, validates whether that tool supports the operation and reconstructs a launch plan. A tracked resume retains name, prior session and cursor. A tracked fork reserves a fresh child name and rewrites identity prompts while relying on the CLI's native fork support. [hooks/common.rs](../repo/src/hooks/common.rs), lines 1363–1391; [commands/resume.rs](../repo/src/commands/resume.rs), lines 398–485, 556–621 and 705–733. Missing session/transcript state can prevent restoration. This is not an independent, portable model-conversation archive.

Subscriptions and thread memberships are also included in stop snapshots and can be restored. Replay is positioned at the stop boundary to avoid re-evaluating old events with hindsight; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 360–395. This is useful continuity for an agent waiting on other workers, but there is no task backlog or product decision state to restore automatically.

### Scheduling, interruption and cancellation

The scheduling primitives are reactive: durable event subscriptions, request-watch subscriptions, `events --wait` and workflow scripts such as `onidle`. They can wake an idle agent or launch a successor when another goes idle. They do not independently choose useful portfolio work or periodically run a ProjectMaster review. [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 318–357 and 740–790; [scripts/bundled/onidle.sh](../repo/src/scripts/bundled/onidle.sh), lines 1–28. Hooks/PTYs have polling, retry and heartbeat timers, and the relay worker has its own watchdog. These timers monitor transport/process health.

Mid-turn steering reaches supported CLIs after tool calls through hooks; idle steering uses the integration's wake path. PTY submission checks approval state and current human typing before inserting/submitting text. The message loop has retry delays and verification rather than assuming a successful write means the agent consumed the message. [delivery.rs](../repo/src/delivery.rs), lines 1552–1605, 2042–2139 and 2271–2301. Direct `term inject` is a lower-level input-control surface, not the same semantic guarantee as the queued mailbox.

`stop` disconnects/finalizes hcom participation; `kill` additionally targets execution and supported terminal panes. These should not be confused with a task-level cancel that rolls back edits. Kill marks intent before signaling to preserve the reason despite racing PTY cleanup, guards against a reused PID, and restores tracking/status when termination fails. [commands/stop.rs](../repo/src/commands/stop.rs), lines 47–105; [commands/kill.rs](../repo/src/commands/kill.rs), lines 952–1036. Remote kill follows the same device-control path. Native CLI interruption and hcom kill do not imply cancellation of external side effects already performed.

### Failure, recovery, completion and retirement

Launch placeholders time out into launch-failure diagnostics; status calculation considers liveness and wake grace rather than trusting a stale string forever. [instance_lifecycle.rs](../repo/src/instance_lifecycle.rs), lines 25–61 and 248–295. Hooks prepare batches before advancing their cursor, and acknowledgments are forward-only and guarded against a replaced instance incarnation. Codex commits after serialized output successfully flushes. This avoids losing messages on a failed output write and avoids an old delivery moving a newer cursor backward; [hooks/common.rs](../repo/src/hooks/common.rs), lines 304–395; [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 980–1016. It is a transport-side acknowledgment, not proof the agent reasoned about or completed the request.

A request watch detects “went idle/stopped without replying,” with tool-specific handling for noisy intermediate idle states. It prompts follow-up but does not restart failed implementation tasks or adjudicate successful completion; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 194–266 and 318–357. For Codex, Stop marks `listening`, making it available for further work; [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 940–951. Task completion and product acceptance remain a conversation-level convention. There is no completion gate tied to tests, definition of done or human acceptance.

Retirement snapshots and cleans live bindings, subscriptions, endpoints and scoped actor capabilities. Snapshot publication and row/control-plane deletion happen in one transaction. An event-write failure rolls deletion back so teardown can be retried. Parent teardown also accounts for child relationships. [hooks/common.rs](../repo/src/hooks/common.rs), lines 1393–1420 and 1478–1527. Database archives preserve historical coordination stores; [db/mod.rs](../repo/src/db/mod.rs), lines 814–867. This is runtime/session cleanup, not an archive of an entire accepted product with immutable deliverables.

## Coordination mechanics and traced request

The shared coordination record is an append-only event stream plus mutable instance and KV records. Messages preserve sender kind, delivery scope, intended recipients, intent, thread, reply reference and optional context bundle. Threads are seeded through participants and subsequent unaddressed thread sends target the stored membership. They are not access-controlled project rooms. Request/inform/ack conventions reduce conversational ambiguity, and send rejects ack-on-ack and ack-to-inform replies to reduce unproductive loops. [commands/send.rs](../repo/src/commands/send.rs), lines 280–338 and 405–459. There are no tickets or task-dependency edges: subscriptions express event conditions, not prerequisite work satisfaction.

Consider a real supported request shape: an existing agent sends `hcom send @nova --intent request --thread api-review -- "Review the API change and reply with test failures"` while `nova` is a Codex session. The following is a **source-traced path**, not a request executed during this assessment:

1. Identity resolution distinguishes instance, external and system senders and supports a live process binding; [identity.rs](../repo/src/identity.rs), lines 382–468 and 650–665. Send queries currently deliverable agents, excludes stopped/failed/explicitly exited records and resolves the explicit target; [commands/send.rs](../repo/src/commands/send.rs), lines 258–338.
2. Send writes a `message` event containing the text and `delivered_to`, creates/updates the thread membership and creates a one-shot request watch for this sender/recipient/event. The event's ID is the reply correlation key. It wakes local delivery loops and triggers an immediate relay push; [commands/send.rs](../repo/src/commands/send.rs), lines 389–489. A remote participant would receive an imported, namespaced event rather than a shared network-mounted SQLite row.
3. The database invokes subscription processing for the new event. A relevant standing watch may produce a system notification or message reaction; reactions carry subscription-chain metadata rather than being invisible side effects. [db/events.rs](../repo/src/db/events.rs), lines 495–526; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 740–790 and 1133–1200.
4. If Codex is already working, a PostToolUse hook prepares unread mail and returns it in both visible `systemMessage` and model-facing `additionalContext`. Cursor advancement occurs only after successful JSON output and flush; [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 753–761, 920–937 and 980–1016. If idle, the PTY delivery loop waits for a safe prompt and injects/submits through its gated state machine; [delivery.rs](../repo/src/delivery.rs), lines 1552–1605 and 2042–2139.
5. Codex's implementation and test execution take place in Codex, outside hcom. Tool hooks update status and file/command activity; multi-file patches produce additional file events so collision watches can see each touched path; [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 895–910.
6. The agent replies with `hcom send` using `--reply-to` and the thread. The explicit reply correlation can satisfy/cancel the request watch. If it goes idle or stops without an appropriate reply, the sender receives a watch notification instead; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 194–266 and 318–357. A reply says what the agent reports; hcom does not verify whether the test claim is true.
7. The human sees the communication/activity in the TUI or attached terminals. A connected Hermes chat can expose incoming messages with off/preview/full visibility and inject them through the gateway's allowlist-checked public API; [hermes_plugin/__init__.py](../repo/src/hermes_plugin/__init__.py), lines 1106–1131 and 1412–1437. hcom does not decide that a test failure warrants a management escalation or attach it to a product ticket.

The closest human-decision path is an agent message to a bridged chat, followed by a human response through Hermes and hcom. This is usable messaging infrastructure, but Butler would still need durable question IDs, project/task association, decision ownership and answer-routing rules. Native CLI approval prompts concern tool execution and remain distinct from this business/product decision path.

## Major additional capabilities

**Heterogeneous coding-tool interoperability.** hcom integrates Claude, Codex, Gemini, OpenCode/Kilo, Pi/OMP, Hermes, Cursor, Kimi, Copilot, Qoder, Grok and Antigravity rather than assuming every worker is Codex. The typed registry unifies launch, delivery, help and resume facts while retaining adapters; [integration_spec.rs](../repo/src/integration_spec.rs), lines 1–17 and 43–135; [router.rs](../repo/src/router.rs), lines 119–163. Wingman could use different tools as specialist/reviewer resources, but every additional tool introduces permission, transcript and lifecycle compatibility obligations. This flexibility exceeds the stated all-Codex starting organization.

**Remote inspection and execution control as one protocol.** The relay carries not just chat but remote launch, kill, resume, screen read/inject, transcript, event-query, subscription and configuration RPC; [relay/control.rs](../repo/src/relay/control.rs), lines 449–483. This is particularly useful for supervising Endeavour from the Mac. It also makes relay membership highly privileged. The source security model is a single operator trust domain with a shared key, no read-only peers, per-device permission scopes or token expiry; [SECURITY.md](../repo/SECURITY.md), lines 17–44. Wingman would need to choose whether that is sufficient for its own two hosts and design a separate boundary for less-trusted workers.

**Context handoff with inspectable provenance.** Bundles gather descriptions and references to files, event IDs and transcript ranges. A bundle can extend an earlier one. Preparation reads the actual session exchanges and recent categorized events and proposes relevant files; validation checks shape and bounds estimated output size. [commands/bundle.rs](../repo/src/commands/bundle.rs), lines 720–803 and 919–1036; [core/bundles.rs](../repo/src/core/bundles.rs), lines 105–165 and 251–290. This is a useful way to hand investigations to another specialist while preserving references. It requires accessible underlying files/transcripts. It is not an immutable artifact package or substitute for curated project knowledge.

**Composable event reactions and collision awareness.** Subscriptions can match status, commands and file events, and request watches are automatically attached to directed requests. Collision notifications compare observed file activity across agents. They can reveal concurrent edits before a human notices. [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 318–357, 740–827 and 1237–1391. Wingman could build blocker and integration watches on these primitives. Collision detection does not reserve files, isolate worktrees or resolve conflicts, and a quiet/stuck task still needs a higher-level supervisor.

**Reusable multi-agent evaluation workflows.** Bundled debate and confession scripts launch or recruit participants, send role prompts, wait for responses and perform cleanup. Confession compares a participant's self-report with a fresh transcript-based calibration and a judging agent; [scripts/bundled/confess.sh](../repo/src/scripts/bundled/confess.sh), lines 1–61. User scripts can override bundled workflows; [commands/run.rs](../repo/src/commands/run.rs), lines 1–4 and 89–112. These are useful research/quality patterns beyond the baseline product description. They remain script-orchestrated model judgments and cannot replace executable tests or product acceptance.

## Distinctive mechanisms and grounded innovation

The following are meaningful design choices demonstrated by code, without claims of historical invention or industry uniqueness.

**A persistent mailbox delivered at each CLI's native turn boundaries.** hcom separates the durable message from its delivery adapter. It can show Codex hook output to the user and put the same content into model context. It advances the cursor only after successful output. It rejects an old acknowledgment after stop/resume replaces an instance. See [hooks/common.rs](../repo/src/hooks/common.rs), lines 304–395, and [hooks/codex.rs](../repo/src/hooks/codex.rs), lines 753–761 and 980–1016. This permits communication without owning the model runner. Hook output proves transport delivery only. Compatibility depends on each tool's contract.

**Terminal state becomes a delivery safety signal.** For tools without an adequate native wake surface, hcom combines captured screen readiness, approval detection, typing awareness and verified submission. The code has explicit states, retries and per-tool gates rather than treating stdin as an always-safe queue; [delivery.rs](../repo/src/delivery.rs), lines 1552–1605, 2042–2139 and 2271–2301; [integration_spec.rs](../repo/src/integration_spec.rs), lines 71–87. This preserves usable real interactive CLI sessions while enabling automation. It is also a maintenance hotspot: terminal layout, prompt and approval changes in upstream tools can invalidate assumptions.

**Request completion is observed without pretending to be a task engine.** Sending an intentional request creates a durable watch for idle/stop without reply, with tool-specific idle grace and reply cancellation; [db/subscriptions.rs](../repo/src/db/subscriptions.rs), lines 194–266 and 318–357. This enables an agent to discover a dropped conversation handoff. The mechanism deliberately has weaker semantics than a ticket: “idle without reply” is actionable evidence, not a proof of failure, and a syntactically valid reply is not acceptance.

**A distributed agent namespace with encrypted control and gap recovery.** Relay payloads use XChaCha20-Poly1305 with associated data binding relay ID, MQTT topic and timestamp. Replay checks distinguish fresh control from retained state, and missed event ranges trigger bounded backfill using remote event queries and device/event-ID deduplication. [relay/crypto.rs](../repo/src/relay/crypto.rs), lines 1–18 and 64–148; [relay/replay.rs](../repo/src/relay/replay.rs), lines 1–23 and 75–149; [relay/backfill.rs](../repo/src/relay/backfill.rs), lines 1–14 and 99–167. This lets independent local databases offer useful cross-host continuity over a broker with packet limits. It is not a globally transactional shared database, guarantees no project filesystem synchronization, and uses total-trust shared-key membership.

**Session/process/actor distinctions prevent identity corruption.** Nested identity scrubbing, separate bindings, incarnation-checked delivery acknowledgment and transactional stop snapshots address real races between tools, child processes, forks and cleanup. [main.rs](../repo/src/main.rs), lines 47–70; [instance_binding.rs](../repo/src/instance_binding.rs), lines 1–18; [hooks/common.rs](../repo/src/hooks/common.rs), lines 314–333 and 1478–1527. This gives a more credible foundation for persistent workers than equating a display name with a live PID. It still preserves a tool session rather than an independently defined organizational employee record.

## Practical fit for Wingman

Wingman could directly reuse hcom to launch named Codex workers, send targeted/room-like threaded messages, observe commands/files/status, wake agents after handoffs, resume conversations and route real remote control between Mac and Endeavour. The existing TUI would be a useful operational console. Context bundles and event provenance could support debugging and explainability before the executive dashboard is complete.

Adaptation would need a stable application-facing interface around CLI commands/JSON and event records. The TUI itself already calls the executable rather than a general service API. Wingman should introduce durable organizational agent IDs and project/team memberships above hcom's session/process identities, map Room1/Room2 to managed membership, retain question/decision correlations and translate low-level events into meaningful per-agent summaries. A Hermes gateway bridge may accelerate Telegram connectivity, but using it adds a separate gateway/plugin runtime and does not implement Butler. The relay can connect hosts once software and product workspaces are provisioned; project placement and Git/artifact transfer remain Wingman responsibilities.

The largest remaining work is the product layer:

- Portfolio intake and registry.
- Butler, ProjectMaster, ProductMaster and TechMaster policies.
- Proportional discovery, scope, specification and acceptance records.
- Tickets, ownership and dependencies.
- Recurring supervision, delivery acceptance and stopping rules.
- Linked directory, chat, project and executive interfaces for web/mobile use.
- Detailed session controls.

A tag or thread can carry a reference to these records. It should not be their sole identity or source of truth.

There are three practical boundaries to resolve before choosing hcom as a foundation. First, tool hook/PTY compatibility is part of ongoing operations, so upstream Codex changes require contract validation. Second, the relay grants every enrolled device broad control, which suits one operator's own machines better than independently permissioned teams. Third, runtime progress events do not answer whether a product is actually closer to acceptance: a semantic work model and test/delivery evidence must exist above the event stream. The code is promising for transport and execution; its completeness in those areas should not hide how much Wingman's organizational behavior remains to build.
