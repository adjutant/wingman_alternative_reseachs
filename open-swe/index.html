Method Read-only source and test inspection; no dependency installation, service startup, remote execution, or live integration calls

Verdict: a substantial delivery-engine and coding-workspace reference, but not an implementation of Wingman's standing development organization. Robin has real concurrent worker agents, persistent conversations, durable coordinator/worker messaging, Slack intake and concierge routing, reviewable plans, sandboxes, detailed coding workspaces, scheduled work, CI follow-up, and sophisticated PR review/delivery machinery. These capabilities are materially closer to useful autonomous engineering than a collection of role prompts. Its durable organizational objects, however, are principally threads, tasks, workspaces, projects-as-thread-folders, people, PRs and automations. ProductMaster/TechMaster-style project leadership, a specialist profile directory, a shared product ticket system, proportionate domain discovery, product acceptance, portfolio supervision and executive agent summaries remain to build.

The most important deployment boundary is architectural: the checked-out live agent implementation requires Managed Deep Agents (MDA). It is not the older self-contained Open SWE graph implementation suggested by some historical descriptions. The backend refuses startup without an MDA URL and runtime-token secret. The model loop, checkpoints and tool execution run in the separate mda/ project. A desktop or CLI "local" thread still runs the cloud agent and serves its filesystem/shell from the user's machine. This is not a native Codex-agent organization. See runtime client, lines 1–7, 58–78, 120–161; desktop preparation, lines 824–851; CLI, lines 32–51.

Architecture and actual execution model

Control plane, runtime and interfaces

The backend is a Python ASGI/FastAPI application registered as openswe.webapp:app, surrounded by the Agent Server API. langgraph.json registers agent, reviewer and review-scout, but these names should not be read as three standing employees. They select three run kinds that MDA executes through one deployed graph, open-swe. The runtime graph factory, lines 1–30, 126–175, 230–342, builds a shared graph from model choices, installs middleware, and declares both ordinary subagents and an asynchronous general-purpose worker graph. The graph is cached/shared, while identity, catalog and state are resolved for the current run. Sharing the compiled graph is not sharing conversations.

PostgreSQL is the durable control-plane store. ThreadStore, lines 129–220, owns the indexed thread record, copies metadata to the relevant runtime, reads state from that runtime and removes runtime/index copies on deletion. ThreadRouter, lines 258–345 and 390–446, answers thread creation/search from the index, creates all new threads as mda, rewrites run payloads and forwards them to MDA. Older local runtime threads remain readable but reject new activity; succession, lines 1–36, creates metadata-carrying successor threads for continuing system work. A migration successor is not proof that the entire predecessor conversation/checkpoint is copied.

The backend resolves a run's tool set, model choices, skills, sandbox specification, grants and loop rules once before dispatch. It signs the run token and sends a names-only catalog in context. MDA calls named typed backend endpoints for operations needing credentials or database access. RunCatalog, lines 1–7, 111–145, 190–240, shows both the data-driven catalog and an important tool boundary: delegating coordinators receive start_async_task; Deep Agents' other async management tools and synchronous task are withheld in that mode. Robin's own durable task tools manage workers afterward. Client, lines 97–161, signs the resolved run. The backend is not executing middleware around every model call in-process.

Human interfaces include the React dashboard, Electron desktop shell, CLI, Slack, GitHub and Linear. MDA channel declarations call the backend to decide which run an inbound event should start; see channel intake, lines 1–7, and the actual channel declarations under mda/channels. Workspace routing is explicit precedence, rather than semantic portfolio management: recorded thread workspace, opening-message tag, Slack channel binding, repository binding, person's default, instance default (routing, lines 1–19, 141–190). Projects are named folders of threads, optionally bound to a repository; their own module explicitly says they only group threads, and thread authorization remains separate (project store, lines 1–9, 70–126, 147–174).

Execution and persistence boundaries

A coding thread normally has one persistent Linux sandbox owned by MDA. Workers have separate conversations/checkpoints but inherit their coordinator's sandbox and its repository/workspace/access metadata (worker indexing, lines 393–478). This permits fast collaboration on one checkout but gives no automatic file, branch or test-process isolation among siblings. The prompt explicitly instructs file ownership and setup coordination and calls those instructions behavioral guidance rather than an isolation boundary (task role prompt, lines 62–78).

The alternative execution path is a remote filesystem and command bridge, not an alternative local model loop. A cloud run enqueues shell/file requests in PostgreSQL. A CLI or desktop client on another machine claims and answers them. Heartbeats, liveness checks, conditional transitions and SKIP LOCKED claims make this more substantial than a local subprocess wrapper (bridge store, lines 1–19, 91–132; bridge backend, lines 1–12, 105–175). Electron records checkout/worktree ownership and diff checkpoints locally. The backend retains title, transcript and read state under the same cloud thread ID (local thread store, lines 11–32). "This Mac" can therefore be driven from elsewhere while the app serves its bridge, but task workers all share the coordinator's chosen execution location.

The MDA middleware loop handles task context, inbox additions, model routing, GitHub-proxy refresh, reply obligations and end-of-run work. RunLoop, lines 1–12, 300–339, 461–508, 626–710, demonstrates that these are actual control-flow mechanisms, not just prompt prose. Nonetheless, task correctness and PR/product completion are still largely model judgments. The goal-mode guard checks that a successful work-state or wait tool was called. It does not independently prove that the requested product has met its definition of done.

Agent definition and lifecycle

1. What an agent is, and how it is configured

There are several distinct concepts that should not be collapsed into one "agent":

  • A graph definition is a reusable compiled model/tool/middleware shape. MDA shares it across runs and users. agent, reviewer and review-scout are run kinds played on it.
  • A thread is the durable conversation and execution-state identity. It carries an owner/principal, source, workspace, optional project/repository, model settings and sandbox reference. The dashboard often calls these threads "agents".
  • A run/invocation is one period of work on a thread, whether started by a person, automation, worker event or resumption.
  • An async worker is a real MDA subagent thread registered as a member of a durable Robin task. Its assignment is a prompt plus persisted delegation data, not an independently provisioned employee profile.
  • A task connects one coordinator thread and workers. It is not the entire product backlog. A sandbox is an execution environment, not agent identity. A background shell command or monitor is a process, not another coding agent.

These distinctions follow graph construction, lines 1–30, 126–175, 306–333; task model, lines 27–35, 146–179; and thread metadata construction, lines 280–347.

Configuration is layered by deployment/workspace/person/thread/request, then resolved into the run catalog. Actual tools and integration grants are computed from the current run's permissions and credentials. Workspace and repository instructions, personal instructions, memories, skills, source-specific rules, task role and run context are assembled into the model input. A worker normally inherits coordinator model/effort, while reviewer and scout use different catalogs and limits. RunCatalog, lines 122–145, 174–240; server, lines 2155–2277; kinds, lines 72–97. Defining a new permanent organizational role still requires an additional domain model and lifecycle policy.

2. Creation, identity and routing

An authenticated dashboard session creation resolves repository access and workspace defaults, generates a thread UUID and persists title/owner/visibility/model/repository metadata. With PostgreSQL configured it stamps transcript version v2 and appends a ThreadCreated event. The API may then issue run.start. Routes, lines 105–141; session creation, lines 262–381, 444–481. ThreadRouter indexes new threads as MDA and creates the remote runtime thread. Thus a fresh human request normally creates or continues a session. It does not create ProductMaster and TechMaster agents as a project onboarding transaction.

For delegation, the coordinator must own the relevant task context, have an attached sandbox, a usable connected execution machine where applicable and a configured completion webhook. Sandbox guests cannot create further siblings themselves. MDA parent metadata is checked before the backend accepts a worker. The stable tool-call ID is used as the launch identity. Reservation takes a PostgreSQL advisory transaction lock on the coordinator, ensures one task, creates coordinator/worker membership, and rejects replay attempts that reserved another worker for the same launch. Worker indexing then validates persisted ownership, workspace, task, sandbox host and access metadata. Delegation authorization, lines 491–590; reservation, lines 43–125. This is real identity and authorization work. It is much stronger than assigning a role name in a prompt.

3. Execution, tools and permissions

Before the run starts, the backend resolves the catalog and signs a token; MDA adopts that run-specific context. File/shell tools execute in the selected sandbox or through backend-served remote files/bridges. The same middleware checks apply when these tools are composed through code mode. Shell commands matching push/PR patterns go through backend guards; reads can validate images and load ancestor AGENTS.md instructions. File tools, lines 1–15, 56–78, 83–126. This is not a universal authorization barrier for all possible shell/network mutations: the detected shell patterns and workflow approval policy have narrower coverage. Reviewer catalogs omit commit/push/PR-creation tools and use read-only review credentials, but review instructions alone do not make a general shell immutable (reviewer, lines 1–15, 45–48).

Human and machine identities are also differentiated from mere attribution. A wakeup/event/task-message run can be attributed to a person without acting as that person; only verified sender-triggered runs receive the acting-user field (dispatch preparation, lines 387–418). Machine bridges authorize the run against their owner on every request and fail when disconnected, rather than silently replacing the workspace (bridge backend, lines 113–123, 177 onward). Wingman could reuse this separation when implementing Telegram-delivered decisions, but cannot infer employee authority from a worker message.

4. Concurrency and communication

Launching an async worker returns its thread immediately. Coordinators remain able to respond to new human input and do other work, then end their turn when waiting so completion can wake them. All task threads share one mutable sandbox and separate conversations/checkpoints. There is no evidence of an enforced file-lock manager, per-worker worktree or merge protocol; coordinating ownership, branch changes, installs, formatting and tests is instructed behavior. Task guidance, lines 29–41, 59–78.

Workers can send a task message to the coordinator; coordinators select a particular owned worker. A worker specifying another worker is denied. Messages are recorded before delivery, with deterministic/deduplicated delivery IDs and structured task-event display metadata. Delivery takes an advisory lock, avoids waking a cancelled worker, defers when an enqueue recipient is busy, increments bounded attempts and starts a durable agent run when deliverable. Task service, lines 657–705; messages, lines 42–105, 190–233. This is a durable task mailbox, not arbitrary rooms or direct sibling collaboration. A technical dependency is usually a message/instruction. The task schema has no general ticket dependency graph. PR merge dependencies exist separately in the delivery subsystem and do not fill that project-management gap.

5. Persistence, resumption and scheduling

MDA checkpoints retain conversation/graph state; PostgreSQL retains the index, metadata, transcript events, task/delegation records, undelivered messages, artifacts, comments, skills, memories and job state. A task's worker can finish, later receive a follow-up in the same thread, and continue using its existing sandbox. Completed task messages are not an indefinite archival room: message recording/reading prunes delivered records under a retention policy, while pending messages remain owed (messages, lines 56–105). Durable project knowledge must therefore not depend solely on transient delivery queues.

Resumption may come from a human message, task result, event subscription, background command/monitor completion, one-shot wakeup or recurring/event automation. Wakeup tool, lines 30–38, 127–148, 162–185, stores new wakeups in the job queue while retaining migration cleanup for old Agent Server crons. Automation store, lines 97–209, 479–511, 1026–1135, defines schedule/GitHub/Slack/Linear trigger types and launches a fresh automation run under its configured workspace and execution identity. Cron support is concrete but does not establish a default portfolio supervisor.

The job worker, lines 15–19, 40–78 and 92–133, claims due jobs on replicas. Each worker allows up to 20 jobs in flight and renews leases every ten seconds. It cancels work for cancelled jobs and retries raised failures. Shutdown allows a lease to lapse so another worker can resume a job. These are backend job semantics, not a guarantee of exactly-once external side effects or a benchmark for agent concurrency.

6. Interruption, cancellation and steering

Human thread controls can interrupt all currently live runs, including those triggered outside the browser. The cancellation path updates transcript turns and metadata, and can dispatch previously queued human follow-ups afterward. Thus "stop" does not necessarily mean discarding all queued direction (handlers, lines 281–336). Steering and queued follow-ups are explicit mechanisms (runs, lines 1240–1355, 1406–1512), not edits to a shared prompt file.

Worker cancellation is stronger and task-specific: it marks the delegation cancelled, forgets event subscriptions, interrupts live runs, deletes owed messages and cancels wakeups. When a person stops a coordinator task, still-active workers can be silenced so pending/later results do not restart the coordinator; completed workers are spared. Worker cancellation, lines 724–774; activity settlement, lines 91–135, 157–164. A cancelled worker cannot simply be reused as if it were a paused employee; indexing requires a new worker for further work.

7. Failure, retry and recovery

Recovery is deliberately differentiated. Model retries, lines 1–2, 31–32, 35–76, 116–123, 149 onward, retry transient provider failures at the model-call boundary and can supersede partially streamed visible output. They do not replay the full tool-using run. Synchronous subagent task retry is separate, limited to two retries for configured transient failures, and returns model-fixable request errors as structured failures (task retry, lines 12–25, 65–98). That mechanism must not be misdescribed as automatic retry of every async worker assignment.

An unreachable coding sandbox ends the run and reports the condition rather than silently creating an empty replacement. Transient rejected calls and command-level errors follow different paths. The tests explicitly exercise this distinction (sandbox recovery tests, lines 16–87). Worker error, timeout and interrupted outcomes are delivered to their coordinator as well as success; if the final answer cannot be recovered, the handoff still reports that the worker finished. A run paused for a human is not reported as completed (task events, lines 18–49, 69–134).

Stalled runs with no transcript activity for 90 minutes are failed through the completion path and cancelled. The subsystem explicitly declines automatic restart because repeated frozen runs had frozen again (stalls, lines 1–7, 27–34, 75–130). Task activity separately treats starts/report handoffs older than five minutes as lost or no longer expected (activity, lines 22–25, 43–88). That is bounded operational settlement, not semantic proof all work was delivered. It is useful for preventing a CLI from serving forever, but Wingman should preserve explicit unresolved-result states for project accountability.

8. Completion, acceptance and retirement

A successful worker invocation ends with a final answer automatically handed to the coordinator, truncated to about 16,000 characters. Execution status and goal satisfaction are intentionally separate: the coordinator must assess combined results against the request/acceptance criteria. The prompt says task_status reports execution, not goal satisfaction (task guidance, lines 22, 62–64; result extraction, lines 18–49).

The normal coding delivery contract is a pushed branch and opened/updated PR; thread resolution can be tied to PR merge/close. Goal mode adds instructions to wait for passing checks and review rounds at the current head before reporting complete. Its runtime guard merely re-enters the model until a successful work-state/wait call or bounded nudge exhaustion, while report_work_state returns/sends a blocked/complete message. Delivery prompt, lines 3–39; goal prompt, lines 9–35; tool, lines 16–31; guard, lines 626–656. There is no first-class human acceptance of a product against a durable product definition of done.

Threads may be resolved/unresolved or deleted, workers cancelled and automations disabled/deleted. Thread deletion cancels the latest known run best-effort, removes runtime/index copies, then deletes the mirrored transcript (handlers, lines 392–419; store, lines 204–210). Desktop local files/worktrees have their own ownership records. No inspected path established comprehensive deletion of every cloud sandbox/resource as part of thread deletion; sandbox expiry/cleanup belongs partly to MDA. This is session/resource retirement, not archiving a standing employee and reassigning its unfinished tickets.

Coordination trace: a dashboard request delegated to a worker

This is a source-traced possible execution, not a live run or a captured production request. Consider an authenticated user asking Robin to fix a substantial login defect and the model deciding to delegate investigation.

  1. Intake and context. POST /threads calls create_dashboard_session, checks repository access, resolves the workspace and persists a UUID thread with immutable ownership/visibility. If start is true the route emits protocol run.start with the actual human message. Routes, lines 105–141; runs, lines 444–481, 280–381. This is explicit user/session/repository context, not product discovery or automatic project-team creation.
  2. Runtime dispatch. Backend run-start enrichment resolves catalog/settings and signs a token. ThreadRouter routes the new run to MDA open-swe; MDA owns the loop and checkpoint. Run client, lines 120–161; router, lines 328–345, 390–446. User, source, workspace and tool grants remain bound to this execution.
  3. Worker launch. The model calls start_async_task with assignment instructions. Runtime middleware performs authorized launch/registration and MDA creates open-swe--general-purpose. The backend checks the child's actual parent/subagent identity, reserves a task/delegation by stable tool-call ID, indexes worker ownership and shared sandbox, then exposes the child in the sidebar. Middleware launch constants, lines 120–130; registration, lines 554–590; reservation, lines 43–102. A duplicate launch registration maps back to the first worker instead of becoming a second logical assignee.
  4. Question or dependency. If investigation finds an ambiguity, worker message_task_thread selects only its coordinator. The service records a structured event and durable TaskMessage before attempting to deliver. If the coordinator is busy, enqueue delivery defers; its inbox/run-completion processing can pick up owed messages. Message service, lines 657–705; mailbox, lines 56–105, 190–233. No sibling room is involved. The coordinator can decide itself, message an affected worker, or ask the human in the current thread.
  5. Human steering. The user may send clarification while work continues. Dashboard controls can steer the current thread or enqueue another turn. The task prompt explicitly says this does not automatically redirect workers: the coordinator must message/cancel the selected children. Runs, lines 1240–1355, 1406–1512; task guidance, lines 59–64. This avoids pretending conversation steering is a global shared instruction update.
  6. Result handoff. A terminal completion webhook finds worker membership, extracts the result from that invocation's payload/history, checks human pauses and cancellation, records finished:<worker>:<run> and wakes the coordinator through the same durable message path. The UI renders a worker result/event with a thread link. Events, lines 22–49, 69–134; message UI, lines 17–46. Failure also follows this path; task execution does not silently become success.
  7. Integration and delivery. The coordinator integrates shared-checkout work, performs focused verification, pushes/opens or updates the PR, and replies to the requester. Goal mode can keep it working/waiting through CI and review. The coordinator, not worker status, judges whether the user request is complete. Task guidance, lines 62–78; delivery, lines 13–39. The trace ends at engineering delivery. A product acceptance/ticket-closing ceremony is not present.

The strongest coordination property is durable handoff with authenticated identities and idempotent event keys. The principal structural limitation is the coordinator-centered topology: shared filesystem and worker/coordinator messages, rather than independently staffed product teams collaborating in durable rooms over a common ticket system.

Major capabilities beyond Wingman's stated product

PR review and review-centered delivery

Robin has a distinct reviewer catalog with deterministic repository/diff preparation, evolving findings, in-diff location validation and reconciliation with GitHub review threads (reviewer, lines 1–15, 590 onward, 1036 onward). The review-scout kind gathers human-input context and finishes a review plan, with a separate 150-call limit and specific termination/end hooks (kind rules, lines 77–97). Human-review assignment, readiness and expedited approval are substantial subsystems under human_review and expedited_review. These extend beyond Wingman's functional TestMaster remit: engineering review is a first-class delivery product.

For Wingman this is valuable as an independent review service and PR evidence surface. Integrating it would require mapping review outcomes to a project/ticket/acceptance record and keeping automated findings distinct from product acceptance and human merge authority. Review capabilities do not themselves establish domain correctness or security coverage for the generated product.

Durable CI babysitting and merge orchestration

The opt-in babysitter persists watches per PR, periodically checks every ten minutes, tracks the current head and retry/delivery/alert keys, bounds retry counts and routes follow-up into the task coordinator (baby_sit, lines 44–53, 76–140). It is a practical post-implementation follow-through mechanism, not simply a notification of CI failure.

The merge queue supports native observation or a custom runtime. It verifies the configured repository identity, branch and mode. It applies constrained GitHub permissions and checks a configured workflow digest in custom mode. It schedules reconciliation and validates dependency cycles (controller, lines 24–73, 116–144; queue store, lines 813–818). This is delivery infrastructure Wingman does not describe explicitly. Adoption would require repository-specific policy/configuration and a clear ownership boundary. It should not be mistaken for general task dependency management.

Remote local-machine execution with one continuous cloud conversation

The CLI can continue a cloud thread against the current local directory, and Electron prepares task folders or worktrees with a diff checkpoint and persistent bridge. Local bridge registrations can reopen with the same bridge ID after sleep/app restart (CLI, lines 32–51; desktop, lines 824–854; local bridges, lines 10–18, 49–85). This allows cloud coordination and machine-resident build tools without requiring inbound access to the machine.

Wingman could reuse the protocol/ownership/liveness pattern for heterogeneous execution hosts. It would still need per-agent host placement and multi-host team state. The existing "local" path executes shell/file operations with local-machine authority. It does not supply cloud-sandbox isolation or local Codex sessions.

Learned reusable guidance and a workspace memory curator

Beyond persistent conversation, Robin has personal/workspace memories with pending/held/adopted/superseded/declined states and versioned workspace prompts. A long-lived system curator thread wakes daily only for workspaces with undecided memories, queues behind an existing run and uses deterministic workspace identity (memory store, lines 1–6, 26–39, 43–95; curator, lines 1–5, 26–29, 47–99). Curator-visible person keys are HMAC-derived, and private-thread evidence links are withheld from the public curator representation (memory models, lines 66–79, 110–127).

This is a concrete organizational-learning primitive. It could improve Wingman's reusable runbooks and instructions, but distilled guidance must be scoped to products/roles and reviewed for correctness; workspace memories are not authoritative product decisions, specifications or acceptance evidence. Memory is also an experimental preference in the UI map, so availability in a deployment should be checked rather than assumed.

Event-driven automations and fine-grained integration tools

Automations support time, GitHub, Slack and Linear triggers with configured filters and durable run history/configuration; tools can be loaded through instance/workspace/personal integrations. Catalog construction keeps large integration tool sets out of the model's initial schema list and resolves/discovers them as needed, while code mode composes allowed tools (automation schemas, lines 97–209; catalog, lines 194–240). This is useful for recurring maintenance, reports, repository triage and bounded external workflows beyond Wingman's ordinary product journey. Integration would require mapping identities, authorization and trigger outcomes into Wingman's organization rather than letting every automation become an untracked project.

Incident investigation and evidence records

Robin also contains an incident-oriented workflow with watching/needs-attention/paused/completed states, policy/channel bindings, persisted reports and responder commands. An IncidentSession checks that the incident and policy still permit the run, collects evidence from human inputs/tool results, records failed-tool evidence gaps and exposes report/search/read tools (incident runtime, lines 50–156; incident service, lines 37–58, 122–132). Evidence records use content-derived IDs, source locations, bounded observations and redaction, explicitly retaining gaps when content was bounded (evidence collector, lines 27–74). This is operational investigation beyond Wingman's product-development and functional-test remit. It could provide a later operations specialist and evidence model, but it is not project leadership or a substitute for a product tracker; production monitoring integrations, authority and escalation policy would need separate mapping.

Delivery and usage analytics

The dashboard exposes authenticated usage leaderboards and PR merge-rate analysis by model, in addition to per-thread cost and trace links (analytics routes, lines 42–87; thread summary, lines 588–594). This can help Wingman evaluate model cost and engineering outcomes across its delivery engine. Such measurements need project/agent attribution and careful interpretation: a merge-rate metric does not establish user acceptance, product quality or the effectiveness of a standing specialist.

Distinctive mechanisms and grounded innovation

These are distinctive implementation choices in this checkout, not claims of historical invention or industry uniqueness.

One graph with a signed run catalog. Robin separates graph shape from run-specific models/tools/skills/grants/sandbox/loop rules, resolving credentials once in the backend and having MDA execute the loop with named typed callbacks. Shared graph caching therefore avoids recompiling an employee-like object for every task while preserving per-run context. This is useful for scaling a credentialed control plane across replicas. Its limit is equally concrete: this checkout depends on the MDA runtime/API contract, so a Wingman implementation centered on independently controlled Codex agents needs an adapter or runtime replacement, not just prompt customization. Graph, lines 1–30, 126–175, 306–333; run client, lines 120–161.

Async subagents adopted into a durable task model. MDA launches the child. Robin verifies its actual parent and reserves one logical delegation per tool-call identity. It indexes the child as an inspectable thread. Its own mailbox returns results without duplicate parent wakeups. It combines real concurrency with auditability and recovery. The boundaries are a single coordinator, one shared sandbox, no nested worker delegation and a bounded final-report size. Registration, lines 554–590; reservation, lines 43–102; worker graph, lines 306–333.

Result delivery refers to the completed invocation, not whatever state is newest. Worker-result extraction first uses the completed payload, then invocation/run-filtered history. Deterministic finished delivery IDs, persisted messages and locked delivery prevent a completion callback from spuriously reading a later run or creating unbounded duplicate logical results. Cancelled/silenced workers and human-paused runs have distinct handling. This matters directly to trustworthy inter-agent coordination. It is not a general exactly-once guarantee for arbitrary model/tool side effects. Events, lines 22–49, 69–134; mailbox, lines 56–105, 190–233.

Goal mode distinguishes saying "done" from reporting work state, but keeps its epistemic limit visible. The middleware inspects successful tool outcomes and loops back when the agent neither reports blocked/complete nor starts a valid wait. Reply guards can also prevent Slack silence by requesting a real reply and eventually posting available assistant text on the model's behalf. This improves persistence and delivery reliability. It remains bounded nudging and a model-reported outcome, not an external verifier of CI, acceptance criteria or product quality. Loop, lines 626–710; work-state tool, lines 16–31.

Bridge queues and fail-preserving sandbox recovery. PostgreSQL request state, heartbeat expiry and liveness re-reads let cloud runs use a remote local filesystem across replicas without relying on one backend process's memory. Failure preserves the identity of the original environment instead of quietly replacing it and losing uncommitted state. This is a strong pattern for Wingman host adapters. It still needs host selection, artifact synchronization and distributed task ownership. Bridge store, lines 1–19; bridge backend, lines 1–12, 113–123; recovery tests, lines 16–87.

Practical fit for Wingman

Use directly as a bounded engineering service: send sufficiently defined repository work to Robin, let its coordinator/workers implement it, and consume PRs, reviews, plan artifacts and CI outcomes as deliverables. Its dashboard is useful for inspecting coding activity, its worker task model is real, and the durable mailbox/job/bridge patterns are practical references. This is the shortest route to useful value while keeping Wingman's product definitions and portfolio records outside Robin.

Adapt for the desired organization: add a Telegram Butler adapter with explicit mapping among human conversation, product, project leadership and task threads. Introduce stable agent/profile/team records separately from the current thread identity. Represent a BackendCoder or ProductMaster as a durable principal with explicit responsibilities and authorization, then bind its successive sessions/runs to that principal. Add project scopes/specifications/harness records and associate Robin plans/PRs with them; connect review/CI evidence to Wingman tickets and TestMaster's acceptance scenarios. Replace or extend the coordinator-star communication topology where ProductMaster, TechMaster and specialists need direct room participation.

Build missing product/organization surfaces:

  • A portfolio registry with semantic intake/new-vs-existing routing.
  • Distinct per-project product and technical leadership.
  • Proportionate domain discovery and stored question/answer cycles.
  • Technical tickets with acceptance/dependencies/assignment/progress.
  • Room1/Room2 with persisted participants/history.
  • Active cross-project supervision.
  • Executive current/recent/next/blocker summaries.
  • Employee timelines linked to the underlying conversations/tasks/workspaces. Project folders, a status sidebar and raw transcripts are useful inputs, not these finished surfaces.

Resolve execution-model fit before adopting the whole platform. Wingman is explicitly a persistent organization of real Codex agents. Robin's graph/tool/permission contract is MDA/Deep Agents, and its model configuration does not create native Codex conversation identities. Using Robin as an external engine is straightforward conceptually; replacing its runtime with Codex sessions while retaining catalogs, typed calls, task lifecycle, transcript streaming, bridge semantics and completion webhooks is a substantial integration project. The code has Python/TypeScript packages, PostgreSQL, MDA, sandbox and external identity/integration requirements. This was not deployed or costed. The checkout's README describes active breaking development and MDA dependence (README, lines 27–40). No claim of production readiness follows from the breadth of its source tree.

Material code-reuse boundary: the root README states that MIT covers Robin's own code and excludes everything under vendor/ (README, lines 89–94). The vendor notice, lines 3–8 and 18–20, says that inclusion grants no license to that code and that rights depend on its respective owner's terms. These are active runtime dependencies, not incidental unused copies: MDA package sources, lines 36–43, resolve managed-deepagents and langchain-quickjs to editable paths inside vendor/. The vendor notice also says MDA build/deploy bundles the vendored runtime/code mode. Consequently, MIT status for Robin alone does not establish permission to redistribute or reuse its complete bundled runtime. This assessment establishes that declared boundary. It does not determine the separate owners' granted rights. Adopting the engine as checked out requires resolving those dependency terms or replacing the dependencies.
