Gas Town assessment

Identity and fit verdict

  • Project: Gas Town, the gt multi-agent workspace manager.
  • Repository: https://github.com/gastownhall/gastown
  • Local checkout: research/gastown/repo.
  • Actual inspected commit: 466aa41c83ee73b1fa0eb79eb9d172fb1eca9476 (read from checkout HEAD; module/import paths still use steveyegge/gastown).
  • Assessment date: 2026-11-05.
  • Method: static source and test inspection, against WINGMAN_PURPOSE.md and the complete assessment guide. No dependencies installed, services launched, live agent work dispatched, or checkout files changed.

Verdict: Gas Town provides a strong coding-delivery and supervision foundation for Wingman. Independent coding processes use isolated Git worktrees. Durable task ownership, operational identities, messages, dependencies, and failure supervision coordinate the work. A merge engine integrates submissions through configured gates. The source also includes a web dashboard and an idea-to-PRD-to-plan workflow. Wingman's complete product organization still needs adaptation.

Its organization is a town containing repository-oriented rigs. The town-wide Mayor coordinates; Deacon/Boot and per-rig Witnesses supervise; Polecats execute assignments; Refineries integrate; persistent Crew workspaces support longer-lived human-directed work. This is materially different from Wingman's Butler/ProjectMaster/ProductMaster/TechMaster arrangement. Telegram intake, separate standing product and technical leadership, a profile-extensible organization directory, product-level acceptance and shutdown, and linked executive summaries remain to build. Remote execution is especially concrete as a gap: the machine registry accepts SSH configuration but its connection factory returns ssh connections not yet implemented (registry.go, lines 12–18, 168–182).

Architecture and execution model

The executable is a Go CLI: cmd/gt/main.go, lines 1–12, calls cmd.Execute(). Cobra commands form the control plane. The root pre-run initializes the town/session registries, records command activity and touches Polecat heartbeats (root.go, lines 25–40, 124–168). The CLI does not itself contain a coding model loop. It launches installed coding tools such as Claude Code and Codex, supplying role context, startup prompts, environment, hooks and working directories. Those tools own model interaction and their native editing/shell tools.

There are several persistence domains rather than one universal agent object:

Domain Actual representation and boundary
Town and rigs Town settings plus a mayor/rigs.json registry mapping rig names to repository/push/upstream URLs and Beads prefixes. A rig is a repository workspace/container, not a full product/business record. See types.go, lines 614–633, 648–677.
Work and relationships Beads issues, dependencies, labels, assignees, descriptions and attachment metadata, backed by Dolt; CLI paths frequently invoke bd, while the daemon also opens Beads stores. See daemon.go, lines 478–489, 2073–2118, and sling.go, lines 944–977, 1034–1075.
Agent identity Named role/address and an agent bead, carrying role, rig, hook, state, active MR and completion information. These can outlive one model conversation or tmux process. See polecat/manager.go, lines 850–859, and done.go, lines 1827–1842, 1887–1906.
Execution Local tmux session/pane running an external coding CLI, with declared GT_*, BD_ACTOR, process-name and run-ID environment. Optional ACP proxy supplies a separate JSON-RPC process path, especially for Mayor integration. See session/lifecycle.go, lines 161–222, and acp/proxy.go, lines 42–83, 94–125.
Files and code Polecats receive branches/worktrees sharing a rig repository; Crew receive separately cloned persistent workspaces. Both redirect Beads access toward shared coordination state. See polecat/manager.go, lines 733–821, and crew/manager.go, lines 208–237, 267–285.
Communication and activity Town-level message beads, channel/list/queue abstractions, a filesystem nudge queue, and .events.jsonl. Message persistence and delivery notification are separate mechanisms. See mail/router.go, lines 214–225, and nudge/queue.go, lines 1–9, 58–70.

The background daemon holds an exclusive lock, manages Dolt and process health, handles lifecycle requests, and uses periodic tickers for recovery and optional maintenance. Its heartbeat starts/restarts configured Deacon, Witness, Refinery and Mayor processes, checks non-progressing hooked work and orphan assignments, and respects emergency-stop state (daemon.go, lines 446–510, 728–785, 853–975). This deterministic infrastructure complements LLM patrol roles. It is not all prompt-based coordination. A separate mTLS proxy client/server exposes allowed host coordination commands and Git to externally isolated workers. It is a genuine network boundary, but does not implement the missing managed remote-host launcher or distributed supervisor (gt-proxy-client/main.go, lines 31–119; proxy/exec.go, lines 27–110).

The web UI is an embedded Go template/static-JavaScript dashboard. It fetches rigs, workers, tasks, convoys, queue state, mail, escalations and activity; API handlers execute validated gt, bd, gh and tmux commands. It has issue CRUD and mail threads, not merely a terminal grid (web/templates.go, lines 16–35; web/api.go, lines 111–146, 153–195). The dashboard still observes a local town and exposes a much narrower individual-workspace experience than Codex-style structured conversations/tools/artifacts.

Agent definition, creation and full lifecycle

What is an agent here?

Three concepts must stay separate. A role definition is TOML containing scope, session/workdir patterns, environment, health thresholds, nudge and prompt-template name. A runtime preset says which installed coding CLI to invoke, arguments, resume/fork abilities, instruction file, hook provider and readiness behavior. A named worker identity is the rig/name/address and persistent record associated with work and mail. A tmux session is one execution of that identity. A Beads issue is work, not an agent. A convoy leg is an assignment/prompt which becomes an independent agent execution when dispatched.

Role TOML loads built-ins then merges town and rig overrides. Importantly LoadRoleDefinition rejects unknown roles: custom prompts do not create a new first-class role taxonomy (config/roles.go, lines 18–80, 108–175). Runtime extensibility is broader: settings choose default aliases, role aliases and named Crew aliases, and presets declare capabilities for Claude, Codex and other CLIs (config/agents.go, lines 20–56, 63–175; config/types.go, lines 52–75, 680–703). Changing crew_agents[alice] chooses Alice's runtime. It does not by itself define Alice as ProductMaster with a reporting structure and UI schema.

Roles have distinct responsibilities:

  • Mayor coordinates the town.
  • Deacon and Dogs perform maintenance.
  • Each rig's Witness monitors workers.
  • Refinery owns merge processing.
  • Crew provides a persistent user-managed workspace.
  • Polecat performs task-oriented execution.

The code's role list includes dog. Some session UI enums hardcode only Mayor, Deacon, Witness, Refinery, Crew, and Polecat. New profiles therefore need changes across layers. A new prompt alone cannot provide that extensibility.

Provisioning and launch

For Polecats, AllocateAndAdd locks the pool and reconciles existing state. It allocates a name, locks that identity, and creates its directory. The pool lock releases only after allocation becomes visible. Separate workers can then perform expensive setup concurrently. See polecat/manager.go, lines 658–719.

Setup selects a fresh branch or resumed PR branch and fetches the rig repository. It creates a worktree and installs context files. It connects Beads to shared state, copies overlays, and runs setup hooks/commands. It then creates a spawning agent bead and hook. Failure removes newly created worktrees/directories and releases the name (lines 725–859).

Crew differs: creation clones the repository, optionally makes crew/<name>, establishes mailbox/shared Beads/PRIME and overlays, and saves worker timestamps/state. Start can create a missing workspace, resolves its named runtime and validates a requested resume command before killing an existing session (crew/manager.go, lines 195–343, 682–760, 803–840). This is closer to a lasting personal development seat; Polecats are dispatch capacity around independently tracked work.

The Polecat session manager resolves explicit agent overrides before role defaults. It prepares runtime settings and a startup beacon. tmux creation receives GT_ROLE, GT_RIG, worker/actor identity, branch/path/run ID, and supported process names. The manager then checks startup, readiness, and liveness. Hook-capable and promptless tools use different fallback nudges. Runtime declaration lets Witness distinguish non-Claude processes. See polecat/session_manager.go, lines 369–498 and 508–605. These are independent CLI processes.

Tools and permissions

Coding tools come primarily from the selected runtime. Gas Town supplies CLI coordination commands, Git workspace and environment, runtime hooks and optional wrapper plugins. The defaults favor autonomous host execution: Claude starts with --dangerously-skip-permissions; Codex uses --dangerously-bypass-approvals-and-sandbox (config/agents.go, lines 232–257, 283–301). Worktree separation is a change-isolation mechanism, not an OS sandbox. Role instructions forbid certain behavior, and gt sling explicitly prevents Polecat delegation, but these do not form a general capability boundary (sling.go, lines 215–226; mol-polecat-work.formula.toml, lines 223–232).

Exec-wrapper plugins can insert a sandbox command around startup, but require that wrapper/configuration to exist; their existence should not be reported as sandboxed default behavior (plugin/types.go, lines 112–147). Wingman would need to choose trust/approval policy per role and host rather than inheriting broad defaults silently.

Routing, concurrency and scheduling

gt sling accepts tasks/formulas/epics/convoys and different target forms. A rig target can allocate a Polecat. A Crew address selects an existing named worker. It guards cross-rig ownership, serializes hook writes, persists formula/arguments/dispatcher metadata, then starts a newly created session only after attachment state is durable. Direct and deferred/batch scheduler paths coexist; source explicitly notes that the single-sling path still duplicates the unified dispatch flow (sling.go, lines 443–529, 698–780, 1018–1107).

Capacity scheduling filters unresolved blockers, excludes communication artifacts, limits dispatch to available slots and batch size, and can retry or quarantine after failure counts. Persistent scheduler state tracks pause/dispatch information (scheduler/capacity/pipeline.go, lines 85–211; state.go, lines 13–40, 64–119). Concurrency is local process/worktree concurrency, not host-resource placement. Formula workflow dependencies and convoy synthesis allow more structure than a flat pool, while the LLM still performs semantic decomposition and decides what the issue should contain.

Scheduling also includes ongoing operational work. The daemon has independent tickers for Dolt health/backups, optional checkpointing and main-branch tests, maintenance, compaction and quota scans (daemon.go, lines 650–717, 752–785). Patrol formulas wait on actual activity with bounded exponential idle backoff rather than requiring a human to poll (mol-witness-patrol.formula.toml, lines 75–135). This schedules engineering operations, not a business/project lifecycle calendar.

Persistence, resume and context replacement

Work continuity is centered on durable records: shared Beads, role directives, branch contents, mail, formula attachment, dispatcher arguments and completion checkpoints. gt prime resolves identity/current assignment, injects role/work details, memory and mail, and outputs an autonomous work directive (prime.go, lines 530–549, 606–691, 743–785, 898–1030). It reconstructs the relevant state for a successor rather than guaranteeing that the old model context remains alive.

gt handoff --auto saves state without cycling; --cycle collects state, mails a handoff and respawns with the work hook intact. Normal Polecat handoff redirects toward deferred completion; other standing roles can restart in place (handoff.go, lines 30–65, 111–145). Crew can resume a native runtime session explicitly. Preset flags record that resume semantics and hook support differ by tool; Codex does not declare fork-session support (agents.go, lines 83–107, 283–301). Thus “persistent agent” means identity and work can survive a fresh process/conversation, not that every agent always resumes the same conversation.

A separate seance facility discovers predecessor sessions from events and can start a forked/resumed native conversation to ask the predecessor questions. Its value is retaining access to reasoning context that was omitted from a handoff; its boundary is runtime-specific transcript availability, not a universal organizational memory system (seance.go, lines 33–62, 85–105).

Interruption, cancellation and retirement

A running session supports stop, capture, attachment, and input injection. Stop kills the session and process descendants. Queued nudges target natural turn boundaries. They need not interrupt an active tool call. See polecat/session_manager.go, lines 631–658 and 770–831; crew/manager.go, lines 909–940; and nudge/queue.go, lines 1–9 and 58–70. Queue TTL and depth limits bound delivery. Nudges do not replace durable message beads.

Emergency stop uses a town or per-rig sentinel. It freezes agent work and prevents daemon restarts. Mayor remains available to coordinate recovery. See estop.go, lines 1–7, 56–75, and 79–122; and daemon.go, lines 853–869.

Stopping a process is distinct from canceling its assigned issue. Recovery intentionally notices dead agents with open work, so Wingman must also update durable assignment/work state when canceling a business request, or its supervisor may try to resume it. Likewise, “park/dock rig” is needed for intentional dormancy rather than merely killing support sessions, as the Mayor instructions explain (mayor.md.tmpl, lines 310–332).

Removal checks uncommitted/unpushed/stashed work and active MRs before resetting identity state and deleting resources, with force/nuclear overrides as explicit escape paths (polecat/manager.go, lines 1138–1199). The persistent agent identity is not equivalent to a permanently allocated directory or live session. Wingman's agent-conversation archive/rename/fork UX is only partially covered through underlying CLI/session operations.

Failure, retry and recovery

There are several layers of recovery, each addressing a different failure:

  • Allocation/setup failures roll back resources and release worker capacity; failed session startup rolls back attached work/artifacts (polecat/manager.go, lines 739–755; sling.go, lines 1098–1107).
  • Startup nudges are verified/retried and runtime capability mismatches detected; daemon health checks recover missing infrastructure and hooked-but-dead sessions (polecat/session_manager.go, lines 549–597; daemon.go, lines 894–975).
  • Witness distinguishes explicit stuck requests, dead processes, dead sessions, incomplete completion and pending merge state. Its restart path preserves worktree/branch rather than treating every failure as permission to delete work (witness/handlers.go, lines 1298–1315, 1616–1627, 1728–1854).
  • Failed dispatch can retry or enter quarantine. Failed gates and conflicts return typed outcomes with a rework route. Stale escalation can increase severity up to configured limits. See capacity/pipeline.go, lines 181–211; engineer.go, lines 606–627 and 653–682; and escalate_impl.go, lines 416–458.

These are recovery mechanisms, not proof that all autonomous failure modes are solved. Some operational truth is reported by agents and some is independently checked; silent warnings and provider-specific readiness paths remain integration risks.

Completion, acceptance and conflicting lifecycle descriptions

gt done is specifically a Polecat command. It validates identity/worktree and exit type (COMPLETED, ESCALATED, DEFERRED), checks/pushes work, creates or reuses a merge-request bead, records completion/checkpoint metadata, updates agent state and nudges Refinery/Witness. Push/MR failure preserves session/hook for recovery. Clean successful non-local completion retires the live session only after durable handoff (done.go, lines 92–100, 668–695, 1807–1859, 1881–1955, 2400–2443). A submitted MR can outlive its worker execution.

Refinery rechecks source-issue eligibility and unchecked acceptance criteria. It runs configured gates and performs provider PR merging or local merge/push. It verifies delivered work before clearing the corresponding state. See engineer.go, lines 504–535, 606–684, 997–1025, and 1352 onward. Review-only/no-merge paths report to the dispatcher. They can close source work without merging (done.go, lines 1536–1605).

These controls support task-level acceptance. A passing gate or closed convoy does not establish the complete product definition of done. Wingman still needs product acceptance, human delivery, and a rule that stops active testing after acceptance.

The checkout contains inconsistent lifecycle prose. The work formula says “submit + nuke yourself” (mol-polecat-work.formula.toml, lines 8–31), while the Witness formula introduction says sandbox preserved/reusable and no automatic nuke (mol-witness-patrol.formula.toml, line 1). Current types explicitly distinguish persistent identity, retired session, pending cleanup and safe idle capacity (polecat/types.go, lines 8–28); executable runDone retires successful sessions and leaves sandbox cleanup to Witness/Refinery (done.go, lines 1936–1937). This report privileges those implementation paths. The contradictions are an adoption concern because agents consume the templates as operational instructions. They should be reconciled before relying on unattended behavior.

Coordination mechanics and a concrete task trace

A code-grounded request trace is gt sling <existing-work-bead> <rig>, issued by Mayor/Crew after a request has been turned into a concrete issue. This trace is reconstructed from source, not a runtime experiment:

  1. Intake context and ownership. Mayor's injected instructions prescribe “user request → create bead → sling,” keeping global coordination separate from normal code work. The owning rig/prefix determines task location, not the issuer's current directory (mayor.md.tmpl, lines 44–63, 147–172). Natural-language routing is agent judgment above these primitives.
  2. Validate and admit. runSling rejects Polecat delegation, resolves town/target, chooses direct or deferred scheduling and prevents assigning a rig's task to the wrong repository. It reserves named/local worker capacity (sling.go, lines 215–226, 443–485, 712–780).
  3. Create identity/workspace, then attach. New target resolution provisions a Polecat. Bare task dispatch normally applies mol-polecat-work; instantiation bonds a workflow wisp to the original issue. Hook status/assignee, dispatcher arguments and molecule metadata are stored, then the session starts. This ordering prevents a newly primed worker seeing an assignment without its workflow (sling.go, lines 878–977, 1034–1107).
  4. Execute with recovered context. Startup beacon plus hooks/fallback prompt lead the external CLI to gt prime, task details and role/work instructions. The ordinary work formula is inline/root-only by default: its many checklist steps are not automatically independent agent executions or separate step-bead checkpoints. Formula.Pour explicitly controls materialized sub-wisps (formula/types.go, lines 27–36; mol-polecat-work.formula.toml, lines 19–21; prime.go, lines 898–1030).
  5. Ask and coordinate. Worker stores discoveries in issue notes and sends durable mail for unclear requirements/scope. Message beads live at town scope, including rig-agent messages; router resolves addresses, lists, queues and channels, while notifications use immediate/queued nudges (mail/router.go, lines 83–185, 214–225; mol-polecat-work.formula.toml, lines 109–118, 223–240). Persistent message payload and transient attention signal are intentionally different.
  6. Escalate a blocker. Witness/worker can create an escalation bead linked to the task. Severity selects mail/human notification actions; JSON delivery reports preserve partial failures. Ack/close and stale re-escalation are separate actions (escalate_impl.go, lines 114–218, 356–458). This is richer than printing an approval prompt, but human answer correlation back to a Telegram project discussion is absent.
  7. Submit and integrate. gt done records branch/MR/source links, completion metadata and events; successful task handoff retires its session. Refinery verifies source/criteria/gates, merges and proves delivery. Task/convoy completion can release the next dependency-ready assignment (done.go, lines 1807–1955; engineer.go, lines 606–684, 997–1025). Witness's slot-open handler can run the scheduler before notifying Mayor (witness/handlers.go, lines 752–853).
  8. Observe. The UI joins workers/hooks/issues and convoy relationships, exposes mail threads/task details, and reads operational events into a short town timeline (web/api.go, lines 119–146; web/fetcher.go, lines 1812–1875). The CLI audit --actor additionally merges readable Git/issue/town/feed provenance with timestamps and IDs (audit.go, lines 30–70, 89–144). The UI can show the current terminal preview but does not preserve a complete navigable task-to-tool-call-to-artifact chain.

The idea-to-plan path should receive separate credit. formula run creates actual workflow/convoy/leg issue records and dependency edges; parallel review legs are slung to independent Polecats, while synthesis is blocked on legs. For workflows containing interactive steps, ready work stays hooked in the current session and output tells the orchestrator to close steps as it proceeds (formula.go, lines 457–695, 739–828, 831–915). The supplied idea formula uses this to write a PRD and ask clarified questions. It is executable orchestration scaffolding plus model instructions, not a deterministic product-discovery service that independently checks whether a human's answers are sufficient. Subsequent agent actions still matter. The report does not infer that every narrated multi-round workflow has been proven end to end.

Major additional capabilities and integration consequences

Merge factory with work-delivery proofs and configurable gate phases

Gas Town has a dedicated merge-request lifecycle. Named gates can run concurrently with per-gate timeouts. A separate phase verifies the combined merge result. GitHub/Bitbucket PR providers can apply provider policies. A local merge/push path is also available. The engine rejects unchecked issue criteria and source-head drift.

Tests assert three important properties. Failed post-merge proof preserves the remote branch. Verified cleanup uses the submitted head. An advanced source branch is rejected. See engineer.go, lines 58–89, 136–155, 606–684, 997–1025, and 1147–1189; and engineer_test.go, lines 1055–1170. These are inspected assertions, not a reported test run.

This is directly valuable for integrating many worker branches. Wingman would need to map task-level criteria and real product acceptance separately, configure suitable language/project gates, and treat PR-provider behavior as a runtime dependency. The configuration may omit gates. The presence of the engine alone does not mean every project is verified.

Composable workflow and multi-perspective review library

Formulas describe parallel convoy legs plus synthesis, sequential dependency-bearing steps, expansion and aspect types. Definitions can extend parent workflows and expand individual steps; shiny-enterprise extends shiny with rule-of-five at implementation (formula/types.go, lines 13–76, 103–129; shiny-enterprise.formula.toml, lines 1–11). Executable formula run directly handles convoy/workflow types. The CLI explains alternate bd cook/molecule paths for others (formula.go, lines 217–307).

The shipped PRD/plan/design/security review patterns can bootstrap Wingman discovery and independent review. They also bring overhead: a fixed six-leg or multiple-round process may be excessive for a mockup, and semantic criteria remain instructions rather than a guarantee. Adapt formula selection to product size and preserve one stable product record across runs.

Operational maintenance as first-class work

Plugins have gate schedules (cron/cooldown/condition/event/manual), execution modes (agent-interpreted Markdown, script, startup wrapper), timeout/severity and tracking metadata. The daemon can dispatch maintenance Dogs and run optional checkpoint, compaction, backup and main-branch-test cycles (plugin/types.go, lines 1–8, 16–51, 65–147; daemon.go, lines 650–717, 948–960). This extends the organization into self-maintenance and continuous infrastructure work, beyond Wingman's outlined product-team loop.

The value is explicit operational ownership instead of ad hoc repair prompts. The cost is a persistent Dolt/tmux/process estate, data retention, task garbage collection and host configuration. Wingman should distinguish infrastructure supervision from agents actually developing the human's products.

Credential/quota rotation and heterogeneous runtime support

Quota planning scans hard/near-limited sessions, reads persisted account quota state, clears expired states, validates alternate tokens, and groups swaps by shared configuration directory. The daemon can schedule quota scans (quota/rotate.go, lines 10–63, 64–140; daemon.go, lines 708–717). The runtime registry centralizes resume flags, hook support, instruction filenames and readiness differences across coding tools (config/agents.go, lines 63–175).

This can improve long-running capacity and allow different models per role. It is not a generic Codex budget/goal controller, and credential/keychain assumptions are provider/platform-sensitive. A Codex-only Wingman could use the adapter/capability design while omitting unrelated account rotation.

Wasteland work federation and reputation

Wasteland implements a DoltHub commons using fork/clone/register/push/upstream primitives, with CLI workflows for posted work and a reputation/trust subsystem. The Spider component queries patterns such as reciprocal/collusive stamps, rubber stamping, confidence inflation and self-loops (wasteland/wasteland.go, lines 1–6, 97–169, 315–375; spider.go, lines 105–200, 249–301).

This is additional cross-organization work/reputation machinery, not required by Wingman's personal organization. It could support outside contributions but adds identity, trust and synchronization policy. It must not be mistaken for distributing one Wingman project's live agents across Mac and Linux: the missing SSH connection implementation remains decisive.

Authenticated coordination/Git bridge for isolated workers

The proxy client can stand in for gt/bd inside an externally provisioned worker environment, forwarding arguments over mTLS and returning the actual host-command exit code. Server command/subcommand allowlists, binary-path resolution, per-client rate limits, global subprocess concurrency and deadlines restrict the exposed command surface. The Git smart-HTTP bridge serves host bare repositories and checks allowed worker push refs (gt-proxy-client/main.go, lines 31–119; proxy/server.go, lines 24–60, 105–138; proxy/exec.go, lines 27–110; proxy/git.go, lines 1–38, 75–118).

This could let Wingman execute coding tools in an isolated environment while retaining shared tasks/mail/Git without mounting the host coordination filesystem or distributing its direct provider credentials. It is more than a design document and merits F17 primitive credit. It still requires certificate provisioning, a reachable service, worker environment creation and lifecycle orchestration. It does not fill the SSH factory or manage Endeavour placement. Normal CLI sessions remain broad host processes unless a wrapper/deployment supplies isolation. Proxy and regular Polecat branch conventions also deserve an explicit integration test before deployment.

Run-correlated operational telemetry

Optional OpenTelemetry export adds run IDs to agent-session and subprocess events. It derives a machine/town instance ID. Counters cover lifecycle changes, prompts, agent events, dispatch, messages, completion, and daemon restarts. Optional conversation logging streams native JSONL output. See telemetry/telemetry.go, lines 1–14 and 88–100; telemetry/recorder.go, lines 24–58 and 79–108; and polecat/session_manager.go, lines 607–617.

This supports diagnosing a town and measuring the coordination machinery beyond the dashboard. It needs a configured collector/storage and retention policy, is best-effort, and has provider-specific conversation coverage. A correlated log stream remains different from Wingman's readable executive outcomes and structured per-agent workspace; Wingman could consume it as evidence for those views.

Emergency stop and predecessor interrogation

Town/per-rig emergency stops preserve an explicit operator intent that the recovery daemon must obey, instead of letting automatic restarts undo a human stop. The predecessor seance facility goes beyond flat transcript browsing by asking a resumed/forked old session to explain past work (estop.go, lines 1–7, 56–122; seance.go, lines 33–62). Both are worthwhile operational concepts. E-stop still needs cross-host propagation for Wingman, while seance needs supported native transcripts and cannot substitute for durable scopes/specifications.

Distinctive mechanisms and grounded innovation assessment

Durable work hooks separate “what must happen” from the disposable model session. Sling stores task ownership and workflow attachment before starting the CLI; prime reconstructs obligations; completion metadata/checkpoints let supervisors distinguish a worker that died from one that submitted. This enables replaceable conversations without losing the assignment. Its limit is that the agent must persist semantic discoveries; unsaved reasoning still disappears, and default inline formula checklist steps are not individually checkpointed. Evidence: sling.go, lines 1034–1107; prime.go, lines 898–1030; done.go, lines 1855–1913, 2439–2443.

An engineering organization has multiple recovery layers instead of one immortal coordinator. Deterministic daemon recovery, Boot/Deacon judgment, per-rig Witness scans and separate Refinery integration divide failure ownership. The system cross-checks declared assignment/completion state against process/worktree/Git reality, and distinguishes explicit stuck work from dead execution. This is useful for Wingman's proactive ProjectMaster supervision, but role prompt contradictions and partial self-reporting mean the hierarchy needs coherent policy and verification. Evidence: daemon.go, lines 894–975; witness/handlers.go, lines 1298–1315, 1616–1627, 1728–1854.

Communication payload and attention delivery are split. Mail is durable task-like state; nudge queues carry bounded/expiring attention signals for the next safe turn, avoiding destructive injection during tool use. Provider capability metadata handles tools with different turn-boundary hooks. This is a useful model for Butler escalation and direct worker collaboration; Wingman would still need message/project/question correlation and a stable room application. Evidence: mail/router.go, lines 214–225; nudge/queue.go, lines 1–9, 35–70; config/agents.go, lines 159–175.

Verification can be moved toward workers while retaining merge-time invalidation. ProcessMRInfo accepts a pre-verified base SHA; if the target still matches it can skip gates, otherwise reruns them. Submitted-head checks and post-merge proof protect the transition from worker completion to landed work. This reduces centralized integration cost, but the fast path relies on truthful/relevant recorded verification. It is not independent product QA. Both pre-merge and post-squash gate execution are skipped by the matching-base fast path. Evidence: engineer.go, lines 606–611, 673–677, 1329–1349; engineer_test.go, lines 1055–1170.

One issue/dependency substrate can represent implementation, review synthesis, mail, escalation and operational lifecycle. Formula dispatch creates concrete legs/steps and tracking edges, and capacity scheduling explicitly filters communication artifacts out of executable work. This makes one shared record inspectable to agents and dashboard, but also creates type/retention/routing complexity. The defensive messaging filter is evidence of the boundary that must be maintained. Evidence: formula.go, lines 457–695, 739–828; capacity/pipeline.go, lines 126–178.

These are distinctive implementation choices within this checkout. No claim of historical novelty or industry-wide uniqueness is made. The strongest transferable ideas are recoverable work ownership, separation of identity/session/worktree/task, and integration proofs. The least appropriate extrapolation would be assuming that the named town roles already implement Wingman's complete product organization.

Practical fit and remaining work

Useful mechanisms for direct use or thin integration include:

  • Local Codex workers, isolation, and named Crew seats.
  • Beads tasks, dependencies, assignments, and task/convoy scheduling.
  • Durable mail, nudges, monitoring, recovery, and role directives.
  • Task-level merge gates and engineering dashboard.

Keep task submission separate from verified integration when several specialists edit one repository.

Adapt substantially: model Wingman products independently from rigs, because one product can have several repositories and one repository can contain several products. Map ProductMaster and TechMaster into independently named persistent agents with a clear interface rather than renaming Witness/Refinery, whose existing operational responsibilities are useful. Choose bounded discovery formulas for mockups and richer workflows for substantial products. Preserve DIRECTIVES/SCOPES/SPECS/HARNESS as durable product artifacts and map tasks/acceptance back to those records. Extend the dashboard around actual role/profile metadata and stable task/session/conversation identifiers.

Build:

  • Telegram Butler with correlated multi-project questions/answers and human decisions. An organization-wide product registry/intake router.
  • Genuine product and technical leadership relationships. A room-first chat application.
  • Executive per-agent current/recent/next summaries and outcome timelines with links. A structured per-agent coding workspace for tools, edits, tests, approvals, artifacts and usage.
  • Explicit product acceptance/delivery/idle behavior.
  • Real Mac/Endeavour execution transport, host placement and shared coordination. The SSH stub means the last item is implementation work, not configuration work.

Adoption should first settle lifecycle semantics and privilege policy. The code and consumed prompts currently mix self-cleaning, preserved sandbox and clean-session-retirement descriptions. A Wingman integration should make exactly one owner responsible for each transition (worker submission, session retirement, MR acceptance, sandbox/branch cleanup and slot reuse), then verify those transitions against the intended Codex runtime. Default broad permission flags and local credential assumptions should become deliberate role/host policy. These are material engineering integration issues, not reasons to discount the working coordination machinery.
