# Symphony assessment against Wingman

Assessment date: 2026-11-05. Product: OpenAI Symphony, with the Elixir reference implementation (`symphony_elixir` version 0.0.3). Repository: https://github.com/openai/symphony . Local checkout: `researchs/symphony/repo`. Actual checked-out commit: `be10a1b79df723d6d7612b5651c8522704dafb2e`. License: Apache-2.0 ([LICENSE](../repo/LICENSE)). This is a source assessment of that revision, not a claim about a deployed service or later upstream behavior.

**Fit verdict: a strong candidate for Wingman's bounded coding-delivery execution layer, but a poor substitute for Wingman's organization.** Symphony converts eligible tracker issues into independent Codex runs with isolated workspaces, concurrency limits, retry/reconciliation, operational visibility and genuine SSH execution. It does not implement Butler, product discovery, project leadership, a durable directory of role-bearing agents, agent rooms, or the connected executive/project/session experience. Its agents are issue attempts and Codex threads, not continuing organizational identities. The distinction is fundamental: putting a ProductMaster paragraph in its workflow would create instructions for an issue worker, not the persistent ProductMaster entity and collaboration behavior Wingman requires.

The checked-out implementation is broader than the introductory Linear-focused description: it includes Linear, GitHub Issues, Jira, Asana and GitLab adapters, a Phoenix LiveView dashboard, host-side tracker tools and SSH worker placement. These are implemented capabilities, while much of PR validation, human review and landing remains a workflow/skill contract executed by Codex. No dependencies were installed, services started, credentials exercised or runtime tests run for this assessment.

## Architecture and execution model

The executable entry is [CLI](../repo/elixir/lib/symphony_elixir/cli.ex), lines 38–76: parse one workflow path and options, require the unattended-operation acknowledgement, select the workflow and start the OTP application. [Application](../repo/elixir/lib/symphony_elixir.ex), lines 35–50, starts Phoenix PubSub, `WorkflowStore`, `AgentRuntimeSupervisor`, HTTP service and terminal status dashboard. [AgentRuntimeSupervisor](../repo/elixir/lib/symphony_elixir/agent_runtime_supervisor.ex), lines 15–32, groups the task supervisor and orchestrator under `:one_for_all`. Restarting the scheduler therefore restarts its owned workers instead of leaving an old task fleet beside a new scheduler.

The scheduler is one `GenServer`, not an LLM manager. Its [State](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 24–44, holds `running`, `claimed`, `completed`, `blocked`, retry timers, token totals and rate limits in memory. Initialization loads config, cleans terminal workspaces and immediately schedules a poll (lines 55–79). Each [poll](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 118–125 and 256–332, reconciles existing work, fetches eligible issues, dispatches into capacity and schedules the next poll. Tracker reads are behind [Tracker](../repo/elixir/lib/symphony_elixir/tracker.ex), lines 13–40. Ecto is used for embedded configuration schemas, not a project/agent database; see [Schema](../repo/elixir/lib/symphony_elixir/config/schema.ex), lines 292–318, and [dependencies](../repo/elixir/mix.exs), lines 70–85.

The actual execution path is `Tracker.Issue → monitored Task → AgentRunner → Workspace → Codex app-server`. [Dispatch](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 953–991, starts an independent supervised task, monitors it and stores issue/host/session metadata. [AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 38–51 and 88–139, prepares the workspace, runs hooks, opens one Codex session, runs sequential turns while the issue remains active and then closes the session. [AppServer](../repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 192–237 and 275–340, launches the configured process locally or over SSH and speaks JSON-RPC over stdio, including `initialize`, `thread/start` and then `turn/start` (lines 343–361). It does not embed a model engine or implement its own shell/file tool suite.

Persistence is deliberately external and filesystem based: the tracker contains task state and comments. The workspace retains files. The versioned workflow carries instructions; rotating application logs capture operational history. The scheduler does not restore its in-memory claims, blocked map, retry timers or usage counters after a process restart. It repolls tracker state and reuses existing workspace directories. Codex itself may retain its native session artifacts, but Symphony does not implement thread lookup/resume across attempts: `start_session` always reaches `thread/start`. This is useful recovery of work, not durable conversational identity.

## Agent definition and full lifecycle

### Definition, creation and identity

There is one workflow contract per runtime: YAML front matter chooses tracker, workspace, polling, worker hosts, concurrency, hooks and Codex policies; Markdown becomes the agent prompt. [Schema](../repo/elixir/lib/symphony_elixir/config/schema.ex), lines 89–249, validates the execution settings. [PromptBuilder](../repo/elixir/lib/symphony_elixir/prompt_builder.ex), lines 8–25 and 34–41, uses strict Solid rendering, so undefined variables/filters fail rather than quietly producing incomplete instructions. A role can be described in this text, but no separate role-bearing runtime entity is created.

The external work item is the durable scheduling identity. [Issue](../repo/elixir/lib/symphony_elixir/tracker/issue.ex), lines 5–27, distinguishes stable dispatch `id`, provider `native_ref`, human-readable `identifier`, description, state, blockers and labels. A running entry adds an Elixir PID/monitor, worker host, workspace, session ID and usage. These identify a particular attempt. There is no lifetime agent ID with a name, supervisor, project membership and personal history. Task assignment to a tracker assignee is eligibility routing, not assignment to a named organizational specialist.

Before launching, the scheduler sorts by priority then creation time then identifier ([Orchestrator](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 781–814). It checks nonempty required fields, provider dispatchability, active/terminal states, required labels, claims, blocked/running maps, global capacity, per-state capacity and host capacity (lines 816–874). It refreshes the issue immediately before dispatch (lines 907–938 and 1006–1021), avoiding execution based solely on a stale poll. Claims are local to this scheduler process. There is no distributed lease that prevents two separately launched Symphony services with overlapping scopes from both selecting an issue.

### Workspace, execution, tools and permissions

[Workspace](../repo/elixir/lib/symphony_elixir/workspace.ex), lines 15–31 and 40–90, derives/reuses a directory and invokes `after_create` only for a new directory. Without a bootstrap hook it is merely an empty directory, not automatically a Git checkout. The included [workflow](../repo/elixir/WORKFLOW.md), lines 20–29, explicitly supplies clone/setup and cleanup commands. Workspace keys sanitize the identifier and add a hash when sanitization changed it (Workspace lines 259–285), preventing distinct unsafe identifiers from collapsing to the same directory key.

Local paths are canonicalized and checked against the workspace root before running Codex ([AppServer](../repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 150–175; [Workspace](../repo/elixir/lib/symphony_elixir/workspace.ex), lines 461–510). Remote validation is less comprehensive: nonempty/newline/NUL checks and remote shell preparation are present, but local canonical containment guarantees do not automatically apply to the remote filesystem (Workspace lines 465–477; AppServer lines 178–188). The remote host and configured hooks are trusted execution infrastructure, not a hostile-tenant sandbox.

The worker runs `before_run`, then one app-server session, then `after_run` in a `try/after` ([AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 38–51). Bootstrap/before-run failures abort the attempt; after-run failures are ignored with logging ([Workspace](../repo/elixir/lib/symphony_elixir/workspace.ex), lines 219–246 and 394–447). Hooks have timeouts. This normal-path cleanup structure should not be read as proof that every remote descendant is killed or every hook runs under arbitrary forced process death.

Codex provides the actual coding tools. Symphony adds provider-native dynamic tools: session startup captures the adapter, settings, tool schemas and declared secret environment names ([Tracker](../repo/elixir/lib/symphony_elixir/tracker.ex), lines 43–73). The app-server advertises those schemas in `thread/start`, receives `item/tool/call`, runs the tool in the central service and sends a structured result ([AppServer](../repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 314–328 and 587–619). Remote Codex can therefore update the tracker without receiving its token in the child environment. The launcher removes declared token variables (lines 221–255). This is credential mediation, not authorization to a single assigned issue: raw [Linear GraphQL](../repo/elixir/lib/symphony_elixir/linear/agent_tool.ex), lines 8–25 and 56–66, passes queries/mutations through with the credential's broader rights.

Defaults and the included workflow differ. [Schema](../repo/elixir/lib/symphony_elixir/config/schema.ex), lines 181–197 and 570–578, defaults to approval rejection settings, `workspace-write` and network-disabled workspace policy. The sample [WORKFLOW](../repo/elixir/WORKFLOW.md), lines 33–39, explicitly chooses `approval_policy: never` and network access. `auto_approve_requests` is true only for the `never` setting (AppServer lines 47–57); recognized command/file approval RPCs then get automatic responses. Other policies can surface approval-required blocking. The CLI acknowledgement is an operational startup requirement, not a Wingman human decision workflow.

### Routing, concurrency and multi-host placement

With no SSH hosts, workers execute locally. With hosts configured, [selection](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 1281–1340, filters full hosts, retains a preferred retry host if available and otherwise chooses the least loaded host, breaking ties by configuration order. Global and per-state limits remain in force. The selected task lifetime never silently hops machines ([AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 21–35); failures return to the orchestrator. SSH prepares directories/hooks and streams app-server RPC, while central OTP messages retain issue association. This is actual distributed execution, not merely a command string mentioning a host.

Host affinity is an attempt/retry preference, not a durable project location record. If another host is selected, there is no built-in synchronization of unpushed workspace files. No SSH host provisioning, capacity discovery from real machine load, remote secret installation or shared cross-host filesystem is supplied. For Mac/Endeavour use, the remote Bash/Codex/toolchain/auth and repository access must be provisioned independently, and the product/project placement layer still needs a stable mapping.

### Continuation, scheduling, interruption and recovery

Inside one attempt, a successful turn triggers a fresh issue read. If it is still active and routable and the turn limit has not been reached, the runner sends continuation guidance into the same thread; otherwise it returns ([AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 101–186). Default `max_turns` is 20. This limits one runner lifetime, not total project effort or token spend: a normal exit schedules a one-second active-state continuation check ([Orchestrator](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 208–223), which can start another attempt and a new thread. Existing files and the tracker workpad carry continuity into that attempt.

Poll timers, retry timers and workflow reload are the native scheduling mechanisms; no cron/persona wake schedule or organizational supervision agent exists. Abnormal exits retry with 10-second exponential backoff capped by configured `max_retry_backoff_ms` (Orchestrator lines 242–253 and 1232–1242). Retry callbacks refetch/revalidate eligibility and wait again if capacity is unavailable (lines 1093–1129 and 1181–1220). Timer tokens prevent an obsolete callback consuming a newer retry record (lines 1034–1089). The retry state is memory-only; restart reconstitutes eligibility from the tracker instead of restoring its previous retry clock.

The scheduler notices non-active states, terminal states, routing removal or issues becoming invisible, then terminates the task. Terminal states request workspace cleanup; ordinary suspension or invisibility preserves it ([Orchestrator](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 421–443, 478–496 and 554–578). There is no user-facing `turn/interrupt`, steering or queued input API. [AppServer](../repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 423–433, recognizes cancellation notifications as errors; session shutdown closes the port (lines 145–148). End-to-end remote descendant termination under network loss was not exercised.

Stall detection uses elapsed time since the last Codex activity or startup, rather than tests of actual useful progress ([Orchestrator](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 581–655). A noisy but unproductive model can keep emitting activity. Normal stalls are stopped/retried; approval/input-required cases become claimed blocked entries so the service does not repeatedly restart a question that needs a human (lines 659–778). The dashboard shows that block, but cannot answer it. While an issue stays active and routable, blocked reconciliation refreshes metadata and retains the block (lines 456–473); editing a comment alone does not implement resume. An observed move out of active/routed state releases the block, after which re-entry can make it dispatchable again. A service restart also loses the memory-only block, with the corresponding risk of redispatching unresolved input.

The `:one_for_all` runtime ownership boundary is useful restart recovery, but not high-availability coordination. It prevents owned OTP workers remaining under a dead scheduler in the same service. It does not implement cross-service leader election, durable distributed claims or a proven remote process fencing protocol.

### Completion, acceptance, retirement and cleanup

Normal process completion is not accepted product delivery. The scheduler's `completed` set records an attempt outcome and still schedules a continuation check. It does not inspect a merged PR, CI evidence or a product definition of done. The sample workflow makes issue states the delivery contract: implement and validate, enter Human Review, let a human move to Merging, follow the landing skill and then mark Done ([WORKFLOW](../repo/elixir/WORKFLOW.md), lines 199–251). Human Review is outside the sample active-state list (lines 7–17), so the native scheduler stops/does not dispatch that issue while waiting. The prompt's instruction to poll review should not be confused with a guaranteed long-lived review-monitor agent.

When terminal, the service removes the recorded workspace, or derives a workspace location; startup also removes terminal workspaces (Orchestrator lines 1113–1174). [Workspace](../repo/elixir/lib/symphony_elixir/workspace.ex), lines 93–215, supports local/remote removal and across-host cleanup. `before_remove` is best-effort; local removal then deletes files, and remote removal executes `rm -rf`. The sample hook calls [workspace.before_remove](../repo/elixir/lib/mix/tasks/workspace.before_remove.ex), lines 35–50 and 88–109, which can close open branch PRs when tracker work is retired. That is an external side effect requiring deliberate adaptation to a new repository. There is no archive/retirement record for an enduring agent because no such entity is modeled; durable evidence must live in Git, the tracker or independently retained logs/artifacts before cleanup.

## Coordination mechanics and a concrete request trace

Consider a Linear `Todo` implementation ticket with the required labels, an eligible assignee and no unfinished blocker. The following is a source-derived execution trace through real handlers, not a test run or an invented production transcript.

1. [Linear Client](../repo/elixir/lib/symphony_elixir/linear/client.ex), lines 14–52, 108–134 and 224–247, polls the configured project with pagination. Lines 465–510 normalize issue metadata and set `dispatchable`; dependency gating applies to `Todo` issues with non-terminal inverse `blocks` relations. This is provider-specific dependency interpretation, not a general scheduler-owned DAG.
2. [Orchestrator](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 256–265, 781–874 and 907–938, reconciles current work, sorts candidates, checks labels/claims/capacity and refetches the selected issue. Lines 953–991 launch the task and associate telemetry with the issue ID.
3. [AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 38–51 and 88–109, creates/reuses its workspace, runs the pre-hook and starts Codex with the rendered workflow. The included prompt tells Codex to move Todo to In Progress and create/reuse the single `## Codex Workpad` comment ([WORKFLOW](../repo/elixir/WORKFLOW.md), lines 118–169). These mutations are actions of the prompted coding agent, not actions hidden in the dispatcher.
4. A `linear_graphql` mutation arrives as `item/tool/call`. [AppServer](../repo/elixir/lib/symphony_elixir/codex/app_server.ex), lines 587–619, executes it through the session-bound tracker tool and returns its result. [Linear AgentTool](../repo/elixir/lib/symphony_elixir/linear/agent_tool.ex), lines 56–66, performs the authenticated API call. The workpad is shared external state. There is no message to a ProductMaster or FrontendCoder.
5. Turn and tool activity flows back through the runner's `{:codex_worker_update, issue_id, message}` ([AgentRunner](../repo/elixir/lib/symphony_elixir/agent_runner.ex), lines 58–68), into [orchestrator updates](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 167–184, then dashboard notification. [LiveView](../repo/elixir/lib/symphony_elixir_web/live/dashboard_live.ex), lines 12–37, subscribes and refreshes the snapshot. This event channel is observability, not agent-to-agent discussion.
6. Codex implements/tests/publishes a PR and records evidence according to the prompt. When it sets Human Review, the next runner refresh or scheduler reconciliation stops active execution. The human reviews through the tracker/GitHub, then changes the issue to Merging. A later poll dispatches a fresh attempt using the existing directory/workpad. Codex follows the bundled landing procedure and sets Done. The scheduler then cleans up. The runtime itself does not verify that setting Merging was performed by a human or that acceptance criteria were actually satisfied.

The coordination model is consequently a central deterministic control loop plus a tracker state machine. State transitions are the dispatch/stop signal; comments/PRs are the work record; blockers/labels/assignee narrow eligibility; process messages carry telemetry. There are no Room1/Room2 conversations or management deliberations. Human decisions are mediated through external tracker/review workflow, and the service has no separate durable question/answer correlation model. This makes integration with an existing engineering tracker comparatively small, but implementing Wingman's collaborative organization requires new entities and protocols above this layer.

## Substantial capabilities beyond Wingman's described product

**Multiple provider adapters and provider-native tool brokering.** [Tracker](../repo/elixir/lib/symphony_elixir/tracker.ex), lines 13–31 and 43–73, supplies a read interface and per-session tool binding. [GitHub Adapter](../repo/elixir/lib/symphony_elixir/github/adapter.ex), lines 14–45, implements explicit state validation, reads and tool exposure; [Asana tools](../repo/elixir/lib/symphony_elixir/asana/agent_tool.ex), lines 8–65, and [GitLab tools](../repo/elixir/lib/symphony_elixir/gitlab/agent_tool.ex), lines 8–65, expose actual REST request paths. [Adapter profiles](../repo/elixir/README.md), lines 209–294, document differing provider scopes/state semantics. This could connect Wingman to established engineering systems without replacing their trackers. It is one selected adapter per runtime, not a federation of all five, and the Linear-specific sample workflow must be rewritten for other providers. Raw mutation tools retain credential-level access, so Wingman must add assignment/project authorization if its agents are to have narrower rights.

**Hot-reloadable workflow with last-known-good protection.** [WorkflowStore](../repo/elixir/lib/symphony_elixir/workflow_store.ex), lines 65–120 and 122–179, checks changes every second, validates the new workflow/settings and preserves the prior working version on error. The stamp includes content hash as well as mtime/size. This allows operational prompt/routing/capacity tuning without requiring the service to stop. Settings are not one atomic immutable organization revision for every subsystem: future polls use current config while tools in an existing app-server session remain bound to their startup adapter/auth. Wingman would need explicit migration/ownership rules for changing active project mappings or tracker identity.

**An explicit PR landing toolkit.** The [land skill](../repo/.codex/skills/land/SKILL.md), lines 26–56 and 101–149, directs conflict resolution, review replies, CI repair and squash merging. Its [async watcher](../repo/.codex/skills/land/land_watch.py), lines 39–62, 82–161 and 184–218, performs real `gh` polling with pagination, rate-limit backoff and check-run deduplication. These are reusable delivery mechanisms beyond a generic “deliver the product” requirement. They remain GitHub/repository-specific helpers invoked by the agent. The core scheduler has no independent release gate. Skills include assumptions about review bots, branch handling and repository checks that should be adapted before reuse.

**Operational usage and recovery telemetry.** [Presenter](../repo/elixir/lib/symphony_elixir_web/presenter.ex), lines 8–26 and 102–151, exposes running/retry/blocked state, usage and rate-limit snapshots for monitoring; [token integration](../repo/elixir/lib/symphony_elixir/orchestrator.ex), lines 1688–1740, computes deltas from reported cumulative/turn usage. [LogFile](../repo/elixir/lib/symphony_elixir/log_file.ex), lines 9–11 and 68–77, implements bounded rotating logs. These could form Wingman's infrastructure health and consumption feed. They are not durable accounting across restarts, spend enforcement or semantic executive reporting; rate-limit observation also does not by itself constitute a cross-project budget allocator.

## Distinctive mechanisms and grounded innovation

No historical novelty or industry-wide uniqueness is claimed. The notable design contribution is a small control plane in which the external issue is the scheduling authority and the repository carries the execution contract. Revalidation immediately before spawn, eligibility reconciliation while running and filesystem reuse work together to turn a tracker into an unattended dispatch loop with relatively little persistent service state. The mechanism makes a good boundary between Wingman's future planners and its coding workers: planners can create bounded eligible work while a deterministic engine handles its execution. Its limit is that issue status is not proof of quality, and reconstructing eligibility is not reconstructing every prior conversation or approval.

The ownership coupling in [AgentRuntimeSupervisor](../repo/elixir/lib/symphony_elixir/agent_runtime_supervisor.ex), lines 21–32, is more meaningful than simply calling the system “fault tolerant.” It prevents a restarted scheduler from coexisting with tasks owned by its previous instance. The corresponding [restart test](../repo/elixir/test/symphony_elixir/core_test.exs), lines 351–472, kills the orchestrator and asserts a new scheduler/task supervisor, old worker death and at most one replacement child. This is a concrete local process-ownership invariant. It is not evidence of cross-machine fencing or safe overlapping independent installations.

The session-bound dynamic-tool design is another useful mechanism. Live reload can change the selected adapter, but tools already advertised to a thread still execute with that thread's captured adapter/settings ([Tracker](../repo/elixir/lib/symphony_elixir/tracker.ex), lines 43–73). [The test](../repo/elixir/test/symphony_elixir/dynamic_tool_test.exs), lines 46–75, binds Linear, reloads to memory, then asserts the old Linear binding retains its original settings. This prevents schema/credential drift inside a running session and supports a central broker for remote workers. It does not restrict the credential to the assigned ticket, and it does not freeze every scheduler setting for that thread.

Finally, the explicit distinction between failure and human-input blocking is useful unattended-operation design. Generic failures get backoff. An approval/input signal retains a block and claim rather than becoming an automatic retry storm (Orchestrator lines 208–253 and 659–778). That makes unresolved operator needs visible. Its limit is equally concrete: there is no answer/resume protocol, and the block is not persisted through restart. Wingman could reuse the classification while supplying durable human decision records and Butler routing.

## Practical adoption for Wingman

**Usable directly as a bounded delivery backend:**

- the OTP poll/dispatch/reconcile loop.
- workspace isolation and hooks.
- same-thread multi-turn execution.
- label/assignee/state eligibility.
- local and SSH app-server launch.
- retry/stall/input classification.
- tracker adapters.
- operational snapshots.

Wingman's TechMaster could emit implementation tickets with explicit acceptance criteria and let this layer run them. The useful starting integration boundary is a ticket/run API and event bridge, rather than pretending each dispatched worker already represents a standing employee.

**Needs adaptation:**

- map persistent Wingman agent identities/roles and project IDs to ephemeral Symphony attempts.
- establish stable Mac/Endeavour project placement and host provisioning.
- preserve artifact/workpad evidence before terminal cleanup.
- namespace workspaces/claims across projects.
- reconcile specialist permissions and tracker credential scope.
- make validation and approval decisions explicit records.
- rewrite the sample workflow's clone, model/tool assumptions, tracker states, landing and PR-close hook for the target repositories.

The single global workflow/adapter and singleton named runtime are constraints for a portfolio service: multiple deployments need isolation and a coordinating authority, or the implementation needs a deliberate multi-project model.

Still to build:

- Telegram/Butler intake and question routing.
- Project registry and new/existing matching.
- Independent ProductMaster/TechMaster leadership.
- Proportionate domain discovery and iterative human clarification.
- Managed product scopes/specs/definition of done.
- Durable role/profile/team directory.
- Agent-to-agent chat/rooms and escalation.
- Cross-project semantic supervision.
- Stable agent/conversation continuity.
- Full project/executive dashboards and per-agent timelines.
- Coding-session drill-down with files, artifacts and commands.
- Steering, approvals, fork/archive/compact controls.
- Independent integrated verification and product acceptance. These are the central Wingman experience, not minor UI additions to the existing scheduler.

For a personal organization, the best fit is to retain Wingman's organizational model as the source of identity, conversation and product decisions, and use Symphony's mechanics beneath it where they reduce execution risk. Building the complete Wingman experience entirely inside its current issue-worker schema would require adding most of the product's distinguishing concepts.
