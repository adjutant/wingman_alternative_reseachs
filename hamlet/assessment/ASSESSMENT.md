# Hamlet assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/voxell-tech/hamlet

Local checkout: `researchs/hamlet/repo`. Inspected commit: `c944a2ff4081bf54cf3049e613c0833a7910e180`.

Baseline: [Wingman purpose](../../WINGMAN_PURPOSE.md). This is a fresh static assessment of the checked-out implementation. No dependencies were installed, services launched, model calls made or tests run. Source links below are relative to this report; line numbers refer to this commit.

## Fit verdict

Hamlet is a substantial **persistent agent society with a human oversight application**. Its agents really have separate durable identities, private memory and conversations, execute coding tools, exchange messages through an authorized graph, and survive beyond the window that displays them. It is useful reference material for Wingman's standing organization, particularly identity, communication authorization, human questions, cancellation, recoverable organizational changes and execution boundaries.

It does not supply Wingman's software-development organization as a product. The implemented model runtime is pi-durable, with a general personal-assistant charter. There is no Codex runtime adapter, Telegram Butler, project intake reconciliation, product/technical leadership pair, shared ticket system, discovery-to-specification workflow or integrated acceptance/delivery process. A hamlet can be used as a project team, and purpose strings can describe specialists, but those conventions do not create the missing application layer.

Its distributed execution deserves qualified credit: a central server can execute tools and keep agent houses on a real remote Linux worker. However, the server selects one local or remote workspace for the whole realm. It does not place different agents simultaneously on different hosts. Remote selection also disables founding/removing/restoring hamlets and some other lifecycle operations. Treat it as remote execution infrastructure, not Wingman's complete multi-host organization.

## Architecture and execution model

```text
Native Bevy window or terminal CLI
  -> authenticated WebSocket client protocol
Rust hamlet_server
  -> realm.sqlite: identities, records, approvals, bindings, inputs,
     correspondence, accounting and operation markers
  -> JSON-lines runtime protocol over a child process's stdin/stdout
Node pi adapter + pi-durable SQLite store
  -> independent conversations, model calls, compaction and recovery
  -> tool requests return to the Rust server's permission gate
Rust tool execution
  -> local OS sandbox OR one configured remote Linux workspace worker
```

[requests.rs](../repo/crates/hamlet_server/src/requests.rs), lines 48–129, parses/schema-checks client requests and requires the server connection token in the initial hello. Lines 162–206 route chat operations to their owners. The server schema composes record, harness, chat and society tables, with SQLite WAL and FULL synchronization; [store.rs](../repo/crates/hamlet_server/src/store.rs), lines 72–104 and 113–135. The server owns organizational authority and execution permission. The harness owns model execution and its conversation store. The GUI is a client rather than the execution owner. Disconnect handling removes client watches/model interactions rather than stopping agent work; [runtime.rs](../repo/crates/hamlet_server/src/runtime.rs), lines 262–276.

The pi child is launched with a stable runtime identity and store path, communicating over stdio; [harness/process.rs](../repo/crates/hamlet_server/src/harness/process.rs), lines 102–170. The adapter opens pi-durable SQLite storage, checks the recorded runtime identity and advertises capabilities before starting work; [runtime.ts](../repo/harnesses/pi/src/runtime.ts), lines 64–84 and 128–189. The pinned adapter identifies itself as `hamlet-pi 0.1.0` and its underlying harness as `pi-durable 1.2.0`. A configurable harness name is not evidence of multiple implemented harnesses: [harness.rs](../repo/crates/hamlet_server/src/harness.rs), lines 578–612, explicitly refuses a harness other than the default pi implementation.

An **agent is a durable organizational identity**, represented by hamlet ID and monotonically allocated number, with name, purpose, model override and character. It is not a dedicated process. A **hamlet** is a persistent group with one mayor, limits, a record and an optional shared project folder. A **realm** groups hamlets. A **conversation** is tied to an agent and permanently bound to the runtime in which it began; one agent can have human sessions plus separate peer conversations. A **runtime** is a Node process that can serve many such conversations. An **errand** is a constrained conversation used for a ballot, hearing, review, notes or librarian job. A **root task** identifies an instruction and propagated work for accounting/message limits. It is not a project ticket.

Concurrency is real between conversations. Pi keeps a separate request chain per conversation, while its settings execute tools sequentially inside each conversation; [runtime.ts](../repo/harnesses/pi/src/runtime.ts), lines 78–84 and 211–226. The Rust server owns the event loop and moves slow tool/house work into tasks. This separates responsive coordination from model and tool work, but it provides no automatic source branch or integration discipline for concurrent specialists.

## Agent definition, creation and lifecycle

### Definition and authority

A created agent's configurable substance is `name`, `purpose`, optional `roads`, `model` and `character`, accompanied by a creation reason; [agents.rs](../repo/crates/hamlet_server/src/society/agents.rs), lines 17–27. Prompt assembly adds the shared charter, machine environment, project instructions, character, notes, personal skills, shared library and organizational brief; [prompt.rs](../repo/crates/hamlet_server/src/prompt.rs), lines 145–210. Thus durable identity/configuration is distinct from the prompt rendered for a particular turn.

The shipped [charter](../repo/crates/hamlet_server/assets/charter.md), lines 1–18, defines a personal assistant that grows skills, keeps NOTES.md, uses file/shell tools, cannot install software and should not open an application/browser. That is a material fit boundary for development and browser verification. It can be replaced, but Wingman's responsibilities and permitted toolchains would need an intentional new charter and policies. Personal notes are prompted memory, not a structured project specification store.

Role authority is server-owned. Mayor-only creation/removal/merging differs from every-agent messaging and question tools; ballot conversations get narrowly scoped ballot authority. The tool/role table is explicit in [society.rs](../repo/crates/hamlet_server/src/society.rs), lines 65–154. Giving an ordinary worker a character saying “TechMaster” does not grant mayor capabilities or establish a new permission class.

### Admission, identity and first execution

Founding a hamlet creates agent number zero as mayor, establishes chief membership and resets the group's next agent number to one; [record.rs](../repo/crates/hamlet_server/src/record.rs), lines 899–924. Later `create_agent` calls flow through a record operation and transactional result marker. Admission checks globally available names, nonempty mayor-supplied purpose, agent-room limits and allowed models. It allocates a stable number, stores configuration and creation/model decisions, then tries the requested roads; [membership.rs](../repo/crates/hamlet_server/src/record/membership.rs), lines 56–126. Road refusals can coexist with successful agent creation, so the caller receives that distinction.

After the identity is committed, house initialization runs as separate work. Creation returns “Give it work with ask_agent”. It does not start an autonomous perpetual process simply because a record exists. Initialization builds missing folders/notes locally or asks the selected remote worker; [papers.rs](../repo/crates/hamlet_server/src/papers.rs), lines 290–327. [agents.rs](../repo/crates/hamlet_server/src/society/agents.rs), lines 109–119, deliberately allows initialization to be retried at startup. This avoids conflating a failed filesystem step with nonexistent organizational identity.

First use binds a conversation to the agent's selected model and the pi runtime. Existing conversations retain their runtime; changing the configured harness affects later conversations only. [bindings.rs](../repo/crates/hamlet_server/src/harness/bindings.rs), lines 35–48 and 149–184. Agent creation is therefore distinct from conversation creation, model generation and OS tool-process creation.

### Tools, permissions and concurrent work

Basic tools cover reading, searching/finding, writing/editing and shell execution. The permission gate classifies the call by reach; read operations differ from edits/commands, and chief limits may reserve society changes. [gate.rs](../repo/crates/hamlet_server/src/gate.rs), lines 19–110 and 196–239. A call identity is tied to its runtime, conversation, input, tool and canonical argument digest, preventing reuse of an operation key with altered content; [decide.rs](../repo/crates/hamlet_server/src/chats/calls/decide.rs), lines 76–114.

Manual project mode asks before edits and commands; auto mode relies on grants and confinement. Local project commands write in the shared project and agent house, while prompt instructions suggest mayor-arranged git worktrees when agents must work apart; [prompt.rs](../repo/crates/hamlet_server/src/prompt.rs), lines 436–499. That is guidance, not an implemented worktree allocator, file-lock system or merge queue. Several agents can therefore edit one product concurrently without guaranteed branch isolation. Shell commands have a 120-second maximum that the model may shorten; [shell.rs](../repo/crates/hamlet_server/src/tools/shell.rs), lines 27–29. Long build/test workflows need accommodation. The local sandbox selects Seatbelt on macOS and bubblewrap on Linux; Windows has an explicit insecure mode, so confinement guarantees are platform-dependent; [sandbox.rs](../repo/crates/hamlet_server/src/sandbox.rs), lines 30–76.

The code also loads hand-added tool manifests with schema validation, reserved-name protection, executable and declared sandbox reach; [hand.rs](../repo/crates/hamlet_server/src/hand.rs), lines 20–32, 68–131 and 133–180. Runtime definitions refresh dynamically. This is a concrete extension route, not an existing Telegram/Codex/project-management integration.

### Persistence, resume, scheduling and recovery

Chief input is associated with a root task and persisted before it is sent to the harness. Request identifiers deduplicate repeated admission; [say.rs](../repo/crates/hamlet_server/src/chats/say.rs), lines 853–885; [harness.rs](../repo/crates/hamlet_server/src/harness.rs), lines 615–628. The harness records queued/placed/done/unanswered states. Sessions can be started, retired with an owed reflection, and resumed; [deeds.rs](../repo/crates/hamlet_server/src/chats/deeds.rs), lines 114–212. Rewind creates a fork of earlier conversation entries and changes the current pointer. It does not undo commands, changed files or spend.

Startup relaunches runtimes with their bound conversations. Unexpected closure schedules restart unless shutdown or protocol refusal prevents it. See [harness.rs](../repo/crates/hamlet_server/src/harness.rs), lines 363–397 and 904–982. Pi bounds ordinary retries and does not retry inside a stream. Its separate cutoff-recovery task aborts the old generation, compacts, and creates one successor under the original input. Stop/retry bookkeeping persists. See [runtime.ts](../repo/harnesses/pi/src/runtime.ts), lines 78–93, and [recovery.ts](../repo/harnesses/pi/src/recovery.ts), lines 15–101 and 117–165.

The strongest recovery guarantee applies to server-owned transactional operations. Authority, organizational effect and result marker commit together; replay can return the saved result, while a conflicting request digest is refused. [operation.rs](../repo/crates/hamlet_server/src/operation.rs), lines 144–218. This does not make arbitrary shell side effects transactional. Remote transport explicitly reports uncertain outcomes rather than silently retrying a possibly completed operation; [workspace.rs](../repo/crates/hamlet_server/src/workspace.rs), lines 16–18 and 70–117.

The 50-ms server tick and two-second tool rescan are runtime maintenance. The tick advances votes, reviews, merges and overdue provider requests; [runtime.rs](../repo/crates/hamlet_server/src/runtime.rs), lines 132–175 and 308–353. Automatic reflection is based on completed human turns and session retirement; [follow.rs](../repo/crates/hamlet_server/src/chats/follow.rs), lines 17–40 and 98–151. Neither implements a periodic project manager that wakes to inspect delivery progress, discover blockers and contact owners. Such a supervisor remains to build.

### Interruption, completion and retirement

Stopping an agent traverses its running conversations, stops tool tasks, durably cancels harness work, drops queued input and closes waits. Cancellation can survive runtime downtime; [deeds.rs](../repo/crates/hamlet_server/src/chats/deeds.rs), lines 464–549. Remote pending-operation drop additionally sends a cancel request to the worker; [workspace.rs](../repo/crates/hamlet_server/src/workspace.rs), lines 165–181. This is execution interruption, not automatic rollback of completed effects.

Input completion is followed once. The server marks instructions done, counts turns, requests reflection, reports failures and continues queued work; [follow.rs](../repo/crates/hamlet_server/src/chats/follow.rs), lines 43–151. “Done” means that input's execution ended successfully, not that product acceptance scenarios passed. There is no supplied product acceptance authority or delivery artifact gate.

Removal archives identity/roads, stops conversations and revokes network/unconfined grants and session trust; [leaving.rs](../repo/crates/hamlet_server/src/society/leaving.rs), lines 73–161. The record protects agents with outstanding/recent human instructions against mayor removal/merge; chiefs can override the protection; [membership.rs](../repo/crates/hamlet_server/src/record/membership.rs), lines 129–197. Restoration/erasure are explicit chief actions. Merge is a richer lifecycle operation with saved manifests, house snapshots, note combination and reversible file transfers. Local startup can finish interrupted file work; remote uncertain attempts are not blindly replayed; [merging.rs](../repo/crates/hamlet_server/src/society/merging.rs), lines 689–747 and 821–870. These are substantial retirement/recovery mechanisms, though not Wingman's conversation archive/profile lifecycle verbatim.

## Coordination mechanics and one traced request

The shared coordination substrate consists of organizational records, road topology, durable pairwise correspondence, waits/approvals, instructions and accounting. Shared project files give collaborators a common filesystem. There is no ticket dependency DAG or multi-party room schema: [society/schema.sql](../repo/crates/hamlet_server/src/society/schema.sql), lines 1–79, stores peer bindings, messages, a message counter, pending society calls and JSON society documents.

A representative implemented request path is a chief asking the mayor to have another agent implement a change. This is a source trace, not a claim that a live model was observed choosing these actions:

1. A client `Say` request authenticates and dispatches into chat handling; [requests.rs](../repo/crates/hamlet_server/src/requests.rs), lines 99–129 and 174–176. The chief's text gets an instruction/root-task mark, current conversation binding and durable input before runtime submission; [say.rs](../repo/crates/hamlet_server/src/chats/say.rs), lines 839–885.
2. If another specialist is needed, the mayor's `create_agent` call is checked against server authority/limits and commits the agent record/result once, then initializes its house. It still needs a separate work message; [agents.rs](../repo/crates/hamlet_server/src/society/agents.rs), lines 37–120.
3. The mayor calls `ask_agent(name, message)` to wait for the specialist's result, or `tell_agent` to continue while a later reply arrives. `ask_agent` resolves and preserves the recipient identity across replays; [letters.rs](../repo/crates/hamlet_server/src/society/letters.rs), lines 229–328. The server requires a road, rejects empty messages, inherits the root task, creates/reuses a recipient conversation dedicated to this sender and message kind, and commits correspondence before submission; lines 626–749.
4. Sending increments the root-task message count and records use of the communication road. New requests can be capped, but replies have a return path even when the cap/road would refuse new traffic; [letters.rs](../repo/crates/hamlet_server/src/society/letters.rs), lines 560–623. Synchronous questions also check waiting cycles; lines 338–369. These mechanisms constrain delegation loops without creating ticket dependencies.
5. The specialist receives its own prompt/memory and accesses shared project files through the tool gate. In manual mode a changed file or command raises a human wait. An ambiguous product choice can be asked through `ask_chief`. Human decisions are attached to the call/session rather than relayed through Butler or a management room.
6. The recipient answer/failure is retained with the correspondence, wakes a synchronous caller, or is submitted as a new input for an asynchronous letter; [letters.rs](../repo/crates/hamlet_server/src/society/letters.rs), lines 870–997. A watched native peer chat exposes the underlying exchange; [watch.rs](../repo/crates/hamlet_server/src/chats/watch.rs), lines 81–121. The mayor can incorporate the result into its response to the chief. That closes conversational delegation, not a verified product delivery milestone.

This supports real direct collaboration and durable attribution. Wingman would need project/ticket IDs and room membership threaded through these records to connect correspondence, acceptance records and executive summaries.

## Major additional capabilities and grounded innovations

**Organizational governance.** Agents can propose replacing the mayor or founding another hamlet. A vote fixes its voters and records reasons, hearings, and ballots. Timeout and threshold rules control progression. A chief can overturn the result. See [votes.rs](../repo/crates/hamlet_server/src/society/votes.rs), lines 27–78 and 345–442.

Grounding uses a limited text check. A normalized four-word evidence sequence must occur in frozen notes or recent history. Policy can require grounded yes votes (lines 554–575 and 891–949). This makes evidence traceable. It does not prove the claim's meaning or truth. Wingman would need to reconcile elective leadership and group formation with appointed project responsibility and human direction.

**Communication topology as enforceable policy and resource.** Roads are checked before messages, usage is recorded, and root-task limits bound new correspondence while preserving answers; [letters.rs](../repo/crates/hamlet_server/src/society/letters.rs), lines 560–623 and 645–707. The visible graph therefore corresponds to real permitted communication, rather than decorative reporting lines. This can limit uncontrolled chatter and expose actual collaboration patterns. It can also obstruct a worker who needs an unconnected specialist, requiring mayor relay or road creation. Room-wide discussion would need a different membership/broadcast abstraction.

**Recoverable organizational mutations at a runtime boundary.** Input admission, immutable runtime binding and operation markers coordinate two durable stores. Authority/effect/result commit together for realm operations, and changed requests cannot reuse call keys; [operation.rs](../repo/crates/hamlet_server/src/operation.rs), lines 98–122 and 144–218; [decide.rs](../repo/crates/hamlet_server/src/chats/calls/decide.rs), lines 76–114. This is a useful design for Wingman actions such as creating agents or assigning authority across restarts. Its limits matter: filesystem/shell effects and remote uncertain responses require different recovery treatment.

**Memory-aware merge and restoration.** Agent retirement can combine knowledge and skills into another identity, preserve file collisions and save a restoration manifest. Hash checks preserve subsequently edited files during restoration; [merging.rs](../repo/crates/hamlet_server/src/society/merging.rs), lines 689–747. This is more sophisticated than deleting a completed worker process. The integration consequence is significant: knowledge ownership, agent identity, conversation references and project obligations must stay coherent after organizational restructuring. It is not a merge of product source branches.

**Private learning promoted through a shared librarian.** Reflection asks agents to save reusable lessons into notes and skills; [follow.rs](../repo/crates/hamlet_server/src/chats/follow.rs), lines 17–24. Skill offers snapshot files and prompt a separate librarian judgment about usefulness, clarity, duplication and private information. An answer whose first word is `ACCEPT` publishes the snapshot with provenance; unchanged private copies are removed while later private edits are preserved; [library.rs](../repo/crates/hamlet_server/src/society/library.rs), lines 257–296 and 313–409. This is a concrete personal-to-organizational knowledge pipeline. Textual librarian acceptance is not execution validation, test coverage or a reliable privacy proof; Wingman should add capability/security checks appropriate to reusable development scripts.

**Explicit execution isolation and remote uncertainty.** The Rust authority controls model-originated tools independently of the model runtime, and a bearer-authenticated worker transports scoped operations rather than giving the runtime arbitrary host access; [workspace.rs](../repo/crates/hamlet_server/src/workspace.rs), lines 20–98. In remote mode the agent sees `/house`, shared `/project` and read-only `/library`, with buffered command output capped at 1 MiB and per-file transfer capped at 4 MiB; [papers/remote.rs](../repo/crates/hamlet_server/src/papers/remote.rs), lines 17–35. This helps maintain host boundaries, but large build artifacts, rich live terminal output and integrations needing arbitrary private-network access require adaptation.

These are distinctive implementation mechanisms relative to Wingman's described product. No historical novelty or industry-wide uniqueness is claimed. The 3D world usefully visualizes persistent agents and communication relations, but its appearance alone is not evidence for project management or executive reporting.

## Multi-host boundary and practical adoption

[Houses](../repo/crates/hamlet_server/src/papers.rs), lines 56–103, owns one `Workspace::Local` or `Workspace::Remote` selected at startup. This permits a local control server/window and remote Linux tools, but not agent A on Mac and agent B on Endeavour under individual execution-host routing. The Linux-only worker is an actual executable implementation, not merely a remote UI connection; [worker main](../repo/crates/hamlet_workspace/src/main.rs), lines 1–34 and 47–65.

Remote `Houses::allows` refuses all enumerated special capabilities: erase house, found/move/remove/restore/erase hamlet and move house between hamlets; [papers.rs](../repo/crates/hamlet_server/src/papers.rs), lines 29–52 and 122–130. Founding checks this before proceeding; [realm/deeds.rs](../repo/crates/hamlet_server/src/realm/deeds.rs), lines 35–47. Existing remote agents can still perform supported work, including some merges, but local group-lifecycle behavior must not be assumed to carry over. Remote outcomes can be uncertain. There is deliberately no automatic host fallback to rerun an operation elsewhere.

Wingman could use Hamlet directly as a separate persistent society/execution experiment, and could borrow its identity/binding model, road authorization, durable waits, operation markers, memory lifecycle and native agent inspector design. Those are the strongest assets.

Adopting it as the core product would require substantial adaptation: a Codex harness adapter; software-development charter and reusable role profiles; per-project product/technical/test responsibilities; project-aware shared room messaging; and client surfaces matching Wingman's dashboards. The native Rust/Bevy and Node/pi architecture is a concrete technology commitment, not a drop-in extension to existing Codex chats.

The principal missing layer remains Telegram Butler; ProjectMaster portfolio intake/reconciliation and periodic supervision; scope/specification/acceptance records; tickets/dependencies and progress tracking; semantic current/recent/next/blocker summaries and linked timelines; integrated code/diff/test/browser review; acceptance/delivery gates; and per-agent multi-host placement. Generic tools and prompts could implement pieces, but the checked-out product does not ship their coordination guarantees.
