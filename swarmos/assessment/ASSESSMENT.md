# SwarmOS assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/supernovae/SwarmOS . Local checkout: `research/swarmos/repo`. Assessed commit: `76604741648a59b6d1cd7afab66ddfb4ea7e0aa9` (read from the checkout, rather than inferred from a release). This report follows [Wingman's purpose](../../WINGMAN_PURPOSE.md) and the [assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md). The checkout's [AGENTS.md](../repo/AGENTS.md) was read before implementation inspection. The embedded scaffold AGENTS template was not treated as instructions for this assessment.

**Fit verdict:** SwarmOS is a strong candidate for Wingman's bounded coding-task delivery layer, especially when several machines or external contributors must coordinate safely through GitHub. It is not a substitute for Wingman's standing development organization. Its durable actors are approved issue contracts, fenced task claims, artifacts and PRs; its planner, reviewer, developer and tester are successive harness executions. Butler, conversational product discovery, persistent employee identities, management rooms and connected executive/agent workspaces would remain a substantial product to build.

This is an implementation assessment, not a runtime certification. Source and selected tests were read; no dependencies were installed, services launched, model calls made or tests executed. Statements about test behavior below describe assertions present in the checked-out tests.

## 1. Product identity and execution architecture

SwarmOS is a Go CLI with a concrete delivery engine, not just a collection of role prompts. [The entry point](../repo/cmd/swarm/main.go), lines 10–15, delegates to Cobra. [Root command construction](../repo/internal/cli/root.go), lines 71–146, registers `repo`, `node`, `issue`, `pr`, storage and fork-coordinator resources, establishes repository routing and creates a command-scoped sandbox inspection session. There is no resident organizational server in that entry path.

The core path is:

```text
repo policy + GitHub/local issue containing WorkUnit
  → maintainer approval pins task/policy/base
  → eligible worker selection + boundary preflight
  → fenced claim in Git remote CAS state (or local file CAS)
  → isolated issue worktree + compiled role/task bundle
  → planner → human/agent/no plan gate → developer → tester
  → trusted-base required checks → bounded repair if applicable
  → checkpoint/artifacts → explicit submit → Draft PR
  → GitHub review/merge → reconciled outcome and cleanup
```

[`WorkUnit`, `Lease`, `Artifact`, workflow and configuration types](../repo/internal/contract/types.go), lines 27–99 and 129–236, establish the data model. A WorkUnit carries objective, constraints, acceptance criteria, workflow, dependencies, required capabilities and task dimensions. The lease carries owner, node, harness, claim ID, phase, status and expiry. Artifacts are typed design/test-plan/review/implementation/validation records. This is task-centered continuity. A configured agent key is a policy selector rather than a durable employee record.

The tracker abstraction has GitHub and local implementations. [GitHub tracker construction](../repo/internal/tracker/github.go), lines 21–85, resolves repository and token policy and builds REST clients. The shared authority is **not the issue comment stream**: [`Store` and implementations](../repo/internal/coordination/store.go), lines 21–52, 113–153 and 210–247, expose revision-based compare-and-swap. Local state is file-locked and atomically replaced; Git state uses the upstream remote. [Ref layout](../repo/internal/coordination/refs.go), lines 16–80, supports the branch namespace `refs/heads/swarm-state/issue-N` or a trusted-policy-selected hidden `refs/swarm/state/` namespace, with separate checkpoint-retention and contributor-index families. This is real shared coordination across independent clones, not an implication drawn from local subprocess parallelism.

The actual [Git CAS write](../repo/internal/coordination/store.go), lines 303–328, creates a `state.json` blob/tree/commit and pushes with `--force-with-lease` against the captured state ref. Checkpoint publication at lines 446–527 and PR publication at lines 540–577 combine expected state/head leases with `git push --atomic`. They do not simulate atomicity by updating an issue comment after an ordinary branch push. The state-push path also inspects remote outcome before bounded retries (lines 373–405), which matters when transport failure leaves publication uncertain.

[`IssueState`](../repo/internal/lease/manager.go), lines 261–323, persists approvals and digests, plans and review history, claims, checkpoint heads, artifacts, role attestations and telemetry, PR linkage/revisions, recovery and cleanup records. [`checkStateClaim`/`mutate`](../repo/internal/lease/manager.go), lines 1455–1506, require the current owner, active unexpired lease, current local token and approved task, retrying bounded CAS conflicts. This is a meaningful stale-worker boundary.

[`ExecuteWork`](../repo/internal/workflow/engine.go), lines 552–660, runs setup, heartbeat, planning, review and implementation/validation. It does not execute an arbitrary agent graph supplied by the model. Although `WorkflowSpec` has steps, actual orchestration in this engine is explicitly coded around four roles and known phases. Role names are checked in [harness configuration loading](../repo/internal/harness/scaffold.go), lines 653–659 and 809–816. Additional configured harness/model instances are easier to add than a new organizational responsibility with new lifecycle semantics.

## 3. Agent definition and lifecycle

### Definition, creation and identity

`.swarm/config.yaml` defines allowlisted agent keys with binary, harness, model, effort, allowed roles, authentication and execution-related settings. [`NewConfiguredRunnerWithOptions`](../repo/internal/agent/configured.go), lines 29–129, resolves approved execution policy, verifies environment restrictions and supported harness, and creates a CLI adapter. Supported configured drivers are `claude`, `codex`, `opencode` and `omp` in [`resolveHarness`](../repo/internal/agent/configured.go), lines 324–336. Broader switch cases in command construction and docs should not be mistaken for an unrestricted driver/plugin system: the configured runner's admission path is decisive. `mock` is deliberately restricted to explicit trusted-local execution.

Configuration creates no persistent running entity. A role invocation constructs a runner and supplies a [`RunRequest`](../repo/internal/agent/runner.go), lines 11–36, containing role, task prompt, worktree, system prompt, model, mode, dependencies and coordinator callbacks. Execution starts a real harness process, or the native/delegated sandbox path starts it against a detached task snapshot. Identity has several separate meanings: tracker-authenticated human owner; node ID; configured agent/harness/model; random fenced claim ID; and per-run telemetry ID. None is an employee identity with a lifetime conversation. Node ID defaults to hostname/OS/architecture in [host-profile detection](../repo/internal/node/profile.go), lines 29–55.

Role selection follows per-role CLI override, configured mapping/defaults through [`resolveRoleAgent`](../repo/internal/workflow/engine.go), lines 273–314. The same model/harness may fill several roles; independent-review policy can require a different harness or model, and for humans a reviewer distinct from the claim owner. [Reviewer-policy tests](../repo/internal/lease/reviewer_policy_test.go), lines 78–150, show both the allowlist enforcement and the narrower meaning of independence: a different model on the same harness may satisfy it. This is useful separation of evaluation, not proof of independently trained organizational judgment.

### Admission, routing, tools and permissions

A work invocation validates phase/gate combinations before mutation ([work command](../repo/internal/cli/work.go), lines 19–69). Selection scans explicit or all registered repositories and lists ready issues. It skips parent, PR-open, completed and actively claimed items. It checks dependencies, capability matching and current task approval. It selects a handoff phase and checks harness readiness before claiming ([selection](../repo/internal/cli/selection.go), lines 78–237). Dependencies are prepared from approved base before the role starts; [`AgentDependencies`](../repo/internal/workflow/dependencies.go), lines 16–59, explicitly stops on preparation errors.

The default mode is isolated. A trusted-local override is rejected if repository policy requires isolation ([execution resolution](../repo/internal/contract/execution.go), lines 25–82). Native Codex gets coordinator-selected filesystem/network permissions; [native policy](../repo/internal/sandbox/native.go), lines 95–167, disables general network and features including external integrations and multi-agent delegation. Boundary inspection/canaries are part of the path, not a permissive fallback. Claude/OpenCode/OMP run through harness-specific mediated execution, with approved file/shell tools inside Bubblewrap. [Delegated execution](../repo/internal/sandbox/delegated.go), lines 133–241, supplies the tool executor, controlled settings and driver-specific sessions; [`executorTools`](../repo/internal/sandbox/tools.go), lines 17–30, exposes read/write/edit/shell with bounded command lifetime and no ordinary host network/credentials.

Planner/reviewer are source-read-only roles with explicitly imported output artifacts; developer/tester may change a detached snapshot subject to coordinator import checks ([isolated adapter](../repo/internal/agent/isolated.go), lines 45–83; [native workspace boundary](../repo/internal/sandbox/native.go), lines 700–840). Git worktrees alone are therefore not the security boundary. OCI is another boundary, but [configured runner admission](../repo/internal/agent/configured.go), lines 88–113, currently limits it to offline/no-auth use rather than promising arbitrary credentialed container execution. Explicit trusted-local mode runs host harness commands with restricted environment and temp HOME, and must be treated as a different trust choice.

### Execution, concurrency and scheduling

`ExecuteWork` controls the sequence. The planner writes `PLAN.md` and `TEST_PLAN.md`, records them as a pair, and may hand off or recommend decomposition. Human gates return a paused result and notify reviewers; agent gates run a sandboxed reviewer with content-bound verdicts. A rejected agent plan may be revised within an approved replan allowance. Developer execution produces a checkpoint and implementation artifact, tester execution produces acceptance evidence, and the coordinator runs required checks and records trusted validation. The sequence is visible in [engine](../repo/internal/workflow/engine.go), lines 603–660, [planner](../repo/internal/workflow/execute_plan.go), lines 26–165, and [validation/repair](../repo/internal/workflow/execute_validation.go), lines 17–198.

`node run` creates `concurrency` goroutines, each pulling and executing its own issue; max-jobs counts admitted attempts, not a team capacity model. `--all` spans the local repository registry. `--watch` sleeps between scans after draining ready work, while failures end the invocation ([node loop](../repo/internal/cli/node.go), lines 224–332). This is an on-demand or long-running worker-pool process. There is no durable scheduler that restarts itself after machine/process failure, no calendar, and no autonomous ProjectMaster examining management rooms. Multiple hosts must each start their worker; their remote CAS claims prevent duplicate authority.

Touchpoint overlap ranking reduces likely collisions using paths inferred from task text and active tasks. It is advisory, preserves eligibility and reports incomplete information ([overlap scheduling](../repo/internal/cli/selection.go), lines 352–422; [overlap definition](../repo/internal/workflow/task_shape.go), lines 147–170). It is not a semantic conflict detector or distributed transaction across dependent products.

### Persistence, resumption, interruption and recovery

Claims persist outside agent worktrees in a clone-identity-specific user-config location; local locks reject concurrent execution of the same issue on one machine ([claim control](../repo/internal/lease/claims.go), lines 24–36 and 95–120). Across clones, Git remote CAS arbitrates ownership. Worktrees and checkpoints retain code; authoritative state retains artifact/digest/phase history. [`Resume`](../repo/internal/lease/manager.go), lines 1435–1453, binds and verifies a claim token. It resumes authority over a task. It is not a harness-chat resume API.

That distinction matters in native execution: [`RunNativeCodex`](../repo/internal/sandbox/native.go), lines 606–626, runs each exec turn as its own session, discovers only that invocation's session IDs for telemetry and supplies continuation instructions via files. [Claude delegated execution](../repo/internal/sandbox/delegated.go), lines 218–238, similarly documents fresh print-turn sessions. Harness-native logs may exist on the host, but SwarmOS does not present a unified durable conversation lifecycle for them.

The [heartbeat](../repo/internal/lease/heartbeat.go), lines 22–103, renews every third of the lease duration (minimum one second), reloads policy/budget and cancels work when renewal/fencing fails. [Process execution](../repo/internal/agent/adapters.go), lines 259–279, stops the child when context is canceled. Isolated paths also own teardown and import policy. Active/wall-time budgets and interactive-idle accounting are implemented by [agent budgets](../repo/internal/sandbox/agent_budget.go), lines 70–145, rather than merely prompting the agent to stop.

Lease-budget exhaustion is a controlled pause: [pause logic](../repo/internal/workflow/claim_budget.go), lines 82–154, records a resumable next phase and can preserve a checkpoint. Timeout/import rejection recovery is different: detached-snapshot changes are not silently adopted; [native workspace timeout handling](../repo/internal/sandbox/native.go), lines 773–794, preserves a recovery patch with a bounded cleanup context. [Rejected-import handling](../repo/internal/workflow/execute_run.go), lines 108–167, preserves private recovery evidence and records the failure. Recovery requires respecting task, head and policy identity, rather than replaying an arbitrary patch into a new claim.

Validation failure can trigger bounded developer → tester/check repair. Pre-existing or outside-candidate failures are distinguished; exhausted repair allowance requires explicit continuation ([validation loop](../repo/internal/workflow/execute_validation.go), lines 125–195). Provider capacity/quota/rate/network failure classification exists ([failure classifier](../repo/internal/agent/failure.go), lines 55–123), but is not a general automatic provider-failover or endlessly restarting supervisor. The node loop returns failure after a failed attempt. A human/operator still has recovery work in cases the coordinator cannot safely automate.

### Completion, acceptance and retirement

Passing checks completes the implementation phase, not final product acceptance. [`issue submit`](../repo/internal/cli/submit.go), lines 18–33 and 111–129, checks exact approval and checkpoint, validates or reuses appropriately bound evidence, and opens an idempotent Draft PR. Optional node auto-submission calls this same submit command ([node](../repo/internal/cli/node.go), lines 197–222). Thus publication is an explicit operation in the CLI design, with an operator option authorizing automatic use after validation. It is not an agent deciding freely to push.

[Submission reconciliation](../repo/internal/lease/lifecycle.go), lines 38–150, observes GitHub PR outcome. A submitted/completed execution attempt does not mean a merged product. Reviewers/maintainers still accept the finished change through GitHub. Acceptance mappings are explicitly advisory ([acceptance snapshot](../repo/internal/validation/acceptance_evidence.go), lines 16–20): syntactically valid evidence can still be inaccurate, so it cannot replace review.

Harness processes terminate after runs and native snapshots are cleaned up. Task worktrees/branches have explicit inspected retirement paths, with dirty/unexpected files blocking unsafe removal ([workspace cleanup](../repo/internal/workspace/cleanup.go), lines 63–100 and 246–286). Checkpoint-retention refs are designed to remain independent of task-branch cleanup ([ref layout](../repo/internal/coordination/refs.go), lines 68–75). There is no organizational employee retirement/archive operation because such durable agents are not the model.

## 4. Coordination mechanics and one concrete request trace

Coordination is contract-and-artifact exchange. Issues are tickets; WorkUnit dependency fields and tracker relationships establish ordering; claims decide who may mutate; typed artifacts pass context between roles; status comments are readable projections; GitHub Actions issue-comment events can carry fork-worker requests. There is no peer chat transport. A developer does not send a message to a separately active tester: the coordinator compiles the next role's bundle using authoritative artifacts and starts that role.

A concrete supported request is an operator running `swarm issue work --next --all` against registered repositories:

1. **Intake and target selection.** [Work CLI](../repo/internal/cli/work.go), lines 19–69 and 79–132, validates selectors, builds role/gate/instruction options, then calls `pullNextReadyIssue`. There is already a repository and structured approved issue. This is not discovery from a blank product idea.
2. **Queue coordination.** [Selection](../repo/internal/cli/selection.go), lines 78–210, resolves registry targets and node capabilities, loads ready issues, ranks dependencies/overlap, verifies approval and plan/human prerequisites, and preflights selected harnesses. Active claims are skipped. Conflicting claim acquisition is expected and causes selection to continue, not double execution.
3. **Authoritative ownership.** [Selection](../repo/internal/cli/selection.go), lines 211–270, locks the local claim, acquires through the lease manager, stores the token and provisions a checkpoint-aware worktree. [`checkStateClaim`/`mutate`](../repo/internal/lease/manager.go), lines 1480–1506, fence subsequent changes. Comments cannot mint this authority.
4. **Shared instructions.** [Bundle compiler](../repo/internal/workspace/worktree.go), lines 789–882, combines approved-base role instructions, project knowledge, rules, skills, task profile and current artifact history. The worktree contains `.swarm/active/WORKUNIT.md` and `SYSTEM_PROMPT.md`; temporary AGENTS/CLAUDE pointers direct the harness there and are stripped before checkpoints.
5. **Plan and decision.** [Planner](../repo/internal/workflow/execute_plan.go), lines 59–133, runs the selected planner and records paired plan/test-plan artifacts. [Review routing](../repo/internal/workflow/execute_review.go), lines 10–23 and 44–67, either invokes reviewer, proceeds without a gate, or returns awaiting human approval. Authenticated human review binds verdict to exact task/policy/plan/test-plan hashes ([human review](../repo/internal/lease/manager.go), lines 1727–1800); later plan changes cannot reuse an old approval.
6. **Implementation, evidence and recovery.** [Developer round](../repo/internal/workflow/execute_implementation.go), lines 18–80, invokes the developer with import checks; [tester/required checks](../repo/internal/workflow/execute_validation.go), lines 17–123, records independent tester output and coordinator-derived validation. Repair is limited by trusted policy. Handoffs persist a next phase that another suitable node can claim.
7. **Delivery and subsequent changes.** `issue submit` validates the approved checkpoint and opens the Draft PR; [PR service](../repo/internal/pr/service.go), lines 155–166, 279–332 and 691–710, verifies authoritative issue↔PR linkage for continued development. [PR submission](../repo/internal/pr/service.go), lines 1243–1280, starts the explicit update-publication path. GitHub merge/closure later reconciles the outcome. A PR body alone is only a lookup hint, not authority to revise an unrelated issue.

There is code-level test evidence for this coordination design: [`TestGitCASAcrossClonesAndAtomicCheckpointFence`](../repo/internal/coordination/store_test.go), lines 19–101, races two independent clones and asserts exactly one winner, then asserts a stale state revision cannot publish its checkpoint. The following PR test, lines 104–161, separately fences captured PR head and state revision. These tests use a local bare Git remote. They do not by themselves establish a successful live two-machine GitHub deployment.

## 5. Major capabilities beyond Wingman's described scope

**Untrusted contributor/fork delivery protocol.** Wingman describes a personal organization operating its own agents; SwarmOS also supports people donating compute without upstream write credentials. [Fork coordinator](../repo/internal/fork/coordinator.go), lines 119–198 and 199–220, re-fetches issue/comment data, verifies repository, issue state, unedited content, author and non-bot identity before interpreting operations. A comment is parameters, not authority. Together with contributor-index CAS, replay/cap controls and verified fork/PR operations, this allows an open contribution pool. Integration would add public-contributor trust policy and GitHub Actions operations to Wingman, not just another agent adapter.

**Policy and publication fencing as a first-class delivery system.** Approved-base prompts/checks/protected paths, claim tokens, content-digest approvals and atomic state/head publication form a stronger provenance chain than a generic shared ticket board. [Trusted validation](../repo/internal/validation/validator.go), lines 210–286, refuses absent base and loads policy from that base; [claim validation](../repo/internal/lease/manager.go), lines 1455–1506, ties writes to a still-approved task. Wingman could use this to prevent a stale or compromised worker publishing after reassignment. It would also need to reconcile conversational scope changes with explicit contract reapproval.

**Controlled execution across several coding harnesses.** Native Codex, delegated Claude/OpenCode/OMP, read-only review snapshots and offline OCI boundaries are significant infrastructure. [Runner admission](../repo/internal/agent/configured.go), lines 29–129, rejects unqualified overrides rather than silently weakening isolation. The tradeoff is reduced tool freedom: default worker shells cannot use arbitrary internet, credentials, plugins, peer subagents or persistent background services. Wingman's research/browser/integration agents may need separate capabilities and host placement, not a broad bypass of these policies.

**Trusted dependency preparation and isolated browser testing.** [Dependency preparation](../repo/internal/workflow/dependencies.go), lines 16–59, prefetches from the approved base and makes caches available under node-controlled policy; private module patterns are node-side settings ([node profile](../repo/internal/contract/types.go), lines 226–235). [Browser launch](../repo/internal/sandbox/browser.go), lines 20–89, uses a managed Linux systemd scope, explicit environment and memory constraints. This gives offline workers useful build/test capacity without exposing the general host. It introduces platform prerequisites: a Mac/Arch deployment must qualify the actual native/browser boundaries and assign Linux-only capabilities accordingly. Browser support here is task preview/testing, not Wingman's human-facing browser workspace.

**PR continuation and rebase/recovery rather than one-shot generation.** [PR service](../repo/internal/pr/service.go), lines 279–332, 691–710, 890–920 and 1243–1280, verifies linked WorkUnits, stages revisions, rebases and publishes through claim/head fences. [Checkpoint recovery tests](../repo/internal/workflow/recovery_test.go), lines 25–108, exercise retained-work recovery against a moved base in a fixture. This is useful for the long tail of delivery after initial generation. It requires Wingman's tracker to distinguish implementation, submission, open PR, requested changes and merged acceptance rather than a single “done” field.

**Evidence-aware repair, backlog planning and lessons.** [Project planning](../repo/internal/workflow/project_plan.go), lines 130–228 and 469–575, can parse a Markdown/YAML roadmap or invoke an explicitly requested planner to produce WorkUnits, then calculate execution waves. [Task assessment](../repo/internal/workflow/task_shape.go), lines 51–138, provides deterministic uncertainty/risk/scope hints; overlap ranking is advisory. [Lessons](../repo/internal/workflow/lessons.go), lines 136–180, harvests only authoritatively linked merged work and proposes local rule updates for maintainer review. These are useful organizational inputs, but they are not an autonomous product research department or self-authorizing memory.

**Operational storage accounting.** [Storage inventory](../repo/internal/storage/inventory.go), lines 25–51, 85–132 and 151–165, models resource/scan bounds and accounting; [discovery](../repo/internal/storage/discovery.go), lines 313–324, scopes registered repositories. This matters when repeated snapshots, caches and worktrees consume worker disks. It is operational hygiene outside Wingman's stated executive experience; adopting it would require retaining provenance/active-use safety rather than treating all scratch-looking directories as disposable.

## 6. Distinctive mechanisms and grounded innovation

The strongest design contribution for Wingman is **using Git's remote compare-and-swap and atomic ref updates as the delivery control plane**. Authority and checkpoints can move together without a bespoke central database. The separation between state refs, permanent checkpoint-retention refs and mutable PR heads gives recovery explicit objects rather than merely trusting a last log line. Independent-clone race tests ground the mechanism. Its limits are equally concrete: GitHub/Git availability and authorization remain infrastructure dependencies; repeated state writes/heartbeats are remote operations; local mode has different distribution properties; worker provisioning and team conversation are outside the mechanism. This is a distinctive composition in this codebase, not a claim of historical novelty.

The second is **artifact-bound delegation with coordinator-owned trust**. A model may propose a plan, write code or claim tests passed. The coordinator owns claim fencing, content hashes, approved policy, import checks and required-check outcomes. Comments remain projections and telemetry remains descriptive. [Telemetry contract](../repo/internal/contract/telemetry.go), lines 11–15 and 34–63, explicitly excludes telemetry from gates. [Acceptance evidence](../repo/internal/validation/acceptance_evidence.go), lines 16–20 and 49–87, bounds/parses the tester's report without making it truth. This is a useful way to keep an agent organization's records informative without allowing those records to manufacture authority. It cannot establish that acceptance prose is semantically correct. The maintainer still reviews the product.

Third, **mediation adapts a logged-in harness to a narrow task capability set**. Delegated tools keep model access with the harness while file/shell work runs in the selected boundary; native Codex gets an explicitly qualified policy. Detached snapshots allow outputs to be checked before import, and rejection/timeout patches preserve recoverable work without granting it execution authority. This solves a real tension between practical harness use and a trusted coordinator. It does not give arbitrary harnesses the same guarantees; driver/version/platform qualification and feature suppression are material restrictions.

Fourth, **bounded continuity is represented as explicit task-state transitions**: paired plan generations, human/agent review digests, phase handoffs, renewal budgets, repair counts, dropped checkpoints and PR revisions. That is more precise than telling a model to “keep working until done.” It supports useful resumability across role and host changes, while making clear that Wingman would still need persistent conversations, manager identities and product context above the task engine.

## 7. Practical Wingman adoption

Use directly as a delivery subsystem:

- Approved WorkUnits.
- GitHub/local task tracking.
- Dependency-aware pull queues.
- Parallel node workers.
- Git worktrees and checkpoints.
- Planner/reviewer/developer/tester execution.
- Human plan decisions.
- Required-check validation.
- Draft PR delivery.
- Continued PR revision/rebase.
- Provenance and recovery. A sensible boundary is for TechMaster to translate an agreed technical ticket into a WorkUnit and submit it to SwarmOS, while Wingman retains product ownership and human communication.

Adapt rather than rename:

- Map Wingman project IDs to repository entries.
- Give every execution an organization agent/task/host correlation ID without misusing lease owner as employee identity.
- Translate scope/specification changes into contract revisions and reapproval.
- Expose structured status/progress/attestation records as events.
- Build an agent-centered timeline from actual run outcomes and planned assignments.
- Send approval requests through Butler and invoke the authenticated decision path.
- Enforce host capabilities for Mac versus Linux. Wingman needs a supervisor that starts/restarts workers and understands failures because `--watch` is a process-local queue loop, not durable organizational supervision.

Still build:

- Telegram/Butler intake and reply routing.
- ProjectMaster's cross-product registry and ongoing supervision.
- ProductMaster's research and clarification.
- Persistent ProductMaster/TechMaster/specialist identities and conversations.
- Shared management/product rooms and direct peer messaging. A growing directory/team model.
- Portfolio/project/executive dashboards.
- Per-agent summary feeds and detailed live coding workspaces with steering, queued input, attachments and conversation lifecycle controls.
- Final integrated product acceptance and delivery communication. SwarmOS JSON and GitHub records can supply evidence to these views, but do not implement the experience.

The integration decision is therefore architectural: SwarmOS can materially reduce the amount of delivery/security machinery Wingman must invent, while its contract-first repository workflow will shape how the organization authorizes and revises work. If Wingman expects specialists to debate interfaces continuously in shared rooms, keep those conversations above SwarmOS and publish their resolved decisions as explicit task inputs. If it expects broad internet/tool access inside every coding worker, the current qualified execution boundaries will require deliberate additional capability design.
