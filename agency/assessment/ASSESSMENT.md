**Verdict: a useful standing-agent governance and knowledge dashboard, with lightweight local dispatch, but a partial foundation for Wingman rather than its development organization.** Agency strongly matches durable role definitions, editable agent memory, a multi-group directory, human decisions and observation-to-action traceability. Its operating center is an **observation → proposal → human decision → execution** pipeline. Wingman's operating center is a continuing software organization that discovers products, delegates tickets to concurrent specialists, collaborates in rooms and delivers verified products. Agency has useful pieces of that organization, but does not implement that whole journey.

The most consequential distinction is between a **persistent agent record** and a **persistent running agent conversation**. Agency keeps a named directory, native tool instructions, memory and attributed outputs. A scheduled run starts an external coding CLI with a prompt and waits for the process to finish. It does not retain and address a Codex thread, resume the preceding conversation or operate a durable worker control protocol. The SDK integration is explicitly a file contract with no execution. Those boundaries matter more for Wingman than the presence of attractive agent profile pages.

## What the product actually contains

Agency uses Python, FastAPI, and Jinja templates. Configuration maps groups to directories and agent lists. Each group has a `shared/` tree for observations, proposals, decisions, prompts, and logs. Each agent has a tool-native identity file and usually `memory.md`. Dashboard queries read Markdown files with YAML frontmatter. Edits write those files. The application does not use an organization database. See [app.py](../repo/agency/app.py), lines 32–77, 303–315, and 592–622. [config.py](../repo/agency/config.py), lines 6–35, normalizes agent declarations and resolves their directories.

The installed `agency` command enters `agency.cli:main`; `serve` delegates to `app.main()`, which reloads configuration and starts Uvicorn. This is a web management process, while periodic execution is a separate OS-launched Python process. The group switcher selects a governance namespace. It is not an automated request router or a portfolio scheduler. [pyproject.toml](../repo/pyproject.toml), lines 17–18; [cli.py](../repo/agency/cli.py), lines 81–90; [app.py](../repo/agency/app.py), lines 3061–3075.

Two execution paths sit beside this file-backed control plane:

1. The OS timer invokes `agency.dispatch.run`. It reads enabled groups, evaluates daily or interval rules, calls an integration synchronously and writes captured stdout/stderr to dated log files. See [dispatch/run.py](../repo/agency/dispatch/run.py), lines 57–203.
2. A web proposal decision writes a decision document and schedules a FastAPI background task. That task resolves the originating agent, creates a prompt telling it to read the proposal and answers, invokes its integration, records completion/failure and deletes the temporary prompt. See [app.py](../repo/agency/app.py), lines 437–517 and 2526–2584.

The integration registry separates Agency's records from the tool used to execute them. Its contract is a `RunResult` containing exit code, complete stdout/stderr and duration, plus native-file identity parsing/writing. It is not an event stream or session API. [integrations/__init__.py](../repo/agency/integrations/__init__.py), lines 12–94, defines the contract. For Codex, `run()` executes `codex exec --yolo <prompt>` with the agent directory as cwd and captures the result. The Claude implementation similarly starts a new `claude ... -p` process. [codex.py](../repo/agency/integrations/agency/codex.py), lines 15–53; [claude_code.py](../repo/agency/integrations/agency/claude_code.py), lines 68–89.

A third, supplied **template path** matters: the setup skill can generate a project-specific shell dispatcher and a tmux session. The shell template includes backgrounded parallel invocations and a coordinator routine for outstanding proposal feedback. The tmux template starts separate interactive Claude sessions. These are concrete scripts for a coding agent/operator to generate and run, not routes or services automatically wired into the core Python scheduler. Their behavior must be credited separately from the installed dispatcher. [dispatch-templates.md](../repo/skills/agency-setup/references/dispatch-templates.md), lines 91–115, 175–240, 243–259 and 359–440. The setup instruction limits the generated team to one code-editing builder, even though multiple observation agents can run together.

Workspace plugins are a different abstraction again. They describe tmux scripts, IDE configuration, external applications or chat-channel metadata. They do not turn the dashboard into those applications. The chat workspace stores platform/channel/notes and renders a summary. It has no bot transport, message history, subscriptions or delivery function. [workspaces/chat.py](../repo/agency/workspaces/chat.py), lines 6–33. The tmux plugin returns a shell launch command, while the implemented workspace routes list plugins and edit their allowlisted configuration files. The template renders a “Launchable” label rather than a launch action, confirming the boundary. [workspaces/tmux.py](../repo/agency/workspaces/tmux.py), lines 32–44; [app.py](../repo/agency/app.py), lines 2971–3058; [workspaces.html](../repo/agency/templates/workspaces.html), lines 24–35.

## Agent definition and lifecycle in depth

### Definition, creation and identity

An agent is primarily a configured **name → directory → integration** mapping. A string entry inherits the group's default integration. A dict can carry integration metadata and an absolute external directory. The latter lets several groups refer to an existing agent directory, but does not create a host-independent identity or execution handle. See [config.py](../repo/agency/config.py), lines 6–35 and 57–60.

The create endpoint normalizes the agent name and adds it to the group. It creates the directory and any missing generic instruction and memory files. It does not start a process or allocate a conversation. It also does not copy a specialist profile, assign a ticket, or connect channels. See [app.py](../repo/agency/app.py), lines 2069–2107. The operator edits the role body and display metadata. Codex keeps instructions in `AGENTS.md` and display metadata in `.agency-meta.yaml`. Claude keeps YAML frontmatter directly in `CLAUDE.md`. See [codex.py](../repo/agency/integrations/agency/codex.py), lines 21–31; [integrations/__init__.py](../repo/agency/integrations/__init__.py), lines 111–163; and [claude_code.py](../repo/agency/integrations/agency/claude_code.py), lines 26–66.

Group initialization and agent creation are distinct operations: initialization creates shared record directories and empty agent directories, while auto-detection scans recognized identity files and replaces the configured list when it finds agents. Thus a directory alone is not a functioning specialist, and detection is a filesystem indexing operation rather than agent discovery over a network. [app.py](../repo/agency/app.py), lines 1838–1906. A stable agent is the named record and its files. A scheduled task is a prompt/rule pair. An invocation is an external process; and peer-role subagents are delegated inside that process's tool. Agency stores no durable session entity linking these concepts.

There are two ways to reason about an agent's specialization. The application permits arbitrary roles through editable text. Separately, the shipped setup skill proposes project-specific agents after inspecting project context and writes instructions, memory, prompts and tmux/dispatch scaffolding. That is a real supplied onboarding workflow, but it is interpreted by a coding agent, not executed as an Agency server orchestration service. Its default policy is a lean team of three to five, with **only one code-editing builder**. That differs materially from Wingman's concurrent backend/frontend/mobile/test workers. [skills/agency-setup/SKILL.md](../repo/skills/agency-setup/SKILL.md), lines 17–66, 84–140. This assessment reads that skill as product source. It does not invoke it.

### Execution and tool/permission model

The integration interface provides whole-run invocation and identity I/O. Native tools own actual tool execution, model context, changes and any internal subagents. Agency does not define a common tool registry, per-role tool capabilities or per-session sandbox. Codex's execution path explicitly uses `--yolo`; Claude's uses `--dangerously-skip-permissions`. Roles can include textual boundaries, but those instructions are not enforced by an Agency permission layer. This is an architectural distinction for Wingman, whose organizational approvals should not be confused with whether a subprocess has technical authority to act. [codex.py](../repo/agency/integrations/agency/codex.py), lines 33–53; [claude_code.py](../repo/agency/integrations/agency/claude_code.py), lines 68–89; [_observation-system-steps.md](../repo/agents/shared/prompts/_observation-system-steps.md), lines 127–140.

The custom script integration substitutes prompt/directory placeholders into a configured shell command and executes it locally. It can adapt a non-native runner, including one that performs remote work, but anything beyond the command invocation is supplied by that script. SDK mode is different: it advertises `supports_execution = False` and returns a non-success result if asked to run. Its value is registering externally managed agents that already write the file contract. It is not an embedded agent SDK or remote worker scheduler. [script.py](../repo/agency/integrations/agency/script.py), lines 15–33 and 62–91; [sdk.py](../repo/agency/integrations/agency/sdk.py), lines 14–20 and 53–59.

### Routing, scheduling and concurrency

Human navigation and config choose the group. Proposal `origin_agent` chooses who should receive the decision. In the web executor, integration resolution checks on-disk identity detection before configured integration metadata. The scheduler resolves the explicitly normalized integration name. This means the two paths are not completely identical when native files and configured tool disagree. [app.py](../repo/agency/app.py), lines 318–336, 458–497; [run.py](../repo/agency/dispatch/run.py), lines 85–88 and 170–184. That is worth standardizing if Agency becomes a shared Wingman control plane.

A concrete consequence is the custom-script/file-contract collision: both Script and SDK use `agent.md`, Script deliberately never auto-detects, and SDK detects that file. With that ordinary layout and no higher-priority native identity, the web resolver selects non-executable SDK before consulting a configured `script` integration, while periodic dispatch honors the configured Script. This is an inferred inconsistency from the actual detection branches, not an exercised failure. [script.py](../repo/agency/integrations/agency/script.py), lines 14–33; [sdk.py](../repo/agency/integrations/agency/sdk.py), lines 14–27; [integrations/__init__.py](../repo/agency/integrations/__init__.py), lines 182–192. A shared execution-resolution function should precede integrating the two launch paths.

Daily rules allow execution in a window around an `at` time and create a dated marker; interval rules compare a persistent marker's mtime against an `Nm`/`Nh` duration. The timer itself periodically invokes the cycle, with native systemd/launchd configuration. Windows timer installation is explicitly unimplemented. The generic cycle skips `condition` rules and expects a separate group dispatcher for those conditions. [run.py](../repo/agency/dispatch/run.py), lines 20–48, 95–152; [install.py](../repo/agency/dispatch/install.py), lines 16–57, 95–146 and 189–232.

Within a cycle, groups, agents and rules are nested loops, and integration execution blocks until finished. There is no configured parallelism, cross-agent work dependency or task claim protocol. Web background tasks and external runners can independently operate at the same time, but no common agent-level lock, lease or workspace arbitration coordinates those paths. This is not evidence that simultaneous work is impossible. It means Agency does not make concurrent development safe or tractable as an organizational capability. A shared directory exposes data. It does not establish ownership of code changes.

The generated shell dispatcher is a more capable concurrency primitive than the Python cycle: `run_agents_parallel()` starts `run_agent` in the background, saves PIDs and waits for them. Its output is redirected directly to `.out/.err` files, so those files can grow during execution. This differs from Python's post-run writes. However, it is a template with event-handler placeholders, no durable run IDs or ownership claims, and no browser terminal/event stream. Its optional coordinator reads `status: feedback` proposals and prompts a coordinator to dispatch missing reviewers. The standard shipped observation instructions instead require all peer feedback within one run. These are two supplied coordination patterns, not one consistently enforced state machine. [dispatch-templates.md](../repo/skills/agency-setup/references/dispatch-templates.md), lines 91–115, 175–259, 262–286; [standard steps](../repo/agents/shared/prompts/_observation-system-steps.md), lines 93–125.

The daily limit counts produced `.out` files for that group/day. It is a run-count limit, not a monetary/token budget or a global concurrency quota. It applies in the scheduler path. Decision-triggered background execution follows its own path and does not consult that scheduler limit. [run.py](../repo/agency/dispatch/run.py), lines 71–83, 112–115; [app.py](../repo/agency/app.py), lines 465–497.

### Persistence, resume and continuity

Identity, memory, observations, proposals, answers and completed run outputs survive restarts as files. A later invocation can reconstruct context by reading them, provided its instructions tell it to. The supplied product role explicitly reads personal/shared memory at session start and writes durable corrections/preferences back to those files. [product/CLAUDE.md](../repo/agents/product/CLAUDE.md), lines 59–65.

Configuration replacement is atomic, but decision/observation/memory writes are ordinary read/modify/write operations, with no shared transaction across proposal status, answers and execution status. Concurrent background runs or human/agent edits therefore have no source-level lost-update protection. This follows from the write paths; no race was exercised. [app.py](../repo/agency/app.py), lines 43–52, 421–434, 2566–2582 and 2956–2968. For Wingman's many independent writers, an execution claim and versioned coordination record would be needed even if Markdown remains the human-readable representation.

Agency itself does not load those documents into a context envelope or persist the CLI's conversation identity. The Codex command lacks a resume operation, session/thread identifier, fork ancestry or compaction control. Therefore **knowledge continuation is file-mediated**, while **conversation continuation is delegated to the external tool/operator and not implemented by Agency's run contract**. An output log gives attribution and evidence after a run. It does not restore an interrupted tool operation.

The so-called subagent control is also a filesystem/dashboard distinction: toggling moves the directory between the group root and `_subagents/` and changes list membership. It is not a runtime spawn, supervisor/child relationship or cancellation tree. The observation prompt separately instructs the current coding tool to spawn peer-role subagents and collect feedback during the same run. That behavior depends on the selected tool following the prompt and supporting delegation. [app.py](../repo/agency/app.py), lines 2299–2335; [_observation-system-steps.md](../repo/agents/shared/prompts/_observation-system-steps.md), lines 93–116.

### Interruption, recovery, completion and retirement

External subprocess timeouts become exit code 124 in the native integrations. Their implementations return an empty stdout and a timeout message rather than preserving partial output as a live run record. The scheduler writes output/error files after the integration returns. It logs failure but has no persisted retry queue, backoff or interrupted-run reconciliation. It touches scheduling markers after `_run_agent()` returns, so the marker means the scheduled dispatch attempt was processed. It does not certify successful work. [codex.py](../repo/agency/integrations/agency/codex.py), lines 33–53; [run.py](../repo/agency/dispatch/run.py), lines 143–152 and 194–203.

The caller also marks a rule processed after some normal early returns. These include a missing agent, missing prompt, or non-executable integration. `_run_agent()` does not catch an exception around `integration.run()`. A missing CLI can therefore abort the cycle before later agents run. Web decision execution has a separate exception boundary that records failure.

Agency exposes a timeout setting. It does not expose a process handle or cancellation endpoint. Python's subprocess timeout limits the immediate invocation. Agency has no explicit cancellation tree for descendant processes. See [run.py](../repo/agency/dispatch/run.py), lines 143–152 and 155–203; [codex.py](../repo/agency/integrations/agency/codex.py), lines 37–53; and [app.py](../repo/agency/app.py), lines 474–517.

Web decision execution has a more explicit `pending → running → complete/failed` record. Exceptions produce failed status. A retry endpoint finds the linked proposal's originating agent, resets the fields and launches the execution again. It does not require the currently stored execution to be failed, and the visible code does not establish idempotency or a durable execution claim. Web background work is tied to the serving process rather than a durable queue. A restart after setting `running` has no startup reconciliation in the inspected application. [app.py](../repo/agency/app.py), lines 437–517, 2649–2682 and 3061–3075.

Completion is inferred from process exit code unless the decision already contains `complete` or `failed`. There is no independent verifier requiring tests, acceptance scenarios, integration evidence or human delivery acceptance. The same launch path receives **all** answers, including deferred or rejected ones, and the prompt instructs the agent how to interpret them. Consequently the governance semantics are partly model-mediated: the server dispatches the agent to close the loop rather than enforcing an approval-only execution branch. [app.py](../repo/agency/app.py), lines 443–455, 501–511 and 2576–2582.

Retirement removes the agent from configuration, optionally deletes its local directory and avoids deleting externally shared directories. Group deletion removes the registry entry but retains files. These are configuration/file lifecycle operations, not termination of an active process or archival of a resumable conversation. Renaming similarly changes config/directory, without migrating historical observation attribution or scheduled rule keys in that endpoint. [app.py](../repo/agency/app.py), lines 1817–1835, 2110–2178.

## Coordination: a concrete source-level journey

Consider a reviewer finding a regression and proposing a fix. This is a reconstruction of the supplied code/instructions, not a live execution trace.

1. A timer fires. `run_dispatch_cycle()` selects a due prompt for a configured reviewer. `_run_agent()` finds `shared/prompts/<prompt>.md`, the reviewer directory and its integration, invokes it, and later stores captured logs. [run.py](../repo/agency/dispatch/run.py), lines 57–203.
2. The example review prompt tells the agent to read shared memory, inspect six hours of commits and write severity/file/line/suggested-fix observations. It does not create technical tickets. [review-recent.md](../repo/examples/code-review-team/shared/prompts/review-recent.md), lines 1–15.
3. The standard observation instructions tell agents to scan floated findings, deduplicate their own findings, link related findings from peers, and write timestamped Markdown records. With at least two converging observations they draft a proposal, subject to a prompt-level maximum of three nonterminal proposals. These rules are **instructions**, not validation enforced by the Python application. [_observation-system-steps.md](../repo/agents/shared/prompts/_observation-system-steps.md), lines 7–91.
4. The agent is instructed to read relevant peers' role definitions, spawn their expertise as subagents, synthesize returned feedback and finalize proposal questions in the same run. The record is a synthesized proposal document, not a persistent group-room exchange among separately scheduled workers. Same source, lines 93–125.
5. The human sees actionable proposals and floated findings on the dashboard. The proposal page resolves linked observations and existing decision answers. Answer submission writes `shared/decisions/<slug>.md`, updates the proposal to `decided` and schedules `execute_decision()` for `origin_agent`. [app.py](../repo/agency/app.py), lines 2338–2379, 2465–2584.
6. The executor prompts the origin agent to read the decision/proposal, interpret approval/defer/reject/other answers and close the loop. It records outcome from the process result. The decision page follows links back through the proposal to observations. A retry button can resubmit execution. [app.py](../repo/agency/app.py), lines 437–517 and 2599–2682.

This is a useful **evidence-and-decision chain**. It does not yet implement **request → ProductMaster discovery → TechMaster tickets → specialist collaboration → TestMaster acceptance**. The single origin agent is the execution target. There is no decomposition/ownership/dependency transition creating work for a team.

One integration concern is visible in the generated execution prompt: it spells paths as `agents/shared/...` while the selected process cwd is the agent directory (or group fallback). The scheduler examples also use their own relative-path conventions. The actual runner may infer or find the intended files, but the application does not consistently pass absolute artifact paths. A Wingman adapter should pass explicit canonical references rather than assume layout-dependent path interpretation. This is a source-level concern, not a demonstrated runtime failure. [app.py](../repo/agency/app.py), lines 443–446 and 461–497.

The CLI decision path has an additional boundary: it writes the answers and pending execution state but does not invoke `execute_decision()` in `cmd_decide()`. Thus browser decision auto-dispatch and CLI decision persistence are not equivalent behaviors at this revision. [cli.py](../repo/agency/cli.py), lines 269–357. An external dispatcher could consume the decision, but the generic periodic runner does not implement a pending-decision queue.

The records provide semantic dependencies (`linked_observations`, `observations`, `proposal`, `origin_agent`) rather than executable task dependencies. A proposal can point to evidence and the human answer can return to its originator, but no queue turns those links into a ready/running/blocked task graph. Similarly, a floated observation asks peers to notice a finding through subsequent file reads. It does not deliver a message or wake the intended peer. These distinctions explain why Agency's document cooperation earns partial credit without being treated as Wingman's agent chat and shared tracker.

## Major capabilities beyond Wingman's described product

### Continuous organizational sensing and proposal governance

Agency supports ongoing role-based observation of an environment. Agents can combine weak signals into a proposed action. A persistent human-governance pipeline records the resulting decision. Examples cover research, content opportunities, recent-code review, documentation, and security scans. Business teams can use this model without turning every finding into a coding ticket. See [examples/content-team](../repo/examples/content-team), [examples/code-review-team](../repo/examples/code-review-team), and the [observation instructions](../repo/agents/shared/prompts/_observation-system-steps.md), lines 7–125. Wingman's required supervision concerns ongoing product development.

The value for Wingman is an upstream opportunity/risk inbox for agents to surface things the human did not request. Its integration cost is maintaining a distinction between an observation, a product decision and an assigned technical task. Automatically treating proposals as tickets would lose the very evidence/convergence semantics that make the pipeline useful.

### Heterogeneous tool and external-agent governance

Wingman is specifically an organization of Codex agents. Agency's product model permits mixed CLI tools, custom scripts and externally managed agents under one identity/memory/decision interface. Native files are respected through integration-specific parsers and sidecars, instead of requiring every tool to adopt a synthetic instructions format. In addition to Codex/Claude, actual adapters invoke Gemini, Aider, Goose, OpenCode and Pi through their own command forms. This is implemented adapter breadth, not proof those installed tool versions were exercised. [integrations/__init__.py](../repo/agency/integrations/__init__.py), lines 51–77, 217–239; [integrations.yaml](../repo/agency/integrations/integrations.yaml), lines 1–10; [gemini.py](../repo/agency/integrations/agency/gemini.py), lines 33–54; [aider.py](../repo/agency/integrations/agency/aider.py), lines 33–53; [goose.py](../repo/agency/integrations/agency/goose.py), lines 33–54; [opencode.py](../repo/agency/integrations/agency/opencode.py), lines 31–52; [pi.py](../repo/agency/integrations/agency/pi.py), lines 31–52; [sdk.py](../repo/agency/integrations/agency/sdk.py), lines 14–20, 53–59.

This could let Wingman coordinate specialist research or automation tools beside its Codex workforce. The tradeoff is a lowest-common-denominator run result. Fine-grained steering, event streaming, permissions, resume and cancellation would require a richer adapter contract rather than merely registering more integrations.

### Human-editable operational knowledge as a management product

Agency exposes agent roles, memory, prompts, documents and schedules for direct editing in the management interface. This is more than display polish: the operator can alter the standing team's remit and recurring investigative behavior without building a new code-defined workflow. [app.py](../repo/agency/app.py), lines 2236–2262, 2797–2918 and 2921–2968.

Wingman could use this as an organization configuration/knowledge editor. To connect it to continuing conversations, edits would need versioning and a defined application point: next invocation, explicit context refresh or live steering. Agency currently changes source files for future reads. It does not prove an already running worker incorporates the change.

## Distinctive mechanisms and their limits

**Signal convergence with explicit provenance.** Agents can invite related observations, link peer findings, and combine them into a proposal. The dashboard follows the observation, proposal, and decision chain. This supports teams with different standing areas of expertise. A lightweight file contract connects evidence to decisions. Duplicate detection, convergence thresholds, peer feedback, and proposal caps remain prompt rules. Enforcement and consistency across tools depend on agent behavior. See [standard steps](../repo/agents/shared/prompts/_observation-system-steps.md), lines 7–125, and [app.py](../repo/agency/app.py), lines 2402–2440, 2465–2523, and 2599–2646.

**Native identity formats and sidecar metadata.** Agency preserves each tool's native instruction format. A Codex agent keeps `AGENTS.md` and separate display metadata. One dashboard can index these different file contracts. Filesystem detection and configuration precedence can still disagree. A shared directory alone cannot provide a universally addressable agent identity. See [integrations/__init__.py](../repo/agency/integrations/__init__.py), lines 118–170 and the detection registry; [codex.py](../repo/agency/integrations/agency/codex.py), lines 23–31; and [app.py](../repo/agency/app.py), lines 318–336.

**Temporal hygiene for an agent inbox.** Observations and proposals carry TTLs. Reading their lists checks expiry and archives stale items, while dashboard statistics identify a rough observation-to-proposal bottleneck. This prevents an indefinite accumulation of obsolete weak signals, which is a real issue for continuously running agents. Expiry is lazy, triggered by reads. It is not evidence that an agent resolved the issue. The bottleneck is a count heuristic, not causal workflow analysis. [app.py](../repo/agency/app.py), lines 530–565, 592–618 and 625–666.

**Separation of management, execution and viewing environments.** Integration plugins execute tools; workspace plugins describe the environment where a human uses them; files hold durable organizational records. This decomposition is useful if Wingman wishes to manage both local and external runners without rebuilding their IDEs. Its current implementation stops short of a live cross-runner session protocol, so “workspace” should not be read as an embedded coding session. [integrations/__init__.py](../repo/agency/integrations/__init__.py), [workspaces/__init__.py](../repo/agency/workspaces/__init__.py), [app.py](../repo/agency/app.py), lines 2971–3058.

These are distinctive choices within this checkout. The assessment does not claim first invention or uniqueness across the market.

## What Wingman could reuse, adapt and still needs

Reuse directly as concepts or a limited component:

- The observation/proposal/decision document contract.
- Agent-native identity adapters.
- Group-scoped directory/profile pages.
- Memory/prompt editing.
- Explicit human question types.
- Native periodic wake mechanisms.
- Traceable decision records. These would be valuable even if Wingman keeps its own Codex runtime and task tracker.

Adapt before using as Wingman's control plane:

- Replace whole-process `RunResult` with durable run/session/event identifiers.
- Distinguish stable agents from profile instances and ephemeral tasks.
- Unify scheduler and decision execution policies and integration resolution.
- Add idempotent execution claims, versioned shared writes, durable queue/recovery and safe per-workspace concurrency.
- Pass canonical artifact paths.
- Enforce authorization outside prompt text.
- Make completion depend on task/acceptance evidence. The built-in Codex invocation is a real execution adapter, but insufficient for Wingman's detailed session lifecycle and host routing. The separate parallel shell/tmux templates are useful prototypes for local process launching, not substitutes for those guarantees.

Build as substantial new product behavior:

- Telegram Butler and correlated clarification routing.
- Portfolio intake and project-continuation decisions.
- Distinct ProductMaster/TechMaster/TestMaster responsibilities.
- Shared technical tickets/dependencies/ownership.
- Persistent chat rooms and cross-host messaging.
- Mac/Endeavour worker registration/placement.
- Integrated verification and acceptance delivery.
- Per-agent current/recent/next/blocker briefings.
- A live per-agent coding workspace with approvals, steering, cancellation, resume/fork/compact/archive and usage/budget controls.

The practical adoption boundary is therefore **Agency as an organizational observation/governance surface over Wingman agents**, or as a design reference for those surfaces. Adopting it as the full organization would still leave most of the development coordination runtime to implement. Its clean, inspectable file model helps bootstrap a small personal organization, but does not replace the distributed work and lifecycle guarantees that Wingman needs when several specialists share products across machines.
