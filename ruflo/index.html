Ruflo assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/ruvnet/ruflo . Local checkout: research/ruflo/repo. Examined commit: bf5d71a1852071660b3489a0ff02d998676200e5. Root package identifies itself as claude-flow 3.71.4; Ruflo and Claude Flow names coexist. This report assesses the checked-out source, not the health of a published package or hosted service.

Verdict

A substantial coordination, memory, policy and execution toolkit, with a useful terminal workbench; not a ready-made Wingman organization. Ruflo can really launch independent Claude Code and Codex subprocesses through its dual-mode orchestrator. It also has durable team mailboxes, task records, mission planning, a console, periodic background workers, federation, and a separate hosted-team service implementation. Those are significant reusable pieces.

The important qualification is that these capabilities belong to different execution and persistence paths. agent_spawn normally creates metadata, agent_execute makes a model request, team_spawn returns a host spawn plan, the dual-mode runtime launches coding processes, and console missions hand work to the primary Claude session. They must not be collapsed into one persistent agent organization. The durable mission API explicitly refuses execution admission and resume because its independent executor has not been implemented. A console autopilot exists, but its liveness depends on a running host session. No Telegram Butler, automatic organization-wide project intake, standing ProductMaster/TechMaster pair, connected web/mobile executive dashboard, or complete durable per-agent session control was established.

For Wingman, the best use is selective infrastructure reuse or design reference, especially the policy/receipts boundary, team communication bus, bounded worktree execution and honest observation model. Adopting the whole repository would require reconciling multiple stores, host-specific integrations and optional native/cloud dependencies before building the product organization above them.

Architecture and actual execution model

Entry points and boundaries

The root CLI launcher, lines 1–11, imports the bundled v3 CLI entry point. The package manifest, lines 1–52 and 71–110, identifies the umbrella package and packaged CLI/shared/guidance components; its dependencies include Codex, MCP, security and federation components alongside optional AgentDB, vector and agentic-flow integrations. This is a large TypeScript/Node monorepo with plugins, not one small daemon owning every concept.

CLI commands such as agent spawn call the local tool registry. mcp-client.ts, lines 255–288, looks up the tool, obtains a policy decision, invokes the handler and optionally screens tool results. Calling an MCP-named tool from this path does not imply a remote server or running executor. The agent registry, lines 17–87 and 330–440, persists .claude-flow/agents/store.json, model/role/configuration and swarm membership. Its spawn path contains no process launch.

There are several materially different meanings of “agent”:

Evidence: agent execution core, lines 257–283 and 615–687; team tools, lines 1–11 and 100–129; dual-mode orchestrator, lines 157–278; Mission Control, lines 1–8; managed tools, lines 1–18; AI Team server, lines 84–138.

The hive worker consumer, lines 142–188 and 223–266, reads the oldest pending hive task and selects an idle hive worker. It assigns the task and runs Claude with a Ruflo-aware MCP configuration. It then records completion or failure. This closes a queue-to-execution gap for that command. It does not make every registered hive worker a standing process. The queue read, pending check and assignment are separate tool operations, so they should not be assumed to constitute a globally atomic distributed claim.

Persistence and observation

Basic agent and task stores use synchronous JSON read/replace operations. The task implementation, lines 35–76, does not establish a transactional database despite tool descriptions referring to .swarm/memory.db. Tasks contain status, progress, assignees, tags and results; ordinary task records do not contain dependency edges. Dependency semantics live in mission plans, the team bus and dual-mode worker graphs instead.

The newer mission store, lines 1–18, 60–71 and 152–217, has a stronger contract: per-mission locks, append-only newline events, fsync, replay, atomic snapshots and crash-tail handling. MissionService, lines 134–155 and 200–238, gives deterministic request-scoped IDs, request deduplication, expected-revision checks and plan digests. However, admit and resume return executor-unavailable at lines 220–225. Durable planning is implemented; durable independent mission execution is not.

The terminal console reads bounded snapshots rather than assuming missing files mean zero activity. Its snapshot reader, lines 1–5 and 66–130, joins agents, tasks, claims, hive, daemon, learning, federation and managed observations. Its separate console mission ledger, lines 14–18 and 50–97, uses per-project host-store keys and a best-effort .claude-flow/console/mission-ledger.json mirror. It keeps the newest 20 missions. This is not the same authority as the durable mission event store. Wingman integration must choose canonical entities and explicitly reconcile these read models.

Agent definition and complete lifecycle

Definition, creation and identity

A plugin agent such as coder.md, lines 1–22, is a model/persona/instruction definition. It is a useful specialist profile, not evidence of an active process. The generic registry accepts an agent type, optional custom ID/display name, arbitrary configuration, domain, task and model, then determines model routing and saves an idle record. agent-tools.ts, lines 285–306 and 330–440, also registers membership in the requested or most recently created swarm and refuses membership beyond its live-agent cap. This capacity check counts records, not OS or native-host liveness. A default health of 1.0 at registration is likewise not evidence that useful work ran.

Team creation is distinct. team-tools.ts, lines 73–129, creates metadata and registers named members, returning a native-host spawn plan. The lead still has to perform the host spawn. A dual-mode WorkerConfig, lines 31–43, instead directly describes a real process run: platform, role, prompt, model, dependencies, cwd/worktree, read-only flag and capability envelope. Its supplied ID indexes in-memory worker results. It is not automatically the same identity as an agent_spawn record or a native conversation ID.

Execution, tools and permissions

agent_execute retrieves the registered configuration, rejects terminated IDs, chooses the persisted model and instructions, marks the record busy, and makes a provider request. agent-execute-core.ts, lines 615–687, establishes that path. The Anthropic request at lines 257–283 sends a system prompt and one user message. It does not attach coding tools or a native conversation transcript. A successful response can be useful analysis or code text, but is not an independently acting coder.

In contrast, dual-mode execution, lines 205–278, launches claude -p or codex exec, selects read-only/workspace-write Codex sandboxing, sets cwd and worker environment, closes stdin, captures bounded stdout/stderr, and resolves on process exit. The native coding host supplies its own tools and permissions. The dual CLI, lines 61–80, requires enabled automation, bounds requested concurrency/time by configured ceilings and turns on policy preflight. The underlying class can also be constructed directly, so these CLI defaults must not be generalized to every embedding.

mcp-client.ts, lines 270–288, is a concrete local Ruflo-tool authorization boundary. policy-runtime.ts, lines 857–915, validates worker capability envelopes and resolves policy roots; policy engine, lines 33–47, defaults to legacy. Thus policy code exists, but enforcement depends on configured mode and native-host integration. It does not magically authorize or contain every shell command a host can run.

Routing, dependencies and concurrency

Registry model routing considers explicit model/provider choices, task-based enhanced routing and role defaults. agent-tools.ts, lines 171–280, includes deterministic-codemod hints, embeddings and fallback heuristics. Routing chooses a model, not a Wingman project or accountable project leader.

Dual-mode execution builds dependency levels, rejects cycles and validates writer ownership, then partitions each level into batches with separate total-worker and writer caps. A batch runs with Promise.all; later work can be skipped or cancelled after failures. See orchestrator, lines 336–387 and 432–482. CodexWorktreeCoordinator, lines 43–90, prepares named branches/detached worktrees, refuses a dirty starting repository by default, and records assignments. Separate worktrees reduce file conflicts; acceptance and integration still require an explicit integration owner and checks.

Persistence, resume and scheduling

Agent records, task records and memory are durable files/stores. The direct-call path keeps latest result and a bounded execution history, re-reading current metadata at completion so a concurrent termination/update is not overwritten (execution core, lines 832–861). The generic session snapshot schema, lines 24–65, holds memory/tasks/agents. Restoring those records is not resuming a native model conversation or restarting a lost coding subprocess.

Dual-mode worker/process maps are not a restart-durable supervisor. The Codex loop runner, lines 116–180 and 218–222, starts with a fresh iteration state and invokes new codex exec runs with a continuation prompt. It persists progress/output and stops on a completion file, error or configured limit, rather than preserving one native Codex session. Lines 203–207 can label an exhausted loop completed even without a completion marker. This status is a runner outcome, not accepted product delivery.

The daemon offers real periodic code mapping, audit, optimization, test-gap and memory jobs. The supervisor registry, lines 1–39, prevents every worktree from independently scheduling the same recurring headless spend. This is valuable execution hygiene, but it supervises recurring jobs for a repository, not the project portfolio and human product questions.

Console autopilot has a journaled step machine and a one-minute live tick. ap-live.ts, lines 1–6 and 96–113, explicitly says it is not a standalone scheduler: liveness comes from the session staying up and its /loop re-arm. The durable mission service separately refuses admission/resume. Persistent records, recoverable UI state and independent background execution are therefore three different guarantees here.

Steering, interruption, cancellation and failures

Console steering can submit a visible prompt, call native SendMessage, append task guidance or broadcast into hive/channel state. wf-send.ts, lines 75–107, documents their distinct delivery semantics: task guidance is seen only when read, hive broadcast does not interrupt a worker, and a proposal does not compel execution. The session workspace open action, line 247, explicitly reports that no opener is wired. Inspection should not be mistaken for a universal resume/steering endpoint.

Generic task_cancel updates the record and frees tracked assignees. It does not establish termination of an underlying native worker (task-tools.ts, lines 541–590). Console mission pause similarly means no more handoffs. An already handed-off task finishes first (mission-specs.ts, lines 108–115). The headless executor does have real cancellation, tracks processes and escalates termination; headless-worker-executor.ts, lines 886–938 and 1441–1467, includes process-group handling for descendants. The simpler dual-mode timeout at orchestrator lines 264–276 sends SIGTERM and reports failure. These guarantees should not be conflated.

The hive consumer's runner, lines 159–185, also sets a SIGTERM timeout and waits for child close. Its result includes native session ID and reported spend when Claude returns them. This improves traceability for one queued execution, but no automatic crash-resume of that native session or equivalent process-group cancellation is established by this path.

Direct model execution has a bounded fallback chain for retryable errors (execution core, lines 689–721). Generic task retry, lines 602–650, clones the original specification into a new pending task and preserves history. It is a requeue, not automatic worker recovery. Autopilot keeps failure counts/backoff and parks work for once/deny answers, with a failure budget of five (step machine, lines 17–47 and 98–135). An interruption or API transport uncertainty still requires inspecting actual runtime/provider state before retrying mutations.

Completion, acceptance, retirement and cleanup

Dual-mode completed means process exit zero (orchestrator, lines 188–199 and 269–276). Generic task completion records a result and releases assignees (task-tools.ts, lines 306–348). Neither inherently validates the product. Console verification gates, lines 98–124, are stronger: they preserve exit codes and distinguish failed, unknown and verified outcomes, resetting evidence relevance after a new dispatch. The meaning of the configured commands remains the operator's responsibility.

Registry termination marks an agent terminated and optionally promotes/discards its memory branch (agent-tools.ts, lines 566–601). It does not imply a native session was archived. The worktree coordinator, lines 112–137, integrates branches separately and removes worktrees without forced removal, retaining failures and retaining the registry while anything remains. That is a useful explicit cleanup boundary. Full organizational retirement—reassigning tickets, closing room participation, preserving a human-readable history and archiving a native conversation—remains to implement.

Coordination mechanics and a traced request

Ruflo combines several coordination mechanisms rather than a single chat/tracker. Team mailboxes support named direct handoffs and broadcasts with filesystem persistence, locking and atomic writes (team-tools.ts, lines 4–11). Generic task state records responsibility, while mission ledgers and dual-mode graphs add dependencies. Swarm/hive metadata records topologies, proposals and votes; policy decisions determine action admission. Network federation carries authenticated envelopes. The console Room merges these observations with human speech/actions, but is not itself a durable conversation among all organizational members.

The following is a static implementation trace, not a live run: entering a feature goal in console Mission Control and asking it to proceed.

  1. Goal interpretation: setGoal, lines 39–47, retains the goal text, chooses a profile unless manually selected and calls the pure planner. The GOAP library, lines 38–60 and 83–103, selects actions for profile/rigor. It does not conduct product discovery simply by computing this graph.
  2. Reviewable plan and task creation: mission-create.ts, lines 128–144 and 248–269, builds the mission-create/plan/task CLI sequence as one confirmed action and records returned task IDs. Its retry/read-back contract at lines 4–15 checks late task-creation successes and cancels partial creation on failure. Every task receives mission/node tags. The console keeps the dependency edges.
  3. Shared durable planning: mission_create/mission_plan use the same MissionService, lines 134–155 and 200–208, as other adapters. IDs deduplicate requests; plan writes check expected revision and graph validity. MissionStore, lines 152–217, locks, appends events and updates snapshots. This still executes no coding work.
  4. Ready-task selection: derive/nextTask, lines 59–85, reads the generic task store, checks dependencies and refuses another ordinary handoff when a task is running or failed. The console's dependency graph matters because ordinary task records lack dependency fields.
  5. Actual execution handoff: mission-specs.ts, lines 57–97, dispatches the instruction through the host's prompt submission. The primary Claude session does the work and is instructed to report task_complete or failure. A role name in a plan does not itself spawn a separate native agent. Mission Control's contract, lines 1–8, states this explicitly.
  6. Evidence and next step: The console reads updated task state, records ordered local ledger events, and advances under confirmed or opted-in auto-run. mission-verify.ts, lines 81–124, executes configured gates and records their exit-code evidence. The durable mission API is not thereby admitted to an independent executor; its separate execution state remains constrained as described above.
  7. Human decision or interruption: Steering is a visible prompt/aside, policy-sensitive actions ask through console controls, and autopilot can park a question. Pausing stops subsequent handoffs. It does not retract work already running. There is no automatic routing from this point through a management room and Telegram Butler.

An alternative real multi-process trace is dual run: dual-mode CLI, lines 61–115, resolves automation/template configuration, prepares worker specifications and creates the orchestrator; runCollaboration, lines 336–395, initializes shared memory, runs bounded dependency levels and collects results. That path supplies independent coding processes, but does not automatically populate every console mission/team/hosted-board entity with a shared identity.

The ordinary agent_logs drill-down is especially limited: agent-tools.ts, lines 1012–1056, explicitly returns synthetic creation/last-result entries because structured per-agent activity logging is not yet wired. Both can carry the creation timestamp. Those rows should not become Wingman's durable activity timeline; native transcript observations and meaningful accomplishment summaries need their own model.

Substantial capabilities beyond Wingman's stated product

Policy envelopes and auditable admission

Ruflo has a dedicated policy engine, budget/approval state, signed capability-envelope handling and a common tool-dispatch gate. policy-runtime.ts, lines 647–678 and 857–915, exposes evaluation, mode/rule/budget/approval operations and verifies worker context before authorization. The engine, lines 25–47 and 81–99, owns policy state and monotonic configured-mode elevation. These are more explicit governance primitives than Wingman's product description demands. They could constrain tool/network/spend authority across specialists and preserve reasons for admission/denial. Integration needs a trusted root, deliberate legacy/observe/enforce rollout and native-host controls; tool registration alone proves neither authorization nor containment.

Retrieval, learning and bounded self-improvement

The memory system goes beyond appended project notes. Hybrid retrieval, lines 1–11, 85–110 and 130–145, combines normalized BM25 and dense similarity with diversity-oriented retrieval. Memory tools, lines 698–890 and 1458–1477, distinguish retrieval backends and can report hash/mock fallback rather than claiming real ONNX embeddings. This can improve cross-session reuse, but retrieved text is evidence/context, not automatically an accepted directive or product truth.

The harness flywheel, lines 1–21 and 41–73, harvests a retrieval corpus, selects candidate configurations on training data, checks held-out/anchor/drift/replay/receipt/canary conditions and emits evaluation receipts. Explicit promotion is separate. The managed learning loop, lines 25–62, only accepts authenticated measured outcomes in scope and returns advisory recommendations without changing defaults. These mechanisms offer measurable adaptation, but their utility depends on meaningful evaluation data and trusted verifiers. They are not proof of autonomous general learning or better product delivery.

Speculative memory isolation

SwarmMemoryBranches, lines 13–39 and 107–123, connects optional agenticow copy-on-write branches to an agent lifecycle: fork from a shared memory base, work privately, then promote or discard. This is valuable for exploratory specialists whose tentative knowledge should not immediately pollute shared memory. It is opt-in, degrades when the dependency is absent, and does not isolate source files or replace Git worktrees. The module's tiny-branch-size statement is an upstream implementation claim, not a measurement reproduced here.

Network federation, public/private channels and tenant collaboration

The federation inbound dispatcher, lines 8–19, 65–87 and 136–172, combines peer status, signatures, authorization and recursively canonicalized envelopes before delivering events. The routing service, lines 64–133, applies live trust-dependent PII handling and signs outgoing envelopes. Private channel grants, lines 125–143 and 185–207, distribute an encrypted channel key and publish locally encrypted messages. This offers genuine distributed communication infrastructure; key lifecycle, network deployment and actual remote task execution remain additional responsibilities. Channel-key grants explicitly lack revocation semantics, so they are not a complete organizational access-control system.

Separately, AI Team, lines 84–138, and its store, lines 73–120, supply tenant-scoped teams/runs/tasks/memory/evidence and a private MCP App board with Firestore deployment support. This can provide a hosted coordination surface across clients. It is not a distributed coding agent runtime, and its units/statuses must not be interpreted as measured provider spend or independent verification.

The board UI, lines 34–37 and 47–111, implements Teams/Runs/Tasks/Evidence navigation and refresh through tools/call to team_board. This is a real dashboard surface in source, rather than a screenshot or hypothetical integration. It remains a read-only view of that service's coordination records. External ruOS/desktop product references elsewhere in the repository are not credited as a bundled Wingman workspace.

Cloud-managed execution and background maintenance

Managed-agent tools, lines 12–18, 57–95 and 204–240, wrap external agent/environment/session creation, event observation and scoped controls. The adapter distinguishes configuration facts, access/health uncertainty, prompt observation timeouts and interruption requests. It could complement local hosts, but needs remote credentials/access and introduces provider-specific permissions, costs and lifecycle semantics. The remote implementation was not available for validation through local source inspection.

Periodic background mapping, test-gap detection, security analysis, memory distillation and backup are also meaningful extras. Worker daemon, lines 1–43, connects those jobs. The elected repository supervisor avoids multiplying expensive schedules across worktrees. These are maintenance/knowledge services rather than substitutes for product leadership.

Distinctive mechanisms and innovation assessment

The most useful design contribution here is the separation of observation, authorization, execution and acceptance. A mission record can be durable without an executor. An admitted native process can exit zero without verified product success. An evaluation can produce a recommendation without authority to promote it. The code often makes these distinctions explicit instead of inventing successful activity when a dependency is missing. The mission service's executor-unavailable response and snapshot readers' unknown/missing states are particularly relevant to an honest Wingman dashboard.

Three mechanisms merit closer study:

  • Deterministic planning with inspectable task edges. The console planner searches a finite SPARC action library using facts, costs and profile/rigor goals, then derives dependencies/waves (goap.ts, lines 1–14, 38–63 and 108–120). This enables repeatable process selection and visible reasons for ordering. It cannot infer whether the selected generic actions are sufficient for a mortgage LOS; product discovery must still provide the content.
  • Journaled bounded autonomy. The autopilot's pure state fold, sealed envelope, ordered kill/settlement/budget checks, parked questions and backoff permit replayable decisions with narrow authority (ap-loop.ts, lines 1–47; ap-live.ts, lines 220–249 and 321–419). This is a concrete pattern for supervised autonomy. The bound remains a live session and configured host controls, not a durable cluster scheduler.
  • Evidence-bound adaptation and speculative state. Held-out evaluation separated from promotion, signed measured managed outcomes, and optional memory branches let an installation experiment without treating every experiment as accepted shared knowledge (harness-flywheel.ts, lines 5–20; managed-learning-loop.ts, lines 25–62; swarm-memory-branches.ts, lines 13–39). The safety/quality depends on the scope and evaluator, and optional backend failure reduces capabilities.

These are grounded mechanisms worth borrowing. This report makes no historical priority claim, industry-wide uniqueness claim or reproduced performance claim. “Neural,” “hive,” “consensus” and role counts do not by themselves establish better coordination or independent agents. The relevant evidence is the concrete path used.

Practical fit for Wingman

Usable directly after focused integration:

  • bounded native Codex/Claude subprocess execution.
  • explicit worktree preparation/status/integration/cleanup.
  • filesystem team mailboxes.
  • durable mission planning/events.
  • tool-policy decisions and receipts.
  • namespaced retrieval.
  • local observations and transcript parsing.

They can accelerate the executor and coordination substrate without defining Wingman's organization for it.

Needs adaptation:

  • assign one stable Wingman agent identity to native session, host, role/profile, project and current task.
  • map all execution paths into a canonical event/task model.
  • distinguish recorded, running, interrupted, completed and accepted states.
  • replace cwd-only isolation with a portfolio registry and host routing.
  • make supervision survive UI/host restarts.
  • bridge team messages and channels into durable conversations with explicit participants and task links.

The terminal console and hosted board are useful precedents, but neither is the connected web/mobile product requested by Wingman.

Still to build:

  • Telegram transport and Butler routing with question/reply correlation.
  • ProjectMaster's existing/new-project intake and portfolio supervision.
  • Durable per-project ProductMaster and TechMaster instances.
  • Proportionate domain discovery with persisted questions/answers.
  • Authoritative scope/specification/acceptance knowledge.
  • Organization-level directory and rooms.
  • Executive current/recent/next/blocker briefings. A human-readable per-agent timeline.
  • Complete per-agent native session lifecycle and steering. A verifiable Mac/Endeavour remote execution agent and shared state protocol.
  • Product acceptance and delivery closure that stops active development until further work.

A practical integration would first use one native execution path, one task authority and one durable agent/session identity mapping. Keep policy, evidence and memory behind those boundaries. Combining every available Ruflo path up front would create multiple “busy,” “complete,” “session” and “agent” meanings before Wingman has its own stable model. The report's strongest fit is as an advanced infrastructure/reference layer, not as an almost-complete Wingman with only a Telegram plugin missing.

This was a read-only static assessment. No dependencies were installed, no services or coding-agent subprocesses were launched, and no hosted API, Telegram account, network federation or multi-machine setup was exercised. Repository sources were not modified. Runtime assertions above mean “implemented in the inspected path,” not “successfully run in this environment.”
