Agent Orchestrator assessment

Identity, revision and verdict

  • Product: Agent Orchestrator / Orchestrator.inc, a desktop supervisor for fleets of coding sessions.
  • Repository: https://github.com/OrchestratorInc/agent-orchestrator
  • Checkout: research/agent-orchestrator/repo/
  • Assessed commit: fc92e7ec6f43fc06317cd47cdf8813956612fe50.
  • Assessment date: 2026-11-05.
  • Basis: static inspection of this checkout, including implementation and selected test bodies. No dependencies installed, services launched, model calls made, or runtime tests executed. The checkout was not modified.

Verdict: Agent Orchestrator (AO) provides a strong execution and detailed-workspace foundation for Wingman. Independent coding sessions retain conversations and work state. An orchestrator coordinates workers and reacts to pull-request (PR), continuous-integration (CI), and review events. Recurring automation and remote-host controls support ongoing operation.

Wingman still needs Telegram Butler, portfolio intake, and separate product and technical leaders. Proportionate discovery, organizational rooms, product acceptance, and executive work summaries also need implementation.

This revision matters: the live architecture is a Go daemon and Electron/React client, not the older TypeScript in-process CLI/plugin architecture sometimes associated with this project. The public checkout includes remote-daemon clients and cloud contracts. The hosted cloud control plane is explicitly outside it. See repository guidance, lines 7–16, and current architecture, lines 3–19. Findings below credit public implementation rather than assuming the private service works as advertised.

The companion agent lifecycle and continuity chapter expands identity lifetimes, asynchronous provisioning, host adoption, task continuation, branching/fork limits, delivery receipts and cleanup generations. The verdict and complete feature comparison remain in this master report.

Architecture and execution model

The ao executable enters the Cobra CLI through cmd/ao/main.go, lines 10–14. The compatibility backend executable calls the daemon directly (backend/main.go, lines 1–16). The service-facing boundary is HTTP: session creation, task delegation, orchestrator creation, send, kill, restore, interface transitions, workspace inspection and artifact versioning are registered in sessions controller, lines 210–283. Electron is a supervisor rather than the authoritative lifecycle owner.

The main path is controller → session service → session manager → workspace/agent/runtime or native Chat driver → durable lifecycle facts. SessionManager.Spawn resolves the project and harness, composes role instructions and task context, validates model and interface capability, creates a durable session, materializes its workspace, provisions it, and starts exactly one controller. The key split is in manager.go, lines 989–1115 and 1344–1435:

  • A TUI session runs an installed agent CLI in a native PTY/ConPTY runtime, with tmux compatibility/fallback. Its terminal is streamed to viewers, while provider hooks and runtime probes supply facts.
  • A Chat session uses a native protocol driver. Codex is driven through codex app-server; other supported providers use ACP or provider-specific drivers. It has no agent terminal runtime. A shell terminal can still be opened alongside it.
  • Both modes share the AO session identity, workspace, project association and lifecycle machinery. A durable transition can move a compatible native conversation between interfaces; two controllers are not supposed to own it simultaneously.

Projects are durable registry rows, not inferred businesses or product organizations. They can be a single repository, a root with child repositories, or a scratch directory. A workspace project has a registered root plus child repositories and per-session worktree inventory (project domain, lines 5–39 and 62–91). Workers normally receive separate branches/worktrees. Scratch and standalone workers provide a genuine non-Git execution path, not a fictitious PR workflow.

SQLite stores projects, sessions, conversation branches, turns, messages, activities, reviews, reports, automation definitions/runs and related facts. The crucial distinction is between facts and presentation. Session status is derived from activity, termination and SCM facts at read time (status.go, lines 19–58). A board column is not a second stored workflow state. Database triggers feed a change log, a CDC poller fans changes to clients, and durable catch-up is separate from live fan-out (cdc_wiring.go, lines 11–35). This is a useful foundation for several connected Wingman views without letting every UI invent its own truth.

Independent detached Chat hosts are particularly consequential. The provider process can outlive daemon or desktop replacement, and the replacement daemon attaches to its authenticated local host rather than replaying a live task into a fresh process. ACP hosts retain initialization/session snapshots, request correlation, pending interactions and prompt-result acknowledgements (persistent host, lines 1–4, 31–88 and 123–142). Host identity is not a second execution machine: this mechanism is local process continuity. Real remote execution is a separate feature described below.

Agent definition, creation and lifecycle in detail

What an “agent” actually is

AO distinguishes a harness (provider/CLI integration), an AO session (durable task execution identity), a native conversation (provider-owned transcript), a controller generation (one AO owner of a conversation), and a runtime/host process (execution resource). An orchestrator is an AO session with a different role prompt and project-scoped conversation continuity. A worker is another independently launched AO session, not an internal subagent inside the orchestrator. Reviewer processes have their own review records and conversations, rather than pretending to be ordinary implementation workers.

Consequently an AO session is more durable than a subprocess and more concrete than a prompt, but less organizationally persistent than Wingman's BackendCoder identity. It can retain files and context over many turns or PRs, yet there is no separate stable employee/profile record above the session. The available role set and provider vocabulary are explicit in session.go, lines 19–26, and harness.go, lines 3–70.

Definition and configuration

A project stores its default branch, environment, shared symlinks, setup/cleanup commands, worker and orchestrator instructions, default model/configuration, reviewer selection and opt-in intake/review policy. Inline instructions can be supplemented by repo-relative files; missing/escaping files fail preparation rather than silently dropping rules. Worker and orchestrator overrides pick a harness and tune model, effort, mode and permissions. Spawn arguments override the resolved role/project defaults. These are meaningful reusable behavior templates, but there is no arbitrary named profile object or team composition DSL (ProjectConfig, lines 20–91; AgentConfig, lines 5–58; rules loader, lines 165–206).

The orchestrator's coordinator-only boundary is primarily prompt policy: it is told to inspect state, delegate changes, communicate via AO and report progress. This is not evidence that its process lacks filesystem write authority. Wingman should separate organizational authority from executable tool permission if it requires enforceable managerial boundaries.

Creation, identity and routing

A desktop task submits a project, brief, harness, model, approval mode, attachments and optional idempotency/preparation handles. DelegateTask directly spawns a worker. The “delegate” route does not imply an intervening intelligent project manager (delegation.go, lines 27–50 and 68–133). An orchestrator may separately call the CLI spawn route for named workers. One active orchestrator per project is guarded by a project lock; replacement retires the old orchestrator and verifies the replacement (session service, lines 738–845).

Spawn validates the harness/model and Chat readiness before durable resources are created where possible. It resolves permission inheritance from a stored parent when supplied, never merely trusts a request's claim that it is an orchestrator, and refuses unsupported explicit interface requests. Default Chat may fall back to TUI for selected availability failures; explicit unsupported Chat requests return an error. Client request IDs/hashes make task creation replayable without casually duplicating workers (manager, lines 989–1109).

A session is seeded, receives an AO ID/branch/workspace, has setup and attachments prepared, then launches its chosen controller. Async Chat creation may return an addressable session before provisioning finishes. The pending state is real, not proof the provider is already running. Project workspace gates serialize sensitive Git preparation, while provider work remains concurrent. Speculative task preparation can pre-create worktrees and is cancellable independently of a claimed task (manager, lines 1286–1435; delegation, lines 52–65).

Tools, permissions and execution

The installed harness provides code editing, commands and native tools. AO adds session communication, reporting, reviews, browser/preview, workspace and artifact APIs. It does not implement every provider tool itself. Chat controllers record tool activity and provider interactions into a durable projection. Capability checks determine which providers support features such as Chat, native resume, fork, compaction, permission modes or interface handoff.

Permissions are provider-specific. Codex Chat maps accept-edits/auto to on-request approval with workspace-write sandboxing; auto chooses the provider's auto reviewer. Other modes in that adapter map to never/danger-full-access. Read-only reviewers receive read-only policy. Worktree separation alone is not an OS sandbox, and a managerial role prompt does not impose permissions (Codex driver, lines 678–727). AO's browser service checks a session-scoped capability verifier before dispatching actions to the Electron panel or configured Chrome runtime (browser service, lines 26–55, 90–141 and 175–188).

Persistence, resume and interface migration

AO IDs, native transcript IDs, runtime launch IDs and provider-controller generations are deliberately different. Session metadata retains user task direction separately from AO-authored coordination, preventing internal handoff traffic from replacing the visible assignment (session metadata, lines 181–215). Project-scoped orchestrator conversation IDs can survive clean replacement even though the current controlling session changes (conversation record, lines 181–209).

A surviving detached host can be adopted without relaunching or reinitializing the native provider. Host control is authenticated and exclusive, and an inconclusive ownership probe is not treated as death. A per-session launch lock prevents duplicate hosts. Actual provider failure falls back to native load/resume when supported. For TUI restore, AO selects a native restore command when a conversation exists; otherwise it may start fresh in the retained workspace and explicitly distinguish the restore mode. This is an important limit: preserving an AO session/worktree is not a universal guarantee of preserving the full provider transcript (persistent host, lines 74–121 and 185–210; restoreArgv, lines 7100–7142).

TUI↔Chat transitions are durable sagas with phases, preflight checks, cancellation, rollback and a message outbox. They require evidence that the source native identity belongs to its current launch and stop the old controller before starting the target. The transition persists the mode/controller epoch rather than letting the UI toggle two live interfaces. This is richer than opening the same terminal in another view (interface_transition.go, lines 34–58 and 167–206). Provider capability and transcript replay remain boundaries. The implementation does not make every harness interoperable.

Idle worker Chat hibernation is another distinct state: it stops a safely settled provider to save resources, retains the native conversation and wakes it on viewing or work. View leases avoid shutting down a provider currently being viewed; renewals do not repeatedly retry a failed wake. Current code has a 90-second idle threshold, whereas an architecture-doc table still discusses shorter sweeps; implementation takes precedence (hibernate.go, lines 16–24 and 63–110). Ordinary idle hibernation excludes orchestrators through the durable eligibility filter (session.go, lines 449–457). Hibernation is not retirement or product completion.

Scheduling, interruption, failure and recovery

Recurring automations persist canonical timezone-aware RRULE schedules, accepting a supported cron subset and rejecting sub-minute or finite COUNT/UNTIL schedules. They materialize durable run occurrences and claim them with leases before calling the normal spawn boundary. Claims prevent sibling runs of the same definition from dispatching simultaneously; expired claims are reconciled with already-created sessions to avoid duplicate execution. Transient launch errors can release a run for retry, while invalid/not-found and incomplete retained launches become failed runs (schedule.go, lines 13–79; scheduler, lines 52–98, 135–179 and 185–286). This could schedule supervision prompts, but those are scheduled tasks rather than a continuing ProjectMaster identity automatically reasoning across the portfolio.

Chat supports interrupting a turn separately from terminating the session, provider-dependent compaction/rollback, queued inputs, steering handles, retries and branch activation. Durable delivery reservations avoid treating an uncertain provider response as permission to resend blindly (controller store contract, lines 100–164; send recovery, lines 99–120). Stop/rollback are not a general filesystem transaction: code and external effects still require the harness/workspace-specific treatment appropriate to the action.

Conversation branching must also be distinguished from creating an independently forked AO worker/workspace. ForkConversation exists as an internal provider call but is deliberately not exposed over HTTP: native history fork does not copy the source worktree changes. Message-edit branches and branch activation operate within the existing session/worktree. A full session fork with a coherent source workspace snapshot remains adaptation work (history.go, lines 127–162 and 863–876). Continue likewise adds a bounded interrupted-task reminder rather than resuming an executable checkpoint. The companion chapter traces this distinction.

The runtime reaper samples approximately every five seconds. It keeps unknown probe results separate from confirmed process death. A circuit breaker limits correlated false death reports during infrastructure failure. See reaper, lines 1–33. Spawn failure rolls back seed rows and newly created resources where safe. Later failures can retain terminated records and workspaces for inspection. See manager, lines 986–988, 1356–1389, and 2201–2314. Startup reconciliation removes a host only when its durable ownership is no longer live. A failed session-list read cannot prove orphanhood. See persistent_chat_wiring.go, lines 19–49.

Completion, acceptance and retirement

A worker's done report is a coordination claim with optional PR/artifact outputs. It does not terminate the session or prove acceptance. The report service explicitly separates these claims from authoritative lifecycle state (report service, lines 94–138). PR-driven automatic termination is optional and requires no remaining open PR plus at least one merged PR. It also waits for actual quiescence, avoiding termination while an agent prepares another PR (reactions, lines 82–117 and 291–329). This is an engineering-delivery heuristic, not Wingman's product definition of done.

Explicit kill stops the mode-specific controller, reviewers, previews/browser and session shell terminals, persists termination intent, and attempts workspace retirement. Cleanup failures or unsafe worktree teardown preserve inventory and record the refusal; restore markers must not resurrect deliberately killed sessions. Setup and pre-remove commands are project configuration, and cleanup may continue as daemon-owned background work (manager, lines 2650–2783 and 2790–2849). Cleanup scripts operate only under the managed workspace root; ordinary failures preserve the worktree for retry. Forced orchestrator replacement has a bounded exception that logs cleanup-script failure and proceeds, so integration should preserve that distinction (workspace_cleanup.go, lines 55–76 and 92–150). Deleting/archiving task sessions is not a personnel-retirement workflow because there is no separate personnel model.

Coordination mechanics and a source-traced request

AO's coordination substrate combines direct messages, durable worker reports, external issues/PRs, shared configuration/files, and daemon events. It does not offer a multi-party room bus or an independent internal ticket dependency graph. PR stacks are derived from source/target branches: an open parent blocks the child and influences merge-conflict handling (stack.go, lines 8–33). That is a useful engineering dependency, not a general task dependency.

A concrete implementation path is an orchestrator assigning a worker a task and receiving a decision blocker:

  1. The human speaks to a project's native conversation. The orchestrator's role instructions encourage inspecting current state before spawning or redirecting a named AO worker. This policy resides in the prompt. The program does not deterministically decompose the request (prompt.go, lines 215–267).
  2. Worker creation goes through POST /sessions and the service/manager path. The controller passes the project, parent, kind, harness, branch, task brief, settings and attachments to the service (sessions.go, lines 327–393). The manager validates, seeds, provisions and launches the independently addressable worker described above.
  3. If the worker needs a product decision, it creates a needs_input report. The service validates that the reporting session is a worker, derives project ownership from the stored session, and persists an immediately available pending report. A checkpoint normally has an hour fallback deadline. A done report starts a five-minute settlement window (report service, lines 94–138; report constants, lines 46–64). These delays intentionally batch informational traffic rather than waking management for every tool call.
  4. The coordinator selects the current live project orchestrator at delivery time, claims a batch and submits semantic context with an idempotency key. If management has been replaced, pending work follows the replacement. A stuck report may interrupt an active Chat orchestrator, rate-limited per worker to three minutes; TUI orchestrators are not Ctrl-C interrupted by this path. Busy unsent human drafts defer delivery for 30 seconds rather than starving other projects (coordinator.go, lines 20–51, 156–220).
  5. An accepted submission acknowledges the durable batch; failure releases or defers it for retry. SQLite tables retain claim/delivery state, ordered outputs, deadlines and attempts (reports migration, lines 3–42; delivery migration, lines 3–11). The orchestrator then reasons about the blocker and asks the human or redirects another worker. That final management choice is model behavior, not a programmed escalation ladder.
  6. The answer can be sent directly to the worker with ao send. CLI-authored messages include the sender session identity and use HTTP, with optional steer-or-send and recover-only handling (send.go, lines 68–120). Delivery is mode-aware; TUI readiness checks avoid assuming that an existing process can already receive a pasted message (message_delivery.go, lines 19–35 and 81–119).
  7. As the implementation produces PRs, SCM observation persists checks/reviews/comments and lifecycle reactions send deduplicated CI/review/conflict work back to the owning worker. Reaction signatures persist over daemon restart. Multiple actionable conditions are queued independently, while permission-blocked sessions remain protected from unsolicited injection (reactions.go, lines 42–70, 139–165 and 938–1053). Final completion is still separate from the worker's self-report.

This is a meaningful autonomous feedback loop. Its limitation for Wingman is structural: there is one project coordinator, the human remains in that project's session, and decisions are not moved through organizational rooms and a common Butler conversation. Reports are project-local; remote UI aggregation does not turn local report stores into a distributed collaboration fabric.

Major capabilities beyond Wingman's description

Heterogeneous native harness operation and interface migration. AO supports a much wider provider vocabulary than Wingman's Codex-only starting point and distinguishes native terminal from structured protocol interfaces. Moving one native conversation across Chat/TUI with checkpoint evidence, controller fencing and rollback is a major operational capability. It enables an operator to switch observation/control surfaces without abandoning work. Integration would need to select which providers and capabilities Wingman guarantees, because a broad provider list is not uniform behavioral parity (harness vocabulary, lines 6–70; transition API, lines 34–58 and 167–206).

PR maintenance and independent review. AO tracks multiple PRs per worker, branch-stack blockers, and current heads. It runs separately configured reviewers. It avoids repeated review of the same head unless the caller requests a rerun. Automatic reviews wait for a quiet worker and bound repeated failures on one head. This supports engineering review. It does not replace functional acceptance or provider-account approval. See review engine, lines 245–282 and 394–461; autoreview, lines 15–39 and 84–124; and stack derivation, lines 8–33. Reviewer manifests authorize one worker and an exact target SHA. The host-trusted path explicitly disclaims universal containment. See review gateway, lines 29–76.

Recurring automation and tracker intake. The scheduler stores timezone schedules and leases each occurrence. It can adopt a committed launch after a crash. Issue intake selects eligible GitHub or GitLab issues, removes duplicates, and applies per-project failure backoff. These mechanisms can support maintenance and supervision. Repeatable tasks still need bounded policies. Intake reads the external tracker. It does not provide Wingman's shared task-update workflow. See scheduler, lines 52–98 and 135–179; intake, lines 19–31 and 164–210; and project config, lines 65–68.

Remote-machine supervision and mobile access. An Electron main-process proxy authenticates to the remote machine and forwards streams. It keeps remote credentials outside the renderer. Host-qualified IDs separate local and remote resources. This supports Mac and Endeavour visibility.

Desktop remote-host IPC requires an AO Cloud account. Each machine still owns independent local state. Hosted Cloud sessions have public client contracts and UI, but a private execution control plane. Wingman must choose whether to accept this service dependency or implement its own federation. See remote proxy, lines 29–50; host identity keys, lines 1–34; remote account gate, lines 58–120; and public/private boundary, lines 7–16.

Multi-repository task workspaces, browser operation and artifact history. Workspace projects create a coherent root plus child worktree inventory, useful for products with separate applications/services. The detailed workspace includes session-bound browser execution and preview, versioned artifacts and source file/diff/history inspection. Artifact versions are immutable content-addressed snapshots with provenance and explicit restoration metadata, which can support reviewable deliverables beyond code (project.go, lines 62–91; artifact version domain, lines 131–151; artifact/workspace routes, lines 215–255). These are substantive workspace features; Wingman would still need to connect artifacts to product acceptance and project knowledge.

Distinctive mechanisms worth studying

These are mechanisms supported by this checkout, not claims of historical uniqueness.

  1. Continuity as three identities rather than one process handle. Durable AO session, native conversation and current controller epoch are kept distinct. Detached host adoption preserves live execution, while native resume repairs actual host loss and mode transitions fence stale owners. This enables UI/daemon replacement and interface movement without declaring a new worker every time. Its limits are provider-native resumability, verified history and local-host health, not a promise of flawless restart under all failures (host, lines 74–142; conversation, lines 181–209; transition store, lines 34–58).
  2. Durable worker-report settlement and urgency. Reports have semantics, output references and delivery deadlines separate from lifecycle state. Checkpoints can batch, completion allows a settlement window, and urgent stuck reports wake a manager under a persisted rate limit. Target selection happens when delivery occurs, so management replacement does not strand messages. This is a strong starting point for Wingman's supervision/escalation service, but not yet a room conversation or decision-resolution protocol (report service, lines 94–138; coordinator, lines 156–220).
  3. Facts-first status and repairable event-driven views. Operational state is observed and persisted once, derived into display status, then exposed through CDC/live transports. Probe failures do not assert death, and a circuit breaker protects against correlated false failures. This reduces contradictory status across board, terminal and mobile views and would suit Wingman's connected dashboards. It still requires a new semantic summary layer: activity/PR facts alone do not explain product progress (status.go, lines 19–58; CDC wiring, lines 11–35; reaper, lines 1–33).
  4. Automation launch reconciliation instead of simple timers. A scheduled occurrence is durably materialized and leased, linked to a session, and adopted after a crash if launch completion was committed. An incomplete seed is rolled back rather than adopted as successful work. This mechanism is useful for reliable supervision jobs and recurring maintenance. It does not judge whether a completed session fulfilled a business objective (scheduler, lines 52–98, 135–179 and 185–286).
  5. Host-qualified addressing with a credential-holding local proxy. Remote resources carry host plus ID, and the renderer resolves an owning daemon at request time. This avoids an easy multi-machine failure mode where identical IDs or stale UI state act on the wrong machine. It is a practical building block for Wingman routing, but does not supply cross-host agent messaging or distributed project ownership (hosts.ts, lines 7–34; host-clients.ts, lines 44–85; proxy, lines 29–50).

Practical fit and remaining work

Use directly or with a thin integration:

  • The Go HTTP daemon and lifecycle/workspace engine.
  • Independently addressable Codex Chat workers.
  • Native resume and detached-host continuity.
  • Session steering and approval UI.
  • File/diff/browser/artifact workspace.
  • Project boards.
  • Report delivery and SCM follow-up.
  • Scheduling and reviewer machinery.

Use the CLI/API boundary for integration. It preserves lifecycle ownership and avoids external manipulation of the Electron UI or provider PTYs.

Adapt deliberately: introduce a durable organizational agent/profile identity above AO sessions, mapping an agent's assignment/history to one or more task sessions. Extend project-local coordination into host-qualified organizational routing and a shared tracker/room store. Use AO reports as evidence for summary generation while retaining separate authoritative lifecycle facts. Either align project knowledge with the repository rules/files mechanism or add a managed directive service whose artifacts are visible in the workspace. Remote-host account gating, private cloud dependencies, provider capability differences and lifecycle ownership need explicit deployment decisions. A long-lived manager should not be confused with an automation that repeatedly spawns fresh sessions.

Build as Wingman's distinct product layer:

  • Telegram Butler, portfolio ProjectMaster and request disambiguation.
  • Persistent role/profile/team directory.
  • Separate ProductMaster and TechMaster leadership.
  • Scalable discovery/clarification and decision routing.
  • Product scopes/specs/acceptance/definition-of-done records.
  • Independent tickets and general dependencies.
  • Browsable Room1/Room2 collaboration.
  • Integrated functional TestMaster acceptance and post-acceptance stop policy.
  • Executive plain-language briefings and long-lived agent timelines.
  • Shared Mac/Endeavour project placement and collaboration.

Role prompts alone cannot supply these durable records and connected views.

The strongest architectural fit is Wingman organizational services above AO execution services. Replacing AO's facts/lifecycle system with an independent competing status database would discard one of its best mechanisms. Conversely, treating AO's task board as the entire organization would leave the main Wingman product requirements unmet.

AO agent lifecycle and continuity mechanics

Companion to Agent Orchestrator assessment, at revision fc92e7ec6f43fc06317cd47cdf8813956612fe50. Static implementation review, 2026-11-05; no runtime or tests executed. Re-audited against the master report and cited source on 2026-11-05. This chapter adds detail without changing the master verdict.

1. Identity has several independent lifetimes

Concept Actual meaning Wingman implication
Project Durable registry row with path, kind, repository identity and configuration. A useful product workspace identity. It does not contain product ownership/discovery/acceptance by itself.
Harness Provider/CLI adapter identity and capability set. Codex is an execution technology, not an employee role.
AO session Persistent execution/work ownership, optionally associated with a project, with worker/orchestrator kind, title, metadata and lifecycle facts. Useful binding target for a Wingman agent instance, but it is not already the employee/profile/team model.
Native provider conversation Opaque provider context handle. Preserve separately from AO IDs; not every harness proves identity interchangeability.
Controller generation/runtime launch One particular owner of a live provider/runtime. Fence obsolete events so a replaced process cannot update the current agent.
Chat turn One queued/dispatched provider request with outcome and history. A turn is not a ticket, product or standing employee.
Report Worker-originated checkpoint/input/stuck/done claim with output references and delivery lifecycle. A meaningful coordination event; do not promote it automatically to verified task completion.
Review run Separate reviewer execution against an owned worker's PR/head. Useful quality role, distinct from TestMaster's integrated product acceptance.
Side conversation Separate native context/host attached to a session and explicit boundary. Useful focused questions; not a project room or a new permanent employee.

The distinctions come directly from project.go, lines 27–91; session.go, lines 19–26, 226–237 and 264–290; report.go, lines 55–135; and side_chat.go, lines 8–46.

2. Definition → durable creation → one controller

The caller selects a registered project and submits a worker prompt or requests its orchestrator. Project configuration supplies reusable rules and defaults. The session manager resolves the harness and mode. It combines project, role, and request settings. It checks model and permission support before durable creation. An unsupported explicit Chat request fails. An inherited Chat preference can fall back to TUI for selected capability or readiness errors. This preserves the caller's explicit interaction contract.

Creation can use a client request key/hash to return an already committed session on retry. Scheduled runs have a separate durable automation-run association. Hidden task-preparation rows reserve speculative workspaces, then become real sessions at claim/commit rather than multiplying unused worktrees on every interaction. A session receives an artifact directory and composed task/system instructions; AO provisions its workspace and attachments before the mode-specific launch. Role rules become provider instructions, not an enforced filesystem permission boundary.

Chat can return early with a durable provisioning session. That row has progress steps (fetch, worktree, setup, agent) and a persistent error message if startup fails. Queued input can survive startup failure and await retry. This is an important boundary: “addressable in the dashboard” does not yet mean “agent running.” AO's explicit provisioning facts give Wingman a way to show the truth.

Source: manager.go, lines 989–1188, 1205–1238 and 1370–1429; delegation.go, lines 52–133; session.go, lines 334–353 and 418–478.

After shared setup, exactly one mode launches. TUI uses native runtime I/O; Chat starts a protocol controller and delivers an initial prompt as a turn or drains a durable queue. It has no agent pane into which text should be injected. The Chat launcher contract retains semantic message identity and sender attribution for relayed session messages. The mode-aware boundary avoids accidentally delivering the same task through both a terminal paste and a protocol call.

Source: chat_spawn.go, lines 15–59; manager.go, lines 1395–1435.

3. Live execution and truthful observation

AO's durable activity facts are separate from the board's derived status. The read model combines session activity, signal freshness, termination and SCM facts. There is a grace period for an expected terminal hook that has not arrived. An unobserved worker need not be confidently labelled idle. PR state is also separate from runtime activity. These distinctions prevent a single status enum from having to represent all execution and delivery facts at once.

The reaper polls runtime liveness and sends observations to lifecycle logic. It does not write session rows directly. An adapter or probe error does not establish process death. A circuit breaker requires at least five dead conclusions in one pass. It also requires dead conclusions to exceed half of all observations. The breaker changes those conclusions to failed probes. This can delay recognition of genuine simultaneous exits. It prevents a temporary backend outage from terminating the entire board.

Source: status.go, lines 10–39; reaper.go, lines 1–6, 19–33 and 139–190.

4. Three different ways to continue work

Adopt a still-live provider

The strongest continuity case is not resume at all. A detached per-session host still owns the provider process while the desktop/daemon disappears. The new daemon authenticates to that host and reattaches. A host descriptor retains session identity, protocol, ownership fingerprint, address and PID. Explicit “already attached,” “ownership inconclusive,” “not running” and “incompatible” errors prevent treating every reconnect failure as permission to spawn a duplicate provider.

ACP retains initialization state, session state, request correlation, and pending requests. Its prompt journal appends provider frames before daemon delivery. The journal has a 256 MiB limit. Event and request identities survive daemon reattachment. Replacement hosts use different identities. A pending completion needs acknowledgment before another prompt can overwrite its recovery state. This protects the gap between provider completion and SQLite projection.

The mechanism primarily survives supervisor replacement while the host lives. It is not a VM checkpoint or durable serialization of arbitrary running tools after host/machine loss. The journal appender shown here writes bytes but is not evidence of a full power-loss-safe distributed transaction. Avoid expanding its guarantees beyond the implementation.

Source: persistenthost/host.go, lines 74–141; acp_journal.go, lines 11–61; acp_relay_restart_test.go, lines 10–86.

Resume a provider conversation after actual controller/host failure

AO persists native handles separately from its session ID and rotates controller generations for replacement owners. Native resume capability and provider history are adapter-dependent. The restore path returns whether it used native resume, saved-prompt fallback or fresh launch. These are semantically different outcomes. A terminated session needs enough workspace metadata to be restorable, and fallible restore I/O runs before durable resurrection.

For Wingman, fallback should be visible in the agent timeline: “native conversation resumed” and “fresh process started with task context” preserve different amounts of working context. Simply retaining an AO row does not prove that the provider kept all previous reasoning/history.

Source: session.go, lines 226–237; manager.go, lines 3045–3104 and restoreArgv beginning at line 7105.

Continue an interrupted task with a reminder

The Continue mechanism locates the interrupted turn in the active lineage. It derives bounded task context and stores that reminder with the new request. It refuses continuation when it cannot establish the stopped task. The reminder omits reasoning and tool outputs. It is not an execution checkpoint. It cannot restore a command at its exact instruction pointer.

Source: continuation.go, lines 15–59 and 62–87.

5. Interface handoff, branching and fork limits

The public interface transition API durably records source, target and policy, then runs the drain/interrupt transition in background so the request timeout does not own its lifetime. It checks whether the session is terminated, the target differs, the workspace exists and native conversation identity can be established. Source intake is fenced while ownership moves. Some adapter paths permit explicitly degraded identity reset; such paths must not be described as preservation of the same native context.

This is a good model for Wingman's detailed agent workspace: the dashboard can change interaction mode without granting two controllers authority over one agent. It is not live migration between the Mac and Endeavour. The same session/workspace remains on its owning execution host.

Chat also supports rollback, message edits that branch before a prior prompt, and activation of stored conversation branches. However, the standalone ForkConversation function explicitly says it is not reachable over HTTP pending a coherent second-session/workspace-state decision. Native provider history fork copies conversational memory, not filesystem changes; giving a new worktree to an agent that remembers edits missing from that tree would be misleading. Thus full-session fork must remain a Wingman gap/adaptation even though provider branch tools exist.

Source: interface_transition.go, lines 167–222 and 278–292; history.go, lines 110–162 and 865–879. Native ownership integration tests, lines 22–37, cover transcript preservation/unavailability, identity change and project coordinator replacement under controlled external I/O.

6. Steering, queued input and human decisions

AO separates queueing, steering, and interruption. Cancelling a queued item does not cancel the running turn. Queue edits and reordering apply to undispatched items with conflict and idempotency checks. Steering requires provider capability. It retains the provider turn ID and records a delivery result. Provider acceptance can occur before persistence becomes certain. A typed uncertainty state prevents automatic double delivery in that case. The CLI offers receipt recovery. Provider acceptance alone does not prove agent action.

Approvals and structured input are native-provider interactions. These are valuable execution controls and can return a human answer to the correct provider request. They do not contain Wingman's product-question lifecycle: a question such as “which lending jurisdiction?” still needs project discovery context, Butler transport and an accountable agent, rather than merely a provider permission dialog.

Source: queue.go, lines 23–108; steer.go, lines 15–74; send.go, lines 99–148; ChatTimelineItems.tsx, lines 57–70, maps approval/input/usage/error activity kinds to presentation icons. The controller, rather than this icon map, owns native interaction handling.

7. Wake, completion, retirement and cleanup are different operations

The automation scheduler creates durable run occurrences and claims with leases before spawning. It reconciles existing run/session associations on retry, distinguishes completed launch from a seed and supports bounded catch-up. These are scheduled executions. A new scheduled worker is not automatically the same persistent organizational employee.

Optional worker Chat hibernation conserves resources after a settled idle period when no active view/work/pending interaction prevents it and native resume is available. Opening a view or sending work can wake the cold session. View lease expiry and a 90-second idle threshold are implementation facts, not a product completion judgment. Orchestrators are excluded by the cheap durable eligibility check.

Worker done reports are meaningful progress claims with references, but do not mutate authoritative lifecycle. PR-based automatic termination is an optional delivery rule: no open PR remains, at least one merged and the worker is quiescent. This differs from product acceptance, especially for multi-application products or artifacts without PRs.

Kill uses a guarded multistep operation with its own teardown budget. Browser or request cancellation must not leave a dead provider with a logically live row. Cleanup processes terminated records and checks workspace ownership. Cleanup generations prevent an earlier episode from claiming current success. The system reports skipped or refused cleanup. Repeated cleanup does not revisit settled workspaces. Pre-remove scripts apply only to AO-managed workspaces. Forced orchestrator replacement has a separate cleanup policy. Wingman's reusable agent profiles still need an explicit retirement workflow.

Source: scheduler.go, lines 52–98 and 135–179; hibernate.go, lines 16–24 and 63–110; session.go, lines 449–457; report/service.go, lines 94–141; reactions.go, lines 82–118; manager.go, lines 2670–2733 and 5532–5623; workspace_cleanup.go, lines 55–71 and 92–145.

The practical design lesson for Wingman is to retain these separate lifetimes: employee identity, assignment, native context, live controller, report delivery, code-delivery outcome, accepted product outcome and workspace reclamation. AO provides substantial machinery for several of them, but collapsing them into a single “agent status” would discard one of its strongest architectural ideas.
