# Automaker assessment against Wingman

Assessed **2026-11-05**, from the local checkout `researchs/automaker/repo`, actual commit **`5888d2e6f3618e06762803687ea7b181c10edcbd`**. Upstream: https://github.com/AutoMaker-Org/automaker

**Verdict: a substantial implementation workbench and useful reference for Wingman's execution and project views, but not a standing development organization.** Automaker runs actual coding SDK/CLI invocations, maintains feature boards and conversations, dispatches dependency-aware work across projects and branches, and exposes logs, diffs, plans and operational controls. Its primary organizational unit is a feature execution, with a separate interactive chat-session subsystem. It does not implement Butler, a portfolio-routing agent, persistent product/technical leaders, agent rooms or coordinated workers on multiple hosts. Adding those would require an organizational control plane, not merely new system prompts.

The checked-out [LICENSE](../repo/LICENSE) lines 1–9 explicitly declares that the project is no longer actively maintained and supplies the code under MIT terms. This is a statement in this revision, not an independently checked claim about current upstream activity. A fork would therefore need an explicit maintenance owner.

## Architecture and execution model

The backend is an Express HTTP server with authenticated API routes and WebSocket event/terminal channels; React provides browser and Electron interfaces. [Server entry point](../repo/apps/server/src/index.ts) lines 338–371 constructs settings, interactive AgentService, feature loader, automatic-mode compatibility service, provider usage services, ideation, notifications and event hooks. Lines 477–530 mount the API families and WebSocket servers; lines 595–629 forward subscribed events to connected clients. The backend owns work independently of an open page. A remote browser can use this server, but every checked execution path still runs on that server's filesystem/process host.

There are two importantly different execution paths:

* **Interactive Agent Runner:** [AgentService](../repo/apps/server/src/services/agent-service.ts) lines 57–99 stores a map of sessions, each with messages, working directory, model options, running flag, AbortController, provider session ID and queued prompts. `sendMessage` loads context and provider configuration, builds execution options, and streams a provider query (lines 247–568). Session identity is a durable conversation identity, not a persistent employee with relationships or assigned tickets.
* **Feature automation:** the public compatibility layer delegates to a project facade and shared services. [Facade construction and execution helper](../repo/apps/server/src/services/auto-mode/facade.ts) lines 184–381 wires AgentExecutor, plan approvals, provider selection and SDK options. [ExecutionService](../repo/apps/server/src/services/execution-service.ts) lines 165–332 acquires a running-feature lease, loads the feature, chooses the working directory, composes its prompt and calls that helper. [AgentExecutor](../repo/apps/server/src/services/agent-executor.ts) lines 119–368 consumes normalized provider events, records output and tool-use markers, detects plans and updates task state. The feature, its plan and its output survive. The invocation is transient.

The provider boundary is real execution, not simulated personas. [ProviderFactory](../repo/apps/server/src/providers/provider-factory.ts) lines 58–155 registers providers, resolves model IDs and creates the selected implementation. [ClaudeProvider](../repo/apps/server/src/providers/claude-provider.ts) lines 188–251 constructs Claude Agent SDK options including tools, MCP servers, subagent definitions and permission bypass. [CodexProvider](../repo/apps/server/src/providers/codex-provider.ts) lines 803–929 constructs `codex exec` or `codex exec resume`, streams JSONL from a local subprocess, supplies an abort controller and captures the returned thread ID. It also has an SDK execution branch at lines 784–798. Other adapters include Cursor, OpenCode, Gemini and Copilot; their presence should not be taken as proof of behavioral parity.

Storage is primarily inspectable JSON and Markdown rather than an organizational database. [Platform paths](../repo/libs/platform/src/paths.ts) lines 18–54 and 153–161 locate project data under `.automaker/`, including features and `app_spec.txt`. [FeatureLoader](../repo/apps/server/src/services/feature-loader.ts) lines 347–394 and 478–484 writes feature JSON atomically with backups; feature output is stored beside the feature. AgentService uses `DATA_DIR/agent-sessions` and `sessions-metadata.json` (lines 90–93, 886–918). Settings persist project references and defaults, while runtime maps own active leases and approvals. These boundaries are well suited to a local workbench but provide no distributed transaction or multi-host lease protocol.

## Agent definition, creation and lifecycle

### Definitions are not all the same kind of agent

`AgentDefinition` is a named SDK subagent configuration with `description`, `prompt`, optional restricted `tools`, and one of `sonnet/opus/haiku/inherit` as its model ([provider types](../repo/libs/types/src/provider.ts), lines 138–151). Global and project `customSubagents` maps merge with project entries taking precedence ([settings helpers](../repo/apps/server/src/lib/settings-helpers.ts), lines 418–440). AgentService only loads these when subagents are enabled, dynamically includes the Task tool and forwards the definitions into provider options ([AgentService](../repo/apps/server/src/services/agent-service.ts), lines 385–394, 481–523, 549–565). ClaudeProvider passes them to the SDK. This supports specialized delegation in a coding session, but Automaker does not allocate a durable employee/session record for each such definition or maintain the child's organizational lifecycle.

Feature configuration is a different object: title, description, dependencies, priority, model/provider, branch, attachments, test skipping and planning/approval options ([Feature](../repo/libs/types/src/feature.ts), lines 81–110). The backend creates a feature record, then later creates an invocation to execute it. A pipeline step is just ordered `instructions` on that feature ([pipeline types](../repo/libs/types/src/pipeline.ts), lines 5–18). Calling a step “reviewer” does not make it a separately accountable, persistent reviewer.

The normal automatic feature helper builds SDK options and passes them to AgentExecutor. It does **not** merge custom subagent definitions into that payload. See [facade](../repo/apps/server/src/services/auto-mode/facade.ts), lines 283–362, and [executor options](../repo/apps/server/src/services/agent-executor.ts), lines 119–137. Interactive custom-subagent configuration therefore does not establish the same behavior in automatic board execution.

### Creation, identity and execution

An interactive session is created with generated ID, name, projectPath, resolved workingDirectory, timestamps and optional model. `createSession` writes metadata; loading into the runtime map happens through `ensureSession` ([AgentService](../repo/apps/server/src/services/agent-service.ts), lines 169–241, 942–976). A new message is refused while that same session is already processing (lines 278–280). Multiple sessions can run independently. There is no standing organizational scheduler assigning them tickets.

A feature is created through [the create route](../repo/apps/server/src/routes/features/routes/create.ts) lines 11–38, which writes it and emits `feature:created`. A manual run supplies explicit projectPath/featureId and launches in the background. Manual starts deliberately bypass configured automatic-mode concurrency ([run route](../repo/apps/server/src/routes/auto-mode/routes/run-feature.ts), lines 15–41). `ExecutionService` marks active state early to avoid UI races, resolves an already-existing worktree by feature branch when enabled and fails if that required worktree cannot be found (lines 173–260). Thus the hot path does not create a new isolated worktree for every invocation; worktree setup is a separate workflow and multiple features can target one branch.

The feature lease contains project, branch/worktree, startTime, model/provider, abort controller and a reference count. Nested resume/execute calls can increment the count and release only on the final return ([ConcurrencyManager](../repo/apps/server/src/services/concurrency-manager.ts), lines 81–128). The map is keyed by **featureId**, not projectPath plus ID. Generated IDs normally avoid collisions, but imported or descriptive IDs reused across projects would need attention in an organizational adaptation.

### Tools, permissions and routing

The central SDK options layer validates working directories against configured allowed roots and defines read-only and full coding tool presets ([SDK options](../repo/apps/server/src/lib/sdk-options.ts), lines 95–163). Tools include filesystem operations, Bash, web access, Task and Skill. MCP definitions come from settings. Context rules are prepended to prompts and optional CLAUDE.md loading is delegated to SDK setting sources. Model prefixes and configured compatible endpoints route requests to a provider. They are execution/provider settings, not staff profiles.

Permissions favor autonomy. Claude's actual provider sets `permissionMode: bypassPermissions` and `allowDangerouslySkipPermissions: true` ([ClaudeProvider](../repo/apps/server/src/providers/claude-provider.ts), lines 230–249). Codex's CLI command includes its YOLO flag while also supplying configured approval-policy overrides ([CodexProvider](../repo/apps/server/src/providers/codex-provider.ts), lines 819–889). A plan approval is therefore a workflow checkpoint, not a per-command permission system. Wingman could reuse the execution adapters, but would need to deliberately map tools and host access to its own organizational authorization model.

### Concurrency, scheduling and supervision

Automatic mode creates a state keyed by projectPath and branch, resolves concurrency settings and runs an abortable polling loop ([AutoLoopCoordinator](../repo/apps/server/src/services/auto-loop-coordinator.ts), lines 99–170). It counts manual and automatic work against the automatic dispatch limit, loads pending and all features, filters satisfied dependencies, sorts eligible items by priority and launches the next feature (lines 172–249). Parallelism comes from multiple outstanding promises/provider processes. Each feature's parsed plan tasks execute sequentially ([AgentExecutor](../repo/apps/server/src/services/agent-executor.ts), lines 428–490).

The loop continues sleeping when idle and can pick up later work. It does not research blockers, converse with a worker, allocate a specialist team or periodically wake a management agent. Stopping the loop cancels dispatch and clears its saved execution state. It returns the number of still-running features and does not itself abort each running feature ([coordinator](../repo/apps/server/src/services/auto-loop-coordinator.ts), lines 258–276). This distinction matters for both UI language and unattended shutdown policy.

### Persistence, resume and recovery

Interactive messages are saved as session JSON and metadata retains provider session IDs; `ensureSession` reloads both plus the queued prompts. On a stale provider session error, AgentService clears the saved ID so a later attempt can start fresh ([AgentService](../repo/apps/server/src/services/agent-service.ts), lines 169–241, 794–801, 886–918). The provider may resume its native conversation or receive reconstructed history; backend session identity does not guarantee that a provider retains an identical live process/context.

Feature recovery is chiefly artifact-based continuation. `contextExists` checks for `agent-output.md`; `resumeFeature` reloads that text into a customized continuation prompt, or starts fresh when no output exists. It can instead resume a detected pipeline position ([RecoveryService](../repo/apps/server/src/services/recovery-service.ts), lines 168–246). The server first reconciles transient states and then starts background recovery for registered projects ([startup](../repo/apps/server/src/index.ts), lines 422–453). The recovery scan consults saved running IDs because reconciliation may already have reset their statuses, resumes them in sequence and clears saved state (RecoveryService lines 250–328).

This is useful continuity, with limits: execution-state storage uses one project file, writes a single branch field and clears the same file while ignoring its branch parameter (RecoveryService lines 92–165). It is not a durable independent record for every active branch loop. Disk saves also contain several catch-and-ignore paths. Multi-branch crash recovery warrants runtime validation before reuse as a reliability guarantee.

### Interruption, failure and retry

`stopFeature` persists `interrupted` immediately, aborts the provider and force-releases its lease ([ExecutionService](../repo/apps/server/src/services/execution-service.ts), lines 588–609). The comments explicitly acknowledge that CLI termination can lag. Immediate lease removal is not proof the old OS process has finished, so an external coordinator should not equate a free slot with completed cancellation. Interactive stop is a separate per-session AbortController action (AgentService lines 848–860).

Feature errors are classified, emitted to the UI and normally return the feature to backlog; if pipeline work has already completed they route it to waiting approval and preserve merge-conflict status (ExecutionService lines 529–584). Failure windows, quota exhaustion and rate limits pause the relevant automatic loop ([AutoLoopCoordinator](../repo/apps/server/src/services/auto-loop-coordinator.ts), lines 355–410). Pending plan tasks cause up to three additional agent runs (ExecutionService lines 334–413). This is bounded continuation plus dispatch-level retry, not an independently reasoned blocker/escalation loop.

Plan approval is more robust than a transient dialog alone: a project/feature key owns a promise; timeout rejects by default after 30 minutes; edited plans, approval and rejection are persisted. After a restart, `planSpec.status=generated` can trigger recovery without an in-memory promise ([PlanApprovalService](../repo/apps/server/src/services/plan-approval-service.ts), lines 69–134, 168–215). That is a useful pattern for Wingman's eventual human question handling, although domain questions and conversational routing remain to be built.

### Completion, acceptance and retirement

Completion semantics require care. The sequential task loop recognizes explicit task markers, but if no completion marker appears it still marks the task completed after the stream ends ([AgentExecutor](../repo/apps/server/src/services/agent-executor.ts), lines 523–595). After the incomplete-task retries, the feature can proceed to final status even with tasks remaining. The ordinary feature completion path decides `verified` from a tool-use marker and at least 200 trimmed output characters, unless tests were skipped; insufficient output goes to waiting approval ([ExecutionService](../repo/apps/server/src/services/execution-service.ts), lines 402–478). Its automatic completion event still uses `passes: true` even when routed to waiting approval (lines 516–527). These fields measure execution outcomes imperfectly. They are not evidence that acceptance scenarios passed.

There is a genuine explicit verification action: it runs `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`, stops on the first failure and gives each command a 120-second timeout ([facade](../repo/apps/server/src/services/auto-mode/facade.ts), lines 780–837). This assumes an npm project and does not automatically provide Flutter, Rust or Python acceptance. `executeTestStep` implements a command/test-failure/agent-fix loop, but searches found no caller in the production source; normal pipeline execution simply runs each instruction step and optionally attempts merge ([PipelineOrchestrator](../repo/apps/server/src/services/pipeline-orchestrator.ts), lines 73–158, 474–534). The helper's existence must not be reported as an always-enforced gate.

Session retirement supports rename/update, archive/unarchive and deletion. Archive updates metadata. It does not stop a running invocation. Deletion removes metadata, conversation file and runtime map, without an explicit abort in that method ([AgentService](../repo/apps/server/src/services/agent-service.ts), lines 989–1034). Feature data can be deleted ([FeatureLoader](../repo/apps/server/src/services/feature-loader.ts), lines 493–503). Pipeline auto-merge explicitly leaves the worktree and branch in place ([PipelineOrchestrator](../repo/apps/server/src/services/pipeline-orchestrator.ts), lines 588–598); cleanup is a separate user/worktree operation. No organizational retirement, reassignment or retention policy exists.

## Coordination mechanics and a request trace

Automaker coordinates through shared feature files, dependency IDs, branch/worktree selection and backend events. Its coordination is centrally programmed rather than conversation between project leaders. A representative implemented request is **create and run a feature with a reviewed plan**. The following is a static code trace, not a request exercised during this assessment.

1. The client posts a projectPath plus partial feature. [Create handler](../repo/apps/server/src/routes/features/routes/create.ts) lines 14–38 calls FeatureLoader and emits `feature:created`; [FeatureLoader](../repo/apps/server/src/services/feature-loader.ts) lines 347–394 writes the durable feature record. The human supplies the project context explicitly.
2. A manual [run request](../repo/apps/server/src/routes/auto-mode/routes/run-feature.ts) lines 15–41 starts background execution, or the [auto-loop](../repo/apps/server/src/services/auto-loop-coordinator.ts) lines 207–247 dispatches it when dependencies permit. Neither operation sends a ticket to a persistent staff member.
3. [ExecutionService](../repo/apps/server/src/services/execution-service.ts) lines 173–332 leases the feature, marks it active, resolves its branch/worktree, loads knowledge and chooses its model/provider. The selected provider runs in that directory, sharing repository artifacts rather than a collaboration room.
4. [AgentExecutor](../repo/apps/server/src/services/agent-executor.ts) lines 267–290 detects `[SPEC_GENERATED]` or a fallback spec. Its [approval handling](../repo/apps/server/src/services/agent-executor.ts) lines 613–808 records plan/task state, emits planning events, waits for approval where required and proceeds or rejects. The approval route reaches [facade resolution](../repo/apps/server/src/services/auto-mode/facade.ts) lines 1048–1074, including restarting orphaned approved work.
5. Tasks execute sequentially and update `planSpec` task counters/status (AgentExecutor lines 450–595). Other features can run concurrently, but no peer communication is synthesized from these task updates. A dependency completion can make a later feature eligible on the next dispatcher pass.
6. Optional ordered pipeline prompts consume the prior output, update `pipeline_<id>` statuses and attempt branch merge ([PipelineOrchestrator](../repo/apps/server/src/services/pipeline-orchestrator.ts), lines 85–158). Conflicts produce `merge_conflict` and an event. A return value saying agent resolution is needed is not itself a launched conflict-resolution worker (lines 600–610).
7. Final status, summary and learnings are saved; output/tool events travel over the server event stream. [Output modal](../repo/apps/ui/src/components/views/board-view/dialogs/agent-output-modal.tsx) lines 288–451 subscribes to events and lines 597–684 renders tasks/diffs/summaries/logs. [Event hooks](../repo/apps/server/src/services/event-hook-service.ts) lines 193–217, 389–430 store selected events and invoke enabled matching hooks. This offers notification/integration points, but no organizational conversation or accepted-product handoff.

## Major capabilities beyond the described Wingman product

**A multi-provider development workbench.** Model-prefix routing, native SDK/CLI adapters, compatible API endpoints, phase-specific configuration and provider usage services provide execution choice beyond Wingman's specified Codex organization. The value is selecting different execution backends while keeping one feature UI. The integration cost is preserving provider-specific resume, tools, structured-output and approval semantics; normalized event shapes do not make these semantics identical. See [ProviderFactory](../repo/apps/server/src/providers/provider-factory.ts) lines 87–155 and [facade provider resolution](../repo/apps/server/src/services/auto-mode/facade.ts) lines 259–316.

**Git/worktree integration as a first-class workflow.** The source has branch synchronization, stash, pull/push, cherry-pick, rebase, merge, commit history and PR services rather than merely asking a coding agent to perform Git operations. Pipeline merge uses a direct service call and emits conflicts, leaving the branch/worktree available for investigation ([PipelineOrchestrator](../repo/apps/server/src/services/pipeline-orchestrator.ts), lines 579–629). This could provide Wingman a strong change-delivery surface, but requires project-specific merge policy and explicit interpretation of non-conflict merge failures, which the normal pipeline does not universally turn into hard failure.

**GitHub-aware issue and review analysis.** [Issue validation](../repo/apps/server/src/routes/github/routes/validate-issue.ts) lines 299–345 supports read-only code analysis, structured verdicts, comments and linked PR context. [Review-comment service](../repo/apps/server/src/services/pr-review-comments.service.ts) lines 106–133, 161–240 calls `gh` GraphQL, paginates review threads and associates resolved status. This supplies repository-maintenance inputs beyond Wingman's original Telegram intake. Reuse would require mapping an issue/review thread to a project ticket and responsible persistent agent, and retaining the limits around authenticated CLI availability and pagination.

**Hook automation with durable history and replay.** Selected feature events are persisted even if no hook matches, and matching hooks execute concurrently ([EventHookService](../repo/apps/server/src/services/event-hook-service.ts), lines 389–430). Actions include shell commands, HTTP and ntfy; HTTP headers/body support variable substitution (lines 439–520). [Replay route](../repo/apps/server/src/routes/event-history/routes/replay.ts) lines 1–9, 55–114 can repeat these side effects. This is useful for organizational notifications and external integrations, but is not reliable agent messaging or exactly-once event processing. Wingman would need idempotent consumers, correlation IDs and explicit replay policy before treating it as a coordination bus.

**Task-relevant project memory.** [Memory loader](../repo/libs/utils/src/memory-loader.ts) lines 325–405 ranks Markdown memories by tag/relevance/summary matches, importance and prior usage, takes five and always tries to include `gotchas.md`. Execution records memory usage and learnings ([ExecutionService](../repo/apps/server/src/services/execution-service.ts), lines 496–505). This reduces context overhead and accumulates practical experience. Its success signal inherits the feature-completion limitations, so Wingman should distinguish accepted learning from merely completed execution and add provenance/versioning.

## Distinctive mechanisms and innovation assessment

These are useful mechanisms in this codebase, not claims of historical novelty.

The **combination of durable feature artifacts and lease-counted execution** addresses a practical reentrancy problem: resuming can enter execution through several nested calls without prematurely freeing the running slot. The same feature record can back the board, output viewer, retries and restart recovery. [ConcurrencyManager](../repo/apps/server/src/services/concurrency-manager.ts) lines 81–128 and [RecoveryService](../repo/apps/server/src/services/recovery-service.ts) lines 197–246 show the mechanism. Its limit is scope: process-local leases, feature-only keys and project-level recovery files are not a multi-host scheduler.

The **plan-to-task stream protocol** bridges free-form model output and inspectable workflow state. Spec detection creates a plan; task markers and structured task counters drive progress; optional approval edits steer subsequent execution. [AgentExecutor](../repo/apps/server/src/services/agent-executor.ts) lines 267–290 and 450–595 implements this. It makes a coding invocation legible without requiring a full separate planning agent. Its limit is trust: fallback detection and automatic task completion infer state from output and stream termination, so they need independent verification before representing product truth.

The **approval recovery path** treats the persisted generated plan as the durable checkpoint and reconstructs continuation when the in-memory approval promise is lost ([PlanApprovalService](../repo/apps/server/src/services/plan-approval-service.ts), lines 168–215; [facade](../repo/apps/server/src/services/auto-mode/facade.ts), lines 1060–1074). Wingman could apply the same principle to Telegram questions: persist the question, owning agent and resolution before waiting. Automaker supplies the plan checkpoint pattern, not the messaging correlation layer.

The **relevance/usage-weighted memory selector** is a concrete lightweight alternative to loading all project history or introducing a retrieval database. It is transparent enough to inspect and tune, and conservative enough to always include gotchas. Its lexical matching, small fixed selection and outcome quality limit its reach. It is a promising reusable primitive for Wingman's directives, with acceptance-aware promotion of learnings.

Automaker can be used directly as a human-operated feature workbench around a local project, with real agent execution, backlog management, plan review and detailed change inspection. Its source is particularly useful for Wingman's feature execution adapters, project/branch queueing, output/diff UI, file-backed records and restart/approval recovery patterns. “Directly” here means existing component behavior, not a claim that this checkout was installed or successfully launched.

Place Wingman's organization control plane above these execution primitives:

- Represent profiles, instances, teams, hosts, and project leadership.

Concurrency and recovery need composite keys, durable per-run records, and cross-host ownership. Explicit tests need enforceable gates before automatic verification. Define language-specific commands and product acceptance evidence. Review each provider's autonomy settings separately from plan approval.

- Proactive blocker follow-up.

Use Automaker as an execution/workbench reference or a maintained fork beneath that organization layer. Compare the maintenance cost with selective component reuse.
