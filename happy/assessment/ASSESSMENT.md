# Happy assessment against Wingman

Assessment date: **2026-11-05**. Repository: https://github.com/slopus/happy

Local checkout: `researchs/happy/repo`. Inspected commit: **`76ed3d0abaf5586b1929df77797af8783b38d21c`**. The checkout was clean when inspected. This report assesses that revision through static source and test review; no dependencies were installed, services started, providers invoked, or tests executed.

## Verdict and product boundary

**Happy is a strong source of remote coding-session control and mobile visibility, but this checkout is not a complete persistent development organization.** Its fully traceable runtime wraps independently executing coding harnesses, synchronizes encrypted conversations through a relay, and exposes machine-scoped start/resume/stop and session-scoped approval, file, command, and goal controls. Several machines can register against the same account and execute their own sessions. Those are useful building blocks for Wingman's detailed agent workspace and distributed execution layer.

The revision requires particular care about repository boundaries. The [README](../repo/README.md), lines 41–55, separates this mobile/CLI/relay repository from the desktop application and Happy Agent runtime:

- Desktop: https://github.com/slopus/happy-desktop
- Happy Agent runtime: https://github.com/slopus/happy-agent

The native client here implements substantial **Happy Protocol V2 client behavior**: bot/task creation, nested agents, collaborator messages, joined tasks, questions, retries, todo surfaces, artifacts and a `chief_of_staff` bot target. These are more than marketing claims or design notes. However, their `/v0` execution backend belongs to the separate runtime. This checkout's relay registers `/v1` and `/v3` session APIs, not that runtime's agent/task/bot APIs: [API registration](../repo/packages/happy-server/sources/app/api/api.ts), lines 101–118, versus [native AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 122–172 and 264–286. Client implementation receives credit below; uninspected runtime policy is explicitly uncertain.

Wingman still needs its Telegram Butler, portfolio intake, product and technical leadership, discovery policy, specification and acceptance records, assigned technical tickets, shared management/project rooms, supervision and executive progress synthesis. Subagent presentation and a chief-of-staff identifier do not establish those organizational behaviors.

## Architecture and actual execution

### Two execution paths coexist

**Original CLI/relay path.** The `happy` command chooses a harness, authenticates the installation, ensures a background daemon and starts the runner. For example, generic ACP dispatch resolves an executable and arguments before `runAcp`: [CLI entry](../repo/packages/happy-cli/src/index.ts), lines 361–395. Codex is a real subprocess: [CodexAppServerClient](../repo/packages/happy-cli/src/codex/codexAppServerClient.ts), lines 595–651, launches `codex app-server --listen stdio://` with optional Happy sandbox wrapping. Claude remote execution calls the official agent SDK and passes cwd, resume identifier, model, permissions, tools, MCP configuration and system prompt: [SDK adapter](../repo/packages/happy-cli/src/claude/sdk/query.ts), lines 15–84. Happy does not implement those models' reasoning engines or underlying coding tools.

The daemon controls an execution host. It registers the machine with encrypted metadata/state, creates a realtime client, and installs spawn/resume/stop handlers. See [daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 1002–1034. Remote creation validates the working directory, builds the environment, selects a runner, and starts a detached process. The daemon tracks its PID and waits for a session-registration webhook. Successful `spawn()` alone does not establish a usable conversation. See the same file, lines 277–410 and 530–699. tmux is an optional launch method. It does not provide the coordination or identity model.

**Happy Agent connection path.** Native iOS `AgentClient` makes authenticated requests over an `AgentTransport`, and client records describe bots, tasks, agents, runs and workspaces. [AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 19–75, implements transport/error handling; lines 129–157 create tasks/bots by client-supplied IDs. [Agent wire records](../repo/packages/happy-ios/Sources/HappyCore/Agents/Wire.swift), lines 176–260, distinguish an agent conversation from a bot/task embedding it. A task is therefore not automatically a technical ticket, and a bot is not evidence of an implemented specialist profile in the local CLI.

The native client also implements private-tunnel transport resource separation: [TailcatClients](../repo/packages/happy-ios/Sources/HappyCore/AgentConnection/TailcatClients.swift), lines 19–33 and 86–98, separates realtime, small query and file traffic, using independent node keys and up to eight file clients. That is client networking machinery. It does not prove the external runtime's scheduling, agent delegation or organizational supervision.

### Persistence and synchronization

The relay starts database connectivity, authentication, file storage, Fastify APIs, metrics and presence timeout handling: [server main](../repo/packages/happy-server/sources/main.ts), lines 14–43. [Prisma schema](../repo/packages/happy-server/prisma/schema.prisma), lines 95–160, stores sessions, optional project association, versioned encrypted metadata/agent state, sequenced messages and idempotency keys. Lines 236–253 store separately addressable machines; lines 291–325 store encrypted artifacts and session/machine access keys. The relay is persistent transport/storage, not an autonomous project manager.

Encryption happens at endpoints. [CLI API](../repo/packages/happy-cli/src/api/api.ts), lines 36–88, creates a random session data key, encrypts it for the account public key, and encrypts metadata/state before posting. [RPC manager](../repo/packages/happy-cli/src/api/rpc/RpcHandlerManager.ts), lines 64–95, decrypts request parameters and encrypts responses. Routing still exposes method/scope identifiers to the relay; encrypted content does not mean every operational field is hidden. Local execution hosts necessarily have plaintext and the necessary keys.

Messages are durably appended before interested clients receive updates. [V3 message route](../repo/packages/happy-server/sources/app/api/routes/v3SessionRoutes.ts), lines 123–234, deduplicates `localId`, allocates message sequences in a transaction, inserts ciphertext and emits updates. The CLI consumes messages in sequence and decrypts/routes user text or file events: [ApiSessionClient](../repo/packages/happy-cli/src/api/apiSession.ts), lines 574–649. This is delivery and replay machinery, not shared task assignment or a project-room conversation model.

Native client continuity has a further local layer. [OfflineFile](../repo/packages/happy-ios/Sources/HappyCore/Agents/Offline.swift), lines 14–38 and 83–110, persists agent sidebar/task/bot snapshots and configuration with ordered atomic writes. [IntentOutbox](../repo/packages/happy-ios/Sources/HappyCore/Sync/IntentOutbox.swift), lines 4–67 and 77–95, models durable pending rename/archive/answer/todo intents and transient delivery backoff. The phone can retain pending human actions while disconnected. This does not imply a remote agent continues executing without its host.

There is a real project registry primitive: [project routes](../repo/packages/happy-server/sources/app/api/routes/projectRoutes.ts), lines 161–234, implement authenticated create-or-load by `externalId`, race-safe duplicate creation, change-filtered listing and retrieval. Its data model contains encrypted metadata and sessions, not a product lifecycle, leaders, task dependencies or acceptance state. The [project home derivation](../repo/packages/happy-ios/Sources/HappyCore/Home/ProjectHomeList.swift), lines 5–63 and 188–212, groups work by computer/project/checkout and exposes bots/tasks. That makes projects navigable. It does not supply Wingman's project-management dashboard.

## Agent definition, creation and lifecycle

### What “agent” means here

The CLI's `AgentBackend` is a session transport abstraction, not an employee record. [Interface](../repo/packages/happy-cli/src/agent/core/AgentBackend.ts), lines 15–84 and 104–170, defines session IDs, provider/transport/cwd/environment/MCP configuration, prompt submission, cancellation, events and disposal. [AgentRegistry](../repo/packages/happy-cli/src/agent/core/AgentRegistry.ts), lines 37–88, maps provider IDs to factories. Registration creates a backend object. It does not establish an autonomous standing worker, durable responsibilities or a place in an organization chart.

A **Happy session** is the relay conversation and metadata row. A **provider thread/session** is the model harness's resumable conversation. A **CLI process** connects these and runs the model tool loop. A **daemon** supervises process ownership and remote controls. A provider's **subagent** is represented in protocol events and can be independently executing inside that provider's runtime, but Happy's event mapper does not create a Wingman profile or assign a project ticket. The V2 native model additionally separates **bot**, **task**, **workspace**, **agent conversation**, **run** and **todo**. Its local UI/control code cannot establish the external runtime's durability guarantees.

### Definition and creation

For a CLI session, configuration consists of cwd, provider flavor, model/effort/permission selections, environment, optional custom/appended system prompt and harness-specific tools/plugins/MCP. [Claude enhanced mode](../repo/packages/happy-cli/src/claude/loop.ts), lines 18–50, exposes these fields. Native defaults are provider-oriented, not job-oriented: [AgentDefaults](../repo/packages/happy-ios/Sources/HappyCore/Settings/AgentDefaults.swift), lines 7–39 and 74–100, defines harness enums, retired offerings and permission/model defaults. Renaming or prompting a session “BackendCoder” could shape behavior, but would not create a reusable role schema, agent directory membership or supervision contract.

The daemon validates a requested directory and can return an explicit directory-creation decision, constructs a sanitized environment, chooses a runner and starts a detached child. The child produces metadata containing hostname, OS, machine ID, PID, cwd, flavor, lifecycle state and fork lineage: [metadata factory](../repo/packages/happy-cli/src/utils/createSessionMetadata.ts), lines 91–122. Codex obtains a relay row or reconnects an existing one, then reports its identity/key information to the daemon: [runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 158–245. A relay ID and provider ID are deliberately different and both matter for resume.

V2 creation is materially different. [NewTask](../repo/packages/happy-ios/Sources/HappyCore/Agents/NewTask.swift), lines 3–11 and 57–93, initially creates only a local draft. First send calls `make()`, coalesces simultaneous creation and retries transient failures up to three attempts with the same identity and mutation ID. [AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 129–157 and 614–620, supplies task, agent and workspace IDs. It receives the external runtime's conversation ID. This establishes a concrete creation protocol, not an inspected backend implementation of bot scheduling, specialist roles or persistent memory.

### Execution, tools, permissions and routing

The Codex runner serializes incoming text handling, drains attachments, resolves sticky model/effort/permission overrides and enqueues messages: [runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 262–350. It starts a provider thread on first work, persists its thread ID and awaits tool-using turns; permission and sandbox settings can change per turn without changing the thread: lines 942–1007. Claude alternates between a local interactive terminal launcher and a remote SDK launcher while retaining the same session object: [Claude loop](../repo/packages/happy-cli/src/claude/loop.ts), lines 53–109. These are two ways to control the same work, not two specialist agents collaborating.

The generic ACP path spawns the configured executable, initializes ACP, creates a session, submits prompts, forwards tool/status events, handles mode/model changes and cancels/disposes the backend. Evidence: [AcpBackend](../repo/packages/happy-cli/src/agent/acp/AcpBackend.ts), lines 374–405, 709–837 and 1241–1325; [ACP runner](../repo/packages/happy-cli/src/agent/acp/runAcp.ts), lines 870–970. ACP initialization advertises file read/write capabilities as false (AcpBackend lines 714–722), so it should not be inferred that every backend receives a universal Happy filesystem API through ACP. Tools remain provider-specific. The separate mobile common RPC layer exposes bash/read/write/list/search/diff operations: [registerCommonHandlers](../repo/packages/happy-cli/src/modules/common/registerCommonHandlers.ts), lines 168–176, 262–348 and 492–547.

Codex permission modes map explicitly to approval policies and sandboxes: [executionPolicy](../repo/packages/happy-cli/src/codex/executionPolicy.ts), lines 17–75. Happy-managed sandboxing transfers enforcement to the outer sandbox; otherwise `auto`, read-only, workspace and unrestricted modes differ. Sandbox initialization can fail and continue without the outer sandbox ([CodexAppServerClient](../repo/packages/happy-cli/src/codex/codexAppServerClient.ts), lines 612–623). This is a material deployment boundary to validate before using it for unattended workers. The permission handler stores pending promises and publishes requests; human responses are correlated to IDs and copied into completed state. A permission transcript is not a product decision log or management escalation policy.

RPC method names are scoped as `machineId:method` or `sessionId:method`: [RpcHandlerManager](../repo/packages/happy-cli/src/api/rpc/RpcHandlerManager.ts), lines 36–47 and 137–138. The relay finds a connected endpoint in an account-scoped Socket.IO room, waits briefly through reconnection and forwards encrypted parameters to one target: [rpcHandler](../repo/packages/happy-server/sources/app/api/socket/rpcHandler.ts), lines 128–220. A room here is a network routing room, not Wingman's human-readable management/project chat room.

### Concurrency, persistence, scheduling and recovery

Sessions can run concurrently, including on independently registered hosts. The daemon's `resumesInFlight` map coalesces attempts for the **same** Happy session. It does not serialize unrelated sessions. It checks live/stopping/registering ownership and refuses ambiguous persisted live owners, because PIDs can be reused: [daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 725–760. There is no local workload allocator, shared-worktree merge coordinator or agent-assignment scheduler. Two launched sessions given the same directory can therefore require coordination outside this controller.

Local resume records persist encryption information, metadata, sequence/version values, PID context and last-known-live time. [Persistence](../repo/packages/happy-cli/src/persistence.ts), lines 419–531, retains stopped records for fourteen days from last known liveness, preserves still-running records and writes via temporary-file rename. The relay message history and the provider's own saved thread are separate layers; keeping the relay record alone does not reconstruct missing provider state. `buildResumeLaunch` supports Claude and Codex and fails for missing provider IDs or unsupported flavors: [resume mapping](../repo/packages/happy-cli/src/resume/handleResumeCommand.ts), lines 43–89. Daemon resume can use the client's encrypted fallback and fetch missing metadata, but its fallback fetch covers the recent 150-session listing: [daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 763–861. This is a specific recovery limit, not universal durable-agent restoration.

Timers maintain transport/process health. The daemon's roughly sixty-second loop prunes dead processes, detects an on-disk CLI replacement, hands off to a fresh daemon and writes a heartbeat. It never reads product tickets to ask why a worker is blocked. The Codex runner's keepalive and goal-state APIs expose provider execution continuity, not scheduled portfolio reviews. Native V2 `wait`, retry and status-line fields suggest richer external runtime behavior, but client decoders cannot verify scheduling policy or wake semantics.

Failure handling is layered. Relay create/network failures can use offline reconnection ([runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 206–227). RPC lookup has a reconnect grace window and bounded request timeout; no durable management queue is implied. Codex process generations are tracked so stale child exits cannot invalidate a replacement connection: [CodexAppServerClient](../repo/packages/happy-cli/src/codex/codexAppServerClient.ts), lines 644–673. A failed coding turn is reported and state reset, not automatically converted to an assigned remediation ticket. V2 clients expose retry or model-switch resolution endpoints ([AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 417–428); that backend's recovery strategy remains unverified here.

### Interruption, completion and retirement

Turn abort and process termination are separate. [Codex abort](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 418–460, resolves pending permissions as abort, requests an interrupt and force-restarts the app-server after a three-second grace period if needed, attempting to resume the previous thread. A stopped inference can leave the session alive for later prompts. [Daemon stop](../repo/packages/happy-cli/src/daemon/run.ts), lines 872–955, cancels pending resumes, signals the whole detached process group on Unix where possible, and retains ownership until exit/liveness confirms death. The Windows/external-process fallback has narrower signaling behavior. Successful stop acknowledgement should not be interpreted as proof every descendant has already exited.

Turn completion marks thinking false, resets permission/reasoning/diff state and emits readiness only when the queue is idle: [runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 1001–1036. It does not compare output against product scope, execute a mandatory integration suite, request business acceptance or stop a project after delivery. Session cleanup sends death, flushes/closes the relay client, disconnects the provider, stops MCP and clears terminal/heartbeat resources: lines 1041–1091. Provider history and project files are not thereby deleted.

Native V2 APIs can archive tasks/bots/agents and leave a joined task: [AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 198–220. Relay deletion is separately implemented: [sessionDelete](../repo/packages/happy-server/sources/app/session/sessionDelete.ts), lines 22–118, verifies ownership, deletes messages/usage/access keys/session, emits an update and attempts blob cleanup after commit. Archiving, stopping a process, expiring local resume keys and deleting relay history are distinct actions. No standing-role retirement or reassignment process exists in the inspected runtime.

## Coordination mechanics and traced request

One implemented coordination path starts Codex on a selected remote machine. The human then sends work, answers a tool approval, and observes completion. The following is a static source trace, not a runtime exercise:

1. Native [MachineActions](../repo/packages/happy-ios/Sources/HappyCore/Machines/MachineActions.swift), lines 21–43, builds `spawn-happy-session` for a selected machine and normalizes success/pending/directory-approval/error results.
2. The relay [RPC handler](../repo/packages/happy-server/sources/app/api/socket/rpcHandler.ts), lines 160–220, locates the machine-scoped method inside the authenticated user's room and forwards the ciphertext. This can cross server replicas and host connections. It is not SSH or a local-only terminal invocation.
3. [ApiMachine](../repo/packages/happy-cli/src/api/apiMachine.ts), lines 184–207, unwraps spawn parameters and calls the daemon callback. The daemon validates the path/environment, chooses `codex`, starts a detached Happy child and awaits registration ([daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 277–325 and 530–699).
4. [runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 158–245, creates/reconnects the Happy session, records metadata and registers with the daemon. The caller gets a Happy session ID. The underlying provider thread ID is added after thread creation.
5. User text reaches the encrypted `/v3/sessions/:id/messages` append route. [V3 routes](../repo/packages/happy-server/sources/app/api/routes/v3SessionRoutes.ts), lines 148–234, persist/deduplicate and emit the update; [ApiSessionClient](../repo/packages/happy-cli/src/api/apiSession.ts), lines 574–649, decrypts/routes it; [runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 295–350 and 942–1007, resolves mode, queues work and submits the turn.
6. A provider approval becomes a pending ID-addressed request through [CodexPermissionHandler](../repo/packages/happy-cli/src/codex/utils/permissionHandler.ts), lines 75–114. Human response arrives through the session's `permission` RPC and resolves its promise; [BasePermissionHandler](../repo/packages/happy-cli/src/utils/BasePermissionHandler.ts), lines 75–118, moves it into completed state.
7. Provider text/tools/subagent events become unified protocol envelopes ([runCodex](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 777–805), are encrypted/appended and become inspectable history. Turn completion/readiness is local runner state, not shared product acceptance.

There is **no ticket dependency, ProductMaster consultation or management escalation** in that path. Correlation uses account, machine, session, provider thread and tool-call IDs. Shared state is conversation/state blobs plus project association, rather than a shared organizational tracker. Human choices address the originating session directly.

The V2 client adds a more collaborative representation. [Conversation](../repo/packages/happy-ios/Sources/HappyCore/Agents/Conversation.swift), lines 7–25, differentiates collaborator reports from the focal agent; [Agents](../repo/packages/happy-ios/Sources/HappyCore/Agents/Agents.swift), lines 18–64, reconciles independently versioned parent/child snapshots and removes archived children. It also submits steering with `delivery: "steer"` ([AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 343–379). The external daemon determines when that steering enters a run, who may message whom, how work is delegated and whether collaboration survives failures. This report does not infer those rules from comments or client JSON alone.

## Major capabilities beyond Wingman's described product

**Endpoint-encrypted remote coding control.** Per-session/machine encryption and encrypted RPC are a concrete transport/security feature beyond Wingman's stated requirements. They permit a relay to synchronize data without owning conversation plaintext. Wingman could reuse the endpoint/relay split, but its shared tracker, organizational identity and summaries would need deliberate key access and authorization design. An encrypted relay cannot independently compute plaintext executive summaries. Evidence: [API key wrapping](../repo/packages/happy-cli/src/api/api.ts), lines 36–88 and 150–165; [RPC encryption](../repo/packages/happy-cli/src/api/rpc/RpcHandlerManager.ts), lines 64–95.

**Harness portability and subscription-compatible sessions.** The local architecture supports multiple execution protocols, arbitrary ACP commands, Claude's official SDK and Codex app-server. Wingman explicitly starts from autonomous Codex roles. A portable host interface could add other harnesses later. This is not behaviorally transparent interchangeability: resume support, permission modes, provider tools and subagent semantics vary, and remotely spawning an arbitrary ACP command is not supported by the daemon's finite runner switch. Evidence: [ACP resolver](../repo/packages/happy-cli/src/agent/acp/acpAgentConfig.ts), lines 17–52; [daemon switch](../repo/packages/happy-cli/src/daemon/run.ts), lines 534–557; [resume mapper](../repo/packages/happy-cli/src/resume/handleResumeCommand.ts), lines 43–89.

**Provider-native fork, duplicate and rewind support.** [ApiMachine](../repo/packages/happy-cli/src/api/apiMachine.ts), lines 228–348, implements Claude/Codex fork and rewind-point operations. [Daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 354–371, preserves lineage and requests provider-history backfill. Wingman asks for conversation forking, but this explicit provider-history/rewind bridge goes further than a simple copied chat. It enables alternative investigations with retained context. It does not isolate project files or automatically reconcile parallel code changes; conversation lineage is not a Git merge strategy.

**Remote artifact application and browser access.** The V2 client fetches versioned artifact manifests/files, bounded byte ranges and an artifact API ([AgentClient](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 480–538). [BrowserTunnel](../repo/packages/happy-ios/Sources/HappyCore/Browser/BrowserTunnel.swift), lines 34–85, authenticates a workspace proxy and opens CONNECT tunnels; [BrowserPolicy](../repo/packages/happy-ios/Sources/HappyCore/Browser/BrowserPolicy.swift), lines 8–15 and 55–80, constrains routing and artifact paths/origins. This can let a phone inspect an agent host's localhost application and interactive generated deliverables. The client side is implemented here; serving, workspace authorization and lifecycle depend on the external runtime. Wingman could use this for acceptance previews, but would still need its own test and acceptance workflow.

**Voice-based navigation and steering across conversations.** [CallTools](../repo/packages/happy-ios/Sources/HappyCore/Call/CallTools.swift), lines 4–55, defines list/context/open/send tools for a hosted voice agent, including explicit delivery uncertainty. This is broader than Telegram text intake. It can make mobile monitoring hands-free, but is not a Butler implementation: it does not answer approvals/questions, and “queued” means queued on the device, not read by the worker. The hosted voice agent, its service configuration and network operation were not verified.

**Versioned collaborative todo surfaces.** [Todo routes](../repo/packages/happy-ios/Sources/HappyCore/Todos/AgentClient+Todos.swift), lines 27–69, include idempotent creation, optimistic concurrency through `If-Match`, deletion, reordering and revision traversal. These are useful shared-work interfaces beyond a coding transcript. Their backend is external, and their local data model has author/status rather than Wingman agent assignee, dependency, acceptance and escalation fields. Adopting the surface would not eliminate the need for ProjectTracker.

**Self-hostable relay with embedded storage.** [Standalone server](../repo/packages/happy-server/sources/standalone.ts), lines 24–32, 65–108 and 111–135, supports local PGlite persistence and migration application; [server library](../repo/packages/happy-server/sources/index.ts), lines 17–49, starts the same API with explicit storage/configuration. This provides a deployment choice beyond Wingman's specified experience and can keep the relay under the operator's control. It still needs operational validation, backups, authentication configuration and separately installed coding harnesses. It is not a bundled implementation of the external Happy Agent `/v0` runtime or a self-contained organizational service.

## Distinctive mechanisms and grounded innovation

No historical novelty or industry uniqueness is claimed. These mechanisms are distinctive and useful within the inspected design:

1. **Session control survives host-controller replacement without conflating logical work and PID ownership.** Persisted keys/metadata, reconnect-in-place environment, single-flight resume, boot-aware liveness and late ownership rechecks cooperate to avoid duplicate producers. The daemon even retains a stopping owner until confirmed exit. This matters to Wingman because a manager restart must not start two workers against one task. Limits are explicit: incomplete provider metadata can prevent resume, fallback listing is bounded, local resume records expire and the mechanism is session-scoped rather than task/role-scoped. Evidence: [daemon](../repo/packages/happy-cli/src/daemon/run.ts), lines 725–861 and 872–955; [persistence](../repo/packages/happy-cli/src/persistence.ts), lines 444–512.
2. **An encrypted durable message log and independent RPC routing cooperate without requiring the relay to understand tool payloads.** Sequenced/idempotent appends handle conversation delivery; scoped encrypted RPC handles immediate host controls. Cross-replica Socket.IO lookup adds reconnect grace and disconnect detection. Wingman can borrow the separation between records and control traffic, but still needs semantic task/decision events and durable manager commands. Evidence: [V3 append](../repo/packages/happy-server/sources/app/api/routes/v3SessionRoutes.ts), lines 148–234; [RPC router](../repo/packages/happy-server/sources/app/api/socket/rpcHandler.ts), lines 7–34 and 178–238.
3. **Native creation uses a stable identity before the remote object exists.** A draft task already has task/workspace/conversation IDs; simultaneous first sends share one creation and retries reuse that identity. This prevents an optimistic mobile interface from producing duplicate work merely because a network acknowledgement was lost. It could be adapted to Wingman task dispatch and worker creation. The locally inspected guarantee is client behavior and a contract with the remote runtime, not proof of server-side idempotency. Evidence: [NewTask](../repo/packages/happy-ios/Sources/HappyCore/Agents/NewTask.swift), lines 30–93; [creation payload](../repo/packages/happy-ios/Sources/HappyCore/Agents/AgentClient.swift), lines 129–157.
4. **Independent child versioning avoids overwriting a newer worker with an older parent snapshot.** [Agents](../repo/packages/happy-ios/Sources/HappyCore/Agents/Agents.swift), lines 18–64, stores agents separately, reconciles version transitions, detects a missing predecessor and recomposes the tree on read. This is a concrete solution to nested agent visibility under concurrent updates. Its tree/depth and version rules do not provide organizational authorization, work scheduling or shared-resource isolation.
5. **Interrupt is a recovery workflow, not only a stop signal.** The Codex path first aborts pending human decisions, attempts graceful turn interruption and can restart/resume the backend when commands fail to settle. This can keep a mobile user in control of long-running tools while preserving the logical conversation. It is provider-specific and can fail to restore the prior thread. The code reports that possibility instead of assuming success. Evidence: [Codex abort](../repo/packages/happy-cli/src/codex/runCodex.ts), lines 418–460.

## Practical fit for Wingman

**Use directly as reference or a component:** remote session/machine routing, provider event normalization, mobile approval/questions, file/diff/command drill-down, per-host detached execution, encrypted synchronization and carefully guarded resume/stop. The local relay/CLI path is sufficient to study these without relying on the separately hosted product. Its existing project association can anchor a project selector, but should remain distinct from product-management state.

**Adapt deliberately:** define Wingman's durable `agent instance` above Happy's session/provider process, with role/profile, project, team, assignment, host, current conversation and recovery policy. Add authenticated worker-to-worker communication and a shared tracker whose records have real assignees, blockers, dependencies and acceptance criteria. Associate Happy messages/tool calls with those records rather than trying to infer organization state from active/thinking flags. Reconcile logical session ownership with task ownership before unattended restart; evaluate sandbox failure behavior and host filesystem isolation. If adopting V2 client features, assess the Happy Agent runtime separately before assuming its bots/tasks implement standing organizational roles.

**Build:** Telegram Butler and cross-project intake, ProductMaster/TechMaster discovery/planning duties, SCOPES/SPECS/HARNESS knowledge conventions, management/project collaboration rooms, proactive supervision, integration-test and acceptance transitions, delivery stop conditions, extensible organizational directory, and linked executive current/recent/next/blocker timelines. Multiple-host connectivity is available; coherent project placement, shared records and agent collaboration across the Mac and Endeavour still require Wingman policy and infrastructure.

The most defensible adoption strategy is to treat Happy as a **coding-session access and control layer** beneath Wingman, with the organizational model kept explicit. Replacing that model with session titles, native task labels or provider subagents would leave the hardest Wingman requirements unsatisfied.
