# Ralph Orchestrator assessment against Wingman

Assessment date: 2026-11-05. Repository: https://github.com/mikeyobrien/ralph-orchestrator

Local checkout: `researchs/ralph-orchestrator/repo`. Inspected commit: `b5789dfbb25bd4aa65ce565c756d95acc8c42f76`. Workspace package version: 2.10.1; MIT license ([manifest](../repo/Cargo.toml), lines 20–29). This report assesses the local revision, not current upstream behavior. Source files were read only; no dependencies, services, agents, or test suites were started.

**Fit verdict:** a strong candidate for Wingman's bounded coding-workflow execution layer, particularly fresh-context handoffs, local parallel work, Telegram interaction, durable artifacts, and configurable verification gates. It is not a substitute for Wingman's persistent organization. Its normal hats are role instructions for successive invocations of a constant Ralph coordinator, not a directory of independently living ProductMasters, TechMasters, and workers. Waves and separate loops do launch real concurrent backend processes. Wingman would still need its organization, portfolio routing, durable agent identities/conversations, collaboration rooms, supervision, multi-host dispatch, and connected executive views.

A material revision-specific qualification: the default dashboard backend is now the Rust RPC API. Its task `run` and planning `start`/`resume` handlers persist state but do not launch agents in the inspected implementation. The Rust Builder collection-run path does launch real autonomous loops. A separate legacy Node backend has task queue/process execution. These distinct paths must not be combined into an imaginary fully integrated task/planning capability.

## Architecture and execution model

The CLI is the executable coordinator. Its dispatch includes run/resume, events, tools, waves, loops, interactive planning/code-task SOPs, web, bot, MCP, and TUI entry points ([main.rs](../repo/crates/ralph-cli/src/main.rs), lines 638–708 and 1196–1285). `run_command` resolves configuration, applies preflight, chooses primary versus worktree context through a workspace lock, and enters the loop runner ([main.rs](../repo/crates/ralph-cli/src/main.rs), lines 1474–1560 and 1648–1858). The core crate owns event routing, configuration, hats, tasks, memories, verification parsing, loop state and merge records; adapters launch existing coding-agent CLIs or ACP backends. Ralph supplies orchestration, while the chosen coding agent supplies actual filesystem/shell/browser capabilities.

The runtime initializes an objective, current loop ID, event-file marker and persisted state. Each iteration builds a prompt, invokes a backend and reads emitted JSONL events. Gate evaluation determines whether to continue or stop ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 121–275, 2295–2315, 2520–2710). The important architectural fact is explicit in `next_hat`: with custom hats, the executor returned is still `ralph`; custom hats define pub/sub topology and the instructions active in the next prompt. `build_prompt` consumes pending events, determines active hat IDs, injects their instructions and the original objective, and prepends skills, scratchpad and ready tasks ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 849–910 and 1132–1278). A “multi-agent” sequential preset is consequently a sequence of fresh role-conditioned coding-agent invocations. This can provide separation of reasoning, but not independent simultaneous conversations or persistent people.

There are two real process-concurrency mechanisms. A second `ralph run` in the same locked repository creates an isolated Git worktree unless exclusive mode or configuration prevents it. The registry records a loop's ID, PID, prompt, worktree and workspace; liveness is local PID/process inspection ([main.rs](../repo/crates/ralph-cli/src/main.rs), lines 1660–1765; [loop_registry.rs](../repo/crates/ralph-core/src/loop_registry.rs), lines 44–180). Within a loop, wave dispatch launches separate workers with a semaphore limit, individual event files, backend overrides and wave IDs, then collects results ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 5385–5585). These are real coding-agent instances with bounded lifetimes, not a standing team.

Durable execution state lives mainly under `.ralph/`: tasks, Markdown memories, specs, code-task artifacts, events, loop-state/history, lock/registry and merge-queue files. Worktree contexts share **memories, specs and code-task documents** through symlinks. Runtime `agent/tasks.jsonl` and scratchpads are resolved within each loop's workspace. The code explicitly distinguishes runtime tasks from shared `.ralph/tasks/` documents ([loop_context.rs](../repo/crates/ralph-core/src/loop_context.rs), lines 180–241, 392–493 and 566–575). This is not one organization-wide ProjectTracker even though selected knowledge is shared.

The dashboard is a React application with task list/detail, planning, workflow builder and settings routes ([App.tsx](../repo/frontend/ralph-web/src/App.tsx), lines 12–29). Its compatibility object named `trpc` now calls versioned RPC methods via `rpcCall`, rather than proving use of the legacy tRPC backend ([trpc.ts](../repo/frontend/ralph-web/src/trpc.ts), lines 30–78 and 210–285). `ralph web` defaults to `cargo run -p ralph-api`; `legacy_node_api` selects the Node backend ([web.rs](../repo/crates/ralph-cli/src/web.rs), lines 418–480). The Rust runtime instantiates workspace-scoped task, loop, planning, collection, config, preset, robot and stream domains ([runtime.rs](../repo/crates/ralph-api/src/runtime.rs), lines 36–108). Its server starts an event-file watcher, not a task executor ([transport.rs](../repo/crates/ralph-api/src/transport.rs), lines 76–109).

Specifically, Rust tasks are stored in `.ralph/api/tasks-v1.json`; `run` calls `queue_task`, which marks a task pending and persists it. Planning start writes metadata/artifact directories/conversation files; resume changes status. No agent-spawn step occurs in those handlers or their dispatch paths ([task_domain.rs](../repo/crates/ralph-api/src/task_domain.rs), lines 89–106, 298–305 and 441–478; [planning_domain.rs](../repo/crates/ralph-api/src/planning_domain.rs), lines 195–259; [runtime/dispatch.rs](../repo/crates/ralph-api/src/runtime/dispatch.rs), lines 80–132 and 214–230). Legacy Node code instead contains SQLite queue storage, dispatcher, task bridge, detached-process supervisor and planning child processes ([schema.ts](../repo/backend/ralph-web-server/src/db/schema.ts), lines 17–79; [Dispatcher.ts](../repo/backend/ralph-web-server/src/queue/Dispatcher.ts), lines 330–383; [ProcessSupervisor.ts](../repo/backend/ralph-web-server/src/runner/ProcessSupervisor.ts), lines 44–120; [PlanningService.ts](../repo/backend/ralph-web-server/src/services/PlanningService.ts), lines 178–196 and its session/process methods). Launching the legacy server does not establish that the migrated frontend works against it; that compatibility was not exercised.

The Builder uses the Rust API operation `collection.run` to export a saved graph to `.ralph/collections/{id}-run.yml`. It spawns `ralph run -H <config> -a -p <prompt>`. A bounded stderr tail supports early failure reporting. The operation returns the PID and starting hat, then eventually reaps the child ([collection_domain.rs](../repo/crates/ralph-api/src/collection_domain.rs), lines 420–610; [dispatch](../repo/crates/ralph-api/src/runtime/dispatch.rs), lines 314–324; [BuilderPage.tsx](../repo/frontend/ralph-web/src/pages/BuilderPage.tsx), lines 413–492). This is a concrete dashboard-to-agent execution path. It is separate from task queue execution and planning-session startup. The report credits the actual distinction.

## Agent definition and complete lifecycle

### Definition, creation and identity

A hat is a configuration object keyed by a HatId, not a deployed agent. `HatConfig` gives it name, description, triggers, publications, instructions, optional backend/arguments, maximum activations, scratchpad override, disallowed tools, timeout, concurrency and aggregation ([config.rs](../repo/crates/ralph-core/src/config.rs), lines 1947–2118). The registry translates these into protocol hats and keeps configuration separately. Empty hats configuration leaves a universal Ralph fallback. The coordinator cannot be configured away ([hatless_ralph.rs](../repo/crates/ralph-core/src/hatless_ralph.rs), lines 1–35; [hat_registry.rs](../repo/crates/ralph-core/src/hat_registry.rs), lines 25–60).

A loop is a longer-lived objective/execution context with its own runtime state, IDs, prompt and process. A wave worker is a temporary backend instance identified by wave ID/index. Tasks are durable work records. Specs and code-task Markdown files are artifacts. None of these automatically becomes a persistent employee identity. Wingman should keep those concepts separate if adopting this execution engine.

Creation begins through run, bot, Builder collection execution or the legacy queue. The CLI chooses workspace and lock ownership. An available primary lock means in-place work; contention can block under exclusive mode, fail if parallel execution is disabled, or allocate a named worktree/branch and register its loop ([main.rs](../repo/crates/ralph-cli/src/main.rs), lines 1648–1765). Resume reuses a marker or explicit loop ID so old tasks remain owned by the continued work. Fresh runs create a new timestamped events file and clear stale scratchpad content; continue attempts restoration instead ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 190–252).

### Execution, tools, permissions and routing

Each ordinary iteration starts from newly assembled context: objective, active roles, pending event payloads, ready tasks, skills and disk artifacts. Tool execution is delegated to the installed backend. Adapter factories cover Claude, Kiro/ACP, Gemini, Codex, Amp, Copilot, Pi/OMP, Roo, OpenCode, Forge and custom commands; behavior differs by backend ([cli_backend.rs](../repo/crates/ralph-adapters/src/cli_backend.rs), lines 118–174, 294–345 and 648–773). The current Codex factory invokes `codex exec --yolo` and Claude uses `--dangerously-skip-permissions` in autonomous execution (lines 160–174 and 357–365). Those are consequential execution defaults, not an organization permission model.

Hat tool restrictions are primarily prompt instructions. The file-modification audit checks `git diff --stat HEAD` after an iteration when Edit/Write is disallowed and emits a scope-violation event. It is detection, not a sandbox or rollback, and should not be interpreted as preventing all filesystem writes ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 2077–2140). Routing follows topic subscriptions, wildcard matching and publication contracts; unknown/unhandled situations can return to Ralph. Event-publishing instructions require `ralph emit`, so a natural-language claim that work was handed off is insufficient ([hat_registry.rs](../repo/crates/ralph-core/src/hat_registry.rs), lines 118–178; [hatless_ralph.rs](../repo/crates/ralph-core/src/hatless_ralph.rs), lines 71–110).

### Concurrency and persistence

Waves let one configured role process several payloads concurrently. The runner resolves the role's backend, acquires semaphore permits, builds a focused worker prompt and writes each worker's events separately. It injects `RALPH_WAVE_WORKER`, `RALPH_WAVE_ID`, `RALPH_WAVE_INDEX` and `RALPH_EVENTS_FILE`, collects successes/failures and merges results into the main stream. Aggregation tracks expected count and deduplicates indices ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 5385–5685; [wave_tracker.rs](../repo/crates/ralph-core/src/wave_tracker.rs), lines 12–48 and 93–180). Workers share the workspace: code-editing waves need careful ownership conventions; per-worker event isolation does not isolate source edits.

Parallel loops provide stronger source isolation through Git worktrees. Shared memories/specs/code-task documents remain available, while loop-local events, scratchpads and runtime task tracking reduce interference. TaskStore takes an exclusive lock, reloads before mutation, and saves; memory operations similarly use file locks ([task_store.rs](../repo/crates/ralph-core/src/task_store.rs), lines 52–142; [memory_store.rs](../repo/crates/ralph-core/src/memory_store.rs), lines 102–142). These local filesystem mechanisms do not establish distributed consistency across the Mac and Endeavour.

Resume restores saved counters, cumulative cost and state, hydrates historical topics, and replays events appended after the last `loop.terminate`; older records remain history rather than rerunning completed phases ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 503–564 and 912–995). This is reconstruction from durable work state, not resuming the same model's complete conversation. The legacy web runner adds detached processes with file-based logs/status and reconnect behavior; its queue reloads pending tasks and can mark crashed running tasks failed ([ProcessSupervisor.ts](../repo/backend/ralph-web-server/src/runner/ProcessSupervisor.ts), lines 44–120; [PersistentTaskQueueService.ts](../repo/backend/ralph-web-server/src/queue/PersistentTaskQueueService.ts), lines 88–119).

### Scheduling, interruption and recovery

There is no inspected organization scheduler assigning recurring ProjectMaster supervision. The loop runs while work/events are available; persistent mode suppresses completion and reinjects task.resume. Telegram daemon waits for external messages between loops, while check-ins report progress during active iteration handling. These mechanisms can support a supervisor implemented above Ralph, but are not that supervisor.

Interruption uses signal watchers and process-group termination, graceful `loop.cancel`, stop/restart marker files and lifecycle suspension. RPC distinguishes guidance/follow-up intended for the next iteration from urgent steering intended for the current work; urgent markers also gate emission until steering is addressed ([rpc_stdin.rs](../repo/crates/ralph-cli/src/rpc_stdin.rs), lines 84–174; [loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 612–660 and 1030–1045). This is useful control without assuming every provider supports identical mid-generation interaction. API task cancel, by contrast, updates its stored record. It does not prove a running child was stopped.

Recovery is bounded. Iteration count, elapsed runtime, cumulative cost, consecutive failures, repeated malformed events, abandoned-task redispatch and stale event signatures can terminate work ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 636–704). Missing outputs/events can trigger fallback routing; hat activation limits can publish exhaustion events. Hook handling additionally supports retries with backoff or waiting for a resume signal, then durable suspension if necessary ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 1887–2000; [loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 3291–3705). These stop loops from consuming resources indefinitely, but do not diagnose every product blocker or reassign work to another durable agent.

### Completion, acceptance and retirement

Completion is an emitted promise (or guarded text fallback), not merely backend exit zero. The core rejects completion if required event topics were not seen, human guidance is unacknowledged, or runtime tasks remain open; persistent mode suppresses it altogether. Open-task verification failure is checked as `if let Ok(false)`, so this branch itself is not a fail-closed guarantee for every task-store read error. Required topics establish phase occurrence, not semantic truth or order of all desired work ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 734–839).

Task terminality is also important: both Closed and Failed are terminal. A dependency is ready only when its blockers are Closed ([task.rs](../repo/crates/ralph-core/src/task.rs), lines 11–28 and 111–122). A loop with no remaining open tasks is therefore not automatically proof that every requested product requirement succeeded. Presets use critics/finalizers/validators to interpret acceptance, but Wingman would need to preserve separate delivered, failed, blocked and human-accepted outcomes.

Successful completion runs landing/handoff and may auto-commit work, enqueue a worktree for merge or leave it for manual handling. Primary completion processes queued merges through separate merge-Ralph execution; merge states include queued, merging, merged, needs-review and discarded ([loop_completion.rs](../repo/crates/ralph-core/src/loop_completion.rs), lines 154–226; [loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 837–900 and 4802–4979; [merge_queue.rs](../repo/crates/ralph-core/src/merge_queue.rs), lines 119–175). The registry supports deregistration/stale cleanup, and loops discard removes worktree/artifacts while preserving explicit queue state ([loop_registry.rs](../repo/crates/ralph-core/src/loop_registry.rs), lines 242–288; [loops.rs](../repo/crates/ralph-cli/src/loops.rs), lines 710–747). This is retirement of processes/workspaces, not archival of a permanent agent's identity and conversation.

## Coordination mechanics and a concrete code trace

The following is a trace of the shipped `wave-review` request path, not a live execution claim. It follows an actual preset and implementation rather than inventing a management conversation.

1. A user launches a code-review objective using `presets/wave-review.yml`. CLI configuration resolves the preset/prompt. The preset sets `review.start`, completion topic `review.complete`, a coordinator, concurrent reviewer and aggregator ([preset](../repo/presets/wave-review.yml), lines 1–37). The event loop stores the objective and publishes the start topic ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 849–877).
2. Topic subscriptions activate the coordinator role within Ralph's next fresh prompt. The coordinator is instructed to split the request into Rust/frontend/documentation perspectives and call `ralph wave emit review.perspective --payloads ...`, rather than a provider-native subagent tool ([preset](../repo/presets/wave-review.yml), lines 29–62). The wave CLI records correlated events and returns a wave ID ([wave.rs](../repo/crates/ralph-cli/src/wave.rs), lines 1–85).
3. The loop reads emitted records, separates wave events and detects a target role with concurrency enabled. `handle_wave_events` invokes the wave execution path. The reviewer has concurrency 3 and timeout 600 ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 2295–2310, 2520–2535 and 5173–5380; [preset](../repo/presets/wave-review.yml), lines 64–71).
4. Separate backend workers receive their own focused role/payload and events file. Semaphore permits bound concurrency. They emit `review.done`; worker failures and partial output are collected into the wave result, not treated as an independent ongoing conversation ([loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 5385–5685). `WaveTracker` counts success or failure per index and ignores duplicate indices ([wave_tracker.rs](../repo/crates/ralph-core/src/wave_tracker.rs), lines 56–80 and 111–168).
5. Results are merged into the main event stream. The synthesizer subscribes to `review.done`, has wait-for-all aggregation with timeout 300, and is instructed to synthesize a report at `.ralph/agent/review-report.md` ([preset](../repo/presets/wave-review.yml), lines 93–136). Its event payloads are the handoff. No room, shared conversational transcript or peer negotiation is involved. The synthesizer's configured restrictions include Edit while its instructions also request writing an artifact, illustrating why prompt-level role rules need integration review.
6. `review.complete` becomes the completion request and passes through the normal termination safeguards. The runner records termination/landing and returns control to the caller. This gives a bounded scatter/gather review with durable evidence. It does not recruit named permanent reviewers into a team.

Human decisions are a parallel event path. An active agent emits `human.interact`. The core sends a question through the robot service, waits for a response or timeout, then publishes the corresponding event. Telegram's handler correlates reply-to message IDs, explicit `@loop-id` or the primary loop, and writes into that loop's current event file ([handler.rs](../repo/crates/ralph-telegram/src/handler.rs), lines 29–144). Unsolicited input becomes human.guidance, is persisted/injected into prompts and must be acknowledged before completion. The daemon can start another objective while idle, but it does not infer which durable product owns the message.

Tickets and dependencies are separate coordination channels. Runtime tasks provide ready-work selection and stable task keys; PDD carries task IDs/keys in phase payloads and asks agents to update artifacts. This is effective coordination through records/events, with the tradeoff that synchronization and semantic integrity depend on task discipline and model behavior. Chat history, named participants and management escalation are not supplied by the event bus.

## Major additional capabilities and integration consequences

**Backend portability and mixed-provider phases.** Per-hat backend overrides and common execution adapters make it possible to use different coding products for research, implementation and review without rewriting the event workflow. Custom commands extend this further ([config.rs](../repo/crates/ralph-core/src/config.rs), lines 1947–2007; [cli_backend.rs](../repo/crates/ralph-adapters/src/cli_backend.rs), lines 294–345). Wingman's stated all-Codex organization does not require this breadth. Reusing it adds adapter/version/authentication variability and requires normalization of usage, tools and cancellation behavior.

**Local change integration and remote review delivery.** Worktree completion feeds an event-sourced merge queue, launches a merge agent, supports retry/needs-review/discard, and offers branch diff, publish-review and rebase operations ([merge_queue.rs](../repo/crates/ralph-core/src/merge_queue.rs), lines 119–175 and 226–382; [loops.rs](../repo/crates/ralph-cli/src/loops.rs), lines 35–84 and 159–210). This is more concrete Git integration machinery than Wingman's high-level delivery description. It could save implementation effort but must respect product approval and source ownership; automatic merge/commit is not business acceptance.

**Programmable lifecycle hooks and durable suspension.** Hooks resolve around named lifecycle phases, receive structured context/metadata, execute commands and can stop or suspend progress with retry/resume policies ([hooks/engine.rs](../repo/crates/ralph-core/src/hooks/engine.rs), lines 24–83 and 204–246; [hooks/suspend_state.rs](../repo/crates/ralph-core/src/hooks/suspend_state.rs), lines 26–55 and 97–153; [loop_runner.rs](../repo/crates/ralph-cli/src/loop_runner.rs), lines 3291–3705). These offer enforceable integration points for Wingman tracker updates, policy gates and acceptance evidence. They also add a second state machine that must remain coordinated with agent/task states.

**Machine-facing control plane and visual workflow authoring.** Rust HTTP/WebSocket RPC and stdio MCP expose task/loop/planning/config/preset/collection/robot domains, with schema validation, authorization and mutation idempotency. MCP forwards tools to the same runtime ([runtime.rs](../repo/crates/ralph-api/src/runtime.rs), lines 36–108 and 138–200; [mcp.rs](../repo/crates/ralph-api/src/mcp.rs), lines 32–85). The React builder observes event topology, supports role collections and actually launches saved collections through [collection.run](../repo/crates/ralph-api/src/collection_domain.rs), lines 420–610. Its bounded stderr drain and child reaper also avoid an undrained-output deadlock or zombie process while exposing early launch failures. Wingman could use the API as an integration surface, but must implement/verify missing task/planning execution, map its own identities, and account for in-memory idempotency retention rather than assume durable exactly-once effects.

**Recorded sessions and deterministic replay.** Replay fixtures and a SmokeRunner allow event/parser behavior to be checked without paid live agent calls; recording supports diagnostics and backend regression work ([testing/smoke_runner.rs](../repo/crates/ralph-core/src/testing/smoke_runner.rs), lines 24–60 and 176–235; [smoke tests](../repo/crates/ralph-core/tests/smoke_runner.rs), lines 45–126). This is valuable infrastructure for Wingman orchestration regressions. Replay covers recorded interactions, not live provider behavior, actual coding quality or the complete modern loop runner.

**Experiment-oriented autonomy.** The shipped autoresearch preset defines a measurable try/measure/retain-or-discard workflow beyond ordinary feature delivery ([autoresearch.yml](../repo/presets/autoresearch.yml), lines 1–125). This could support performance/quality tuning. It is a prompt/preset-driven experiment discipline, requiring trustworthy measurement commands and explicit stopping budgets, rather than a general scientific experimentation platform.

## Distinctive mechanisms and grounded innovation

The notable contribution is the combination of **fresh context with explicit disk/event contracts**. Instead of relying on a model's increasingly long conversation, Ralph reconstructs a bounded prompt from durable artifacts, ready tasks, the original objective and event handoffs. Resume rehydrates historical phase knowledge while delivering only post-termination events. This makes handoffs inspectable and can reduce stale conversational baggage. It also means essential details must actually be written to artifacts; undocumented reasoning disappears, and “agent continuity” must be implemented above the loop.

The **constant coordinator plus event topology** is a distinctive simplifying choice. Arbitrary hats describe what events they receive/publish and which instructions apply; Ralph remains the executor and fallback. Publication guides explain the downstream recipient in the prompt ([hatless_ralph.rs](../repo/crates/ralph-core/src/hatless_ralph.rs), lines 71–110 and 161–216). It permits reusable workflows and recovery without building a society of long-lived agents. Its limit is exactly Wingman's central requirement: sequential hats do not supply independent durable coworkers, and several active hats can contribute instructions to one invocation.

The **two-level concurrency model** is practically useful: worktrees isolate objectives, while correlated waves fan out homogeneous work inside one objective. Per-worker event files, IDs and aggregation prevent results from being confused at the handoff level. The model is strongest for read-only review/research. Waves do not provide code isolation, and aggregation timeouts/partial results require synthesis policies that recognize missing work.

Finally, **completion as a guarded protocol event** provides more backpressure than trusting an agent's final sentence. Required topics, task terminality and guidance acknowledgements constrain completion. The limit is that `build.done` validation parses agent-reported pass/fail evidence rather than independently executing all checks ([event_loop/mod.rs](../repo/crates/ralph-core/src/event_loop/mod.rs), lines 2577–2655). Hook-enforced test commands could strengthen this. These are distinctive mechanisms in this checkout, not claims of historical novelty or uniqueness across orchestration systems.

## Practical adoption for Wingman

Use Ralph directly, or study it as a reference, for a single assigned engineering objective:

- fresh-context coding loops.
- phase presets.
- runtime task dependencies.
- Markdown memory.
- Telegram questions/guidance.
- local worktree isolation.
- scatter/gather review.
- diagnostics.
- controlled termination and merge handoffs.

Its code is particularly instructive for separating a long-lived execution objective from short-lived model invocations.

Adapt its event/task boundaries before using it under Wingman. Every loop/worker needs organization agent ID, product ID, ticket ID, host ID and conversation linkage. Wingman's shared tracker should be authoritative; local runtime tasks and web API task records should either mirror it through explicit synchronization or be hidden as execution details. Map DIRECTIVES to Ralph's artifact paths without conflating memory with product scope. Convert test evidence from self-report into captured commands/results where practical. Route Telegram via Butler, preserve question correlation across products, and reconcile completion/failed/accepted states. Resolve the Rust API execution gap and migrated frontend/legacy backend compatibility before depending on web controls.

Build the organization above this layer:

- project intake and registry.
- ProductMaster/TechMaster continuity.
- a durable expandable agent directory.
- Room1/Room2 collaboration.
- organizational supervision.
- cross-host dispatch and shared coordination.
- personal summary timelines.
- executive portfolio views and full individual conversation lifecycle controls.

Those are substantial product work, not a few hat names. A credible architecture is Wingman as the organization/control plane with Ralph-like bounded workers underneath, rather than pretending hats already are the organization.
