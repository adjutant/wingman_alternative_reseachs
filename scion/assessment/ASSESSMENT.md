# Scion assessment

**Repository:** https://github.com/GoogleCloudPlatform/scion  
**Checkout:** `research/scion/repo`  
**Revision inspected:** `fe4556ad66b7ce68cf0c2d6871544496dfdfd4c4`  
**Assessment date:** 2026-11-05  
**Basis:** local source and tests, read only; no dependency installation, running agents, services or browser sessions.

Scion is a strong candidate for Wingman's **agent execution, communication and operational control substrate**, but it is not the development organization described in [WINGMAN_PURPOSE](../../WINGMAN_PURPOSE.md). It has real independent containerized coding agents, persistent identities, projects, templates, a web application, Telegram integration, direct agent messaging, schedules and a genuinely distributed Hub/Runtime Broker architecture. The most substantial missing layer is organizational: interpreting conversational requests across a portfolio, product discovery, product/technical leadership, ticket decomposition and ownership, integrated acceptance and executive summaries of completed/current/next work. These would require implemented workflows and data models, not simply renaming templates.

This revision is much more capable than a terminal multiplexer. Conversely, an agent's initial `Task`, a runtime state badge or a durable message must not be mistaken for a ticket system, acceptance gate or executive timeline. The checkout calls itself alpha in [AGENTS.md](../repo/AGENTS.md), lines 3–5. Several architecture-document statements lag implementation: for example the current source has Ent-based SQLite/PostgreSQL machinery and several workspace sharing modes, rather than only the older SQLite/worktree descriptions. Findings below favor executable source over those descriptions.

Further implementation detail, including Codex harness limits, delivery outcomes, wake behavior and retirement mechanics, is in [Lifecycle and Coordination](Lifecycle_and_Coordination.md). The verdict and complete feature comparison remain in this master report.

## Architecture and execution model

The entry surface is the Go/Cobra CLI plus a Lit/TypeScript application served by the Go Hub. A user must explicitly run a Hub; agents are not secretly started as independent CLI-only subprocesses. The Hub authenticates users and agents, owns project and agent records and dispatches work to Runtime Brokers. A Runtime Broker provisions files and drives `agent.Manager`, which drives a container runtime and an external agent harness. The LLM reasoning loop belongs to the harness, not to Scion's Hub. The implementation-facing contracts are [Manager](../repo/pkg/agent/manager.go), lines 45–145, [create API](../repo/pkg/hub/handlers_agents_core.go), lines 231–295 and 716–800, and [agent startup](../repo/pkg/agent/run.go), lines 98–160 and 2790–3020.

The normal path is:

1. A CLI/web/API request identifies a project and names an agent, template, harness configuration and optionally placement and task.
2. The Hub validates and authorizes creation, resolves the project and records attribution. `createAgentInProject` resolves placement/configuration, reserves capacity and persists the agent before launch orchestration. See [creation implementation](../repo/pkg/hub/handlers_agents_core.go), lines 1585–2130 and 2795–2920.
3. A Runtime Broker performs provisioning and runtime launch. Agent state/configuration and a dedicated home live outside the reasoning process. The workspace can be a clone, worktree, shared directory or empty private workspace depending on project setup. [Provisioning](../repo/pkg/agent/provision.go), lines 914–1015, 1128–1305, 1355–1433 and 1513–1585, separates initial setup, reconfiguration and template/harness resolution.
4. The manager composes runtime environment, identity labels, mounts, harness command and resource settings, then starts the runtime and records the resulting run. See [run implementation](../repo/pkg/agent/run.go), lines 98–160 and 2790–3020. Harness configuration can use a container-side script provisioner rather than require a new hard-coded adapter: [container-script harness](../repo/pkg/harness/container_script_harness.go), lines 25–125.
5. Status reports, broker heartbeats, persistent messages and events update the Hub and web views. A durable dispatch queue bridges interrupted Hub/broker communication. [Reconciliation](../repo/pkg/hub/reconcile.go), lines 30–100 and 728–755, claims pending commands and resolves an agent's current broker before delivery.

This describes the normal brokered coding-agent path. A separate managed-agent backend can create cloud interactions directly without a container or Runtime Broker; that exception is discussed below.

This is real host separation: the Hub can route through a broker-initiated control channel to a different machine behind NAT. It is not merely running two local containers and calling them distributed. See [Runtime Broker control channel](../repo/pkg/runtimebroker/controlchannel.go) and [Hub control channel](../repo/pkg/hub/controlchannel.go), which implement the remote transport, with the end-to-end command durability path in [reconcile.go](../repo/pkg/hub/reconcile.go), lines 30–100. Deploying brokers on the Mac and Endeavour is a plausible direct use, but no such deployment was exercised here.

The Hub database holds identities, project association, current run/state, configuration and communication records; broker files and storage hold provisioned homes/workspaces and harness history. [Agent model](../repo/pkg/store/models.go), lines 32–115, makes this explicit. The storage contract is [store.go](../repo/pkg/store/store.go), lines 180 onward; actual Ent-backed SQLite/PostgreSQL opening is visible in [server database backfill](../repo/cmd/server_backfill.go), lines 167–220. This is evidence of implemented backend support, not a claim that every installation uses PostgreSQL.

## Agent definition, creation and lifecycle

### What constitutes an agent

An **agent** is a durable Hub record plus configuration/home/workspace and an independently executed external harness. A **template** is reusable harness-agnostic instruction/resource material. A **harness configuration** selects and configures vendor software, credentials and execution details. A **broker profile** selects runtime execution settings. The initial **task** is a prompt, not a separate durable work item with assignment history and dependencies. A **run** is an execution incarnation, and a harness **session** is the vendor's conversation state. Restarting a container does not by itself recreate that conversation, and a new generation is not a new organizational identity. These distinctions follow [Agent fields](../repo/pkg/store/models.go), lines 32–115, [Manager contract](../repo/pkg/agent/manager.go), lines 45–145, and [lifecycle resume checks](../repo/pkg/hub/handlers_agent_lifecycle.go), lines 531–570 and 846–900.

The platform can therefore instantiate BackendCoder twice as separate agents rather than ask a single model to simulate two personas. However, their professional responsibilities, test expectations and reporting relationships need templates and organizational data supplied by Wingman.

### Definition, admission, identity and routing

The create schema accepts name, project, template, harness config/auth, runtime broker/profile, branch/workspace, labels, initial task and optional notification/resume behavior. Provision-only creation prepares state without beginning reasoning. See [request schema](../repo/pkg/hub/handlers_agents_core.go), lines 231–295. The Hub resolves slug versus UUID, enforces authorization and records the creator/ancestry. Names are meaningful within a project; UUIDs distinguish durable identities. The agent's runtime container carries identity and run labels, so stop/input operations can target the actual execution rather than an ambiguously reused name.

Admission and execution are distinct. The [manager preflight contract](../repo/pkg/agent/manager.go), lines 55–68, resolves template/harness validity without provisioning. Creation can opt into asynchronous launch under an experiment. The request schema explicitly conditions `AcceptAsyncLaunch` on this, so immediate API acceptance is not proof the harness is ready. Environment gathering may also defer launch while missing inputs are collected. [Creation dispatch](../repo/pkg/hub/handlers_agents_core.go), lines 2795–2920, handles accepted launch and unknown dispatch outcomes separately.

Routing selects a project-associated Runtime Broker and profile, then that broker supplies actual execution. Project association determines communication scope; physical host placement does not make agents separate organizations. For Wingman, one Hub and brokers on both hosts would preserve this distinction well. Worktree mode relies on a shared clone and has runtime constraints; clone-per-agent supplies isolation without assuming the same path exists everywhere. Shared directories are a different resource from an isolated worktree.

### Provisioning, tools, permissions and concurrency

Provisioning prepares the agent home, resolves template and harness settings, creates instruction/configuration files and establishes workspace/storage. Reprovisioning re-renders configuration while preserving supported home/workspace state. The actual launch then composes runtime settings, token transport, environment and mounts and starts the harness container. See [provision.go](../repo/pkg/agent/provision.go), lines 914–1015, 1128–1305 and 1355–1433, and [run.go](../repo/pkg/agent/run.go), lines 98–160 and 2790–3020.

Coding tools belong to the chosen harness and container image. Scion adds its in-container control/status utilities, credential distribution, runtime boundaries and Hub authorization. Agent permission roles (`none`, `readonly`, `baseline`, `full`) are explicitly validated in [creation](../repo/pkg/hub/handlers_agents_core.go), lines 770–775. They are not the same thing as BackendCoder or TechMaster, and Hub scopes do not prove that arbitrary shell execution within an authorized container is harmless. Extending harness support via [container-side provisioners](../repo/pkg/harness/container_script_harness.go), lines 25–125, lowers adapter coupling but introduces an image/script contract to maintain.

The shipped [Codex harness configuration](../repo/harnesses/codex/config.yaml), lines 15–123, makes several adoption boundaries concrete: readiness uses an eight-second settling delay; ordinary submission uses Enter plus extra submits; resume is `resume --last`. The default command bypasses native Codex approval/sandbox controls inside the container. Its capability declarations mark model-call-limit enforcement unsupported, system prompts as instructions rather than a native system channel, and project MCP entries as demoted to global. Wingman should therefore rely on the actual configured runtime/Hub boundaries and verified harness capabilities, rather than assume every generic limit or permission field is enforced identically by Codex. These are checked-in configuration findings, not runtime-tested guarantees.

Concurrency is independent containers plus shared Hub records and dispatch claims. Project-scoped filtering prevents same-name agents in different products from colliding; run-scoped targets prevent old stops/deletes from hitting a replacement run. [Manager](../repo/pkg/agent/manager.go), lines 75–110 and 505–558, documents these exact boundaries. Separate working trees reduce edit conflicts, but the platform does not resolve application integration conflicts or infer task dependencies for the team.

### Continuity, schedules and interruption

Stopping execution need not delete identity or home. Resume is conditional on harness support and retained session state. Suspension checks resume capability, stops the current run, records suspended state and revokes credentials while guarding against a newer run. [Suspend lifecycle](../repo/pkg/hub/handlers_agent_lifecycle.go), lines 531–650, is a stronger mechanism than simply closing a terminal. Starting a suspended agent sets resume semantics; force-resuming an error-phase agent is best effort, not automatic proof of safe recovery (lines 846–900).

The scheduler stores one-shot events, reloads them on startup, fires expired events and runs recurring handlers with jitter/concurrency limits. Project schedules can send a message or dispatch a new agent using a cron expression and time zone. They also expose pause/resume/history operations. See [scheduler](../repo/pkg/hub/scheduler.go), lines 30–100, 344–392 and 511–550, and [schedule API](../repo/pkg/hub/handlers_schedules.go), lines 28–52 and 652–807. These can drive a ProjectMaster's periodic inspection, but the reasoning about product progress must be supplied. Operational stalled detection and auto-suspension concern runtime health, not whether the correct product work is moving.

Input delivery normally debounces bursts into a single delivery. Interrupt input bypasses buffering and sends the harness's configured interrupt sequence before the message. Per-container injection locking serializes tmux input against other messages/keystrokes. This is implemented in [manager messaging](../repo/pkg/agent/manager.go), lines 632–666 and 1420–1490. A noteworthy limit is documented in that code: a background flush waiting on a hung tmux operation can hold the injection lock indefinitely. The later retry loop cannot bound an operation that never returns. This matters when assuming that “sent” means “immediately steered.”

### Failure, retry and recovery

Durable broker dispatch intent and persisted messages survive missing notifications and broker reconnects. Pending operations are claimed through store compare-and-swap before execution; already-claimed items are skipped. [Reconcile](../repo/pkg/hub/reconcile.go), lines 30–100 and 205–294, is the control-plane durability backstop. This supports recovery from transport loss. It does not establish exactly-once external code effects or guarantee that a model never repeats a shell command. Agent holds and missing broker/dispatcher state also prevent delivery ([lines 728–755](../repo/pkg/hub/reconcile.go)).

Creation separately handles ordinary failure, unknown launch outcome and accepted asynchronous launch. An uncertain outcome is not treated as proof that no runtime was started. Broker heartbeat reconciliation records runtime target/inventory and tracks missing agents: [broker reconciliation](../repo/pkg/hub/broker_heartbeat_reconcile.go), lines 94–174 and 232–283. The runtime might die, the Hub might lose transport, and the harness might fail to finish its task. These are different states requiring different recovery.

**Reincarnation** is a particularly useful continuity mechanism: re-resolve configuration and launch a new generation while retaining the same agent identity and a handoff. Its request/response includes dry-run planning, generation and source/target broker information, and can change supported fields such as model/image/auth. Unsupported overrides are explicitly rejected, including harness-config replacement, arbitrary environment patching and rollback flags: [reincarnation API](../repo/pkg/hub/handlers_agent_reincarnate.go), lines 30–130. Cross-broker moves have workspace eligibility checks rather than pretending every state directory is transferable. Failed transitions restore a clearly marked recovery handoff for the previous generation rather than claiming a successful upgrade: [recovery](../repo/pkg/hub/reincarnate_recovery.go), lines 25–75. This is not unlimited session migration; storage, harness behavior, permissions and supported patch fields still constrain it.

### Completion, acceptance and retirement

Default instructions ask the agent to summarize and invoke `sciontool status task_completed`, then stop asking follow-up questions. They also distinguish intentionally blocked waiting from a stalled agent: [default instructions](../repo/pkg/config/embeds/templates/default/agents.md), lines 1–27. This provides observability of self-reported completion, not independent acceptance of a finished product. There is no demonstrated built-in TestMaster or definition-of-done evaluation. The opt-in alpha artifact subsystem supports versioned reviews with human feedback. Owner notification is best effort and is refused during reincarnation. A review does not establish that all requirements or integrated tests passed.

Deletion is separate from stop/suspend. Manager deletion can remove runtime resources, retained files and optionally a branch, using exact run targets and project scope. [Manager deletion](../repo/pkg/agent/manager.go), lines 516–611, and [file/worktree teardown](../repo/pkg/agent/provision.go), lines 69–182 and 653–792, implement cleanup. Wingman would need an organizational retirement/archive policy that keeps delivery records and knowledge while freeing compute; deletion of an execution resource is not that policy by itself.

## Coordination mechanics and a traced request

Scion coordinates through structured direct/group/broadcast messages, durable conversations, status events, scheduled events and shared files/storage. It does not supply a ticket dependency engine. Native group conversations are project-scoped: creation requires a project ID and participant insertion rejects an agent belonging to another project ([conversation handlers](../repo/pkg/hub/handlers_conversations.go), lines 740–748 and 1070–1097). Group-message forwarding independently rejects project-qualified references outside the anchor agent's project ([messaging](../repo/pkg/hub/handlers_agent_messaging.go), lines 3420–3450). A project-local specialist room can therefore approximate Room2, but a shared Room1 containing organization-wide Butler/ProjectMaster and leaders from several products requires an additional coordination layer or an explicit change to these boundaries. Global DMs are a separate primitive, not evidence of a native cross-project room. Membership, escalation rules and responsibility also remain organizational configuration. New agents are subscribed from lifecycle events by [MessageBrokerProxy](../repo/pkg/hub/messagebroker.go), lines 346–466. User-directed messages can be persisted and routed with conversation affinity (lines 659–871), so dashboard and Telegram interactions need not become unrelated histories.

A concrete code-path trace is a human mentioning an existing agent in a linked Telegram group, for example `@butler investigate the CRM onboarding failure`. This is a source trace, not an executed test of Telegram:

1. [Telegram V2 input](../repo/extras/scion-telegram/internal/telegram/broker_v2.go), lines 2200–2255, accepts supported message/attachment types, filters bot echoes and commands, then routes group messages. Unstructured private DMs receive help, which is a material difference from Wingman's desired single private conversation.
2. [Group routing](../repo/extras/scion-telegram/internal/telegram/broker_v2.go), lines 2285–2340 and 2460–2550, finds the linked project and topic/chat default, resolves the sender's Hub identity, fetches that user's visible agents and classifies mention targets. It does not create a project based on the meaning of “CRM”. The group already identifies the project.
3. [Inbound delivery](../repo/extras/scion-telegram/internal/telegram/broker_v2.go), lines 3490–3545, packages a structured message and posts to the Hub's broker inbound endpoint with broker/plugin identity and HMAC signing where configured.
4. [Hub inbound](../repo/pkg/hub/handlers_broker_inbound.go), lines 60–115, validates broker authentication and body; lines 535–665 persist conversation-linked message state, preserve deferred messages during reincarnation and handle persistence failure before dispatch. Conversation identity is carried into delivery rather than reconstructed only in the UI.
5. The Hub dispatches to the agent's Runtime Broker; [delivery reconciliation](../repo/pkg/hub/reconcile.go), lines 728–755, resolves the current broker and refuses a held agent. [Manager message delivery](../repo/pkg/agent/manager.go), lines 632–666 and 1420–1490, buffers ordinary input, selects the project-scoped target and injects text using the harness delivery specification.
6. The harness reasons and uses its coding tools. If configured as Butler it can message other agents using [outbound handling](../repo/pkg/hub/handlers_agent_messaging.go), lines 1122 onward, and request clarification via the documented status convention. That organizational behavior is custom agent logic, not an implicit step of the transport.
7. Replies pass through message routing and persisted user conversations in [MessageBrokerProxy](../repo/pkg/hub/messagebroker.go), lines 659–871, with Telegram publishing handled by the plugin. A product acceptance decision still needs Wingman records and policy.

The inspected [conversation-envelope tests](../repo/pkg/hub/handlers_broker_inbound_def135_test.go), lines 88–133 and 134–179, assert that delivered conversation identity matches persisted identity for DM/thread cases. They use a test dispatcher and do not prove a real Telegram-to-container round trip. This precision matters: routing durability is substantial evidence; autonomous product management is not established by it.

## Major additional capabilities and grounded innovations

**Multiple harnesses and extensible container-side provisioning.** Scion supports an external-harness boundary instead of making one model SDK the center of the product. Reusable harness configurations can stage authentication and invoke provisioner scripts inside the container: [container-script harness](../repo/pkg/harness/container_script_harness.go), lines 25–125. For Wingman this enables heterogeneous specialist backends and versioned execution images. Integration would require maintaining harness delivery/resume/status contracts, credentials and images; substituting Codex as the reasoning loop does not automatically standardize all session semantics.

**Distributed control with durable intent and identity-aware runtime operations.** The combination of outbound broker control channels, persisted intent, compare-and-swap claiming and exact run targeting is more valuable than simply “remote containers.” [Reconciliation](../repo/pkg/hub/reconcile.go), lines 30–100, and [exact-run manager contracts](../repo/pkg/agent/manager.go), lines 75–110 and 505–558, let commands outlive a transient transport failure without casually stopping the next incarnation. This is an implementation-distinctive resilience mechanism, not a claim of industry novelty or universal exactly-once execution.

**Reincarnation with explicit configuration changes and recovery handoff.** [Reincarnation API](../repo/pkg/hub/handlers_agent_reincarnate.go), lines 30–130 and 681–809, and [recovery handoff](../repo/pkg/hub/reincarnate_recovery.go), lines 25–75, support evolving a persistent worker, including eligible host moves, while keeping stable identity. This could let Wingman upgrade a long-lived leader or move execution capacity without inventing a new agent. It still needs a reliable handoff and supported storage mode. It is not a serialization of arbitrary process memory.

**Skill registry with content pinning.** The [skill registry handlers](../repo/pkg/hub/skill_registry_handlers.go), lines 55–82 and 281–323, expose registry management and pin a URI to a content hash. The broader resolution/configuration path integrates reusable skills with provisioning. This supplies a foundation for audited reusable organization instructions beyond Wingman's directory convention. Wingman would still need decide who publishes/updates role skills and how changed versions propagate to existing agents; pinned content improves reproducibility rather than magically improving instructions.

**Versioned artifact bundles with constrained review and agent feedback (opt-in alpha).** This is a substantial publication/review subsystem, not only a notification callback. `hub.artifacts` is alpha and defaults to false: [experiment registration](../repo/pkg/experiments/registry.go), lines 503–512. The Hub also requires the artifacts settings section to be enabled; [route guard](../repo/pkg/hub/artifacts_host.go), lines 815–836, returns 404 before authentication outcomes when either gate is off. Thus the capabilities below are implemented but are not generally available in the default configuration. Chat attachment artifacts have their own experiment and must not be conflated with enabling this publication UI/API.

An artifact has stable identity and version references. A publisher creates a **pending version**, uploads the required files, and finalizes it into a ready version. Each manifest file carries path, byte size, SHA-256 and media type, with an entry file for a bundle: [API](../repo/pkg/artifacts/api.go), lines 117–165. Required uploads omit unchanged current-version content and deduplicate identical hashes. Upload handling actually verifies size and digest rather than trusting the manifest ([versions](../repo/pkg/artifacts/versions.go), lines 640–705). Finalization refuses missing files, reapplies current bundle/file limits and claims the pending version before advancing state, so a partially uploaded bundle is not exposed as a ready release (lines 738–845). This could support Wingman's versioned specifications, reports, screenshots and deliverable bundles with inspectable references. It introduces blob storage, publication ownership, retention and artifact-to-task relationships that Wingman would need operate.

Reviews are versioned bundles of kind `review`, whose text carries CriticMarkup against an explicit published base. This is deliberately constrained: after stripping markup and normalizing text, the result must match the base; reviewers cannot silently add/remove files, move the entry, alter non-text content, or introduce text changes outside marks. [Review implementation](../repo/pkg/artifacts/review.go), lines 30–50 and 87–150, implements these comparisons. The review must name a still-current base; stale bases and a concurrent newer publication are rejected/discarded with `stale_review`, while unmarked changes yield `unmarked_changes` ([review finalization](../repo/pkg/artifacts/review.go), lines 185–245; [finalize race checks](../repo/pkg/artifacts/versions.go), lines 824–849). This is a grounded review-integrity mechanism, not proof that the reviewed material is correct.

After a review version becomes ready, [artifact review notification](../repo/pkg/hub/artifacts_review.go), lines 42–105, sends system feedback to the owning agent. Delivery is best effort and refuses an owner currently reincarnating. Wingman could connect specification/deliverable reviews to the responsible ProductMaster or worker and use version references as evidence in executive summaries. Publication readiness and marked review integrity still do not establish test completion, product acceptance, or delivery against a definition of done. Those workflow gates remain Wingman functionality.

**Delegated authority and bounded scheduled work.** Beyond a personal single-user organization, Scion carries multi-user authorization and explicit delegation. A user can issue an agent-bound, expiring grant with a frozen permission ceiling, which the agent exchanges for a short-lived credential. It is not an unrestricted delegation of the user. See [delegation model](../repo/pkg/store/models.go), lines 5362–5425, and [delegation handlers](../repo/pkg/hub/handlers_agent_delegation.go). Scheduled work stores an authority revision and frozen effect ceiling and intersects applicable ceilings at execution: [scheduled authority](../repo/pkg/hub/scheduled_authority.go), lines 30–65 and 446 onward. This helps prevent a future wake from becoming an implicit privilege escalation. Wingman could use this to bound ProjectMaster and specialist powers, but would need map responsibilities to permissions. It is authorization machinery, not management approval of product decisions.

**Authenticated access to running application ports.** [Port forwarding](../repo/pkg/hub/port_forward_handlers.go), lines 40–74, 241–292 and 393 onward, implements agent registration and Hub-authorized forwarding over a reverse tunnel, with request/stream limits. This can give a human access to a development server inside a remote agent environment without exposing an inbound host port. Wingman could connect previews to deliverables and acceptance sessions. It still needs application-start/test logic, and authenticated forwarding is not production deployment or product acceptance.

**Managed cloud interactions as an alternative execution path.** [Managed agents](../repo/pkg/hub/handlers_managed_agents.go), lines 95–145 and 202–222, create background cloud interactions and retain interaction/environment references, with separate message/stop/delete operations. This broadens the platform beyond container-only execution. Wingman should distinguish those resources from independent Codex containers: workspace, terminal, tools and provider availability have different boundaries. No cloud API was called here, so availability and feature parity remain unverified.

**Optional A2A interoperability bridge.** The separate `extras/scion-a2a-bridge` service exposes discoverable agent cards and per-project/per-agent JSON-RPC endpoints, with optional v0.3 REST compatibility: [bridge server](../repo/extras/scion-a2a-bridge/internal/bridge/server.go), lines 218–275. Its SDK executor translates incoming A2A messages into Hub structured messages, waits on the event log, and translates responses into SDK task events ([executor](../repo/extras/scion-a2a-bridge/internal/bridge/executor.go), lines 55–75 and 264–340). This could connect Wingman agents to external agent clients without exposing Scion-specific messaging APIs. It requires operating another service and defining which agents are exposed, credentials and task ownership. An A2A protocol task is request/execution state, not a ProjectTracker ticket.

Authentication is configurable, including API key, bearer, Hub-validated credentials and federation; `none` explicitly opens authentication ([server validation/auth setup](../repo/extras/scion-a2a-bridge/internal/bridge/server.go), lines 161–213). Streaming is implemented, but transport boundaries differ: the legacy channel-based SSE path sends as the bridge administrator and refuses federated callers, whereas the SDK executor supports caller-aware routing ([stream](../repo/extras/scion-a2a-bridge/internal/bridge/stream.go), lines 267–278 and 325–338; [SDK streaming adapter](../repo/extras/scion-a2a-bridge/internal/bridge/durable_handler.go), lines 349–360). Cancel emits a canceled task event and attempts a Hub interrupt when possible. Federated users receive no interrupt. Missing routes or failed sends can still produce a canceled protocol status. One credential-construction failure path falls back to the bridge administrator ([executor cancellation](../repo/extras/scion-a2a-bridge/internal/bridge/executor.go), lines 471–525). Thus protocol cancellation does not prove the coding process stopped. No interoperability, auth or streaming round trip was exercised here.

**Operational scheduling and resource conservation.** Persisted one-shots, cron/time-zone schedules, scheduler concurrency control, explicit blocked reporting and auto-suspend mechanisms give the platform useful long-running operations features. See [scheduler](../repo/pkg/hub/scheduler.go), lines 30–100 and 511–550; [schedules](../repo/pkg/hub/handlers_schedules.go), lines 28–52; [blocked convention](../repo/pkg/config/embeds/templates/default/agents.md), lines 11–19. Their value is avoiding lost wakeups and distinguishing intentional waiting from runtime stalls. They do not measure productive progress; Wingman must supply the tracker evidence and agent reasoning that makes supervision useful.

These mechanisms are grounded design strengths of this checkout. No research was performed to claim historical originality or superiority to every other system.

## Practical use for Wingman

Use directly, subject to deployment validation: the Hub/project/agent registry, independent container workers, reusable templates, remote Runtime Brokers, direct/group messaging, Telegram transport, retained homes, lifecycle/input controls, scheduler and operational web views. These cover a large fraction of the difficult infrastructure behind the Mac/Endeavour organization. A human can already inspect an agent and reach its live session. The UI is a credible starting point for Wingman's detailed workspace.

Adapt:

- Create Butler/ProjectMaster/ProductMaster/TechMaster and specialist templates.
- Configure permissions and spawning authority.
- Assign project leadership and communication membership.
- Give each product durable directives and shared coordination records.
- Implement Butler's cross-project conversation context and a management-room bridge or additional cross-project coordination layer compatible with native project-scoped groups.
- Add notifications and schedule-driven ProjectMaster inspections. Telegram requires special attention: this revision's V2 group/topic workflow and DM-help behavior do not implement the desired single private Butler relationship. The transport can be reused, but intake/routing must be designed deliberately.

Build as product functionality:

- conversational existing/new-project classification.
- proportional discovery and tracked clarification cycles.
- product definitions and testable acceptance criteria.
- a shared task model with assignment/dependencies/blockers/comments.
- technical planning and integration policy.
- independent verification and delivery acceptance.
- semantic executive briefings and linked agent summary timelines.

The existing agent graph and logs should remain underlying evidence rather than be relabeled as these missing views. Add relationships between agents, tasks, specifications, conversations, changes and tests so an executive summary can be traced through the same organization.

Recommendation: evaluate Scion as a foundation or reference architecture for **execution plus collaboration**, not as a turnkey replacement for Wingman. Its strongest fit is the distributed persistent-agent substrate. A Wingman implementation on top would still be a meaningful application with its own domain model, workflows and acceptance tests.
