Scion assessment

Repository: https://github.com/GoogleCloudPlatform/scion
Checkout: research/scion/repo
Revision inspected: fe4556ad66b7ce68cf0c2d6871544496dfdfd4c4
Assessment date: 2026-11-05
Basis: local source and tests, read only; no dependency installation, running agents, services or browser sessions.

Scion is a strong candidate for Wingman's agent execution, communication and operational control substrate, but it is not the development organization described in WINGMAN_PURPOSE. It has real independent containerized coding agents, persistent identities, projects, templates, a web application, Telegram integration, direct agent messaging, schedules and a genuinely distributed Hub/Runtime Broker architecture. The most substantial missing layer is organizational: interpreting conversational requests across a portfolio, product discovery, product/technical leadership, ticket decomposition and ownership, integrated acceptance and executive summaries of completed/current/next work. These would require implemented workflows and data models, not simply renaming templates.

This revision is much more capable than a terminal multiplexer. Conversely, an agent's initial Task, a runtime state badge or a durable message must not be mistaken for a ticket system, acceptance gate or executive timeline. The checkout calls itself alpha in AGENTS.md, lines 3–5. Several architecture-document statements lag implementation: for example the current source has Ent-based SQLite/PostgreSQL machinery and several workspace sharing modes, rather than only the older SQLite/worktree descriptions. Findings below favor executable source over those descriptions.

Further implementation detail, including Codex harness limits, delivery outcomes, wake behavior and retirement mechanics, is in Lifecycle and Coordination. The verdict and complete feature comparison remain in this master report.

Architecture and execution model

The entry surface is the Go/Cobra CLI plus a Lit/TypeScript application served by the Go Hub. A user must explicitly run a Hub; agents are not secretly started as independent CLI-only subprocesses. The Hub authenticates users and agents, owns project and agent records and dispatches work to Runtime Brokers. A Runtime Broker provisions files and drives agent.Manager, which drives a container runtime and an external agent harness. The LLM reasoning loop belongs to the harness, not to Scion's Hub. The implementation-facing contracts are Manager, lines 45–145, create API, lines 231–295 and 716–800, and agent startup, lines 98–160 and 2790–3020.

The normal path is:

  1. A CLI/web/API request identifies a project and names an agent, template, harness configuration and optionally placement and task.
  2. The Hub validates and authorizes creation, resolves the project and records attribution. createAgentInProject resolves placement/configuration, reserves capacity and persists the agent before launch orchestration. See creation implementation, lines 1585–2130 and 2795–2920.
  3. A Runtime Broker performs provisioning and runtime launch. Agent state/configuration and a dedicated home live outside the reasoning process. The workspace can be a clone, worktree, shared directory or empty private workspace depending on project setup. Provisioning, lines 914–1015, 1128–1305, 1355–1433 and 1513–1585, separates initial setup, reconfiguration and template/harness resolution.
  4. The manager composes runtime environment, identity labels, mounts, harness command and resource settings, then starts the runtime and records the resulting run. See run implementation, lines 98–160 and 2790–3020. Harness configuration can use a container-side script provisioner rather than require a new hard-coded adapter: container-script harness, lines 25–125.
  5. Status reports, broker heartbeats, persistent messages and events update the Hub and web views. A durable dispatch queue bridges interrupted Hub/broker communication. Reconciliation, lines 30–100 and 728–755, claims pending commands and resolves an agent's current broker before delivery.

This describes the normal brokered coding-agent path. A separate managed-agent backend can create cloud interactions directly without a container or Runtime Broker; that exception is discussed below.

This is real host separation: the Hub can route through a broker-initiated control channel to a different machine behind NAT. It is not merely running two local containers and calling them distributed. See Runtime Broker control channel and Hub control channel, which implement the remote transport, with the end-to-end command durability path in reconcile.go, lines 30–100. Deploying brokers on the Mac and Endeavour is a plausible direct use, but no such deployment was exercised here.

The Hub database holds identities, project association, current run/state, configuration and communication records; broker files and storage hold provisioned homes/workspaces and harness history. Agent model, lines 32–115, makes this explicit. The storage contract is store.go, lines 180 onward; actual Ent-backed SQLite/PostgreSQL opening is visible in server database backfill, lines 167–220. This is evidence of implemented backend support, not a claim that every installation uses PostgreSQL.

Agent definition, creation and lifecycle

What constitutes an agent

An agent is a durable Hub record plus configuration/home/workspace and an independently executed external harness. A template is reusable harness-agnostic instruction/resource material. A harness configuration selects and configures vendor software, credentials and execution details. A broker profile selects runtime execution settings. The initial task is a prompt, not a separate durable work item with assignment history and dependencies. A run is an execution incarnation, and a harness session is the vendor's conversation state. Restarting a container does not by itself recreate that conversation, and a new generation is not a new organizational identity. These distinctions follow Agent fields, lines 32–115, Manager contract, lines 45–145, and lifecycle resume checks, lines 531–570 and 846–900.

The platform can therefore instantiate BackendCoder twice as separate agents rather than ask a single model to simulate two personas. However, their professional responsibilities, test expectations and reporting relationships need templates and organizational data supplied by Wingman.

Definition, admission, identity and routing

The create schema accepts name, project, template, harness config/auth, runtime broker/profile, branch/workspace, labels, initial task and optional notification/resume behavior. Provision-only creation prepares state without beginning reasoning. See request schema, lines 231–295. The Hub resolves slug versus UUID, enforces authorization and records the creator/ancestry. Names are meaningful within a project; UUIDs distinguish durable identities. The agent's runtime container carries identity and run labels, so stop/input operations can target the actual execution rather than an ambiguously reused name.

Admission and execution are distinct. The manager preflight contract, lines 55–68, resolves template/harness validity without provisioning. Creation can opt into asynchronous launch under an experiment. The request schema explicitly conditions AcceptAsyncLaunch on this, so immediate API acceptance is not proof the harness is ready. Environment gathering may also defer launch while missing inputs are collected. Creation dispatch, lines 2795–2920, handles accepted launch and unknown dispatch outcomes separately.

Routing selects a project-associated Runtime Broker and profile, then that broker supplies actual execution. Project association determines communication scope; physical host placement does not make agents separate organizations. For Wingman, one Hub and brokers on both hosts would preserve this distinction well. Worktree mode relies on a shared clone and has runtime constraints; clone-per-agent supplies isolation without assuming the same path exists everywhere. Shared directories are a different resource from an isolated worktree.

Provisioning, tools, permissions and concurrency

Provisioning prepares the agent home, resolves template and harness settings, creates instruction/configuration files and establishes workspace/storage. Reprovisioning re-renders configuration while preserving supported home/workspace state. The actual launch then composes runtime settings, token transport, environment and mounts and starts the harness container. See provision.go, lines 914–1015, 1128–1305 and 1355–1433, and run.go, lines 98–160 and 2790–3020.

Coding tools belong to the chosen harness and container image. Scion adds its in-container control/status utilities, credential distribution, runtime boundaries and Hub authorization. Agent permission roles (none, readonly, baseline, full) are explicitly validated in creation, lines 770–775. They are not the same thing as BackendCoder or TechMaster, and Hub scopes do not prove that arbitrary shell execution within an authorized container is harmless. Extending harness support via container-side provisioners, lines 25–125, lowers adapter coupling but introduces an image/script contract to maintain.

The shipped Codex harness configuration, lines 15–123, makes several adoption boundaries concrete: readiness uses an eight-second settling delay; ordinary submission uses Enter plus extra submits; resume is resume --last. The default command bypasses native Codex approval/sandbox controls inside the container. Its capability declarations mark model-call-limit enforcement unsupported, system prompts as instructions rather than a native system channel, and project MCP entries as demoted to global. Wingman should therefore rely on the actual configured runtime/Hub boundaries and verified harness capabilities, rather than assume every generic limit or permission field is enforced identically by Codex. These are checked-in configuration findings, not runtime-tested guarantees.

Concurrency is independent containers plus shared Hub records and dispatch claims. Project-scoped filtering prevents same-name agents in different products from colliding; run-scoped targets prevent old stops/deletes from hitting a replacement run. Manager, lines 75–110 and 505–558, documents these exact boundaries. Separate working trees reduce edit conflicts, but the platform does not resolve application integration conflicts or infer task dependencies for the team.

Continuity, schedules and interruption

Stopping execution need not delete identity or home. Resume is conditional on harness support and retained session state. Suspension checks resume capability, stops the current run, records suspended state and revokes credentials while guarding against a newer run. Suspend lifecycle, lines 531–650, is a stronger mechanism than simply closing a terminal. Starting a suspended agent sets resume semantics; force-resuming an error-phase agent is best effort, not automatic proof of safe recovery (lines 846–900).

The scheduler stores one-shot events, reloads them on startup, fires expired events and runs recurring handlers with jitter/concurrency limits. Project schedules can send a message or dispatch a new agent using a cron expression and time zone. They also expose pause/resume/history operations. See scheduler, lines 30–100, 344–392 and 511–550, and schedule API, lines 28–52 and 652–807. These can drive a ProjectMaster's periodic inspection, but the reasoning about product progress must be supplied. Operational stalled detection and auto-suspension concern runtime health, not whether the correct product work is moving.

Input delivery normally debounces bursts into a single delivery. Interrupt input bypasses buffering and sends the harness's configured interrupt sequence before the message. Per-container injection locking serializes tmux input against other messages/keystrokes. This is implemented in manager messaging, lines 632–666 and 1420–1490. A noteworthy limit is documented in that code: a background flush waiting on a hung tmux operation can hold the injection lock indefinitely. The later retry loop cannot bound an operation that never returns. This matters when assuming that “sent” means “immediately steered.”

Failure, retry and recovery

Durable broker dispatch intent and persisted messages survive missing notifications and broker reconnects. Pending operations are claimed through store compare-and-swap before execution; already-claimed items are skipped. Reconcile, lines 30–100 and 205–294, is the control-plane durability backstop. This supports recovery from transport loss. It does not establish exactly-once external code effects or guarantee that a model never repeats a shell command. Agent holds and missing broker/dispatcher state also prevent delivery (lines 728–755).

Creation separately handles ordinary failure, unknown launch outcome and accepted asynchronous launch. An uncertain outcome is not treated as proof that no runtime was started. Broker heartbeat reconciliation records runtime target/inventory and tracks missing agents: broker reconciliation, lines 94–174 and 232–283. The runtime might die, the Hub might lose transport, and the harness might fail to finish its task. These are different states requiring different recovery.

Reincarnation is a particularly useful continuity mechanism: re-resolve configuration and launch a new generation while retaining the same agent identity and a handoff. Its request/response includes dry-run planning, generation and source/target broker information, and can change supported fields such as model/image/auth. Unsupported overrides are explicitly rejected, including harness-config replacement, arbitrary environment patching and rollback flags: reincarnation API, lines 30–130. Cross-broker moves have workspace eligibility checks rather than pretending every state directory is transferable. Failed transitions restore a clearly marked recovery handoff for the previous generation rather than claiming a successful upgrade: recovery, lines 25–75. This is not unlimited session migration; storage, harness behavior, permissions and supported patch fields still constrain it.

Completion, acceptance and retirement

Default instructions ask the agent to summarize and invoke sciontool status task_completed, then stop asking follow-up questions. They also distinguish intentionally blocked waiting from a stalled agent: default instructions, lines 1–27. This provides observability of self-reported completion, not independent acceptance of a finished product. There is no demonstrated built-in TestMaster or definition-of-done evaluation. The opt-in alpha artifact subsystem supports versioned reviews with human feedback. Owner notification is best effort and is refused during reincarnation. A review does not establish that all requirements or integrated tests passed.

Deletion is separate from stop/suspend. Manager deletion can remove runtime resources, retained files and optionally a branch, using exact run targets and project scope. Manager deletion, lines 516–611, and file/worktree teardown, lines 69–182 and 653–792, implement cleanup. Wingman would need an organizational retirement/archive policy that keeps delivery records and knowledge while freeing compute; deletion of an execution resource is not that policy by itself.

Coordination mechanics and a traced request

Scion coordinates through structured direct/group/broadcast messages, durable conversations, status events, scheduled events and shared files/storage. It does not supply a ticket dependency engine. Native group conversations are project-scoped: creation requires a project ID and participant insertion rejects an agent belonging to another project (conversation handlers, lines 740–748 and 1070–1097). Group-message forwarding independently rejects project-qualified references outside the anchor agent's project (messaging, lines 3420–3450). A project-local specialist room can therefore approximate Room2, but a shared Room1 containing organization-wide Butler/ProjectMaster and leaders from several products requires an additional coordination layer or an explicit change to these boundaries. Global DMs are a separate primitive, not evidence of a native cross-project room. Membership, escalation rules and responsibility also remain organizational configuration. New agents are subscribed from lifecycle events by MessageBrokerProxy, lines 346–466. User-directed messages can be persisted and routed with conversation affinity (lines 659–871), so dashboard and Telegram interactions need not become unrelated histories.

A concrete code-path trace is a human mentioning an existing agent in a linked Telegram group, for example @butler investigate the CRM onboarding failure. This is a source trace, not an executed test of Telegram:

  1. Telegram V2 input, lines 2200–2255, accepts supported message/attachment types, filters bot echoes and commands, then routes group messages. Unstructured private DMs receive help, which is a material difference from Wingman's desired single private conversation.
  2. Group routing, lines 2285–2340 and 2460–2550, finds the linked project and topic/chat default, resolves the sender's Hub identity, fetches that user's visible agents and classifies mention targets. It does not create a project based on the meaning of “CRM”. The group already identifies the project.
  3. Inbound delivery, lines 3490–3545, packages a structured message and posts to the Hub's broker inbound endpoint with broker/plugin identity and HMAC signing where configured.
  4. Hub inbound, lines 60–115, validates broker authentication and body; lines 535–665 persist conversation-linked message state, preserve deferred messages during reincarnation and handle persistence failure before dispatch. Conversation identity is carried into delivery rather than reconstructed only in the UI.
  5. The Hub dispatches to the agent's Runtime Broker; delivery reconciliation, lines 728–755, resolves the current broker and refuses a held agent. Manager message delivery, lines 632–666 and 1420–1490, buffers ordinary input, selects the project-scoped target and injects text using the harness delivery specification.
  6. The harness reasons and uses its coding tools. If configured as Butler it can message other agents using outbound handling, lines 1122 onward, and request clarification via the documented status convention. That organizational behavior is custom agent logic, not an implicit step of the transport.
  7. Replies pass through message routing and persisted user conversations in MessageBrokerProxy, lines 659–871, with Telegram publishing handled by the plugin. A product acceptance decision still needs Wingman records and policy.

The inspected conversation-envelope tests, lines 88–133 and 134–179, assert that delivered conversation identity matches persisted identity for DM/thread cases. They use a test dispatcher and do not prove a real Telegram-to-container round trip. This precision matters: routing durability is substantial evidence; autonomous product management is not established by it.

Major additional capabilities and grounded innovations

Multiple harnesses and extensible container-side provisioning. Scion supports an external-harness boundary instead of making one model SDK the center of the product. Reusable harness configurations can stage authentication and invoke provisioner scripts inside the container: container-script harness, lines 25–125. For Wingman this enables heterogeneous specialist backends and versioned execution images. Integration would require maintaining harness delivery/resume/status contracts, credentials and images; substituting Codex as the reasoning loop does not automatically standardize all session semantics.

Distributed control with durable intent and identity-aware runtime operations. The combination of outbound broker control channels, persisted intent, compare-and-swap claiming and exact run targeting is more valuable than simply “remote containers.” Reconciliation, lines 30–100, and exact-run manager contracts, lines 75–110 and 505–558, let commands outlive a transient transport failure without casually stopping the next incarnation. This is an implementation-distinctive resilience mechanism, not a claim of industry novelty or universal exactly-once execution.

Reincarnation with explicit configuration changes and recovery handoff. Reincarnation API, lines 30–130 and 681–809, and recovery handoff, lines 25–75, support evolving a persistent worker, including eligible host moves, while keeping stable identity. This could let Wingman upgrade a long-lived leader or move execution capacity without inventing a new agent. It still needs a reliable handoff and supported storage mode. It is not a serialization of arbitrary process memory.

Skill registry with content pinning. The skill registry handlers, lines 55–82 and 281–323, expose registry management and pin a URI to a content hash. The broader resolution/configuration path integrates reusable skills with provisioning. This supplies a foundation for audited reusable organization instructions beyond Wingman's directory convention. Wingman would still need decide who publishes/updates role skills and how changed versions propagate to existing agents; pinned content improves reproducibility rather than magically improving instructions.

Versioned artifact bundles with constrained review and agent feedback (opt-in alpha). This is a substantial publication/review subsystem, not only a notification callback. hub.artifacts is alpha and defaults to false: experiment registration, lines 503–512. The Hub also requires the artifacts settings section to be enabled; route guard, lines 815–836, returns 404 before authentication outcomes when either gate is off. Thus the capabilities below are implemented but are not generally available in the default configuration. Chat attachment artifacts have their own experiment and must not be conflated with enabling this publication UI/API.

An artifact has stable identity and version references. A publisher creates a pending version, uploads the required files, and finalizes it into a ready version. Each manifest file carries path, byte size, SHA-256 and media type, with an entry file for a bundle: API, lines 117–165. Required uploads omit unchanged current-version content and deduplicate identical hashes. Upload handling actually verifies size and digest rather than trusting the manifest (versions, lines 640–705). Finalization refuses missing files, reapplies current bundle/file limits and claims the pending version before advancing state, so a partially uploaded bundle is not exposed as a ready release (lines 738–845). This could support Wingman's versioned specifications, reports, screenshots and deliverable bundles with inspectable references. It introduces blob storage, publication ownership, retention and artifact-to-task relationships that Wingman would need operate.

Reviews are versioned bundles of kind review, whose text carries CriticMarkup against an explicit published base. This is deliberately constrained: after stripping markup and normalizing text, the result must match the base; reviewers cannot silently add/remove files, move the entry, alter non-text content, or introduce text changes outside marks. Review implementation, lines 30–50 and 87–150, implements these comparisons. The review must name a still-current base; stale bases and a concurrent newer publication are rejected/discarded with stale_review, while unmarked changes yield unmarked_changes (review finalization, lines 185–245; finalize race checks, lines 824–849). This is a grounded review-integrity mechanism, not proof that the reviewed material is correct.

After a review version becomes ready, artifact review notification, lines 42–105, sends system feedback to the owning agent. Delivery is best effort and refuses an owner currently reincarnating. Wingman could connect specification/deliverable reviews to the responsible ProductMaster or worker and use version references as evidence in executive summaries. Publication readiness and marked review integrity still do not establish test completion, product acceptance, or delivery against a definition of done. Those workflow gates remain Wingman functionality.

Delegated authority and bounded scheduled work. Beyond a personal single-user organization, Scion carries multi-user authorization and explicit delegation. A user can issue an agent-bound, expiring grant with a frozen permission ceiling, which the agent exchanges for a short-lived credential. It is not an unrestricted delegation of the user. See delegation model, lines 5362–5425, and delegation handlers. Scheduled work stores an authority revision and frozen effect ceiling and intersects applicable ceilings at execution: scheduled authority, lines 30–65 and 446 onward. This helps prevent a future wake from becoming an implicit privilege escalation. Wingman could use this to bound ProjectMaster and specialist powers, but would need map responsibilities to permissions. It is authorization machinery, not management approval of product decisions.

Authenticated access to running application ports. Port forwarding, lines 40–74, 241–292 and 393 onward, implements agent registration and Hub-authorized forwarding over a reverse tunnel, with request/stream limits. This can give a human access to a development server inside a remote agent environment without exposing an inbound host port. Wingman could connect previews to deliverables and acceptance sessions. It still needs application-start/test logic, and authenticated forwarding is not production deployment or product acceptance.

Managed cloud interactions as an alternative execution path. Managed agents, lines 95–145 and 202–222, create background cloud interactions and retain interaction/environment references, with separate message/stop/delete operations. This broadens the platform beyond container-only execution. Wingman should distinguish those resources from independent Codex containers: workspace, terminal, tools and provider availability have different boundaries. No cloud API was called here, so availability and feature parity remain unverified.

Optional A2A interoperability bridge. The separate extras/scion-a2a-bridge service exposes discoverable agent cards and per-project/per-agent JSON-RPC endpoints, with optional v0.3 REST compatibility: bridge server, lines 218–275. Its SDK executor translates incoming A2A messages into Hub structured messages, waits on the event log, and translates responses into SDK task events (executor, lines 55–75 and 264–340). This could connect Wingman agents to external agent clients without exposing Scion-specific messaging APIs. It requires operating another service and defining which agents are exposed, credentials and task ownership. An A2A protocol task is request/execution state, not a ProjectTracker ticket.

Authentication is configurable, including API key, bearer, Hub-validated credentials and federation; none explicitly opens authentication (server validation/auth setup, lines 161–213). Streaming is implemented, but transport boundaries differ: the legacy channel-based SSE path sends as the bridge administrator and refuses federated callers, whereas the SDK executor supports caller-aware routing (stream, lines 267–278 and 325–338; SDK streaming adapter, lines 349–360). Cancel emits a canceled task event and attempts a Hub interrupt when possible. Federated users receive no interrupt. Missing routes or failed sends can still produce a canceled protocol status. One credential-construction failure path falls back to the bridge administrator (executor cancellation, lines 471–525). Thus protocol cancellation does not prove the coding process stopped. No interoperability, auth or streaming round trip was exercised here.

Operational scheduling and resource conservation. Persisted one-shots, cron/time-zone schedules, scheduler concurrency control, explicit blocked reporting and auto-suspend mechanisms give the platform useful long-running operations features. See scheduler, lines 30–100 and 511–550; schedules, lines 28–52; blocked convention, lines 11–19. Their value is avoiding lost wakeups and distinguishing intentional waiting from runtime stalls. They do not measure productive progress; Wingman must supply the tracker evidence and agent reasoning that makes supervision useful.

These mechanisms are grounded design strengths of this checkout. No research was performed to claim historical originality or superiority to every other system.

Practical use for Wingman

Use directly, subject to deployment validation: the Hub/project/agent registry, independent container workers, reusable templates, remote Runtime Brokers, direct/group messaging, Telegram transport, retained homes, lifecycle/input controls, scheduler and operational web views. These cover a large fraction of the difficult infrastructure behind the Mac/Endeavour organization. A human can already inspect an agent and reach its live session. The UI is a credible starting point for Wingman's detailed workspace.

Adapt:

  • Create Butler/ProjectMaster/ProductMaster/TechMaster and specialist templates.
  • Configure permissions and spawning authority.
  • Assign project leadership and communication membership.
  • Give each product durable directives and shared coordination records.
  • Implement Butler's cross-project conversation context and a management-room bridge or additional cross-project coordination layer compatible with native project-scoped groups.
  • Add notifications and schedule-driven ProjectMaster inspections. Telegram requires special attention: this revision's V2 group/topic workflow and DM-help behavior do not implement the desired single private Butler relationship. The transport can be reused, but intake/routing must be designed deliberately.

Build as product functionality:

  • conversational existing/new-project classification.
  • proportional discovery and tracked clarification cycles.
  • product definitions and testable acceptance criteria.
  • a shared task model with assignment/dependencies/blockers/comments.
  • technical planning and integration policy.
  • independent verification and delivery acceptance.
  • semantic executive briefings and linked agent summary timelines.

The existing agent graph and logs should remain underlying evidence rather than be relabeled as these missing views. Add relationships between agents, tasks, specifications, conversations, changes and tests so an executive summary can be traced through the same organization.

Recommendation: evaluate Scion as a foundation or reference architecture for execution plus collaboration, not as a turnkey replacement for Wingman. Its strongest fit is the distributed persistent-agent substrate. A Wingman implementation on top would still be a meaningful application with its own domain model, workflows and acceptance tests.

Scion: agent lifecycle and coordination mechanics

Companion to the main assessment. Same pinned revision and static-verification limits apply. Paths below resolve into the unmodified local checkout.

1. What is persistent, and what is a run?

Scion's durable agent record is an organizational/execution identity. ID is a UUID, Slug is unique within a project, and Name is a display name. It records template, project, broker, runtime, status, configuration, owner/creator, ancestry and generation. A new container/process run is not automatically a new agent identity. For the normal brokered coding-agent path, several instances of the same template really are independent agents: separate rows, homes, execution and native harness state. The optional managed-cloud path is different: it retains provider interaction/environment references without a local container or mounted home, as described in the main assessment. Agent model, lines 34–155.

Do not collapse these concepts:

Concept Actual role Wingman implication
Template Reusable instructions/configuration/material used to define an agent A reasonable place for BackendCoder or TestMaster profile definition.
Harness configuration Provider/tool-specific executable, provisioner, credentials, readiness/delivery and capabilities Codex compatibility is an operational property, separate from a job title.
Agent Durable identity associated with a project, ownership and ancestry Can be a directory member and tracker assignee.
Run/container A particular execution of that agent Must be distinguished in logs, cancellation and retry handling.
Native harness session Coding tool's own conversation/checkpoint state in its home Resume is harness-dependent. The Hub record alone cannot reconstruct it.
Hub conversation Persisted human/agent DM or project-scoped group collaboration Can support project-local Room2; cross-project Room1 needs an additional layer. Not the full native tool transcript.
Task prompt/task summary Initial instruction or short current description Does not supply a ticket's acceptance/dependency/history semantics.

The agent state has infrastructure phase and runtime activity. Activity completed is separate from phase stopped. An agent can finish an assignment without ceasing to exist. blocked explicitly indicates intentional waiting, while stalled is an inferred operational problem. State definitions, lines 348–462. Wingman should preserve this distinction in executive views: “container running,” “waiting for a business decision” and “accepted product delivery” are different facts.

2. Definition and creation

The default template is intentionally generic. It references agents.md and system-prompt.md. The shipped system prompt is a placeholder, while the instructions require explicit status reporting for user questions, intentional blocking and task completion. That is a useful reporting convention but no predefined ProductMaster/TechMaster organization. Template, lines 15–19; instructions, lines 1–29.

CreateAgentRequest can name project, broker, template, harness config/auth, profile, task, branch, workspace, labels and inline configuration. It supports provision-only and environment-gather/bootstrap paths. The Hub's attribution function records either a creating user's root ancestry or a creating agent's existing ancestry plus that parent. This is concrete hierarchical agent creation, rather than only a nested textual roleplay. The lineage is also relevant to permission decisions. Creation request and attribution, lines 243–330 and 807–844.

createAgentInProject performs the extensive admission/configuration work before broker dispatch. The agent gets a project identity and explicit placement. The optional asynchronous launch protocol has a launch ID and broker-owner identity, distinct outcomes for missing environment versus accepted background launch, and eligibility checking. Its gate includes the experiment, request opt-in, a launching request rather than provision-only/reprovision, timeout and broker capabilities. “Async launch exists” therefore does not mean all calls are always asynchronous. Creation implementation, lines 1585 onward and 2814–2991; launch protocol, lines 30–173.

Broker-side provisioning resolves the template/configuration, builds the home/workspace, writes agent state and prepares instructions/skills. The provisioning code has explicit containment, worktree and host-state handling. It is much more than copying one prompt into an LLM request. Prompt rendering and skill installation occur through separate mechanisms. Provisioning, line 1890 onward; instruction injection, lines 5051–5184; skill installation, lines 5184–5405.

3. Execution, tools and authority

AgentManager.Start resolves retained/new agent material, checks resume preconditions, reads or replaces prompt.md, builds runtime configuration and calls Runtime.Run. Homes carry harness configuration and state; workspaces carry source/artifacts. The supported workspace choices include a shared workspace, private clones, worktrees over a shared base, and non-git shared/private directories. These modes govern whether colleagues see files immediately, need git integration, or can be moved together. Start, lines 291–404, 2798–2890; workspace request modes, lines 60–77.

The current resolver is declarative/container-script oriented. A container-script harness has an on-disk bundle and runnable provisioner; unusable legacy/missing provisioners fail resolution. Generic declarative metadata can supply command/environment/capability/readiness/delivery behavior. This opens an extension point for different coding tools while keeping execution ownership in Scion. Harness resolver, lines 28–130.

Codex's bundle uses container-side Python provisioning for authentication, MCP translation and native config writing. It declares C-c interruption, delayed readiness, Enter submission, native instruction/skills paths and resume --last. Its default command bypasses Codex's own approvals/sandbox. Its capability table honestly reports incomplete support: model-call limit enforcement is unavailable, project MCP is not native, and the system prompt becomes instructions. Codex config, lines 15–123. A Wingman deployment cannot assume that a configured maximum or generic prompt field has identical semantics across harnesses.

Platform authority is a separate layer. Ancestry/standing checks require a live, unheld chain and an active root human admitted to the project. Security role values are capabilities, not job responsibilities. Delegation grants name boundary, allowed permissions, expiry, purpose and credential TTL; v1 rejects subdelegation. Grant exchange/use still checks current authority. Soft/hard deletion, restore and reincarnation revoke grants through transaction hooks; agent/issuer suspension and issuer deletion use best-effort revocation after commit, backed by use-time/exchange denial. Suspension preserves grants associated with a newer run. Standing, lines 28–106, 150 onward; delegation request, lines 64–135; revocation, lines 31–87.

That separation is useful for Wingman: a ProductMaster may need to communicate and publish specifications without the same infrastructure permissions as a machine-maintenance agent. It also means that creating a child agent is both a work-delegation and an authority-admission event. It should not be modeled solely by an unrestricted shell spawn.

4. Routing and concurrent execution

The Hub routes commands to the agent's assigned broker. HybridBrokerClient.route distinguishes:

  1. The current Hub replica owns the broker's control socket: send locally through it.
  2. Another live replica owns it: record/forward durable intent and notify that owner.
  3. No live owner but the broker exposes an endpoint: use direct HTTP.
  4. No current route: retain pending intent for reconciliation on reconnect.

Stateless co-located broker identities have a separate replica-independent direct HTTP rule. Router, lines 30–118. This is actual multi-host/multi-replica machinery, not a list of terminal tabs.

Concurrent agents have separate runtime execution. Capacity limits/quotas can constrain launch placement. The capacity read model explicitly distinguishes resolved values and enforcement state: a configured value may be presented with not_enforced. Capacity, lines 29–105. Thus concurrency is real, but the assessment does not infer a tested fleet size or promise 100 simultaneous healthy coding agents.

Distributed execution does not automatically unify source files. The shared-dir API states that a declaration does not create directories everywhere immediately; first use provisions backing storage, and Hub writes can only reach storage the Hub can resolve. A remote broker-local directory remains local unless the selected storage/export design shares it. Shared-dir contract, lines 102–124. For Wingman, shared coordination can live in the Hub while product source placement remains stable per host.

5. Chat input is not a transactional task queue

The DM operation consolidates send budget/rate limiting, length validation, mode/cross-project authorization, attachments, message persistence, SSE, delivery rendering and dispatch. Adapter paths handle conversation resolution, group/human routing, wake and mentions. DM operation contract, lines 37–143. This is a strong common delivery core. It also makes clear that persistence, transport delivery and agent understanding are separate stages.

Ordinary input uses a debounce buffer because multiple collaborators “typing” into a terminal concurrently can corrupt native harness input. It coalesces bursts, waits for harness readiness, serializes flushes per agent/project and retries bounded delivery failures. One agent's readiness wait does not block another agent's buffer. Interrupt input bypasses the normal buffer and is delivered immediately. The manager first checks for a definitively missing/stopped target, while transient lookup errors allow buffering; asynchronous failures can be reported back through a callback. Buffer, lines 30–126, 200–307 onward; manager message path, lines 632–711.

This provides steering and useful background operation. It is not an exactly-once semantic task executor. The DM result contract explicitly distinguishes accepted, failed, ambiguous and deferred results. Accepted means persisted and dispatch accepted, not harness consumption. Ambiguous means the send may have landed while bookkeeping or the request failed, and callers must not automatically replay it. A reincarnating target can receive a persisted deferred message without immediate dispatch. The next generation reads it through conversation catch-up. DM outcome contract, lines 175–219. The buffer is not a shared backlog of acceptance-governed tickets. Wingman should add durable assignment states and acknowledgments above this layer rather than trying to infer completion from a successful message send.

Group conversations have an execution-aware default agent. When an agent posts without mentioning another agent, the group's default can receive a delivery copy. A sender never wakes itself; mention-copy message types do not recursively fan out; symmetric per-pair caps limit storms. Those controls matter for autonomous teams conversing without a human gating every turn. Group default delivery, lines 28–120. A project-local management room can therefore appoint a coordinator, but native groups do not span projects: creation requires a project ID and adding an agent from another project is refused (conversation handlers, lines 740–748 and 1070–1097). Cross-project group[] forwarding is also rejected before effects (message handler, lines 3420–3450). This supports project-local Room2 or local management discussions; Wingman's shared Room1 spanning organization agents and product leaders requires an additional coordination layer or a deliberate change to project boundaries. The escalation policy itself must also come from Wingman instructions and records.

6. Telegram request trace

The current Telegram V2 plugin is worth distinguishing from the legacy V1 implementation still in the checkout. It has persisted group/topic links, user mappings, agent caches, registration, notifications and both polling/webhook handling. V2 implementation, lines 48–127, 390–442 and 2196 onward.

For a plain message in a linked product group:

  1. handleGroupMessage loads the group link and applies a topic default override before the group default.
  2. It resolves the sender to a linked Scion human and obtains the agent list as that sender. This avoids making the bot's broad service identity the effective human's visibility.
  3. Explicit bot/agent mentions, replies to bot messages and default routing select recipients. A default must still exist in the sender-visible agent set; unknown/unavailable lists are distinct from proven absent agents.
  4. The plugin creates structured messages with project/channel/thread/sender context and forwards them with authenticated inbound delivery.
  5. The Hub's broker inbound and agent message adapters authorize and dispatch to the agent's assigned execution broker.
  6. The manager submits input to the native harness. The agent can issue outbound messages or report a question/completion to trigger notifications.

Evidence: V2 group route, lines 2285–2671; V2 delivery, lines 3398 onward; Hub inbound; outbound message request/routing paths, lines 61–150.

/setup presents accessible projects, /default selects a group/topic agent, and /agents lists the linked project's agents. Commands, lines 173–330, 387–419. This is substantial Telegram coordination infrastructure. It is still an explicit addressing model: a single Butler that semantically identifies projects, creates new ones and returns each answer to the correct ProductMaster would be additional behavior running on top.

7. Persistence, resume, wake and scheduling

Hub collaboration state persists independently of the viewing browser. Native harness continuity relies on the retained per-agent home/session. Start refuses a resume of an agent without its state directory; Codex's bundle supplies native resume arguments. A new prompt may replace prompt.md, while a resumed run is not automatically re-fed the original task. Start/resume, lines 291–404; Codex resume declaration, lines 75–85.

Message wake is explicit lifecycle work. Admission runs before wake so a rejected message cannot start a target. A suspended agent is resumed under a start claim, quota re-reservation and run intent; readiness is awaited and remaining initializing input can be buffered. A managed cloud runtime explicitly refuses suspend/resume wake. Concurrent starts may defer delivery rather than duplicate the start. Wake, lines 35–180; readiness polling, lines 41–103.

Cron schedules can send messages or dispatch agents, with author-time and fire-time authority checks. One-shot events are persisted and reloaded; overdue events can fire after downtime. Multi-replica claim support transitions the event before side effects, preventing several replicas from delivering the same timer independently. A handler error/panic is recorded as failure. This is useful scheduled work infrastructure, but not proof of automatic recovery from every failed handler: claiming before effects also means application-level idempotency/retry design remains important. Schedule inputs, lines 29–62, 140 onward; timer recovery/claims, lines 511–650.

Notifications subscribe to status events and can deliver to another agent or a human. The fan-out example tells an orchestrator to request notifications and wait instead of polling researchers. Notification dispatcher, lines 37–117; example, lines 39–62. Wingman can combine these: completion messages for routine handoffs, periodic ProjectMaster review for missed blockers. The platform does not decide what constitutes useful product-management intervention.

8. Failure, interruption and recovery boundaries

Run identity is a recurring safety mechanism. The Manager contract supports stopping an exact run and deleting a resolved runtime target rather than blindly re-resolving a reused slug. Hub status handlers mark reports with the authenticated token's run ID and guard against deletion/reincarnation/start-window regressions. Late status from an older container must not make a deleted or replaced agent look healthy. Manager contract, lines 72–111; status guards, lines 105–205.

Broker routing recognizes transient deferral and bounded retry separately from non-transient failure. The reconciliation loop drains persisted dispatch intent when the appropriate broker connection becomes available. Retry, lines 138 onward; reconciliation, lines 31–102, 205 onward. This supports continuity across disconnected execution hosts. It does not itself restore lost source files or infer whether a partially completed code change is correct.

Stall detection and optional auto-suspend address operational waste. Auto-suspend runs through a bounded, deduplicated pending set and a server-owned worker. A slow/panicking batch does not hold the detection scheduler slot indefinitely. Overflow agents remain stalled rather than being silently counted as suspended. Worker, lines 30–71, 95–178. This is infrastructure supervision, distinct from a ProjectMaster discussing a stalled integration with ProductMaster and the coder.

The container's sciontool init/supervisor handles child execution and termination; configured duration limits signal the child and report a limit-exceeded status. Status values include explicit crash/exit reasons. Supervisor, lines 165–326; init limit path, lines 1508–1607 and 2047–2096. The report does not infer a universal automatic “retry the failed coding task until product accepted” loop from these controls.

9. Completion, reincarnation and retirement

The default instructions tell agents to announce task_completed and stop asking further questions. This is self-reported task completion. The platform can notify a creator/subscriber; when the opt-in alpha artifact subsystem is enabled, versioned artifact bundles can be reviewed, but it does not independently determine that a product's definition of done was met. Wingman must distinguish a worker's claim, TestMaster's verification and human/product acceptance. Default completion instructions, lines 21–29; status command, lines 20–103.

Reincarnation is a managed identity-preserving replacement, not native transcript compaction. The API accepts handoff and a dry run, supports selected persistent configuration patches and rejects unsupported overrides such as changing harness config through that request. It returns a plan with old/new fields, warnings and target generation. The worker uses step-specific writes so fresh status/configuration fields are not overwritten by a stale full-row snapshot. It always starts a fresh native session, without the harness resume flag. A generated preamble tells the agent to verify its environment, catch up on saved conversations, notify the responsible owner and continue the handoff's immediate active work without repeating completed work. With no handoff, it must reconstruct context from branch, conversations and project scratchpad. Reincarnation API, lines 37–140; worker contract and fresh-session start, lines 31–116, 905–913 and 1646–1703.

Broker moves have an explicit eligibility contract: runtime target, workspace mode, reported storage, same export, actual workspace location, target profile/health/access/capability/capacity. A shared-export move carries the workspace. A forced recreate move permits fresh provisioning and calls out local state lost. Neither is arbitrary live process migration. Move contract, lines 33–142.

Deletion claims a leased sticky marker, publishes deleting state and starts a detached engine. A quick completion responds synchronously. A slow one returns accepted and reports later. Concurrent deletes join rather than independently tearing down the agent. Cleanup is run-aware, with file retention/deletion decisions and soft/hard deletion separated. Grant revocation participates in lifecycle transactions; expired soft-deleted rows have a purge contract. Delete engine, lines 36–107; purge/finalization contract, lines 201–244; credential lifecycle, lines 31–87.

These are strong lifecycle foundations for a standing organization. Wingman still needs its own retirement policy: when to suspend after acceptance, retain knowledge, archive a project, reuse a specialist or create a fresh instance. Scion provides the mechanisms. The purpose document specifies the policy.
