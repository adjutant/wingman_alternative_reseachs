# AgentRail assessment

## Identity and fit verdict

- **Repository:** https://github.com/oxnw/agentrail
- **Local checkout:** `research/agentrail/repo`
- **Assessed commit:** `ac75225f090ac67fafbdf63b3fdcd5ad520d867d`
- **Assessment date:** 2026-11-05
- **Product at this revision:** `@agentrail-core/cli` 0.1.8, Node.js >=24, a self-managed, single-instance coding-task control plane; see [package.json](../repo/package.json), lines 1–25, and [README](../repo/README.md), lines 9–18.

**Verdict: a useful delivery subsystem and design reference, but a weak replacement for Wingman's standing development organization.** AgentRail implements real local coding processes, durable specialist profiles, issue assignment, PR submission, actionable CI/review feedback, human blockers, task events, and shipping APIs. Its strongest fit is the execution-and-delivery portion after someone has already established a repository and a well-defined issue. It does not implement Butler, Telegram intake, product/technical leadership, product discovery, organizational rooms, an executive dashboard, or distributed host management. Planned cloud team/fleet/history/dashboard features must not be credited to this checkout.

Two boundaries materially affect adoption. The managed runner launches fresh executions rather than resuming a durable Codex conversation, and its normal automatic path submits a PR but does not call the shipping API. Also, the role-template tool preferences are configuration data without an enforcement path into the runner. These are implementation findings, explained below, rather than conclusions drawn only from marketing language.

## Architecture and execution model

AgentRail uses a TypeScript CLI, Node HTTP service, provider adapters, and local JSON/JSONL storage. It does not supply a conversational team framework or operational workspace UI. [server.ts](../repo/src/server.ts), lines 116–182, constructs authentication, run, subscription, delivery-worker, and runner-supervisor objects. It injects lifecycle, provider, and routing services into HTTP. It starts the supervisor after listening, then starts provider and outbound event delivery.

[server-runtime.ts](../repo/src/server-runtime.ts), lines 103–223, wires `AgentTaskQueue` and `AgentProfileStore`. It also wires routing rules, audits, cursors, and background polling. Adapters provide GitHub/Linear intake, GitHub submission/review, and GitHub Actions/CircleCI status. Provider operations require real credentials. Unsupported runtime configurations return errors.

The authoritative coordination entity is a **task**. [task-store.ts](../repo/src/task-store.ts), lines 96–145, stores status, assignee, criteria, project/goal context, source issue, submissions, CI, review outcome, blocker, ship/rollback state, and routing provenance. The service exposes agent-scoped task reads/mutations and operator routing/run APIs; [app.ts](../repo/src/app.ts), lines 414–705 and 732–1190, is the relevant route inventory. The root HTTP page serves the static marketing landing page, not an operational dashboard ([app.ts](../repo/src/app.ts), lines 304–306).

A local **agent profile** is a durable identity and routing configuration, backed by an env file and API key. The supervisor discovers those env files and starts one `agent run --env-file ...` Node child per valid agent. Each child continuously reads assigned tasks, starts work, constructs a fresh run, launches an external coding CLI, consumes its structured handoff, publishes changes, and returns to its queue. This gives genuinely independent coding processes across profiles. It does not create an organizational hierarchy or peer chat: see [local-runner-supervisor.ts](../repo/src/cli/local-runner-supervisor.ts), lines 103–179, and [agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 547–750.

Persistence is deliberately local. Profiles are JSON snapshots ([agent-profile-store.ts](../repo/src/agent-profile-store.ts), lines 90–117); events are appended JSONL, with a 72-hour in-memory replay window ([task-event-store.ts](../repo/src/task-event-store.ts), lines 4–5, 74–126 and 142–150). The run store adds file locking, reloads, and atomic temp-file rename for multiple local processes ([agent-run-store.ts](../repo/src/agent-run-store.ts), lines 312–409 and 426–483). These are useful single-host coordination mechanisms, not a shared database or distributed lease service.

## Agent definition, creation and full lifecycle

### What is actually an agent?

The durable **profile** carries `agentId`, display name, arbitrary role, template ID, active/paused/disabled routing status, capability/ownership tags, repo allowlist and maximum concurrent tasks. Its stored source/change reason/updated-by fields support auditability ([agent-profile-store.ts](../repo/src/agent-profile-store.ts), lines 21–35 and 171–193). A **template** is reusable specialization content. It is not a running agent. A **managed runner process** is the queue-watching Node process attached to one profile/env. A **run** is one task execution by an external CLI, with a newly generated `run_...` identity and local artifacts. A **task** outlives runs and carries delivery state. There is no persistent model conversation ID in `AgentRunRecord`; see [run schema](../repo/src/agent-run-store.ts), lines 46–74.

Templates can express specialist focus without code changes: frontend, backend and review roles use routing metadata, instructions, preferred/caution/forbidden workspace areas, checks, required evidence and escalation cases. The loader validates YAML, disallows unknown keys and resolves installed versus built-in IDs; ambiguous duplicate IDs fail ([agent-role-template.ts](../repo/src/agent-role-template.ts), lines 73–95 and 139–175). That is strong extensibility for issue workers, but adding “ProductMaster” as a string would not create product-scoped leadership, conversations or delegation semantics.

A crucial distinction is **declared preferences versus effective permissions**. `runtime.cleanSlate` and builtin/MCP/skills allow/prefer/deny lists are parsed and validated ([agent-role-template.ts](../repo/src/agent-role-template.ts), lines 30–37 and 254–263), but a search of `src` finds no consumer of `template.runtime`. The role-brief builder includes instructions, paths, checks, evidence, escalation and commands, and omits runtime tools ([managed-run-role-brief.ts](../repo/src/managed-run-role-brief.ts), lines 63–89). Therefore a role's `deny: browser` is not an enforced capability boundary. Effective restrictions come from the separate global runner execution policy.

### Creation and provisioning

`agent create` performs these steps:

1. Collect runner, model, name, template, repository, capacity, and scopes.
2. Prepare instructions and PUT the routing profile.
3. Configure routing and create a setup verification task.
4. POST an API key and build the per-agent environment.
5. Run the doctor check. Write the environment only if that check succeeds.

Failure reports identify completed provisioning steps and recovery information. Creation is not one atomic transaction. See [agent-management.ts](../repo/src/cli/agent-management.ts), lines 449–673. Instances can share a template while retaining separate IDs, keys, queues, and histories.

The env selects the executable family and optional model, stores the API credential and repo allowlist, and supplies capacity to the managed queue. Creation does not itself launch a model. On server startup the local supervisor discovers managed envs once and spawns queue watchers; newly created profiles are not dynamically discovered by that running supervisor ([local-runner-supervisor.ts](../repo/src/cli/local-runner-supervisor.ts), lines 103–115). An explicit agent-run command starts one without restarting the server.

### Assignment, scheduling, concurrency and workspace selection

Provider routing first considers enabled deterministic rules. A single top-priority target wins; conflicting targets go to triage. Otherwise a configured local classifier extracts work requirements, with confidence/missing-information gates and suitable-agent versus explicitly configured best-effort fallback. Selection scores optional capabilities, ownership hints and idle/load information. An agent's capacity is a score penalty, not a hard intake exclusion. Paused/disabled profiles are excluded from new routing. See [routing control plane](../repo/src/intake-routing-control-plane.ts), lines 847–934, 1003–1097, 1197–1223 and 1542–1552. There is no agent-created technical work breakdown or dependency scheduler.

A watcher counts active local runs and builds a priority/due-date queue: resume in-progress work first, retry CI/review feedback second, new tasks next, setup verification only when no normal work is runnable. Blocked/terminal/already-running tasks are skipped ([managed-run-task-queue.ts](../repo/src/managed-run-task-queue.ts), lines 49–178). When idle it waits for task SSE with a timeout, then rereads state; wake events include task updates, CI failure/recovery, review changes and user blockers ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 2184–2244). This is continuous reactive scheduling, not a calendar or a reasoning supervisor periodically inspecting a portfolio.

Although capacity/open-slot accounting is real, the selected tasks run in an awaited `for` loop, so one watcher does not concurrently execute its selected batch ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 614–655 and 686–745). Concurrency is naturally obtained through different profile processes. The capacity test only proves that an already-active run prevents another launch. It does not establish parallel batch execution ([test](../repo/test/agent-runner.test.ts), lines 2782–2885).

Another multi-project limitation is repository selection: a watcher resolves one repository from the first configured allowlisted match, or a primary/default repo, **before** entering its task loop ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 581–586 and 2616–2636). It does not select a local repo afresh from each task's source. A Wingman adapter should therefore bind profiles to one repo or change this path before allowing broad multi-repo assignments.

### Execution, permissions and reporting

Each run creates prompt, log, result, report, and context paths. It allocates a run-scoped context token. It resolves the role brief and repository map, then fetches CI and review context. It compiles policy, stores a starting record, prepares the workspace, and transitions to running. See [agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 870–1008.

The implementation calls its workspace a `worktree`. Default preparation actually uses `git clone --no-local --no-hardlinks`. It rewrites origin and selects a stable task branch. A retry prefers the existing remote branch. See the same file, lines 3023–3043. Each run consumes a full clone rather than linked-worktree storage.

Codex execution uses sandboxed `exec`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, disabled hooks, JSON output and a filtered environment. Claude gets generated sandbox/settings and a recipe prompt; Cursor/custom execution has weaker mappings and strict validation can block unsupported enforcement. External sandbox wrapping can supply an additional boundary, but source labels should not be mistaken for proof of an installed sandbox's behavior. See [runner-execution-policy.ts](../repo/src/runner-execution-policy.ts), lines 450–517 and 526–730. Provider credentials and operator API keys are filtered; AgentRail owns push/submission. Pre/post filesystem checks can block denied files and unauthorized changes ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 1009–1057 and 1090–1110).

The child can inspect a live run-scoped context or fall back to the snapshot when networking is unavailable ([run-context.ts](../repo/src/cli/run-context.ts), lines 131–175). Progress, completed results and blocked metadata go through local mailbox JSON/JSONL files or report APIs. The wrapper archives and consumes local files after the launch returns, validates handoffs and persists reports. See [agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 1083–1129 and 1768–1859. Run reports are useful durable milestones, but there is no live semantic tool-call viewer: stdout/stderr accumulate in memory and are written to `runner.log` on child close ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 3130–3202).

### Continuity, interruption, failure and recovery

Identity, task state, provider metadata, reports and branches survive process restarts. A resumed task starts a **new run**, with latest task/CI/review and previous user-action context. It does not resume the Codex conversation. The stable task branch preserves published code changes, while uncommitted/unpublished state in an abandoned clone is not automatically rebased into a new run. See [prompt/run setup](../repo/src/cli/agent-runner.ts), lines 870–914, [previous user action lookup](../repo/src/cli/agent-runner.ts), lines 2166–2169, and workspace preparation above.

Runner timeouts SIGTERM then SIGKILL the child ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 3150–3156). Service SIGINT/SIGTERM invokes controller/supervisor shutdown. The supervisor signals managed Node children, but there is no dedicated per-run cancellation/steering API, and this inspection did not establish recursive descendant cleanup ([server.ts](../repo/src/server.ts), lines 172–176; [supervisor](../repo/src/cli/local-runner-supervisor.ts), lines 118–128). A `cancelled` enum is not equivalent to a human lifecycle control.

The run store checks owner process liveness and age to reclaim orphaned active runs into failed records. Repeated infrastructure failures become an awaiting-user task blocker. The supervisor separately applies restart delay/window/limit and pauses automatic restarts when failures repeat. See [run reclaim](../repo/src/agent-run-store.ts), lines 506–594, [reclaim handling](../repo/src/cli/agent-runner.ts), lines 753–824, and [supervisor restart](../repo/src/cli/local-runner-supervisor.ts), lines 158–194. Exceptions during setup/launch/handoff are recorded and can block the task ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 1151–1196). CI/review failures instead make the existing task runnable for a new corrective execution. This is a meaningful operational recovery system, with local PID semantics that should not be extended unchanged across hosts.

A human blocker includes a reason, action required and resume instructions. Operator resolution requires an idempotency key and resolution summary, clears the blocker, restores `todo/start`, and appends a task event ([agent-task-queue.ts](../repo/src/agent-task-queue.ts), lines 545–643). That is an explicit handoff to a human. It is not an ongoing discovery conversation or a management-level escalation.

### Completion, acceptance and retirement

A zero exit code alone is insufficient. The wrapper requires a meaningful structured handoff/state transition. It can commit uncommitted changes, push the stable task branch and submit through AgentRail. Submission records summary, checks and artifact references and results in reviewable task state ([agent-runner.ts](../repo/src/cli/agent-runner.ts), lines 1712–1764 and 2040–2056). Checks are supplied by the coding runner; required-check names in a role brief do not independently execute tests or prove acceptance.

CI/review observations project allowed actions onto tasks, reject stale observations for an older submission, and expose `fix` or `ship` as appropriate ([agent-task-queue.ts](../repo/src/agent-task-queue.ts), lines 1100–1204 and 1425–1489). The ship API validates task eligibility and delegates to GitHub merge, then marks the task done and emits shipment state ([agent-task-queue.ts](../repo/src/agent-task-queue.ts), lines 823–922). **The managed queue does not select ship-only tasks, and no automatic ship caller exists in its runner or provider poller.** Shipping must be driven by another API client/agent/operator. Thus “run succeeded” can mean “PR submitted,” not “product shipped/accepted.”

Profile paused/disabled status prevents future routing, but the watcher does not poll profile status to kill already-running work. Source searches found no agent archive/delete lifecycle, conversation rename/fork/compact, or automatic post-run clone garbage collection. Repository removal edits configuration only ([global-management.ts](../repo/src/cli/global-management.ts), lines 141–160). Runs, clones and exports are retained for inspection. A Wingman deployment would need explicit retirement, retention and storage cleanup policy rather than assuming task completion cleans them up.

## Coordination mechanics and a traced request

AgentRail coordinates by durable task state, assignment rules, provider observations and events. Agents normally see their own assigned queue; operator scopes handle configuration and broader run inspection. API scopes distinguish tasks, routing, review, CI, shipping and webhook access ([agent-auth-store.ts](../repo/src/agent-auth-store.ts), lines 10–24). It does not implement Wingman's all-agent shared conversational tracker: a frontend worker and backend worker cannot simply join a room, discuss an API and create dependency-linked subtasks through a built-in coordination protocol.

The following is a concrete **source trace of an ordinary GitHub issue**, not a claim that a live issue was executed during this assessment:

1. **Intake and continuity:** GitHub polling/webhook handling feeds the intake adapter. It resolves the repo, creates a deterministic `github:owner/repo:issues/N` identifier and recognizes already-imported tasks; updates preserve the existing lifecycle while refreshing issue data. Criteria come from the issue's acceptance-criteria list. [GitHubIssueIntakeAdapter](../repo/src/github-issue-intake-adapter.ts), lines 148–260, 314–355 and 483–506.
2. **Route and explain:** New intake asks `RoutingControlPlane.ingestProviderIssue`, which evaluates rules/classifier, persists assignee/triage and a routing reason plus decision ID, records an audit and emits an assigned-task update. Conflicts or missing information remain triaged, without automatically asking the human product questions. [Routing control plane](../repo/src/intake-routing-control-plane.ts), lines 666–702, 847–934 and 1442–1519.
3. **Wake and start:** The assigned profile's queue watcher wakes from SSE or timeout, selects the task, starts it, assembles context and launches the coding CLI in its own clone. [Runner](../repo/src/cli/agent-runner.ts), lines 647–713 and 870–1008. A task start is not a peer delegation conversation.
4. **Implement and hand off:** Runner returns mailbox JSON. The wrapper checks policy/files and handoff, commits/pushes the branch, and calls submit with a run-derived idempotency key. [Runner](../repo/src/cli/agent-runner.ts), lines 1083–1129 and 1722–1751. GitHub submission reuses an existing PR by idempotency marker or head/base before creating another. It can post back to the issue and request reviewers. [Submit adapter](../repo/src/github-submit-adapter.ts), lines 38–128.
5. **Observe and correct:** Provider CI/review delivery projects fresh state onto the task. CI failure or review changes can expose `fix`, emit events and awaken another clean execution with compact failure/review context. [Task queue](../repo/src/agent-task-queue.ts), lines 1100–1204 and 1207–1245; [queue classification](../repo/src/managed-run-task-queue.ts), lines 129–150.
6. **Human decision or shipment:** A blocked runner can persist a human action and pause that task until operator resolution; otherwise CI/review eventually expose ship. A caller invokes the separate ship API to merge and mark done. [Resolution](../repo/src/agent-task-queue.ts), lines 545–643; [shipment](../repo/src/agent-task-queue.ts), lines 823–922. Neither branch creates a Butler/Telegram exchange or a product-wide acceptance ceremony.

Task events carry task versions, trace IDs, actors, changed fields, summaries and links. SSE supports replay/filtering, and outbound subscriptions deliver signed events with persisted retry state. These are good integration seams for Wingman's tracker and notification services. They remain event transport rather than chat history, a dependency graph or executive summaries.

## Major additional capabilities and distinctive mechanisms

### Provider lifecycle control, idempotency and compact agent-facing state

Beyond Wingman's broad product description, AgentRail supplies a concrete GitHub/Linear/CI adapter layer with retry-safe task mutations, persisted source metadata, PR reuse and actionable `availableActions`. Provider operations sit outside the sandboxed model process, separating code production from authenticated publishing. [GitHub submit adapter](../repo/src/github-submit-adapter.ts), lines 38–128, and [task queue](../repo/src/agent-task-queue.ts), lines 823–922, ground this behavior. Wingman could avoid making every specialist rediscover provider APIs, but must define who may submit/merge and make its own product acceptance rule authoritative. Idempotency is bounded by local persistence/provider lookups, not a general distributed transaction guarantee.

The **task affordance projection** converts provider state into a compact set of next actions. Actions include `fix`, `view_ci_status`, `resolve_blocker`, and `ship`. Agents can use those actions without replaying raw service logs. Submission-head and timestamp checks reject stale CI/review feedback that would regress a newer submission. See [agent-task-queue.ts](../repo/src/agent-task-queue.ts), lines 1425–1489. This supports economical repeated execution. It does not evaluate the product's business definition of done. This assessment makes no historical or industry-wide novelty claim.

### Role templates combined with repository maps

Reusable roles name semantic areas such as frontend source or tests; repository maps translate those areas into actual paths and commands. Brief construction caps paths/lists/instruction length and falls back with warnings if mapping/template data is missing ([managed-run-role-brief.ts](../repo/src/managed-run-role-brief.ts), lines 36–115 and 143–161). Repo setup can obtain an AI proposal but retains a deterministic starter fallback ([global-management.ts](../repo/src/cli/global-management.ts), lines 102–137).

This is a useful portable-specialist mechanism: one BackendCoder profile definition can be mapped to different codebases without embedding all repository paths in its identity. Its limits matter: instructions truncate at 600 characters and lists at six items; runtime tool preferences never reach effective permissions. Wingman would need a richer versioned directive/context system for leadership and product knowledge, and should preserve the distinction between instruction advice and enforced policy.

### Runner policy and run-scoped read context

The system compiles sandbox and environment policy for each run and coding CLI. It refuses unsupported strict mappings. It checks protected filesystem paths before and after execution. A hashed run token and snapshot fallback expose task context without giving provider credentials to the child. See [execution policy](../repo/src/runner-execution-policy.ts), lines 450–517 and 526–730; [token verification](../repo/src/agent-run-store.ts), lines 597–605; and [context loading](../repo/src/cli/run-context.ts), lines 131–175.

The valuable mechanism is a **restricted coding execution that hands results back to a privileged lifecycle owner**. It maps well to specialist agents producing code while TechMaster/delivery services own publishing. It is runner-dependent, not universally enforced: Cursor/custom adapters and arbitrary commands have explicit limitations, and role-template denies are separate from these global restrictions. Runtime compatibility with the installed vendor CLIs was not exercised.

### Event subscriptions and bounded recovery

Signed webhook subscriptions have persisted per-event/per-subscription delivery records, retry schedule, attempt numbers, delivery IDs, response/error state and exhaustion. Success is 2xx; 410 deactivates the subscription; network/5xx failures retry ([event-delivery-worker.ts](../repo/src/event-delivery-worker.ts), lines 12–25, 69–96 and 122–230). This could connect lifecycle events to Butler notifications, tracker updates or independent review services, with receiver deduplication and a plan for the 72-hour event replay boundary.

Local process restart limits and stale-run reclaim complement event delivery recovery. They prevent an infrastructure fault from endlessly consuming model runs while still allowing new work after a recoverable exit. These mechanisms are operationally useful but do not replace semantic supervision: a stalled product, missing design decision or inter-agent disagreement requires a reasoning/management layer.

### Rollback API, SDKs and evaluation harness

The GitHub rollback adapter creates a revert-style commit from the merged commit's parent tree, creates a rollback branch/PR and best-effort reopens the source issue ([github-rollback-adapter.ts](../repo/src/github-rollback-adapter.ts), lines 49–159). That is a concrete code rollback proposal, beyond Wingman's described acceptance flow. It is not application/database deployment rollback; Wingman must assess it alongside later repository changes and operational state.

TypeScript and Python SDKs expose task/provider/shipping/event APIs; see [TypeScript client](../repo/sdk/typescript/src/client.ts), lines 41–225, and [Python client](../repo/sdk/python/src/agentrail/client.py). They make an adapter integration more plausible than wrapping interactive CLI output. The repository also contains a lifecycle benchmark with control, AgentRail, paired and phase-attribution execution, local lifecycle artifacts and aggregate results ([benchmark entry](../repo/benchmarks/agentrail-swe-lifecycle/run.mjs), lines 5–45 and 68–85). That supplies a reusable evaluation approach for lifecycle overhead and correctness. No benchmark performance claim is adopted here. The harness was not run and its existence does not prove product success.

## Practical use for Wingman

**Usable directly as an internal delivery component:** specialist profile IDs, provider issue intake/routing, structured task state, PR submit/reuse, CI/review adapters, blocker/resume protocol, task events and SDK surfaces. The intended integration boundary would be TechMaster-created implementation tickets entering AgentRail, with task/run/provider events reflected back into ProjectTracker. Butler and project leadership would remain Wingman actors above that boundary. Separate single-repo specialist profiles are the safest match to the current runner's fixed repository resolution.

Adapt these areas:

- Retain native Codex conversation IDs where Wingman requires conversation continuity.
- Connect role profiles to the agent directory and team model.
- Enforce real permissions through profile tooling.
- Adapt run snapshots and brief truncation for authoritative product directives.
- Add a shipping caller that follows acceptance decisions.
- Route blockers through Butler and retain answers as project knowledge.
- Generate human summaries and timelines from reports and events.

Multi-host work needs registration, placement, shared coordination, leases, remote runner state, and host-aware recovery. Local file locks and PID checks cannot provide that distributed contract.

**Still to build:** Telegram/Butler, portfolio/new-project intake, per-project leadership and discovery, research/clarification records, specifications and product DoD, technical decomposition/dependencies, rooms/direct collaboration, ProjectMaster supervision, executive/project dashboards, directory/timeline/workspace drill-down, conversation lifecycle/steering controls and integrated product acceptance. These dominate Wingman's organizational product experience, so adopting AgentRail would accelerate a bounded subsystem rather than supply most of the platform.

The repository is source-available under a custom license, not a permissive open-source license. The checked-in text explicitly describes internal use/modification and restricts third-party offerings incorporating/exposing the software ([LICENSE](../repo/LICENSE), lines 7–13, 22–42 and 69–98). That is a material reuse constraint for deciding between internal deployment, source incorporation and a separately distributed Wingman product. This report does not establish permission for a particular future distribution.
