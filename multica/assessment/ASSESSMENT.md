# Multica assessment

## Identity and fit verdict

- **Product:** Multica, an issue and collaboration workspace for humans and externally installed coding agents.
- **Repository:** https://github.com/multica-ai/multica
- **Local checkout:** `researchs/multica/repo`
- **Assessed commit:** `3c5c8b245359b9b8e913a47f97211f2a3426f149`
- **Assessment date:** 2026-11-05.
- **Method:** fresh static source assessment against [Wingman's purpose](../../WINGMAN_PURPOSE.md) and [the assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md). No dependency installation, services, real-agent execution, or source changes.

**Verdict: a strong candidate for Wingman's shared operating platform, with substantial organization behavior still to configure and build.** Multica already supplies durable named agents, real CLI execution on separately registered machines, projects and issues, agent-to-agent delegation, squads, scheduled/event-driven wakeups, Telegram transport, live transcripts, and an actual management UI. The built-in Mika Chief of Staff is a persisted workspace agent. Its instructions tell it to accept goals and select chat or issue execution. They also specify project creation, work routing, and proposals for reusable specialists, squads or autopilots. It is more than a terminal grid or model-persona catalog.

The fit is strongest at execution, coordination records, continuity, and visibility. It does not ship Wingman's complete product organization: there is no first-class ProductMaster/TechMaster pair, proportional domain discovery process, scope/specification/acceptance record system, cross-project executive supervision policy, or organization-room escalation hierarchy. Those can be implemented on its primitives, but a configurable prompt and a custom workflow are not evidence that the complete product-development discipline already exists. Its normal unit is an **issue-backed run**, not an always-running employee conversation. One durable agent can also have several concurrent runs, so identity and process instance are separate.

**Reuse constraint:** the checked-in [LICENSE](../repo/LICENSE), lines 1–65, is Apache 2.0 **with additional conditions**, including restrictions on third-party hosted/embedded services and UI branding changes. Its text distinguishes internal organizational use. Treat this as a source-available candidate and inspect those terms before deciding to redistribute a Wingman derivative. This report does not establish a licensing entitlement.

## Architecture and execution model

The deployed system separates a central coordination service from execution hosts. The Go API owns workspace membership, agents, runtimes, projects, issues, squads, conversations, task queues and event emission. PostgreSQL/sqlc is the durable source of truth. WebSocket hubs provide user-facing updates and daemon communication; Redis-backed components support cross-process realtime delivery, liveness and claim optimizations. The server constructs the router/services, starts lifecycle/recovery work and registers database-backed scheduled jobs in [server main](../repo/server/cmd/server/main.go), lines 683–735 and 821–863. This is a service plus workers, not a single prompt runner.

A user's machine runs the Multica Go daemon. It registers provider runtimes, heartbeats, claims persisted work, prepares local execution directories and provider-native configuration, and calls a backend for the provider executable. [Daemon execution](../repo/server/internal/daemon/daemon.go), lines 8820–8865 and 8933–8947, constructs the executable path, environment, task/runtime identity and provider options, resolves a backend, and passes a prior provider session ID. [Backend interface](../repo/server/pkg/agent/agent.go), lines 17–23 and 179–230, returns a running `Session` with streamed messages and one terminal result. For Codex specifically, [codex.go](../repo/server/pkg/agent/codex.go), lines 375–382 and 1079–1212, launches `codex app-server --listen stdio://` and manages its process lifecycle. Agents really execute tools/code through the underlying provider; Multica does not supply the model itself.

The work queue is an explicit execution state machine. Assignment/status/mention/chat/autopilot/wakeup inputs create queued records; claims mark them dispatched; environment preparation precedes a guarded start. The provider emits messages; completion/failure/cancellation settles the durable state. [Queue SQL](../repo/server/pkg/db/queries/agent.sql), lines 760–821, uses runtime-health conditions, same-agent/conversation serialization, priority order and `FOR UPDATE SKIP LOCKED`. The service enforces independent agent and runtime concurrency limits under locks: [task service](../repo/server/internal/service/task.go), lines 3602–3710. It is therefore possible for agents on different machines to collaborate through the same issue/comment state. It is not shared process memory or automatic migration of a local provider session to another host.

The UI is a monorepo with Next.js web and Electron desktop consumers of headless `packages/core`, UI primitives and shared business pages in `packages/views`; mobile is a separate Expo client. These boundaries are explicit in [repository instructions](../repo/AGENTS.md), lines 13–30. Project pages contain editable metadata/resources and an issue surface, rather than merely execution tiles: [project detail](../repo/packages/views/projects/components/project-detail.tsx), lines 114–168 and 270–350. Individual agent pages combine identity/configuration, live presence, Now/Recent work and links to transcripts. UI inspection here establishes source wiring, not rendered runtime verification.

There is also a cloud-runtime integration and Qoder-specific execution path in the tree. The distributed-daemon conclusions below do not depend on assuming the externally operated cloud runtime is available, equivalent to local Codex, or fully auditable from this checkout.

## Agent definition, creation and lifecycle

### What an agent actually is

A Multica agent is a persistent workspace-owned configuration and identity, backed by the database, with a name, instructions, description, owner, invocation access, runtime binding, provider settings, skills, custom arguments/environment and MCP configuration. The runtime describes where and how an agent can execute. The task is one queued attempt. A backend `Session` is a currently running provider execution. The provider's session/thread ID is conversation state. These are distinct concepts. One named agent can execute several tasks concurrently, while repeated turns for the same issue/chat are serialized. It is inaccurate to describe every database agent row as its own continuously alive process, or every retry as a new permanent teammate.

The primary creation path starts at [CreateAgent](../repo/server/internal/handler/agent.go), lines 1458–1538. It requires a name and runtime. It validates concurrency, invocation permissions, workspace membership and runtime access. It also validates provider options and skill ownership. A transaction inserts the agent, access targets and attached skills (1654–1733). UUID identity is durable. A duplicate workspace name produces a conflict (1705–1711). Description/persona text does not itself make an independent agent: the persisted runtime binding and subsequent task execution do.

There is also an AI builder. [agent_builder.go](../repo/server/internal/handler/agent_builder.go), lines 21–44, specifies a structured `<agent_draft>` protocol with instructions, model, skills and permission scope. The model proposes/refines a configuration, while the UI reviews/confirms creation. The server creates a **hidden carrier agent and private chat session** to run that builder conversation (57–161), and persists unfinished drafts (168–241, 271–355). This carrier is an execution implementation detail, not an additional product worker the user hired. Builder model/runtimes can be changed only through guarded rebind handling (407–536); that is a concrete lifecycle path, not merely a static agent form.

Mika is a third, distinct case. [mika_agent.go](../repo/server/internal/handler/mika_agent.go), lines 74–103 and 121–176, provisions/reuses one workspace Chief of Staff under a workspace-level advisory lock. Its `system_key` is product identity independent of editable name. [builtin_agents.go](../repo/server/internal/service/builtin_agents.go), lines 8–21 and 50–79, distinguishes visible user-kind Mika from invisible system carriers and composes shipped system instructions with workspace notes. Updating the server's embedded system instructions changes subsequent executions without overwriting workspace notes. This is a useful organization-wide representative, although its role remains an instruction layer over the common execution engine.

### Triggering, routing and actual execution

An issue write is inspected by [WillEnqueueRun](../repo/server/internal/service/issue_trigger.go), lines 102–208. Backlog parks assignments; triage refuses runs; direct agent assignment selects that agent; squad assignment resolves its leader. A workflow-column handoff is new work even when it routes to an already involved agent. Pending-task deduplication and self-loop suppression prevent common duplicate dispatches. Comments have a separate trigger path, because a mention can intentionally wake an agent even on a backlog issue.

The task service captures agent/runtime/conversation identity and attribution when enqueueing: [task.go](../repo/server/internal/service/task.go), lines 1281–1414 and 1460–1544. The runtime ID on a task is not irrevocable authority: claims revalidate the current agent binding and runtime health. SQL and service locks protect dispatch and capacity. Default agent concurrency is six with a supported range of one to fifty: [concurrency configuration](../repo/server/internal/agentconfig/concurrency.go), lines 5–23. Runtime capacity is a separate ceiling. This offers real concurrency, but does not allocate an automatic best team size for a product.

On the host, the daemon prepares an environment before provider execution, with a preparation deadline and renewable lease; [daemon.go](../repo/server/internal/daemon/daemon.go), lines 70–99 and 7341–7393. Environment creation injects workspace/project context, agent instructions, skill files and provider-specific configuration. [execenv.go](../repo/server/internal/daemon/execenv/execenv.go), lines 38–90 and 129–163, describes a generated task directory, a configured local directory, or a per-task git worktree. Repositories can be checked out on demand. An in-place local directory is an actual user directory, not a copied sandbox; worktree mode isolates code branches for parallel tasks. Sidecar manifests support removing only daemon-created files afterwards: [context.go](../repo/server/internal/daemon/execenv/context.go), lines 121–160.

Prompt construction distinguishes wakeup, chat, comment, autopilot, quick-create and ordinary assignment: [prompt.go](../repo/server/internal/daemon/prompt.go), lines 328–393. The ordinary assignment prompt directs the agent to fetch the current issue and thread summaries, rather than treating an old embedded issue snapshot as authoritative. Stable runtime instructions precede run-specific appended context, preserving a reusable provider prompt prefix. The backend receives the executable, effective model/settings, MCP and resume pointer. [executeAndDrain](../repo/server/internal/daemon/daemon.go), lines 9747–9791, starts the provider and forwards events while installing supplementary-input handling only when negotiated.

### Tools, authorization and containment

Tools are primarily the real coding CLI's tools plus the Multica CLI/API, configured MCP and skills. A dispatched run gets a task-scoped credential, not the user's general personal token: [daemon identity/environment](../repo/server/internal/daemon/daemon.go), lines 155–186. Invocation permissions decide which humans/agents may start or steer another agent; runtime access is separately checked. Attribution tracks an originating/accountable human even across agent delegation, which matters for permission checks and connected application access.

This is not equivalent to strong host isolation. The checked-in Codex policy defaults to `danger-full-access` on Linux and Windows and currently falls back to it on macOS unless a known fixed version is configured. The policy explicitly places containment at the daemon user's VM/container/OS-account boundary. See [codex_sandbox.go](../repo/server/internal/daemon/execenv/codex_sandbox.go), lines 64–131. A worktree/task directory separates files and configuration, but does not itself revoke host capabilities. Wingman would need to choose its execution-host boundary and credential policy deliberately, especially for agents on different machines.

### Persistence, resume and scheduling

Completed/failed attempts retain provider session IDs, workdirs, branch pointers, result/error and usage. [CompleteTaskWithTransition](../repo/server/internal/service/task.go), lines 4640–4726, atomically settles the task and chat outcome/session pointer; its compare-and-swap semantics make replay idempotent. The queue's [GetLastTaskSession](../repo/server/pkg/db/queries/agent.sql), beginning at line 1042, is the issue continuation lookup. A runtime change or lost local session can force a fresh provider conversation. Codex session-rollout existence is checked before a resume pointer is accepted; missing state becomes a continuity gap rather than silently pretending that the provider remembers (daemon lines 9173–9188).

Issue comments and project knowledge remain available even when a provider thread is lost. Thus **durable organizational record** is stronger than **guaranteed durable model context**. Host-local stores are not centrally replicated and are subject to configured retention. This is a practical, explicit limitation for a Wingman distributed organization.

Agents normally sleep by having no process between tasks. Scheduled persistence is implemented at the platform level: issue wakeups support `at`, `every`, `cron` and `event`; rules have expiry, revision, maximum-fire limits and conditions; autopilots support scheduled/manual/webhook dispatch. [Wakeup input/validation](../repo/server/internal/service/issue_wakeup.go), lines 31–58 and 108–227, and [autopilot dispatch](../repo/server/internal/service/autopilot.go), lines 417–515, show actual durable scheduling/idempotency. A ProjectMaster can therefore be reactivated by a configured schedule rather than occupying an idle long-running CLI. Nothing in the examined default Mika instructions automatically creates the Wingman portfolio-supervision schedule.

### Steering, cancellation and recovery

Live steering is persisted and authorized per run, not assumed for every provider. [Session](../repo/server/pkg/agent/agent.go), lines 185–195, distinguishes a supplement hook from provider-confirmed readiness; [task_supplement.go](../repo/server/internal/handler/task_supplement.go), lines 19–106, exposes capability and delivery receipts. Agent comments can target active runs using the same permission model. A normal new comment may instead queue a later turn. The squad instructions explicitly distinguish new delegation from steering an existing worker ([squad brief](../repo/server/internal/handler/squad_briefing.go), 211–222).

Cancellation changes the server record and then stops the host execution. The source documents a short lag while daemon polling catches cancellation: [agent.go](../repo/server/internal/handler/agent.go), lines 2906–2916. Codex uses bounded turn interruption/process cleanup, and the common session contract requires cleanup acknowledgement when advertised. A `cleanup_unconfirmed` result becomes blocked rather than automatically continuing alongside a potentially live old process: [daemon.go](../repo/server/internal/daemon/daemon.go), lines 9195–9201; [Session contract](../repo/server/pkg/agent/agent.go), lines 179–184. These are stronger safeguards than simply marking a task cancelled in the UI.

Failures are classified, not all blindly retried. [FailTaskWithTransition](../repo/server/internal/service/task.go), lines 5074–5163, normalizes the reason, determines reason-specific retry eligibility/attempt budget/backoff, and creates a retry in the same transaction as failure. Lost runtimes, stale dispatch leases and running-time liveness have recovery queries: [agent.sql](../repo/server/pkg/db/queries/agent.sql), lines 1230–1320. The daemon separately attempts fresh-session recovery when a provider resume is positively rejected or known unsafe. It retires poisoned session IDs and checks rollout availability. Those mechanisms address transport/process/context failures. They do not prove that a superficially successful implementation meets requirements.

Terminal delivery itself has a durable local outbox. [terminal_report_queue.go](../repo/server/internal/daemon/terminal_report_queue.go), lines 34–104, 209–280 and 703–784, writes one namespaced file per task, atomically flushes it and replays completion/failure acknowledgements after disconnection. It persists no auth token. Repeated permanent rejection can quarantine a report instead of discarding it. This reduces a serious distributed-system gap: code can finish while the server is temporarily unavailable, without the daemon simply forgetting the result on restart.

### Completion, acceptance and retirement

A backend's `completed` status means the provider finished its turn. An empty text result is valid if work occurred through tools. The daemon's [terminal mapping](../repo/server/internal/daemon/daemon.go), lines 9195–9247, makes this explicit. It is separate from issue completion and product acceptance. Squad leaders are instructed to keep the parent in progress during delegation, assess the overall goal on later turns, and move to review when satisfied; humans or integrations normally finish the issue. Custom project workflows replace those specific status moves. Pull-request linkage and merge/CI events provide additional delivery signals. There is no universal gate that forces integrated product tests or a ProductMaster's DoD assessment before a provider run is called successful.

Retiring a user agent archives its identity, cancels its pending/active tasks, and preserves the record for restoration: [ArchiveAgent/RestoreAgent](../repo/server/internal/handler/agent.go), lines 2812–2903. Built-in Mika cannot be archived through that path. Host resource cleanup is separately governed by GC retention for completed/orphan task directories, artifacts, caches and conversation/memory stores: [gc.go](../repo/server/internal/daemon/gc.go), lines 27–81 and 85–128. Keeping a historical agent row does not guarantee its detailed local workspace remains forever.

## Coordination mechanics and a request trace

The clearest real coordination protocol is **issue assignment → squad leader → worker mention → worker response → leader reevaluation**. This is source-traced behavior, not a live experiment or an invented sample transcript.

1. A human creates or updates an active issue with `assignee_type=squad`. `WillEnqueueRun` resolves the persisted squad and leader, checks readiness and selects that leader ([issue_trigger.go](../repo/server/internal/service/issue_trigger.go), 175–208). The squad task enqueue path records leader-task/squad context ([task.go](../repo/server/internal/service/task.go), 1431–1544).
2. The registered daemon claims the queued row with runtime and serialization guards. The claim payload includes the squad operating protocol and roster. The [brief](../repo/server/internal/handler/squad_briefing.go), 34–95 and 179–209, instructs the leader to read the issue, select members by role/skills, post exact mention links, record an `action/no_action/failed` evaluation and end its turn after dispatch.
3. The leader uses the real Multica CLI to post a delegation comment. [CreateComment](../repo/server/internal/handler/comment.go), 1659–1738 and 1948–1953, persists the message and invokes trigger/steering handling. `triggerTasksForComment` computes target agents and enqueues them; explicit agent/squad mention outcomes distinguish queued/coalesced/blocked targets (1995–2015, 2082–2095, 2134–2253). Plain text `@name` is insufficient: dispatch uses structured mention links containing target type and UUID.
4. Worker tasks may execute on different runtime hosts, sharing the same issue record and comment history through the API. The ordinary worker prompt fetches current issue and threads. These workers are independent provider executions, not roles alternated inside the leader's one context.
5. A worker posts a progress/result comment. Routing can return to the **exact delegating guest squad**, not just whichever squad currently owns the issue. The implementation carries authoring-task/delegation provenance. [The regression test](../repo/server/internal/handler/squad_worker_comment_wakes_leader_test.go), 24–61 and 64–152, exercises exact guest routing, changed leader/permission rejection and deleted-delegation fallback. Its later test (157–170 onward) explicitly covers the ordinary squad-owner leader being woken by worker output.
6. The leader gets another real task. It may delegate the next step, ask the reporter, record `no_action` silently, or move the parent toward review. Mandatory evaluation gives humans an observable decision even when no chat comment is necessary. A successful dispatch is explicitly not accepted completion.

There are two complementary coordination styles. **Comments/mentions** are conversational, permit several agents on one issue, and preserve a shared discussion. **Project workflows** are structured handoffs: entering a status assigns the issue to the configured agent, squad, human, creator or project lead and supplies step instructions ([issueworkflow.go](../repo/server/internal/issueworkflow/issueworkflow.go), 1–18, 36–43, 158–172). **Wakeups** provide dependencies on child stages, another issue's state or PR conditions. They evaluate stored facts, not business success. The parent-child records and task/provenance events are a practical shared work graph, but this is not evidence of arbitrary DAG planning or guaranteed deadlock-free organizational execution.

Human direction can begin in Mika chat or Telegram. A Telegram installation resolves a workspace and bound agent, verifies the sender's account binding and current workspace membership, isolates direct chats/groups/forum topics, and feeds the shared channel engine. [Telegram resolvers](../repo/server/internal/integrations/telegram/resolvers.go), 68–79 and 104–156, provide the concrete routing/security boundary. Mika's instructions turn goals into issues/projects and route them, but project selection is model reasoning over the workspace, not a Telegram transport feature. Wingman would still need to specify which agent owns every pending clarification, how a human answer resumes the right project conversation, and how management escalation traverses its leadership layers.

## Substantial additional capabilities

**Provider and runtime interoperability.** The unified backend contract supports many externally installed coding-agent CLIs, not only Codex; custom runtime profiles separate a protocol family from the actual executable/launch prefix. The daemon resolves actual executable paths and provider-specific model/thinking controls at run time ([daemon execution](../repo/server/internal/daemon/daemon.go), 8820–8865, 8902–8947; [backend Config](../repo/server/pkg/agent/agent.go), 342–361). This lets Wingman use heterogeneous specialists or alternative hosts. It also adds compatibility and resume/capability variation that a Codex-only organization would otherwise avoid. This report traced Codex deeply. It does not certify every adapter by association.

**External event automation and channels.** Autopilots can run on manual, cron and webhook inputs, use persisted idempotency keys, create issues or execute work, and retain accountable principals/rule versions ([autopilot.go](../repo/server/internal/service/autopilot.go), 62–80, 120–179, 417–515, 611–658). Telegram shares a normalization/routing/session engine with other integrations, rather than requiring a separate task engine. This supports audits, operational reporting or external-triggered work beyond Wingman's initial human product-intake story. Integrating it means deciding who authorizes each automation and ensuring it cannot create unbounded organizational churn.

**Reusable pipeline handoffs and condition-driven joins.** Project workflows encode owner/instructions per status; wakeup predicates can wait for stages of child issues, other issue transitions, checks finishing, merge or conflicts. This is a substantial process engine beyond simply scheduling a supervisor. The useful distinction is implemented in [wakeup conditions](../repo/server/internal/service/issue_wakeup_condition.go), 22–57 and 625–658: the platform checks facts and wakes an agent to interpret them. Wingman could use this for test/acceptance and dependency joins while keeping product judgment in its agents.

**VCS delivery integration.** The server mirrors pull requests, reconciles issue links from PR identifiers, handles merge transitions and CI status, and can reevaluate issue completion ([vcs_webhook.go](../repo/server/internal/handler/vcs_webhook.go), 158–265). Adapter source exists for GitLab and Forgejo alongside GitHub pathways. This can connect work records to actual delivery artifacts and remote CI. It still requires repository conventions and acceptance rules. A merged PR is a delivery signal, not a domain acceptance oracle.

**Plugin and connected-application extension surface.** Plugins have versioned manifests, scope grants, installation/configuration, scheduled/event hooks, callback tokens, storage/secrets and agent-tool/MCP integration. [Plugin service](../repo/server/internal/service/plugin.go), 29–56, 340–406, 490–523 and 698–749, shows a real lifecycle rather than a directory of prompt snippets. The Composio overlay is resolved per originating user and agent toolkit allowlist ([task service](../repo/server/internal/service/task.go), 375–415; [agent fields](../repo/server/internal/handler/agent.go), 1395–1401). This could give specialist agents domain tools without hardcoding them into Wingman, with authorization/versioning and external-service dependencies to manage. Feature gates and deployed external services constrain availability.

**Operational metering and multi-client collaboration.** Usage totals, per-agent/model cost, run-time, failure classification, workspace membership, invocation access and mobile/desktop/web surfaces go beyond Wingman's minimal personal dashboard. [dashboard.go](../repo/server/internal/handler/dashboard.go), 113–128, 176–227, 257–290 and 363–425, includes privacy filtering of restricted agents rather than exposing all agent details through aggregate endpoints. These capabilities matter if Wingman grows into several people/hosts or needs cost oversight, but adopting the platform also means operating its database, realtime connections and upgrade compatibility.

## Distinctive mechanisms and grounded innovation

1. **Coordination turns deliberately end after dispatch.** The squad leader protocol converts a leader into a short-lived, event-reactivated coordinator. It delegates via the same human-readable issue comment that forms the durable record, then records a structured evaluation and stops. Worker messages wake it again. The `no_action` path leaves an evaluation without spamming acknowledgements. This enables standing-team behavior without keeping a leader's CLI waiting for children, and limits gratuitous loops. The boundary is important: selection and correct protocol compliance still depend on the model, while permission, dedup and routing are server mechanisms. Evidence: [squad brief](../repo/server/internal/handler/squad_briefing.go), 34–95, 179–222; [evaluation endpoint](../repo/server/internal/handler/squad.go), 976–1145.
2. **Conversation provenance drives return routing.** Worker replies can wake the specific guest squad that delegated the work even when another squad/human owns the issue. Tasks/comments carry source-task and delegation context; test cases require changed/private leaders to fail closed. This preserves collaboration context more precisely than blindly notifying the current assignee. It is still a policy for known comment/task relationships, not universal semantic conversation routing. Evidence: [guest routing tests](../repo/server/internal/handler/squad_worker_comment_wakes_leader_test.go), 24–152; [comment trigger structure](../repo/server/internal/handler/comment.go), 1495–1506.
3. **Continuity failure is an explicit state.** Resume rejection, missing provider rollout and retired/poisoned sessions are represented and propagated rather than treated as equivalent to a cold start. Stable runtime instruction prefixes and appended per-turn context also preserve caching while allowing current issue data. This enables honest recovery without permanently trapping future runs in a broken conversation. It cannot recreate lost provider history or transfer host-local stores automatically. Evidence: [ExecOptions/Result](../repo/server/pkg/agent/agent.go), 79–99, 294–329; [prompt construction](../repo/server/internal/daemon/prompt.go), 328–343; [rollout check](../repo/server/internal/daemon/daemon.go), 9173–9188.
4. **Execution finality and reporting finality are separate.** Provider cleanup acknowledgement, guarded terminal transitions and the persistent local terminal outbox address different failures. An old process can remain alive. The server can fail to acknowledge a successful turn. A callback can arrive more than once. The platform refuses unsafe continuation for unconfirmed cleanup and replays terminal data idempotently. This is useful distributed execution engineering, not a claim of industry uniqueness. Evidence: [Session](../repo/server/pkg/agent/agent.go), 179–225; [outbox](../repo/server/internal/daemon/terminal_report_queue.go), 34–104, 209–280; [completion transaction](../repo/server/internal/service/task.go), 4640–4726.
5. **Product-owned representative identity with workspace-owned notes.** Mika's stable system key and shipped prompt are separate from editable display name and local instructions. The server can improve the Chief of Staff's baseline without deleting user context, and cannot create another by simply naming a normal agent “Mika.” This is directly applicable to a Butler-like organizational front door. It is a configuration/identity mechanism, not proof that Mika already performs all Wingman management responsibilities. Evidence: [builtin_agents.go](../repo/server/internal/service/builtin_agents.go), 8–21, 50–79; [provisioning](../repo/server/internal/handler/mika_agent.go), 74–103, 121–176.

## Practical fit and remaining work

**Use directly:** the issue/project tracker, agent directory, identity and runtime binding, distributed daemon execution, conversations/comments, squad leader dispatch, task state/retry/cancel, transcript inspection, skill delivery, project resource attachment, workflow handoffs, wakeup scheduling and Telegram adapter. These are implemented systems with clear persistence boundaries. Multica is a credible base for a prototype of the standing organization, not just a set of ideas to borrow.

Adapt:

- Define Butler/ProjectMaster responsibilities through Mika or additional durable agents.
- Choose whether a single workspace contains the portfolio or projects are split across workspaces.
- Create ProductMaster/TechMaster/specialist configurations and squads.
- Bind the Telegram front door.
- Configure project workflow stages and supervisory autopilots.
- Establish shared repository conventions for `DIRECTIVES/SCOPES`, `SPECS` and `HARNESS`.
- Choose host containment, repository/worktree policy, retention and per-agent permissions. Multica's single project-lead field need not prevent two leadership agents collaborating, but the missing relationship and creation/lifecycle policy must be supplied.

Build:

- A reliable product-intake/continuation protocol with project disambiguation.
- Proportional research and iterative clarification with outstanding questions tied to project/agent. A durable scope/spec/acceptance/DoD model and its UI links.
- Automatic project-team instantiation/scaling.
- Policy for product/technical leadership negotiation.
- Management-room or equivalent cross-project escalation.
- Portfolio supervision beyond runtime liveness. An executive view summarizing next work/business blockers.
- Integrated product verification/delivery/acceptance that distinguishes run success, issue review, PR merge and actual product completion. If a full per-agent coding workbench is essential, add it or integrate a development environment.
- Transcripts alone do not satisfy that experience.

A practical first implementation could preserve Multica's issue discussion as Wingman's collaboration record and use custom workflow stages plus wakeups to connect discovery, definition, execution and verification. The main design decision is whether the required room-centered organization should become new native structures or a carefully presented layer over projects/issues. Avoid assuming role prompts alone enforce this process: the existing source demonstrates execution and coordination primitives, while Wingman's semantic obligations need explicit records, validators and end-to-end acceptance evidence.
