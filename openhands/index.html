OpenHands / Agent Canvas assessment

Assessment date: 2026-11-05. Repository: https://github.com/OpenHands/OpenHands

Local checkout: research/openhands/repo. Actual commit inspected: 6d2d9df4af1337abf4ed967a7b396f46fed7559c. The checked-out package is @openhands/agent-canvas 1.35.0, an MIT-licensed React/TypeScript coding-agent interface and local-stack launcher. Its default Agent Server and TypeScript client version is 1.59.0; default automation service is 1.26.1 (package, lines 1–35; stack defaults, lines 3–39). This revision must not be assessed as an older monolithic Python OpenHands distribution.

Fit verdict: a strong candidate for Wingman's detailed coding-agent workspace and a useful reference for profile configuration, conversation lifecycle, worktree isolation, remote backend access, event replay and automation management. It is not a ready-made persistent software-development organization. Its primary durable unit is a conversation on a selected backend. Product ownership, shared project tickets, agent rooms, a Butler/Telegram front door, portfolio intake and management supervision still need an organizational control plane. Crucially, the agent loop, subagent execution, canonical persistence, and scheduler are dependencies or external services. This checkout establishes its integration with those systems, not their complete implementation or runtime correctness.

Assessment target is Wingman's purpose, following the assessment guide. No checkout source was modified, dependencies installed, service launched, or runtime test executed.

Architecture and actual execution model

The published CLI is bin/agent-canvas.mjs, lines 1–24 and 54–126. It is designed to start a static frontend, an Agent Server through uvx, and an automation service through uvx; frontend-only and backend-only modes are explicit. The implementation for the combined stack is scripts/dev-with-automation.mjs: service processes are spawned at lines 727 onward; automation is launched at lines 1252–1348 with an Agent Server URL, session authentication, local storage, and workspace base. Lines 1355–1386 stop service process trees with SIGTERM and then SIGKILL. These are service processes, not a standing collection of ProductMaster and specialist workers. Actual Python service behavior belongs to the separately versioned packages named in config/defaults.json.

The frontend uses React routes, TanStack Query for backend data, and Zustand for UI/conversation state. API calls go through the pinned @openhands/typescript-client, with separate cloud adapters. The repository ownership instructions, under Repository Ownership, explicitly assign Python SDK/Agent Server/conversations/events to software-agent-sdk, reusable extensions to extensions, and scheduling/webhooks/run dispatch to automation. Related source repositories are https://github.com/OpenHands/software-agent-sdk , https://github.com/OpenHands/extensions , and https://github.com/OpenHands/automation . Their source was not fetched as part of this assessment.

The browser chooses a backend and optional cloud organization. Backend types, lines 1–32, represent an ID, host, credentials, local/cloud kind and optional remote-session identifiers. “Local” is an API/backend classification; its host can be remote. Client option resolution, lines 35–68, prioritizes an explicit conversation runtime URL and session key over the currently selected local backend. Cloud conversations split into an App API record and a per-conversation sandbox runtime; sends resolve the runtime URL/key and then send an event with run: true (conversation service, lines 501–535). Remote transport is real, but there is no cross-backend organizational message bus in this path.

Creation has materially different paths. Cloud creation submits repository, branch, optional profile and sandbox information to an App API and receives a provisioning task. Local creation requires a saved agent profile, generates a conversation UUID, resolves the backend's workspace, selects host versus Docker execution where supported, and calls ConversationClient.createConversation. The UI synthesizes a READY start-task wrapper around that response (conversation service, lines 538–754). This “task” is a startup/provisioning operation, not a product backlog ticket. Workspace resolution, lines 20–99, probes server capabilities and resolves host paths against the backend rather than the browser machine.

Persisted records and events are server-owned. The UI additionally caches workspace/profile/repository metadata and preferences in browser storage; some workspace/repository fields are also server tags so grouping can survive browser changes. Values over the server tag length limit fall back to browser metadata (conversation service, lines 681–736). Cloud event history is read from the App API, separately from the live runtime. Local history uses RemoteEventsList (event service, lines 17–37 and 75–154). The implementation of server-side snapshot/event writes and crash ownership is outside this checkout.

Agent definition and lifecycle

What counts as an agent here

A saved agent profile is a backend record with a stable UUID, name, revision and OpenHands/ACP configuration. Activation changes a launch pointer. It does not create an executing worker (profiles service, lines 86–124). An LLM profile is model configuration and is distinct from an agent profile. A conversation is the independently addressable execution/history unit created from a profile. A planner is another conversation with restricted tools and a parent relationship. An SDK delegated task returns a task ID, subagent name, status and content. This is different from the startup task returned by Cloud provisioning and from the frontend's task-list item. None of these should automatically be called a durable organizational employee.

Profiles permit model selection, skill and tool scopes, MCP/secret references and behavior settings. The client represents default tool scope as null and explicit custom scope as a tool array; selecting task/workflow delegation tools also adds task_tracker (profile-tools, lines 16–62). Actual tool execution and enforcement belong to Agent Server. The ACP registry exposes Claude Code, Codex, Gemini CLI, Pi and OpenCode UI metadata and delegates launch command definitions to the TypeScript client (ACP providers, lines 73–113 and 123–150). Codex is an external ACP-backed harness option, not evidence of native Codex app-server orchestration or all-Codex teams.

Creation, identity and execution

resolve-conversation-launch.ts, lines 55–156, awaits backend/org-keyed profile data, resolves explicit versus active profile ID, validates model references, and reads detailed profile router/ACP configuration. Local launches require a profile; cloud can fall back to an org default, with care around restricted secret scopes (lines 159–197). The normal local create path selects a UUID and workspace before calling the server. The server assembles the agent from agent_profile_id. The browser adds runtime-service instructions, skills and optional LLM override rather than reconstructing the full backend agent (request builder, lines 1141–1228).

Creation sends a confirmation policy, maximum iterations and stuck_detection: true. OpenHands profiles also receive Canvas UI, child-launch and secret-request client tools; ACP profiles receive no such Canvas client-tool array (lines 1201–1219). Saved secrets are passed as lookup references for server resolution, not copied plaintext values into the launch payload (secret builder, lines 1109–1138). This demonstrates the client's separation of configuration references and launch data. It does not independently verify server secret policy or sandbox isolation.

Execution runs outside the React application. User input sends an event with run: true. The UI consumes state, actions, observations, errors and streaming frames. Main/planner routing follows the selected code/plan mode and separate sockets. If the runtime is reachable but its socket is unavailable, the REST client can queue input. If a cloud sandbox has no runtime URL, a per-target in-memory map holds messages until its socket opens (WebSocket provider, lines 1300–1329 onward). That last queue is not a durable organization mailbox.

Planning, concurrency and routing

The local planner is a separately created Agent with glob, grep and planning_file_editor, its own model/condenser, the parent's workspace and a plannerparent tag. Its tools cannot implement arbitrary code changes through this configured path. The planner shares project context and writes .agents_tmp/PLAN.md. The code agent builds from it after a human selects Build (planner assembly, lines 1295–1403; build handler, lines 25–51). This is a concrete planner/executor boundary, not two standing leadership positions.

Independent child conversations are another mechanism. The client advertises that the child runs independently, has no parent history and does not stream results back to the parent. Local children inherit the parent's profile/current model and request the same base workspace. The server creates a worktree when requested. Default worktrees branch from the repository's default branch, so they do not carry the parent's in-progress changes. Shared mode is available when that visibility matters (child tool, lines 14–58; launch service, lines 247–343). Parallel execution is therefore possible, but assignment decomposition, conflict avoidance, merges and result harvesting remain the caller's responsibility. The UI contains no organization-wide resource scheduler.

Persistence, resume and scheduling

Conversation identity, launch profile snapshots, server tags and event search enable reopening a session. The main UI loads recent REST history, advances a sequence cursor, subscribes after that cursor and deduplicates replayed durable events. Streaming progress is transient and cleared across reconnection so a later durable message can replace it. Planner and main cursors are independent (WebSocket provider, lines 167–216, 388–488 and 1175–1263). The client supports manual compaction and local forks from a chosen event; Cloud forking explicitly throws as unsupported (conversation service, lines 1083–1109 and 1240–1273). This is substantial session continuity, but it does not establish durable employee identity after changing products or replacing a runtime.

Scheduling is represented by a separate automation object: cron/schedule or event source/pattern/filter, optional continue_conversation destination, selected agent profile, timeout, repository inputs and sandbox keep-alive (automation types, lines 1–28 and 45–123). CRUD, dispatch, cancel-run, capabilities, drafts and Git synchronization call the separate automation API. A goal loop is another external backend operation: /goal --max N objective asks the server to pursue an objective and judge completion after runs. It is not a time scheduler or portfolio supervisor. Neither scheduler implementation nor goal judge internals are present here.

Managed-host lifecycle is a separate layer

DigitalOcean Managed Agents (MARS) introduces another durable definition: an immutable remote Agent Config from which multiple microVM sessions can be launched. Each session runs an Agent Server with its own disk/conversations. This is a real managed execution-host lifecycle, not just an arbitrary backend URL. MARS API, lines 68–82, 243–247 and 282–322, constructs an OpenHands manifest and calls config/session creation, pause, resume, destroy and config deletion endpoints. The launch hook, lines 63–128, creates or opens a session and resumes the latest connectable one; connection routing, lines 62–83, lands in its latest conversation with the backend pinned in the URL.

A session connection is registered as an ordinary local-kind backend even though execution is remote. The Node bridge owns the port-forward tunnel and credentials. Backend attachment/restoration, lines 95–165, registers one backend per session and restores only the active tunnel, since attaching can wake a paused remote sandbox. Disconnecting the transport is distinct from pausing the sandbox or destroying its session. Managed Agents controls, lines 231–268, destroy first and detach only after success, preserve a connection if destruction is refused, and put Stop/Delete behind confirmation. The remote microVM implementation, actual checkpoints/storage guarantees and billing remain external. A durable host config is not Wingman team membership, role authority or a cross-host collaboration bus.

Interruption, failures and recovery

Local Stop calls interruptConversation, intended to cancel in-flight requests; Cloud Stop pauses its sandbox, with a different timing boundary. Resume runs an existing runtime or wakes a Cloud sandbox that has no URL. Stopping a goal cancels the background loop while deliberately leaving its current agent turn running, so halting both needs the separate conversation interrupt (mutation utilities, lines 48–127 and 150–190). This distinction matters for Wingman's Stop semantics and cost controls.

Transport retries are substantive: use-websocket, lines 25–27 and 91–145, uses exponential reconnect delay capped at 30 seconds plus jitter; replaced sockets cannot mutate live connection state, and unmount disables reconnect (lines 95–100 and 162–195). This recovers a view, not necessarily a failed worker task. The client surfaces errors and provisioning failures. Child launch validates inputs, bounds Cloud provisioning polling to 180 seconds, reports corrective guidance, and can retry a failed worktree launch as a shared-directory child (child service, lines 109–203, 294–317 and 351–377). Shared fallback explicitly reports that agents may conflict. There is no automatic management reassignment, project rollback, or acceptance repair workflow here. Stuck detection is requested, but its actual algorithm is external.

Completion, acceptance and retirement

Finish/task observations and automation run statuses report execution outcomes; critic output provides another evaluation signal. Completion does not implement a product acceptance gate, required independent tester approval or Wingman's stop-after-accepted-delivery policy. A planner explicitly ends after finalizing its plan. Product definition of done must come from a higher layer.

Archive is a backend-keyed browser preference (archive store, lines 33–81), distinct from pausing a runtime or deleting server state. Deleting a local parent explicitly deletes tagged planner helpers because the server otherwise orphans children; unrelated delegated conversations are deliberately not indiscriminately cascaded (conversation service, lines 812–845 and 1131–1163). Deleting a profile removes launch configuration, not proof of terminating its existing conversations. Filesystem/worktree deletion details and backend TTL cleanup are external; automation keep_alive exposes the cleanup choice but does not implement it locally.

Coordination mechanics and one concrete request trace

The principal shared medium is a backend conversation event stream plus workspace files. The task list is reconstructed from a TaskTrackerObservation, and the plan is a workspace Markdown file. SDK delegated TaskAction/TaskObservation pairs are rendered with a subagent name, prompt, task ID, status and result (observation types, lines 305–325; visualizer, lines 41–80). Those are credible task/result exchange primitives. They do not by themselves create rooms, shared tickets, dependencies or direct specialist discussions. The profile UI acknowledges workflow_tool_set, but the workflow engine source is external; no unsupported claim about its scheduling/DAG semantics is made.

A concrete inspected route is “start an independent child to add a parser regression test”, matching a checked-in behavioral test rather than an imagined product flow:

  1. An OpenHands profile conversation is created with launch_child_conversation in its client-tool set (builder, lines 1201–1215). The tool schema requires target and a self-contained task brief (schema, lines 61–110).
  2. Agent Server emits the action. The mounted WebSocket provider, lines 922–929, invokes handleLaunchChildConversationAction for that conversation/tool-call ID. This is a browser-mediated side effect, not an always-running backend dispatcher.
  3. The handler, lines 511–545, claims the call in a browser-storage ledger before doing work, validates target/isolation/repository constraints, and dispatches local or Cloud creation. The ledger, lines 10–33, prevents ordinary replay within that stored context but proceeds if storage fails. It is not a distributed exactly-once transaction; multiple browsers and storage loss remain boundaries.
  4. Local creation reads the parent's working directory, profile and current LLM, then calls the common launch path with parentConversationId, initialUserMsg and a worktree/shared workspace mode (child service lines 247–292). The regression-test fixture specifically expects the task “Add a regression test for the parser,” an independent profile launch and the same base directory (test, lines 278–296).
  5. Worktree failure may fall back to shared isolation, with explicit consequences (service lines 294–317). The local start result provides the child ID/status. A best-effort rename may follow, and the outcome includes URL, applied isolation and whether a server parent link exists (lines 319–343).
  6. The result is shown as a toast/link and normally returned to the parent as a prefixed synthetic user message, which runs the parent so it can explain the launch (lines 467–502; result transport, lines 4–28). It is a launch result, not the child's eventual implementation result. During an active goal loop this result message is skipped, because an inbound message would cancel that loop. The toast remains.
  7. Cloud creation targets a connected backend and polls provisioning. A local parent's ID is intentionally not attached as a Cloud parent. The returned outcome says the relationship was not persisted (child service lines 380–463). The user can open the separate conversation. No same-path automatic result join, dependency unlocking, ticket completion, peer room message or merge is performed.

This trace illustrates both a useful mechanism and the gap: creating independent work is implemented; continuous organizational accountability for that work is not. Human approval travels directly through the current runtime's confirmation response. Escalation ownership and routing through multiple leadership agents would need explicit additional records and services.

Major capabilities beyond Wingman's stated product

Multiple coding harnesses and live model configuration. OpenHands and ACP agents share a client surface, with effective runtime model discovery and configurable provider commands. Model router references and launch-time routing instructions can steer an OpenHands profile through a model-selection tool (profile behavior, lines 4–24; request builder, lines 1144–1172). This offers model/harness experimentation beyond Wingman's all-Codex starting organization. It also creates policy differences: ACP and native OpenHands do not receive identical client tools, model switches, settings or cloud options. Wingman should require explicit capability reporting rather than assume one adapter gives identical semantics.

Managed remote-host provisioning and lifecycle. MARS is a substantial additional product surface: create an immutable OpenHands Agent Config with a validated optional VM size, launch sessions, connect through a port-forward tunnel, resume paused sessions, pause/destroy them, and delete unused configurations. The manifest builder, lines 53–82, sets agent: openhands, an explicit template and keep_warm: false; LLM credentials are configured later in the session's Agent Server. The Node bridge, lines 343–438, owns creation/wake/tunnel/cleanup calls rather than exposing a cloud token to renderer code. The credential store, lines 103–116, 160–211 and 249–271, uses supplied secret storage or Electron encryption, with memory-only fallback when persistence is unavailable. This could supply Wingman execution capacity on remote hosts; integration still needs team/assignment routing, provisioned workspace initialization, credential ownership and explicit policies distinguishing disconnect, pause and destructive retirement. It does not supply remote inter-agent coordination by itself.

Event-triggered automation product. The client manages scheduled prompts, event filters, continuation destinations, profile selection, custom bundle uploads, run cancellation, drafts, import/export, custom webhooks and Git synchronization. Automation service, lines 527–670, 748–820, 824–1020 and 1054–1195, contains the API paths and orchestration. These go beyond periodic management supervision: they can support issue-to-agent and repository-triggered work. Integration requires the external automation service, deployment capabilities, credentials and outcome mapping. This checkout does not establish delivery guarantees or retry policies of the scheduler.

Embeddable workspace and extension pages. Library exports, lines 1–59, expose browser/conversation/files/settings/sidebar/terminal components, providers, query client, scoped styling and extension types. Canvas extensions can contribute additional pages. The module loader, lines 25–41, imports an authenticated, self-contained ESM source through a Blob URL without putting the session key in that URL. This is a practical opening for a Wingman-specific tracker or directory frontend. An in-process imported module is a trusted code extension, not evidence of a security sandbox. It still needs a backend organizational data model.

Local, container and Cloud working environments with Git inspection. Workspaces are selected using backend capability probes; code browsing, commits/diffs, terminal, browser and VS Code sit beside the chat. Git service, lines 101–158 and 161–239, supports conversation changes, commits and commit diffs. This makes review and diagnosis concrete and reduces dependence on conversational claims. It does not automatically integrate branches from independent workers or implement deployment acceptance.

Verification/critic and secret interaction. Profile-owned critic configuration and action confirmation are exposed alongside live coding. Secret request and lookup mechanisms allow a running agent to obtain configured integrations without embedding raw values in the task prompt. These are useful independent controls, but their actual enforcement and evaluation algorithms live in Agent Server. Wingman could reuse their interface patterns while retaining separate product acceptance authority.

Distinctive mechanisms and grounded innovation assessment

These are noteworthy engineering mechanisms in this revision, not claims of historical invention or industry-wide uniqueness.

A durable-event / transient-stream split with resumable UI reconstruction. The provider handles durable frames with sequence numbers separately from transient token progress, hydrates history first, resumes using after_seq, and keeps independent main/planner cursors. On reconnect, it clears transient slots and awaits durable truth. This allows low-latency display without treating partial streaming text as canonical history (provider, lines 167–216 and 1175–1269). Wingman can borrow the principle for agent timelines and reconnectable workspaces. It still needs higher-level activity summaries, and this client alone does not prove server event durability or gap-free delivery.

Profile identity is separate from execution and launch additions. A stable profile pointer plus revision metadata defines reusable behavior. The launch request adds workspace context, skill invocations and runtime hints without conflating a model preference with a live worker. This supports reproducible configuration and controlled specialization (profile service, lines 86–124; builder, lines 1141–1228). For Wingman, add a persistent agent-instance record above it: profile UUID alone cannot answer which BackendCoder owns a ticket or is on a project team.

Browser-mediated agent tools bridge execution and UI actions. The child-launch mechanism turns an emitted tool action into real conversation creation, applies replay suppression, and returns a structured launch result via a prefixed message. It enables agents to initiate independent local/Cloud work without asking the human to run a CLI. Its limitations are unusually important: the browser must be handling events, the acknowledgment precedes actual execution, the ledger is local storage, result posting is skipped in goal loops, and eventual child completion is not joined. Wingman should move mission-critical delegation and acknowledgments into a durable backend coordinator while keeping the UI as an observer/controller.

Planning is constrained by tools as well as instructions. The planner receives only search and a plan editor, its own condenser and explicit boundaries; Build hands execution back to the main conversation. This is stronger than simply telling a full-power coding persona to “act as planner.” It enables reviewable planning with limited write scope (planner builder, lines 1337–1403). It is still a task planning tool and cannot substitute for broad product research or project leadership.

A managed-host tunnel is adapted into the existing conversation backend contract. MARS maps each remote session to a normal local-kind backend and then reuses existing conversation, files and terminal services. The tunnel client, lines 127–188 and 244 onward, maps each local TCP connection to an authenticated upstream WebSocket dial with keepalive; bridge, lines 411–438, binds tunnel opening to the active credential and owns teardown. Restoration deliberately touches only the active session, avoiding accidental wakes of every registered remote host (restoration policy, lines 156–165). This enables one coding workspace to span managed hosts without duplicating the conversation UI. The transport abstraction does not merge session files, agent identities or collaboration state, and service-side hosting guarantees remain unverified.

Manifest-driven automation capability negotiation. manifest-capabilities.ts, lines 17–21 and 48–108, evaluates declared required features, supported action kinds, trigger kinds and deployment readiness. It distinguishes unknown capability support from a reported “no.” This is reusable for heterogeneous execution hosts and extension compatibility. It negotiates automation setup, not workload placement or organizational authority.

Practical use for Wingman

The most direct reuse is the detailed session surface: embed Canvas components for files/diffs, terminal/browser, usage, events, planner and controls; adapt conversation IDs to Wingman agent-instance/session records. The library export surface makes this more realistic than extracting UI from an application with no public component boundary. Reuse requires compatibility with the pinned TypeScript client/Agent Server contract and explicit decisions about whether Wingman adopts that backend or builds an adapter to its Codex host controller.

Profiles, project skills, server tags, worktree selection and event cursors are useful implementation references. A Wingman specialist should map to persistent instance → role profile → current conversation(s) → execution host, not just to a profile name. For shared product knowledge, use Wingman's durable DIRECTIVES structure and project registry as authoritative; Canvas's plan and metadata can be views or execution attachments. Stable assigned tickets should be independent of transient array-position task-list IDs.

The central work still to build is a backend organization layer:

  • Butler/Telegram transport and routing.
  • portfolio/project registry.
  • ProductMaster and TechMaster lifecycle.
  • team membership and agent directory.
  • shared tickets/dependencies.
  • rooms/direct messages.
  • structured human questions.
  • periodic ProjectMaster supervision.
  • outcome collection.
  • merge/integration policy.
  • acceptance gates and executive/current-next-blocker summaries.

Host access must be separate from collaboration authority so remote specialists participate in the same shared records. Cross-backend parentless Cloud launches are not sufficient.

The highest integration risk is mistaking frontend convenience paths for durable orchestration. Do not use a mounted browser and local-storage call ledger as the reliable dispatcher for unattended work. Use server-side idempotency keys, persistent delegation records, completion subscriptions and recovery, while allowing Canvas to inspect and steer the resulting conversations. The documented worktree-to-shared fallback also needs a Wingman policy: successful startup with reduced isolation may be unacceptable for concurrently editing specialists.

This revision is therefore worth studying or adopting as an execution workspace and integration shell. Adopting it does not eliminate most of Wingman's organizational behavior; that behavior is the differentiating layer that would sit above it.
