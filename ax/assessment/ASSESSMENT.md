**AX is a plausible remote execution substrate for Wingman workers, but is not a substitute for Wingman's organization.** It implements real sandbox provisioning, resource limits, remote command access, workspace initialization, suspension, restoration, and durable control-plane resources. Its actual domain model has only Task, Workspace, and Model. It does not implement standing agent identities, product organizations, conversational intake, discovery, tickets, collaboration rooms, human decision routing, or executive/project dashboards.

The central distinction is that an AX Task is an immutable declaration of a sandbox and its launch command. It is not a product ticket, a durable organizational agent, or an agent conversation. A coding CLI can run independently inside the sandbox; AX does not understand that CLI's plan, messages, tool calls, deliverables, or acceptance. Indeed, the runner deliberately remains alive after the command exits, and task status does not expose that exit. A ready sandbox therefore does not establish that a coding job is progressing or complete.

This conclusion follows from the complete [RPC and resource schema](../repo/pkg/apis/v1alpha1/ax.proto), lines 24–208; [server handlers](../repo/internal/server/server.go), lines 144–365; and [runner lifecycle](../repo/runner/runner.go), lines 83–201. The repository's [concepts document](../repo/docs/concepts.md) explicitly places planning, delegation, retries, and task trees above AX. The assessment credits mechanisms present in code, rather than treating that composability as a delivered agent organization.

## Architecture and execution model

The implementation is a small Go control plane with three production entry points and an optional Claude Code runner. `ax` parses manifests and calls typed gRPC operations. `ax-server` opens PostgreSQL, initializes its schema, constructs a Substrate client and TaskReconciler, and serves gRPC plus `/healthz`. It does **not** launch a periodic reconciliation worker. Handlers call the reconciler directly while holding a resource lock. `ax-task-runner` runs inside the sandbox and starts the actual workload as a child process. See [CLI apply](../repo/cmd/ax/main.go), lines 250–360; [server startup](../repo/cmd/ax-server/main.go), lines 90–141; and [runner](../repo/runner/runner.go), lines 96–166.

```text
Human or higher-level orchestrator
  -> ax apply / resume / suspend / get / ssh / delete
  -> ax-server gRPC handler
       -> PostgreSQL resource documents + per-resource lease locks
       -> TaskReconciler -> Agent Substrate Control API
                            -> ActorTemplate -> Actor -> assigned worker
                                 -> /usr/local/bin/ax-task-runner
                                      -> workspace setup + metadata/probe server
                                      -> configured agent command/process group
```

The server stores AX-owned resources as protojson in PostgreSQL JSONB tables keyed by `(atespace, name)`. There are tables for tasks, workspaces, models, and leases; no project, message, ticket, relationship, or conversation tables. The actor is the authority for its phase, worker assignment, and readiness. AX saves its own Pending/Failed/Terminating states, task ID, and workspace condition, but strips actor-owned status before writing. Reads overlay current Substrate actor state; lists batch actor reads by atespace. This avoids a permanently duplicated actor phase, at the cost of task reads depending on the remote control plane. Unavailability produces Unknown rather than an invented healthy status. Evidence: [schema](../repo/internal/store/postgres/schema.sql), lines 1–40; [status boundary](../repo/internal/server/server.go), lines 368–584.

The reconciler serializes status-free Task YAML and the bound Workspace into environment variables, computes a task-specific template name from image and environment, creates an ActorTemplate, and ensures an Actor with the task's name. Resource limits are propagated into the template. The actor's fixed container command is `/usr/local/bin/ax-task-runner`; `spec.command` is interpreted by that runner rather than used directly as the container entrypoint. The template requests a durable `/workspace` directory and VOLUMES snapshot fidelity. This is genuine delegation to a remote worker service, not a local child process masquerading as multi-host execution. Worker scheduling and sandbox isolation themselves belong to the external Substrate dependency. Evidence: [reconciler](../repo/internal/controller/reconciler.go), lines 130–248 and 437–448; [template construction](../repo/internal/substrate/client.go), lines 335–403; [worker assignment](../repo/internal/substrate/client.go), lines 523–551.

The runner provides public health/readiness endpoints and, only with `debug: true`, guest process/filesystem gRPC. Task and workspace metadata are served separately on loopback. It initializes repositories, inline files, and a skills directory, then starts the command in its own process group. Workload stdout/stderr go to the runner's stdout/stderr. The runner supplies a callback for command exit, but AX ships no callback-to-control-plane completion protocol. See [metadata server](../repo/internal/metadata/server.go), lines 64–128; [workspace setup](../repo/internal/workspace/setup.go), lines 68–108; [runner](../repo/runner/runner.go), lines 126–201.

## Agent definition and complete lifecycle

### Definition, creation, and identity

The configuration unit is a Task manifest, not an Agent object. `TaskSpec` contains image, command, environment, CPU/memory resources, one workspace binding, debug flag, and free-form runner config. A Workspace describes initial files and repositories plus tool/skill declarations. A Model resource describes provider/model/parameters/secret reference. No field associates a Task with a role, standing employee identity, team, product ticket, human conversation, parent agent, or predecessor session. Role prompts can be embedded in files or config, but AX does not infer them.

The CLI submits multi-document YAML sequentially, so a bound Workspace must be declared before its Task. The server validates the task, defaults its atespace, takes an exclusive task lock, rejects mutation of existing tasks, verifies the workspace exists in that atespace, timestamps the record, and persists Pending before provisioning. A repeated Create is allowed only when the existing task is Pending with an equal spec. This supports retrying a transient provisioning failure rather than general declarative Task updates. The server explicitly creates new actors **suspended**, calling `reconciler.Suspend`; applying a Task does not by itself activate its coding workload. Evidence: [apply](../repo/cmd/ax/main.go), lines 268–338; [CreateTask](../repo/internal/server/server.go), lines 144–217.

The durable address is `(atespace, task name)`. The Substrate actor deliberately has the same name. A status ID of the form `task-<name>-<Unix-seconds>` is assigned while ensuring resources. This is runtime identity, not independent agent identity across task replacement. Removing and recreating a name does not preserve an organizational employee's conversation or work record. See [reconciler identity](../repo/internal/controller/reconciler.go), lines 154–169.

### Execution, tools, permissions, and routing

`ResumeTask` ensures resources, asks Substrate to resume the actor, receives the worker IP, and briefly polls `/readyz?check=workspace`, directly or through the atenet router with `ate-target-actor: <atespace>/<actor>`. It records WorkspaceReady separately; Ready is then derived from running actor state plus that condition. A timeout of this workspace poll records initialization rather than failing the entire Resume. No background controller then keeps polling for that first setup to finish; callers must account for readiness that may remain false until a subsequent lifecycle operation updates it. Evidence: [Resume](../repo/internal/controller/reconciler.go), lines 266–376; [derived readiness](../repo/internal/server/server.go), lines 489–507.

Inside the sandbox, `runner.Run` serves metadata, sets up the working directory, and launches the configured command. The optional Claude adapter turns camelCase config keys into CLI flags, adds MCP JSON, and appends a required prompt after `--`. It is a headless CLI adapter, not an embedded multi-agent scheduler or persistent conversational router. A Task with an explicit command bypasses that translation. See [Claude adapter](../repo/cmd/runners/claude-code-runner/config.go), lines 64–99, 181–192.

Tool capabilities come from the image, agent runtime, environment, and declared MCP servers. The Claude adapter passes static servers and explicitly enumerated registry servers as HTTP or stdio MCP config. It does not query a registry provider/project/query. General workspace setup creates a skills directory but does not download skill registries or install skills. Generic runner metadata exposes the declarations for agents to interpret. Permission flags are runner-specific pass-through, and AX supplies no approval decision service. CPU/memory limits are validated and forwarded to Substrate; resource requests are rejected rather than silently ignored. Guest arbitrary execution/file access is gated by debug and metadata is loopback-only. These are useful boundaries, but task-level identity/egress/approval policies listed on the roadmap are not implemented here. Evidence: [MCP mapping](../repo/cmd/runners/claude-code-runner/config.go), lines 148–174; [skills setup](../repo/internal/workspace/setup.go), lines 242–250; [resource validation](../repo/pkg/apis/v1alpha1/resources.go), lines 37–55; [metadata exposure](../repo/internal/metadata/server.go), lines 74–128.

Human inspection uses task routing, not conversational routing. `ax ssh` requires a Running task with debug enabled and a worker IP. It attempts direct guest access, then router mTLS via Kubernetes port-forward, then a plaintext router fallback when TLS setup is unavailable. It streams a newly started guest process, forwards stdin and signals, and returns that process's exit status. This is a useful operational shell but not a view into the original agent's conversation or an authenticated end-user organization UI. [SSH implementation](../repo/cmd/ax/main.go), lines 1019–1167; [guest Exec](../repo/internal/guest/client.go), lines 113–184.

### Concurrency and scheduling

Multiple differently named Tasks can execute independently; tasks in separate atespaces are isolated in resource addressing. PostgreSQL lease keys include resource kind, atespace, and name, so one slow lifecycle call does not globally serialize all workers. Each held lease renews at TTL/3 using the database clock. The default design is suitable for replicas sharing PostgreSQL and avoids pinning database sessions across slow snapshot operations. However, there is no fencing token: if renewal fails beyond the lease TTL, an old holder continues working while a new holder can acquire the lease. This limitation is documented directly in the implementation and matters for conflicting remote mutations. See [lease implementation](../repo/internal/store/postgres/lock.go), lines 29–69, 70–108, 137–195.

Placement is delegated to Substrate's ResumeActor operation; AX has no host-selector field, specialist-capacity policy, queued ticket dispatcher, schedule/cron API, dependent-task DAG, or supervision wake loop. A higher-level agent could create tasks through the API, but no parent-child ownership or delegation tracking comes with that. “Reconciler” here means synchronous resource-ensuring methods, not a continuously running controller that autonomously repairs every pending task.

### Persistence and resume: meaningful implementation caveats

PostgreSQL preserves the AX resource record across server restarts. Substrate is asked for VOLUMES snapshots and a durable directory mounted only at `/workspace`. Resume starts a fresh container process tree; `runner.Run` starts the configured command again. AX does not checkpoint the language model context, process memory, terminal, or agent conversation. A coding CLI must persist its own session data in the durable directory and be launched with suitable resume options if continuity is required. Arbitrary free-form flags make that possible in principle but do not implement automatic resumption. Evidence: [snapshot and volume definition](../repo/internal/substrate/client.go), lines 364–396; [runner startup](../repo/runner/runner.go), lines 126–156; [persistence E2E test](../repo/test/e2e/e2e_test.go), lines 461–495.

Two source-level issues deserve explicit validation before relying on recovery:

1. **The initialization marker is outside the durable volume.** Setup checks/writes `/ax/initialized-<workspace-path>`, but the template requests only `/workspace` durability. Under the documented and E2E-tested cold-rootfs semantics, `/ax` is not shown as durable. This implies resumed default runners can repeat initialization, rewrite inline files and run `git checkout -f FETCH_HEAD` over restored working trees. An alternate workspace binding path outside `/workspace` likewise is not matched by a corresponding volume mount in BuildActorTemplate. These are grounded risks from the configured paths; actual loss of edited files was not reproduced in this assessment. [marker location](../repo/internal/workspace/setup.go), lines 31–35, 85–108; [forced checkout](../repo/internal/workspace/setup.go), lines 194–214; [volume mount](../repo/internal/substrate/client.go), lines 387–395. The inspected E2E persistence case checks a plain durable file and `/tmp` reset, not preservation of modified tracked Git files or the marker.
2. **Git clone failures can still produce ready status.** `SetupWorkspace` omits the marker on Git failure but returns `(res, nil)`; `runner.Run` marks WorkspaceReady whenever that error is nil, then proceeds to start the command. Inline-file and skills-directory errors are also logged rather than propagated. Readiness therefore does not reliably assert that every declared source/directive was materialized. [Git failure return](../repo/internal/workspace/setup.go), lines 94–108; [runner readiness](../repo/runner/runner.go), lines 126–150; [file writes](../repo/internal/workspace/setup.go), lines 299–320.

Workspace resources are mutable. Launch serializes their contents into the environment and reuses existing actors by name. A stored Workspace change does not establish a live update of running or restored files. Retained initialization markers can also suppress updates. Wingman needs versioned context and an explicit file-update protocol. See [workspace fetch](../repo/internal/server/server.go), lines 587–598; [template environment and actor ensure](../repo/internal/controller/reconciler.go), lines 179–239; and [existing actor handling](../repo/internal/substrate/client.go), lines 460–519.

### Interruption, failure, recovery, completion, and retirement

Suspend operates through Substrate and requests checkpointing. Runner cancellation/SIGTERM forwards SIGTERM to the command's process group, waits ten seconds, then SIGKILLs it. A later resume reexecutes the command. SSH Ctrl-C is separately forwarded to the SSH-launched process; double interrupt exits the local SSH client. No native pause/steer/queue controls reach the coding CLI's internal conversation. [runner shutdown](../repo/runner/runner.go), lines 50–52, 158–185; [SSH interrupts](../repo/cmd/ax/main.go), lines 1085–1102.

Substrate calls use bounded exponential retry with jitter, typically ten attempts for selected gRPC codes. Resume and suspend retry Aborted and Unavailable. The server records transient provisioning/resume errors as Pending with Unavailable. It records permanent failures as Failed. Further explicit requests drive recovery. There is no durable retry queue or timer-based backoff scheduler.

For a crashed actor, `EnsureActor` first attempts reversion to the last snapshot. If reversion fails, it deletes and recreates the actor. That path cannot guarantee preservation of all work. See [retry classification](../repo/internal/substrate/client.go), lines 218–289; [crash recovery](../repo/internal/substrate/client.go), lines 460–495; and [failure record](../repo/internal/server/server.go), lines 353–365. Reading a missing actor returns Failed. The read path does not reconstruct it. See [status overlay](../repo/internal/server/server.go), lines 469–481.

Workload completion is intentionally separate from sandbox lifetime. On command exit the runner logs success/failure and calls an optional local hook, then keeps serving until cancellation. A command failure can leave the actor Running and Ready. There is no Succeeded/product-accepted phase, test result schema, acceptance decision, artifact index, automatic stop-on-delivery, or retry of failed agent commands. Wingman must add a reliable completion/result protocol and distinguish sandbox health from agent progress and product acceptance. [runner completion](../repo/runner/runner.go), lines 158–201; [TaskStatus](../repo/pkg/apis/v1alpha1/ax.proto), lines 111–126.

Delete sets Terminating, blocks for actor removal, attempts removal of task-specific templates, then removes the store record. Actor deletion failure retains the record for retry. Template cleanup errors are logged and do not prevent successful Task deletion; template listing warns when truncated rather than following pages. There is no archive, retention policy, task history, artifact export, identity retirement, or scheduled cleanup. These must precede delete if Wingman needs audit and continuation. Evidence: [delete handler and helper](../repo/internal/server/server.go), lines 220–257, 426–444; [template cleanup](../repo/internal/controller/reconciler.go), lines 457–508; [template listing](../repo/internal/substrate/client.go), lines 671–685.

## Coordination mechanics and concrete request trace

AX's shared coordination is infrastructure state and per-resource serialization. There is no agent chat, shared ticket/dependency state, event subscription/watch API, or human approval exchange. Conditions are overwritten current state with timestamps, not a retained event stream. PostgreSQL locks coordinate handlers across server replicas. They do not coordinate developer assignments, code integration, or specialist conversations. Workspaces are reusable initialization definitions, not a shared live filesystem between independently created task sandboxes.

A concrete repository-provided path is the Claude Code task that clones a library, runs tests, fixes failures or improves its README, and writes `/workspace/claude-output.md`. This is a trace of supplied source, not a run performed here:

1. The [example manifest](../repo/examples/claude-code/task.yaml), lines 41–102, declares a Workspace with Git and CLAUDE.md plus a Task bound to it. It is a template: image digest and credentials require operator substitution. Its single prompt is the entire job definition. It contains no tickets or management roles.
2. `ax apply` decodes each YAML document in order. Workspace goes through UpdateWorkspace; Task goes through CreateTask. Failures stop later documents and there is no multi-resource transaction. [CLI](../repo/cmd/ax/main.go), lines 268–360.
3. CreateTask validates, locks, requires the workspace, stores Pending, ensures the task-specific template/actor, and leaves the actor suspended. [server](../repo/internal/server/server.go), lines 144–217. A separate `ax resume task claude-code` is required to execute the job. The example's inspection comments alone should not be mistaken for activation.
4. ResumeTask locks the named task, fetches its workspace and calls reconciler.Resume. That ensures resources and invokes ResumeActor, which returns a worker assignment. Readiness polling records workspace setup separately. [server](../repo/internal/server/server.go), lines 309–350; [reconciler](../repo/internal/controller/reconciler.go), lines 270–376.
5. The container's specialized runner reads its launch specs and replaces an empty Task command with `claude --print` plus config flags and MCP configuration. The common runner materializes workspace sources and runs that command. [Claude main](../repo/cmd/runners/claude-code-runner/main.go), lines 43–81; [config](../repo/cmd/runners/claude-code-runner/config.go), lines 181–192; [common runner](../repo/runner/runner.go), lines 126–156.
6. Test execution, modifications and Markdown report generation are Claude's interpretation of the prompt. AX neither parses that report nor determines whether the tests meet product acceptance. Once Claude exits, the sandbox remains available. A human or higher layer can use `ax ssh ... -- cat /workspace/claude-output.md` or inspect Git changes and then suspend/delete it. [example expectations](../repo/examples/claude-code/task.yaml), lines 76–88; [exit handling](../repo/runner/runner.go), lines 158–201.

This path provides independent unattended execution and inspectable files. It does not send peer-agent messages or assign work through technical leadership. It does not release task dependencies on completion. It also does not return human decisions to an originating ProductMaster. Those collaboration contracts belong above AX.

## Substantial capabilities beyond Wingman's description

**Declarative sandbox infrastructure and resource sizing.** AX separates an immutable execution request from a reusable initialization specification and central model configuration. A caller can request different digest-pinned images and CPU/memory limits per Task and get a standard lifecycle. This is useful beneath a standing organization because workers can use heterogeneous toolchains in isolated remote sandboxes. It requires Wingman to own image production, registry access, runner compatibility, credentials and Substrate operations. The default image is not a complete Codex toolchain. Evidence: [TaskSpec](../repo/pkg/apis/v1alpha1/ax.proto), lines 69–88; [limits/template](../repo/internal/substrate/client.go), lines 301–403; [runner contract](../repo/docs/runner.md).

**Checkpoint-based capacity reclamation and explicit recovery.** VOLUMES snapshots allow workspace data to outlive a worker assignment; crash recovery attempts revert before replacement. This could reduce idle resource use and preserve worker files independently of a dashboard session. It is substantially more concrete than merely backgrounding a local process, but it preserves filesystem state rather than a continuing model turn, and the marker/path issues need correction. Automatic idle suspension and branching are roadmap items, not shipped behavior. Evidence: [snapshot template](../repo/internal/substrate/client.go), lines 364–396; [revert recovery](../repo/internal/substrate/client.go), lines 465–494; [roadmap](../repo/docs/roadmap.md), actor architecture section.

**Remote operational guest API.** Process and filesystem gRPC, signal forwarding, output streaming, actor-target routing and Kubernetes tunnels provide a concrete operational path into sandboxes that are not directly reachable from the developer machine. Wingman could build workspace inspection and debugging tools on it, but would still need agent transcript/tool-event collection and UI linking. Evidence: [guest client](../repo/internal/guest/client.go), lines 35–87, 113–184; [routing](../repo/cmd/ax/main.go), lines 1114–1167.

**PostgreSQL rather than Kubernetes CRDs for the task record.** AX retains Kubernetes-shaped declarative resources without storing each task in etcd. Resource documents and pool-compatible renewed leases support a potentially large population of short-lived executions with narrow locks. This is an architectural choice, not an assessed throughput guarantee: no scale benchmark was run, migrations are only CREATE TABLE IF NOT EXISTS, and lock fencing remains a known limit. Evidence: [design rationale](../repo/DESIGN.md); [schema](../repo/internal/store/postgres/schema.sql), lines 1–40; [leases](../repo/internal/store/postgres/lock.go), lines 29–69.

**Runner and model extension seams, with uneven completeness.** The public Go runner package can be embedded by custom images and exposes an OnCommandExit hook. The supplied Claude adapter converts generic config to actual CLI flags and concrete MCP connections, avoiding coupling the control plane to that agent. Model CRUD and a model client also exist, but they are not the same as integrated model routing for task execution. Source search found no production caller importing `internal/model`; TaskSpec contains no Model reference and reconciler environment construction does not inject Model credentials. Example comments claiming GEMINI key injection therefore should not override the code. The standalone client implements Google generation, returns a synthetic fallback when disabled or missing a key, and errors on other remote providers. It is not a general multi-provider agent backend. Evidence: [runner hook](../repo/runner/runner.go), lines 55–80, 188–201; [model client](../repo/internal/model/client.go), lines 458–509, 608–621; [environment construction](../repo/internal/controller/reconciler.go), lines 179–202. Wingman should use explicit runtime credential/model adapters rather than assume applying Model config changes its coding agents.

## Grounded distinctive mechanisms and innovation assessment

The most useful mechanism is the deliberate separation of **AX-owned declarative intent from actor-owned observed state**. `storedStatus` removes actor data on writes; get/list synthesize current status from Substrate, including Unknown on failures. This lets AX remain a thin execution facade without maintaining a second health loop and stale actor cache. It also exposes the boundary clearly: a healthy actor is not a healthy agent task, and semantic progress needs a separate reporting channel. This is a distinctive design within the repository, not a claim of historical novelty. [status helpers](../repo/internal/server/server.go), lines 368–584.

The **content-derived per-task actor template** makes image, launch environment, serialized workspace and resource configuration part of a stable hash, while excluding status so health changes do not create new snapshots/templates. That supports independent custom runners and reproducible launch inputs. Existing actors are reused and the name includes the task, so this is not cross-task deduplication or automatic live reconfiguration. [template preparation](../repo/internal/controller/reconciler.go), lines 189–239; [hash](../repo/internal/controller/reconciler.go), lines 437–448.

The **runner contract** is a practical plug-in boundary: fixed entrypoint, status-free launch YAML, probe endpoints, loopback metadata, optional debug guest services, command process-group supervision, and exit hook. This allows different real coding engines to coexist without teaching the control plane their flags. The Claude implementation demonstrates that path with actual CLI argument and MCP conversion. Its limits are equally important: no common transcript, resume protocol, progress event schema or acceptance result exists across runners. [runner](../repo/runner/runner.go), lines 83–201; [Claude adapter](../repo/cmd/runners/claude-code-runner/config.go), lines 64–99, 148–192.

Finally, **renewed database-clock leases** avoid session-bound advisory locks while a slow remote lifecycle operation executes. They permit replicas without requiring tightly synchronized application clocks or holding one PostgreSQL connection throughout a snapshot. The implementation explicitly admits unfenced lease loss. This should inform integration design rather than be hidden behind claims of strict distributed correctness. [lock implementation](../repo/internal/store/postgres/lock.go), lines 29–69, 112–195.

## Practical Wingman fit

Wingman could directly reuse the Task lifecycle API, durable remote working directories, runtime image/config seam, per-task resource limits, actor-target guest access, and centralized resource inventory **as infrastructure**, after validating the persistence/readiness issues. A worker adapter could submit an AX Task for a concrete ticket and inspect/suspend/delete its sandbox. The organization would remain the owner of ticket identity, agent identity, product state and human interaction.

Adaptation is substantial. A Codex runner needs a durable session location under the mounted volume, explicit resume behavior, a secure credential path, structured tool/activity/progress reporting, and an exit/result upload protocol. Wingman must map its agent and ticket IDs to AX addresses externally, preserve source/artifact revisions, and handle concurrent branches/integration. It should version workspace inputs and correct the initialization marker/custom-path and Git-error readiness behavior before trusting suspend/resume with uncommitted code. It also needs infrastructure authentication/authorization appropriate to its control-plane exposure. The AX server constructed here has no application auth interceptors and its HTTP listener enables unencrypted HTTP/2. Substrate TLS configuration and router mTLS do not themselves authorize individual Wingman users or roles at AX's API. [server construction](../repo/internal/server/server.go), lines 57–78; [listener](../repo/cmd/ax-server/main.go), lines 118–124.

Wingman needs an organization layer above AX:

- Telegram Butler and project intake registry.
- Role/profile directory and durable agent conversations.
- Discovery, clarification, and product/technical leadership.
- Tickets, dependencies, shared rooms, and escalation.
- Active supervision, product verification, and acceptance.
- Executive summaries, timelines, portfolio views, and detailed agent workspaces.

Prompts alone do not implement these records and workflows. Atespaces provide namespace boundaries. They do not replace the product model or host-placement policy.

For the specified MacBook/Endeavour arrangement, AX is a change of execution architecture: it expects a reachable Agent Substrate control plane and worker environment, plus PostgreSQL and registry-hosted images. This is not a drop-in launcher for an existing Codex desktop session on either host. The checked `go.mod` pins `go.ate.dev/substrate v1.0.0-rc.1` and Go 1.27.1; actual infrastructure provisioning requirements should be reviewed separately from product fit. No cluster availability, machine compatibility or deployment readiness was verified here.
