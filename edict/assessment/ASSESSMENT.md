# Edict assessment against Wingman

Repository: https://github.com/cft0808/edict  
Local checkout: `researchs/edict/repo`  
Revision inspected: `14a207557719c046af0f993a7bff1cc5a5015b33`  
Assessment date: 2026-11-05  
Baseline: [WINGMAN_PURPOSE.md](../../WINGMAN_PURPOSE.md)

Edict is a strong reference for **a standing hierarchy that coordinates through tasks, review gates and observable handoffs**. Its Taizi intake agent, Zhongshu planner, Menxia reviewer, Shangshu dispatcher and departmental executors correspond to several Wingman responsibilities. These are registered OpenClaw agents with separate workspaces, not simply labels on one coding conversation. The implemented product, however, is a general-purpose task organization with a mostly fixed roster. It does not establish a persistent software-product portfolio with a ProductMaster and TechMaster team per project, arbitrary specialist instances, distributed execution placement, or Wingman's connected per-agent development workspace.

Its most useful ideas are explicit plan rejection before execution, recovery that escalates through the organization, and progress records that make intended next work visible beside activity. Its most important assessment trap is that the repository contains **two independent execution stacks and a separate discussion simulator**. Combining their advertised capabilities into one mature product would overstate what this revision proves.

## Execution architecture and product boundaries

### Default stack: files, Python dashboard, OpenClaw

[start.sh](../repo/start.sh), lines 34–95, initializes dashboard data, launches `scripts/run_loop.sh` when the OpenClaw CLI is available, and starts `dashboard/server.py`. The shell loop synchronizes external OpenClaw sessions/configuration, applies model changes, calculates official statistics and refreshes presentation data. It also calls the scheduler periodically ([run_loop.sh](../repo/scripts/run_loop.sh), lines 44–89).

The authoritative task record is `data/tasks_source.json`. Agents operate it through [kanban_update.py](../repo/scripts/kanban_update.py), using create/state/flow/progress/todo/done/block commands. Atomic JSON updates and file locks provide coordination among local processes. The dashboard reads and mutates the same task source and dispatches `openclaw agent --agent <id> -m <context>` in background threads. Its dispatch path records queued/success/failure/timeout status rather than assuming that an HTTP request means the agent worked ([server.py](../repo/dashboard/server.py), lines 2114–2290).

The React components under `edict/frontend/src` are primarily the default dashboard client: [api.ts](../repo/edict/frontend/src/api.ts), lines 1–41, explicitly targets `dashboard/server.py`. The default Python server serves `dashboard/dist` (server lines 54–57 and 2411–2412). The root [Dockerfile](../repo/Dockerfile), lines 6–27, builds and copies that client into place. Frontend source location alone does not make it proof of alternate-backend integration.

OpenClaw owns the actual model interaction, tools, session behavior and agent execution. Edict contributes role instructions, allowed delegation relationships, shared task state and supervision. It is not a standalone Codex harness. A process invocation, a persistent registered agent, an OpenClaw session and a task are different objects: one registered department can handle many tasks and sessions. A dashboard task is not itself an independently provisioned employee.

### Alternate stack: Postgres, Redis Streams, separate workers

The nested `edict/` tree contains a FastAPI API, SQLAlchemy models, Redis Streams event bus, React frontend, orchestrator, dispatcher and outbox relay. [TaskService](../repo/edict/backend/app/services/task_service.py), lines 39–195, writes task creation/state transitions and outbox records in one database transaction; transitions use a row lock. [OutboxRelay](../repo/edict/backend/app/workers/outbox_relay.py), lines 54–114, publishes pending records to Redis. The [orchestrator](../repo/edict/backend/app/workers/orchestrator_worker.py) consumes creation/status/stall events and publishes dispatch requests. The [dispatcher](../repo/edict/backend/app/workers/dispatch_worker.py) constructs context and invokes the same external OpenClaw CLI.

This is a substantive alternative implementation, not just architecture prose. But it should be treated as an incompletely integrated path at this snapshot:

- The JSON CLI explicitly says that the two modes do not synchronize automatically ([kanban_update.py](../repo/scripts/kanban_update.py), lines 3–10). A deployed database backend does not automatically make the installed SOUL prompts' JSON commands database writes.
- The supplied [nested Compose file](../repo/edict/docker-compose.yml) launches backend, orchestrator and dispatcher, but **no outbox relay service**. The API's committed outbox events therefore need a separately started relay before normal worker progression occurs. `main.py` starts a bus connection, not that worker.
- Retry comments say unacknowledged events are automatically redelivered, but both workers invoke stale claiming at startup; their normal polling paths consume new events. A continuously running stale-event reclamation loop is not established by those call sites. Leaving a message unacknowledged is not by itself proof of prompt retry.
- The supplied frontend calls `/api/live-status`, `/api/agent-config` and `/api/officials-stats` ([api.ts](../repo/edict/frontend/src/api.ts), lines 27–35). FastAPI instead mounts the task router at `/api/tasks`, where its live-status route becomes `/api/tasks/live-status` ([main.py](../repo/edict/backend/app/main.py), lines 66–72; [tasks.py](../repo/edict/backend/app/api/tasks.py), lines 105–109). No equivalent top-level dashboard compatibility router is mounted. Compose pointing `VITE_API_URL` to port 8000 therefore does not establish a working replacement dashboard.
- The rich task context and skill-selection helpers consume fields from the dispatch event, but ordinary orchestrator events supply only task ID, agent, state and message. They do not carry description/todos/tags, and `_dispatch` does not fetch the database task ([orchestrator_worker.py](../repo/edict/backend/app/workers/orchestrator_worker.py), lines 166–225; [dispatch_worker.py](../repo/edict/backend/app/workers/dispatch_worker.py), lines 382–429). These helpers are implemented but normal wiring supplies only partial context. `_on_task_status` also resolves departments specially for `Assigned`, with no corresponding `Doing`/`Next` mapping in `STATE_AGENT_MAP`; do not assume every state automatically dispatches an executor.
- The orchestrator stall scan emits `stall_count=0` and `escalation_level=0` each time. `_on_task_stalled` selects escalation from those payload fields, but the inspected handlers do not persist increments back into the task or subscribe to `task.escalated` for database mutation. The complete bounded escalation lifecycle is stronger in the default JSON scheduler than in this rewrite.

These observations concern functional wiring, not stylistic quality. They materially affect using the alternate stack as Wingman's coordination foundation.

### Discussion is a third execution model

The dashboard's court discussion generates personas rather than connecting registered agents to a room. [court_discuss.py](../repo/dashboard/court_discuss.py), lines 112–203 and 498–592, stores sessions in a module-level dictionary. One LLM call returns a JSON array of several officials' messages. If unavailable, rule-based simulation supplies the discussion. The interface can support deliberation. It does not demonstrate each official using a separate coding session or tools. Restart loses the session store.

## Agent definition, provisioning and lifecycle

### Definition and identity

The shipped organization has eleven OpenClaw identities: Taizi, Zhongshu, Menxia, Shangshu, six departments, and Zaochao. `agents/<id>/SOUL.md` defines behavior. Separate model and skill configuration adjusts capabilities.

- Taizi handles intake and human representation.
- Zhongshu plans. Menxia checks plans. Shangshu allocates work.
- Bingbu's SOUL defines engineering.
- Gongbu's SOUL defines infrastructure, operations, and security.
- Xingbu defines quality and audit.
- The remaining departments cover documentation, data/resource analysis, and organization support.

Shangshu's routing table and court profiles reverse the engineering and infrastructure labels for Bingbu and Gongbu. Role metadata therefore disagrees across the product. See [Bingbu SOUL](../repo/agents/bingbu/SOUL.md), lines 3–12; [Gongbu SOUL](../repo/agents/gongbu/SOUL.md), lines 3–12; and [Shangshu SOUL](../repo/agents/shangshu/SOUL.md), lines 15–24. The roster covers more than software development. It does not provide Wingman's separate backend, frontend, and mobile specialist structure.

Installation creates distinct workspaces and copies substituted SOUL files, then registers stable agent IDs in OpenClaw configuration ([install.sh](../repo/install.sh), lines 91–184). It links each workspace's shared `data` and `scripts` back to the repository (lines 239–290). This is a practical way to avoid isolated agents accidentally updating separate trackers. It also means the installed structure assumes shared local storage rather than explicit distributed-state access.

Allowed subagent relationships establish an organizational graph: Taizi→Zhongshu; Zhongshu→Menxia/Shangshu; Menxia→Zhongshu/Shangshu; Shangshu→departments; departments→Shangshu. These are OpenClaw delegation allowances and operational conventions, not separate OS security identities. Installer-generated instructions say interdepartmental cooperation should be routed through Shangshu. That differs from Wingman's direct backend/frontend/test conversations in a project room.

### Creation and execution

Edict provisions the roster at installation time. Starting a task selects an already registered agent. It does not clone a profile into a new durable per-project employee. Dashboard submission creates a task with a stable task ID, initializes scheduler metadata and dispatches Taizi. CLI task updates are short local processes that mutate shared records. The actual coding run is an OpenClaw agent invocation, potentially involving subagent tool calls requested by the SOUL instructions.

The default dispatcher supplies state-specific instructions and task context. A daemon thread calls the CLI with a 300-second agent timeout and 310-second subprocess timeout, records outcomes, and makes at most two subprocess attempts for nonzero exits (one retry). Gateway reachability has a separate three-check loop. A configured delivery channel adds `--deliver --channel`; without it the dashboard does not force a Feishu dependency ([server.py](../repo/dashboard/server.py), lines 2114–2290). A successful process exit means the invocation returned. It is not independent proof of task acceptance or working software.

In the rewrite, an async worker consumes dispatch events, uses helpers to enrich messages with available task details, shared rules, ranked agent memories, upstream decisions, matching skills and state reminders. The ordinary orchestrator payload is sparse, so complete details and task-tag matching require additional wiring, as described above. It exports task/trace identifiers and writes a temporary structured context file, invokes OpenClaw through a thread-pool subprocess, truncates captured outputs, and removes the temporary file ([dispatch_worker.py](../repo/edict/backend/app/workers/dispatch_worker.py), lines 98–250, 277–305 and 542–630). `_build_soul_context` exists at lines 76–95, but the inspected `_dispatch` assembly does not call it; do not assume that helper alone proves three-level SOUL injection. Registered OpenClaw workspace instructions remain the actual role-loading foundation.

### Permissions and tools

OpenClaw supplies coding tools and their runtime policy; Edict is not implementing a separate command/file/browser tool engine. Its tracker CLI has an additional `AGENT_POLICY` mapping with different commands for coordination and execution roles, infers identity from environment/workspace/task context, and writes denial/audit records ([kanban_update.py](../repo/scripts/kanban_update.py), lines 133–187 and 243–268). This is useful organizational guardrail logic but not strong authorization: unidentified and unknown agents are allowed, the identity is inferred rather than authenticated, and every workspace has shared file access.

High-risk task transitions can enter `PendingConfirm`; confirmations and review actions record outcomes. That is a task governance mechanism, distinct from a sandbox or per-command approval system. The CLI records `confirm_by` but `cmd_confirm` checks only that the task is pending and the requested action. It does not compare the caller with that recorded authority (CLI lines 383–391 and 506–545). The command-level role policy is the remaining check. The rewrite's regex injection detector reports suspicious agent output while returning the original text unchanged (dispatcher lines 253–274). It should be credited as alerting, not proven prevention.

### Scheduling, concurrency and routing

The default dashboard dispatches concurrent threads; OpenClaw determines how calls sharing a registered agent/session are scheduled. Edict does not implement an elastic profile-instance pool. The rewrite has separate semaphores for fast management agents (four) and slower executors (three), avoiding all management work waiting behind long execution calls. It deduplicates in-flight work by task ID within one worker process (dispatcher lines 309–399). This is neither a distributed lock nor per-agent serialization. It also means a second dispatch for the same task can be ACKed as a duplicate while an earlier phase is still running.

The task state machine routes through intake/planning/review/assignment/execution/final review, with allowed recovery/cancellation edges ([task.py](../repo/edict/backend/app/models/task.py), lines 15–83). In the JSON CLI, `delegate` creates a child task with parent reference, requested return format and depth/path checks; cyclic delegation and depth beyond three are rejected. It does **not** itself invoke the target agent (CLI lines 828–891). Execution still requires an actual OpenClaw delegation or dispatcher integration. `timeout_minutes` and `review_required` fields are stored metadata here, not proof that every child gets an enforced timeout/review.

### Persistence, resume and recovery

Persistent objects include registered identity/workspace, OpenClaw session files, task JSON, audit history, per-agent memory and per-task decision chains. The dashboard reads external `sessions.json`/JSONL and generates session-facing records. These make background work inspectable after a viewer disconnect, but the dispatch command selects an agent ID without explicitly selecting a task-specific resume session. Wingman would need reliable product/task/conversation identifiers rather than rely on matching text in the latest sessions.

The default scheduler implements a recovery ladder: retry, escalation first to Menxia and then Shangshu, tracker-state rollback, and eventual Blocked status after repeated rollbacks. Wake messages ask those offices to intervene. Its mutation phase holds the shared JSON lock and releases it before external dispatch/wake calls ([server.py](../repo/dashboard/server.py), lines 1254–1382). Startup recovery redispatches records still marked queued (lines 1393–1412). It does not restore a checkpointed coding process.

Several details weaken unattended reliability. The server scans every 120 seconds and the separately launched shell loop also requests scans every 120 seconds. Both pass a 180-second threshold, but `_ensure_scheduler` initializes each task with `stallThresholdSec=600`, which the scanner prefers (server lines 1042–1054, 1283–1288 and 2924–2937; [run_loop.sh](../repo/scripts/run_loop.sh), lines 73–87). The ordinary effective threshold is therefore ten minutes. CLI progress/state changes update `updatedAt` without refreshing an existing scheduler `lastProgressAt`. The scanner prefers that older timestamp. Active work can consequently enter the recovery ladder despite regular agent reports ([kanban_update.py](../repo/scripts/kanban_update.py), lines 366–413 and 607–640). The ladder also does not wait for a dispatch to finish before a later scan escalates again. This warrants correcting progress freshness and duplicate scan ownership before adopting the supervisor.

Rollback restores task state, organization, and summary. It does not reverse filesystem, Git, or database effects from code execution. Automatic rollback does nothing when the saved snapshot matches the current task state (server lines 1322–1350). The policy therefore does not guarantee eventual recovery or blocking for every stalled task.

The rewrite has useful transport pieces but weaker end-to-end guarantees in the inspected wiring. Stale event claiming occurs at startup; retryable failures return without ACK, and the workers' normal loops do not demonstrate periodic pending reclamation. Process-local `_inflight` cannot prevent duplicate execution after worker restart or across workers. At-least-once transport therefore needs idempotent task effects. The outbox relay publishes before marking/committing publication, creating a normal duplicate-publication crash window; its call does not forward the original `OutboxEvent.event_id` as an explicit stable publish identifier. [EventBus.publish](../repo/edict/backend/app/services/event_bus.py), lines 73–98, creates a new UUID for every publication, while its consumer reads only new entries (`>`), lines 118–147. These are reasons to verify recovery with real fault injection before adopting the rewrite as reliable autonomous infrastructure.

### Interruption, completion and retirement

Dashboard stop sets Blocked, cancel sets Cancelled, and resume restores the previous task state and redispatches it ([server.py](../repo/dashboard/server.py), lines 200–246). Those functions do not keep a process handle or issue a stop instruction to OpenClaw. They are workflow controls, not demonstrated interruption of active tool use. Rewrite shutdown waits for active dispatch calls. The 300-second subprocess timeout bounds the wrapper invocation but does not establish cancellation propagation to any detached gateway work.

The JSON `done` handler accepts only execution states and checks existing todos. It moves completed work to Review with output evidence. Dashboard Review approval also rejects unfinished todos. Free-form criteria and a quality role support verification. They do not establish that the artifact passes a product test suite.

Other paths bypass these gates. The canonical map permits `Doing → Done`. Generic CLI `state` applies that transition without the `done` handler's todo check. See [task.py](../repo/edict/backend/app/models/task.py), lines 34–43, and [kanban_update.py](../repo/scripts/kanban_update.py), lines 366–403. `delegate-result` marks a child Done despite its stored `review_required` flag (CLI lines 875–877 and 894–915).

Menxia's SOUL forces approval on the third plan-review round. See [menxia/SOUL.md](../repo/agents/menxia/SOUL.md), lines 90–94. This bounds the loop but can admit an unresolved plan. Wingman's final product acceptance needs a different rule.

Task archive marks a record hidden/archived. It does not retire a registered agent. [uninstall.sh](../repo/uninstall.sh), lines 57–135, removes the fixed agent registrations/workspaces and optionally data at installation scope. There is no per-project team retirement, employee reassignment/archive lifecycle, or conversation fork/compact UI in the inspected routes and frontend controls.

## A concrete coordination trace

Consider a human submitting an engineering task through the dashboard. This is a source-level trace, not a task executed during this assessment.

1. `handle_create_task` sanitizes the title, allocates `JJC-YYYYMMDD-NNN`, stores an initial Taizi record with empty output/acceptance fields, scheduler snapshot and flow entry, then calls `dispatch_for_state` ([server.py](../repo/dashboard/server.py), lines 665–729).
2. Dispatch maps Taizi to its registered OpenClaw identity, records a queued attempt, starts a CLI invocation and records its outcome. Taizi's SOUL asks it to distinguish casual queries from work, extract goals/requirements and transfer the task to Zhongshu. This behavioral classification is agent instruction, while dashboard task creation itself is deterministic.
3. Zhongshu drafts a short execution plan, updates the shared tracker, and calls Menxia as a subagent. Menxia returns an approval or rejection, and Zhongshu revises when necessary. The prescribed chain asks OpenClaw to perform subagent calls. A flow-log entry alone does not send a message, and this assessment did not observe those calls executing ([Zhongshu SOUL](../repo/agents/zhongshu/SOUL.md), lines 24–60).
4. Shangshu receives the approved plan, selects departments and collects results. The specialists use progress/todo commands. Each progress entry records timestamp, agent, summary, task state, organization and planned/completed work. Cooperation is primarily mediated delegation plus shared state, not free-form rooms.
5. An executor's `done` submits output for review. Human dashboard approval can close completed work, or rejection returns it to planning. The record connects phases and agent contributions, while coding details are supplemented from OpenClaw JSONL.
6. If updates stop, the scheduler retries/wakes management and can roll back tracker state or block for human intervention. Taizi is instructed to return the final result in the originating Feishu conversation.

The split between instructions and enforcement matters. Taizi's installed prompt always shows `create`, even though dashboard dispatch says the task already exists; CLI `create` can replace a nonterminal task and its accumulated metadata (Taizi SOUL lines 40–68; CLI lines 302–319). The SOUL workflow sometimes carries older command assumptions: Zhongshu and Shangshu both prescribe `done`, although their inferred coordination identities are denied that command. The specialists prescribe `state`, which their execution-role policies also deny ([Zhongshu](../repo/agents/zhongshu/SOUL.md), lines 62–66; [Shangshu](../repo/agents/shangshu/SOUL.md), lines 35–39; [Bingbu](../repo/agents/bingbu/SOUL.md), lines 29–45; CLI lines 161–187). If identity inference fails these policies permit the call instead. These inconsistencies prevent treating prompt workflow as an enforced, tested end-to-end protocol. Wingman should adopt a single authoritative workflow API rather than rely on prompts and handlers remaining semantically aligned. Also, automatic dispatch on dashboard transitions and prompt-directed subagent calls are two triggers for the same organizational handoff; their coexistence needs integration testing to exclude duplicate work.

## Major capabilities beyond Wingman's described scope

**Pre-execution plan review as an independent product mechanism.** [Menxia's review contract](../repo/agents/menxia/SOUL.md), lines 3–20 and 57–94, is the source-backed mechanism. Wingman's ProductMaster/TechMaster collaboration and acceptance are complemented here by a distinct plan-review office with explicit rejection and revision before dispatch. Menxia checks feasibility, completeness, risks and resources. This is valuable for costly work because it can reject a bad decomposition before specialists spend tokens. Integration requires defining whether the reviewer advises, blocks execution, or escalates to the human. The forced third-round approval should not transfer unchanged.

**General organizational operations beyond software delivery.** The actual Gongbu SOUL covers infrastructure, operations and security (despite routing metadata assigning that department engineering); Hubu handles resource/data/cost analysis; Libu supports documentation/communications; Libu HR covers capability/prompt/organizational maintenance. The [Gongbu](../repo/agents/gongbu/SOUL.md), [Hubu](../repo/agents/hubu/SOUL.md), [Libu](../repo/agents/libu/SOUL.md) and [Libu HR](../repo/agents/libu_hr/SOUL.md) profiles, each at lines 3–12, are reusable prompt-defined departments, not proven autonomous services for every listed discipline. They nevertheless expand the product into an organization that can carry out operational, analysis and communication tasks. Wingman could add such profiles without overloading TestMaster, whose defined scope excludes security/DevOps.

**Agent capability administration.** The dashboard can change models and manage local/remote skills, while refresh scripts reconcile these with OpenClaw. [server.py](../repo/dashboard/server.py), lines 288–584, implements add/update/remove remote skill flows; [skill_manager.py](../repo/scripts/skill_manager.py) provides related tooling. This is a meaningful operator capability distribution surface. Adopting it requires preserving Wingman's profile/version/permission ownership and reviewing downloaded executable instruction content. A new skill is not the same as a new employee.

**News intelligence and configurable subscriptions.** This is a separate substantial product: the RSS collector merges built-in and user feeds, filters categories, deduplicates source URLs, boosts configured keywords and writes dated/latest briefing JSON ([fetch_morning_news.py](../repo/scripts/fetch_morning_news.py), lines 112–141 and 143–234). [MorningPanel](../repo/edict/frontend/src/components/MorningPanel.tsx), lines 16–91 and 151–195, provides viewing, collection and subscription controls. The server starts collection in a background thread (server lines 2658–2670). It could become an organization research digest, but this pipeline is RSS aggregation rather than evidence of ProductMaster doing project-specific discovery. The [Zaochao SOUL](../repo/agents/zaochao/SOUL.md), lines 3–44, separately asks an agent to search and summarize news; that instruction is not the code executed by the dashboard refresh button. The collector's header claims daily 06:00 execution, but the inspected installer/run loop supplies no such scheduled invocation; daily automation needs an external scheduler or additional wiring.

**Multi-channel outbound notification infrastructure.** [NotificationChannel](../repo/edict/backend/app/channels/base.py), lines 7–26, and [channel registry](../repo/edict/backend/app/channels/__init__.py), lines 5–23, implement Telegram, Feishu, Slack, Discord, QQ, WeCom and generic webhook adapters. Their demonstrated consumer is the morning-news notification, which formats category counts and a dashboard link ([server.py](../repo/dashboard/server.py), lines 614–648). They are reusable send mechanisms, but no task-wide failure/approval subscription routing is established. Wingman could adapt these for organizational alerts; inbound message authentication, conversation continuity and correlated question/answer routing would remain to build.

**Deliberation interface separate from execution.** [Court discussion](../repo/dashboard/court_discuss.py), lines 115–203 and 498–592, provides selectable perspectives, human interventions and summaries. Its value is a structured brainstorming room. Because it generates personas in one request and can silently fall back to simulated responses, it must be presented as an advisory deliberation mode if used alongside real execution agents. It cannot serve as evidence that those agents discussed or agreed to a decision.

## Distinctive mechanisms and innovation

The interesting mechanism is the mapping of a familiar governance structure onto concrete agent boundaries. Planning, challenge/review, dispatch and execution are separated, and the tracker makes the transitions visible. This is more operationally specific than a collection of role prompts: [installer relationships](../repo/install.sh), lines 138–150, [state maps](../repo/edict/backend/app/models/task.py), lines 34–83, [review actions](../repo/dashboard/server.py), lines 739–792, and scheduler wake messages (server lines 1368–1377) reinforce the organization. It gives Wingman a useful vocabulary for checks and balances, without requiring the historical metaphor in its own UI.

The [progress protocol](../repo/scripts/kanban_update.py), lines 556–640, is another practical mechanism. Agents emit a short current-work statement plus a list whose completed/current/future statuses are parsed and stored with identity and time. The dashboard can combine these human-readable records with low-level tool traces. That is a useful bridge toward Wingman's executive briefing: planned work is represented explicitly instead of inferred from terminal output. Its limits are that summaries are agent-reported and task-centered, a new pipe list replaces the task's current todos, and each task retains only the last 100 progress entries. The next step is a per-agent, cross-task projection with links and freshness semantics.

The recovery ladder makes an unattended organization more concrete: stall → retry → wake a responsible office → tracker-state rollback → human intervention. It treats coordination failure as a workflow issue that can move up the organization. That is useful for Wingman's ProjectMaster, subject to the timestamp/scan limitations above, but inactivity alone cannot distinguish a slow build, an unresolved question and a crashed agent. Host/session liveness and meaningful progress evidence would improve the decision.

The rewrite adds [layered memory](../repo/edict/backend/app/workers/dispatch_worker.py), lines 186–250, [dynamic skill selection](../repo/edict/backend/app/workers/dispatch_worker.py), lines 277–305, and management/execution concurrency buckets (lines 309–335). These are source-backed engineering mechanisms with clear potential, but their existence should be separated from demonstrated integration. Likewise transactional outbox and Redis consumer groups are established patterns used here, not evidence of historical novelty. No claim of industry-wide uniqueness is made.

## Practical use in Wingman

Reuse the ideas of one shared task record, explicit agent-attributed progress, an independent plan reviewer, a management escalation ladder and inspectable task history. Those directly help Wingman remain accountable while operating unattended. The JSON stack is particularly understandable as a prototype reference because its state is easy to inspect and the supervision loop is tangible.

Adapt the fixed hierarchy into a **profile → durable agent instance → project membership → execution session** model. Keep organizational Butler/ProjectMaster agents distinct from project-owned ProductMaster/TechMaster instances and workload-driven workers. Replace fixed ID maps with data-driven registries so creating a role updates communication, assignments, dashboards and permissions consistently. Add a project registry and stable host placement before trying to infer projects from free-form task titles or tags.

Wingman would still need the full Telegram inbound/clarification/reply loop, durable real-agent rooms, project discovery/specification/acceptance records, cross-host execution/control, per-agent executive feeds, reliable session association, queued steering, conversation lifecycle controls, and an integrated coding/review workspace. These are substantial products, not configuration polish.

Before adopting the database/event rewrite:

1. Select one authoritative execution mode.
2. Replace JSON-writing prompts with that mode's API.
3. Start the outbox relay and load complete task context.
4. Align frontend API routes.
5. Persist retry and escalation state.
6. Add periodic reclamation of pending work and stable idempotency.
7. Test process cancellation and restart boundaries.

These integration steps precede autonomous operation on that foundation.
