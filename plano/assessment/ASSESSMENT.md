# Plano assessment against Wingman

Assessed on 2026-11-05. Repository: https://github.com/katanemo/plano . Local checkout: `research/plano/repo`. Actual checked-out commit: `b13ddd632bde1fea7678386c345665ea5fa671af`. This report assesses that local revision against [Wingman's purpose](../../WINGMAN_PURPOSE.md), using the [assessment guide](../../generic/assessments/ASSESSMENT_GUIDE.md). Sources were read only; no dependencies were installed and no services or tests were launched. Line references below refer to this commit.

## Verdict

**Plano is a useful candidate for Wingman's model and service data plane, but a poor replacement for Wingman's persistent development organization.** It routes HTTP requests among independently implemented agent services, translates LLM APIs, composes filters, preserves some model conversation state, and produces detailed telemetry. It does not implement the product/technical leadership, durable worker assignments, project registry, rooms, Telegram Butler, supervision loop, acceptance process or connected organization dashboards described by Wingman.

The distinction is visible in implementation, rather than just positioning. An `Agent` is an ID and network endpoint, with optional transport/tool/type metadata. A listener associates IDs with natural-language descriptions. It is not a durable Codex worker with a workspace, supervisor, task queue and conversation lifecycle ([configuration.rs](../repo/crates/common/src/configuration.rs), lines 53–68, 118–142). The request orchestrator selects an ordered list, awaits each agent, injects intermediate text into the next request, and returns the last response ([orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 264–401). There is also a real convenience launcher for externally installed Codex and Claude Code; that launcher does not turn Plano into a team manager ([core.py](../repo/cli/planoai/core.py), lines 187–299).

There are no **Exact** Wingman feature matches in this assessment. This reflects the category difference, not a claim that Plano lacks substantial implementation. Its strongest reusable mechanisms are described separately below so that infrastructure value is not confused with organization coverage.

## Architecture and execution model

### Configuration becomes a network data plane

The Python CLI is the operator entry point. Its Click group exposes infrastructure commands and imports `start_plano`, `start_cli_agent`, trace and observability commands ([main.py](../repo/cli/planoai/main.py), lines 18–50, 184–202). The configuration generator validates and renders the schema, rejects duplicate agent IDs, parses agent/filter URLs into endpoint clusters and validates filter references ([config_generator.py](../repo/cli/planoai/config_generator.py), lines 202–233, 255–300, 604–612). This is configuration compilation, not autonomous worker creation.

Native mode renders Envoy and Plano configuration, starts two separate daemon processes—`brightstaff` and Envoy—and saves their PIDs. It checks listener health, detects startup process exits, and kills the counterpart or stops the pair on failure ([native_runner.py](../repo/cli/planoai/native_runner.py), lines 69–158, 161–278). Container mode uses supervisord: config generation must finish before the two runtime processes start. The inspected configuration has `autorestart=false` and requests supervisor shutdown when a runtime exits ([supervisord.conf](../repo/config/supervisord.conf), lines 5–50). Neither path starts every YAML-defined agent service. Those are supplied by the application operator.

Envoy is the public network front end. An agent listener stamps `x-arch-agent-listener-name`, rewrites requests under `/agents/`, and forwards them to brightstaff. Its internal API router uses `x-arch-upstream` to select configured clusters. Model ingress forwards to brightstaff, while the lower LLM provider route applies provider routing and configured transport retries ([envoy.template.yaml](../repo/config/envoy.template.yaml), lines 248–287, 330–350, 419–435, 525–549). Endpoint clusters can use DNS, TLS and, optionally, prefix-affinity ring hashing (lines 998–1044).

### Native orchestration and LLM processing

Brightstaff loads rendered YAML once, constructs shared application state and launches a Tokio/Hyper server. It combines configured agents and filters into an ID map, resolves filter pipelines, initializes providers, optional model-metrics feeds, optional conversation storage and session affinity storage ([main.rs](../repo/crates/brightstaff/src/main.rs), lines 83–164, 200–228, 291–422, 450–486, 682–689). There is no live organization database behind that map.

The dispatcher has distinct execution routes: `/agents/...` invokes `agent_chat`; `/routing/...` returns a model routing decision; normal chat/messages/responses requests invoke `llm_chat`; `/function_calling` supports the prompt gateway; `/v1/models` lists models ([main.rs](../repo/crates/brightstaff/src/main.rs), lines 570–626). Each accepted TCP connection gets a spawned Tokio task (lines 635–676). That provides concurrent request handling. It is not a scheduler for independently continuing product teams.

For agent routing, `AgentSelector` resolves the listener, bypasses model classification for a single agent, otherwise converts descriptions to routing preferences and asks `OrchestratorService` for routes. Empty/no route results use a default or first configured agent. An orchestration error is returned as an error ([selector.rs](../repo/crates/brightstaff/src/handlers/agents/selector.rs), lines 39–165). `OrchestratorService` generates an LLM request, propagates trace/request IDs, calls an orchestrator endpoint, and parses the returned route list ([router/orchestrator.rs](../repo/crates/brightstaff/src/router/orchestrator.rs), lines 403–479). The actual routing model's weights and quality are not established by reading this repository. The repository contains the client protocol and prompt-building code.

The selected services execute **sequentially within a request**. For each, optional filters run first, followed by a POST through Envoy's internal router. Intermediate responses are collected to text, named with the agent ID and placed before the original final message. Only the last agent response is streamed to the caller ([handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 279–401; [pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 567–595). This is service-chain composition with transcript handoff. It has no durable task DAG or mailbox.

For LLM traffic, brightstaff parses the client's API, resolves aliases, runs input filters, normalizes requests for the upstream API, injects cache markers when configured, restores eligible Responses API history, derives affinity and makes routing decisions. Streaming observation records usage and behavioral signals ([handlers/llm/mod.rs](../repo/crates/brightstaff/src/handlers/llm/mod.rs), lines 140–178, 198–335; [streaming.rs](../repo/crates/brightstaff/src/streaming.rs), lines 520–580). HermesLLM contains the provider/API representations and transformations, rather than forcing each downstream agent to implement provider differences ([hermesllm/src/lib.rs](../repo/crates/hermesllm/src/lib.rs), lines 1–23; [providers/id.rs](../repo/crates/hermesllm/src/providers/id.rs), lines 30–95).

### WASM and persistence boundaries

The checkout also contains `prompt_gateway` and `llm_gateway` Proxy-WASM filters. They are Envoy extension components, not worker sandboxes. For example, the prompt gateway buffers/parses a chat request, maps configured prompt targets to tools and issues a `/function_calling` HTTP callout ([prompt_gateway/http_context.rs](../repo/crates/prompt_gateway/src/http_context.rs), lines 79–125, 154–250). It should not be assumed that every current agent request traverses both WASM plugins: the rendered template explicitly routes agent/model ingress into brightstaff, with separate internal/provider routes. Reading those routes is more reliable than flattening all components into one generic diagram.

There are several unrelated kinds of state:

| State | Implementation and scope | What it does not preserve |

## Agent definition and complete lifecycle

### Definition, creation and identity

An agent is registered by an operator, normally in YAML, as a stable ID plus URL. Listener-specific entries add descriptions, default selection and input filter references. The executable service and its own prompt/tools/framework live outside Plano's `Agent` object. The travel demo makes the separation concrete: `config.yaml` names `weather_agent` and `flight_agent` endpoints and descriptions, while separate FastAPI programs implement them ([travel config](../repo/demos/agent_orchestration/travel_agents/config.yaml), lines 3–54; [weather_agent.py](../repo/demos/agent_orchestration/travel_agents/src/travel_agents/weather_agent.py), lines 25–42).

Creation therefore means registration and separate deployment, not spawning a durable autonomous worker. The config generator checks unique IDs and converts endpoints into clusters. Brightstaff loads this configuration once during startup; no agent creation/update/delete management API or hot-reload watcher was found in the dispatcher. Adding an agent generally means changing configuration and restarting the infrastructure, as the README also explicitly describes ([README](../repo/README.md), lines 163–169). An ID identifies a service target; several requests can share it, so it does not identify one worker instance or one conversation.

The coding CLI path is different: `planoai cli-agent` reads the model listener endpoint and invokes an installed CLI synchronously with environment overrides. Codex receives a `--model` argument; Claude can receive forwarded settings. No agent record, PID-to-role map or project membership is created for that process ([core.py](../repo/cli/planoai/core.py), lines 156–172, 187–299). Its tool use, shell, repository changes, own persistent sessions and approvals remain the CLI's responsibilities.

### Execution, tools, permissions and routing

An HTTP request starts the agent lifecycle visible to Plano. The listener header determines the available service group. One agent bypasses classification; multiple agents produce natural-language routing preferences for the orchestrator model. The model is asked to return exact route names, with no requirement to generate a task plan, specify owners or evaluate acceptance. Its prompt drops system/developer/tool messages, retains recent text messages and applies a token estimate/trimming bound ([orchestrator_model_v1.rs](../repo/crates/brightstaff/src/router/orchestrator_model_v1.rs), lines 117–139, 185–220). Consequently, routing context is deliberately narrower than the full downstream working conversation.

The executor runs each selected entry's filters and invokes the service with current messages and the original provider request. `build_agent_headers` propagates tracing, sets the selected upstream ID and sends an Envoy retry-count header ([pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 81–109, 570–595). This is not a permission grant. No filesystem sandbox, per-role shell permission model, command approval policy or tool allowlist for coding workers was found in the agent schema or execution path.

Filters are more concrete than vague hooks. `process_raw_filter_chain` walks ordered IDs. An MCP filter initializes a session, receives `tools/call` with the raw `body` and `path`, and returns transformed content. A non-MCP filter receives raw bytes over HTTP. Failures become structured pipeline errors, and downstream request parsing rejects malformed filter output ([pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 210–340, 406–443, 446–565; [handlers/llm/mod.rs](../repo/crates/brightstaff/src/handlers/llm/mod.rs), lines 198–260). Applications can implement moderation, retrieval or memory there, but the actual policy and external service remain application-owned.

### Concurrency, persistence, resume and scheduling

Different requests can execute concurrently in Tokio tasks. Agents in one chosen list execute sequentially and the intermediate output becomes a named assistant message. There is no claim/lease per endpoint ID to make a service a single exclusive worker. There is no forked team, task pool, dependency release or resource allocation policy in that path. HTTP servers may implement their own concurrency, but that is outside Plano's management.

Persistence is deliberately narrower than agent continuity. With `state_storage` omitted, brightstaff disables conversation state management; memory loses it with the process; PostgreSQL writes `conversation_states` keyed by response ID. PostgreSQL requires a pre-existing table, connects using `NoTls`, and its background connection task logs connection failure ([main.rs](../repo/crates/brightstaff/src/main.rs), lines 450–486; [state/postgresql.rs](../repo/crates/brightstaff/src/state/postgresql.rs), lines 18–74, 78–170). The model path merges eligible Responses API history before deriving affinity ([handlers/llm/mod.rs](../repo/crates/brightstaff/src/handlers/llm/mod.rs), lines 291–335). More precisely, it manages state when the selected upstream lacks native Responses API support. A missing previous response returns HTTP 409, while another storage retrieval error is logged and execution can continue with current input alone (same file, lines 724–814). This is a material continuity limitation during backend failures. It supports continuing a model conversation, not recovering an interrupted coding task or replaying a half-completed service chain.

Redis bindings can persist model affinity between instances and reconnect after backend connection drops. Their TTL is a garbage-collection bound, separate from inferred provider cache warmth ([session_cache/redis.rs](../repo/crates/brightstaff/src/session_cache/redis.rs), lines 11–30, 39–71). MCP session IDs are retained only in the processor constructed for that incoming execution, so they must not be read as durable personal-agent sessions. No cron/task scheduler, project wake-up timer or agent supervisor was found. Periodic metric refresh and observability repaint timers maintain infrastructure rather than advancing work.

### Interruption, failures, recovery and completion

Plano has process-level stop and request/stream-level interruption behavior. Native `down` reads infrastructure PIDs, sends SIGTERM, waits up to ten seconds and escalates to SIGKILL. The Hyper loop exits its accept loop on Ctrl-C. It does not explicitly join all spawned connection tasks. A source comment says in-flight connections can finish, but this does not establish a verified graceful drain ([native_runner.py](../repo/cli/planoai/native_runner.py), lines 371–425; [main.rs](../repo/crates/brightstaff/src/main.rs), lines 635–676). A final-response streaming task stops relaying when its receiver drops ([response.rs](../repo/crates/brightstaff/src/handlers/response.rs), lines 84–110). There is no explicit remote-agent cancellation protocol or durable interrupted-work state.

Routing distinguishes no-route fallback from orchestration failure: an empty routing result chooses the configured default/first agent; model-call errors propagate. Filters distinguish HTTP client/server errors and MCP tool errors. The orchestrator preserves a pipeline client error's status/body in its error response ([selector.rs](../repo/crates/brightstaff/src/handlers/agents/selector.rs), lines 135–165; [pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 279–320, 498–513; [handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 70–106). Selected-agent invocation itself returns a raw `reqwest::Response`, so its error treatment is not identical to filter validation ([pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 570–595).

Transport retry support should be credited narrowly. The template supplies configurable retry policy on the LLM provider route, including selected 429/5xx failures and bounded backoff; agent/filter headers request retries, but the inspected internal agent route does not itself declare the same retry policy ([envoy.template.yaml](../repo/config/envoy.template.yaml), lines 265–282, 539–549). This does not provide task idempotency, checkpoint retry, semantic failure repair or resumable workflow recovery. The model-selection type documents ranked models as possible fallbacks ([model_selection.rs](../repo/crates/brightstaff/src/handlers/llm/model_selection.rs), lines 26–31); that comment alone is not evidence that every execution path iterates through those models on failure.

Completion means the chain reaches its last service and returns its response; empty chains and missing IDs are errors. An HTTP response is not a reviewed deliverable or accepted project. There is no organization stop-after-acceptance rule because there is no continuing project lifecycle in the first place. Retirement is removing service configuration and restarting, separately terminating the external service or CLI, and arranging data retention. Response storage offers a delete primitive; Redis has delete/TTL and the CLI has bounded telemetry buffers. No organizational archive/retire action ties identity, task ownership, conversation and artifacts together ([state/mod.rs](../repo/crates/brightstaff/src/state/mod.rs), lines 63–77; [session_cache/redis.rs](../repo/crates/brightstaff/src/session_cache/redis.rs), lines 51–71).

## Coordination mechanics and a concrete request trace

The implemented coordination primitive is **request chaining with message handoff**. There are no tickets, room posts, worker mailboxes or dependency events. The shared state is configuration plus optional response history/affinity. Human decisions are ordinary future inputs to a downstream application; Plano does not create an approval object with an owner or route it to Telegram. Traces record execution after/during requests, but do not serve as the control state for a project manager.

Consider the repository's real travel-services configuration and a request asking for Paris weather and NYC-to-Paris flights. This is a static execution trace through the implementation, not a runtime observation or a guarantee about the classifier's chosen order:

1. **Registration:** the travel config declares weather and flight service URLs and gives each a specialized description on listener `travel_booking_service`, port 8001 ([config.yaml](../repo/demos/agent_orchestration/travel_agents/config.yaml), lines 3–7, 16–54). The operator must run those services separately.
2. **Ingress:** Envoy stamps the listener name, rewrites the request under `/agents/`, and forwards to brightstaff ([envoy.template.yaml](../repo/config/envoy.template.yaml), lines 330–350). The native dispatcher invokes `agent_chat` ([main.rs](../repo/crates/brightstaff/src/main.rs), lines 570–578).
3. **Request interpretation:** `parse_agent_request` resolves the listener, parses the supported client API into a provider request and extracts messages, maintaining a request ID ([handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 123–204). `select_agents` converts the two descriptions into model preferences and invokes orchestration ([selector.rs](../repo/crates/brightstaff/src/handlers/agents/selector.rs), lines 86–165).
4. **Intent classification:** the orchestration prompt asks for exact route names in a JSON list. The service calls the configured model endpoint, parses its response and maps names back to configured IDs ([orchestrator_model_v1.rs](../repo/crates/brightstaff/src/router/orchestrator_model_v1.rs), lines 117–139; [router/orchestrator.rs](../repo/crates/brightstaff/src/router/orchestrator.rs), lines 420–479). If it returns weather then flight, that order is the execution order. There is no independent dependency planner.
5. **Weather execution:** `invoke_agent` sends the request to Envoy's internal API router with the weather upstream ID. The external weather FastAPI implementation uses the model gateway to extract a city, then calls Open-Meteo geocoding/weather APIs and handles some errors with a New York fallback ([pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 570–595; [weather_agent.py](../repo/demos/agent_orchestration/travel_agents/src/travel_agents/weather_agent.py), lines 64–141, 143–195). That domain logic is downstream agent code, not provided by Plano's orchestrator.
6. **Handoff:** the weather response is fully collected; its text is added as a named assistant turn before the original user message. The next request goes to flight with that history. No worker sends a room message, creates a task or acknowledges a persistent assignment ([handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 374–398).
7. **Return:** the final service's response is streamed to the caller, with nested spans kept alive for the streaming duration ([response.rs](../repo/crates/brightstaff/src/handlers/response.rs), lines 63–118). A full combined travel answer depends on the final agent using the prior information. The proxy returns that final response rather than running a separate synthesis/acceptance agent.

The repository has particularly useful implementation-level tests for steps 6–7: intermediate named-message insertion, ordered three-agent execution, only-final-response visibility, single-agent behavior, empty chains and unknown agents ([handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 531–707). These make the coordination semantics much clearer than the general term “multi-agent orchestration.”

## Major additional capabilities and integration consequences

### Provider/API translation and model agility

Plano implements a language-independent gateway that can accept chat completions, Messages and Responses client shapes and transform requests/responses for multiple providers. Provider identity is an explicit enum with supported API/cache capabilities; model aliases and route preferences are first-class configuration. The model-routing path distinguishes the semantic route from ranking models within it ([providers/id.rs](../repo/crates/hermesllm/src/providers/id.rs), lines 30–95, 100–221; [configuration.rs](../repo/crates/common/src/configuration.rs), lines 47–50, 223–254; [router/orchestrator.rs](../repo/crates/brightstaff/src/router/orchestrator.rs), lines 321–398).

For Wingman this could centralize credentials and provider behavior under the Codex/Claude client or HTTP services. It would not replace the agent harness. It also creates an interoperability burden: coding clients use rich tool calls, streaming events and conversation semantics, so successful basic chat routing does not establish complete harness compatibility. The checkout contains detailed Responses/custom-tool transformation work, but those transformations should be tested against Wingman's chosen client versions before adoption. Model IDs/defaults here describe this revision and are not a recommendation about present provider availability.

### Cost/latency ranking and cache-aware routing

The repository implements cost and latency catalog adapters, periodic refresh, and policy-based model ranking. Cost metrics retain distinct input/output/cache-read rates; actual per-request cost calculation handles provider conventions about whether prompt tokens include cache hits ([model_metrics.rs](../repo/crates/brightstaff/src/router/model_metrics.rs), lines 18–73, 90–145). This goes beyond Wingman's high-level usage visibility.

More distinctive is the separation between a quality/intention router and a session switch-cost gate. A binding retains the model a session began on, current warm model, observed context size, cumulative baseline and switch spend, plus up to eight model visits. A return to a recently used model can credit its warm prefix, making A→B→A cheaper than a cold switch ([session_cache/mod.rs](../repo/crates/brightstaff/src/session_cache/mod.rs), lines 20–101; [router/orchestrator.rs](../repo/crates/brightstaff/src/router/orchestrator.rs), lines 29–56). Session resolution uses explicit affinity IDs or stable prompt-prefix-derived IDs after filters/state merge; optional tenant scoping separates bindings ([session_router.rs](../repo/crates/brightstaff/src/handlers/llm/session_router.rs), lines 1–89; [handlers/llm/mod.rs](../repo/crates/brightstaff/src/handlers/llm/mod.rs), lines 307–335).

Wingman could use this to limit waste from switching models in long coding conversations. This estimates routing overhead. It does not cap total product-development spending or provider bills. Cache warmth is inferred. Pricing feeds can omit cache rates, and token accounting can use estimates. Bindings can be evicted. Cache-creation token pricing excludes a write premium ([model_metrics.rs](../repo/crates/brightstaff/src/router/model_metrics.rs), lines 38–72; [session_cache/mod.rs](../repo/crates/brightstaff/src/session_cache/mod.rs), lines 76–81). Concurrent requests sharing a session also warrant integration testing because the inspected Redis interface reads and writes a serialized binding rather than exposing a transactionally locked task budget ([session_cache/redis.rs](../repo/crates/brightstaff/src/session_cache/redis.rs), lines 39–64).

### Standardized HTTP/MCP filter chains

Input and output transformation pipelines can centralize retrieval, policy enforcement, memory or content handling across agents and model listeners. The same raw body plus API-path contract reaches either ordinary HTTP filters or MCP tools, keeping provider-shape processing outside each agent's business logic ([pipeline.rs](../repo/crates/brightstaff/src/handlers/agents/pipeline.rs), lines 210–340, 446–565; [handlers/llm/mod.rs](../repo/crates/brightstaff/src/handlers/llm/mod.rs), lines 198–260). This is broader middleware infrastructure than Wingman currently specifies.

For Wingman the value is consistent context injection and policy boundaries. The cost is an extra network dependency and failure surface on every filtered request, plus careful handling of schema validity, latency and streamed output. A filter is not automatically a trusted organizational knowledge source or worker permission boundary. Application-specific guardrails must still be implemented and validated; marketing references to moderation should not be read as proof of every built-in safety policy.

### Behavioral signals and detailed telemetry

Plano's signal analyzer groups interaction misalignment/stagnation/disengagement/satisfaction, execution failure/loops and environment exhaustion. It derives a quality report and summary from transcripts, with both batch and incremental APIs. Tool loops compare canonicalized call arguments and detect repeated calls, drift or oscillation ([analyzer.rs](../repo/crates/brightstaff/src/signals/analyzer.rs), lines 57–95, 141–207, 229–262; [loops.rs](../repo/crates/brightstaff/src/signals/execution/loops.rs), lines 11–16, 36–79, 140–190). The live stream observer emits these as span attributes/events and marks concerning spans ([streaming.rs](../repo/crates/brightstaff/src/streaming.rs), lines 557–570).

This could give ProjectMaster an additional evidence source for stuck or frustrated sessions and improve infrastructure investigations. The analyzer is heuristic evidence, not proof of correctness, user satisfaction or product acceptance. It does not wake workers or fix loops. The current live path calls batch `analyze_openai`. The existence of an incremental analyzer API is not evidence that the live path uses it. Turning signals into supervision requires Wingman-owned policies that link signals to a real project/worker/task and choose what to do.

The telemetry stack is independently useful: nested spans, custom propagated attributes, Prometheus HTTP/LLM/routing/cache/process metrics, trace CLI and a live TUI with latency/cost/token rollups ([metrics/mod.rs](../repo/crates/brightstaff/src/metrics/mod.rs), lines 1–25, 57–88; [obs/render.py](../repo/cli/planoai/obs/render.py), lines 22–51, 63–97). Exported telemetry needs identity correlation, retention and a presentation layer before it becomes Wingman's executive dashboard. Local buffers are bounded and ephemeral; persistent audit history should not depend on leaving the TUI open.

### Cross-provider Responses history and real network deployment

The conversation storage layer enables some non-OpenAI providers to participate in a `previous_response_id` workflow by reconstructing prior input/output history ([state/mod.rs](../repo/crates/brightstaff/src/state/mod.rs), lines 15–34, 79–101, 122–132). Network clusters can target remote HTTP(S) services and optionally preserve warm replica affinity with DNS ring hashing ([envoy.template.yaml](../repo/config/envoy.template.yaml), lines 265–282, 998–1044). These make Plano a plausible common data plane for agents deployed on the Mac and Endeavour.

Wingman must still deploy and supervise those agents, preserve code/workspaces and secure the shared services. The optional PostgreSQL backend requires its own schema and retention operations. The conversation table is keyed by response ID, unlike affinity's explicit tenant-prefix facility. A multi-project deployment needs application-level authorization and correlation design rather than assuming that configuring shared storage creates secure organizational isolation.

## Distinctive mechanisms and innovation assessment

The strongest architectural idea is **moving orchestration and model plumbing out of framework-specific agent code into a programmable proxy**. A generic HTTP service plus a declarative description can participate without adopting one agent framework, and routing/filtering/tracing can be changed centrally. Code shows the mechanism: listener descriptions become `AgentUsagePreference`, model-returned route names become configured agents, and an ordered executor hands history between HTTP services ([selector.rs](../repo/crates/brightstaff/src/handlers/agents/selector.rs), lines 86–159; [handlers/agents/orchestrator.rs](../repo/crates/brightstaff/src/handlers/agents/orchestrator.rs), lines 264–401). Its limit is equally concrete: one sequential request chain with textual handoffs does not produce a distributed task organization, autonomous follow-up or peer collaboration.

The **quality-router/cache-cost separation** is a more technical mechanism worth studying independently. It allows semantic routing while retaining a warm model unless a switch fits a cumulative overhead allowance. Keeping the original default model separate from the moving warm anchor avoids redefining the baseline after every switch. Bounded route history gives a return visit a context-size/time estimate. The mechanism enables deliberate model agility in expensive long contexts, but its quality decision still comes from a model and its affordability decision depends on approximate external cache/pricing behavior. It should not be marketed internally as a guaranteed total budget controller.

The **behavioral-signal taxonomy attached to ordinary tracing** gives operational tooling a cheap, framework-neutral way to find suspicious interactions without a separate judge call. Canonical tool-argument comparisons and bounded transcript processing make that more substantial than an error counter. Its limits are domain/language heuristics, false positives/negatives and observability without remediation. The code does not establish research benchmark claims, historical priority or industry uniqueness, and this report makes none.

Finally, the **raw-body/path filter contract across HTTP and MCP** is a practical interoperability design. One pipeline can host retrieval, moderation or transformation at a service boundary while preserving which client API shape is being handled. Its limits include protocol expectations, separate service availability, per-request MCP session handling and the need for output validation. These are reusable infrastructure patterns. They are not new Wingman roles by themselves.

## Practical fit for Wingman

Use directly, after integration verification:

- A model proxy behind Wingman's coding clients.
- Model aliases/provider adaptation.
- OTEL and Prometheus telemetry.
- Model cost/latency routing.
- Network access to independently deployed HTTP services. A low-risk first integration would keep Wingman's existing role/session/task machinery authoritative while routing a bounded subset of LLM traffic through Plano and comparing tool/streaming behavior, cost and latency.

Adapt substantially:

- Map Wingman agent instance IDs, project IDs, task IDs and host IDs into trace attributes.
- Retain exported spans durably.
- Connect signals to ProjectMaster without treating heuristics as decisions.
- Define an HTTP wrapper/protocol if role agents should be reachable as Plano services.
- Validate continuation/tool/attachment behavior for the selected Codex harness. Network orchestration could route to host-local service wrappers, but remote process launching and shared workspace correctness still belong to Wingman.

Build elsewhere:

- Telegram Butler and question correlation.
- Portfolio registry/intake.
- ProductMaster/TechMaster and scalable specialist profiles.
- Durable tickets/dependencies.
- Rooms/direct messaging.
- `DIRECTIVES` Knowledge management.
- Real per-agent session lifecycle.
- Recurring supervision.
- Product testing and acceptance.
- Executive summaries/timelines.
- Directory/project/dashboard links.
- Secure multi-host agent deployment and lifecycle. Plano's data plane can sit beneath these, but adopting it does not materially reduce their product-level scope.

A wholesale fork into an organization manager would require introducing a control plane almost entirely absent today. The better fit is an optional infrastructure component or source of mechanisms. Its strongest relevance is operational consistency and model economics, while its weakest relevance is Wingman's defining persistent organization and human-facing working environment.
