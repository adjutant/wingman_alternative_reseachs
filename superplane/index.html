SuperPlane assessment against Wingman

Identity and verdict

  • Product: SuperPlane, an engineering automation engine with a substantial Factory task delivery layer.
  • Repository: https://github.com/superplanehq/superplane
  • Local checkout: research/superplane/repo.
  • Assessed commit: 7d755d16b8ae836ecebf61639efc6266d74a4b0b.
  • Assessment date: 2026-11-05.
  • Basis: the local revision, read-only source and test inspection. No dependency installation, build, test execution, service launch, browser session, or external service verification.

Fit verdict: a strong delivery and execution substrate, but a substantial adaptation for Wingman's standing organization. This revision is much more than a generic workflow canvas. It persists repository workspaces, work orders, planning conversations, specifications, checks, artifacts, line traversals, PR activity, runner tasks, and remote runner fleets. Real Codex, Claude Code, and OpenCode processes execute work. A human can refine a task, start an implementation, inspect progress, respond to questions, and review the resulting PR. These are valuable implemented capabilities.

Its durable center is nevertheless the task and workflow, rather than an organization of named agents. A planner is a configured execution mode attached to a work order. An implementation agent is a coding CLI invoked inside a runner task. A runner is execution capacity, not a ProductMaster or BackendCoder. The source does not establish Butler, ProjectMaster, per-product leadership teams, agent rooms, an agent directory, or an executive view of each agent's current/recent/next work. Wingman could use SuperPlane behind that organization; adopting it as the organization itself would require a new domain and communication layer.

Architecture and execution model

Control plane, workflow engine, and Factory layer

The server entry point is only server.Start() in cmd/server/main.go, lines 1–7. pkg/server/server.go, lines 124–338, starts separate workers for event routing, run initialization/finalization, node execution, node queues/requests, runner task scheduling, log compaction, cleanup, and Factory synchronization. The API is Go with protobuf/gRPC and a REST gateway. The operational client is React/TypeScript. PostgreSQL models carry authoritative state. RabbitMQ distributes notifications and execution events. This is a service-backed application, rather than a CLI wrapper with a terminal grid.

The Factory model represents an organization-scoped repository workspace. It includes a stable URL identity, description, planning settings, optional auto-start line, visibility, and budget in pkg/models/factory.go, lines 50–93. A FactoryWorkOrder has title, description, state/result, origin, repository/branch, assignees, and current wait notes in pkg/models/factory_work_order.go, lines 18–99. These records are usable project/task primitives, but do not establish a product registry with autonomous leadership.

A line is an ordered sequence of workflow applications. Each step references an application and its onRun entry point, with a default maximum parallelism of 10. See pkg/models/factory_line.go, lines 14–60 and 122–133. Dispatch creates a separate durable traversal that snapshots the line's steps and records model/thinking overrides. Admission locks the line, preserves FIFO ordering, and either starts a step or queues it. See pkg/models/factory_work_order_line_dispatch.go, lines 34–58, 78–138, and 210–245. This distinction between reusable line, one traversal, step execution, and runner task is important for interpreting status and retries.

Canvas runs are version-bound records with parent run/execution references, callbacks, input, state, errors, cancellation, and finish timestamps: pkg/models/canvas_run.go, lines 19–52. The workflow layer is event driven with database recovery sweeps. RunInitializer consumes pending-run messages and also scans once per minute; NodeExecutor likewise consumes RabbitMQ and scans pending executions once per minute; RunFinalizer consumes several terminal-event channels and scans started/cancelling runs every five minutes. See run_initializer.go, lines 53–89; node_executor.go, lines 79–125; and run_finalizer.go, lines 69–104. These are mechanical recovery and progression loops, not an LLM manager reviewing project health.

How code actually runs

RunCodex.Execute resolves secrets/environment, mints scoped context, attaches task files/MCP/resources, builds ordered commands, and creates an integrated runner task with host execution mode. See pkg/components/runner/codex/component.go, lines 130–188. Its specification configures machine type, ordered bash/prompt steps, credentials, model, reasoning level, working directory, environment, timeout, and visual evidence; see codex/spec.go, lines 10–21 and 85–120. Parallel provider implementations are registered for Claude Code, Codex, OpenRouter/OpenCode, and the hosted SuperPlane agent in pkg/registryimports/registryimports.go, lines 22–26.

BuildAgentTask materializes preparation scripts, provider wrapper, telemetry/activity helpers, setup commands, attachments, and per-step prompt/script files. Each step carries separate preview text and dispatched text. Prompt steps install workspace skills in their working directory. See pkg/components/runner/agent_task.go, lines 19–77, 136–165, and 204–240. The creation context checks fleet admission/credit, encrypts payloads, and persists a pending task; pkg/workers/contexts/runner_task_context.go, lines 38–83. The scheduler admits organizations independently of live sockets and exposes committed queued work to runners; pkg/workers/runner_task_scheduler.go, lines 17–20 and 44–88. Organization-slot admission serializes using database locks and oldest-task ordering in pkg/models/runner_task_scheduler.go, lines 31–83.

Remote runners register with a short-lived token, obtain runner credentials, connect over WebSocket, and execute tasks. The runner loop is sequential per runner, while many runners can work concurrently. Ephemeral runners exit after one acknowledged task; reusable runners accept another. See pkg/runners/agent/agent.go, lines 85–147. The host executor runs actual shell commands/processes, materializes task files, and cleans temporary task files and optional isolated homes; pkg/runners/agent/host_executor.go, lines 38–74. A general Docker executor also exists, but the reviewed Codex component selects host mode. A Docker fleet may therefore isolate the runner host in a container while the task itself still uses the host executor.

Fleet Manager is a separate infrastructure reconciler. It reads fleet state/capacity, lists provider resources, removes terminated resources, and adjusts capacity. AWS, Azure, GCP, and Docker providers are local code, not just promised integrations. See pkg/fleets/reconcile/reconciler.go, lines 143–220; pkg/fleets/provider; and pkg/fleets/README.md. For a concrete provisioning call, the GCP provider, lines 157–210, calls InsertInstance with runner bootstrap data, handles unknown operation results and retries capacity across zones. Thus multi-host execution is real in the implementation. It shares central tasks/events/artifacts, not a common mounted Wingman project/room filesystem.

Agent definition and full lifecycle

What the entities actually mean

SuperPlane has several distinct identities which should not be collapsed into “agent.” A Factory is durable workspace configuration. A canvas/application defines automation behavior. A line orders applications. A work order is a durable request and its delivery record. A line dispatch is one snapshotted traversal. A canvas run/node execution is workflow runtime state. A runner task is the durable executable unit assigned to one runner. A runner is a registered machine/process with ephemeral or reusable lifetime. A planning session is a persistent work-order conversation. A coding agent is the provider CLI process invoked for one or more prompt turns inside that task. Model instructions and skill files can make that process behave like a specialist, but do not create an independently managed organizational member.

This is visible directly in RunnerTask, lines 50–84: organization, fleet, runner, payload, execution state and result are stored, with no agent-role/person identity. The owner selected during task creation is a user identity, sometimes tied to that user's Codex subscription, not the coding process. See create_work_order.go, lines 123–152.

Definition, configuration and creation

An operator configures an agent node with provider, model/reasoning, credentials, steps, timeout, environment and working directory. A line or intake builder materializes these nodes into a workflow. Workspace resources supply reusable knowledge and tools. The workflow execution resolves all of that into task files and commands. RunCodex.Execute creates a fresh task UUID; CreateTask serializes the payload; RunnerTaskContext.Create encrypts it and writes a pending task. The stable identities are task/run/order UUIDs and saved configuration. Creating an automation or giving a prompt a title does not instantiate a long-lived named specialist.

The preparation step checks that the CLI exists on PATH. The report does not assume SuperPlane downloads a coding harness dynamically. See agent_task.go, lines 264–270, and codex/spec.go, lines 85–102.

Tools, permissions and routing

The runner executes bash and coding CLI tools with injected integration environment. Workspace MCP servers support connection-level resources and disabled/enabled tool choices. Skills are copied into the coding working directory while existing repository skills are preserved. Context repository credentials are distinguished from the write credential for the primary repository. See workspace_agent_resources.go, lines 30–44 and 110–152; agent_task.go, lines 211–240.

A global SuperPlane MCP server exposes tasks, owners, checks, plans and artifacts. Flow-specific scopes distinguish planning, implementation and merge-confidence tools. However the current shared scopes give every flow task create/close and artifact/check mutation permissions. These should not be described as a narrowly read-only planner capability. See runner_tools.go, lines 38–76. Request tokens scope organization/workspace/run operations, while actual shell permissions remain those of the runner host.

In particular, codex/run.js, lines 167–195, unconditionally passes --dangerously-bypass-approvals-and-sandbox, and adds managed developer instructions when planning is enabled. The source describes analysis as read-only, but this is a protocol/instruction boundary, not a Codex filesystem sandbox. Wingman would need to choose runner isolation, credentials and approval placement accordingly. Human workflow approval nodes do not automatically constrain each tool call in a coding task. Permission details also differ by harness: the Claude wrapper, lines 128–163, selects a planning tool allowlist/default permission mode and acceptEdits otherwise. The Codex bypass finding should not be generalized as identical command construction across all providers.

Routing is explicit: organization → factory → order/line/session, and machine type → fleet. No Butler resolves an arbitrary conversational reference across products. The workflow graph routes events via nodes and output channels. It does not send an addressed message to another durable agent.

Execution, concurrency and scheduling

A task moves through pending, queued, reserved and running to succeeded/failed/canceled/lost. The constants and fields are in runner_task.go, lines 14–84. Organization slot admission precedes fleet visibility; per-line step admission has its own FIFO capacity constraint. One runner executes tasks serially, while independent runners execute concurrently. This supports many task instances without claiming a team of collaborating specialists.

A scheduled intake runs an agent to propose a task. Other work begins from UI/API/MCP calls, VCS events, monitoring intake, or explicit line dispatch. These triggers are configured automation rather than an agent deciding when to wake. Infrastructure workers continuously repair queues and capacity, not the semantic plan for a product.

Persistence, resume and follow-up

Normal Codex prompt steps in a task save the CLI thread ID to codex_session and later invoke codex exec resume <id>; codex/run.js, lines 174–178 and 198–224. This is process/task-local provider continuity. It is not evidence of an agent resuming its identity on another machine after arbitrary task retirement.

Planning has stronger application-level continuity. A FactoryPlanningSession stores messages, draft reference, survey, wait state, canvas/run identity and heartbeat. Reattachment reuses a session for the same work order and can reopen it with a new agent run. Sending a new human message locks the draft/session, persists the message, adds the sender as a draft owner, and restarts analysis when necessary. See planning_session.go, lines 134–163. AppendPlanningSessionContinuation supplies instructions and a generated rewind file. The analysis path can intentionally start a fresh CLI conversation instead of resuming a provider thread. planning_session_assets.go, lines 121–151, and codex/run.js, lines 213–224, make that distinction explicit.

The rewind is bounded: the model constants use a 24,000-character recent-message limit and an 80% retention target in factory_planning_session_analysis.go, lines 35–44. The actual suffix-selection and truncation algorithm is at lines 480–509. Application state therefore persists more durably than the exact model context. Long histories do not imply that every message is present in every future model prompt.

Planning tasks append a follow-up wait loop and keep the machine available while awaiting a human message. The documented construction waits up to five minutes for the next message before exit; see codex/spec.go, lines 135–168, and the actual loop in follow_up_loop.js, lines 768–801. This supports an interactive refinement session, not an indefinitely resident agent.

Interruption, cancellation, failure and recovery

The task model cancels pending/queued unassigned work immediately; for assigned tasks it records CancelRequestedAt, which is delivered to the runner. Runner execution uses a cancellable context and timeout. A shutdown signal requests an orderly protocol: cancel current task if necessary, stop execution, upload logs, acknowledge completion, then shut down. A second signal or 30-second grace expiry stops immediately. See runner_task.go, lines 122–180; agent.go, lines 163–205 and 330–399.

Starting implementation explicitly ends the draft planning session and requests completion/cancellation of its runner tasks within the dispatch transaction. It does not leave the planner concurrently modifying the same draft. See factory_planning_session_analysis.go, lines 150–204. This is a useful ownership handoff, although not a ProductMaster remaining available as an independent colleague.

Recovery occurs at several levels. Database sweeps catch missed RabbitMQ progression. Fleet-unavailable unassigned tasks can return to pending. Pending execution retries may recover transient database/billing verification errors; confirmed admission failures become failures. See node_executor.go, lines 551–583. Task history and rerun APIs allow explicit stage retries without discarding earlier traversal evidence. This does not establish automatic safe replay of all failed external side effects.

Disconnected runners are allowed a recovery window, then marked lost. runner_registration_cleanup_worker.go, lines 17–18 and 99–135, uses a 15-minute connection-loss threshold. runner_connection_lifecycle.go, lines 10–73, marks active work lost, clears its payload, terminates the runner and revokes credentials. It does not resume the same OS process on a replacement host. Distinguish transport reconnect, workflow retry, rerunning a stage, and provider conversation continuation. They have different guarantees.

Completion, acceptance and retirement

Runner completion is deliberately ordered after retained log upload acknowledgement. agent.go, lines 294–325, closes/waits for the log spool before sending the terminal result and waiting for acknowledgement. A completion hash in runner_task.go, lines 78–83, supports idempotent completion across reconnects. Success here means command/task success. It does not prove product acceptance.

The implementation template instructs the coding agent to run relevant repository tests/lint/build checks and produce a substantiated PR description. It then commits, pushes and creates or updates a PR, attaching artifacts to the work order. PR checks and reviews can launch feedback repair. The PR-closure automation maps a merged PR to completed, and a closed unmerged PR to pr_closed. A user can also close/reject/archive work through the order state machine. This is concrete software delivery, but PR state is a narrower acceptance boundary than Wingman's product definition of done.

Temporary task files are removed by the host executor; optional isolated homes are removed after execution. Terminal task transitions discard encrypted input payloads, while task outcomes/log lifecycle/artifact records remain according to cleanup policy. Ephemeral runners retire after acknowledged work; Fleet Manager deletes owned terminated provider resources. Reusable runners keep accepting unrelated tasks. None of these retirement paths preserve a durable worker's organizational identity because the model does not define one.

Coordination mechanics and an implementation trace

The coordination fabric combines SQL state, workflow graph edges, RabbitMQ notifications, task threads, artifacts, PR discussions and scoped MCP tools. Work-order events are independent rows with type/data/time in factory_work_order_event.go, lines 14–26. Comments have first-class storage and mention rows rather than existing only as log fragments. Planning messages and activity snapshots preserve a human-agent exchange. These are useful records, but no Room1/Room2 participant model or agent-to-agent deliberation runtime was found.

The graph and line structure represent execution dependencies. The source inspected does not establish an autonomous product planner that builds a ticket DAG for several specialists. In fact managed refinement explicitly narrows a large request to one runnable task instead of creating subtask records. Cross-application AppMessage delivery is a subscription broadcast: it creates downstream events and deletes the queued message after transactional delivery. It should not be credited as an agent chat application.

The following is a source-traced supported request path, not a runtime observation: a human asks for a bounded repository change through a Factory task.

  1. Create the task. CreateWorkOrder authenticates the user, resolves a specified Factory, validates ownership/model, writes the task and binds description files transactionally. It then emits workOrder.created and publishes a board update. create_work_order.go, lines 24–120.
  2. Route to refinement. The Backlog canvas has an On Work Order trigger, a taskRefinementEnabled filter, and a Refine Task agent node with a failure branch. backlog_template.go, buildBacklogCanvas, lines 177–224. The workflow engine creates node execution and the selected provider creates a runner task. The analysis session is linked/reused for the work order in factory_planning_session_analysis.go, lines 59–143.
  3. Read and clarify. The managed protocol asks the agent to inspect actual repository behavior, implementation options and checks before scoring/asking. It publishes scores, spec and optional survey through propose_plan. The backend locks the session, validates all three scores and applies the update atomically. A survey with all scores at maximum is rejected. analysis_user_prompt_review.md, lines 25–64; factory_planning_session_update.go, lines 68–122. The human answers in the saved session. The follow-up loop continues or a new run reconstructs context.
  4. Dispatch implementation. Manual Start resolves the named line and accepts optional stage/model/reasoning/replacement choices. It locks the order, ends planning and checks owner/line readiness. The line snapshots its definition and admits or queues the first requested stage. dispatch_work_order.go, lines 22–71 and 178–232; factory_work_order_line_dispatch.go, lines 95–138 and 210–245. Optional auto-start uses a separate readiness policy and atomic claim, rather than pretending the model's confidence is an approval.
  5. Run the code agent on a host. The provider builds files/commands and persists an encrypted task. The organization scheduler admits it. A fleet runner reserves it and runs the host executor. codex/component.go, lines 139–188; runner_task_context.go, lines 38–83; runner_task_scheduler.go, lines 31–83; agent.go, lines 123–147 and 279–325.
  6. Deliver a PR and inspect it. The implementation template supplies the work-order description, repository conventions and testing requirements; subsequent steps commit/push, generate PR title/body, attach branch and PR artifacts, and record failures. line-implementation.canvas.yaml, lines 74–160 and 195–313. The board/timeline links the resulting runs and artifacts. The split view loads live execution data. The supported trace is workflow handoff, not several named agents negotiating in a room.
  7. Respond and settle. PR mentions/reviews trigger configured feedback workflows; CI repair reads failed checks and verifies the remote PR head before pushing. pr_feedback_template.go, lines 112–180; pr_feedback_checks_template.go, lines 270–342. Merge/closure updates the work-order result through pr-closure.canvas.yaml, lines 62–115. Product-wide human acceptance remains outside this trace.

Major capabilities beyond the Wingman description

Engineering and operations integration graph

The registered catalog includes VCS, CI/CD, observability, incident response, cloud infrastructure, chat, email, HTTP/GraphQL and memory components. See registryimports.go, lines 7–87. This permits a source issue, monitor or incident to feed delivery, and a completed workflow to affect existing engineering systems. That is broader than Wingman's described personal organization and basic functional testing. Integration breadth is useful only after configuring credentials, webhook endpoints and event semantics. It does not prove every connector works in a deployment. Wingman could reuse the graph for delivery and operational automation while keeping product-direction decisions in its own agent organization.

PR feedback and CI repair as continuing delivery work

SuperPlane can react to PR comments, reviews and replies, and separately wait for/check CI outcomes and launch repairs. Feedback concurrency is partitioned by PR number so unrelated PRs can proceed while one PR serializes. See pr_feedback_template.go, lines 13–63 and 112–180. CI repair has a concrete stale-head guard before pushing, shown in pr_feedback_checks_template.go, lines 270–286. This is more specific delivery machinery than a general “test and report” worker. Wingman would need to connect the resulting review/repair events to its shared tracker and avoid duplicate repair agents working the same branch.

Merge confidence and visual evidence

The built-in merge assessment breaks review into blast radius, performance, security, specification drift and reversibility, using separate prompts in risk-score.canvas.yaml, lines 65–235. visual-evidence.canvas.yaml, lines 70–158, captures evidence and updates the PR description. These provide review aids beyond Wingman's stated TestMaster scope, which excludes Security and DevOps. Scores are model assessments. The source does not establish their calibration as a reliable substitute for human review or deterministic checks. Visual evidence requires a usable runner/browser/application environment.

Fleet provisioning and execution accounting

The distributed fleet stack handles real VM/container demand, warm capacity, maximum capacity, registration, remote execution, log upload and cleanup. Runner payload encryption and credential revocation are explicit control-plane behavior. This gives Wingman an operational foundation for multi-host workers without building that infrastructure first. It also introduces cloud provider configuration, runner images, service reachability, secrets, central PostgreSQL/RabbitMQ and artifact/log storage. Host-mode code execution means the fleet's trust and isolation boundaries matter.

Task execution is also subject to admission/credit/plan checks in runner_task_context.go, lines 50–60, and node_executor.go, lines 551–583. This revision includes hosted, BYOK and subscription-specific concerns, rather than being only a local free orchestration script. Deployment/license configuration was not exercised, so those guards should be evaluated for the intended self-hosted mode before reuse.

Multimodal task intake and reusable resources

Task files can be images, audio or video; attachment preparation and inspection are integrated into task construction. The agent task builder, lines 38–75, attaches preparation steps. The managed protocol, lines 39–49, directs attachment/frame/transcript inspection before planning. Workspace context repositories, skills, setup commands and OAuth-backed MCP tools provide reusable task environments. This could let Wingman receive richer product evidence and give workers consistent tools, but it requires installed media/browser utilities and explicit knowledge ownership. It is not automatic durable product knowledge curation.

Distinctive mechanisms and their limits

Atomic planning publication. propose_plan packages three review parameters, specification and optional survey as one domain update. Validation rejects incomplete/invalid scores, requires first-turn scoring, and prevents a needless survey when all scores are maximum. This makes the UI and stored plan represent one coherent planning turn instead of partial tool updates. See factory_planning_session_update.go, lines 43–122. The mechanism enforces shape and timing. It cannot establish that the model researched correctly or chose good scope. The managed prompt's Clarity/Complexity/Verifiability separation is useful to Wingman because it distinguishes “understood,” “fits one run,” and “can be proved.”

Conservative automatic start based on first assessment. Auto-start requires planning enabled, a draft, no outstanding survey, current-turn scores, a specification, and the first report of each review parameter at maximum. A later upgrade after an initially low score does not automatically start work. See factory_planning_session_analysis.go, lines 626–680, and runner_planning_session.go, lines 466–508. This is a concrete autonomy policy rather than a generic approve button. Its limit is that first assessment still comes from an LLM and can be wrong. It also deliberately leaves some refined tasks for manual Start.

Snapshotted delivery traversals with fair admission. A line dispatch saves its stage list independently of later line edits, while stage admission locks and FIFO queues prevent concurrent starts from overfilling a stage or jumping queued work. See factory_work_order_line_dispatch.go, lines 34–58, 78–138 and 210–245. This makes delivery history/retry semantics inspectable. It is not a scheduler for specialist skills, task difficulty, cross-ticket dependencies or shared working-tree conflicts.

Log-complete acknowledgement barrier. The runner waits until every retained log chunk is accepted before sending completion, and then waits for the completion acknowledgement. Together with durable task state and completion hashing, this gives a stronger debugging record across reconnects than simply recording an exit code first. agent.go, lines 294–325; runner_task.go, lines 78–83. “Retained” is a meaningful limit: the spool is bounded, and the guarantee is not infinite logs or process migration.

Planning continuity separate from provider sessions. A saved work-order conversation can be rewound into a fresh CLI run, while normal multi-prompt implementation can resume the exact provider thread. planning_session_assets.go, lines 121–151; codex/run.js, lines 198–224. This makes application-level continuity less dependent on a provider's local session artifacts. Its bounded context and task scope still fall short of a persistent agent identity with lifelong project responsibilities.

These are distinctive combinations in this codebase. No claim of historical novelty or industry uniqueness is made.

Practical Wingman fit and integration gaps

Directly useful: use the Factory work-order record, task board, artifact/check/timeline machinery, real coding CLI components, scoped task APIs/MCP, workflow gates, remote runner/fleet services, PR creation/feedback/check-repair workflows, and durable run recovery. The task planning protocol is a useful starting point for bounded change discovery and acceptance planning. These capabilities could shorten development of Wingman's delivery subsystem substantially.

Needs adaptation: map a Wingman product to one or more repository workspaces without confusing repositories with products. Map organization agent identities to execution requests and user/provider credentials separately. Save the organizational agent ID on run/task/comment events so current activity and history can be aggregated by agent. Add durable project directives and decisions as first-class references and ensure every prompt gets the right versions. Convert task artifacts and PR status into tracker updates and acceptance evidence. Decide which actions belong to an LLM role and which remain deterministic workflow transitions. Connect Telegram through a dedicated Butler router which preserves project, agent and question identity. The current planner's one-task rule would need a separate technical decomposition stage for substantial products.

Still to build:

  • Persistent agent/profile/instance/team models.
  • Butler/ProjectMaster/ProductMaster/TechMaster behavior and separate conversations.
  • Multi-agent rooms, direct messages and escalation.
  • Conversational new/existing project routing.
  • Research and iterative product discovery beyond repository task refinement.
  • Specialist assignment/dependency management.
  • Proactive semantic supervision.
  • Product-wide functional acceptance and stopping after accepted delivery. An agent directory.
  • Portfolio executive agent summaries.
  • Per-agent timelines and detailed personal coding workspaces. Missions and Wiki stubs should not be counted as delivered versions of those features.

A practical adoption boundary is Wingman organization above SuperPlane execution: the organization owns goals, product truth, staff identity and communication; SuperPlane owns durable task execution and integration workflows. A complete fork making the Factory UI the entire Wingman experience would require substantial schema, authorization, lifecycle and UI changes. This is an architectural judgment based on the inspected execution model, not a measured integration estimate.
