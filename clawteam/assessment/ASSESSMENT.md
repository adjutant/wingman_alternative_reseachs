## Fit verdict

**ClawTeam is a useful execution-and-coordination foundation for Wingman, but is not the continuing software organization Wingman describes.** Its strongest implemented combination is independent native coding-agent processes, logical team membership, shared tickets with dependencies and claim locks, durable direct/broadcast communication, Git workspaces, and an agent-facing CLI/MCP interface. A leader can actually delegate to separate Codex or other CLI processes and receive their reports. This is substantially closer to Wingman's execution layer than a library that merely runs several role prompts in one conversation.

The organizational gap remains large. A team is not a portfolio project with durable product and technical leadership. A runtime profile is not a standing professional role. The board is not a detailed per-agent coding workspace. There is no Telegram Butler, cross-project conversational intake, product registry routing, Room1/Room2 management structure, or executive briefing/timeline for every agent. The bundled software team has a tech lead, backend developer, frontend developer, QA engineer and DevOps engineer, but product discovery and long-term product ownership are not first-class organizational responsibilities.

There is a plan/execute/verify harness with meaningful specification, contract and human-gate primitives. The checked-out package labels itself Alpha. Its source reveals material integration limits: gates check registration/status rather than verified acceptance; loaded runs lose their gates. The running conductor does not refresh separately saved approvals; lifecycle journals use inconsistent paths; and two harness CLI paths still treat string phases as enums. This is a useful design to study, but this revision does not establish a dependable autonomous product-delivery engine.

This assessment concerns the pinned source. No dependencies were installed, agents launched, services started, or tests executed. Findings below distinguish implemented mechanisms, prompt-level instructions and inferred integration work.

## Architecture and execution model

The package exposes `clawteam` through Typer and `clawteam-mcp` through FastMCP. There is no central model inference engine in ClawTeam. The models, tools, conversation handling and coding abilities reside in the external CLI it starts. ClawTeam supplies process launch, identity injection, shared coordination state, workspace management and monitoring. See [package entry points](../repo/pyproject.toml), under `[project.scripts]`, and [MCP server](../repo/clawteam/mcp/server.py), lines 13–33.

The main operating paths are different and should not be conflated:

1. **Individual spawn:** `spawn` resolves the backend/runtime profile and checks the logical worker's liveness. It can create a Git worktree. It registers the member and builds its identity, task, and coordination prompt. It can add a saved native resume command before invoking the backend. Launch failure removes newly added membership and attempts workspace cleanup. See [CLI](../repo/clawteam/cli/commands.py), lines 3093–3332.
2. **Template launch:** `launch` loads a TOML team, creates the leader and members, seeds its tasks, then launches their native CLIs. The template supplies job instructions. This path defaults to **no isolated workspaces** unless requested, unlike individual `spawn`'s automatic worktree behavior. [CLI](../repo/clawteam/cli/commands.py), lines 4034–4219.
3. **Harness conductor:** `harness conduct` builds a phase orchestrator and a foreground polling controller, loads plugins, and spawns planner/executor/evaluator roles as phases advance. This is an optional state machine around agents, not the same behavior as a software-dev template team. [CLI](../repo/clawteam/cli/commands.py), lines 4499–4544; [conductor](../repo/clawteam/harness/conductor.py), lines 83–174.

The distinction also applies to `harness-default.toml`: although that file contains `harness`, `human_gates` and wave settings, the generic template parser's `TemplateDef` and `_parse_toml` only retain ordinary team fields. `launch` does not instantiate HarnessOrchestrator from those settings. Launching this named template should therefore not be credited with automatically activating its declared phase/gate configuration. The separate harness command is the implemented controller path. [Template parser](../repo/clawteam/templates/__init__.py), lines 35–44 and 78–105; [harness template](../repo/clawteam/templates/harness-default.toml).

The default state directory is `~/.clawteam`, overrideable through configuration/environment. It holds team configurations, inboxes, persistent message events, task JSON, spawn registries, native session references, costs, workspaces, plans, snapshots and harness artifacts. The team schema contains a leader ID, members and a budget. It does not contain a product ID, product scope, permanent host placement or a portfolio relationship. [Models](../repo/clawteam/team/models.py), lines 15–23 and 65–142; [manager](../repo/clawteam/team/manager.py), lines 78–133.

The tmux backend creates `clawteam-{team}` and a separate window for each agent. It installs exit/crash hooks and waits for CLI readiness. It then injects the task and records the target and pane PID for liveness checks. Execution continues independently of the web board. The subprocess backend uses `Popen`, discards stdout/stderr, and records a PID. The `wsh` backend integrates terminal blocks. Observability therefore depends on the backend. See [tmux backend](../repo/clawteam/spawn/tmux_backend.py), lines 156–330; [subprocess backend](../repo/clawteam/spawn/subprocess_backend.py), lines 122–158; and [backend registry](../repo/clawteam/spawn/__init__.py).

The coordination data flow is `human/leader/native worker → CLI or MCP → team/task/mail files → board collector → HTTP/SSE snapshot → web view`. Live attention takes an additional route through InboxWatcher, RuntimeRouter and the selected execution backend. This is a shared-file control plane with optional messaging transports and foreground watchers, not a daemon that owns all model sessions. MCP's registered tools cover teams, tickets, mailbox, plans, board, cost summary and Git context. The registry does **not** expose spawn, stop, harness control or full coding-session inspection. [MCP inventory](../repo/clawteam/mcp/tools/__init__.py), lines 28–55; [inbox watcher](../repo/clawteam/team/watcher.py), lines 40–78; [board server](../repo/clawteam/board/server.py), lines 128–187 and 222–241.

The conductor's member named `conductor` is a logical placeholder created by PhaseRoleSpawner. The conductor itself is a Python polling process, not a separate reasoning agent. Also, the harness spawner calls the backend directly with no workspace/CWD creation even though its executor role prompt says “isolated workspace.” Worktree behavior established for `spawn --workspace` cannot be assumed for this path. [Role spawner](../repo/clawteam/harness/spawner.py), lines 62–93; [executor role](../repo/clawteam/harness/roles.py), lines 34–40.

## What an agent actually is, and how its lifecycle works

### Definition, creation and identity

There are three definitions to keep separate. `AgentProfile` defines a reusable **runtime**: executable, model, provider base URL, environment mapping and arguments. `AgentDef`/TOML definitions describe a **job** through a name, type and task prompt. `TeamMember` is a **logical registered participant** with name, user, generated ID and type. A running agent is an external CLI process associated with that participant through environment variables and a spawn registry. A team member can exist when no process is alive. [Configuration](../repo/clawteam/config.py), lines 14–37; [template loader](../repo/clawteam/templates/__init__.py); [models](../repo/clawteam/team/models.py), lines 65–86.

`spawn` generates a fresh ID, checks duplicate liveness, resolves its runtime, prepares worktree/CWD, and auto-creates a team if needed. The first member becomes the leader of an automatically created team. Reusing an already registered logical name catches and ignores add-member failure; therefore the fresh process ID is not necessarily a refreshed persistent membership ID. This is a useful practical distinction if Wingman wants identity to survive replacement with an auditable instance lineage. [Spawn CLI](../repo/clawteam/cli/commands.py), lines 3130–3270.

The initial prompt contains name, ID, type, team, leader, workspace and task. It also tells the agent how to claim/update tasks, commit changes, report completion/costs, contact the leader and continue polling while idle. Those instructions make a native coding CLI coordination-aware, but are behavioral instructions rather than enforced guarantees of continued work. The process environment supplies the same identity information independently of the prose. [Prompt builder](../repo/clawteam/spawn/prompt.py), lines 27–108; [subprocess environment](../repo/clawteam/spawn/subprocess_backend.py), lines 45–69.

### Execution, tools and permissions

NativeCliAdapter translates launch details for clients rather than implementing a common coding tool engine. The external CLI decides how it edits files, uses tools and stores its conversation. ClawTeam runtime profiles can select different models/providers, so Wingman could standardize on Codex while retaining another CLI for a specialized team. Skills injected through the CLI path are client-specific. They are not a universal role skill registry. [Adapter](../repo/clawteam/spawn/adapters.py), lines 31–147; [profile application](../repo/clawteam/spawn/profiles.py), lines 86–142; [spawn skill injection](../repo/clawteam/cli/commands.py), lines 3288–3310.

Permissions are largely delegated to the underlying client. The default config sets `skip_permissions=True`, and native adapters convert that into client-specific flags. A Git worktree is branch/file separation, not a process sandbox or role-level permission boundary. Wingman would need explicit policy about which agents may deploy, access credentials, approve work or alter the organization's records; ClawTeam's `agent_type` alone does not enforce that separation. [Config](../repo/clawteam/config.py), lines 50–69; [adapter](../repo/clawteam/spawn/adapters.py).

### Concurrency and assignment

Concurrency means several actual operating-system processes, not several model calls inside a shared conversation. Optional workspaces create branches named `clawteam/{team}/{agent}` and record their base branch/repository/worktree path. Tasks carry explicit owners. Claims use both an OS-level advisory write lock and logical `locked_by`/`locked_at` state; unknown liveness does not automatically permit stealing another worker's claim. Dead-owner locks can be released. Dependency cycles are rejected, and completing a task removes it from dependent tasks' `blocked_by` lists. [Workspace manager](../repo/clawteam/workspace/manager.py), lines 65–176; [task store](../repo/clawteam/store/file.py), lines 54–75, 150–206, 241–268 and 316–375.

This protects task claims. It does not itself guarantee every dependency is respected by an agent or that two workers never edit the same files. The Git context layer detects overlapping work and provides teammate diffs/logs to inform agents. Contract execution uses round-robin assignment and wave barriers, not a semantic skill/capacity scheduler. Its task conversion uses previous wave numbers. The `SprintContract.depends_on` field is not used in that conversion. [Contract executor](../repo/clawteam/harness/contract_executor.py), lines 12–26 and 56–99; [contract schema](../repo/clawteam/harness/contracts.py), lines 25–38.

Specifically, setting a blocked task to `in_progress` acquires its claim but does not check that `blocked_by` is empty. Dependencies are recorded, displayed and automatically removed on predecessor completion, rather than enforced as an execution barrier. Likewise, the claim check applies when starting work; completion/pending updates clear claims without a comparable owner check. These are coordination safeguards for cooperating agents, not authorization boundaries. [Task update](../repo/clawteam/store/file.py), lines 150–206 and 241–251. The standard template seeds backend, frontend, QA and CI tasks immediately with no dependencies. The leader is instructed to establish the actual plan afterward. [Seed tasks](../repo/clawteam/templates/software-dev.toml), lines 110–128; [template task schema](../repo/clawteam/templates/__init__.py), lines 31–44.

### Persistence, resume and supervision

The persistent logical record includes team configuration, tasks, messages/events, plans and artifacts. Native session capture records a client/session ID and discovery metadata; client locators handle explicit session IDs, environment IDs or matching recently created native logs. This is more careful than blindly attributing the parent Codex thread to a child. The session-capture tests include a case proving that child discovery ignores a parent thread ID. These tests were inspected, not run. [Session capture](../repo/clawteam/spawn/session_capture.py); [session tests](../repo/tests/test_session_capture.py), lines 18–159.

Codex capture still has an important boundary. It scores recent logs by workspace, boosts logs containing prompt hints, and otherwise accepts the latest matching candidate; that fallback can be ambiguous when several agents share a CWD. New Codex sessions use asynchronous capture in a daemon thread, while the spawn command returns immediately. Persistence after a short-lived launcher exits is therefore not guaranteed by the discovery algorithm alone. The inspected child-ID test explicitly sets `async_capture=False`, so it verifies attribution using a synthetic log rather than the lifetime of this production capture thread. [Codex locator](../repo/clawteam/spawn/session_locators/codex.py), lines 29–78; [capture thread](../repo/clawteam/spawn/session_capture.py), lines 66–112 and 155–174; [test](../repo/tests/test_session_capture.py), lines 114–158. This is a source-level risk, not an observed session-loss incident.

Explicit `spawn --resume` can use the saved session ID. Automatic keepalive instead uses native continuation forms such as `codex resume --last` or `claude --continue`. The keepalive shell loops after a **clean** exit if the team still exists and the worker's inbox does not contain `shutdown_approved`. Thus the organization can remain active between batches, but completion of all tickets alone does not stop its processes. This is unlike Wingman's accepted-delivery pause until new work. The on-exit hook clears ClawTeam's saved session reference, so retention and later precise resume are weaker than the mere existence of SessionStore suggests. [Keepalive](../repo/clawteam/spawn/keepalive.py), lines 11–35 and 53–90; [exit/keepalive CLI](../repo/clawteam/cli/commands.py), lines 2943–2954 and 3007–3026.

LeaderWatcher is a concrete useful supervision mechanism. It polls team tasks/mail and local spawn health, computes a signature to avoid repeated identical alerts, and sends a heartbeat even without a change. Defaults are a 60-second check and 300-second heartbeat. It counts completed work by owner, names dead workers, flags blocked tasks, and recommends inspecting the board/inbox. Redis pub/sub can wake it sooner; state remains in files and Redis is an optional wakeup rather than the authoritative task database. An injection failure falls back to the leader's mailbox. [Leader watcher](../repo/clawteam/team/leader_watcher.py), lines 39–61, 87–158 and 200–277.

This is a good primitive for ProjectMaster, but it only brings evidence to a leader. It does not independently research a blocker, route a human decision across a portfolio, or prove that a live process is making useful progress. Its change signature emphasizes completed/blocked tasks, unread-message count and dead agents; current/pending changes alone are not equivalent executive reporting.

Scheduling also requires an explicit controller lifetime. `team watch` constructs and runs LeaderWatcher as a blocking command. Neither ordinary `spawn` nor template `launch` automatically starts that watcher. Inbox runtime routing is another independently running watcher, and agent polling is otherwise a prompt instruction. Wingman would need to supervise these controllers themselves, reconnect them to the correct host and preserve their operating state across machine restarts. [Team watcher CLI](../repo/clawteam/cli/commands.py), lines 1581–1625; [template launch](../repo/clawteam/cli/commands.py), lines 4125–4215.

### Interruption, failure, retry and recovery

Shutdown is a **message protocol**: request, approve/reject and idle notifications. Sending approval does not itself terminate a process. Actual stopping is separate and best-effort: tmux `kill-window`, subprocess `SIGTERM`, or deletion of a `wsh` block, followed by liveness polling. The native process may also be controlled interactively in its terminal. [Lifecycle manager](../repo/clawteam/team/lifecycle.py), lines 19–80; [registry stop](../repo/clawteam/spawn/registry.py), lines 121–168.

There is a further mismatch between the cooperative shutdown protocol and keepalive: `approve_shutdown` sends `shutdown_approved` to the requester, while `should-keepalive` looks for that message in the exiting worker's own inbox. The standard leader-requests/worker-approves exchange therefore does not itself establish the worker's keepalive stop condition. A worker that has consumed relevant mail also leaves no durable shutdown flag for the check. This makes accepted-delivery cessation a policy and state-machine change, not just a new shutdown prompt. [Approval destination](../repo/clawteam/team/lifecycle.py), lines 34–46; [keepalive condition](../repo/clawteam/cli/commands.py), lines 3007–3026; [protocol test](../repo/tests/test_lifecycle.py), lines 38–46.

Single-worker `spawn` attempts rollback on a returned backend error. Template launch is weaker: it creates all membership/tasks first, appends every backend result and emits `status=launched` without rejecting `Error` results or undoing earlier launches. A partial team launch needs reconciliation by a caller. [Single spawn rollback](../repo/clawteam/cli/commands.py), lines 3313–3325; [template result handling](../repo/clawteam/cli/commands.py), lines 4176–4198.

The post-exit hook records an exit journal entry, clears the session reference, resets that owner's in-progress tasks to pending and sends the leader a report. TaskWaiter independently detects dead agents and requeues their in-progress work. This recovers availability of assignments. It does not roll back partially written code or automatically find an appropriate replacement specialist. [Exit hook](../repo/clawteam/cli/commands.py), lines 2928–3004; [TaskWaiter](../repo/clawteam/team/waiter.py), lines 168–191.

Runtime message routing has a separate retry mechanism: an envelope records source/target/priority/evidence, and policy throttles repeated updates, aggregates pending messages, deduplicates and schedules failed injection retries. It is important not to confuse a successfully queued notification with successful implementation of the task it describes. [Router](../repo/clawteam/team/router.py), lines 31–112; [routing policy](../repo/clawteam/team/routing_policy.py), lines 93–256; [routing tests](../repo/tests/test_runtime_routing.py).

The optional Ralph-loop plugin checks incomplete tasks on WorkerExit, caps iterations at five by default, builds role-scoped recovery context and calls respawn. Its iteration counter is in memory. The default conductor response strategy is `NoRespawn`. The conductor reads its run-specific exit journal and would call that strategy for new entries, while RalphLoop subscribes to in-process WorkerExit events. Those are different paths. There is also a concrete journal-path mismatch in the default wiring: the conductor constructs FileExitJournal with a harness ID, while `lifecycle on-exit` constructs it with only the team name. The journal class uses different paths for those arguments. This snapshot does not establish reliable restart across real process exits. An adoption would need to reconcile these paths and exercise an integration test. [Plugin](../repo/clawteam/plugins/ralph_loop_plugin.py), lines 30–79; [conductor](../repo/clawteam/harness/conductor.py), lines 32–39, 63–67 and 106–117; [journal paths](../repo/clawteam/harness/exit_journal.py), lines 20–24; [exit writer](../repo/clawteam/cli/commands.py), lines 2943–2947.

### Completion, acceptance and retirement

In the ordinary team path, a worker reports completion by setting ticket status and messaging the leader. The software-dev tech lead is prompted to review and merge. The tracker does not itself prove tests passed or acceptance criteria were satisfied. Test commands and `verified` fields are data fields until a responsible agent/system evaluates them.

The harness promises a more structured route, but its precise mechanics matter:

- A fresh orchestrator registers `spec.md` presence and human approval gates on **leaving plan**, and an all-team-tasks-complete gate on **leaving verify**. ArtifactRequiredGate checks the registration map. It does not validate the referenced file's existence/content. HumanApprovalGate likewise checks registration. [Orchestrator](../repo/clawteam/harness/orchestrator.py), lines 55–61; [gates](../repo/clawteam/harness/phases.py), lines 64–103.
- There is no default execute-phase completion gate. The conductor can spawn executors, create contract tasks, then move to verification on the next poll. It can reach ship when task statuses are completed without requiring an evaluator report or verified success criteria. Ship has no default agent and the conductor declares completion upon entering the final phase. [Phase-role map](../repo/clawteam/harness/phases.py), lines 30–36; [conductor](../repo/clawteam/harness/conductor.py), lines 119–139.
- Persisted `PhaseState` does not serialize gates. `PhaseRunner.load()` creates a runner with an empty gate map; `HarnessOrchestrator.load()` uses `__new__` and does not re-register the defaults. Commands that load an existing run therefore lack those gate checks unless another caller restores them. This is a source-level finding, not a reproduced runtime incident. [Runner load](../repo/clawteam/harness/phases.py), lines 109–115 and 177–192; [orchestrator load](../repo/clawteam/harness/orchestrator.py), lines 120–135.
- Conversely, the live conductor retains its original gated orchestrator and never reloads `state.json` while polling. The separate `harness approve` command loads another object, writes an approval file and updates that object's registration map. That does not update the conductor's in-memory `state.artifacts`. `ArtifactStore.write_spec()` similarly writes a file without registering it in PhaseState. These distinct file-store and registration paths need synchronization; merely writing a spec and running the advertised approval command does not establish that a running conductor can leave plan. [Conductor loop](../repo/clawteam/harness/conductor.py), lines 97–149; [approval CLI](../repo/clawteam/cli/commands.py), lines 4487–4495; [artifact write](../repo/clawteam/harness/artifacts.py), lines 22–32 and 65–67; [registration](../repo/clawteam/harness/orchestrator.py), lines 94–97.
- `Phase` and `current_phase` are strings, but `harness start` and successful `harness advance` dereference `.value` while building their output. Those paths save the run/transition first, then encounter an incompatible attribute access. This is a concrete source inconsistency, not a claim that the commands were exercised. It also means a CLI error can follow a persisted state mutation. [String phases](../repo/clawteam/harness/phases.py), lines 19–28 and 39–46; [start output](../repo/clawteam/cli/commands.py), lines 4370–4382; [advance output](../repo/clawteam/cli/commands.py), lines 4424–4433.
- `abort()` appends an aborted-history record and saves it. It does not set a terminal state or stop agent processes. [Abort](../repo/clawteam/harness/orchestrator.py), lines 99–105.

There is no discuss-completion gate either: a new conductor starts a discuss planner, immediately advances to plan in its first loop, and spawns another planner. The phase labels therefore should not be read as proof of completed discovery. These findings lower the strength of F07/F08/F12/F22. Wingman should retain the contract idea but require a coherent persisted state machine, completed execution before verification, evaluator evidence, explicit accepted delivery and actual worker shutdown. The checked code demonstrates useful primitives and integration work still required, not an exercised accepted-product journey.

Cleanup can remove workspaces/branches and team/task/cost/session/plan records. That is deletion rather than durable organizational retirement/history. Workspace creation for the same agent also removes stale worktree/branch state before recreation, so explicit conversation resume should not be assumed to imply preservation of the same working branch. Wingman needs a separate archive and instance-history policy. [Workspace lifecycle](../repo/clawteam/workspace/manager.py), lines 65–90 and 199–228; [team cleanup](../repo/clawteam/team/manager.py), lines 192–221.

## Coordination: tracing a full-stack request

Consider a human starting the bundled `software-dev` template with a product goal. This is an implementation trace of supported behavior, not an executed demonstration.

1. `launch` parses the template, substitutes the goal/team/member variables, creates `tech-lead`, `backend-dev`, `frontend-dev`, `qa-engineer` and `devops`, and seeds initial tickets. It launches the leader first and then workers. Creating a team and launching members are separate operations. [Launch implementation](../repo/clawteam/cli/commands.py), lines 4034–4190; [template](../repo/clawteam/templates/software-dev.toml).
2. The lead receives instructions to break the work down, add dependencies, coordinate backend/frontend/QA, monitor and merge. These are prompts for an actual independently running leader. There is no separate deterministic planner that guarantees a sensible breakdown.
3. A backend worker reads its assigned task, changes status to in-progress and receives a logical claim lock. It edits in its native CLI/workspace. Completion clears the claim and unlocks dependent tasks; Git commit-before-completion is a prompt instruction. [Store](../repo/clawteam/store/file.py), lines 150–206 and 362–375; [prompt](../repo/clawteam/spawn/prompt.py), lines 82–105.
4. An API integration question can go directly from backend to frontend through an addressed inbox, or to the tech lead. Mailbox delivery serializes a typed message and writes an independent permanent event; receiving the inbox does not erase the event history shown by the board. Broadcast fans out across recipients. [Mailbox](../repo/clawteam/team/mailbox.py), lines 72–192 and 216–242.
5. If an inbox watcher is running in runtime mode, messages can be normalized and injected into the target's live terminal. Otherwise agents explicitly poll their inboxes. The routing policy prevents every small update from becoming an immediate model interruption, while failed dispatches remain pending for retry. [Watcher](../repo/clawteam/team/watcher.py); [router](../repo/clawteam/team/router.py), lines 70–112.
6. The leader watcher can wake the lead about a blocked task or dead worker. If a worker dies, on-exit/TaskWaiter requeues in-progress tasks. The lead must decide what to do with the recovered task. This is not a guaranteed automatic reassignment pipeline.
7. The QA role runs tests through its CLI and reports bugs/verification through tickets/mail. The tech lead is prompted to integrate via workspace merge. The board shows the resulting task/message state. A human can attach to native terminals. There is no automatic Butler delivery briefing, formal product acceptance or global development stop.

The key design is **tickets and conversation together**. Tickets describe ownership/dependencies; inboxes carry negotiation, findings and escalation. This maps well to Wingman's ProjectTracker plus agent discussion, while room structure and human-facing semantics still need to be layered on.

Plan approval is a separate, useful correlated exchange: `submit_plan` persists team-scoped content and sends the lead a `plan_approval_request` containing the plan ID, path, summary and body; approval/rejection sends that same ID back with feedback. It is agent-to-leader collaboration, not a multi-round human product-discovery conversation or an enforced permission to execute. [Plan manager](../repo/clawteam/team/plan.py), lines 109–161.

Message durability has a defined boundary. File transport atomically renames a message into a claimed state, holds an advisory lock, deletes it on acknowledgment, and quarantines malformed payloads with error metadata. MailboxManager acknowledges after schema parsing, before the receiving agent has interpreted or acted on it; event history remains as a separate record. This protects concurrent readers and preserves evidence but is not an end-to-end “agent acted on the request” acknowledgment. P2P successful sends additionally bypass the durable recipient file path, using ZeroMQ queues with file fallback on an observed send failure. [File claims/acknowledgment](../repo/clawteam/transport/file.py), lines 112–190 and 192–224; [schema acknowledgment](../repo/clawteam/team/mailbox.py), lines 204–227; [P2P send](../repo/clawteam/transport/p2p.py), lines 207–219.

## Major capabilities beyond Wingman's stated scope

### Heterogeneous agent runtime and provider operations

Wingman's baseline explicitly centers Codex agents. ClawTeam can coordinate multiple native CLI families while profiles supply model/provider/environment selection. This enables mixed-vendor teams and independent model specialization without replacing the coordination protocol. The tradeoff is uneven lifecycle/tool visibility and client-specific resume, prompt and permission behavior. Wingman would need a capability contract per runtime rather than assuming uniform Codex semantics. [Profiles](../repo/clawteam/spawn/profiles.py), lines 86–183; [adapters](../repo/clawteam/spawn/adapters.py).

### Git collaboration as an explicit coordination subsystem

Isolated worktrees, checkpoints, merges, file ownership/overlap detection and teammate change context are a substantial engineering capability, not a cosmetic terminal feature. The context layer derives evidence from branch diffs and logs, allowing a worker to learn what peers changed before touching an interface. Wingman specifies collaboration but not this Git-level integration mechanism. Borrowing it would reduce accidental cross-worker interference, while still requiring conflict ownership, test gates and host-aware repository placement. [Workspace manager](../repo/clawteam/workspace/manager.py); [context layer](../repo/clawteam/workspace/context.py), lines 58–180; [conflict detection](../repo/clawteam/workspace/conflicts.py).

### Team state snapshots and restoration

SnapshotManager bundles configuration, tickets, events, session references, costs and pending inboxes into a restorable JSON state. Restore replaces the corresponding current directories rather than overlaying old records. This supports recovery/checkpointing of the coordination environment independently of running models. The bundle excludes source branches, native conversations, workspace/spawn registries, plans and harness artifacts, so it is not a whole-product or live-process checkpoint. Wingman's persistent knowledge requirement does not specify this recovery product; adopting it would require an expanded backup boundary and a policy for stopping writers during a coherent capture/restore. [Snapshot capture](../repo/clawteam/team/snapshot.py), lines 123–183; [restore](../repo/clawteam/team/snapshot.py), lines 204–285.

### Reusable orchestration across non-software domains

Research-paper, hedge-fund, code-review and strategy-room templates demonstrate that the team protocol is domain-independent. This is broader than Wingman's personal software-development organization. The implemented product is configurable team launching and job prompts, **not** evidence that autonomous trading, scientific validation or research breakthroughs are guaranteed. Those domain claims need their own tools, data and acceptance systems. [Bundled templates](../repo/clawteam/templates); [template loader](../repo/clawteam/templates/__init__.py).

### Agent-facing coordination through both CLI and MCP

Team/task/mail/plan operations and workspace context reads are exposed as typed MCP tools in addition to shell commands, so an MCP-capable host can use the coordination substrate without scraping terminal output. That is a meaningful integration product. Spawn/stop and workspace creation/merge remain outside this registered MCP inventory. It does not itself provide Wingman's human chat application or a networked, authenticated organizational control plane. [MCP registration](../repo/clawteam/mcp/server.py), lines 13–33; [tool set](../repo/clawteam/mcp/tools/__init__.py), lines 28–55.

### Event hooks and pluggable control policies

Hooks can invoke a shell command or Python callable with typed lifecycle/task/message event data; plugins are discoverable through package entry points, configured modules and local manifests. This enables custom auditing, notifications and orchestration behavior without rewriting the mailbox/store. The in-process event bus calls handlers by priority and supports a caller-checked veto for suitable before-events. The scope is important: the bus is a process-local singleton, handlers' exceptions are swallowed, and some events named “Before” are emitted asynchronously after storage changes. For example `BeforeTaskCreate` is emitted after task persistence, so it cannot serve as a reliable task-creation authorization gate. Wingman could reuse these hooks for integration but should use durable cross-process events and explicit transaction boundaries for decisions that must be enforced. [Hook registration/execution](../repo/clawteam/events/hooks.py), lines 35–62 and 77–101; [plugin loading](../repo/clawteam/plugins/manager.py), lines 21–69 and 91–150; [bus](../repo/clawteam/events/bus.py), lines 86–107; [task event position](../repo/clawteam/store/file.py), lines 99–121.

### Team cost accounting and advisory budgets

Agent-reported cost events retain model/provider/token/cost information and support per-agent/team aggregation, a rolling summary cache and board display. That adds an explicit operational accounting model to Wingman's general usage-visibility requirement. Budget handling in `cost report` prints a warning when the reported total exceeds the team budget. It does not stop workers or reject further spawning. Worker reporting is explicitly prompted rather than derived from every native client invocation. Wingman can reuse the ledger but would need trustworthy metering and enforced budget actions if spending limits should control execution. [Cost schema/cache](../repo/clawteam/team/costs.py), lines 21–73 and 163–219; [report and warning](../repo/clawteam/cli/commands.py), lines 2333–2376; [worker instructions](../repo/clawteam/spawn/prompt.py), line 95.

## Distinctive mechanisms and innovation

These are grounded design observations, not claims of first invention or uniqueness across the industry.

**A framework-independent coordination protocol for agents themselves.** ClawTeam avoids making every worker part of one custom inference framework. Separate native coding tools share a small language of tickets, inboxes, plans and lifecycle messages. This lets a capable leader construct and operate a team dynamically through the same CLI a human can inspect. The price is reliance on agents following the protocol and native client differences. The actual mechanism is in [spawn prompt construction](../repo/clawteam/spawn/prompt.py), lines 82–105, [message/task models](../repo/clawteam/team/models.py), lines 90–142, and [native adaptation](../repo/clawteam/spawn/adapters.py), lines 31–146, rather than a shared inference framework.

**Durable delivery separated from live attention routing.** Inbox/event storage records the message; RuntimeRouter decides when/how to get it into a live agent. Pending envelopes, throttling, priority, deduplication and aggregate notifications keep repeated updates from flooding active coding sessions. The leader watcher adds state-change and heartbeat attention. This separation is valuable to Wingman: an organizational conversation should survive even when its target agent is offline, while delivery urgency can change independently. Limits include backend-dependent injection and the need to run watchers. [Router/policy](../repo/clawteam/team/router.py); [policy](../repo/clawteam/team/routing_policy.py), lines 93–256.

The implementation is deliberately simpler than a general priority scheduler: same-source/target throttling is checked before any priority-specific decision, while priority is retained/maximized in accumulated state. An urgent management decision therefore needs a deliberately designed bypass/acknowledgment policy if Wingman requires immediate handling. Pending-envelope deduplication also does not prove exactly-once model action. [Throttle decision](../repo/clawteam/team/routing_policy.py), lines 100–156; [pending aggregation](../repo/clawteam/team/routing_policy.py), lines 315–355.

**Git-derived collaboration context.** Rather than relying only on agent self-reports, ClawTeam can show branch-level work, overlapping files and teammate commits. This gives coordination some externally observable evidence. It is particularly relevant to Wingman's TestMaster/TechMaster relationship: branch evidence can supplement conversational status. It still does not establish functional correctness or maintain a semantic executive timeline. [Context](../repo/clawteam/workspace/context.py); [prompt context hook](../repo/clawteam/spawn/prompt.py), lines 10–24 and 73–80.

**Artifacts-to-contracts-to-wave tasks.** Specification and sprint contracts can become actual shared tasks with owners and wave dependencies. This is a concrete bridge between product intent and execution state, rather than a plan that only exists in a model transcript. Its implementation currently uses simple round-robin assignment, coarse all-earlier-wave barriers and incomplete acceptance gating. The valuable concept is the bridge. The code does not yet justify trusting fully autonomous accepted delivery. [Contract executor](../repo/clawteam/harness/contract_executor.py), lines 40–99.

**Transport-level support for remote peers without pretending local PIDs are global.** P2P peer records include host, port, heartbeat and lease. Remote hosts use lease freshness, whereas local peers may be checked by PID. This is a concrete distributed-systems distinction. It supplies messaging groundwork for a Mac/Linux organization, but peer discovery and fallback still need shared file visibility, and task/worker lifecycle does not become distributed merely because messages can cross TCP. [P2P](../repo/clawteam/transport/p2p.py), lines 79–179.

## Practical adoption for Wingman

Useful library or service mechanisms include:

- Logical team membership and independent Codex execution.
- Task JSON with ownership, priorities, and blockers.
- Direct/broadcast mail and persistent event history.
- Leader heartbeat and checker.
- Git workspace/context tools, runtime notification envelopes, and MCP integration.

These mechanisms support specialist execution and team coordination.

Adapt these areas before using ClawTeam for Wingman's product journey:

- Separate durable role profiles from runtime/provider profiles.
- Give workers stable organization IDs and replacement history.
- Map teams to product records and include scope/specification/task references in messages.
- Preserve native session and workspace continuity.
- Put process control behind host-aware executors.
- Add durable worker archives and restart-safe supervision.
- Reconcile phase strings, stored gates, active approvals, and lifecycle journals.
- Enforce implementation/verification order and accepted-delivery shutdown.

**Still a Wingman build:** Telegram Butler; cross-project ProjectMaster registry/intake; separate ongoing ProductMaster and TechMaster conversations; iterative human clarification linked to projects; management and project rooms with explicit membership/escalation; executive agent briefings and per-agent outcome timelines. The connected detailed coding workspace; coherent web/mobile control across both hosts. A dashboard facade over the existing team board would not by itself supply those organizational behaviors.

The most promising use is to borrow or wrap the coordination substrate while keeping Wingman's product organization explicit. Replacing Wingman wholesale with the software-dev template would collapse product discovery, portfolio management and human representation into one tech-lead prompt.
