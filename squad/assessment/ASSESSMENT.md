## Fit verdict

**A substantial candidate for Wingman's project-team execution and durable knowledge layer, but not a replacement for the continuing organization.** Squad contains real independent Copilot sessions, configurable specialist charters, dynamic roster loading, issue/PR coordination, communications adapters, periodic autonomous work polling, remote terminal control, model/cost policy, and an implemented opt-in distributed work-claim mechanism. These are useful working components, beyond a collection of agent personas.

Its organizing unit is an initialized project `.squad/`, not a portfolio with Butler, ProjectMaster and separate product/technical leadership for every product. The CLI explicitly rejects the former global-team mode ([cli-entry.ts](../repo/packages/squad-cli/src/cli-entry.ts), lines 139–142). Product Manager and Lead/Architect role content can seed Wingman roles, but that content does not implement product intake, iterative clarification through Telegram, product acceptance, or management rooms. Its terminal agent panel, mobile session selector and OTel dashboards provide execution visibility. They do not provide the connected agent directory, executive briefings, task-linked timelines and portfolio workspace described by Wingman.

There are significant differences between advertised/configurable surface and operational wiring in this revision: the wave dependency dispatcher receives no issue body and consequently executes no subtasks. The generic local scheduler returns success stubs for Copilot/workflow tasks. The experimental conversation backend starts with an empty harness registry. The report credits running-code mechanisms at their actual boundary rather than combining these components into an assumed complete system.

## Architecture and execution model

There are several execution surfaces, and their behavior must be distinguished.

**Interactive SDK shell.** The default CLI entry calls `runShell` ([cli-entry.ts](../repo/packages/squad-cli/src/cli-entry.ts), lines 333–337). The Ink shell resolves the current project, discovers agents, creates a Copilot SDK coordinator session, and keeps a map of specialist sessions. A named specialist gets its own `client.createSession`, system charter and working directory. Sessions are reused during that shell process. The adapter actually imports `CopilotClient` and `RuntimeConnection` from `@github/copilot-sdk`, adapts SDK `send`/`sendAndWait`, and maps events rather than implementing its own model engine ([adapter/client.ts](../repo/packages/squad-sdk/src/adapter/client.ts), lines 10, 168–250, 442–459, 602–621). Independent sessions are real independent execution contexts. A roster entry by itself remains a definition.

The shell coordinator is a model prompted with `team.md` and `routing.md`. It emits `DIRECT:`, `ROUTE:` or `MULTI:` text, which the shell parses and dispatches. This is materially simpler than the separately exported `SquadCoordinator`, which compiles rule routing, chooses direct/single/multi/fallback strategy and calls injected fan-out dependencies ([shell/coordinator.ts](../repo/packages/squad-cli/src/cli/shell/coordinator.ts), lines 232–357; [SDK coordinator](../repo/packages/squad-sdk/src/coordinator/coordinator.ts), lines 106–194). The shell is not evidence that every SDK policy module is automatically active.

**Native host projection.** Init/upgrade can generate coordinator and MCP configuration for multiple coding clients. For Codex it writes a custom `squad` agent TOML, a short `AGENTS.md` discovery pointer, and `.codex/config.toml` MCP configuration ([adapters.ts](../repo/packages/squad-sdk/src/client/adapters/adapters.ts), lines 256–289). The Codex-specific coordinator explicitly instructs the host to spawn one worker per specialist, inline charters, and wait for results ([coordinator adapter](../repo/packages/squad-sdk/src/client/adapters/coordinator.ts), around line 183). This supports reusing Squad organization in Codex, but host permissions, subagent implementation and actual session continuity remain the host's responsibility. It is not a separately implemented universal Codex daemon.

**Ralph watch.** `squad watch` is an independently running local polling process. It reads platform work items, filters machine requirements, labels untriaged issues using roster/routing/module ownership, checks PR review and CI state, then invokes opt-in capabilities in phases. The execute capability starts a CLI process with all won/eligible issues and asks Ralph to delegate; Fleet dispatch sends a `/fleet` prompt for parallel analysis tracks. The watcher itself does not unconditionally create one process per specialist ([watch/index.ts](../repo/packages/squad-cli/src/cli/commands/watch/index.ts), lines 323–407, 1127–1179; [execute.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/execute.ts), lines 309–378; [fleet-dispatch.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/fleet-dispatch.ts), lines 49–125). It can operate without the terminal shell being open, as long as its process remains running.

**State and experimental conversation backend.** Team knowledge has a `SquadState` facade over agents/config/decisions/routing/team/skills/templates/log collections ([squad-state.ts](../repo/packages/squad-sdk/src/state/squad-state.ts), lines 24–45). Storage providers include filesystem, in-memory and SQLite; SQLite is explicitly single-process and loads the database into memory ([sqlite-storage-provider.ts](../repo/packages/squad-sdk/src/storage/sqlite-storage-provider.ts), lines 14–43). Separately, Git-native state backends expose read/write/append/delete/create-if-absent for local/external/orphan/two-layer modes ([state-backend.ts](../repo/packages/squad-sdk/src/state-backend.ts), lines 123–147). These are not interchangeable guarantees of multi-host transactional database access.

The experimental 2.0 `SquadBackend` models conversations, run/turn/task states, cursor event logs, approvals and harness adapters. `LocalSquadBackend` persists admission and cancellation/approval deliveries; HTTP client code speaks to an external DurableSquad service. The local backend defaults to an empty `DefaultHarnessRegistry`, so admission without a harness can stay queued. It is not automatic coding execution ([local-backend.ts](../repo/packages/squad-sdk/src/backend/local-backend.ts), lines 281–299, 326–420; [harness-registry.ts](../repo/packages/squad-sdk/src/backend/harness-registry.ts), lines 27–46). The HTTP server implementation is external to this checkout; only the client can be assessed here ([durable-http-backend.ts](../repo/packages/squad-sdk/src/backend/durable-http-backend.ts), lines 21–129).

**Remote control.** `squad start` runs Copilot in a PTY, mirrors output over a WebSocket bridge and accepts terminal/mobile keyboard input. The PWA's dashboard lists remote sessions, not products or executive agent briefings ([start.ts](../repo/packages/squad-cli/src/cli/commands/start.ts), lines 58–92, 153–234; [remote-ui/app.js](../repo/packages/squad-cli/src/remote-ui/app.js), lines 24–84, 87–137). Remote viewing of a process does not by itself schedule execution on another host.

## Agent definition and lifecycle

### Definitions, creation and identity

A Squad member is primarily a named charter plus project history and roster metadata. Configuration has arbitrary `name`, `role`, `displayName`, `charter`, model/reasoning/context overrides, tools and active/inactive/retired status. The charter compiler validates/parses identity, responsibilities, non-responsibilities and collaboration; its Examples section is explicitly Markdown rather than executable tests ([charter-compiler.ts](../repo/packages/squad-sdk/src/agents/charter-compiler.ts), lines 32–82, 88–119). These definitions can describe serious specialist work, but describing a role does not start a process.

Onboarding writes the member directory, charter and initial history. Built-in templates include lead, developer, tester and scribe. A generic fallback permits arbitrary responsibilities ([onboarding.ts](../repo/packages/squad-sdk/src/agents/onboarding.ts), lines 60–150, 262–319, 347 onward). Initial interactive casting produces/asks confirmation of a team proposal before persisting roster files, then redispatches the request. The shell has explicit cancellation/error handling for this process ([shell/index.ts](../repo/packages/squad-cli/src/cli/shell/index.ts), lines 969–1110, 1190–1231). Theme-based casting gives memorable names and a registry/history. It is identity selection, not independent execution.

At execution time a Copilot session ID identifies the actual session. Shell's `agentSessions` map is keyed by name, so direct requests to a member reuse that session within the process. SDK `AgentLifecycleManager` instead stores session-ID handles and returns an object with status, timestamps, send and destroy. Several handles can be based on the same charter. Wingman would still need stable organization-wide instance IDs tying a particular worker to its project/host/tickets; cast names alone are insufficient.

### Launch, tools and routing

`dispatchToAgent` loads the charter, builds the system prompt, registers missing members, and calls real `createSession` with streaming and project working directory ([shell/index.ts](../repo/packages/squad-cli/src/cli/shell/index.ts), lines 489–515). The shell uses `approveAllPermissions` for coordinator and member sessions. This is an actual permission choice, not a human approval workflow. Separately, SDK hooks implement allowed write paths, blocked shell patterns, ask-user limits, PII scrubbing and reviewer lockout ([hooks/index.ts](../repo/packages/squad-sdk/src/hooks/index.ts), lines 56–111, 152–211, 315–375). They are useful configurable policy machinery, but the inspected shell session creation does not wire this entire hook pipeline automatically. They also rely on tool names/path/pattern inspection, not an OS-level sandbox.

The shell prompt route format is text parsed with regular expressions; unknown/unparseable output becomes a direct answer. Native named-agent entry bypasses coordinator selection, while multi-mentions can invoke several agents concurrently. The SDK coordinator is a separate rule-based API with dependencies supplied by the caller. Its fan-out uses `Promise.allSettled` and returns spawn outcomes. A successful spawn is not equivalent to the task passing tests ([fan-out.ts](../repo/packages/squad-sdk/src/coordinator/fan-out.ts), lines 38–75, 97–118). A further spawn-backend abstraction supports host task tools or session creation through callbacks; host-specific execution must be present for those paths ([spawn-backend.ts](../repo/packages/squad-sdk/src/coordinator/spawn-backend.ts), lines 14–75).

### Concurrency, persistence and resumption

Multi-agent shell dispatch is real concurrency, with per-result failure reporting for explicitly mentioned agents. All sessions use the same `teamRoot` working directory. Worktree isolation exists as host guidance, not an unconditional part of this launch path; Wingman should not assume concurrent edits are isolated. Session pool APIs offer capacity/health management to SDK consumers, but the shell map and SDK lifecycle/pool are distinct layers ([client/index.ts](../repo/packages/squad-sdk/src/client/index.ts), lines 82–109, 140–164).

Durable charter/history/decisions/skills are the strongest continuity layer. Shell session JSON stores ID, timestamps and messages. The latest session is offered within a 24-hour recent window ([session-store.ts](../repo/packages/squad-cli/src/cli/shell/session-store.ts), lines 15–36). Loading that envelope does not restore each previous member's SDK session: the dispatch path creates one when the in-process map is empty. SDK consumers can explicitly call `resumeSession`, but Wingman would need to persist and reconnect the correct per-instance session IDs. The experimental backend does provide a richer durable transcript/run/event abstraction; its presence should not be conflated with shell restart behavior.

`AgentLifecycleManager`'s introductory comments promise history persistence, but its concrete handle `destroy()` only changes status, closes the session, and invokes its removal callback ([agents/lifecycle.ts](../repo/packages/squad-sdk/src/agents/lifecycle.ts), lines 692–704). No additional automatic history write occurs in that method. Agent-authored history and other state writers must do that work. Its periodic idle checker only marks active handles idle. It does not wake them to supervise or automatically retire them (lines 482–493).

### Scheduling and autonomous wake

Ralph watch performs a real immediate round followed by `setInterval`, prevents overlapping rounds, honors duration/round bounds and stop signals, and executes capability preflight/phase hooks. Its PR/issue loop is useful ongoing operational supervision. `RalphMonitor` separately tracks event-driven activity and stale thresholds, but a stale status is detection rather than a repair conversation.

The generic scheduler has manifest/schema validation, cron/interval/startup/event types, state and retry/backoff, and real local script/webhook execution. However, `LocalPollingProvider` explicitly returns successful stub messages for `workflow` and `copilot` task types ([scheduler.ts](../repo/packages/squad-sdk/src/runtime/scheduler.ts), lines 527–572, 650–659). Searching CLI/SDK call sites found scheduler use in `schedule` commands, not actual evaluation of `schedule.json` inside the inspected watch loop. Its comments about watch integration are therefore insufficient to credit automatic arbitrary scheduled agent wake. Ralph's own polling is independently implemented and does work at the source level.

### Cancellation, failure, recovery, completion and cleanup

During shell work, Ctrl+C aborts active init/coordinator/all member SDK sessions and clears stream state. This is global cancellation rather than a rich per-agent stop UI. Empty responses go through ghost-response retry; other dispatch failures evict the dead member session so a subsequent request creates a new one ([shell/index.ts](../repo/packages/squad-cli/src/cli/shell/index.ts), lines 123–153, 620–650, 929–960). This retries transport/empty-response problems, not an automatic product-level recovery policy.

Watch's subprocess runner tracks timeout versus caller abort and kills the process tree, waiting for termination before resolving ([agent-spawn.ts](../repo/packages/squad-cli/src/cli/commands/watch/agent-spawn.ts), lines 359–403). Watch persists circuit-breaker state and uses cooldown after rate-limit failures; failed scans skip execution rather than being reported as clear boards. Claims renew while work is running and abort their passed signal if fencing/expiry means ownership is lost. Release runs in `finally`, including failure/cancellation outcomes ([claims.ts](../repo/packages/squad-cli/src/cli/commands/watch/claims.ts), lines 299–495). These are concrete recovery controls, but do not transactionally undo external side effects already made by a worker.

The conversation backend distinguishes queued/running/awaiting-approval/completed/failed/cancelled. It persists outstanding harness approval/cancel delivery and retries after missing acknowledgments ([local-backend.ts](../repo/packages/squad-sdk/src/backend/local-backend.ts), lines 677–710). That is a stronger control-state guarantee than a console status label; real execution still requires a registered adapter. A model returning, a child exiting zero, a backend completion event and a product being accepted are different events. No code was found that establishes Wingman's integrated acceptance and stops all project development until the next human request.

Retirement exists as agent configuration status; process cleanup consists of closing SDK sessions, shutting down client pools/watch timers, subprocess/PID cleanup and state archival routines. History archival has real integrity checks: verify a git-tracked destination, append and verify before trimming the source ([archival.ts](../repo/packages/squad-sdk/src/state/io/archival.ts), lines 1–24, 73–110). There is no single organization-wide retirement workflow detaching tasks/rooms/hosts and preserving a browsable agent archive.

## Coordination mechanics and request trace

Coordination mixes deterministic operations and model instructions. Durable team/decision/skill/history files are shared knowledge. GitHub/ADO issues hold work state; labels indicate specialist responsibility and blocked conditions. The communications interface can post an update and poll replies, with GitHub Discussions, ADO, Teams Graph or file-log implementations. These are exported SDK interfaces: the independent source audit found no built-in shell/watch caller of `createCommunicationAdapter`, `postUpdate` or `pollForReplies`. Their presence therefore does not establish an automatically connected room or reply loop in the shipped shell/watch path (see [QA18](../../generic/assessments/_audits/qa18.md)). The file adapter returns all text after a marker as one human reply with a new timestamp. It does not use `since` to separate individual replies. This limits its use as a chat protocol ([comms-file-log.ts](../repo/packages/squad-sdk/src/platform/comms-file-log.ts), lines 62–83). There are no typed room participants or guaranteed peer-agent delivery semantics.

A representative, source-traced request is an existing `squad`-labelled issue such as “Fix login redirect,” available to two independently running watch processes. This is a code-path reconstruction, not a claim that a live issue was executed during assessment.

1. **Intake and ownership hint:** watch `runCheck` obtains up to 20 open `squad` issues, filters `needs:*` against machine capabilities, parses the roster/routing/module ownership and adds the selected member label ([watch/index.ts](../repo/packages/squad-cli/src/cli/commands/watch/index.ts), lines 335–380). This labels an existing issue. It does not create a new product or research the request.
2. **Execution selection:** opt-in `ExecuteCapability` separately lists up to 50 issues, excludes human-assigned/blocked work and issues already dispatched this round, then attempts work claims ([execute.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/execute.ts), lines 317–369). The issue-body field is not populated in this normalization, so the prompt instructs the agent to read details through platform tools.
3. **Cross-host exclusion:** if `git-ref` is configured, each watcher contends on a ref derived from the normalized platform/repo/issue key. A commit stores holder machine/instance, epoch and lease times. `git push --force-with-lease=<ref>:<expected>` makes the shared remote decide the winner. A loser skips rather than merely trusting labels ([claims-git.ts](../repo/packages/squad-sdk/src/ralph/claims-git.ts), lines 1–20, 284–315, 586–605). With default `none` there is no such cross-executor exclusion.
4. **Launch:** the watcher passes only won issues to one Ralph invocation, optionally prefixes Ralph's charter and includes the claimed-work contract. It requests branches, PRs and progress, instructing the model to spawn specialists in parallel. This delegation is model/host behavior rather than an explicit watcher-created process for every issue ([execute.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/execute.ts), lines 126–178, 210–250, 371–378).
5. **Liveness and human boundary:** claims renew periodically; loss of ownership aborts the process tree. A blocked issue is meant to receive a comment and be left for later action. The external tracker/human can respond; no Butler routes the question through Telegram. Watch's blocked-label skip and the model's comment instruction are different mechanisms.
6. **Result:** child success/failure is reported as dispatch outcome, claims are released with the outcome, telemetry records estimated context utilization, and later polls classify draft/review/CI states ([execute.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/execute.ts), lines 372–410; [watch/index.ts](../repo/packages/squad-cli/src/cli/commands/watch/index.ts), lines 237–312). Green approved PRs are identified, not independently established as product acceptance. A later interval restarts the scan.

The dependency mechanism deserves a specific warning. `WaveDispatchCapability` contains a parser for Markdown checkboxes with `(depends_on: ...)`, bounded parallel batches and a completed set. Its live loop calls `parseSubTasks(undefined)` for every listed item, so no tasks are scheduled. Even if hydrated, the shown loop marks every wave completed irrespective of failed results and treats an empty wave/cycle by adding remaining IDs to completed then breaking ([wave-dispatch.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/wave-dispatch.ts), lines 67–105). This cannot be adopted as a trustworthy dependency execution engine without repair.

## Major additional capabilities beyond Wingman's description

**Portable host projections and embedding.** The same team can generate native coordinator/MCP setup for several coding hosts. The Codex adapter is particularly relevant. A .NET `SquadAgent` integrates Copilot-backed execution into Microsoft Agent Framework through DI/options/delegation ([SquadAgent.cs](../repo/src/Squad.Agents.AI/SquadAgent.cs), lines 8–29, 53–81). Wingman could reuse role/state conventions in Codex or expose projects to other tooling. Integration must distinguish generated host instructions from tested runtime APIs. A projection does not guarantee identical permission, tool or session behavior across clients.

**Governed memory, external knowledge providers and inheritance.** Memory classification separates transient/local/decision/policy/external/forbidden content, rejects credential-like text and routes promoted knowledge. External memory writes can require explicit approval and a host-injected provider. The actual Copilot provider is explicitly unavailable locally, rather than pretending an API exists ([memory/index.ts](../repo/packages/squad-sdk/src/memory/index.ts), lines 24–83, 682–705, 777–822). Upstream inheritance is more than copying a prompt: resolver code handles provenance, depth limits, cycles and shared read budgets with containment checks ([upstream/resolver.ts](../repo/packages/squad-sdk/src/upstream/resolver.ts), lines 1–15, 41–50, 102–120, 252–275). This could propagate organization-wide policies/skills into product squads. Wingman must define authority/override rules and avoid allowing inherited knowledge to override project-specific human decisions silently.

**Cost/context/quality instrumentation.** Model resolution is centralized and records why a model was chosen; preview-model failure can fall forward once while explicit choices are not silently retried as something else. Lifecycle emits resolution provenance and cost-policy events ([agents/lifecycle.ts](../repo/packages/squad-sdk/src/agents/lifecycle.ts), lines 291 onward, 351–369, 525–544). Shell usage ledger/streaming metrics and watch context estimates provide operational evidence. OTel file observation emits spans/events on `.squad` changes; Aspire integration is an observability dashboard, not an executive product dashboard ([squad-observer.ts](../repo/packages/squad-sdk/src/runtime/squad-observer.ts), lines 79–131; [aspire.ts](../repo/packages/squad-cli/src/cli/commands/aspire.ts), lines 1–26). These mechanisms help Wingman manage a large organization, but semantic progress and financial accounting still require careful attribution and validation.

**Operational integrations and autonomous maintenance.** Platform adapters support GitHub and Azure DevOps; communications add Teams/Discussions; optional watcher capabilities inspect Teams/email, decisions and board state. Some integrations are model-mediated: MonitorTeams spawns a prompt asking WorkIQ to find actionable messages and create deduplicated GitHub issues; its preflight checks Copilot availability rather than proving WorkIQ is connected ([monitor-teams.ts](../repo/packages/squad-cli/src/cli/commands/watch/capabilities/monitor-teams.ts), lines 16–46). This is useful expansion beyond Telegram, with account permissions, external costs and deduplication behavior to validate before relying on it.

**Remote terminal control with explicit session security.** WebSocket remote control uses session tokens, one-time tickets, expiry, rate limits and audit logging ([bridge.ts](../repo/packages/squad-sdk/src/remote/bridge.ts), lines 26–64, 109–132). It can provide mobile access to work without building a coding IDE immediately. PTY mirroring exposes the actual terminal session rather than a structured per-agent work model; tunnel provisioning, authentication lifetime and multi-session navigation would need integration into Wingman's host routing.

## Distinctive mechanisms and innovation assessment

The strongest reusable mechanism is **Git remote compare-and-swap as a cross-machine work-ownership primitive**. Empty-tree commits hold structured lease records outside the working tree. A remote atomic ref update decides races. Renewals carry epoch/handle identity, and the watcher self-fences/aborts before it can knowingly continue without a valid lease. This is a concrete way to coordinate independently running Mac/Linux workers without a new central lock service. Its boundaries matter: default exclusion is off, machines must share a namespace/remote, clocks need a skew allowance, pushes need server permission, and already-issued external side effects are not fenced transactionally. The repository's own real-Git tests explicitly distinguish local bare-repo evidence from unverified GitHub/ADO custom-ref rules and HTTP-load behavior ([ralph-claims-git.test.ts](../repo/test/ralph-claims-git.test.ts), lines 1–25). This assessment did not run those tests or reproduce multi-host operation.

A second useful mechanism is **separating canonical conversation control from a coding harness**. Backend envelopes carry control/execution streams, correlation/causation, monotonically ordered events and opaque resume cursors; `(runId, seq)` admission is idempotent. Approval hash validation and persisted outstanding deliveries prevent a lost harness response from losing the decision ([backend/types.ts](../repo/packages/squad-sdk/src/backend/types.ts), lines 76–122, 200–230; [local-backend.ts](../repo/packages/squad-sdk/src/backend/local-backend.ts), lines 326–420, 488–524, 692 onward). Wingman could use this boundary to decouple Telegram/dashboard clients from Codex execution. It is marked experimental. A registry of interfaces plus an external HTTP client does not establish a complete remotely deployed execution service.

A third is **portable, inspectable agent identity combined with controlled knowledge movement**. Charters can be edited/versioned without hiding the team inside a platform database, projections adapt them to several hosts, and upstream resolution includes provenance/containment budgets. Archival explicitly guards against deleting source content when the destination cannot be committed. This addresses long-lived organization maintenance more concretely than simply appending unbounded chat history. However, retrieval relevance, learning quality, historical continuity and human acceptance remain dependent on actual agent usage. No historical priority or industry uniqueness is claimed for these mechanisms.

## Practical fit for Wingman

**Usable directly as design/code candidates:**

- charter and roster formats.
- arbitrary specialist onboarding.
- source/provider abstractions.
- Codex host projection and state MCP pattern.
- local durable decisions/skills/history.
- real session routing/fan-out.

The Ralph polling/capability structure; opt-in Git-ref claims with renewal/fencing; canonical transcript/event/approval contracts; OTel/context/model provenance. These can reduce the amount of project execution infrastructure Wingman needs to invent.

**Needs adaptation:**

- keep Wingman identity and instance IDs separate from names/casting.
- bind every session to project/host/task.
- replace shell's all-permission policy with the actual Codex permission model.
- implement reproducible worktree allocation and integration.
- persist actual per-agent session IDs and resume them.
- choose one consistent state/conversation backend.
- connect accepted human answers to the correct waiting project and leader.

Validate distributed claims against both actual hosts and the selected Git service, enable exclusion explicitly, and decide how non-Squad clients participate. Repair the no-op dependency dispatcher, stub scheduler routes and missing scheduler/watch wiring before using them for supervision guarantees. Do not treat external-provider approval booleans or model-authored comments as an authenticated organization-wide decision system.

Still to build:

- Telegram Butler and conversation/project correlation.
- Portfolio registry and new/existing product intake.
- Standing ProjectMaster supervision across products.
- Mandatory ProductMaster/TechMaster roles and clarification/definition/planning handoffs.
- Scopes/specs/acceptance/DoD records and integrated delivery gates.
- Shared task dependencies and resource scheduling.
- Room1/Room2 participants/direct collaboration and escalation.
- Connected organization directory/executive/project/chat interfaces.
- Meaningful per-agent current/recent/next/blocker summaries and linked timelines.
- Detailed coding-session drill-down and lifecycle controls across Mac/Endeavour. Squad's platform/knowledge primitives can sit underneath those products, but they do not remove this work.

The practical adoption route is one isolated product-team trial using the Codex projection and durable state, followed by source-level hardening and real cross-host tests. Adopting the complete preview runtime as Wingman's organizational core would inherit several differently wired execution surfaces and externally provided capabilities before the organization model is established.
