**Verdict:** Agent Deck provides a strong execution and operations foundation for Wingman. It runs independent coding harnesses and retains their sessions. Telegram conductors delegate to child sessions and receive durable completion records. Supervision, web/TUI control, and SSH execution support ongoing operation. The Command Center presents conductor summaries and decisions.

The main operational unit is a coding session. Wingman still needs product discovery, a project registry, separate product and technical leadership, and shared tickets with dependencies. Product acceptance and delivery also need explicit records. The portable role/post registry supports adoption and display. It does not schedule or execute those roles.

Supporting implementation chapter: [Execution and coordination details](Execution_and_Coordination.md), covering channel authorization, busy-queue overflow, harness-specific delivery, remote imports and visibility boundaries.

## Architecture and execution model

The Go binary dispatches CLI commands from [main.go](../repo/cmd/agent-deck/main.go), lines 538–743. Commands include `launch`, `conductor`, `agents`, `remote`, `watcher`, `web`, `run-task`, and inbox operations. Bubble Tea provides the default TUI. The installed coding harness executes the model and tool loop.

An `Instance` binds a stable manager ID to its directory, group, parent, tool, account, and optional native conversation ID. See [instance.go](../repo/internal/session/instance.go), lines 127–265. The constructor generates the ID and creates a tmux descriptor. `Start` prepares the environment or container and builds the harness command. It applies skills and MCP configuration, starts tmux, and records process ownership. See the same file, lines 1304–1335, 1487–1575, and 1675–1760. Separate instances can execute as independent processes. A role label alone does not start a process.

Session and group metadata reside in a per-profile SQLite state database. CLI, TUI and web act on the same local state, rather than routing every action through a central server. Storage includes targeted insert/verify operations to avoid overwriting sibling concurrent launches ([storage.go](../repo/internal/session/storage.go), lines 263–402, 821–891, 1290–1444 and 1684–1696; [launch_cmd.go](../repo/cmd/agent-deck/launch_cmd.go), lines 765–777). Native transcripts remain owned by the coding harness. Agent Deck stores native IDs and reads transcripts for output, recovery, search and handoff. Keeping a database record, keeping a live tmux process and retaining the native conversation are three separate forms of persistence.

The web server exposes menu/session/group APIs, menu SSE and a session terminal websocket ([server.go](../repo/internal/web/server.go), lines 163–184). A separate notify daemon polls status, observes hook signals, journals transitions and wakes parents. It can continue without an open front end ([transition_daemon.go](../repo/internal/session/transition_daemon.go), lines 234–267). Conductors are ordinary long-lived Claude, Codex, Hermes or Pi sessions with generated instructions and metadata ([conductor.go](../repo/internal/session/conductor.go), lines 37–74 and 1104–1304). An embedded Python bridge handles Telegram and other channels, invoking the same CLI rather than introducing a separate execution backend.

Remote execution is real: a persistent SSH channel runs `agent-deck remote-agent` on the remote host, multiplexes JSON-line command requests and change notifications, and falls back to individual SSH executions when necessary ([remote_channel.go](../repo/internal/session/remote_channel.go), lines 22–114). This is not a local subprocess advertised as multi-host. Each host still owns its own state and files; incremental remote talkback brings remote completions into enrolled local conductors' inboxes ([transition_daemon_remote.go](../repo/internal/session/transition_daemon_remote.go), lines 12–79).

## Agent definition, creation and lifecycle

There are three important concepts. A **session instance** is the controlled execution object, with its manager ID, process, native harness identity and stored metadata. A **conductor** is a session supplied with orchestration instructions, a named directory, policy, state and heartbeat settings. A portable **agent post/role definition** describes an existing setup for inspection. In `RuntimeSpec`, the adopted session is explicitly provenance rather than control; `RestartPolicy` is recorded but not acted upon, triggers are display-only, and posts are disabled ([definition.go](../repo/internal/agents/definition.go), lines 119–184 and 198–209). The CLI has adopt/list/show, not enable/start/schedule-post commands ([agents_cmd.go](../repo/cmd/agent-deck/agents_cmd.go), lines 71–107). This last distinction is crucial when judging a standing organization: the schema is promising but does not instantiate a role repeatedly on demand.

**Definition and configuration.** Runtime tools come from built-ins and user-defined `ToolDef` entries, including command, compatibility, wrappers, status/prompt patterns, resume flags, native-ID capture and environment ([userconfig.go](../repo/internal/session/userconfig.go), lines 3585–3643). Storage profiles partition operational state; account selection and model settings choose execution context rather than specialist job descriptions. Role specifications can reference an entrypoint, policy, playbooks, workflows and curated learnings without copying their steps into a second format. Post placement adds project/group/machine/reports-to. These are inspectable declarations; actual specialist behavior still arrives through harness instructions and prompts.

**Creation and identity.** `launch` validates creation options, can create/reuse a Git/Jujutsu worktree, resolves a parent and group, creates an instance, assigns parent identity, and saves the row before starting. Parent selection is separate from group organization: workers can belong to a product group while reporting to a conductor ([launch_cmd.go](../repo/cmd/agent-deck/launch_cmd.go), lines 389–464, 482–575 and 765–786). A generated manager ID, not a mutable title, is the durable session identity. Conductors additionally store a stable `ConductorName` ([instance.go](../repo/internal/session/instance.go), lines 138–148). Repeated BackendCoder instances therefore require repeated session creation; choosing a “BackendCoder” role name alone does not launch one.

**Execution, tools and permissions.** `Start` validates the account, serializes competing spawn attempts, refuses to overlap with a still-owned process tree, prepares scratch configuration, builds a harness-specific fresh/resume command and starts tmux. It applies configured skills/MCPs before the tool starts and captures a durable process-ownership receipt ([instance.go](../repo/internal/session/instance.go), lines 1496–1546 and 1692–1747). The actual coding tools and permission enforcement belong substantially to the harness. Custom tool definitions may specify dangerous-mode flags; Codex's configuration explicitly includes yolo approval/sandbox bypass ([userconfig.go](../repo/internal/session/userconfig.go), lines 2922–2924 and 3623–3627). Optional Docker sessions introduce an execution boundary, but a role's descriptive policy is not an enforced capability system. A Wingman deployment must choose these settings deliberately rather than assuming an organization chart isolates workers.

**Routing and concurrency.** Native session resolution supports IDs/titles/paths; message delivery uses prompt readiness, send verification and, for Codex, accepted-turn identity fencing. Human bridge calls serialize reply ownership before blocking waits, so colliding arrivals queue rather than claim another request's response ([conductor_bridge.py](../repo/internal/session/conductor_bridge.py), lines 1176–1242). Group concurrency caps queue a new instance with its initial prompt, while launch throttling bounds parallel process starts ([launch_cmd.go](../repo/cmd/agent-deck/launch_cmd.go), lines 809–841 and 868–878). These are resource/lifecycle limits, not ticket dependency scheduling. SSH transport adds execution locations; remote files remain on those hosts.

**Persistence and resume.** Session rows survive UI exit. Native harness IDs let restart resume a conversation, subject to transcript availability and account/host compatibility. Generic custom-tool identities carry tool/command/location provenance so a saved ID cannot be reused blindly after moving runtimes ([instance.go](../repo/internal/session/instance.go), lines 252–265). Conductors are instructed to read/update `state.json`, append `task-log.md`, and retain shared/per-conductor learnings across compaction ([conductor_templates.go](../repo/internal/session/conductor_templates.go), lines 342–407). Those semantic records are model-maintained, unlike database-backed session state. Their freshness/completeness is not mechanically guaranteed.

**Scheduling and supervision.** Conductors have optional heartbeat settings, can use OS heartbeat scripts without Telegram, and the bridge avoids sending duplicate ticks when the OS timer already owns that job ([conductor.go](../repo/internal/session/conductor.go), lines 87–105 and 1322–1339; [conductor_bridge.py](../repo/internal/session/conductor_bridge.py), lines 5008–5024). Heartbeats name changed waiting/error sets or pending inbox records. They do not repeatedly invoke the model when nothing actionable changed. A fully unchanged stalled worker can therefore require another signal or explicit operator check. Declared post cron triggers must not be confused with this active conductor scheduler: adopted triggers are only displayed.

**Interruption, cancellation and recovery.** Session stop/kill and restart are explicit controls. `KillAndWait` verifies process-tree death with termination/escalation; teardown supersedes stale death watchers and reaps tracked MCP descendants before tmux removal ([instance_restart.go](../repo/internal/session/instance_restart.go), lines 244–283). This is cancellation of execution, not rollback of filesystem edits. `Start` records diagnostic evidence for early launch failure and monitors fast process death (instance lines 1692–1760). Restart reconstructs native identity and MCP configuration. Conductor policy says to inspect substates, avoid restarting credential-held sessions, and escalate or change unavailable models rather than looping ([conductor_templates.go](../repo/internal/session/conductor_templates.go), lines 284–293). Deterministic self-heal policy includes rate caps, backoff and circuit breakers, but its policy implementation explicitly supports observe-only operation; its mere presence does not prove every failure automatically recovers ([selfheal/policy.go](../repo/internal/selfheal/policy.go), lines 10–79).

**Completion and acceptance.** Interactive sessions can finish a turn without finishing their assignment; waiting is not proof of task completion. One-shot task workers instead run to process exit, capture output and finalize a completion record. A last completion sentinel takes precedence over exit-derived ok/fail; without a sentinel, exit zero means ok ([taskworker.go](../repo/internal/session/taskworker.go), lines 17–52 and 181–240). That proves process-level/report-level completion, not product correctness. Unacknowledged records replay after daemon/parent downtime; unresolved records can eventually be parked in dead letters ([transition_daemon.go](../repo/internal/session/transition_daemon.go), lines 310–354). The product does not impose a TestMaster acceptance gate, integrated definition of done or a human delivery-acceptance state.

**Retirement and cleanup.** Sessions can be stopped, archived or removed; archive metadata and handoff lineage are persisted separately from identity ([instance.go](../repo/internal/session/instance.go), lines 233–249). Storage deletion and deferred cleanup are separate operations ([storage.go](../repo/internal/session/storage.go), lines 687–725). Removing a session is not retiring a reusable role profile, and deleting its operational record does not establish deletion of harness-owned transcripts or project files. Worktree cleanup is an explicit source-management concern, not an implicit consequence of accepted product delivery.

## Coordination mechanics and a concrete request trace

The central coordination pattern is parent/child sessions plus durable records, not shared-room conversation. The comms ledger records turn text, sends, delivery states, wakes, errors and human-bound messages. Records have sender, recipient IDs, profile/store identity, remote origin, reply references, tier and latency information ([comms/record.go](../repo/internal/comms/record.go), lines 25–55 and 69–128). This is considerably stronger than relying on terminal scraping alone, but still differs from a room with participants, product discussions and navigable ticket relationships. Ticket IDs are session hints. The Hermes-specific template uses `hermes kanban` only for durable blocked escalation records; that is an external harness capability, not an Agent Deck task database ([conductor_templates.go](../repo/internal/session/conductor_templates.go), lines 655–675).

The durable comms ledger stores bounded transport and audit records. It does not preserve complete room history. Text defaults to 600 bytes and has a 2,048-byte ceiling. Ingestion limits turn text and completion summaries. See [record.go](../repo/internal/comms/record.go), lines 62–67 and 205–225, and [comms_ingest.go](../repo/internal/session/comms_ingest.go), lines 301–305.

Defaults include 90-day retention, 1,024 sealed segments, and a 2 GiB quota per profile. Recently active consumers protect unacknowledged segments from compaction. Quota exhaustion refuses new commits. See [ledger.go](../repo/internal/comms/ledger.go), lines 21–36 and 211–215. A consumer loses protection after the retention window. If compaction passes its cursor, the returning consumer receives an explicit gap. See [consumer.go](../repo/internal/comms/consumer.go), lines 43–47 and 433–446. Wingman needs a separate room and project archive. It also needs complete-source links and explicit gap and quota handling.

A real implemented path for an ordinary Telegram request such as “api: fix the login validation” is:

1. The Telegram handler checks authorization/addressing, strips the bot mention and resolves `api:` against configured conductors, falling back to the default. A pre-message hook may gate or transform the text. It ensures the chosen conductor session runs ([conductor_bridge.py](../repo/internal/session/conductor_bridge.py), lines 2848–2907). This code does not infer a product registry entry. The conductor name is the routing unit.
2. If busy, the bridge stores the request with a reply callback in its in-memory queue. If ready, it calls `session send --wait --json --ignore-budget`, tags `channel:telegram`, and reserves accepted-turn ownership. A timeout after acceptance yields a pending receipt and an asynchronous late-reply watcher rather than resending the request (bridge lines 1102–1242 and 2912–2998). That distinction prevents duplicate work, but bridge-memory queues are not equivalent to durable inboxes across bridge crashes.
3. The conductor's instructions authorize creating workers with `launch <path> ... -m <prompt>`, reading output, steering existing sessions and resolving approvals ([conductor_templates.go](../repo/internal/session/conductor_templates.go), lines 263–279). Whether it actually decomposes this request is a model decision. If it launches a worker, the CLI resolves/inherits parent linkage and records purpose/parent hints before saving and starting the new instance (launch lines 482–575 and 765–786). There is no hidden automatic ticket decomposition between these calls.
4. Worker execution takes place in its own tmux/harness process. Interactive turn transitions/hooks and explicit completion sentinels feed notification logic. A one-shot `run-task` path instead derives completion from actual process exit ([taskworker.go](../repo/internal/session/taskworker.go), lines 181–240). Child results commit to the parent's durable inbox. The supported drain stages records into an in-flight WAL before removing pending input, then uses a consumed fingerprint ledger to deduplicate redelivery ([inbox.go](../repo/internal/session/inbox.go), lines 17–35 and 73–110). The contract is at-least-once delivery with deduplication, not a universal exactly-once distributed execution claim.
5. Hook-capable conductors drain at turn boundaries; heartbeats provide an idle/fallback drain. Urgent child questions/errors/completions wake the parent while info is batched. The conductor chooses its response and can explicitly notify the human. NEED/urgent lines reach the human, info becomes a digest, and routine status stays local ([conductor_templates.go](../repo/internal/session/conductor_templates.go), lines 303–340). The human's next reply takes the same bridge route. General project/question identity still needs Wingman's own records.
   For a Codex-only Wingman, the current ledger delivery canary requires special care: automatic prompt/Stop-hook injection is restricted to enrolled Claude-compatible parents, while Codex children still produce text records and Codex parents retain inbox/drain delivery. The canary supplements the inbox; enrollment does not remove that path ([comms_deliver.go](../repo/internal/session/comms_deliver.go), lines 18–34 and 79–98). The Codex drain/heartbeat latency needs direct integration verification.

6. The web Command Center combines the shared menu snapshot with conductor `status.json` headlines and session annotations; SSE pushes changed snapshots. Input validates its target then invokes the same `session send` primitive ([handlers_command_center.go](../repo/internal/web/handlers_command_center.go), lines 181–268, 339–357, 509–534 and 594–693). It is an operational view of this flow, not a replacement product tracker.

Remote children extend step 4 through incremental talkback. The notify daemon periodically drains enrolled remote hosts, applies bounded waits/backoff and writes an urgent alert after repeated failures rather than treating lost connectivity as silence ([transition_daemon_remote.go](../repo/internal/session/transition_daemon_remote.go), lines 12–79). Shared coordination is therefore implemented through transfer/import and local inboxes. It does not synchronize a product's entire working tree or transactional task state across machines.

## Substantial additional capabilities

**Heterogeneous harness operation and conversation transfer.** Wingman describes Codex agents; Agent Deck supports several coding harnesses, accounts and custom wrappers. More significantly, its handoff code validates an exact Claude transcript and builds a bounded conversational context prompt for a fresh Codex session, rather than writing fabricated native rollout data ([handoff.go](../repo/internal/session/handoff.go), lines 16–100). The broader cross-harness switch stages a separate destination, requires independent native readiness/identity evidence and only then finalizes source/destination lineage ([cross_harness_switch.go](../repo/internal/session/cross_harness_switch.go), lines 20–95). This enables recovery or model specialization without silently destroying the original conversation. Integration must distinguish native continuation from a lossy context transfer: truncation and a new harness identity matter to auditing and responsibility.

**Cross-harness recall and native timelines.** Recall indexes conversations across harnesses and offers context extraction, artifacts and native-event timelines. Its timeline cursor hashes the observed prefix, and native sources are read because the search index intentionally omits some tool/non-text records ([recall/query/timeline.go](../repo/internal/recall/query/timeline.go), lines 20–115; [recall/query/context.go](../repo/internal/recall/query/context.go), lines 69–150). This can make past investigation reusable across Wingman projects. It is a retrieval layer over agent history, not authoritative specifications; remote digest-only cards cannot supply a local transcript timeline.

**Event-source automation beyond Telegram.** Watcher adapters cover GitHub, Gmail, Slack, ntfy and webhooks. The engine matches senders to conductors, preserves reply-thread session routing, persists deduplicated events and can send unrouted arrivals to triage ([watcher/engine.go](../repo/internal/watcher/engine.go), lines 675–751). Delivery uses an outbox, tracks retryable failures and explicitly records queue-full refusal (lines 1009–1060). Wingman could accept issue/customer signals directly, but would need product routing, authority rules and deduplication across Telegram and other intake paths. This does not automatically make an external message an authorized product change.

**Cost control beyond usage display.** Configured daily/weekly/monthly, group and session limits can gate agent-originated sends/wakes in a single read transaction ([costs/budget_send.go](../repo/internal/costs/budget_send.go), lines 8–42). This is useful portfolio resource governance. It gates future interactions, rather than proving a hard cap on all already-running provider activity; human bridge messages explicitly bypass that gate. Wingman would need to expose the resulting paused/blocked work state so budget refusal does not masquerade as completion.

**Shared MCP process pooling.** The pool owns named proxies, reuses existing servers and allows explicit inclusion/exclusion/fallback policies ([mcppool/pool_simple.go](../repo/internal/mcppool/pool_simple.go), lines 18–100). This reduces redundant tool-server processes in large specialist fleets. Shared process lifetime and cross-session tool state introduce operational coupling. It should not be assumed to enforce project permission boundaries merely because the server is shared.

## Distinctive mechanisms and grounded innovation

The useful innovation here is engineering the unreliable edges between independent interactive agents into explicit, inspectable protocols. These observations concern this code. They do not claim historical novelty.

**Completion and prompt readiness use separate evidence.** Persistent panes need hooks or completion sentinels. One-shot workers use process exit and durable completion records. The inbox stages input in a write-ahead log (WAL). A consumed-turn ledger removes duplicate deliveries. The parent can remain busy or offline without losing the child's report. This supports asynchronous delegation and recovery.

A sentinel records an agent assertion. Process success does not establish product acceptance. At-least-once transport can repeat delivery. Agent side effects still need their own idempotency controls. See [taskworker.go](../repo/internal/session/taskworker.go), lines 17–52 and 181–215, and [inbox.go](../repo/internal/session/inbox.go), lines 17–35.

Second, **supervision is delta-triggered to avoid paying for repetitive model turns**. `BuildHeartbeatTick` fingerprints the actionable waiting/error set and inbox digest, sends nothing for unchanged state, and asks to reread rules only when their file stamp changes. Pending tick state is committed against the exact printed message hash, because sending itself may drain the inbox ([conductor_heartbeat_tick.go](../repo/internal/session/conductor_heartbeat_tick.go), lines 20–35, 64–123 and 176–208). This makes persistent management more economical. It also means recurring inspection of an unchanged condition is not equivalent to Wingman's open-ended blocker follow-up policy; escalation aging and model policies still matter.

**Execution and observation use explicit identities.** Codex accepted-turn checks guard concurrent sends. Cross-harness switching requires native evidence from the destination. Remote message deduplication uses stable store identity. A mutable host display name cannot replace that identity. See [session_send_codex_acceptance.go](../repo/cmd/agent-deck/session_send_codex_acceptance.go), lines 33–98 and 238–263; [cross_harness_switch.go](../repo/internal/session/cross_harness_switch.go), lines 41–95; and [comms/record.go](../repo/internal/comms/record.go), lines 85–94 and 131–142. These controls support concurrency, restart, and remote import. They still depend on native transcript and hook contracts. They do not establish product acceptance.

Fourth, **the role/post registry makes uncertainty visible**: adopted definitions retain provenance, disabled/external trigger state, unresolved decisions and broken reporting-chain attention. It avoids silently taking over a discovered systemd/launchd/conductor setup ([definition.go](../repo/internal/agents/definition.go), lines 164–216; [view.go](../repo/internal/agents/view.go), lines 115–133). That is a sound migration surface for an existing agent organization. Its current limitation is intentional: no automatic execution or scheduling of these posts, and the current CLI returns unconfirmed remote agents rather than fetching them ([agents_cmd.go](../repo/cmd/agent-deck/agents_cmd.go), lines 655–680).

## Practical Wingman fit

Use directly, after deployment validation: session launch/control/resume, parent-linked workers, durable inbox/comms, Telegram conductor transport, heartbeat supervision, remote execution/talkback, terminal drill-down, annotations, cost information and event intake. A conductor could host Butler-like behavior, and additional conductors could become project managers. The code already supports Codex conductors. This is not intrinsically Claude-only ([conductor.go](../repo/internal/session/conductor.go), lines 46–74).

Adapt the organization model:

- Give profiles explicit role instructions and durable product IDs.
- Keep profile, account, and group separate from agent responsibility.
- Link workers to tracker assignments.
- Add question and decision IDs to Telegram callbacks.
- Define acceptance evidence and interrupted-work states.

The Command Center supports authored Markdown summaries, session hints, and two-way input. Its decision parser uses one conductor file path. It routes decisions to `conductor-agent-deck`. It excludes error and stopped children from the relevant view. Group-equality membership also needs adaptation for nested teams. See [handlers_command_center.go](../repo/internal/web/handlers_command_center.go), lines 428–461 and 537–587. The adopted-agent view needs an implemented lifecycle integration. Changing a YAML `enabled` field cannot supply that integration.

Still build:

- Product registry and new/existing intake resolution.
- Proportionate discovery with project-scoped clarification history.
- ProductMaster/TechMaster responsibilities.
- Scopes/specs/scenarios/definition of done.
- Shared tickets with dependencies and assignable workers.
- Project/portfolio progress.
- Readable rooms with durable participation and decisions.
- Executive/individual timelines linking conversations, tasks and artifacts.
- Integrated verification and human delivery acceptance. Arbitrary prompts can request much of this behavior, but prompts alone do not deliver the shared-state and connected-view contracts in Wingman's purpose.

Overall, this is a credible base for the execution and operational-visibility layer and a source of strong reliability patterns. It is not a drop-in replacement for the complete standing development organization. Its growing agent directory and Command Center reduce the UI gap, while the product-management and collaboration-domain gap remains substantial.
