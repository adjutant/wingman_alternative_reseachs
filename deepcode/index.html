DeepCode assessment against Wingman

  • Product: DeepCode, an open agentic coding runtime with terminal, desktop and browser clients, plus research-to-code workflows.
  • Repository: https://github.com/HKUDS/DeepCode
  • Local checkout: research/deepcode/repo
  • Assessed commit: aa6ed16148719101b994882c94608ae12e88f870
  • Assessment date: 2026-11-05
  • Method: read-only source and test inspection. No dependency installation, service launch, provider request or live workflow execution.

Fit verdict: DeepCode is a substantial candidate for Wingman's individual coding-agent execution layer and detailed workspace, with useful persistence, local concurrency, approvals, goals and automation. It is not an implemented standing software-development organization. Its projects are registered local directories; its durable people-like entities are coding sessions; its delegated specialists live within one parent Turn. Butler, Telegram intake, product/technical leadership, shared tickets and rooms, organizational supervision, executive briefings and execution across the Mac and Endeavour remain work for Wingman. This distinction matters because the current checkout is much broader than the original paper-to-code description, but its rich coding workbench still does not supply the missing organization.

Architecture and actual execution model

The public Python entry point dispatches chat/tui, desktop, web, serve, exec, sessions, loop, schedule and automation commands. These are implemented routes, not just README examples (deepcode.py, lines 94–191). Desktop/browser use a React client; native desktop has a Tauri runtime adapter and browser has its own transport. An application host owns the backend independently of connected clients: closing a peer detaches that peer, while ServiceHost retains the application and shared notifications (host.py, lines 17–41, 87–112). The background HTTP service binds loopback and checks the exact loopback Host header (service.py, lines 48–79, 141–168). This is background local operation, not an Internet organization server or a host federation.

The domain deliberately separates Project, Thread, Turn and runtime worker. Project contains an absolute canonical directory, display name, trust and settings; Thread is a session projection with project, workspace, model route, optional parent/worktree and activity/archive status (project.py, lines 21–45; thread.py, lines 23–61). ProjectService.add() canonicalizes a directory and reuses an existing path registration, and ThreadService.start() requires an explicit project ID (project_service.py, lines 51–99; thread_service.py, lines 174–205). Neither performs conversational product identification.

Canonical identity, title, transcript, origin and session settings live in SessionStore JSONL and metadata. SQLite holds application projections: Turns, Items, approvals, workflow/automation state and replay events. ThreadService documents and implements reconciliation in this direction, including rebuilding from established sessions (thread_service.py, lines 137–172). Session operations include create, append, branch, settings, rename and metadata mutation (store.py, lines 317–385, 473–513, 586–621, 650–679, 730–764). Preserving a session does not preserve its Python task, in-memory child roster or an external tool's process.

TurnService.start() and _submit() create a durable Turn from each request. They capture input identity, model profile, security snapshot, and Goal association before scheduling. ExecutionCoordinator admits queued Turns through cross-process resource claims. ExecutionRegistry provides a bounded background asyncio loop. Default concurrency is two top-level Turns.

Admission claims a thread key, a slot in global capacity, and a workspace key. Canonical project work shares a write fence. Managed worktrees receive separate thread workspace keys. See turn_service.py, lines 352–396 and 398–425; execution_registry.py, lines 21–69 and 211–252; and execution_admission.py, lines 35–66.

Execution acquires a long-lived AgentSession associated with the canonical session, prepares approvals/history and projects kernel events into durable Items. A factory loads workspace configuration, composes the selected preset, resolves providers and builds the session (turn_service.py, lines 1377–1417, 1555–1629; agent_adapter.py, lines 108–181). The actual model/tool loop is AgentRunner, not a separate Codex process for every native agent. Native provider adapters run model requests; tools implement file operations, commands, search, memory, plans and optional delegation/MCP. The runner handles model responses, tool batches, permissions and compaction (runner.py, lines 540–550, 1189–1283, 1380–1414, 1750–1816, 1995–2146).

A second path handles paper, repository and brief workflows. WorkflowService makes a durable WorkflowRun and interaction/artifact projection; WorkflowAdapter dispatches local/URL papers to the research pipeline and briefs/repositories to chat planning. It places outputs beneath .deepcode/workflows, serializes progress callbacks and enables strict outcomes (workflow_adapter.py, lines 85–195). The pipeline's named analysis/planning/implementation agents are phase-specific sessions and compatibility wrappers. They should not be counted as a standing ProductMaster/TechMaster organization. The code explicitly uses a single planning agent for the stable full-document path (agent_orchestration_engine.py, lines 105–128).

Agent definition and full lifecycle

What an agent actually is

There are four relevant concepts. A preset is reusable model-facing composition, not a running identity. A canonical Session/Thread is a durable conversation tied to a directory and settings. An AgentSession is a loaded in-process runtime with provider, history, tools and hooks, reused across admitted Turns while valid. A SubAgent is an in-memory child record and asynchronous execution owned by one parent Turn. A runtime worker is the backend process admission identity, not a specialist. Phase names such as Research Analysis Agent may describe prompts, calls or workflow functions, so they are not additional durable employees merely because their names contain “Agent.”

Definition, creation and identity

A top-level session can select a preset from .agents/presets, .claude/agents, the DeepCode user directory or built-ins. The file stem is the preset identity; nearest roots win duplicate IDs, broken definitions remain visible, and persona/tool/delegation values are snapshotted at session creation. Model connection and permissions remain separate controls (agent_presets, lines 1–33, 94–146, 234–292). This is useful reproducibility: changing a profile file does not silently redefine existing sessions. It also means a central role update would require an explicit migration or new session policy in Wingman.

ThreadService.start() requires an existing Project and creates canonical session metadata/projection. The durable ID is the SessionStore ID; early thr_ IDs and existing short session IDs are accepted (thread.py, lines 53–61). There are no separate employee ID, reporting-line, host-affinity or project-role membership records. To make BackendCoder a standing agent, Wingman would need to associate its organizational identity with this session ID.

Child creation is model-driven through spawn_agent: a stable name or normalized task supplies the dedup key, an optional persona narrows the role, optional tools narrow capability, and a JSON schema requests a structured result. It returns immediately after creating asyncio.ensure_future(self._run(sub)). Native children inherit execution profile and security. They cannot spawn children themselves. Re-spawning a still-running or already-successful task is refused, while failed work may be retried (control.py, lines 281–397, 598–617). A schema is enforced through a capture tool; finishing with prose but no structured submission is a failure (lines 633–640). These are real independent model executions, even though their organization and durability are limited.

Execution, tools, permissions and routing

build_agent_session() resolves the provider/model and creates immutable security settings. It assembles instructions, memory, skills, hooks, and tools. See agent_setup.py, lines 391–507, 519–595, and 666–708. Default tools include read/write/edit/patch, Bash, Grep/Glob, memory, update_plan, and web fetch. Interactive callers can add request_user_input. Top-level sessions can add delegation. Read-only reviewers receive safe read/search tools and restricted Bash where the platform can enforce it. See tools/init.py, lines 52–120 and 136–155. Tool policy and workspace/network sandboxing provide enforcement beyond persona instructions.

Ask, read-only, and full-access are execution settings. They do not define specialist roles. The application factory passes a security snapshot and hook approval to the runtime. Full access can permit work outside the workspace. External-command hooks need separate approval because they run outside the command sandbox. See agent_setup.py, lines 563–595, and tools/init.py, lines 121–150. Preserve those boundaries when wrapping the runtime.

Routing is explicit: project/session IDs determine the request destination; provider connection/model profiles determine model execution. The loaded parent AgentControl determines child message destination. An external backend may invoke local Codex or Claude Code CLIs, but its contract is one self-contained task and final answer. Parent-history forks, persona/tool/schema composition and follow-up messaging are rejected when unsupported (control.py, lines 69–75, 304–339; external_backend.py, lines 86–177). This is a useful bridge to Codex, not a Codex organization transport.

Concurrency and workspace isolation

A parent defaults to five actively running native/external children, one level deep. A native child owns a worktree for its conversation, can park idle after a turn and resumes on a follow-up; active count limits running work rather than turning every idle conversation into a slot. The base Git operations are serialized; child model/tool work proceeds concurrently. Each successful child turn merges its branch into the base and reports conflicts rather than silently overwriting them (control.py, lines 41–44, 448–511; worktree.py, lines 1–11, 71–83). Non-isolated children instead share the parent workspace and its associated race risks.

The worktree manager may initialize an unversioned directory, create a base commit and install local excludes. It stages worker changes with safe Git options (worktree.py, lines 87–137). Thus its isolation/merge behavior has real repository consequences; adopting it requires choosing how Wingman integrates commits, conflict resolution and acceptance. The cross-process top-level workspace fence does not itself manage child task dependencies or integration contracts.

Persistence, follow-up and resume

Top-level sessions keep canonical transcript/settings independently of the UI and loaded runtime. The runtime cache reloads history when needed and invalidates based on execution configuration/preset/security changes (session_runtime.py, SessionRuntimeRegistry; agent_adapter.py, lines 183–235). Thread APIs support resume, rename, archive and fork (thread_service.py, lines 298 onward, 505 onward, 616–633 onward). Forking is a new conversation branch, not cloning an autonomous role with all outstanding assignments.

Native children are conversational only within the parent Turn. _converse() parks after a result and send_message() either injects into a running child's next step or wakes an idle child. _run_subagent() builds a fresh kernel session for each child turn and seeds it with the child's accumulated history. It closes that session after the turn (control.py, lines 225–256, 448–506, 598–646). Child transcripts are written via the parent's transcript sink. Crucially, the parent kernel always calls _cancel_turn_subagents() in its Turn finalizer, including normal completion (session.py, lines 938–955). Idle children do not become standing agents across the next parent Turn or a service restart. Their stored transcripts are evidence, not an automatic reconstruction of the child roster.

Scheduling and autonomous continuation

Goals add durable objectives, budgets, checks, outcomes and automatic continuation to ordinary Turns. GoalExtension.on_turn_settled() accounts a completed Turn and starts the next when the Goal remains active and the thread is idle. It guards against repeated no-progress continuations and limits unbudgeted unattended continuation (goal_extension.py, lines 1115–1186, 1237–1335). This lets an agent pursue a larger outcome over multiple Turns without a human re-prompting every step.

Automations are durable definitions/revisions and idempotent occurrences, each accepted run owning one real Thread Goal. They reuse Turn execution rather than inventing another agent engine. The scheduler acquires a single leader file lease, runs due work, calculates the next wake, and survives one scheduling-pass exception (automation_service.py, lines 1–7; automation_scheduler.py, lines 109–145). They provide a substrate for “check progress every interval,” but Wingman would still implement the registry inspection, blocker interpretation, agent contact and escalation logic.

Interruption, failure, retry and recovery

Top-level interruption persists cancellation, cancels locally or lets the claim-owning process observe the request, and waits for a durable terminal state. Unclaimed queued Turns can be interrupted before start (turn_service.py, lines 1295–1374). A soft child interrupt cancels only its current native turn and parks it for redirection; external CLI interruption cancels its whole run. Parent teardown cancels and joins every child, including idle ones, so resource cleanup finishes before the parent becomes terminal (control.py, lines 196–223, 778–799). Kernel session close also closes MCP/tool/provider resources (session.py, lines 746–762).

Provider request retry and finalization retry operate inside the runner; application retry creates a new Turn with recorded origin rather than rewinding mutations (runner.py, lines 1189–1283; turn_service.py, _retry_origin, lines 2436–2465). A missing terminal kernel event is treated as protocol failure. Normal, error and cancellation outcomes all converge on persistent finishing and usage/history accounting (lines 1377–1389, 1609–1706).

Recovery distinguishes safe queued work from lost running work. recover_incomplete() can preserve ordinary queued Turns for later scheduling, cancels stale approval state and interrupts lost live work; owned execution recovery is separately coordinated. The worker's OS lock must prove it is dead before claim recovery, and running/approval-waiting side effects are not automatically replayed (turn_service.py, lines 2248–2305; execution_coordinator.py, lines 477–496). This current source is more nuanced than older architecture prose saying every queued Turn is simply interrupted. Ordinary interactive Goals pause after restart unless an unattended owner authorizes continuing; automation-owned Goals may continue in the eligible cases (goal_extension.py, lines 1052–1094).

Completion, acceptance and retirement

A normal Turn completing means its kernel run reached a terminal result, not that an entire product was accepted. Goal completion may execute user-confirmed checks, an evidence rule and optionally a separate read-only reviewing agent. The default completion-verifier setting is off; even this mode retains confirmed checks, but without configured checks it is not equivalent to independent acceptance (config.py, lines 422–439; agent_setup.py, lines 340–388). The router resists premature blocked reports, repeated rejected claims and claims while children are running, with finite bounds rather than endless verification loops (goal_runtime.py, lines 23–39, 239–318, 469–565).

Strict workflow implementation reports incomplete if no discovered tests run or if tests fail. The app adapter enables strict outcomes. The research/brief pipeline passes that into require_verification (workflow_adapter.py, lines 140–175; agent_orchestration_engine.py, lines 2028, 2343; code_implementation_workflow.py, lines 536–571). These are meaningful gates but do not cover integrated product requirements, manual/browser validation or human delivery acceptance automatically.

Archive removes a session from active navigation while keeping its history. Deletion uses a dedicated session-deletion service and guarded canonical store operations. A loaded runtime's close tears down owned tools, hooks and children. Isolated child teardown cleans its worktree (thread_service.py, lines 616–633; session_deletion_service.py; store.py, lines 621–650, 1132–1177; control.py, lines 507–511). No organizational retirement/reassignment/handoff protocol sits above these operations.

Coordination and a source-traced request

Consider a concrete native coding submission to a known project session, followed by delegation and an approval. This is a source trace of a supported request shape, not a claim that an LLM session was run during this assessment.

  1. The client targets an existing canonical session with turn/start; TurnService.start() validates the Goal association and creates a submission, preserving message identity, client surface and execution settings. Explicit project registration/thread creation occurs beforehand. There is no inference that “the CRM” refers to this project (methods.py, lines 55–94; turn_service.py, lines 352–396).
  2. The coordinator claims eligible queued execution under capacity/thread/workspace resources, then the registry runs it on the background loop. Worker identity is its local PID, file lease and SQLite row (execution_coordinator.py, lines 180–211, 287–333; execution_admission.py, lines 49–66).
  3. The Turn acquires its session runtime, installs approval/history/input callbacks and streams UserInput. AgentRunner calls the configured model, exposes permitted tools and executes returned calls; TurnEventProjector turns resulting activity into messages, commands, changes, tool/approval Items and replay events (turn_service.py, lines 1377–1417, 1555–1559; turn_projection.py).
  4. If the model calls spawn_agent(task=…, name=…, isolate=True), AgentControl deduplicates and admits a child. The child receives a real worktree/session and optional inherited visible parent history. It cannot call sibling agents. Its result merges back and is posted as SubagentMessage to the same active Turn input boundary used for user steering. If that boundary has closed, a late result is saved as a canonical context note for a later Turn (control.py, lines 281–397, 448–511, 679–724).
  5. The parent can wait_agent, continue other work, send a correction to that child or wake it after an answer. Waiting wakes on mailbox activity, rather than joining all children and forcing a barrier (control.py, lines 225–256, 726–742). This is hierarchical collaboration, without room broadcasts or durable tickets.
  6. A permission decision of “ask” creates the durable approval Item and Approval row, sets Turn to waiting and Thread to waiting, and suspends the exact request. approval/respond records a once/session/deny decision; approval service observes the durable decision and resumes/declines the suspended call. Session grants are scoped according to the tool arguments/workspace, rather than making a persona trusted (approval_service.py, lines 71–155, 192 onward). This is direct human tool authorization, not management judging product intent.
  7. Additional user steering uses expected_turn_id and message_id, receives a delivery receipt and is persisted without starting another Turn (turn_input_service.py, lines 52–99). When execution ends, child work is joined/cancelled, history and usage are recorded and the Turn becomes terminal. If a Goal remains active, GoalExtension may schedule another Turn. The UI can reconnect and replay existing work because execution belongs to the host, not the view.

The persistent collaboration artifacts are session messages, execution Items/events, Goal/check/review records, workflow artifacts and plan-review versions. update_plan is a self-maintained checklist. It does not provide dependency graphs, ticket assignment, shared blocker records or issue ownership. The requirement-analysis helper is real code, but search found its orchestration wrapper defined separately rather than called by the current application workflow dispatch. Plan review is positively wired into that dispatch, so it is the stronger human-clarification evidence. The factory also does not pass an ask_user_callback in its application construction path. The optional tool supported by direct session assembly should not be presumed to be available in every desktop/browser Turn (agent_adapter.py, lines 108–181).

Major additional capabilities and their integration consequences

A complete local coding workbench and shared backend across clients. The inspector exposes source editing, changes, artifacts, tests, terminal and execution details. The backend owns these operations and a client-independent host owns execution. This is considerably more concrete than a generic agent status dashboard. It could supply the “open BackendCoder's detailed session” experience. Wingman would need a stable mapping between organization agent IDs and canonical sessions, authorization/routing for its dashboards, and a strategy for opening remote-host workspaces. Reusing the loopback client unchanged does not provide mobile access to the organization (Inspector.tsx, lines 40–65; host.py, lines 17–41; service.py, lines 48–79).

Research/paper/repository-to-code pipelines. Inputs can be papers, URLs, repository references, or briefs. Acquisition, optional segmentation, planning, reference indexing, implementation, review, and verification produce workflow-directory artifacts. The system retains plan versions and feedback. Retry/checkpoint paths can reuse acquired inputs and plans.

These bounded workflows can support algorithm reproduction and research prototypes. They do not establish a complete product organization or guarantee research quality. Preserve their artifact contracts and completion rules during integration. See workflow_adapter.py, lines 85–195, 276 onward, and 320 onward; plan_review_runtime.py, lines 42–101; and agent_orchestration_engine.py, execute_multi_agent_research_pipeline and execute_chat_based_planning_pipeline.

Goal completion gates, budgets, and evidence. Confirmed checks run once per distinct argv command. Output limits and per-command/aggregate timeouts bound execution. Rule and reviewer modes add verification. The reviewer is read-only and has no delegation, hooks, or MCP. Structured findings must support the requirements. Rejection can return work to the worker. Repeated rejection eventually blocks further work.

These controls can connect completion claims to evidence. Wingman still needs suitable product scenarios and explicit enablement of stronger verification. A reviewing model can also make errors. See goal_checks.py, lines 1–39 and 72–127; goal_reviewer.py, lines 329–404 and 417–455; and goal_runtime.py, lines 239–318 and 469–565.

Provider, skill, plugin and MCP extension systems. Native sessions can select model/provider connections, expose generic MCP tools with OAuth/credential handling, and load versioned skill context progressively per Turn. Linked local Agent Plugin packages contribute supported skills and MCP declarations; discovery itself does not import plugin code or start it (agent_setup.py, lines 609–655; skills/runtime.py, lines 1–63; plugins/host.py, lines 44–82). This is a useful way to connect Wingman tracker/chat tools and role practices, with clearer provider independence than hardwiring one CLI. It introduces its own credential, approval, package revision and capability-filter contracts. A tool connection alone does not implement the business workflow around it.

Automation as a durable product feature. Scheduling supports durable definitions/revisions, occurrences, run history and actual Goal-based execution, with an automations management page. This could host recurring maintenance or research as well as Wingman supervision. It requires translating organizational supervision into concrete instructions/tools and defining overlap, unattended permissions and escalation behavior. It does not automatically supervise every project (automation_service.py, lines 1–7, 644–683; automation_scheduler.py, lines 39–145; AutomationsPage.tsx).

External coding-agent delegation. Codex and Claude Code children use their native CLIs and credentials. DeepCode manages invocation, worktrees, and result integration. These backends do not inherit parent context or support interactive child messages. They also receive no DeepCode persona, tool, or schema injection. They therefore cannot transparently replace native conversational specialists. See external_backend.py, lines 86–177, and control.py, lines 304–339.

Distinctive mechanisms and grounded innovation

The useful innovations are implementation choices, not claims of historical uniqueness. Several modules explicitly acknowledge adaptation from other agent blueprints; no industry-first claim is justified.

  1. Canonical sessions plus rebuildable application projections. Thread identity and transcript stay in a frontend-neutral canonical store, while high-volume live Items and replay events belong to SQLite. Config/preset/security snapshots make it possible to understand what actually ran and to reload a runtime without redefining its conversation. This offers a sound foundation for Wingman's connected summary-to-detail views, but Wingman still needs organizational/task records and links on top. The two-store design also demands reconciliation discipline; blindly treating SQLite as all durable truth would lose canonical semantics (thread_service.py, lines 137–172; agent_adapter.py, lines 183–235).
  2. One input boundary for steering and child results, with a late-result fallback. Typed messages carry target Turn and unique identity into the runtime. Child results use this same route; if completion wins the delivery race, they are persisted as a between-turn context note. This reduces silent loss and ambiguity when human steering and delegated work race with parent completion. It is scoped to one parent's execution, not a durable multi-party chat bus (control.py, lines 679–724; turn_input_service.py, lines 52–99; injections.py).
  3. Continuable children with separate soft and hard stops. A child can answer, idle, receive new direction, and reuse history. Parent teardown joins and ends every child. Interrupting an attempt therefore differs from destroying its conversation. Persisted transcripts still do not establish enduring organizational identity. See control.py, lines 196–256, 448–511, 619–646, and 778–799; and session.py, lines 938–955.
  4. Fenced local admission and conservative dead-worker recovery. Capacity/thread/workspace claims coordinate multiple local backend processes. A stale heartbeat alone is insufficient proof of death; OS lock acquisition proves the old worker is gone, after which queued work can be rehomed and running work explicitly settled without replay. This enables safer multi-client/background concurrency. It is not a distributed consensus or cross-host scheduling system (execution_admission.py, lines 35–66; execution_coordinator.py, lines 477–496).
  5. Evidence-sensitive loop breaking and bounded completion disagreement. EvidenceLedger fingerprints canonical calls and the normalized results the model actually saw, catching alternating calls that produce no new information. It gives a warning before stopping repeated stale-result/action streaks and exempts waiting tools; Goal verification separately bounds repeated disputed completion claims. This addresses a real failure shape more precisely than one repeated-call counter. Fingerprints remain a heuristic: changed noise can look like new information, and different useful work may still repeat commands (evidence_ledger.py, lines 1–47, 56–85, 112 onward; goal_runtime.py, lines 23–39, 469–565).
  6. Snapshot-based extensible composition without merging permissions into personas. Presets persist by value while Skills resolve fresh immutable Turn context; provider route and execution authority remain independent. This permits role reuse and hot-added knowledge without silently changing a running Turn's instructions or granting a role extra system privileges. It would help extensible Wingman profiles, but central organization policies and profile migrations still need an explicit design (agent_presets, lines 19–33; agent_setup.py, lines 519–522; skills/runtime.py, lines 46–63).

Practical fit and build/adapt boundary

Use directly or study closely: native model/tool execution, local per-session coding workspaces, canonical transcripts and forks, immutable security/execution snapshots, durable approvals, stream/event projection and replay, local concurrency fencing, worktree-based delegation, Goal/check/reviewer mechanisms and automation scheduling. These cover much of the difficult individual-agent harness and detailed-session visibility that Wingman describes.

Adapt: map Butler/ProjectMaster/ProductMaster/TechMaster/workers to durable organizational IDs and explicit sessions rather than temporary child names. Add tracker/chat tool adapters through the existing MCP/tool interfaces, and associate product scope, tickets, decisions and evidence with session/Turn IDs. Use presets for reusable role composition and repository directives for project knowledge, while adding organizational policy and role responsibility records. Decide whether native DeepCode providers or external Codex backends satisfy the requirement for real Codex agents; external children currently lose native conversational collaboration. Preserve DeepCode's safety and persistence contracts instead of bypassing them with ad hoc shell orchestration.

Build these capabilities above or beside DeepCode:

  • Telegram Butler with conversation/project correlation.
  • Product-aware intake and continuity.
  • Shared ProjectTracker with assignees, dependencies, and blockers.
  • Agent directory, team membership, and product/technical leadership.
  • Shared rooms, peer communication, and discovery/clarification ownership.
  • Periodic portfolio supervision and acceptance/delivery orchestration.
  • Executive summaries and linked individual timelines.
  • Host-aware Mac/Endeavour execution.

The Project object and sidebar can support navigation. They do not implement these organizational workflows.

A practical architecture would expose DeepCode as a local worker service on each execution host and put Wingman's organization, tracker, rooms, Telegram and executive views in a separate control plane. That is an integration proposal, not a capability found in the checkout. Multi-host routing, remote authentication, artifact/source access, worker liveness and ownership require a new protocol; sharing its SQLite files between machines would not be an evidenced or sound substitute for that work.

The assessment therefore favors DeepCode as a harness/workbench building block, especially if model-provider flexibility and research reproduction matter. Rebranding it as Wingman would leave the central organizational experience unimplemented. The fit is stronger for the bottom layer of the architecture than for the human-facing organization.
